# Каркас документа «Архитектура решения человеческим языком»

Полный аннотированный шаблон для `plans/architecture/YYYY-MM-DD-<имя>.md`. Это второй слой скилла `solution-blueprint` — читай, когда уже пишешь документ. Эталон-образец из корпуса: `plans/analysis/2026-06-28-day-company-daily-brief-blueprint.md` (владелец делал этот формат руками; здесь он кодифицирован).

Калибруй объём: правка на один экран — короткий документ (что есть → что делаем → один макет было→стало → одна развилка). Новая фича на несколько экранов — полный каркас. Документ для **человека** — лучше короче и яснее, чем полно и нечитаемо.

---

## Frontmatter (целевой)

```yaml
---
type: architecture
status: draft            # draft → approved ТОЛЬКО после явного «да» владельца
feature: <kebab-имя>     # совпадает с feature анализа и будущего ТЗ — по нему tz-author найдёт файл
date: YYYY-MM-DD
owner: <кто одобряет — владелец>
relates_to:
  - plans/analysis/YYYY-MM-DD-<имя>.md   # вход-анализ, если был
  - plans/tz/YYYY-MM-DD-<имя>.md          # путь будущего ТЗ (резервируем имя)
  - second-brain/01_projects/<feature>.md # профильная заметка
  - plans/analysis/<имя>-prototype/index.html # прототип-эталон, если есть
approved_at:             # YYYY-MM-DD при approved; пусто пока draft
---
> Что это: <одно предложение, что строим>. Для кого: <роль человеческими словами>.
> Цепочка: анализ `plans/analysis/...` → **эта архитектура** → ТЗ `plans/tz/...`
> Статус согласования: <дата, когда владелец одобрил, или «ожидает одобрения»>
```

`feature` — критичен: `tz-author` ищет архитектуру по совпадению этого slug. Держи единым через анализ → архитектуру → ТЗ.

## Разделы документа (по порядку)

### 1. Что это и зачем
Одно-два предложения сути + кто страдает сегодня и как. Роли — человеческими словами («руководитель», «гость встречи», «уходящий сотрудник», «админ компании»), не «host/CEO/tenant-admin». Боль конкретная.

- ✅ «Руководитель при входе видит сетку из ~10 виджетов-цифр — числа без истории. Не понимает, как прошёл день, пока не полистает и не посчитает в уме.»
- ❌ «Дашборд имеет низкую usability и требует cognitive load для интерпретации метрик.»

Метафора, выравнивающая образ, тут уместна: «разворачиваем экран на 180° — сверху рассказ, цифры вниз».

### 2. Как сегодня (от чего отталкиваемся)
Текущее поведение/функционал простым языком — это «какой был функционал» из запроса владельца. Из baseline (vexp), но **без имён сервисов/таблиц/эндпоинтов**. Цель — владелец понимает стартовую точку и масштаб изменения.

- Если что-то уже частично работает, но спрятано/сломано — скажи прямо («таблица план/факт уже есть, но недостижима с главного экрана»). Это бережёт от «переписать то, что есть».

### 3. Что делаем (решение простыми словами)
Суть решения. Что меняется для пользователя. Расширяем существующее или делаем новое — назови честно (это масштаб для владельца). Без «как» на уровне кода.

### 4. Как это будет выглядеть (ядро — три приёма)

#### 4а. Сценарии «было → стало»
Для каждого ключевого пути. Шаблон:

```
**Сценарий: <название пути, человеческими словами>**
- Было: <что пользователь делает сейчас> → <что видит> → <чем недоволен>.
- Стало: <что делает> → <что видит> → <какой исход/польза>.
```

Один сценарий = один пользовательский путь. Не «функция X» — а «пользователь хочет Y».

#### 4б. ASCII-макеты экранов
Грубые текстовые рамки для всего с UI. Состав и расположение, не цвета/шрифты. Рисуй и состояния (пустое/ошибка/загрузка), если меняют смысл. Пример:

```
┌──────────────────────────────────────────────┐
│  ⚠️ День с трением            Пятница, 27 июня │   ← обложка-вердикт
│  ┌─Команда─┐ ┌─Клиенты─┐ ┌─Исполн.─┐ ┌─Общий─┐ │
│  │ 🟢 Норма│ │ 🔴 Риск │ │ 🟡Букс. │ │🟡Трен.│ │   ← 4 оси-светофора, каждая «почему» одной строкой
│  └─────────┘ └─────────┘ └─────────┘ └───────┘ │
├──────────────────────────────────────────────┤
│  [ Читать полный отчёт за день ▾ ]             │   ← одна кнопка, разворачивает письмо
├──────────────────────────────────────────────┤
│  Цель и компас      ▸ к цели сегодня +3/10     │
│  Зависшие задачи ↔ кто просрочил  (клик→фильтр)│
│  [Показать цифры ▾]   ← старые виджеты уехали   │
└──────────────────────────────────────────────┘
```

Подпиши стрелками `←` что есть что и что меняется при действии. Цель — владелец ткнёт «вот этого тут быть не должно» / «а где X».

#### 4в. Живой образец (золотой пример)
Где применимо (отчёт, письмо, чат-ответ, экран с контентом) — **конкретный заполненный пример реальными словами**, не «тут будет текст отчёта». Эталон — раздел «Пример отчёта» в `day-company-blueprint`:

```
**⚠️ День с трением** · Пятница, 27 июня 2026
_Команда в норме, но день держат две вещи: «Молочные реки» 2-й раз
написали про молчание поддержки (риск ухода), а интеграция снова
сдвинулась из-за неоплаченных коннекторов._

- Команда — Норма · настроение зелёное (5/6), Айназ не сдала отчёт
- Клиенты — Риск · «Молочные реки» — 2-е упоминание молчания
...
```

Живой образец ловит несоответствие тона/состава мгновенно — это сильнейший антидот к «не то имел в виду». Тон бери из `06_marketing/` (как мы говорим о продукте).

### 5. Делаем поверх существующего (масштаб своими словами)
Главный вопрос владельца — «это большая стройка или небольшое расширение?». Ответь человеческим языком: «это расширение того, что уже бежит каждую ночь — новых умных частей не плодим» ИЛИ «новый раздел с нуля». Можно перечислить, что переиспользуем — но **названиями-функциями для человека** («существующий ночной сбор отчёта», «готовые AI-отчёты встреч»), без листинга Prisma-полей. Глубокий reuse-маппинг (`path:line`, имена сервисов) — добирает `tz-author` сам через vexp; здесь — только масштаб и принцип «не плодим лишнего».

### 6. Границы — что НЕ делаем
Простыми словами, что осознанно за рамками — чтобы владелец не ждал лишнего. Каждый отложенный кусок — с короткой причиной и (если знаешь) «на потом». Это вход в `Scope: не входит` ТЗ.

- «Деньги/финансы в отчёт пока не берём — нет источника данных. Отдельной задачей позже.»

### 7. Решения, которые я принял за тебя (+ почему)
Продуктовые развилки, закрытые тобой (на основе анализа/кода/рекомендации). Таблица:

| # | Решение | Почему так (человечески) |
|---|---|---|
| Р1 | Недельный отчёт сводим из 5 дневных, а не пересчитываем неделю заново | Дёшево; то, что ты уже читал по дням, не разойдётся с недельным итогом |

Владелец читает и может возразить — это дешевле, чем поймать на коде. Развилку, которую закрыл анализ рекомендацией, перенеси сюда простыми словами.

### 8. Что реши ты (открытые развилки)
Только **реальные продуктовые** развилки (меняют что видит/делает пользователь И не решаемы за владельца обоснованно). Каждая — с рекомендацией:

> **Тон письма Коры: сухо-деловой или «личный COO»?**
> Рекомендую «личный COO» (как в образце выше) — он держит внимание и отражает позиционирование «операционный директор», а не «отчёт-выгрузка». Не так — поправь.

Технические развилки («расширять сервис или новый», «sync vs очередь») сюда НЕ выноси — это `tz-author`.

### 9. Как поймём, что получилось (глазами пользователя)
Критерий «сделано» так, как его проверит человек, не машина:
- «Руководитель за 30 секунд после входа понимает, как прошёл день, не листая виджеты.»
- «Гость заходит на встречу по ссылке без регистрации и сразу видит видео.»

Это вход в acceptance ТЗ — `tz-author` переведёт в машинные предикаты (что грепать, какие тесты). Здесь — человеческий исход.

### 10. Связи
Ссылки: вход-анализ, путь будущего ТЗ, прототип-эталон, профильная second-brain. Одной строкой «дальше → ТЗ `plans/tz/...`».

## Протокол точки одобрения (draft → approved)

1. Документ дописан, `status: draft`.
2. В чат — **короткое резюме** (3–6 строк), не пересказ файла: что строим · как выглядит одной фразой · главные решения за владельца · что осталось решить ему. Ссылка на файл за деталями.
3. Явный вопрос: «Это то, что ты имел в виду? Одобряем или правим?» + открытые развилки Шага 8 батчем (с рекомендациями), через `AskUserQuestion` или текстом.
4. Реакция владельца:
   - **«да / одобряю»** → `status: approved` + `approved_at: <дата>`; назови путь ТЗ; скажи, что `tz-author` теперь возьмёт архитектуру.
   - **правки/возражения** → внеси в документ, покажи снова, остаёшься в `draft`.
5. **Никогда не ставь `approved` сам.** Это «решение владельца» (необратимо влияет на продукт). Автономия из `implement-autonomously-prove-and-proceed` — про реализацию, не про продуктовое одобрение замысла.

## Человеческий язык vs жаргон (грепни перед показом)

| ❌ Жаргон (провал звена) | ✅ Человеческий язык |
|---|---|
| «Добавляем эндпоинт `GET /digest` с Zod-DTO» | «Главный экран начнёт показывать готовый отчёт за день» |
| «Расширяем модель `WeeklyOperationsDigest` тремя JSON-полями» | «К недельному отчёту добавляем вердикт, письмо и компас к цели» |
| «Синтез через map-reduce, один LLM-проход, persist снапшота» | «Кора сжимает каждый источник отдельно, потом собирает связный рассказ и запоминает его» |
| «Виджет осиротел: зарегистрирован в пресетах week/month, но canvas прибит к rhythm=today» | «Таблица уже построена, но до неё нельзя добраться с главного экрана» |

Допустимое исключение — раздел 5 «делаем поверх существующего», где краткое упоминание «что переиспользуем» функциональными именами помогает владельцу понять масштаб. Везде ещё — перевод обязателен.

## Антипаттерны каркаса
- **Документ-отчёт вместо документа-решения** — пересказал анализ, но не показал «как будет выглядеть». Владельцу нужно увидеть результат, а не прочитать исследование заново.
- **Пропущенный живой образец** там, где есть контент (отчёт/письмо/экран) — абстрактное описание не ловит рассинхрон тона.
- **Технические развилки, вынесенные владельцу** — он не должен решать «sync или очередь».
- **approved без явного «да»** — ломает весь смысл звена.
- **Дубль анализа** — копипаст разборов вместо ссылки и выводов.
