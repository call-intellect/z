# Интерактивное публичное демо кабинета Коры (витрина для сайта)

## Что было поставлено
Владелец: прототип редизайна кабинета (`plans/analysis/2026-06-13-cabinet-redesign-prototypes/`) — статичный HTML, всё внутри экранов декоративно. Нужно сделать из него эффектную **интерактивную витрину для сайта**, где потенциальный клиент «потыкает»: каждая вкладка открывается, drill-down по карточкам, «в два раза больше что нажать», чат «Спросить Кору» по базе знаний продукта, богато выдуманная компания. Сначала ТЗ (`tz-author`), затем реализация (`tz-orchestrator`). По ходу владелец срезал лишнее: гид-тур/welcome/сброс/бейдж «Демо» — НЕ делать («просто показываем прототип»).

## Как решал
- **ТЗ** `plans/tz/2026-06-14-public-demo-cabinet-interactive.md` (+orchestrator-prompt), 9 фаз. 4 развилки закрыты владельцем: standalone-статик · отдельная демо-копия · мобилка синхронно · чат офлайн-скрипт по KB.
- **Реализация** на ветке `feature/public-demo-cabinet`, фаза за фазой суб-агентами, приёмка каждой через Playwright (локальный node-статик-сервер :8822, `file://` блокируется харнессом). Итог в `plans/analysis/2026-06-14-public-demo/`: `index.html`+`mobile.html`+`design-system.css`+`app.js`+`demo-data.js`+`README.md`.
- Архитектура: единый делегированный движок `data-action` в `app.js` (overlay/tabs/toast/filter/chat), данные и база знаний — в `demo-data.js` (`window.DEMO`). Никаких фреймворков, бэкенда, сети.

## Что вышло (верификация)
Все Ф0–Ф8 зелёные, проверены лично в браузере: 17 вкладок-переключателей + реальная фильтрация tasks/feed; drill-down встреч (транскрипт+AI-отчёт), задач, решений (очередь «Принять» синхронно гасит 3 счётчика), людей/отделов/клонов роли (мини-чат по образцам); чат «Спросить Кору» (28 Q&A, цитаты→встреча, fallback); мобилка — единый интерактивный телефон; светлая/тёмная темы читаемы; консоль без ошибок. 11 коммитов, ветка запушена. Прод-операций нет (чистая статика).

## Чему научился
- **`_parts/`+`build.mjs` прототипа 2026-06-13 рассинхронизированы** — собранный `index.html` (3455 строк) богаче `_parts/` на ~228 строк (тема + контент жили только в собранном файле; есть 11-й экран `feed`). `node build.mjs` ЗАТИРАЕТ ручные правки. Поймал это при разведке (случайно запустил build, восстановил из git). Урок: перед доверием build-пайплайну проверить, воспроизводит ли он закоммиченный артефакт (`node build.mjs` + `git diff`). Для демо-копии split вообще выкинул — один index.html + внешние app.js/demo-data.js, дрейфа нет.
- Суб-агент при картографии данных правильно **разошёлся с подсказкой в ТЗ** (я написал «Дмитрий Смолин/Руководитель разработки», а на экране «Команда» реально «Дмитрий Соколов/Руководитель внедрения») — приоритет «данные совпадают с тем, что показано пользователю» дал верный результат. В ТЗ-подсказках по данным лучше писать «сверь с экраном», а не диктовать имена по памяти.
- Playwright MCP под `file://` блокируется харнессом — поднимал свой node-静ик-сервер для приёмки; держать один порт на всю сессию удобно (перезагрузка после правок агента).
- Generic-механизмы окупились: один `data-action`-делегатор + один `activateTab` + один `applyFilter` покрыли 11 экранов без точечных хендлеров — «чини класс, не кейс».
