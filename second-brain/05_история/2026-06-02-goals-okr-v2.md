# Goals OKR v2 (Граф целей) — Фазы 0–5

## Что было поставлено

Реализовать ТЗ [`plans/tz/2026-06-02-goals-okr-v2.md`](../../plans/tz/2026-06-02-goals-okr-v2.md) целиком — превратить плоский список целей (`goals` модуль) в **граф целей**: двухуровневую OKR-надстройку (Цель → измеримые Key Results), где цель рождается двумя равноправными путями (авто из встреч + руками), выстраивается в дерево «главная → подцели», обновляет прогресс сама из родных источников, и подсвечивается еженедельным «пульсом». Ключевое решение владельца — **M0 (ручной контроль первичен)**: авто это удобство поверх ручного слоя, AI никогда не перетирает поле, отредактированное человеком.

6 фаз, строго последовательно, с верификацией между ними.

## Как решал (фазы → коммиты)

Роль агента-оркестратора: фазы вели кодящие суб-агенты, я закрывал развилки, верифицировал результат (grep маркеров, re-Read, typecheck, тесты) и двигался дальше.

- **Фаза 0** `40d5ee3` — модель данных: расширен `Goal` (source/promotionState/progressStatus/sourceBlockIds/confidence/manualOverride/bitemporal+supersede/relations), новые `GoalKeyResult`+`GoalKeyResultCheckpoint`, FK `Idea.goalId`/`Cycle.primaryGoalId`, 4 enum'а, GIN-индекс `Goal_sourceBlockIds_gin` (postgres-init.sql), RBAC `goal_key_result`, `backfill-goal-v2-defaults.ts` (+ STEPS apply-prod-deploy).
- **Фаза 1** `2f7f672` — ручной слой M0: `GoalKeyResultsService` (CRUD KR + checkpoint при ручном currentValue), `goals.service.supersede`, reparent с `assertNoCycle`, `mergeManualOverride`; KR-эндпоинты + supersede; фронт секция KR + reparent/supersede диалоги + маркер «Предложено Корой». 24 backend + 9 frontend тестов.
- **Фаза 2** `e9bc21d` — авто-добыча: воркер `specialist-3-14-goals.worker.ts` (очередь `core.specialist-routing`) + сервис (extract→KNN→hierarchy-арбитр→create), промпты `goal-extract`/`goal-hierarchy-link`, RouterService `SPECIALIST.GOALS`, seed `seed-llm-task-routes-goals.ts`, 15 golden-фикстур.

- **Фаза 4** `ab82f9a` — пульс + дерево: модель `WeeklyGoalsPulseDigest`, `GoalsPulseService` + cron (`0 6 * * 1` = пн 09:00 МСК), доставка через `ConversationalService` eventType `goals.pulse`, дашборд `goalsTree`/`goalsPulse`, фронт виджет «Пульс целей» + дерево + переключатель Список/Дерево.

## Что вышло (верификация)

- Все 6 фаз: **typecheck / lint / build / vitest зелёные** (backend 182 тестов после Ф4, +фронт).
- **Ключевые решения оркестратора:**
  - триггер специалиста = `commitment` + `plan_item` (НЕ `decision` — иначе двойная обработка со специалистом 3-3);
  - dedup → promote существующей `suggested` (не плодим дубль); `promotionState='suggested'→'active'` при `confidence≥0.8` или повторе;
  - cap = 7 active+suggested целей на горизонт (антиплодёж);
  - `manualOverride`-поля авто никогда не трогает (M0 прошит и в специалист, и в авто-прогресс);
  - `metric_entity` → `Entity.mentionsCount` (best-effort — у Entity нет числовой value/score);
  - пульс — клон COO-дайджеста, cron пн 09:00 МСК, идемпотентность `(tenantId, isoWeek)`;
  - probe при `idea.status='shipped'` только **предлагает** обновить KR, не пишет автоматически (outcome требует подтверждения).
- Реализация — достройка на готовой архитектуре (специалист Слоя 3 + расширение Goal + переиспользование COO-дайджеста и дашборд-виджетов), не переписывание.

## Чему научился / грабли

1. **tsc ловит `mock.calls[0][0]` под `noUncheckedIndexedAccess`, а vitest — нет.** Доступ к индексу массива моков в тестах проходит рантайм vitest, но валит `bun run typecheck`. Вывод: после каждой фазы прогонять typecheck **отдельно** от тестов — зелёные тесты не гарантируют зелёный tsc. (Кандидат в `code-pitfalls.md`.)
2. **У `Entity` нет числовой метрики кроме `mentionsCount`.** При проектировании `metric_entity` sourceKind ожидалась реальная value/score сущности — её нет. Пришлось ограничиться `mentionsCount` как best-effort прокси и явно задокументировать долг, а не делать вид, что это полноценная метрика KPI.
3. **`horizon` не отдавался в response DTO целей.** На Фазе 1 обнаружилось, что `GoalListItemDto`/`GoalDetailDto` не возвращали `horizon`, а он нужен дереву Фазы 4 для группировки по горизонтам. Зафиксировали как «заметку для Фазы 4», supersede-диалог временно дефолтил горизонт на quarterly. Урок: при проектировании response DTO сразу класть поля, которые понадобятся последующим фазам визуализации.
4. **`ChartTone` беднее, чем набор статусов.** `progressStatus` имеет 5 значений, а `ChartTone` не содержит `info`/`sand` — пришлось маппить `achieved→accent`, `dropped→neutral` (ближайшие валидные тона), а не вводить новые токены под одну фичу.
5. **Параллельные сессии в общем репо.** Всё время шли чужие коммиты (smart-tables, expert-clones, action-center) и untracked-файлы в `plans/`. Коммитил только свои пути явным `git add`, проверял `git status` перед каждым коммитом. См. [[feedback_parallel_sessions_git_check]], [[feedback_git_index_hygiene]].
