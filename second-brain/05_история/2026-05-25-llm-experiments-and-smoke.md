# Рефлексия — серия LLM-экспериментов, golden, smoke 28 агентов, ТЗ-копилка

## Что было поставлено

Сессия началась с handoff-документа от предыдущей сессии: три эксперимента (sales-merge, dialog, specialists) были уже частично сделаны. Задачи на сегодня:

1. Закрыть оставшееся в эксперименте 3: судья Б+ vs Г (специалисты knowledge-core).
2. Провести эксперимент 4 (operations) — 3 гипотезы: weekly-digest, checkin-sentiment batch, кэш-префикс на малых.
3. Зафиксировать архитектурные решения в едином ТЗ-документе («копилка»).
4. Провести golden-прогон skill-trait-detect (gpt-5.4 vs deepseek-v4-pro) — выяснить, можно ли переключить чувствительный агент.
5. Описать «как работает клон сотрудника», обсудить эволюцию: память диалога, доступ через галочки, два режима, маркетплейс.
6. Прогнать smoke-тесты всех 28 непокрытых LLM-агентов проекта.

## Как решал — конкретно

### Эксперимент 3 — судья Б+ vs Г

Написал [judge-specialists-bplus-vs-g.ts](../../backend/scripts/eval/judge-specialists-bplus-vs-g.ts) — отдельный судья, потому что Б+ и Г работают на 8 типах сущностей (5 типов у старого судьи). Результат: Б+ выиграл 18:13. Главные дефекты Г: галлюцинация (blk_032 использован дважды), пустые поля, поверхностные альтернативы. Подтверждено: один объединённый вызов выигрывает не только по экономике, но и по качеству.

### Эксперимент 4 — operations

Создал 5 runner-скриптов + судью для weekly-digest. Команда из эксп.3 (Иван, Анна, Дмитрий, Виктор) использована в фикстуре для сюжетной связности. Результаты:

- **Weekly-digest:** Б (LLM-агрегация) ГАЛЛЮЦИНИРОВАЛ — придумал дедлайн «6 июня», спутал день. Судья дал Б больше баллов по глубине, но назвал победителем A — точность критичнее. Решение: оставляем код-агрегатор.
- **Checkin-sentiment:** Batch (10 за вызов) выиграл в 2× по цене, 100% точность vs 96%, на 20% быстрее. Заодно нашёл КРИТИЧЕСКИЙ БАГ в проде: текущий `max_tokens: 300` на DeepSeek-Pro даёт 56% пустых ответов (thinking-токены съедают лимит).
- **Кэш-префикс на малом:** работает — 83-87% hit даже на коротком system 254 токена. Расширение system до 901 токена с 5 примерами даёт +4 пп точности за +22% цены. Опционально.

### Golden skill-trait-detect

Написал [run-skill-trait-detect-golden.ts](../../backend/scripts/eval/run-skill-trait-detect-golden.ts), который поддерживает обе модели (DeepSeek через chat.completions, OpenAI gpt-5.4 через Responses API). Результат: DeepSeek-Pro **96%** vs gpt-5.4 **92%**, в 4.5× дешевле. Переключение подтверждено.

### Описание клона + эволюция (§9 копилки)

Долгий продуктовый разговор. Зафиксировано 10 решений:
- Доступ только через галочку главного админа (носитель и руководитель не видят автоматически).
- Два режима ответа: factual (с цитатами `[BLOCK:id]`, temperature 0.2) и judgmental (без цитат, «я считаю», temperature 0.7) — выбираются автоматически через `dialog-classify`.
- Подключить полный `dialog-layer` (contextualize + multi-query + summarize) к `clone-respond`.
- Новый промпт `dialog-multi-query-clone` — расширяет вопрос аналогиями.
- topic-density guard сохранить, но в judgmental ослабить (min 1 блок).
- Маркетплейс клонов с карточками, видимость по галочкам.
- Кнопка «Новый диалог» как в ChatGPT.
- Историзация (клон должности живёт после ухода сотрудника) — отдельная фаза, юр-вопрос снят: «клон должности, не клон личности».

Пользователь два раза поймал меня на упрощениях: сначала я ошибочно сказал что chat-v2 — одиночный вызов (на деле 5 LLM в dialog-layer + 1 финальный + 1 cron summarize). Это **самая важная находка сессии** — я смотрел только в chat-v2.service.ts, а «умная часть» вынесена в отдельный модуль `dialog-layer`.

### Smoke 28 агентов

Использовал 4 параллельных general-purpose subagent в background. Каждому — список из 7 taskType, инструкция читать `*.prompt.ts` (или встроенные константы из сервисов), создавать минимальную фикстуру, писать runner по образцу `run-variant-b-single.ts`, запускать. Один батч (Batch 3) пришёл с неполным отчётом — субагент сам запустил под-агентов и не дождался. Перепроверил по диску — все артефакты есть, один `executable-persona-compile` пропущен, догнал вручную.

Результат: 28/28 OK, $0.036 суммарно. 3 системные находки:
1. `role-profile-build` — обрезался на max_tokens=6000 → поднял до 16000.
2. 5 промптов «встроены в сервисы», не в `prompts/` (block-distill, block-linker, theme-classify, reframing, entity-merge-arbiter).
3. Два паттерна на Pro: «структурный» (tools+auto) для большинства, «текстовый» (без tools) для 4 агентов.

## Чему научился (для дистилляции)

### 1. ВСЕГДА читать сервис до утверждений про архитектуру
Пользователь поймал меня на «chat-v2 — один LLM-вызов» — я смотрел только chat-v2.service.ts. На деле dialog-layer вынесен в отдельный модуль с 5 LLM-вызовами. Урок: для разговорных AI — проверять есть ли pre-processor / dialog-layer вокруг.

### 2. Многошаговая память диалога — это паттерн, который применим везде
chat-v2 имеет полный pipeline (contextualize + confidence + classify + multi-query + summarize + final), а clone-respond и concierge-respond — нет. Это потенциал для развития: подключить тот же dialog-layer к clone-respond — большой gain в качестве длинных диалогов.

### 3. Smoke-test через subagents — рабочая модель, но с нюансом
4 параллельных subagent в background ускорили работу в ~4 раза. Но один из них «забыл» дождаться своих под-агентов и вернул неполный отчёт. Урок: **после возврата subagent перепроверять артефакты на диске**, не доверять только summary.

### 4. max_tokens на thinking-моделях — частый источник тихих падений
Дважды наткнулся: `checkin-sentiment max_tokens: 300` → 56% пустых ответов; `role-profile-build max_tokens: 6000` → обрыв JSON. Урок: **при миграции на любую thinking-модель — аудит max_tokens — обязательный шаг**. Минимум 1500, для длинных текстов — 8000-16000.

### 5. «Юридический вопрос» иногда не нужно создавать
Я добавил в §9.10 секцию «согласие сотрудника», «KEEP_ARCHIVED_CLONES_AFTER_LEAVE», «анонимизация». Пользователь снял её: «мы создаём клон ДОЛЖНОСТИ, не личности — персональных данных там нет». Урок: спрашивать про юридический контекст до того как делать секции про согласие. Это снимает целую фазу без потерь.

### 6. Index hygiene — критично при параллельных сессиях
Перед моим коммитом в индексе было 16 staged файлов от параллельной сессии (модуль `feedback/`). `git restore --staged` снял их перед моим коммитом. Урок зафиксирован в памяти давно, но впервые столкнулся с проблемой реально — `git status` показал staged ВСЁ, что могло привести к катастрофе если бы я просто `git commit -am`.
