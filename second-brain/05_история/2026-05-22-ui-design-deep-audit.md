# 2026-05-22 — Глубокий UI/UX design audit Z

## Что было поставлено

Собственник проекта попросил провести глубокий аудит интерфейса Z по линии «data-heavy admin» (Mixpanel / Amplitude / Cloudflare Dashboard) — для двух кабинетов:

1. **Org-кабинет** (то, что видит клиент Z).
2. **Z-Admin** (то, что вижу я как собственник платформы — все 10+ компаний, экономика, эксперименты, health).

Контракт: записывать **все варианты с tradeoffs**, не выбирать одно решение — это банк альтернатив для будущих ТЗ. Объём не ограничен. Не останавливаться на уточнения.

## Как решал

### Этапы

1. **Сбор фактуры — 3 параллельных стрима** (через subagents):
   - Стрим A: инвентаризация текущего фронта Z (65+ маршрутов, AppShell, design system, 12 design-system гэпов).
   - Стрим B: UX-материалы из `delivery/06-ux-ui.md`, `delivery/13-glossary.md`, `delivery/ui/copy-strings.ru.md`, `second-brain/06_marketing/positioning.md`.
   - Стрим C: разбор эталонов Mixpanel / Amplitude / Cloudflare (через WebFetch/WebSearch — пользователь разрешил интернет на этом этапе).

2. **Outline аудита** — фиксировал в чате, согласовывать не пришлось (пользователь сказал «иди сам»).

3. **Раздел 4 (Design language)** — обнаружил **критический баг**: light-mode mint `#14b8a6` на белом даёт контраст 2.5:1, не проходит WCAG AA (нужно ≥4.5:1 для текста). Dark-mode mint `#5eead4` на `#0a0e14` — 13:1 (AAA). Зафиксировал как Priority 0 fix.

4. **Раздел 5 (Архитектурные решения)** — 10 развилок с вариантами и tradeoffs (двойной Z-Admin, реструктуризация Director Dashboard, унификация Empty/Loading/Error, ...).

5. **Раздел 6 (Per-screen)** — глубоко разобрал 12 экранов (6 Z-Admin + 6 Org-кабинет). Для каждого: текущий wireframe, проблемы (10–16 на экран), рекомендации с ASCII-wireframes, состояния (empty/loading/error/over-loaded), мобильная адаптация (360/480/768/1024/1280), действия и иерархия, контракт API, альтернативы. Перед каждым экраном — читал реальный код (Read tool) для реалистичного «текущего состояния».

6. **Раздел 7 (Cross-cutting)** — 15 улучшений уровня design system (Breadcrumbs, FilterPanel, DataTable, LoadingButton, Charts, OrgSwitcher, CommandPalette, Sonner миграция, иконки, motion, ...).

7. **Раздел 8 (Action items)** — ~50 пунктов в 4 приоритетах (P0 блокеры, P1 для Фазы 0, P2 после, P3 на γ). Все 12 design-system гэпов из стрима A покрыты ссылками на конкретные приоритеты.

8. **Разделы 9–11** — отложенное, связи с другими документами, TLDR.

### Главные находки

2. **Z-Admin раздвоен** (`/(authenticated)/admin/*` + `/(admin)/admin/*`) — описан план миграции в 5.1.
3. **Director Dashboard перегружен 10 виджетами** — рекомендация Hero KPI + Collapsible Sections в 5.2 и 6.2.1.
4. **`/admin/orgs` критическая боль:** нет sorting / pagination / status filters, inline tier-dropdown = риск опечатки.
5. **`/admin/health` без LLM providers** — самое нужное super_admin отсутствует.
6. Многие экраны Фазы 0 **уже реализованы в коде** — фокус аудита сдвинулся с «что добавить» на «как поднять качество».

## Чему научился

### Технические уроки

1. **Стримы через subagents работают отлично для широкой инвентаризации.** Три параллельных стрима (внутренний код / внутренние материалы / внешние эталоны) собрали фактуру за 5 минут вместо часа последовательной работы.

2. **Перед per-screen анализом — обязательно читать реальный код.** Я делал Read для каждого экрана. Это убирает риск «гипотетических» рекомендаций — wireframe «текущего состояния» строится по факту, не по памяти.

3. **WCAG-контраст можно считать на лету** (формула с linearization sRGB → relative luminance → ratio). Это поймало баг в tokens.css, который мог бы остаться незамеченным до WCAG-аудита перед релизом.

4. **Cross-engine файл с состоянием контекста** — TodoWrite сильно помогает в многоэтапной работе. Без него я бы потерял track «где я».

### Процессные уроки

5. **«Иди сам, записывай все варианты»** — это очень мощный режим работы для аналитики. Пользователь снял с меня нагрузку «согласовывать каждую развилку», но потребовал зафиксировать tradeoffs. В итоге документ стал в 3 раза больше, чем планировался изначально, но это правильно — банк альтернатив, который потом превращается в ТЗ.

6. **ASCII-wireframes — рабочий инструмент.** Не нужны pixel-perfect mockups для аналитики. Box-drawing characters + псевдо-таблица передают иерархию информации, состояния, mobile-адаптацию. Это быстрее и читаемее, чем описание текстом.

7. **Per-screen unified structure** (текущее → проблемы → рекомендуемое → состояния → mobile → API → альтернативы) — даёт согласованность по 12 экранам и упрощает написание sub-TZ потом (можно копировать секции по шаблону).

### Доменные уроки про Z

8. **Z уже сильно дальше, чем я предполагал по плану.** Аналитика ЛК Фазы 0 фактически реализована: `/structure`, `/documents`, `/roles`, `/me`, `/dump`, wizard `/onboarding/company/*`, OrgSwitcher, CommandPalette с поиском по новым сущностям, Sidebar в 3 группы, coming-soon-страницы γ. Аудит должен это учитывать.

9. **Z-Admin визуально не отделён от Org-Admin** — оба в подгруппе «Админка» в Sidebar. Это «архитектурный шов»: пользователь (собственник платформы) не сразу понимает, что переходит между кабинетами. Зафиксирован как развилка 5.6 (отдельная топ-секция Sidebar + danger-color + Shield icon).

10. **Принцип «память не контроль» исключает целый класс паттернов эталонов** (лидерборды, push о просрочках, очки). Это нужно держать в голове при дизайне дашбордов — иначе скатимся в Mixpanel-style engagement-нудж, что противоречит позиционированию Z.
