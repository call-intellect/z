## РЕШЕНИЯ ВЛАДЕЛЬЦА по 3 развилкам (зафиксированы — кодируй строго по ним)

### ① Д1 — консолидация одноимённых сущностей разных типов → **Вариант B** (НЕ A)
- Тип ОСТАЁТСЯ в идентичности, но добавить **кросс-типовой проход**: снять type-фильтр в **выборке кандидатов**
  (там, где сейчас KNN/выборка ограничена тем же типом — `entity-merge.service.ts:201`, cron-пары,
  `entity-merge-arbiter.prompt.ts:5` «один кандидат того же type»), чтобы одноимённые разных типов попадали в пул.
- **Арбитр** (LLM) решает по существу: «tech-Битрикс + vendor-Битрикс = один объект → merge», но
  «проект „Портал“ ≠ продукт „Портал“ → keep». Обязательно давать арбитру **тип каждого кандидата в контекст**.
- Гейт кросс-типового прохода — **строгое совпадение имени** (exact/нормализованное), НЕ fuzzy.
- Предохранители сохранить: negative-cache, person-инвариант (`type='person'` не мёржить кросс-типово), откат порогом.
- Отдельно — **детерминированный `client→customer`** (deprecated-enum, `schema.prisma:504`): чистая безопасная нормализация.
- ❌ НЕ вариант A (убрать тип из идентичности совсем) — риск тихого пере-слияния разных объектов.

### ② Д1 — канонический тип при мёрже + сабрекорды → **матрица + арбитр + ОБЯЗАТЕЛЬНАЯ миграция сабрекордов**
- Канонический тип: **матрица приоритетов** (customer > client; domain-specific > generic) для очевидного;
  где спорно (customer vs vendor у «Логистик Плюс») — арбитр.
- **Сабрекорды 1:1 (Vendor/Customer) ОБЯЗАТЕЛЬНО перецепить на каноническую сущность** — НЕ оставлять
  сиротами и НЕ ограничиваться `warn`. Использовать/расширить единый `EntityMergeService.mergeEntities`
  (он уже мигрирует `IdeaBlockEntity`/`EntityLink`/`SourceEntity`/`ThemeEntity`/`Card`/`Person` — добавить
  Vendor/Customer). **Причина жёсткости:** оставленные сироты сабрекордов — ровно тот класс багов, что уже
  ловили и чинили в Package A (Person↔Entity integrity: NULL-компаньоны составного FK → тихая потеря
  родословной). Повторять нельзя.
- Мульти-тип/роли (у сущности несколько ролей одновременно) — **vNext, НЕ сейчас**, схему не трогать;
  зафиксируй отдельной строкой в реестре не-сделанного.

### ③ Д2 — чистка дедуп-вектора → **Вариант A, ЗАМЕРЕННЫЙ линейкой** (эскалация в C только по данным)
- Корень (подтверждён): дедуп-вектор загрязнён контекст-хедером — в `IdeaBlock.embedding` печётся
  `header + criticalQuestion + trustedAnswer` (`embedding.service.ts:14-23`, хедер = источник/участники/тип/дата).
  Один факт с разных дней → разный хедер → cosine < 0.85 → не кандидат → мгновенный canonical (арбитр не зван).
- **Вариант A:** убрать хедер из эмбеддинга блока (оставить только `criticalQuestion + trustedAnswer`).
- ⚠️ **Вектор двойного назначения:** тот же `IdeaBlock.embedding` читает retrieval (`search.service.ts:301/380`,
  `b.embedding <=> query_vec`), причём запрос эмбеддится без хедера. Значит снятие хедера влияет и на поиск.
- **Порядок:** (1) сделать A; (2) пере-эмбеддить блоки (backfill); (3) **замерить retrieval-recall линейкой
  до/после** (см. ниже). Если retrieval держится/растёт → оставить A. Если **просел** → эскалировать в
  **Вариант C** (два вектора: чистый `dedupEmbedding` для дедупа + контекстный `embedding` для retrieval,
  +колонка/миграция/backfill). НЕ вариант B (снижение порога — не корень, пере-слияние везде).

## Как мерить эффект (когда стенд освободится)

Линейка recall уже построена (dev-only, влита в work): `backend/scripts/eval/run-recall-eval.ts` + gold-набор
`backend/scripts/eval/gold/recall-gold.json`. Она заземлена на **сигнатуры (entity + фразы), не на block-id**
→ переживает пере-сев в свежий тенант. Порядок замера:
1. Пере-извлечь «Стрелу» новым кодом в **свежий изолированный тенант** (свой orgId; не трогай канонический эталон и чужой клон-стенд-тенант).
2. Навести линейку на этот orgId (добавь чистый override, напр. env `RECALL_EVAL_ORG`, с каноническим как фолбэк — `eval-config.ts`).
3. Прогнать `run-recall-eval.ts` (при живом судье — `--judge`) до и после фикса → сравнить отвечено/провал %
   и постадийные метрики. Для ③ это **решающий замер** (не просел ли retrieval).
