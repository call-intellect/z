# Спринты в Z — анализ продуктового концепта и архитектурного встраивания

## 1. Цель документа

Зафиксировать продуктовую концепцию фичи «Спринты» (настраиваемые циклы работы команды) и архитектурное решение, как встроить её в **уже работающие модули** Z (трекер, knowledge-core, livekit, AI-pipeline) — без параллельных контуров, но с одним новым AI-агентом «Помощник по спринтам».

Документ — основа для будущего ТЗ в `plans/tz/`.

## 2. Что хочет владелец (6 продуктовых принципов)

1. **AI не двигает задачи сам.** Помощник не создаёт задачи, не назначает исполнителей, не меняет статусы. Только показывает, читает и подсказывает.
2. **Никаких жёстких ритуалов.** Никаких «понедельник в 9:00», никакой обязательной последовательности встреч. Просто методология «бьём работу на спринты, идём к цели».
3. **Длина спринта — настройка пользователя**, не методология. 1/2/3 недели — на усмотрение того, кто создаёт спринт.
4. **Спринт — гибкая привязка.** Может быть спринт компании, под клиента/поставщика, под отдел, под сотрудника (например, онбординг), под проект.
5. **Задачи добавляются вручную или полуавтоматом.** AI может предложить черновик (через уже работающий механизм извлечения действий из встречи), но человек обязательно подтверждает во входящих. Никаких автоматических созданий.
6. **Подсказки качества — сразу.** Создал задачу без срока — сразу подсказка в трекере. Это не пост-фактум-отчёт, а живая валидация при работе.

**ЦА:** любой бизнес, не только IT-команды. Тезис: «любой бизнес должен идти к цели; чтобы быстрее добежать — идти спринтами».

## 3. Главное открытие анализа: 80% инфраструктуры уже есть

Поход по `second-brain` показал, что спринт почти полностью лежит на уже работающих модулях Z.

### 3.1 Что уже работает (что переиспользуем)

| Элемент | Где живёт | Как используем |
|---|---|---|
| Сущность `Cycle` (цикл) в трекере | `backend/src/modules/tracker/` | **Это и есть спринт.** Привязан к Project, имеет даты, набор задач, endpoint `POST /api/v1/cycles/:id/complete` уже делает автоматический перенос незакрытых задач |
| Сущность `Project` в трекере | `tracker/` | Контейнер спринта. У Project есть шаблон команды (10 шаблонов: продажи/разработка/маркетинг/HR/финансы и т.д.) |
| Поток событий трекера в граф знаний | `ingest/adapters/tracker/` | Каждое событие задачи (создана/завершена/заблокирована/просрочена/комментарий) уже становится записью в графе знаний компании |
| Тип встречи «обсуждение задачи» + создание встречи из задачи | `tracker` + `livekit` | Уже умеем создавать видеовстречу из задачи. Тот же паттерн повторяем для спринта |
| Извлечение действий из встречи + предтриаж | `tracker/services/` | После встречи AI **уже** извлекает кандидаты-задачи → попадают во входящие с подсказками (исполнитель/срок/приоритет/уверенность/цитата). Руководитель подтверждает — задача создаётся. Это и есть полуавтомат |
| Реестр специалистов AI-чата | `chat-v2/` + `tracker/handlers/` | AI-чат уже отвечает «покажи мои просроченные», «что обсуждали по KORA-123». Тот же паттерн → `SprintCardHandler` |
| Контроль качества (triage) + журнал активности задач | `curation/` + `tracker/` | Подсказки качества встраиваются в существующий механизм |

## 4. Решения владельца по всем 11 развилкам

### 4.1 Терминология (вопрос 1)
В коде остаётся `Cycle`, в русском интерфейсе показываем **«Спринт»**. Никаких переименований.

### 4.2 Привязка спринта (вопрос 2 — scope)
К `Project` добавляются 4 опциональных поля привязки:
- `customerCardId?` → `Card` с `kind='client'`
- `vendorId?` → `Vendor`
- `subjectPersonId?` → `Person`
- `departmentId?` → `Department`

**UX создания спринта:**
1. Шаг 1: выбор «к чему привязать» — radio-список: `Компания / Отдел / Сотрудник по должности / Клиент / Поставщик / Проект`.
2. Шаг 2: для выбранного типа (кроме «Компания») — combobox **«выбрать существующую сущность ИЛИ создать новую прямо здесь»**.
3. Особый случай **«Сотрудник по должности»**: двухступенчатый выбор — сначала должность, потом человек на этой должности.
4. Если выбрана «Компания» — все 4 поля привязки остаются пустыми.

### 4.3 «Спринт компании» (вопрос 3)
Все 4 поля привязки пустые → это и есть общеорганизационный спринт. Без отдельной галочки.

### 4.4 Цель спринта (вопрос 4)
Сейчас НЕ добавляем поле для привязки к существующей `Goal`. Цель формируется из обсуждений и попадает в финальный отчёт. Опциональная привязка — во 2-й версии.

### 4.5 Финальный отчёт спринта (вопрос 5)
Используем существующий механизм `CardVersion` (`resourceType='cycle'`). Отдельную таблицу `CycleReport` НЕ создаём.

### 4.6 Тип встречи для итогов спринта (вопрос 6)
Создаём **новый** тип встречи `sprint_review`. Русское название — **«Итоги спринта»**. НЕ переиспользуем `plan_fact`, не плодим вариаций — отдельный тип со своим шаблоном.

### 4.7 Русское название типа встречи (вопрос 7)
**«Итоги спринта».** Самое понятное для бизнеса (не только IT), сразу понятно — про результат.

### 4.8 Одна задача — в скольких спринтах? (вопрос 8)
**Только в одном активном.** История переносов сохраняется через `IssueActivity` (verb='cycle_changed').

### 4.9 Расположение в навигации (вопрос 9)
**Отдельный пункт сайдбара «Спринты»** на верхнем уровне (как «Цели», «Трекер»). Не зарываем внутрь трекера — это бизнес-методология, должна быть видна. При этом внутри страницы спринта показываем задачи из трекера и связанные встречи — глубокие связи никуда не уходят.

### 4.10 Подсказки качества — отдельный AI-агент ⚠ (вопрос 10)
**Важное архитектурное решение.** Подсказки делает **не SQL-правила, а отдельный AI-агент** — «Помощник по спринтам».

**Почему именно агент:**
- Правила «нет срока» — слишком тупо. AI-агент может понять контекст: «эта задача — исследование, срок не нужен» vs «у этой задачи нет срока, и от неё зависит другая со сроком — это плохо».
- Подсказки могут быть умнее: «эта задача похожа на ту, что делали 2 спринта назад за 3 дня», «эту задачу можно разбить на 3», «обсуждения на встрече расходятся с целью спринта».
- Методология спринта зашивается в системный промпт агента — её можно редактировать в админке без выкатки кода.

**Что это значит технически:**
- Появляется новый специалист по паттерну существующих (α-6 Project/Customer, α-7 Regulations, β-2 KnowledgeClone и т.д.).
- Регистрируется в реестре `CardSpecialistRegistry`, имеет свой LLM-таск с тройной цепочкой провайдеров (DeepSeek primary → OpenAI proxy → Ollama).
- Слушает блоки графа знаний с привязкой к спринту (через `IdeaBlockEvidence.rawEvent.meeting.linkedCycleId` или через задачи спринта).
- Выдаёт подсказки в специальную сущность (например, `SprintHint` или через `CardVersion` спринта).
- Подсказки показываются на странице спринта отдельным блоком («Помощник предлагает»).
- Промпт админ-редактируемый — по правилам `z-ai-agent-rules` (реестр в БД с code-fallback).

**Два слоя дополняют друг друга:**
- **SQL-агрегатор** (`SprintAnalystService`) — счётчики, выборки, базовые метрики. Без LLM. Быстро. Дёшево. Всегда доступен.
- **AI-агент** («Помощник по спринтам») — смысловые подсказки на основе методологии. С LLM. Медленнее. Дороже. Может не работать при недоступности провайдеров.

### 4.11 Финальный отчёт без AI (вопрос 11)
**Не создаётся.** Пишем пользователю «AI недоступен, попробуйте позже» + кнопка «Сгенерировать ещё раз». Никаких частичных отчётов без нарратива — отчёт = AI-генерация по определению. Дашборд продолжает работать (SQL-блоки), но финальная свёртка идёт только через LLM.

## 5. Модель данных (предварительный набросок)

### 5.1 Расширение `Project`

```
model Project {
  // ... существующие поля ...

  // Новые опциональные поля привязки (scope спринта)
  customerCardId   String?  // карточка клиента (Card.kind='client')
  vendorId         String?  // поставщик
  subjectPersonId  String?  // сотрудник (для онбординга или индивид. работы)
  departmentId     String?  // отдел

  customerCard     Card?       @relation("ProjectCustomerCard", fields: [customerCardId], references: [id])
  vendor           Vendor?     @relation(fields: [vendorId], references: [id])
  subjectPerson    Person?     @relation("ProjectSubjectPerson", fields: [subjectPersonId], references: [id])
  department       Department? @relation(fields: [departmentId], references: [id])
}
```

**Инвариант:** одновременно может быть заполнено не более 1 из 4 полей (валидация в сервисе, не в БД).

### 5.4 Новая сущность `SprintHint` (подсказки помощника по спринтам)

```
model SprintHint {
  id          String       @id @default(cuid())
  tenantId    String
  cycleId     String       // привязка к спринту
  cycle       Cycle        @relation(fields: [cycleId], references: [id], onDelete: Cascade)

  kind        SprintHintKind  // тип подсказки (см. ниже)
  severity    SprintHintSeverity  // info | warning | critical
  title       String       // короткий заголовок («Задача без срока»)
  body        String       // развёрнутая подсказка с контекстом
  affectedIssueIds String[] // на какие задачи указывает (опц.)
  sourceBlockIds   String[] // блоки графа, на основании которых сделана подсказка

  status      SprintHintStatus  // active | dismissed | resolved
  dismissedByUserId String?
  dismissedAt DateTime?
  createdAt   DateTime     @default(now())

  confidence  Decimal      @db.Decimal(4,3)
}

enum SprintHintKind {
  no_due_date
  no_description
  no_assignee
  due_date_at_risk
  recurring_carry_over  // переносится X+ спринтов
  no_recent_mentions    // 5+ дней молчания
  conflicts_with_goal   // расходится с целью спринта
  can_be_split          // можно разбить
  similar_to_past_task  // похожа на задачу из истории
  generic               // прочее
}

enum SprintHintSeverity { info, warning, critical }
enum SprintHintStatus { active, dismissed, resolved }
```

### 5.5 Cycle — без изменений

Сущность `Cycle` остаётся как есть. Все нужные поля уже там: имя, даты, статус, связь с проектом, набор задач.

## 6. Единый контур данных (схема)

```
Создан Спринт (= Cycle внутри Project)
   ↓
   Project имеет опц. scope: customer / vendor / person / department / null (компания)
   ↓
Пользователь создаёт видеовстречу из спринта (тип по умолчанию = «Итоги спринта»,
                                                можно выбрать standup / task_discussion / project)
   ↓
   Meeting.linkedCycleId = <id спринта>
   ↓
   (УЖЕ РАБОТАЕТ) merge.worker → две параллельные ветки:
        ├─ [Б] meeting-report-fast → отчёт пользователю по типу встречи
        │     · Для типа «Итоги спринта» — новый шаблон извлечения (см. §7)
        │
        └─ [A] block-ingest → IdeaBlock + Entity + Theme + специалисты Слоя 3
                                ↓
                           IntakeIssue (через meeting-extract-actions, УЖЕ РАБОТАЕТ)
                                ↓
                           Руководитель apruve'ит во входящих → Issue.cycleId = <id спринта>
                                ↓
                           Триггер на специалиста «Помощник по спринтам»
                                ↓
                           Анализ блоков и задач спринта согласно методологии
                                ↓
                           Запись в SprintHint (active, ждёт реакции пользователя)
   ↓
Страница спринта показывает:
   1. SQL-блоки (счётчики, прогресс, задачи без срока — SprintAnalystService)
   2. «Помощник предлагает» (active записи из SprintHint)
   3. Связанные встречи (Meeting.linkedCycleId)
   4. Что обсуждали по задачам (через IssueCardHandler в реестре)
   5. Кнопку «Создать видеовстречу»
   ↓
POST /cycles/:id/complete (УЖЕ работает rollover) → дополнительно:
   1. Новый LLM-таск sprint-review-summary
   2. Сохранение через CardVersion(resourceType='cycle')
   3. ЕСЛИ LLM упал — показываем «AI недоступен, попробуйте позже»
```

**Что новое:**
- 1 новый специалист («Помощник по спринтам») в реестре `CardSpecialistRegistry`.
- 1 новый LLM-таск для специалиста + 1 LLM-таск для финального отчёта.
- 1 новый сервис `SprintAnalystService` — SQL-агрегатор для дашборда.
- 1 новый handler в реестре (`SprintCardHandler`) — для ответов AI-чата по теме спринта.
- 1 новая сущность `SprintHint` + связанные перечисления.
- 1 новый тип встречи «Итоги спринта» + шаблон извлечения.

**Что НЕ новое (переиспользуем):**
- Очереди BullMQ — стандартные `core.specialist-routing`, `core.raw-events`.
- Cron'ы — никаких новых, агент работает по триггерам блоков.
- Mehanizm триажа — `CurationService` уже умеет triage для resourceType=cycle.

## 7. Новый шаблон AI-отчёта «Итоги спринта»

Поля, которые AI должен извлечь из транскрипта встречи итогов спринта (отдельный промпт от подсказок «Помощника»):

| Поле | Что извлекаем |
|---|---|
| Цель спринта | Если на встрече озвучили — фиксируем; если нет — берём из предыдущих обсуждений по этому спринту через граф знаний |
| Что было запланировано | Список задач, попавших в спринт при создании (из БД, не из транскрипта) |
| Что выполнено | Задачи в статусе Done + упоминания «закрыли X» на встрече |
| Что не выполнено | Задачи не-Done + причины (если озвучены) |
| Причины расхождений | Из обсуждения — почему не сделали |
| Решения по переносам | Какие задачи переносим в следующий спринт, какие закрываем, какие разбиваем |
| Проблемы / блокеры | Что мешало (из обсуждения + блоки с типом сигнала pain/risk) |
| Подсказки качества | Берутся из существующих active записей `SprintHint`, прикладываются к отчёту как блок «Помощник отмечал» |
| План следующего спринта | Если на встрече обсуждали — извлекаем как кандидаты задач (попадают во входящие) |
| Нарратив | 3-5 предложений «как прошёл спринт» — для удобства чтения |

Промпт лежит в `backend/src/modules/ai/services/prompts/sprint-review.prompt.ts`, регистрируется через `seed-llm-task-routes-sprint.ts` с тройной цепочкой провайдеров.

## 8. Что показывает страница спринта

Все блоки — выборки из существующих источников + новый блок от AI-агента:

| Блок UI | Источник данных | Тип запроса |
|---|---|---|
| Прогресс % и burn-down | `Issue` по `cycleId` GROUP BY `state` | SQL count |
| Задачи без срока / срок горит | `Issue.cycleId`, `dueDate` | SQL where |
| Задачи без движения 3+ дня | `IssueActivity.epoch` | SQL aggregate |
| Что обсуждали по теме спринта | `IdeaBlock` через `IssueCardHandler` / `SprintCardHandler` | существующий реестр специалистов |
| Перенесённые задачи (история) | `IssueActivity` где `verb='cycle_changed'` | SQL |
| Связанные встречи | `Meeting.linkedCycleId` | SQL |
| **«Помощник предлагает»** | `SprintHint` где `cycleId=X` и `status='active'` | новый блок |
| Кнопка «Создать видеовстречу» | новый endpoint `POST /cycles/:id/start-meeting` | — |

LLM работает в двух режимах:
- **Фоновый** — «Помощник по спринтам» после каждой встречи спринта анализирует и пишет в `SprintHint`.
- **По кнопке** — финальный отчёт при закрытии спринта.

## 9. Где спринт автоматически «слышит» обсуждения

1. На встрече типа «Итоги спринта» (или «Планёрка»/«Обсуждение задачи»), привязанной к спринту, кто-то говорит «закрыли регистрацию».
2. После встречи: `merge.worker` → `block-ingest` создаёт блок с типом сигнала `done_item`, evidence ссылается на встречу → на спринт.
3. На странице спринта блок «Что обсуждали по задаче KORA-123» автоматически показывает эту цитату.
4. **Статус задачи AI не меняет** — пользователь либо сам кликает Done в трекере, либо принимает предложение во входящих (если механизм извлечения действий создал кандидат-задачу).
5. **Помощник по спринтам** видит этот же блок и может предложить подсказку, например: «Задача KORA-123 закрыта по словам Маши, но в трекере статус не изменился — обновить?».

## 10. Права (RBAC)

- Добавляется action `cycle:create` (сейчас совмещён с `cycle:write`).
- В админке появляется галочка в настройках роли: **«Может создавать спринт»**.
- По умолчанию — `owner` и `admin` могут, `manager` и `member` — нет (можно включить).

Для `SprintHint` — отдельный ResourceType:
- Чтение — все участники проекта, к которому относится спринт.
- Закрытие подсказки (dismiss) — `owner` / `admin` / создатель спринта.

## 12. Что НЕ делаем (фиксируем границы)

| Не делаем | Делаем вместо |
|---|---|
| Активного AI-агента, который сам ставит задачи | Только подсказки через `SprintHint` + полуавтомат через существующий механизм извлечения действий из встречи + входящие |
| Обязательной структуры планёрки (как в EOS L10) | Никаких 7 шагов, агенды, таймера |
| Жёстких временных рамок (понедельник 9:00 и т.п.) | Длина спринта и расписание встреч — на усмотрение пользователя |
| Approval-ленты («Tinder для задач») | Используем уже работающий механизм входящих с триажем |
| Параллельных очередей или новых cron'ов | Всё лежит на существующем pipeline |
| Частичных отчётов без AI | Отчёт = AI-генерация; если AI недоступен — пользователю «попробуйте позже» |
