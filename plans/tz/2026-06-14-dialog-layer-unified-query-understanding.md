# Dialog-layer: один history-aware модуль понимания запроса вместо трёх агентов

## 1. Цель и контекст

Препроцессор помощника (и AI-чата компании) разбит на отдельные LLM-агенты,
которые исторически выросли из одного ТЗ
[SBA α-5 (2026-05-23)](../archive/2026-05-23-sba-alpha-5-dialog-layer-and-cache.md):

1. **Контекстуализатор** (`dialog-contextualize`) — переписывает follow-up
   («а сколько это стоит?») в самодостаточный вопрос по истории диалога.
2. **Оценщик уверенности** (`dialog-confidence`) — отдельным LLM-вызовом
   проверяет, не исказил ли смысл контекстуализатор; при низкой уверенности —
   откат на сырой текст.
3. **Расширитель** (`dialog-multi-query`) — 1 вопрос → 3 переформулировки для
   recall; запускается только для intent ∈ {exploratory, analytical}.

### Что сломано
Изначальный замысел расширителя (владелец): он должен получать **историю
диалога** и **сам** превращать неполную реплику в три самодостаточных вопроса.
По факту при реализации его «обрезали»:

- **Расширитель слеп к истории.** На вход идёт только `question`, без summary и
  истории — см. [multi-query-expansion.service.ts:36-41](../../backend/src/modules/dialog-layer/services/multi-query-expansion.service.ts#L36)
  и промпт [buildMultiQueryUserPrompt](../../backend/src/modules/dialog-layer/prompts/multi-query.prompt.ts#L47).
- **Расширитель загейтлен** на exploratory/analytical
  ([multi-query-expansion.service.ts:91-96](../../backend/src/modules/dialog-layer/services/multi-query-expansion.service.ts#L91)):
  для factual-реплики «сколько это стоит» он вообще не запускается.
- Поэтому контекстуализацию пришлось вынести в отдельный агент №1, а его выход —
  страховать отдельным агентом №2.

Итог: контекстуализатор делает половину работы расширителя, оценщик страхует
эту половину третьим вызовом — три последовательных LLM-вызова там, где
задумывался один.

### Доказательная база (industry, состязательная перепроверка в сессии)
- **Контекстуализация follow-up'а как шаг — индустриальный стандарт** (LangChain
  `create_history_aware_retriever`, LlamaIndex `CondenseQuestionChatEngine`) и
  научно обоснован (QReCC NAACL-2021: baseline F1 19.1 vs human-oracle 75.4 —
  переписка вопроса главный рычаг recall). Сам шаг нужен.
- **Отдельный LLM-верификатор переписки (№2) — антипаттерн.** Ни один из главных
  фреймворков не верифицирует переписку вторым LLM-вызовом; самокоррекция тем же
  классом модели без внешнего сигнала ненадёжна (Huang et al., ICLR 2024) и
  завышает себя (Panickssery 2024); confidence LLM не калиброван (2503.15850).
- **Три формулировки для recall — паттерн RAG-Fusion** (генерируешь несколько
  запросов → ищешь по каждому → сливаешь). Замысел владельца корректен.
- **Вывод:** контекстуализацию и расширение нужно слить в ОДИН history-aware
  вызов (= исходный замысел), а верификатор-агент убрать.

## 2. Принятые решения

1. **Слияние в один шаг.** `MultiQueryExpansionService` (org-режим) становится
   полноценным «модулем понимания запроса»: на вход — `summary` + история
   (последние 4 пары сообщений) + реплика; на выход — **3 самодостаточных
   разноплановых вопроса**. Контекстуализация (раскрытие «это/он/там» по истории)
   происходит внутри ЭТОГО же промпта.
2. **Удаляем агента №1** (`ContextualizerService`, `dialog-contextualize`) и
   агента №2 (`ConfidenceEstimatorService`, `dialog-confidence`) из
   `DialogService.process()`. Их работу полностью покрывает слитый шаг.
3. **Расширитель работает всегда (без intent-гейтинга по exploratory/analytical
   в org-режиме).** Раз он теперь и контекстуализирует — он обязан запускаться и
   на factual-follow-up'ах, иначе «сколько это стоит» снова сломается. Для
   factual три формулировки не вредят: это просто больше recall за тот же 1
   вызов. Глобальный kill-switch `MULTI_QUERY_EXPANSION_ENABLED` остаётся (можно
   выключить весь шаг → вернуться к одному сырому запросу).
4. **Глубина истории — крутилка в `AdminSetting`** (`DIALOG_QUERY_HISTORY_PAIRS`,
   дефолт 4), не хардкод. [[feedback_admin_settings_not_env_or_code]].
5. **Классификатор №3 (`dialog-classify`) остаётся** — он не дубль: нужен для
   выбора режима ответа (factual/synthetic/clone) в chat-v2 и для бот-интентов
   (task/show_tasks/plan/report). Вне scope этого ТЗ — его логику не трогаем,
   только подаём ему сырую реплику + контекст по новому порядку.
6. **Маршрут переиспользуем.** taskType остаётся `dialog-multi-query` (route
   admin-editable, модель `deepseek-v4-flash` primary). Меняется только промпт и
   версия JSON-схемы (`dialog_multi_query_v2`). Это разово инвалидирует
   prompt-cache — приемлемо.
7. **`clone`-режим расширителя не трогаем** — он уже работает всегда и со своим
   промптом (`dialog-multi-query-clone`). История ему добавляется так же
   (опционально, тем же входным контрактом), но это можно отдельной строкой; в
   обязательный scope входит только org-режим.
8. **Извлекатель плана (`dialog-extract-plan`) переезжает ПОСЛЕ расширителя и
   кормится тремя вопросами, а не одним.** Причина (доказана): извлекатель умеет
   только извлекать явные условия из текста — на сырой реплике «сколько это
   стоит» он находит пусто (имя «Маяк» живёт в истории, не в реплике). Раньше его
   спасал контекстуализатор №1; раз мы его удаляем — единственный, кто раскрывает
   сущности, это расширитель. Поэтому: расширитель (3 самодостаточных вопроса) →
   извлекатель собирает по этим трём ОБЪЕДИНЁННЫЙ план (условие включается, если
   явно есть хотя бы в одной формулировке). Подаём 3 вопроса в ОДИН вызов
   извлекателя (цена = 1 вызов, вход богаче). Промпт переписан по методологии —
   Приложение B, схема `dialog_extract_plan_v2`.

## 3. Архитектура: было → стало

**Было** (последовательно в `DialogService.process()`):
```
contextualize(№1) → confidence(№2) → answerCache → classify(№3)
  → [queryPlan] → multiQuery(№4, без истории, гейт exploratory/analytical)
```
factual-follow-up с историей = 2-3 LLM-вызова прелюдии; exploratory = 3-4.

**Станет:**
```
classify(№3, по сырой реплике+истории) → answerCache
  → queryUnderstand(слитый, с историей → 3 самодостаточных вопроса)
  → [queryPlan](на 3 вопросах → объединённый структурный план)
  → поиск(по 3 вопросам + фильтр-сито плана)
```
любой follow-up = **1 LLM-вызов** понимания запроса + (опц.) 1 вызов извлекателя
плана; плюс classify, у которого эвристика-first закрывает 60-70% без LLM.

> Порядок 1: `classify` переезжает до слитого шага (раньше классифицировал
> контекстуализованный вопрос — теперь сырую реплику; для выбора режима ответа и
> бот-интентов этого достаточно, эвристики работают по сырому тексту).
> Порядок 2 (решение 8): `queryPlan` переезжает ПОСЛЕ `queryUnderstand` и
> кормится тремя самодостаточными вопросами — иначе на сырой реплике он слепнет
> (имена/темы живут в истории, раскрываются только расширителем).

## 4. Scope

**Входит:**
- Новый промпт «модуль понимания запроса» (Приложение A) — финальный, согласован
  с владельцем 2026-06-14.
- `MultiQueryExpansionService.expand()` (org-режим): принимает `summary` +
  `history`, убирает intent-гейтинг, всегда возвращает `[реплика, ...3 вопроса]`
  (реплика первой — fallback при пустом поиске, как сейчас).
- `DialogService.process()`: убрать вызовы `contextualizer` и `confidence`;
  передать `summary`+`history` в `multiQuery.expand()`; перенести `classify` до
  слитого шага и подать ему сырую реплику; **перенести `queryPlanExtractor.extract`
  ПОСЛЕ `multiQuery.expand` и подать ему 3 вопроса (`mq.queries` без оригинала)
  одним вызовом**.
- `QueryPlanExtractorService.extract()`: вход `question: string` → `questions:
  string[]` (3 формулировки); промпт по Приложению B; схема `dialog_extract_plan_v2`.
  `resolveStructuralFilters` без изменений.
- Удаление `ContextualizerService`, `ConfidenceEstimatorService` и их промптов
  (`contextualize.prompt.ts`, `confidence.prompt.ts`) + снятие из DI
  (`dialog-layer.module.ts`).
- ENV-чистка: удалить `CONTEXTUALIZER_CONFIDENCE_MIN`; добавить `AdminSetting`
  `DIALOG_QUERY_HISTORY_PAIRS` (дефолт 4).
- Эталон промпта в `docs/methodology/prompts/examples/query-understand.md` +
  строка в реестре `upgrade-progress.md`.

**Не входит:**
- Логика классификатора №3 (отдельная история).
- `clone`-режим расширителя (история ему — отдельной мелкой строкой, опц.).
- Замена классификатора на эмбеддинг-роутер (отдельный анализ, не сейчас).
- AnswerCache/RetrievalCache, temporal validAt, summarizer-cron — без изменений.

## 10. Риски
- **Класс-ошибка переписки внутри одного вызова.** Митигейшн: первым в массиве
  всегда оригинальная реплика (fallback при пустом retrieval); LLM-падение →
  возвращаем `[реплика]` (как сейчас).
- **Регрессия chat-v2 (не только помощник).** dialog-layer общий. Митигейшн:
  kill-switch `DIALOG_LAYER_ENABLED` и `MULTI_QUERY_EXPANSION_ENABLED` остаются.
- **classify по сырой реплике хуже, чем по standalone.** Эвристики работают по
  сырому тексту; для бот-интентов и так подаётся сырой текст. Наблюдаем долю
  `source='llm'` и распределение intent.
- **Рост output-токенов factual** (теперь 3 вопроса вместо 1). Незначимо на
  flash-модели; перекрыто экономией на −2 вызовах.
- **Извлекатель пере-сужает поиск по объединённому плану.** Три формулировки —
  один запрос; если расширитель занесёт лишнюю тему/сущность, извлекатель добавит
  лишний фильтр и отсеет нужное. Митигейшн: промпт извлекателя собирает ОБЩУЮ
  структуру (а не валит подряд), порог уверенности 0,6, fail-open, оригинальная
  реплика остаётся первым запросом поиска (не зависит от фильтра).
- **Извлекатель плана не доходит до быстрого предпоиска помощника.** Структурные
  фильтры потребляет только chat-v2 (`ask_chat_v2`), а `ConciergeService.preRetrieve`
  использует лишь `queries`. В scope этого ТЗ — не чинить (отдельная заметка в
  `04_не-сделано`), но переезд порядка тут ничего не ломает.

## Приложение A — финальный промпт (taskType `dialog-multi-query`, схема `dialog_multi_query_v2`)

### SYSTEM (стабильный, few-shot внутри → кэшируется)
```
Ты — модуль понимания запроса в Коре, памяти компании. Кора хранит знания
компании графом: встречи, решения, задачи, договорённости, риски, люди.
Твоя работа — превратить реплику сотрудника в живом диалоге в запросы, по
которым система найдёт нужное в этом графе.

ЗАЧЕМ ЭТО НУЖНО.
Сотрудник пишет в диалоге, и его реплика часто неполная: «а сколько это
стоит?», «а он что решил?», «почему так вышло?». Без истории диалога
непонятно, о ком и о чём речь. Ты восстанавливаешь смысл по истории и
формулируешь полноценные вопросы.

КОМУ АДРЕСОВАН ТВОЙ ВЫВОД.
Твои вопросы читает НЕ человек, а поисковый движок по графу знаний. Поэтому
каждый вопрос должен быть понятен сам по себе, без истории диалога.

ЧТО СТАНЕТ С РЕЗУЛЬТАТОМ.
Каждый из трёх вопросов уйдёт ОТДЕЛЬНЫМ поиском по графу, а результаты
объединятся. Поэтому три вопроса должны покрывать запрос с РАЗНЫХ сторон —
чтобы поймать записи, где то же самое сказано другими словами.

ЧТО СДЕЛАТЬ (два шага).
1. Восстанови смысл. По краткому содержанию и последним сообщениям пойми,
   о ком/чём реплика. Замени «это», «он», «там» и пропущенные сущности на
   конкретные имена из истории.
2. Сформулируй ТРИ самодостаточных вопроса об одном и том же, но по-разному:
   • Вопрос 1 — точная переформулировка (та же суть, другие слова/синонимы).
   • Вопрос 2 — другой ракурс (тот же предмет с иной стороны: причина,
     участники, сроки, последствия).
   • Вопрос 3 — конкретизирующий, узкий (одна явная под-цель запроса).

КРИТЕРИИ ХОРОШЕГО РЕЗУЛЬТАТА.
1. Каждый вопрос понятен БЕЗ истории — все местоимения и подразумеваемые
   сущности раскрыты конкретными именами.
2. Все три — об одном и том же запросе пользователя; не уводи в сторону.
3. Три вопроса РАЗНЫЕ по ракурсу, а не одна фраза, пересказанная синонимами.
4. Язык оригинала: русский вопрос → русские формулировки.
5. Каждый вопрос — одна мысль, не длиннее ~200 символов.
6. Если реплика и так полная и простая — всё равно дай три формулировки для
   полноты поиска, но НЕ выдумывай деталей, которых нет в реплике и истории.
7. Не отвечай на вопрос и ничего не поясняй — только формулируй.

ЗАПРЕТЫ.
• Ни одного английского слова, кода, идентификатора, названия таблицы или
  поля — даже если они встретились в истории. Только человеческий русский.
• Не добавляй сущности и факты, которых нет ни в реплике, ни в истории.

ПЕРЕД ОТВЕТОМ ПРОВЕРЬ.
(а) В каждом вопросе раскрыто, о ком/чём речь; (б) три вопроса различаются
ракурсом, а не только словами; (в) нет английских слов и кодов. Если
что-то не так — перепиши.
```

## Приложение B — финальный промпт извлекателя плана (taskType `dialog-extract-plan`, схема `dialog_extract_plan_v2`)

Переписан по методологии. Главное отличие от v1: на вход — **три самодостаточных
вопроса** (выход расширителя), а не один сырой; извлекатель собирает по ним
ОБЪЕДИНЁННЫЙ план. Согласован с владельцем 2026-06-14.

### SYSTEM (стабильный, few-shot внутри → кэшируется)
```
Ты — анализатор структуры запроса в Коре, памяти компании. Кора хранит
знания компании графом: встречи, решения, задачи, договорённости, риски,
люди. Тебе дают ТРИ формулировки ОДНОГО запроса сотрудника. Твоя задача —
понять, по каким условиям сузить поиск по графу, и вернуть один JSON-план.
Ты НЕ отвечаешь на вопрос и не ищешь — только извлекаешь структуру.

ЗАЧЕМ ЭТО НУЖНО.
По твоему плану система отсеет лишнее из найденного: оставит нужный период,
темы, упомянутых клиентов и проекты, нужные типы записей. Плохой план — либо
потеряем нужное (слишком узко), либо не сузим вовсе.

ПОЧЕМУ ТРИ ФОРМУЛИРОВКИ.
Это три варианта одного запроса, написанные разными словами. Имя клиента,
тема или тип записи могут быть названы явно только в одной из формулировок.
Собери их ОБЩУЮ структуру: если условие явно относится к запросу и встретилось
хотя бы в одной формулировке — включи его. Не накапливай лишних условий,
которых в запросе нет.

ПРАВИЛО-ИНВАРИАНТ: если оси в формулировках НЕТ — верни пустое значение
(пустой массив / "none" / false / null). НИКОГДА не выдумывай значения,
которых нет в перечисленных ниже наборах.

──────────────────────────────────────────────────────────────────
ОСЬ 1 — periodExpr (период времени)
Один токен: this_week, last_week, yesterday, today, this_month,
last_month, last_n_days, none.
  • «эта неделя» → this_week · «прошлая неделя» → last_week
  • «вчера» → yesterday · «сегодня» → today
  • «этот месяц» → this_month · «прошлый месяц» → last_month
  • «за последние N дней», «за месяц» → last_n_days + periodDays
periodDays — число дней для last_n_days, иначе null. «За месяц» = 30.
Если времени нет — "none". Если период есть, но НЕ ПОДДЕРЖАН (квартал,
год, полгода, конкретные даты) — тоже "none", periodDays=null.

──────────────────────────────────────────────────────────────────
ОСЬ 2 — signalTypes (типы записей знаний)
Массив строго из официального набора (см. JSON-схему), иначе [].
  • «решали», «решение» → decision
  • «дела», «задачи» → task_created, task_completed, commitment, plan_item
  • «риски» → risk, churn_risk · «блокеры» → blocker
  • «идеи» → idea · «запрос клиента» → client_request

──────────────────────────────────────────────────────────────────
ОСЬ 3 — themeBranches (темы / отделы)
Массив строго из набора: strategy, clients, sales, marketing, product,
operations, team, finance, technology, production, partnerships, legal.
  • «маркетинг»→marketing · «продажи»→sales · «продукт»→product
  • «финансы/бюджет/деньги»→finance · «команда/HR/найм/люди»→team
  • «операции/процессы»→operations · «юр/договор/право»→legal
  • «стратегия»→strategy · «клиенты»→clients · «технологии/разработка»→technology
  • «производство»→production · «партнёры»→partnerships
Если тема не упомянута — [].

──────────────────────────────────────────────────────────────────
ОСЬ 4 — entityHints (имена собственные)
Массив имён собственных (клиенты, компании, люди, проекты) КАК НАПИСАНО.
Если их нет — [].

──────────────────────────────────────────────────────────────────
ОСЬ 5 — personScope: true, если запрос про самого спрашивающего
(«я», «мой», «мне», «у меня»), иначе false.

ОСЬ 6 — aggregation: true при «сколько», «сумма», «самый»,
«количество», «больше всего», иначе false.

ОСЬ 7 — needsAction: true, если просят действие/совет («предложи»,
«что делать», «посоветуй»), иначе false.

ОСЬ 8 — activeNow: true, если про текущее/действующее сейчас
(«сейчас», «актуальные», «действующие», «текущие»), иначе false.

──────────────────────────────────────────────────────────────────
confidence — уверенность в собранном плане, 0..1.
  • 0.9-1.0 — оси явные. • 0.6-0.89 — уверен, одна ось под вопросом.
  • <0.6 — почти угадываешь (система проигнорирует слабый план).

КРИТЕРИИ ХОРОШЕГО ПЛАНА.
1. Включай ось, только если она ЯВНО есть хотя бы в одной формулировке и
   относится к сути запроса.
2. Не угадывай тему/тип/период, которых нет в тексте.
3. Значения — строго из разрешённых наборов.

ПЕРЕД ОТВЕТОМ ПРОВЕРЬ.
Каждое включённое условие реально стоит в одной из формулировок; ничего не
выдумано; значения — из разрешённых наборов. Если нет — убери.

ПРИМЕРЫ.

[Пример 1 — тема в одной формулировке, тип записи в другой]
Формулировки:
1. Почему выручка отдела продаж в этом квартале ниже плана на 15%?
2. Какие причины слабых продаж называли на встречах?
3. Что отдел продаж решил предпринять из-за отставания по выручке?

```
