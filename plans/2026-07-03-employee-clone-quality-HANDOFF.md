# Передача агенту: качество клонов сотрудников — стенд, линейка, петля до идеала

> Это **единственная точка входа** для агента, который ведёт работу дальше. Здесь — весь контекст, одобренные решения, карта документов, дорожная карта и первое конкретное задание. Прочитав только этот файл + 4 документа по ссылкам ниже, ты имеешь всё, чтобы вести работу без переспросов у владельца по уже решённому.

## 0. Что это и зачем (одним абзацем)

Кора строит **клона сотрудника/должности** автоматически из встреч, чатов и закрытых задач (черты рассуждений → персона → регламенты → процедуры). Владелец хочет сделать Кору **лучшей в зарождающейся категории «AI-клоны сотрудников»**: сотрудник уволился — клон отвечает на любой вопрос **как он или лучше**, всегда **как эксперт** (позиция → совет → план действий), опираясь на роль/черты/скиллы/регламенты/знания и **перенос по аналогии** («точно такого не было, но в похожей ситуации я делал так»). Ответ «по факту есть/нет» — это режим справочника, а не эксперта. Задача агента: построить **измерительный стенд + линейку оценки**, снять точку отсчёта, и **петлёй итераций (прогон → диагноз → ТЗ → фикс → перепрогон)** довести клона до планки качества.

## 3. Ключевое, что нужно понять до старта

**Главное противоречие.** Текущий клон спроектирован ПРОТИВОПОЛОЖНО замыслу — «лучше отказ, чем выдумка». Четыре контура отказа (аудит §1.3): (1) < 3 черт → 404; (2) анти-deepfake гейт «< 2 блоков по теме» → отказ ДО LLM; (3) промпт велит отказываться; (4) ответ без цитат заменяется отказом. «Экспертный» режим по аналогии в коде ЕСТЬ (`judgmental`), но заперт за выключенным флагом `CLONE_V2_ENABLED`. Ретрив клона — «последние 20 блоков», не поиск по вопросу; механизм «поиск похожей ситуации» вычисляется, но никуда не подключён. **Baseline это подтвердит числом — и это нормально, это точка отсчёта.**

**Канал «уведомляльщика» реализован** (важно, ранее была ошибка в оценке). Мостик «задача перешла в „решено" → probe „расскажи, как решал" → ответ → reasoning-блок → клон» работает (Ф5/Ф6, 2026-06-29): probe на любой переход в completed, ответ ингестится в общий конвейер. НО у канала есть глушители пропускной способности (complexity-гейт 0.5, rate-limit 20/день, дедупы) — стенд меряет их воронкой кормления, а не «открывает мостик заново».

**Данных для клонов сейчас нет.** В Стреле клонного корма 9 блоков на весь тенант, профили по 1 черте (порог 3), ролей/назначений 0, Елена намеренно слита с Игорем. Поэтому **Фаза 0 (наполнение) — обязательный первый шаг при любом раскладе**: без неё стенд упрётся в «клон не сформирован».

**Рынок подтверждает ставку** (аудит §7): категория живая (Viven $35M, Delphi $16M), но никто не делает лестницу ответа при пробелах, клона должности, автосбор из встреч для SMB, публичную метрику качества. В РФ прямых конкурентов нет. Научный факт для линейки: LLM-судьи оценивают клонов плохо (PersonaEval 69% vs 90.8% у людей) → **линейка опирается на ground truth по построению** (сеем метод сами — знаем эталон каждого ответа), LLM-панель только поверх.

## 5. ТЗ-0 «Стенд + baseline» — детальное задание (первый шаг)

**Цель:** построить работающий стенд, наполнить клонов, снять baseline. Поведение клона НЕ трогаем (кроме read-only расширения трассы).

**Файлы к созданию** (контракт — проект стенда §7):
```
backend/scripts/clone-stand/
  seed-clone-feed.ts   Фаза 0: наполнение (Канал А + Б) + манифест
  layer0-annotate.ts   Фаза 0в: слепые разметчики прозы сида → манифест ожидаемых черт
  layer0-match.ts      Фаза 0в: сверялка read-only манифест ↔ база клона
  stand.ts             раннер: prepare|build|status|run|judge|report|all
  judge.ts             панель 3 линз через directLlmCall (образец: probe-stand/judge.ts)
  report.ts            scorecard + оси + диагнозы (атрибуция по слою) + «было→стало»
docs/testing/
  clone-feed-manifest.json   генерит seed-clone-feed (ground truth; черты выведены, не скопированы — Слой-0 правило №1)
  clone-stand-report.md      отчёт baseline (+ Слой-0 фиделити)
  clone-stand.md             README стенда (по образцу probe-stand.md)
```

**Фаза 0а — наполнение (детали в проекте стенда §5, §5.1):**
- Пере-сев Стрелы (новый org, обновить `STRELA_ORG` в `.env`/доках) — Елена/Игорь чистые.
- 4 клона-цели: Сергей (CEO, +person), Михаил (интегратор, +person), Дарья (маркетолог, +person), Игорь←Елена (поддержка, смена носителя + frozen v1). Методы каждого — таблица §5.
- Канал А: reasoning-встречи (паттерн `clone-build-harness.ts`), ≥3 близких формулировки на навык, эпизоды разнесены по датам.
- Регламенты: консолидация дублей + «Регламент обработки обращений v2» (SLA ≤4ч, severity) + org-политика «данные клиентов — серверы РФ [blocking]» + advisory-политики.
- Stale-эпизоды (daysAgo ≥40, под вопросы c071–c076), KnowledgeProfile-корм Сергею/Михаилу/Дарье, CloneAccessGrant, событие `role.bearer_changed` (увольнение Елены).
- **Конфиг окружения стенда** (не поведение!): `PERSONA_ROLE_AGG_MIN_PERSONS=1` (роли по одному носителю), поднять квоты/лимиты стенда локально.
- **Манифест** `clone-feed-manifest.json`: методы по клонам (у support — раздельно v1 Елена / v2 Игорь), `statusFacts` (что НЕ завершено), `absentFacts` (чего намеренно нет — под вопросы честной лестницы).

**Фаза 0б — Канал Б (штатный путь, детали §5.1):**
- 60 синтетических задач (15/клон, повторяющихся типов) с описанием ≥280 символов, assignee, приоритетом (иначе complexity-гейт 0.5 не пропустит probe).
- Программно: закрыть задачу (`transitionState`) → poll `ProbeEvent(task.method_capture)` до `status=dispatched` → найти `Notification` по `dispatchedNotificationId` → `ConversationalService.respondToProbe({notificationId, userId:<исполнитель>, payload})` от userId адресата.
- Чистить `probe:dedup:*`, `probe:ratelimit:*` между закрытиями; учесть `probe.dialogEnabled` (confirm-петля).
- **Воронка кормления** (§5.2) — отдельная метрика: задач закрыто → probe задан/задиспатчен → ответ → блок клон-типа (не только methodology_step!) → черта → verify → персона. Планка: ≥70% ответов доходят до блока клон-типа; каждый клон ≥3 черт + активная персона.

**Фаза 0в — Слой 0 фиделити построения** (проект §5.3, метод [synthetic-fidelity-eval-method.md](../docs/methodology/synthetic-fidelity-eval-method.md)): 2+ слепых агента читают ТОЛЬКО прозу сида о сотруднике + якоря → пишут ожидаемую черту (какой метод/поведение должны появиться) → ревизор сводит в манифест + agreement → сверялка read-only матчит с реальной базой клона (trait recall / **derivation** — черта выведена, не скопирована (правило №1!) / no_false_merge — носитель не слит / persona fidelity). Партиями по ~10 якорей. Граница пере-сева (проект §5.3): фиделити ИЗВЛЕЧЕНИЯ клон-блоков снимается на существующей базе сразу; фиделити СИНТЕЗА черт — после наполнения (Фазы 0а/0б). Изоляция агентов обязательна (не видят базу и друг друга).

**Фаза 1 — раннер:** бьёт в `ClonesService.askPerson/askRole/askAllFormers` (полный AppModule, как `batch-recall-trace.ts`); CONCURRENCY ≤3; цепочки — один `conversationId`; per-run файлы. **Расширить трассу llmMeta** списком вошедших регламентов/скиллов/блоков (read-only, для оси L — единственная разрешённая правка прод-кода). Детерминированные ассерты отдельно от судей.

**Фаза 2 — судьи:** панель majority-of-3, разные линзы (экспертность+персона / верность методу vs эталон / честность-fabricated), `directLlmCall` без AppModule, deepseek-v4-pro, JSON-схема. Линзе честности давать retrieved-контекст, не только groundTruth. Вердикт вычисляется детерминированно (порядок в §4.2 проекта). Каждый FABRICATED — ручной разбор.

**Фаза 3 — baseline:** чистка кэшей/дедупов → run → judge → report на 110 + фиксация конфигурации прогона (CLONE_V2_ENABLED, CLONE_TOPIC_*, LlmTaskRoute, пороги). Отчёт владельцу: scorecard + воронка + Слой-0 фиделити + таблица диагнозов **с атрибуцией по слою** (сколько отказов — политика Слой 2/3 → ТЗ-1; сколько — непостроенная черта Слой 0 → извлечение). **Прогноз для калибровки:** REFUSED ≈ 50 из 96 отвечаемых — если так, стенд меряет верно; если резко иначе — сначала чинить стенд (диагноз ruler-defect), а не радоваться/паниковать.

**Acceptance ТЗ-0:** стенд гоняется командой; 4 клона наполнены (≥3 черт, персона); воронка кормления посчитана; **Слой-0 фиделити снят (trait recall/derivation/no_false_merge), пороги зафиксированы как baseline**; baseline-отчёт со scorecard, осями, воронкой, Слоем 0 и диагнозами (атрибуция по слою) лежит в `docs/testing/clone-stand-report.md`; конфигурация прогона зафиксирована; манифест ground truth на месте (черты выведены из источника слепой разметкой, не скопированы). `typecheck/lint/build` зелёные по затронутому. Прод не тронут.

## 6. Линейка оценки — «маркеры идеальности» (кратко; полно — проект §4)

**5 осей (0..1):** E экспертность · M верность методу (шкала 1.0/0.5/0.3/0.0) · G заземлённость (не выдумал) · L опора на нужный слой · P персона.

**Вердикт на вопрос** (детерминированно, сверху вниз): BOUNDARY_OK/FAIL (для boundary+off_domain) → FABRICATED → REFUSED → EXPERT_PASS (E≥0.7 ∧ M≥0.5 ∧ L ∧ P) → WEAK (остаток).

**Планка (приёмка петли):** EXPERT_PASS ≥95% на отвечаемых (96 из 110) И ≥90% на свежем банке ~20; **железные инварианты:** FABRICATED=0, BOUNDARY_OK=14/14, ср. M≥0.7. Планку задаёт владелец.

**Петля, 3 исхода:** планка взята → финал; остаток вне рычагов scope → стоп + честный разбор потолка + решение владельца; иначе → следующая итерация. Чинить КЛАСС провалов, не кейс. Каждый провал сверять с сырым ответом, не с флагом линейки (дефект линейки = отдельный класс, чинится первым).

## 7. Гипотезы для ТЗ-1 (каркас разворота — уточнить по baseline)

- **H1** разворот 4 контуров отказа на «лестницу опоры» (гейты из блокираторов → переключатели ступени; запретная зона остаётся). Главный рычаг.
- **H3** интент-роутинг: `clone_roleplay` → экспертный режим (не строгий); судьба флага `CLONE_V2_ENABLED`.
- **H5** пороги ответа (minTraits, topic*, grounding) → AdminSetting `clone.answer.*` — без этого петля не итерируется быстро. Делать рано.
- **H2** семантический ретрив субграфа по вопросу + подключить multi-query аналогии (уже написаны). **H4** симметрия слоёв (регламенты в person, KnowledgeProfile/decisions в role). **H7** пропускная способность канала «расскажи, как решал». **H11** «материалы дела» из общего графа. — по показаниям baseline.
