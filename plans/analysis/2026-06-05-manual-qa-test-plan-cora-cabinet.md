# План большого ручного теста кабинета Коры (UX + техника)

> Дата: 2026-06-05 · Автор: Claude (по запросу владельца)
> Тип: план сквозного ручного тестирования (manual QA, ручное тестирование качества) боевого прода `https://meet.crossmark.ru`.
> Статус: ⏳ согласование плана → затем прогон по фазам.

## 0. Цель

Пройти кабинет Коры как живой пользователь и одновременно смотреть «под капот», фиксируя находки в **двух измерениях**:

1. **UX (удобство и понятность).** Понятно ли, что делать? Кнопка делает ровно то, что обещает её надпись? Нет ли тупиков, непонятных терминов, английских слов в русском интерфейсе, нелогичных переходов?
2. **Техника.** Нет ли битых вызовов (404 / 500 / 401 / 403 не к месту), ошибок в консоли, висящих/повторяющихся запросов (поллинг-шторм), расхождений между тем, что показал UI, и тем, что реально легло в базу.

## 1. Чем я наблюдаю (методология одного прохода)

На **каждом** шаге снимаю четыре слоя одновременно:

| Слой | Инструмент | Что ловлю |
|---|---|---|
| Что видит пользователь | `browser_snapshot` / скриншот | состав экрана, надписи кнопок, состояния (пусто/грузится/ошибка) |
| Console (как F12 → Console) | `browser_console_messages` | JS-ошибки, красные `Failed to load`, варнинги |
| Network (как F12 → Network) | `browser_network_requests` + детали запроса | статусы 2xx/4xx/5xx, тело ответа, дубли/поллинг |
| Реальное состояние в БД | `diag.ts` (read-only) | легла ли встреча/должность/сообщение; статус AI-цепочки; логи; LLM-вызовы |

**Ключевой приём — сверка двух сторон:** сделал действие в UI → тут же проверяю в `diag`, что данные реально появились и в правильном статусе. Расхождение «UI сказал ОК, а в базе пусто/ошибка» — это самый ценный класс находок.

`diag` строго **только чтение**. Любые изменения данных делаю исключительно руками через кабинет — как настоящий пользователь.

## 2. Критерии оценки и шкала важности

**UX-критерии (по каждому экрану):**
- надпись кнопки = её действие (нет «Сохранить», который удаляет; нет «Создать», ведущего в никуда);
- понятно без подсказки, что делать дальше; нет тупиков;
- состояния пусто / загрузка / ошибка — человеческие, на русском, с выходом;
- только русский язык в пользовательском интерфейсе (английские слова — находка), термины понятны не-разработчику;
- мобильная вёрстка не ломается (проверю ключевые экраны в узком окне).

**Технические критерии:**
- нет неожиданных 4xx/5xx; ожидаемые отказы (например, нет прав) — отдельно помечаю как «ожидаемо»;
- консоль чистая (ошибки = находка);
- нет дублирующихся/циклических запросов в простое;
- ответы быстрые (засекаю явно медленные > ~2–3 с);
- UI и БД сходятся.

**Шкала важности находки:**
- 🔴 **Crit** — блокирует сценарий / теряются данные / падает страница.
- 🟠 **High** — функция работает неверно или вводит в заблуждение, обход есть.
- 🟡 **Med** — заметное неудобство / косметический техдолг (напр. лишний 401 в консоли).
- ⚪ **Low** — придирка, «было бы лучше».

## 3. Формат записи находки

Каждую находку фиксирую единообразно:

```
[ID] severity · экран · слой(UX|Техника)
Что: одной строкой
Шаги: как воспроизвести
Ожидал / Получил:
Доказательство: статус запроса + url / текст ошибки консоли / результат diag
Гипотеза причины (если вижу по коду):
```

## 4. Сценарии теста

Иду путём реального человека: от первого входа до проведённой встречи с AI-отчётом. Каждый сценарий — отдельная фаза.

### S0. Онбординг и первый вход `[x]` — пройдено (см. RESULTS)
- Вход по выданным кредам, первый экран после логина (куда попадает новичок?).
- Принудительная/предложенная смена пароля («после первого входа смените пароль» из письма — есть ли этот флоу вообще?).
- Тур/подсказки для новичка (`tour-progress` уже дёргается — что он показывает?).
- Профиль: имя, аватар, email.
- _Сверка:_ `diag` — что аккаунт реально провязан с Org, какая роль.

### S1. Навигация и каркас кабинета `[x]` — пройдено (найден крит-баг детальных страниц)
- Пройти по всем пунктам бокового меню: каждая страница грузится, нет 404/500, заголовок соответствует пункту.
- «Подтверждения: N», «Помощник компании», «Concierge» — что это и совпадает ли поведение с надписью.
- Скрытые/пустые разделы (у нового пользователя многое пусто — как выглядит пустое состояние).

### S2. Оргструктура и должности `[x]` — пройдено (инвайт 403; должности OK)
- Создать должность/роль, заполнить поля, сохранить.
- Проверить обязательность полей, валидацию, понятность ошибок формы.
- Отредактировать, удалить.
- _Сверка:_ `diag` — должность реально создалась/обновилась/удалилась.
- _UX-фокус:_ понятно ли неподготовленному человеку, что такое «должность», «роль», «клон роли».

### S3. Concierge и «Помощник компании» — печать мыслей/вопросов `[x]` — чат 403
- Открыть Concierge (плавающий значок — главный вход), задать вопрос текстом.
- Проверить: ответ только текстом (по продуктовому правилу — без голосового вывода, без inline-кнопок в уточнениях).
- «Помощник компании» — чем отличается от Concierge, не дублируют ли друг друга (уже видно две разные кнопки — это потенциальная UX-находка).
- _Сверка:_ `diag llm-calls` — какой провайдер/модель ответили, не было ли ошибки цепочки.

### S4. Создание встречи `[x]` — 403 (ядро заблокировано демо-гейтом)
- «Создать встречу» → выбор типа (9 типов), параметры, гостевой доступ.
- Понятность выбора типа встречи (главное продуктовое отличие — влияет на AI-отчёт).
- Ссылка-приглашение, вход гостя без регистрации.
- _Сверка:_ `diag meetings` — встреча создалась с правильным типом/статусом.

### S5. Проведение встречи и запись `[—]` — ЗАБЛОКИРОВАНО (встреча не создаётся, S4-01)
- Зайти в комнату, проверить медиа-контролы (микрофон/камера/screen share), запись.
- _UX:_ понятно ли, что встреча записывается; как завершить.
- _Сверка:_ `diag trace --meeting <id>` — статус FSM, появились ли дорожки записи.
- _Примечание:_ полноценную многопользовательскую встречу имитировать сложно одним браузером — отметим как ограничение, проверим что доступно соло.

### S6. AI-отчёт по итогам встречи `[—]` — ЗАБЛОКИРОВАНО (нет встречи, S4-01)
- Дождаться/проверить генерацию отчёта под тип встречи.
- _Сверка:_ `diag trace` + `diag report --meeting <id>` + `diag llm-calls` — прошла ли цепочка transcription → speaker split → отчёт, или где встала.
- _UX:_ понятен ли отчёт, соответствует ли типу встречи.

### S7. Личный кабинет «Я», каналы, уведомления `[ ]`
- `/me`, каналы доставки (Telegram), настройки уведомлений.
- Честные состояния («бот не настроен», deep-link) — недавняя фича, проверить по факту.

### S8. Биллинг и лимиты `[ ]`
- Страница подписки/баланса (`billing/subscription` уже дёргается).
- _UX:_ понятно ли, что входит в тариф; нет ли английских слов.
- _Только просмотр_ — реальную оплату не провожу.

### S9. Кросс-секущие проверки `[~]` — мобайл OK, logout OK; остальное частично
- Мобильная вёрстка ключевых экранов (узкое окно).
- Поведение при отсутствии прав (ожидаемые 403 — не баг, фиксирую отдельно).
- Шторм поллинга (см. находку ниже) — замерить на нескольких экранах.
- Выход из аккаунта (logout) — чистый ли.

### S10. Трекер-задачник (SPRIN: доски, задачи, спринты, циклы) `[~]` — частично: создание проекта 403 (paywall), глубину заблокировало

> Запрос владельца: «сам не понимаю, как им пользоваться — как доски создавать и т.д.». Тестировать вглубь: и UX, и backend (NestJS) — что операции реально персистятся.

**UX-проверки:**
- Можно ли с нуля понять, как создать доску/проект/спринт — без инструкции.
- Создание задачи; смена **ответственного** и **приоритета** прямо в задаче (вопрос тестировщика — возможно ли это вообще).
- Доска (drag-and-drop между колонками Бэклог → В работе → …), Список, Календарь, Циклы, Входящие, Документы — что из этого реально работает, а что заглушка.
- Вкладка «Приложения» (интеграции: импорт Jira, Telegram-уведомления, Webhooks, AI-помощник проекта) — отделить рабочее от «Не настроено»/заглушек; убрать ложное обещание, если функции нет.
- Терминология: «Спринт», «Цикл», «Бэклог», «SPRIN» — понятно ли не-разработчику; нет ли английских слов.

**Backend-проверки (NestJS):**
- На каждое действие (создать доску/задачу, сменить ответственного/приоритет, перетащить карточку) — смотреть Network: статус, тело; затем сверять, что данные легли (diag/логи).
- Идемпотентность и валидация ручек трекера; нет ли 500 на пустых/граничных вводах.
- Соответствие модуля бэка фактическому поведению UI (по коду модуля трекера).

## 6. Уже найдено на этапе проверки инструментов (примеры формата)

```
[F-001] 🟡 Med · /login · Техника
Что: запрос профиля уходит до авторизации и падает красной ошибкой в консоли.
Шаги: открыть /login (ещё не залогинен).
Ожидал / Получил: тихую проверку сессии / [ERROR] 401 Unauthorized @ /api/v1/accounts/me.
Доказательство: console error + network #19 GET /api/v1/accounts/me => 401.
Гипотеза: гард/хук тянет accounts/me без проверки наличия токена; стоит не считать это ошибкой на публичной странице.
```

```
[F-002] 🟠 High(перепроверить) · /meetings · Техника
Что: циклический поллинг множества эндпоинтов в простое.
Шаги: залогиниться, ничего не делать ~1–2 мин на /meetings.
Получил: десятки повторов GET intake / pending-actions/count / me/proactive-notifications /
         feed/probe_question / feed/insight (см. network #141–165 и далее).
Доказательство: browser_network_requests — одни и те же запросы повторяются пачками.
Гипотеза: несколько независимых SWR/интервалов с коротким refreshInterval; стоит проверить
          частоту и объединить. Перепроверить — возможно часть из-за переоткрытий снапшота.
```

Это показывает: инструменты видят обе стороны, формат находок рабочий.

## 7. Гигиена теста (договорённости — нужно решение владельца)

- **Боевой прод.** Всё, что создам (должности, встречи, сообщения), — реальные данные. Предлагаю помечать тестовые сущности узнаваемым префиксом (напр. `[QA-test]`), чтобы потом легко вычистить руками.
- **Удаление за собой.** После прогона — список созданного, чтобы владелец (или я через UI) удалил.
- **diag — только чтение**, мутаций не делаю.
- **Деньги/внешние эффекты:** оплату не провожу; письма/Telegram-доставку — только если владелец подтвердит (уйдут реальные сообщения).
