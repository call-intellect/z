## 🟢 ЗЕЛЁНАЯ ЗОНА — что реально крепко (охранять от регресса)

| # | Что | Почему держится |
|---|---|---|
| G1 | **Владелец = кто решал, а не кто рассказал** | Структурно: владелец = `Issue.assignee` (`resolveOwnerPerson`), упомянувший владельцем не становится. Сценарии-сторожа `a5-ownership-solver` (Сергей рассказал → Михаил владелец), `a5-owner-not-mentioner` (Дарья рассказала → Иван) — держатся на реальном LLM. |
| G2 | **Одна задача = одно решение** | `tenantId_sourceIssueId` уникальный; повторный прогон без новых блоков → `skippedNoNew`, Δ=0 (идемпотентность подтверждена). |
| G3 | **Цикл 1 закрыл 2 настоящих дефекта** | Гейт содержательности (`hasConcreteMethod`) — «само решилось» больше не плодит карточку; рост клонов соисполнителей (`resolveSubjects`) — второй решавший растит свой клон. |
| G4 | **Соисполнитель НЕ подменяет рассказавшего** | `resolvePersonByHint` возвращает null при неуверенности → чужого в subjects не тащит (precision-bias промпта подтверждён на LLM). |
| G5 | **Стенд как инструмент окупился** | Он же нашёл дефекты, он же за один перепрогон доказал фиксы (было→стало) со сторожами-регрессами. |

**Важно:** G1 крепок только на «чистых» данных стенда (корпус задаёт `assignee=решавший` во всех 12).
Это же — источник иллюзии (см. R2, R3, Y6): на грязных прод-данных фундамент даёт трещины.

## 🔴 КРАСНАЯ ЗОНА — high-дефекты, реально теряющие знание

Ранжировано по силе удара по «памяти компании».

### R1 — Решения из встреч/чатов НЕ материализуются НИКОГДА `[самое ценное]`
- **Что:** детекция требует `re.payload->>'contextCardId' IS NOT NULL` (`service.ts:70,78`). Единственный писатель `contextCardId` — ответ на probe `task.method_capture` (`conversational-ingest.adapter.ts:77`). `ingestFreeNote`/`ingest`/meetings его НЕ пишут.
- **Удар:** человек рассказал «как починил» на планёрке или в чате — это НЕ станет «Решением задачи». Для платформы памяти — крупнейшая дыра захвата.
- **Стенд это маскирует:** `seed-reg-feed.ts:221` ставит `contextCardId` каждому блоку независимо от канала → метка канала косметическая, 92% PASS завышают покрытие каналов.
- **Фикс:** линковать how-solved блок ↔ Issue через связь блок↔задача на ingest встреч/чата, а не через `payload.contextCardId`.
- **Провабельность:** нет на текущем стенде (нужен новый detection-режим на реальном RawEvent без `contextCardId`). → **Большое ТЗ.**

### R2 — Задача без assignee, но с решателем в тексте → знание теряется целиком
- **Что:** `service.ts:155` `if (!ownerPersonId) return 'skippedNoOwner'` выполняется ДО refine (`:219`); `resolveOwnerPerson` возвращает null при Issue без assignee; solverNames рефайнера в этой ветке не запрашиваются.
- **Удар:** на проде (40–100 юзеров, грязные данные) «задача не назначена + Иван починил X» → решение не рождается, клон Ивана не растёт.
- **Фикс:** при null-owner фолбэк на рефайнер — единственный однозначный solverName резолвить в Person и брать владельцем (ограничить одним, чтобы не приписать чужое).
- **Провабельность:** да (adversarial-сценарий). → **Большое ТЗ** (пакет атрибуции).

### R3 — Владелец жёстко = assignee, даже если текст говорит про другого
- **Что:** `ownerPersonId` только из `resolveOwnerPerson(issue.assignees)`; `refined.solverNames` идут лишь в subjects.
- **Удар:** переназначенный/заведённый координатором тикет → решение уходит не тому, его клон впитывает чужую работу (та самая cross-clone-болезнь, но по владельцу).
- **Фикс:** сверять assignee с solverNames — `assignee ∉ solverNames` и назван ровно один решатель → владелец = решатель (или снизить confidence + аудит-расхождение).
- **Провабельность:** да. → **Большое ТЗ** (пакет атрибуции).

### R4 — При дополнении: компилятор выключен/упал → новый кусок теряется НАВСЕГДА и молча
- **Что:** `service.ts:263-266` на update при `compiled==null` (kill-switch OFF) или `!compiled.ok` (LLM-ошибка) `bodyMd=existing.solutionMd` — новые блоки НЕ мержатся, но `sourceBlockIds` юнионится (`:273`), версия++ и `CardVersion 'extension'` пишется. Следующий проход: `newBlockIds` пуст → `skippedNoNew` → **контент уже не пересобрать**.
- **Удар:** худший режим для памяти — тихая безвозвратная потеря дневной порции знания. Риск живой: kill-switch реален (Ship-On), сбои LLM часты.
- **Фикс:** на update без успешной компиляции НЕ помечать блоки потреблёнными и НЕ бампить версию (defer → повтор позже, когда компилятор вернётся).
- **Провабельность:** да (unit-тест control-flow + сценарий стенда с компилятором OFF). → **Цикл 2 (pick #3).**

### R5 — Гейт содержательности по длине (40 символов) режет краткие-но-конкретные решения
- **Что:** `service.ts:195-201` `totalChars < 40 → skippedGate` ДО рефайнера. `a5-trivial-gated` «Перезапустил под, всё поднялось» (32 симв) — конкретный метод, режется по длине; эталон это узаконивал как PASS.
- **Удар:** «Добавил индекс на user_id — стало быстро» (~38 симв) молча выбрасывается, хотя `hasConcreteMethod` вернул бы true. Потеря знания невидима.
- **Фикс:** тривиальность решать семантикой (`hasConcreteMethod`), длину оставить грубым предфильтром пустого (порог 40→15).
- **Провабельность:** да. → **Цикл 2 (pick #2).**

### R6 — Окно детекции по `createdAt`, но повтор мержится в СТАРЫЙ блок → рецидивы невидимы после 48ч
- **Что:** детект фильтрует `ib.createdAt >= now-48ч` (`service.ts:64,74`). `block-distill.worker.ts:308` переносит evidence нового draft-блока на старый canonicalId, `createdAt` победителя НЕ обновляется. «Снова 429» схлопывается в canonical недельной давности → выпадает из окна.
- **Удар:** флагманская фича «повтор ×N → кандидат в инструкцию» перестаёт видеть рецидивы.
- **Фикс:** фильтровать окно по свежести evidence (`GREATEST(IdeaBlockEvidence.sourceTimestamp / RawEvent.occurredAt)`), а не по `IdeaBlock.createdAt`.
- **Провабельность:** нет на текущем стенде (мерж не гоняется). → **Большое ТЗ.**

### R7 — Узкий набор how-solved signalType; A1 гонит «как я решил» мимо набора
- **Что:** `HOW_SOLVED_SIGNAL_SQL = reasoning/rationale/decision_basis/methodology_step`. `block-ingest.prompt.ts:353` требует past-tense результат («сделал», «закрыл») → `signalType=task_completed/done_item`, которых в наборе НЕТ. Стенд жёстко проставляет signalType из корпуса → классификация не гоняется.
- **Удар:** реальный % захвата ниже измеренного.
- **Фикс:** расширить набор (`task_completed/done_item`, привязанные к Issue) или ввести отдельный `how_solved`; A1-сценарии на сыром тексте.
- **Провабельность:** нет на текущем стенде (A1 не гоняется). → **Большое ТЗ.**

## Что делаем в цикле 2 (эта сессия) — 3 дёшево-доказуемых правки

1. **Честность стенда по субъектам** (Y1 + Y2) — только стенд, без прод-кода: заполнить `subjectPersons=[owner]` во всех 6 single-solver рулерах, ввести поле `mustNotSubject` (+ассерт), поправить линзу судьи (undefined ≠ «пусто»). *Гипотеза:* фантомные flawed 6→0, `subject_accuracy` 3/9→9/9, сторож утечки в subjects включён.
2. **Смысловой гейт вместо длины** (R5 + Y3) — прод-код: порог длины 40→15 (грубый предфильтр), тривиальность на `hasConcreteMethod`; `skippedNoMethod` в скоркарт. *Гипотеза:* `a5-trivial-gated` skipped→created, в отчёте появляется колонка среза по смыслу.
3. **Защита дополнения от тихой потери** (R4) — прод-код: на update без успешной компиляции defer (не потреблять блоки, не бампить версию). *Гипотеза (unit-тест):* компилятор OFF на дополнении → Δверсии=0, блоки не потреблены, повтор позже.
