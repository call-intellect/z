# GEPA вынесен из backend в отдельный контейнер z-gepa

## Что было поставлено

В проекте Python-приложение (GEPA prompt evolution — обёртка над `gepa`/`dspy`)
запускалось из NestJS через `child_process.spawn('python3', [runner.py])` ВНУТРИ
контейнера backend. Это: раздувало образ backend (pip install gepa/dspy через
`--break-system-packages` в alpine), мешало атомарности сборки, добавляло
attack surface и плодило дочерние процессы в API. Задача — вынести Python в
отдельный контейнер и переписать код взаимодействия (контейнер + API вместо
child_process).

## Как решал

Транспорт: **HTTP**. Python стал FastAPI-сервисом, backend ходит по
`POST {GEPA_SERVICE_URL}/optimize`. Контракт payload/ответа сохранил 1:1 —
переписал только транспорт.

Файлы (коммит `03b214cc`):
- `backend/python/gepa/server.py` (new) — FastAPI `/optimize` (вызывает
  существующий `_run_gepa` из `runner.py`, не дублируя логику), `/health`,
  `/version`. Ошибки → JSON `{error,...}` с HTTP 200, чтобы backend различал по
  полю `error`, как раньше различал по stdout subprocess'а.
- `backend/python/Dockerfile` (new) — `python:3.11-slim`, pip install, непривилегированный юзер, `CMD python server.py`.
- `gepa-runner.service.ts` — `spawnRunner` (child_process) → `callGepaService`
  (`fetch` + `AbortController`). Тип результата, метрики
  (`success/failed/timeout/skipped_no_python`), graceful-fallback сохранены.
  Классы ошибок матчатся по подстроке message: `unavailable` (ECONNREFUSED/DNS/5xx),
  `timeout` (AbortError). `skipped_no_python` оставил как label «сервис недоступен»
  ради совместимости метрик/дашбордов.
- `env.schema.ts` / `typed-config.service.ts` — `GEPA_PYTHON_PATH`/`pythonPath`
  → `GEPA_SERVICE_URL`/`serviceUrl` (default `http://gepa:8000`).
- `backend/Dockerfile` — убраны `python3 py3-pip`, `pip install gepa`, `COPY python`.
- `docker-compose.yml` — сервис `gepa` (build `./backend/python`, `env_file: [.env]`,
  healthcheck, только `z-internal`). `docker-compose.dev.yml` — `gepa` с портом
  `127.0.0.1:58000` (dev-backend крутится процессом на хосте).
- Тесты: `gepa-runner.service.spec.ts` — моки `spawn` → `fetch` (включая timeout
  через abort signal). `gepa-ab-monitor.cron.spec.ts` — `pythonPath` → `serviceUrl` в моке.
- Docs: `tech-stack.md`, `prod-deploy-log.md` (Шаг 1/11/12 обновлены inline),
  `backend/python/gepa/README.md`.

`runner.py` оставил как ядро логики (`_run_gepa`) + CLI-режим для smoke-теста
`gepa-runner-real.spec.ts` — минимальное изменение, обратная совместимость CLI.

## Чему научился

- **Правило проекта (записал в память):** в этом проекте НИЧЕГО не запускать
  через `child_process` — особенно Python. Python-приложение → отдельный
  контейнер + HTTP API. См. memory `feedback-no-child-process-python-container`.
- `preserve-caught-error` (eslint): любой `throw new Error(...)` из `catch` должен
  нести `{ cause: err }`. Грабля — словил на lint после tsc/build (tsc это не ловит).
- В этом окружении заблокированы `rm -rf`/`find -delete` и доступ к `.env*` —
  чистить артефакты (`__pycache__`) и править `.env.example` пришлось перекладывать
  на пользователя; стейдж только явными путями обходит мусор.
- При выносе subprocess'а в сервис важно перенести env-зависимости: gepa-контейнер
  получает весь `.env` (`env_file`), т.к. litellm/deepseek-креды раньше наследовались
  subprocess'ом от backend.

## Осталось пользователю
- Поправить `.env.example`: убрать `GEPA_PYTHON_PATH`, добавить `GEPA_SERVICE_URL`.
- При выкате: `docker compose build backend gepa && docker compose up -d`.
