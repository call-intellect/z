# Z — обзор для команды интегрируемого проекта

> **Кому документ:** разработчикам и продакт-менеджерам проекта-источника данных (далее «ваш проект»), которых попросили подумать, какую информацию и как они смогут отдавать в Z.
> **Что от вас на выходе:** список каналов / источников / выгрузок, которые у вас реально есть и которые можно подключить к Z. Без обязательств по форматам — это второй шаг.

---

## 1. Что такое Z в одном абзаце

Z — это **корпоративная AI-память компании**. Любая входящая информация (видеовстреча, переписка в Telegram, email, звонок в саппорт, ручная заметка сотрудника, аналитическое событие из продукта) проходит через единый pipeline, превращается в структурированные **блоки знания**, дедуплицируется, связывается в граф и становится доступной через поиск, AI-чат и дашборды.

Z **не заменяет ваши инструменты** — он накапливает поверх них смысловой слой, к которому потом можно задавать вопросы вроде «что клиент Ромашка говорил про доставку за последние полгода во всех каналах сразу».

В MVP главный источник — AI-видеовстречи (LiveKit-комната + AI-отчёт под тип встречи). Но архитектура с первого дня рассчитана на то, что встречи — лишь **один из** источников.

---

## 2. Главная идея — почему вам это интересно

Сейчас у вашего проекта данные размазаны по разным системам: что-то в БД, что-то в Telegram-чатах, что-то в почте, что-то в выгрузках. Каждый источник живёт своей жизнью, на стыках теряется контекст.

Z решает эту проблему **сбоку**, не ломая ваши процессы:

1. Вы оставляете всё как есть в своих системах — БД, чаты, почта, аналитика.
2. Z подключается **как ещё один потребитель**, забирающий копию данных (или поток событий) по согласованным каналам.
3. У Z данные нормализуются в единый формат, дедуплицируются и кладутся в общий граф знаний.
4. Дальше любой сотрудник вашего проекта может задавать вопросы AI-чату Z и получать ответы со ссылками на первоисточник — в вашей переписке, в вашей БД, в вашей встрече.

Прямой выгоды две:
- **Сквозной поиск и Q&A по всем каналам сразу** — то, чего нельзя получить ни в Telegram, ни в CRM, ни в почте по отдельности.
- **AI-саппорт с памятью** — отдельный ассистент-агент со своим набором вопросов-ответов, который отвечает клиентам/сотрудникам по тому, что мы вручную в него закладывали (см. раздел 6).

## 3. Архитектура простыми словами — пять слоёв

```
┌────────────────────────────────────────────────────────────┐
│ 5. Продуктовые поверхности                                 │
│    AI-чат, поиск, дашборды, карточки клиентов, саппорт     │
├────────────────────────────────────────────────────────────┤
│ 4. Тонкие AI-агенты                                        │
│    задачи, главы, хайлайты, ролл-апы карточек, темы        │
├────────────────────────────────────────────────────────────┤
│ 3. ЯДРО ЗНАНИЙ (главное)                                   │
│    блоки знания + сущности + темы + связи + поиск          │
├────────────────────────────────────────────────────────────┤
│ 2. Сырая память                                            │
│    иммутабельный первоисточник (что пришло, как пришло)    │
├────────────────────────────────────────────────────────────┤
│ 1. Адаптеры источников                                     │
│    встречи, чаты, email, звонки, БД, web-формы, боты       │
└────────────────────────────────────────────────────────────┘
```

Принципиальное правило: **слой 1 (адаптеры) — это всё, что вас касается**. Вы готовите данные на своей стороне в любом удобном виде; адаптер на стороне Z приводит их к стандарту. Дальше Z разбирается сам.

## 4. Какие источники Z умеет / будет уметь принимать

| Тип источника        | Что это в реальности                                                                 | Зрелость в Z        |
|----------------------|---------------------------------------------------------------------------------------|---------------------|
| **Встречи**          | LiveKit-комната, запись по дорожкам, транскрипт, AI-отчёт под тип встречи            | Готово (MVP)        |
| **Чаты / мессенджеры** | Telegram-боты в групповых и личных диалогах; экспорт каналов; webhook-и из Slack    | На стадии адаптера  |
| **Email**            | IMAP-чтение почтового ящика или подписка на forward-адрес `*.crossmark.ru`            | На стадии адаптера  |
| **Звонки / телефония** | Запись разговоров + транскрипт от телефонии (Mango, Sipuni, UIS, OnlinePBX и др.)   | На стадии адаптера  |
| **Боты / web-формы** | Любая форма обратной связи, сбор фидбэка, чат-виджет с сайта                          | На стадии адаптера  |
| **БД-выгрузки**      | Снимок таблиц / поток изменений (CDC) / периодический ETL из БД вашего проекта        | На стадии адаптера  |
| **Аналитика**        | События продукта (Amplitude/Mixpanel-style) — клики, конверсии, пути пользователей    | На стадии адаптера  |
| **Ручной ввод**      | Заметки сотрудников, голосовые надиктовки, ручной дамп мысли                          | На стадии адаптера  |

Все «на стадии адаптера» — это значит, что ядро (слои 2-5) умеет принимать такой источник через универсальный pipeline; конкретный адаптер пишется под канал, когда подтверждается ценность. **Ваш список источников нам нужен в том числе для приоритизации — какие адаптеры писать первыми.**

## 5. Что именно нам нужно от вас подумать

Не пишите интеграцию. Пока что задача — **инвентаризация**. Вам нужно посмотреть у себя и составить список:

### 5.1. Каналы переписки

- Какие Telegram-чаты / каналы / боты у вас есть и где идёт ценная коммуникация (внутренняя, с клиентами, с подрядчиками)?
- Какие почтовые ящики используются для переписки с клиентами / партнёрами? (`sales@`, `support@`, `info@` и т.п.)
- Есть ли корпоративный Slack/Mattermost/Rocket.Chat?
- Есть ли веб-чат на сайте, чат-бот на лендингах, форма обратной связи?

### 5.2. База данных проекта

- Какие сущности у вас в БД (клиенты, заказы, заявки, тикеты, проекты, документы, договоры — что угодно)?
- Какие из них имеют смысл для семантического анализа? (Например, поле «комментарий менеджера» к заказу — да; поле «дата создания» — нет.)
- Какие таблицы меняются часто, какие — почти статика?
- Есть ли уже репликация / CDC / поток изменений, который мы могли бы подцепить?

### 5.3. Аналитика и события продукта

- Что вы трекаете (Amplitude, Mixpanel, Yandex.Metrica, GA, свой ClickHouse)?
- Какие события несут смысл (не просто `page_view`, а «клиент отправил жалобу», «пользователь оставил оценку 1 звезда», «сделка перешла в стадию переговоров»)?

### 5.4. Звонки и голос

- Ведёте ли запись звонков клиентам?
- Через какую телефонию?
- Есть ли уже транскрипция или только аудио?

### 5.5. Q&A для саппорт-ассистента (см. также раздел 6)

- Кто у вас сейчас отвечает на повторяющиеся вопросы клиентов/сотрудников?
- Можете ли начать собирать пары «вопрос → доверенный ответ» вручную в общую таблицу/Notion/Google Sheet?
- Сколько таких пар реально набрать за месяц?

### 5.6. Чувствительные данные

- Что точно **нельзя** выгружать (персональные данные клиентов в чистом виде, банковские реквизиты, медицинские данные)?
- Что нужно маскировать перед отправкой в Z?
- Есть ли у вас процедура DPA / соглашения о персональных данных, которая накладывает ограничения?

**Формат выдачи:** простая таблица или список — название канала, тип, объём (примерно), уровень чувствительности, как технически до него добраться. Без детального API-описания, это уже следующий шаг.

## 6. Особый случай — саппорт-ассистент с Q&A

Это отдельная продуктовая линия поверх Z:

1. Человек-эксперт вручную пишет пары «вопрос → доверенный ответ» (в Google Sheet, Notion или прямо в админке Z).
2. Эти пары загружаются в Z как отдельный источник с явной разметкой «trusted Q&A».
3. Поверх собирается AI-агент-саппорт, который:
   - Сначала пытается ответить из «доверенного» Q&A.
   - Если не нашёл — может расширить ответ информацией из общего корпуса (встречи, переписка, БД).
   - Всегда показывает источник ответа, чтобы можно было проверить.

**Что важно для вашей стороны:** саппорт-ассистент работает на своём срезе знаний. Это значит, что Q&A-коллекция, которую вы будете собирать, будет приоритетным источником для саппорт-агента, но при этом он *не закрыт* от общего корпуса. У вас есть выбор:

- **Изолированный режим** — саппорт отвечает строго по Q&A, не лезет в общую память. Безопасно, но узко.
- **Расширенный режим** — Q&A приоритетно, но при отсутствии ответа агент идёт в общий корпус с пометкой «уверенности меньше». Полезнее, но требует доверия к данным в общем корпусе.

Это решение принимается позже. Сейчас от вас — просто понимание, кто будет собирать Q&A и в каком объёме.

## 7. Что Z делает с вашими данными после получения

Кратко, чтобы вы понимали, что происходит на нашей стороне:

1. **Ingest.** Адаптер принимает ваш payload (текст, аудио, событие из БД), нормализует, кладёт в **сырую память** как иммутабельный первоисточник. Здесь данные ещё не анализируются — просто хранятся «как пришло».
2. **Distill.** Раз в N минут pipeline разбирает свежие записи в сырой памяти, превращает их в **блоки знания** — структурированные единицы вида «ключевой вопрос / доверенный ответ / упомянутые сущности / ссылка на источник с цитатой». Похожие блоки сливаются в канонический через LLM-merge.
3. **Linker.** Между блоками и сущностями (клиенты, продукты, проекты) автоматически строятся типизированные связи: «упоминает то же», «развивает», «противоречит», «следствие».
4. **Retrieve.** Поверх этого работают поиск, AI-чат, дашборды и тонкие агенты (задачи, главы встреч, темы).

Любой ответ AI **всегда восстанавливается до источника** — пользователь Z видит «эта мысль пришла из вашего письма от 14.05» с ссылкой на оригинал.

## 8. Что Z **не делает** — границы

- **Не ходит в вашу боевую БД из прод-кода Z.** Любая интеграция — через явный канал поставки (выгрузка, очередь событий, ETL, API-вебхук). Прямой коннект к вашей БД — максимум на этапе обсуждения архитектуры.
- **Не подменяет ваши инструменты.** Z не становится вашим CRM, не заменяет вашу почту, не управляет вашими чатами. Только читает.
- **Не делает SSO** между Z и вашим проектом на первом этапе. Сотрудники заходят в Z по своим логинам / приглашениям от админа Org. Если потом понадобится единый вход — обсудим отдельно.
- **Не рассылает ничего от вашего имени.** Z не пишет письма, не шлёт сообщения в Telegram, не звонит. Только пассивное накопление и поиск.
- **Не хранит данные сверх retention-периода.** Срок хранения настраивается отдельно для каждой Org-учётки и каждого типа источника.

## 9. Multi-tenancy и что значит «ваша Org»

Z — multi-tenant SaaS. Ваш проект подключается как отдельная **Org** (учётная запись компании). Внутри Org:

- **Owner** — главный администратор, видит и настраивает всё.
- **Менеджеры** — обычные пользователи, по умолчанию видят встречи друг друга и общий корпус знаний компании.
- **Строгий режим** (опционально) — менеджер видит только свои источники + результаты, общие сущности и темы.

Это значит, что данные вашего проекта **не пересекаются** с данными других клиентов Z. Все таблицы ядра содержат `tenantId`, изоляция гарантирована на уровне БД.

## 10. Что нужно сделать сейчас — короткий чек-лист для вас

- [ ] Прочитать этот документ командой (тимлид + продакт + один-два разработчика, которые знают вашу архитектуру лучше всех).
- [ ] Составить список источников по разделу 5 — пусть он будет неполный, без деталей; нам важнее понять «что вообще есть», чем «как это технически отдать».
- [ ] Отметить, какие источники для вас критичны для бизнеса в первую очередь (с чего вообще есть смысл начать).
- [ ] Отметить чувствительные данные и красные линии, что точно нельзя выгружать.
- [ ] Назначить одного человека, который будет отвечать на наши вопросы по интеграции.
- [ ] Запланировать встречу с нашей стороной через ~1–2 недели — обсудить список и приоритеты.

Дальше уже будет конкретный технический контракт по каждому каналу: endpoint, формат, аутентификация, идемпотентность — мы пишем это под утверждённый список, а не заранее.

## 11. Кратко — что у вас должно остаться в голове после чтения

1. Z — это «второй мозг» компании, который собирает информацию из любых каналов и даёт её через AI-чат и поиск.
2. Главное ограничение — данные сначала должны до нас доехать. Каналы готовите вы; формы поставки согласуем вместе.
3. Минимальный шаг — собрать список того, что у вас есть. Технику обсуждаем после.
4. Q&A для саппорт-ассистента — отдельный поток, его собирают руками люди-эксперты.
5. Z не лезет в ваши системы, не заменяет их, не рассылает ничего от вашего имени. Только пассивный приём + анализ + ответы.
