# Аналитика — Единый drill-down + provenance parity

## 0. Рамка проблемы

**Симптом (от пользователя-клиента, скрин 2026-07-01):** в панели «Задачи» на встрече строку нельзя открыть, кружок выглядит кликабельным (можно отметить «выполнено»), но мёртв.

**Iceberg — корень глубже симптома.** Это не баг одного виджета. Провенанс-хребет (клик → первоисточник) построен ТЗ 2026-06-20 и работает для решений/регламентов/идей/журнала хода задачи, но **применён неравномерно**: на части поверхностей сущность рендерится как «мёртвый» текст/иконка — есть данные-источник, но нет ни перехода на второй уровень, ни аффорданса «откуда». Плюс свежий редизайн дашборда («День/Неделя/Месяц компании») **регрессировал**: показывает блокеры/риски/идеи/конфликты, но ни один элемент не проваливается.

**Две конкурирующие формулировки:**
- **Ф-A (узкая):** «почини кликабельность там, где её забыли» — точечные фиксы per-поверхность.
- **Ф-B (структурная, выбрана владельцем):** «сделай кликабельность/провенанс СВОЙСТВОМ сущности, а не поверхности» — единый контракт, по которому любая атомарная сущность с резолвимым источником автоматически проваливается и показывает «откуда», а элемент без источника не притворяется кликабельным. Ф-B чинит и текущие дыры, и будущие (новая сущность/поверхность наследует инвариант).

**Кто страдает (роли Z):** владелец/CEO (видит блокер/конфликт на дашборде, не может проверить «откуда это» → не доверяет → игнорирует); руководитель (видит задачу встречи, не может открыть); рядовой (видит цель, не понимает, из какого разговора она родилась). Прямая связь с доверием к автоизвлечению.

**Метрика «решено»:** доля атомарных сущностей на поверхностях, у которых (а) есть переход на второй уровень и (б) кликабельный аффорданс «откуда» с прыжком к моменту-первоисточнику (при наличии источника и права зрителя) → цель 100% для перечисленных в §2 живых сущностей; и 0 «мёртвых аффордансов» (элемент выглядит кликабельным, но не резолвится).

## 1. Дерево вопросов (MECE) — каркас будущих фаз

Корень: «любая видимая сущность → клик → второй уровень → откуда, с учётом прав зрителя».

1. **Инвентарь.** Какие сущности реально живут на фронте сейчас и на каких поверхностях появляются? (§2)
2. **Второй уровень.** У каких есть детальная карточка/панель (drill), у каких нет? (§2 матрица)
3. **Откуда.** У каких есть резолвимый источник в данных (`sourceBlockIds`/evidence) и кликабельный аффорданс к моменту? (§2, §4)
4. **Права зрителя.** Как фильтровать источник по доступу зрителя, чтобы drill не стал деагрегацией/утечкой? (§4 инвариант, §5 конфликты)
5. **Честность аффорданса.** Как гарантировать, что «кликабельно ⟺ есть непустой резолвимый источник» — не больше и не меньше? (§4 red-team Р3)
6. **Особый класс — конфликт/трение между людьми.** Приватность vs дифференциатор: до какого уровня раскрывать источник? (§3, §5 Р1)

**Ключевые факты кода:**
- `SignalRow` в `DaySignalsGrid.tsx` — презентационный `div`, **никогда** не ссылка → ни риск/идея/конфликт не кликаются. Тот же анти-паттерн в Week/Month (0 кликабельных).
- Провенанс-контракт бэка: `ProvenanceEntityType = decision | issue | regulation | instruction` (`provenance.service.ts:16-20`, VALID `:552-556`). Задача=issue. **Цель, блокер, трение, insight, идея — вне контракта.**
- Конфликты: `operations-dashboard.service.ts:543-604` читает `EntityLink` (relationType ∈ TEAM_FRICTION), `select` **не включает** `sourceBlockIds` (`:560-569`), маппинг отдаёт только имена+причину+% (`:590-604`). Источник есть на модели, потерян в проекции.
- Регресс дашборда: в реестре есть `BlockersByThemeWidget` с готовым `ProvenanceDrawer`, но `DayCompanyHero` монтирует некликабельный `DayBlockers`.
- **E (сквозной корень, `04_не-сделано`):** задачи и их журнал хода из встреч fast-путём идут с `evidenceBlockIds:[]` (`meeting-report-fast.worker.ts:480`; `MeetingReportFastTaskSchema` несёт только title/assigneeRaw/dueDateIso/sourceQuote/confidence, IdeaBlock в fast-воркере не создаётся) → `deepLink=null` → прыжок к моменту мёртв ИМЕННО для сущностей, рождённых на встрече. Даже где `ProvenancePreviewSnippet` рисуется, кнопка мертва.

**Уже готово к переиспользованию (провенанс-хребет, ТЗ 2026-06-20):** `ProvenanceService.resolve(entityType, id, viewer)` с deny-by-default фильтром по группам доступа (`KnowledgeAccessResolver.partitionProjectionsByAccess`); `resolveByRawEventIds` (батч); `buildDeepLink` (мс→`/meetings/:id?t=<sec>`); эндпоинт `GET /provenance/:type/:id`; фронт `ProvenancePreviewSnippet / ProvenanceChip / ProvenanceDrawer / ProvenancePopover`; domain `ProvenanceRef`; ленивый `useProvenance`; разметка `attribution: quoted|inferred`.

## 3. Ландшафт аналогов (РФ + зарубеж, snapshot 2026-07-02)

Рынок «клик→источник» уже разобран в анализе 2026-06-20 (Glean/Gong/Onyx/МТС Линк/Яндекс Нейро); здесь — только новое по drill-в-сигнал на дашбордах и по конфликтам между людьми.

| Класс | Игроки | Что умеют | Вывод для Z |
|---|---|---|---|
| Meeting/Revenue Intelligence | Gong, Fireflies, Grain | Клик по инсайту/риску → прыжок к моменту звонка с цитатой (Gong: 3+ точки входа; Fireflies Soundbites — URL к таймкоду) `[verified: help.gong.io, guide.fireflies.ai]` | **table-stakes** для встреч — мы просто закрываем гигиену |
| Enterprise Search | Glean, Onyx | Citations first-class, клик→нативный источник+preview; инвариант «citations never grant new access» / ACL-mirroring `[verified: docs.glean.com, github.com/onyx-dot-app]` | **копируем инвариант прав зрителя дословно** (наш `KnowledgeAccessResolver`) |
| Трекеры/дашборды | Linear, ClickUp, Asana | Клик по датапоинту виджета → отфильтрованный список → карточка задачи (first-party объект, не цитата разговора) `[verified: help.clickup.com, linear.app/docs]` | **table-stakes** для задач |
| People/Org-health | Culture Amp, Viva/ONA, Gong People | Трение/силосы показывают **только агрегатом**; drill к человеку/моменту **архитектурно запрещён** приватностью: «Rule of 5» / min-group-size, де-идентификация, anti-triangulation `[verified: support.cultureamp.com 2026-05-21, learn.microsoft.com/viva, culturemonkey.io]` | см. §5 — это одновременно наш ров и наш риск |

**Главный рыночный вывод:** паттерна «конфликт/трение между конкретными людьми с кликом → к моменту разговора-первоисточника» на рынке **не найдено**. Revenue-intelligence умеет drill-to-moment, но не про внутреннее трение; org-health умеет про трение, но **намеренно** без drill к человеку/моменту (n<5 подавляется). → **Конфликты (D) — дифференциатор/ров, а не догон.** Но именно потому, что все конкуренты закрыли это приватностью, наш drill обязан строиться на инварианте прав зрителя, иначе ров = приватностный риск (§5).

**Единый инвариант (переписан по red-team Р3):** не «всё видимое кликабельно», а **«элемент несёт кликабельный аффорданс ⟺ у него есть непустой резолвимый первоисточник, доступный этому зрителю; иначе аффорданса нет»**. Кликабельность рендерится по наличию provenance, а не по типу элемента → «выглядит кликабельным, но мёртв» невозможен по построению. Агрегаты/счётчики/средние (например «7 рисков», «средний прогресс целей») — статичны или дают «раскрыть список», НЕ «провалиться к цитате». Соблюдать правило прогрессивного раскрытия ≤3 уровня `[verified: nngroup.com, uxpin.com]`.

## 5. Матрица вариантов по спорным развилкам (с состязательным проходом)

### Развилка D-1 — где хранить источник конфликта/трения

| Критерий | A. Денорм-снимок на сущности трения (`previewQuote` как у Decision) | B. On-demand резолв через ProvenanceService по `EntityLink.sourceBlockIds` (рекоменд.) | C. Новая модель-источник трения |
|---|---|---|---|
| Staleness (трение — derived, пересчитывается кроном) | 🔴 снимок протухает при пересчёте, нужна инвалидация `[inferred: event-sourcing projection staleness]` | 🟢 резолв всегда по актуальному набору блоков | 🟡 та же проблема + миграция |
| Переиспользование | 🟡 копирует чужой паттерн без нужды | 🟢 сервис + `EntityLink.sourceBlockIds` уже есть | 🔴 новая сущность |
| Масштаб (трений единицы-десятки) | 🔴 денорм ради N+1, которого нет | 🟢 N+1 неощутим на коротком списке | 🔴 избыточно |
| Стоимость | средняя | **низкая** | высокая |

**Вывод D-1: B.** Red-team подтвердил: денорм на пересчитываемой derived-величине = гарантированное протухание; резолв через сервис снимает staleness и переиспользует существующий `sourceBlockIds`. Правка: `select` + DTO + резолвер.

### Развилка D-2 — глубина раскрытия источника конфликта (приватность)

| Критерий | A. Полная цитата «кто-что-сказал» всем по фильтру групп | B. Двухуровнево: агрегат/тема всем, вправе; дословно — за отдельным правом (владелец/HR) (рекоменд.) | C. Только агрегат, без дословного вообще |
|---|---|---|---|
| Приватность (трение n=2 < «Rule of 5») | 🔴 нарушает отраслевой минимум-групп `[verified: cultureamp, culturemonkey]` | 🟢 дословное гейтится ролью, как «Strong»-уровень Culture Amp | 🟢 |
| Ценность/ров | 🟢 но ценой эскалации | 🟢 сохраняет дифференциатор для того, кто вправе | 🟡 теряет часть рва |
| Риск эскалации конфликта | 🔴 «вещдок» одной стороне | 🟡 ограничен кругом вправе | 🟢 |

**Вывод D-2: B.** Дифференциатор (drill к моменту трения, которого нет у конкурентов) сохраняется, но дословное «кто что сказал» открыто только владельцу/HR-роли — не общим фильтром групп. Это и ров, и защита от приватностного риска, на который все конкуренты ответили подавлением.

### Развилка B-1 — цель: снимок или on-demand

| Критерий | A. Денорм-снимок previewQuote + backfill (как Decision/Issue) | B. On-demand резолв, без снимка, без backfill (рекоменд.) |
|---|---|---|
| N+1 на списке | 🟢 но список целей короткий → выигрыша нет | 🟢 неощутим на коротком списке |
| Staleness | 🔴 снимок протухает при смене источника | 🟢 всегда актуально |
| Стоимость | 🔴 миграция + backfill-скрипт | 🟢 добавить `goal` в резолвер |

**Вывод B-1: B.** Red-team: денорм оправдан на длинных горячих списках (Decision/Issue/Regulation — оставляем как есть), не на коротком списке целей. Snapshot/backfill не вводить, пока замер не покажет реальный N+1.

### Развилка G-1 — как обобщить провенанс-контракт на новые сущности

| Критерий | A. Добавлять enum+case per-сущность (goal, entity_link, blocker, insight, idea) | B. Обобщённый резолвер «любая сущность с `sourceBlockIds`» + маленький реестр (рекоменд.) |
|---|---|---|
| Рост | 🔴 N новых case-ов, легко забыть при N+1-й сущности | 🟢 новая сущность с `sourceBlockIds` наследует инвариант |
| Права зрителя | одинаково (обе через `partitionProjectionsByAccess`) | одинаково |
| Совместимость | 🟢 | 🟢 текущие 4 типа = частный случай |

**Вывод G-1: B** — это техническое воплощение структурной формулировки Ф-B: инвариант становится свойством «есть `sourceBlockIds`», а не списком типов. (Конфликт — с надстройкой D-2 по глубине.)

## 6. Рекомендация (ADR-каркас)

**Контекст Z:** провенанс-хребет готов, но применён неравномерно; владелец выбрал структурное решение с бэкендом.

**Решение:** единый инвариант «кликабельно ⟺ есть резолвимый источник, доступный зрителю», реализованный через обобщение `ProvenanceService.resolve` на любую сущность с `sourceBlockIds` (G-1:B), on-demand без денорма для новых сущностей (B-1:B, D-1:B), с двухуровневой глубиной для конфликтов (D-2:B). Раскатка волнами по зависимостям, но **одна архитектура**:
- Приоритет 1 — **A** (задача из встречи, фронт, прямая жалоба).
- **B** (цель), **C** (дашборд блокер/риск/идея), **D** (конфликт, дифференциатор+приватность), **E** (deep-link из встреч — сквозной корень).

**Последствия:** новая сущность/поверхность наследует drill+откуда бесплатно; «мёртвых аффордансов» нет по построению; конфликт — управляемый дифференциатор; deep-link оживает везде после E.

## 7. Открытые вопросы владельцу (каждый с рекомендацией)

- **В-1. Глубина источника конфликта (D-2).** Рекомендую **B** (агрегат/тема всем вправе; дословно «кто-что-сказал» — только владельцу/HR-роли), потому что trение n=2 ниже отраслевого «Rule of 5», а полная цитата = риск эскалации; так ров сохраняется без приватностного провала. Альтернатива C (совсем без дословного) — если хочешь максимально консервативно.
- **В-2. Кто «вправе» на дословный источник конфликта.** Рекомендую владелец + admin (роли уже есть в `nav-config` LEADERSHIP_ROLES). Нужна ли отдельная HR-роль — решаемо позже, не блокирует.
- **В-3. Порядок E (deep-link из встреч).** Рекомендую включить в общую бэкенд-волну (без него «откуда» у всех meeting-рождённых сущностей — сниппет без прыжка). Альтернатива — отдельным ТЗ следом, если хочешь быстрее выкатить A+B+C+D.

## 8. Допущения и риски

- **[feasibility]** `EntityLink.sourceBlockIds` содержит валидные block-id с evidence (не пусто у реальных трений) — **[assumption, проверить на «ооо ромашка»/«Стрела»]**; если пусто — конфликт упирается в тот же E.
- **[desirability]** Владельцу ценно проваливаться к моменту трения — **[verified: прямой запрос владельца]**.
- **[viability/приватность]** Двухуровневый гейт (D-2) достаточен против деагрегации — риск утечки «кто что сказал» рядовому; ревью `strict-production-review-gate` обязателен на путях D.
- **Staleness** снят выбором on-demand (D-1:B, B-1:B).
- **Over-linking** снят инвариантом «кликабельно ⟺ есть источник» (Р3) + правилом ≤3 уровня.
- **E — не дешёвый:** нужен матчинг IdeaBlock или evidence-блок в fast-воркере; риск, что fast-путь намеренно лёгкий (латентность отчёта) — оценить в ТЗ.
