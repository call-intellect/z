## Архитектурные паттерны (новые в этой сессии)

1. **`viewedUserId` query-фильтр** — расширение существующего endpoint
   ActivityFeed без отдельного endpoint для «вопросов AI этому человеку».
   Простое поле в Zod schema + where-фильтр, поверх существующего
   visibility scopedToMe. Применимо к ленте, нотификациям, любым
   per-target read-эндпоинтам.

2. **Cache-friendly inverted threshold KpiHero** —
   `<KpiHero threshold={{green:24, yellow:72, inverted:true}}>`. Для
   KPI «меньше = лучше» (KnowledgeVelocity median часов, hanging
   decisions). Inverted флаг переворачивает логику цветов без
   дублирования компонента.

3. **Mega-agent для 5 cron'ов одной schema-волной** — C1 закрыл 5 фаз
   ТЗ за один agent-call. Ключ: общая schema:push, общий шаблон cron
   (`forecaster.cron.ts` как образец), общая регистрация в module. Это
   ~3-5× быстрее чем 5 последовательных агентов.

4. **Параллельные агенты на независимых модулях** — B1 (tracker/sprints)
   и B2 (conversational/concierge) запускались одновременно. Файлы не
   пересекались, оба ушли по своим путям, я объединил commit. Сэкономил
   ~50% wall-clock.

5. **Единый pulse-patterns endpoint** — вместо 7 endpoints для 7 виджетов
   Волны 6 сделал один `getPulsePatterns()` с `Promise.all` по 7 методам.
   Frontend делает 1 запрос вместо 7. Backend кодa в 5-6 раз меньше.

6. **Chained dispatch для event-driven worker'ов** — Meeting ROI
   срабатывает после analyze.worker через DashboardQueueService.
   Optional inject не ломает DI существующих модулей.

7. **`SignalType` enum mismatch — proxy через ближайшие значения** —
   ТЗ упоминает signalType='insight' и 'decision_basis' которых нет
   в текущей онтологии. Агенты использовали ближайшие
   (idea/knowledge_gap/fact для learning, alternatives JSON для type-1)
   с inline-комментарием. Лучше чем падать на missing enum.

## Уроки

- **Параллельные сессии Claude Code → перепроверка git status**.
  Untracked файлы в `plans/tz/2026-05-31-*.md` (7 шт) — это другая
  сессия делает несвязанные ТЗ. Каждый коммит проверял что не задел
  их.
- **B2 видел B1 в промежуточном состоянии** — он запустил build
  когда B1 ещё писал sprint-analyst.service.ts → отчёт «build падает».
  После фактического завершения обоих агентов build зелёный. Урок:
  типичные ошибки параллельной разработки — последний слово
  оркестратора (cd backend && bun run build && bun run typecheck).
- **Decimal(4,3) vs Decimal(8,3)** — в ТЗ §4.1 указан Decimal(4,3)
  для Meeting.roiScore. Это потолок 9.999, что недостаточно для
  high-intensity встреч. В C2 явно сказал агенту использовать 8,3 —
  агент честно отметил расхождение с ТЗ в отчёте. Это правильный
  паттерн (явная подстройка ТЗ оркестратором, а не «по своему усмотрению»).
- **22 фазы за одну сессию** — повторил прошлый рекорд (27-28 фаз),
  не побил. Сочетание факторов: средняя сложность фаз (cron'ы
  однотипные после первого), удобные образцы (forecaster.cron как
  template), параллельные агенты, аккумулированный код-style.
