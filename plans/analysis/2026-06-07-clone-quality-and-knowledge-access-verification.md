# Клон сотрудника: аудит качества + верификация «доступа к знаниям»

> **Метод.** (1) Полная карта подсистемы по коду (7 параллельных читателей, сверено по файлам). (2) Верификация изменения knowledge-access (`typecheck` + 156 тестов + состязательный разбор off-пути, 8 агентов). (3) Качество цепочки — по уже снятому реальному прогону DeepSeek-V4-Pro на 25 эталонах + разбор промптов. (4) 23 предложения улучшений, каждое независимо перепроверено состязательным верификатором (реальность пробела / величина / лучший ли вариант / инварианты).
>
> **Живой билд клона «с нуля» на стенде НЕ выполнен** — Docker-движок не поднялся в этой сессии (см. §6). Все выводы ниже — из кода + реального снятого golden-прогона, без нового живого прогона.

## 0. TL;DR

1. **Изменение «доступ к знаниям» (8 фаз, PR #34) НЕ сломало клонов/второй мозг при текущем дефолте прода** (`KNOWLEDGE_ACCESS_ENFORCEMENT=off`) — поведение байт-в-байт прежнее. Доказано: `typecheck` зелёный, 156 затронутых тестов проходят, миграция чисто аддитивная, все 15 точек резолвера за гейтом `enf !== 'off'`, прод-логи без ошибок от нового кода.
2. **Но есть одна реальная ошибка, активная СЕЙЧАС (включена по умолчанию), и она про клонов:** Фаза 1 (привязка автора на все типы) + chatbox = факты КЛИЕНТА втекают в knowledge-клон менеджера. Серьёзность **HIGH**.
3. **Цепочка клона спроектирована добротно и работает** (96% на golden-эталоне детектора). Главная реальная проблема — **не качество, а «голод»**: на разрежённых встречах клон почти никогда не формируется (пороги слишком высоки). Плюс несколько локальных багов: merge затирает накопленную уверенность, merge не обновляет якорь-эмбеддинг, decay роняет на две ступени за проход.
4. **Честно про «≥20%»:** все предложения по магнитуде — `gain_unproven`. Не потому что пробелы ненастоящие (они реальны и локализованы), а потому что **в репозитории нет метрики точности/частоты формирования клона**, против которой можно доказать 20%. Единственный измеритель — golden детектора (и его реальный прогон — заглушка `it.todo`). **Главная рекомендация: сначала построить измерительный harness формирования+точности клона на стенде, снять baseline — потом доказывать и ранжировать фиксы по измеренной выгоде.**

## 1. Как устроен «Клон сотрудника» (карта по коду)

Клон — это **ролевой** артефакт (`ExecutablePersona`, scope=`role`), не персональный (решение владельца 2026-05-25). Внутри строится по-человечно, наружу — по должности.

**Цепочка наполнения:**
```
встреча/дамп → block-ingest пишет IdeaBlockEntity{role=subject} для reasoning-сигналов
  → RouterService раздаёт canonical-блоки специалистам
  → 3-7-skill: группирует reasoning-блоки по cosine ≥ 0.78, группы ≥ 5 →
      LLM skill-trait-detect → SkillTrait (KNN-merge 0.85 через skill-trait-merge;
      decay 6 мес / archive 12 мес)
  → SkillTraitConcept нормализация (cron, merge 0.92)
  → ExecutablePersona (LLM executable-persona-compile, 300–800 слов, топ-20 черт)
  → ответ: ClonesService.askRole → анти-дипфейк гейт (≥2 reasoning-блока cosine ≥ 0.70,
      иначе отказ БЕЗ вызова LLM) → clone-respond (factual t=0.2 / judgmental t=0.7)
      → цитаты [BLOCK:id]
```

**Пороги создания.** Person-клон: ≥3 active traits. Role-клон: ≥2 сотрудника на роли + ≥3 агрегированных traits. Сборка — крон вс 06:00 + watcher каждые 2 ч (или ≥2 новых traits/24ч, или возраст >48ч).

**Параллельная ветка (за флагом OFF):** PracticeSkill (выполняемые процедуры «триггер→шаги») — у них, в отличие от skill-traits, ЕСТЬ верификационный гейт (adversarial-verify + composite-judge + A/B). Это важный контраст (см. §4, фикс C).

**Дизайн-правила (подтверждены):** черты — гипотезы, не приговоры (qualifier «похоже/склонен»); без персданных; цитирование [BLOCK:id]; «лучше промолчать, чем сгенерировать дипфейк»; самообучение — composite judge + A/B, без human-in-loop (только kill-switch).

**Прод-состояние тестовой Org «ооо ромашка»:** 1 сотрудник, 0 должностей, **0 клонов** (`/clones` → «Всего: 0»). Билд «с нуля» в проде моими инструментами невозможен (нет прод-шелла, крон+пороги, нужен объём) — глубокий тест клона по дизайну идёт на контролируемом стенде (решение Р1 предв. плана).

## 2. Верификация: не сломало ли изменение «доступ к знаниям»

**Что это.** 8 фаз (коммиты `e253dd19`..`6e3a17c9`, влиты PR #34): провенанс автора на все типы + per-adapter identity (Ф1) → модель групп доступа (Ф2) → вывод групп блока при ingest (Ф3) → security-гейт во всех поверхностях retrieval (Ф4) → **контекст клонов в правах спрашивающего (Ф5)** → наследование на проекции (Ф6) → admin-UI (Ф7) → выкат off→shadow→enforce (Ф8). Миграция `20260606114416_knowledge_access_groups`.

### Вердикт: при `off` (дефолт прода) — НЕ сломало, байт-в-байт

| Проверка | Результат |
|---|---|
| `bun run typecheck` | ✅ exit 0 |
| Затронутые юнит-тесты (knowledge-access/rbac/clones-feed/api) | ✅ **156 passed**, 16 файлов |
| Миграция | ✅ чисто аддитивная (новый enum + 4 таблицы + 2 nullable-колонки; **без DROP / NOT NULL на существующих** → ноль риска потери данных) |
| off-инвариант (8 агентов, состязательно) | ✅ `off_is_noop` по всем 3 гейт-измерениям |
| Прод-логи (read-only diag) | ✅ ни одной ошибки/WARN от нового кода |

**Почему off безопасен (доказательства из кода):**
- `KNOWLEDGE_ACCESS_ENFORCEMENT` default `'off'` (`env.schema.ts:1682`); геттер `typed-config.service.ts:2111` возвращает `enforcement: mode ?? 'off'`.
- Все 15 точек `resolveAccessibleGroups` за гейтом `enf !== 'off'` → при off резолвер, его DB-запросы и 60-сек кэш не трогаются.
- Все `where` подмешиваются как `...(accessWhere ?? {})`, где `accessWhere=undefined` при off → запрос байт-в-байт.
- `TenantGuard` при off группы не резолвит (`tenant.guard.ts:103`).
- Клон Ф5: `accessCtx` прокинут во все 4 пути ответа, но при off = `null` → фильтрации нет; density-гейт считает ПОСЛЕ фильтра (корректный `topic_starved`); owner/admin — bypass; defense-in-depth post-filter идемпотентен.
- `@Optional()` резолвер в проде резолвится в реальный инстанс (`RbacModule` `@Global`+exports) → enforce реально включается; `null` только в тестах.

### Реальная ошибка (HIGH), активная СЕЙЧАС — и она про клонов

**Chatbox: факты клиента → knowledge-клон менеджера.**
- Chatbox грузит весь диалог клиент+менеджер ОДНИМ событием с единым `responsible.personId = менеджер` (`chatbox-ingest.service.ts:51-63, 243-311`; per-message `from:'client'|'manager'` есть в payload, но дальше отбрасывается).
- Ф1 включила `subjectAttributionAllTypes` **по умолчанию true** (`seed-admin-settings.ts:275`) → `attributeSubject` срабатывает на ВСЕ signalType (`block-ingest.worker.ts:1089-1093`).
- `entity-resolution.service.ts:928-935` отдаёт `authorPersonId` высший приоритет (шаг 0) → для chatbox это ВСЕГДА менеджер, сегмент-спикер не смотрится.
- → каждый блок (в т.ч. факт, сказанный КЛИЕНТОМ) получает `IdeaBlockEntity{role=subject}=менеджер`.
- `specialist-3-2-knowledge-clone.service.ts:504-517` тянет `role IN ('subject','mentioned')` БЕЗ фильтра по signalType → клиентские факты вливаются в клон менеджера как его знание.
- 3-7 skill-клон защищён жёстким фильтром signalType (reasoning/rationale/decision_basis), НО клиентский *reasoning*-блок («я выбрал X потому что Y») всё равно утёк бы к 3-7 как subject=менеджер.

**Подтверждено сквозной состязательной проверкой по коду.** Это «не off-default» — включено по умолчанию, поэтому пишет в прод-граф уже сейчас (хотя при `enforcement=off` ещё не фильтруется на выдаче).

### Чисто-enforce проблемы (НЕ болят при off — «до полного включения»)

| Находка | Серьёзность (испр.) | Суть |
|---|---|---|
| RetrievalCache ключ без userId | low | при enforce утечки НЕТ (выходной гейт перефильтровывает per-user), но асимметрия recall + неверная shadow-метрика. Добавить отпечаток групп в ключ до GA |
| Пагинация проекций `total` over-count при enforce | low | `count()` до фильтра → over-count + страница может быть короче limit. Косметика + лёгкий count-side-channel |
| `insights.list/listMine` under-fill при enforce | low | post-filter после `take:limit` → полупустая страница. Over-fetch+refill |
| Проекции с пустым `sourceBlockIds` — fail-open при enforce | info | ручные decisions без source-блоков видны всем. Проверить материализацию Ф3 / дефолт-группу |

## 3. Качество цепочки клона (по реальному golden-прогону)

**Источник:** `backend/test/eval/skill-trait-detect-golden/reports/golden-deepseek-v4-pro.json` — реальный прогон DeepSeek-V4-Pro на 25 эталонах (20 valid + 5 reject), 2026-05-25.

**Итог: 24/25 (96%).** validPassRate=1.0 (20/20), rejectPassRate=0.8 (4/5). Стоимость ~$0.0008–0.0017/черта, ~14–18с, кэш-хит 78%.

**Что хорошо:** формулировки качественные — гипотезные («Похоже, склонен…»), привязаны к цитатам, описывают ПОВЕДЕНИЕ при решениях, без приговорного стиля. Отказы (reject) корректно дают пустой `sourceBlockIds` в 4/5 случаях.

**Дефекты на живых выходах:**

1. **Ложное извлечение (rejectPassRate 80%).** Фикстура 24 (три уточняющих тех-вопроса: «Где конфиг логгера? Кто owner? Когда обновляли зависимости?») → модель **выдумала черту** «уточняет операционный контекст перед действием» с 3 blockId и confidence=medium. Это анти-дипфейк-провал: вопросы содержат не «ПОЧЕМУ», а информационный запрос; промпт уже содержит анти-фабрикационное правило + adversarial-пример (`skill-trait-detect.prompt.ts:46-70`) — и всё равно ошибся. Вывод: одно-проходный детектор сам себя не аудирует.

2. **Уверенность.** Распределение medium:21 / low:4 / **high:0**. ⚠ **Важная поправка** (поймана верификатором): на golden-эталоне это **корректно по дизайну** — каждая фикстура даёт 3–5 цитат в одном детекте, что по правилу = medium; «high» возникает только из накопления через РАЗНЫЕ ДАТЫ. То есть «детектор сплющивает уверенность» — НЕверная трактовка. **Реальный баг — в merge-пути** (см. §4, фикс «merge затирает уверенность»): черта, подтверждённая 30 наблюдениями, навсегда остаётся medium.

## 4. Предложения улучшений (с состязательной проверкой)

> 23 предложения, каждое перепроверено независимым верификатором. **Все по магнитуде — `gain_unproven`** (см. §5 почему). Ниже — выжимка по приоритету ПОСЛЕ верификации. P1 = реальный баг/верный-по-построению фикс; P2 = верное направление, величина не доказана; drop = отклонено.

### P1 — реальные баги / верные-по-построению фиксы

**A. Chatbox cross-attribution (HIGH-баг из §2).** Фикс в корне: атрибуция автора по-сообщениям в chatbox-ingest + НЕ передавать session-level `responsible.personId` для смешанных диалогов; fail-closed (нет subject), если спан нельзя уверенно привязать к менеджеру. *Поправка верификатора:* решающее место — `block-ingest` + `entity-resolution` (там `authorPersonId` короткозамыкает на шаге 0), а не только сегмент-билдер; и гейтить так, чтобы менялись ТОЛЬКО смешанные chatbox-события (одно-авторные free_note/dump/email не регрессируют). Лучше глобального выключения флага (убьёт легитимные факты менеджера) и лучше фильтра в 3-2 (оставит битые subject-строки в графе → утечка через /search, /chat, дашборды).

**B. Merge затирает накопленную уверенность (`specialist-3-7-skill.service.ts:931`).** `mergeIntoExisting` пишет `confidence: args.draft.confidence` (последний medium), выбрасывая накопленное → черта на 30 наблюдений навсегда medium, никогда не high. Фикс: пересчитывать confidence из **разброса РАЗНЫХ ДАТ/встреч** (не из числа блоков — иначе одна болтливая встреча даст false-high и нарушит правило ladder’а). Требует подгрузки дат блоков в merge-пути.

**C. Merge не обновляет якорь (statement+embedding).** `mergeIntoExisting` обновляет только sourceBlockIds/observationCount/confidence/lastConfirmedAt — НЕ statement и НЕ pgvector-эмбеддинг (`:912-944`). Якорь застывает на первой формулировке → будущие близнецы падают ниже 0.85 → ложное «new» (компаундит фрагментацию). Фикс дешёвый (S): переиспользовать уже посчитанный query-эмбеддинг (он в scope на `:692`), обновлять **эмбеддинг и текст ВМЕСТЕ** (никогда не порознь — иначе вектор/текст рассинхрон). Бонус-баг: `runDecay` делает два последовательных updateMany (high→medium, потом medium→low) без изоляции → застаревший «high» падает на ДВЕ ступени за один проход.

**D. Нет верификационного гейта на skill-traits перед персоной (паритет с practice-skills).** Черта пишется `status='active'` сразу после одного detect-вызова (`createNewTraitRaw:856`), персона тянет все active. Фикс: добавить статус `pending_verification` + дешёвый второй проход (taskType `skill-trait-verify`, deepseek-v4-flash, cron-батч): «подтверждается ли черта ≥2 цитируемыми reasoning-блоками, или выведена из уточняющих вопросов/общих фраз?» → active только на PASS. Это бы поймало фикстуру 24. Fail-open kill-switch, shadow→enforce. *Это — предохранитель, включающий безопасное снижение порогов (E).* Поправка верификатора: «паритет с practice-skills» — преувеличение (там A/B на реальном outcome; тут только grounding-срез), но для черт grounding-check на момент создания — верный инструмент; +20% на rejectPassRate = артефакт n=1 фикстуры, не робастный эффект.

### P2 — верное направление, величина не доказана

- **E. «Голод» формирования на разрежённых данных** (ГЛАВНАЯ реальная проблема). Двойной гейт: ≥5 всего И ≥5 на каждый 0.78-кластер → 10 блоков обычно 0 traits → клон не формируется (SMOKE сценарии 2-3; встреча «111» = 72 слова). Фикс: развести cluster-floor (≥3) и profile-floor (≥5), НО только ПОСЛЕ гейта D (иначе рост фабрикаций — единственная 3-блочная улика как раз фабрикация фикстуры 24). NB: `SKILL_MIN_OBSERVATIONS` сейчас ENV (рестарт), не AdminSetting — нужна динамическая обвязка.
- **F. Мёртвая зона merge 0.78–0.85.** Драфты в [0.78,0.85) идут в force-new без арбитража → фрагментация. Two-tier: арбитровать серую зону существующим LLM-судьёй.
- **G. clone-respond.** judgmental-режим (t=0.7, override на 1 блок, ответ «по аналогии» без прецедента, цитаты спрятаны) — ослабление анти-дипфейка; рассмотреть пол 2-блока + гейт на уверенность классификатора. Плюс post-generation faithfulness self-check; парсинг `[DECISION:id]`.
- **H. persona-compile.** Для role-клона нет cross-person dedup → одна и та же черта от 3 людей повторяется в персоне роли. Дедуп по conceptId.

### drop (отклонено верификатором)
- Concept attach Top-K (путь не нагружает клон-цепочку; вред-механизм преувеличен).
- Композитный score черт вместо confidence-desc (не то «бутылочное горло»; persona уже tie-break’ит по observationCount).
- Прокидывать sourceBlockIds черты в персону (клон-респонс и так грузит свой reasoning-subgraph).

## 5. Главный вывод про «минимум 20%»

**Все 23 предложения по величине — `gain_unproven`.** Это не слабость предложений, а **диагноз зрелости измерения**:

- Единственный измеритель качества в репо — golden детектора (25 фикстур), и он покрывает ТОЛЬКО skill-trait-detect (один проход), не merge, не формирование, не персону, не clone-respond. Его реальный LLM-прогон — заглушка `it.todo` (в репо лежит ОДИН снятый вручную прогон).
- Нет метрик: частоты формирования клона, точности черт на входе в персону, recall’а merge, качества ответа клона.
- Поэтому «≥20%» нельзя ни доказать, ни опровергнуть статически — нужен baseline на живом прогоне.

**→ Рекомендация-«мета», самая важная:** **сначала построить измерительный harness** (на стенде, по образцу `backend/scripts/agent-quality-harness.ts` + `_lib/combat-harness.ts`):
1. Синтетический тенант + сотрудники + reasoning-встречи через РЕАЛЬНЫЙ конвейер (пороги снижены на стенде).
2. Метрики: % профилей, сформировавших персону; точность черт (доля грунтованных vs фабрикаций) на расширенном golden; near-dup-ratio; качество ответа клона на наборе вопросов (валид/отказ/фабрикация).
3. Снять baseline → применять фиксы A–H по одному → мерить дельту. Тогда «≥20%» становится доказуемым и фиксы ранжируются по ИЗМЕРЕННОЙ выгоде.
