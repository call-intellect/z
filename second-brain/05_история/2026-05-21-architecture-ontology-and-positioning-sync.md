# Архитектура памяти компании, онтология и синхронизация позиционирования

## Что было поставлено

Пользователь хотел обсудить архитектуру «будущего проекта» — расширение Z из «AI-встреч» в полноценную **память компании / memory layer**. Просьба: спроектировать онтологию, разобрать как разные сущности (люди / процессы / регламенты) укладываются в систему, и подумать как пользователь будет с этим работать.

В ходе сессии задача росла: появилось дополнительное требование (1) реализовать «ленту вопросов» от агента-куратора, (2) изучить текущий код Z и подготовить gap-анализ, (3) синхронизировать позиционирование во всех файлах, (4) выбрать стратегию миграции, (5) детально проработать Role-first onboarding, (6) применить пользовательский каркас «5 уровней основы компании» к нашей онтологии и продогфудить на самом Z.

## Как решал

**11 итераций обсуждения с пользователем**, всё фиксировалось живьём в `plans/analysis/`:

1. **`2026-05-21-ontology-process-regulation.md`** — главный документ обсуждения (1100+ строк). Структура: 10 слоёв архитектуры → онтология (3 класса сущностей + Declared/Observed) → `CuratorAgent` + лента вопросов (`Inquiry` как узел графа) → Role-first onboarding и клон должности → каркас 5 уровней основы компании (Миссия → Видение → Стратегия → Цель → Процесс → Регламент → Должность → Инструмент → Метрика → Ретро). Девять разделов основного контента + лог из 11 итераций. Все 16 вопросов закрыты решениями.

2. **`2026-05-21-z-gap-analysis-to-memory-layer.md`** — gap-анализ текущего кода Z против целевой 10-слойной архитектуры (700+ строк). Готовность Z оценена в ~42%. Сильные стороны (3 из 4 архитектурных принципов работают): двухуровневое извлечение (RawEvent → IdeaBlock), provenance везде, eventual consistency. Главные пробелы: нет графового хранилища (Apache AGE / Neo4j), нет bi-temporal слоя, нет ABAC на уровне фактов, нет query planner LLM, нет агентного слоя (клоны, агент-куратор, нарраторы процессов). Roadmap из 8 фаз: 0 (Должности+онбординг) → α (Apache AGE + bi-temporal) → β (ABAC) → γ (остальные новые типы Entity + динамическая онтология) → δ (агент-куратор) → ε (новые адаптеры ingest) → ζ (специализированные агенты) → η (query planner + MCP).

**Ключевые архитектурные решения** (все зафиксированы в разделе 8 главного документа):
- Граф знаний — через **Apache AGE** (расширение PostgreSQL), не отдельный Neo4j. Один кластер БД, транзакционная консистентность.
- **«Клон должности», а не «клон сотрудника»** как первичный концепт. Должность стабильна, человек меняется — знание не уходит с увольнением. Это прямо обещание из `positioning.md`.
- **Двухслойная модель знаний роли:** activity subgraph (всё, что произошло) + `RoleProfile` (отфильтрованная карта роли — обязанности, навыки, типовые решения, грабли). Аналог `Card.summaryCache` в текущем Z.
- **Inquiry — узел графа**, а не отдельная таблица. Тогда provenance, ABAC, история — работают «бесплатно» на той же модели, что и остальные факты.
- **Diff Declared vs Observed — артефакт агента, не узел.** Вычисляется по запросу или кэшируется.
- **Стратегия миграции — эволюция (вариант "а")**. Не строим memory-layer с нуля и не делаем жёсткий pivot. Идём фазами 0 → η. Текущая вертикаль «AI-встречи» работает, валидирует рынок, приносит деньги; параллельно растут граф, новые источники, агенты.
- **Membership.role (Casbin owner/admin/manager) ≠ Role (бизнес-должность).** Это две разных модели. Первая — права доступа в системе Z, вторая — должность в компании клиента.
- **5 новых сущностей онтологии** в Фазе 0: `Role`, `JobDescription`, `Skill`, `Document`, `RoleProfile`. Department добавляется бесплатно для оргструктуры.
- **Каркас 5 уровней основы компании** обогащает Фазу γ полным списком: Mission/Vision/Strategy/Department/Process/ProcessStep/Regulation/Policy/Standard/Metric/Review/Retrospective/ChangeRequest.
- **Векторное выравнивание (alignment) — главный продуктовый вопрос памяти компании.** Не просто хранилище, а живая обратная связь: «то, что делают команда и сотрудники — ведёт к выполнению целей или вектор уходит в сторону?». В Z уже есть фундамент (Phase 9: Goal + GoalAlignmentSnapshot + strategic-alignment.worker), но только на уровне всей компании. Расширяем на 5 уровней (компания/отдел/должность/сотрудник/событие) через обобщённый AlignmentSnapshot и AlignmentAgent. Это вариация того же паттерна Declared vs Observed. У CuratorAgent появляется новый режим Inquiry — alignment_drift с 4 типами триггеров. Goal расширяется полями horizon (strategic/annual/quarterly/monthly/sprint) и parentGoalId (декомпозиция).

## Что вышло

**Получено:**
- Целевая 10-слойная архитектура с 4 принципами поверх (two-tier extraction, memory-is-state, provenance everywhere, eventual consistency).
- Полная онтология «памяти компании» (3 класса сущностей + 5 уровней каркаса + Inquiry для агента-куратора).
- Gap-анализ текущего кода Z → целевая архитектура с оценкой 42% готовности и списком сильных сторон, которые нельзя ломать (LlmRouter, IdeaBlockEvidence провенанс, 152-ФЗ, retention, entitlements).
- Roadmap из 8 фаз (0 → α → β → γ → δ → ε → ζ → η).
- Решение по стратегии миграции — эволюция, не переписывание и не жёсткий pivot.
- Полностью спроектированная Фаза 0 (Должности + знакомство с компанией). Готово к написанию ТЗ.
- 7 файлов с позиционированием синхронизированы.
- Два новых правила в памяти агента: «русский в скобках для всех английских слов» и «админка только на русском».

**Не проверено в коде:**
Сессия была чисто проектная — кода не писали, тесты не запускали. `bun run typecheck`/`lint`/`test` не выполнялся, потому что не было причин — только редактировались документы и memory-файлы.

**Не закоммичено:**
Все изменения только локально. Файлы готовы к коммиту, но `git add` / `git commit` я ещё не делал — жду явного подтверждения пользователя по содержимому коммита (правило из CLAUDE.md).

## Чему научился

1. **Когда пользователь хочет «обсудить» — сразу создавать живой документ обсуждения** в `plans/analysis/` и складывать туда каждую итерацию. Это спасает контекст от потери, даёт пользователю возможность вернуться к разговору, и в конце документ сам становится материалом для ТЗ. Без такого документа после 11 итераций обсуждение бы рассыпалось.

2. **CLAUDE.md в системном промпте может быть устаревшим.** При попытке отредактировать его я обнаружил, что фактическое содержимое файла отличается от того, что мне подгрузилось в начале сессии. Урок: если файл важен для текущей задачи (позиционирование, ключевые правила) — лучше один раз перечитать через Read tool до правки. На это ушло одно лишнее `tool_use_error` и одна Read.

3. **Англоязычные термины — это барьер.** Пользователь дважды просил пересобрать ответ на русском: один раз неявно через ранее зафиксированное правило в memory (`feedback_language_plain_russian.md`), второй раз явно — расширив правило с «аббревиатур» на «любые английские слова». Это значит первое правило не работало на практике — я нарушал его регулярно, оставляя «backend», «extraction», «query layer» без пояснений. Усиленное правило в memory должно это закрыть. Урок: правила в memory работают только если их применять без оглядки, не «когда вспомнил».

4. **Концептуальная разница «клон должности» vs «клон сотрудника» — большая.** Я в начале писал `EmployeeClone`, пользователь поправил: клон роли, не человека. Это сильнее в продукте (стабильность знания при увольнении) и точнее в онтологии. Урок: когда название сущности приходит от меня — проверять, не накладывает ли оно скрытых предположений на жизненный цикл данных.

5. **Dogfooding идеи** — сильный мысленный инструмент. Применил каркас 5 уровней к самой компании Z и сразу увидел: мы работаем по всем уровням, но только в markdown в `second-brain/`. Это и тест продукта, и сильный sales-аргумент. Стоит делать чаще: «а как это работает у нас самих?» — особенно при проектировании новых концепций.

6. **Right-sized vs over-engineered.** Когда пользователь дал каркас 5 уровней, я мог развернуть огромный список новых таблиц БД. Удержался — каркас обогащает существующие фазы, новой фазы не вводит. Это важно для эволюционного подхода: каждая фаза должна быть «следующая разумная порция», а не «давайте сразу всё». Хорошая дисциплина.
