# Эталон промпта: модуль понимания запроса (`dialog-multi-query`, схема `dialog_multi_query_v2`)

> История-aware шаг dialog-layer: из реплики сотрудника в живом диалоге делает 3 самодостаточных вопроса для поиска по графу знаний.
> **Где живёт:** `backend/src/modules/dialog-layer/prompts/query-understand.prompt.ts`, используется `MultiQueryExpansionService` (org-режим), `taskType='dialog-multi-query'`.
> **Контракт реализации:** `plans/archive/2026-06-14-dialog-layer-unified-query-understanding.md` (Приложение A).

---

## Зачем (что заменил)

Слил ТРИ бывших агента в один history-aware вызов:
- **контекстуализатор** (`dialog-contextualize`) — переписывал follow-up в самодостаточный вопрос;
- **оценщик уверенности** (`dialog-confidence`) — вторым LLM-вызовом страховал контекстуализатор (антипаттерн: самокоррекция без внешнего сигнала, ICLR 2024);
- **расширитель** (`dialog-multi-query`) — 1 вопрос → 3 формулировки, но был слеп к истории и загейтлен на exploratory/analytical.

Теперь любой follow-up = **1 LLM-вызов**: контекстуализация («это/он/там» → имена из истории) и расширение (3 ракурса) происходят внутри одного промпта. Расширитель работает всегда при включённом флаге (intent-гейтинг убран).

## Эталонный промпт (канон)

SYSTEM — копировать байт-в-байт из `query-understand.prompt.ts` (`DIALOG_QUERY_UNDERSTAND_SYSTEM_PROMPT`). Ключевые блоки: роль → ЗАЧЕМ → КОМУ АДРЕСОВАН ВЫВОД (поисковый движок, не человек) → ЧТО СТАНЕТ С РЕЗУЛЬТАТОМ (3 отдельных поиска → объединение) → 2 шага (восстанови смысл / 3 вопроса разного ракурса) → 7 критериев → запреты (английский/коды/выдумывание сущностей) → self-check → 3 few-shot примера (непонятный follow-up / аналитический / уже полная реплика).

### Пример USER (`buildQueryUnderstandUserPrompt`)
```
Краткое содержание диалога:
(нет)

Последние сообщения диалога:
— Пользователь: Что у нас по продукту «Маяк»?
— Ассистент: Это новая система для логистики, запуск в августе.

Реплика пользователя:
а сколько это стоит?

Три вопроса:
```
Модель должна вернуть `{"queries":[...]}`, где «это» уже раскрыто в «Маяк» во всех трёх формулировках.

### Выходной контракт
```json
{ "queries": ["…", "…", "…"] }
```
`schema_name = "dialog_multi_query_v2"` (версия поднята с v1 — в USER добавлены summary+history). `minItems:1` — защита от провайдера; парсер дедупит, режет до 3, первой кладёт оригинальную реплику (fallback при пустом retrieval).

## Почему так

| Блок методологии | Как реализован |
|---|---|
| **Роль/персона** | «Ты — модуль понимания запроса в Коре… превратить реплику в запросы по графу». |
| **Якоря смысла** | ЗАЧЕМ (реплика неполная) + КОМУ (поисковый движок, не человек) + ЧТО СТАНЕТ (3 отдельных поиска → объединение) — модель понимает, почему вопросы должны быть самодостаточными и разноплановыми. |
| **Критерии хорошего** | 7 нумерованных правил (раскрытость без истории, один запрос, разные ракурсы, чистый русский, ≤200, не выдумывать). |
| **Few-shot** | 3 примера, включая антипример «это не раскрыто → поиск пуст». |
| **Self-check** | «Перед ответом проверь (а)(б)(в); если не так — перепиши». |
| **Контракт** | строгий JSON `{queries}`, schema `strict`. |
| **Запреты Z** | ни одного английского слова/кода даже из истории; не добавлять несуществующих сущностей. |
| **Cache-friendly** | весь текст и few-shot в стабильном SYSTEM; summary/history/question — в конце USER. |
