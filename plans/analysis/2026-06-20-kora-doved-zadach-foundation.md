# Кора — опорный документ: доведение задач до подтверждённого результата

**Дата:** 2026-06-20
**Тип:** манифест-эталон (целевая модель «как должно быть»). НЕ аудит реализации.
**Назначение:** единая точка опоры для анализа, доработок, новых фич и приоритизации платформы Кора. Любое предлагаемое изменение сверяем с этим документом: «приближает нас к этой модели — да/нет».
**Доказательная база:** живой клиент «Молочные реки» (встреча 20.06.2026, разбор — раздел 5) + сессионные заметки владельца.

## 1. Главный тезис (фундамент)

**Кора не даёт закрыть задачу на уровне действия, пока не подтверждён бизнес-результат.**

Это не таск-менеджер. Это **система доведения задач до подтверждённого результата**. Всё остальное в продукте подчинено этому.

### Сдвиг модели

| | Было (обычный трекер) | Стало (Кора) |
|---|---|---|
| Цепочка | Задача → Исполнитель → «Сделано» | Задача → Действия → Проверки → Подтверждение результата → Закрытие |
| Единица закрытия | статус «выполнено» (заявление) | подтверждённый результат (доказательство) |
| Что хранит задача | статус | цель + критерии завершения + доказательства |

**Структура задачи:** не «статус: выполнено», а **цель + критерии завершения + доказательства** (скриншот, файл, подтверждение клиента и т.д.). Пока хоть один критерий не закрыт — задача открыта.

---

## 2. Принципы (выведены из тезиса)

1. **Результат, а не действие.** После каждого апдейта исполнителя система классифицирует: *это действие или результат?* Если действие — спрашивает, какой измеримый результат оно даёт и какие доказательства подтверждают.
2. **Контроль ясности, а не шагов.** Для новых задач без чек-листа Кора требует ясности по пяти осям (см. §3), а не диктует шаги.
3. **AI-опердиректор следит, а не подсказывает.** Не говорит, что делать. Гарантирует, что у каждой задачи есть цель, критерий завершения, следующий шаг, ответственный, подтверждение. Флагует аномалии.
4. **Нулевой порог ввода.** Любой ввод данных — голосом/в чате/со встречи; «заполнять графы» руками недопустимо (см. §5, блок В: главная причина провала прошлых систем у клиента).
5. **Память хранит скрытую инструкцию.** Требование собственника «не хочу держать это в голове» = система извлекает из опыта обязательные следующие шаги и превращает их в принудительный сценарий.
6. **Каждая извлечённая сущность отслеживаема и обратима.** У всего есть провенанс (откуда взято) и возможность удалить — в т.ч. из графа.

---

## 3. AI-опердиректор: контракт

**Что делает:** следит, чтобы у каждой задачи были — цель · критерий завершения · следующий шаг · ответственный · подтверждение.

**Что флагует (аномалии):**
- нет критерия успеха;
- N дней нет следующего шага (например, 10 дней «висит»);
- исполнитель пишет про действия, а не про результаты;
- нет ответственного / нет подтверждающего.

**Для новой задачи без чек-листа** Кора требует ответить:
1. какой результат нужен →
2. как поймём, что достигнут (критерий) →
3. кто подтверждает →
4. какие риски / неизвестные →
5. следующий шаг.

## 4. Шесть продуктовых направлений

Каждое — из заметок владельца. По каждому: суть · какую боль клиента закрывает (ссылка на §5) · открытые вопросы для REALITY-CHECK.

### Н1. Закрытие по результату (ядро, = §1–3)
**Суть:** структура задачи «цель + критерии + доказательства»; классификатор «действие/результат» на каждый апдейт; гейт закрытия по критериям.
**Закрывает боли клиента:** А1 (спокойствие без надзора), А4 («сказал, что сделал, а не сделал»), Б6 (расхождение замысла и понимания), Б7 (форма результата).
**Открытые вопросы:** как не превратить это в «заполнение граф» (принцип 4) — классификатор должен сам вытаскивать критерии из диалога, а не требовать форму; где порог «достаточного доказательства».

### Н2. Память по уточняющим вопросам (обучение probe)
**Суть:** при уточняющем вопросе сохраняем не только пару «вопрос-ответ», но и весь контекст: *почему* спросили (цепочка рассуждения → вопрос → ответ). Вечерняя рефлексия → выводы. Цель: **не переспрашивать уже выясненное** — система учится на ответах.
**Закрывает боли клиента:** Д14 («а он учится?»), Д16 (обучение на специфике и синонимах), В9 (меньше дёргать людей).
**Открытые вопросы:** связь с существующей probe-системой (см. memory `project_probe_system_research_done`); где живёт «вывод рефлексии» в графе; как инвалидировать устаревший вывод.

### Н3. Контекст в самих уточняющих вопросах
**Суть:** каждый вопрос несёт **минимально достаточный контекст** — что система уже знает, почему спрашивает, какой ответ ожидает. Чтобы ответить сразу, не открывая задачу и не вспоминая.
**Проблема сейчас (со слов владельца):** приходит «Можете уточнить, пожалуйста?»; 5 вопросов, часть дублируется, привязка — только скобкой в конце, этого мало.
**Закрывает боли клиента:** В9, В10 (простота, низкий порог), Б6.
**Открытые вопросы:** формат «контекстной обёртки» вопроса; дедуп похожих вопросов; лимит длины для Telegram/мобильного.

### Н4. Удаление данных (роли + чистка графа)
**Суть:** роли «админ/руководитель» vs «простой пользователь». Админ и руководитель могут удалять извлечённое Корой (в т.ч. ошибочно): задачи, решения, регламенты — любую сущность. **Ключевое:** удаление проходит и из базы знаний (графа), не только из UI, чтобы удалённое нигде не всплывало и на него не ссылались.
**Закрывает боли клиента:** Д14 (правят руками неверно извлечённое), доверие Ани (технический фильтр сделки).
**Открытые вопросы:** каскад по графу (связи IdeaBlock/Entity/links/themes); soft- vs hard-delete и аудит; кто видит «было удалено».

### Н5. Агент-чистильщик базы знаний (продолжение Н4)
**Суть:** извлечённая сущность бывает ошибочной или **попала из другого чата** (кросс-контаминация контекста). Нужен агент, который проходит по всему графу и **вычищает все упоминания** заданной сущности/тематики — не точечно, а везде, где она «расползлась».
**Закрывает боли клиента:** Ж20 (выборочные чаты — риск чужого контекста), Д16 (специфика/синонимы), доверие к графу.
**Открытые вопросы:** как агент находит «все упоминания» (semantic + graph traversal); ручной триггер vs авто; защита от ложного массового удаления.

### Н6. Провенанс сущностей (кнопка «Подробнее»)
**Суть:** у любой созданной сущности (задача, решение, инструкция, регламент) — кнопка «Подробнее» → проваливание к **источнику**: конкретный кусок текста, сообщение из чата или фрагмент встречи, откуда извлечено. Цель: видеть происхождение и точнее понимать контекст.
**Закрывает боли клиента:** Г12 (единый поиск + доверие к ответу), Д14/Д16 (проверить, откуда взялось), доверие Ани.
**Открытые вопросы:** хранится ли уже ссылка на исходный фрагмент при ингесте; гранулярность (сообщение vs цитата с таймкодом встречи); UX «провалиться к источнику».

## 5. Доказательная база — клиент «Молочные реки»

Молочное производство + дистрибуция в федеральные сети (X5, Магнит, Светофор). **Традиционный бизнес**, не айтишники. ЛПР: **Миша** (собственник, перегружен, хочет «спокойствия») и **Аня** (процессы, технически грамотная — технический фильтр сделки). Уже обожглись на CRM, дашбордах, скраме, геймификации — **«не работает»** → главный критерий: простота + работа без ручного надзора.

### Боли и запросы (по блокам)

**А. Контроль исполнения (главная боль владельца)**
- А1. «Спокойствие» вместо надзора: знать, что задачи выполняются; если нет — фиксируется само. «Интересно, но сидеть смотреть — неинтересно».
- А2. Задачи от директора устно/на ходу теряются (нет ассистента, «висят между исполнителем и директором»).
- А3. Напоминания исполнителю + эскалация руководителю. Кейс: 2 месяца назад поручил разделить мерчендайзера на 3, сделать отчётность — не сделали, забыл проконтролировать, «закипает». Названо «самым важным».
- А4. Фиксация «сказал, что сделал, а на самом деле нет» (кто/когда/что заявил).
- А5. Связка с мотивацией/ЗП (отложенный, но живой): % выполнения → премия; баллы за помощь коллегам.

**Б. Постановка и понимание задач**
- Б6. Расхождение «как поставил» vs «как понял исполнитель» — узнают только на результате.
- Б7. Непонятна форма результата (распечатать/прислать/куда) — переспрашивают.
- Б8. Идентификация говорящего (чтобы вторая сторона представлялась).

**В. Барьер сложности (критический риск сделки)**
- В9. «Заполнять некому и некогда»: «задачу быстрее сделать, чем заполнить все графы». ← Причина провала всех прошлых систем.
- В10. Требование «максимально простой функционал — контроль выполнения».
- В11. Люди разного уровня + сопротивление (кто-то только голос/телефон; кто-то саботирует).

**Г. Память и поиск**
- Г12. Единый быстрый поиск по всей истории на естественном языке («вышли всю информацию по проекту X» → по датам). Сейчас поиск ручной по папкам/чатам/совещаниям.
- Г13. Сбор из всех каналов (голос, очно, телефон, переписка).

**Д. Качество AI (вопросы Ани — технический фильтр)**
- Д14. Точность распознавания/протокола: правит руками (названия, ответственный, не зафиксировано как задача). Вопрос: «а он учится?».
- Д15. Привязка ответственного по контексту без имени («этикетки» → снабжение → Наташа; «образцы» → Катя).
- Д16. Обучение на их специфике и синонимах; вопрос — сколько времени/усилий на настройку.

**Е. Мобильность и ввод**
- Е17. Приложение на телефоне; сценарий «директор в машине наговорил, иначе забудет».
- Е18. Носимый рекордер («человек из кармана») → выгрузка в граф.
- Е19. Лёгкая загрузка видео/аудио извне (собеседования, диктофон), в т.ч. через Telegram.

**Ж. Telegram (приватность)**
- Ж20. Выборочное подключение чатов (личные Telegram на 90%) → отдельный рабочий аккаунт в нужные группы.

**З. UX задачи для исполнителя**
- З21. Понятная карточка/список задачи.
- З22. Прикрепление файла к «Готово» (таблица отчётности прямо в задаче), переписка внутри карточки.

**И. Коммерческое**
- И23. Пробный доступ на месяц, совместная доработка «день в день».
- И24. Следующие шаги: общая Telegram-группа сегодня → обновление в понедельник → тех-встреча во вторник.
- И25. ⚠️ Неясно: начало встречи «возьмём такую штуку семьсот… кнопку внедрять» (тариф/объём ~700?) — **уточнить отдельно**.

## 7. Открытые вопросы / развилки (для REALITY-CHECK перед ТЗ)
