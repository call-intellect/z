## Правила работы

### Жёсткие
1. **Не комитить и не пушить без явного подтверждения владельца.** Любая фаза заканчивается отчётом и просьбой «закоммитить и идти к следующей?». Владелец отвечает «да/нет», тогда коммит. Push — отдельное подтверждение.
2. **Не пропускать тесты.** Каждая фаза включает написание unit/e2e-тестов из её Acceptance criteria. Если тесты не пишутся — фаза не закрыта.
3. **Не пропускать typecheck.** После любой правки кода в backend → `cd backend && bun run typecheck`. В frontend → `cd frontend && bun run typecheck`. Красное → не идёшь дальше.
4. **Не править Prisma через `migrate`.** Только `bun run prisma:push` + `bun run prisma:generate`. См. skill `prisma-db-push-rules`.
5. **Не вводить Python в `backend/`.** Стек — Bun + Node + TS. См. правило 7 в CLAUDE.md и skill `core-engineering-standards`.
6. **ENV/настройки — через `TypedConfigService` или `AdminSetting`, никогда `process.env.*` в коде.** См. skill `nestjs-rules`.
7. **LLM-промпты cache-friendly** (стабильный SYSTEM, переменные в USER в конце). Раздел «Совместимость с prompt caching» проверь у каждого нового prompt-key. См. `feedback_llm_prompts_cache_friendly` и `second-brain/02_architecture/llm-cache-status.md`.
8. **Sub-агенты иногда лгут про `[x]`.** После каждого спавна агента — re-Read изменённые файлы, `git status`, grep ключевых маркеров (новых функций / новых файлов). Не верь отчёту агента без верификации. См. `feedback_agents_can_lie_about_edits`.
9. **Не использовать `git add .` или `-A`.** Перечисляй файлы явно при стэйджинге.
10. **На каждое изменение кода — обновление second-brain** по таблице из CLAUDE.md (раздел «Триггер 1: после git push»). Не комит без обновления `01_projects/smart-tables.md`.

### Мягкие (рекомендации)
1. **Каждая развилка → доказывай.** Если нужно выбрать между «положить cellProvenance в новую таблицу vs JSON-поле в TableRow» — спавн `Plan` агента с конкретным вопросом, получи 2-3 варианта с pros/cons, выбери, кратко объясни выбор в `second-brain/05_история/`.
2. **Если фаза тормозит на одной задаче > 1 часа реального времени работы агента** — приостанови, отчитайся владельцу, спроси «продолжить так / переключиться на другой подход / отложить».
3. **Логируй прогресс в `second-brain/05_история/2026-06-02-smart-tables-auto-creation-<phase>.md`** — короткая запись: что делал, на чём споткнулся, как обошёл, ссылки на коммиты.
4. **Используй TodoWrite** для трекинга шагов внутри фазы. Очищай чек-лист после закрытия фазы.

### Шаг 2 — Развилки (если есть, 10-30 минут)

### Шаг 3 — Промпт для кодящего агента (5-10 минут)
- Составь точный промпт для sub-агента-кодера. Структура:
  ```
  Цель фазы: <цель из ТЗ>

  Что НЕ входит: <список из ТЗ>
  ```

- Промпт должен быть **самодостаточным** — агент не должен догадываться, что ты имел в виду.

### Шаг 4 — Выполнение (длительность варьируется)
- Спавн агента (`Agent` tool, type `general-purpose` или `claude` для большой задачи; `Explore` тут не подходит — он read-only).
- Когда агент вернёт результат — **верифицируй**:
  - `git status` — какие файлы реально изменились?
  - Re-Read ключевые файлы → правки на месте?
  - Grep по новым функциям / классам → они реально добавлены?
  - `bun run typecheck` — компилируется?
  - `bun run lint` — не сломал стиль?
  - Тесты из ТЗ — реально написаны и проходят?

### Шаг 5 — Acceptance criteria (10-30 минут)
- Пройди по чек-листу acceptance из ТЗ.
- Каждый пункт — либо проверь руками (тестом, запуском, grep'ом), либо запиши «не проверено: <причина>» в `second-brain/05_история/`.

### Шаг 6 — Отчёт владельцу (5 минут)

- Открытые вопросы.
- Запрос: «закоммитить?» / «push?» / «продолжить к фазе N+1?».

### Шаг 7 — Коммит (только после подтверждения владельца)

- Коммит с conventional-style сообщением: `feat(tables): Фаза N — <короткое описание>`.

## Чего НЕ делать

- ❌ Не пропускать фазы. Если ТЗ говорит «Фаза 0 → 1 → 2», не прыгать сразу в Фазу 3.
- ❌ Не оптимизировать «по дороге». Видишь странный код в соседнем модуле — игнорируй, это вне scope. Открой отдельную issue/задачу владельцу.
- ❌ Не вводить новые библиотеки без обоснования. Если нужна новая dep — обоснование + Context7-проверка актуальной версии + согласование с владельцем.

- ❌ Не вводить feature-flags «на всякий случай». Если ТЗ требует флаг (Фаза 1.5 → `feature.tables_text_to_schema`) — да; иначе — нет.
- ❌ Не использовать destructive git операции без явного подтверждения (reset --hard, push --force, branch -D).
- ❌ Не отчитываться галочкой `[x]` без верификации. Sub-агенты могут lie — всегда греп / re-Read.

## Что делать при блокере

2. Спавн `Plan` агента с описанием блокера и 2-3 идеями.
3. Если Plan не находит решения → отчёт владельцу + предложение «отложить фазу, перейти к параллельной».
