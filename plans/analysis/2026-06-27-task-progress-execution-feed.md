# Ход выполнения задачи из диалогов + развязка трёх смыслов «решения»

## 1. Рамка проблемы

**Симптом (слова владельца):** «У нас путаница. Была петля задача↔решение. Нам не хватает сущности „действие / выполнение задачи“: поставили задачу → человек работает → из всех диалогов надо забирать действия по этой задаче и фиксировать в карточке („по задаче — такое действие, такое действие“); а где звучит „задача выполнена“ — задача двигается по статусу. Вот этого не хватает, это сломано.»

**Две конкурирующие формулировки корня:**

- **P1 — «не хватает сущности/конвейера „ход выполнения“».** В коде есть два полюса задачи (① постановка, ③ завершение), а **середина — промежуточный прогресс из бесед — не извлекается**. Сущность под журнал (`IssueProgressUpdate`) есть, но кормится только из сигналов завершения и ручных действий.
- **P2 — «терминологическая путаница „решения“».** Слово «решение» носит три несовместимые роли (выбор / «решение порождает задачи» / «решение = выполнение задачи»), и из-за этого и пользователь, и AI-классификатор валят сущности в чужие реестры (33% мусора в `/decisions` — задачеподобные).

**Iceberg (симптом → корень):** P1 и P2 — две грани одного. Корень — **в модели не выделен отдельный объект «ход исполнения» (execution/progress), а слово «решение» перегружено тремя смыслами.** Поэтому система ловит «поставили задачу» и «задача готова», но слепа к тому, ЧТО по задаче реально делается между этими точками, и параллельно засоряет реестр решений поручениями.

**Кто страдает (роли Z):** исполнитель (его работа не видна, прогресс приходится дублировать вручную), руководитель/CEO (дашборд «что движется» строится на пустоте), память компании (теряется самое ценное — как именно дело делалось, какие шаги и блокеры).

**Метрика «решено»:**
- по открытой задаче из разговоров копится журнал действий с провенансом (≥1 авто-запись на активную задачу, по которой реально шли беседы), а не только в момент закрытия;
- сигнал «готово» из беседы → предложение сдвинуть статус (подтверждение человеком), а не тишина;
- три смысла «решения» разведены: реестр `/decisions` — только выборы; поручения — в задачи; ход исполнения — в журнал задачи.

## 2. Дерево потока (MECE) — каркас фаз будущего ТЗ

Корень: «жизнь задачи в памяти компании от постановки до результата». Ветви — этапы потока, без пересечений:

| Ветвь | Что происходит | Состояние в коде |
|---|---|---|
| **① Постановка** | реплика-поручение → создаётся `Issue` + провенанс `TaskSource` | ✅ `specialist-3-15-tasks` |
| **② Распознавание «работа по задаче ведётся»** | в беседе звучит промежуточное действие по существующей задаче | 🔴 **нет сигнала `task_progress`** |
| **③ Сопоставление реплики ↔ открытая задача** | какой именно задаче принадлежит действие | 🟡 механизм есть (`SimilarIssuesService.findSimilarByVector(openOnly)`, KNN/HNSW по `Issue.embedding`), но вызывается только на завершении |
| **④ Наполнение журнала** | действие копится в карточке (что сделано / что дальше / здоровье) с провенансом | 🟡 сущность `IssueProgressUpdate` есть, но кормится не из «середины» |
| **⑤ Завершение** | сигнал «готово» → кандидат на закрытие → подтверждение → сдвиг статуса | ✅ `TaskCompletionHandler` + `TaskClosureCandidate` |
| **⑥ Подтверждение/доверие** | человек принимает/правит/отклоняет авто-черновик | 🟡 механика `draftState pending→accepted` есть |

Cross-cutting: развязка трёх смыслов «решения» (поверх ②④); провенанс «откуда это» на каждой записи журнала.

## 3. Baseline по нашему коду (что уже есть — через чтение backend)

### 3.1 Жизненный цикл задачи: два полюса, провал в середине
- **① Постановка.** `signalType ∈ {action_item, commitment}` → `RouterService` → `specialist-3-15-tasks.service.ts` создаёт `Issue` + `TaskSource` (провенанс: meeting/chatbox + цитата). `[verified: код]`
- **③ Завершение.** `block-ingest` ставит `signalType ∈ {task_completed, done_item, task_status_changed}` (прошедшее время + результат). `RouterService` (`router.service.ts:397-419`) эмитит событие **`task.completion_signalled`** (НЕ `targets.add` — отдельная петля). `TaskCompletionHandler` (`operations/services/task-completion.handler.ts`, зеркало `CommitmentResponseHandler`): гард от зацикливания (блок из самого трекера пропускается) → синхронный embed текста блока → KNN среди ОТКРЫТЫХ задач (`SimilarIssuesService.findSimilarByVector`, `openOnly`, порог `taskClosure.matchThreshold` default 0.85) → LLM `task-closure-verify` («сделано?») → при `done=true` создаёт `TaskClosureCandidate(status='pending')` ИДЕМПОТЕНТНО, **НЕ закрывая Issue** (инвариант R13: закрытие только через подтверждение человеком в pending-actions). `[verified: код]`
- **② Середина — ДЫРЫ.** В `SIGNAL_TYPE_VALUES` (`block-ingest.prompt.ts`) есть `action_item`/`done_item`/`task_completed`/`task_status_changed`/`task_created`/`commitment`, но **нет типа «работа по задаче ведётся, но не завершена»** (task_progress/work_in_progress). В `RouterService` для не-завершающих упоминаний задачи **нет эмита `task.progress_signalled`** — это событие эмитит только сам `TaskCompletionHandler` ПОСЛЕ нахождения completion-кандидата. `[verified: код]`

### 3.2 Сущность журнала уже есть, но недокормлена
- `IssueProgressUpdate` (модель Prisma): `health` (on_track/at_risk/off_track = в норме/риск/буксует), `body`, `doneText` («что сделано»), `nextText` («что дальше»), `sourceBlockIds` (провенанс-блоки графа), `evidenceQuote`, `confidence`, `previewQuote`/`previewSourceRef` (снимок источника), `authorType` (human|ai_agent), `draftState` (pending|accepted|edited|rejected). **Это в точности «ход выполнения, собранный AI, с подтверждением человека».** `[verified: код]`
- Кормит её только `tracker/workers/progress-auto-draft.cron.ts` (`@Cron('0 7 * * *')` + `@OnEvent('task.progress_signalled')`, крутилка `tracker.progressAutoDraftEnabled` default ON). Но `collectSignals` берёт сигналы из ТРЁХ тонких источников: выполненные пункты чек-листа (вручную), смены статуса (`IssueActivity verb=status_changed`, вручную), и `TaskClosureCandidate` (= **снова только завершения**). Вывод: журнал наполняется лишь когда задача почти закрыта, а не по ходу работы. `[verified: код]`
- Рядом: `IssueActivity` (verb-лента created/updated/status_changed/…), `IssueWorklog` (трудозатраты, ручные), `IssueComment` (комментарии, в т.ч. голос+транскрипт). `[verified: код]`

### 3.3 Параллельная петля «задача↔решение» — это НЕ «выполнение»
- `DecisionTaskLink(decisionId, issueId, linkType, createdAt)`, `linkType ∈ {implements, derived, manual}` + денорм `Decision.linkedTaskCount` + `Decision.implementationStatus` (not_started|in_progress|done|stalled). `[verified: код]`
- Создана в `plans/tz/2026-06-08-agents-daily-value-engine.md` **Фаза 3.B «Контролёр внедрения решений»**. Назначение (дословно из ТЗ): строить метрику **«% решений, доведённых до результата»** и ловить решения, под которые не завелось задач: `DecisionImplementationCron` (`@Cron('0 6 * * *')`) — `Decision(approved/implemented)` старше `decision.stale_days` (default 21) с `linkedTaskCount=0 AND actualOutcomes IS NULL` → `implementationStatus='stalled'` + push ответственному + агрегат в дайджест директора. `[verified: код+ТЗ]`
- **Направление петли: решение → порождает задачи (исполнители).** Это контроль гигиены реестра решений, а НЕ «решение/выполнение задачи». `[verified]`

### 3.4 Три смысла «решения» (источник путаницы)

| Смысл | Что в коде | Направление | Реализован? |
|---|---|---|---|
| Решение-**выбор** (Decision) | «берём вариант Б», стратегический выбор + rationale | живёт как память о выборе | ✅ |
| Решение **порождает задачи** (`DecisionTaskLink`) | контролёр внедрения, дашборд | решение → задачи | ✅ (для метрики) |
| **«Решение задачи»** = выполнение/ход | — | задача → ход исполнения | 🔴 нет сущности-конвейера |

Доп. усугубление: классификатор валит поручения в `/decisions` (33% мусора, разбор от 25.06) — ТЗ `2026-06-25-task-decision-disambiguation` это чинит на уровне промптов, но «середину» (ход выполнения) не создаёт.

Воронка: ~35 продуктов просмотрено (5 контуров параллельно) → отобрано ~30 для teardown по силе пересечения со сценарием «реплика → ход выполнения существующей задачи → авто-готово». Все факты сняты 2026-06-27.

**Белое пятно — подтверждено ВСЕМИ пятью контурами независимо:** никто не ведёт **живой структурный журнал прогресса внутри карточки конкретной задачи, авто-собираемый из ЛЮБЫХ разговоров (встречи + звонки + чаты + переписка) через семантическую привязку реплики к задаче**, с авто-движением статуса по смысловому сигналу из реплики. Рынок застрял на трёх разорванных половинках: (1) создать задачу из встречи (старт); (2) обзор/саммари активности из ВНУТРЕННИХ данных трекера; (3) rule-based авто-статус или авто-закрытие по структурному артефакту (GitHub `Fixes #123`).

## 5. Teardown ключевых аналогов (функциональный + технический, маппинг на Z)

### 5.1 Linear «Write with Agent» (июнь 2026) `[verified]` — ближайший верифицированный «из беседы в апдейт»
- **Функционально:** агент сам сверяет изменения активности проекта + сообщения привязанного Slack-канала и пишет ЧЕРНОВИК апдейта проекта; публикует человек. Ролевая аналогия — секретарь, набрасывающий «что произошло» к планёрке.
- **Технически:** двусторонний Slack-sync треда/статуса; «Write with Agent» = LLM поверх (diff активности + linked Slack channel). Action-item extraction/RAG `[inferred]`.
- **Маппинг на Z / чего НЕ копировать:** уровень ПРОЕКТА, не задачи; черновик-с-ревью; источник — один Slack-канал, не весь граф. Z обобщает на уровень issue и на все источники.

### 5.2 Gong / Avoma / Otter (sales conversation-intelligence) `[verified/claimed]` — «прогресс по сделке из разговоров → CRM»
- **Функционально:** слушают звонки по сделке, копят next steps / pain points / buying intent, обновляют CRM-поля после каждого касания. Avoma — авто-обновляемые MEDDIC-скоркарты по серии звонков.
- **Технически:** NLP topic/action-item extraction near-real-time; привязка к сделке через CRM-объект (Opportunity); Avoma — конфигурируемый маппинг полей + (опц.) авто-смена стадии. `[inferred]` про модели.
- **Маппинг на Z:** доказывает спрос на «прогресс из разговоров», но единица — **текстовое поле sales-сделки**, не дискретный журнал действий по произвольной задаче. **Важный анти-паттерн:** Gong намеренно НЕ двигает deal stage авто (иначе ломается форкаст) — high-confidence авто, low-confidence на ревью с цитатой-источником. Это прямой прецедент дизайна «порог уверенности → авто vs подтверждение».

### 5.3 Fellow `[verified]` — carry-forward + двусторонний sync статуса
- **Функционально:** переносит незакрытые action items в следующую встречу, ресёрфейсит «ты обещал X», двусторонне синхронит статус с Jira/Asana.
- **Технически:** интеграции; bidirectional completion-status sync; pill со статусом из внешнего тула.
- **Маппинг на Z:** ближайшее к «середине» по трекингу, но (а) про сами поручения (continuity), не про вытаскивание действий-апдейтов по существующей задаче из тела разговора; (б) статус двигает изменение В ТРЕКЕРЕ человеком, не NLP-сигнал из реплики.

### 5.4 GitHub `Fixes #123` `[verified]` — канонический прецедент «текст → авто-статус без человека»
- **Функционально:** ключевое слово в коммите/PR → issue авто-закрывается при мёрже в default-ветку, без подтверждения. Карточка имеет timeline-ленту событий.
- **Технически:** детерминированный парсинг синтаксиса (fix/close/resolve + #id) в структурированном артефакте, НЕ NLP; только закрытие; только при мёрже (нет premature-close by design).
- **Маппинг на Z:** доказывает, что авто-статус надёжен, когда привязан к **структурному факту**. Z обобщает с синтаксиса коммита на (а) NLP-сигнал из живой беседы (там нужен human-confirm) и (б) промежуточные статусы. Структурный путь (commit/PR/закрытие в трекере) Z может вести детерминированно и авто.

### 5.5 Huly `[claimed/verified-repo]` — авто-статус без подтверждения, но не из беседы
- **Функционально:** задача в Todo → авто Action Item в личном Planner; человек ставит её в календарь → статус issue авто становится In Progress.
- **Маппинг на Z:** редкий пример авто-статуса без ручного апрува, но триггер — **календарное намерение**, не сигнал «сделал» из разговора. Перехода в Done из беседы нет.

### 5.6 Техпаттерны (research/patent) `[verified: arXiv/USPTO]` — фундамент Z
- **Извлечение прогресса из транскрипта:** intent-recognition на маркерах + NER + Semantic Role Labeling + **tense-detection** («сделал A» прошедшее = прогресс/готово vs «сделаю B» будущее = новая задача) + BERT-классификатор «реплика = action item?» (заявл. 95.4% на тесте). Триада статусов COMPLETED/IN_PROGRESS/INTERRUPTED.
- **Привязка реплики к задаче:** embedding реплики → cosine к вектору задачи/центроиду кластера; **два порога** — hard (авто-привязка), soft (запрос подтверждения у человека). Типичные пороги RAG: >0.7 уверенный, >0.3 кандидат.
- **Маппинг на Z (прямой):** `Issue.embedding` (HNSW, есть) = корпус; реплика = query; tense-detection отделяет прогресс от новой задачи; hard/soft-порог = готовый дизайн «авто vs спросить человека». Это ровно недостающие звенья ②③④, и они переиспользуют уже работающий KNN из `TaskCompletionHandler`.

| Маршрутизация апдейта владельцу | рынок: completion 50→85% от роутинга `[market]` | journal пишется, но не роутится явно владельцу | **Роутинг записи/смены health владельцу** (закрывает accountability gap) |

## 7. Матрица вариантов глубины

Критерии = ограничения Z: единый Bun+Node+TS, Prisma-миграции, multi-tenancy, ранний прод (~4 юзера, корпус мал → false-positive не виден сейчас, но выстрелит при росте), Ship-On, крутилки в AdminSetting, не сломать работающую completion-петлю, переиспользовать существующее.

## 8. Рекомендация (ADR-каркас)

**Контекст:** сущность журнала (`IssueProgressUpdate`) и механизм матчинга (`SimilarIssuesService` + completion-петля) уже в коде. Боль — не отсутствие сущности, а (1) непокрытая «середина» жизненного цикла и (2) перегруженность слова «решение». Ранний прод маскирует риск false-positive — при росте он выстрелит.

**Альтернативы (steelman):**
- *B — отдельный сигнал task_progress (исходная гипотеза):* интуитивно чисто, но red-team доказал: наследует подтверждённый рынком класс false-positive/misattribution (Gong, Fellow `[verified]`), «непрерывный» журнал рискует стать игнорируемым потоком (`[verified: SRE/alert-fatigue]`), и не адресует главный разрыв середины — accountability/routing gap (70% action items не выполняются; completion растёт от роутинга владельцу, не от нового сигнала `[market]`).
- *C — полный execution-объект + авто-статус из беседы:* мощно, но против рынка (Gong намеренно не двигает stage авто; Asana — «co-pilot, not autopilot» `[verified]`) и overbuild для раннего прода.

**Рекомендация: Вариант A** — расширить существующую completion-петлю, а не строить новый тракт.

Фазовый порядок (он же каркас ТЗ):
1. **Побочный класс «не-терминальное упоминание задачи»** на ТОМ ЖЕ матче, что уже делает `TaskCompletionHandler`: блок сматчился к открытой задаче (KNN), но это не «готово», а прогресс/блокер (tense-detection: прошедшее-без-завершения / упоминание-работы). Не новый сигнал/событие/воркер — побочный выход существующего классификатора. *Снимает риск второго шумящего классификатора.*
2. **Журнал событийный, по дельте, не непрерывный.** Запись в `IssueProgressUpdate` создаётся ТОЛЬКО при уверенной новой дельте (новый факт по задаче), с провенансом (цитата + deep-link). *Снимает fatigue.*
3. **Soft/hard-порог уверенности** (как у Gong): high-confidence → авто-запись в журнал; средняя → в pending-actions «это по задаче X? подтвердите». *Готовый дизайн против дублей и мисматча.*
4. **Авто-статус — два РАЗНЫХ пути по типу сигнала:** разговорный сигнал «готово» → только предложение с подтверждением (текущий `TaskClosureCandidate`, R13 не трогаем); **структурный факт** (commit/PR `Fixes #`, закрытие связанной задачи в трекере) → отдельный детерминированный коннектор с авто-движением. *Граница по типу сигнала, не «человек vs авто».*
5. **Роутинг владельцу.** Запись прогресса / смена health видна ответственному (не молчаливый лог). *Адресует accountability gap — главный разрыв середины.*
6. **Развязка трёх смыслов «решения»** (cross-cutting, дешёвый): зафиксировать в second-brain и в промптах терминологию — Decision (выбор), DecisionTaskLink (контроль внедрения), execution-журнал (ход). Совмещается с уже готовым ТЗ `2026-06-25-task-decision-disambiguation`.

**Последствия:** «середина» закрывается переиспользованием готового (KNN, петля, сущность журнала), без нового воркера, с калибруемым порогом и без alert-fatigue; обгон рынка — по белому пятну (журнал хода из всех разговоров + семантическая привязка), которое не закрывает никто. Зона обгона усилена позиционированием Коры «помнит за всю команду» (журнал переживает увольнение/смену исполнителя).

## 9. Открытые вопросы к владельцу (каждый — с рекомендацией)

1. **Архитектура: расширить петлю (A) или отдельный сигнал (B)?** — **Рекомендую A:** red-team доказал, что отдельный сигнал наследует false-positive/fatigue и не лечит главный разрыв; реюз дешевле и точнее. (Если хочешь максимально «чистую» модель сигналов — это аргумент за B, но ценой шума.)
2. **Авто-движение статуса по разговорному сигналу — авто или только предложение?** — **Рекомендую только предложение + подтверждение** (как сейчас `TaskClosureCandidate`): весь рынок (Gong, Asana) держит разговорный сигнал за человеком; авто-закрытие по услышанному «вроде сделал» — риск порчи данных. Авто — только для структурных фактов (commit/закрытие в трекере).
3. **Источники прогресса: сразу все (встречи+чаты+переписка) или поэтапно?** — **Рекомендую начать со встреч LiveKit** (поток уже в графе), чат/переписку подключать по мере появления потока — иначе строим под пустоту (та же логика, что в анализе слоя-источника).
4. **Как назвать сущность для людей?** — **Рекомендую «ход выполнения» / «журнал работы по задаче»** (а не «решение» — слово перегружено; и не калька execution). В коде — переиспользовать `IssueProgressUpdate`, новую таблицу не плодить.
5. **Роутинг владельцу — отдельная нотификация или в существующий pending-actions/«Твой день»?** — **Рекомендую в существующие каналы** (`pending-actions` + персональный бриф), не плодить новый поток нотификаций (снова fatigue).

## 10. Допущения и риски (desirability / viability / feasibility)

- `[feasibility, High]` Реюз KNN (`SimilarIssuesService.findSimilarByVector(openOnly)`, HNSW по `Issue.embedding`) и петли `TaskCompletionHandler` для прогресса — проверено по коду; сущность `IssueProgressUpdate` готова.
- `[feasibility, High]` Tense-detection и hard/soft-порог — доказанные техпаттерны (`[verified: arXiv 2312.17581, 2410.18481]`), ложатся на текущий LLM-роутер и pgvector.
- `[risk, High]` **Precision/misattribution** разговорного извлечения прогресса — подтверждённый класс проблем рынка (Gong, Fellow `[verified]`). Митигация: soft-порог → подтверждение человеком, событийность по дельте, калибровка порога (крутилка). Ранний прод (~4 юзера) маскирует риск — закладывать запас.
- `[risk, Med-High]` **Alert/notification fatigue** при «непрерывном» журнале (`[verified: SRE/Datadog]`). Митигация: событийно-по-дельте + роутинг в существующие каналы.
- `[risk, Med]` **Accountability gap** (70% action items не выполняются `[market]`) — журнал сам по себе не лечит; нужна маршрутизация владельцу+дедлайн. Заложено в Фазу 5.
- `[viability, Med]` Дубли (память проекта про дубли Task/Issue) — soft/hard-порог прямо против них; но требует аккуратной калибровки KNN-порога.

## 11. Ограничения и непроверенное

- `[unverified]` Height «status updates write themselves» и автономность — только маркетинг, независимой техдоки нет. Не опираться как на доказательство, что «авто работает».
- `[claimed]` Большинство AI-фич РФ-игроков (Bitrix CoPilot, Weeek-GPT, ПланФикс AI, Pyrus) описаны маркетингово; стек/модели не раскрыты (`[inferred]`). Pyrus «боты меняют статус» — триггер по входящим обращениям, не по обсуждению хода (проверить при ТЗ, если важен прямой аналог).
- `[claimed]` Spinach «обновляет существующий тикет из встречи» — first-party доку подтверждает только СОЗДАНИЕ задач; накопление прогресса не подтверждено.
- `[unverified]` Точная стоимость embed+LLM на каждое не-терминальное упоминание при росте корпуса не замерена — оценить при ТЗ (важно для крутилки порога/частоты).
- `[уточнить чтением]` Точные строки `TaskCompletionHandler` для встройки побочного класса и формат `task-closure-verify.prompt` — подтвердить картографией кода при написании ТЗ.
