# vNext-заглушка: применение probe-ответов для доменов без apply-слоя

> **Статус:** отложено развилкой В4 в [probe-clarify-dialog-tz.md](2026-06-27-probe-clarify-dialog-tz.md). Реализовывать ТОЛЬКО по явному «реализуй» с подтверждения владельца.

Расширить детерминированный idempotent apply-слой (`ProbeResponseHandler`) на домены, для которых сейчас нет пути применения ответа: цели, карточки, темпоральные факты, идеи, навыки, инсайты, атрибуция, владелец/шаги регламента, consistency. Сейчас probe для этих доменов умеет спросить и (через диалоговую петлю) понять ответ, но записать результат детерминированно — некуда.

## Контекст (почему отложено)

Текущая итерация (probe-clarify-dialog Ф1) построила надёжный детерминированный apply для поднабора доменов (решения `decision.overdue`, уроки экспериментов, описания задач, профиль компании, curation `approve_with_edits`). Остальные домены — **онтологический долг O(домены)** (развилка В4): каждый домен требует своего идемпотентного set-once пути (как `deadline:{not:due}` для решений, дедуп урока для экспериментов, `getRaw`-guard для профиля), потому что:
- у каждого домена своя модель, свои инварианты идемпотентности и своя защита от затирания ручных правок;
- единый «универсальный» apply невозможен без потери детерминизма и идемпотентности — это и есть онтологический долг, растущий линейно по числу доменов;
- ценность каждого домена разная — выгоднее закрывать по востребованию, а не разом.

## Scope (черновик)

Для каждого домена — отдельная ветка в `ProbeResponseHandler` с идемпотентным set-once применением и guard от затирания ручного:
- **Цели** — корректировка/закрытие цели по ответу.
- **Карточки** (regulation/process/policy/instruction вне `approve_with_edits`) — применение правки тела/владельца/шагов.
- **Темпоральные факты** — корректировка `validFrom`/`validUntil` / supersede по подтверждению.
- **Идеи** — статус/обоснование/слияние.
- **Навыки** (skill-traits) — подтверждение/правка черты.
- **Инсайты** — митигация/возврат в active/атрибуция.
- **Атрибуция** (`attribution.unresolved_at_ingest`) — привязка `customer`/`vendor`-сущности.
- **Регламент: владелец / шаги** — назначение владельца, дозапись/правка шагов.
- **Consistency** — разрешение противоречия по ответу человека.

Каждая ветка: идемпотентный ключ (set-once / дедуп), guard `getRaw`/provenance против затирания человеко-правок, типизированный `ApplyResult` (включая `needs_clarification`), метрика исхода.

## Нецели

- Универсальный «один apply на всё» — противоречит детерминизму/идемпотентности.
- Менять диалоговую петлю (clarify/confirm/escalate) — она доменно-независима и уже работает; добавляются только пути записи.

**Запуск — с подтверждения владельца.** Брать домены по востребованию и по явному «реализуй»; предусловие — probe-clarify-dialog выкачен и подтверждён на проде.
