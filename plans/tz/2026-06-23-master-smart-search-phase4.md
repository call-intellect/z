# Умный поэтапный поиск «Мастера» — встройка в прод (Ф4)

## Цель
Заменить «слепую» реактивную петлю помощника (`MAX_TOOL_LOOP_ITERATIONS=5` без плана) на управляемую цепочку: **понять → (для сложного) спланировать → искать поэтапно с переформулировкой → понять, что хватит → честно ответить или признать незнание**. Убрать лишние переспросы и ложное «Готово ни с чем».

## Зачем (болезненное состояние, доказано на проде 2026-06-23)
- Помощник переспрашивает там, где надо просто взять разумное умолчание (кейс «Александр робототехника»: бот допросил про «какого Александра/период/источники» вместо поиска).
- Петля крутится вслепую до потолка 5 → трата токенов; на агрегатах «плывёт» или обрывается.
- `chat-v2` отдаёт ответ без проверки заземления → ложное «Готово»/выдумка вместо честного «не нашёл».
Доказательство выбора и цифры — `plans/analysis/2026-06-23-smart-staged-retrieval/` (синтез + red-team + 3 раунда прототип-экспериментов). Не пересматривать без новых данных.

## Граница с другими ТЗ (НЕ дублировать)

## Scope
**Входит:** Ф4.1 сторож+лимит-в-AdminSetting+честный частичный; Ф4.2 гейт честности+over-abstention-метрика; Ф4.3 строгий гейт переспроса; Ф4.4 роутер сложности; Ф4.5 ReWOO-план+переплан; Ф4.6 условный реранк+RRF; Ф4.7 достаточность.
**Не входит:** retrieval/граф (граф-ТЗ); probe-баг Telegram (Ф0); cross-encoder-микросервис (vNext при объёме — v1 LLM-as-reranker); смена эмбеддера; единый-помощник UI (Ф1-Ф3 умбрелла-ТЗ).

## Требования (EARS)
- **R1.** Когда сообщение — вопрос-поиск (не действие, меняющее данные), система shall НЕ задавать уточняющий вопрос, а брать разумные умолчания (вся память, всё время, все источники) и искать.
- **R2.** Когда помощник на входе управляет инструментами, система shall использовать модель с надёжным tool-calling (gpt-5-mini); downstream-стадии (роутер/план/реранк/достаточность/синтез/гейт) shall использовать DeepSeek.
- **R3.** Если на явно-командное сообщение модель входа не вернула вызов инструмента, система shall сделать один повтор/форс выбора инструмента (страховка).
- **R4.** Когда вопрос классифицирован как `single`/`none`, система shall НЕ строить план и НЕ входить в многошаговую петлю.
- **R5.** Когда вопрос `iterative`, система shall построить план ReWOO (2-4 шага) и исполнить; переплан shall запускаться ТОЛЬКО при явных gaps от судьи достаточности.
- **R6.** Когда пул кандидатов превышает порог (крутилка), система shall применять реранк; иначе — пропускать (условность).
- **R7.** Когда сливаются результаты нескольких подзапросов, система shall использовать RRF (k — крутилка).
- **R8.** Когда собран контекст, система shall оценивать достаточность (FAIR-RAG: confirmed/gaps/sufficient) и останавливаться по ней, а не по фиксированному числу шагов.
- **R9.** Если на шаге повторяется запрос (нормализованный отпечаток) — сторож shall остановить переформулировку (без LLM).
- **R10.** Когда достигнут лимит шагов (крутилка, на шаг плана) — система shall вернуть честный частичный ответ «не хватило шагов/данных», не пустоту.
- **R11.** Перед выдачей ответа система shall проверять заземление (модель ≠ генератор); если ответ не подтверждён блоками — честный отказ; частота отказов shall писаться в метрику (контроль over-abstention).
- **R12.** Все пороги/лимиты/выбор-модели shall жить в AdminSetting (resolveSync/getDynamic, admin→ENV→code-fallback); промпты — в registry (cache-friendly).

## Фазы (порядок = по ROI; владелец решил «всё сразу» по дизайну, но каждый слой Ship-On и проверяем)
Граф: Ф4.1, Ф4.3 независимы; Ф4.2 поверх chat-v2; Ф4.4→Ф4.5→Ф4.7 (роутер→план→достаточность); Ф4.6 в retrieval.

### Ф4.1 — Сторож зацикливания + лимит в AdminSetting + честный частичный `[x]`
**Картография:** `concierge.service.ts:30,253`. **Что входит:** перенести `MAX_TOOL_LOOP_ITERATIONS` в AdminSetting `concierge.max_steps` (лимит на шаг плана); детерминированный сторож (модуль по образцу `scripts/proto/smart-search/loop-guard.ts`: SHA/fp + Set, threshold-крутилка); при лимите — частичный ответ. **Acceptance:** unit сторожа (повтор блокируется, нормализация регистра — образец 6/6); лимит из AdminSetting; при достижении — текст частичного ответа, не пустота. **Закрывает:** R9, R10.

### Ф4.2 — Гейт честности + честный отказ + метрика over-abstention `[x]`
**Картография:** после синтеза в `chat-v2.service.ts` ask() (`:839`). **Что входит:** taskType `rag-groundedness` (DeepSeek, ОТЛИЧНАЯ от генератора), промпт P6 (02-winning-prompts); если `grounded=false` → честный отказ; метрика `incRagAbstain`. Порог/режим — AdminSetting. **Acceptance:** изолированный тест детектора (выдумка→false, честный отказ→true — образец 2/2); метрика инкрементится; over-abstention под наблюдением. **Закрывает:** R11.

### Ф4.3 — Строгий гейт переспроса `[x]`
**Картография:** `concierge-respond` системный промпт (правило №4) в registry. **Что входит:** заменить правило №4 на строгий гейт (промпт P1/P7-логика: на вопросах-поиск переспрос запрещён, умолчания; переспрос только перед необратимым действием). **Acceptance:** suite (4 поиска → не спросил; 2 действия → спросил — образец 6/6). **Закрывает:** R1.

### Ф4.4 — Роутер сложности `[ ]`
**Картография:** перед `dialog.service`/петлёй концьержа. **Что входит:** taskType `rag-route` (DeepSeek, промпт P1), Zod `{complexity:none|single|iterative,...}`; `single`/`none` НЕ входят в план/петлю; fallback-инвариант «при сомнении → single». **Acceptance:** простой вопрос → single без плана; агрегат → iterative; сомнение → single (не none). **Закрывает:** R4.

### Ф4.5 — ReWOO-план + переплан при gaps `[ ]`
**Картография:** эволюция `query-plan-extractor.service.ts` → planner; исполнение поверх concierge-петли. **Что входит:** taskType `rag-plan` (DeepSeek, промпт P2), план 2-4 шага одним проходом; исполнять как есть; переплан ТОЛЬКО при gaps от Ф4.7. **Acceptance:** агрегат → план ≥2 шага, ответ со ссылками; 0-результат → честный отказ без зацикливания (образец cold-start). **Закрывает:** R5.

### Ф4.6 — Условный реранк + RRF `[x]`
**Картография:** `chat-v2-retrieval.service.ts` (слияние/1-hop), `dialog-multi-query` слияние. **Что входит:** RRF-слияние подзапросов (k — `rag.rrf.k`); taskType `rag-rerank` (DeepSeek, промпт P3) ПОД порогом `rag.rerank_min_pool` (по размеру/шуму пула); LLM-as-reranker v1 (cross-encoder — vNext). **Acceptance:** RRF меняет порядок при нескольких подзапросах; реранк включается только при пуле > порога; на шуме режет посторонние (образец). **Закрывает:** R6, R7.

### Ф4.7 — Судья достаточности `[ ]`
**Картография:** в петле исполнения шагов. **Что входит:** taskType `rag-sufficiency` (DeepSeek, промпт P4), Zod `{sufficient,gaps,nextQuery}`; остановка по достаточности; gaps → переплан (Ф4.5) с переформулировкой (под сторожем Ф4.1). **Acceptance:** хватает → стоп без лишних шагов; не хватает → одна переформулировка, потом стоп; нет в памяти → sufficient (честный отказ). **Закрывает:** R8.

## Pre-mortem / Риски (с red-team)
- **R-cold-start (критичный):** малый граф нового тенанта ломает тяжёлые ветки (breadth не на чем; sufficiency вечно gaps; over-abstention↑). Митигация: нижний порог объёма данных → простой режим (одношаговый chat-v2). Доказано: на 0-результате прототип честно отказывал, не зацикливался.
- **R-latency:** агрегат = 6-8 последовательных вызовов. Митигация: DeepSeek (2× быстрее), жёсткий wall-clock SLA (крутилка), параллелить per-item через BullMQ flows.
- **R-judge-self-enhancement:** гейт честности и генератор — разные промпты/модель (Р5). 
- **R-over-abstention:** метрика + порог-крутилка (Ф4.2), не бинарный отказ вслепую.
- **R-iterative-cost-no-gain:** «iterative»-ветку держать за гейтом сложности + A/B; на медиане одношаговый может бить гибрид.
- **R-RRF-domain-shift:** k и веса dense/sparse — калибровать на нашем графе, не из papers.
