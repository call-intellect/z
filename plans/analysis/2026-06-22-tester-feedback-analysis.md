## 1. Самое важное (2 находки, которые бьют по всей команде)

### 🔴 A1. Сотрудники не видят транскрипт встреч — это НЕ сбой распознавания, а ошибка прав
**Что происходит.** Под вашим аккаунтом (владелец) транскрипт встречи открывается полностью (проверено: «Александр производство-молочные реки», 124 реплики с таймкодами и спикерами). А сотрудники на той же встрече видят «Транскрипт ещё не готов». Раньше мы думали, что это зависший ASR — **это не так**.

**Почему (доказано кодом).** Эндпоинт транскрипта `GET /meetings/:id/transcript` отдаёт реплики **только владельцу встречи**:
```ts
// backend/src/modules/ai/services/transcript-cleaning.service.ts:38
if (meeting.ownerId !== args.userId) throw new ForbiddenException('not_meeting_host');
```
Любой сотрудник (даже в той же компании, даже когда у встречи стоит «Видно всей компании») получает отказ 403. А фронт показывает этот отказ как безобидное «Транскрипт ещё не готов» — то есть **сообщение врёт**. Для сравнения: краткое содержание (которое сотрудник видит) грузится через правильную проверку `assertCanView` — поэтому обзор виден, а транскрипт нет.

**Решение.** В эндпоинте транскрипта заменить «только владелец» на ту же проверку видимости, что у обзора (`assertCanView`) — тогда транскрипт виден ровно тем, кому видна встреча. На фронте: показывать «Нет доступа» отдельно от «ещё не готов», чтобы баг не маскировался. **Приоритет — наивысший**: общая память команды (главная ценность продукта) сейчас до команды не доходит.

### 🟡 A2 (ПОНИЖЕНО — не та причина). Протухание сессии: на 401 фронт не редиректит
> ⚠️ **КОРРЕКЦИЯ (22.06, сверка с `dev`):** настоящая причина зависания — **НЕ** это, а **бесконечный рендер-цикл в хлебных крошках** (`useRegisterBreadcrumb` зависел от всего объекта `ctx`) → ~25k DOM-мутаций/сек → планировщик React забит → переходы по `<Link>` не коммитятся, **refresh не помогал**, спасал только уход со страницы. Затрагивало все detail-страницы. Починено другим программистом (Tozix), коммит `84b72e90`, влито в `dev` (PR #53). Тот же PR (`708a7e98`) уже убрал и консольный шум `/version` + `accounts/me`. **A2 ниже — отдельная, менее срочная проблема (стрельнёт при протухании cookie), не то зависание; дубль не делать.**

**Что происходит (отдельный сценарий).** При протухании сессии запросы начинают отдавать 401.

**Почему (доказано кодом).** Когда сессия (cookie) протухает, следующий запрос отвечает 401. Обработчик 401 на фронте делает только `setState({ user: null })` и **не уводит на страницу входа и не показывает окно «войдите снова»** (`auth-context.tsx:152`). Запросы данных идут без повторов (`shouldRetryOnError:false`). Итог: пользователь застревает на текущем экране, любые клики дёргают API → всё 401 → ничего не грузится → «зависло». Единственное, что физически уводит со страницы — «Выход».

**Решение.** При протухании сессии — жёстко уводить на `/login` (или показывать модалку «Сессия истекла, войдите снова»), а лучше добавить тихое продление сессии, чтобы она не умирала посреди работы. Параллельно починить поллер версий: `/api/version` сейчас отдаёт 404, поэтому оповещение «вышла новая версия, обновите страницу» не срабатывает вообще.

## 3. «Непонятно, зачем этот раздел» — что это на самом деле и что предлагаю

Тестировщик 6 раз повторила один мотив: раздел есть, но не считывается **зачем он и что с ним делать** (#3 Компания, #9 Процессы/Шаблоны, #11 Реестры, #14 Ритмы/Аналитика, #18 Домены, #19 Зрелость, #23 Голос бренда). Это не баги — это **провал онбординга разделов**. Общее решение одно: в начале каждого раздела — одна строка «что это и зачем вам», на человеческом языке, без терминов вроде «ось FUNCTIONAL» и «signalType».
