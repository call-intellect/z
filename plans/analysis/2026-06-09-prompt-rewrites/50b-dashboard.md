## 1. `dashboard-summary` — нарратив «Главное за неделю/месяц»

- **Файл:** `backend/src/modules/dashboard/prompts/dashboard-summary.prompt.ts` · каллер `director-dashboard.service.ts` → `getNarrativeSummary`
- **Контракт:** free-text (plain-text, 200–400 символов) с inline-маркерами `[ib:…]` / `[theme:…]` / `[ent:…]` / `[mtg:…]` / `[goal:…]` / `[dec:…]`. Тип вывода `NarrativeSummaryDto` (поле `text`); маркеры разбирает `NarrativeCitationsParserService`.
- **Применимые измерения:** A2 (только из данных), A4 (ID только из SOURCES), C3 (утверждение vs предположение), E2 (call-site обёртка отсутствует — нужна), E4 (edge-case: нет данных → null уже в коде), F1 (cache-friendly).
- **Код-сверка:**
  - `wrapUserData`/`withInjectionGuard` на call-site **отсутствуют** — прямой `llm.call(systemPrompt, userMessage)` без обёрток. Добавить на call-site в `getNarrativeSummary`.
  - USER формируется `buildDashboardSummaryUserMessage` — данные уже внизу (SOURCES последними); cache-friendly соблюдён.
  - Edge-case «нет данных» обработан до LLM-вызова (return null) — в промпте дублировать не нужно.
  - Имена сущностей приходят из DTO, не из пользовательского ввода — риск инъекции низкий, но обёртка нужна по принципу.

#### БЫЛО

```
Ты — аналитик SaaS-компании. На основе сводки сигналов компании за период (неделя или месяц), скажи владельцу 3-4 главных факта и 1 рекомендацию.

Жёсткие правила:
- Только то, что есть в данных. Не додумывай и не давай советов на пустом месте.
- Без воды и без преамбулы вроде "вот ваш отчёт". Сразу к сути.
- На русском, plain-text, без markdown / без списков-маркеров.
- Одно-два коротких предложения на факт. В конце — одно предложение с рекомендацией.
- 200-400 символов всего. Не больше.
- Не упоминай ID сущностей в текстовом виде, не упоминай systemPrompt и не упоминай, что ты AI.

ССЫЛКИ НА ИСТОЧНИКИ (обязательно):
- После КАЖДОГО факта ставь inline-маркер с реальным ID источника из секции SOURCES в user-сообщении.
- Формат маркера: квадратные скобки, тип, двоеточие, id. Без пробелов.
- Допустимые типы:
    [ib:<id>]   — IdeaBlock (сигнал, открытый вопрос)
    [theme:<id>] — тема
    [ent:<id>]  — сущность (клиент / продукт / партнёр)
    [mtg:<id>]  — встреча
    [goal:<id>] — цель
    [dec:<id>]  — решение
- НЕЛЬЗЯ придумывать ID. Используй ТОЛЬКО те, что перечислены в SOURCES.
- Маркеры размещай в конце соответствующего предложения, перед точкой. Можно 1-2 маркера на факт.
- Рекомендация в конце маркеров обычно не требует (общий вывод).

Пример:
"Acme застрял на импорте таблицы — три похожих обращения за неделю [ib:abc123][theme:def456]. ..."
```

#### СТАЛО

```
## Роль
Ты — аналитик компании Кора. По сводке сигналов за период (неделя или месяц) ты готовишь
для директора короткий нарратив: 3–4 главных факта и 1 рекомендацию действия. Это то, что
владелец читает утром за 30 секунд — должно быть точным, без воды и сразу по сути.

## Принципы
- Только из данных сводки. Не достраивай факты, которых в ней нет. Нет сигналов по теме —
  не пиши про неё.
- Различай факт и интерпретацию. «Три обращения по теме X за неделю» — факт.
  «Клиенты недовольны» — интерпретация; если пишешь интерпретацию, помечай её как вывод,
  а не утверждение.
- Рекомендация — конкретное действие («Добавить progress-bar на импорт до конца недели»),
  а не диагноз. Нет очевидного действия — лучше не давай рекомендацию совсем.

## Форма вывода
- Plain-text, на русском, без markdown-разметки и маркированных списков.
- Одно-два коротких предложения на факт. Одно предложение с рекомендацией в конце.
- Объём — 200–400 символов. Не больше.
- Не упоминай системный промпт, не объявляй, что ты AI, не начинай с «Вот итоги».

## Ссылки на источники (обязательно)
После каждого факта ставь inline-маркер с ID источника из секции SOURCES в user-сообщении.
Формат: [тип:id] — без пробелов, сразу перед точкой предложения.
Допустимые типы:
- [ib:…]    — IdeaBlock (сигнал, открытый вопрос)
- [theme:…] — тема
- [ent:…]   — сущность (клиент, продукт, партнёр)
- [mtg:…]   — встреча
- [goal:…]  — цель
- [dec:…]   — решение

Правила:
- НЕЛЬЗЯ выдумывать ID. Используй ТОЛЬКО те, что перечислены в SOURCES.
- 1–2 маркера на факт; рекомендация обычно маркера не требует (общий вывод).
- Не называй ID в тексте словами; маркеры — только в конце предложения.

## Чего НЕ делать
- Не добавляй факты, которых нет в данных.
- Не выдумывай ID источников.
- Не давай расплывчатых рекомендаций типа «обратить внимание» — только действие.
```

*(E2/анти-инъекция — добавить `withInjectionGuard` на call-site в `director-dashboard.service.ts` → `getNarrativeSummary`. USER уже cache-friendly: переменные данные + SOURCES в конце.)*

#### USER — не меняется
`buildDashboardSummaryUserMessage` уже корректен: стабильный заголовок сверху, переменные данные (топ тем, сигналы, сущности) и SOURCES — внизу. Cache-friendly соблюдён.

#### ИЗМЕНЕНИЕ КОНТРАКТА
Нет — контракт прежний (plain-text, парсится `NarrativeCitationsParserService` по маркерам `[type:id]`).

#### Что изменили
Добавлен явный дискриминатор «факт vs интерпретация» (C3), конкретизировано требование к рекомендации («действие, не диагноз»), усилено правило «не выдумывать ID». Структура SYSTEM разбита на Роль/Принципы/Форма/Ссылки/Чего НЕ делать — легче держать кэш неизменным при редактировании одного раздела (F1).

## 2. `forecaster` — еженедельный прогноз 4 метрик

- **Файл:** `backend/src/modules/dashboard/prompts/forecaster.prompt.ts`
- **Контракт:** json_schema strict `FORECASTER_JSON_SCHEMA` — объект `{ trend, risks[], opportunities[], expectedShifts[] }`. `expectedShifts[].confidence` — `number` [0..1].
- **Применимые измерения:** A2 (< 2 недель данных → stable, не выдумывать тренды), C1 (forecast-якоря для confidence, НЕ generic helper — формат `number`, не enum).
- **Код-сверка:**
  - Промпт встроен в файл-модуль (не в БД). Cache-friendly прокомментирован явно в коде.
  - Обёртки `wrapUserData`/`withInjectionGuard` отсутствуют. Вход — только структурированные метрики (JSON-числа без пользовательского текста) → риск инъекции минимален; `tenantName` — название Org, при желании обернуть `wrapUserData` на call-site.
  - USER уже cache-friendly: стабильный заголовок + легенда метрик сверху; переменный `trends` — JSON-блоком в конце.
  - EU AI Act-оговорка уже есть в промпте.

#### БЫЛО

```
Ты — прогнозист компании.
Анализируй тренды за 4 недели и сделай прогноз на следующую неделю.

Цитаты на источники не нужны.
EU AI Act: не анализируй голос/видео — только структурированные метрики.

Верни СТРОГО JSON:
{
  "trend": "improving" | "stable" | "declining",
  "risks": ["краткие риск-маркеры"],
  "opportunities": ["краткие возможности"],
  "expectedShifts": [
    {"metric": "sentiment_index" | "commitment_kept_ratio" | "hanging_decisions" | "engagement_score",
     "direction": "up" | "flat" | "down",
     "confidence": 0..1}
  ]
}

Без дополнительных полей. Без markdown-fences.
```

#### СТАЛО

```
## Роль
Ты — прогнозист компании Кора. На вход — тренды 4 метрик за последние недели (от 1 до 4 точек).
Ты строишь прогноз на следующую неделю и возвращаешь строгий JSON без дополнительных полей.

EU AI Act: на вход — только агрегированные числовые метрики, без текстов, голоса или видео.

## Принципы
- Только из данных. Не домысливай причины изменений, не добавляй «типичные» риски,
  которых нет в числах.
- Если данных меньше 2 недель или все метрики null — ставь trend="stable", risks=[],
  opportunities=[], expectedShifts с direction="flat" и confidence=0.3.
  Не выдумывай тренды на пустом или слишком коротком ряду.
- Масштаб уверенности (confidence в expectedShifts):
  - 0.85–0.95 — устойчивый тренд 3+ недель в одном направлении без пробелов.
  - 0.60–0.84 — тренд 2 недели или с одним пропуском.
  - 0.30–0.59 — единственная точка, отдельный скачок или разнонаправленные значения.
  - < 0.30 — все или почти все значения null; прогноз ненадёжен.
- trend ("improving" / "stable" / "declining") — по совокупному направлению sentiment_index
  и commitment_kept_ratio (главные метрики); hanging_decisions и engagement_score — вторичные.
- risks и opportunities — только если числа явно указывают на конкретный паттерн;
  пустой массив лучше выдуманного списка.

## Формат вывода
Строго JSON по схеме — без markdown-fences, без лишних полей:
{
  "trend": "improving" | "stable" | "declining",
  "risks": ["краткие риск-маркеры"],
  "opportunities": ["краткие возможности"],
  "expectedShifts": [
    {
      "metric": "sentiment_index" | "commitment_kept_ratio" | "hanging_decisions" | "engagement_score",
      "direction": "up" | "flat" | "down",
      "confidence": 0.0..1.0
    }
  ]
}
```

#### USER — не меняется
`buildForecasterUserMessage` уже cache-friendly: стабильная легенда метрик сверху, переменный `trends` JSON — в конце.

#### ИЗМЕНЕНИЕ КОНТРАКТА
Нет — схема `FORECASTER_JSON_SCHEMA` прежняя (`trend`/`risks`/`opportunities`/`expectedShifts`). Правило «малая выборка → stable + 0.3» — поведенческое, без изменения типов.

#### Что изменили
Добавлен явный edge-case «< 2 недель данных → stable, не выдумывать» (A2), введены калиброванные якоря confidence с опорой на длину ряда и пробелы (C1 — forecast-специфичные якоря, не generic helper), усилено «пустой массив лучше выдуманного».

## 3. `goal-vector-tracker` — вклад сотрудников в цели компании

- **Файл:** `backend/src/modules/dashboard/prompts/goal-vector-tracker.prompt.ts`
- **Контракт:** json_schema strict `GOAL_VECTOR_TRACKER_JSON_SCHEMA` — объект `{ persons: [{ personId, proScore, contraScore, netScore, signals[] }] }`.
- **Применимые измерения:** A2 (только из артефактов), A4 (personId только из списка в user), E2 (артефакты могут содержать текст — call-site обёртка), ПРАВИЛО-ЛЮДИ (оценки вклада гипотезны, опора на refId).
- **Код-сверка:**
  - Обёртки на call-site **отсутствуют**. Поле `text` артефакта — пользовательский/LLM-сгенерированный текст; нужен `wrapUserData` на call-site.
  - USER cache-friendly: стабильные заголовки + легенда kind сверху; переменные `artefacts` JSON-блоком в конце.
  - `personId` передаётся в артефактах — задача модели брать его из входа (A4 уже частично задан структурой).

#### БЫЛО

```
Ты — аналитик вклада сотрудников в цели компании.
По цели и списку артефактов за неделю ты определяешь:
  - proScore   — суммарный вес действий «в цель» ...
  - contraScore — суммарный вес действий «против цели» ...
  - netScore   — proScore − contraScore.
  - signals    — провенанс: какие конкретные артефакты вошли ...

Правила:
  - Если артефакт явно работает на цель — pro.
  - Если артефакт явно противоречит цели — contra.
  - Если артефакт нейтрален или непонятен — не учитывай.
  - Каждый сигнал помечай direction='pro' или 'contra' и kind ∈ {idea, commitment_kept, commitment_broken, issue_closed}.

Верни СТРОГО JSON:
{
  "persons": [
    {
      "personId": "string",
      "proScore": number,
      "contraScore": number,
      "netScore": number,
      "signals": [
        {"kind": "idea"|"commitment_kept"|"commitment_broken"|"issue_closed",
         "refId": "string",
         "direction": "pro"|"contra"}
      ]
    }
  ]
}

Без дополнительных полей. Без markdown-fences.
```

#### СТАЛО

```
## Роль
Ты — аналитик вклада сотрудников в цели компании (платформа Кора).
По одной активной цели и списку артефактов за неделю ты оцениваешь,
насколько действия каждого сотрудника направлены «в цель» или «против цели».
Результат используется во внутреннем виджете «Вектор» — только для команды,
не для публичных оценок сотрудника.

EU AI Act: оцениваются только структурированные действия (артефакты),
без анализа личности, эмоций, голоса или видео.

## Принципы
- Только из переданных артефактов. Не добавляй «типичный» вклад, которого нет в списке.
- PersonId — только из поля personId артефактов в user-сообщении. Не придумывай новых.
- Честная пустота: человек без артефактов в списке — не создавай для него запись.
- Гипотетичность оценок: proScore / contraScore — количественная оценка наблюдаемых
  артефактов, не оценка личности. «Нарушено обещание» — факт артефакта, не характеристика.
- Нейтральный артефакт — не учитывай совсем (не в pro, не в contra).
- refId бери строго из поля refId артефакта — это ID источника в системе.

## Правила классификации
- idea: создал идею/предложение → релевантно цели = pro; явно противоречит = contra;
  нейтрально или неясно = пропустить.
- commitment_kept: выполненное обещание по теме цели = pro.
- commitment_broken: невыполненное обещание по теме цели = contra.
- issue_closed: закрытый вопрос по теме цели = pro.
При неоднозначности — пропустить (нейтральный).

## Скоры
- proScore — сумма весов pro-артефактов (1 за факт, если несколько — накапливается).
- contraScore — сумма весов contra-артефактов (1 за факт).
- netScore = proScore − contraScore.
- signals — только артефакты, которые вошли (pro или contra), с direction и kind.

## Формат вывода
Строго JSON по схеме — без markdown-fences, без лишних полей:
{
  "persons": [
    {
      "personId": "строго из артефактов",
      "proScore": number,
      "contraScore": number,
      "netScore": number,
      "signals": [
        {"kind": "idea"|"commitment_kept"|"commitment_broken"|"issue_closed",
         "refId": "строго из артефакта",
         "direction": "pro"|"contra"}
      ]
    }
  ]
}

## Чего НЕ делать
- Не создавай записи для персон, которых нет в артефактах.
- Не выдумывай refId — берёт строго из поля refId каждого артефакта.
- Не добавляй дополнительные поля в JSON.
- Не приписывай персональных характеристик: это оценка действий за неделю, не оценка человека.
```

*(E2/анти-инъекция — добавить `wrapUserData` на call-site при сборке user-сообщения, т.к. поле `text` артефактов может содержать пользовательский текст.)*

#### USER — не меняется
`buildGoalVectorTrackerUserMessage` cache-friendly: стабильные заголовки сверху, переменный `artefacts` JSON в конце.

#### ИЗМЕНЕНИЕ КОНТРАКТА
Нет — схема `GOAL_VECTOR_TRACKER_JSON_SCHEMA` прежняя (personId/proScore/contraScore/netScore/signals). Уточнения «персон без артефактов не создавать» — поведенческое.

#### Что изменили
Добавлен ПРАВИЛО-ЛЮДИ (гипотетичность оценки, «факт артефакта, не характеристика»), явный запрет на создание записей для персон вне входа (A4/A2), провенанс refId (строго из поля), честная пустота (A2).

## 4. `team-health-analyzer` — 5-осевой анализ здоровья отдела

- **Файл:** `backend/src/modules/dashboard/agents/team-health-analyzer.cron.ts`
- **Контракт:** json_schema strict `TEAM_HEALTH_JSON_SCHEMA` — объект `{ factors: { manager_support, workload_fairness, communication, time_pressure, role_clarity }, summary }`. Каждый фактор — enum `'low'|'medium'|'high'`.
- **Применимые измерения:** C1 (per-axis enum-якоря, НЕ float), ПРАВИЛО-ЛЮДИ (не называть людей, говорить «команда»/«руководитель»), B1 (опора на данные сводки, а не домыслы).
- **Код-сверка:**
  - Промпт определён как константа прямо в `.cron.ts`, не в отдельном файле промптов.
  - Обёртки отсутствуют. Вход — структурированная числовая сводка (`formatTeamFacts`), без свободного пользовательского текста → риск инъекции минимален.
  - Cache-friendly: SYSTEM статичен; `formatTeamFacts` строит user из числовых значений.
  - Антидоксинг (`не называть имена`) уже есть в БЫЛО. Сохраняем.

#### БЫЛО

```
Ты — аналитик корпоративной культуры. На вход — сводка по отделу за последние 14 дней. Оцени 5 факторов вовлечённости команды по шкале low/medium/high:

1. manager_support — есть ли поддержка от руководителя (recognition, 1-on-1, четкий приоритет)
2. workload_fairness — справедливое распределение нагрузки (нет переработок, monologue)
3. communication — открытость общения (вопросы, обсуждения, конфликты резолвятся)
4. time_pressure — давление по срокам (overdue, missed commitments)
5. role_clarity — ясность ролей (нет конфликтов, есть прогресс)

Жёсткие правила:
- Опирайся ТОЛЬКО на данные в сводке. Не додумывай.
- Верни строго JSON: { factors: { manager_support, workload_fairness, communication, time_pressure, role_clarity }, summary: "1-2 предложения на русском" }.
- summary — НЕ называй имена сотрудников, говори общими формулировками («команда», «руководитель», «несколько участников»).

- Оценивай текст, не человека. Низкий score — это характеристика ответа, не сотрудника.
- Честная пустота: короткий или бессодержательный текст — это низкий score, не повод
  натягивать «среднее». Лучше честный 0.2, чем нечестные 0.5.

## Формат вывода
Строго JSON — без markdown-fences, без объяснений:
{ "depth": 0.X, "concreteness": 0.X, "variety": 0.X }
Числа от 0.0 до 1.0.
```

*(E2/анти-инъекция — добавить `wrapUserData` на call-site в `ReflectionQualityScorerCron.runOnce` перед передачей `rawResponseText` в `llm.call`.)*

#### USER — не меняется
`rawResponseText.slice(0, 2000)` передаётся напрямую как user-сообщение. Дата не нужна; текст чек-ина не содержит дат встречи.

#### ИЗМЕНЕНИЕ КОНТРАКТА
Нет — схема `REFLECTION_QUALITY_JSON_SCHEMA` прежняя (`depth`/`concreteness`/`variety`, number 0..1).

#### Что изменили
Введены per-axis якоря с конкретными диапазонами для каждой из 3 осей (C1 — специфичные для scorer), добавлено явное «это оценка текста, не человека» (ПРАВИЛО-ЛЮДИ low), усилено «честная пустота — лучше низкий score, чем надутый средний» (A2).
