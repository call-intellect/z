# ТЗ: Карточки — CRM-структура для встреч

> История обсуждения: переход от модели People+Folders+Smart-rules к чистому CRM по решению владельца от 2026-05-09 (рефлексия после реализации).

## Цель

Дать пользователю CRM-карточки (клиент / сделка / проект / тема), к которым подвязываются встречи. Главный сценарий: пользователь заходит в карточку и стартует встречу прямо оттуда — встреча автоматически попадает в карточку. Никакого LLM-угадывания привязок. AI работает только в безопасных режимах: сводка по карточке и чат с архивом встреч карточки.

## Scope

**Входит:**

- Сущность `Card` — универсальная карточка (kind: client | deal | project | topic | custom). Один опциональный primary-контакт прямо полями (имя/email/телефон).
- `Meeting.cardId` — встреча принадлежит максимум одной карточке. Привязка только явная: либо при создании из карточки (автоматически), либо ручным прикреплением через UI.
- Воркер `card-rollup` — пересобирает AI-сводку по карточке при появлении новой обработанной встречи в ней. Дебаунс.
- Расширение `chat` — `cardId` в `MeetingChatMessage`, эндпоинты `POST /cards/:id/chat`, `GET /cards/:id/chat/history` с RAG по встречам карточки.
- Frontend: AppShell sidebar с секциями Pinned / Recent / Карточки / Все встречи; страницы `/cards` (список) и `/cards/[id]` (шапка + таймлайн + сводка + AI-чат + кнопки `Начать встречу` / `Запланировать`).
- Frontend: `⌘K` (Ctrl+K) command palette — глобальный поиск по карточкам/встречам/задачам.
- Frontend: на форме создания встречи — опциональный селектор `Привязать к карточке`. Если зашли через deeplink `?cardId=...` из карточки — поле спрятано и значение проставлено.
- Frontend: на странице результата встречи — chip с названием карточки (если есть `cardId`) или кнопка `Прикрепить к карточке`.
- Public REST API: `/api/v1/public/v1/cards`, `/cards/:id`, `/cards/:id/meetings`, ручные link/unlink эндпоинты.
- Webhook-события: `card.created`, `meeting.linked_to_card`, `meeting.unlinked_from_card`.
- Audit-log: `CARD_CREATE`, `CARD_UPDATE`, `CARD_DELETE`, `CARD_RESTORE`, `MEETING_LINK_TO_CARD`, `MEETING_UNLINK_FROM_CARD`.
- Soft-delete `Card` с 30-дневным grace, retention-cron на hard-delete.

**Не входит (vNext):**

- Несколько контактов на карточку (отдельная таблица `CardContact`, дедуп по email). Сейчас — один primary полями.
- Привязка встречи к нескольким карточкам одновременно (м-к-м pivot). Сейчас — `cardId String?` (one-to-many от Card к Meeting).
- Smart-правила и DSL автомаршрутизации встреч по условиям (домен email, тип встречи, regex по названию).
- AI auto-suggest «может, прикрепить к Ивану?» — выкинуто полностью, привязка только явная.
- Персональная агрегация по гостям (`Person` как auto-collected entity).
- CRM-поля типа стадии сделки / суммы / pipeline / kanban-доски.
- Импорт карточек из CSV / интеграция с внешними CRM (Salesforce / HubSpot).
- Sharing карточек между несколькими хостами одной организации.
- Sentiment / прогресс-метрики по карточке (для психолога: динамика жалоб). Отдельное ТЗ.

## Технические изменения

### База данных

**Новая модель:**

```prisma
model Card {
  id               String    @id @default(cuid())
  ownerId          String
  owner            User      @relation(fields: [ownerId], references: [id], onDelete: Cascade)
  name             String
  kind             String    @default("client") // 'client' | 'deal' | 'project' | 'topic' | 'custom'
  color            String    @default("#5EEAD4")
  icon             String?
  description      String?   @db.Text

  // Один опциональный primary-контакт. Несколько — vNext через CardContact.
  contactName      String?
  contactEmail     String?
  contactPhone     String?

  pinned           Boolean   @default(false)
  archivedAt       DateTime?
  deletedAt        DateTime?

  // AI rollup-кэш
  summaryCache     String?   @db.Text
  summaryUpdatedAt DateTime?

  // Денормализация для сортировки списка без JOIN
  meetingCount     Int       @default(0)
  lastMeetingAt    DateTime?

  createdAt        DateTime  @default(now())
  updatedAt        DateTime  @updatedAt

  meetings         Meeting[]
  chatMessages     MeetingChatMessage[]

  @@unique([ownerId, name])
  @@index([ownerId, lastMeetingAt])
  @@index([ownerId, archivedAt])
  @@index([deletedAt])
}
```

**Расширения существующих:**

- `Meeting`:
  - `cardId String?`
  - `card Card? @relation(fields: [cardId], references: [id], onDelete: SetNull)`
  - индекс `@@index([cardId, createdAt])`
  - При удалении карточки — `cardId` встреч обнуляется (`onDelete: SetNull`). Soft-delete карточки на это не влияет (relation остаётся, отфильтровываем в запросах по `card.deletedAt IS NULL`).
- `MeetingChatMessage`:
  - `cardId String?`
  - `card Card? @relation(fields: [cardId], references: [id], onDelete: Cascade)`
  - индекс `@@index([cardId, createdAt])`
  - Инвариант (валидация на уровне сервиса): ровно одно из `meetingId | cardId` непустое. Существующая семантика — `meetingId IS NULL` означало cross-meeting chat — деприкейтится: cross-meeting чат теперь живёт только в контексте конкретной карточки.
- `User` — relation `cards Card[]`.

**Применение схемы:** только `bun prisma db push` (см. правила prisma-db-push-rules — никаких `migrate`).

### Backend

#### Новый модуль `modules/cards`

- `CardsController` — REST + Swagger:
  - `GET /api/v1/cards` — список с фильтрами (`kind`, `pinned`, `archived`, `search`), сортировка по `lastMeetingAt` desc.
  - `GET /api/v1/cards/:id` — карточка + summaryCache + meetingCount.
  - `GET /api/v1/cards/:id/meetings` — лента встреч карточки с пагинацией.
  - `POST /api/v1/cards` — создание; body: `{ name, kind, color?, icon?, description?, contactName?, contactEmail?, contactPhone? }`.
  - `PATCH /api/v1/cards/:id` — частичное обновление.
  - `DELETE /api/v1/cards/:id` — soft-delete (`deletedAt = now`), 30-дневный grace.
  - `POST /api/v1/cards/:id/restore` — снять soft-delete в пределах grace.
  - `POST /api/v1/cards/:id/meetings/:meetingId` — ручное прикрепление встречи (set `Meeting.cardId`). 409 если у встречи уже есть `cardId` другой карточки — клиент должен сначала отвязать.
  - `DELETE /api/v1/cards/:id/meetings/:meetingId` — отвязка (set `Meeting.cardId = null`).
- `CardsService`:
  - CRUD + перерасчёт `meetingCount` / `lastMeetingAt` при link/unlink (через триггер сервиса, не БД).
  - `linkMeeting(cardId, meetingId)` — транзакция: проверка владельца обоих, проверка занятости, set `cardId`, инкремент счётчиков, audit-log, webhook event, постановка job `card-rollup` через `BullMQService`.
  - `unlinkMeeting` — обратная.
- DTO-цепочка по правилам nestjs-rules: `CardDto`, `ListCardsQueryDto`, `CreateCardDto`, `UpdateCardDto`.
- Lookup-резолвер для `⌘K` поиска (см. § Search endpoint).

#### Изменения в существующих модулях

- **`modules/ai/workers/analyze.worker.ts`** — после `ai_ready`:
  - Если `meeting.cardId != null` → enqueue job в очередь `ai.rollup` с `jobId = "rollup:card:${cardId}"` (BullMQ автоматически дедуплицирует — повторные постановки в окне дебаунса игнорируются). `removeOnComplete: true`, `delay: 5_000` (5 сек, чтобы успели слиться несколько встреч из серии).
- **`modules/ai/workers/`** — новый воркер `card-rollup.worker.ts`:
  - taskType: `card-rollup` через `LlmRouter`.
  - Вход: `card.name`, `card.kind`, до 20 последних встреч карточки (по `endedAt desc`) — берём `Meeting.title`, `AiResult.summary`, опционально `MeetingChapter[]`.
  - Промпт по `kind`: client → «как развивается работа с этим клиентом»; deal → «как развивается сделка»; project → «состояние проекта»; topic → «о чём встречи на эту тему»; custom → дефолтный.
  - Выход: 1-2 абзаца текста (markdown-разрешён) → запись в `Card.summaryCache`, `summaryUpdatedAt = now()`.
  - Concurrency 2, retry 3 с экспоненциальным backoff.
- **`modules/chat`** — расширение:
  - `POST /api/v1/cards/:id/chat` — body: `{ question }`. Вызывает `ChatService.askCard(cardId, question)`.
  - `GET /api/v1/cards/:id/chat/history` — пагинированная история.
  - `ChatService.askCard(cardId, question)`:
    1. Эмбеддинг вопроса через `EmbeddingFallbackService`.
    2. `MeetingTranscriptChunk` query: `WHERE meetingId IN (SELECT id FROM Meeting WHERE cardId = $1 AND deletedAt IS NULL) ORDER BY embedding <-> $vec LIMIT 16`.
    3. taskType `card-chat` через `LlmRouter`. System prompt — инструктирует ссылаться на встречи через `[meeting:<id>]`.
    4. Запись `MeetingChatMessage` с `cardId = $1`, `meetingId = null`.
- **`modules/ai/services/llm-router.service.ts`** — добавить новые taskType в seed `LlmTaskRoute`: `card-rollup`, `card-chat`. Дефолтные модели по аналогии с `chapters` / `chat`. Изменение через `/admin/ai-models` UI.
- **`modules/audit`** — константы `AUDIT.CARD_CREATE`, `CARD_UPDATE`, `CARD_DELETE`, `CARD_RESTORE`, `MEETING_LINK_TO_CARD`, `MEETING_UNLINK_FROM_CARD`.
- **`modules/webhooks-out`** — события:
  - `card.created` — `{ cardId, ownerId, name, kind, createdAt }`.
  - `meeting.linked_to_card` — `{ meetingId, cardId, addedBy: 'manual' | 'create-flow' }`.
  - `meeting.unlinked_from_card` — `{ meetingId, cardId }`.
- **`modules/public-api`** — добавить роуты:
  - `GET /api/v1/public/v1/cards`, `GET /cards/:id`, `GET /cards/:id/meetings`.
  - `POST /cards`, `PATCH /cards/:id`, `DELETE /cards/:id` (требует scope `write`).
  - `POST /cards/:id/meetings/:meetingId`, `DELETE /cards/:id/meetings/:meetingId`.
- **`modules/quotas`** — лимит `cards_per_user` (стартовый: 500). При превышении — 429 с `Retry-After`. Snapshot в `UserQuotaCounter`.
- **`modules/retention`** — расширить `retention-extras.cron.ts`: hard-delete `Card.deletedAt < now - 30d`.

#### Search endpoint (для `⌘K`)

`GET /api/v1/search?q=<query>&types=cards,meetings,tasks&limit=20` — единый эндпоинт. Реализация — Postgres `ILIKE` по relevant-полям (`Card.name`, `Card.contactName`, `Card.contactEmail`, `Meeting.title`, `Task.title`). ts_vector / pg_trgm — vNext.

Ответ:

```json
{
  "cards":    [{"id", "name", "kind", "lastMeetingAt", "meetingCount"}],
  "meetings": [{"id", "title", "type", "cardId", "createdAt"}],
  "tasks":    [{"id", "title", "status", "meetingId"}]
}
```

#### Очереди BullMQ

- `ai.rollup` — concurrency 2, дебаунс через `jobId = "rollup:card:<cardId>"` + `delay: 5_000`. retry 3, backoff exp.

## Флоу создания встречи

**Главный — из карточки:**

```
/cards/[id]
  ├─ клик «Начать встречу сейчас»
  │   → POST /api/v1/meetings { cardId, type: <последний из карточки или sales дефолт>, ... }
  │   → редирект /meet/<id>
  └─ клик «Запланировать встречу»
      → редирект /meetings/create?cardId=<id>
      → поле «Карточка» readonly с предзаполнением
      → submit создаёт Meeting с проставленным cardId
```

**Свободный — без карточки:**

```
/meetings/create  (без ?cardId)
  ├─ опциональное поле «Привязать к карточке» — async-select
  └─ если оставлено пустым — Meeting.cardId = null
```

**Ручная привязка задним числом:**

```
/meetings/[id]/result
  └─ если cardId == null:
      кнопка «Прикрепить к карточке»
      → AttachToCardDialog (поиск + create-new)
      → POST /api/v1/cards/:cardId/meetings/:meetingId
```

## Privacy / Security

- `Card` содержит PII (имя/email/телефон контакта) → soft-delete с 30-дневным grace, retention-cron убирает hard.
- При GDPR-export пользователя — включаем `Card[]` со всеми связанными `Meeting[]`.
- Audit-log на все CRUD карточек + link/unlink с указанием `addedBy`.
- Public REST API: scope `read` для GET, `write` для POST/PATCH/DELETE и link/unlink.
- Гостевой экран `/meet/[id]/join` — без дополнительных дисклеймеров (мы больше **не сохраняем** имена гостей в карточки автоматически — карточку создаёт хост вручную).

  - `01_projects/ai-jobs.md` — taskType `card-rollup`, `card-chat`,
  - `01_projects/workers-queues.md` — воркер `card-rollup`.

## Риски и ограничения

- **Один primary-контакт мало для команд.** Если на стороне клиента двое (директор + бухгалтер) — пишем основного, остальные в `description`. vNext — отдельная таблица `CardContact`. Принято осознанно для простоты MVP.
- **Одна карточка на встречу мало для пересекающихся проектов.** Общий созвон с клиентом по двум проектам сейчас можно положить только в одну карточку. Workaround — выбрать «более важную» или создать отдельную «общую» карточку. vNext — м-к-м pivot.
- **`Card.summaryCache` устаревает.** Если кто-то редактирует `AiResult` встречи (regenerate), rollup не пересобирается автоматически. Mitigation: добавить enqueue rollup в `regenerate.service.ts` тоже. Прописано в Фазе 5.
- **Размер контекста rollup.** При 50+ встречах в карточке summary не влезут. Mitigation: берём топ-20 последних. vNext — иерархический rollup.
- **AI-чат по большой карточке тормозит на retrieval.** HNSW-индекс на `MeetingTranscriptChunk.embedding` уже есть. Если нужно — добавить partial-индекс по `userId`.
- **Стоимость LLM растёт линейно по числу карточек.** Каждая обработанная встреча в карточке = 1 вызов rollup. Дебаунс через `jobId` + delay 5 сек смягчает серии встреч в течение минут. Квота `card_rollup_per_day` (например, 100/день) на пользователя — защита от спама.
- **PII в `Card.contactEmail`.** Хранится в открытом виде (это не секрет). Доступ через owner-scoped запросы и audit-log. Шифрование PII — отдельное ТЗ, если потребуется compliance.
- **Конкурентная привязка.** Двое одновременно прикрепили одну встречу к разным карточкам — выигрывает второй (`UPDATE` поверх). Транзакция с `SELECT ... FOR UPDATE` в `linkMeeting` снимает race. Прописано в Фазе 2.

## Фазы реализации

- [ ] **Фаза 1 — DB-модель.** Prisma schema: `Card`, `Meeting.cardId`, `MeetingChatMessage.cardId`. `bun prisma db push` + `bun prisma generate`. Подтверждение работоспособности — `SELECT count(*) FROM "Card"`.
- [ ] **Фаза 2 — Backend `cards` модуль.** Controller / Service / DTO + Swagger. CRUD, link/unlink с `SELECT ... FOR UPDATE`-транзакцией, перерасчёт счётчиков. Audit-логирование. Юнит-тесты на link/unlink включая 409.
- [ ] **Фаза 3 — Лимит карточек + retention.** Квота `cards_per_user` через `QuotaService`. Расширение `retention-extras.cron.ts` для hard-delete `Card.deletedAt < now - 30d` и обнуления `cardId` соответствующих встреч.
- [ ] **Фаза 4 — `card-rollup.worker` + промпты.** taskType `card-rollup` в `LlmRouter` с дефолтными моделями. Воркер с дебаунсом через jobId. Промпты в registry + code-fallback + `seed-prompts-cards.ts`. Унит-тесты на дебаунс.
- [ ] **Фаза 5 — Триггеры rollup.** Из `analyze.worker` после `ai_ready`. Из `regenerate.service.ts` после ручной regenerate. Из `linkMeeting` / `unlinkMeeting`. Integration-тест.
- [ ] **Фаза 6 — Расширение `chat`.** `cardId` в `MeetingChatMessage`. Эндпоинты `POST /cards/:id/chat`, `GET .../chat/history`. RAG-запрос с фильтром по `Meeting.cardId`. Цитаты `[meeting:<id>]`. Integration-тест на ответ с корректной цитатой.
- [ ] **Фаза 7 — Frontend AppShell sidebar.** Pinned / Recent / Карточки секция. Lazy-load + виртуализация при >50.
- [ ] **Фаза 8 — Frontend страницы карточек.** `/cards` (список + create-modal + фильтры) и `/cards/[id]` (шапка + таймлайн + сводка + чат + кнопки create-meeting). Компоненты CardCard / CardTimeline / CardRollupCard / CardChat.
- [ ] **Фаза 9 — Расширения формы создания встречи и журнала.** `CreateMeetingFormV2`: опциональный селектор карточки + readonly-режим при `?cardId`. Кнопка `Прикрепить к карточке` на странице результата. Фильтр `cardId` в журнале. Chip `Карточка: ...` в шапке встречи.
- [ ] **Фаза 10 — `⌘K` Command Palette + search endpoint.** `GET /api/v1/search` (cards + meetings + tasks через ILIKE). Глобальный hotkey, async-search, группировка по типу.
- [ ] **Фаза 11 — Public REST API + webhooks events.** Роуты под `/api/v1/public/v1/cards` и `/cards/:id/meetings`. Регистрация событий `card.created`, `meeting.linked_to_card`, `meeting.unlinked_from_card`. Swagger обновить.
- [ ] **Фаза 12 — Тесты, observability, second-brain.** Полный прогон unit/integration/e2e. Метрики Prometheus: `z_cards_total{kind}`, `z_card_rollup_runs_total{status}`, `z_card_chat_questions_total`. Обновление всех файлов второго мозга по чек-листу выше.
