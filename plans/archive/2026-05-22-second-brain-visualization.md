## Часть I. Оригинал спецификации (от владельца продукта, v1.0)

### 1. Назначение и принцип

Документ описывает только визуализацию системы «Второй мозг компании» — клиентскую часть, где пользователь видит собранного цифрового двойника своей компании.

Базовый принцип: **один граф — два представления**. Обе вкладки читают из одного и того же графа знаний и отличаются только способом отрисовки. Это исключает рассинхрон: данные везде одни, меняется лишь форма показа.

Две вкладки решают разные задачи: «Карта» — вау-эффект и обзор; «Структура» — практическая работа.

### 2. Работа на реальных данных

Визуализация всегда строится на фактическом состоянии графа конкретной компании, а не на демо-картинке. Это значит:

- Где система знает мало — там граф разрежённый, узлов мало, видны пустоты.
- Где собрано много — там узлы плотные, яркие, с заполненными слотами.
- По мере поступления новых созвонов и чатов граф растёт прямо на глазах: появляются новые узлы и связи.

Эффект «тут маленькая, тут растёт» — ключевой. Клиент должен видеть динамику: вчера мозг был меньше, сегодня больше. Именно это создаёт доверие и ощущение, что система реально работает.

### 3. Технологический стек визуализации

Все движки визуализации — открытые и проверенные, лицензия MIT.

| Назначение | Технология | Примечание |
|---|---|---|
| Базовый UI | React | Каркас интерфейса, обе вкладки, дерево и панели. |
| Вкладка «Карта» (3D-граф) | react-force-graph-3d | Облако-мозг. Рендер canvas/WebGL, физика d3-force, поддержка добавления узлов в реальном времени. |
| Просмотр процессов | React Flow (xyflow) | Процессы как блок-схемы со стрелками, кастомные узлы-карточки, миникарта. |
| Опц.: плоский рабочий граф | Cytoscape.js или AntV G6 | Если понадобится 2D-граф со стилями по типам узлов и фильтрами. |
| Живые обновления | WebSocket | Анимация роста графа после обработки источников. |

Дерево-навигатор и панель узла строятся на обычных компонентах React — отдельный движок графа для них не нужен.

### 4. Вкладка «Карта» (вау-эффект)

3D force-directed граф — парящее облако-мозг компании. Связанные узлы притягиваются, несвязанные расталкиваются, структура сама собирается в кластеры. Назначение: эмоциональный обзор всей компании целиком.

**Что содержит**

- Узлы всех типов: компания, отделы, домены, должности, процессы — раскрашены и/или с иконками по типу.
- Связи между узлами — линиями (типизированы цветом при необходимости).
- Призрачные узлы для дыр: то, чего система ещё не знает (открытые вопросы), рисуется полупрозрачными контурами — наглядно видно, что осталось собрать.
- Кольцо зрелости поверх вида: «Мозг заполнен на N%».
- Анимация роста: после обработки созвона новые узлы появляются с анимацией.

**Поведение и производительность**

- По умолчанию граф свёрнут: крупными узлами показаны компания, отделы и домены. Детали разворачиваются по клику.
- Без свёртки 3D деградирует на сотнях узлов — поэтому кластеризация заложена с самого начала.
- Клик по узлу — подсветка соседей и переход к нему во вкладке «Структура».

### 5. Вкладка «Структура» (практичность)

Сознательно **не второй граф** — для работы граф неудобен (в нём не почитаешь и не заполнишь). Рабочий вид из трёх частей плюс панель прогресса.

**Что содержит**

- **Дерево-навигатор** (слева): Компания → Отделы / Домены → Должности → Процессы. Сворачивается и разворачивается.
- **Панель узла** (справа): слоты узла (что заполнено), дыры с открытыми вопросами, провенанс (из какого созвона факт), прогресс по узлу. Здесь клиент отвечает на уточняющие вопросы.
- **Просмотр процесса**: при открытии процесса он рисуется блок-схемой — шаги и стрелки между ними (React Flow).
- **Панель прогресса по доменам** (постоянно): например, Маркетинг 70%, Продажи 40%, Производство 15%.

### 6. Отображение роста и зрелости

Приёмы, которые показывают, насколько мозг наполнен и как он растёт. Работают на обеих вкладках:

| Приём | Где и как |
|---|---|
| Цвет / яркость по полноте | Заполненный узел — яркий, полупустой — блёклый. На «Карте» и в дереве. |
| Размер узла по важности | Ключевые роли и процессы — крупнее. На «Карте». |
| Призрачные узлы дыр | Полупрозрачные контуры для неизвестного. На «Карте». |
| Кольцо / индекс зрелости | Общий процент «Мозг заполнен на N%». Герой на «Карте». |
| Прогресс-бары по доменам | Проценты по функциям. Панель во «Структуре». |
| Анимация появления | Новые узлы вырастают после обработки. На «Карте», через WebSocket. |
| Таймлайн роста (опц.) | Слайдер «как мозг рос по неделям». Показывает динамику. |

### 7. Открытые вопросы (только по визуализации)

- 2D или 3D для заглавного вида: 3D эффектнее, 2D понятнее и быстрее.
- Рост графа в реальном времени во время созвона или обновление пачкой после обработки.
- Какая метрика-«герой» зрелости: общий процент или кольцо по доменам.
- Стратегия свёртки при росте до сотен/тысяч узлов (кластеры, уровни детализации).

## Часть II. Инженерный анализ (от агента, 2026-05-22)

### 8. Куда это встаёт в существующей карте плана

Документ — это первая внятная спецификация UI-«хирома» Второго мозга. Раньше тема жила тремя разрозненными кусками:

1. [tz/2026-05-10-knowledge-core-tz.md:1010](../tz/2026-05-10-knowledge-core-tz.md) — «UI визуализация графа — vNext» (заглушка).
2. [analysis/2026-05-21-phase-gamma-ontology-ui-design.md §A1](2026-05-21-phase-gamma-ontology-ui-design.md) — `/map` (Cytoscape) **явно вынесена из γ-core в отдельную фазу `γ-map`**.
3. [analysis/2026-05-21-user-cabinet-design.md](2026-05-21-user-cabinet-design.md) — в Sidebar заложены только списковые страницы (Процессы / Регламенты / Решения), без графовой вкладки.

Этот документ — заполняет дыру `γ-map`, но делает шаг дальше: не одна `/map`-страница, а **«хиро»-раздел из двух вкладок**, который концептуально становится главным экраном продукта (заменяет `/dashboard` как первое впечатление после wizard'а).

### 9. Что от данных уже есть, и чего ещё нет

Граф знаний физически уже работает (Фазы 3-4 knowledge-core), но **не в той форме, которую требует «Карта»**.

| Что требует визуализация | Что есть сейчас | Гэп |
|---|---|---|
| Узлы компании / отделов / должностей / процессов | `Entity`, `Person`, `Department`, `Role`, `Process`, `Regulation` — в БД будут к концу γ-core (см. umbrella ТЗ §2.C) | Нет единого `GET /api/v1/brain/graph` — есть только покусочные endpoint'ы. |
| Связи между узлами | `EntityLink` + `IdeaBlockLink` (Фаза 3) | Endpoint `GET /api/v1/graph/neighbors?depth=1..3` есть, но он **локальный** (от точки) — для «облака-мозга» нужен **глобальный** обход с серверной кластеризацией. |
| «Заполненность» узла (для цвета/яркости) | RoleProfile считает «slot fillness», но это только для ролей | Нет единой метрики «node maturity» для всех типов узлов. Нужно определить формулу для каждого. |
| «Призрачные узлы дыр» | Нет вообще | Принципиально новая сущность: «то, что система ожидает увидеть, но не увидела». Связано с динамической онтологией (γ-фаза) и Слоем 6 (Probe-Agent — он эти дыры и генерирует). |
| Кольцо зрелости (общий процент) | Нет | Нужна агрегатная метрика «brain fillness» — отдельный сервис. |
| WebSocket для роста в realtime | Нет канала «graph.updated» — текущие WS только для встреч | Нужен новый namespace + событие, эмитимое после `block-ingest.worker` / `block-linker.worker` / специалистов Слоя 3. |
| Прогресс по доменам | Нет понятия «домен» как агрегата (Маркетинг/Продажи/Производство) | Либо derive из `Department` каркаса Фазы 0, либо вводить новый агрегат. Нужно решение. |

**Вывод:** визуализация на 70% бэкендовая задача. Сам React-фронт без серверных агрегатов и кластеризации не взлетит даже на 200 узлов.

### 10. Конфликты и развилки, которые требует продуктового решения

**10.1. 3D vs anti-3D в дизайн-системе.**
В [analysis/2026-05-09-ai-meeting-workspace-design.md:501](2026-05-09-ai-meeting-workspace-design.md) явно зафиксировано «не использовать 3D-элементы». Контекст там — про glassmorphism/neumorphism (визуальные «понты» в карточках), не про дата-визуализацию. Но формально правило сейчас одно для всего. **Нужно явно разрешить 3D для графа знаний или принять 2D-вариант** (тот же react-force-graph поддерживает 2D-режим). Без явного решения дизайнер заблокирует первый прототип.

**10.2. «Заменяет ли граф `/dashboard`?»**
В аналитике ЛК (`user-cabinet-design.md` §5) `/dashboard` — дефолтный экран для admin после wizard'а. Если «Карта» становится новым «вау»-экраном, она должна занять это место. Альтернатива — отдельный `/brain` или `/map`. Решение влияет на Sidebar и onboarding.

**10.3. `Cytoscape` или `react-force-graph` для будущего 2D-режима?**
γ-аналитика называла Cytoscape, этот документ — `Cytoscape.js или AntV G6` как опцию. Зафиксировать выбор. Cytoscape — более «инженерный» (выше потолок), AntV G6 — китайская экосистема, проще стилизация, но меньше комьюнити в России. **Рекомендация:** взять `react-force-graph` сразу с поддержкой обоих режимов (2D и 3D) — у него один API для обоих, переключение тривиально, меньше зависимостей.

**10.4. Granularity «дыр».**
Призрачные узлы — самая принципиальная новая идея. Сейчас граф знает только то, что в него положили. Чтобы рисовать «дыры», нужен механизм **ожиданий**:
- Либо из эталонной модели компании (например: «у любой B2B-компании должен быть процесс продаж» — динамическая онтология Фазы γd).
- Либо из активных вопросов Probe-Agent (Слой 6) — каждый незакрытый вопрос = одна «дыра».
- Либо из «декларации vs наблюдения» — admin в wizard'е сказал «у нас есть отдел продаж», а блоков по нему 0.
**Рекомендация:** взять третий вариант как самый дешёвый MVP (`declared but unobserved`), остальные — γ+.

**10.5. Realtime во время созвона vs пакетная анимация после.**
Realtime во время созвона — это нагрузка на extraction + WS на каждое слово. Прагматично — **пакетно после `meeting.completed`** (после AI-отчёта), с явной плашкой «обновляем карту…» и красивой анимацией прорастания. Это закрывает 95% «вау» без отдельной инфраструктуры streaming-extraction.

**10.6. Метрика-«герой».**
Общий процент «Мозг заполнен на N%» — опасно: что значит 100%? Никогда не наступит, девальвирует метрику. **Рекомендация:** кольцо «герой» = не процент, а **число активных узлов с заполненностью ≥ X%** (например: «Мозг знает 247 фактов о компании, +12 за неделю»). Это растёт всегда, не упирается в потолок. Процент же показывать **per-domain** в боковой панели — там он осмыслен (потому что Маркетинг 70% означает «70% слотов RoleProfile + Process + Regulation для домена Маркетинг заполнено»).

### 11. Привязка к фазам umbrella ТЗ

Этот UI **сильно завязан на наполнение Слоя 3** (специалисты). До β у нас ещё нет ни Decision, ни Insight, ни Skill — облако будет полупустым. Поэтому:

- **α-фаза:** ничего из этой визуализации не входит. Слишком рано — данных нет, нечего показывать.
- **β-фаза:** базовая «Карта» в 2D (без 3D-pretty) + «Структура» с tree+panel для уже существующих сущностей (Person, Department, Role, Process, Regulation, Decision, Insight) — `brain-vis-mvp`.
- **γ-фаза:** 3D-режим, призрачные узлы, кольцо зрелости, WebSocket-анимация роста, прогресс-бары по доменам, таймлайн — `brain-vis-full`.
- **γ+:** realtime во время созвона, streaming-extraction, кастомные иерархии узлов от admin.

### 12. Предлагаемый раскрой на ТЗ (для будущего)

Когда будем готовы превратить это в ТЗ — разбить на 4 sub-TZ под `plans/tz/`:

1. **`brain-vis-1-graph-api`** — бэкендовый. Endpoint `GET /api/v1/brain/graph` с серверной кластеризацией, агрегатами зрелости per-node, флагом «expand/collapse» уровня. WS-канал `brain.graph.updated`. Без UI.
2. **`brain-vis-2-structure-tab`** — фронт. Вкладка «Структура»: tree-navigator + node-panel + slot-provenance + React Flow для процессов. На существующих данных Слоя 3.
3. **`brain-vis-3-map-tab`** — фронт. Вкладка «Карта» в 2D-режиме на `react-force-graph-2d`. Базовая физика, клик-в-структуру, без 3D и без анимации роста.
4. **`brain-vis-4-maturity-and-growth`** — поверх 1+3. Кольцо зрелости, призрачные узлы (по `declared but unobserved`), цвет/яркость по полноте, WS-анимация прорастания после `meeting.completed`. **Опционально**: 3D-режим как переключатель.

Таймлайн (слайдер «как мозг рос») — отдельный 5-й ТЗ, только если придёт явный запрос от пилотов.

### 13. Что закрыть до перехода к ТЗ

Прежде чем писать sub-TZ, нужно явное решение владельца продукта по:

- [ ] 3D разрешён в продуктовом UI как исключение для дата-визуализации? (см. §10.1)
- [ ] «Карта» заменяет `/dashboard` как landing после wizard'а, или живёт на отдельном `/brain`? (см. §10.2)
- [ ] Базовая библиотека графа — `react-force-graph` (универсальная 2D+3D) или Cytoscape (только 2D)? (см. §10.3)
- [ ] Источник «дыр» в MVP — `declared but unobserved` или активные вопросы Probe-Agent? (см. §10.4)
- [ ] Realtime во время созвона нужен для MVP или хватит пакетной анимации после `meeting.completed`? (см. §10.5)
- [ ] Что значит «100% мозга»? Если не значит ничего — принимаем альтернативу «N фактов, +K за неделю» вместо процента? (см. §10.6)
- [ ] «Домены» (Маркетинг/Продажи/Производство) — это `Department` Фазы 0, или новый агрегат?

После закрытия — пишется зонтичный ТЗ `tz/YYYY-MM-DD-second-brain-visualization-umbrella.md` с 4 sub-TZ по §12.
