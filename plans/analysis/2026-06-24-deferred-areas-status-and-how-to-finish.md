## 1. Задачи (task_closure / task_review / progress_draft) — РЕШЕНО ЧАСТИЧНО (PR #56)

**Что уже сделала параллельная сессия (PR #56, коммиты в `dev`):**
- **Ф6** (`probe-response.handler.ts:152`, коммит `0a9613fb`) — единый диспетчер ответов на probe: `task.*`, `task.completion_detail_missing`, `decision.*` маршрутизируются; отрицательный ответ «удалить» → `softDelete`/intake reject (обратимо); `poorly_specified`/`false_positive` → дозапись в описание. **Петля «человек ответил → система применила» закрыта.**
- **Ф7** (`me-tasks.service.ts:386`, `1221ee85`) — gate конкретики при закрытии: пустой note / непрошедший LLM-verify → НЕ плодит молчаливого кандидата, поднимает probe `task.completion_detail_missing` автору. Fail-open.
- **Ф8** (`pending-actions.service.ts:590`, `d9edd103`) — постановщик уведомляется при закрытии задачи исполнителем (`task.closed_for_review`, kill-switch `tracker.closureNotifyCreatorEnabled`).
- **Ф9** (`task-completion.handler.ts:188`, `443e14e0`) — verdict «не выполнено» даёт ЗАМЕТКУ-прогресс (живая карточка), а не ложный кандидат на закрытие; описание не перетирается; идемпотентно по `sourceBlockId`.

**Что НЕ решено и почему:** количество ручных подтверждений закрытия принципиально не снижено. **Инвариант R13: авто-закрытие задачи запрещено** — каждый `TaskClosureCandidate` ждёт ручного confirm. Это сознательная политика (не баг): закрытие задачи — необратимое для отчётности действие, человек подтверждает.

**Как доделать (если владелец захочет ослабить R13):**
- Ввести AUTO-закрытие за порогом уверенности верификатора + kill-switch `tracker.autoCloseEnabled` (дефолт OFF — это «решение владельца» по матрице флагов, необратимо меняет что видят люди). Высокая уверенность (≥0.9) + явный сигнал «сделано» из разговора → закрыть с аудит-выборкой; иначе кандидат человеку.
- `task_review` (задача «под вопросом» после supersede) — увести из счётчика подтверждений в дайджест (NUDGE): человек проверяет пачкой, не по одной.
- `progress_draft` — публиковать молча при высокой уверенности (сейчас Р2 запрещает авто-постинг); ослабить за kill-switch.
- **Рекомендация:** это решение владельца (необратимость R13). Не делать без явного «ослабляем R13». Оформить отдельным ТЗ при запросе.

## 2. Конфликты (conflict-arbiter.cron.ts) — автономен на 90%, одна дыра

**Что есть:** авто-резолв `keep_old`/`accept_new`/`merge` при консенсусе дебата (unanimous|majority), без fallback, `avgConfidence ≥ 0.7` (крутилка `knowledge.curationConflictArbiterMinConfidence`). Арбитр **получает первоисточник** — обе версии `CardVersion.payload` + `evidence`/`relationType`/`detectedBy` в `contextBlocks` (`conflict-arbiter.cron.ts:238`). Крон суточный 02:00. Разобрал 36/40 в Org «Ооо луа».

**Дыра (НЕ решено):** эскалация к человеку = ровно ОДНА ступень. Если консенсуса/уверенности нет ИЛИ вердикт `evolving`/`escalate` → `return 'leftOpen'` (строка ~280) — конфликт остаётся open **МОЛЧА**. `notifyOwner` (строка ~339) зовётся ТОЛЬКО при `auto_resolved`, при `leftOpen` уведомления НЕТ. Конфликты копятся невидимо.

**Как доделать (малый объём, low-risk):**
- Вторая ступень: дозревший `leftOpen`-конфликт (по возрасту, напр. >24ч с `detectedAt`) → одно уведомление/probe владельцу с обеими версиями (контекст уже собран в `existingVersion`/`newVersion`). Kill-switch `knowledge.conflictEscalateStaleEnabled` (ON).
- Опц. vNext: причесать промпт арбитра по методологии (как судью курации, Блок A) — выигрыш мал, первоисточник уже есть.
- **Рекомендация:** сделать вторую ступень (это закрывает «молчаливое накопление»). ~1 кодер, тест на «leftOpen старше N → уведомление вызвано один раз (идемпотентно)».

## 3. Доставка-«добивалки» — расхождение код vs ТЗ

**Две сущности:**
- `PendingActionsReminderCron` (`pending-actions-reminder.cron.ts`) — крон ежечасный, шлёт только в слот-часы. `buildSlotHours(start,end,step)` на дефолтах `start=9/end=9/step=12` (typed-config) даёт **только `[9]`** → фактически 1 напоминание/день в 9:00, а НЕ «9/12/15/18/21 до 5×/день» как описывал ТЗ. Дедуп Redis по `userId:tenant:дата:час`.
- `ProactiveWatcherCron` (`proactive-watcher.cron.ts:17`) — сторож `@Cron('0 */6 * * *')` каждые 6ч за флагом `proactive.enabled`. 8 правил «застрявшее без владельца» (не очередь подтверждений).

**Мелкая дыра:** `progress_draft` есть в `SOURCE_LABEL` и в `PendingActionsService.providers`, но выпал из массива `breakdown` в `buildReminderBody` → черновики прогресса не перечисляются в тексте напоминания.

**Почему отложено:** мастер-ТЗ §4 — параллельная сессия писала уведомления постановки задач (Ф8); правки доставки рисковали сломать. Сейчас Ф8 в `dev` — зона свободна.

**Как доделать (только крутилки + 1 строка, low-risk):**
- Реальные слоты: сменить дефолты AdminSetting `reminderWindowEndHour=21`, `reminderStepHours=3` → `buildSlotHours` даст `[9,12,15,18,21]`. **Это решение владельца** (сколько раз/день добивать) — спросить, не менять молча. Код менять НЕ надо (крутилки).
- `progress_draft` в breakdown: добавить элемент в массив `buildReminderBody` (1 строка).
- **Рекомендация:** строку `progress_draft` — починить сразу (тривиально); частоту слотов — вынести владельцу как настройку (по умолчанию оставить как есть, не спамить).

## 4. Intake (22 висящих задачи) — не тронуто PR #56; Блок C частично помогает

**Условие авто-создания** (`intake-auto-triage.worker.ts:330`, `canAutoAccept`): для встречи — проект + не-дубль + источник разрешён (`meetingTasksAlwaysPromote=true`); для НЕ-встречи — ещё `confidence≥0.75` И исполнитель определён И проект. Висящие 22 = не-встречные / низкоуверенные / без исполнителя/проекта. Видны ТОЛЬКО owner/admin (`intake.provider.ts:40` isPrivileged) + `confidence≥0.3` — отсюда «всё свалено на владельца».

**Что улучшил Блок C этой сессии:** для не-встреч добавлен смысловой подбор исполнителя по навыкам (`SkillRoutingService`) ПЕРЕД fallback на владельца Org — часть «нет исполнителя» теперь закрывается авто-подбором (коммит `8c329916`). Это снижает долю висящих по причине «не выведен исполнитель».

**Что осталось (Развилка 2 — на паузе у владельца):**
- Дефолт авто-приёма intake без исполнителя — Р2 мастер-ТЗ, анализируется в параллельной сессии. Не входит в эту сессию.
- Адресация probe `task.assignee_unresolved` для intake-канала идёт на owner, а не на автора (Ф5 author-probe сделана только для meeting-extract).
- **Как доделать:** по итогам Р2 — либо понизить порог `confidence` авто-приёма для доверенных источников (`intake.autoAcceptSources`), либо авто-создавать с владельцем Org как временным исполнителем + пометка (как уже делается для не-встреч). Решение владельца (необратимо плодит задачи) — ждёт Р2.
