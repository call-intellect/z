# ТЗ: задачная петля «разговор → трекер → доуточнение → отклонение/доработка → закрытие», авторство реплик и симметрия с решениями

## Цель
Довести задачную петлю Коры до канонической постановки владельца (анализ §0.1): задача из любого разговорного канала автоматически попадает в трекер с 4 сущностями (название, описание, исполнитель, срок); при нехватке исполнителя/срока Кора сама задаёт уточняющий вопрос **автору реплики** в кабинет И Telegram (с опцией «удалить»); ответ применяется; закрытие требует конкретики; постановщик узнаёт о закрытии; карточка живёт. Тот же механизм уточнений работает и для решений.

## Зачем (болезненное состояние)
- Доказано на проде (встреча `01KVQDR2`, анализ §3): задача «изучить сервис» приехала **без исполнителя**, хотя в реплике звучало «задача мне». Корень — инструкция агента запрещает само-назначение; реальный A/B на `deepseek-chat` показал: текущий промпт `null`↔спикер (лотерея), правленый — стабильно ставит автора реплики. **Смена модели не лечит — лечит промпт + передача автора реплики.**
- Уточнения уходят владельцу встречи, а не тому, кто проговорил задачу (анализ §4).
- Нельзя словами сказать «это не задача / распиши подробнее / удали»; ответы на уточнения по решениям не применяются вообще.
- Постановщик не узнаёт о закрытии; карточка не обогащается деталями из последующих разговоров.

## Доказательство выбора
Полная состязательная база и матрицы вариантов — в анализе §3/§7. Ключевое: корень потери исполнителя — промпт (A/B на `deepseek-chat`, 2/2), поэтому Ф3 правит инструкцию агента, а не модель; авторство теряется в `SegmentBuilder` для не-встреч (Ф1); резолвер-дубль убираем единым сервисом (Ф4).

## Scope
**Входит:** Ф1–Ф9 ниже (авторство реплик; промпт само-назначения; резолвер встреч; адресат probe; отклонение/доработка словами; общий диспетчер ответов задачи+решения; gate закрытия в concierge; уведомление постановщику + движение карточки; живая карточка; двухканальные уведомления).
**Не входит (vNext, отдельные ТЗ):** тонкие decision-сценарии (устаревание/конкурирующие версии/`outcome_unknown` авто-сбор); полный отказ от legacy-модели `Task`; UI-редизайн карточки задачи; голосовой ВЫВОД (только текст, инвариант). Каждый хвост — в `relates_to` будущего ТЗ при появлении.

## Граничные контракты

- Прод-доставка Telegram (`conversational`/notification-слой) — используем существующий канал; новые типы уведомлений добавляем в него.

## Фазы

### Ф1 — ФУНДАМЕНТ: сквозная привязка автора реплики к сотруднику (Р-3/П9)
**Цель.** Довести `authorPersonId` каждой реплики до агента извлечения по всем каналам.
**Картография.** `segment-builder.service.ts:89-100` (`tryGetFullText` — берёт `fullText`, игнорирует `turns`), `:255-333` (`buildFromMeeting`, `:294` сохраняет `speakerParticipantId`); `chatbox-ingest.service.ts:289-302` (`turns` с `authorPersonId`, клиент=null); `bitrix-ingest.service.ts:269-280` (`turns` с `authorPersonId`); `schema.prisma` IdeaBlock `commitmentAuthorPersonId:3424` (только commitment).
**Что входит.**
1. Миграция: добавить `authorPersonId String?` на единицу текста, доходящую до извлечения (сегмент/evidence). Точную модель определить по факту прохождения текста в агент (`IdeaBlockEvidence` или промежуточный segment-store) — **[ASSUMPTION: поле на `IdeaBlockEvidence`; перечитать путь `segment → block → evidence → specialist` и закрепить там, где quote реально формируется]**. `@@index([tenantId])` если таблица tenant-scoped.
2. `SegmentBuilder` для чат-бокса и Битрикса: не терять `authorPersonId` из `turns` — сохранять в сегмент (как `speakerParticipantId` для встреч). Для клиента чат-бокса (`authorPersonId=null`) проставлять явный маркер внешнего автора (`authorExternalLabel='Клиент'`).
3. Довести `authorPersonId`/метку до входа агента извлечения задач (структура `{quote, авторPersonId, авторLabel}` вместо плоской цитаты).
**Не входит.** Изменение самих агентов извлечения (Ф3); Telegram-заметка (одиночное сообщение — автор=отправитель, уже есть).
**Acceptance.**
- Миграция-файл в `prisma/migrations/`, повторный `migrate deploy` = no-op.
- unit: чат-бокс-сессия из 2 реплик (клиент+менеджер) → сегменты несут `authorPersonId` менеджера и метку «Клиент» для клиента (grep поля в результате `SegmentBuilder`).
- unit: Битрикс-сообщения с `authorExternalId` → сегмент несёт `authorPersonId` автора.
- интеграц: на входе агента извлечения для чат-бокса видно авторство каждой цитаты (не только подпись-строка).
**Закрывает:** Р-3.

### Ф2 — Двухканальное уведомление с взаимным закрытием (Р-9, инфра для Ф3–Ф8)
**Цель.** Любое уточнение/уведомление — одно логическое, в кабинете И Telegram; ответ в одном канале закрывает в другом.
**Картография.** Probe-слой `probe.suggest`/доставка (`probe-response.handler.ts`), notification-слой (`pending-actions`/`conversational`). REALITY-CHECK при старте: проверить, доставляется ли probe уже в оба канала и есть ли единый статус.
**Что входит.**
1. Единый статус логического уведомления (`open`/`answered`/`dismissed`) с дедупом по `(reason, contextId, recipientId)`.
2. Доставка в кабинет И Telegram одной сущностью; ответ/подтверждение в одном канале → перевод статуса → второй канал гасит элемент (в кабинете пропадает, в Telegram помечается закрытым).
3. Крутилки окон/повторов — `AdminSetting` через `getDynamic` (не ENV).
**Не входит.** Сами reasons (Ф5); контент уведомлений о закрытии (Ф8).
**Acceptance.**
- интеграц: уточнение создаёт ОДНО уведомление, видимое в кабинете и в Telegram; ответ в Telegram → запись в кабинете гаснет (статус `answered`); повторная доставка не дублирует.
- unit: дедуп по `(reason, contextId, recipientId)` — второй `suggest` не плодит вторую запись.
**Закрывает:** Р-9.

### Ф3 — Само-назначение «мне/я» в промпте + автор реплики агенту (П1, Р-2)
**Цель.** На честное само-назначение агент ставит исполнителем автора реплики.
**Картография.** `tasks-unified.ts:173-182` (`BASE_SYSTEM`, правило «спикер не определён → assignee=null»); `meeting-extract-actions.service.ts:174-187` (вызов `buildMeetingExtractActionsPrompt` — список авторов реплик в промпт сейчас не передаётся структурно).
**Что входит.**
1. Правка инструкции агента (промпт): добавить правило само-назначения — «если человек берёт задачу на себя („задача мне“, „я сделаю“, „беру на себя“), исполнитель = автор этой реплики; если это пересказ чужих слов — не подставлять (различай по смыслу)». **Без жёсткого кода-парсера** (Р-2).
2. Передать агенту имя/идентификатор автора каждой реплики (из Ф1). Переменная часть (список авторов реплик) — в КОНЕЦ user-сообщения (caching).
**Не входит.** Смена модели (доказано: не лечит); резолвер (Ф4).
**Совместимость с prompt caching.** Правка SYSTEM ломает кэш на один деплой — допустимо разово (анализ §9). Список авторов — переменная часть, идёт в конец user, SYSTEM далее стабилен.
**Acceptance.**
- A/B-регрессия на захваченном промпте встречи `01KVQDR2` (`ab-extract-model.ts` или эквивалент): текущий промпт даёт `null` хотя бы в части прогонов, правленый — стабильно ставит автора реплики для «задача мне изучить сервис». Прогон документировать.
- unit: реплика-пересказ «Петя сказал, задача мне…» → исполнитель НЕ автор-пересказчик (или `null`+probe), не ошибочная привязка.
**Закрывает:** Р-2 (часть), каноника п.2.

### Ф4 — Резолвер исполнителя встреч: все сотрудники Org + автор реплики (П2-встречи, Р-4)
**Цель.** Имя из разговора резолвится по всей компании; «мне» → автор реплики.
**Картография.** `task-assignee-resolver.service.ts:27-51` (узкий матч по участникам встречи, `:38-48` `byName`); широкий резолвер `intake-auto-triage.worker.ts:728-746`; единый `AssigneeResolverService` (`ee6ef1fa`).
**Что входит.**
1. Для встреч матчить имя по всем сотрудникам Org (`Person relationship=employee`), не только участникам; per-tenant (`tenantId`).
2. Fallback: при `assignee=null` и наличии `authorPersonId` реплики (Ф1) — подставить автора реплики.
3. Свести к единому резолверу с текстовыми каналами — не плодить дубль; узкий `task-assignee-resolver` либо расширить, либо заменить вызовом единого.
**Не входит.** Изменение промпта (Ф3).
**Acceptance.**
- unit: «Айназ» (сотрудник, НЕ участник встречи) → resolved userId; per-tenant изоляция (чужой Org не матчится).
- unit: задача с `assignee=null` но известным автором реплики → исполнитель = автор.
- греп: один резолвер исполнителя на встречи и текстовые каналы (нет двух параллельных substring-резолверов).
**Закрывает:** Р-4.

3. Мягкое обратимое удаление задачи (Р-1): миграция soft-delete для `Issue` (поле `dismissedAt`/`deletedAt` + причина) **[ASSUMPTION: проверить, есть ли уже архивное поле у Issue; если есть — переиспользовать]**; окно возврата — `AdminSetting` (`getDynamic`, дефолт ~1 день); аудит-запись.

**Закрывает:** П3, Р-1, Р-5 (часть).

1. При подтверждении закрытия — уведомление постановщику (`createdById`) «исполнитель закрыл „…“, проверьте» через Ф2 (двухканально); НЕ слать если `createdById == исполнитель` (Р-7).
2. REALITY-CHECK движения карточки на проде: механизм есть; проверить выкат `dev`→прод и доставку запроса подтверждения (иначе кандидат висит `pending`, карточка стоит — жалоба владельца). Если кандидат не доходит — починить доставку (через Ф2).
**Не входит.** Новый state-transition (механизм есть).
**Acceptance.**
- интеграц: исполнитель≠постановщик → постановщик получил уведомление о закрытии (кабинет+Telegram); исполнитель=постановщик → не получил.
- интеграц: подтверждение закрытия → `Issue.stateId` = completed, карточка в «Готово», `completedAt` проставлен.
**Закрывает:** П7, П8, Р-7.

### Ф9 — Живая карточка: авто-обогащение из разговоров (П10, Р-8)
**Цель.** Детали по существующей задаче из новых разговоров сами дописываются в карточку.
**Картография.** `me-tasks.service.ts:397-431` (`reportTaskProgress`→`ProgressUpdatesService`); `comments.service.ts` (`issueComment.create`); связывание задачи с разговором — `unified-task-extraction` дедуп/`TaskSource`; `knowledge-core` в карточку не пишет (проверено: нет `progressUpdates.create`).
**Что входит.**
1. Когда анализ разговора находит детали по уже связанной существующей задаче (прогресс/шаги/факт выполнения) — дописывать **отдельным комментарием/заметкой** с пометкой «из разговора от <дата>» + ссылка на источник; не перезатирать описание и ручной ввод (Р-8).
2. Идемпотентность: один и тот же блок-источник не дописывается дважды (дедуп по источнику).
**Не входит.** Авто-закрытие по найденному «выполнено» (это путь Ф7, через кандидата+подтверждение).
**Acceptance.**
- интеграц: разговор с деталями по существующей задаче → в карточке появился комментарий «из разговора от <дата>» со ссылкой; описание не перезаписано.
- unit: повторный прогон того же блока → второго комментария нет (идемпотентность).
**Закрывает:** Р-8.
