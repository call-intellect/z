# Анализ: Фаза γ — UI для каркаса 5 уровней, дельта Declared vs Observed, динамическая онтология

> **Это скелет с картой развилок.** Решения по каждой развилке пишутся итеративно после ревью этого скелета. До следующего ревью трактовать как _работу в процессе_, не как источник правды.

## 0. Зачем этот документ

К моменту запуска Фазы γ в БД пилотных компаний уже несколько недель копятся сущности группы Б — Mission, Vision, Strategy, Process, ProcessStep, Regulation, Policy, Tool, Metric, Decision. Они извлекаются автоматически из встреч и документов через `BlockExtractionService` (Фаза 0b), сохраняются с провенансом через `GraphService.upsertEntity` (Фаза 0a), дедуплицируются через `EntityResolutionService`. Но снаружи их видно только как readonly-провенанс на странице документа (`/documents/:id`, см. аналитика ЛК §7.4, решение 11) — отдельных страниц для этих сущностей в Фазе 0 нет.

Фаза γ снимает этот провал: добавляет UI поверх уже наполненной БД, без переписывания каркаса ЛК (обещание зонтичного ТЗ Фазы 0, строка 316 матрицы и раздел 9 «Связь с roadmap'ом»).

Этот документ — **аналитика γ-фазы, аналогичная аналитике ЛК Фазы 0**. Цель — закрыть все большие развилки до того, как писать зонтичный ТЗ. Без этой аналитики писать ТЗ опасно: scope γ объёмнее Фазы 0, и попытка сразу разбить её на sub-TZ без предварительного scope-кат'а почти гарантированно даёт переделку.

**Что я НЕ решаю в этом документе:**
- Визуальный дизайн страниц группы Б (цвета, шрифты, motion — `second-brain/02_architecture/design-system.md` + design-system).
- Конкретные API-контракты эндпоинтов CRUD группы Б (это уровень sub-TZ γa/γb).
- Деталь промптов LLM для динамической онтологии и для дельты Declared vs Observed (это sub-TZ γc/γd).
- Текст копирайта на страницах группы Б (это `second-brain/13_glossary/copy-strings.ru.md`).

## 1. Контекст: что уже стоит к моменту γ и что осталось добавить

### 1.1. Что физически есть в БД и коде к моменту γ (после Фазы 0)

**Модели данных:**
- 10 моделей группы Б (Mission, Vision, Strategy, Process, ProcessStep, Regulation, Policy, Tool, Metric, Decision) — есть, наполняются.
- 17 типов рёбер каркаса 5 уровней — есть, объявлены и используются extraction'ом.
- Apache AGE + `GraphService` — стоят, работают.
- `EntityLink(fromId, fromType, toId, toType, linkType, validFrom, validTo, properties)` — единая модель рёбер, есть.
- `Document` с парсенным текстом и провенансом — есть.
- `RoleProfile` — есть, наполняется `RoleProfileAgent`.

**Что наполняется автоматически:**
- Extraction-LLM (расширенный `BlockExtractionService`) при разборе встреч и документов создаёт типизированные сущности группы Б с провенансом (`sourceDocumentId`, `sourceIdeaBlockId`, `confidence`).
- `EntityResolutionService` дедуплицирует по доменным правилам + cosine + LLM-arbiter (зонтичный ТЗ строки 65, 308).
- На неуверенных случаях (LLM колеблется Process/Regulation/Policy) — сохраняется как `Process` с `confidence<0.6` + `ambiguousTypes` в metadata (зонтичный ТЗ строка 373, решение по открытому вопросу №9).

**UI:**
- Sidebar в 3 группах (Компания / Оперативка / Настройки) — есть с Фазы 0c.
- В группе «Компания» свёрнутая подгруппа «Будет в следующей фазе» с 4 disabled-γ-пунктами: `/processes`, `/regulations`, `/policies`, `/metrics` (`<ComingSoonPage>` с счётчиком «N собрано» для admin).
- На странице документа `/documents/:id` сущности группы Б — readonly-провенанс (имя+тип+confidence, без CRUD, без ссылок на отдельные страницы).
- Команд-палитра ⌘K расширена на Role / Department / Person / Document / RoleProfile / Theme.

**Чего НЕТ:**
- Отдельных страниц для любой сущности группы Б (Mission/Vision/Strategy/Process/Regulation/Policy/Tool/Metric/Decision).
- Возможности редактировать / отвергнуть / слить / утвердить автоизвлечённые сущности.
- Возможности создать сущность группы Б вручную через UI.
- Модели `OntologyType` (динамическая онтология) и связанной инфраструктуры extraction.
- UI «дельта Declared vs Observed» (между JobDescription и RoleProfile, между Regulation и фактически наблюдаемыми ProcessStep).
- UI для RACI (`responsible_for` / `accountable_for` / `consulted_on` / `informed_about` — типы рёбер заведены, UI отсутствует).
- Срезов времени (`/today`, `/week`, `/month`) и смысловой карты (`/map`) из `second-brain/02_architecture/design-system.md`.
- Полного `/dump` (голос, файлы, AI-feedback) и полной `/me` (обещания, настроение).

### 1.2. Что в roadmap'е изначально приписано к γ

Из зонтичного ТЗ Фазы 0, раздел 9 «Связь с roadmap'ом»:

> **Фаза γ** (UI для слотов группы Б: страницы и админка процессов / регламентов / политик / метрик / целей; динамическая онтология OntologyType; дельта Declared vs Observed)

Из аналитики ЛК Фазы 0, §12 «Что отложено явно» — на γ помечены **дополнительно**:
- `/today`, `/week`, `/month` (срезы времени).
- `/map` (смысловая карта компании, Cytoscape).
- `/decisions`, `/ideas`, `/risks` (новые разделы).
- `/knowledge` (wiki).
- Полная `/me` (обещания) — частично γ.
- Голос / файлы / AI-feedback в `/dump` — γ.
- Иерархия отделов и должностей в UI.
- UI назначения RACI.

Это **уже не одна фаза**, а 3-4 разных фазы, если каждый блок мерить по объёму sub-TZ.

### 1.3. Главная развилка γ-аналитики

Сравнить γ-аналитику с аналитикой ЛК Фазы 0:
- Аналитика ЛК Фазы 0 закрыла **навигацию** ЛК + 5 новых страниц + wizard.
- γ-аналитика по объёму = **5-7 новых разделов ЛК** (страницы группы Б — это уже 10 сущностей, плюс срезы, плюс карта, плюс расширения).

Поэтому первая и главная задача этого документа — **честно вырезать ядро γ**, а остальное явно вынести в γ-extensions / δ / ε / ζ. Без этого reduction γ растягивается на полгода и блокирует все последующие фазы.

## 2. Что хотим сделать (одним абзацем)

В Фазе γ к личному кабинету Z добавляется уровень «каркас компании»: 10 типов сущностей группы Б получают свои страницы (списки + детальные карточки + ручное редактирование автоизвлечённого + workflow «утвердить / отвергнуть / слить»). Появляется визуальный паттерн «дельта Declared vs Observed» — между тем, что записано в документе/JobDescription, и тем, что система реально наблюдает из встреч. Появляется механизм динамической онтологии — компания может добавить свой тип сущности (например, «Кейс» для консалтинга), и extraction-LLM начинает его распознавать. Сидбар не перестраивается — 4 disabled-γ-пункта (Процессы / Регламенты / Политики / Метрики) превращаются в реальные страницы на тех же URL; дополнительно добавляется блок «Стратегия» (Mission/Vision/Strategy на одной странице) и «Решения» (`/decisions`). Срезы времени, смысловая карта, полные `/dump` и `/me`, иерархия отделов / должностей и UI RACI — **в γ не входят**, выносятся в отдельные пост-γ фазы.

## 3. Зачем (цель и ценность)

- **Для пользователя-admin:** через 2-3 недели после Фазы 0 у него уже есть в БД сотни автоизвлечённых сущностей группы Б, но видеть и работать с ними нельзя. γ — это «открыть крышку»: показать, что Z увидел в компании, дать редактировать и утверждать факты, превратить «AI-сводка из knowledge-core» в «карта компании, на которую я могу опереться».
- **Для пилотных клиентов:** Z из «приложения для встреч + AI-чат» становится **первой версией «памяти компании»** — продуктом, который удерживает структурированную картину организации, обновляющуюся автоматически. Это та продуктовая ценность, ради которой клиенты вообще подписывались на пилот.
- **Для продукта Z:** без γ позиционирование «память компании» (см. `second-brain/06_marketing/positioning.md`) остаётся обещанием. γ — момент, когда позиционирование становится реальной фичей.
- **Для последующих фаз:** в δ (CuratorAgent + Inquiry) и ζ (специализированные агенты — ProcessNarrator, DecisionArchaeologist, AlignmentAgent) нужны UI-поверхности, на которых эти агенты что-то показывают. γ создаёт эти поверхности — без них δ/ζ некуда «писать».

## 4. Карта больших развилок γ (что закрывает эта аналитика)

Список 15 ключевых развилок, по которым γ-аналитика должна принять решение. По каждой — короткий заголовок + 1-3 предложения «в чём суть выбора» + ссылка на источник. **Сами решения — в §5 (после ревью этой карты).**

### A. Скоп и структура γ

**A1. Бордюр γ-фазы — что входит, что явно вынесено.**
Большая проблема: roadmap-определение γ + аналитика ЛК Фазы 0 §12 + delivery/06 вместе дают объём 3-4 фаз. Нужно решить: γ-core = только UI для группы Б + дельта + динамическая онтология (как в исходном roadmap-определении); срезы / карта / полный dump / полное me / RACI / иерархии — отдельные фазы (γ-time, γ-map, γ-capture, γ-me, γ-org-tree). Альтернатива — расширить γ до «всё, что отложено на γ в аналитике ЛК».
_Источник:_ зонтичный ТЗ §9, аналитика ЛК §12.

**A2. Количество и границы sub-TZ γ.**
Если γ-core = UI группы Б + дельта + онтология, то логично разбить на: γa (модели OntologyType + API + RBAC + расширения extraction под динамические типы), γb (UI для 10 сущностей группы Б + workflow утверждения / слияния / отвержения), γc (UI «дельта Declared vs Observed»), γd (динамическая онтология — UI создания типа + интеграция в extraction). Альтернатива — другой раскрой (например, по сущностям: γ-process, γ-regulation, ...).
_Источник:_ структура Фазы 0 как референс (0a/0b/0c/0d).

**A3. Группировка 10 сущностей по разделам ЛК.**
Развилка: 10 отдельных пунктов в Sidebar (Mission / Vision / Strategy / Process / Regulation / Policy / Tool / Metric / Decision + ProcessStep — внутри Process)? Или объединить в логические группы (Стратегия = Mission+Vision+Strategy; Процессы = Process+ProcessStep; Регламенты = Regulation; Политики = Policy; Метрики = Metric; Решения = Decision; Инструменты = Tool)? Какие из них вообще достойны отдельной страницы в γ-core, а какие — только readonly-провенанс на странице документа?
_Источник:_ зонтичный ТЗ §2 группа Б; аналитика ЛК §6 (4 disabled-γ-пункта в Sidebar — Процессы / Регламенты / Политики / Метрики).

### B. UX-паттерны для автоизвлечённого

**B1. Workflow доверия к автоизвлечённому: статусы сущности.**
Сущности группы Б в БД заведены без UI — extraction'ом просто создаются. В γ нужен явный workflow: какой статус у сущности, когда она показывается на странице (всё подряд? только утверждённое? фильтр по confidence?), кто и как переводит сущность из «proposed» в «approved». Развилка по статусной модели: {`proposed / approved / rejected / merged_into`} vs {`auto-extracted / curated / archived`} vs «без статусов, только confidence + флаг hidden».
_Источник:_ зонтичный ТЗ §6 (решение по open-question №9 — `confidence<0.6` + `ambiguousTypes`); риск «Сущности группы Б накапливаются с шумом» §8.

**B2. UI слияния дублей.**
`EntityResolutionService` дедуплицирует автоматически, но иногда ошибается (Process «Onboarding клиента» и «Подключение клиента» — это одно или разные?). В γ нужна возможность смержить два процесса вручную. Развилка: UI инициируется со страницы списка («выберите 2 для слияния»), или со страницы сущности («предложить слияние с другой»), или вообще из отдельной admin-страницы «дубли, требующие внимания»?
_Источник:_ зонтичный ТЗ строка 308 (EntityResolutionService для группы Б); риск «Сущности группы Б накапливаются с шумом».

**B3. Provenance UI — как показываем «откуда мы это знаем».**
У каждой сущности есть провенанс — связи `sourceDocumentId`, `sourceIdeaBlockId`, `sourceMeetingId`. Развилка: показывать провенанс **inline в карточке сущности** (как сейчас IdeaBlock с цитатой), или **отдельной вкладкой «Источники»** на странице сущности, или **expand-на-клик** для каждого факта внутри сущности? Разные сущности требуют разной детализации — Decision вообще не имеет смысла без момента принятия и спикера.
_Источник:_ зонтичный ТЗ строки 154, 309 (провенанс через extraction); аналитика ЛК §7.4 (readonly-провенанс на странице документа в Фазе 0).

**B4. Действия редактирования: переименовать / переклассифицировать / отвергнуть.**
Что admin может делать с автоизвлечённой сущностью? Перечень действий: переименовать (без потери связей), переклассифицировать (Process → Regulation — это смена типа, перенос связей), отвергнуть (отметить как ложное извлечение, чтобы extraction не создавал такую же снова), смержить с другой, разделить (одна сущность ошибочно слилась из двух — split). Развилка по объёму: какой минимальный набор действий обязателен в γ-core, какие можно отложить в γ-extension.
_Источник:_ зонтичный ТЗ строка 373 (ambiguousTypes — кейс смены типа); риск «Extraction-LLM ошибается с типами».

### C. Дельта Declared vs Observed

**C1. Где живёт компонент «дельта» — отдельная страница или встроенный паттерн.**
Дельта Declared vs Observed возникает в нескольких местах: JobDescription vs RoleProfile (Фаза 0 уже даёт обе сущности), Regulation vs реально наблюдаемые ProcessStep, Mission (заявленная) vs Strategy (наблюдаемая по решениям и приоритизации). Развилка: отдельная страница `/declared-vs-observed` со списком всех расхождений (как «inbox для admin'а»), или встроенный блок на каждой странице соответствующих сущностей (на странице Role — раздел «расхождения с RoleProfile»), или гибрид (отдельная страница как агрегатор + блок на странице сущности)?
_Источник:_ онтология анализ §11.4-11.5, аналитика ЛК §12.

**C2. Триггер расчёта дельты: on-demand vs cron.**
Дельта — это вычисляемая штука, требующая LLM-вызова (сравнить два набора фактов). Развилка: считать по cron (раз в день для всех Role/Process с активными изменениями), или on-demand при открытии страницы, или гибрид (предвычислять для admin'а на дашборде, on-demand на детальной странице). Это влияет на BullMQ-воркеры в γ и на стоимость LLM.
_Источник:_ зонтичный ТЗ строки 41-42 (RoleProfile уже cron+on-demand, паттерн понятен).

**C3. Что считать «расхождением» и какой статус ему присваивать.**
Не всякое отличие — это плохо: Declared может быть устаревшим, Observed может быть шумом, оба могут быть правы (роль расширилась). Развилка по типам расхождений: missing (заявлено, не наблюдается), extra (наблюдается, не заявлено), changed (формулировка отличается). И по последствиям: показать ли admin'у предложение «обновить JobDescription согласно RoleProfile» (опасно — может перезаписать корректный текст) или просто отмечать факт расхождения без CTA.
_Источник:_ онтология анализ §11.4.

### D. Динамическая онтология

**D1. Модель `OntologyType` — что в ней лежит.**
Минимально нужно: `id, orgId, name, baseType (Process|Regulation|Policy|...), descriptionForLLM, schemaExtension (JSON), createdAt`. Развилка: разрешать ли пользовательский тип, который **не наследуется** от системного (свободный тип «Кейс» без привязки к каркасу 5 уровней)? Если да — как extraction-LLM с ним работает? Если нет — насколько ограничивает гибкость?
_Источник:_ зонтичный ТЗ §2 «Не входит», строка 92.

**D2. Как extraction подхватывает новый тип.**
Развилка: динамически подгружать `OntologyType.descriptionForLLM` в системный промпт extraction (рост промпта при росте кастомных типов; кэширование сложнее) vs отдельный extraction-проход «классификация по кастомным типам» поверх IdeaBlock'ов уже извлечённых vs гибрид (системные типы в основной промпт, кастомные — в дополнительный проход)?
_Источник:_ зонтичный ТЗ открытый вопрос №8 (разбивка extraction на проходы — уже решение в Фазе 0b «эксперимент на старте»; здесь — продолжение).

**D3. UI создания типа: master-flow vs inline в админке.**
Развилка: создавать новый тип через отдельный wizard «опишите свой тип» (3-4 шага: имя, базовый тип, описание для LLM, тестовый прогон на 3 ваших документах) — или через inline-форму в Org-Admin? Master-flow даёт лучший UX (помогает пользователю сформулировать описание для LLM), но дороже в разработке.
_Источник:_ зонтичный ТЗ §2 «Не входит».

### E. Навигация, дашборд, расширения

**E1. Расширения Sidebar в γ.**
4 disabled-γ-пункта (Процессы / Регламенты / Политики / Метрики) превращаются в активные. Развилка: добавлять ли новые пункты (Стратегия = Mission+Vision+Strategy на одной странице; Решения = `/decisions`; Инструменты = `/tools`)? Это удваивает количество пунктов в группе «Компания». Альтернатива — часть из них спрятать (Решения и Инструменты не вешать в Sidebar, доступны через прямые URL и команд-палитру).
_Источник:_ аналитика ЛК §6 (карта навигации после Фазы 0).

**E2. Виджеты дашборда CEO в γ.**
Сейчас на `/dashboard` 5 виджетов knowledge-core + виджет «Структура компании» (после Фазы 0). В γ возможны: «Каркас компании» (счётчики по 10 типам группы Б), «Дельта Declared vs Observed» (топ расхождений), «Свежие решения» (`Decision` за последние 7 дней), «Дубли, требующие внимания» (EntityResolution ниже порога). Развилка: какие из этих виджетов в γ-core, какие в γ-extension.
_Источник:_ аналитика ЛК §7.1 (виджеты дашборда).

**E3. Расширение страницы документа в γ.**
В Фазе 0 на `/documents/:id` сущности группы Б — readonly-провенанс. В γ клик на сущность ведёт на отдельную страницу. Развилка: остаётся ли провенанс по-прежнему flat-list, или меняется на «сводная таблица: что нового мы из этого документа узнали» с группировкой по типу и ссылками на сущности. Это маленькая, но важная UX-эволюция.
_Источник:_ аналитика ЛК §7.4 (решение 11).

**E4. CommandPalette ⌘K — расширение на сущности группы Б.**
В Фазе 0c команд-палитра расширена на Role / Department / Person / Document / RoleProfile / Theme. В γ она должна искать ещё и Process / Regulation / Policy / Metric / Decision / Tool / Mission / Vision / Strategy. Развилка: какой backend (расширение существующего `/api/v1/search` или отдельный эндпоинт), как ранжировать (по типу? по confidence? по recency?).
_Источник:_ аналитика ЛК §4.4, §15 п.10; строка 83 матрицы.

### F. Глоссарий и расширения скопа

**F1. Расширение глоссария UI новыми терминами.**
В Фазе 0 в глоссарий попали 12 терминов группы А. В γ добавляются термины группы Б: Миссия, Видение, Стратегия, Процесс, Шаг процесса, Регламент, Стандарт, Политика, Инструмент, Метрика, Решение, Каркас компании, Дельта (заявленного и наблюдаемого), Тип сущности (для динамической онтологии). Развилка: какие термины подходят без английских аналогов (в Z уже есть правило «UI только на русском»), а где нужны новые формулировки.
_Источник:_ feedback_admin_ui_russian_only.md; зонтичный ТЗ строка 77.

**F2. Что попадает в `<ComingSoonPage>` уже в Фазе 0c как заглушка под γ, а что добавляется новыми пунктами Sidebar в γ.**
Сейчас в Фазе 0c есть 4 заглушки: `/processes`, `/regulations`, `/policies`, `/metrics`. Если γ добавляет ещё разделы (Стратегия, Решения, Инструменты), нужно либо расширить список заглушек в Фазе 0c (чтобы пользователь сразу видел будущее), либо сразу делать новые пункты только в γ. Это влияет на патч аналитики ЛК Фазы 0.
_Источник:_ аналитика ЛК §7.7 (preview-страницы).

**F3. Tradeoff: γ-core (UI группы Б + дельта + онтология) vs полный γ (с срезами/картой/RACI).**
Главный tradeoff документа. От него зависит длительность γ (2-3 месяца vs 6-8) и порядок последующих фаз. Развилка явно фиксируется как ключевая.
_Источник:_ выводы из §1.2-1.3 этого документа.
