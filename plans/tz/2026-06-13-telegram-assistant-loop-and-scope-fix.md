# ТЗ: помощник в каналах — убрать зацикливание, вернуть управляемость, ограничить тему

> **Контекст:** инцидент 13.06.2026 — вечерний чек-ин в Telegram: ответ-отчёт принят за заказ, бот зациклился (повтор каждые ~3с), игнорировал «Стоп».
> Полный разбор: [plans/analysis/2026-06-13-telegram-assistant-checkin-incident-and-agent-channel-risks.md](../analysis/2026-06-13-telegram-assistant-checkin-incident-and-agent-channel-risks.md).
> **Статус:** реализация НЕ начата (контракт-документ).
> **Приоритет фаз: Ф1→Ф2 — корень «долбёжки и игнора» (инфраструктура, НЕ промпт). Ф3→Ф4 — корень «не понял» (маршрутизация + границы темы).**

## Принцип: два РАЗНЫХ бага, не путать (порядок = приоритет)

**🔴 БАГ №1 — самоподдерживающаяся петля. ИЗ-ЗА НЕГО 40 ЗАПУСКОВ (было бы 4000). КРИТИЧЕСКИЙ, чинится первым (Ф1).**
Помощник запускается ВНУТРИ ответа вебхуку → сервер отдаёт «принял» (HTTP 200) только через 20–30 сек (когда ИИ додумал) → прокси `telegram.crossmark.ru` не дожидается за свой таймаут → шлёт то же сообщение заново → новый запуск ИИ → снова не успели → снова повтор. **Петля СТРУКТУРНО не затухает** — обработка всегда дольше таймаута. Плюс нет дедупа по `update_id`, который оборвал бы повтор. Подтверждено логами прода: 40 доставок вебхука на ~6 реплик, ~230 LLM-вызовов; остановилось ровно когда владелец убил ключи (быстрый 401 → быстрый 200 → прокси перестал повторять).
**Петля НЕ зависит от сортировщика.** При идеальной классификации лавина случилась бы всё равно — крутились бы «правильные» ответы. Сортировщик определил, ЧТО генерилось; петлю создал синхронный вебхук. Поэтому Ф1 (быстрый ack + дедуп) — отдельный и первый фикс, не смешивать с классификатором/промптом.

**🟡 БАГ №2 — сортировщик ошибся потоком** (ответ-отчёт на чек-ин принят за обращение к помощнику). Отдельный и меньше: про «ответил не туда», НЕ про лавину. Чинится Ф3 (классификатор видит контекст диалога) и Ф4 (границы/роль). Замок темы — в коде (методология промптов Z, README §4: гейт «делать/не делать» — правилом, не на LLM).

«Долбёжка каждые 3с» = БАГ №1 (+Ф2 авто-анти-флуд, БЕЗ стоп-слов — пользователь их не знает). «Принял отчёт за заказ» = БАГ №2.

Повторное включение `ASSISTANT_CHANNEL_ROUTING_ENABLED=true` — **только после Ф1+Ф2**. До этого канал остаётся на старом узком роутере (free_note).

## Ф1 — Идемпотентность входящих + быстрый ack (убирает «каждые 3 секунды»)

**Проблема.** `TelegramWebhooksController.processUpdate` обрабатывает синхронно: HTTP 200 возвращается только ПОСЛЕ всего агентного цикла ([telegram-webhooks.controller.ts:318-354](../../backend/src/modules/conversational/adapters/telegram-bot/telegram-webhooks.controller.ts#L318) → `dispatchInbound` await → `bridge` await → `concierge.process`). Цикл дольше таймаута прокси → прокси шлёт тот же `update` повторно. `update_id` **нигде не дедуплицируется** (греп: только логируется [controller.ts:329], idempotency-дедуп есть лишь в `telegram-digest.cron.ts`). Каждый повтор = новый прогон помощника = новый ответ.

**Что делаем.**
1. **Дедуп `update_id`** на самом входе `processUpdate` (после verify secret, до ingest): `SET tg:update:<channelId>:<update_id> 1 NX EX 600`. Если ключ уже есть (`NX` вернул null) — `return { ok: true }` немедленно, без обработки. TTL 10 мин с запасом перекрывает окно ретраев прокси.
2. **Быстрый ack + фоновая обработка.** Тяжёлый путь (`ingestUpdate` с LLM-классификацией + `dispatchInbound` → агент) вынести из тела webhook в фон: webhook отвечает 200 сразу после дедупа+постановки в работу. Варианты (решение в Ф1-импл): (а) `setImmediate`/детач после ack — минимально; (б) отдельная lightweight-очередь `conversational.inbound` — надёжно (переживает рестарт). **Рекомендация: (б)** — BullMQ-очередь по образцу `conversational.send`, dedup-ключ ставится синхронно в контроллере (до enqueue), обработка — в воркере.

**Файлы.** `telegram-webhooks.controller.ts` (дедуп + ack), новый `conversational-inbound.worker.ts` + запись в `conversational-queue.ts`/`.service.ts` (по образцу send), `max-bot` webhook — тот же паттерн (C7).

**Флаг.** Не требуется (исправление дефекта, не фича). Поведение строго лучше прежнего.

**Верификация.** Unit: повтор того же `update_id` → один прогон, второй — no-op. Мини-e2e: webhook с дублем не плодит второй ответ. Метрика `telegram_inbound_deduped_total`.

## Ф2 — Автоматические предохранители от флуда (БЕЗ действий пользователя)

**Решение (14.06): стоп-команду УБИРАЕМ.** Обычный пользователь не знает кодового слова «стоп» — нельзя на это рассчитывать. Защита от лавины должна работать сама, в коде. Петлю в корне убирает Ф1; здесь — страховка на случай ЛЮБОЙ будущей петли.

**Проблема.** Нет лимита исходящих в один чат: при петле (ретраи, дубли событий, баг крона) бот может слать без ограничения.

**Что делаем.**
1. **Анти-флуд на исходящие — автоматический.** Перед `sendChatReply` из моста — счётчик `concierge:outrate:<bindingId>:<minute>` (Redis INCR+EXPIRE). Лимит (крутилка `assistant.channel.maxRepliesPerMinute`, дефолт 3): превышен → не слать, лог + метрика `assistant_channel_flood_suppressed_total`. Срабатывает само, человек ничего не делает и не знает никаких команд.
2. **Ограничитель «подряд без нового ввода».** Если помощник уже ответил N раз, а нового осмысленного сообщения от человека не было — притормозить (то же окно/счётчик). Вторая страховка поверх Ф1.

**Файлы.** `assistant-channel.bridge.ts` (rate-limit перед отправкой), крутилка в `env.schema.ts`/AdminSetting + строка в `docs/operations/feature-flags.md`.

**Флаг.** Крутилка-лимит (Ship-On, работает с дефолтом).

**Верификация.** Unit: N+1-я отправка в минуту в один чат подавлена; метрика инкрементируется. Никаких стоп-слов в логике нет.

## Ф3 — Классификатор видит контекст диалога (чинит «не понял»). БЕЗ метки.

**Решение (14.06): метку «жду ответа» НЕ ставим.** Человек может проигнорировать чек-ин — метка повиснет и будет мешать. Вместо неё классификатор сам определяет всё по последним сообщениям переписки. Одна логика, без костыля.

**Проблема (R8).** `QueryClassifierService.classify` принимает одну строку `question`; историю НЕ грузит ([query-classifier.service.ts:89](../../backend/src/modules/dialog-layer/services/query-classifier.service.ts#L89), [:233](../../backend/src/modules/dialog-layer/services/query-classifier.service.ts#L233)), Telegram передаёт `conversationId: null`. На вход идёт только `Сообщение пользователя: <текст>` — ответ-отчёт после вопроса Коры не с чем связать.

**Что делаем.**
1. **Накопление хвоста переписки per-binding.** В Redis хранить последние ~4 сообщения канала, ВКЛЮЧАЯ исходящие Коры (`checkin.prompt`, probe, ответы помощника) и входящие пользователя. TTL ~12ч. Точка записи исходящих — единый hook на доставку в канал по eventType (или `sendChatReply`/доставка чек-ина).
2. **Передать контекст классификатору.** `ClassifyInput` +`recentContext`; `buildClassifyUserPrompt` кладёт переписку в USER (переменная часть — кэш SYSTEM не страдает).
3. **Новый SYSTEM-промпт** — добавлен блок «Сначала посмотри контекст» + few-shot на живом провале + одна ловушка. Полный согласованный текст — **Приложение А** (14.06). 9 категорий, старые ловушки, формат и JSON-схему (порядок enum) НЕ трогаем.
4. **Маршрут — как сейчас, без gateway.** Решает intent: `daily_report_evening`/`daily_plan_morning` с conf≥0.7 → чек-ин; иначе прежняя логика. Контекст лишь поднимает уверенность правильной категории: «Написание кода» после вечернего вопроса Коры → `daily_report_evening` conf≥0.7.

**Модель (Р-5).** Сейчас `dialog-classify` primary = `deepseek-v4-pro` (thinking, медленнее/дороже; проверено `diag-routes` 14.06). Для классификации по 9 категориям с few-shot достаточно `deepseek-v4-flash`. **Рекомендация:** flash primary + pro secondary (надёжный JSON-откат). После Ф1 скорость классификатора на петлю не влияет — мотив flash чисто экономический. Условие: flash стабильно отдаёт strict JSON (форс tool-choice `LLM_DEEPSEEK_FORCE_TOOL_CHOICE_ENABLED` уже ON). Менять через админку `ai-models` (dialog-classify) или сид.

**Файлы.** `classify.prompt.ts` (новый SYSTEM + USER — Приложение А), `query-classifier.service.ts` (`ClassifyInput.recentContext`), `telegram-bot.adapter.ts`/`max-bot` (накопление хвоста + передача), точка записи исходящих Коры.

**Флаг.** Не требуется (улучшение классификации). Пустой хвост → прежнее поведение.

**Верификация.** Unit: контекст «[Кора] Что закрыл сегодня?» + «Написание кода…» → `daily_report_evening` conf≥0.7. Тот же текст без контекста → прежнее. Обновить снапшот `classify.snapshot.spec.ts.snap` под новый SYSTEM.

## Ф4 — Замок темы: кодовый on-topic гейт + блок роли/границ в промпте

**Проблема.** (1) Системный промпт помощника без границ ([concierge.service.ts:158-190](../../backend/src/modules/concierge/services/concierge.service.ts#L158)) — ведёт себя как ChatGPT. (2) Но граница — НЕ задача промпта (методология §4).

**Что делаем.**
1. **Кодовый on-topic гейт ДО агента** (главное). На входе `assistant_turn` (после Ф3-привязки, до `concierge.process`) — дешёвый классификатор `assistant-scope-classify` (deepseek-v4-flash primary, как `assistant-confirm-classify`): `on_topic` (знания/задачи/встречи/люди/решения/цели/процессы компании) vs `off_topic` (написать код/стихи/эссе, решить математику, общие энциклопедические вопросы). `off_topic` → шаблонный вежливый отказ, агент **не запускается** (экономия токенов + не позорится). Решение-действие (отказать) — в коде; LLM лишь классифицирует (согласовано с методологией: классификация — можно LLM, гейт-действие — код).
2. **Блок роли/границ в системном промпте** (подпорка). Добавить в стабильный SYSTEM-префикс (cache-friendly) короткий блок: кто он, что умеет (память/задачи/встречи/люди/решения), и явный запрет браться за код/стихи/математику/общее — с вежливым перенаправлением. Это вторая линия на случай, если гейт пропустил.

**Новый промпт `assistant-scope-classify` — по методологии Z** (`docs/methodology/prompts/README.md`, анатомия 7 блоков):
- Блок 1 (роль): «Ты — фильтр уместности для помощника памяти компании Кора».
- Блок 2 (якоря): зачем (отсечь не-наши запросы до дорогого агента), кому (служебный, не пользователю), что дальше (off_topic → пользователь получит вежливый отказ).
- Блок 3 (критерии): нумерованный список признаков on/off-topic.
- Блок 4 (few-shot «плохо→хорошо», ≥3, на реальных входах): вкл. живой кейс «Написание кода, нового дизайна и шаблонов» (это ОТЧЁТ о работе → on_topic если идёт как чек-ин, но как прямой запрос «напиши код» → off_topic) — показать различие «отчёт о коде» vs «просьба написать код».
- Блок 5 (self-check): «если сомневаешься между рабочим-в-контексте-компании и офтопом — это on_topic (recall-safe: лучше пустить, чем отказать сотруднику)».
- Блок 6 (контракт): строгий JSON `{decision: on_topic|off_topic, confidence: 0..1}` + schema.
- Блок 7 (запреты): чистый русский, без кодов; гейт-порог — крутилка, не в промпте.
- **Cache-friendly:** SYSTEM (роль+критерии+few-shot+self-check) стабилен; переменная часть (текст реплики) — в конце USER.

**Файлы.** Новый `concierge/prompts/assistant-scope-classify.prompt.ts`; гейт в `assistant-channel.bridge.ts`; блок границ в `buildSystemPrompt` ([concierge.service.ts:158](../../backend/src/modules/concierge/services/concierge.service.ts#L158)); регистрация `taskType` в LLM-роутере/реестре (z-ai-agent-rules); запись промпта в `docs/methodology/prompts/` (чек-лист) + эталон в `examples/` если удачный.

**Флаг.** `ASSISTANT_SCOPE_GATE_ENABLED` (kill-switch, default ON) + крутилка `assistant.scope.offtopicThreshold` (дефолт, AdminSetting). Строка в `feature-flags.md`.

**Верификация.** Unit на гейт: «реши пример 2+2», «напиши стих про осень», «напиши код сортировки» → off_topic; «какие у меня задачи», «что решили на встрече по бюджету» → on_topic. Снапшот промпта. Прод-наблюдение (методология, ship-on без golden): доля off_topic, отвечаемость, жалоб.

## Доработки по итогам прод-разбора (14.06, на реальных логах)

Прод-логи подтвердили механизм (40 доставок вебхука на ~6 реплик, `deepseek-v4-flash` validate-fail → fallback, 401 при отключении ключей — детали в анализе §8.1). Доработка к фазам (контекст диалога Ф3.1 слит в Ф3 выше — метку убрали 14.06; модель классификатора — Р-5):

### Ф4.1 — Промпт знает, ЧЕЙ это помощник (данные компании из профиля)
**Проблема (R9).** Промпт зовёт себя «помощник компании Z (Кора)» ([concierge.service.ts:159](../../backend/src/modules/concierge/services/concierge.service.ts#L159)); контекст — только `Организация: <имя> (<slug>)` ([context-builder:44](../../backend/src/modules/concierge/services/concierge-context-builder.service.ts#L44)), без описания бизнеса.
**Источник данных НАЙДЕН (проверено 14.06) — новое поле НЕ нужно:**
- `Org`: `name`, `industry` (отрасль — software/services/manufacturing/retail/construction/finance/education/other), `teamSize`. Заполняется онбордингом (`/welcome`).
- `CompanyProfile` (1:1 к tenant): `displayName`, `missionJson` (миссия, contentMd), `strategyJson` (стратегия/рынки), `stage` (early-stage/growth/scale/enterprise). Заполняется онбордингом / агентским билдом из встреч.
**Что делаем.** `ConciergeContextBuilderService.build` дополнительно тянет `CompanyProfile` + `Org.industry/teamSize` и кладёт человеческий блок «о компании» в контекст. Преамбулу `buildSystemPrompt` переписать на per-tenant: «Ты — помощник компании _<displayName/name>_ (_<industry>_, _<teamSize>_). Компания: _<миссия из missionJson>_. Ты отвечаешь по её базе знаний…». Профиль пустой → fallback на просто имя (как сейчас).
**Кэш.** Блок о компании стабилен внутри тенанта (не ломает кэш между ходами одного тенанта); per-tenant префиксы — норма. В промпт — только человеческий текст из `contentMd`/`displayName`, НЕ сырой JSON и не коды (методология §2,7).
**Файлы.** `concierge-context-builder.service.ts` (+чтение `CompanyProfile`/`Org`), `concierge.service.ts` `buildSystemPrompt` (преамбула-переменная).
**Решение владельца.** Р-4 — СНЯТО: источник найден (`CompanyProfile` + `Org`, заполняется онбордингом). Отдельное поле и admin-UI не нужны.

## Решения владельца
- **Р-1.** Что считать «по теме»: только домен компании, а рабочее-но-общее («помоги сформулировать письмо клиенту») — пускать или нет? **Рекомендация:** пускать рабочее-в-контексте, отказывать в чистом офтопе (код/стихи/математика/энциклопедия). Recall-safe: в сомнении — on_topic.
- **Р-2.** ~~Окно метки~~ — снято: метку НЕ ставим (14.06), маршрут определяет классификатор по контексту переписки. Остаётся параметр — глубина контекста (сколько последних сообщений давать классификатору). **Рекомендация:** 4 (≈2 последние пары «Кора ↔ человек»).
- **Р-3.** Порядок выката: Ф1+Ф2 → включить routing обратно → Ф3 → Ф4. **Рекомендация:** да, не включать routing до Ф1+Ф2.
- **Р-5.** Модель классификатора `dialog-classify`: сейчас в проде `deepseek-v4-pro`. **Рекомендация:** `deepseek-v4-flash` primary + `deepseek-v4-pro` secondary — дешевле/быстрее, с надёжным откатом на pro для strict JSON.

- Полный аудит 14 проактивных eventType на «ожидание ответа» (Ф3 закрывает чек-ин+probe; остальное — отдельным ТЗ, P2 анализа).

## Приложение А — новый промпт классификатора `dialog-classify` (согласован 14.06, дословно)

Целевой полный текст для `backend/src/modules/dialog-layer/prompts/classify.prompt.ts`. Изменения относительно действующего: (1) шапка-роль, (2) новый блок «СНАЧАЛА ПОСМОТРИ КОНТЕКСТ» + примеры, (3) одна ловушка про контекст, (4) USER-шаблон с перепиской. 9 категорий, остальные ловушки, формат и JSON-схема — **дословно как в текущем файле** (приведены полностью ниже для единого источника). ```

отвечаешь пользователю — только возвращаешь категорию одним JSON.

──────────────────────────────────────────────────────────────────
СНАЧАЛА ПОСМОТРИ КОНТЕКСТ ПЕРЕПИСКИ

Тебе дают последние сообщения переписки, включая те, что писала САМА
Кора (бот). Прежде чем выбирать категорию, посмотри на ПОСЛЕДНЕЕ
сообщение от Коры:

• Если Кора только что задала вопрос, а пользователь отвечает — это
  ОТВЕТ на её вопрос. Классифицируй по смыслу вопроса Коры:
   – Кора спросила про план на день / «что планируешь сегодня» →
     ответ пользователя = daily_plan_morning;
   – Кора спросила про итоги дня / «что закрыл сегодня», «как прошёл
     день», «есть ли блокеры» → ответ пользователя = daily_report_evening;
   – Кора задала другой уточняющий вопрос → note (если нет точной
     категории ниже).

• Если перед сообщением нет вопроса от Коры, или сообщение пользователя
  явно самостоятельное (новая тема, свой вопрос, своё поручение) —
  классифицируй по содержанию самого сообщения (правила ниже).

Даже короткий ответ («писал код», «всё сделал», «ничего не успел») —
это полноценный daily_report_evening, если он идёт сразу после вечернего
вопроса Коры. Не понижай уверенность из-за краткости: связь с вопросом
Коры важнее формы сообщения.

ПРИМЕРЫ С КОНТЕКСТОМ:

[Без контекста — так ошиблись 13.06]
   Сообщение: «Написание кода, нового дизайна и шаблонов»
   → воспринято как обращение к помощнику. НЕВЕРНО.

[С контекстом — это ответ на вечерний вопрос]
   [Кора] Что удалось закрыть сегодня? Есть блокеры на завтра?
   [Пользователь] Написание кода, нового дизайна и шаблонов
   → {"intent": "daily_report_evening", "confidence": 0.9}

[Тот же текст, но БЕЗ вопроса Коры перед ним — просто заметка]
   [Пользователь] Сделал код, дизайн и шаблоны
   → {"intent": "note", "confidence": 0.6}

Возможные намерения (ровно 9 категорий):

──────────────────────────────────────────────────────────────────
ВОПРОСЫ К AI-ЧАТУ КОМПАНИИ (категории 1-4)

1. factual — пользователь хочет факт, цифру, имя, дату, конкретный
   ответ. Один правильный ответ.
   Примеры:
   • «Какой бюджет на маркетинг в марте?»
   • «Кто отвечает за договор с Заречным?»
   • «Сколько встреч было на прошлой неделе?»

2. exploratory — пользователь хочет обзор темы, не ищет один точный
   факт. Просит «рассказать», «показать», «дать полную картину».
   Примеры:
   • «Расскажи, что обсуждали про найм»
   • «Что у нас по проекту КП-2?»
   • «Покажи всё, что есть про клиента Заречный»

3. analytical — пользователь хочет причинно-следственный анализ,
   сравнение, тренд, вывод. Слова «почему», «сравни», «динамика».
   Примеры:
   • «Почему упала конверсия в марте?»
   • «Сравни эффективность каналов рекламы»
   • «Какая динамика по выручке за квартал?»

4. clone_roleplay — пользователь явно хочет ответ от лица конкретного
   сотрудника или роли. В вопросе есть имя сотрудника, или слова
   «в стиле», «как ответил бы», «спроси клон», «клон <роли>».
   Примеры:
   • «Что бы Иван сказал про эту проблему?»
   • «Спроси клон маркетолога про каналы продвижения»
   • «Как ответил бы CFO про этот контракт?»

──────────────────────────────────────────────────────────────────
ЛИЧНЫЙ ПЛАН/ОТЧЁТ СОТРУДНИКА (категории 5-6)

5. daily_plan_morning — пользователь сам рассказывает свой план
   на сегодня или ближайший рабочий день. Это его рабочий план,
   а не вопрос и не идея для будущего.
   Признаки:
   • речь о делах сотрудника на СЕГОДНЯ/завтра (рабочий день)
   • перечисление задач или приоритетов
   • часто в начале сообщения есть слова «план», «планирую»,
     «сегодня хочу», «на сегодня», «утренний план»
   Примеры:
   • «План на день: КП Заречному, созвон с дизайнером, отчёт за апрель»
   • «Доброе утро, мой план на сегодня — добить три задачи по проекту»
   • «Сегодня хочу закрыть КП и созвониться с Петровым»
   • «На сегодня: А, Б, В. Блокер: ТЗ от Петрова не пришло»

6. daily_report_evening — пользователь сам подводит итоги своего
   рабочего дня. Это отчёт о том, что он сделал/не сделал, не вопрос.
   Признаки:
   • речь о делах сотрудника, которые УЖЕ произошли сегодня
   • перечисление «сделал/не сделал/не успел»
   • часто в начале есть слова «итоги дня», «отчёт за день»,
     «сегодня сделал», «по итогам дня», «как прошёл день»
   Примеры:
   • «Итоги дня: КП отправил, созвон перенесли, отчёт не успел»
   • «Сегодня закрыл задачу А, по Б застрял на согласовании»
   • «По итогам дня — две задачи закрыл, одна в работе»
   • «Как прошёл день: норм, закрыл КП, остальное завтра»

──────────────────────────────────────────────────────────────────
ВСЁ ОСТАЛЬНОЕ

7. note — обычное высказывание, заметка, мысль, описание ситуации,
   которое не подходит ни под одну категорию выше.
   Примеры:
   • «Клиент Заречный сказал, что готов подписать в пятницу»
   • «У Петрова болеет ребёнок, переносим встречу»
   • «Идея: добавить в коммерческое раздел про поддержку»

──────────────────────────────────────────────────────────────────
ЗАДАЧИ В ТРЕКЕР (категории 8-9)

8. task — пользователь поручает поставить КОНКРЕТНУЮ задачу в трекер
   (себе или другому). Это поручение с действием, часто со сроком или
   исполнителем. Не план дня (категория 5), не вопрос, не общая заметка.
   Признаки:
   • повелительная форма действия: «поставь задачу», «создай задачу»,
     «сделай», «надо сделать», «нужно», «запланируй задачу», «напомни
     сделать», «оформи задачу», «заведи задачу»
   • ОДНО конкретное дело (а не перечень плана на день) + часто срок
     («к пятнице», «до конца недели») или исполнитель («Петрову»)
   Это конкретнее, чем note: если явно просят поставить дело —
   выбирай task, а не note.
   Примеры:
   • «Поставь задачу: подготовить КП Заречному к пятнице»
   • «Сделай отчёт по продажам до конца недели»
   • «Создай задачу Петрову — проверить договор»
   • «Напомни завтра позвонить клиенту»

9. show_tasks — пользователь хочет УВИДЕТЬ СПИСОК своих текущих
   (открытых) задач. Это запрос показать его реестр задач, а НЕ новая
   задача и НЕ вопрос к памяти компании.
   Признаки:
   • просьба показать/перечислить ИМЕННО задачи самого пользователя
   • «какие у меня задачи», «мои задачи», «что мне нужно сделать»,
     «покажи мои задачи», «список задач», «что на мне», «мои дела»
   Примеры:
   • «Какие у меня задачи?»
   • «Покажи мои задачи»
   • «Что мне нужно сделать сегодня?»
   • «Мои открытые задачи»

──────────────────────────────────────────────────────────────────
ВАЖНЫЕ ЛОВУШКИ — НЕ ПУТАЙ

⚠ «План на отпуск», «план на квартал», «план на год», «план встречи»,
  «план запуска проекта» — это НЕ daily_plan_morning. Это note (или
  factual/exploratory, если сформулировано как вопрос). daily_plan_morning
  — ТОЛЬКО про рабочий день сегодня/завтра, личный план сотрудника.

⚠ «Отчёт квартальный», «отчёт по проекту», «отчёт о встрече»,
  «итоги встречи», «итоги квартала», «итоги проекта» — это НЕ
  daily_report_evening. Это note. daily_report_evening — ТОЛЬКО про
  итоги текущего рабочего дня сотрудника.

⚠ «Обсудим план на день на встрече», «надо составить план на день
  команде», «у нас есть план на день в Notion» — это note. План
  должен быть СВОИМ и КОНКРЕТНЫМ (с пунктами), а не разговором о
  планах вообще.

⚠ «Что я сегодня сделал?» — это вопрос (factual), а не отчёт. Отчёт
  — это утверждение «сегодня я сделал X», а не вопрос.

⚠ «Почему не успел отчёт?» — это вопрос (analytical), а не отчёт.

⚠ Если сообщение похоже и на план и на заметку — выбирай НЕ план
  (note), если confidence ниже 0.7. Лучше потерять план в общем
  потоке заметок, чем создать ложный отчёт в дашборде руководителя.

⚠ «План на день: А, Б, В» — это daily_plan_morning (перечень дел
  сотрудника на день), а НЕ task и НЕ show_tasks. task — это ОДНО
  конкретное поручение в трекер; show_tasks — просьба ПОКАЗАТЬ уже
  существующие задачи, а не перечисление новых.

⚠ «Какие задачи у проекта X?», «какие задачи у команды?», «задачи
  Петрова?» — это вопрос про ЧУЖИЕ/проектные задачи (factual или
  exploratory), а НЕ show_tasks. show_tasks — ТОЛЬКО про задачи самого
  пишущего («у меня», «мои», «мне»).

⚠ «Что я сегодня сделал?» — это вопрос (factual), а не show_tasks и не
  daily_report_evening. show_tasks — про ОТКРЫТЫЕ задачи впереди, а не
  про уже сделанное.

⚠ «Сделай вывод по отчёту», «сделай сравнение» — это analytical-вопрос,
  а НЕ task. task — поставить РАБОЧЕЕ дело в трекер, а не попросить
  AI-чат что-то проанализировать.

⚠ Если есть свежий вопрос Коры, не классифицируй ответ как note по
  инерции: «писал код», «всё сделал», «закрыл два КП» после вечернего
  вопроса Коры — это daily_report_evening, а не note.

──────────────────────────────────────────────────────────────────
ФОРМАТ ОТВЕТА

Отвечай СТРОГО в JSON, без markdown-блоков, без префиксов, без
пояснений:

{"intent": "<категория>", "confidence": <число от 0 до 1>}

confidence — твоя уверенность в классификации:
• 0.9-1.0 — очевидно (явные признаки категории, ловушек нет)
• 0.7-0.89 — уверен (несколько признаков, ловушки исключены)
• 0.5-0.69 — сомневаешься (один признак, есть похожие категории)
• <0.5 — почти угадываешь (лучше выбрать note)

Если сомневаешься между категорией и note — выбирай note и
ставь confidence 0.5-0.6. Система обработает корректно.
