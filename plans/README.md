# plans/ — технические планы функций

Один план = одна функция.

## Структура

```
plans/
  analysis/      — анализ фичи: рынок, аналоги, gap-таблица, матрица вариантов (feature-analyst)
  architecture/  — архитектура решения человеческим языком: что есть → что делаем → как будет выглядеть; владелец одобряет ДО ТЗ (solution-blueprint)
  tz/            — техническое задание: scope, изменения, DoD (tz-author)
  archive/       — завершённые или отменённые планы
  README.md      — этот файл
```

## Жизненный цикл

1. **Анализ** → `analysis/YYYY-MM-DD-название.md` (доказательная база, рынок, варианты)
2. **Архитектура** → `architecture/YYYY-MM-DD-название.md` (замысел простым языком; `status: draft → approved` — владелец одобряет «да, именно это»)
3. **ТЗ** → `tz/YYYY-MM-DD-название.md` (контракт; пишется только при одобренной архитектуре)
4. **Реализация** → агент отмечает фазы `[ ]` → `[x]`
5. **Завершение** → файлы переносятся в `archive/`

Цепочка скиллов: `feature-analyst → solution-blueprint → tz-author → tz-orchestrator`. **Gate:** `tz-author` не пишет ТЗ без `architecture/<feature>.md` со `status: approved` — жёстко, без исключений.

## Правила

- Имя: `YYYY-MM-DD-название.md` (kebab-case); `feature`-slug единый через анализ → архитектуру → ТЗ.
- План делится на фазы. У каждой статус `[ ]` или `[x]`.
- Архитектура — для человека-владельца (простой язык, «было→стало», макеты), не машинный контракт.
- В конце ТЗ — итоговый блок: реализован целиком или нет, что осталось.
- **Любой агент обязан актуализировать план** после каждой сессии.
- Шаблоны: `analysis/_template.md`, `architecture/_template.md`, `tz/_template.md`.
