## Правила работы

### Жёсткие
1. **Не коммитить и не пушить без явного подтверждения владельца.** Каждая фаза заканчивается отчётом и просьбой «закоммитить и идти дальше?». Push — отдельное подтверждение.
2. **Меняем ТОЛЬКО видимые пользователю строки.** Запрещено трогать: имена переменных/функций/типов, props, ключи объектов, URL-маршруты, enum-значения, значения с бэка, `data-testid`, ключи i18n, CSS-классы, токены. Если перевод метки требует переименовать переменную — НЕ переименовывай, переводи только строковый литерал.
3. **Источник правды — глоссарий.** Перед правкой строк фазы убедись, что нужные пары есть в `delivery/13-glossary.md`. Нет — сначала Фаза 0 (пополнение глоссария), потом код. Не выдумывай переводы в коде мимо глоссария.
4. **Не пропускать typecheck.** После правок фронта → `cd frontend && bun run typecheck`. Красное → дальше не идёшь.
5. **Не пропускать lint.** `cd frontend && bun run lint` после фазы. Красное → чинишь.
6. **Проверка на остаточную латиницу.** После каждой фазы — Grep по затронутым файлам на латинские слова в JSX-тексте/строковых литералах меток. Найденное (кроме allowlist брендов из §4.2 ТЗ) — не закрыто.
7. **Sub-агенты иногда лгут про `[x]`.** После каждого спавна — `git status`, re-Read изменённых файлов, Grep ключевых старых англ. строк (должны исчезнуть) и новых русских (должны появиться). Не верь отчёту без верификации.
8. **Не использовать `git add .` / `-A`.** Перечисляй пути явно.
9. **Не «улучшать по дороге».** Видишь рядом плохой код/логику — не трогай, это вне scope. Зафиксируй владельцу отдельной строкой «замечено вне scope».
10. **Бренды/протоколы (§4.2 ТЗ) НЕ переводим**, а обрамляем русским пояснением при первом упоминании на странице. Не переводи S3/LiveKit/BullMQ/IMAP в «эс-три» и т.п.

### Мягкие
1. **Развилка перевода → доказывай.** Если у термина несколько разумных русских вариантов (напр. «Provider» → «Провайдер» vs «Поставщик»), выбери по уже принятому в глоссарии/copy-strings канону; если канона нет — `Plan` агент с 2-3 вариантами, выбор, одна строка обоснования в `second-brain/05_история/`. НЕ оставляй выбор владельцу без нужды — ты решаешь и доказываешь.
2. **Консистентность важнее буквальности.** Один и тот же английский термин переводи одинаково во всех файлах. Если в глоссарии уже есть пара — используй её, даже если «по вкусу» перевёл бы иначе.
3. **Логируй прогресс** в `second-brain/05_история/2026-06-02-admin-ru-localization-<phase>.md` — кратко: что переведено, спорные термины, ссылки на коммиты.
4. **Используй TodoWrite** для шагов внутри фазы. Чисти после закрытия фазы.

## Шаги внутри каждой фазы

### Шаг 1 — Понимание (5-10 мин)
- Прочитай раздел фазы в ТЗ (включая чек-лист §6 для своих файлов).
- Вызови `run_pipeline` (если доступен) с задачей фазы; иначе Glob/Grep.
- Спавн `Explore`: «выпиши ВСЕ видимые пользователю строки с латиницей в файлах <список фазы>, с `файл:строка` и контекстом (заголовок/кнопка/колонка/вкладка/placeholder)». Получи точную карту строк — она точнее, чем номера в ТЗ (строки могли сместиться).

### Шаг 2 — Развилки (если есть, 5-15 мин)
- Выпиши в TodoWrite спорные термины фазы.
- Каждый: канон из глоссария → закрыл; нет канона → `Plan` агент → выбор → строка в `05_история/`.

### Шаг 3 — Промпт для кодящего агента (5-10 мин)
Составь самодостаточный промпт. Структура:
```
Цель фазы: <из ТЗ>
Файлы к правке: <точные пути + строки из карты Explore>
Словарь переводов: <выписка нужных пар из delivery/13-glossary.md — дай агенту готовые пары, не отсылай "посмотри в глоссарии">
Что МОЖНО менять: только строковые литералы видимого текста (JSX-текст, label, title, placeholder, aria-label, заголовки колонок, метки вкладок, тексты тостов/кнопок/пустых состояний).
Что НЕЛЬЗЯ менять: имена переменных/функций/props/ключей объектов, URL, enum, data-testid, CSS-классы, значения с бэка.
Бренды/протоколы (не переводить, дать пояснение в скобках при первом упоминании на странице): <список из §4.2 ТЗ, релевантный файлам>
Acceptance: ноль латиницы в видимом тексте (кроме брендов), typecheck зелёный, lint зелёный.
Правила: no git add ., re-Read после каждого Edit, верни git status в отчёте.
```

### Шаг 4 — Выполнение и верификация
- Спавн кодера (`general-purpose`/`claude`).
- После возврата — ВЕРИФИЦИРУЙ сам:
  - `git status` — какие файлы реально изменились?
  - Re-Read ключевые файлы → правки на месте?
  - Grep старых англ. строк → исчезли? Grep новых русских → появились?
  - Grep латиницы в видимом тексте затронутых файлов → пусто (кроме allowlist)?
  - `cd frontend && bun run typecheck` → зелёный?
  - `cd frontend && bun run lint` → зелёный?

### Шаг 5 — Acceptance criteria (10-20 мин)
- Пройди чек-лист §6 и §8 ТЗ для своей фазы.
- Каждый пункт: проверь грепом/typecheck, либо запиши «не проверено: <причина>» в `05_история/`.
- Хоть один не закрыт → назад к Шагу 3 с уточнённым промптом.

### Шаг 6 — Отчёт владельцу (5 мин)
- Фаза N: закрыта / частично / заблокирована.
- Список изменённых файлов + что переведено (несколько примеров пар).
- Спорные термины и как решил.
- Что не закрыто и почему.
- Запрос: «закоммитить? / push? / идти к фазе N+1?».

### Шаг 7 — Коммит (только после подтверждения)
- `git status` → только нужные файлы?
- `git add <явные пути>`.
- Коммит: `feat(admin-i18n): Фаза N — <короткое описание>` (или `chore(i18n)` для Фазы 0 глоссария).
- Co-Authored-By trailer (см. CLAUDE.md).
- Обнови `second-brain/01_projects/admin.md` (раздел про русификацию UI).
- Рефлексия — отдельным коммитом `docs(second-brain): рефлексия — Фаза N русификация админок`.
- Prod-операций в этой задаче, скорее всего, НЕТ (только фронт-строки) — в отчёте явно укажи «prod-операций нет, достаточно пересборки фронта».

### Шаг 8 — Push (только после отдельного подтверждения)
- `git push origin <branch>`.
- Хук post-push может сделать auto-pull — учитывай при параллельных сессиях.

## Чего НЕ делать
- ❌ Не пропускать фазы и не прыгать вперёд.
- ❌ Не переводить имена переменных/маршрутов/enum/`data-testid`/значения с бэка.
- ❌ Не переводить бренды/протоколы (S3, LiveKit, IMAP, BullMQ, DeepSeek и т.п.) — только пояснять.
- ❌ Не выдумывать переводы мимо глоссария; не плодить второй источник правды.
- ❌ Не «улучшать» соседний код, стили, логику — строго scope строк.
- ❌ Не делать destructive git (reset --hard, push --force, branch -D) без явного подтверждения.
- ❌ Не отчитываться `[x]` без личной верификации грепом/re-Read.
- ❌ Не переоткрывать решённые в разделе 0 ТЗ развилки.

## Что делать при блокере
1. Не воюй с одной правкой > 1 часа.
2. Спавн `Plan` с описанием блокера и 2-3 идеями.
3. Plan не помог → отчёт владельцу + предложение (отложить файл / другой подход).

Типовые блокеры этой задачи:
- Строка приходит с бэка (enum/значение) и рендерится по-английски → НЕ переводи литерал; реши: добавить русскую подпись-маппинг рядом в UI или вынести в отдельную задачу на бэк. Согласуй.
- Перевод ломает верстку (узкая колонка) → сократи формулировку, не жертвуй смыслом; при сомнении — `Plan`.
