# Методология стендов качества (локальная фиксация фич)

Стенд — измерительный инструмент качества одной фичи/подсистемы, который можно гонять повторно и сравнивать прогоны между собой. Не разовый тест «глазами», а **петля**: прогон → диагноз → ТЗ → фикс → перепрогон, до заданной планки. Выведена из трёх стендов: probe-stand (уточняющие вопросы), recall-стенд «Мастера» (111 вопросов + петля to-99), клон-стенд (проект 2026-07-03).

## 1. Когда создавать стенд

Создавай стенд, когда выполняются все три условия:
1. Качество фичи **вероятностное** (LLM/retrieval/ranking) — юнит-тесты не отвечают на вопрос «насколько хорошо».
2. Планируются **итерации улучшений** — нужно доказуемое «было → стало», а не ощущения.
3. Есть или можно построить **ground truth** — эталон правильного поведения.

Не создавай стенд для детерминированной логики (это vitest) и для разовой проверки «работает ли вообще» (это smoke/combat-harness).

## 1.5 Слоистая модель: мерь ВХОД в базу отдельно от ВЫХОДА (Слой 0)

> Полный метод — [docs/methodology/synthetic-fidelity-eval-method.md](../methodology/synthetic-fidelity-eval-method.md). Здесь — обязательное правило для любого стенда.

Обычно меряют **выход** системы (ответ чата, поведение клона). Но если сама база построена неверно — факт не извлёкся, сущность слита, черта не выведена — выход провалится **не по своей вине**, и провал спишется «на выход». Это **мис-атрибуция**: чинишь синтез/политику ответа, а корень — в извлечении. Поэтому стенд разделяет слои и атрибутирует промах ПО СЛОЮ:

| Слой | Что | Эталон |
|---|---|---|
| **0. Запись/извлечение** | сырьё → база (блоки/сущности/связи; или профиль/черты/память клона) | **манифест из ИСТОЧНИКА** |
| 1. Достача | база → кандидаты | манифест |
| 2/3. Резолв/выход | кандидаты → ответ/поведение | эталон-выход (банк) |

Слой 0 — фундамент: если факт не записан, никакой тюн выхода его не вернёт. **Baseline выхода без замера Слоя 0 даёт ложные диагнозы** — до петли улучшений замерь Слой 0 и разложи провалы по слою.

**Метод Слоя 0 — непересекающиеся разметчики → сверка → сверялка** (изоляция обязательна: агенты не видят ни базы, ни друг друга, иначе меряешь согласие модели с собой):
1. **Разметка (2+ слепых агента):** каждый читает ТОЛЬКО сырьё + список якорей (несущих фактов), пишет ожидаемую запись (тип, суть, сущности, связи). Не видит базу и другого разметчика.
2. **Сверка (ревизор):** сводит в единый манифест + фиксирует agreement (`full`/`partial`/`conflict`). **`conflict` — не шум, а сигнал:** место, где текст неоднозначен и где будет плавать извлечение → нормировать явным правилом.
3. **Сверялка (матчер, read-only):** матчит якорь манифеста с базой: `found`/`wrong_type`/`partial`/`missing`. **По смыслу, не по строке** (нормализация + overlap/cosine + судья 2-из-3).

**Три правила против «зелёного вхолостую»** (оплачены ошибками — соблюдать жёстко):
1. **Эталон ≠ вход.** Нельзя брать «правильное значение» из поля, которое система просто копирует со входа — метрика станет тавтологией. Для клона критично: если «правильная черта» скопирована из сырья без вывода — метрика липовая; проверяй, что система **вывела** черту из свидетельств, а не переложила поле.
2. **Не сверять выход LLM с эталоном, сгенерённым LLM из той же прозы** — парафраз-цикл (cosine ложно завышен). Источник и разметку пишет человек/слепой агент, не тот же проход, что извлекает.
3. **Нечёткое сравнение, пороги — baseline, не абсолют.** LLM переформулирует → строгий substring клеймит валидное «выдумкой». Матчить по смыслу; первый прогон = зафиксировать фактические пороги как non-regression, ужесточать итеративно.

## 2. Анатомия стенда — 7 обязательных частей

### 2.1 Данные: синтетический тенант с ground truth по построению

- Гоняем ТОЛЬКО на локальной «Стреле» (или свежем синтетическом тенанте). Прод — никогда (read-only диагностика — отдельный канал).
- Данные сеются **через реальный конвейер** (RawEvent → block-ingest → специалисты), не прямыми INSERT — иначе меряем не продукт.
- **Главный приём: ground truth по построению.** Мы сами сеем контент → знаем эталонный ответ каждого вопроса. Посеянное фиксируется в манифесте (`*-feed-manifest.json`) — судьи сверяются с ним, а не с «мнением» LLM. Урок PersonaEval: LLM-судья без эталона ненадёжен. **НО манифест выводится из ИСТОЧНИКА слепой разметкой (§1.5), а не из вывода системы** — иначе «ground truth по построению» вырождается в парафраз-цикл (правило №2).
- Известные состояния тенанта документируются (что слито/сломано намеренно).
- **Пере-сев — не всегда обязателен (граница по слою).** Фиделити ИЗВЛЕЧЕНИЯ (сырьё → блоки/сущности) проверяется на СУЩЕСТВУЮЩЕЙ базе без пере-сева: размечаешь прозу текущего сида и сверяешь с тем, что уже в базе (доказано recall-прогоном 10/10). Пере-сев нужен только когда: (а) база под нужный слой пуста (напр. клон-черты/персоны ещё не построены — нечего сверять, сначала кормить); (б) тенант намеренно испорчен под тест ответов (слитые сущности). Не пере-сеивай ради фиделити извлечения — это лишняя работа.

### 2.2 Банк вопросов/кейсов — фиксированный, с предсказаниями

- 100–120 объектов, разбитых по **категориям-углам** (каждая категория целит в свой слой/трещину). Плюс счётчик `targeted` — вопросы, целящие в известные трещины из аудита.
- У каждого объекта: `id`, категория, вопрос, `groundTruth` (эталонный ход/факты), `forbidden` (что означает провал), **`prediction` — ожидание ДО прогона**. Сравнение факт-vs-прогноз валидирует сам стенд: массовое расхождение = стенд меряет не то.
- **Контрольные пары** (canonical ↔ synonym): та же суть разными словами — мера слепоты к формулировкам.
- **Цепочки** (3-4 хода с анафорой «она/это») — перенос контекста диалога.
- **Ловушки-приманки**: вопросы, провоцирующие типовую выдумку (статус «готово/доволен», несуществующий регламент, конкретная цифра) — ловят fabrication, главный анти-паттерн.
- Банк **не меняется** между прогонами петли (сравнимость). Правки эталонов — только через ручной разбор с фиксацией причины.
- **Свежий банк** ~20 новых вопросов на каждую приёмку — защита от оверфита под основной банк (цель на свежих ниже на ~5 п.п.).

### 2.3 Раннер

- Отдельный скрипт `backend/scripts/<stand>/stand.ts` с режимами: `prepare` (данные) | `build`/`trigger` (форс конвейера) | `status` (готовность) | `run` (прогон банка) | `judge` (судьи) | `report` (+ `report:nollm`) | `all`. Лёгкие режимы — без LLM и без записи.
- Бьёт в **сервисы напрямую** через полный AppModule (как batch-recall-trace) — снимает трассу (llmMeta, гейты, вошедшие слои, латентность). HTTP/UI/боты покрываются 2-3 smoke-кейсами отдельно, не всем банком.
- `assertNotProd` обязателен; ORG через ENV; результаты — в JSON per-run + человекочитаемый MD-отчёт; предыдущие прогоны сохраняются для «было→стало».

### 2.4 Два слоя проверки: детерминированные ассерты ≠ LLM-судья

- **«Сработало ли правильно»** — детерминированно, без LLM: коды отказов, наличие цитат, регэкспы (дисклеймер, первое лицо), латентность, срабатывание ожидаемого слоя по трассе. **Матч по точной строке допустим ТОЛЬКО для код-констант продукта** (фикс-тексты отказов клона — константы класса); для LLM-генерируемого текста опираться на машинные признаки API (needsClarification/refusalReason/answerKind), не на текст — урок recall (Дефект B, q074): модель отказала своими словами, точная строка не сматчилась → ложный false_empty.
- **«Хорошо ли по смыслу»** — LLM-судьи. Никогда не смешивать слои: механическая эвристика врёт на сложных ответах (урок recall: флаг honest ложно срабатывал на list-ответах), а LLM-судья дорог и шумен для того, что можно проверить строкой. Детерминированный ассерт по citations/usedBlockIds валиден, только если валидация покрывает ВЕСЬ контекст, показанный модели (граф-соседи/contradiction-блоки могут быть шире contextBlocks — провенанс-аномалия q088).

### 2.5 LLM-судьи: панель, а не одиночка

- **Панель majority-of-3** с РАЗНЫМИ линзами (например: полезность/экспертность · верность эталону · честность/fabricated), вердикт по большинству. Один судья шумит и систематически строг/мягок.
- **Линзе честности давать retrieved-контекст**, а не только groundTruth: судья, видящий эталон, но не контекст модели, клеймит деталь-из-контекста как выдумку (главный источник пере-строгости в recall).
- Судья = фиксированная рубрика + JSON-схема через tool-call (`directLlmCall` из `scripts/_lib/llm-direct`, без AppModule). Модель фиксируется (deepseek-v4-pro). Судит LLM, не человек — воспроизводимость между прогонами.
- Судья видит `groundTruth`/`forbidden` из банка — оценивает против эталона, не «из головы».
- Готовые образцы рубрик: `probe-stand/judge.ts` (польза/шум), `persona-behavior-judge.prompt.ts` (шкала 1.0/0.5/0.3/0.0 с ценой отказа), `RAG_GROUNDEDNESS_LENIENT` (критерии fabricated: статус/провенанс/конкретика без опоры — выдумка; неполнота/осторожность — нет).
- Каждый вердикт «выдумка» **разбирается вручную** против реальных данных: опыт recall — до половины «галлюцинаций» строгого судьи оказываются пере-строгостью.
- Судейскую панель **коммитить в репо** (не одноразовый Workflow-скрипт) — иначе следующая приёмка строит судей заново и числа несравнимы (грабля recall).

### 2.6 Линейка оценки: оси → вердикт → инварианты → планка

1. **Оси** (3-5 штук, 0..1) — что именно меряем (у клонов: экспертность, верность методу, заземлённость, опора на слои, персона).
2. **Вердикт на объект** — композит осей в одну категорию (EXPERT_PASS / WEAK / REFUSED / FABRICATED / BOUNDARY_OK…). Главная метрика прогона — распределение вердиктов.
3. **Железные инварианты** — то, что не входит в проценты, а проваливает приёмку целиком (0 выдумок; 100% запретной зоны; 0 утечек тенанта). Инвариант ≠ ось с весом: его нельзя «компенсировать» другими осями.
4. **Планка** — целевой % главного вердикта на банке И на свежем банке (например ≥95% / ≥90%), + пороги осей. Планка задаётся владельцем до первой итерации.

### 2.7 Петля итераций (протокол «до идеала»)

```
0. baseline (прогон «как есть» ДО фиксов — точка отсчёта и доказательство)
1. ДИАГНОЗ: каждому провалу — диагноз-КЛАСС (по трассе: какой гейт/слой/этап виноват)
   И атрибуция ПО СЛОЮ (§1.5): промах в извлечении (Слой 0, черта/факт не построены) или
   в выходе (Слой 2/3, политика/синтез)? Без Слоя 0 «отказ» ошибочно спишется на политику.
   Каждый провал сверяется с СЫРЫМ ответом/трассой, не с флагом линейки: линейка сама
   может врать (recall: 7 из 12 «пустых» по флагу — ложные срабатывания линейки).
   Дефект линейки — отдельный диагноз-класс ruler-defect и чинится ПЕРВЫМ.
2. ГРУППИРОВКА: классы → 1-3 ТЗ. Чинить КЛАСС, не кейс (фикс «под вопрос» = оверфит)
3. ФИКС: реализация ТЗ + unit-тесты на класс
4. ПЕРЕПРОГОН: те же кэш-чистки, тот же банк + свежие ~20-25; отчёт «было→стало»
5. Три исхода: планка взята → финальный отчёт; остаток провалов ДОКАЗУЕМО вне рычагов
   scope → СТОП: честный разбор потолка, follow-ups в реестр не-сделанного, решение
   владельца о новой планке/системах; иначе → шаг 1
```

Правила честности замера (нарушение любого = замер недействителен):
- **Шум LLM ±3-5 п.п.** на ~110 объектах — дельта такого размера НЕ вывод. Доказательство улучшения = целевые кейсы починились ПОИМЁННО и агрегат не упал.
- **Гипотезы проверять на масштабе, не на 3 примерах**: закономерность, видная на 6 записях, на 111 оказывается частным случаем (урок recall про инверсию канон/синоним).
- Перед каждым прогоном чистить кэши и дедупы (answer-кэш Redis, jobId-дедупы BullMQ) — иначе меряется прошлый прогон.
- Эталоны и банк не подгоняются под ответы; предсказания не переписываются задним числом.
- Kill-switch-конфигурация прогона фиксируется в отчёте (какие флаги/крутилки стояли).
- **Честный разбор потолка** в after-report: какие провалы лечатся рычагами текущего ТЗ, а какие — отдельные системы (урок recall: 79%→95% оказался не «дожать синтез», а несколько отдельных систем; это фиксируется, а не маскируется).

## 3. Операционные грабли (проверено)

| Грабля | Что делать |
|---|---|
| jobId-дедуп BullMQ (rebuild раз в 24ч) | чистить `bull:*` ключи тенанта в prepare/build |
| Answer-кэш отдаёт старые ответы | чистить `dlg:ans:<tenant>:*` перед run |
| Дневные квоты (ai_chat 50/день, dump) | ENV поднять локально ИЛИ run через сервис мимо контроллера (429-ветка — отдельный smoke) |
| Недетерминизм: выборки без orderBy, shadow-сэмплинг от conversationId, fail-open гейты при сбое эмбеддера | фиксировать conversationId; кратные прогоны; логировать срабатывание fail-open |
| Синтетика не кластеризуется (черты не рождаются) | ≥3 близких развёрнутых формулировки на навык, эпизоды разнесены по датам (confidence-ladder) |
| Cron-окна (персона — вс 06:00) | форсить кроны в build (`diag-clone run-cron` / прямые вызовы) |
| «Конвейер не устоялся» | ждать RawEvent.received=0 перед run |
| Хардкод-путей/ORG в раннере | всё через ENV с дефолтами (batch-recall-trace этому НЕ соответствует — см. долг в §5) |
| Латентность харнесса ≠ латентность пользователя | двойной understand в трассе завышает время (~78с/вопрос у recall) — не выдавать за прод-латентность |
| Промпт под снапшот-тестом | правка промпта в итерации = осознанное обновление снапшота |
