# Экономный режим лимита расходов на ИИ + хвосты предыдущей сессии

## Что было поставлено

Продолжение сессии (новый чат с самостоятельным брифом-передачей контекста от прошлой). Четыре независимых потока:
1. Пуш 16 незапушенных коммитов прошлой сессии (llm-cost-dashboard) — блокер, требовал подтверждения владельца.
2. QA-приёмка нового дашборда расхода `/admin/analytics/llm-cost` браузером.
3. Разбор 13 упавших тестов из полного прогона backend (пре-существующие или сломаны сессией?).
4. Полная цепочка `solution-blueprint → tz-author → tz-orchestrator` для третьего режима лимита ИИ («экономный», downgrade) — пункт, уже одобренный владельцем в чате прошлой сессии, без дополнительных вопросов.

## Как решал

**Параллельный старт.** Push подтверждён владельцем через `AskUserQuestion` (рекомендовал «запушить как есть, мерж — после QA» — принято). Одновременно с вопросом запущены в фоне: QA-агент (Skill `qa-tester`) и `Workflow` из 26 суб-агентов (pipeline: прогон каждого упавшего теста → для реальных (не инфра) провалов — root-cause через изолированный `git worktree` на коммите до сессии).

**Диагностика тестов — все 13 pre-existing.** Ни один из 16 упавших тестов не связан с сессиями 07-03/07-04 (llm-cost-dashboard, LLM routing vNext). Находки: `SsrfGuardService` не блокирует IPv6 `[::1]` до DNS-резолва (security-relevant, баг с 05-10/06-17); 4 ENV-ключа не занесены в classifier-списки; `ProbeService.policy_silent` регрессировал между 06-29 и 07-03 (не расследовано до конкретного коммита); `chatbox-analyze.worker` — устаревший assert; 6 e2e-сьютов молча не проверяют логику из-за хардкод-`DATABASE_URL` в `test/setup-test-env.ts`, не совпадающего с реальным dev-портом 55435 (долгоживущая поломка харнесса, минимум с мая); `clones-v2`/`analyze-worker-with-resolver` — расхождения бизнес-логики/мока, не связаны с сессией. Все 9 находок оформлены строками в `second-brain/04_не-сделано/README.md`.

**QA — заблокирована повторно, но по-другому.** В прошлой сессии — не получилось создать суперадмина + завис Playwright-браузер. В этой — браузер установился штатно, но `.qa-cabinet.local.json` физически отсутствует в окружении; агент честно не стал обходить (прямой запрет в промпте), сделал что мог статически (подтвердил редиректы/404/self-service-untouched по коду и git diff, не вживую).

**Архитектура + ТЗ + реализация («экономный» режим).** Одобренная архитектура написана с нуля через `solution-blueprint` (владелец одобрил с первого раза, обе развилки были закрыты заранее). Ключевая техническая находка при картографии кода: `LlmTaskRoute` уже хранит для каждой AI-задачи упорядоченную цепочку моделей (primary→secondary→tertiary), которая сегодня используется ТОЛЬКО при ошибках провайдера — решение (proof-loop A/B в ТЗ) переиспользовать эту же цепочку для бюджетного даунгрейда: при превышении лимита с `capKind='downgrade'` роутер просто пересортировывает уже готовый список по цене (`MODEL_PRICES`), вместо изобретения отдельного «списка дешёвых моделей». REALITY-CHECK вскрыл дополнительную дыру, не описанную в архитектуре человеческим языком: `BudgetAlertCron` сканировал только Org с явной строкой `OrgBudgetCap` — платформенный дефолт-лимит (новая фича) для Org без строки никогда не долетел бы уведомлением. Закрыто отдельной фазой (Org.findMany вместо OrgBudgetCap.findMany, auto-vivify пустой строки для дедупа).

Реализация — 4 фазы через суб-агентов, Фаза 1 (данные/контракт) блокирующая, 2/3/4 — параллельно тремя агентами в одном сообщении. Между фазами — независимая проверка (не на слово агента): git diff построчно, свежий typecheck/lint/build, module-wide `vitest run` (64 файла/797 тестов после всех фаз, без регрессий). `strict-production-review-gate` нашёл 1 minor (асимметрия observability — downgrade-ветка не логировала активацию в отличие от observe-ветки) — исправлено в этой же сессии отдельным коммитом, не отложено.

## Что вышло

Push сделан (`db3d80c8..07d487fc`). Архитектура одобрена, ТЗ `ready-to-implement` → реализовано целиком, 5 коммитов (`b3257d3a`/`0ce443c5`/`f8eb61db`/`67c292f8`/`ca36e54c`). `capKind` расширен до `soft`/`hard`/`downgrade` БЕЗ Prisma-миграции (поле уже было `String`). Мерж в `dev` — сознательно НЕ сделан, ждём реальную browser-QA (решение владельца: не срезать угол несмотря на то, что тесты чисты и статическая проверка кода пройдена).

## Чему научился

- **REALITY-CHECK на этапе ТЗ должен смотреть не только на «как это сделать», но и на «что молча сломается у соседнего механизма»** — платформенный дефолт-лимит технически работал бы (роутер бы его подхватил), но без правки `BudgetAlertCron` уведомление — единственное, что видит владелец, — никогда бы не пришло для большинства компаний. Нашлось только потому, что явно проверил «а что если у Org нет строки вообще», а не только happy-path с уже настроенным лимитом.
- **Переиспользование существующего tier-fallback-списка для ДРУГОЙ причины (бюджет, не ошибка) — сильнее, чем городить параллельный список «дешёвых моделей»** — но требует явного маркера (`fallbackReason='budget_downgrade'`), т.к. позиционная tier-метка (`primary`/`secondary`/`tertiary`) может стать неточной для legacy (не-tier-нормализованных) маршрутов после пересортировки. Явный маркер дешевле, чем гнаться за 100%-точностью `tier` для редкого edge-case.
- **Ревью после коммита — тоже работает, но правильный порядок (ревью → коммит) дешевле** — в этой сессии коммитил каждую фазу сразу после локальной приёмки, `strict-production-review-gate` прогнал уже поверх 4 готовых коммитов и нашёл 1 находку — пришлось коммитить фикс отдельно вместо того, чтобы включить в исходный коммит фазы. Не критично (git-история чуть менее гладкая), но на следующий раз — ревью каждой фазы ДО коммита, не пачкой в конце.
