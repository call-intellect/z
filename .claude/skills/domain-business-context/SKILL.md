# Z: бизнес-контекст

## Что такое Z

Z — самостоятельный сервис AI-видеовстреч на LiveKit. Цель — пользователь не просто провёл встречу, а сразу получил **результат под тип встречи**: задачи, решения, follow-up, CRM-заметка, риски, следующий шаг.

Z деплоится отдельно (свои сервера, своя БД, свой код). Crossmark интегрируется через API, но архитектурной связи нет.

## Главная продуктовая ценность

**AI-отчёт зависит от типа встречи.** Не универсальное саммари — конкретный шаблон под продажу, стендап, custdev, собеседование и т.д. Это главное отличие от «обычной» транскрибации.

## Ключевое разделение №1: LiveKit vs Backend

| Слой | Что делает | Чего НЕ делает |
|------|-----------|----------------|
| LiveKit Server | media routing (audio/video/screen share) | бизнес-логику, авторизацию, биллинг |
| LiveKit Egress | пишет общую запись + аудиодорожки → S3 | ничего больше |
| Наш Backend (NestJS) | встречи, токены, права, FSM, webhooks, AI-оркестрация | media |

**Все LiveKit-токены генерирует только backend.** Гость не получает API key/secret LiveKit. Любой код на фронте/у гостя, который выглядит как «обращаюсь к LiveKit напрямую с секретом» — ошибка.

## Ключевое разделение №2: Host vs Guest

### Host (авторизованный пользователь, создатель встречи)
- начать/остановить запись
- mute участнику, удалить участника
- завершить встречу
- видеть AI-отчёт и запись после встречи
- поднять/опустить свою руку

### Guest (по ссылке, без регистрации)
- ввёл имя — зашёл, без регистрации
- камера, микрофон, screen share, чат
- поднять/опустить свою руку
- выйти

**НЕТ:** управлять записью, управлять другими, видеть AI-отчёт.

Guest token имеет ограниченный capability set в LiveKit — без admin-permissions комнаты.

### Где сохранять разделение

| Слой | Правило |
|------|---------|
| API | `/meetings` (host scope, JWT) vs `/g/:guest_token` (guest scope) |
| Guards | `JwtAuthGuard` vs `GuestTokenGuard` |
| LiveKit token | разные `permissions` для host и guest |
| UI | разные страницы (`/meetings/:id` vs `/g/:guest_token`), разные компоненты |
| Action buttons | проверка роли перед рендером (запись, исключить, mute другого) |

## 9 типов встреч (MVP)

Тип выбирается при создании. Определяет, какой AI-шаблон применится после встречи.

| Код | Название |
|---|---|
| `team` | Командная встреча |
| `standup` | Планёрка |
| `plan_fact` | План / факт по задачам |
| `project` | Проектная встреча |
| `sales` | Продажная встреча |
| `custdev` | CustDev / интервью |
| `partner` | Партнёрская встреча |
| `interview` | Собеседование |
| `customer_success` | Customer Success |

**Правило:** всё, что зависит от типа (промпт, поля отчёта, UI карточки результата) — параметризуется через `meeting.type`. Никаких `if (type === 'sales') { ... } else if ...` в 200 строк — таблица типов в конфиге/БД.

Полные шаблоны полей по типу — в [[../01_projects/ai-analysis-by-type|second-brain/01_projects/ai-analysis-by-type.md]].

## Запись и AI: как они связаны

1. Egress пишет:
   - **общую запись** (видео + общий звук + screen share) — для пользователя
   - **отдельные аудиодорожки** на каждого участника — для AI

2. **Не полагаться только на общий микс.** AI-анализ требует разделения по спикерам — общий микс ломает качество диаризации.

3. После встречи:
   - забираем аудиодорожки из S3
   - транскрибация (наш ASR — Vox/GigaAM по умолчанию)
   - склейка по времени + разделение по спикерам
   - LLM (Claude Sonnet через Anthropic; fallback `proxy.agent-lia.ru`) применяет шаблон по `meeting.type`
   - отчёт сохраняется в `ai_results`

## Retention записи (TTL по тарифу)

Записи и аудиодорожки имеют TTL, зависящий от тарифа пользователя. Конкретика — в [[../01_projects/recording|second-brain/01_projects/recording.md]] и `plans/analysis/2026-05-06-recording-retention.md`.

**Правило:** TTL не хардкодим — берём из конфига тарифа. Удаление прошедших TTL — отдельная фоновая задача, не side effect HTTP-хендлера.

## Границы MVP (что НЕ делаем сейчас)

- Не больше 10 участников
- Нет вебинаров на 100+, нет breakout rooms
- Нет co-host (несколько ведущих), зрителей-без-аудио, зала ожидания
- Нет сложной матрицы прав

Если фича пытается выйти за эти границы — флаг, поднять с пользователем.

## Продуктовые приоритеты

При принятии любого решения — дизайнерского, технического, UX — проверяй по этому порядку:

1. **Скорость до встречи.** Создание встречи — 1 экран, 2 клика. Гость — без регистрации.
2. **Понятная ценность после встречи.** Карточка результата открывается сразу, без «AI ещё думает 20 минут без объяснения».
3. **Качество AI-отчёта зависит от качества аудиодорожек.** Не экономить на дорожках per-участник.
4. **Прод-стабильность важнее фич.** Разделение нод (SFU / Egress / TURN / Backend / DB) — критично; ломать ради простоты деплоя нельзя.

## Терминология (не менять без причины)

| Термин | Смысл |
|--------|-------|
| Meeting | Встреча (entity) |
| Meeting type | Один из 9 типов; определяет AI-шаблон |
| Host | Создатель встречи, авторизован |
| Guest | Участник по ссылке без регистрации |
| Guest link / `/g/:token` | Гостевой URL входа |
| Recording | Общая запись (видео + микс) |
| Audio track | Отдельная аудиодорожка на участника |
| AI Result | Результат AI-обработки по шаблону типа |
| Egress | Сервис LiveKit, пишущий в S3 |
| TURN | Сервис NAT traversal |
| Raise hand | «Поднять руку» — состояние в `participant.attributes` LiveKit |

## Как применять

- Перед добавлением нового поля или эндпоинта — проверь: это host-scope или guest-scope? Затрагивает ли тип встречи?
- Перед изменением FSM встречи — проверь, не ломаешь ли retention/AI-pipeline.
- Перед изменением промпта/шаблона — это admin-editable, защити от overwrite (см. `safe-seed-rules`).
- Перед добавлением UI-элемента в комнату — проверь, видит ли его guest и должен ли видеть.
- Если фраза «давай тут просто на фронте сгенерим LiveKit-токен» — стоп, это нарушение принципа.
