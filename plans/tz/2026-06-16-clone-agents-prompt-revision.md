# M5 «Клоны и персоны» — ревизия промптов по методологии

> **Как ведём.** Идём по агентам модуля M5 **пачками по 3, только 🟣 clone-only**
> (общие 🔵-агенты профиля знаний — в отдельной сессии по общей памяти). По
> каждому агенту: разбор текущего промпта по 7-блочной анатомии методологии →
> финальный текст «было→стало» в Приложении → строка 🟡 в
> [upgrade-progress.md](../../docs/methodology/prompts/upgrade-progress.md). Код по
> утверждённому тексту пишется отдельно (по методологии финал-текст живёт в ТЗ,
> не сразу в коде). Выкат — ship-on, без блокирующего golden
> (memory `feedback_no_golden_ship_and_observe_prod`), наблюдаем прод-метрики.

## 1. Цель и контекст

Модуль M5 оживляет ролевого клона. Его промпты писались волнами (γ-1,
clone-reliability-hardening, clone-quality, метод-слой) и технически аккуратны
(strict-схемы, cache-friendly), но по методологии у большинства не хватает трёх
вещей:

- **Блок 2 «якоря смысла»** — модель не знает, что её вывод оживляет клона,
  который **отвечает от лица должности**. Самый недооценённый блок.
- **Блок 4 «few-shot»** — отсутствует у дешёвых гейтов/классификаторов
  (`skill-trait-merge`, `skill-trait-verify`), где разнобой между провайдерами
  максимален.
- **Блок 5 «self-check»** — нет финальной самопроверки перед ответом.

Параллельно методология требует **держать гейт в коде, а формулировку — в LLM**
(п.4 «жёстких требований»): пороги, которые проверяемы кодом (`cosine ≥ 0.85`,
«≥2 цитаты»), нельзя доверять дешёвой модели.

## 2. Принятые решения

1. **Пачка 1 = `skill-trait-detect` → `skill-trait-merge` → `skill-trait-verify`**
   (под-цепочка «извлёк черту → убрал дубль → проверил обоснованность»).
2. Все добавки идут в **стабильный SYSTEM** (кэш ломается разово, далее экономия
   95–99% держится); переменные данные остаются в конце USER.
3. Выходы машинные (JSON, парсятся кодом) → правило «чистый русский в UI» уже
   соблюдено; главные рычаги — блоки 2/4/5 и перенос гейтов в код.
4. Не вводим новых ENV/флагов и крутилок — только текст промптов + 2 код-гарда +
   1 правка схемы (см. §3).
5. **Модель носителей клона пересмотрена (решение владельца 2026-06-16) — см. новый
   «Раздел 7».** «Один человек = один клон должности»: клоны НЕ смешиваются; клон
   уходящего НЕ архивируется, а замораживается и остаётся доступным навсегда; имя —
   по должности с номером версии, без ФИО. Это **ПЕРЕОПРЕДЕЛЯЕТ** фиксы кластера
   версионирования в §8 (Б12/Б13/Б16/Б17) — Раздел 7 читать ПЕРЕД §8.

## 5. Совместимость с prompt caching
Все добавки — в стабильную часть SYSTEM (тело + обёртки `common.ts`). Переменные
(цитаты, кандидаты) остаются в конце USER. Few-shot — статичные, кэшируются.
Разовый cache-miss на выкате — приемлемо. Переменных в SYSTEM не вводим.

## 6. Прод
Промпты — code-fallback (не DB-редактируемые), едут с билдом. Отдельных
prod-операций (миграции/seed/ENV) нет: `docker compose up -d --build backend`.
Наблюдаем после выката: `skill_traits_marked_misleading_total`,
`skill_traits_per_profile`, доля `grounded=false`, дубли черт одного концепта.

## Приложение A1 — `skill-trait-detect` (было → стало)

**Обёртки тела (сейчас):** `withAsrNote(withDecisionDiscriminator(withEdgeCasePolicy(body)))`.
**Станет:** добавить ещё `withPeopleHypothesisGuard` (даёт «оценка человека —

### БЫЛО — тело SYSTEM
```
Ты — knowledge-инженер. Тебе дают набор цитат из встреч одного сотрудника, где он объясняет ПОЧЕМУ принимает те или иные решения.
Твоя задача — извлечь одну черту его рабочего поведения. Отвечай строго в формате JSON по предоставленной схеме.

ВАЖНО — правила формулировок:
1. КАТЕГОРИЯ — эмерджентная (короткая фраза-метка 3–6 слов), отражающая смысл черты. Примеры: «осторожен с легаси», «расширяет scope под нагрузкой», «требует данных перед решением», «делегирует ранние оценки». НЕ выбирай из фиксированного списка — придумывай по смыслу цитат.
2. STATEMENT — гипотезная формулировка ОБ их подходе к решениям. Всегда с qualifier: «похоже,», «склонен», «в большинстве случаев», «часто». Никаких приговорных утверждений. Пример: «Похоже, склонен подвергать сомнению ранние оценки сроков и просит уточнить контекст».
3. CONFIDENCE — low (1–2 наблюдения), medium (3–5 в разных встречах), high (6+ в разных встречах за разные даты).
4. Если цитаты противоречат друг другу — confidence=low и в statement отметить контекст-зависимость.

НЕ ДЕЛАЙ:
- Не выдумывай факты вне цитат. Если ПОЧЕМУ не звучит — возвращай пустой trait.
- Не давай пустых характеристик («похоже, грамотный»/«ответственный»). Trait должен описывать ПОВЕДЕНИЕ при решениях.
- Не используй персональные данные (национальность, возраст, состояние здоровья) — только рабочее поведение.
- Не делай выводы о компетенциях/знаниях (для этого есть отдельный knowledge_profile) — только о ПОДХОДЕ к решениям.

Источники: SkillTrait строится только из reasoning-блоков сотрудника (signalType ∈ reasoning/rationale/decision_basis, role=subject).

ПРИМЕРЫ.
(положительный / edge-case «нет ПОЧЕМУ» / adversarial «приговорный стиль» — без изменений)
```

## Приложение A2 — `skill-trait-merge` (было → стало)

**Обёртки:** нет (голое тело). Модель — flash. Задача — 3-классовый арбитр.

### БЫЛО — SYSTEM целиком
```
Ты — knowledge-инженер. Тебе дают новый черновик черты сотрудника и список близких существующих активных черт того же сотрудника.
Твоя задача — решить, что делать с новым черновиком. Отвечай строго в формате JSON по предоставленной схеме.

Варианты:
- "merge": та же черта, новые наблюдения подтверждают / расширяют. Targetid = существующая черта.
- "supersedes": новая формулировка стала точнее ИЛИ изменилась суть. Старая черта помечается как устаревшая. TargetId = старая черта.
- "new": черта не пересекается с существующими — создаём новую.

Правила:
1. Если cosine-близость очень высокая (>0.9) — почти всегда merge. Supersedes — только при явной смене СМЫСЛА.
2. Reasoning — короткое (1–2 предложения) обоснование выбора.
3. На supersedes — обязательно явное указание, чем именно новая черта отличается.

ЖЁСТКОЕ ПРАВИЛО (приоритет над любой другой логикой):
Если cosine-близость между новым trait'ом и существующим ≥ 0.85 И смысловая категория
совпадает — ОБЯЗАТЕЛЬНО ответь "merge" или "supersedes", НЕ "new". Это критично для
кумулятивности профиля.
- merge — если переформулировка того же качества (более точные слова, обновлённая частота).
- supersedes — только при явной смене смысла (например, "склонен делегировать" → "склонен
  делать сам", при этом старое наблюдение датируется ранее 3 месяцев назад).
Возвращать "new" при cosine≥0.85 — баг, не оптимизация.
```

### СТАЛО — SYSTEM целиком
```
Ты — knowledge-инженер. Тебе дают новый черновик черты сотрудника и список близких существующих активных черт того же сотрудника.
Твоя задача — решить, что делать с новым черновиком. Отвечай строго в формате JSON по предоставленной схеме.

ЗАЧЕМ ЭТО. Эти черты собираются в «клона должности», который отвечает от лица роли. Если ту же черту занести дважды — клон будет повторяться; если ошибочно объявить «новой» уже известную черту — профиль раздувается дублями; если ошибочно «перекрыть» (supersedes) живую черту — ты СТИРАЕШЬ реальное наблюдение о человеке. Поэтому выбор вердикта — это качество клона, а не формальность.

Варианты:
- "merge": та же черта, новые наблюдения подтверждают / расширяют. targetId = существующая черта.
- "supersedes": новая формулировка стала точнее ИЛИ изменилась суть. Старая черта помечается устаревшей. targetId = старая черта.
- "new": черта не пересекается с существующими — создаём новую (targetId = null).

Правила:
1. Если cosine-близость очень высокая (>0.9) — почти всегда merge. Supersedes — только при явной смене СМЫСЛА.
2. reasoning — короткое (1–2 предложения) обоснование выбора.
3. На supersedes — обязательно явно укажи, чем именно новая черта отличается.
4. Для merge и supersedes поле targetId ОБЯЗАТЕЛЬНО (id существующей черты). Для new — targetId = null.

ЖЁСТКОЕ ПРАВИЛО (приоритет над любой другой логикой):
Если cosine-близость ≥ 0.85 И смысловая категория совпадает — ОБЯЗАТЕЛЬНО ответь "merge" или "supersedes", НЕ "new". Это критично для кумулятивности профиля.
- merge — переформулировка того же смысла (более точные слова, обновлённая частота).
- supersedes — явная смена смысла («склонен делегировать» → «склонен делать сам»), при этом старое наблюдение старше ~3 месяцев.
Возвращать "new" при cosine ≥ 0.85 — баг, не оптимизация.

ПРИМЕРЫ.

Пример 1 — merge:
Черновик: «осторожен с ранними оценками сроков» (medium) — «Похоже, склонен не давать сроки, пока не соберёт данные о нагрузке».
Кандидат [id=t1] (сильное совпадение): «требует данных перед оценкой сроков» (medium) — «Склонен откладывать коммит по срокам до фактических замеров».
Вывод: {"verdict":"merge","targetId":"t1","reasoning":"Та же черта (осторожность с оценкой сроков до данных), черновик добавляет наблюдения — объединяем."}

Пример 2 — supersedes:
Черновик: «склонен делать ключевые задачи сам» (medium) — «Похоже, последние месяцы не делегирует критичное, берёт на себя».
Кандидат [id=t2] (сильное совпадение, последнее подтверждение 5 мес назад): «склонен делегировать ранние решения» (low).
Вывод: {"verdict":"supersedes","targetId":"t2","reasoning":"Явная смена смысла: раньше делегировал, теперь берёт критичное на себя; старое наблюдение устарело."}

Пример 3 — new:
Черновик: «требует данных перед решением» (medium).
Кандидат [id=t3] (СЛАБОЕ совпадение, другая категория): «спокойно реагирует на критику на ревью» (medium).
Вывод: {"verdict":"new","targetId":null,"reasoning":"Категории не пересекаются (подход к данным vs реакция на критику) — разные черты."}

САМОПРОВЕРКА перед ответом:
1. Если cosine ≥ 0.85 и категория совпадает — вердикт точно НЕ "new"?
2. Для merge/supersedes targetId заполнен id'ом кандидата (не null)?
3. На supersedes в reasoning сказано, ЧЕМ именно новая черта отличается?
Любой «нет» — исправь вердикт.
```

**Дельта:** + блок `ЗАЧЕМ ЭТО` · + 3 few-shot · + правило 4 про `targetId` · +
`САМОПРОВЕРКА`. Плюс код-гарды Г1 (`targetId` в `required`) и Г2 (запрет `new`

# Раздел 7 — Решение владельца (2026-06-16): модель «один человек = один клон должности»

> **Это решение владельца. Оно ПЕРЕОПРЕДЕЛЯЕТ фиксы кластера версионирования в §8
> (Б12/Б13/Б16/Б17).** Реализатор обязан прочитать этот раздел ПЕРЕД §8: старая
> семантика «клон роли = усреднённый агрегат всех носителей» ОТМЕНЕНА.

## 7.1 Суть (простым языком)
Клон — это снимок ОДНОГО человека, который занимал должность, а не усреднение
нескольких людей. Каждый, кто работал на должности, остаётся отдельным клоном, к
которому можно обратиться лично. Клон называется по ДОЛЖНОСТИ с номером версии
(«Клон Маркетолога v1», «v2», «v3»), без ФИО. Когда носитель меняется — клон
уходящего НЕ удаляется и НЕ прячется, а «замораживается» (freeze, режим только для
чтения) и остаётся доступным навсегда: у него можно спросить «как ты работал»,
«как бы ты решил». Новому носителю заводится новый клон следующей версии. Со
временем можно опросить всех бывших носителей должности и сравнить ответы («совет
бывших экспертов»).

## 7.2 Инварианты (целевое поведение)
- **И1. Один активный носитель на должность.** В каждый момент у должности (`Role`)
  один активный носитель. Если в отделе реально нужны и главный, и рядовой
  маркетолог — это ДВЕ должности (`Role`), у каждой свой клон. На одной должности
  одновременно — один человек.
- **И2. Клон = снимок одного носителя, без смешивания.** `ExecutablePersona`
  строится из профиля ОДНОГО носителя. Агрегация черт нескольких людей в один клон
  роли (`buildForRole` — `dedupeTraitsByConcept` по всем носителям) — УБРАТЬ.
- **И3. Имя по должности + версия, без ФИО.** `publicName = «Клон <Должность> v<N>»`.
  ФИО носителя в ответ клона и в историю НЕ выводим.
- **И4. Смена носителя = freeze + новая версия.** Уходящий клон переходит в статус
  «заморожен» (read-only снимок), остаётся доступным для чтения/вопросов навсегда;
  новому носителю создаётся клон `v(N+1)` со статусом `active`.
- **И5. Ровно один `active` на должность; бывшие — `frozen`.** «Активный» клон =
  текущий носитель (один). Бывшие — статус `frozen`: доступны для чтения, но не
  активны, не обновляются и не декеятся.
- **И6. Замороженный клон не дообучается.** Никакого decay / recalibrate / rebuild /
  нормализации концептов по frozen-персонам — это снимок на момент ухода.
- **И7. На экране должности — список всех носителей.** Текущий `active` + все
  `frozen`, у каждого кнопка «спросить». Плюс новая возможность «спросить всех
  бывших и сравнить» (под-фича §7.5).
- **И8. Это НЕ персональные данные.** Клон — артефакт памяти компании, а не личные
  данные носителя: ФИО не хранится в выводе, владелец Org НЕ управляет хранением
  клонов бывших и НЕ может их ограничивать/удалять как «свои» данные. 152-ФЗ к этой
  модели НЕ применяем (явное решение владельца).

## 7.3 Карта изменений в коде (входной контракт для реализатора)
Привязка к существующим сущностям: `ExecutablePersona.scope='role'` переосмысляется
как «клон должности у конкретного носителя» (снимок одного человека + версия), а не
агрегат. `scope='person'` — внутренний снимок профиля носителя, из которого и
собирается role-снимок (можно консолидировать).

- **Р1. `buildForRole` — перестать агрегировать** (`executable-persona-build.service.ts:440-499`).
  Строить клон из профиля ЕДИНСТВЕННОГО текущего носителя должности (активный
  `PersonRole`/`Appointment`, `validTo=null`), а не из всех. Убрать
  `aggregatedTraits.push(...всех)` и `dedupeTraitsByConcept` по нескольким людям.
  ВСЕГДА проставлять `roleVersion`, `currentBearerPersonId`, `publicName`,
  `succeedsPersonaId` (этим закрываются Б12/Б16 «по построению»).
- **Р2. Убрать порог `roleAggMinPersons` (default 2).** Должность с ОДНИМ носителем
  обязана давать клон (в этом вся суть). Гейт переносится на `minTraits` профиля
  носителя. Крутилку `roleAggMinPersons` вывести из использования/AdminSetting.
- **Р3. Freeze вместо скрытого `superseded`.** Ввести читаемый статус заморозки
  (новый `frozen` ЛИБО сделать `superseded` доступным для чтения). Уходящий клон →
  `frozen` (read-only), НЕ исчезает из доступа.
- **Р4. Чтение замороженного клона.** `askRole` сейчас берёт только `status='active'`
  (`clones.service.ts:504-512,1041-1049`). Добавить путь «спросить конкретную
  версию / бывшего носителя»: параметр `roleVersion`/`personaId` → читаем
  frozen-персону и отвечаем от её лица. Топик-density и grounding-гейты применяем как
  обычно (анти-дипфейк остаётся per-версия).
- **Р5. Person-scope: уход НЕ делает клон недоступным.** Сейчас
  `Person.relationship='former'` → `SkillProfile.status='archived'` → `askPerson`
  отдаёт `no_clone` (`clones.service.ts:207`). Заморозку профиля оставить, но
  соответствующую role-персону (снимок этого носителя) держать читаемой как `frozen`.
- **Р6. Краны не трогают frozen.** `runDecay` / `skill-profile-recalibrate.cron` /
  `executable-persona-build.cron` / нормализатор концептов — исключить frozen-персоны
  и профили бывших из выборок пересборки/декея (И6).
- **Р7. История = список носителей.** `getCloneHistory(roleId)` возвращает все версии
  (`active` + `frozen`) как «Носитель v1…vN» (без ФИО) для списка на экране
  должности; UI — кнопка «спросить» у каждой версии.
- **Р8. Анонимизация имени.** `clone-respond` сейчас получает `bearerName` = реальное
  `Person.name` (`clones.service.ts:606-615,1116-1125`). Заменить на ярлык
  «Клон <Должность> v<N>»; ФИО в ответ не подставлять (И3/И8).

## 8.1 Группа A — конвейер черт (`specialist-3-7-skill.service.ts`, recalibrate/verify cron)

**Б1 🔴 `pending-never-decays-leak`** — `specialist-3-7-skill.service.ts:260-263,1452-1500` + `skill-profile-recalibrate.cron.ts:79/92/101`.

**Б2 🔴 `verify-no-order-starvation`** — `specialist-3-7-skill.service.ts:199-210`.
Симптом: `findMany(pending)` без `orderBy` + `take:100`, глобально по всем тенантам. Фикс: пересчитывать confidence из `distinctDays` (≥4 high / ≥2 medium / иначе low) на create и merge, `maxConfidence` с floor, fail-open try/catch как в эталоне.

**Б10 🟠 `create-embedding-not-guarded-dedup-leak`** — `role-principle-synthesis.service.ts:518-539`.
Симптом: `create` + отдельный `$executeRawUnsafe UPDATE embedding` БЕЗ try/catch и без транзакции; при сбое вектора строка остаётся `active` с `embedding=NULL` → `findClosestActivePrinciple` фильтрует `IS NOT NULL` → невидима дедупу → каждый ночной прогон плодит дубль. Эталон `createNewTraitRaw:1304-1315` оборачивает в try/catch. Фикс: обернуть raw-update в try/catch (best-effort) ИЛИ в `$transaction` (как `mergeIntoExisting:489-505`); опц. бэкофилл NULL-векторов.

**Б11 🟠 `budget-consumed-by-skipped-roles`** — `role-principle-synthesis.cron.ts:111-142`.
Симптом: `budget -= roles.length` по числу ВЫБРАННЫХ ролей, а LLM не зовётся на skip-ветках (`no_persons`/`no_entities`/`below_threshold`/`no_groups`); Org со 100+ пустыми ролями обнуляет глобальный бюджет → зрелые роли других Org не синтезируются. Образец `persona-layer-validation.cron` предфильтрует — здесь нет. Фикс: декрементить бюджет только при фактическом LLM-вызове (флаг `llmInvoked` / `skipped===null`) ИЛИ предфильтровать роли по наличию носителей.

## 8.4 Группа D — сборка персоны (`executable-persona-build.service.ts`, cron)

**Б12 🔴 `role-clone-version-metadata-lost-on-rebuild`** — `executable-persona-build.service.ts:484-499`. **(чинить с Б16)**
Симптом: `create` role-persona НЕ задаёт `roleVersion`/`currentBearerPersonId`/`publicName`/`succeedsPersonaId` → `roleVersion=1@default`, `bearer=null`. Любой rebuild (weekly cron, on_demand `askRole`, immediate из handler) стирает версионную идентичность. Последствия: `clone-respond` без имени носителя (`clones.service.ts:607`); `getCloneHistory` сортирует по `roleVersion desc` → свежая active=v1 проваливается вниз, цепочка `succeedsPersonaId` рвётся. Фикс: в `buildForRole` вычислять/наследовать роле-версионные поля (`nextRoleVersion = prevActive.roleVersion+1`, `currentBearerPersonId` = текущий носитель роли, `succeedsPersonaId = prevActive.id`, `publicName='Клон <role> vN'`) и писать в `create`.
> **→ ПЕРЕОПРЕДЕЛЕНО Разделом 7 (Р1):** клон строится из профиля ОДНОГО носителя (без агрегации), поэтому версионные поля проставляются по построению — отдельный «дописать в агрегат» не нужен.

**Б13 🔴 `role-persona-duplicate-active-race`** — `executable-persona-build.service.ts:440-500`.
Симптом: `nextVersion` читает `max(version)` ВНЕ транзакции; для `scope='role'` `profileId=NULL` → составной `@@unique` не конфликтует (NULL в Postgres) → две конкурентные tx создают ДВА active клона роли; `updateMany` не видит незакоммиченную строку. Лока на role-путь нет (Redis-лок только per-`profileId` в `versioning.service`). Конкуренция: weekly cron + `askRole` + bearer-changed handler. Фикс: Redis-SETNX лок `persona:rebuild:role:${roleId}` вокруг `buildForRole` + partial unique `(scope,scopeRefId) WHERE status='active'` (одна active на роль).
> **→ Совместимо с Разделом 7:** инвариант остаётся «ровно одна `active` на должность»; прошлые версии не удаляются, а переходят в `frozen` (Р3) — partial unique навешиваем только на `status='active'`.

**Б14 🟡 `persona-sweep-starvation-fixed-cap`** — `executable-persona-build.cron.ts:69-79` (+ `trigger-watcher.cron.ts:100-104`).
Симптом: `take:500` профилей / `take:200` ролей без `orderBy`, глобально; хвост не пересобирается; role-scope не покрыт staleness-watcher вообще (латентно, scale). Фикс: `orderBy` по возрасту последнего snapshot ASC + курсор; staleness-watcher для role-scope; тот же `orderBy` в trigger-watcher.

**Б15 🟡 `cron-prefilter-counts-all-layers-vs-skill-gate`** — `executable-persona-build.cron.ts:73-84`.
Симптом: предфильтр считает traits всех слоёв, а `buildForProfile` гейтит только `layer='skill'` (`service:108/118`) → профиль с N value/process-черт но 0 skill проходит предфильтр, тратит вызов, возвращает null, кривые счётчики. Фикс: в предфильтре `where {status:'active', layer:'skill'}`.

## 8.5 Группа E — версионирование персоны (`role-clone-persona-versioning.handler.ts`, `executable-persona-versioning.service.ts`)

**Б16 🔴 `rebuild-drops-bearer-fields-runaway`** — `role-clone-persona-versioning.handler.ts:229-244` + `executable-persona-build.service.ts:484-499` + `appointments.service.ts:472-484`. **(один фикс с Б12)**
Симптом: handler пишет bearer-поля в `pending_rebuild`, затем `buildForRole` создаёт active БЕЗ них и handler гасит свой pending → active с `bearer=null`. `maybeEmitBearerChanged` видит `currentBearerPersonId(null) ≠ реальный носитель` → реэмитит `role.bearer_changed` → при КАЖДОЙ операции с назначениями полная пересборка (LLM-вызов + инкремент версии) без сходимости (runaway-расход, инфляция версий). НЕ tight-loop (реэмит только на appointment-операциях), но стойкая порча. Фикс: тот же, что Б12 — active role-persona ОБЯЗАНА нести `currentBearerPersonId`; либо передавать version-контекст в `buildForRole`, либо после build обновлять созданную active полями из handler в одной транзакции.
> **→ ПЕРЕОПРЕДЕЛЕНО Разделом 7 (Р1):** при сборке из одного носителя `currentBearerPersonId` заполнен всегда → `maybeEmitBearerChanged` не видит расхождения → runaway-реэмит устраняется по построению.

**Б17 🔴 `supersede-before-successful-build-gap`** — `role-clone-persona-versioning.handler.ts:169-209,229-254`.
Симптом: транзакция БЕЗУСЛОВНО гасит `prevActive→superseded` и создаёт pending-стаб ДО build; `buildForRole` может вернуть null (LLM упал / `<minTraits` / `<roleAggMinPersons`) → роль остаётся БЕЗ active → `askRole` бросает `role_persona_unavailable` (раньше клон работал). Cron-фолбэк на тех же данных снова null → стаб висит. Фикс: не гасить `prevActive` до подтверждённой новой active (supersede только ВНУТРИ транзакции с новой active — как умеет `buildForRole:474-483`); либо компенсирующий откат `prevActive→active` при null build. Инвариант: всегда ровно одна active до подтверждения новой.
> **→ ПЕРЕОПРЕДЕЛЕНО Разделом 7 (Р3):** `prevActive` не гасится в `superseded`, а переводится в `frozen` (read-only, остаётся доступной для вопросов) только ПОСЛЕ подтверждённой новой `active`. «Пропажи клона» (`role_persona_unavailable`) при смене носителя не возникает в принципе — старый клон всегда читаем.

**Б18 🟡 `duplicate-pending-on-repeated-vacate`** — `role-clone-persona-versioning.handler.ts:118-151`.
Симптом: при повторном освобождении роли (`newPersonId=null` через admin force-rebuild) идемпотентность-2 ищет pending по `succeedsPersonaId=null`, но у первого pending `succeedsPersonaId=A` → не матчит → второй pending-стаб. Авто-путь закрыт гардом `oldBearerId===newBearerId`. Фикс: идемпотентность-2 при `newPersonId=null` искать любой pending с `currentBearerPersonId=null` для роли; частичный unique `(tenant,scope=role,scopeRefId)` ≤1 `pending_rebuild`.
