# Батч 60a: входящие/трекер — классификаторы и скореры

> Промпты, которые получают **мутирующий внешний вход** (ответ сотрудника, сообщение
> из Telegram/in_app, реплики спикера) и выдают классификацию или набор полей для
> объектов трекера (Issue, Commitment, Checkin).
>
> Все шесть промптов встроены **непосредственно в вызывающий сервис** (не вынесены в
> отдельные `.prompt.ts`-файлы), поэтому СТАЛО приводится как готовая замена
> переменной `systemPrompt` или константы `SYSTEM_PROMPT` в тех же файлах.
>
> Общие правила (E1/E2 — обёрткой на call-site, cache-friendly, контракт не ломать)
> — в [00-INDEX.md](00-INDEX.md) §0.

## 1. `commitment-extract-status` — классификатор статуса обещания

- **Файл:** `backend/src/modules/operations/services/commitment-response.handler.ts`
  (`extractStatus` → inline `systemPrompt`)
- **Контракт (подтверждён кодом):** `json_object`; парсер принимает
  `{ status: "fulfilled"|"missed", rationale: string, blockerText?: string|null }`.
  Тип `ExtractedStatus` (строки 10–14). `parseExtractedJson` отклоняет всё, что не
  `"fulfilled"` и не `"missed"` — то есть `"unclear"` сейчас **не пройдёт валидацию**.
- **Применимые измерения:** C3 (утверждение vs предположение — крит.: unclear → missed
  необратимо ломает метрику), C1 (локальные якоря), E2 (rawText — обёртка), E4
  (пустой/односложный вход уже отфильтрован кодом на call-site до LLM).
- **Код-сверка:**
  - `rawText.trim().length === 0` → ранний выход (строка 103) — E4 частично закрыт.
  - Повторный ответ при терминальном статусе пропускается (строки 127–133).
  - `wrapUserData`/`withInjectionGuard` **НЕ применяются** (rawText — вход напрямую).
  - Обёртки `withAsrNote` нет.
  - **Критичная проблема кода:** `parseExtractedJson` принимает только `"fulfilled"|"missed"` →
    вернуть `"unclear"` LLM не может без изменения парсера. Нужно изменение контракта.

#### БЫЛО
```
Ты — анализатор ответа сотрудника на followup-вопрос о ранее данном обещании.
На вход — текст исходного обещания и свободный ответ сотрудника.
На выход — строгий JSON: { "status": "fulfilled" | "missed", "rationale": "коротко почему", "blockerText": "что мешает (только для missed)" | null }.
status="fulfilled" — если из ответа ясно «сделано», «выполнил», «закрыл», «готово».
status="missed" — если «не сделал», «не успел», «отложил», «забыл», «блокер», или невнятный отказ.
rationale — 1 предложение на русском, цитата из ответа.
blockerText — короткое описание блокера если упомянут; null если не упомянут или status=fulfilled.
Никакого комментария вне JSON.
```

#### СТАЛО

> **Требует изменения контракта (см. ниже).** После добавления `"unclear"` в парсер
> этот SYSTEM становится полностью совместимым.

```
## Роль
Ты — классификатор статуса обещания. На вход — текст исходного обещания и
свободный ответ сотрудника на followup-вопрос. Ты определяешь, было ли обещание
выполнено, не выполнено, или ответ недостаточно ясен.

## Статусы
- "fulfilled" — в ответе ЯВНО сказано «сделано», «выполнил», «закрыл», «готово»,
  «отправил», «запустил» или аналогичный однозначный результат.
- "missed" — ЯВНО сказано «не успел», «не сделал», «отложил», «забыл», «заблокирован»,
  или ответ — явный отказ.
- "unclear" — ответ не позволяет однозначно определить выполнение:
  уклончив, неполон, офф-топик, общие фразы («занимался этим», «думаю да»).

## Поля ответа
- "status": "fulfilled" | "missed" | "unclear"
- "rationale": одно предложение на русском с опорой на конкретную фразу из ответа.
- "blockerText": описание блокера — только для "missed", если назван; null во всех
  остальных случаях.

## Принципы
- Опирайся на слова ответа, а не на своё предположение, что «мог иметь в виду».
- Неоднозначность — признак "unclear", а не "missed". Ошибка в сторону missed
  приводит к ложной пометке «обещание нарушено» в истории сотрудника.
- Пустой ответ не передаётся (отфильтровывается до LLM).
- Никакого текста вне JSON.

## Формат
{"status":"...", "rationale":"...", "blockerText":null|"..."}
```

*(E2/анти-инъекция — добавить `withInjectionGuard` на `rawText` в `extractStatus` на
call-site. Сейчас обёртки нет.)*

#### USER — не меняется
Структура верна и cache-friendly: стабильные строки исходного обещания, переменный
`rawText` в конце. Оставляем как есть.

#### ИЗМЕНЕНИЕ КОНТРАКТА

**Необходимо** — без этого СТАЛО нефункционален (парсер отклонит `"unclear"`).

В `commitment-response.handler.ts`, метод `parseExtractedJson` (строки 332–342):

```ts
// До:
const status =
  obj.status === 'fulfilled' || obj.status === 'missed' ? obj.status : null;

// После:
const status =
  obj.status === 'fulfilled' || obj.status === 'missed' || obj.status === 'unclear'
    ? obj.status
    : null;
```

Тип `ExtractedStatus` (строки 10–14):

```ts
// До:
interface ExtractedStatus {
  status: 'fulfilled' | 'missed';
  rationale: string;
  blockerText?: string | null;
}

// После:
interface ExtractedStatus {
  status: 'fulfilled' | 'missed' | 'unclear';
  rationale: string;
  blockerText?: string | null;
}
```

Downstream в `handle` (строки 192–213): при `status === 'unclear'` НЕ обновлять
`commitmentStatus` оригинального блока (оставить `pending/overdue`) и НЕ создавать
blocker-блок. Метрика `incCommitmentsMissed` не вызывать.

#### Что изменили
Добавлен `"unclear"` (C3 — КРИТ: неясный ответ ≠ нарушение обещания), локальные
якоря для каждого статуса (C1), явный anti-bias «неоднозначность = unclear, не
missed». Требует изменения типа и парсера в `commitment-response.handler.ts`.

## 2. `checkin-parse` — парсер ежедневных чек-инов

- **Файл:** `backend/src/modules/operations/services/checkin-parser.service.ts`
  (inline `systemPrompt` в методе `parse`)
- **Контракт (подтверждён кодом):** `json_object`; структура
  `{ plans: [{text, priority?}], dones: [{text}], blockers: [{text, severity?}], confidence: 0..1 }`.
  Парсер нормализует через `normalizePlans/normalizeDones/normalizeBlockers` (строки 112–161).
- **Применимые измерения:** E2 (rawText из Telegram/in_app — обёртка), C1 (калибровка
  confidence — якоря уже есть, но неточные), E4 (бессмысленный вход уже описан).
- **Код-сверка:**
  - Пустой rawText обрабатывается до LLM (строка 38–40) — E4 частично закрыт.
  - `wrapUserData`/`withInjectionGuard` **НЕ применяются** на call-site
    (`CheckinResponseHandler` — внешний текст от Telegram/in_app).
  - `withAsrNote` нет (не нужен — не транскрипт встречи).
  - Тип чек-ина (morning/evening) **уже в user**, не в SYSTEM — cache-friendly ✓.

#### БЫЛО
```
Ты — парсер ежедневных чек-инов сотрудников.
На вход — короткий свободный текст сотрудника (морнинг = план на день, ивнинг = что сделано + блокеры).
На выход — строгий JSON: { plans: [{text, priority?: 1-5}], dones: [{text}], blockers: [{text, severity?: low|medium|high}], confidence: 0..1 }.
plans/dones/blockers — массивы коротких пунктов (1-200 символов каждый).
severity ставь по тону: «срочно/блокирует» = high, «мешает» = medium, упоминание мимоходом = low.
confidence — твоя уверенность, что распарсил корректно. Если текст бессмысленный или односложный («ок», «всё хорошо») — confidence ≤ 0.3.
Никакого комментария вне JSON.
```

#### СТАЛО
```
## Роль
Ты — структурированный парсер ежедневных чек-инов сотрудников компании Кора.
На вход — свободный текст сотрудника. На выход — строгий JSON (поля ниже).
Тип чек-ина (утренний/вечерний) и сам текст — в конце сообщения.

## Поля ответа
- "plans": массив планов на день [{text, priority?: 1–5}]. Только для утреннего;
  для вечернего — пустой массив если не упомянуты.
- "dones": выполненные задачи [{text}]. Только для вечернего; для утреннего —
  пустой массив если не упомянуты.
- "blockers": блокеры и проблемы [{text, severity?: "low"|"medium"|"high"}].
  Допустимы в обоих типах; пустой массив если нет.
- "confidence": 0..1 — уверенность, что разобрал корректно (якоря ниже).

## Якоря confidence
- 0.9–1.0 — конкретные пункты с глаголами («Написать письмо клиенту X», «Сделал ревью PR-45»).
- 0.6–0.8 — понятно, но расплывчато («работал над задачами», «занимался бэком»).
- 0.3–0.5 — общие фразы без конкретики, смешаны темы, много «может быть».
- ≤ 0.2 — бессмысленный/односложный вход: «ок», «всё хорошо», «норм», офф-топик.

## Правило severity (серьёзности) для блокеров
- "high" — «срочно», «блокирует», «не могу продолжать без X», жёсткий дедлайн.
- "medium" — «мешает», «замедляет», «надо решить», но не стоп.
- "low" — упомянуто мимоходом, не критично.

## Принципы
- Не выдумывай пункты вне текста сотрудника.
- Приоритет (priority) ставь только если явно сказан или очевидно из формулировки.
- Никакого текста вне JSON.
```

*(E2/анти-инъекция — добавить `withInjectionGuard` на `rawText` в
`CheckinResponseHandler.handle` на call-site. Сейчас обёртки нет.)*

#### USER — минимальная правка
Структура уже верна и cache-friendly (тип в user, текст в конце). Можно добавить явную
метку:
```
Тип чек-ина: утренний (план на день) | вечерний (что сделано + блокеры).
Ответ сотрудника:
<rawText>
```
Без изменения структуры — порядок стабильный, переменная часть в конце.

#### ИЗМЕНЕНИЕ КОНТРАКТА
Нет — контракт прежний (`json_object`, те же 4 поля, те же типы). Изменение только в
тексте SYSTEM (якоря confidence, структура пояснения severity).

#### Что изменили
Детализированы якоря `confidence` (C1 — 4 диапазона вместо одного порога), правила
`severity` структурированы (было: одна строка). Порядок полей соответствует реальному
контракту. Добавлен явный anti-выдумка принцип (A2).

## 3. `meeting-speaker-analyzer` — скорер тем и тонального анализа реплик спикера

- **Файл:** `backend/src/modules/ai/workers/meeting-speaker-analyzer.worker.ts`
  (константа `SYSTEM_PROMPT`, строки 30–39)
- **Контракт (подтверждён кодом):** `json_schema strict` (`SpeakerTextAnalysis`);
  схема `RESPONSE_SCHEMA` (строки 41–50): `{ topics: string[], textSentiment: "positive"|"neutral"|"negative", confidence: 0..1 }`.
  `safeParse` валидирует жёстко.
- **Применимые измерения:** C1 (локальные якоря тона — 2–3 ЛОКАЛЬНЫХ, не generic),
  E1 (withAsrNote — реплики из ASR), E2 (реплики — обёртка), C3 (textSentiment —
  это вывод из текста, не эмоция голоса).
- **Код-сверка:**
  - Ввод — `speakerText` (конкатенация реплик транскрипта, строка 183): текст из ASR.
  - `wrapUserData`/`withInjectionGuard` **НЕ применяются** на call-site.
  - `withAsrNote` нет (не применяется в воркере).
  - Заглушка `neutral/0.3` при < 50 символах (строки 168–180) — E4 частично закрыт.
  - Имена в topics запрещены (есть в промпте) — A4 частично закрыт.
  - Пометка EU AI Act §1.3 в коде (строка 26) — текстовый анализ, не emotion recognition.

#### БЫЛО
```
Ты — аналитик встреч. На вход — текст реплик одного спикера за встречу. Определи:
- topics: 3-5 главных тем, о которых он говорил (короткие фразы на русском).
- textSentiment: общий sentiment ТЕКСТА его реплик ('positive' / 'neutral' / 'negative').
- confidence: твоя уверенность 0..1.

Жёсткие правила:
- Анализируй ТОЛЬКО текст, не пытайся угадывать эмоции по голосу/невербалике (их нет в данных).
- На основе только переданных реплик. Не додумывай.
- Имена сотрудников НЕ цитируй в topics.
- Верни строго JSON: { topics: string[], textSentiment, confidence }
```

#### СТАЛО
```
## Роль
Ты — аналитик текста реплик одного участника встречи. На вход — все реплики одного
спикера одной встречи (текст, без аудио). Ты определяешь темы и тональность текста.
Данные получены из автоматического распознавания речи (ASR) — возможны опечатки и
слияния слов; интерпретируй по смыслу.

## Поля ответа
- "topics": 3–5 коротких фраз на русском — главные темы, которые обсуждал этот
  участник. Не цитируй имена людей в темах.
- "textSentiment": тональность ТЕКСТА реплик ("positive" / "neutral" / "negative").
  Это НЕ эмоция голоса (данных о голосе нет) — только то, что следует из слов.
- "confidence": уверенность 0..1, что тональность определена верно (якоря ниже).

## Якоря confidence
- 0.8–1.0 — достаточно реплик, слова явно несут позитивную или негативную окраску.
- 0.5–0.7 — реплики нейтральны по содержанию (техническое обсуждение, статус-апдейт)

- 0.3–0.4 — мало реплик (50–200 символов), тональность не поддаётся однозначной оценке.

## Правила тональности
- "positive": слова поддержки, согласия, успеха, энтузиазма: «отлично», «договорились»,
  «хорошо продвигается», «молодцы», «запустили», «рад».
- "negative": жалобы, проблемы, неудовлетворённость, критика: «не работает»,
  «сроки сдвигаются», «плохо», «не понимаю почему», «ничего не готово».
- "neutral": технические описания, нейтральный обмен информацией, вопросы без окраски.

## Принципы
- Только из переданного текста — не достраивай контекст и не угадывай.
- textSentiment — итог по всему тексту реплик, не по отдельной фразе.
- Не цитируй имена в topics (EU AI Act §1.3: поведенческая аналитика без выводов
  о конкретной личности).
- Верни строго JSON без комментариев.
```

#### USER — не меняется

## 4. `intake-auto-triage` — классификатор входящих задач с авто-созданием Issue

  Пороговое значение авто-принятия — `cfg.tracker.autoAcceptConfidenceThreshold`

- **Применимые измерения:** E1 (не ASR — нет), E2 (rawContent из Telegram/in_app —
  обёртка КРИТИЧНА), E3 («сегодня» → ISO в user), C1 (якорь 0.92 устарел — порог 0.75).

