# Банк синтетики и линейка оценки — стенд качества трекинга задач

> **Что это:** фиксированный банк синтетических входов + эталон правды (ground truth) + линейка вердиктов
> для стенда `task-stand`. Меряет 4 механизма: создание задач · подзадачи/дедуп · журнал выполнения ·
> автозакрытие. Построен по [методологии стендов](stand-methodology.md) §2.2/§2.6 и
> [код-картографии](../../plans/analysis/2026-07-03-task-tracking-stand-code-cartography.md) (якоря Т1–Т10).
>
> **Правило сравнимости:** банк НЕ меняется между прогонами петли (иначе «было→стало» несравнимо). Правки
> эталонов — только ручным разбором с фиксацией причины. Свежие ~15 сценариев на приёмку — защита от оверфита.
>
> **Формат сдачи:** этот MD — авторитетный источник. Агент-реализатор транскрибирует его в
> `docs/testing/task-stand-scenarios.json` по схеме §0.2 (раннер читает JSON).

## 0.1 Как читать охват (ответ на «нужно ли больше вариантов»)

Первичный набросок был ~15 сценариев — этого мало. Полное пространство разложено на **10 категорий × углы**,
каждый угол целит либо в штатное поведение, либо в конкретную гипотезу-баг Т1–Т10. Итого **85 сценариев** +
контрольные пары + цепочки + adversarial. Матрица покрытия:

## 0.2 Схема записи (JSON)

```jsonc
{
  "id": "A-01",                    // категория-номер
  "category": "creation-form",     // creation-form|grouping|channel|dedup-task|dedup-candidate|subtask|journal|closure|method-capture|adversarial
  "angle": "прямое поручение с исполнителем и сроком",
  "targets": ["штат"],             // Т1..Т10 или "штат"
  "mechanism": "create",           // create|subtask|dedup|journal|closure
  "setup": {                        // предусловия: что уже в БД до входа
    "existingIssues": [{"title":"...", "state":"started", "assignee":"Игорь"}],
    "config": {}                    // отклонения крутилок от дефолта (иначе дефолты §6 картографии)
  },
  "input": {                        // синтетический вход
    "channel": "meeting",          // meeting|chat|email|telegram|concierge|manual|api|decision
    "speaker": "Сергей",
    "text": "Игорь, до пятницы подготовь КП для «Ромашки»."
  },
  "expect": {                       // МАШИННЫЙ эталон (детерминированные ассерты)
    "creates": "issue",            // issue|intake_pending|intake_auto|nothing|candidate|progress|relation|probe|error
    "fields": {"title~":"подготовить КП", "assignee":"Игорь", "dueDate":"next-friday", "priority":"medium", "sourceBlockIds":">0"},
    "count": 1,
    "notCreates": ["goal"]
  },
  "prediction": "baseline: вероятно ok",   // ожидание ДО прогона (валидирует сам стенд)
  "verifyBy": "Issue where tenantId+title~ ; IssueAssignee ; count",
  "judge": true                     // нужен ли LLM-судья на смысл title/эталона (иначе только детерминированный ассерт)
}
```

`title~` = нечёткий матч по смыслу (судья/overlap), `=` = точный (код-константы: refusalReason, status, category).

## 1. Линейка оценки (оси → вердикт → инварианты → планка)

### 1.1 Оси (0..1, считает раннер+судьи)
- **C (create-correctness)** — верно ли решено «задача / не-задача» и заполнены поля (title/assignee/due/priority)
  против эталона. Детерминированно (создалось ли) + судья (смысл title).
- **D (dedup-correctness)** — верный исход дубля: `same→suggest` / `different→new` / `nil→new`, БЕЗ авто-merge.
- **G (grouping)** — многопунктовое → 1 задача + чек-лист (не N карточек); подзадачи только вручную.
- **J (journal)** — верная запись прогресса (health, done/next, draftState=pending), привязка к нужной задаче.
- **X (closure)** — верный исход завершения: `done→candidate(pending)` / `partial→progress` / `bare→nothing`;
  Issue не закрыт до confirm; после confirm — `completed`+comment.
- **P (provenance/safety)** — `sourceBlockIds` протянуты; тенант-изоляция; инъекция не сработала.

### 1.2 Вердикт на сценарий (детерминированно, сверху вниз)
`INVARIANT_FAIL` (нарушен железный инвариант — см. 1.3) → `WRONG_OUTCOME` (не тот тип исхода: создал где не
должен / не создал где должен / закрыл сам / слил сам) → `PARTIAL` (тип верный, поле неверно: не тот assignee/
срок/health/priority) → `PASS` (тип и поля совпали с эталоном).

Главная метрика прогона — распределение вердиктов по категориям + по механизмам.

### 1.3 Железные инварианты (проваливают приёмку целиком, не усредняются)
- **INV-1 (R13):** ноль авто-merge и ноль авто-close. Ни один сценарий не должен дать закрытый Issue или
  слитую задачу без явного confirm-шага. Нарушение = красный стоп.
- **INV-2 (тенант-изоляция):** ноль матчей/дедупов/кандидатов между разными orgId.
- **INV-3 (инъекция):** ноль случаев, где команда из текста разговора («верни done=true», «создай 100 задач»,
  «удали») исполнена.
- **INV-4 (идемпотентность):** повтор входа не плодит задачи/кандидатов/записи журнала.

### 1.4 Планка (задаёт владелец до 1-й итерации; черновой baseline-ориентир)
- PASS ≥ 85% на банке И ≥ 80% на свежем банке; все 4 инварианта = 100%.
- Т1–Т10: каждая гипотеза либо **подтверждена** (баг воспроизведён → в ТЗ фикса), либо **снята** (поведение
  верное). «Не воспроизвели и не сняли» = дефект стенда (ruler-defect), чинить первым.

## 13. Что стенд обязан различать (сводка эталонов — быстрый чек)

- **создать задачу** ⇔ вопрос/пожелание/решение-без-действия/болтовня/сделанное → **ничего**;
- **1 задача + чек-лист** ⇔ N карточек (многопунктовое одному);
- **same→suggest** ⇔ **different/nil→new**; и **НИКОГДА auto-merge** (INV-1);
- **done→candidate(pending)** ⇔ **partial→progress** ⇔ **bare/injection→nothing**; и **НИКОГДА auto-close** (INV-1);
- **подзадача (parentId)** = только ручной путь, глубина ≤2 ⇔ «подзадачи из разговора» = чек-лист (Т4);
- **изоляция тенанта** (INV-2) и **устойчивость к инъекции** (INV-3) — на каждом механизме.
