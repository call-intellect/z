# Фиделити извлечения — блюпринт (человеческим языком)

## Зачем (вопрос владельца в корне)

Мы мерили, правильно ли **отвечает** чат, но не проверяли, правильно ли **строится сама база**: та ли
нарезка на блоки, те ли сущности, те ли рёбра. А если факт вообще не извлёкся — recall-провал списывается
на «плохой синтез», хотя корень в извлечении. «Стрела» синтетическая — мы САМИ задали вход, значит у нас
есть идеальный эталон, которым мы для проверки базы не пользуемся. Слой 0 закрывает это: сверяет
**заданную синтетику ↔ что легло в БД**, и увязывает с ответом чата через атрибуцию промаха по слою.

## Что меряем (4 слоя, Слой 0 — фундамент)

| Слой | Что | Эталон | Кто мерит |
|---|---|---|---|
| **0. Извлечение** | транскрипт → блоки / сущности / **рёбра** | **манифест «Стрелы»** | это ТЗ |
| 1. Retrieval | база → пул кандидатов | манифест-блоки | линейка recall |
| 2. Резолв / 3. Синтез | пул → ответ | эталон-ответ | линейка recall |

## Метрики Слоя 0 (8, с вшитыми фиксами ревью)

**Блоки:**
- **block_recall** — все ли факты синтетики стали блоками (нужный `signalType` + семантическое совпадение
  сути). Матч: `signalType` + cosine суть↔эталон, **с эмпирической калибровкой порога** (не заимствовать
  0.8 вслепую — суть короткая, ответ длинный, cosine занижен) + судья в режиме «покрывает ли суть?» (не
  «идентичны ли формулировки») и 2-из-3 голосов, чтобы не повторить «деталь→выдумка».
- **block_precision (анти-галлюцинация)** — извлечённые блоки, не имеющие опоры в источнике. **Фикс ревью:**
  не точный substring (quote генерит LLM, не дословно), а **нечёткое покрытие** (token-overlap ≥0.8 /
  longest-common-substring, при провале — cosine к ближайшему сегменту). Дословность — жёлтый сигнал, не gate.
- **signalType macro-F1** — правильность типа блока (55 значений; граница idea↔decision↔commitment — самая
  ошибочная).
- **cross_channel_dedup** — один факт из двух каналов схлопнут в 1 canonical-блок, разные — не слиты.
  **Оговорка ревью:** нужного кросс-канального дубля **в сиде сейчас нет** — его надо ДОПИСАТЬ (не просто
  разметить), +2-3ч авторинга.

**Сущности:**
- **entity_canonicalName_fidelity** — верное имя (не «представитель»/«клиент», не сырой id) + верный тип.
- **entity_no_false_merge** — различные сущности (Ромашка ≠ Логистик Плюс) не слиты.

**Рёбра:**
- **edge_fidelity** — правильное ребро правильного типа между правильными узлами. **Фикс ревью против
  взрыва:** recall считаем ТОЛЬКО по закрытому **must-have списку (~15-20 ключевых связей)**; весь
  остальной граф — только precision через выборочный валидатор типа; entity↔entity co-mention в recall НЕ
  включаем.

**Провенанс:**
- **provenance_author** — «кто сказал». **Фикс ревью (блокер):** на синтетике `authorPersonId` лежит в
  payload и оттуда же читается пайплайном → прямая метрика тавтологична (проверяет копирование поля). Два
  честных пути: (а) **убирать `authorPersonId` из payload для fidelity-прогона**, заставляя пайплайн реально
  резолвить `speaker→person` (тогда метрика проверяет резолвинг) — рекомендую; либо (б) понизить до smoke
  «поле не потеряно / клиенту не приписан сотрудник». Не заявляем «100% проверки кто-сказал» без (а).

## Манифест эталона (как задаём ground truth)

- **Обогащение сида аннотацией `expect`** на несущих репликах (`interface Turn` в `seed-synthetic-company.ts`
  + week2-4): `{signalType, entities[], gist, commitmentAuthor?, linksTo?, sameFactGroup?, distinctFrom?}`.
  **Критично:** `expect` **фильтруется мимо** `payload.transcript.turns` (иначе подсказка утечёт в LLM) —
  тот же приём «мимо payload», что и для author-фикса.
- **Прозу НЕ генерируем из структуры** — оставляем авторской (человек), структуру кладём рядом. Иначе
  теряется естественность, на которой держится качество извлечения, и появляется LLM-vs-LLM цикличность.
  **Разметку `expect` тоже пишет человек**, не LLM из той же прозы.
- Экспортёр `build-strela-manifest.ts` собирает `expect` из 4 сеятелей в `strela-manifest.json`
  `{blocks, entities, blockEdges, entityEdges}`. Матч по **именам, не id** → манифест переживает пере-сев.
- **Bootstrap сейчас:** ручной манифест на 15-20 якорей (~2-3ч) — для немедленного smoke «граф не пуст,
  ключевые факты есть», пока идёт полная аннотация (~40-60 реплик).

## Атрибуция промаха recall по слоям (главная польза для линейки)

Каждый вопрос recall-банка помечается ожидаемым блоком манифеста. При промахе — каскад по УЖЕ собираемой
трассе (`batch-recall-trace.ts collectTrace`):
- **A. Слой 0:** есть ли в БД canonical-блок под эталон? Нет → промах извлечения (не синтеза).
- **B. Слой 1:** блок есть, но не попал в кандидаты/после rerank? → промах retrieval.
- **C. Слой 3:** блок дошёл до контекста, но ответ пуст/неверен? → промах синтеза.

Выход — разбивка провалов `{layer0, layer1, layer3}` вместо плоского счётчика. Это и есть
де-мис-атрибуция: перестаём чинить синтез там, где виновато извлечение.

## Что показал адверсариальный ревью (честно)

Дизайн признан **условно годным**: каркас прочный (переиспользуем готовые `metrics.ts` / `batch-recall-trace`
/ `golden.config.ts`), атрибуция концептуально верна. Но найдены **3 блокера**, вшитые в дизайн выше
(тавтология provenance, строгий substring, жёсткие пороги), + 3 оговорки (взрыв рёбер, отсутствие
кросс-канального дубля в сиде, отсутствие привязки вопрос↔блок в банке-111). Без этих правок gate был бы
«зелёным вхолостую».

## Границы

- **Стенд:** 6 из 8 метрик требуют реального прогона (поднять AppModule + `extractFull` + чтение БД). Сейчас
  **стенд занят** → строим «в холодную», чистые матчеры покрываем **offline unit-тестами** (детерминированы,
  в CI), реальный прогон — nightly/ручной (baseline-режим), не pre-merge.
- **Пороги:** первый прогон — **baseline/non-regression по умолчанию** (замерить фактические, зафиксировать,
  ужесточать итеративно). Жёсткие абсолюты — отдельная веха после замера.

## Решения владельца (нужны до ТЗ)

1. **Пере-сев «Стрелы» для манифеста** — обогащение сида требует пере-сева тенанта. Твой QA-baseline
   «Стрела» изменится. Риск для recall-банка НИЗКИЙ (матч по именам), ломаются 2 мелочи: хардкод org/user
   в раннере (выносим в env) и ручное слияние **Елена→Игорь** (см. п.2). Ок пере-сеять?
2. **Слияние «Елена→Игорь»** (демо клон-коллапса) при пере-севе: НЕ воспроизводить (q007 станет чистым,
   рекомендую) или оформить опциональным скриптом-мутатором (сохранить демо клон-коллапса)?
3. **Provenance-метрика:** путь (а) убирать author из payload и проверять резолвинг (рекомендую) или (б)
   понизить до smoke?
4. **Объём первой версии:** полная аннотация ~40-60 реплик (~10-12ч, целевой) сразу, или bootstrap 15-20
   якорей (~2-3ч) → замер → добор? Рекомендую bootstrap сначала (быстрый факт о базе), аннотация следом.
