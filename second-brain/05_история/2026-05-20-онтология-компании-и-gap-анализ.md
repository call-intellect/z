# 2026-05-20 — Онтология компании и gap-анализ knowledge-core

## Что было поставлено

Основатель сформулировал базовую онтологию «второго мозга компании»: 13 классов сущностей (Person, Process, Decision, Project, Document, Event, Technology, Customer, Vendor, Product, Goal, Risk, Metric), ~40 типов рёбер с обязательными атрибутами (`valid_from/to`, `source_event_id`, `confidence`, `weight`), механика клона сотрудника как subgraph + stylistic profile, РФ-специфика (LegalEntity / GovernmentBody / Tender / License). Попросил:

1. Зафиксировать онтологию в second-brain для маркетинга.
2. Проанализировать, что уже реализовано в Z по части сбора информации и AI-агентов.
3. Сохранить аналитику.

## Как решал

**1. Фиксация онтологии.**
- Создал [second-brain/06_marketing/company-ontology.md](../06_marketing/company-ontology.md) — полностью сохранил формулировку основателя, добавил структуру (заголовки, списки), не перефразируя.
- Обновил [second-brain/06_marketing/index.md](../06_marketing/index.md) — ссылка на онтологию.
- Решение: положить в `06_marketing/`, а не в `02_architecture/`, потому что пользователь явно сказал «для маркетинга», и это пока концептуальный фундамент, не описание реализованного.

**2. Аудит фактического состояния knowledge-core.**
- Делегировал глубокое исследование Explore-агенту с явным форматом отчёта по 4 разделам (pipeline + БД + API + фазы / воркеры + taskType + промпты / сравнение с онтологией / delivery/).
- Агент прочитал [knowledge-core.md](../02_architecture/knowledge-core.md), [data-model.md](../02_architecture/data-model.md), плюс код в `backend/src/modules/knowledge-core/` (48 TS-файлов), Prisma schema, папку [delivery/](../../delivery/).
- Синтезировал в чате компактный ответ: pipeline RawEvent → IdeaBlock → Theme, 11 моделей, 8 воркеров + 6 cron-job'ов, 10 taskType в LlmRouter, 11 API endpoints. Сопоставил с онтологией: ~13/40 рёбер реализовано, 5 классов прямо, 3 косвенно через signalType, 3 в custom, 2 partial.

**3. Сохранение аналитики.**
- Создал [plans/analysis/2026-05-20-knowledge-core-vs-ontology-gap-analysis.md](../../plans/analysis/2026-05-20-knowledge-core-vs-ontology-gap-analysis.md) — gap-анализ с разделами: что есть, сопоставление по классам и рёбрам, 5 главных пробелов (Decision как класс, Document как класс, временной слой графа, stylistic profile человека, полнота рёбер), минимальный план закрытия на ~1.5-2 недели.
- Решение: положить в `plans/analysis/`, а не в `second-brain/` — это разбор «как улучшить», не описание текущего состояния. Прямое следование правилу из CLAUDE.md: «работает → second-brain; идея/анализ → plans».
- Добавил обратную ссылку из company-ontology.md на gap-анализ, чтобы оба документа знали друг о друге.

## Что вышло

- 2 новых документа: онтология (marketing) + gap-анализ (plans/analysis).
- Обновлены 2 индекса: [06_marketing/index.md](../06_marketing/index.md) и [second-brain/index.md](../index.md).
- Кода не трогал — это чисто документационная сессия.
- Не делал коммита — нет явного запроса от пользователя.

**Главный продуктовый вывод аналитики:** Z knowledge-core покрывает ~45% онтологии. Сильно сделан сбор и кластеризация (pipeline, дедупликация, темы). Слабые места — Decision не выделен как класс (это главная боль knowledge loss из самой онтологии), Document живёт только как Evidence, рёбра без `valid_from/to` (значит, временной срез графа невозможен → клон сотрудника технически недостижим без правки схемы), нет stylistic profile у Person. Минимальная инвестиция для подъёма до ~70% — 1.5-2 недели работы одного бэкенд-разработчика.

## Чему научился

1. **Когда пользователь даёт большой блок текста с просьбой «зафиксируй» — нельзя перефразировать.** Структуру можно добавить (заголовки, списки), но содержательно — сохранять как есть. Это его формулировка, не моя.
2. **Делегирование Explore-агенту окупается, когда нужен полный аудит «что есть».** Я мог бы прочитать knowledge-core.md и data-model.md сам, но 48 файлов кода + сравнение с двумя независимыми концепциями — это уже не «найти X», это «синтезируй карту состояния». Сэкономил контекст основной сессии.
3. **Различие second-brain ↔ plans/analysis по правилу «работает vs идея» работает на практике.** Онтология описывает целевое состояние → marketing (концепция продукта). Gap-анализ описывает дельту → plans/analysis. Если бы положил оба в одно место, ссылки между ними не имели бы смысла.
4. **Обратная линковка между документами стоит дёшево и сильно повышает связность.** Минута на Edit вместо потерянного контекста через месяц.
5. **«Закрываем обсуждение» — это триггер 2 завершения работы**, даже если push'а в сессии не было. Применяю весь блок: обновить → записать рефлексию → ждать команды на коммит.
