# Рефлексия — фиделити извлечения (Слой 0): метод, прогон, ТЗ на консолидацию

## Что было поставлено

Из диалога про recall-потолок владелец вскрыл корневой вопрос: мы проверяем ОТВЕТ чата, но не проверяем,
**правильно ли строится сама база** (та ли нарезка на блоки, те ли сущности/рёбра). Синтетика «Стрела» —
наш эталон, которым для проверки базы не пользовались. Задача: построить метод фиделити «источник→база»
(Слой 0), прогнать на «Стреле», найти дефекты, написать ТЗ на исправление и передать другому агенту. Плюс —
переносимая методология (для параллельного клон-стенда).

## Как решал

**Цепочка планирования по-честному.** feature-analyst-стиль анализ → блюпринт (approved) → ТЗ. Сначала —
диагностика recall-потолка (workflow: 4 картографа → дизайн → адверсариальный ревью): выяснилось, что часть
«провала» — артефакт линейки (7/12 «пустых» ложные), анафора РАБОТАЕТ (снял свою же гипотезу), а таблицы
уже подключены к chat, но пусты. Затем — блюпринт линейки recall (слои 1-3) и, по наводке владельца,
блюпринт Слоя-0 (извлечение).

**Слой-0 спроектирован workflow с адверсариальным ревью — и это окупилось:** ревьюер поймал 3 блокера
(тавтология provenance: authorPersonId и вход = одно поле; строгий substring на LLM-цитате; жёсткие пороги
до замера) — вшил фиксы ДО ТЗ.

**Прогон — непересекающимися агентами (по указанию владельца «ты как человек размечаешь»).** 44 якоря из
всех источников «Стрелы», партиями: 2 слепых разметчика (видят только прозу) → сверка (inter-annotator
agreement) → сверялка с реальной базой (read-only). Числа дедупа доп. верифицировал прямым запросом.

## Что вышло (честно)

**Полнота отличная — 0 потеряно из 44.** Дедлайны/метрики захвачены точно, атрибуция авторов верна,
онтология типов богатая (client_request/objection/process_step). НО **консолидация сломана** (верифицировано
запросом): 171 сущность, **23 имени задвоены разными типами** (Битрикс=technology+vendor+product,
retention=goal+topic+metric); блоки-дубли (429-блокер ×4, webhook ×3, «Моя история» ×2). Это фрагментирует
граф → вероятный корень ведра ④ recall.

**Главная честность (владелец сам поймал):** замерён только **Слой 0** (источник→база). Влияет ли дефект на
ОТВЕТ — НЕ трассировано; банк даёт ~77-79% recall УЖЕ с дефектами → они не фатальны. Связь «фрагментация →
провал recall» — гипотеза, её надо доказать атрибуцией. Записал это явно в анализ и в prompt пере-проверки.

**Артефакты:** метод `docs/methodology/synthetic-fidelity-eval-method.md` (переносимый, с §6 под клон-стенд);
блюпринты + ТЗ линейки/фиделити/провенанса/консолидации; манифесты `strela-manifest.batch{1,2,3-rest}.json`;
prompt для агента пере-проверки `docs/testing/consolidation-reverify-agent-prompt.md`. Коммиты `56c7f67f`
(recall-ceiling) · `96339c07` (методология+блюпринт) · `1002598c` (fidelity+ТЗ) · `6872b7b2` · `6878c656`.

## Чему научился

1. **Слепые непересекающиеся агенты реально разрывают цикличность.** signalType совпал ~40/44 при
   независимой разметке → согласие честное, а conflict-якоря (A9/A10 объект риска) точно указали, где и
   извлечение плавает. Ключ — разметчик видит ТОЛЬКО источник, сверялка ТОЛЬКО базу.
2. **Онтология ≠ словарь разметчика.** База хранит plan_item/action_item/client_request, а не goal/task —
   матчить надо ПО СМЫСЛУ, иначе ложные «wrong_type».
3. **Полнота и консолидация — разные оси.** Можно захватывать всё (44/44) и при этом иметь мусорный граф
   (дубли). «Извлекается» ≠ «консолидируется».
4. **Слой-0-дефект ≠ доказанное влияние на ответ.** Легко увлечься «нашли дефект → чиним», но recall уже
   приемлемый С дефектами. Сначала атрибуция (какой слой стоит ответа), потом инвестиция в фикс.
5. **Адверсариальный ревью дизайна до ТЗ окупается** — поймал 3 тавтологии/ловушки, которые дали бы «зелёный
   вхолостую» гейт.
6. **Read-only проверка базы — не «запуск стенда».** Пока стенд занят другой фичей, прямой Prisma-read
   (createPrismaClient, импорт по абсолютному пути из scratchpad) даёт точные цифры без конфликта.
