# Прод-SSH доступ и точечные прогоны на проде

> Назначение: как агент (Claude) и владелец делают **точечные ручные прогоны** на прод-сервере Коры (backfill, форс cron, разовая диагностика), когда штатная автоматика недостаточна.
> Секреты (host/пароль) — **только** в gitignored `/.prod-access.local.json` в корне репо. В этот файл (он в git) пароль НЕ писать никогда.

## 🔒 ПРАВИЛО №1 — каждый SSH-прогон согласовывать с владельцем

Любая команда, выполняемая на прод-сервере по SSH, требует **явного «да» владельца в текущей сессии** под конкретную команду. Общее «добро» на доступ ≠ разрешение на конкретный прогон. Перед каждым SSH:
1. Показать владельцу точную команду, которую собираешься выполнить.
2. Дождаться подтверждения.
3. Только потом выполнять. Вывод (без секретов) — обратно в чат.

Это правило-близнец к «прод-диагностика (diag.ts) только с явным да» — но строже: SSH даёт запись/выполнение на проде, а не только чтение.

## Доступ

- Реквизиты (host, gateway, user, password, projectDir) — в `/.prod-access.local.json` (gitignored).
- Пароль временный, владелец ротирует — после смены обновить gitignored-файл.
- Технический префикс для неинтерактивного запуска из локального Git Bash: нужен `sshpass` (на машине агента сейчас НЕ установлен) **или** добавленный публичный ключ агента на сервер. Без одного из этого агент не может выполнить пароль-SSH сам — тогда команду выполняет владелец/программист и присылает вывод.

### Как агент подключается сам на macOS — проверенный путь и грабли (2026-07-03)

> На эти грабли уже наступали ДВА агента подряд, вывод нигде не был записан. Фиксируем — при слове «SSH / зайди на прод» сверяйся с этим списком, не переоткрывай заново.

1. **`sshpass` на macOS нет, но есть `expect`** (`/usr/bin/expect`). Пароль-SSH гоним через expect-обёртку: `spawn ssh -tt -o PubkeyAuthentication=no -o PreferredAuthentications=password user@HOST "su root -c \"<cmd>\""`.
2. **root по SSH напрямую ЗАПРЕЩЁН** (`root@HOST` → `Permission denied (publickey,password)`). Заходить **обычным пользователем `user`**, затем `su root` для docker.
3. **`su` спрашивает пароль ПО-РУССКИ — «Пароль:», а не «Password:».** expect-ветка обязана ловить оба: `-re {(assword|ароль):}`. Именно на русском промпте залипали в таймаут.
4. **`su -` (login-shell) виснет/медленный** → использовать `su root -c '<cmd>'` (без дефиса).
5. **`docker compose ps` без `--format` может висеть** → давай `--format` и expect `set timeout 200`.
6. **Не мучиться с экранированием SQL**: слать удалённый bash одним base64-блобом — `echo <b64> | base64 -d | bash`, внутри heredoc для psql.
7. **psql на проде (read-only!):** `cd /home/docker/z && set -a && . ./.env && set +a && docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -P pager=off -A -F '|'`. БД = `z_main`. Имена таблиц — Prisma-стиль: `"User"`, `"Org"`, `probe_events`, `persons`, `"Membership"`.
8. **Только чтение** (правило №1). Для диагностики — исключительно `SELECT` / чтение логов; никаких write/restart/deploy без отдельного явного «да».

## Когда вообще нужны ручные прогоны (важно — это НЕ повседневность)

В НОРМАЛЬНОЙ работе ручные команды НЕ нужны — конвейер знаний и клонов работает сам:
- встреча/заметка → block-ingest → router → специалисты → событийная перестройка профиля (дебаунс ~60с) → ночные cron'ы добивают (`SkillTraitConceptNormalizerCron` 03:00, `SkillTraitVerifyCron` 03:30, `SkillProfileRecalibrateCron` 05:00, `RolePrincipleSynthesisCron` 05:30, сборка персон — Вс 06:00).

Ручной прогон оправдан только в трёх случаях:
1. **Разовая миграция данных после деплоя**, который меняет, какие данные участвуют (пример: `backfill-skill-profiles-rebuild.ts` после фикса `methodology_step` — событийная перестройка ловит только НОВЫЕ блоки, исторические надо догнать backfill'ом ОДИН раз). Это не повторяется.
2. **Ускорение приёмки**: форснуть cron через админку cron-ов или скриптом, чтобы не ждать ночного расписания во время теста. В реальной эксплуатации просто ждут ночь.
3. **Точечная диагностика инцидента** (read-only diag.ts / чтение логов/Redis).

> Если ловишь себя на «надо прогонять команду регулярно» — это сигнал, что чего-то не хватает в автоматике (cron/событие), и это надо чинить кодом, а не превращать в ручной ритуал.

## Частые точечные команды (выполнять по правилу №1)

Все — внутри docker-compose на сервере (`cd /home/docker/z`):
- Backfill пересборки клонов: `docker compose exec backend bun run scripts/backfill-skill-profiles-rebuild.ts --tenant=<orgId>`
- Полный апдейт-выкат скриптов: `docker compose exec backend bun run scripts/apply-prod-deploy.ts --mode update --continue-on-fail`
- Форс cron: через админку `POST /api/v1/admin/crons/:name/run` (или диагностикой `diag-clone.ts run-cron <name>`).
- Очистка застрявшего rebuild-джоба (jobId-дедуп держит 24ч): см. ниже.

### Нюанс: jobId-дедуп очереди перестройки клона

`enqueueRebuildSkillProfile` всегда `jobId=skill-profile-rebuild_<profileId>`, очередь хранит завершённые джобы 24ч (`removeOnComplete age:86400`). Пока завершённый джоб в Redis — повторная перестройка того же профиля **схлопывается** (no-op). Чтобы форснуть свежую перестройку раньше 24ч — удалить ключ джоба в Redis, затем backfill (команда — по правилу №1, согласовать).
