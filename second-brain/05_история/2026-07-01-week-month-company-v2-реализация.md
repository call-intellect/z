# 2026-07-01 — Реализация «Неделя/Месяц компании v2» (паритет с днём, 8 фаз оркестрацией)

## Что поставлено

Реализовать ТЗ `plans/tz/2026-07-01-week-month-company-v2.md` (status ready-to-implement): поднять экраны «Неделя компании» (/dashboard таб «Неделя») и «Месяц компании» (/month) до уровня «Дня компании v2» — единый продукт на всех горизонтах. Пять кусков поверх готового: письма недели/месяца в COO-голос v2; кормить недельный синтез полными дневными письмами; снапшотить сигналы за окно периода (риски-по-причине/кластеры/трения/блокеры) в metricsJson и рендерить из дайджеста, а не live-top; `decisions`→`ownerForks` («Развилки месяца»); ось «Команда» краснеет от трений; скрыть canvas-дубль для owner + перенести month-виджеты в герой. Границы: без миграций БД (всё в metricsJson), без нового извлекающего агента, движок целей не трогать.

## Как решал

Оркестрация скиллом `tz-orchestrator` — код руками не писал, вёл через суб-агентов фаза за фазой с собственной приёмкой каждого.

- **Картография (сам, ~15 файлов).** Прочитал образец дня v2 (`daily-digest.prompt.ts` — SYSTEM/few-shot/12 ключей/строгая zod), реальные промпты/сервисы/DTO недели и месяца, фронт-герои и дневные плитки-образцы (`DaySignalsGrid`/`DayBlockers`), API-типы. Три параллельных Explore-агента добыли мапперы источников: `InsightsService.toListItem`, `IdeasService.toClusterDto`, отсутствие crutch-порога трений в дне, ключ `raw_char_budget` дня.
- **8 фаз, максимум безопасного параллелизма** (граф зависимостей + one-writer на файл):
  - Ф1∥Ф2 (письма недели/месяца — разные файлы) → Ф3 (сигналы недели, backend) ∥ Ф5 (фронт недели) → Ф4 (сигналы месяца) ∥ Ф6 (фронт месяца) → Ф7 (clamp, backend) ∥ Ф8 (canvas+виджеты, фронт).
  - Backend-фазы, делящие `weekly-digest.service.ts`/`monthly-digest.service.ts`, шли строго последовательно; фронт-фазы параллелились с backend (разные слои, согласованные имена полей: `risksByCause`/`ideaClusters`/`teamFrictions`/`blockers`).
- **Ключевое инженерное решение — helper `collectWindowSignals`** (`operations/services/window-signals.ts`): один чистый модуль собирает 4 формы сигналов за окно в точных фронт-shape (мапперы клонированы из insights/ideas-сервисов; трения/блокеры — через `OperationsDashboardService`, которому добавлены окно `to`/`window`). Переиспользован недельным И месячным сервисом (DI OperationsDashboardService — оба уже провайдеры одного OperationsModule, в модуль ничего добавлять не пришлось).
- **Приёмка каждой фазы сам** (не по отчёту агента): грепы маркеров → re-Read критичной логики → targeted `tsc` → vitest затронутого модуля. Финал: 537 тестов `src/modules/operations` зелёные, backend build (`tsc -p tsconfig.build.json`) EXIT=0, фронт typecheck/lint/build зелёные. Коммит по фазам явными путями.

## Что вышло

- **Реализовано целиком, все 8 фаз.** Коммиты: Ф1 `f363df0f`, Ф2 `0191c211`, Ф3 `675ee57c`, Ф5 `f493b127`, Ф4 `a7443e1b`, Ф6 `b7de394e`, Ф8 `ac680c2d`, Ф7 `1386e514`.
- Письма `week-company-v2`/`month-company-v2` — 12 COO-секций, имена, петля с прошлым периодом, взгляд COO; строгая zod (`z.enum` ключей отклоняет `decisions` и любой невалидный ключ). Недельный синтез читает полные дневные `letterJson` (бюджет символов — крутилка `operations.weekly_digest.raw_char_budget`=60000).
- Сигналы окна снапшочены в `metricsJson` недели/месяца (0 колонок БД, 0 миграций). Плитки фронта рендерятся из дайджеста за смотримый период — навигация в прошлый период показывает его снимок, а не «топ сейчас».
- `decisions`→`ownerForks` сквозняком (промпт/схема/zod/сервис/DTO/фронт); UI «Развилки месяца» (иконка GitFork). `MonthDecisions.tsx` удалён → `MonthForks.tsx`.
- Ось «Команда» краснеет: `computeTeamFrictionClamp` (≥1 трение выше порога уверенности → warn, ≥ порога повторяемости → risk, эскалирует overall). Пороги — крутилки `operations.digest.team_friction_{min_confidence=0.7,repeat_count=2}`.
- Canvas-дубль скрыт для owner на неделе И месяце; 5 month-only виджетов (month-recap/achievements/weekly-dynamics/maturity/bus-factor) перенесены в секцию «Итоги месяца» героя — не-owner видит canvas как раньше.
- 3 новые крутилки AdminSetting (сид `seed-admin-setting-week-month-v2.ts`, в STEPS `seed-base`); новых feature-флагов и ENV нет (Ship-On, code-fallback).

## Что реконсилировал / открытые нюансы

- **ТЗ Ф7 предполагало «существующий порог трений» — его нет.** В дне clamp по трениям отсутствует. Ввёл минимально по правилу проекта (порог = AdminSetting): 2 крутилки в реестре+сиде. Это единственное отклонение от буквы ТЗ, config-compliant.
- **Косметика (не блокер):** `Week/MonthBlockers` считают «N-й день» блокера от `createdAt` до `now` (форк дневного компонента, Б2) — для навигации в прошлый период число дней растёт к «сейчас», а не к концу окна. Приемлемо для снапшота; отдельного ТЗ не заводил.
- Старые дайджесты недели/месяца до перегенерации покажут пустые плитки (empty-state) и пустые «Развилки» — допустимо (прод ~4 юзера, Ship-On перегенерирует).

## Чему научился

- **При многофазной оркестрации максимум ускорения даёт параллелизм по слоям, а не по фичам:** фронт-фаза (Ф5/Ф6/Ф8) безопасно идёт параллельно со своей backend-фазой, если жёстко зафиксировать имена контрактных полей в промптах ОБОИХ кодеров — тогда фронт билдится независимо (`?? []`-guards), а сверка контракта — на финальной приёмке. One-writer соблюдать только на реально общих файлах.
- **`collectWindowSignals` как единый чистый helper окупился дважды:** неделя и месяц получили идентичный сбор + `computeTeamFrictionClamp` без дублирования; тестируется точечно, DI не разрастается (переиспользован уже-провайдер `OperationsDashboardService`).
- **Локальный `bun run build` OOM'ит на 8GB heap — проверять DI через `NODE_OPTIONS=--max-old-space-size=8192 bun run build` (= `tsc -p tsconfig.build.json`), а не гонять полный `bun run build` по дефолту.**
