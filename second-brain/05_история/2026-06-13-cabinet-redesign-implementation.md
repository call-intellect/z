# 2026-06-13 — Реализация редизайна кабинета (Ф0–Ф10, ритмы + очередь решений)

## Что было поставлено
Реализовать ТЗ [`plans/tz/2026-06-13-cabinet-redesign-rhythms-and-decision-queue.md`](../../plans/tz/2026-06-13-cabinet-redesign-rhythms-and-decision-queue.md) целиком — все фазы Ф0–Ф10. Цель из аудита `2026-06-12`: перестроить кабинет от «свалки 30 пунктов меню и противоречащих дашбордов» к модели **ритмов** (Сегодня / Неделя / Месяц) + сквозной **очереди решений** «Требует вас», с современным визуалом и светлой темой. Ветка `feature/cabinet-redesign-rhythms`.

## Как решал
Оркестрация фаза-за-фазой силами суб-агентов по схеме **картография кода → точные промпты кодеру → независимая приёмка (re-Read + грепы маркеров + свой typecheck/lint/build/тесты) → коммит по фазе**. 23 коммита на ветке. Порядок Ф0 (каркас навигации) → Ф1 (Сегодня) → Ф4 (очередь решений) → Ф2 (Неделя) → Ф7б → Ф3 (Месяц) → Ф5 → Ф6 → Ф7а → Ф8.5 → Ф8.6 (Лента Коры) → Ф8.2/8.1 → Ф10 (светлая тема).

Ключевые решения по реализации:
- **Единый источник навигации** `frontend/src/ui/components/app-shell/nav-config.ts` — одна карта меню для десктопа и мобилки (раньше дрейфовали два списка). Новое меню: 3 ритма + Работа + Я + Система (роль-зависимо), CTA «+ Создать». Старые дашборды и битые cron deep-link → `redirects` в `next.config.mjs`.
- **Плейсхолдеры для атомарного выката** — `/week`, `/month`, `/memory` сначала вышли заглушками (Ф0), наполнялись в последующих фазах. Это дало безопасный порядок: меню и роутинг уже работают, разделы доезжают по одному.
- **Гейт полноты обещаний — предикатом, без реклассификации** (Ф7б): не вводить новый статус, а считать «полнота» производным предикатом поверх существующих обещаний; `/me/promises` разделён на `items` / `openQuestions`. Не ломает экстракцию и не плодит новых сущностей.
- **Лента Коры — гибрид Р10** (Ф8.6): `GET /feed/cora` поверх уже построенного движка ActivityFeed (наполнили недостающие типы + open_question-детектор), `POST /feed/cora/seen` + курсор прочтения (миграция `feed_read_cursor`), `GET /probe/control` для «ответил / молчит». Фича = вьюха поверх готовых данных (`Notification.responseStatus`/`status=read`), не стройка с нуля.
- **Светлая тема через CSS-переменные + калибровка контраста** (Ф10): тема-зависимые поверхности в `tokens.css` / `modern.css` / `tokens.ts`, переключатель уже существовал. Контраст калибровали по правилу «не светлое-на-светлом».
- **Очередь решений** (Ф4): суть + detail в pending-actions, сквозной `POST /pending-actions/confirm`, миграция `add_expiresat_conflict_intake` (TTL `expiresAt` на `ConflictItem`/`IntakeIssue`) + sweep-крон; фронт — 4 группы с inline-резолвом.
- **Авто-название встреч** (Ф5): новый taskType LLM `meeting-title`; `POST /meetings/:id/next-steps/to-intake`; поиск по памяти `/memory` поверх `/knowledge/search`.
- **Silence-детектор тем** (Ф8.2/8.1): новый `@Cron('theme-silence-detector')` (тема молчит ≥N недель → Insight) за kill-switch `dashboard.theme_silence.enabled` (ON) + крутилка `dashboard.theme_silence_weeks` (default 3); детерминированный decision auto-implement (по задачам/outcomes).

## Что вышло
23 коммита на `feature/cabinet-redesign-rhythms`; typecheck / build / тесты зелёные по фазам (приёмка после каждой). Новые эндпоинты, 2 миграции Prisma, новая зависимость `pptxgenjs@^4.0.1` (PPTX-экспорт Месяца), новый taskType `meeting-title`, новый cron, новый kill-switch + 3 крутилки. Прод-операции при выкате — см. [`docs/operations/prod-deploy-log.md`](../../docs/operations/prod-deploy-log.md) (блок «Накоплено к выкату»).

## Чему научился
- **`modern/tokens.ts` хардкодил тёмное** — это и был корень проблемы контраста в светлой теме. Токены-значения для поверхностей нельзя задавать одним (тёмным) набором: они должны быть тема-зависимыми, иначе светлая тема даёт «светлое-на-светлом». Калибровать контраст обязательно глазами/скриншотом, а не «значения выглядят правильными».
- **Новый taskType без сид-роута = DEFAULT-цепочка.** `meeting-title` добавлен в реестр (`ALL_LLM_TASK_TYPES`), но отдельного `LlmTaskRoute` под него не сидим — он ходит по DEFAULT-цепочке. Прод-действий не требует; это осознанный выбор (дешёвая вспомогательная задача).
- **Связи Task↔Cycle в схеме нет** — при работе над планом-фактом и спринтами выяснилось, что прямой связи задачи с циклом нет; это влияет на то, какой остаток можно закрыть без миграции (петля `sourceBlockIds` + `DecisionTaskLink` требует новой миграции `IntakeIssue.sourceBlockIds`).
- **goalVector уже author-based** — нота в ТЗ о том, что вектор целей «меряет recipient, не author», устарела: на текущем коде он уже считается по автору. Перед опорой на ТЗ-ноты сверять с кодом — ТЗ писалось до части фиксов на dev.
- Подтвердился паттерн **«движок есть, продюсеры — нет»** (см. [[2026-06-13-cabinet-redesign-tz-prototypes-stash-recovery]]): Лента Коры строилась как наполнение недостающих типов готового ActivityFeed, а не новый движок.
