# ТЗ. Inline-создание проекта в «Выборе проекта» + калибровка авто-триажа входящих

## Что делаем (коротко)

Во «Входящих» (Intake — инбокс трекера) при нажатии «Принять» на входящей, у которой не определён проект, открывается модалка **«Выбор проекта»**. Сейчас в ней можно только **выбрать** существующий проект (поиск + список + «Отмена»). Создать новый проект прямо отсюда нельзя — пользователь вынужден прервать разбор входящих, уйти в раздел проектов, создать проект и вернуться.

Добавляем:
- **Фаза 1 (фронт):** кнопку **«+ Создать проект»** прямо в модалке «Выбор проекта» с мини-формой (имя проекта; `identifier` (буквенный префикс задач) и `slug` автогенерируются из имени). После создания — сразу выбираем новый проект и продолжаем accept без перезахода.
- **Фаза 2 (бэк, по необходимости):** серверная автогенерация `identifier`, чтобы фронт не был обязан её придумывать и не падал на коллизиях.
- **Фаза 3 (калибровка):** поднять долю входящих, у которых авто-триаж сам определил проект (`suggestedProjectIdentifier`), не переписывая весь промпт воркера (он правится в параллельной ветке).

Английские термины: **intake** — входящая задача до разбора; **triage** — разбор входящей (принять / отклонить / отложить / дубликат); **identifier** — короткий буквенный префикс задач проекта (например `KORA`, задачи получают вид `KORA-123`); **slug** — латинская строка-адрес проекта, уникальная в рамках организации.

### Бэк

То есть **создавать проект может тот же, кто и так принимает входящие** (admin/owner). Дополнительной развилки по ролям не требуется (см. развилку Р2).

Создание делает в транзакции: проект + 4 дефолтных `IssueState` + `ProjectMember(admin)` + дефолтную доску.
- Триаж: `IntakeService.triage` — `intake.service.ts:220-365`. Для `accept` цель проекта = `dto.targetProjectId ?? intake.projectId ?? intake.suggestedProjectId ?? null` (`:241-245`); если `null` → `400 target_project_required` (`:246-254`). Создание `Issue` — `issues.create(targetProjectId, …)` (`:263`).
- Авто-триаж: `IntakeAutoTriageWorker` — `intake-auto-triage.worker.ts`. LLM (`taskType='intake-auto-triage'`) возвращает `suggestedProjectIdentifier` (`:40-44`, `:72-73`). Контекст проектов грузится `take:40`, `select {id, identifier, name}`, `orderBy updatedAt desc` (`:194-200`) и подаётся в user-сообщение строками `  - {identifier}: {name}` (`:531-537`). Маппинг hint→id — `resolveProjectId` (`:587-600`): матч **только по точному `identifier`** (`p.identifier.toLowerCase() === norm`), иначе fallback на `intake.suggestedProjectId`. Описание проекта модели НЕ подаётся.
- Метрика уже есть: `ai_intake_suggested_total{tenant_top,status}` со статусами `auto_accepted | pending | llm_error | skipped_already_triaged` (`business-metrics.service.ts:3512`, `:7610`; вызовы в воркере `:186/:284/:348/:373`). Прямой метрики «доля входящих без определённого проекта» нет — `pending` агрегирует все недо-атрибуции (нет исполнителя, низкий confidence и т.п.), не только «проект не найден».

Фаза 3 этого ТЗ **не переписывает `INTAKE_AUTO_TRIAGE_SYSTEM` целиком** — только точечные правки (контекст проектов + fuzzy-резолвер + метрика). Перед стартом Фазы 3 — `git fetch` и сверить актуальное состояние воркера, чтобы не наступить на параллельные правки.

## Решение по фазам

### Фаза 1 — Inline-создание проекта в `ProjectPickerDialog` `[ ]`
**Файл:** `frontend/app/(authenticated)/intake/IntakeClient.tsx` (компонент `ProjectPickerDialog`, `:690-776`).
**Переиспользуем:** `projectsApi.create` (`projects.api.ts:125`), `useProjects().mutate` (ревалидация списка), `toast` (sonner), существующие UI-примитивы (`Button`, `Input`, `Dialog*`).

**Что входит:**
1. В футер/тело модалки добавить кнопку **«+ Создать проект»** (переключает модалку в режим мини-формы; список/поиск скрываются, или форма рендерится над списком — на усмотрение, главное один диалог без перезахода).
2. Мини-форма создания:
   - Поле **«Название проекта»** (`name`, обязательное, 1–200). Предзаполнять из `intakeDisplayTitle(item)`/`item.extractedTitle`? **Нет** — это название задачи, не проекта; поле пустое с подсказкой-плейсхолдером (например «Маркетинг», «Продажи»).
   - `identifier` и `slug` **не показываем как обязательные поля ввода**: генерируем на лету из `name`. Допустимо показать их в свёрнутом виде «Идентификатор: KORA» только для прозрачности (read-only превью), без принуждения пользователя их править. Кнопка accept не должна требовать от пользователя знать, что такое identifier.
   - Клиентская автогенерация (fallback, если Фаза 2 не делается): `identifier` = первые 3–5 заглавных латинских символов из транслитерации `name` (кириллица → латиница), очистка под `^[A-Z][A-Z0-9]*$`, длина 2–5; `slug` = транслит `name` в нижнем регистре под `^[a-z0-9-]+$` (пробелы → `-`, обрезка до 60). Если транслит дал пусто (например, имя из эмодзи) — fallback на `PRJ` / `proj-<короткий-рандом>`.
3. Submit: `projectsApi.create(orgId, { name, identifier, slug })` → при успехе:
   - `await mutate()` списка проектов (чтобы новый проект появился, если пользователь вернётся к списку),
   - **сразу** `onSelect(created.id)` → продолжение accept (триаж создаст задачу в новом проекте), модалка закрывается.
4. UX-состояния (правило `frontend-rules` — loading/empty/error обязательны):
   - **loading:** кнопка submit в состоянии «Создаём…», поля disabled, нельзя закрыть двойным сабмитом.
   - **ошибка `409 project_slug_taken`:** не показывать сырой код. Если Фаза 2 не делается — на клиенте при 409 дослать суффикс к `slug` (`-2`, `-3`…) и повторить **один раз** автоматически; если и это не помогло — человекочитаемый тост «Проект с похожим адресом уже есть, измените название». Если Фаза 2 делается — этот кейс закрывает сервер.
   - **прочие ошибки** (нет подписки `RequireSubscription`, нет прав, сеть): тост с человекочитаемым текстом, форма остаётся открытой, данные не теряются.
5. Русский UI целиком (правило `admin_ui_russian_only`): «Создать проект», «Название проекта», «Создаём…», «Отмена», «Назад к списку». Английского текста для пользователя нет (служебное превью «Идентификатор» допустимо со значением латиницей — это и есть значение поля).
6. Кнопка/форма создания доступна только при `canTriage` (owner/admin) — она и так внутри пикера, который открывается только из доступного accept; явных доп. проверок прав на фронте не добавляем (бэк-RBAC — источник правды).

**Acceptance:**
- В модалке «Выбор проекта» есть кнопка «+ Создать проект»; по клику — мини-форма с одним обязательным полем «Название».
- Ввод названия → submit создаёт проект (`POST /projects`), модалка **не** закрывается на список, а сразу продолжает accept в новый проект; входящая принята, задача создана в новом проекте (проверяемо: в журнале проекта появилась задача с title из входящей).
- При коллизии адреса проект всё равно создаётся (авто-суффикс slug) либо пользователь видит понятный тост — сырого `project_slug_taken` пользователь не видит.
- Loading-состояние блокирует двойной сабмит; ошибки не роняют диалог и не теряют введённое название.
- Весь видимый пользователю текст — на русском.
- (Если есть RTL-инфраструктура) — мини-тест: рендер формы, сабмит вызывает `projectsApi.create` с непустыми `name/identifier/slug` и затем `onSelect(созданныйId)`.

### Фаза 2 — Серверная автогенерация `identifier` (опц., но рекомендуется) `[ ]`
**Файлы:** `backend/src/modules/tracker/dto/projects/create-project.dto.ts`, `backend/src/modules/tracker/services/projects.service.ts`.
**Зачем:** убрать с фронта ответственность за корректную генерацию `identifier`/`slug` (правила `^[A-Z][A-Z0-9]*$`, транслит кириллицы, длина) и устранить хрупкость клиентских ретраев. Сервер — единственный, кто знает текущие проекты тенанта и может гарантировать пригодные значения.

**Что входит:**
1. Сделать `identifier` и `slug` в `CreateProjectSchema` **опциональными**. Если фронт прислал — валидируются как сейчас. Если не прислал — сервер генерирует из `name`.
2. В `ProjectsService.create` (или в выделенном чистом хелпере, легко юнит-тестируемом) при отсутствии `identifier`/`slug`:
   - `slug`: транслит `name` → нижний регистр, `[^a-z0-9]+` → `-`, обрезка концевых дефисов, длина 2–60; если занят (`tenantId_slug`) — добавлять числовой суффикс `-2`, `-3`… до свободного.
   - `identifier`: первые буквы транслита `name`, заглавные, 2–5 символов, под `^[A-Z][A-Z0-9]*$`. `identifier` в БД **не уникален** (см. «как сейчас»), коллизия допустима — но желательно (best-effort) избегать точного дубля среди существующих проектов тенанта, добавляя цифру (`MARK` → `MARK2`), т.к. совпадающие identifier ухудшают авто-триаж (две строки `MARK: …` в контексте LLM). Это soft-уникальность, не констрейнт.
   - На вырожденном `name` (нет латинизируемых символов) — fallback `PRJ` + slug `proj-<rand>`.
3. Уникальность `slug` гарантировать **внутри транзакции/повторной проверки**, а не только клиентским ретраем; сохранить текущую явную `409 project_slug_taken` для случая, когда `slug` пришёл явно от клиента и занят.
4. **Без новой миграции БД** — поля и констрейнты не меняются (identifier остаётся неуникальным, slug уже уникален). Меняется только DTO (часть полей становится опциональной) и сервисная логика.

**Acceptance:**
- `POST /projects` с телом `{ name: "Маркетинг" }` (без `identifier`/`slug`) создаёт проект с валидными автогенерированными `identifier` (заглавные латинские, 2–5) и уникальным `slug`.
- Повторный `POST /projects` с тем же `name` создаёт второй проект с другим `slug` (суффикс) — без 409.
- Явный `slug`, который уже занят, по-прежнему даёт `409 project_slug_taken`.
- Юнит-тесты на хелпер генерации: кириллица→латиница, спецсимволы, пустой/эмодзи-`name`, коллизия slug→суффикс.
- Если Фаза 2 делается — Фаза 1 шлёт только `{ name }` и не генерирует identifier/slug на клиенте (упрощение фронта); авто-суффикс-ретрай 409 из Фазы 1 убирается как ненужный.

### Фаза 3 — Калибровка матчинга проекта в авто-триаже `[ ]`
**Файл:** `backend/src/modules/tracker/workers/intake-auto-triage.worker.ts` (точечно: `buildUserMessage`, контекст-запрос проектов, `resolveProjectId`, метрика). **Не трогаем `INTAKE_AUTO_TRIAGE_SYSTEM` целиком** — координируем с параллельной веткой.
**Цель:** поднять долю входящих, для которых авто-триаж сам определил проект, и снизить долю попадающих в ручной «Выбор проекта».

**Что входит:**
1. **Подавать модели описание проекта.** В контекст-запрос проектов (`:194-200`) добавить `description: true`; в `buildUserMessage` (`:531-537`) выводить `  - {identifier}: {name} — {краткое описание (обрезка ~120 симв.)}`. Это даёт LLM семантику проекта, а не только аббревиатуру (которую по короткому тексту входящей угадать сложно). `select` и обрезку держать дешёвыми — описание уже грузится одной выборкой.
2. **Fuzzy-match по имени, не только по точному identifier.** Расширить `resolveProjectId` (`:587-600`): если точного совпадения по `identifier` нет, пробовать
   - совпадение по `name` (case-insensitive, точное),
   - затем — однозначный (ровно один результат) подстрочный матч `hint` ⊂ `name` или `name` ⊂ `hint`,
   - при ≥2 кандидатах — **не угадывать** (вернуть fallback), чтобы не атрибутировать в неверный проект.
   Чистая функция — расширить юнит-покрытие (точный identifier / точное имя / однозначный подстрочный / неоднозначный → fallback).
   > Совместимость с prompt caching: добавление `description` меняет **переменную** часть user-сообщения (в конце), SYSTEM не трогаем — кэш не ломается (правило `llm_prompts_cache_friendly`).
3. **Метрика наблюдаемости «доля входящих без определённого проекта».** Текущий `ai_intake_suggested_total{status}` смешивает причины. Добавить **узкий** сигнал, чтобы видеть именно проектную атрибуцию. Рекомендация: новый label-вариант или отдельный счётчик `ai_intake_project_resolved_total{tenant_top, resolved}` (`resolved = 'true' | 'false'`), инкремент после `resolveProjectId` в `process` (до решения об auto-accept). Это даёт прямую метрику «доля `false`» = доля входящих, попадающих в ручной «Выбор проекта». Регистрация метрики — `business-metrics.service.ts` (рядом с `ai_intake_suggested_total`, см. `:3512`).
   > Новый счётчик метрики → добавить запись в `prod-deploy-log.md` Шаг 12 (smoke `/metrics` grep) и обновить `second-brain/01_projects/tracker.md:262` (список метрик трекера).

**Acceptance:**
- В user-сообщении LLM проекты идут с описанием (проверяемо юнит-тестом на `buildUserMessage`).
- `resolveProjectId` матчит проект по точному имени и по однозначному подстрочному совпадению; при неоднозначности возвращает fallback (не угадывает). Юнит-тесты на каждый путь.
- `/metrics` отдаёт `ai_intake_project_resolved_total` с метками `resolved=true/false`; на проде по этому счётчику видно долю входящих без проекта.
- `INTAKE_AUTO_TRIAGE_SYSTEM` (SYSTEM-промпт) не изменён — кэш промпта сохранён, конфликт с параллельной веткой минимизирован.

## Развилки владельца

| # | Вопрос | Варианты | Рекомендация |
|---|---|---|---|
| Р1 | Как обрабатывать «непонятный» проект: давать создавать новый (вариант A) или класть всё неопределённое в один системный «проект-инбокс» по умолчанию (вариант B)? | **A** — inline-создание проекта (это ТЗ). **C** — серверная автогенерация identifier (Фаза 2). **B** — единый дефолтный проект-инбокс, куда падают все входящие без проекта; пользователь не создаёт проект, а потом раскидывает задачи. | **A+C.** Вариант B плодит «свалку»: все задачи из разных направлений в одном контейнере, теряется смысл проектов как направлений работы, и авто-триаж перестаёт учиться различать проекты (всё валится в один). A+C даёт пользователю завести правильное направление за один клик, не выходя из разбора, и сохраняет сигнал для калибровки (Фаза 3). B можно оставить как будущий «быстрый режим», но не вместо A. ## Прод-операции

- **Миграций БД нет.** Схема `Project` не меняется (identifier остаётся неуникальным, slug уже уникален). Фаза 2 меняет только `CreateProjectSchema` (часть полей → опциональные) и сервисную логику.
- **Фаза 3** добавляет новый счётчик метрики `ai_intake_project_resolved_total` → запись в `docs/operations/prod-deploy-log.md` Шаг 12 (smoke `/metrics` grep) + строка в `second-brain/01_projects/tracker.md` (список метрик `:262`). ENV/флагов/seed/patch/backfill — нет.
- Выкат — обычный `docker compose up -d --build` (фронт+бэк). Отдельных команд на проде не требуется, кроме обновления prod-deploy-log по Фазе 3.
- **Координация веток:** перед мержем Фазы 3 — `git fetch` + сверка `intake-auto-triage.worker.ts` с параллельной веткой калибровки confidence (см. блок «Координация» выше).

## Что НЕ входит

- Полноценная страница/визард создания проекта (статусы, участники, шаблон команды) — из пикера создаётся «лёгкий» проект с дефолтами; донастройка — в разделе проектов.
- Выбор `identifier`/`slug` пользователем как обязательный шаг — намеренно скрыто (ЦА не разработчики).
- Уникальный constraint на `identifier` в БД (миграция) — не вводим; soft-уникальность best-effort в Фазе 2 достаточно для качества авто-триажа.
- Переписывание `INTAKE_AUTO_TRIAGE_SYSTEM` / общая калибровка confidence / auto-accept-порога — это зона параллельной ветки, здесь только матчинг проекта.
- Вариант B (единый проект-инбокс по умолчанию) — отклонён в Р1, не реализуется.
- Эмбеддинг-поиск проекта по семантике входящей (векторный матч) — возможное будущее улучшение Фазы 3, в этот объём не входит.

## Итог

Реализуемо тремя независимыми фазами. **Фаза 1** (фронт) самодостаточна и даёт основную ценность — создать проект, не выходя из разбора входящих. **Фаза 2** (бэк) делает создание надёжным и упрощает фронт (рекомендуется делать вместе с Ф1). **Фаза 3** (калибровка) — отдельный трек, координируемый с параллельной правкой воркера; поднимает долю авто-определённого проекта и добавляет прямую метрику наблюдения. Миграций БД нет; единственная прод-производная — регистрация новой метрики (Ф3) в prod-deploy-log и tracker.md.
