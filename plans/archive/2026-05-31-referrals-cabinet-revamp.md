# Партнёрский кабинет Коры — перестройка UX и расширение аналитики (первый запуск)

## 1. Контекст и зачем

Партнёрская программа Коры уже работает (см. `second-brain/03_processes/referral-program.md`): есть slug, beacon на 90 дней, attribution → ClientReferralLink → ReferralPayout, cron 10-го числа, кабинет и админка.

**Проблема UX (со слов пользователя 2026-05-31):**

1. Текущая страница `/referrals` сразу требует ИНН, форму ведения деятельности и реквизиты банка. Без всего этого партнёр **не может даже создать ссылку**. Это убивает виральность — человек пришёл «попробовать», а его заставили вводить реквизиты ещё до того, как он понял, что зарабатывает.
2. Нет маркетингового мотиватора. Текущий заголовок «Реферальная программа» и подзаголовок «Приведи клиента — получи 20 000 ₽ за каждый его paid-платёж» не показывают экономику в цифрах и используют английское слово `paid`.
3. Нет нормальной аналитики. Сейчас 4 цифры: всего клиентов, платящих, к выплате, выплачено. Нет: сколько кликнули по ссылке, сколько зарегистрировались, сколько НЕ купили, какой доход по месяцам, график.
4. Утечка приватности клиентов. `GET /referrals/me/clients` отдаёт `org.name` — партнёр видит названия компаний приведённых клиентов. Это даёт партнёру возможность увести клиента мимо Коры. Нужно скрыть.
5. Оферта оформлена как отдельный шаг с кнопкой «Принять оферту» в карточке профиля. По смыслу — это согласие при создании ссылки. Должна быть чекбоксом у кнопки «Создать ссылку».

**Цель этого ТЗ:**

Перестроить страницу так, чтобы **главное действие — получить ссылку и начать привлекать — было доступно за один клик**. Реквизиты и верификация ИНН — это отдельная задача «подготовиться к выводу денег», которая не блокирует основной поток.

Заодно — добавить нормальную аналитику, починить приватность, сменить тон копи на маркетинговый.

## 2. Принципы перестройки

1. **Ссылка — главное действие.** Создать её можно одним кликом, до заполнения чего-либо. Согласие с офертой — чекбокс у кнопки.
2. **Реквизиты — отдельная задача.** Не блокирует получение ссылки, не блокирует просмотр аналитики. Блокирует только вывод денег.
3. **Аналитика рассказывает воронку.** Партнёр должен видеть: сколько перешли по ссылке, сколько из них зарегистрировались, сколько заплатили, сколько активны. И сколько денег он на этом сделал.
4. **Приватность клиентов — без компромисса.** Партнёр никогда не видит названия и контакты компаний, которые он привёл.
5. **Никакого английского.** Платформа называется **Кора**. В копи нет слов `paid`, `lead`, `referral`. Только русские термины: «партнёр», «партнёрская программа», «партнёрская ссылка», «оплата клиента», «приведённый клиент».

## 4. Что НЕ входит в первый запуск (явно отложено)

- **Несколько ссылок с метками** (`Телеграм-канал`, `Инстаграм-сторис` и т.п.). Сейчас один партнёр — один slug. Менять модель не будем.
- **Сравнение ссылок side-by-side.** Следствие предыдущего пункта.
- **Лента событий** («новый клиент по ссылке X», «начисление 20 000 ₽», «клиент отписался»).
- **Уведомления партнёру** (e-mail или Телеграм-бот).
- **Экспорт в Excel.**
- **Автоматическая выплата** (через ЮKassa / Тинькофф API). Пока — финдиректор руками через банковский интерфейс (как сейчас).
- **Воронка как отдельный график** (горизонтальные столбики с переходами). На первом запуске воронка — просто блок 4 цифр.
- **Множественные тенанты у одного партнёра** (несколько юр.лиц на одного человека).
- **Настоящая бесплатная подписка** при 3+ активных приведённых клиентах (кросс-tenant credit / пересчёт `Subscription.monthlyPriceKopecks`). На первом запуске промо-баннер для руководителя формулирует это как «отбей подписку с запасом» (20k × 3 = 60k ₽/мес возврата), без изменения биллинга. Реальная льгота — отдельная фича, рассматриваем после первого запуска.
- **A/B-тесты текстов промо-баннера** (несколько вариантов на роль с рандомизацией). На первом запуске — один текст на роль.

Все эти пункты — кандидаты на следующие запуски. Сейчас задача — снять барьер входа и дать честные цифры.

## 5. Сущности — изменения

### 5.1. Модель `Referral` (изменения)

Цель — позволить создать `Referral` только со slug-ом, без всего остального.

```prisma
model Referral {
  id                 String    @id @default(cuid())
  ownerUserId        String    @unique
  owner              User      @relation(fields: [ownerUserId], references: [id], onDelete: Cascade)

  slug               String    @unique

  // ↓ БЫЛО required, СТАНОВИТСЯ optional
  inn                String?   @db.VarChar(20)
  innVerifiedAt      DateTime?
  legalForm          ReferralLegalForm?
  payoutDetails      Json?

  contractAcceptedAt DateTime?
  createdAt          DateTime  @default(now())
  updatedAt          DateTime  @updatedAt

  attributions       ReferralAttribution[]
  clientLinks        ClientReferralLink[]
  payouts            ReferralPayout[]
}
```

**Миграция:** `bun run prisma:push` (не `migrate`). Опциональность полей — обратно-совместимое изменение, существующие записи не теряют данных.

**Поведение `ReferralPayoutCron`:** не меняется. Условие выплаты — `innVerifiedAt && contractAcceptedAt`. Если они null — payout уходит в `void` с `voidReason='referral_not_verified'` как сейчас. Дополнительно стоит проверять `payoutDetails != null` (иначе фактическая выплата невозможна) — расширить условие в `closePeriod`.

### 5.2. Новых таблиц нет

На первом запуске агрегаты считаем на лету из существующих таблиц:

- **Клики** = `count(ReferralAttribution where referralId=X and createdAt in period)`
- **Регистрации** = `count(Org where pendingAttributionSlug=referral.slug and pendingAttributionAt in period)` + `count(ClientReferralLink where referralId=X and attachedAt in period)`. (Первое — те, кто привязался, но ещё не оплатил. Второе — те, кто уже стал клиентом.)
- **Первые оплаты** = `count(ClientReferralLink where referralId=X and firstPaidAt in period)`
- **Активные клиенты сейчас** = `count(ClientReferralLink where referralId=X and firstPaidAt != null and subscription.status='ACTIVE' and subscription.paymentMode='paid')`
- **Доход по месяцам** = `sum(ReferralPayout.amountKopecks group by periodMonth where status in ('paid','pending'))`

Если на второй итерации (или при росте) запросы станут медленными — введём `ReferralLinkDailyStats(slug, day, clicks, signups, paid_activations)` с ежедневным cron-агрегатором. Это **не сейчас**.

## 6. Бизнес-правила

### 6.1. Создание партнёрского профиля

- Любой авторизованный пользователь может одним кликом получить slug.
- Поля `inn`, `legalForm`, `payoutDetails` не обязательны на момент create.
- Принимая чекбокс оферты — мы фиксируем `contractAcceptedAt=now()`. Без чекбокса кнопка «Создать ссылку» disabled.
- Slug нельзя сменить (как и сейчас).

### 6.2. Создание ссылки без оферты — невозможно

Чекбокс оферты обязателен. Это снимает риск «случайно создал ссылку → не понимал условий». Текст: «Создавая ссылку, я принимаю условия [оферты партнёрской программы]». Ссылка ведёт на отдельную страницу с текстом оферты (адрес TBD, см. открытые вопросы).

### 6.3. Условия выплаты — без изменений

Cron 10-го числа переведёт `pending` payout в `paid` только если:
- `innVerifiedAt != null` (ИНН верифицирован через `InnLookupService`)
- `contractAcceptedAt != null` (оферта принята — теперь это есть всегда, т.к. чекбокс обязателен при создании ссылки)
- **(новое)** `payoutDetails != null && payoutDetails != {}` (есть куда переводить)

Если что-то из этого не выполнено — payout → `void`, `voidReason='referral_not_verified'` (имя оставляем для обратной совместимости).

### 6.4. Маскировка клиентов

`GET /referrals/me/clients` больше не возвращает:
- `org.name`
- `org.id` (всё, что позволяет идентифицировать конкретное юр.лицо)
- любые поля, через которые можно восстановить ИНН/email/телефон

Возвращает:
- `clientId` — анонимный, генерится один раз при создании `ClientReferralLink` (новое поле `displayCode String?` в схеме или просто `id` ссылки в base36 — обсудить, см. открытые вопросы).
- `attachedAt` — дата привязки.
- `firstPaidAt` — дата первой оплаты или `null`.
- `status` — `'active'` (платит сейчас) / `'churned'` (был активен, ушёл) / `'pending'` (привязан, ещё не платил).
- `monthlyEarningsKopecks` — сколько начисляется в этом месяце (`20_000_00` или `0`).
- `totalEarnedKopecks` — за всё время по этому клиенту.

### 6.5. Кнопка «Вывести»

Активна только если:
- `innVerifiedAt != null`
- `contractAcceptedAt != null`
- `payoutDetails != null && payoutDetails != {}`
- `totalPendingKopecks > 0` (есть что выводить)

Иначе — серая с тултипом, который показывает первую нерешённую причину:
- «Заполни реквизиты для вывода» (если `payoutDetails` пуст)
- «Проверь ИНН — кнопка в карточке Реквизиты» (если `innVerifiedAt == null`)
- «Пока нечего выводить» (если баланс 0)

### 6.6. Атрибуция — без изменений

Окно куки 90 дней, first-touch, beacon — всё остаётся как есть. Это не предмет текущего ТЗ.

## 7. Бэкенд — изменения

### 7.1. Prisma schema

См. §5.1: `inn / legalForm / payoutDetails` → optional.

После правки — `bun run prisma:push && bun run prisma:generate`.

### 7.2. `ReferralsService`

**`create()`** — принимает опциональные поля:
```ts
export interface CreateReferralInput {
  ownerUserId: string;
  contractAccepted: boolean;          // ← обязательный чекбокс
  inn?: string;
  legalForm?: ReferralLegalForm;
  payoutDetails?: Prisma.InputJsonValue;
}
```
- Бросает `BadRequestException` если `contractAccepted !== true`.
- Если `inn` задан без `legalForm` — `BadRequestException`. (И наоборот.)
- Записывает `contractAcceptedAt = now()`.
- Если `inn` задан — НЕ запускает автоматически verifyInn (это явное действие позже).

**`update()`** — без изменений по сигнатуре, но теперь корректно работает с null.

**`acceptContract()`** — оставляем для обратной совместимости (используется в текущем UI), но в новом флоу не нужен — оферта принимается при `create`.

**`listClients()`** — переписать. Возвращает анонимизированный DTO (см. 7.4).

**`getStats()`** — расширить:
```ts
{
  // ... существующие поля
  clicks30d: number;
  signups30d: number;
  firstPayments30d: number;
  conversionClickToPaidPercent: number;  // (firstPayments30d / clicks30d) * 100, округление до 0.1
  conversionSignupToPaidPercent: number;
}
```

### 7.3. Новые методы сервиса

**`getIncomeChart(referralId): Promise<MonthlyPoint[]>`**
```ts
interface MonthlyPoint {
  month: string;          // 'YYYY-MM'
  incomeRub: number;      // сумма payouts paid+pending за месяц
  activeClients: number;  // активных в конце месяца
}
```
Возвращает 12 точек: последние 12 месяцев включая текущий. Месяцы без данных — `{month, incomeRub: 0, activeClients: 0}`.

**`getFunnel(referralId, period: '30d'|'90d'|'all'): Promise<Funnel>`**
```ts
interface Funnel {
  period: '30d'|'90d'|'all';
  clicks: number;
  signups: number;
  firstPayments: number;
  activeNow: number;       // для 'all' — снимок; для периодов — на конец периода
  conversions: {
    clickToSignupPercent: number;
    signupToPaidPercent: number;
    clickToPaidPercent: number;
  };
}
```

### 7.4. Новые DTO

```ts
// listClients больше не возвращает org/subscription напрямую
export const ReferralClientMaskedSchema = z.object({

  status: z.enum(['active', 'churned', 'pending']),
  monthlyEarningsKopecks: z.number().int().nonnegative(),

export const ReferralStatsExtendedSchema = z.object({

  totalClients: z.number().int(),
  activePaying: z.number().int(),
  totalEarnedKopecks: z.number().int(),
  totalPaidKopecks: z.number().int(),
  totalPendingKopecks: z.number().int(),
  // new fields
  clicks30d: z.number().int(),
  signups30d: z.number().int(),
  firstPayments30d: z.number().int(),
  conversionClickToPaidPercent: z.number(),
  conversionSignupToPaidPercent: z.number(),
});

export const MonthlyPointSchema = z.object({
  month: z.string().regex(/^\d{4}-(0[1-9]|1[0-2])$/),
  incomeRub: z.number().int(),
  activeClients: z.number().int(),
});

export const FunnelSchema = z.object({
  period: z.enum(['30d', '90d', 'all']),
  clicks: z.number().int(),
  signups: z.number().int(),
  firstPayments: z.number().int(),
  activeNow: z.number().int(),
  conversions: z.object({
    clickToSignupPercent: z.number(),
    signupToPaidPercent: z.number(),
    clickToPaidPercent: z.number(),

});
```

`clientCode` — генерим как `'C' + base36(crc32(ClientReferralLink.id))` без сохранения в БД. Идемпотентно для одной и той же ссылки, длина ~7 символов, не раскрывает порядковый номер.

### 7.5. Новые эндпоинты

```
GET  /api/v1/referrals/me/income-chart       → MonthlyPoint[]  (12 точек)
GET  /api/v1/referrals/me/funnel?period=30d  → Funnel
```

Существующие `GET /referrals/me/stats` и `GET /referrals/me/clients` — меняют форму ответа (расширяются / маскируются). Это **breaking change** для фронта, но он переписывается в этом же ТЗ.

### 7.6. Изменение `POST /referrals/me`

Body теперь принимает `contractAccepted: boolean` (required) + остальные поля optional:

```ts
export const CreateReferralBodySchema = z.object({
  contractAccepted: z.literal(true),
  inn: InnSchema.optional(),
  legalForm: LegalFormSchema.optional(),
  payoutDetails: z.record(z.string(), z.unknown()).optional(),
});
```

Если `contractAccepted !== true` — Zod валидация падает (это и есть наш гард).

### 7.7. Изменение `ReferralPayoutService.closePeriod`

Добавить проверку `payoutDetails != null && payoutDetails !== {}` в условие верификации (см. 6.3). Конкретно:

```ts
const hasPayoutDetails =
  payout.referral.payoutDetails != null &&
  typeof payout.referral.payoutDetails === 'object' &&
  Object.keys(payout.referral.payoutDetails as Record<string, unknown>).length > 0;
const verified =
  payout.referral.innVerifiedAt &&
  payout.referral.contractAcceptedAt &&
  hasPayoutDetails;
```

## 8. Frontend — изменения

### 8.1. Полная переделка `ReferralsClient.tsx`

Три явных состояния:

**Состояние A: профиля нет** (`referral === null`)
Показываем:
1. Маркетинговый герой-блок (текст в §9).
2. Карточка «Получи ссылку прямо сейчас»:
   - Кнопка «Создать ссылку» (disabled пока не отмечен чекбокс).
   - Чекбокс: «Создаю ссылку → соглашаюсь с условиями [оферты партнёрской программы]».
   - Мелким под кнопкой: «Реквизиты для вывода заполнишь, когда захочешь получить деньги.»
3. Под карточкой — те же три плитки маркетинга (5 клиентов = 100 000 ₽ и т.д.), как декорация воронки воображения.

**Состояние B: профиль есть, ссылка свежая** (`referral != null && stats.clicks30d === 0`)

Показываем:
1. Верхние три плитки: «Активных клиентов: 0», «Доход в этом месяце: 0 ₽», «К выводу: 0 ₽» + кнопка «Вывести» (серая, тултип).
2. Карточка «Твоя ссылка»: URL, кнопка «Копировать», QR-код (используем существующий компонент — TBD, если нет, библиотека `qrcode.react`).
3. Состояние «ещё нет данных»: «Поделись ссылкой — здесь появятся клики, регистрации и оплаты».
4. Карточка «Реквизиты для вывода»: статус-бейдж «Не заполнены — вывод недоступен», свёрнутая форма с кнопкой «Заполнить».

**Состояние C: профиль активен** (`stats.clicks30d > 0`)

Показываем всё из B плюс:
- Карточка «Воронка за 30 дней»: 4 цифры — Кликов / Регистраций / Первых оплат / Активных сейчас. Под каждой — процент конверсии от предыдущей.
- График дохода и активных клиентов за 12 месяцев (компонент `IncomeChart` на `recharts` — он уже в зависимостях фронта, см. `frontend/node_modules/recharts`).
- Карточка «Приведённые клиенты»: таблица с замаскированными строками (см. §6.4).

### 8.2. Карточка «Реквизиты для вывода» — отдельный компонент

Поля: ИНН (10/12 цифр), форма (самозанятый/ИП/юрлицо), название банка, номер счёта.

Поведение:

### 8.3a. Промо-полоса `ReferralPromoStrip` (новое — §3 п.11)

**Зачем.** Партнёрская программа существует, но про неё никто не знает, потому что страница `/referrals` лежит в меню и пользователь туда не заходит, пока ему не подскажешь. Нужен постоянный мягкий призыв, который виден на тех страницах, где человек что-то решает (дашборд, ленты, списки), и **не лезет туда, где он сфокусирован** (формы, мастера, чат, страница встречи).

**Где живёт в DOM.** Новый компонент `<ReferralPromoStrip />`, монтируется в `AppShell.tsx` сразу под `<PaywallBanner />`. Это уже работающий паттерн «узкая горизонтальная полоса сверху main».

**Почему не floating-карточка справа.** Правый нижний угол занят: `ConciergeFloatingButton` + `AssistantSidebar` (FAB-кнопка ленты «Срочное / Уточнения от Коры»). Третий элемент в том же углу — визуальный мусор и конфликт смысла («что важнее: ассистент, концерн или промо?»). Полоса сверху — компромисс: видна, но не отвлекает.

**Внешний вид.**
- Высота ~40–48 px, лёгкий тёплый фон (`bg-emerald-50` или брендовый `bg-brand-soft`, выбрать в Tailwind-конфиге через парный токен `bg-{color} + text-{color}-fg` — см. memory `paired-color-tokens`).
- Слева: иконка-эмодзи (🎁 для руководителя, 💼 для сотрудника) + текст в одну строку.
- Справа: кнопка-ссылка «Получить ссылку →» + крестик «×» (dismiss).
- На мобильных (≤640 px): текст становится компактнее, кнопка превращается в «→», крестик остаётся.

**Что видит руководитель (`orgRole === 'owner'`).**

> 🎁 **Пригласи 3 руководителя в Кору — отбей свою подписку с запасом.** 20 000 ₽ × 3 = 60 000 ₽ в месяц возвращается тебе. → Получить ссылку

Формулировка «отбей подписку» вместо «пользуйся бесплатно» — потому что **реальная льгота «бесплатная подписка при 3 клиентах» — это новая механика в биллинге** (кросс-tenant credit, пересчёт подписки), её в этом ТЗ нет (см. §4 «Что НЕ входит» — мы туда добавим явный пункт). 60 000 ₽/мес с лихвой покрывают подписку Коры (текущая цена — обсуждается, но даже верхний тариф не >60k) — это честно и без новой инфраструктуры. Если решим вводить настоящую льготу позже — переформулируем в «пользуйся бесплатно».

**Что видит сотрудник (`orgRole ∈ {admin, manager, coo, hr_partner}` или нет роли).**

> 💼 **Расскажи о Коре в другой компании — заработай 20 000 ₽/мес с каждого активного клиента.** → Получить ссылку

Никаких «отбей подписку» — это не сотрудник её платит. Только про личный доход.

**Где показывается (белый список).**
- `/` (главная, дашборд)
- `/dashboard`
- `/activity-feed`
- `/goals`, `/clones`, `/persons`, `/entities`, `/themes`, `/insights` (списки)
- `/meetings` (список встреч)
- `/tracker` (если рабочая поверхность)

**Где НЕ показывается (явные исключения).**
- `/referrals` (уже в кабинете — баннер бы избыточен)
- `/admin/**` (super_admin-контекст, не его аудитория)
- `/onboarding/**` (не отвлекаем нового пользователя)
- `/login`, `/signup` (public, не authenticated)
- `/meetings/create`, `/meetings/[id]/result`, `/chat/**`, `/clones/[id]` (страницы с фокусом — встреча, чат, диалог с клоном)
- Любой `/settings/**` (настройки — фокус)
- На любой странице с modal'ом / wizard'ом — там и так не до промо

Алгоритм решения: **белый список префиксов**. Если префикс маршрута не в белом списке — баннер не рисуем. Это безопаснее чёрного списка (новые страницы добавляются как «по умолчанию без промо», осознанно включаем).

**Когда автоматически скрывается.**

1. **У пользователя уже есть Referral-профиль** (партнёрская ссылка создана, даже если ИНН ещё не введён). Логика: после создания ссылки пользователь уже в воронке, баннер ему не нужен. Проверка: `referralsApi.getMe()` отдал не-null → баннер не рендерим. Кэшируем в `localStorage` на 24 часа, чтобы не дёргать API на каждой странице.
2. **Пользователь нажал «×» (dismiss).** В `localStorage` пишем `z.referralPromo.dismissedAt = ISO-timestamp`, скрываем на 30 дней. После — снова появляется (мягкое напоминание).
3. **Tenant в paywall-режиме** (подписка просрочена). На таких страницах уже висит `PaywallBanner` — не дублируем шум.

**Поведение по клику.**

- Клик на «Получить ссылку» → `router.push('/referrals')`. На странице кабинета — состояние A («профиля нет») с уже отмеченным чекбоксом оферты? **Нет**, чекбокс должен быть отмечен пользователем явно — это юридическое согласие. Просто переход.
- Клик на крестик → dismiss + скрываем без перехода.

**Метрики (Prometheus).**
- `referral_promo_impression_total{role="owner"|"member"}` — инкремент один раз за сессию (а не на каждый ререндер), при первом показе.
- `referral_promo_click_total{role}` — клик по «Получить ссылку».
- `referral_promo_dismissed_total{role}` — клик по «×».

На бэкенде это новый endpoint `POST /api/v1/referrals/me/promo-event` с body `{type: 'impression'|'click'|'dismissed', role: 'owner'|'member'}`, который только инкрементит метрики. Throttle 30/min/IP (защита от шума с одного клиента).

**Тексты, варианты на A/B на втором запуске.** Сейчас — две константы (руководитель / сотрудник). В будущем можно ввести 2–3 варианта на роль, рандомизировать и смотреть конверсию. На первом запуске **не делаем** — один текст, прямой.

### 8.3. Кнопка «Вывести»

Компонент `WithdrawButton`. Проверяет в порядке: `payoutDetails empty → 'Заполни реквизиты для вывода'`, `innVerifiedAt null → 'Проверь ИНН в разделе Реквизиты'`, `balance === 0 → 'Пока нечего выводить'`. Если всё ок — кнопка активна, по клику открывает диалог подтверждения.

На первом запуске «Вывести» **создаёт обращение в админку** (запись в существующей таблице `ReferralPayout` ничего нового не нужно — у партнёра уже есть pending payouts, кнопка «Вывести» — это просьба «обработайте мои pending payouts вне cron-расписания»). Может быть достаточно текста-инструкции: «Деньги выплачиваются автоматически 10-го числа каждого месяца. Хочешь раньше — напиши в поддержку.»

Решение между «нужен запрос на досрочный вывод» и «просто инструкция» — см. открытые вопросы.

## 14. Метрика успеха

Через 30 дней после выкатывания первого запуска:
- **CR-1** (Создание ссылки): % пользователей, открывших `/referrals` и нажавших «Создать ссылку», должен вырасти **≥ в 3 раза** по сравнению с текущей формой (текущая — обязательное заполнение всего сразу).
- **CR-2** (Первая активность): % партнёров, у которых хотя бы 1 клик в первые 7 дней после создания ссылки, должен быть **≥ 30%**.
- **CR-3** (Промо → кабинет): % пользователей, увидевших `ReferralPromoStrip` и кликнувших «Получить ссылку», — **≥ 5%** для роли owner, **≥ 2%** для member (учитывая dismiss и автоскрытие у тех, кто уже партнёр). Это базовый ориентир, ждать накопления статистики 14 дней.
- **CR-4** (Промо → создание ссылки): % пользователей, кликнувших по баннеру и создавших ссылку в течение 24 часов, — **≥ 40%** (если меньше — кабинет всё ещё страшный, надо смотреть, где они отваливаются).
- **Жалобы партнёров** на блокирующий вход — **0**.
- **Жалобы пользователей на навязчивость промо-баннера** — **0**. Если приходят — переходим на «показывать раз в день» или ужесточаем белый список.

Если CR-1 не вырос или CR-2 < 10% — UX герой-блока надо переписать (текст не цепляет) или поменять структуру (например, добавить онбординг-туториал). Если CR-3 < 1% для обеих ролей — переписать текст промо-баннера.
