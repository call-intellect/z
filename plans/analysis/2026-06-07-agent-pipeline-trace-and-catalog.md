## 4. Находки и сверка по коду

### №1 — Vox вернул текст, но 0 пословных таймингов (⚠ деградация, не баг)
- **Факт:** `vox.no_words` — модель `v3_e2e_rnnt` отдала 437 символов текста, но ни одного word-timing.
- **Сверка по коду** ([vox.service.ts:233–256](backend/src/modules/ai/services/vox.service.ts#L233), парсер [строки 365–385](backend/src/modules/ai/services/vox.service.ts#L365)): код **корректен** — пробует плоский `words`, `wordsTimestamps`, и `segments[].words` (стили Whisper/Google/Deepgram), top-level и вложенно в `result/data`. Слов нет ни в одном формате.
- **Последствие:** `BehaviorMetricsWorker` считает «кто сколько говорил» по нулям; диаризация на уровне слов отсутствует; merge кладёт речь одним turn. На текстовые агенты (summary/задачи/граф) это **не влияет** — текст есть.
- **Это уже отслеживается:** WARN-диагностика добавлена ТЗ 2026-06-06 (S5-02) именно чтобы на реальной встрече увидеть форму ответа Vox. **Открытый вопрос:** включить ли в Vox `diarizationEnabled` / выбрать модель с word-level timestamps, или признать, что endpoint их не даёт.

### №2 — Арбитр графа: DeepSeek-flash 8× отдал битый JSON (✅ resilience сработал)
- **Факт:** 8× `LlmRouter dispatch fallback: deepseek/deepseek-v4-flash: ответ не прошёл validate caller'а` в KNOWLEDGE_GRAPH.
- **Сверка:** это **штатная работа** механизма из ТЗ-3 (`graph-arbiter-json-resilience`, 2026-06-06): `validate`-callback бракует битый JSON primary-провайдера → router падает на secondary, итог `dispatch success`. Раньше HTTP-200-с-мусором молча принимался.
- **Вывод:** устойчивость работает, граф достроился. Но это **сигнал**, что `deepseek-v4-flash` нестабилен по строгому JSON для арбитра — кандидат на capable-модель или forced `tool_choice` (флаг `LLM_DEEPSEEK_FORCE_TOOL_CHOICE_ENABLED` уже есть, default OFF).

### №3 — Специалистов слоя 3 не видно в trace (❓ дыра наблюдаемости, не сбой)
- **Факт:** в diag chain после block-distill видно только block-linker; ни `decision-extract`, ни `idea-extract`, ни `goals` не залогированы.
- **Сверка по коду:** диспатч **есть** ([block-distill.worker.ts:189](backend/src/modules/knowledge-core/workers/block-distill.worker.ts#L189), на canonical). Но специалисты (напр. [specialist-3-3-decisions.worker.ts](backend/src/modules/knowledge-core/workers/specialist-3-3-decisions.worker.ts)) пишут только через `this.logger` (stdout) + метрику `core_specialist_skipped_total`, **не через LogService с traceId**. Поэтому в БД-цепочку по `mtg_<id>` они не попадают.
- **Вывод:** по diag chain **нельзя сказать**, отработали ли специалисты или сделали skip. Чтобы узнать факт — нужно (а) глянуть метрики Prometheus `core_specialist_skipped_total{specialist,reason}`, либо (б) запросить граф напрямую (есть ли Decision/Idea/Goal по встрече), либо (в) **добавить специалистам DB-лог с traceId** — это самое полезное на будущее.

### №4 — Расхождение «решений» между двумя путями отчёта (⚠ продуктовый нюанс)
- **Факт:** `structuredData` (MiniMax, путь analyze) → `decisions: []`. А `summaryFast` (DeepSeek-V4-Pro, meeting-report-fast) → 4 «принятых решения».
- **Сверка:** это два разных промпта/модели, работающие параллельно (A/B). MiniMax строже трактует «решение» (ничего стратегического не было), DeepSeek вынес операционные намерения как «решения».
- **Вывод:** не баг, но видно расхождение трактовки. Когда свернём A/B на один путь — закрепить единое определение «решения» в промпте.

- **Конвейер здоров.** 21 агент отработал, 0 ошибок ERROR, отчёт качественный (5 задач с исполнителями, честные blockers, связные главы) даже на 72 словах.
