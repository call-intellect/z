# Модель по умолчанию — защита при удалении конкретной модели провайдера

## 1. Что есть сегодня

`llm-provider-default-fallback` (2026-07-06, уже реализован) закрыл проблему на уровне ПРОВАЙДЕРА: удаление занятого провайдера теперь либо жёстко блокируется (если дефолт-провайдер не назначен), либо автоматически переключает все маршруты (`LlmTaskRoute`) на дефолт-провайдера.

Экран «Модели провайдера» (`LlmModelsClient` → `AdminLlmModelsService.softDelete`) остался нетронутым: удаление КОНКРЕТНОЙ модели (`LlmModel`) внутри провайдера не проверяет вообще ничего. `LlmTaskRoute.model` — отдельная строка, независимая от факта удаления провайдера, может указывать на модель, которую только что тихо удалили. Владелец наткнулся на это при повторном тестировании и явно попросил защиту того же рода, но для модели.

## 2. Что делаем

Тот же паттерн: у провайдера уже есть `defaultModelKey` («модель, которая используется, если ни вызов, ни маршрут её не указали») — используем его буквально как «дефолтную модель ЭТОГО провайдера». Удаление модели:

- Если удаляемая модель == `defaultModelKey` провайдера → сначала обязать выбрать другую активную модель того же провайдера дефолтной (аналог Р5 — одним диалогом «выбери и удали»).
- Если у провайдера дефолтная модель НЕ назначена (либо назначенная — не эта) → как и в провайдерской фиче: нет дефолта — жёсткий отказ, если модель где-то используется (Р3); есть дефолт, отличный от удаляемой, — маршруты (`LlmTaskRoute.model`, tier-нормализованные + legacy JSON, global + per-org) автоматически переключаются на дефолтную модель, providerName не меняется (модель всегда в рамках одного провайдера).

## 3. Границы — что НЕ делаем

- НЕ переключаем модель на модель ДРУГОГО провайдера — дефолт модели всегда внутри своего провайдера (иначе меняется protocolKind/ключ/маршрут целиком — это уже вопрос дефолта-провайдера, не модели).
- НЕ трогаем `modelId` (опциональный FK на маршруте) при миграции — как и в провайдерской фиче, трогаем только строковые `providerName`/`model` (совпадает с уже принятым поведением `migrateRoutesToDefault`).
- НЕ заводим отдельное поле «isDefaultModel» на `LlmModel` — переиспользуем существующий `LlmProvider.defaultModelKey` (та же логика, что Р1 в провайдерской фиче: одна пара на провайдера, не список).
- НЕ создаём миграцию БД — `defaultModelKey` уже есть, `LlmTaskRouteChange.changeType` — обычная строка (не enum), новое значение `model_deleted_auto_migrated` пишется без изменения схемы.

## 4. Решения (по аналогии с Р1–Р5 провайдерской фичи, тот же владелец, тот же день)

| # | Решение | Почему |
|---|---|---|
| М1 | Дефолт модели = `LlmProvider.defaultModelKey`, ровно одна модель на провайдера. | Уже есть поле, семантика совпадает — не плодим сущности. |
| М2 | Нет дефолта у провайдера → удаление занятой модели жёстко блокируется (как сегодня), без диалога подмены. | Р3-аналог: не переключаем втихую без явного согласия владельца. |
| М3 | Удаление дефолтной модели провайдера — одним диалогом «выбери новую дефолтную модель и удали». | Р5-аналог: быстрее для владельца, чем отдельный поход в настройки. |
| М4 | Дедуп на легаси JSON-маршрутах — по паре (provider+model), не только provider (в отличие от provider-фичи, где дедуп по provider). | Providers у tier-записей не меняются при миграции модели — дубликат может возникнуть только в legacy JSON, если два элемента цепочки внутри одной записи совпадут после замены модели. |
