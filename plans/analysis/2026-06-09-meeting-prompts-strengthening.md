# Усиление системных промптов встреч

> **Рамка работы (важно — чтобы не путать направление).**
> Источник идей — **черновики владельца + это обсуждение**. Цель — **усилить промпты ВНУТРИ системы Z** (в коде): `type-team`, `type-sales`, `meeting-report-fast`, `follow-up`, специалисты графа. Черновики владельца — **донор смыслов, а не объект правки** и не «внедряем как есть».
> Сейчас мы в режиме **«думаем и проектируем»** — код не трогаем. Этот файл копит находки по каждому типу встречи; когда пройдём нужные типы — собираем в ТЗ и правим промпты.

## 1. Сквозные усиления (во все meeting-промпты)

| # | Усиление | Откуда | Статус у нас сейчас |
|---|---|---|---|
| C1 | **Провенанс**: кто / какая сторона сказал (привязка факта к спикеру или к стороне) | командный + клиентский черновики | нет (в `meeting-report-fast` есть только ограничение имён, не привязка факта) |
| C2 | **«Слова участника» vs «наша интерпретация»** — нейтральный регистр vs аналитический | клиентский | нет |
| C3 | **Темпоральность в отчёте**: отметить, что новая договорённость отменяет прежнюю | командный | только в графе (`block-linker` validFrom/validUntil, `decision-supersede-detect`) |
| C4 | **«Что стоит уточнить»** — 1–3 проактивных вопроса для закрытия пробелов | командный | только в графе (`probe-formulate`) |
| C5 | **Честное «не зафиксировано / не обсуждалось»** как факт, а не пустота | оба | частично (пустые массивы) |

**Держим как есть (уже обкатано, обязательно в каждом промпте):** ASR-нота (`withAsrNote`), защита от prompt-injection (`withInjectionGuard` + `wrapUserData`), калибровка confidence (`withConfidenceCalibration`), анти-галлюцинация имён (имена только из переданного списка участников), относительные сроки → ISO от даты встречи (`EDGE_CASE_POLICY`), cache-friendly структура (стабильный SYSTEM, транскрипт/участники/дата в конец user).

## 2. Дуальный вывод для клиентских встреч (ключевое решение)

**Принцип.** Для встреч с внешним собеседником делаем **ДВА документа** вместо одного:
1. **Протокол для отправки** — нейтральный, вежливый, без внутренней оценки; владелец копирует и шлёт собеседнику.
2. **Внутренняя карточка** — честная аналитика «для своих»; наружу не уходит.

**Где применяем (решение владельца 2026-06-09):** `sales`, `partner`, `customer_success` — типы, где есть внешняя сторона, которой можно выслать протокол.
- *Под вопросом:* `custdev` — это исследовательское интервью; формальный «протокол сделки» не нужен, максимум — благодарность/резюме. Решим при разборе типа custdev.
- *Не применяем:* `team`, `standup`, `plan_fact`, `project` (внутренние), `interview` (кандидат — отдельный разговор), `review`, `retro`.

**Правила границы (почему так):**
- **Конфиденциальность держится КОНСТРУКЦИЕЙ, не инструкцией.** Не один промпт с «в Части 1 не пиши оценку», а **два отдельных вызова**: протокол физически не знает про аналитику (нет канала утечки температуры/ЛПР/бюджета в клиентский документ). Дороже на один LLM-вызов — но это вопрос доверия, тут не экономим.
- **Отправка наружу = ручное действие с гейтом.** Протокол генерируем и показываем; «выслать» — всегда руками человека, никогда автоматически.
- **Механизм нейтральности — смена регистра (C2):** в протоколе потребности клиента его словами («вы отметили, что…»), без ярлыков «боль/возражение»; во внутренней карточке — наша трактовка.

### `partner`, `customer_success`
- Применить ту же дуальную схему (протокол + внутренняя карточка), адаптировав внутреннюю аналитику под смысл типа (партнёрство: выгоды сторон, модель, пилот, риски; CS: результат клиента, риск оттока, апсейл). Детально разберём при проходе этих типов.

### Граф знаний (`block-ingest` + специалисты)
- **Не дублируем** машинные факты отчётными промптами. Граф строится один раз из общего транскрипта (иначе расхождение источников — уже ловили fast vs structured). Часть «факты для графа» из черновиков владельца здесь НЕ реализуем — она уже закрыта конвейером.

## 3-bis. Организационные сущности: процесс / регламент / инструкция / политика

Источник — два черновика владельца (агент-экстрактор сущностей + агент-компилятор документации) и баг на проде: страница «Правила, процессы и политики» записала **разовую задачу** «Интеграция чат-бокса с Core» («Никита разрабатывает, Настя тестирует») как **Процесс / Действует**.

### Корневая проблема
Наш [regulation-extract](backend/src/modules/knowledge-core/prompts/regulation-extract.prompt.ts) (специалист 3-1) **не отличает нормативное/повторяемое от разовой задачи**:
- kinds = `regulation / process / policy / standard` — **нет `instruction`** (одиночный исполнитель → валится в «process»);
- **нет негативного гварда** «это документ или просто кто-то сейчас что-то делает»;
- **нет статуса** существует/нужен/обсуждается → статус карточки «Действует» ставится downstream по умолчанию → всё подряд «Действует»;
- работает на блоках с `signalType='process_step'`, а `block-ingest` навешивает `process_step` на любую последовательность «сначала–потом».

### Из Агента-1 (экстрактор) → усиливаем `regulation-extract` (3-1) + `block-ingest`
| # | Усиление | Статус у нас |
|---|---|---|
| R1 | **Негативный гвард «задача ≠ процесс»**: извлекать только нормативное/повторяемое («так принято всегда», повторяется, выбрано как стандарт). Разовая текущая активность → задача, карточку не создавать (или status=обсуждается, низкий confidence) | нет — **главный фикс** |
| R2 | **3-way дискриминатор + добавить kind `instruction`**: 1 субъект + «как» → инструкция; неск. ролей + сроки + «кто за что» → регламент; сквозная цепочка «что за чем» → процесс | нет (instruction отсутствует; дискриминатор размыт) |
| R3 | **Статус `существует / нужен / обсуждается`** в схему экстрактора → чинит «всё Действует» (нужен/обсуждается ≠ активный документ) | нет |
| R4 | `name` как реальное название документа, не пересказ фразы; evidence-цитата как обоснование вердикта | частично |
| R5 | Гвард «как ВООБЩЕ делается, а не сейчас делаю» усилить и в `block-ingest` (определение `process_step`) | слабо |

### Из Агента-2 (компилятор документации) → новый структурный компилятор
У нас есть `regulation-dedupe` (арбитр new/merge/extension/contradicts), но **нет структурного компилятора** `contentMd`. Это пробел.
| # | Усиление | Статус у нас |
|---|---|---|
| D1 | **Режимы СОЗДАНИЕ / ДОПОЛНЕНИЕ** — документ накапливается по кускам из разных встреч, не переписывается заново | нет (dedupe решает verdict, но не компилирует структурный документ) |
| D2 | **Маркеры пробелов** `[требует уточнения: …]` — честная дырка вместо выдумки | нет |
| D3 | **Маркеры конфликта** `[конфликт — требует подтверждения: A / B]` — не угадывать, что новее | частично (conflict-event есть, но без маркера в тексте) |
| D4 | **«Ничего не теряй»** — каждый факт сохраняется или осознанно обновляется с пометкой | нет гарантии |
| D5 | **Версия + «что изменилось»** — связать с `CardVersion` и UI «История версий» | версионирование есть, changelog-текст нет |
| D6 | **Структурные шаблоны по типу** (инструкция/регламент/процесс — разделы) | `contentMd` свободный |

### Развилки (рекомендация)
- **Где ловить «разовость»:** per-block 3-1 теряет контекст → гвард ставить **и в `block-ingest`**, **и в 3-1**; `specialists-combined` (видит все блоки) надёжнее отличит разовость.
- **kind `instruction`:** добавить (изменение схемы `regulation_extract_v1` + downstream-модели — пункт ТЗ).
- **Компилятор документа:** **отдельный новый агент** (берёт накопленные блоки темы + существующий `contentMd` → структурный документ), не раздувать 3-1.
- **Статус в UI:** `нужен/обсуждается` не показывать как «Действует» — маппинг статуса экстрактора в статус карточки.

## 4. Как ложится в архитектуру Z

- **Клиентский протокол** — зародыш есть: агент `follow-up` (генерит письмо клиенту для sales/customer_success). Расширяем его до полноценных минут встречи под отправку.
- **Внутренняя карточка встречи** — это `type-sales` (обогащённый). Она же питает постоянную CRM-карточку клиента — `card-rollup-v2` (kind=client/deal) сводит несколько встреч.
- **Отчёт по типу** идёт через `analyze.worker` (`runStructuredReport`, agentType `report-by-type`) и/или `meeting-report-fast` (поле `summary_markdown` по типу). Дуальность встроится сюда: для клиентских типов — второй вызов на нейтральный протокол.
- Полная карта агентов/промптов/моделей — в [каталоге](plans/analysis/2026-06-09-meeting-agents-catalog-prompts-and-models.md).

- **2026-06-09:** машинные факты для графа отчётными промптами НЕ дублируем.
- **2026-06-09:** организационные сущности (специалист 3-1) — главный фикс: гвард «разовая задача ≠ процесс/регламент/инструкция» (только нормативное/повторяемое); добавить kind `instruction`; добавить статус существует/нужен/обсуждается (чинит «всё Действует»).
