## 🔁 Карта ожидаемого функционала (что должно происходить)

> **Ядро протокола.** Это чек-лист «что Кора обязана делать сама» — по нему идёт каждый прогон. Ошибки в логах — симптом; здесь — **ожидания**: «сработало ли то, что должно, и дало ли выход». Молчаливый не-запуск ошибки не даёт — ловится только сверкой с этой картой.
>
> **Карта самообучающаяся.** Посеяна из кода на 2026-07-08 — критический хребет (в системе всего **≈150 `@Cron`** + триггерные цепочки). Каждый прогон в [блоке рефлексии](#-журнал-лог-прогонов) дописывает недостающее: новый крон, новую цепочку из свежего `feat`. Времена — **UTC**, если не помечено МСК.
>
> **Статус:** `✅` видели живым за период · `⚠️` работает с деградацией · `❌` должен был — не сработал/падает · `❓` ещё не проверяли.

## ▶️ Протокол «запускаем»

Когда владелец говорит **«запускаем»** — идём по шагам сверху вниз.

### Шаг 0 — Определить период
- Открыть [📌 Состояние прогона](#-состояние-прогона), взять **«Последний прогон логов»**.
- Период = `с этой даты` … `по сегодня`. Если прошло два дня — берём логи за два дня; прошло три — за три. Не было ни разу — берём хвост от даты первого коммита в [реестре](#-реестр-коммитов-на-прод-проверку).

### Шаг A — Проверка карты функционала + лог-ревью (что отработало за период)
Цель не «поискать ошибки», а **«всё, что обязано было отработать за период, отработало и дало выход»** (молчаливый не-запуск ошибки не даёт).
- Пройти [Карту ожидаемого функционала](#-карта-ожидаемого-функционала-что-должно-происходить) сверху вниз, по каждой строке — «сработало за период? дало выход?». Основной инструмент (с ноутбука, read-only):
  - `bun --env-file=.env backend/scripts/diag.ts usage --limit 100 --preview 0` — какие taskType бегали, есть ли `FAIL`;
  - `bun --env-file=.env backend/scripts/diag.ts logs --at-least WARN --from <ISO-дата периода> --limit 80` — ошибки/деградации по модулям (крон падает — видно тут);
  - `... diag.ts meetings --limit 20` — свежие встречи в статусе `ai_ready` (цепочка после видео); `... trace --meeting <id>` — разбор конкретной цепочки.
- Паттерны-маркеры в логах: `no eligible provider` (роутинг/провайдер), `требует apiKey` (провайдер без ключа), `упал`/`fallback` (деградация), `P2002`/`Custom Id cannot contain` (гонки/битый jobId), `ошибка на кластере`.
- Глубже (SQL по проду, `IntegrationSyncRun`, метрики `/metrics`) — только через SSH ([prod-ssh-access.md](../operations/prod-ssh-access.md), read-only).
- Что нашли → в [Журнал лог-прогонов](#-журнал-лог-прогонов); статусы в карте (`✅/⚠️/❌`) обновить.

### Шаг B — Проверка коммитов (от свежих назад)
- Открыть [Реестр коммитов](#-реестр-коммитов-на-прод-проверку). Брать **сверху** (новые — первыми).
- По каждому 🆕 коммиту закрыть три галочки:
  1. **В проде** — код реально доехал (образ пересобран, коммит в выкаченном билде).
  2. **Применён** — прод-операции коммита выполнены (миграция/seed/patch/ENV — сверить с [prod-deploy-log.md](../operations/prod-deploy-log.md)).
  3. **Работает** — фича даёт ожидаемое (глазами через `qa-tester` / API / логи / метрики).
- Итог — статус коммита (см. легенду) + короткая заметка с пруфом (что именно проверил).

### Шаг C — Не хватает логов, чтобы доказать
Если по коммиту **нельзя понять из логов, отработал он или нет**:
- добавить точечное структурное логирование в код (в call-site фичи),
- запушить и выкатить на прод,
- на следующем прогоне дочитать эти логи и закрыть строку.

### Шаг D — Зафиксировать прогон + рефлексия (самообучение)
- Обновить статусы коммитов в реестре и статусы (`✅/⚠️/❌`) в [Карте функционала](#-карта-ожидаемого-функционала-что-должно-происходить).
- Добавить строку в [Журнал лог-прогонов](#-журнал-лог-прогонов) с полем **«Рефлексия»**: что нового обязано работать и чего в карте ещё нет (новый крон из свежего `feat`, новая цепочка, новый маркер ошибки) → сразу дописать строку в карту.
- Обновить **«Последний прогон логов»** в [📌 Состоянии](#-состояние-прогона) на сегодняшнюю дату.

## ⚙️ Автотриггер: новые коммиты → в реестр

**Замысел:** как только пушим новые коммиты — они автоматически попадают в [Реестр коммитов](#-реестр-коммитов-на-прод-проверку) **наверх**, чтобы новьё тестировалось первым.

**Как это будет работать (git-хук):**
- Хук на `post-commit` / `pre-push` дописывает строку(и) новых коммитов в начало таблицы реестра со статусом `🆕` и пустыми галочками (`⬜`).
- Doc-only коммиты (`docs:`, рефлексия) хук помечает `➖` (нет прод-действий) автоматически по типу коммита.
- Агент при прогоне Шага B закрывает галочки и статус.

**Статус:** _хук ещё не установлен_ — ставится отдельным шагом (скрипт в `.githooks/` или `backend/scripts/`). До установки реестр ведётся вручную по [Протоколу «запускаем»](#-протокол-запускаем).
