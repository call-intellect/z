# Second Brain — настройка для нового проекта

> Документ-инструкция: как развернуть систему «второго мозга» в новом проекте. Извлечено из практики Crossmark. Содержит принципы, структуру папок, готовые протоколы и шаблоны — копируй файлы, адаптируй имена под свой стек.

---

## 0. Что это и зачем

Система второго мозга — это связка из четырёх артефактов, которые вместе дают AI-агенту (Claude Code и аналогам) и человеку **постоянный, актуальный контекст** о проекте через сессии:

| Артефакт | Назначение | Кто читает |
|---|---|---|
| `CLAUDE.md` (корень репо) | правила работы, триггеры, чек-листы | агент при каждом запуске |
| `second-brain/` | факты о текущем состоянии: архитектура, фичи, ловушки | агент по запросу + человек |
| `plans/` | роадмап: анализ, ТЗ, история фич | агент перед стартом задачи |
| `memory/` (вне репо, в `~/.claude/`) | поведенческие правила и предпочтения **этого** разработчика | агент автоматически |

**Главное правило разделения:** `second-brain/` хранит **то, что есть по факту** (работающий код, принятые решения, реальные ловушки). `plans/` хранит **то, что хотим сделать** (идеи, аудиты, ТЗ). Если путаешь — задавай себе вопрос: «это уже работает или это идея?» Работает → second-brain. Идея → plans.

**Иерархия источников правды (от главного к второстепенному):**
1. **Код** — абсолютная истина о том, как работает система сейчас.
2. **Git-история** — почему и когда что изменилось.
3. **Second Brain** — контекст, решения, договорённости.
4. **Память агента** — вспомогательный слой, всегда проверять.
5. **Слова разработчика** — если противоречат коду, уточнить.

Если second-brain противоречит коду — **верить коду**, обновить second-brain.

## 1. Структура папок

Создай в корне проекта:

```
<project-root>/
├── CLAUDE.md                          ← правила для агента (см. §3)
├── second-brain/
│   ├── index.md                       ← единственная точка входа
│   ├── 00_system/                     ← протоколы (см. §4)
│   │   ├── SECOND_BRAIN_PROTOCOL.md
│   │   ├── SOURCE_OF_TRUTH.md
│   │   ├── STRUCTURE_RULES.md
│   │   ├── LINKING_RULES.md
│   │   ├── INDEX_RULES.md
│   │   ├── TASK_WORKFLOW.md
│   │   ├── UPDATE_AFTER_CODE_CHANGE.md
│   │   └── BOOTSTRAP_FROM_CODE.md
│   ├── 01_projects/                   ← заметки по фичам/модулям
│   ├── 02_architecture/               ← архитектурные карты, ADR, code-pitfalls
│   ├── 03_bugs/                       ← разборы сложных багов
│   ├── 04_archive/                    ← устаревшее (не удалять, переносить)
│   └── 05_история/                    ← рефлексия после каждого push
└── plans/
    ├── README.md
    ├── analysis/                      ← анализ задач, аудиты, backlog идей
    │   └── _template.md
    ├── tz/                            ← технические задания
    │   └── _template.md
    └── archive/                       ← завершённые планы
```

**Правила структуры:**
- Один файл = одна тема.
- Файл без ссылки в `index.md` не существует.
- Не создавать вложенность глубже 2 уровней (исключение — `01_projects/<feature>/` если фича действительно крупная).
- Имена: протоколы — `UPPER_CASE.md`, заметки — `kebab-case.md`, планы — `YYYY-MM-DD-название.md`.

## 2. Что хранить и что НЕ хранить

### В `second-brain/` хранить
- **Почему** принято решение (не что, а почему).
- Неочевидные зависимости и ограничения.
- Контекст задач и договорённости с командой.
- Бизнес-логику фичи на уровне «как устроено сейчас».
- Карты модулей, схему данных, точки входа.
- Ловушки фреймворков/библиотек, конкретные для проекта.

### В `second-brain/` НЕ хранить
- Очевидное из кода (CRUD, типичные паттерны фреймворка).
- Git-историю — она уже в git.
- Идеи и хотелки — это `plans/analysis/`.
- Аудиты «что плохо и как улучшить» — это `plans/analysis/`.
- Code patterns, conventions — выводимы из текущего кода.
- Ephemeral state (текущая задача, незаконченное) — это todos/plan.

### В `plans/` хранить
- Анализ фичи перед реализацией (`analysis/`).
- ТЗ на реализацию (`tz/`).
- Backlog идей с приоритизацией.
- Завершённые/отменённые ТЗ (`archive/`).

### В `memory/` (`~/.claude/projects/<project>/memory/`) хранить
- Поведенческие правила: «не делай Х», «делай Y потому что…».
- Предпочтения разработчика (формат коммитов, способ верификации).
- Reference-указатели на внешние системы (Linear, Slack, Grafana).

### В `memory/` НЕ хранить
- То, что выводится из кода (паттерны, архитектура).
- Историю изменений (есть git).
- Решения багов (есть код + commit message).

## 3. CLAUDE.md — шаблон для нового проекта

Скопируй в корень репо как `CLAUDE.md` и адаптируй имена/команды под свой стек:

```markdown
# <PROJECT_NAME> — навигация по проекту

Этот документ — карта проекта. Читай его в начале каждой сессии.

## Ключевые принципы

1. **Second Brain как источник правды о фактическом состоянии** — любое изменение бизнес-логики или архитектуры должно отражаться в `second-brain/`. Если через месяц будет непонятно ПОЧЕМУ так сделано — фиксируй сразу.
2. **Один план — одна функция** — любая новая фича оформляется планом в `plans/` до начала работы. См. [plans/README.md](plans/README.md).
3. <добавь свои принципы: AI-стек, обязательные практики, табу>

## КРИТИЧЕСКОЕ РАЗДЕЛЕНИЕ: second-brain vs plans

| Содержимое | Куда |
|---|---|
| Что сейчас работает по факту, архитектура, сущности, связи | `second-brain/` |
| История сессий, рефлексия | `second-brain/05_история/` |
| Бизнес-контекст, гипотезы, фидбек | `second-brain/01_projects/` |
| **Анализ фичи / UX-аудит / разбор «как улучшить» / backlog** | `plans/analysis/` |
| **ТЗ на реализацию** | `plans/tz/` |
| Завершённые/отменённые планы | `plans/archive/` |

Правило: **это уже работает или это идея?** Работает → second-brain. Идея → plans.

## Стек

<укажи стек проекта: язык, фреймворк, БД, очереди, инфраструктура>

## Точка входа в second-brain

`second-brain/index.md` — все разделы ведут отсюда.

## Как работать с проектом

- В начале задачи — читай этот файл, затем `second-brain/index.md` и нужные файлы из `second-brain/01_projects/` и `plans/`.
- Если меняется бизнес-логика — обнови `second-brain/index.md` и нужные файлы в `01_projects/` или `02_architecture/`.
- Если меняется план — обнови файл в `plans/`.
- Если появляется новая важная папка/документ — обнови этот `CLAUDE.md`.

## Правила работы с Git

**Перед `git pull`:**
1. Прочитай `second-brain/index.md` — зафиксируй состояние.
2. После pull — проверь `git diff HEAD~1 --name-only`.
3. Если изменились модули/контракты/архитектура — обнови `second-brain/`.

**Перед `git commit` / `git push`:**
1. Отражены ли изменения в `second-brain/`?
   - Новая фича → заметка в `01_projects/`.
   - Архитектурное изменение → обновить `02_architecture/`.
   - Удалён модуль → убрать все ссылки.
2. Обнови статусы в `plans/` (`[ ]` → `[x]`).
3. Коммит: `тип(область): описание` (Conventional Commits).

**ВАЖНО — что коммитить:** только то, что создал или изменил САМ. Никогда `git add .` / `-A` / массовых добавлений. Перед каждым `git add` явно перечисляй пути. Untracked файлы, появившиеся ДО сессии или не относящиеся к задаче, — не трогать.

**ВАЖНО — `git push` только с явным подтверждением:** для каждого нового push спрашивай отдельно. Разрешение на коммит ≠ разрешение на push.

**Исключение — рефлексия в `second-brain/05_история/`:** коммитится и пушится автоматически сразу после основного push, без отдельного подтверждения.

## ВАЖНО: завершение работы и рефлексия

Применяется **по триггеру**, не «в конце сессии».

### Триггер 1: после `git push`

1. **Обнови `second-brain/`** — если изменилась бизнес-логика/архитектура.
2. **Чек-лист производных заметок** — пройди по таблице ниже и обнови ВСЕ затронутые файлы. Заметки ссылаются друг на друга — пропуск ломает связность.

| Что изменил | Что обновить в second-brain (помимо профильной 01_projects/<feature>.md) |
|---|---|
| Новая колонка/таблица в БД | `02_architecture/data-model.md` |
| Новый модуль/контроллер | `02_architecture/module-map.md` |
| Новый AI-агент / воркер / job | `01_projects/ai-jobs.md`, `01_projects/workers-queues.md` |
| Новая admin-страница | `01_projects/admin.md` |
| Новый API-эндпоинт | `01_projects/api-layer.md` |
| Новая публичная страница | `01_projects/frontend-pages.md` |
| Новый context/hook | `01_projects/frontend-contexts-hooks.md` |
| Новый план в `plans/` | `second-brain/index.md` (если крупный) |

3. **Запиши рефлексию** в `second-brain/05_история/YYYY-MM-DD-краткое-название.md`:
   - что было поставлено
   - как решал (с конкретными файлами и коммитами)
   - что вышло (результаты верификации: сборка, тесты, ручная проверка)
   - чему научился

4. **Закоммить и запушь рефлексию** отдельным `docs(second-brain): рефлексия — ...` коммитом.

5. **Напомни про prod-операции** — если в коммитах изменились файлы, чьи данные хранятся в БД и редактируются админкой / требуют миграций / изменений конфига. Подсказка выдаётся ОДИН раз, в виде блока «Для применения на проде выполни: …». Команды должны быть копи-пейст-готовые.

6. **Сформируй полную prod-инструкцию для программиста** — пошагово, в чате (не файлом), включая только применимые шаги под фактический набор изменений.

### Триггер 2: пользователь говорит «всё», «закругляемся», «спасибо», «ок»

Тот же набор действий: обнови → запиши рефлексию → коммит → push.

### Триггер 3: накопилось >10 необработанных файлов в `05_история/`

Перед началом следующей задачи — пройдись по новым рефлексиям (без `distilled: true` в frontmatter) и вынеси повторяющиеся уроки:

| Тип урока | Куда переносить |
|---|---|
| Тех. факт о проекте (поля, контракты, ловушки tsc/Prisma/etc) | `02_architecture/code-pitfalls.md` |
| Поведенческое правило для агента | `~/.claude/projects/<project>/memory/feedback_*.md` + строка в `MEMORY.md` |
| Правило про конкретный модуль | профильная `01_projects/<feature>.md` |

Критерии переноса (хотя бы один):
- урок повторяется в ≥2 рефлексиях, ИЛИ
- грабля с ценой >1 час потерянного времени, ИЛИ
- меняет способ работы (новая команда, новый подход).

После переноса — `distilled: true` в frontmatter обработанных рефлексий. Файлы НЕ удалять — это контекст-источник для будущей дистилляции.

### Чего НЕ делать
- НЕ откладывай рефлексию «на потом, в конце сессии» — конца нет.
- НЕ пиши рефлексию задним числом — детали забудутся.
- НЕ пропускай рефлексию для «мелких» задач — даже фикс на 2 строки даёт урок.

## ВАЖНО: план для каждой новой функции

Любая нетривиальная функция — план в `plans/` ДО кода.

Правила:
1. Один план = одна функция. Если план уже есть — работаем с ним.
2. Имя: `YYYY-MM-DD-название-функции.md`.
3. План делится на фазы. У каждой статус `[ ]` или `[x]`.
4. В конце плана — итог: реализовано целиком или нет, что осталось.
5. План актуализируется после каждой сессии.

## Язык

<укажи язык, на котором отвечать (например, «Всегда отвечай на русском»)>
```

### 4.6 `TASK_WORKFLOW.md`

```markdown
---
type: protocol
---

# TASK WORKFLOW — Процесс работы над задачей

## Три фазы

```
Обсуждение (analysis)  →  ТЗ (tz)  →  Реализация
```

Нельзя перейти к следующей фазе без завершения предыдущей.

---

## Фаза 1 — Анализ (`plans/analysis/`)

**Когда:** при появлении любой нетривиальной задачи.

**Что делаем:**
1. Создать файл `plans/analysis/YYYY-MM-DD-имя-задачи.md` по шаблону `_template.md`.
2. Обсудить: зачем, как сейчас работает, открытые вопросы.
3. Зафиксировать решения в разделе «Решения принятые в ходе обсуждения».

**Критерий перехода:** все открытые вопросы закрыты, решения зафиксированы.

---

## Фаза 2 — ТЗ (`plans/tz/`)

**Когда:** анализ завершён.

**Что делаем:**
1. Создать `plans/tz/YYYY-MM-DD-имя-задачи-tz.md` по шаблону `_template.md`.
2. Заполнить scope, технические изменения, DoD.
3. Указать ссылку на analysis-файл.

**Критерий перехода:** ТЗ просмотрено и подтверждено («да, делаем»).

---

## Фаза 3 — Реализация

После реализации:
1. Обновить Second Brain (заметки в `01_projects/`, `02_architecture/` если нужно).
2. Перенести analysis + tz файлы в `plans/archive/`.

---

## Именование файлов

```
plans/analysis/YYYY-MM-DD-chat-improvements.md
plans/tz/YYYY-MM-DD-chat-improvements-tz.md

## 8. `memory/` — настройка Claude Code

Память Claude Code лежит вне репо: `~/.claude/projects/<project-slug>/memory/`. Slug строится из пути проекта, заменяя `\` и `:` на `-` (например, `c:\work\myproject` → `c--work-myproject`).

### 8.1 `MEMORY.md` — индекс памяти

Создай файл по этому шаблону:

```markdown
# Memory Index — <PROJECT_NAME>

## User
_(краткие факты о роли/опыте/предпочтениях разработчика)_

## Feedback
_(поведенческие правила: «не делай Х», «делай Y, потому что…»)_

## Project
_(статусы фич, дедлайны, договорённости — быстро устаревают, держи актуальным)_

## Reference
_(указатели на внешние системы: Linear, Slack, Grafana и т.п.)_
```

Индекс — это _только пойнтеры_. Сами правила лежат в отдельных файлах рядом, по одной теме на файл:

### 8.2 Шаблон файла памяти

```markdown
---
name: <короткое имя>
description: <одна строка для решения «релевантно ли это сейчас» — будь конкретным>
type: <user | feedback | project | reference>
---

<тело памяти>

# Для feedback и project — структурируй так:
**Why:** <причина — часто инцидент или сильная преференция>
**How to apply:** <когда/где правило срабатывает>
```

### 8.3 Что в memory попадать ДОЛЖНО

- Поведенческие правила, которые нельзя вывести из кода.
- Уроки, которые повторяются в нескольких рефлексиях.
- Грабли с реальной ценой (потеря данных, сломанный прод, потерянные часы).
- Reference на внешние системы.

### 8.4 Что в memory попадать НЕ ДОЛЖНО

- Code patterns, conventions, paths — выводимы из кода.
- Git-история, who-changed-what — есть `git log/blame`.
- Решения багов — есть код + commit.
- Текущая задача — это todo/plan.

## 11. Что важно помнить (мета-уроки из практики Crossmark)

1. **Без обратной петли запись теряет смысл.** Рефлексии полезны не сами по себе — а через дистилляцию в `code-pitfalls.md` и `memory/feedback_*.md`. Канал доставки знания обратно в контекст должен быть автоматическим: либо через `MEMORY.md` (всегда подгружается), либо через `index.md` (читается в начале задачи).
2. **Один файл-копилка > много мелких заметок.** `code-pitfalls.md` лучше держать одним файлом до ~30 пунктов. Дробить на `prisma-pitfalls.md` / `frontend-pitfalls.md` — только когда раздел перерос. Меньше навигации = больше реального чтения.
3. **Триггер по счётчику предсказуемее, чем по дате.** «Раз в неделю» зависит от графика. «>10 необработанных рефлексий» — самоподдерживающийся: не пишешь = не накапливается.
4. **Чек-лист производных заметок — обязательное правило, не пожелание.** Пропуск типа «забыл обновить data-model.md» — это не «исправлюсь следующий раз», а сигнал, что чек-лист не используется как инструмент. Прогоняй его до `git add`, не после.
5. **Push требует подтверждения каждый раз.** Разрешение на коммит ≠ разрешение на push. Разрешение на push одной задачи ≠ разрешение на push следующей. Это не паранойя, это страховка от случайных публикаций.
6. **Идеи и хотелки — не в second-brain.** Аудит «что плохо в фиче X» — это `plans/analysis/`, даже если он чисто исследовательский. Second-brain загрязняется идеями быстро, а чистится медленно.
