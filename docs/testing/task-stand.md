# Стенд качества трекинга задач (task-stand)

Инструмент, чтобы **периодически проверять качество четырёх механизмов трекинга задач Kora — создание задач,
подзадачи/дедуп, журнал выполнения, автозакрытие — на синтетике, судить исход против эталона по построению и
находить слабые места.** Гоняется на **локальной синтетике** (свежая «Стрела» или существующий тестовый
тенант), прод не трогает.

> **Статус:** спроектирован (картография + банк + ТЗ + фикстуры готовы), **раннер реализуется** агентом по
> [ТЗ](../../plans/tz/2026-07-03-task-tracking-stand.md). Ниже — как он устроен и как его гонять; секции с
> результатами (scorecard, вердикт Т1–Т10) заполняются ПОСЛЕ первого baseline-прогона.

## Что меряет

| Механизм | Что проверяем | Ключевой инвариант |
|---|---|---|
| Создание задач | разговор → «Входящие» → задача; задача vs не-задача vs idea vs decision; поля (исполнитель/срок/приоритет) | — |
| Подзадачи / дедуп | дубль → **подсказка** (не авто-merge); многопунктовое → 1 задача + чек-лист; глубина ≤2 | **R13: 0 авто-merge** |
| Журнал выполнения | из разговоров — черновик «что сделано/дальше» (health), публикация только с подтверждением | не авто-постинг |
| Автозакрытие | сигнал «сделал» → **кандидат** (не закрытие); закрывает человек; method-capture → граф/клон | **R13: 0 авто-close** |

## Предпосылки (перед запуском)

1. Dev-инфра из корня: `docker compose -f docker-compose.dev.yml up -d` (Postgres :55435, Redis :56381).
2. **Живой backend с воркерами:** `cd backend && bun run dev` — ОБЯЗАТЕЛЬНО (конвейер крутится in-process; без
   него сиды кладут RawEvent, но задачи/кандидаты не появляются).
3. `backend/.env` смотрит на локальную БД (127.0.0.1, НЕ прод) и содержит LLM-ключи (извлечение/арбитр/
   верификатор/судьи — живые модели).
4. `STRELA_ORG` (тенант A) и `TASK_STAND_ORG_B` (тенант B для тенант-изоляции) заданы в `.env`.
5. Запускать из папки `backend/` (отчёт пишется в `../docs/testing/`).

## Запуск

```bash
cd backend

# по фазам
bun run scripts/task-stand/stand.ts prepare   # Ф0: тенант, проекты, статусы, исполнители (из fixtures.json)
bun run scripts/task-stand/stand.ts seed       # Ф1: baseline setup-задачи + манифест ground truth (ждёт эмбеддинги)
bun run scripts/task-stand/stand.ts inject      # Ф2: подать 100 входов через реальный конвейер + изоляция Т1
bun run scripts/task-stand/stand.ts run         # Ф2+Ф3: прогон + снять сырую трассу
bun run scripts/task-stand/stand.ts report:nollm # Ф3: детерминированные ассерты без LLM
bun run scripts/task-stand/stand.ts judge        # Ф4: панель судей majority-of-3
bun run scripts/task-stand/stand.ts report       # Ф4/Ф5: scorecard + оси + инварианты + Т1–Т10

# всё целиком
bun run scripts/task-stand/stand.ts all
```

Перед КАЖДЫМ прогоном чистить (иначе меряется прошлый): `bull:*` тенанта, answer-кэш `dlg:ans:<org>:*`,
`probe:dedup/ratelimit:*`, SETNX прогресса. См. ТЗ §3.

## Как читать отчёт

`task-stand-report.md` — распределение вердиктов (INVARIANT_FAIL → WRONG_OUTCOME → PARTIAL → PASS) по
**категориям A–J** и по **механизмам** (create/subtask/dedup/journal/closure); оси C/D/G/J/X/P; **статус
инвариантов INV-1..4** (любой FAIL — красный стоп); **таблица Т1–Т10** (подтверждён/снят/ruler-defect с
доказательством из трассы); конфигурация прогона (какие крутилки, какой извлекатель жив). Каждый прогон —
снапшот в `task-stand-runs/<дата-время>/` для «было→стало».

## Что стенд обязан различать (быстрый чек эталонов)

- **создать задачу** ⇔ вопрос/пожелание/решение-без-действия/болтовня/сделанное → **ничего**;
- **1 задача + чек-лист** ⇔ N карточек (многопунктовое одному);
- **same → подсказка** ⇔ different/nil → new; и **НИКОГДА auto-merge** (INV-1);
- **done → кандидат(pending)** ⇔ partial → журнал ⇔ инъекция/голая команда → nothing; **НИКОГДА auto-close** (INV-1);
- **подзадача (parentId)** — только ручной путь, глубина ≤2 ⇔ «подзадачи из разговора» = чек-лист;
- **изоляция тенанта** (INV-2) и **устойчивость к инъекции** (INV-3) — на каждом механизме.

## Цикл улучшения (после baseline)

1. baseline «как есть» (этот стенд) → находки Т1–Т10 + новые.
2. Диагноз каждому провалу ПО СЛОЮ (извлечение vs политика) и по классу; дефект линейки (ruler-defect) — первым.
3. Классы → 1-3 ТЗ-фикса (отдельный файл, НЕ в этом задании). Чинить класс, не кейс.
4. Перепрогон тем же банком + свежие 15; отчёт «было→стало» (дельта ±3-5 п.п. на 100 — не вывод).
5. Сходимость: планка PASS взята на банке И свежем, инварианты 100%, Т1–Т10 закрыты (подтверждены→фикс или сняты).

Границы автономии: банк и эталоны фиксированы (правки — ручным разбором с фиксацией причины); планка и
что считать «правильным» — решение владельца; прод стенд не трогает никогда.

## Границы

- Только локальная синтетика. Прод — исключительно read-only диагностика (см. `docs/operations/prod-ssh-access.md`).
- Вне периметра: цели/OKR-линковка, SLA support-desk, спринт-подсказки, повторяющиеся задачи, кастом-поля,
  вебхуки, импорт Яндекс/Битрикс (отдельные оси).
