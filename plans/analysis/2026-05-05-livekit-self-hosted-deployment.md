# Анализ: Self-hosted развёртывание LiveKit (SFU + Egress + TURN)

## Что хотим сделать

Развернуть LiveKit Server (SFU), LiveKit Egress и TURN-сервер на **наших собственных серверах** компании. Развести их по отдельным машинам (правило из `capacity-and-infra.md`). Подготовить минимальный тестовый вариант (4/4/4 vCPU) с возможностью масштабирования до public beta.

## Зачем (цель и ценность)

- У компании уже есть свои сервера — облачные провайдеры не используем.
- Полный контроль над токенами и приватностью медиа-потоков (важно для интервью / собеседований / sales).
- Записи и аудио-дорожки лежат в нашем S3-compatible (его тип определим).

## Как работает сейчас

Кода нет. Есть финальное продуктовое решение (`livekit_ai_meetings_final_solution.md`) — фиксирует выбор LiveKit и required-формат записи.

## Известно об инфре (по ответам 2026-05-06)

- **Железо:** HP DL360 Gen9 4LFF, 2× Xeon E5-2690v4 (28C/56T per socket pair, 2.6 GHz base), 128 GB RAM 2400, HP Smart Array. **2 сервера** (решение от 2026-05-06).
- **Запас по CPU:** 56C на оба сервера. По ориентирам doc'а (64 ядра ≈ 100 одновременных записываемых встреч до 10 человек) — реальный потолок MVP ~80–90 одновременных встреч.
- **OS / гипервизор:** **Proxmox VE** на обоих серверах, рабочие нагрузки в виртуалках с Ubuntu Server LTS внутри. Решение от 2026-05-06 — снапшоты, backup, изоляция ролей без k8s. k8s не используем (для 2 серверов overkill).
- **Разводка ролей по серверам:**
  - **Сервер A (медиа):** SFU-VM + TURN-VM (публичный IP, UDP открыт).
  - **Сервер B (контроль и запись):** Egress-VM + Backend-VM + PostgreSQL-VM + Redis-VM.
- **Размещение:** дата-центр в Новосибирске. У каждого сервера свой канал и белый IP (решение от 2026-05-06).
- **DNS / поддомены** (под доменом `crossmark.ru`):
  - `meet.crossmark.ru` — frontend (Next.js).
  - `api.crossmark.ru` — backend (NestJS, REST + webhooks).
  - `media.crossmark.ru` — LiveKit SFU (wss). Имя нейтральное, не светит «livekit» наружу.
  - `turn.crossmark.ru` — TURN.
  - `s3-dev.crossmark.ru` — MinIO dev (внутренняя сеть).
  - **Convention:** в LiveKit room names и API keys слово «crossmark» не используется — нейтральные UUID/идентификаторы.
- **TLS:** Let's Encrypt + nginx-reverse-proxy + certbot на обоих серверах. Wildcard от платного CA — только если уже куплен.
- **TURN:** на старте — встроенный LiveKit TURN на сервере A. **Архитектурно закладываем переключение на внешний TURN** (coturn / RU- или зарубежный прокси компании) через ENV-переменную без переписывания кода. Решение от 2026-05-06: «делаем так, чтобы можно было переключаться» — ENV `TURN_MODE = builtin | external`, при `external` — `TURN_HOST`/`TURN_PORT`/`TURN_USERNAME`/`TURN_PASSWORD`/`TURN_TLS`.
- **S3-storage (записи и аудио-дорожки):**
  - **Prod:** Selectel Object Storage в зоне Новосибирска (рядом с DC, минимизирует трафик по магистрали). Решение пересмотрено 2026-05-06 — Yandex Object Storage не имеет зоны в Новосибирске, всё ушло бы через Москву и теряло на скорости загрузки записей.
  - **Dev/staging:** локальный MinIO в третьей VM на сервере B — для тестов без облачного биллинга и без выноса тестовых данных за периметр.
  - **Код агностичен** — работает через `S3_ENDPOINT_URL` / `S3_BUCKET` / credentials, можно переключать между Selectel / Yandex / MinIO без изменений в коде (см. memory feedback `switchable endpoints`).

- [ ] Egress: один инстанс на MVP, потом пул?
- [ ] DNS / TLS: как выпускаем сертификаты для `wss://livekit.<host>` — Let's Encrypt / wildcard от компании?

- [ ] Webhook endpoint: один публичный URL на все события + дедуп по `event.id`.
- [x] **Мониторинг:** свой стек Prometheus + Grafana в отдельной VM на сервере B. Решение от 2026-05-06. Все компоненты Z отдают метрики через стандартные exporters: LiveKit (встроено), PostgreSQL (`postgres_exporter`), Redis (`redis_exporter`), NestJS (через `@willsoto/nestjs-prometheus`), Egress (встроено). Дашборд для основных показателей (активные встречи, загрузка CPU, очередь Egress, время распознавания и LLM, упавшие задания). Если у компании появится центральный Grafana — подключим через Prometheus federation, без перепиливания.

## Что выяснили исследованием (2026-05-05)

- **Helm-чарт официальный.** LiveKit публикует Helm chart, поддерживает GKE / EKS / DOKS «из коробки». Это базовый рекомендованный путь для prod.
- **Host networking → 1 LiveKit-под на ноду.** Стандартная схема — `hostNetwork: true` (rtc.udp/tcp напрямую на ноде). Альтернатива — STUNner (TURN-прокси для k8s, лучше согласуется с k8s-практиками: масштабирование, изоляция, модульность).
- **TLS обязателен.** Клиенты подключаются через `wss://livekit.<host>` — нужен домен и SSL-сертификат. Termination на Ingress (Helm настраивает для GKE и ALB).
- **Redis нужен** для Egress/Ingress и для нескольких LiveKit-реплик.
- **Graceful upgrade** — `terminationGracePeriodSeconds: 5h` (драйнинг идущих встреч).
- **Метрики Prometheus** включаются в чарте, ресурсы по умолчанию: `requests 500m/512Mi`, `limits 1000m/1Gi` (плюс автоскейлинг по CPU).

## Предварительные ответы на открытые вопросы

- **Развёртывание для prod:** Helm в k8s. Для тестового — docker-compose ок.
- **TURN:** на старте — встроенный LiveKit TURN. STUNner стоит рассмотреть, когда понадобится больше 1 пода SFU на ноду.
- **Egress отдельно от SFU** — да, это ещё подтвердилось (запись съедает CPU, на одной ноде роняет качество).
- **Версии LiveKit:** фиксировать тег чарта, обновлять осознанно (есть свежие баги — см. code-pitfalls.md).
- **Регион:** один регион в первой версии, ближайший к основной ЦА.
