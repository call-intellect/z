# Анализ: MVP-флоу встречи (создание → проведение → результат)

## Что хотим сделать

Реализовать сквозной MVP-флоу:
1. Авторизованный пользователь создаёт встречу (выбирает тип).
2. Получает host-ссылку и guest-ссылку.
3. Гость заходит без регистрации, указав имя.
4. Все участники общаются (камера/мик/screen share/чат).
5. Host управляет записью и завершает встречу.
6. После завершения — AI-обработка → пользователь видит результат на `/meetings/:id/result`.

## Зачем (цель и ценность)

Это базовый E2E-тракт продукта. Без него невозможно валидировать ничего: ни UX, ни мощности, ни AI-качество. Всё остальное (тарифы, календарь, follow-up автоматизация) — поверх этого тракта.

### Гостевые ссылки

Решение от 2026-05-06: **одна ссылка на встречу для всех, как в Zoom.**

- Нет отдельной «гостевой ссылки» с своим токеном. Есть один URL встречи: `meet.crossmark.ru/m/<id>`.
- Хост открывает первый раз через deep-link от Crossmark с разовым JWT — устанавливается cookie. Потом ходит без токена.
- Гости открывают тот же URL, видят форму «введите имя», заходят как гости.
- **Срок жизни ссылки** — до конца встречи. После `completed` ссылка показывает «Встреча завершена».
- **Отзыв ссылки** — нельзя отозвать саму ссылку (она привязана к meeting_id). Можно завершить встречу или выкинуть конкретного участника. Это совпадает с моделью Zoom.
- **Z сам приглашения не рассылает** — хост копирует URL и шлёт куда хочет (Telegram, почта, мессенджер).

### Зал ожидания (когда гость пришёл, а хост ещё нет)

Решение от 2026-05-06 (по образцу Google Meet):
- **Хост в комнате (`active`)** → гость заходит сразу.
- **Хост ещё не зашёл (`scheduled`)** → гость видит экран «Ожидание организатора. Встреча начнётся, когда подключится организатор» + автоматическое обновление раз в 5 секунд + крутящаяся иконка ожидания.
- **После окончания (`completed`)** → страница «Встреча завершена», без входа.
- Зала ожидания с одобрением каждого гостя в MVP **нет** — это V2 (актуально для собеседований и приватных продаж).

## Что выяснили исследованием (2026-05-05)

### Webhooks от LiveKit

- Аутентификация — JWT в `Authorization` header, подписан API-ключом и секретом. Дополнительно тело подписано **HMAC-SHA256** (SHA-256 хеш тела вшит в JWT).
- Каждое событие имеет **уникальный ID** — рекомендуется использовать его как ключ дедупликации (таблица `webhook_seen_events` с unique constraint).
- Дубликаты возможны: handler **должен быть идемпотентным**, на повтор — `2xx` no-op.
- Полный набор нужных типов: `room_started`, `room_finished`, `participant_joined`, `participant_left`, `egress_started`, `egress_ended`, `egress_failed` (последний — обязательно ловить).

### LiveKit Egress — модель записи

Подтверждаем выбор подхода:
- **Participant Egress** — пишет конкретного участника по `identity` (handles mute/state changes сам). Транскодинг есть — выходим в нужный формат.
- **Track Egress** — raw отдельных треков, без транскодинга, **самый дешёвый по CPU**. Подходит для отдельных аудиодорожек под AI.
- **Realtime audio через WebSocket** доступен только на TrackEgress — пригодится, если позже захотим streaming-транскрипт.

→ Для MVP: одна Composite egress (общая запись) + Track Egress per participant (raw audio) → S3.

## Предварительные ответы на открытые вопросы

- **Webhooks:** один публичный endpoint, проверка подписи HMAC-SHA256, дедуп по уникальному ID события, идемпотентный handler.
- **Срок жизни гостевой ссылки:** до `Meeting.ended_at` + 24 часа (на случай, если встречу закрыли руками).
- **Одна ссылка на всех гостей:** да, для V1 — экономия в UX. Индивидуальные ссылки — фича V2 (для запланированных встреч с конкретными приглашёнными).
- **Если host вышел:** встреча продолжается до явного `завершить` или таймаута неактивности (15 минут).
- **Webhook `room_finished` не пришёл:** фолбек — крон, который раз в минуту берёт встречи в статусе `active` старше N минут без обновления и закрывает их.
- **Чат:** через LiveKit DataChannel — уже встроен в LiveKit React Components, отдельного канала не делаем.
