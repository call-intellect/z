# 14 — Журнал принятых решений (Decision Records)

Этот журнал — **источник истины** при конфликтах в документах. Каждое решение зафиксировано с обоснованием и ссылкой на context.

Любое значимое архитектурное изменение после старта разработки добавляется как новый DR-NNN. Существующие записи не правятся.

Формат:

```
## DR-NNN: Заголовок

Дата: YYYY-MM-DD
Статус: locked / superseded by DR-MMM

### Контекст
Что было непонятно / какая проблема.

### Решение
Что выбрано.

### Обоснование
Почему именно так.

### Альтернативы
Что отвергнуто и почему.

### Последствия
Что меняется в архитектуре.
```

## DR-001: Никаких MVP — продукт строится сразу полностью

Дата: 2026-05-03
Статус: locked

### Контекст

Изначально в драфте было 4 MVP-этапа с поэтапным включением модулей. Стандартный подход «проверим гипотезы на минимуме».

### Решение

Scope продукта = **все 40 модулей сразу**. Никакого MVP.

### Обоснование

- Ресурс разработки большой (со слов владельца).
- Time-to-market не критичен.
- Главные дифференциаторы (M-11, M-16, M-26) имеют смысл только в комплекте — урезанная версия проигрывает Notion AI / Glean по простоте и не выигрывает по уникальности.
- Пилот «на 10 модулях» дал бы сигналы, не отражающие финальный продукт.

### Альтернативы

1. Минимальный MVP-1 (~10 модулей) — отвергнут: не доказывает дифференциацию.
2. Расширенный MVP-1 (~15 модулей) — отвергнут: «временные решения, потом перепишем» дороже.
3. Сразу всё — выбрано.

### Последствия

- Все 40 модулей проектируются под полный продукт. Никаких «временных решений».
- Storage, Orchestration, Privacy проектируются под нагрузку всех модулей с первого дня.
- Roadmap — это порядок старта команд, не фазирование scope ([12-roadmap.md](12-roadmap.md)).

## DR-002: Композиция open-source с обязательным self-host

Дата: 2026-05-03
Статус: locked

### Контекст

Что брать готовое, а что писать своё? И где лежит граница между дифференциатором и commodity?

### Решение

**Композиция готового open-source с жёстким требованием self-host без внешних зависимостей.** Своё пишем только когда нет ни одного подходящего open-source ИЛИ все варианты не self-host'ятся ИЛИ лицензия не позволяет коммерческого self-host.

Граница «брать или писать своё» проходит **не по линии «дифференциатор vs commodity»**, а по линии **«self-host'ится без внешних зависимостей vs нет»**.

### Обоснование

- Дифференциация продукта приходит не от уникального кода, а от уникальной композиции + доменного слоя поверх + UX.
- Главный риск, снимаемый self-host — зависимость от чужого облака, цен и SLA. Self-host даёт «копию у нас на серверах», работающую независимо от судьбы upstream.

### Принципы выбора источника

1. Self-host обязателен.
2. Лицензия позволяет коммерческое использование при self-host (Apache 2.0 / MIT / AGPL — норма; ELv2 / BSL / Commons Clause — запрещены).
3. Активный maintenance.

### Последствия

- При проектировании каждого модуля первый вопрос — «какой open-source это уже делает и self-host'ится?».
- Запрещены: Pinecone, Supabase, Auth0, Sentry SaaS, Vault (BSL — взяли OpenBao), Redpanda Community (BSL — взяли Apache Kafka), Memgraph (BSL).

## DR-003: Гибридная ролевая модель

Дата: 2026-05-03
Статус: locked

### Контекст

Универсальная ниша требует одновременно:
- стандартных функциональных ролей (CMO/CSO/COO/CTO/CFO/HR);
- иерархии (department-head / team-lead / member);
- кастомизации.

Ни одна «однонаправленная» модель не покрывает.

### Решение

**Гибридная ролевая модель с тремя ортогональными измерениями:**

1. **Функциональная роль** (опционально, преднастроенный список из 12 ролей).
2. **Иерархический уровень** (L0 — owner, L1 — C-level, L2 — dept-head, L3 — team-lead, L4 — member).
3. **Кастомизация** (полная гибкость через OpenFGA).

### Обоснование

- Покрывает 95% типовых компаний 20-500 чел сразу.
- Гибкость через кастомизацию — для нестандартных структур.
- Open-source RBAC-библиотеки (Casbin, OpenFGA) поддерживают многомерные модели.

### Последствия

- M-20 — главный owner ролевой модели.
- Все API-проверки идут через все три измерения.

См. [08-security-privacy.md](08-security-privacy.md).

## DR-004: Departure capture — режим, не отдельный модуль

Дата: 2026-05-03
Статус: locked

### Контекст

Нужно ли создавать отдельный модуль «слепок при увольнении сотрудника»?

### Решение

**Не отдельный модуль.** Departure capture реализуется как режим существующих модулей (M-25 + M-12 + M-26).

При уходе сотрудника:
- Знания накапливаются проактивно в течение всей работы (не «потом разберёмся»).
- При уходе — усиленный квиз (через M-26 + M-23 в чате).
- Слепок остаётся доступен после ухода (`active: false`, но данные сохранены).

### Обоснование

- Накопление слепка — продолжающийся процесс, не одноразовое мероприятие.
- Отдельный модуль создал бы дубликацию.

## DR-005: Cold-start через несколько каналов одновременно

Дата: 2026-05-03
Статус: locked

### Контекст

Как новая компания запускает «второй мозг», если у неё ещё нет накопленных данных?

### Решение

**Multi-channel hybrid cold-start:**

1. **Пассивный** — подключение источников (CRM, чаты, метрики) с historical backfill.
2. **Активный квиз** — 5 вопросов по каждой ключевой роли при онбординге.
3. **Свободный дамп** — приглашение «расскажите, что у вас в голове» в формате потока сознания.

Все три канала включены сразу.

### Обоснование

- Никто из конкурентов (Notion AI, Glean, Sana) не реализует все три одновременно. Они полагаются на пассивные данные → ~40% знаний компании. Мы закрываем 100%.
- Это уникальное преимущество, особенно на early stages.

### Последствия

- Onboarding включает wizard с активным квизом.
- Для импорта старых данных есть отдельный flow.

## DR-006: OpenFGA как primary RBAC backend

Дата: 2026-05-03
Статус: locked

### Контекст

Нужен RBAC backend для трёхмерной ролевой модели (DR-003). Кандидаты: Casbin, Oso, OpenFGA, Permify, Cerbos.

### Решение

**OpenFGA primary backend** для M-20. Casbin — официальный fallback при провале PoC по latency.

### Обоснование

- Zanzibar-модель (на которой основан OpenFGA) идеально ложится на 3 измерения нашей ролевой модели.
- Apache 2.0 лицензия.
- Self-host без внешних зависимостей.
- Активная разработка.

### Альтернативы

- **Casbin** — простой, но абстракция RBAC слабее для нашего случая. Оставлен как fallback.
- **Oso** — полу-коммерческий, не self-host friendly.
- **Permify** — менее зрелый.
- **Cerbos** — больше для context-aware authorization.

### Риски

- OpenFGA `ListObjects` может быть медленным на больших графах. PoC обязателен в Phase 1.

## DR-007: M-19 Mood — двухканальная модель сбора

Дата: 2026-05-03
Статус: locked

### Контекст

Как собирать данные о настроении команды без слежки и с уважением к приватности.

### Решение

**Двухканальная модель:**

1. **Пассивный канал** — cross-source сигналы из открытых каналов (Slack public tone, calendar overload, GitHub velocity, открытые упоминания усталости).
2. **Активный канал** — ежедневный 6-вопросный чек-ин.

Оба работают **параллельно**, не альтернативой.

**Двойной opt-in:** компания включает + сотрудник лично соглашается. Без обоих opt-in модуль для конкретного сотрудника не работает.

### Обоснование

- Только пассивный — пропускает важное (личные ощущения).
- Только активный — низкий response rate, шумные данные.
- Оба вместе — полная картина с правом сотрудника отказаться.

### Этические рамки

- Whitelist пассивных сигналов (закрытый список в коде).
- k-anonymity (агрегаты только при ≥5 человек в группе).
- Личные данные сотрудника видны только ему.
- Скрытое уведомление человеку при детектированном тревожном паттерне (без эскалации менеджеру/HR).

См. [08-security-privacy.md](08-security-privacy.md), раздел Mood.

## DR-008: Стек динамических связей знаний (Layer 5)

Дата: 2026-05-08
Статус: locked

### Контекст

Layer 5 — критический модуль. Нужен temporal KG с поддержкой объяснимости связей и time-travel.

### Решение

**Стек:** Graphiti (temporal KG обёртка) + FalkorDB (graph storage) + pgvector (KNN-кандидаты) + cross-encoder bge-reranker-v2-m3 + LLM-арбитр (Sonnet/локальная 70B+) для типа связи и объяснения.

### Обоснование

- **Graphiti** — единственный production-ready temporal KG с провенансом и time-travel.
- **FalkorDB** — Apache 2.0 (RedisGraph fork), активный maintenance, OpenCypher.
- **pgvector** — векторы в той же БД, что метаданные → atomic-обновления.
- **Cross-encoder rerank** обязателен для качества — KNN сам по себе шумный.
- **LLM-арбитр** — без него нет «явных и неявных связей», только похожесть.

### Альтернативы

- **Neo4j** — Enterprise edition коммерческий, Community edition слабее.
- **Memgraph** — BSL (отвергнут DR-002).
- **Kuzu** — слабый community, риск заглохнуть.
- **Pure embedding similarity** — не объясняет тип связи.
- **Pure graph traversal** — не находит «неявные» связи.

### Риски

- Graphiti v0.x stability. Митигация: PoC в Phase 1, custom wrapper, FalkorDB-only fallback.

## DR-009: Single-tenant deployment в первом релизе

Дата: 2026-05-10
Статус: locked

### Контекст

SaaS multi-tenant или self-host single-tenant?

### Решение

**Single-tenant self-host** в первом релизе. Один экземпляр развёртывания = одна компания.

### Обоснование

- Self-host — обязательное требование DR-002.
- Multi-tenant в нашей доменной области (читаем переписку, mood, метрики) — слишком хрупок. Утечка между тенантами катастрофична.
- Изоляция данных гораздо проще на уровне инфраструктуры.

### Последствия

- Архитектура не предполагает «общий пул эмбеддингов» / «глобальный keyspace в FalkorDB».
- Если в будущем потребуется SaaS — это отдельный архитектурный пакет.

### Альтернативы

- Multi-tenant SaaS — отвергнут на старт. Возможен в будущем релизе.

## DR-011: Российские LLM (YandexGPT, GigaChat) исключены из default

Дата: 2026-05-10
Статус: locked

Поддерживать ли YandexGPT, GigaChat по умолчанию?

## DR-012: Никаких кнопок выбора категории / тегов

Дата: 2026-05-10
Статус: locked

### Контекст

Стандартный UI имеет формы, теги, чекбоксы, выпадающие списки. Они снижают барьер ввода данных, но навязывают пользователю мысль о классификации.

### Решение

**Свободный текст или голос — единственные способы ввода данных.** Без форм. Без выпадающих списков. Без тегов. Без чекбоксов. Без multi-select.

AI на сервере классифицирует, маршрутизирует, связывает.

### Обоснование

- Снижает когнитивный барьер до минимума.
- Пользователь не должен думать в наших категориях.
- Меньше ошибок: нельзя «забыть тег».
- Дифференциатор от Notion / Jira / Bitrix24, где UX перегружен.

### Исключения

- Админка — стандартные формы (другая аудитория, другие задачи).
- Подтверждения «да/нет» в ответ на уточняющий вопрос AI — это диалог, не форма.

## DR-013: «Память, не контроль» как сквозной принцип

Дата: 2026-05-07
Статус: locked

### Контекст

В оригинальной концепции были «AI напоминает о просрочках», «контроль выполнения обещаний», «эскалация к руководителю». Это превращало продукт в task-tracker с бюрократией.

### Решение

**Запрещены:**
- напоминания вида «вы обещали X»;
- блокирующие подтверждения;
- активный возврат AI «вы 3 недели назад сказали»;
- эскалации по дедлайнам;
- gamification через очки/значки/лидерборды.

**Разрешено:**
- ответы на прямой вопрос «что я обещал?»;
- автоматическая сводка «что узнали за неделю» по запросу;
- объяснение, почему AI пришёл к выводу;
- видимая польза от действия пользователя (когда он что-то сказал — AI показывает, что узнал).

### Обоснование

- Продукт = память + анализ + подсказки. Не контролёр.
- Adoption строится через видимую пользу, не через давление.
- Дифференциатор от task-tracker'ов и от «корпоративных шпионов».

### Последствия

- M-37 (обещания) переработан: только память, без напоминаний.
- M-19 (mood) — без эскалаций, только сам человек видит свои данные.
- UI без push-нотификаций о просрочках.

## DR-014: Русский UI обязателен, никаких англицизмов

Дата: 2026-05-08
Статус: locked

### Контекст

В технических продуктах часто используется смесь русского и английских терминов («pipeline отчёт», «embeddingи клиента»).

### Решение

**Весь user-facing текст — на простом русском.** Без англицизмов. Без транслита. Запрещены: «embedding», «pipeline», «retrieval», «churn», «pain», «request» в UI.

Английский остаётся в коде, API, технической документации, в админке.

### Обоснование

- Аудитория — нетехнические руководители российского SMB.
- Продукт должен быть понятен директору финансов производственной компании в Иваново.
- Дифференциатор от продуктов с американским UX.

См. [13-glossary.md](13-glossary.md).

## DR-015: Видимость машинерии — скрыта по умолчанию

Дата: 2026-05-09
Статус: locked

### Контекст

В чате с AI пользователь может видеть «Ответ от CMO-агента: ...», «Использован Claude Sonnet, токенов: ...». Это полезно техническим, но шум для остальных.

### Решение

**По умолчанию — чистый ответ без подписей.** Provenance (источники) — да, всегда. Имя агента, модели, токены — только при включении «Расширенный режим» в настройках.

### Обоснование

- Пользователь не должен думать о «специалистах» и «моделях».
- Чистый ответ снижает когнитивную нагрузку.
- Provenance остаётся для доверия — но это «откуда взяли», а не «кто отвечал».

## DR-016: Сегментация — после готового продукта, не до

Дата: 2026-05-08
Статус: locked

### Контекст

«Под какой сегмент SMB строим? Производство? Услуги? IT?»

### Решение

**Не сегментируем продукт под конкретный sub-сегмент в первом релизе.** Архитектура универсальна (любая компания 20-500 чел любой отрасли).

После запуска продукта смотрим, на каких болях/клиентах он реально работает, и тогда фокусируемся.

### Обоснование

- Не подгоняем функциональность под гипотетический сегмент.
- Кастомизация ролей и веток компании — встроена.
- Если построим продукт целиком и он окажется специфичным для одной ниши — проще будет добавить специфические модули, чем «развернуть обратно из узкого MVP».

## DR-017: Цена и экономика на типового клиента

Дата: 2026-05-10
Статус: proposed (требует валидации в production)

### Контекст

Сколько мы можем тратить на LLM на одного клиента, чтобы оставаться в позитивной экономике?

### Решение (предварительно)

**Целевая стоимость инфраструктуры на компанию 100 чел:** ≤ 15 000 ₽ / мес при `routing_policy = hybrid`.

Достигается через:
- Локальные модели для sensitive data (бесплатно).
- Кэш + semantic cache.
- Fast-default (Haiku/Mini) для классификаторов.
- Smart-default (Sonnet) только для главного analysis-loop.

### Состояние

Будет уточнено после первого пилота. См. [12-roadmap.md](12-roadmap.md), Phase 5.

Статус: locked / proposed / superseded by DR-MMM

### Контекст

Почему именно так.

### Альтернативы

При появлении нового DR — добавить запись в конец файла. **Существующие DR не правятся** — они locked. Если решение пересматривается, создаётся новый DR с пометкой «supersedes DR-NNN», старый помечается «superseded by».
