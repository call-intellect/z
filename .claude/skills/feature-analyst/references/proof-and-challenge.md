# Доказательство выбора и состязательная перепроверка

Метод требования владельца №5: всё исследовать → найти лучшее → **доказать** → **перепроверить независимо**. Представляй варианты, доказывай выбор.

## Gap-таблица «конкурент × Z» (обязательная)
| Возможность | Лучший конкурент (как именно) | Что у Z сейчас (vexp-baseline) | Дельта / что строить |
|---|---|---|---|
| … | … | … | table-stakes (догнать) / обгон |
Прямой главный вход для tz-author: видно, где догоняем рынок, а где закрываем недо-обслуженный исход (ценнее).

## Feature-матрица vs JTBD-матрица
- **Feature-матрица** — по table-stakes, статусы **полностью / частично / нет** (НЕ бинарно да/нет).
- **JTBD-матрица** — строки = шаги работы пользователя Z, ячейки = насколько полно/с каким трением конкурент закрывает шаг. Вскрывает gap'ы уровня исхода, а не фичи. Прямой вход в раздел ценности ТЗ.

## Матрица вариантов
2–3 кандидата (один вариант = замаскированное решение). `Критерий | A | B | C` + **источник каждой оценки**. 4–7 критериев = ограничения Z:
MVP до 10 участников · LiveKit-только-медиа · единый Bun+Node+TS · AI-отчёт под тип встречи · prod-разнесение нод · multi-tenancy · стоимость LLM (deepseek-flash).
Критерий «лучше» = пригодность под ограничения Z, **НЕ популярность технологии у конкурента** (анти-карго-культ). Оценивай чужое решение по тому, КАК оно используется под наш сценарий (масштаб/техдолг/опер-нагрузка).

## ADR-каркас (Architecture Decision Record)
```
Контекст (ограничения Z) → Альтернативы (2-3, каждая в steelman-форме) →
Trade-offs (по критериям) → Рекомендация → Последствия (что принимаем/теряем)
```
Каждое решение нумеруй, колонка «Почему» + ссылка на правило/память. Ни одной открытой развилки без рекомендации.

## Assumption-mapping
| Допущение | Ось (desirability/viability/feasibility) | Критичность | Уверенность | Как проверить |
|---|---|---|---|---|
feasibility в Z завязывай на LiveKit-границу, BullMQ, multi-tenancy, LLM-маршрутизацию. Вывод на непроверенном критичном допущении = гипотеза, не факт → в «Ограничения».

## Состязательный второй проход (ядро «перепроверить»)
1. **Steelman** каждой отвергнутой альтернативы — сильнейшая честная версия, не соломенное чучело.
2. **Red-team суб-агент** с задачей **опровергнуть** рекомендацию: контр-источники, контрпримеры.
3. **Независимый retrieval** — red-team стартует с ДРУГИХ запросов (не та же выдача), по возможности под другим углом. Иначе это self-consistency-иллюзия, не проверка.
4. **Стоп-условие:** один полный red-team-проход без новых опровергающих фактов → вывод выжил. Нашёл опровержение → переписать вывод, повтор. Макс. 2 раунда; не сошлось → вынести как HIGH-развилку владельцу.
5. Для каждой рекомендации явно: **на чём она ломается** (граничное условие).

## Защита от ловушек
- **Self-preference:** не засчитывай свой первый проход как «уже доказано».
- **Эхо-камера:** общая стартовая выдача у агентов = не независимость.
- **Volume ≠ validation:** много перепечаток одного релиза ≠ триангуляция.
- **Карго-культ:** «у всех так» ≠ «лучше для Z».
- **Privacy сейчас deprioritized:** «конкурент шлёт данные туда-то» — нейтральный факт в матрице, НЕ вывод-блокер. SPO/eval не упоминать, пока владелец сам не произнёс.

## Evidence hierarchy (по убыванию веса)
первоисточник/код/релиз-ноут > независимый замер/доклад > отзывы (порог) > вторичная аналитика > вендор-маркетинг > соцсети/слухи.
