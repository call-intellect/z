## 1. Проблема (со слов владельца)

1. «Пропала вкладка **Компания / Команда**», где добавляют должности, приглашают и удаляют людей. По факту она переехала в мастер «Знакомства», который не переоткрывается.
2. Управление командой должно быть **на самом видном месте**, отдельной вкладкой, а мастер «Знакомства» — отдельно (6 шагов).
3. **Приглашение** сотрудника нужно встроить прямо в Структуру: добавил человека (почта уже введена) → рядом кнопка «Пригласить» → ему улетает приглашение. Без отдельного раздела в Настройках.
4. «Не вижу, где настраивать **доступы сотрудникам**» — например, какие клоны видит человек, и «много что ещё». Нужна **индивидуальная настройка по каждому сотруднику** по всем пунктам.

## 3. Принятые продуктовые решения (согласованы в чате)

1. Раздел называется **«Команда»**, выносится отдельным видимым пунктом наверх меню (из свёрнутого «Справочника»).
2. Внутри — **один объединённый список** (строка = человек). У вошедших показываем системную роль и действия участника; участников без карточки сотрудника помечаем отдельно.
3. **Приглашения и управление участниками** переезжают в «Команду». Из «Настройки → Организация» этот блок убираем (в Настройках остаются только название и режим видимости компании).
4. **Доступы настраиваются индивидуально по каждому сотруднику** — на его карточке, по всем осям (см. §4–§6).

## 5. Архитектурный вывод

Доступ в Коре сегодня — **в основном ролевой и на уровне компании**, а не на сотрудника. Индивидуально по человеку настраиваются только **три** оси: роль (#1), доступ к клонам (#4) и согласия (#8). Остальное (память, фичи, квоты, видимость) — «вкл/выкл на всю компанию» или производно от роли.

Поэтому требование «индивидуально по каждому сотруднику по всем пунктам» — это **новый слой данных** (персональные переопределения поверх роли), а не доработка UI. Часть (клоны, согласия) уже готова на бэке и требует только экрана владельца; часть (память, фичи, видимость) сейчас в принципе не умеет «по человеку».

## 6. Рекомендация: единый слой персональных доступов

**Ввести персональные доступы сотрудника как override поверх роли-пресета**, переиспользуя проверенный паттерн `CloneAccessGrant`. Роль задаёт дефолт, на карточке сотрудника владелец точечно переопределяет.

### 6.1 Модель данных (рекомендуемая)

`CloneAccessGrant` уже работает в проде и почти является нужной формой (на пользователя, со сроком, мягким отзывом, аудитом). **Не мигрируем рабочую фичу.** Рядом добавляем обобщённую таблицу для остальных осей:

```
EmployeeCapabilityOverride
  tenantId
  grantedToUserId            // кому (или personId — см. §8)
  capability                 // 'memory:regulations' | 'memory:entities' |
                             // 'feature:<key>' | 'panel:operations' | ...
  effect                     // 'allow' | 'deny'  (override поверх дефолта роли/компании)
  expiresAt?                 // опционально
  grantedById, grantedAt, revokedAt?, revokedBy?
  @@unique([tenantId, grantedToUserId, capability])
```

Доступ к клонам остаётся в `CloneAccessGrant`, но **показывается в том же экране** «Доступы» — для пользователя это единый список.

### 6.2 Точка проверки

Весь доступ уже сходится в `RbacService`. Добавляем один шаг: при проверке `capability` сначала смотрим персональный override (`allow`/`deny`), при отсутствии — падаем на дефолт роли/компании. Это одна точка, а не флаги по всему коду.

### 6.3 Почему так (доказательство)

1. **Переиспользуем рабочий паттерн** — `CloneAccessGrant` уже делает per-user + срок + отзыв + аудит.
2. **Не взрываем сложность** — без пресета-роли пришлось бы выставлять ~20 переключателей каждому. Роль = дефолт, override только на отклонения.
3. **Одна точка проверки** в `RbacService` — дешевле, чем плодить персональные флаги.
4. **Закрывает исходный вопрос сразу** — карточка сотрудника = роль + клоны + память + панели в одном месте; владельцу больше не нужен супер-админ для клонов (API уже разрешает — [OrgAdminGuard](../../backend/src/modules/clones/clones-admin.controller.ts#L67)).

Отвергнутая альтернатива (гранулярные роли вместо персональных override) — не даёт «по конкретному человеку», а запрос именно про это.

### 6.4 Индивидуализация по осям — что готово, что требует бэка

| Ось | Сделать индивидуально | Стоимость |
|---|---|---|
| Роль (#1) | уже на сотрудника | UI: перенести в «Команду» |
| Клоны (#4) | уже per-person (CloneAccessGrant) | UI: вывести экран владельцу из зоны супер-админа |
| Согласия (#8) | уже per-person (`analyticsOptIn`, `consent*`) | + 1 API на запись + UI |
| Память: Правила/Сущности (#3) | сейчас per-Org → нужен персональный override | бэк: `EmployeeCapabilityOverride` + проверка в RbacService |
| Тарифные фичи (#5) | сейчас per-Org → персональный override | бэк: то же; но осторожно — часть фич = биллинг, override может конфликтовать с тарифом |
| Режим видимости (#2) | сейчас per-Org (open/strict) | концептуально это политика компании; индивидуально по человеку — спорно (см. §8) |
| Квоты (#6) | сейчас per-Org | редко нужно индивидуально; отложить |

## 7. Целевая структура раздела «Команда»

```
Команда  (верхний уровень меню, видим всем; CRUD-действия — owner/admin)
├── Отделы          — как есть
├── Должности       — как есть
└── Сотрудники      — главный экран, объединённый список
        строка = человек:
          имя · email · должность · отдел · статус приглашения · системная роль
          действия: Пригласить (починенная) · сменить роль · удалить из компании · сброс Telegram
        участник без карточки сотрудника → строка с пометкой «нет карточки»
        клик по человеку → карточка сотрудника:
          ├── Профиль (имя, почта, должность, отдел)
          ├── Доступы:
          │     системная роль (пресет)
          │     клоны (выдать/отозвать/срок) — из CloneAccessGrant
          │     память: Правила / Сущности (персональный override)
          │     панели/фичи (персональный override) — по мере надобности
          │     согласия (analyticsOptIn и т.п.)
          └── (опц.) журнал изменений доступа
```

«Настройки → Организация»: остаются только название компании и режим видимости. Блоки «Участники» и «Приглашения» — убрать.

## 8. Рекомендации по спорным точкам (с обоснованием)

1. **Ключ персонального доступа — `userId` или `personId`?** → **`userId`** для доступов (это про вошедший аккаунт; согласуется с `CloneAccessGrant.grantedToUserId`). Карточка сотрудника связывает Person↔User через `Person.userId`. До принятия приглашения у человека нет аккаунта — значит и персональных доступов ещё нет, что логично (нечего гейтить, пока не вошёл).
2. **Память индивидуально по сотруднику** → **да, через override**, но дефолт остаётся компанийным (текущий toggle в «Админке компании») — чтобы не выставлять каждому вручную. Это закрывает требование, не ломая существующий per-Org механизм.
3. **Тарифные фичи индивидуально** → **только подмножество, не все.** Фичи, завязанные на биллинг (адаптеры, публичное API, экспорт), оставить на уровне компании. Индивидуально имеет смысл то, что про «что человек видит» (память, панели, граф, чат). Иначе персональный `allow` будет конфликтовать с оплаченным тарифом.
4. **Режим видимости (open/strict) индивидуально** → **не делать персональным.** Это политика компании, а не атрибут человека. Индивидуальность достигается ролью (manager со strict видит своё) и персональными грантами на конкретные ресурсы.
5. **Мастер «Знакомства»** → оставить как разовый онбординг (Отделы→Должности→Сотрудники→…), но: (а) сделать переоткрываемым для owner; (б) выровнять «5 экранов vs 6 шагов» виджета; (в) постоянное управление вынести в «Команду», а из мастера убрать роль «единственного входа».
6. **Участник без карточки сотрудника** (владелец, старые приглашения) → показывать в общем списке с пометкой и кнопкой «создать карточку», чтобы привязать к структуре. Никого не теряем.
7. **Баг 400 (tour-progress) и сломанная кнопка «Пригласить»** → чинить **до** редизайна, отдельными мелкими коммитами — это явные дефекты, не зависящие от дизайна «Команды».

## 9. Что НЕ делаем сейчас / риски

- **Не мигрируем** `CloneAccessGrant` в обобщённую таблицу — рабочую прод-фичу не трогаем, обобщаем только новые оси.
- **Не вводим** персональные квоты и персональный режим видимости (см. §8.3–§8.4) — без явной потребности.
- **Риск:** персональные override поверх тарифа/биллинга могут дать «доступ, который не оплачен». Решение — гейтить override фич, завязанных на деньги, верхним лимитом тарифа компании.
- **Риск миграции UI:** перенос управления участниками из Настроек в «Команду» затрагивает RBAC-видимость экранов — проверить, что не-owner получают корректный empty-state.

## 10. Дальнейшие артефакты

Из этого анализа вырастают:

1. **ТЗ «Раздел Команда»** — видимость в меню + объединённый список (Person + Membership) + перенос приглашений/управления участниками из Настроек + починка кнопки «Пригласить» (`personId`).
