# Архитектура: сущность «Решение задачи»

> Документ человеческим языком — владелец читает и одобряет ДО ТЗ. Что есть сейчас → что делаем →
> как это будет выглядеть. Технические якоря — для последующего ТЗ, не для чтения владельцем.

## 1. Зачем (проблема)

Когда сотрудник закрывает непростую задачу, агент-опросник спрашивает: «Расскажи, как ты её решал?».
Сейчас этот ответ **растворяется в клоне человека** — становится топливом его навыка/персоны. Знание «как
именно решили ВОТ ЭТУ задачу» нигде не лежит **отдельной, просматриваемой единицей**: нельзя открыть список
«вот наши решённые задачи и как их решали», нельзя показать это новичку как готовый кейс.

Это ценнейший актив памяти компании — **опыт решения**, который сегодня не материализуется как объект.

## 2. Что делаем (суть)

Вводим **новую отдельную сущность «Решение задачи»** (`TaskSolution`) — единичный кейс:
**название задачи · описание задачи · как решалась (пошагово)** + кто решал + ссылка на исходную задачу.

Отличие от регламента/инструкции (почему отдельная сущность, а не 6-й вид):
- регламент/инструкция — **повторяемая норма** («как делаем ВСЕГДА»);
- решение задачи — **единичный кейс** («как решили ВОТ ЭТУ»). У него другой жизненный цикл: привязка к
  конкретной задаче, не «правило на будущее».

**Мост к нормам (Q3):** когда несколько решений оказываются про один способ (повторяющийся паттерн) — система
помечает это как **кандидата в Инструкцию** («вы уже трижды так делали — оформить как инструкцию?»). Так кейсы
естественно перерастают в норму, но не сливаются вслепую.

## 3. Поля сущности (черновик — уточняется в ТЗ)

| Поле | Смысл |
|---|---|
| `title` | название задачи |
| `taskDescription` | описание задачи (из issue + уточнения) |
| `solutionMd` | как решалась — пошагово, структурированный текст (собирает компилятор) |
| `ownerPersonId` | **исполнитель-владелец** (кто решал) — ось A4, растёт к его клону |
| `sourceIssueId` | ссылка на исходную задачу (трекер) |
| `sourceBlockIds[]` | блоки-источники (ответ опроса + упоминания за день) |
| `skillTags[]` / тема | навык/область — для группировки и «повтор → кандидат в инструкцию» |
| `promotedToInstructionId` | если кейс перерос в инструкцию — ссылка |
| `status` / `version` / `dataClass` | как у регламентов (история версий, класс данных) |

## 4. Точка входа — Q4 (нужно решение владельца)

Ты верно заметил: про решение могут рассказать **не только после опроса**, но и в течение дня (в чате, на
чек-ине, в комментариях к задаче), а мы забираем и анализируем **раз в сутки**.

Сейчас в системе есть **оба пути** (проверено по коду):
- **Немедленный:** ответ на опрос `task.method_capture` применяется сразу (`maybeApplyMethodCaptureAnswer`) →
  становится блоками `reasoning`/`methodology_step`, привязанными к задаче.
- **Суточный свод:** «в течение дня» сказанное (чат/чек-ины/активность по задаче) собирается через block-ingest
  и **суточные дайджесты** (`operations-daily-digest`, `issue-activity-digest`, `skill-manager-digest`).

**Развилка — когда материализуется `TaskSolution`:**
- **(рекомендую) Копим сигналы весь день → материализуем в суточном своде.** Все блоки «как решалась задача X»
  (из опроса + из дневных упоминаний) за сутки собираются по каждой задаче, и **раз в сутки** агент собирает/
  дополняет одну сущность `TaskSolution`. Плюс: не плодит полусобранные версии на каждую реплику; ловит рассказ
  «в течение дня», а не только опрос; совпадает с тем, как уже устроен суточный анализ. Минус: решение видно не
  мгновенно, а к следующему своду (для памяти компании это нормально).
- Немедленно на каждый сигнал — мгновенно, но дробит: одна задача породит несколько недособранных версий, если
  про неё сказали в три захода; и дневные упоминания без опроса можно упустить.

Итог рекомендации: **опрос и дневные упоминания — оба «точки сбора» сигнала; сборка сущности — раз в сутки**
(как клон и регламенты уже консолидируются кроном). Немедленный ответ на опрос при этом не теряется — он просто
один из входов в суточную сборку.

## 5. Связь с клоном (Q2 — двойное назначение)

Ничего не ломаем: ответ **по-прежнему кормит клон** (навык/персона исполнителя растут, как сейчас). Дополнительно
из тех же блоков **материализуется `TaskSolution`**. Один источник — два потребителя: клон (как решает человек
вообще) + витрина решений (как решили конкретную задачу).

## 6. Владение (Q5 — ось A4)

`TaskSolution` **всегда привязана к исполнителю** (`ownerPersonId`) и растёт к **его** клону. Это ровно наша ось
A4 «Владение» из стенда регламентов — переиспользуем: упомянул ≠ решил (в клон/владение попадает тот, кто решал),
при смене исполнителя владение не «течёт из старого снимка».

## 7. Как это будет выглядеть (UI — Q6)

Новая вкладка **«Решения задач»** рядом с регламентами/инструкциями:

```
┌─ Память компании ──────────────────────────────────────────────┐
│ [Регламенты] [Инструкции] [Политики] [Процессы] [Решения задач] │  ← новая вкладка
├────────────────────────────────────────────────────────────────┤
│  🔎 поиск по решениям…                       фильтр: [навык ▾]  │
│                                                                │
│  ▸ Настроить вебхуки Bitrix при 429            Михаил · 2 дня  │
│    как решалась: троттлинг + очередь ретраев…                  │
│  ▸ Ускорить отчёт «Логистик Плюс»              Дарья · 5 дней  │
│    как решалась: предагрегация витрины…            🔁 ×3 →инстр│  ← повтор: кандидат в инструкцию
│  ▸ Онбординг клиента «Ромашка»                 Сергей · нед.   │
└────────────────────────────────────────────────────────────────┘

┌─ Карточка «Решения задачи» ────────────────────────────────────┐
│ Настроить вебхуки Bitrix при 429                 Михаил (владелец)│
│ Задача: вебхуки отваливались по 429 при пиковой нагрузке…       │
│ Как решалась:                                                  │
│   1. Поставил лимитер на исходящие…                            │
│   2. Очередь ретраев с бэкоффом…                              │
│   3. Проверил на нагрузке 3×…                                  │
│ Источник: задача #1487 · опрос + чат за 12.07  [открыть задачу]│
│ [🔁 Похожие решения ×3 — оформить инструкцию]                  │
└────────────────────────────────────────────────────────────────┘
```

Карточка визуально как регламент (название, тело, источник, история версий, владелец), но помечена как
«Решение задачи» и связана с исходной задачей в трекере.

## 8. Как проверим на стенде (добавляем в стенд регламентов)

Расширяем существующий стенд новой осью **A5 «Решения задач»** (корпус+эталон):
- задача закрыта → опрос отвечен → создалась `TaskSolution` {название/описание/как решалось}, привязана к
  исполнителю, растёт к его клону;
- рассказ «в течение дня» (без опроса) → попал в суточную сборку → та же сущность;
- нет содержательного ответа → сущность не плодится (или заглушка без «как решалось»);
- тривиальная/разовая задача под гейтом сложности → не материализуется;
- повтор способа ×N → помечен кандидатом в Инструкцию;
- упомянул коллега ≠ владелец (владение у решавшего — анти-кросс-клон, ось A4).

## 9. Что дальше

После одобрения этой архитектуры → ТЗ (сущность + агент-материализатор + суточная сборка + UI-вкладка + API) →
реализация. Параллельно — ось A5 в корпус/эталон стенда.
