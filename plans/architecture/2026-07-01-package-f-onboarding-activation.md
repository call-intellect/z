# Пакет F — онбординг-активация (trial-окно)

## Контекст
Это не баг, а **решение владельца** (правило №8): гейт биллинга намеренный. Но при онбординге 40–100 юзеров он стоит **до первой ценности** — человек не может наполнить данными и увидеть «письмо COO», упирается в paywall. Владелец решил: включить онбординг-наполнение.

## Что сейчас
Создание сущностей разрешено только при `Subscription.status === 'ACTIVE'` (`frontend/src/hooks/useCanCreate.ts` + backend-энтайтлменты). `DEMO` = read-only + paywall → новые компании не наполняют данные до оплаты.

## Что делаем
Ввести **trial-окно**: в течение него `DEMO`-компания может создавать/наполнять (как ACTIVE, но с квотами). Гейт: `canCreate = ACTIVE || (DEMO && inTrialWindow)`. Enforcement — **на бэкенде** (энтайтлменты/квоты), фронт лишь отражает; frontend-only гейт обходится.

## Развилки — решены
**Р-1. Как мерить окно: (a) N дней от создания org, (b) до первого дайджеста, (c) до N сущностей?** → **(a) N дней от создания org.**
*Доказательство:* дата-окно предсказуемо и коммуницируемо («14 дней бесплатно»), не связано с внутренностями пайплайна. «До первого дайджеста» хрупко (зависит от доставки/крона). «N сущностей» непрозрачно и геймится. Значение N — **крутилка** `billing.trial_days` (AdminSetting, `getDynamic`), дефолт задаёт владелец.

**Р-2. Что остаётся под замком в trial?** → **Создание/наполнение — открыто; жёсткие квоты и необратимые деньги-действия (расширение лимитов, платные интеграции) — под замком.** *Доказательство:* цель окна — дать почувствовать ценность (наполнение), а не раздать платное. Квоты защищают от абуза.

**Р-3. Правило №8 — как выкатываем?** → **Механизм строим сейчас; окно включается ТОЛЬКО с заданным владельцем `billing.trial_days`.** Нет параметра — не выкатываем (правило №8). Тип флага — «решение владельца», строка в `docs/operations/feature-flags.md`.

## Как будет выглядеть
Новая компания на `DEMO`: N дней может создавать задачи/встречи, копить граф, получить «письмо COO». По истечении окна (или при явном апгрейде) — обычный гейт. В UI — баннер «trial: осталось X дней».

## Объём изменений (для ТЗ)
- Backend: в разрешении создания (энтайтлменты/квоты-guard) добавить ветку `inTrialWindow(org)` = `now - org.createdAt < trialDays` при `status==='DEMO'`. Крутилка `billing.trial_days` в `env.schema`/registry + сид + `getDynamic`.
- `frontend/src/hooks/useCanCreate.ts`: `canCreate = ACTIVE || trialActive`; баннер остатка окна.
- Квоты: в trial применять DEMO-квоты (анти-абуз), не безлимит.
- `docs/operations/feature-flags.md`: строка «trial-окно — решение владельца, параметр `billing.trial_days`».

## Тест-план
- Backend enforcement: `DEMO` в окне → create 201; вне окна → paywall/403.
- Крутилка: изменение `billing.trial_days` меняет границу без деплоя.
- Frontend: баннер остатка; после истечения — paywall.
- Анти-абуз: в trial квоты DEMO соблюдаются.

## Открытый параметр владельца
`billing.trial_days` — **значение задаёт владелец** (рекомендация: 14). Без заданного значения окно не включаем (правило №8).
