**Диагноз (доказан кодом + данными):** клон **построен**, но ответный путь refusal-first:
`loadRoleSubgraph` = последние-20-блоков-по-дате (`orderBy createdAt desc take 20`), НЕ поиск по вопросу →
анти-deepfake `assertTopicDensity` требует ≥2 из 20 с `cosineSim(вопрос,блок) ≥ 0.7`. Проверил: subgraph
полон (19-20 блоков) → отказ из-за **cosine<0.7**, не пустоты. Компаундится header-less пространством (тот же
сдвиг, что уронил порог склейки 0.72→0.60). Прогноз был ~50 REFUSED, факт 96 — НЕ ruler-defect (раннер честно
фиксирует реальные отказы), а компаундинг гейта.

**Слой 0:** фиделити построения ВЫСОКАЯ (спот-чек: у Дарьи 14 черт покрывают все 4 её метода — чистка базы/
сегментация/A-B/юнит-экономика; derivation 100% на сматченных). no_false_merge **FAIL** — frozen-снимок Елены
отсутствует (versioning отдал обе версии support Игорю: v2/active + v1/superseded, оба Игорь).

## Чему научился

1. **«Крутилка» читается из AdminSetting, не из ENV — override ENV бесполезен.** Квота `aiChatQuota.dailyLimitAdmin`
   через `getDynamic` (admin→ENV→code). Shell-override `AI_CHAT_DAILY_LIMIT_ADMIN=100000` НЕ применился, и правка
   `.env` тоже — эффективный лимит остался 50 из AdminSetting. Первый baseline «съел» квоту на c047 (загрязнение).
   Фикс: `UPDATE AdminSetting` + сброс Redis-счётчика `quota:*:ai_chat_messages_per_day:*` → перепрогон. Урок:
   для лимита/порога/флага источник правды — AdminSetting; проверяй эффективное значение в AppModule-контексте,
   не в `bun -e`.
2. **LLM-судейские метрики недостоверны — и под нагрузкой, и системно.** Слой-0 recall: первый прогон 2/18 (11%,
   крашнул на пустом LLM-ответе под нагрузкой), перепрогон с бэкоффом ×5 — 3/18 (17%), но Дарья ВСЁ ЕЩЁ 0/4, хотя
   её 14 черт вручную покрывают все 4 метода. Значит дело не только в нагрузке: recall-судья **теряется при многих
   кандидатах** (у Дарьи 14 черт → судья не находит матч). Метод-док прямо предупреждает: «сверялка — агент на
   мягкой оси, для строгой метрики нужна калибровка cosine-порог + судья 2-из-3». Урок: (а) не гонять LLM-судью
   конкурентно с другой LLM-нагрузкой; (б) бэкофф между ретраями; (в) **молчаливый fail-open в метрике = ложный
   сигнал** (тот же класс, что fail-open в verify черт) — отличать «LLM упал» от «реального промаха»; (г) для
   надёжного Слоя-0-recall нужен embedding-предфильтр top-k кандидатов + 2-из-3 голосов, иначе число врёт вниз.
   Строгий вывод по фиделити брал из РУЧНОГО спот-чека, не из авто-числа.
3. **Гейтинг probe идёт в контексте вызывающего** (transitionToCategory→suggest в seed-скрипте), не в диспетчере —
   поэтому knobs достаточно выставить до boot того контекста, что зовёт suggest; свежий AppModule-boot гидрирует
   AdminSettings сам.
4. **Канал Б: воронка dispatch работает (93%), но ингест — узкое место** (~3-4 блока/мин, LLM-насыщение). Для
   больших наполнений закладывать время; последовательно, не конкурентно с baseline (общая локальная LLM).
5. **topic-density гейт + последние-N-ретрив = ядро refusal-first.** Это Слой 2/3 (ответ), не Слой 0 (построение).
   Baseline это доказал числом: клон построен, но политика ответа душит его собственную фактуру.
