# 2026-07-03 — `analyze.worker` мигрирует на `LlmRouterService`

## Что было поставлено

Третья и самая рискованная из трёх независимых vNext-фич сессии (реестр не-сделанного, строка 285): главный AI-отчёт о встрече (`analyze.worker`) вызывал ИИ через отдельный, устаревший `LlmFallbackService` — мимо единого реестра моделей, бюджетной защиты, tenant-атрибуции расходов, которые уже работают для всего остального ИИ в продукте. Цепочка `solution-blueprint` → `tz-author` → `tz-orchestrator`, с батч-вопросом владельцу по ходу написания ТЗ (модели 1:1 сначала vs сразу экономия — выбрано 1:1).

## Как решал

**Реальность оказалась глубже, чем показывал REALITY-CHECK ТЗ — дважды.** Ни одна из двух находок не была видна на этапе написания ТЗ, обе всплыли только при реализации:

1. При написании ТЗ обнаружил (и получил решение владельца), что `'tasks'` в типе `agentType` — мёртвый литерал (функционал снят 2026-06-10, никогда не передаётся) — 6 «операций» оказались пятью.

2. **При приёмке Фазы 2** (сидирование 1:1-цепочки) — критическая находка: скрипт, написанный буквально по контракту ТЗ, писал легаси-совместимую цепочку в JSON-поле `LlmTaskRoute.providers`. Но реальный роутинг (`refreshCache()`) **полностью игнорирует это поле**, если для `taskType` уже есть tier-строки (новый формат, Фаза A.4) — а они уже существовали для 4 из 5 нужных задач (из `seed-llm-task-routes-default.ts`, дешёвые модели прошлой сессии). Патч в исходном виде переключил бы реальный роутинг только для одной задачи из пяти (`report-by-type`, у которой tier-строк не было) — для остальных четырёх сработал бы тихий регресс: JSON записан правильно, но никем не читается, а реальные вызовы продолжили бы идти по старым дешёвым моделям. Это ПРЯМО противоречило явному решению владельца «1:1 везде на первом шаге». Не отложил находку («технически контракт выполнен, разберёмся потом») — переписал скрипт на запись tier-строк (canonical-паттерн `AdminAiModelsService.putChain()`) и подтвердил эффект не только чтением БД, но и прямым вызовом `refreshCache()` в реальном коде роутера — самый строгий из возможных уровней проверки для этого класса бага.

**Технический риск-менеджмент:** миграция `callLlm()` спроектирована так, что старое тело метода (`callLlmLegacy()`) осталось байт-в-байт нетронутым — единственный способ быть уверенным, что откат по аварийному рубильнику (`aiFeatures.analyzeWorkerRouterEnabled=false`) действительно возвращает точное старое поведение, а не «почти такое же». Тесты подтверждают это тем же путём: `buildWorker()`-хелпер устроен так, что мок `router.call` делегирует в ТОТ ЖЕ мок `llm.complete`, поэтому все 11 существующих тестов (594 строки, написанные до этой сессии) проверяют одно и то же бизнес-поведение независимо от того, какой путь исполняется — сильное доказательство поведение-сохраняющей миграции, а не просто «тесты прошли».

## Что вышло

Все 4 фазы реализованы и закоммичены на ветке `fix/invite-password-existing-user-multi-org`. `bun run typecheck`/`build` зелёные на каждой фазе; `bunx vitest run src/modules/ai/` (весь модуль, 59 файлов/587 тестов) без регрессий; `analyze.worker.spec.ts` — 11→14 тестов (не потеряно ни одного). 2 предсуществующих провала в интеграционном спеке подтверждены идентичными на коде до этой фичи через `git stash` — не моя регрессия.

`second-brain/04_не-сделано/README.md` — строка 285 закрыта, добавлена новая (снятие рубильника + `LlmFallbackService` — отдельное будущее решение владельца, не хвост). `ai-jobs.md`/`feature-flags.md` обновлены. Push не делался — ждёт отдельного подтверждения владельца. Ручная QA-проверка через `qa-tester` на реальной встрече — не выполнялась (код ещё не задеплоен, честно зафиксировано как открытый пункт, не выдумано).

## Чему научился

- **«Буквально по контракту ТЗ» не значит «работает».** Скрипт из Фазы 2 полностью соответствовал написанному в ТЗ коду и прошёл бы формальную приёмку по acceptance-критериям (R3/R4 проверяли именно поле `providers`) — но не достигал бы цели владельца. Автор ТЗ (я сам, в этой же сессии) ошибся в предположении о формате хранения, скопировав его из другого, тоже потенциально нерабочего скрипта, вместо того чтобы свериться с актуальным местом истины (`refreshCache()`, которое я же читал ранее для Фичи 1!). Урок: при написании контракта для миграции данных — всегда проверять эффективное поведение чтения (не только формат записи) на реальных данных, а не полагаться на прецедент другого скрипта без проверки, что тот прецедент сам работает.
- **Самый ценный момент проверки — не «тесты прошли», а «то же самое отличие в архитектуре доказано на исполняемом коде».** Прямой вызов `refreshCache()` после патча (а не только чтение БД) — единственный способ закрыть класс багов «данные записаны правильно, но код их не читает», который формальные acceptance-критерии на уровне SQL/Prisma не ловят.
- **На самом рискованном участке продукта — минимальность изменения важнее элегантности.** `callLlmLegacy()` как точная копия старого кода (не «улучшенная» версия) — осознанный выбор ради возможности доказать эквивалентность старого/нового пути тестами, а не полагаться на code review.
