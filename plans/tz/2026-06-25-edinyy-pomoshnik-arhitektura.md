## 1. Зачем (причина)

Три проблемы, вскрытые разбором и проверкой на проде:

1. **Сломанные ответы в Telegram.** Прод-разговор `cmqs42gdq01lj01qqsblfdon4` (24.06): на простые вопросы бот вместо ответа вывалил сырой JSON. Корень — **ReAct-петля concierge** (`for i<maxSteps=6`): chat-v2 каждый раз отвечал корректно, но петля не понимала, что инструмент уже вернул готовый ответ, зацикливалась и через `buildPartialAnswer` отдавала обрезанный JSON.
2. **Два мозга.** В кабинет ведёт два пути к ответам: «Мастер» (бывш. Concierge) и **прямой** chat-v2 («Спросить» `/chat`, чат встречи, чат задачи, Command Palette, кусочный `/memory`). Пользователь видит то одну, то другую логику.
3. **Вторая скрытая петля внутри chat-v2.** Кроме петли concierge, в самом chat-v2 живёт `route → plan → step-retrieval → sufficiency` — ещё одна петля + 3 агента-дубля, утяжеляющие ответ.

## 2. Цель и принципы

- **Один вход — Мастер.** Единственное пользовательское лицо AI. chat-v2 — внутренний движок-ответчик без своего фронта.
- **Один запрос → одно действие/ответ, один проход.** Никаких ReAct-петель ни в Мастере, ни в chat-v2. Сложных многошаговых сценариев в одном сообщении нет (подтверждено владельцем).
- **Уточнение — это диалог из 2 ходов, а не петля.** Если данных не хватает или подходит несколько вариантов — один уточняющий вопрос, ответ ловится детерминированно.
- **Тяжёлую модель тратим только там, где агент трогает слова пользователя напрямую** (синтез). Всё механическое — лёгкое.
- **Ship-On:** каждая фаза выкатывается включённой. Допустимы только kill-switch (аварийный) и параметр-решение владельца. Выбор модели — крутилка (маршрут в БД), не код.

## 3. Что НЕ трогаем (инварианты)

- Telegram = проактивный канал; ответы на напоминания (план/отчёт/probe) — **структурный ввод**, не вопрос.
- `daily_checkin_self → DailyCheckIn → дашборд` — нельзя потерять.
- Probe — закрытый контур уточнений (фиксация решений/ответственных) — работает, оставляем.
- RBAC/whitelist инструментов, undo-лог и confirm для мутаций, память беседы.
- Сам RAG-поиск (вектор + граф + структурные фильтры + RRF) — механика здоровая, не переписываем.

## 4. Целевая архитектура

```
                       ┌─────────────────────────────────────────────┐
   Кабинет / Telegram  │                  МАСТЕР                      │
   (единственный вход) │  (GPT-5 mini, tool-use)                      │
        ──────────────▶│                                              │
                       │  Слой 1: детерм. перехват «ответа на то,     │
                       │          что МЫ спросили» (без LLM-маршрут.)  │
                       │   • probe? confirm? clarify-pending?          │
                       │   • ждём чек-ин (план/отчёт)?                 │
                       │                                              │
                       │  Слой 2: диспетчер свежего сообщения          │
                       │          (ОДИН LLM-вызов):                    │
                       │   answer | action{tool,args} | note |         │
                       │   checkin_self                                │
                       │                                              │
                       │  Слой 3: исполнение, один проход              │
                       │   answer  ──▶ chat-v2 (движок, ниже)          │
                       │   action  ──▶ один инструмент (+confirm)      │
                       │   note    ──▶ ingest                          │
                       │   checkin ──▶ DailyCheckIn                    │
                       └───────────────────┬──────────────────────────┘
                                           │ answer
                                           ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │              chat-v2 — движок-ответчик (single-pass, 4 вызова)     │
   │                                                                    │
   │  1. ПОНИМАНИЕ (DeepSeek pro): summary+история+вопрос →             │
   │     3 формулировки + фильтры(дата/сущность/тип) + флаг aggregation  │
   │  2. ПОИСК: на каждую формулировку — 30 кандидатов (вектор+граф),    │
   │     слияние RRF; счёт «сколько» — настоящим COUNT/таблицей          │
   │  3. ПЕРЕРАНЖИРОВЩИК (DeepSeek flash): 30→18, ВСЕГДА (по количеству),│
   │     видит summary+историю+вопрос+3 формулировки                    │
   │  4. СИНТЕЗ (DeepSeek pro): ответ из 18 блоков — структура,          │
   │     цитаты-ссылки, честность, переспрос-при-вариантах, флаг         │
   │     needsClarification                                             │
   │  5. КОНТРОЛЁР заземления (DeepSeek flash): анти-выдумка;            │
   │     при needsClarification — пропускается                          │
   └──────────────────────────────────────────────────────────────────┘
```

**Тред диалога один и принадлежит Мастеру.** chat-v2 — **без своей памяти**: на каждый вызов Мастер передаёт `история + суммаризация`. Отдельной `ChatV2Conversation` под Мастером нет.

## 5. Модель по каждому агенту (маршруты в БД, не код)

| Агент | Модель | Почему |
|---|---|---|
| **Мастер** (Слой 2 + действия) | **GPT-5 mini** | tool-use — надёжный вызов инструментов (DeepSeek слабее) |
| **Понимание** | **DeepSeek pro** | один короткий вызов, но определяет ВЕСЬ поиск; ошибка тихая и фатальная |
| **Переранжировщик** | **DeepSeek flash** | читает 30 кандидатов (дорого по токенам), ошибки мягкие |
| **Синтез** | **DeepSeek pro** | финальный текст человеку — тут тратимся |
| **Контролёр (groundedness)** | **DeepSeek flash** | узкая бинарная проверка, частая. Если на тесте рубит хорошее (false-abstain) — поднять до pro |

Изменение маршрутов — через `LlmTaskRoute` (seed/patch-скрипт), без правки кода.

**Цель:** один пользовательский вход, chat-v2 без своего фронта.
- Схлопнуть в Мастер: «Спросить» (`/chat`), Command Palette Ask, мобильный Ask, орфаны `/chat-v2`, `/assistant`.

**Фронтенд входа — плавающая кнопка (поглощает ТЗ [`2026-06-20-assistant-fab-notifications-and-clone-picker.md`](2026-06-20-assistant-fab-notifications-and-clone-picker.md)).** Работа целиком фронтовая, бэк не трогаем:

Сейчас баг: кнопка открывает панель уведомлений `AssistantSidebar`, где чат задвинут в 4-ю вкладку «Спросить» (регресс коммита `d9730afb`). Видимую кнопку прямого `ConciergeChat` вернуть; `AssistantSidebar` как FAB — демонтировать.
- **Переключатель собеседника вверху чата — слим-вкладки «Помощник компании | Клоны ролей»** (дефолт — помощник, не блокирующее меню). Сейчас два счётчика из разных мест — свести в один.

### Ф2 — Убрать ReAct-петлю, ввести 3-слойный single-pass `[x]` (коммиты e5fb42d6, 6a430537, 01bb3958)
**Цель:** один запрос → одно действие/ответ, без петли.
- **Удалить:** `for i<maxSteps`, loop-guard, `buildPartialAnswer`, `passthrough`, инструмент-обёртку `ask_chat_v2`, мёртвый `clarifyMinConfidence`.
- **Слой 1 (детерм. перехват):** проверка pending-state ДО LLM — открытый probe → probe-handler; pending confirm → выполнить/отменить (Redis `channelConfirmKey` есть); **pending clarify → вернуть ответ в исходное действие (НОВОЕ)**; ждём чек-ин → check-in handler. LLM тут только разбирает ответ внутри handler, не маршрутизирует.
- **Слой 2 (один LLM-вызов):** диспетчер заменяет И входной `dialog-classify`, И ReAct-выбор инструмента. Возврат: `answer | action{tool,args} | note | checkin_self`. **Рекомендация:** расширить существующий `dialog-classify` (он уже на доменной лексике), добавив `action`+tool/args.
- **Слой 3 (один проход):** `answer → chat-v2 напрямую`, текст as-is; `action → один инструмент` (мутация → confirm; read → сразу); `note → ingest`; `checkin_self → DailyCheckIn`.
- **Мастер для `answer` — чистая витрина (решение 2026-06-25).** Текст chat-v2 (ответ ИЛИ уточняющий вопрос) отдаётся **слово в слово, без переписывания/пересказа/суммаризации**. Причины: (1) маркеры `[BLOCK:id]` → кликабельные ссылки порвутся при переписывании; (2) ответ уже написан тяжёлой моделью по строгим правилам и прошёл контролёр заземления — повторная обработка GPT-5 mini только просадит качество и рискует вернуть выдумку; (3) синтез сам считает свой ответ финальным. Голос «Коры» — в синтезе, не во втором проходе. Это сегодняшний `passthrough`, возведённый в правило для всего `answer`-пути.
- **Витрина — только для `answer`.** Для `action`/`note`/`checkin_self` Мастер пишет свой короткий статус-текст («Поставил задачу», «Записал», «Подтвердить — да/нет?»).
**Файлы:** [`concierge.service.ts`], [`conversational.service.ts`], [`query-classifier.service.ts`], [`telegram-bot.adapter.ts`].
**Приёмка:** прод-кейс `cmqs42gdq01lj01qqsblfdon4` («позиционирование», «сколько встреч с Александром») — чистый текстовый ответ, ни одного сырого JSON, ноль зацикливаний.

### Ф3 — Петля уточнения (clarify), замкнутая `[x]` (chat-v2 сторона bffc7796; concierge resume 6a430537; канальный перехват 01bb3958)
**Цель:** уточняющий вопрос работает и его ответ возвращается в тот же контекст.
- Синтез возвращает флаг **`needsClarification`** в структурированном выходе.
- **Камень 1 (кэш):** при `needsClarification=true` оркестратор **пропускает** `answerCache.set` (переспрос — не ответ).
- **Камень 2 (общий тред):** тред один, принадлежит Мастеру; флаг переводит тред в состояние **«ждём уточнения»**, которое ловит **Слой 1** → следующая реплика человека уходит обратно в тот же вопрос chat-v2 с полным тредом.
- Контролёр заземления при `needsClarification=true` **пропускается**.
**Файлы:** [`chat-v2.service.ts` (оркестрация, `applyGroundednessGate`, `answerCache.set`)], синтез-промпт, Слой 1 (pending-clarify state).
**Приёмка:** «что приняли на встрече с Александром» при 3 встречах → Мастер задаёт уточнение человеческим языком; ответ «июньскую» разрешается в нужную встречу; переспрос не закэширован.

### Ф4 — Упрощение цепочки chat-v2 `[x]` (retrieval/rerank/K f51e5a0e; слияние понимания 381b717c)
**Цель:** ~10 вызовов → 4, без второй петли.
- **Слить** `dialog-multi-query` + `dialog-extract-plan` → один вызов «понимание вопроса» (3 формулировки + фильтры + флаг `aggregation`). *Условие:* приёмочный тест (см. §8.1) держится.
- **Удалить** `dialog-classify` внутри chat-v2 (intent приходит из Слоя 2), `rag-route`, `rag-plan`, `rag-sufficiency`. Метод итеративного поиска **законсервирован** (см. §7).
- **Поиск:** ввести два числа вместо `topK=12`: **K_retrieve=30** (сбор/кандидаты), **K_context=18** (в ответ). Сложность «агрегат» — из флага `aggregation`, без отдельного LLM-вызова.
- **Переранжировщик (`rag-rerank`) — оживить и переставить:** работает ВСЕГДА когда кандидатов > K_context (сейчас мёртв: `rerank_min_pool=12` ≥ среза 12). Сужает **30→18**. Подавать ему **полный комплект:** summary + последние сообщения + исходный вопрос + 3 формулировки + кандидаты (сейчас видит только голый вопрос).
- **Счёт «сколько»** — настоящим COUNT/табличной веткой ДО сужения (не по числу вытащенных блоков).
- **Синтез — усилить промпт:** (A) структура по содержанию (вывод первой фразой + список/разделы для составных ответов; простой факт — коротко); (B) **переспрос при нескольких вариантах** — описать каждый вариант **своими словами, человеческим языком** (что за встреча, когда, о чём), источник ссылкой, без техномеров; один уточняющий вопрос.
- **Контролёр заземления** — оставить как анти-выдумку.
**Файлы:** [`chat-v2.service.ts`], [`chat-v2-retrieval.service.ts`], [`rag-pipeline.prompts.ts`], [`dialog.service.ts`], [`multi-query-expansion.service.ts`], [`query-plan-extractor.service.ts`]. Крутилки `CHAT_V2_TOP_BLOCKS`→разнести на K_retrieve/K_context; `rag.rerank_min_pool`.
**Приёмка:** §8.

## 8. Приёмка (проверки на реальных данных)

1. **Слияние понимания (Ф4):** ~10 реальных вопросов прогнать «старый (2 вызова) vs новый (1 вызов)», сверить фильтры+формулировки. Держится — сливаем; проседает — раздельно.
2. **Числа 30/18:** на реальных вопросах подтвердить, что не мало (широкие «расскажи всё про X») и не много (шум).
3. **false-abstain контролёра:** как часто рубит ХОРОШИЙ ответ. Часто — поднять модель до pro.
4. **Кейс Александра:** entity-resolution не сматчил имя → не должно быть ложного «не нашёл»; при нескольких встречах — переспрос.
