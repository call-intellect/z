# ТЗ — ASR без пословных таймингов (S5-02): нулевая длительность и «поведение участников» на каждой встрече

> **Приоритет: 🟠 P2** (бьёт по доверию: «провёл встречу — длительность ‘<1 мин’, поведение ‘недоступно’» на КАЖДОЙ записи). Подтверждено в ретесте №1 и №2 ([plans/analysis/2026-06-07-retest2-RESULTS-technical.md](../analysis/2026-06-07-retest2-RESULTS-technical.md) §4) — лог `vox.no_words` сработал и на сегодняшней встрече `01KTGNR4…` (09:14:56, «437 симв., без пословных таймингов»).
> **Тип:** расследование → фикс (backend, ASR). **Одна функция:** восстановить пословные тайминги (или честно их источник), чтобы длительность и поведенческая аналитика были не нулевыми.
> **Статус развилки:** корень ещё не подтверждён — нужен сырой ответ Vox. Диагностика для этого УЖЕ в коде (Фаза 3 прошлого ТЗ), осталось прочитать её и решить. Снимает строку из реестра «не-сделано» (2026-06-06, ASR word-timestamps).

## 1. Проблема

`vox` (`v3_e2e_rnnt`) на проде возвращает `status=COMPLETED` с непустым текстом, но `words.length === 0` ([vox.service.ts:194,233](../../backend/src/modules/ai/services/vox.service.ts#L194)). Следствие:
- длительность встречи считается из пословных таймингов → 0 → UI показывает «<1 мин» (честный fallback на recording есть, но это не настоящая длительность речи);
- «Поведение участников» → «Поведенческая аналитика недоступна для этой записи» (нет word-level данных для метрик говорения).

Это **не** падение — пайплайн доезжает; но продуктовая ценность (тайминги, кто сколько говорил, главы по времени) теряется на каждой встрече.

## 2. Что уже сделано (контекст)

Фаза 3 ТЗ [2026-06-06-meeting-report-reliability-and-ui-honesty.md](2026-06-06-meeting-report-reliability-and-ui-honesty.md):
- парсер расширен на `segments[].words` (на случай, если тайминги лежат там);
- добавлен PII-safe диагностический лог `vox.no_words` ([vox.service.ts:233-256](../../backend/src/modules/ai/services/vox.service.ts#L233)), который пишет **форму ответа** Vox без текста: `rawKeys`, `nestedKeys`, `hasSegments`, `segmentsCount`, `firstSegmentKeys`;
- Фаза 4 закрыла симптом честным UX («недоступно» вместо «тишина 100%»).

Чего НЕ хватает: **прочитать эту диагностику** с реальной встречи и по форме ответа решить — (а) тайминги под другим ключом (фикс парсинга), (б) Vox не вернул их из-за submit-параметра (фикс запроса), (в) модель `v3_e2e_rnnt` их не отдаёт в принципе (сменить модель/режим).

## 3. Решение

### Фаза 1 — Снять правду с прода (расследование, read-only)
Прочитать метаданные `vox.no_words` со свежей встречи:
```
diag chain --trace mtg_01KTGNR4MGBQPAGCF5BDEFKPRV --json   # найти запись vox.no_words → поле meta
# или diag logs --at-least WARN --from <дата> --json → отфильтровать message ~ 'no_words'
```
Зафиксировать `rawKeys` / `nestedKeys` / `hasSegments` / `firstSegmentKeys`. Дополнительно (если доступно) — снять **полный сырой ответ** одного COMPLETED-таска Vox в dev/стейдже (там PII не важен), чтобы увидеть точную структуру.

### Фаза 2 — Фикс по результату Фазы 1 (дерево решений)
- **(а) тайминги есть, но под другим ключом** (`firstSegmentKeys` показывает `start/end/word` или `timestamps`/`alignments`/`chunks`): расширить парсер `vox.service.ts` на этот ключ → пословные тайминги поднимаются, длительность/поведение оживают. Самый дешёвый исход.
- **(б) таймингов нет, но Vox умеет их по submit-флагу** (напр. `word_timestamps:true` / `enable_word_time_offsets` / `response_format:'verbose'`): добавить флаг в submit-запрос Vox (через прокси `agent-lia`). **Осторожно** — неизвестный submit-параметр может дать 400 (прецедент с `language`); сначала мини-e2e на прокси, флаг за ENV.
- **(в) `v3_e2e_rnnt` не отдаёт word-timing в принципе:** оценить альтернативную модель/режим Vox или отдельный forced-alignment шаг (текст готов → выровнять по аудио). Это самый дорогой исход; решение — за владельцем (стоимость/латентность vs ценность таймингов).

### Фаза 3 — Верификация
- На тест-встрече: `diag report --meeting <id>` → `transcript.totalDurationSeconds > 0`; UI `/result` → длительность реальная (не «<1 мин» при настоящей минутной встрече), «Поведение участников» — ненулевое.
- `vox.no_words` перестаёт писаться (или пишется только на реально пустых).

## 4. Acceptance-сигнал
Свежая встреча > 1 мин → длительность совпадает с фактической; «Поведение участников» показывает доли говорения; в логах нет `vox.no_words` на встречах с речью.

## 5. Объём / риски / прод
- Фаза 1 — read-only диагностика (нужен «можно в прод»). Фаза 2 — от 1 строки парсера (исход а) до смены модели (исход в). Риск submit-флага (исход б) — за ENV + мини-e2e.
- **Прод-операций** — зависит от исхода: (а) только рестарт backend; (б) новая ENV (Шаг 1 prod-deploy-log); (в) — отдельно.
