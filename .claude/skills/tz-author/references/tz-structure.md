# Каркас ТЗ — аннотированная структура

Полная структура для нетривиальной фичи. Для лёгкого ТЗ (фикс на 1–2 файла) бери только: Цель → Scope → 1–2 фазы → Acceptance → DoD. Тяжёлый разбор/таблицы/research → в `plans/analysis/`, в ТЗ — вывод + ссылка.

## Целевой frontmatter
```yaml
---
type: tz
status: ready-to-implement   # пока есть незакрытые HIGH-развилки — draft
feature: <kebab-имя>
date: YYYY-MM-DD
owner: <кто принимал продуктовые решения>
relates_to: [plans/tz/...md, plans/analysis/...md]
supersedes: plans/tz/...md   # опц.
---
> Анализ: `plans/analysis/...md` · Статус согласования: <дата>
> Принцип: <одна строка — главный инвариант фичи>
> Вне scope / отложено владельцем: <список с ссылками на vNext-ТЗ>
```

## Секции (по порядку)

### 1. Цель + Зачем
Одно предложение «что работает после реализации» + болезненное состояние сейчас и чем решение лучше. research-числа — с URL.
- ✅ «Гость без регистрации входит во встречу по magic-link; сейчас требуется аккаунт, отваливается 40% приглашённых.»
- 🚫 «Улучшить онбординг гостя.» (не проверяемо)

### 2. REALITY-CHECK (обязательно)
Фактический статус по коду на момент написания: что уже реализовано / мертво / сломано. Таблица:
| Компонент | Статус по коду | path:line | Вывод для фаз |
|---|---|---|---|
| `GuestController.join` | есть, но без проверки tenant | `guest.controller.ts:42` | фаза 1 — фикс |
Если фича на 60–70% готова — пересчитай scope под остаток. Висящий контракт фронт↔бэк — первая фаза-фикс.

### 3. Принятые решения владельца
| # | Решение | Обоснование | Дата |
|---|---|---|---|
| Р1 | magic-link, не пароль | ЦА не разработчики | 2026-06-03 |
Помета «не пересматривать без владельца».

### 4. Доказательство выбора
Состязательная таблица из `proof-loop.md` (или ссылка на анализ). Решения Б1…Бn с колонкой «Почему» + ссылка на правило/память.

### 5. Scope
**Входит:** маркированный список проверяемых пунктов.
**Не входит:** каждый — с судьбой (vNext-ТЗ-ссылка или «не делаем, потому что»).

### 6. Граничные контракты с другими ТЗ
Что мокать/стабить, что реально здесь. Пример: «используем только статус `DEMO` из FSM встречи (FSM в ТЗ-X); `InnLookupService.lookupByInn` вызываем, реализация — ТЗ-Y».

### 7. Контракт-first (единый источник правды)
Дословно, чтобы суб-агент копировал, а не сочинял:
- **Prisma**: модель/поля/enum с `@@index`/`@@unique` и `///`-комментариями.
- **DTO**: Zod-схема + Swagger-описание + machine-readable коды ошибок (`409 guest_already_joined`).
- **Очередь**: имя BullMQ-очереди, payload, формат `jobId` (идемпотентность).
- **Поток**: ASCII «вход → сервис → очередь → воркер → БД».
- **Перечни фронт↔бэк** (accept-форматы файлов, enum-значения) — один источник, обе стороны ссылаются. Урок `document-ingest`: фронт принял `.doc`, бэк упал.

### 8. Границы фичи `✅ Always / ⚠️ Ask first / 🚫 Never`
Локальные для фичи рамки автономии суб-агента (не дубль CLAUDE.md). Пример: `🚫 Never: хард-удаление системной таблицы`.

### 9. Фазы + граф зависимостей
`[ ]`/`[x]`, dependency-ordered: схема Prisma → backend-сервис → контроллер/DTO → frontend (`ApiDto→DomainModel→UiModel`) → e2e. Таблица: какие строго последовательны (и почему «A раньше B»), какие реально параллельны.
Каждая фаза самодостаточна для одного суб-агента: мини-картография `path:line`, Цель / Что входит / **Что НЕ входит** / точные файлы / зависимости поимённо / Acceptance / тесты / `Закрывает: R3, R7`.

### 10. Acceptance per-фаза
Машинные предикаты. Детали — `acceptance-and-ears.md`.

### 11. Pre-mortem / Риски + ревью-аспекты
Что может пойти не так + что искать `strict-production-review-gate` (auth-дыры, идемпотентность, FSM встречи, потеря данных, observability).

### 12. Idempotency / feature-flag / prod-deploy
Скрипты повторно = no-op; флаг + дефолт OFF + kill-switch; затронутые шаги prod-deploy-log (см. `project-invariants-checklist.md`).

### 13. DoD + Итог
DoD — универсальный чек качества (≠ Acceptance). **Итог** — пустая рамка, заполнит оркестратор по факту.

## Что выносить в `plans/analysis/`
Состязательные таблицы целиком, research с цитатами, разбор альтернатив, UX-аудит, backlog. В ТЗ — вывод + ссылка. Правило проекта: анализ = идея/разбор, ТЗ = контракт на реализацию.
