# Клоны собираются плохо: почему «должность + человек → клон» не работает и почему черты не рождаются

> Вскрыто в ходе Фазы 0а клон-стенда 2026-07-03 (наполнял клонов через реальный конвейер и упёрся в то,
> что клоны не строятся). Две независимо подтверждённые находки + данные по эмбеддингам живого прогона.
> Это **Слой 0** (фиделити ПОСТРОЕНИЯ клона) — корень, который иначе спишется на «политику ответа».

## TL;DR для владельца

«Создал должность → назначил Олю → клон сразу есть» **сейчас не работает**, по трём причинам, две из
которых — **чинибельные дефекты кода**, а третья — калибровка порогов, которая делает клоны пустыми даже
при наличии корма:

1. **Сломанный провод (Разрыв №1):** назначение человека из кабинета идёт мимо события, которое запускает
   сборку клона роли. → клон роли ждёт воскресного крона, а не собирается сразу. **Чинибельно.**
2. **Заготовка клона при создании роли не заводится** — только «профиль роли в статусе forming». Сам клон
   (ExecutablePersona) не создаётся до первой успешной сборки. **Полу-чинибельно (продуктовое решение).**
3. **Черты почти не рождаются из корма (Разрыв №2, корневой):** порог кластеризации черт (`cosine ≥ 0.78`
   **захардкожен** + группа ≥3) слишком тугой для живой речи. Перефразировки одного и того же метода
   садятся на cosine 0.72–0.85 — ровно на границе — и «кластер из 3» почти не набирается. **Данные ниже.**

Итог: даже когда сотрудник ЯВНО повторяет один подход разными словами, система не сшивает это в черту →
клон остаётся пустым → на вопрос отдаёт честный отказ «нужно больше встреч». В проде хуже, чем на стенде:
живые говорят разнороднее моих специально-близких синтетических формулировок.

## Находка A — «создал роль + назначил человека → клон» не запускается

Проверено трассировкой продового пути (не тестового).

### A1. При создании должности клон-заготовка не заводится
`RolesDomainService.create` (`src/modules/roles-domain/services/roles-domain.service.ts:128`):
- создаёт `RoleProfile` со `status:'forming'` (`:146`) — это профиль-заготовка, НЕ клон;
- выдаёт `CloneAccessGrant` владельцу/админам (`:187`,`:214`);
- **`ExecutablePersona` (сам клон) НЕ создаётся.**

### A2. Разрыв №1 — назначение из кабинета не эмитит `role.bearer_changed` (сломанный провод)
Авто-сборка клона роли завязана на событие `role.bearer_changed` → его слушает
`RoleClonePersonaVersioningHandler.handle` (`src/modules/knowledge-core/services/role-clone-persona-versioning.handler.ts:87`,
`@OnEvent('role.bearer_changed')`), который заводит версию клона и сразу зовёт `buildForRole`.

**Но событие эмитится ТОЛЬКО из `AppointmentsService`** (`src/modules/appointments/services/appointments.service.ts:373` `maybeEmitBearerChanged`, вызовы `:185/:260/:315`).
**Кабинет назначает человека через `PersonsService`**, который создаёт `Appointment` **напрямую**
(`src/modules/persons/services/persons.service.ts:328` и `:538`, `tx.appointment.create`), **минуя
`AppointmentsService` и НЕ эмитя событие** (в конструкторе `PersonsService` нет `EventEmitter2`, `:30-36`).

Комментарий в самом обработчике (`role-clone-persona-versioning.handler.ts:13`) утверждает, что событие шлётся
«из AppointmentsService / PersonsService» — но по факту `PersonsService` его НЕ шлёт. Расхождение «как
задумано» vs «как в коде». **Это же я подтвердил в стенд-скрипте:** после `PersonsService.update({roleId})`
версионирование не сработало, пришлось дёргать `versioning.handle(...)` вручную.

**Следствие:** клон роли для свежей должности соберётся только на еженедельном кроне (вс 06:00), не «сразу».

**Как чинить (просто и сразу):** внедрить `EventEmitter2` в `PersonsService` и дёргать `role.bearer_changed`
(тот же payload `{tenantId, roleId, oldPersonId, newPersonId, changedAt}`) при появлении/смене активного
`PersonRole` в `create/update`. Один провод — и назначение из кабинета мгновенно поднимает клон роли.

### A3. Авто-триггеры сборки клона (полный список)
| Триггер | Что делает | Работает из кабинета? |
|---|---|---|
| Событие `role.bearer_changed` | мгновенная сборка клона роли | **НЕТ** (Разрыв №1) |
| Крон `ExecutablePersonaBuildCron` `0 6 * * SUN` | строит клоны всех профилей и ролей | да, но раз в неделю |
| Крон-вотчер `0 */2 * * *` | только ПЕРЕсборка person-персон с существующим snapshot | не создаёт первый snapshot/роли |
| On-demand при вопросе (`askPersonV2`/`askRoleV2`) | пробует собрать на лету | да, но без корма → отказ |

## Находка B — черты не рождаются: порог кластеризации туг для живой речи (КОРЕНЬ)

Клон человека = кластеры похожих reasoning-блоков → LLM-черта. Кластер формируется, если блоки попарно
`cosine ≥ GROUP_SIMILARITY_THRESHOLD` **(= 0.78, ЗАХАРДКОЖЕН**, `specialist-3-7-skill.service.ts:59`) и в
группе `≥ knowledge.skillClusterMinObservations` (**= 3**, getDynamic, `:326`; не в admin-реестре).

### B1. Данные живого прогона стенда (58 attributed reasoning-блоков, чистая синтетика)
Насеял 4 клонам по ≥3 близких формулировки на метод. Вброс — детерминированной атрибуцией (userId→person).
Результат сборки: **всего 6 черт**, распределение рваное:

| Носитель | reasoning-блоков | блоков с ≥2 соседями cosine≥0.78 (минимум для кластера ≥3) | родилось черт |
|---|---|---|---|
| Дарья | 11 | **3** | 3 ✓ |
| Михаил | 16 | 1 | 2 |
| Сергей | 14 | 1 | 1 |
| Игорь | 8 | 1 | 0 |
| Елена | 9 | **0** | 0 |

Число черт почти линейно следует за «сколько блоков вообще способны попасть в кластер ≥3» — а таких
единицы, хотя блоков 8–16.

### B2. Косинусы садятся ровно на границу 0.78 (nearest-neighbor, отсортировано)
- **Дарья** (собралась): `0.849, 0.849, 0.841, 0.836, 0.836, 0.835, 0.835, 0.793, 0.793, 0.766, 0.732` — плотное ядро выше 0.83 → черты есть.
- **Елена** (0 черт): `0.838, 0.838, 0.778, 0.778, 0.761, 0.761, 0.726, 0.725, 0.658` — только 2 блока ≥0.83, дальше провал через границу → ни одного кластера ≥3.
- **Игорь** (0 черт): `0.842, 0.842, 0.817, 0.817, 0.794, 0.764, 0.764, 0.733` — то же: пары есть, тройки нет.

**Вывод:** перефразировка одного метода живым языком даёт cosine ~0.72–0.85. Порог 0.78 режет ровно посередине
этого облака, поэтому «кластер из 3» набирается редко и случайно (у кого формулировки чуть теснее — собрался,
у кого чуть шире — ноль). Это не про объём корма (у Михаила 16 блоков и 2 черты), а про **калибровку порога**.

### B3. Почему в проде будет ХУЖЕ
Мои формулировки специально близкие (я сеял «≥3 близких на навык»). Живой сотрудник на встречах формулирует
один принцип гораздо разнороднее и вперемешку с контекстом → cosine ещё ниже → кластеры ещё реже → клоны ещё
пустее. Это прямой механизм риска Т13 «клон пуст не из-за кода вокруг, а из-за того, что ядро не сшивает корм».

### B4. Отягчающие пороги на ВЫХОДЕ (даже собравшиеся черты гейтятся)
- `MIN_TRAITS_FOR_ANSWER = 3` — **хардкод** (`clones.service.ts:62`): person-клон с <3 черт → отказ `starved_profile`.
- `PERSONA_MIN_TRAITS = 3` (`env.schema.ts:607`): персона не компилируется без 3 черт.
- `PERSONA_ROLE_AGG_MIN_PERSONS = 2` (`env.schema.ts:608`): клон роли требует ≥2 носителей с профилем — одиночная
  должность (типовой случай SMB!) клон роли не соберёт вообще.
- `CLONE_V2_ENABLED = false` по коду-дефолту — экспертная ветка ответа заперта.

## Что это меняет для baseline стенда (Слой 0 атрибуция)

Часть провалов baseline будет **не про политику ответа (Слой 2/3), а про непостроенную черту (Слой 0)**.
Без этого разделения ТЗ-1 «разворот политики» нафиксил бы не то. Конкретно: отказы клонов, у которых <3
черт, — это Слой 0 (кластеризация не сшила корм), а НЕ refusal-first политика. Стенд обязан их развести.

## Рекомендации (приоритет — под «просто и автоматически»)

1. **[код, дёшево] Починить Разрыв №1** — эмитить `role.bearer_changed` из `PersonsService.create/update`.
   Даёт «назначил → клон роли поднялся сразу».
2. **[код, корень] Ослабить/сделать крутилкой порог кластеризации** `GROUP_SIMILARITY_THRESHOLD` 0.78 → ~0.72
   (в AdminSetting, не хардкод) и/или `skillClusterMinObservations` 3 → 2. Без этого клоны пусты даже при корме.
   Проверить на данных: при 0.72 у Елены/Игоря кластеры ≥3 появляются.
3. **[код] `PERSONA_ROLE_AGG_MIN_PERSONS` → 1** как валидный кейс (одиночная должность), не только стенд.
4. **[продукт] Что показывать у клона без корма** — сейчас честный отказ «нужно больше встреч». Возможно,
   заводить видимую «заготовку клона» сразу при создании роли (каркас + прогресс наполнения), чтобы «клон
   появился сразу» визуально, а качество ответа догоняло по мере корма.
5. **[стенд, сейчас]** для baseline снизить пороги стенда (cluster, roleAggMinPersons) — но зафиксировать в
   отчёте, что при прод-дефолтах клоны НЕ собираются (это и есть находка, а не «пройденный этап»).
