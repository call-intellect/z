# Машинно-проверяемые Acceptance и требования

Acceptance — это то, что оркестратор проверит **грепом / re-Read / typecheck-lint-build / тестами без человека**. Если критерий нельзя проверить машиной — он не критерий, а пожелание.

## Требования R1…Rn — нумеруй и трассируй
Каждое требование — номер + формулировка-предикат. Запрещены прилагательные «быстро / удобно / корректно / оптимально / гибко» — только проверяемое условие.

**EARS-шаблоны:**
- Ubiquitous: `Система shall <поведение>.`
- Event-driven: `Когда <триггер>, система shall <поведение>.`
- State-driven: `Пока <состояние>, система shall <поведение>.`
- Unwanted: `Если <нежелательное условие>, then система shall <реакция>.`
- Optional: `Где <фича включена флагом>, система shall <поведение>.`

**Given/When/Then** (для сценариев):
```
Given гость без аккаунта и валидный magic-link
When он открывает ссылку
Then создаётся Participant(kind=GUEST, tenantId=<из ссылки>) и он попадает в комнату
```

**Сквозная трассировка.** Каждая фаза заканчивается строкой `Закрывает: R3, R7`. Оркестратор грепом проверяет, что все R покрыты фазами и реализованы.

## Acceptance per-фаза — формы предикатов
- **Грепаемый маркер**: «в `guest.service.ts` появился метод `joinByMagicLink`» (оркестратор грепнет символ).
- **Пример вход→выход**, включая **негативный**:
  - `POST /guest/join {token: valid}` → `200 {roomToken}`.
  - `POST /guest/join {token: expired}` → `410 magic_link_expired` (негативный путь обязателен).
- **Число/порог**: «при >50 участниках — `409 room_full`».
- **Команда**: `bunx vitest run src/modules/guest/guest.service.spec.ts` зелёный; `bun run typecheck` 0 ошибок; Swagger `/api/docs` отдаёт новый тег.
- **Идемпотентность как критерий**: «повторный прогон `seed-guest-roles.ts` = no-op (0 INSERT во втором прогоне)».

## Негативные и граничные пути (всегда)
Для каждого позитивного критерия — негативный: null/пропуск, `manualOverride`, 0-результат, expired/forbidden, конкурентный доступ, пустые и огромные данные. Урок: тесты «оно запускается» не ловят регрессий; тест проверяет **поведение**.

## DoD ≠ Acceptance
- **Acceptance** — что именно работает в этой фазе (специфично).
- **DoD** — универсальный чек качества на каждом коммите:
  - `bun run typecheck` (вкл. `.spec`), `bun run lint` (0 errors), `bun run build` зелёные.
  - vitest по затронутому модулю целиком (не только новые файлы).
  - second-brain обновлён по таблице производных заметок; prod-deploy-log — при затронутых schema/scripts/ENV/очередях/эндпоинтах.
  - Рефлексия записана.

## Bad → Good
| ❌ Bad | ✅ Good |
|---|---|
| «Гость удобно входит» | «`R4`: Когда гость открывает валидный magic-link, shall создаваться Participant(kind=GUEST); проверка — e2e `guest.e2e-spec.ts`» |
| «Обрабатывать ошибки» | «expired-токен → `410 magic_link_expired`; тест на негативный путь» |
| «Тесты написаны» | «`bunx vitest run guest.service.spec.ts` зелёный; покрыты null/expired/room_full» |
