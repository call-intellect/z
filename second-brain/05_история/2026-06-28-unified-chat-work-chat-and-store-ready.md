# Единый чат: разбор для собственника + докрутка ТЗ (work_chat задачи, store-ready)

## Что было поставлено
1. Найти ТЗ про «полноценный внутренний мессенджер между сотрудниками» (аналог Telegram/WhatsApp), прочитать, подтвердить владельцу что это оно, и выдать краткие возможности «со стороны собственника» по пунктам.
2. Докрутить связку **трекер ↔ чат**: из задачи создавать чат и переписываться по ней, из переписки попадать в карточку (журнал/файлы) и обратно.
3. Заложить так, чтобы фундамент подходил под будущее мобильное приложение в **App Store + Google Play + RuStore**.
4. Только ТЗ — код не писать.

## Как решал
- Документ: [`plans/tz/2026-06-21-unified-chat-kora-tz.md`](../../plans/tz/2026-06-21-unified-chat-kora-tz.md) (статус `ready-to-implement`, ещё не реализован). Подтвердил по тексту (стр. 34/36) — это именно чат сотрудник↔сотрудник.
- Вскрыл расхождение: чат задачи **уже есть** (`IssueComment` + WS `issue.chat.*`, presence/typing/вложения/упоминания/голос — Wave 1-3), но единое ТЗ выводило `Issue` из scope, а `work_chat` фигурировал ТОЛЬКО как тип в `InboxItem` — обещание цели без контракта и фаз.
- Владелец выбрал **вариант A (единое ядро)**: чат задачи = `work_chat`. Дописал в ТЗ:
  - **Ф2.5** — `ConversationKind.work_chat`, `Issue.conversationId @unique`, миграция `IssueComment→Message`, `IssueAttachment.messageId`, двусторонняя навигация карточка↔переписка (Р9, R27–R31).
  - **Ф4** — единый экран как точка входа: поиск ленты `q=` (люди/группы/задачи), сортировка `recent|active|unread`, общий badge непрочитанного вкл. work_chat (R32–R33).
  - **Ф6** — `PushService` транспорт-агностичный (APNs/FCM/RuStore/VAPID) + store-compliance (удаление аккаунта, UGC-модерация) под App Store/Google Play/RuStore (R34).
  - Контракт (`Message.contentHtml/thanksUserIds`, `InboxItem.linkedIssue`, эндпоинты), prod-deploy-log, DoD, pre-mortem.

## Что вышло
- 1 файл, +60/−22, коммит `c83a5875`, push в `dev`. Кода не трогал (по требованию).
- Консистентность проверена: 34 ссылки на Ф2.5/work_chat, R27–R34 на месте, FCM согласован с Р8 без отмены owner-решения.

## Чему научился
- **Разрыв «цель обещает — контракт молчит».** В ТЗ `work_chat` был в `InboxItem`, но отсутствовал в enum и фазах. Проверять обещания раздела «Цель» против фактического Prisma-контракта и фаз — иначе фича «как бы есть», а делать нечего.
- **Owner-решение vs новое требование разрешается уточнением, а не отменой.** Р8 «FCM никогда фундамент» конфликтовал с «нужен Google Play». Снято через транспорт-агностичный `PushService`: FCM — один из транспортов для Play-сборки, не единственная опора; ядро доставки от него не зависит (RuStore/APNs для РФ).
- **Не строить заново то, что есть.** Чат задачи существовал на `IssueComment` — корректный ход не «новый чат задачи», а пересадка существующего на единое ядро + депрекейт старого пути записи.

## Докрутка в той же сессии — внешняя переписка с клиентами (Ф3.5, Р10)
Владелец поднял мысль про переписку с внешними людьми/клиентами на той же платформе. Пришёл с предложением, развёл два сценария (реактивный = поддержка `ticket`; проактивный = сотрудник пишет клиенту первым). Владелец выбрал: **и поддержка, и проактивные клиентские чаты** + вход **magic-link-гость → опц. лёгкая дорегистрация**. Дописал в ТЗ:
- **Ф3.5** — `ConversationKind.external`, модель `ConversationAccessLink` (bearer к одному разговору, TTL/отзыв), `User(kind='external_client', verified)` (теневой → подтверждённый), guest-вход + guest-scope (только `access` external/normal), анти-абьюз (rate-limit/captcha/report), ФЗ-152, контур-изоляция (Р10, R35–R40).
- Снял прежний vNext-пункт «коллаб для внешних контрагентов» (строка 27 ТЗ).
- Эндпоинты `/external-conversations`, `/external/access`, `/external/register`; флаг `EXTERNAL_CHAT_ENABLED`; вкладка «Клиенты» в Ф4; риск публичного входа в pre-mortem.

**Урок:** «Вне scope»-пункты ТЗ — живые: новое требование владельца может снять vNext-ограничение, и это надо явно вычеркнуть из «Вне scope», иначе ТЗ противоречит само себе (обещали в фазе, но в «не входит» висит запрет).
