# Цикл улучшения 1 — материализатор «Решений задач»

## Что было поставлено

Владелец: «сделать анализ, предложить гипотезы, написать ТЗ, поправить и запустить новый цикл — всё
исправлять с каждым циклом лучше». Автономный мандат: циклы без одобрения; при доказанной чистоте —
сразу коммит+пуш. Отправная точка — baseline A5-стенда (итерация 0): **PASS 9 · FAIL 2 · N/A 1**.

## Как решал

1. **Анализ корня** (Bash find/grep + Read, vexp-хук блокирует Grep/Glob): дефект 1 — гейт материализации
   по длине сигнала (`minSignalChars=40`), нет проверки сути; дефект 2 — `personSubjectIds=[owner]` жёстко.
   Компилятор документа — общий (регламенты/процессы/политики), трогать его схему рискованно для осей A1–A3.
   Нашёл `EntityResolutionService.resolvePersonByHint` — готовый резолвер имени→Person (не выдумывает).
2. **Гипотеза + ТЗ** (`plans/tz/2026-07-07-task-solution-materializer-fixes.md`): один точечный LLM-проход
   `task-solution-extract` возвращает оба сигнала — `hasConcreteMethod` (гейт) + `solverNames` (кто РЕАЛЬНО
   решал, не рассказал). Изолированно от компилятора → нулевой риск регресса A1–A3.
3. **Реализация:** промпт `task-solution-extract.prompt.ts` + `TaskSolutionRefinerService` (fallback при
   сбое LLM) + `buildOne`: после char-гейта, до компилятора — extract; `!hasConcreteMethod && !existing`
   → `skippedNoMethod`; `subjectIds = union(owner, resolvePersonByHint(solverNames))`. Kill-switch
   `taskSolution.refineEnabled` (реестр+сид+feature-flags, ON). Route переиспользован (`compile-org-document`) —
   без новой инфры роутера.
4. **Верификация:** 5 новых unit-тестов (гейт, update-путь не режем, fallback, union субъектов, нет утечки);
   перепрогон стенда A5 итерация 1 на свежем тенанте с реальным LLM.

## Что вышло

- **Стенд A5 итерация 1: PASS 9 → 11 · FAIL 2 → 0 · N/A 1**, идемпотентность Δ=0.
  - `a5-no-answer` → `created=false` (реальный LLM поставил `hasConcreteMethod=false` на «Да фигня, само решилось»).
  - `a5-multi-solver` → `subjects=[Иван, Михаил]` (клон соисполнителя растёт).
  - **Сторожа no-leak держатся** (это была главная риск-точка): `a5-ownership-solver` subjects=[Михаил]
    (Сергей-рассказавший НЕ добавлен), `a5-owner-not-mentioner` subjects=[Иван] (Дарья НЕ добавлена).
    Реальный LLM корректно отличил решавшего от рассказавшего — precision-bias в промпте сработал.
- Unit 16/16 (5 новых). typecheck ✓ · lint ✓ · build ✓ (build требует heap 8GB — грабля tsc OOM).
- 1 пре-существующий фейл `admin-webhooks-mgmt` (retryDelivery) — не мой домен, вне scope.
- Доки: ТЗ (status: done), реестр не-сделанного (2 дефекта → «Закрытые»), feature-flags, prod-deploy-log Шаг 7.

## Чему научился

- **Компилятор документа общий** — не пихать в его tool-схему поля под один тип (`task_solution`): регресс
  осей регламентов A1–A3. Правильно — отдельный точечный проход, изолированный.
- **`resolvePersonByHint(tenantId, hint)`** — канонический резолвер имени→Person (exact→alias→fuzzy→embedding→
  LLM-арбитр), возвращает null если не уверен → безопасен для «роста субъектов» (не выдумывает клоны).
- **owner=assignee — сильный фундамент:** оба дефекта оказались НЕ в атрибуции владельца (она держится
  структурно), а в (а) гейте и (б) росте субъектов — точечные фиксы поверх крепкого ядра.
- **LLM-гейт с двумя bias'ами:** содержательность — bias к ПОЛНОТЕ (не резать краткие реальные решения);
  соисполнители — bias к ТОЧНОСТИ (не приписать чужое). Оба подтвердились сценариями-сторожами стенда.
- **Стенд окупился:** он же нашёл дефекты, он же за один перепрогон доказал фикс (было→стало), включая
  защиту от регресса (сторожа no-leak) — цикл замкнулся дёшево.
