# Итоговый отчёт эксперимента «Variant A vs Б» — 3 фикстуры × 2 варианта × 2 судьи

Дата: 2026-05-25
Модель Variant A/Б: `deepseek-v4-pro` (thinking on)
Судьи: `deepseek-v4-pro` (только на fixture-01) и `claude-opus-4-7` через KIE (на всех 3)

Цель: выяснить, нужен ли в цепочке отчёта по встрече предварительный шаг block-ingest или большая Pro-модель справится за один объединённый вызов.

|---|---|---|---|---|
| 01-pilot (высокий интерес → пилот) | 419.7 с / $0.168 | 165.8 с / $0.048 | 2.5× | 3.5× |
| 02-objections (возражения → ЛПР отсутствует) | 376.7 с / $0.170 | 93.5 с / $0.031 | 4.0× | 5.5× |

**Б в среднем в 3.5× быстрее и в 4.6× дешевле.**

## 4. Главные наблюдения

### Что в пользу Б
1. **Меньше точек отказа.** Один вызов проще отладить, нет каскадного провала «block-ingest сломался → дальше пустота».
2. **Pro-модель видит весь контекст разом** и даёт более связные главы (нет пропусков начала встречи, нет переставленных блоков).
3. **Цитаты в задачах** — Б систематически их подкрепляет, A в нескольких случаях вернул только agg-ссылку на evidenceBlockId без цитаты.
4. **Стоимость и время** — в 4-5 раз меньше.

### Что в пользу A
1. **Резюме богаче** — длиннее, со структурой по разделам, иногда с таблицами. Это субъективно «приятнее читать».
2. **block-ingest даёт IdeaBlock'и** — без них нельзя строить граф знаний компании (цепочка №2). **A не заменяется на Б целиком — он нужен для памяти.**

### Замеченные баги в проде-цепочке (Variant A)
1. **fixture-03-cold: A не вернул quality_score корректно** — overallScore=undefined в нашей нормализации. Судья тоже отметил «строка вместо объекта». Это значит, что в проде на похожих встречах оценка качества может «теряться» — стоит добавить валидацию в [meeting-analyze-v2.worker.ts](backend/src/modules/knowledge-core/workers/meeting-analyze-v2.worker.ts).
2. **fixture-02-objections: A схлопнул 6+ обязательств в 2 задачи без цитат.** Это серьёзная регрессия для real-world применения (продажникам нужны конкретные поручения, а не агрегаты).
3. **fixture-01-pilot: A пропустил поручение «прислать кейс» от Анны.** Тоже потеря смысла.

### Расхождение судей на простой фикстуре
- **DeepSeek-судья** (fixture-01): Б 18, A 14 → Б победил с разрывом 4.
- **Claude-судья** (fixture-01): Б 16, A 16 → ничья / A победил по словам.
- **Вывод:** одиночный судья — субъективен. На простых фикстурах разные модели расходятся. **Для серьёзных архитектурных решений нужны 2-3 независимых судьи + ≥5 фикстур.**

## 5. Архитектурные выводы

**Б не заменяет A целиком — но Б покрывает 80% потребностей пользователя за 20% бюджета.**

Возможная архитектура продакшена:
1. **Б — быстрый отчёт для пользователя** (1 вызов на сыром транскрипте → главы, задачи, резюме, оценка качества) → пользователь видит результат через ~2 минуты после встречи.
2. **A (block-ingest) — фоновая память компании** (отдельный pipeline для построения графа IdeaBlock → Entity → Theme). Запускается параллельно, не блокирует UX.
3. **Не пересекаются.** Б делает «отчёт по встрече», A — «вклад встречи в граф знаний».

Это **меняет наш [meeting-analyze-v2.worker.ts](backend/src/modules/knowledge-core/workers/meeting-analyze-v2.worker.ts)** концептуально: вместо «block-ingest → 4 параллельных vN-агента» — «Б для отчёта параллельно с block-ingest для графа».
