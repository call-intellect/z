## ⚠️ Это ПРЕДВАРИТЕЛЬНЫЙ план — почему и что будет дальше

Полноценное ТЗ **сейчас НЕ оформляем.** Этот документ фиксирует только то, что найдено при изучении **текущего** кода knowledge-core, чтобы не потерять картину. Финальный план будет после того, как изучим **новый** код.

**Скоро в коде ожидаются изменения, которые прямо заденут предмет теста:**
- **Клоны** — меняется механика (цепочка skill-trait → persona → ответ клона). Заденет всю **Ф4** и пункт «контекст клона в правах спрашивающего».
- **Доступ к базе знаний (разграничение знаний внутри компании)** — сейчас граф фильтруется только по `tenantId+status`; готовится разграничение по правам/секретности (развилка Р-1, анализ [knowledge-access-levels-and-provenance](2026-06-06-knowledge-access-levels-and-provenance.md), строка в [реестре не-сделанного](../../second-brain/04_не-сделано/README.md)). Заденет **Ф5** (чтение мозга: чат/поиск/«Память компании» начнут фильтровать по доступу) и контекст клона/чата.

**Поэтому перед финализацией обязательно:**
1. Заново изучить изменённый код (клоны + доступ к знаниям) — vexp/чтение, не по памяти.
2. Сверить, не сместились ли цепочки/пороги/эндпоинты, на которые опирается план (особенно §4.3 diag-снимок, Ф4, Ф5).
3. Обновить фазы, acceptance-критерии и спецификацию `diag`-расширения под новый код.
4. Только потом — финальный план/ТЗ и прогон.

До этого момента документ держим как **карту найденного**, а не как контракт на исполнение.

## 0. Цель

Проверить НЕ кабинет глазами пользователя (это закрыто manual-QA), а **механизмы под капотом**:

1. **Агенты работают и не падают** — конвейер ingest, 14 специалистов Слоя 3, ~40 cron-агентов отрабатывают без ошибок/таймаутов; провалы видны, а не проглатываются.
2. **Второй мозг наполняется** — из событий рождаются `IdeaBlock` (draft→canonical), `Entity`, связи `IdeaBlockLink` (7 типов) и `EntityLink` (6 типов), кластеры `Theme`. Дедуп блоков и сущностей реально срабатывает.
3. **Клоны создаются** — reasoning-блоки → `SkillTrait` → нормализация концептов → `RoleProfile` → `ExecutablePersona` → ответ клона с анти-фальшивкой.
4. **Правильность** — связи осмысленные, дедуп не склеивает разное и не плодит дубли, специалисты пишут в правильные сущности, клон не выдумывает.

| Слой теста | Окружение | Чем |
|---|---|---|
| Единичный e2e встречи (FSM → запись → транскрипт → отчёт → мост в граф) | **прод-кабинет** | Playwright + `diag trace/chain/llm-calls` |
| UI-честность отчёта/«Память компании»/клонов/чата | **прод-кабинет** | Playwright |

> Демо-кабинет «ТехноСтрим» **наполнен сидом** (данные положены напрямую CLI), а НЕ живым конвейером ([[../../second-brain/01_projects/demo-workspace]]). Поэтому он годится проверить «рендерит ли UI наполненный мозг», но НЕ «наполняют ли его агенты». Живое наполнение проверяем только на стенде/прод-кабинете через реальные события.

## 3. Центральная сложность (почему обычный тест кабинета это не покажет)

1. **Внутрянка невидима в UI.** Нет пользовательских страниц для блоков/связей/тем (UI тем — «вне Фазы 4»; отладочная `/settings/admin/knowledge-core` вырезана из клиента — [[../../second-brain/01_projects/admin-org-knowledge-core]]). Playwright граф не видит. Текущий `diag` заточен под встречи. → главный наблюдатель внутрянки — **расширенный `diag` против БД/метрик** (§4.3).
2. **Пороги объёма гейтят весь граф.** Связи блоков — от 50 canonical, темы — от 100, клон роли — от ~10 reasoning-блоков, граф сущностей — от 3 co-mention. На одной короткой встрече (прогон 2: 2–3 блока) граф/темы/клоны **физически не построятся** — это порог, не баг. → решаем через Р2 (снизить пороги + объём).
3. **Граф строят cron-агенты по расписанию** (темы — `15 * * * *`, граф сущностей — `0 * * * *`, клоны — `0 */6 * * *`, reframing — `0 3 * * *`). `diag` read-only — крон не дёрнет. → на стенде дёргаем воркер/крон вручную; на проде — ждём тик или ловим окно.
4. **Часть критического пути уже чинилась** (МТЗ №1): B2 (один диспетчер вместо 14 воркеров), B3 (draft→canonical), Ф1 (subject-атрибуция для клонов) — в архиве реестра не-сделанного. План должен **подтвердить, что фиксы приземлились**, а не искать заново.

## 4. Инструменты

### 4.1. Playwright (живой пользователь, прод-кабинет)
Как в manual-QA: на каждом шаге `browser_snapshot` + `browser_console_messages` + `browser_network_requests`. Видит ровно те поверхности, что существуют: страница результата встречи, «Память компании», `/clones`, `/roles/[id]/skill-profile`, чат, поиск, `/tables`.

### 4.2. `diag.ts` текущий (read-only, прод)
`trace/report/meetings/logs/chain/llm-calls/call`. Покрывает встречу: FSM, транскрипт, AI/ASR-вызовы (провайдер/модель/успех/стоимость, промпт+ответ), технический след по `traceId=mtg_<id>`, логи `≥WARN`. Прод-доступ — только с явным подтверждением владельца в сессии ([[feedback_prod_diagnostic_access_requires_confirmation]]).

### 4.3. `diag` РАСШИРЕНИЕ — «снимок графа» (Ф0, спецификация)
Новые **read-only** команды, бьющие в уже существующие эндпоинты (`/api/v1/org-admin/knowledge/*` метрики/связи/сущности + `/api/v1/knowledge/*` blocks/entities/themes/graph/search; auth — super-admin cookie + `X-Org-Id`):

| Команда | Что отдаёт | Чем проверяет |
|---|---|---|
| `diag graph --org <tenantId>` | counts: `IdeaBlock` по статусам (draft/canonical/merged_into/archived), `Entity` по типам, `IdeaBlockLink` по relationType, `EntityLink` по relationType, `Theme` по статусам, `RawEvent`; **dedup-ratio** = canonical/total | «мозг создаётся вообще»; дедуп работает |
| `diag blocks --org <tenantId> [--signal <type>] [--status canonical]` | примеры блоков: name / signalType / confidence / evidenceCount / dataClass | блоки осмысленные, signalType размечен |
| `diag entities --org <tenantId> [--type person]` | примеры сущностей + mentionsCount + aliases + mergedIntoId | сущности резолвятся/мёржатся |
| `diag links --org <tenantId> [--kind block\|entity]` | примеры связей: relationType / confidence / explanation / from→to | связи правильного типа и осмысленные |
| `diag themes --org <tenantId>` | темы: name / branch / weight / число блоков / число сущностей | кластеризация сработала |
| `diag specialists --org <tenantId>` | counts: `Decision` / `Insight` / `Idea` / `Regulation` / `Process` / `Experiment` | Слой 3 реально пишет (B2/B3/B4) |
| `diag clones --org <tenantId> [--role <id>]` | `SkillTrait` (по профилю), `SkillTraitConcept`, `RoleProfile`, `ExecutablePersona` (status/version) + пример черты | клон-цепочка наполняется |

> Если для какого-то счётчика готового эндпоинта нет — добавить тонкий read-only aggregate в knowledge-debug-контроллер (не мутирующий). Реализация — задача Ф0, не этого документа.

## 6. Верхнеуровневые фазы

Метод во всех фазах: действие → сверка **UI ↔ БД/логи** → находка по единому формату (§9). Шкала важности: 🔴 Crit / 🟠 High / 🟡 Med / ⚪ Low.

### Ф0 · Инструменты и окружение `[ ]` (gate)
- Расширить `diag` командами снимка графа (§4.3).
- Поднять контролируемый стенд: `docker compose -f docker-compose.dev.yml up -d` (Postgres+pgvector / Redis / MinIO) + backend + воркеры in-process + LLM-ключи из `.env`; применить `apply-postgres-init` (HNSW/GIN-индексы).
- Снизить пороги (§7) на стенде; зафиксировать «как было», чтобы вернуть.
- Проверить, что AGE включён (`shared_preload_libraries='age'`, `search_path`) ИЛИ kill-switch `GRAPH_AGE_ENABLED` корректно деградирует на Postgres/EntityLink (B5).
- **Acceptance:** `diag graph --org <демо>` отдаёт ненулевой снимок наполненного демо-мозга (sanity инструмента).

### Ф1 · Агенты на единичном событии (узкий проход, прод-кабинет) `[ ]`
Провести **одну длинную встречу (>10 мин речи)** + один `/dump` + один документ/telegram. По каждому:
- `diag trace` / `chain` / `llm-calls` / `logs ≥WARN`;
- проверить: каждый узел отработал, **ни один воркер не упал**, `RawEvent` создан, блок реально лёг (UI отчёт ↔ БД).
- **Acceptance:** встреча дошла до `ai_ready` без 5 ретраев Vox (B1); мост `ingestMeeting` создал `RawEvent` (B7 — при провале была бы `failed` с `failureReason`, не молчание); из dump/документа появились `IdeaBlock`.

### Ф2 · Наполнение графа под объёмом (стенд) `[ ]`
Залить ~10–20 осмысленных дампов + 2–3 встречи (Р2) → дать/дёрнуть block-distill, block-linker, entity-resolver, entity-graph-builder, theme-clusterer.
- `diag graph` — появились canonical-блоки; **dedup-ratio** разумный (повтор «купим CRM» = один блок с N evidence, а не N блоков);
- `diag links` — связи 7 типов, confidence ≥ 0.75, explanation осмысленный;
- `diag entities` — дедуп сущностей (один «клиент Acme», а не три);
- `diag themes` — темы построились, branch/name адекватны.
- **Acceptance:** граф связей и темы **не пустые** после снижения порогов (B6); типизированные сущности материализовались, нет `kc_typed_entity_failed` (B5).

### Ф3 · Специалисты Слоя 3 (стенд) `[ ]`
На том же объёме проверить, что из блоков родились сущности, а не потерялись на routing:
- `diag specialists` — Decision/Insight/Idea/Regulation/Skill созданы; счётчики растут с объёмом;
- логи — нет `core_specialist_skipped` массово; probe-вопросы (`decision.missing_decider`, `regulation.missing_owner` и т.п.) реально сформированы и доставлены.
- **Acceptance:** первая проекция создаётся из живого потока (B3); блоки доходят до целевого специалиста (B2); пересборка проекций не падает (B4).

### Ф4 · Клоны (стенд + UI) `[ ]`
Накопить reasoning-блоки одной роли (≥ порога) → skill-trait-detect → concept-normalize → role-profile → executable-persona:
- `diag clones` — SkillTrait/Concept/RoleProfile/ExecutablePersona появились, версии растут;
- Playwright `/roles/[id]/skill-profile` — клон отвечает от первого лица, с цитатами `[BLOCK:id]` и дисклеймером;
- **анти-фальшивка**: на вопрос без ≥2 reasoning-блоков (cosine ≥ 0.70) — отказ БЕЗ LLM-вызова (`refused`, `insufficient_context`).
- **Acceptance:** клон роли создаётся автоматически по накоплению; не выдумывает, не обещает за людей; rate-limit (20/день) держит.

### Ф5 · Чтение мозга пользователем (прод-кабинет + стенд) `[ ]`
chat-v2 / поиск / «Память компании»:
- задать вопрос, на который ответ есть только в накопленных блоках → ответ с цитатами на реальные блоки/встречи;
- поиск `POST /knowledge/search` — гибрид (cosine+BM25) возвращает релевантное.
- **Acceptance:** «мозг реально используется» — ответы опираются на граф, а не на пустоту/галлюцинацию.

## 7. Снижение порогов на тест-окружении (из аудита B6)

```

THEME_CLUSTERING_MIN_BLOCKS=5    # темы (default 100)
THEME_CLUSTER_MIN_SIZE=2         # минимальный кластер (default 3)
ENTITY_GRAPH_MIN_COMENTIONS=1    # граф сущностей (default 3)
# LINK_MIN_CONFIDENCE НЕ трогаем (общий порог качества связей)
```
Применять **только на стенде**. Зафиксировать исходные значения и вернуть после прогона. Если фикс «крутилки в AdminSetting» приземлился (`getDynamic`) — менять через AdminSetting; иначе через ENV + рестарт.

## 8. Гигиена и безопасность

- **Прод-доступ `diag` — только с явным «да» владельца в текущей сессии** ([[feedback_prod_diagnostic_access_requires_confirmation]]). Токены/куки в чат не вставлять.
- **`diag` — строго read-only**, в т.ч. расширение. Любые мутации (создать встречу/дамп) — руками через UI или через стендовые ручки.
- **Снижение порогов и дёрганье воркеров — только на стенде**, не на проде.
- Тестовые данные помечать префиксом `[QA-test]`; в конце — список созданного на чистку.
- Демо «ТехноСтрим» не путать с живым наполнением (см. §2).
