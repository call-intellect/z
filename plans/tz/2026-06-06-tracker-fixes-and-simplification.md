# ТЗ — Трекер-задачник: исправить ВСЁ найденное + упростить

## Принцип

Чиним **все** находки аудита трекера, без отбора по приоритету. Часть уже исправлена в ветке `sergdev` — для неё ТЗ требует **верификации полноты + выката**, а не переписывания. Остальное — полноценные фазы. Каждая правка ложится в текущую архитектуру (`frontend` слои ApiDto→DomainModel→UiModel; `backend/src/modules/tracker`), UI конечного пользователя — **только русский** (это часть фикса), парные цветовые токены, без новых нарушений инвариантов Z.

**Не оптимизируй по-своему:** все развилки закрыты решениями владельца Р1–Р4 и якорями кода ниже. Номера строк — на момент написания (2026-06-06, ветка `sergdev`); перед правкой перечитывать по якорю-символу.

## Цель и Зачем

Владелец прошёл трекер как обычный пользователь и «запутался, что делать». Две группы проблем:

1. **Видимые поломки** — на проде не открываются детальные страницы (таблица/задача/спринт), не работает «Принять» во Входящих, бренд «Z», «Архив гипотез» вместо «Архив спринтов», нет фидбэка дампа. Часть уже починена в `sergdev`, но **не выкачена**.
2. **«Сложность»** — структура и термины: 8 разных инструментов в одной куче меню, «Входящие» под тремя именами, спринт=цикл под двумя именами, 10 подвкладок проекта.

**Метрика успеха (проверяемо):** после реализации на проде — (а) открывается любая таблица/задача/спринт; (б) задача из встречи принимается в проект за один понятный шаг; (в) во всём трекере один термин «Спринт», один смысл «Входящие», ноль англицизмов в перечисленных строках; (г) меню разбито на осмысленные группы; (д) `bun run typecheck/lint/build` зелёные на фронте и бэке.

## Доказательство ключевого решения (Фаза 2 — «Принять»)

Состязательно (детали — в анализе §3.2):

| Критерий | A. Фронт: пикер проекта + привязка к текущему | B. Бэк: авто-назначать дефолтный проект «Входящие» |
|---|---|---|
| Решает корень класса (любой intake без suggested) | ✓ | ✓ |
| Уважает продуктовую идею «владелец сам кладёт задачу в нужный проект» | ✓ | ✗ (прячет выбор) |
| Изменения в данных/схеме | нет (DTO уже принимает `targetProjectId`) | да (фантомный проект, миграция) |
| Риск «мусорных» сущностей | низкий | высокий (ещё один скрытый проект, ср. Фаза 7) |

**Выбор — A.** Challenge-loop: (1) корень — «нет способа выбрать проект при приёме» → пикер закрывает весь класс; (2) эффективнее — бэк уже готов (`targetProjectId` в DTO), нужен только UI; (3) без кода ради кода — переиспользуем существующий паттерн диалогов intake (Reject/Snooze/Duplicate уже есть, добавляем Accept-диалог).

- Фаза 8 — консолидация поллинга бейджей навигации (консервативно).

### Не входит (vNext, с судьбой)
- Слияние «Входящие» + «Подтверждения» в единый «Разбор» — Р3 отложил; отдельное ТЗ при необходимости.

- «email-рассылок», «100 встреч» и т.п. в карточках Входящих — это **AI-сгенерированный** текст из встречи (не статичная строка), правке в коде не подлежит; при желании — глоссарий в промпте экстрактора (отдельно).
- Сам пэйвол `@RequireSubscription` — не трогаем (подтверждено: гейты на месте).

### Граничные контракты
- **Бэкенд `triage` не меняем** — `targetProjectId` уже в `TriageIntakeSchema` (`triage-intake.dto.ts:16-44`) и обрабатывается (`intake.service.ts:240-254`). Фаза 2 — только фронт.

## Фаза 2 — «Принять» во Входящих: выбор проекта 🔴

**Цель:** дать принять любую входящую задачу в проект (а не только ту, где AI заранее предложил проект), и привязать проектный intake к текущему проекту. Бэкенд готов (`targetProjectId` в DTO) — меняем только фронт.

- Образец диалогов: Reject/Snooze/Duplicate уже реализованы в `IntakeClient` (есть `RejectDialog`/`SnoozeDialog`/`DuplicateDialog`).
- Список проектов: `frontend/src/api/tracker/projects.api.ts` → `projectsApi.list` (`GET /api/v1/projects`).

**Что входит:**
1. **Глобальные `/intake`:** при «Принять» — если у входящей нет резолвящегося проекта (`item.projectId == null && item.suggestedProjectId == null`), открыть **AcceptDialog** с выбором проекта (список из `projectsApi.list`, поиск по имени), затем `triage(..., { decision:'accept', targetProjectId: <выбранный> })`. Если проект уже определён — принимать как сейчас (без лишнего диалога), но targetProjectId передавать явно.
2. **Проектный `/projects/[slug]/intake`:** (а) грузить список с фильтром по текущему проекту — резолвить `slug → projectId` (через уже грузящийся `project` в `ProjectViewShell`/`useProject`) и передавать в `useIntake(orgId, { status:'pending', projectId })`; (б) «Принять» здесь всегда шлёт `targetProjectId = <id текущего проекта>` (не `item.projectId`).
