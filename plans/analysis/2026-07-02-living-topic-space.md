> Цель разбора: доказать, стоит ли давать менеджеру «Живое пространство темы» (пользователь заводит тему словами → контент сам стекается по смыслу → красиво читаемая живая страница), и в каком виде — на базе существующего движка Theme.
> Следующий шаг → архитектура (solution-blueprint): plans/architecture/2026-07-02-living-topic-space.md
> Рыночная/конкурентная база (не дублируется здесь): [[2026-07-02-notion-agent-teardown-and-borrow]] — Notion «workflow под тему» держится на ручном теге; Mem/Obsidian Smart Connections «само связывается» только single-user; РФ-аналоги авто-графа из разговора не строят.

## 1. Рамка проблемы
**Мысль владельца:** «нет понятия workflow, чтобы завёл его на тему/проект/мысль, туда сама скидывалась инфа, и это можно было смотреть глазами — текстом, но красиво структурированно».

**Iceberg:** симптом — «нет фичи как в Notion». Корень — **у менеджера нет места, где рабочий поток сам собирается вокруг ЕГО темы и читается как связная картина, а не как список**; и нет ощущения, что это «его» пространство (владение).

**Две формулировки:**
- A: «менеджер не может собрать всё по теме в одном месте без ручного тегирования» → метрика: доля релевантного контента, попавшего в тему без ручного действия.
- B: «менеджеру нужна доверяемая, читаемая глазами живая картина темы, которой он владеет» → метрика: время «понять статус темы» → цель ~30 сек; доля авто-привязок, принятых без правки.

**Роли Z:** менеджер (заводит/владеет темой), руководитель (пульс по теме), сотрудник (контент втекает из его встреч/чатов).

## 2. Что уже есть в коде (baseline, факты)
- **`Theme`** [schema.prisma:4393] — контейнер: `name`, `description`, `summary` (+`summaryUpdatedAt`), `weight`, `dynamic`, `confidence`, `status`, `branch`, `embedding vector(1536)`, `lastSignalAt`.
- Связи: `ThemeIdeaBlock` (M:M блоки, `weight` принадлежности), `ThemeEntity` (люди/клиенты/продукты, `mentionsCount`), `Document` (`attachedThemeId`), `Card` (born-from-theme), `GoalTheme` (цели).
- **Контент сам стекается:** [theme-clusterer.cron.ts] — embedding блоков → `clusterByEmbedding` → создаёт тему + привязывает блоки (seed weight 1.0, «прибившиеся» ниже при reframing).
- **Тема сама называется/резюмируется:** [theme-classification.service.ts] (LLM даёт name/description/branch/tags/weight/confidence через `llm-router` taskType `theme-classify`), [theme-summarize.cron.ts] (инкрементальный `summary`).
- **Ядро retrieval доведено 2026-07-02** (H3 закрыт, резолв людей/клон-коллапс починены — [[../../second-brain/05_история/2026-07-02-retest-fixes-a-e-i-dashboardy-nedelya-mesyac]]).

**Пробелы (ровно мысль владельца):**
1. **Тему создаёт только машина.** API темы read-only: [themes.controller.ts] = `GET` list, `GET :id`, `POST :id/save-as-card`. Нет «создать тему», нет «складывай сюда всё про X».
2. **Вид пассивный.** [ThemeDetailClient.tsx] — список блоков/сущностей (машинный кластер), не «живая страница».
3. **Знания оторваны от витрины менеджера.** Трекер (проекты/доски/спринты/доки, [ProjectViewShell.tsx]) отдельно от тем.

## 3. Gap-таблица «рынок × Кора»
| Возможность | Лучший конкурент (как) | Кора сейчас | Дельта / что строить |
|---|---|---|---|
| Завести свою тему/контур | Notion (БД+тег вручную); Tana (supertag) | Только машинные кластеры | **user-create Theme** (origin=`user`) + именование |
| Контент сам стекается по смыслу | Mem/Smart Connections (single-user) | Есть на командном графе (clusterer) | Привязка входящего к user-теме по pgvector + LLM-классификации |
| Красивая читаемая страница | Notion-страница (руками); NotebookLM | `summary` есть, вид сырой | **Живой вид:** TL;DR + лента + кто-в-теме + решения/задачи + доки |
| Контроль/владение (не «чёрный ящик») | Notion/Tana (рынок платит за это) | Движок решает сам | **HITL:** «предложено → подтверди/убери» + ручной pin/unpin |
| Связь темы с задачами | — (у Notion слабо) | `Card`/`GoalTheme` есть частично | Мост «обязательство темы → задача трекера» |
| Пульс темы для руководителя | — | письмо COO есть (по компании) | Срез письма COO на уровень темы |

## 4. Матрица вариантов
**Критерии (ограничения Z):** ценность менеджеру · ценность руководителю · надёжность на наших данных · дешевизна (что уже в коде) · отстройка · соответствие AI-COO (не контент-планер).

| Критерий | A: только красивый вид авто-кластеров (read-only) | B: user-тема + авто-привязка + HITL + живой вид | C: полный «workflow-конструктор» (правила/автоматизации на тему) |
|---|---|---|---|
| Ценность менеджеру | средняя (не «его» тема) | **высокая** (его пространство, само наполняется) | высокая, но сложная |
| Ценность руководителю | средняя | **высокая** (пульс по теме) | высокая |
| Надёжность на данных | высокая | высокая (HITL страхует привязку) | средняя |
| Дешевизна | **высокая** (только вид) | средняя (create+привязка+вид) | низкая (конструктор правил) |
| Отстройка | низкая | **высокая** (командный авто-граф + владение) | высокая, но over-engineering-риск |
| Соответствие AI-COO | среднее | **высокое** | среднее (уводит в конструктор) |

**JTBD:** «собрать всё по теме без ручного труда» (B закрывает), «понять статус за 30 сек» (живой вид+summary), «доверять и владеть» (HITL — прямой ответ на рыночный сигнал «контроль важнее магии», см. notion-doc red-team).

## 5. Рекомендация (ADR)
**Выбор: B** — user-инициируемая тема + семантическая авто-привязка входящего + **HITL-подтверждение** + живой читаемый вид. Элементы C (правила/автоматизации) — отложить (over-engineering-риск для SMB).
- **Почему не A:** «красивый вид чужого кластера» не решает корень «его тема, которой владеет»; не отвечает на мысль владельца «завести workflow».
- **Почему не C:** конструктор правил поверх темы — это отдельная большая фича (см. банк идей — no-code агент отложен); сейчас витрина, а не автоматизация.
- **Ключевой принцип (из red-team notion-doc):** не «ИИ сам всё раскидал», а «ИИ предложил — ты подтвердил и владеешь». Это и надёжнее на наших данных (диаризация ~30% ошибка на «кто сказал»), и совпадает с тем, за что платит рынок.
- **Витрина для руководителя — операционная** (проект/клиент/цель), «рилсы» держим лишь как пример захвата, чтобы не съехать в контент-планер.

**Последствия:** переиспользуем 80% (Theme/embedding/summary/ThemeEntity/documents); достраиваем create-тему + привязку в user-тему + HITL + живой вид + мост к трекеру. Ядро retrieval доведено → фича не блокирована.

## 6. Открытые вопросы к владельцу (каждый с рекомендацией)
1. **Пользовательская тема = новая сущность или флаг на `Theme`?** — *Рекомендую: флаг `origin: user|auto` + `createdByUserId` на существующей `Theme`.* Почему: не плодим сущность, переиспользуем весь движок (привязка/summary/сущности/доки) сразу.
2. **Как контент попадает в user-тему — только авто по смыслу, или авто + ручной pin?** — *Рекомендую: оба.* Авто-предложение по embedding + LLM-классификации, менеджер подтверждает/пинит/убирает. Почему: HITL — ядро доверия и владения.
3. **Где живёт живой вид — раздел «Темы» или вкладка проекта трекера?** — *Рекомендую: сначала в «Темы» (там уже есть роут/детали), мост к проекту — вторым шагом.* Почему: дешевле, не трогает трекер сразу.
4. **Показывать ли «пульс темы» руководителю отдельным блоком (срез письма COO)?** — *Рекомендую: да, второй фазой.* Почему: двойное лицо (менеджер+руководитель) — сильная сторона, но живой вид важнее в первую очередь.

## 7. Ограничения и непроверенное
- **Диаризация «кто сказал» ~30% ошибка** (общая, из notion-doc red-team) → привязку/авторство подавать через HITL, не как факт.
- Качество авто-привязки в user-тему на реальных данных не замерено (нет A/B) — HITL страхует.
- `summary`-воркер: WARN flash не принимает forced tool_choice (фолбэк 'auto', некритично) — из retest-рефлексии.
