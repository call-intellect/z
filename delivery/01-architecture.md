# 01 — Архитектура

## Принципы организации кода

1. **Слоистая архитектура.** 7 функциональных слоёв обработки + сквозные модули. Каждый слой имеет чётко определённую ответственность и не вмешивается в чужую.
2. **Событийная связность.** Слои общаются через event bus (Redpanda/Kafka-совместимый). Прямые синхронные вызовы между слоями запрещены, кроме обратной связи через API Gateway.
3. **Один процесс — один модуль.** Каждый модуль M-NN — отдельный сервис (или группа сервисов в одной кодовой базе) с собственным контрактом, миграциями и тестами.
4. **Все сервисы stateless** в плане прикладной памяти. Состояние — в PostgreSQL / FalkorDB / pgvector / MinIO. Любой сервис должен переживать перезапуск без потери данных.
5. **Идемпотентность входа.** Любой ingest-приёмник идемпотентен по `idempotency_key = sha256(source_id + external_id + timestamp)`. Повторный приход одного и того же события не создаёт дубль.
6. **Событие неизменно после фиксации.** Once event written to Raw Memory, оно не редактируется и не удаляется (кроме compliance-удалений по запросу субъекта данных, см. [08-security-privacy.md](08-security-privacy.md)).

### Слой 1 — Сбор данных

Цель: принимать всё входящее и приводить к единому формату события.

Модули:
- **M-01** — каталог источников;
- **M-02** — единая точка приёма (Telegram-бот, веб-форма, REST API, файлы, голос);
- **M-04** — транскрипция (аудио/видео → текст, разделение спикеров);
- **M-33** — внешний поиск (мониторинг конкурентов, индустриальных источников);
- **M-40** — коннекторы к бизнес-данным (1С, Bitrix24, amoCRM, МойСклад, generic SQL/CSV).

Что слой **не делает**: не интерпретирует, не классифицирует, не тегирует. Только нормализация и сохранение.

Контракт выхода: запись события в Raw Memory с полным набором метаданных — автор, дата, канал, контекст, права доступа, исходный материал.

### Слой 2 — Сырая память

Цель: хранить первоисточники неизменно. Защищает от подмены оригинала интерпретацией.

Модули: **M-03** (Raw Memory).

Хранилище: PostgreSQL для метаданных + MinIO для бинарей и больших текстов. Чексумма содержимого хранится отдельно для проверки целостности.

### Слой 3 — Понимание

Цель: получить первичный LLM-разбор сырья.

Модули:
- **M-05** — первичный LLM-анализ: краткое содержание, типизированные сигналы, упоминания людей/клиентов/проектов, эмоциональный окрас, важность, уверенность;
- **M-06** — хранилище сигналов (signal store).

Сигналы — типизированные сущности с закрытым перечнем типов (расширяемым через миграцию):

| Код | Русское название | Описание |
|---|---|---|
| `client_pain` | боль клиента | Жалоба, проблема, недовольство |
| `feature_request` | просьба клиента | Запрос на новую функцию |
| `objection` | возражение клиента | Аргумент против покупки/продолжения |
| `churn_risk` | риск ухода клиента | Сигналы готовящегося оттока |
| `idea` | идея | Предложение от сотрудника или клиента |
| `risk` | риск компании | Угроза бизнесу |
| `commitment` | обещание | «Я сделаю X к Y» — без напоминаний, только память |
| `decision` | решение | Зафиксированный выбор |
| `mood` | настроение | Эмоциональный сигнал команды |
| `drift` | дрейф стратегии | Отклонение действий от целей |
| `competitor_move` | действие конкурента | Внешний сигнал |
| `metric_change` | изменение метрики | Существенное движение количественного показателя |
| `knowledge_gap` | пробел в знании | Открытый вопрос компании |

Каждый сигнал несёт `confidence` (0..1) и `evidence_links` (ссылки на первоисточники).

### Слой 4 — Структура знания

Цель: организовать сигналы в смысловые единицы среднего уровня — темы, ветки компании.

Модули:
- **M-07** — карта компании из 12 веток (стратегия, клиенты, продажи, маркетинг, продукт, операции, команда, финансы, технологии, производство, партнёрства, юридика). Адаптивно подкручивается под тип бизнеса;
- **M-08** — темы (имя, описание, ветка, сигналы, источники, вес, статус, динамика);
- **M-09** — оценка важности темы по 8 факторам;
- **M-10** — оценка веса источника (платящий клиент > сотрудник > метрика; разнообразие важнее частоты).

8 факторов важности темы (M-09):

1. Частота упоминания.
2. Разнообразие источников (сколько разных людей/каналов).
3. Свежесть (последняя активность темы).
4. Связь с активной целью компании (M-15).
5. Финансовое влияние (если из сигналов виден метрический эффект).
6. Риск бездействия (есть ли тренд ухудшения).
7. Уверенность AI (среднее по сигналам).
8. Подтверждение человеком (поднимает вес).

Итоговая важность — взвешенная сумма с интерпретируемыми коэффициентами (см. [03-modules-catalog.md](03-modules-catalog.md), M-09).

### Слой 5 — Связи знаний (центральный слой)

Цель: построить граф знаний компании и поддерживать его актуальным.

Модули:
- **M-11** — динамические связи знаний (поиск явных и неявных связей, создание новых узлов, переосмысление);
- **M-12** — граф сущностей (хранение всех связей).

**Это сердце концепции.** Если этот слой не сработает технически, остальные модули превратятся в дорогую CRM с нейросетью.

Технический фундамент: **Graphiti (temporal KG-обёртка) + FalkorDB (graph storage) + pgvector (поиск кандидатов по эмбеддингам) + cross-encoder (rerank) + LLM-арбитр для типа связи и объяснения**. См. [02-stack.md](02-stack.md) и [DR-008](14-decisions-log.md#dr-008).

Стандартные типы связей:
- `подтверждает`, `мешает`, `помогает`, `вызывает`, `противоречит`, `относится_к_цели`.

Кастомные типы связей:
- `стратегическое_расхождение` — детектируется M-16 при дрейфе;
- `ранний_симптом_риска` — детектируется при паттерне «несколько слабых сигналов одного направления»;
- `новая_сторона_старой_проблемы` — детектируется Reframing Agent (M-14);
- `общий_корень_нескольких_проблем` — детектируется Consolidation Agent (M-13).

Каждая связь несёт метаданные: `source_node`, `target_node`, `relation_type`, `explanation` (текстовое объяснение от LLM), `confidence` (0..1), `evidence_signals` (список сигналов-доказательств), `status` (`предложена_AI` / `подтверждена_человеком` / `отклонена_человеком` / `архивирована`), `created_at`, `last_reframed_at`.

### Слой 6 — Консолидация и переосмысление

Цель: фоновые агенты, обновляющие структуру знаний без явного запроса пользователя.

Модули:
- **M-13** — агент консолидации (раз в несколько часов): просмотр новых данных, поиск повторов, обновление весов, добавление связей-кандидатов;
- **M-14** — агент переосмысления (раз в сутки, ночью): переименование тем, разделение/объединение, обновление формулировок, переоценка старых выводов;
- **M-19** — настроение команды (пассивный + активный сбор);
- **M-22** — связь тем и решений с количественными метриками;
- **M-34** — двигатель уроков (дистилляция повторяющихся наблюдений в правила/принципы).

### Слой 7 — Решения и интерфейс

Цель: предоставить пользователю срез памяти, чат, дашборд и канал коррекции.

Модули:
- **M-15** — цели компании (стратегическое ядро);
- **M-16** — стратегический согласователь (главный дифференциатор: «движемся ли к цели?»);
- **M-17** — управление идеями;
- **M-18** — управление рисками;
- **M-21** — отслеживание решений (полный цикл: сигнал → тема → решение → действие → результат → память);
- **M-23** — агент-исполнитель запросов (чат к памяти);
- **M-24** — дашборд (главный визуальный интерфейс);
- **M-25** — база знаний компании (человекочитаемая wiki);
- **M-26** — корректировка пользователем (подтверждение/отклонение AI-выводов);
- **M-32** — реестр открытых вопросов компании;
- **M-36** — постоянный контекст роли (always-loaded память для каждой роли);
- **M-37** — обещания и договорённости (без напоминаний).

### Сквозные модули

- **M-20** — приватность и доступ (RBAC + Visibility);
- **M-27** — оркестрация фоновых задач (Temporal-совместимый);
- **M-28** — архитектура хранилищ (PostgreSQL + JSONB + pgvector + Tantivy + FalkorDB + MinIO);
- **M-35** — версионирование и архив (snapshot-история сущностей, audit trail действий агентов);
- **M-38** — слой AI-команды (9 специалистов + 3 ассистента + Supervisor);
- **M-39** — шина инструментов (двойной транспорт MCP + REST для агентов).

## Главный поток данных

```
[1] Источник (письмо, чат, встреча, файл, CRM)
       ↓
[2] M-02 Ingest → нормализация → idempotency check
       ↓
[3] M-04 Transcription (если аудио/видео)
       ↓
[4] M-03 Raw Memory → запись неизменного оригинала
       ↓                                          (event bus)
[5] M-05 Primary LLM Analysis → сигналы, важность, уверенность
       ↓
[6] M-06 Signal Store → запись типизированных сигналов
       ↓
[7] M-08 Themes → match с существующими темами или создание новой
       ↓
[8] M-09 Theme Scoring + M-10 Source Weighting → пересчёт весов
       ↓
[9] M-11 Dynamic Linking → поиск кандидатов связей через эмбеддинги
       ↓                  → LLM-арбитр для типа и объяснения
       ↓                  → запись связей в M-12 Entity Graph (Graphiti)
       ↓
[10] M-13 Consolidation (фон) → периодически переоценивает веса
[11] M-14 Reframing (ночь) → переоценивает структуру тем
       ↓
[12] M-16 Strategic Alignment → детектирует дрейф от целей
       ↓
[13] M-23 Query Agent ← вопросы пользователя
       ↓                  → выдаёт ответы со ссылками на оригиналы
       ↓
[14] M-26 Human Feedback → корректировки питают M-14
```

Все стрелки между шагами — асинхронные через event bus, кроме [13] и [14] (синхронный диалог пользователя с агентом).

## Жизненный цикл сущности (универсальный)

Любая значимая сущность (тема, идея, риск, решение, связь) проходит цикл:

```
proposed  →  analyzed  →  confirmed  →  locked
                            ↑              ↓
                            └─ unlock procedure (через open question)
```

| Уровень | Кто переводит | Что значит |
|---|---|---|
| `proposed` | AI или пользователь | Гипотеза. Не используется как опора. |
| `analyzed` | AI после анализа | Аргументировано, есть обоснование. |
| `confirmed` | Только пользователь | Рабочая опора. Можно строить дальше. |
| `locked` | Только пользователь | Зафиксировано. Меняется только через процедуру разлочки. |

**Ни один AI-агент не повышает уровень выше `analyzed`.** Это архитектурное правило, ломать его нельзя.

В модели данных каждая сущность несёт поле `confirmation` (enum) и связь на `confirmation_history` (журнал переходов с автором и обоснованием).

## Сквозные принципы реализации

### Идемпотентность

- Любая входная точка имеет `idempotency_key`.
- Любой LLM-вызов с одинаковым промптом и моделью кэшируется (с учётом TTL).
- Любой фоновый job помечает обработанные события `processed_at`, повторный запуск — пропускает.

### Versioning

- Каждое изменение значимой сущности (тема, идея, цель, связь) создаёт snapshot в `entity_versions`.
- Snapshot содержит полный JSON состояния + автор изменения + причина.
- API позволяет получить состояние сущности на момент времени T (time-travel).

### Audit trail

- Каждое действие AI-агента логируется в `agent_actions` с полями: `agent_id`, `tool_called`, `inputs_hash`, `outputs_hash`, `duration_ms`, `cost_tokens`, `confidence_self`.
- Лог иммутабелен. Поиск — по `entity_id` (что делал агент с этой сущностью), `agent_id` (что делал агент за период), `time_range`.

### Provenance (доказуемость выводов)

- Любое утверждение, показанное пользователю, должно быть восстановимо до набора первоисточников.
- На уровне API каждый ответ содержит `evidence: [{source_id, snippet, weight}, ...]`.
- В UI пользователь может развернуть «откуда это» — показывается дословный исходник.

### Retention (сроки хранения)

Матрица сроков по типам знания (см. [08-security-privacy.md](08-security-privacy.md), раздел Retention Policy):

| Тип знания | Срок хранения | Механизм удаления |
|---|---|---|
| Эфемерное (черновики, интерактивные подсказки) | 7 дней | Hard-delete cron |
| Сессия (один разговор с AI, контекст 1 встречи) | 90 дней | Hard-delete cron |
| Проект (контекст активного проекта/инициативы) | До закрытия проекта + 1 год | Архивация + soft-delete |
| Долгосрочное (стратегия, ценности, ключевые решения) | Бессрочно | Только compliance-удаление |
| Сырьё первоисточников | 7 лет (152-ФЗ) или по запросу субъекта | Hard-delete с каскадом |

Decay-функция веса темы во времени: `weight(t) = base * exp(-λ * (now - last_signal_at))`, где `λ` зависит от `data_class`. Подробно — в [03-modules-catalog.md](03-modules-catalog.md), M-09.

### Visibility (видимость данных)

Матрица доступа по 4 измерениям:

1. **Источник данных** (откуда пришло) — `source_class` ∈ {public, team, private, sensitive};
2. **Роль читающего** — функциональная (CMO/CSO/...) + иерархическая (L0..L4);
3. **Тип знания** — `knowledge_type` ∈ {strategy, customer_voice, internal_ops, mood, financial, legal, ...};
4. **Атрибут защиты** (`P-attribute`) — флаги `pii`, `salary`, `legal_privileged`, `medical`, `client_nda`.

См. [08-security-privacy.md](08-security-privacy.md). Реализация — через OpenFGA. Fallback — Casbin.

## Карта зависимостей между слоями

```
       Слой 1 (вход)  ─→  Слой 2 (сырьё)  ─→  Слой 3 (понимание)
                                                       ↓
       Слой 4 (структура)  ←──────────────────  Слой 3 (сигналы)
            ↓
       Слой 5 (связи)  ←──── Слой 4 + Слой 3 (узлы графа)
            ↓
       Слой 6 (консолидация) ─── работает поверх слоёв 3-5
            ↓
       Слой 7 (интерфейс) ─── читает Слои 4-6, пишет в Слой 1 (через корректировки)

       Сквозной M-20 ─── проверяет доступ на каждом слое
       Сквозной M-27 ─── оркестрирует все фоновые задачи
       Сквозной M-28 ─── предоставляет хранилища всем слоям
       Сквозной M-35 ─── ведёт версионирование на слоях 4-7
       Сквозной M-38 ─── спрашивает любой слой через M-39 (шина)
```

## Многотенантность

Архитектурный принцип: **один экземпляр развёртывания = одна компания**.

Причина: self-host без внешних зависимостей — основной режим. Изоляция данных через row-level security в multi-tenant SaaS-режиме слишком хрупка для нашей доменной области (мы читаем переписку, метрики, личные сигналы — утечка между тенантами катастрофична).

Если в будущем понадобится SaaS-режим:
- Каждый тенант — отдельная schema в PostgreSQL + отдельный keyspace в FalkorDB + отдельный bucket в MinIO;
- Никакого общего пула эмбеддингов;
- Encryption-at-rest c per-tenant ключами через Vault;
- Это отдельный архитектурный пакет (см. [DR-009](14-decisions-log.md#dr-009)), не обязательный для первого релиза.

В первом релизе — **single-tenant, self-host**. Все артефакты `delivery/` исходят из этого.

## Граничные случаи (edge cases)

### Что делать, если LLM-провайдер недоступен

- LiteLLM настроен с fallback chain: внешний → локальный (Llama 70B / Qwen 72B на vLLM).
- Если все недоступны — критические ingest продолжают работу (запись в Raw Memory + Signal Store с `confidence: null` и `status: pending_analysis`).
- Анализ запустится при возврате провайдера через retry.

### Что делать, если граф разрастается

- Graphiti поддерживает периодический cleanup устаревших связей.
- M-14 (Reframing Agent) раз в сутки помечает связи с низкой `confidence` и не подтверждённые человеком за 90 дней — как `archived`.
- Архивированные связи не участвуют в выдаче, но остаются для time-travel запросов.

### Что делать с конфликтом AI-вывода и человека

- Человек всегда побеждает. AI-связь, отклонённая человеком (M-26), помечается `status: rejected_by_human`.
- AI **не пытается переубедить.** Не создаёт ту же связь снова.
- Если паттерн повторяется (AI снова находит ту же связь), это попадает в очередь Reframing Agent — может быть, человек был неправ. Но без видимого «настаивания» в UI.

### Что делать, если пользователь хочет удалить свой след

- Поддерживается через GDPR-style endpoint `DELETE /api/v1/persons/{person_id}/data`.
- Срабатывает каскад: помечает `deleted_at` на всех сущностях с этим `person_id` → планировщик в течение 24 часов выполняет hard-delete первоисточников и анонимизацию упоминаний в производных (темы, сигналы, связи).
- Экспорт перед удалением — через тот же endpoint с параметром `?export=true`.

## Что **запрещено** в архитектуре

1. **Прямой доступ frontend к хранилищам.** Только через API Gateway. PostgreSQL/FalkorDB/MinIO смотрят наружу только через VPN для админов.
2. **LLM-вызов из frontend.** Только бэкенд имеет API-ключи. Streaming в браузер — через WSS-проксирование от бэкенда.
3. **Хранение API-ключей в коде или env-файлах в репозитории.** Только Vault / Secrets manager.
4. **Несогласованные изменения схемы.** Любая миграция PostgreSQL — через Alembic с обязательным review. Никакого `ALTER TABLE` в production вручную.
5. **Запись в Raw Memory без идемпотентного ключа.** Дубли первоисточников делают всю систему недоверчивой.
6. **Использование тенантских данных вне процесса конкретного тенанта.** Эмбеддинги, кэш, графы — изолируются строго.
7. **Любой UI с кнопкой выбора категории/тега/приоритета.** Запрещено правилом продукта.
