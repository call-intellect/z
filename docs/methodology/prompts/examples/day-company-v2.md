# Эталон промпта: `day-company-v2` (письмо COO «День компании»)

> Раз в сутки на `/dashboard` владелец получает «День компании» — живой честный разбор прошедшего дня как личное письмо от операционного директора (COO): имена людей и клиентов прямо, петля со вчера, «взгляд COO», привязка фактов к источникам. Не сухая сводка — связный рассказ, который показывает за событиями дня СИСТЕМУ (узкие места, повторяющиеся боли, конфликты, движение к цели).
> **Где живёт:** `backend/src/modules/operations/prompts/daily-digest.prompt.ts` (`DAY_COMPANY_SYSTEM_PROMPT`, `DAY_COMPANY_PROMPT_VERSION='day-company-v2'`, `DAY_COMPANY_JSON_SCHEMA`), `taskType='operations-daily-digest'`, вызывается из `daily-digest.service.ts` (`generate` + `buildDayPackage` + `buildDayCompanyUserMessage`). Маршрут: DeepSeek Pro → GPT → KIE, `maxTokens` снят (большой вход).
> **Контракт реализации:** `plans/tz/2026-06-30-day-company-report-v2.md` Ф4 (промпт) / Ф5 (маршрут).

---

## Ключевое решение: письмо, но выход — строгий JSON

Владелец хочет читать письмо, а фронт хочет рисовать бары/чипы/секции. Поэтому промпт пишет **прозу по секциям**, но упаковывает её в строгий JSON (`verdict` 4 оси + `letter[]` из 12 секций `{key,title,prose,cites?}` + `goalAlignmentDay` + `risksSummary`/`ideasSummary`). Каждая секция — элемент массива с фиксированным `key` (`intro..reflection`); проза каждой секции TTS-friendly (без markdown-таблиц). Сущность «решения» (`decisions`) из письма и схемы **удалена** — осталась в продукте только память факта решения, не в оперотчёте.

Числа дисциплины (план/факт, X из Y, сколько задач поставлено/выполнено) **считает СИСТЕМА** и подаёт готовыми — промпт явно велит «бери как есть, не пересчитывай». LLM отвечает только за нарратив и интерпретацию.

## Эталонный промпт (канон)

### SYSTEM (стабильный, без переменных → кэшируется; заканчивается few-shot JSON)
- **РОЛЬ** — «Ты — личный операционный директор (COO) владельца компании… живой честный разбор дня, как личное письмо».
- **ВХОД** — два блока: «ВЧЕРА» (только для петли/динамики, сам вчерашний день не пересказывать) и «СЕГОДНЯ» (данные за сутки по каналам + ПОСЧИТАННЫЕ числа дисциплины — брать как есть).
- **ТОН** — по-русски, к владельцу на «ты» по имени; живой, без воды/лести/алармизма; имена людей и клиентов прямо (приватный отчёт); факты привязывать к источнику через `cites:{label,ref}`; ничего не выдумывать, нет данных по секции — пропустить секцию.
- **СОСТАВ** — 12 секций строго по порядку (`intro,main,done,not_done,reporting,blocked,clients,ideas,attention,actions,delta,reflection`), у каждой — проверяемое правило (например `done`/`not_done` — обобщённая проза без поштучных списков; `blocked` — суммировать несколько причин, не сводить к одному корню; `reflection` — 5-6 предложений интерпретации без новых фактов).
- **ПРАВИЛА ПЕТЛИ/ДИНАМИКИ** — `attention` и `delta` строить ТОЛЬКО при наличии вчерашних данных.
- **ВЕРДИКТ / КОМПАС / summaries** — контракт полей `verdict` (4 оси team/clients/execution/overall), `goalAlignmentDay`, `risksSummary`/`ideasSummary`.
- **ФОРМАТ ВЫХОДА** — строго JSON по схеме DayCompany, без markdown-обёртки и текста вне JSON.
- **ПРИМЕР** — валидный ответ (`DAY_COMPANY_FEW_SHOT_JSON`): копировать структуру и стиль, не факты.

### USER (переменные — в конце, `buildDayCompanyUserMessage`)
Блок «ВЧЕРА» (вчерашний вердикт + открытые сигналы) + блок «СЕГОДНЯ» (6 слоёв пакета: голос сотрудника с подписью «кто сказал» · переписка Битрикс/чатбокс с автором и меткой сотрудник/клиент · сигналы риски-по-причине/идеи-кластеры/блокеры · конфликты за день · план↔факт по людям с готовыми числами · вчерашние открытые сигналы).

### Выход
Строгий JSON (`DAY_COMPANY_JSON_SCHEMA`, `additionalProperties:false`); Zod `.strict()` синхронно с json_schema `responseFormat`; post-LLM `clampVerdict` (критич. клиентский сигнал ⇒ ось «Клиенты» ≠ ok). При провале LLM/JSON — «сухой» fallback (NULL новых полей).

## Разбор по анатомии (почему классный)

| Блок методологии | Как реализован здесь |
|---|---|
| **1. Роль/персона** | «Ты — личный операционный директор (COO) владельца». Узкая, сильная персона → нужный регистр письма. |
| **2. Якоря смысла** | зачем (увидеть за днём СИСТЕМУ), кому (владелец лично, приватно → имена прямо), что дальше (письмо на `/dashboard` + рассылка). Явно: «ВЧЕРА» нужен ТОЛЬКО для петли. |
| **3. Критерии хорошего** | 12 секций с проверяемыми правилами (обобщённая проза без списков; суммирование причин; ровно 1-3 действия; `reflection` 5-6 предложений без новых фактов) вместо «пиши хорошо». |
| **4. Few-shot** | `DAY_COMPANY_FEW_SHOT_JSON` в конце SYSTEM — валидный ответ, «копируй структуру, не факты». Держит дешёвые/резервные модели в форме. |
| **6. Контракт** | строгий JSON + `DAY_COMPANY_JSON_SCHEMA` (`additionalProperties:false`), Zod `.strict()`, `clampVerdict`, `DAY_COMPANY_PROMPT_VERSION` поднят до `v2`. |
| **7. Запреты Z** | чистый русский; ничего не выдумывать (факты/числа/имена/ссылки); `cites` только из входа; сущность «решения» удалена; числа не пересчитывать. |
| **Cache-friendly** | весь текст + few-shot — в стабильном SYSTEM (ноль переменных); данные дня — в конце USER (`buildDayCompanyUserMessage`). Правка SYSTEM ломает кэш разово. |
| **Гейт ≠ формулировка** | «строить ли отчёт» решает kill-switch `operations.daily_digest.enabled` + идемпотентность `(tenantId,dateLocal)`; числа считает код; LLM — только нарратив. |

## Как мерили (ship-on, без блокирующего golden)

Выкат включённым (kill-switch `operations.daily_digest.enabled` переиспользован — новый флаг не вводился; крон 07:00 МСК). Жёстко — `typecheck`/`lint`/`build` + unit (ответ с 12 секциями и без `decisions` проходит `.strict()`; ответ с key `decisions` отклоняется; `verdict.axes[team].why` умеет содержать конфликт) + e2e на реальном DeepSeek (синтетика дня → JSON-письмо с именами, петлёй, `reflection`). Golden не блокирует ([[feedback_no_golden_ship_and_observe_prod]]).
