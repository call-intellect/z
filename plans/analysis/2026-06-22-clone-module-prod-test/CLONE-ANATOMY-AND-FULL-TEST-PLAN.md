# Клон должности — полная анатомия + план полного теста

> Дата: 2026-06-23 · Источник: код (`backend/src/modules/clones`, `knowledge-core`) + [second-brain/01_projects/skill-and-clone.md](../../../second-brain/01_projects/skill-and-clone.md) + прод-прогон этой сессии ([RESULTS.md](RESULTS.md)).
> Цель документа: простым языком объяснить, ЧТО такое клон, из каких сущностей он собирается, какие характеристики у него появляются, почему 39 блоков дали 1 кластер, сколько их может быть — и дать полный тест-план.

---

## 1. Что такое клон (в идеале, одним абзацем)

Клон должности — это **версионированный «думай как эта должность»** (`ExecutablePersona`), собранный из НАБЛЮДАЕМОГО поведения носителя должности: как он рассуждает, что ценит, по каким принципам решает, какими процедурами действует, что знает и какими письменными правилами обязан руководствоваться. Это **снимок одного текущего носителя** (не усреднение нескольких людей), он не содержит ФИО, пересобирается по мере накопления данных, а при смене носителя прошлая версия замораживается (доступна навсегда как «бывший»).

---

## 2. Из каких СУЩНОСТЕЙ собирается клон (полная карта)

Вокруг клона крутится не одна, а **8 групп сущностей**. Клон (persona) — это их сборка.

| # | Сущность | Что это простым языком | Чем наполняется (источник) |
|---|---|---|---|
| 1 | **SkillProfile** | «Личное дело навыков» сотрудника (контейнер 1:1 на сотрудника) | создаётся, как только у сотрудника появляется ≥1 подходящий блок |
| 2 | **SkillTrait** (черты, 4 слоя — см. §3) | Отдельные черты подхода: «как он работает / что ценит / по каким маркерам действует» | блоки `reasoning/rationale/decision_basis/methodology_step` от сотрудника |
| 3 | **SkillTraitConcept** | Нормализованное «каноническое имя» черты (чтобы у трёх человек одна и та же черта называлась одинаково) | ночной cron слияния близких черт |
| 4 | **RolePrinciple** (принципы роли) | Принципы решений всей ДОЛЖНОСТИ (а не одного человека): «на этой роли принято так» | те же subject-блоки, но агрегируются по должности |
| 5 | **PracticeSkill** (процедуры «ситуация→ход») | Рецепты «когда X — делаю Y» (recognition-primed decision) | извлекаются из накопленных черт/блоков |
| 6 | **KnowledgeProfile** (специалист 3-2 — ОТДЕЛЬНАЯ подсистема) | Что сотрудник ЗНАЕТ (экспертиза/опыт/компетенции): «у кого спросить про энергетику» | блоки `expertise/experience/competence` + факты о сотруднике |
| 7 | **Regulation / Instruction / Policy / Process** (Способ C) | Письменные ПРАВИЛА должности из «Базы знаний», которые клон обязан учитывать | создаются вручную как карточки знаний, привязываются по `scope` (role/department/org) |
| 8 | **ExecutablePersona** (+ `CloneAccessGrant`, `CloneQueryLog`) | Итоговая «личность» клона = сборка 1–7 в system-prompt; грант доступа; журнал вопросов | компилируется из всего выше |

**Важно (различие «навык» vs «знание»):** сущность 2 (SkillTrait) — это «КАК он действует» (навык/подход). Сущность 6 (KnowledgeProfile) — это «ЧТО он знает» (область экспертизы). Это РАЗНЫЕ подсистемы с разными signalType — разработчик специально их развёл. Клон роли в ответе опирается прежде всего на 2/4/5/7; знания (6) — отдельный слой «к кому идти за чем».

## 3. Характеристики клона (SkillTrait) — 4 СЛОЯ (а не одна черта!)

Каждая черта (`SkillTrait`) имеет поле `layer`. При КАЖДОЙ перестройке профиля по одной и той же группе блоков прогоняются **три независимых детектора** → могут родиться черты разных слоёв:

1. **`skill`** — подход к работе/решениям. *Пример (построен сегодня на проде):* «валидирует гипотезы дёшево и быстро». Детектор: `skill-trait-detect`.
2. **`value` / `motivation`** — ценности и мотивация, но ТОЛЬКО из выбора-в-ущерб (revealed preference — что выбрал, когда пришлось чем-то пожертвовать), не из деклараций. Детектор: `value-motivation-detect`.
3. **`process_marker`** — конструктивные маркеры процесса: «перечисляет критерии», «перепроверяет данными». Запрещены оценочные ярлыки («нерешителен»). Детектор: `process-marker-detect`.

Плюс отдельно (на уровне роли):
4. **RolePrinciple** — принципы должности (Reflection-слой), не привязаны к слою черты.
5. **PracticeSkill** — процедуры «ситуация→ход».

> То есть «идеальный» наполненный клон содержит ДЕСЯТКИ черт по слоям 1–3 + несколько принципов роли + набор процедур + знания + указатель регламентов. Одна черта — это только начало наполнения.

## 4. Почему 39 блоков дали 1 кластер и сколько кластеров вообще бывает

**Как из блоков рождается черта (механика, по коду `specialist-3-7-skill.service.ts`):**
1. Берутся все subject-блоки сотрудника нужных signalType (порог: всего ≥5 блоков — `skillProfileMinObservations`).
2. Блоки **группируются по смыслу**: два блока попадают в одну группу, если их косинусная похожесть ≥ **0.78** (`GROUP_SIMILARITY_THRESHOLD`).
3. Группа становится «черта-кандидат», только если в ней **≥3 блока** (`skillClusterMinObservations`).
4. Из каждой такой группы LLM лепит черту (по каждому из 3 слоёв).

**Что показал прод (доказано SQL):** у Алексея 39 блоков `methodology_step`, но это **39 РАЗНЫХ принципов** (выбор канала, найм, когорты, гипотезы, риски, атрибуция…). Попарно они похожи слабо (большинство пар <0.78), максимум пары = 0.896. Поэтому **кластер ≥3 сложился только ОДИН** — когда я залил 8 почти-одинаковых формулировок ОДНОГО принципа (похожесть до 0.98). Отсюда ровно 1 черта.

**Сколько кластеров может быть:** столько, **сколько у сотрудника разных навыков, КАЖДЫЙ из которых наблюдался ≥3 раза в похожих формулировках**. В реальной жизни это набирается само: на встречах человек по нескольку раз возвращается к одному подходу в разных ситуациях → блоки про один навык кучнее → кластеров много → черт много. Короткие синтетические однострочники-«афоризмы» каждый сам по себе → кластеры не набираются.

> **Ключевой вывод для теста:** чтобы «много чего собралось», нужны НЕ 39 разных афоризмов, а **по ≥3 близких наблюдения на каждый из нескольких навыков** (и желательно реальные встречи, а не синтетика). Тогда будут десятки черт по слоям + принципы + процедуры.

### Что нужно, чтобы прогнать ВЕСЬ тест до живого ответа клона
1. **Снять/поднять дневную квоту дампов** (`dump_per_day_per_user`) на тестовом аккаунте — сегодня уперлись.
2. Залить **по ≥3 близких наблюдения на 3–4 РАЗНЫХ навыка** (чтобы стало ≥3 черты `skill` → откроется ответ клона), + несколько блоков `expertise` (для KnowledgeProfile), + пару решений с trade-off (для value/motivation).
3. Создать **роль с носителем** (для звеньев 8 и 10) и **карточку-регламент** scope=role:<id>.
4. Прогнать перестройку (backfill) + ночные cron-ы (форсом) → задать клону роли тематический и вне-темный вопрос → зафиксировать ответ + что подтянулись регламенты.
