## §Р. Решения (приняты доказательно; Р-1/Р-5 уточнены по фидбеку владельца 2026-06-10)

- **Р-1 (блок 2). «Планы на день» → ЧЕК-ИН `daily_plan_morning` со СТРУКТУРИРОВАННЫМИ пунктами (для план-факта), НЕ heavy-задачи в трекере.** Уточнено владельцем: план потом сверяется «выполнен/не выполнен» (план-факт) → пункты должны быть трекаемыми. Решение: план сохраняется списком пунктов; вечерний `daily_report_evening`/план-факт сверяет каждый. НЕ плодить `IntakeIssue` (проект/доска/чужой исполнитель) — мусор; пункты трекаются внутри дневного чек-ина. Явную задачу пользователь создаёт фразой «поставь задачу…» (intent=task). *(При реализации — сверить с текущим хранением daily-checkin: хранится ли план структурой; если нет — добавить структуру пунктов.)*
- **Р-2 (блок 3). probe «про сотрудника X» → самому X (fallback руководитель); структурные про компанию → владельцу.** Отвергнуто: round-robin по владельцам/админам. Почему: владелец не знает экспертизу 30 человек лучше их самих → «соглашаются не вникая» + бутылочное горлышко; субъект отвечает точно, нагрузка распределяется.
- **Р-3 (блок 1, Ф5). `/orchestrator/*` → скрыть от обычных ролей (role-gate, только super_admin/owner).** Отвергнуто: локализация. Почему: отладочная кухня, бизнес-пользователю не нужна даже по-русски; скрыть дёшево, перевод дорог и бессмысленен.
- **Р-4 (блок 4). Чат → стадии-индикатор → SSE-стрим + поднять таймаут синтеза `chat-v2`.** Отвергнуто: «просто ускорить, фидбек не трогать». Почему: боль — «завис или нет», не 58с; синтез 28.6с впритык к 30с теряет ответы → таймаут поднять; ускорение retrieval вторично.
- **Р-5 (блок 5). Подключение канала = СОГЛАСИЕ на анализ → `analysisEnabled` = ON сразу при подключении ChatBox, БЕЗ отдельного вопроса.** Уточнено владельцем: переписку подключают именно ДЛЯ анализа — так же как создание встречи / загрузка аудио уже означают «анализируем». Решение: дефолт `analysisEnabled=true` при подключении (убрать молчаливый OFF, `chatbox-integration.service.ts:175`); для уже подключённых (вкл. «Ооо луа») — включить + бэкофилл истории. Отдельный consent-шаг НЕ нужен.

## §2. Вход Telegram — гейт намерения перед созданием задачи

**Проблема:** любой голос/текст боту → `IntakeIssue` (задача); «сегодня в планах…» стало одной задачей, вопрос боту — тоже задача.
**Корень:** согласованный классификатор `QueryClassifierService` (`dialog-classify`, большой промпт `DIALOG_CLASSIFY_SYSTEM_PROMPT`, 7 категорий) **обходится** — `TelegramBotMessageHandler.tryHandle` (адаптер: текст `telegram-bot.adapter.ts:526-534`, голос `:377-385`) возвращает `true` на любой непустой ввод → `parseCreateTask` → `return null` ДО `classifyIntent` (`:537`). В промпте к тому же **нет категории «задача»**. (Анализ: `plans/analysis/2026-06-10-telegram-intent-classifier-bypass.md`.)

### Фазы
- **Ф1.** Добавить категорию `task` в `classify.prompt.ts` (промпт + `DIALOG_CLASSIFY_JSON_SCHEMA` + примеры + ловушка «план дня ≠ список задач»); confidence-gate task→note при сомнении. *(Кэш `dialog-classify` сбросится разово — ок.)*
- **Ф2.** В адаптере вызвать `classifyIntent` ДО task-handler (reply/forward — остаются спецслучаями раньше); маршрут intent→действие: `task`→task-handler; `daily_plan_morning`/`daily_report_evening`→`daily_checkin_self`; вопросы→`chat_query`; `note`→`free_note`. Бот-ответ под намерение.
- **Ф3.** `tryHandle` — исполнитель intent=task (убрать безусловный `return true`); reply/forward сохранить.
- **Ф4.** Поправить вводящие в заблуждение комментарии; метрика распределения intent.
- **Приёмка:** «сегодня в планах: …» → чек-ин (не задача); «сделай X к пятнице» → задача; «что обсуждали?» → AI-чат; «запиши: …» → заметка; reply «принял» → статус.

## §3. Уведомления / probe / модерация

**Проблемы (4):** (1) адресация «не тому»; (2) технические тексты (FunctionalDomain/CompanyProfile/knowledge_profile/cuid/level/`chydo_002`); (3) заголовки-коды (`proactive.notification`…); (4) ответ как сырой JSON. (Анализ: `plans/analysis/2026-06-10-notifications-probe-subsystem.md`.)
**Корни:** `probe-dispatcher.worker.ts:124-137` берёт `recipientCandidates[0]`, эмиттеры (`consistency-checker.cron.ts:96 findOwnerCandidates`) кладут владельцев; `consistency-checker.cron.ts:57-64 RULE_DESCRIPTIONS` жаргон + `probe-dispatcher:213-214` fallback дословно; `conversational.ts:84 EVENT_TYPE_LABELS` пуст кроме `probe.question`; `NotificationsClient.tsx:433` `JSON.stringify`.

### Фазы
- **Ф1 (приоритет). Адресация (Р-2):** таблица `reason → audience` (субъект/руководитель/владелец); probe про конкретного `Person` → его userId. **Приёмка:** «обнаружена экспертиза у X» → X (или руководителю), не владельцу.
- **Ф2. Человеческие тексты:** `RULE_DESCRIPTIONS` + шаблоны модерации/скиллов → простой русский без классов-сущностей; ID/типы/уровни/логины → имена; `probe-formulate` промпт «только простой русский, без кодов/ID», fallback человеческий.
- **Ф3. Фронт:** заполнить `EVENT_TYPE_LABELS`; `NotificationsClient:433` → текст ответа; не показывать служебные пустые поля.

## §4. Чат «Помощник компании» — обратная связь и латентность

**Проблема:** `POST /chat-v2/messages` синхронный (~25–60с, на реальном вопросе 58с: classify 7с + retrieval 22с + синтез 28.6с), единственный фидбек «Кора печатает…», нет стрима/стадий → «зависает»; синтез впритык к таймауту 30с (риск потери ответа). (Источник: прод-трасса 2026-06-10.)

### Фазы
- **Ф1 (быстрый выигрыш).** Стадии вместо статичного «печатает»: «Понимаю вопрос → Ищу в памяти → Пишу ответ» + явный таймаут-стейт.
- **Ф2.** SSE-стрим токенов ответа; источники/заголовок — по завершению.
- **Ф3 (Р-4).** Повышенный/отдельный таймаут синтеза `chat-v2`; профиль retrieval (22с — кэш/сужение/параллель).
- **Приёмка:** пользователь видит прогресс; тяжёлый ответ не теряется по таймауту.

## §6. Сквозное

- **Прод:** всё — фронтенд + точечный backend (заголовки/тексты/маршруты). **Миграций/новых ENV нет** (пороги/таймауты — в AdminSetting, не в код). Выкат: `docker compose up -d --build`.
- **Флаги (Ship-On):** изменения за kill-switch там, где рискованно (адресация probe, стрим чата, маршрут Telegram — `BOT_INTENT_CLASSIFIER_ENABLED` уже есть). `analysisEnabled` — решение владельца (§5 Ф1).
- **prompt caching:** правки SYSTEM (`dialog-classify` +категория, `probe-formulate`, chat-v2 synthesize-маркеры) ломают кэш разово — приемлемо; далее SYSTEM держать стабильным.
- **Верификация:** `bun run typecheck`/`lint`/`build` (front+back); прод-смоук через `diag.ts` (intent-распределение Telegram, `ChatboxAnalyze` после включения, отсутствие сырых кодов в уведомлениях).

- Переписывание ASR/Vox, retrieval-движка, парсера задачи (только профиль/кэш/гейт намерения).
- Разбиение плана на задачи (отклонено Р-1 V1).
