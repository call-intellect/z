# Сессия: «День компании v2» — архитектура (approved) + ТЗ (ready-to-implement)

## Что было поставлено

Продолжение проектирования дневного отчёта. Владелец: «сначала делаем ТЗ, потом пуш; по плану
сначала архитектура, потом ТЗ» — то есть пройти каноничную цепочку `solution-blueprint` →
`tz-author` до формального ТЗ-контракта (до этого был только анализ + черновик промпта).

## Как решал

- Перечитал оба наших анализа целиком (`input-sources.md`, `report-prompt-v2.md`) — вход из контекста
  после компакта.
- Сверился с форматом-каноном: свежий ТЗ владельца `2026-06-29-task-extraction-pipeline-unification`
  (структура фаз/решений/контракт-first) + архитектура к нему; и **реализованная база**
  `2026-06-28-day-company-daily-brief` (Ф1–Ф6) — из неё взял точные якоря (`DailyOperationsDigest`
  с `verdictJson/letterJson/goalAlignmentDayJson`, `DailyDigestService.buildDayPackage`, промпт
  `operations-daily-digest`, крон `0 3 * * *`, герой `DayCompanyHero`).
- Написал **архитектуру человеческим языком** (`plans/architecture/2026-06-30-day-company-report-v2.md`):
  что есть → что делаем (4 куска) → как выглядит (макет письма + макет дашборда) → границы →
  12 принятых решений → 2 развилки → критерии успеха. Статус `draft`.
- Владелец закрыл обе развилки (усилить разметку конфликтов — да; компас как есть, сдвиг продюсера
  целей — отложить) → перевёл архитектуру в `approved`.
- Написал **ТЗ-контракт** (`plans/tz/2026-06-30-day-company-report-v2.md`): 8 фаз dependency-ordered,
  15 требований R1–R15 с трассировкой, контракт-first К1–К9 (индекс, резолв в Person, структура
  DayCompanyPackage, промпт v2, JSON-схема без «решений», забор конфликтов, усиление team_friction,
  маршрут модели+тайминг, виджеты), pre-mortem, DoD, инварианты Z.

## Что вышло

Цепочка собрана: анализ → архитектура (approved) → ТЗ (ready-to-implement). Коммиты `d250a14c`
(анализ цели/компас+конфликты) + `9a7ec929` (архитектура+ТЗ) запушены в `work/2026-06-29`.
Prod-операций нет — чистые `plans/*`. Реализация (код) — следующий этап (`tz-orchestrator`).

## Чему научился

- **v2 — надстройка, не стройка.** Ключ к точному ТЗ — сначала вытащить якоря из УЖЕ реализованной
  базовой фичи (её ТЗ + «Итог» с коммитами), а не проектировать с нуля. База дала готовый контракт
  персиста (JSON-поля снапшота), в который v2 только добавляет секции и убирает `decisions`.
- **Тайминг-развязка отчётов дня:** чек-ины собираются 05:00 МСК, Битрикс 03:00, чатбокс 00:00,
  продюсер целей (компас) 02:00. Отсюда: генерацию дневного отчёта держать 07:00 (`0 4 * * *` UTC),
  а нюанс «компас 02:00 отстаёт на день» осознанно отложить (окно 30д прощает).
- **Формат выхода — гибрид, не Markdown.** Черновик промпта `report-prompt-v2.md` писал «ФОРМАТ =
  Markdown», но база персистит структурный JSON (`verdictJson/letterJson/goalAlignmentDayJson`) — в ТЗ
  зафиксировал: SYSTEM берём из черновика, но ФОРМАТ ВЫХОДА = строгий JSON-schema, иначе фронт не
  нарисует бары/чипы/карточки.
- **Подпись автора лежит в 3 местах** (`IdeaBlockEvidence.authorPersonId` / `Idea.createdByUserId` —
  это User / `Insight.sourceBlockIds`) → «просто забирать голос сотрудника» = 3 пути в одной выборке +
  единый резолв userId/externalId→Person + новый индекс. Это отдельная фаза (Ф1+Ф2), не однострочник.
- **Gate архитектура→ТЗ работает как дешёвый фильтр:** развилки (конфликты, тайминг компаса) владелец
  закрыл на тексте архитектуры за один обмен — на коде это стоило бы переделок.
