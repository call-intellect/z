# Chat-v2: один промпт-ответчик + человеческий контекст

## 1. Цель и контекст

chat-v2 — «умный ответчик» AI-чата компании: гибридный поиск по графу знаний →
синтез ответа с цитатами `[BLOCK:<id>]`. Сейчас его поведение задаётся **четырьмя
промптами на одном движке** ([chat-v2.service.ts](../../backend/src/modules/knowledge-core/services/chat-v2.service.ts) метод `ask`):

| Промпт | Файл | Где живёт |
|---|---|---|
| `BASE_SYSTEM_PROMPT` | [chat-v2.service.ts:329](../../backend/src/modules/knowledge-core/services/chat-v2.service.ts#L329) | старый `chat`-модуль (встреча/архив через V2) — без override |
| режим «факт» | [factual.prompt.ts](../../backend/src/modules/chat-v2/prompts/factual.prompt.ts) | AI-чат компании, `mode='factual'` |
| режим «синтез» | [synthetic.prompt.ts](../../backend/src/modules/chat-v2/prompts/synthetic.prompt.ts) | AI-чат компании, `mode='synthetic'` (default) |
| режим «в стиле сотрудника» | [clone-style.prompt.ts](../../backend/src/modules/chat-v2/prompts/clone-style.prompt.ts) | заглушка-fallback |

На боевом пути [synthesis.service.ts:184](../../backend/src/modules/chat-v2/services/synthesis.service.ts#L184)
**всегда** подставляет один из режимов как `systemPromptOverride`, целиком
заменяя `BASE`.

### Что сломано (5 проблем, сверено с кодом)

1. **🔴 Десинхрон темпоральных пометок.** [buildUserMessage](../../backend/src/modules/knowledge-core/services/chat-v2.service.ts#L974)
   ВСЕГДА вставляет в контекст секции «цепочка рассуждения» и «противоречащий
   факт», но инструкция, как их читать, есть ТОЛЬКО в `BASE` (строки 337–338).
   Режимы «факт»/«синтез» её не содержат → на боевом пути модель получает
   размеченный контекст, который не научена читать. Главное следствие — модель
   **проглатывает конфликт**: выдаёт один факт как истину, хотя в памяти два
   спорящих. Это прямо против обещания «честная память показывает противоречия».
   Уже было зафиксировано аудитом 09.06 ([40b-chat.md:103](../analysis/2026-06-09-prompt-rewrites/40b-chat.md)),
   в код не внесли.
2. **Ни один из 4 не по методологии.** Нет якорей смысла «кому/зачем/что станет с
   ответом» (блок 2), нет few-shot «плохо→хорошо» (блок 4), нет self-check
   (блок 5), тонкая персона. По методологии это главная причина «плоских» ответов.
3. **Кэш ломается.** `conversationSummary` и `history` кладутся в SYSTEM
   ([buildSystemPrompt:947–959](../../backend/src/modules/knowledge-core/services/chat-v2.service.ts#L947)),
   а не в конец USER — нарушение жёсткого требования №1 методологии. Плюс смена
   режима меняет системный префикс → cache-miss на каждом переключении факт↔синтез.
4. **Тройной дубль «## Формат».** Три режима почти дословно повторяют правила
   markdown/эмодзи/инлайн-маркеров — расходятся в мелочах, поддержка в трёх местах.
5. **Машинный (английский) контекст вместо человеческого.** Модель читает
   `(churn_risk)`, `[REASONING CHAIN FOR BLOCK]`, `[CONTRADICTING BLOCK]` —
   английские коды и теги. Нарушает жёсткое требование №3 методологии («вход
   модели — человеческий, не машинный»). Детальный разбор и доказательство
   фикса — §6.

## 2. Принятые решения (согласованы с владельцем 2026-06-14/15)

1. **Один промпт, без режимов.** Убираем понятия «факт»/«синтез»/«в стиле
   сотрудника» из ответчика. Остаётся ОДИН промпт: есть вопрос — отвечаешь, как
   сам считаешь нужным; глубину выбираешь по вопросу (так и тестировали).
2. **Темпоральные правила — внутри единого промпта.** Раз нет подмены режимов —
   инструкция про «цепочку рассуждения» и «противоречащий факт» живёт в общем
   промпте и больше не теряется (чинит проблему 1).
3. **Границы — только дела компании.** Промпт явно запрещает отвечать на
   посторонние темы, писать код, решать задачи не про компанию — вежливый отказ.
   Та же линия, что у самого помощника
   ([assistant-router-dedup](2026-06-14-assistant-router-dedup-and-prompt.md)).
4. **Длину не зажимаем.** Ориентир — понятность, а не число предложений: коротко
   на простой вопрос, но без искусственной обрезки, если момент надо пояснить.
5. **«О компании» — стабильная секция в конце SYSTEM.** chat-v2 представляется
   сотрудником конкретной компании. Per-tenant, меняется редко → префикс-кэш в
   рамках тенанта цел. Закрывает будущий пункт `company-profile-prompt-variable`.
6. **Кэш-структура.** Всё стабильное (роль, правила, few-shot, запреты, «О
   компании») — в SYSTEM; всё переменное (выжимка диалога, история, найденные
   блоки, вопрос) — в конец USER (чинит проблему 3).
7. **Человеческий контекст.** Английские коды/теги в контексте переводим в
   русские на границе «в промпт» — лучшее решение доказано в §6 (чинит проблему 5).
8. **Клон — НЕ режим chat-v2 и НЕ инструмент помощника.** Клон выбирается
   человеком из выпадающего меню в кабинете (как выбор модели); по умолчанию —
   общий помощник. **Через Telegram — только общий помощник, клоны кабинет-онли.**
   Вынос clone_style из режимов ответчика — здесь; UI-селектор и маршрутизация —
   отдельная работа (см. Scope «Не входит»).
9. **Таблицы — параллельный источник chat_v2, а не отдельный инструмент.** Умные
   таблицы ищутся ВНУТРИ chat_v2 параллельно с графом, на обогащённом понимании
   (3 формулировки + план: даты, сущности, темы). Отдельного `search_tables` у
   помощника нет — он растворён здесь (см. §7).

## 3. Архитектура: было → стало

**Было:** `dialog-layer` решает `mode` → `SynthesisService.modePrompt(mode)`
подставляет один из 3 системных промптов как `override` → `BASE` мёртв на этом
пути; темпоральные правила и формат разъезжаются по 3 текстам; summary/history в
SYSTEM; в контекст течёт английский (`signalType`, теги).

**Станет:** один системный промпт (Приложение A) для ВСЕХ ответов из графа;
`mode` больше не управляет текстом промпта; summary/history → конец USER; контекст
собирается на человеческом русском (русские ярлыки типов + русские теги).
clone_style как «режим письма» удалён.

## 4. Scope

**Входит:**
- Единый промпт-ответчик (Приложение A) — финальный, согласован с владельцем.
- `SynthesisService`: убрать выбор режима для текста промпта; всегда один
  системный промпт; `ChatV2Mode` перестаёт влиять на `systemPromptOverride`.
- `buildSystemPrompt`: вынести `conversationSummary`+`history` из SYSTEM в USER
  (вернуть в конец user-сообщения); «О компании» — стабильный хвост SYSTEM.
- `buildUserMessage`: человеческий контекст (§6) — русские ярлыки `signalType`
  через полный типизированный словарь; русские теги вместо
  `[REASONING CHAIN FOR BLOCK]`/`[CONTRADICTING BLOCK]`/`counter-evidence`.
- Обновить чистилку маркеров (strip-regex) под русские теги.
- `BASE_SYSTEM_PROMPT` — заменить на единый промпт (он же обслуживает старый
  `chat`-модуль; темпоральные правила в нём остаются — ничего не теряем).
- **Таблицы как параллельный источник** (§7): ветка поиска по умным таблицам внутри
  chat_v2, параллельно графу, на обогащённом понимании; строки таблиц — в контекст
  синтезатора с цитатами. Новое: выбор таблицы + server-side «применить фильтр → строки».
- Эталон промпта в `docs/methodology/prompts/examples/chat-v2-answer.md` + строка
  в реестре `upgrade-progress.md`.

**Не входит (отдельная работа, ссылки — чтобы не потерять):**
- **UI-селектор «общий помощник / клон»** у окна ввода (кабинет) + маршрутизация
  выбранного клона на `ClonesService.askPerson`. Фронт + роутинг — отдельное ТЗ.
- **Telegram-ограничение** «только общий помощник» — правило маршрутизации канала
  (в ТЗ помощника/каналов), здесь только фиксируем как решение.
- Логика гибридного поиска/ретривала, пороги графа, `uncertaintyNote`-эвристика —
  без изменений (кроме того, что́ кладётся в текст контекста).
- Brand-voice (`scope=org`) и `ClonesService.askPerson` — свои промпты, не трогаем.

## 6. Доказательство лучшего решения: человеческий контекст (проблема 5)

**Перепроверка показала ДВА разных источника английского — лечатся по-разному.**

### 6.1. Фиксированные теги — это константы, не переменные
`[REASONING CHAIN FOR BLOCK]`, `[CONTRADICTING BLOCK]`, заголовок
`Противоречия (counter-evidence):`, метаданные `depth=N nodes=K` — жёстко
прописаны в `buildUserMessage` ([стр. 996, 1009, 1012](../../backend/src/modules/knowledge-core/services/chat-v2.service.ts#L996)).
Ниоткуда не «заходят».
**Решение:** переименовать в русские и завести именованные константы (единый
источник), чтобы билдер, чистилка-regex и промпт ссылались на одно и то же:
- `[REASONING CHAIN FOR BLOCK <id>]` → `[ЦЕПОЧКА РАССУЖДЕНИЯ К ФАКТУ <id>]`
- `[CONTRADICTING BLOCK]` → `[ПРОТИВОРЕЧАЩИЙ ФАКТ]`
- `Противоречия (counter-evidence):` → `Противоречащие факты:`
- `depth=N nodes=K` убрать из видимого тега (служебное, модели не нужно).

### 6.2. `signalType` — ВОТ «переменная, которая заходит»
У каждого блока знаний есть тип-ярлык (`decision`, `pain`, `churn_risk`,
`objection`, `feature_request`…, ~25 значений `enum SignalType`). Сейчас он
вливается в контекст RAW по-английски ([стр. 982](../../backend/src/modules/knowledge-core/services/chat-v2.service.ts#L982)).
Словарь перевода `SIGNAL_TYPE_RU` в файле уже есть ([стр. 187](../../backend/src/modules/knowledge-core/services/chat-v2.service.ts#L187)),
но (а) применяется только в честном «по этим условиям не нашёл», в контекст НЕ
подставляется; (б) неполный (~10 из ~25); (в) схлопывает типы (`churn_risk`→
«риски»), что годится для фильтр-сообщения, но теряет точность в контексте.

**Матрица вариантов:**

| Вариант | Убирает утечку | Сохраняет смысл типа | Не трогает БД | Защита от будущих утечек | Вердикт |
|---|---|---|---|---|---|
| A. Переиспользовать `SIGNAL_TYPE_RU` как есть | частично (неполный) | теряет (схлопывает) | да | нет | ✗ |
| B. Убрать тип из контекста вовсе | да | нет (теряем рамку «это решение / это боль») | да | да (нечему течь) | ~ запасной |
| C. Переименовать `enum` в БД | да | да | **нет — ломает всю систему** | — | ✗ |
| D. Пусть модель сама переводит коды | нет (коды на входе) | — | да | нет | ✗ антипаттерн методологии |
| **E. Отдельный ПОЛНЫЙ типизированный словарь на границе** | **да** | **да (точные ярлыки)** | **да** | **да** | **✓ лучшее** |

**Почему E:**
- Методология (требование №3) предписывает переводить, а не показывать код. B
  (выкинуть) убирает утечку, но теряет интерпретирующую рамку, которая помогает
  модели калибровать ответ («это решение» vs «это жалоба клиента») → E > B по
  качеству.
- Точные ярлыки (`churn_risk`→«риск оттока», а не общий «риски») важны в
  контексте, в отличие от фильтр-сообщения → нужен ОТДЕЛЬНЫЙ словарь, не
  переиспользование схлопывающего `SIGNAL_TYPE_RU` → E > A.
- Не трогаем `enum` (используется всей системой) → нулевой blast-radius за
  пределами билдера контекста → E > C.
- **Машинный гард:** типизировать как `Record<SignalType, string>` — TypeScript
  заставляет дать русский ярлык КАЖДОМУ значению enum; добавили новый тип в
  схему без ярлыка → **сборка падает**. Это чинит весь КЛАСС утечки, а не
  один случай ([[feedback_fix_the_whole_class_not_the_case]]), и закрывает утечку
  навсегда → E > все.

**Состязательная перепроверка (challenge E):**
- «Зачем трение типизации?» — трение и есть гард: один тип без ярлыка ломает
  сборку (цена — одна строка). Это плюс, не минус.
- «Может, тип в контексте — шум?» — это лёгкая метаданная-рамка; если бы решили,
  что шум, выбрали бы B. Перевод строго лучше английского кода; решили оставить.
- «Часть типов хочется схлопнуть и в контексте?» — нет: в контексте точность
  помогает; схлопывание было нужно только фильтр-сообщению. Держим раздельно.
- Вывод: **E устойчив, фиксируем.**

**Стартовый словарь (дополнить до ВСЕХ значений `enum SignalType`):**
`fact`→факт · `pain`→боль (проблема) · `feature_request`→пожелание (запрос
доработки) · `objection`→возражение · `churn_risk`→риск оттока · `idea`→идея ·
`risk`→риск · `commitment`→обязательство · `decision`→решение · `mood`→настроение
· `drift`→отклонение · `competitor_move`→действие конкурента ·
`metric_change`→изменение метрики · `knowledge_gap`→пробел в знаниях ·
`reasoning`→рассуждение · `rationale`→обоснование · `decision_basis`→основание
решения · `regulation`→регламент · `process_step`→шаг процесса ·
`task_created`→задача · `task_completed`→выполненная задача · `plan_item`→пункт
плана · `done_item`→сделанное · `blocker`→блокер · `client_request`→запрос клиента.
> При реализации — свериться с актуальным `enum SignalType` в schema.prisma и
> покрыть КАЖДОЕ значение (компилятор не пропустит пропуск).

## 7. Таблицы как параллельный источник chat_v2 (одобрено 2026-06-15)

Решение владельца: умные таблицы ищутся НЕ отдельным инструментом помощника, а
ВНУТРИ chat_v2 — параллельной веткой к поиску по графу, на том же обогащённом
понимании запроса. Пользователь не говорит «найди в таблице» — он просто
спрашивает, а chat_v2 смотрит и в граф, и в таблицы и отдаёт синтезатору единый
контекст для одного финального ответа.

**Вход ветки — обогащённое понимание (уже есть в dialog-layer), НЕ сырой вопрос:**
3 переформулированных вопроса + извлечённый план (период/даты, `entityHints` —
имена клиентов/проектов, темы, флаг `aggregation`).

**Механика (4 шага, параллельно с `fetchCandidates` по графу):**
1. **Какая таблица.** Подобрать релевантную(ые) таблицу(ы) по `Table.name` +
   `Table.description` + именам колонок (`TableProperty.name`) против запроса/
   сущностей/темы. Таблиц у тенанта немного → выбор дешёвый (LLM-пик или
   keyword/entity-match; эмбеддинги таблиц не обязательны).
2. **Какие строки.** На выбранной таблице — **готовый** движок
   `TableSemanticFilterService.parseSemanticFilter` (вход — обогащённый вопрос,
   выход — фильтр по колонкам ЭТОЙ таблицы). Нюанс: план dialog-layer — это
   понятия ГРАФА (темы/типы); он выбирает таблицу и даёт контекст, а фильтр по
   КОЛОНКАМ считает табличный движок против реальных колонок.
3. **Достать строки на сервере (НОВОЕ).** Сейчас фильтр применяется на фронте;
   для chat_v2 нужно применить его на бэке и вернуть строки. Быстрый индекс по
   ячейкам (`table_row_cells_gin`, jsonb_path_ops) уже есть → дёшево.
4. **Подмешать в контекст.** Найденные строки идут синтезатору как ещё один
   источник, со своей цитатой-ссылкой на таблицу/строку. Агент пишет ОДИН ответ
   из графа + таблиц.

**Почти бесплатный точный путь (entity-bridge).** Строки таблиц уже умеют
линковаться к сущностям графа (`Table.entitySync`, `TableRow.entityId`). Для
вопросов про конкретную сущность («что по Заречному») таблицу можно не угадывать:
граф нашёл сущность → по `entityId` подтянули её строку. Шаги 1–2 нужны для
запросов-срезов («сколько клиентов из Москвы», «что на гарантии»).

**Что новое / что переиспользуем.**
- НОВОЕ: (а) шаг выбора таблицы; (б) server-side «применить фильтр → строки»;
  (в) ветка в retrieval chat_v2 + цитаты табличных строк + показ их в промпте.
- ГОТОВОЕ: `parseSemanticFilter`, связь строка↔сущность (`entitySync`/`entityId`),
  весь слой понимания запроса (3 формулировки + план), GIN-индекс по ячейкам.

**Параллельность и отказоустойчивость.** Ветка таблиц запускается одновременно с
графовым retrieval (не последовательно) — по времени почти не дороже. Падение
ветки таблиц НЕ валит ответ (граф отвечает как раньше).

**Что станет работать:** «сколько у нас клиентов из Москвы», «какое оборудование
на гарантии», «поставщики с долгом» — данные берутся/считаются из таблицы и
вплетаются в общий ответ.

## 12. Риски
- **Регрессия старого `chat`-модуля.** `BASE_SYSTEM_PROMPT` обслуживает и его.
  Митигейшн: единый промпт — надмножество правил `BASE` (темпоральные правила
  сохранены); прогон тестов `chat.service`.
- **Потеря «короткости» factual.** Раньше «факт» жёстко резал до 1–3 предложений.
  Митигейшн: правило длины в промпте («коротко на простой вопрос, без воды»);
  наблюдаем среднюю длину ответа на проде.
- **Неполный словарь типов.** Митигейшн: типизация `Record<SignalType,string>` —
  сборка падает при пропуске.
- **Кэш-инвалидизация разово.** Смена SYSTEM-промпта разово сбросит prompt-cache —
  приемлемо (требование №1 методологии).
- **Ветка таблиц добавляет латентность/стоимость.** Митигейшн: запускать параллельно
  с графом (не последовательно); выбор таблицы дешёвый; кэш фильтра (Redis 7д) уже есть;
  падение ветки → отвечаем по графу. Лимит числа таблиц/строк в контекст — крутилкой.
- **Неверный выбор таблицы → лишние строки в контексте.** Митигейшн: порог релевантности
  при выборе; entity-bridge точнее угадывания; синтезатор цитирует источник — человек
  видит, откуда данные.

## 13. Prod-операции (при выкате)
- Промпты — code-fallback / registry; маршрут и модель chat-v2 не меняются.
- ENV/миграций нет. «О компании» — источник per-tenant (указать при реализации;
  пустой → секция опускается, поведение деградирует мягко).
- Прочее — обычный `docker compose up -d --build backend`.

### SYSTEM, часть 1 — стабильная (few-shot внутри → кэшируется для всех компаний)
```
## Роль
Ты — Кора, ИИ-помощник по памяти компании. Отвечаешь сотрудникам компании
на их вопросы, опираясь ТОЛЬКО на то, что компания уже зафиксировала: встречи,
переписки, решения, документы. Ты не универсальный чат-бот — ты память
и аналитик одной конкретной компании (она описана в разделе «О компании» ниже).

## Кому ты отвечаешь и что будет с ответом
- Спрашивает сотрудник компании — из кабинета или из мессенджера. Он может быть
  не из технического отдела: пиши на нормальном человеческом языке.
- Твой ответ — финальный. Его покажут человеку как есть, никто не будет его
  переписывать после тебя. Значит, он должен быть сразу понятным, аккуратным
  и честным.
- Человек спрашивает, чтобы быстро узнать, что компания уже знает или решала
  по теме, не поднимая вручную встречи и переписки. Сэкономь ему это время.

## Границы — только дела компании
Ты отвечаешь ТОЛЬКО на вопросы про эту компанию и её работу — то, что есть
или может быть в её памяти (см. «О компании» ниже).
- На посторонние темы (общие знания, новости, погода, развлечения, личные
  советы, «расскажи что-нибудь») — не отвечаешь.
- Код не пишешь и задачи, не связанные с компанией, не решаешь.
- На такую просьбу вежливо откажись: коротко скажи, что ты помощник по памяти
  компании и можешь помочь только с вопросами про неё. Не придумывай ответ
  ради «полезности».

## Как ты отвечаешь
1. Только из контекста. Опирайся строго на раздел «Контекст» в сообщении ниже.
   Не добавляй знаний «из общего опыта», которых в контексте нет.
2. Глубину выбираешь по вопросу — без жёсткого лимита. На простой фактический
   вопрос отвечай коротко и по сути. Но если какой-то момент важно пояснить,
   чтобы человек точно понял, — поясни, не обрезай себя искусственно. На вопрос
   «почему / как / в целом» — давай развёрнутый разбор. Ориентир — понятность,
   а не число предложений; и без воды.
3. Ссылайся на источник. Каждый факт подкрепляй маркером [BLOCK:<id>] прямо
   рядом с фактом — из него получится кликабельная ссылка на источник. Можно
   несколько маркеров на одно утверждение. Не придумывай номера, которых нет
   в контексте.
4. Честно про пустоту. Если ответа в контексте нет — так и скажи: «В памяти
   компании я этого не нашёл» — и не досочиняй.
5. Честно про надёжность. Где это важно, помечай словами, насколько факт
   надёжен: «по нескольким источникам» (подтверждён 2+ блоками), «однажды
   упоминалось» (единичный источник), «возможно устарело» (явно старее
   остальных или есть конфликт). Не вешай эти пометки на каждое предложение —
   только там, где это меняет доверие к факту.
6. Конфликт не заглаживай. Если факты спорят — назови оба
   ([BLOCK:<id1>] vs [BLOCK:<id2>]) и предложи человеку уточнить, какой
   актуальный. Никогда не выбирай «правильный» сам.

## Особые пометки в контексте (подсказки для тебя; в ответе их не показывай)
- «Цепочка рассуждения к факту» — разложенное «почему»: решение ← обоснование
  ← факты. Используй её для хорошего ответа на «почему», но ссылайся маркером
  только на исходный факт, а не на каждое звено.
- «Противоречащий факт» — кусок, который спорит с основным. Обязательно скажи
  про разногласие, не игнорируй; предложи уточнить, что сейчас актуально.
- «Данные из таблиц» — строки из умных таблиц компании. Используй наравне с
  фактами; при ссылке указывай таблицу «<название>» (цитата подставится сама).
  На счётный вопрос («сколько…») посчитай по строкам и дай число.

## Примеры (плохо → хорошо)
1. Два факта спорят.
   ✗ «Запуск назначен на март.»  (взял один, конфликт спрятал)
   ✓ «Данные расходятся: по одному обсуждению запуск в марте [BLOCK:11], по
     более позднему — перенесён на май [BLOCK:42]. Уточните, какая дата в силе.»
2. Ответа в памяти нет.
   ✗ «Обычно онбординг занимает пару недель.»  (досочинил из общих знаний)
   ✓ «В памяти компании я не нашёл, сколько занимает онбординг новичка —
     похоже, это нигде не зафиксировано.»
3. Технический мусор в ответе.
   ✗ «По данным CompanyProfile и блока decisions решение принято.»
   ✓ «Решение принято на встрече по партнёрству [BLOCK:7].»
4. Вопрос «почему».
   ✗ перечисляет каждое звено цепочки как отдельный факт с кучей маркеров.
   ✓ «Скидку убрали: она съедала маржу и не давала роста повторных
     продаж [BLOCK:5].»
```
