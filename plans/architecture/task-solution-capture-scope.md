# Захват решений с любого источника — архитектура человеческим языком

## Зачем (одно предложение)
Сделать так, чтобы «как решили задачу» попадало в «Решение задачи» **из любого источника, который мы и так
разбираем раз в сутки** (встреча, чат, голосовая заметка, ответ на вопрос Коры) — а не только из ответа на
конкретный уточняющий вопрос, как сейчас.

## Как это работает СЕЙЧАС (что есть)
1. Раз в сутки крон собирает «Решения задач». Он находит материал по задаче **только** если у сигнала есть
   пометка `contextCardId` — а её ставит **единственное** место: ответ на probe (вопрос Коры «расскажи, как
   решил»). Итог: рассказал «как починил» на планёрке или в чате — мимо, решение не соберётся.
2. **Но рядом уже работает нужный мост.** Есть петля закрытия задач (`TaskCompletionHandler`): когда в **любом**
   разговоре звучит «сделал / закрыл / починил» (сигналы `task_completed / done_item / task_status_changed`),
   система:
   - берёт этот кусок,
   - ищет по смыслу (embedding → ближайшие ОТКРЫТЫЕ задачи) конкретную задачу,
   - проверяет LLM-верификатором «правда ли про эту задачу»,
   - и связывает кусок с задачей записью `TaskClosureCandidate` (блок ↔ задача, с оценкой похожести).
   Это ровно тот матч «кусок разговора → конкретная задача», которого не хватает сборке решений. Просто сборка
   решений его сегодня **не использует**, а сами эти сигналы (`task_completed/done_item`) **не входят** в её
   узкий набор «как решали».

**Вывод:** «захват с любого источника» и «расширить набор сигналов» — это **одна и та же** задача. Мост
построен и проверен на проде для закрытия задач; надо подключить его к сборке решений.

## Что делаем (суть изменения)
Соединить два конвейера. Дать суточной сборке «Решений задач» второй, главный источник детекции —
**матч блок↔задача из любого разговора** (тот же механизм, что рождает `TaskClosureCandidate`), а не только
пометку `contextCardId`.

Конкретно:
1. **Источник детекции** сборки решений = объединение: (а) блоки с `contextCardId` (как сейчас, probe) **плюс**
   (б) блоки, уже примэтченные к задаче петлёй закрытия (через `TaskClosureCandidate` / тот же матчер
   embedding→задача + верификатор). Любой источник (встреча/чат/заметка) — если кусок примэтчился к задаче.
2. **Набор «как решали» расширяется** и включает ретро-описания результата (`task_completed / done_item`,
   привязанные к задаче) — именно они несут «как именно сделал».
3. Всё остальное (владелец = решавший, гейт содержательности, рост клонов, одна задача = одно решение) —
   **без изменений**, работает поверх нового источника материала.

## Как будет выглядеть (глазами пользователя)
- Инженер на планёрке: «Я поднял SSO — настроил SAML, смапил группы». Задача «Настроить SSO» открыта →
  кусок примэтчился к ней → ночью собралось «Решение задачи: Настроить SSO» (как именно), клон инженера вырос.
- Менеджер в чате: «Закрыл возврат по клиенту — сделал идемпотентный ключ и дедуп». → «Решение задачи» по
  этому тикету, без единого вопроса от Коры.
- Ответ на вопрос Коры (probe) — как и раньше.
Единый смысл: **захват с любого источника, который мы разбираем раз в сутки.**

## Риски и границы (честно)
- **Ложный матч блок↔задача** (кусок привязался не к той задаче). Митигировать тем же порогом похожести и
  LLM-верификатором, что уже держит петлю закрытия; при низкой уверенности — не собирать решение (лучше
  пропустить, чем приписать чужой задаче). Порог — крутилка.
- **Двойной счёт** (один кусок и закрывает задачу, и кормит решение) — это НЕ конфликт: закрытие и «как решили»
  — разные сущности; кусок легитимно участвует в обоих. Дедуп — по `sourceBlockIds` внутри решения (уже есть).
- **Провабельность.** На нынешнем стенде вход хардкодится (`contextCardId` каждому блоку) — новый захват там
  «зелёный» ложно. Доказывать ТОЛЬКО сквозным e2e-режимом стенда (сырой текст → классификация → матч к
  задаче → сборка), это Блок E большого ТЗ. Без e2e — не принимать.
- **Открытые vs закрытые задачи.** Петля закрытия матчит среди ОТКРЫТЫХ задач. «Как решили» часто звучит в
  момент закрытия — надо учесть окно (задача только что закрылась этим же куском). Решить в ТЗ: матчить среди
  открытых + недавно закрытых.

## Что НЕ входит
- Смена самой петли закрытия задач (её поведение не трогаем — только переиспользуем результат матча).
- Ручная привязка «этот кусок — к той задаче» в UI (vNext).

## Решение владельца
Направление одобрено (захват с любого источника — ядро). Эта заметка фиксирует КАК: переиспользовать
существующий матч блок↔задача, а не строить новый. Реализация — Блок A большого ТЗ
[plans/tz/2026-07-08-task-solution-real-defects.md](../tz/2026-07-08-task-solution-real-defects.md),
доказательство — только через e2e-режим стенда.
