# Клоны сотрудников: аудит реализации, разрыв с замыслом «эксперт всегда», гипотезы улучшений

> Снято research-фан-аутом 2026-07-03 (8 параллельных читателей кода/доков/git + критик полноты + живой SQL к Стреле). Строки кода дрейфуют — указаны якорь-символы.

## TL;DR для владельца

1. **Конвейер сборки клона — сильный и глубокий** (5 слоёв персоны, регламенты Способа C, версионирование с freeze при смене носителя, «совет бывших»). Вся фактура для экспертного ответа в промпт уже собирается.
2. **Но политика ответа — ровно противоположна замыслу.** Клон спроектирован refusal-first («лучше отказ, чем выдумка»): 4 контура отказа. Замысел «клон всегда отвечает как эксперт, по аналогии, как сам сотрудник или лучше» ни в одном ТЗ не зафиксирован — единственный «экспертный» режим (judgmental, ответ по аналогии) заперт за выключенным флагом `CLONE_V2_ENABLED=false`.
3. **Ретрив клона не ищет по вопросу.** В контекст идут «последние 20 reasoning-блоков», а не блоки, релевантные вопросу. Механизм «поиск опыта по аналогии» (multi-query) уже написан и даже вызывается — но его результат никуда не подключён.
4. **Разворот — это не «снести анти-deepfake», а переприцелить его.** Запретная зона (обещания от лица носителя, оценки коллег, прогнозы по сделкам, выдуманные конкретные факты) — сохраняется как железный инвариант. Меняется судьба «пробела»: вместо отказа — экспертный ответ по лестнице опоры с честной маркировкой.
5. Дальше: стенд на ~110 вопросов с линейкой оценки и петлёй итераций до планки — проект в [plans/architecture/2026-07-03-clone-quality-stand.md](../architecture/2026-07-03-clone-quality-stand.md).

## 1. Как клон работает сейчас (факт по коду)

### 1.1 Сборка: блок → черта → персона

Вход конвейера — **только** canonical-блоки `signalType ∈ {reasoning, rationale, decision_basis, methodology_step}` с `role='subject'` у сотрудника (`SKILL_SUBJECT_SIGNAL_TYPES`, `backend/src/modules/knowledge-core/constants/skill-signal-types.ts`). Операционка (task_*, decision, commitment, fact) клона НЕ кормит.

Пороги рождения (события + cron-ы, всё автоматически):
- ≥5 subject-блоков клон-типа (`knowledge.skillProfileMinObservations`, fallback 5) → rebuild профиля (debounce 60с);
- кластеризация по cosine ≥ 0.78 (`GROUP_SIMILARITY_THRESHOLD`, хардкод), группа ≥3 блоков → LLM-черта в 4 слоях: skill / value+motivation (только из trade-off) / process_marker (со стоп-листом токсичных ярлыков);
- новая черта — `pending_verification`, промоут кроном 03:30 (LLM-верификатор «≥2 цитаты о СОБСТВЕННОМ подходе»; **сбой LLM = fail-open promote в active**);
- merge: KNN top-5, hard-bucket ≥0.85, LLM-арбитр с форс-merge;
- decay: 6 мес → понижение confidence, 12 мес → архив.

`ExecutablePersona`: person-scope требует ≥3 активных skill-черт (`PERSONA_MIN_TRAITS`); role-scope — ≥2 активных профилей носителей (`PERSONA_ROLE_AGG_MIN_PERSONS`). Компиляция — LLM `executable-persona-compile` (5 секций, инвариант Personality Illusion: «поведенческое правило процесса с якорем, не ярлык», 300–1200 слов). Пересборка: cron вс 06:00 (**захардкожен в декораторе, ENV `PERSONA_BUILD_CRON` не влияет**) + trigger-watcher каждые 2ч + on-demand при ask. Клон роли версионируется: `roleVersion`, `publicName='Клон <Role> vN'` без ФИО, freeze при смене носителя (`role.bearer_changed`), «совет бывших» — `ask-all-formers` (до 8 версий).

Отдельная подсистема — **KnowledgeProfile** (специалист 3-2, «что сотрудник знает»): JSON на Person, из блоков subject|mentioned, ≥10 блоков, материализация при triage `auto` ИЛИ confidence ≥ `knowledgeClone.profileMinConfidence` (0.55, Пакет E).

### 1.2 Ответ: что собирается в промпт

`ClonesService.askPerson/askRole` → один LLM-вызов `clone-respond` (dataClass `internal`; primary по сидам deepseek-v4-flash — порядок STEPS `skill-and-clone` раньше `clone-v2`, фактический прод-роут проверять по `LlmTaskRoute`). В user-промпт (`CLONE_RESPOND_USER_TEMPLATE`, `knowledge-core/prompts/clone-respond.prompt.ts`):

| Блок | Person-клон | Role-клон |
|---|---|---|
| personaPrompt (5 слоёв) | ✅ | ✅ |
| Reasoning-блоки `[BLOCK:id]` | ≤20 **последних** | ≤20 последних всех носителей |
| KnowledgeProfile | однострочная сводка топ-8 «имя (confidence)» | ❌ жёстко null |
| Decisions `[DECISION:id]` | ≤10 недавних | ❌ пусто |
| PracticeSkill `<known_procedures>` | ✅ KNN по вопросу, top-3, cosine ≥0.78 | ✅ |
| Регламенты `<applicable_regulations>` + `<regulations_index>` | ❌ не подмешиваются | ✅ KNN по 4 таблицам, top-6, «ПРИОРИТЕТ над личным опытом», [blocking] нельзя нарушать |

**Ключевая механика ретрива: subgraph НЕ ищется по вопросу.** `loadPersonSubgraph` берёт до 40 mentions (**findMany без orderBy — недетерминированный срез при >40**) → 20 блоков по `createdAt desc`. Векторный поиск по вопросу есть только у practice-skills и регламентов. Вопрос по старой/нишевой теме систематически не попадает в окно → ложный `topic_starved` при реально существующих знаниях (якорь `loadPersonSubgraph`, `clones.service.ts`).

### 1.3 Четыре контура отказа (refusal-first by design)

1. **Гейт существования**: нет active SkillProfile → 404 `no_clone`; активных черт < 3 (`MIN_TRAITS_FOR_ANSWER=3` — **хардкод, не крутилка**) → 404 `starved_profile`; персона не собралась → 404 `persona_unavailable`.
2. **Анти-deepfake topic-density ДО LLM** (`assertTopicDensity`): < 2 блоков субграфа с cosine ≥ 0.7 к вопросу (`CLONE_TOPIC_MIN_BLOCKS=2`, `CLONE_TOPIC_SIMILARITY_THRESHOLD=0.7` — ENV, не AdminSetting) → программный отказ `topic_starved` фикс-текстом. Действует **в обоих режимах** (Ф6 2026-06-08 сознательно). При сбое эмбеддера — **fail-open** (проверка молча пропускается).
3. **Промпт**: factual-правила 3/6/8 прямо предписывают отказ («Лучше промолчать, чем сгенерировать правдоподобный deepfake», «Любой пробел — лучше отказ, чем выдумка»); финальная строка user-промпта дублирует «Если ответа нет — честно скажи».
4. **Grounding-гейт ПОСЛЕ LLM** (`isUngrounded`): factual-ответ без единой валидной цитаты `[BLOCK:id]`/`[DECISION:id]` **заменяется** отказом `ungrounded` (готовый текст LLM выбрасывается). `CLONE_RESPOND_GROUNDING_ENABLED=true`.

Отказ подаётся как фича: прод-приёмка 2026-06-23 ТРЕБОВАЛА отказ на вне-темном вопросе; метрика `clone_ask_refused_total{reason}`.

### 1.4 Режимы и ловушка интента

- `factual`: обязательные цитаты, гейты 2-4.
- `judgmental`: «разрешено отвечать по АНАЛОГИИ: применять общие принципы из опыта роли к новой ситуации, даже если точного прецедента нет»; grounding-гейт выключен, цитаты `[BLOCK:]` вырезаются из текста (остаются в метаданных; `[DECISION:]` при этом НЕ вырезается — микротрещина). Температура режимами не различается (в `llm.call` не передаётся). **Доступен только при `CLONE_V2_ENABLED=true` (default false, в проде ВЫКЛ)** → на проде каждый вопрос идёт factual — с одним исключением: `ask-all-formers` захардкожен на V2-ветку и может уйти в judgmental даже при выключенном флаге (нужен лишь CloneAccessGrant).
- Выбор режима — intent-классификатор dialog-layer: `exploratory|analytical → judgmental`; `factual|clone_roleplay → factual`. **Ловушка:** самая естественная формулировка «спроси клона маркетолога…» / «как ответил бы CFO…» классифицируется как `clone_roleplay` → попадает в САМЫЙ СТРОГИЙ режим.
- **Multi-query «опыт по аналогии» вычисляется, но не используется**: `dialog.queries` (3 формулировки: точная / похожая ситуация / общий принцип) попадают только в `llmMeta.dialogQueriesCount`; retrieval остаётся «последние 20», topic-density считается по standaloneQuestion. Аналогия существует лишь как разрешение в judgmental-промпте, не как поиск.
- Внутреннее противоречие промпта: финальная строка user-шаблона «Цитируй контекст в формате [BLOCK:id]» добавляется всегда, включая judgmental, где system это запрещает.

### 1.5 Поверхности и доступ

- **Frontend умеет спрашивать только клона РОЛИ** (`clonesApi.askRole`); askPerson в UI отсутствует — person-клон достижим только прямым API. Поверхности: `/clones` (маркетплейс), `/clones/[roleId]` (чат), `/me/clone`, `/roles/[id]/clone`, `/admin/clones` (гранты).
- **Telegram**: у консьержа есть tool `ask_role_clone` (confirm-flow) + `list_clones`; person-клона в Telegram нет.
- Доступ (V2 off): person — owner/admin | self | manager того же департамента; role — rbac `role:read` (owner/admin/manager/coo/hr_partner; **рядовой member клона роли спросить не может**). V2: только `CloneAccessGrant` — даже owner/admin без гранта режутся; `ask-all-formers` захардкожен на `cloneV2Enabled:true` → грант нужен уже сейчас.
- Квота: единая ai_chat 50/день (owner/admin/coo) / 20 (member) — через `resolveSync('aiChatQuota.dailyLimit*')`, т.е. admin→ENV→код. `CLONE_ASK_PER_USER_PER_DAY` — мёртвая переменная, никем не потребляется.
- `KNOWLEDGE_ACCESS_ENFORCEMENT='off'` на проде → фильтрация знаний по группам в клоне не активна; dataClass блоков при сборке субграфа не проверяется.

## 2. Главная развилка: замысел владельца vs текущий контракт

**Замысел (зафиксирован владельцем 2026-07-03):** категория «AI-клоны сотрудников» рождается на рынке; Кора должна стать в ней лучшей. Идеальный клон: сотрудник уволился — клон отвечает на любой вопрос как он сам **или лучше**. Клон **всегда** отвечает как эксперт: у него роль, черты, скиллы, регламенты, знания — он обязан выдать позицию/совет/план действий. «Такой ситуации не было» — не ответ: была похожая (в т.ч. с другой компанией/другим объектом) — бери её за основу и рассуждай. Ответ «по факту есть/нет» — это режим справочника, не эксперта.

**Текущий контракт:** ровно обратный (см. 1.3). Единственная фиксация замысла «советуй всегда, без анти-дипфейк-гейта» в доках — одна фраза про ненаписанное ТЗ #2 глобальных экспертных клонов (`plans/tz/2026-06-02-expert-clones-creation.md:144`, draft).

**Что НЕ разворачиваем (сохранить как железные инварианты):** запрет обещаний/согласий/отказов от лица носителя, запрет оценок коллег и прогнозов по конкретным сделкам, запрет выдуманных конкретных фактов (имена/суммы/даты/статусы/провенанс), дисклеймер «ответ — от клона должности», тенант-изоляция. Это ядро доверия к продукту — без него «лучший клон» превращается в опасный deepfake. Разворачиваем только судьбу **пробела**: вместо отказа — экспертный ответ по лестнице опоры с честной маркировкой источника уверенности.

**Целевой контракт ответа — «лестница опоры» (предложение):**

| Ступень | Опора | Как отвечает |
|---|---|---|
| 1. Прямой опыт | ≥2 блока по теме | как сейчас factual: уверенно, с цитатами |
| 2. Аналогия | похожая ситуация/другой объект в опыте | «Точно такого не было, но в похожей ситуации X я делал Y — исходя из этого…» + цитаты аналога |
| 3. Принципы/регламенты | черты, RolePrinciple, регламенты | «Мой принцип в таких случаях — …, поэтому я бы…» |
| 4. Экспертное суждение роли | только персона + профиль знаний | «Прямого опыта нет — как <роль> я бы рассуждал так: … Рекомендую сверить с носителем» |

На каждой ступени — обязательная маркировка ступени (прямой опыт / по аналогии / по принципам / экспертное предположение). Отказ остаётся ТОЛЬКО для запретной зоны и полностью вне-доменных вопросов (и даже там — вежливая переадресация, а не «Спроси напрямую»).

## 3. Сильные стороны (не потерять при развороте)

1. **Слоистая персона с инвариантом Personality Illusion** — «правило процесса с якорем, не ярлык»; 4 слоя черт + принципы роли + процедуры. Это и есть будущий «эксперт»: фактура для ступеней 3-4 лестницы уже собирается.
2. **Регламенты Способа C с субординацией** (blocking → mandatory → опыт → advisory) — уникальный слой «клон подчиняется письменным правилам компании».
3. **Версионирование + freeze + «совет бывших»** — готовая механика сценария «сотрудник ушёл, клон остался» (ядро категории).
4. **Анти-deepfake запретная зона** — конкурентное преимущество доверия (см. §7: рынок это почти не решает).
5. **Наблюдаемость**: CloneQueryLog (each ask, refusalReason), метрики clone_ask_*, llmMeta с topicMatchedBlocks — стенд может диагностировать каждый отказ.
6. **Готовые прецеденты судей**: `persona-behavior-judge` (шкала 1.0/0.5/0.3/0.0, «честный отказ при существовавшем ходе = 0.3»), `RAG_GROUNDEDNESS_LENIENT` (поле fabricated), probe-judge (directLlmCall без AppModule).
7. **Кумулятивность и гигиена черт**: merge-арбитр, verify-гейт, decay, стоп-лексика токсичных ярлыков.

| Т14 | Клон отрезан от общего графа компании: субграф = только СВОИ reasoning-блоки (+сводка знаний/решения); факты дел компании (клиенты, пилоты, блокеры), которые «сотрудник бы помнил», клону недоступны | `loadPersonSubgraph`/`loadRoleSubgraph` | на вопрос «как нам удержать Ромашку?» клон не видит ни жалобу, ни блокер — эксперт без материалов дела |
| Т15 | Штатный канал корма «задача решена → probe „расскажи, как решал“ → ответ → клон» РЕАЛИЗОВАН (Ф5/Ф6 2026-06-29, коммиты c10095ae/d19f6126): probe срабатывает на любой переход в completed (update/transitionState/DnD/Telegram), ответ ингестится в общий конвейер с `signalTypeHint='reasoning'` (`probe-response.handler.ts` якорь `ingestResponseAsRawEvent`) и кормит клона. НО живут остаточные гейты-риски: complexity-гейт ≥0.5 отсекает простые задачи (формула: описание/280 симв. + активности/8 + дни жизни/7); rate-limit probe 5/час и 20/день на юзера; content/semantic-dedup probe; hint применяется только к ПЕРВОМУ извлечённому блоку (длинный голосовой ответ даст остальные блоки не-клонных типов) | `probe-response.handler.ts`, `issues.service.ts` якоря `maybeRaiseMethodCaptureProbe`/`computeMethodCaptureComplexity` | канал по коду работает — стенд валидирует его КОЛИЧЕСТВЕННО (воронка кормления §5.2 стенда): сколько ответов реально доходит до черты и что отсекают гейты |

## 5. Гипотезы улучшений (приоритизировано под замысел)

- **H1 — Разворот политики ответа на «лестницу опоры» (§2).** Гейты topic_starved/ungrounded из блокираторов становятся **переключателями ступени**; отказные тексты уходят; запретная зона остаётся. Новый режим ответа = один system-prompt с лестницей вместо пары factual/judgmental. Ожидаемый эффект: REFUSED → ~0 на отвечаемых, главный рычаг к планке.
- **H2 — Семантический ретрив субграфа по вопросу** (KNN блоков клон-типа по embedding вопроса + multi-query аналогии из Т4, который уже написан) вместо «последних 20». Дешёвый и большой выигрыш: лечит Т2, питает ступень 2 лестницы.
- **H3 — Включить intent-роутинг правильно**: `clone_roleplay` → экспертный режим (не строгий factual); порог судьбы V2 решить (включить или перенести judgmental-механику в v1-путь).
- **H4 — Симметрия слоёв**: регламенты в person-клона; KnowledgeProfile (цитаты, не однострочник) + decisions в role-клона. Лечит Т5/Т6.
- **H5 — Пороги ответа в AdminSetting** (`clone.answer.*`): minTraits, topicMinBlocks, topicSimilarity, groundingMode, ladderEnabled. Без этого петля стенда не сможет итерироваться быстро. Лечит Т8.
- **H6 — Оживить PracticeSkill** (кластер C4): пороги в AdminSetting, shadow→активнее на малом трафике, Р11 (кандидаты «на испытании» с пометкой). Лечит Т7 — это слой «как действовать», ядро экспертного совета.
- **H7 — Раскрутить штатный канал корма**: мостик «задача решена → probe „расскажи, как решал“ → ответ → reasoning-блок → клон» уже реализован (Т15) — рычаг теперь в его ПРОПУСКНОЙ СПОСОБНОСТИ: калибровка complexity-гейта (0.5 отсекает типовые задачи — а именно повторяющиеся задачи дают кластеры черт), rate-limit probe под кампанию наполнения, применение hint ко всем блокам ответа, + CDM-интервью и канал «Мысль». Лечит Т13/Т15 — прод-риск №1 категории: без входа клон пуст при идеальном коде.
- **H8 — Наблюдаемый fail-open**: метрика + флаг «гейт пропущен из-за сбоя» в llmMeta. Лечит Т9.
- **H9 — Цитаты с meetingId/deep-link** (заполнить в loadSubgraph). Лечит Т10, важно для доверия «клон уволившегося».
- **H10 — Замкнуть петлю обучения** (после стенда): 👍/👎 + правка носителя → DPO-loop ТЗ. Лечит Т12; долгосрочный ров.
- **H11 — «Материалы дела» из общего графа**: к личному опыту клона подмешивать релевантные вопросу факты компании (retrieval по графу с фильтром доступа спрашивающего, как в chat-v2) отдельным блоком «Контекст дела» — эксперт отвечает про КОНКРЕТНУЮ ситуацию компании, а не абстрактно. Лечит Т14; без этого «как сам сотрудник или лучше» недостижимо: живой сотрудник помнит дела, клон — нет.

Порядок внедрения через петлю стенда: baseline → H5 (крутилки, без них итерации дороги) → H1+H3 (разворот) → H2+H4 (опора) → перепрогон → H6/H7/H9 по показаниям линейки.

## 7. Рынок employee-clone (сводка ресёрча 2026-07-03, 16 поисков + 6 глубоких разборов)

**Категория реальна и финансируется.** Ключевые игроки: **Viven** ($35M seed, Khosla; основатели Eightfold) — ближайший конкурент: пассивный сбор из email/Slack/Docs/встреч, twins отсутствующих/уволившихся, pairwise privacy, но enterprise-сегмент; **Delphi.ai** ($16M Series A, Sequoia) — клоны экспертов из загруженных материалов, Interview Mode (клон сам интервьюирует создателя), цитаты до секунды видео; **Eudia** (legal) — единственные, кто продуктизировал верность РЕШЕНИЙ (позиции/fallback/риск-толерантность) и продаёт бизнес-метрики (78% ускорение ревью); Praxis AI, Personal AI, MindBank, IgniteTech MyPersonas, Microsoft DigitalMe (внутр.). **В РФ прямых аналогов нет** (Teamly/Minerva — базы знаний, не клоны). Полные ссылки — в отчёте ресёрча (транскрипт агента 2026-07-03).

**Критерии «идеального клона», сложившиеся в категории и исследованиях** (входы для нашей линейки): groundedness/цитируемость; верность знаний (Stanford Generative Agents: 85% совпадения с человеком — эталонная цифра); верность рассуждений/решений (Eudia); стилевая верность (бенчмарк TwinVoice, 6 осей — LLM слабее всего в синтаксическом стиле и **воспоминании фактов**); консистентность в мультитёрне; Individual Turing Test (не проходит никто); privacy-осознанность (Viven); бизнес-исход. **Критично для стенда: LLM-судьи ненадёжны в оценке клонов** (PersonaEval: 69% у лучших LLM vs 90.8% у людей) → линейка обязана опираться на ground truth (на синтетике он известен по построению), LLM-жюри — только поверх.

**Белые пятна категории — совпадают с нашим замыслом:**
1. **Поведение при пробелах как управляемая лестница** — вся категория ловится в вилку «отказ (Delphi/Viven) vs тихий дрейф-галлюцинации»; явной градации «факт → процедура → аналогия → помеченная экстраполяция» нет ни у кого. Это ровно H1.
2. **Клон должности** — все клонируют личность; клон роли (агрегат носителей + регламенты + freeze/версии) у нас уже есть — уникален в категории.
3. **Публичная метрика качества клона** — нет ни у кого; наш стенд + shadow-тест (клон отвечает на вопрос, на который сотрудник потом реально ответил на встрече — бесплатный ground truth из живого потока) = продуктовая фича «fidelity scorecard».
4. **Автоклон из рабочих коммуникаций для SMB** — Viven пассивен, но enterprise; творческие — ручная загрузка. Сегмент 15–60 пуст, в РФ пуст полностью.
5. **Exit-интервью силами клона** — Delphi Interview Mode + наш CDM-probe = «клон сам добирает знания у уходящего за 2 недели» (H7). Нет ни у кого.
6. **Эволюция позиций во времени** («в марте считал X, в июне пересмотрел») — граф с датами это умеет, у конкурентов корпус плоский.

**Вывод:** ров Коры в категории = автосбор из встреч + клон должности + лестница с граундингом (цитаты до момента записи) + измеримое качество (scorecard из стенда) + запретная зона доверия. Слабейшее место LLM-клонов по науке — «воспоминание фактов» — это ровно профиль нашего графа.
