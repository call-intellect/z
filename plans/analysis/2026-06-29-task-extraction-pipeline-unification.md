# Унификация извлечения задач: роль нарезчика и единый тип пайплайна

## Вопрос владельца (2026-06-29)

Наблюдение: видео-встречи извлекают задачи из сырого транскрипта целиком, а переписка/другие каналы — «через нарезчик» (по блокам). «Зачем нарезчик во второй части? Должны прийти к единому типу: либо нарезчик и во встречах, либо убрать его во втором случае. Найди лучшее решение и докажи; предложи несколько на выбор, одно докажи.»

## Ключевая правка картины (факт, не предположение)

**Нарезчик (`block-ingest`) универсален — он работает и для встреч тоже.** После анализа встречи `analyze.worker` вызывает **оба** конвейера параллельно:
- `meetingIngest.ingestMeeting(meetingId)` → нарезчик → граф ([analyze.worker.ts:334](../../backend/src/modules/ai/workers/analyze.worker.ts#L334));
- `meetingExtractActions.extract(...)` → задачи из транскрипта ([analyze.worker.ts:399](../../backend/src/modules/ai/workers/analyze.worker.ts#L399)).

Значит «убрать нарезчик во втором случае» — **ложная развилка**: нарезчик кормит не задачи, а **весь граф знаний** (память, клон, решения, цели, регламенты, процессы, инсайты, идеи, навыки, эксперименты, связи людей). Убрать его для чата = убить память/клон/решения для чата.

**Реальная асимметрия — только в слое ЗАДАЧ:**
- **Встречи:** задачи извлекает `meeting-extract-actions` из **полного транскрипта** (видит участников с identity, roomChat, само-назначение по говорящему, orgContext, тайм-коды; может группировать).
- **Не-встречи:** задачи извлекает `specialist-3-15-tasks` **по одному блоку** (видит 1 блок + до 6 цитат, соседние блоки не видит, исполнитель обезличен, схема плоская без parent/children, гейт confidence 0.45). Блоки встреч он сознательно пропускает (`isMeetingDerived`, [specialist-3-15-tasks.service.ts:93](../../backend/src/modules/knowledge-core/services/specialist-3-15-tasks.service.ts#L93)).

## Что делает нарезчик и кто от него зависит

Нарезчик за один проход: режет источник на сегменты → скользящее окно (5 сегментов, **без overlap**) → LLM извлекает атомарные блоки (`name`/`criticalQuestion`/`trustedAnswer`/`signalType`/`tags`/`evidence`+тайм-коды/entities/commitment-поля) + типизированные сущности (процессы/решения/регламенты/метрики/инструменты). Блок без цитаты отбрасывается. Дальше дистилл → canonical → `RouterService` статически по `signalType` диспатчит блок в дешёвого специалиста.

Потребители `IdeaBlock` (блоки кормят **весь** граф): decisions, regulations, process-detector, insights, ideas, skill, knowledge-clone, project-customer, experiments, personal-relation, helpfulness, **goals** (`commitment`/`plan_item`), **tasks** (`action_item`), + типизированные сущности и память/поиск/темы. Это и есть смысл схемы: **один проход понимания → много дешёвых специалистов**; новый канал даёт сущности «бесплатно».

**Почему встречи оставлены на транскрипт-экстракторе (решение Б-1, [unified-task-extraction §3](../tz/2026-06-23-unified-task-extraction.md)):** у встречи ограниченный набор участников → identity-резолв исполнителя точнее, чем tenant-wide fuzzy по строке. `SpecialistsCombined` (1 проход на 9 сущностей) тоже **meeting-only** по решению Р-3: обобщение на все каналы отвергли как риск регресса качества/цены + ломает prompt-caching.

## Что per-block путь теряет (а от этого зависят обе цели владельца)

- **Нет контекста соседних пунктов → нет группировки родитель/подзадача.** Схема возвращает плоскую запись без parent/children ([task-extract.prompt.ts:100](../../backend/src/modules/knowledge-core/prompts/task-extract.prompt.ts#L100)). «Сделай A, потом B, потом C» из соседних блоков свернуть в одно поручение нельзя.
- **Нет identity участников / orgContext.** Резолв исполнителя — постфактум, кодом, fuzzy по строке.
- **Нет само-назначения по говорящему.** «Беру на себя» без имени → `assigneeHint=""`. Правила «я сделаю → исполнитель = говорящий» в per-block промпте нет.
- **Нет кросс-блок дедупа внутри одного разговора.** Один пункт, размазанный по N блокам, извлекается N раз или не проходит гейт ни в одном.

Обе цели владельца — «обещание = задача себе» и «одна задача + подзадачи» — это **межблоковый контекст**, который per-block теряет конструктивно, а полнотекстовый получает даром.

## Четыре варианта (состязательно проверены)

| Вариант | Цель (а) обещание→задача | Цель (б) подзадачи | Граф/память | Главный killer | Вердикт |
|---|---|---|---|---|---|
| **1. Унификация ВНИЗ** (встречи тоже из блоков) | Хорошо (симметрично) | **Регресс** для встреч | ок | снос зрелого `meeting-extract`, потеря identity-резолва на встречах; против Б-1 | регресс, не решение |
| **2. Унификация ВВЕРХ** (все каналы из разговора целиком) | **Отлично** | **Отлично** | не трогаем | для стриминг-чата нет «разговора как единицы» → нужна сессионизация | **рекомендуется** |
| **3. Усилить нарезчик** (отдаёт иерархию + метит commitment) | Отлично, почти даром | **Слабо**: окно 5 сегм. без overlap режет иерархию; не доезжает до встреч; конфликт с LINK-дедупом/canonical; раздувает горячий общий путь | риск invalid-JSON на всём графе | половинчато |
| **4. Оконный таск-агент** (задачи по всем `action_item` окна сразу) | Половина (нет identity говорящего) | Хорошо на завершённых окнах | не трогаем | гонка сборки окна в живом чате; переоткрывает отвергнутый Р-3 | частный инструмент |

## Доказанная рекомендация: Вариант 2 — Унификация ВВЕРХ

**Тезис:** задачи извлекаются из **разговора целиком** (движок встреч, обобщённый на все каналы), нарезчик продолжает кормить граф. Per-block `specialist-3-15` как sink задач выводится.

**Почему именно он (и почему не остальные):**

1. **Единственный, кто решает ОБЕ цели чисто и симметрично.** Обе цели — про межблоковый контекст. Полнотекстовый проход несёт `SELF_ASSIGNMENT_RULE` («я сделаю X» → исполнитель = автор реплики, [tasks-unified.ts:173](../../backend/src/modules/ai/services/prompts/tasks-unified.ts#L173)) — закрывает (а) по построению, в т.ч. открытый хвост [04_не-сделано:42](../../second-brain/04_не-сделано/README.md). И видит «A, потом B, потом C» как один фрагмент → отдаёт родитель + подзадачи, закрывая (б). Вариант 1 ломает (б) для встреч; вариант 3 ломает (б) об окно/canonical/дедуп; вариант 4 не закрывает (а) (обезличенность блока).

2. **Низкий blast-radius на граф.** Меняется **только sink задач**. `block-ingest` и все остальные специалисты (память/клон/решения/цели) не трогаются. Вариант 1 рискует identity-резолвом и сносит зрелый код; вариант 3 раздувает горячий общий путь нарезчика (риск invalid-JSON на 15+ потребителей).

3. **Инфраструктура в основном есть.** Промпт `tasks-unified` уже generic (принимает `dialog`/`participants`/`orgContext`/`roomChat`). Встречи — готовый эталон. `Issue.parentId` (иерархия подзадач) **уже в схеме и в `CreateIssueDto`** — подзадачи ложатся нативно. Chatbox-сессии **уже несут `transcript.turns` с авторами и сегментируются как диалог** (`tryAsMeeting`) — для них «разговор целиком» на входе уже существует.

4. **Цена нейтральна-к-дешевле.** Сегодня per-block для чата = N вызовов (по числу `action_item`-блоков). Один полнотекстовый/оконный проход на разговор — обычно **меньше** вызовов, и внутри-разговорный дедуп бесплатный.

**Единственная реальная цена — сессионизация стриминговых каналов** (telegram/free_note): нужно понятие «единица разговора» (debounce-окно + флаш). Это ограниченная, понятная задача — и здесь вариант 2 поглощает пользу варианта 4 (оконность как способ нарезать стрим на единицы извлечения задач).

## Как реализовать (фазы, для блюпринта)

1. **Обобщить `meeting-extract-actions` → `ConversationExtractActionsService`**: вход не `meetingId`, а «единица разговора» (сессия/тред/окно). Промпт `tasks-unified` уже generic.
2. **Расширить схему извлечения** полем `subtasks[]` (родитель + подзадачи) — синхронно в 4 местах (`.strict()`-схемы) → материализация через `Issue.parentId`.
3. **Подключить готовые единицы разговора первыми** (chatbox-сессии, документы, завершённые треды) — там «разговор целиком» уже есть.
4. **Сессионизация стрима** (telegram/conversational) — debounce-окно + флаш по таймауту; здесь же — само-назначение по автору реплики.
5. **Вывести per-block task-sink**: убрать `action_item`→`3-15-tasks` из роутера (или оставить как фолбэк), снять двойной источник.
6. Дедуп: внутри-разговорный — в одном проходе; кросс-разговорный — прежний `TaskDedupService`.

## Риски и инварианты

- `.strict()`-схемы ответа LLM — новое поле `subtasks` добавлять во все места синхронно, иначе валидный ответ отбракуется.
- Не сломать двойное покрытие встреч: переходим на единый движок, но meeting-путь = его частный случай, не второй источник.
- Сессионизация стрима — не задерживать извлечение на часы (продукт = быстрая реакция); баланс debounce.
- `Issue.parentId` запрещает 3-й уровень вложенности — иерархия только родитель→подзадачи.

## Открытые решения владельца

- **OD-1.** Представление подзадач: дочерние `Issue` (`parentId`, у каждой свой исполнитель/срок) против чеклист-пунктов (текст+галочка). Для «разные шаги — разные люди» и для дедупа предпочтительны дочерние `Issue`.
- **OD-2.** Граница «единицы разговора» для стрима (по таймауту тишины? по треду? по дню?).
- **OD-3.** Судьба `commitment`→GOALS: при унификации вверх self-directed commitment → задача себе; остаётся ли что-то для Целей (обещания-outcome «обещаю запустить к Q3»). Сверить с [commitment-task-unification](2026-06-29-commitment-task-unification.md).

## Итог

«Прийти к единому типу» — верная интуиция, но ось — **слой задач**, а не нарезчик (он остаётся универсальным понимающим слоем графа). Лучшее решение — **унификация вверх**: один движок извлечения задач из разговора для всех каналов, как у встреч. Он единственный решает обе цели владельца чисто и симметрично, почти не трогая граф, переиспользует готовый движок встреч и существующий `Issue.parentId`. Цена — сессионизация стриминговых каналов, и это ограниченный, понятный объём.
