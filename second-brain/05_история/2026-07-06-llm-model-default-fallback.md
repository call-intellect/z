# Модель по умолчанию у провайдера + фикс UX провайдерского дефолта + ссылка назад из супер-админки

## Что было поставлено

Продолжение сессии с llm-provider-default-fallback. Владелец вернулся с реальным репро: попытался удалить занятого `deepseek`, снова получил голую ошибку `Провайдер "deepseek" используется в активном маршруте taskType="tasks"`, и заявил, что просил защиту для МОДЕЛИ, а не только провайдера, плюс нигде не видит бейдж «по умолчанию». Отдельно — скриншот-баг: из супер-админки не было ссылки назад в обычный кабинет.

## Как решал

**Баг навигации** — тривиальный, без ТЗ: `AdminShell.tsx` — добавил `<Link href="/dashboard">` под шапкой сайдбара.

**Разбор жалобы на «провайдера».** Прочитал код: `softDeleteWithFallback` у провайдера кидает `provider_in_use_by_routes` ТОЛЬКО когда дефолт-провайдер вообще не назначен (Р3 архитектуры — намеренное поведение, не баг). Реальная проблема — UX: фронт при occupied+no-default просто пытался удалить и показывал голую ошибку бэка вместо объяснения «сначала назначь дефолт у другого провайдера». Пофиксил ([LlmProvidersClient.tsx](../../frontend/app/(admin)/admin/ai/catalog/LlmProvidersClient.tsx)) — понятный `toast.error` вместо попытки удаления вслепую.

**Разбор жалобы на «модель».** Проверил отдельный сервис `AdminLlmModelsService.softDelete` (вкладка «Модели» того же каталога) — оказалось, ЭТО реальный, независимый от провайдерской фичи пробел: удаление конкретной `LlmModel` не проверяло вообще ничего, ни блока, ни миграции. `LlmTaskRoute.model` — отдельная строка, независимая от того, жив ли ещё провайдер. Спросил владельца через `AskUserQuestion` (по правилу CLAUDE.md — на русском, с рекомендацией), что делать: он выбрал «оба — протестировать существующий провайдерский фикс + построить модельную защиту».

**Архитектура + ТЗ** — написал по аналогии с уже одобренной провайдерской (`plans/architecture/2026-07-06-llm-model-default-fallback.md`, `plans/tz/...`), переиспользуя все прежние решения владельца (Р1–Р5) как прецедент вместо нового раунда вопросов: дефолт модели = уже существующий `LlmProvider.defaultModelKey` (не заводили новое поле), нет дефолта → жёсткий отказ, удаление самого дефолта → одним диалогом reassign-and-delete. Ключевое упрощение относительно провайдерской версии: модель мигрирует только в рамках СВОЕГО провайдера (`providerName` не меняется), поэтому не нужна dedup-логика по tier (уникальный констрейнт `(taskType,tenantId,tier,providerName)` не включает `model` — конфликтов быть не может), дедуп нужен только для legacy JSON-цепочек.

**Реализация** — сделал сам (не через tz-orchestrator, задача была уже полностью понятна из TZ): `AdminLlmModelsService` (`setDefaultModel`/`previewRemoval`/`softDeleteWithFallback`/`migrateModelRoutesToDefault`), контроллер + DTO, 13 новых тестов в `admin-llm-models.service.spec.ts` (файла не было — написал с нуля по образцу провайдерской спеки), фронт (`LlmModelsClient.tsx` — бейдж, кнопка, `ReassignDefaultModelDialog`, тот же паттерн occupied+no-default → toast).

**Живая QA** — поднял backend+frontend локально (arm64-обход: `bun --env-file=../.env src/main.ts` без `--watch`, msgpackr-extract уже отключён с прошлой сессии), сбросил пароль существующему `qa-superadmin@local.test`, прошёл ОБА сценария через Playwright на реальной БД: провайдерский (191 занятый маршрут у deepseek → назначил дефолт → удалил с миграцией, `DELETE` вернул `routesMigrated:191`) и модельный (бейдж у `kie`/`grsai` подхватил уже существовавшие `defaultModelKey` — хорошая проверка на реальных, не тестовых данных; удаление дефолтной `gpt-4o` без reassign → диалог → выбор `gpt-4o-mini` → маршрут и дефолт переехали). Остановил dev-процессы после QA.

## Что вышло

Оба сценария работают на реальных данных без доработок по итогам QA. 253/253 backend-тестов (economics-модуль), typecheck/lint/build фронта и бэка чистые. Коммиты не делались в рамках этого ответа — ожидает `git add`/commit по явному запросу владельца (правило проекта: коммит только по явной просьбе).

## Чему научился

- **Провайдерский и модельный уровень — разные сущности с разным риском.** Пользователь на бытовом языке называл и то, и другое «моделью» — не стоило считать первую фичу закрывающей весь запрос без явной проверки: реальный код (`AdminLlmModelsService.softDelete`) показал отдельный, никем не защищённый путь удаления.
- **Уникальный констрейнт определяет, нужна ли dedup-логика.** У провайдерской миграции dedup был нужен (два тира могли схлопнуться в одного и того же провайдера); у модельной — нет, потому что `model` не входит в `(taskType,tenantId,tier,providerName)` — сначала свериться со схемой, а не копировать паттерн бездумно.
- **Живая QA на реальных, не тестовых данных ловит то, что моки не покажут** — бейдж «по умолчанию» у `kie`/`grsai` был выставлен ДО этой сессии (сид), и именно поэтому сразу подтвердил, что серверный расчёт `isDefault` в `list()` корректно работает не только на данных, созданных в рамках этой же сессии.
