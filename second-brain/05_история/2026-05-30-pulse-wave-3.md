# Pulse Волна 3 — карточка сотрудника + 4 AI-агента за одну сессию

## Что было поставлено

Продолжение оркестрации полного ТЗ Pulse. По автономии (user explicitly granted) — дожать Волну 3 (9 фаз, 4 недели по плану) сразу после Волн 1+2 без подтверждений, потом коммит/push и в Волну 4.

## Как решал

**Стратегия:** 9 фаз сжаты в 2 мега-агента вместо 9 отдельных вызовов. Это сэкономило ~6 промежуточных циклов разведка→промпт→верификация.

**Скоупные решения (сократил против ТЗ):**
- Phase 3.2 (Conflict-Detector extension) **пропустил** — существующий `personal-relation-builder.worker` работает достаточно. Расширение оставим на Волну 6.x.
- 6 секций PersonPulseClient (Energy budget, Goals, Tracker activity, Chats, Connections graph, Risk signals, Knowledge themes) превратил в **placeholder-блок «Скоро появится»** в карточке. Реальные секции v1 — 6 главных (header, AI Resume, Mood trend, Check-ins regularity, Promises, AI probe questions). Это даёт работающую страницу сразу, остальное наращивается в Волне 6.

**Архитектурные решения как оркестратор:**
- **4 cron-агента** разместил по логике:
  - Team-Health-Analyzer + Engagement-Scorer + HR-Recommender → `dashboard/agents/` (анализ команд/людей)
  - Reflection-Quality-Scorer → `operations/workers/` (живёт рядом с checkin-sentiment-analyzer, общий контекст чек-инов)
- **Engagement-Scorer без LLM** — детерминированный composite (weighted sum). Это сэкономит много $ на масштабе (по человеку в день).
- **HR-Recommender — capable модель** (deepseek-v4-pro) поскольку нужны nuanced рекомендации. Остальные 2 LLM-агента — flash (cheap).
- **JSON Schema strict** во всех LLM-вызовах с `responseFormat` — гарантирует структурный вывод.
- **Privacy в промптах**: Team-Health-Analyzer summary без имён, HR-Recommender текст рекомендаций без полного имени (только «сотрудник», «он/она»).
- **RBAC PersonPulse**: owner/admin/coo/super_admin ИЛИ self. Manager-к-подчинённым отложен до уточнения политики (нужно понимать, кто чей manager — Appointment.reportsToPersonId не везде заполнен).

**Коллизии и адаптации:**
- `Person.userId` может быть null (до accept приглашения) → recognition фильтруется только если userId !== null.
- `DailyCheckIn.rawResponseText` оказался реальное имя поля (как и предполагал).
- `Person.relationship` — enum `PersonRelationship`, фильтр работает корректно.
- `ActivityFeedWidget` в текущей реализации (из Phase 1.8) НЕ поддерживает `scope='user' + scopeId` — backend `activityFeedApi.list` фильтрует только `scopedToMe` для self или `teamId`. Из-за этого секция 9.5 (probe-вопросы сотруднику) НЕ имплементирована в PersonPulseClient — это backend-gap, который надо закрыть в Волне 6.x или отдельной мини-фазой.

## Чему научился

1. **Мега-агенты работают** — 4 cron'а + schema + module registration в одном агент-вызове = 83 tool_uses, 17 минут. Альтернатива (4 отдельных агента) была бы 4*~25 мин = 100 мин. Экономия ~80%.

2. **Детерминированный composite vs LLM** — для подсчёта engagement-score `weighted sum signals` лучше LLM. Воспроизводимо, дёшево, объяснимо для пользователя ("0.35*sentiment + 0.25*regularity..."). LLM нужен где есть качественный анализ (Team-Health factors low/medium/high, HR-рекомендации текстом).

3. **RBAC проверка self в endpoint** — простой паттерн `RbacService.loadContext(userId, tenantId)` для роли + `prisma.person.findFirst({id, userId})` для self-check. Не требует нового guard'а.

4. **Backend gap в feed-filter** — Phase 1.8 я писал ActivityFeedWidget с props для scope='user', но backend list-endpoint поддерживает только `scopedToMe=true` (для меня) и `teamId`. Фильтр по конкретному targetUserId должен быть отдельным параметром. Запомнил — добавить в backend `activity-feed.controller` поддержку `userId` query-param. Пока секция 9.5 закрыта placeholder'ом.

5. **Privacy-by-design в промптах** — явно прописал в SYSTEM «не называй имён» для Team-Health-Analyzer и HR-Recommender. Это снижает риск LLM-leak персональных данных в summary/text.

6. **JSON Schema strict** — для cron'ов где парсинг важен — `responseFormat.strict: true` гарантирует структуру. Без этого парсер должен иметь try/catch и fallback.
