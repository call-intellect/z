# ТЗ — Встреча: войти/вернуться/поделиться ссылкой во время встречи

## Принцип

Заявленная потребность владельца: во время идущей/созданной встречи **переслать кому-то приглашение** двумя способами — (1) **вручную скопировать ссылку** и отправить самому (Телеграм и т.п.), (2) **авто-приглашением** (выбрать сотрудника → почта/Телеграм, как при создании) — и, выйдя случайно, **вернуться** как организатор. Сейчас на платформе у идущей встречи — только «Открыть результат», ссылка живёт лишь в переходном диалоге после создания и в кнопке «Ссылка» в комнате (без фидбэка), а авто-приглашение доступно **только на экране создания**.

Бэкенд **уже умеет** rejoin (`POST /api/v1/meetings/:id/join` выдаёт свежий токен), ссылка `/m/{id}` **детерминирована** → шаринг-ссылка и возврат — фронтовые (Ф1–Ф4, без эндпоинтов/миграций). **Авто-приглашение после создания (Ф5)** добавляет ОДИН бэкенд-эндпоинт, **переиспользуя существующую логику** (пикер `ParticipantPicker` + `deliverMeetingInvites`).

Не оптимизируй по-своему: host-вход не требует секрета в URL (вход по cookie), новые share-токены НЕ вводить; **существующую авторассылку при создании встречи НЕ трогать и НЕ ломать** — только переиспользовать.

## Цель и Зачем

**Болезненное состояние:** организатор не может (а) переслать ссылку на идущую встречу, (б) вернуться в неё после выхода/закрытия вкладки. Встреча «висит» active, путь назад — только переоткрыть письмо/Телеграм или вообще никак.

**Метрика успеха (проверяемо):** для встречи в статусе `scheduled`/`active` — на карточке, в детали, в лобби есть «Войти в встречу», «Скопировать ссылку» (с тостом) и «Пригласить» (авто, почта/Телеграм); после выхода хоста из идущей встречи есть «Вернуться в встречу»; у хоста в комнате есть «Выйти» (уйти, не завершая) отдельно от «Завершить»; существующая авторассылка при создании работает как прежде; `bun run typecheck/lint/build` зелёные.

## Scope

### Входит
- Ф1 — «Войти в встречу» + «Скопировать ссылку» у `scheduled/active` встреч (карточка/деталь/список).
- Ф2 — «Вернуться в встречу» после выхода + хостовое «Выйти» (не завершая).
- Ф3 — надёжная «Ссылка» в комнате (тост успеха + fallback при заблокированном clipboard).
- Ф4 — «Скопировать ссылку» в лобби `/m/{id}` (хост, до входа).
- Ф5 — авто-приглашение ПОСЛЕ создания / во время встречи: `POST /api/v1/meetings/:id/invitees` (reuse `deliverMeetingInvites`) + кнопка «Пригласить» (reuse `ParticipantPicker`) в детали встречи И в тулбаре комнаты.

### Не входит (vNext)
- Отзываемые per-guest ссылки, ротация `inviteToken` — не в этом ТЗ.
- Изменение FSM встречи, токенов LiveKit, логики записи/AI — не трогаем.
- **Изменение/удаление существующей авторассылки при создании** (Р6) — строго не трогаем, только переиспользуем.

### Граничные контракты
- Бэкенд join/rejoin (`participants.*`) и FSM — **без изменений**; фронт дёргает существующий `meetingsApi.join(id, {})` для хоста.
- Ф5 переиспользует существующую логику invitees (тот же контракт `{userId, personId, email, sendVia}`) и `deliverMeetingInvites` — НЕ дублировать, вынести общий метод (см. Ф5).
- Статус встречи в списке/детали — берём из существующих данных журнала (`status` в DTO встречи); если в детали (`meetingsApi.result()`) статуса нет — взять из элемента списка (он там есть).

## Границы автономии
- ✅ Always: добавление кнопок/действий по образцу соседних; вызов существующего `meetingsApi.join`; copy-to-clipboard с тостом; навигация на `/m/{id}`; новый эндпоинт `POST /meetings/:id/invitees`, **переиспользующий** существующую логику invitees + `deliverMeetingInvites` (Ф5).
- ⚠️ Ask first: изменение FSM/токенов; правка логики «Завершить»; правка СУЩЕСТВУЮЩЕЙ авторассылки при создании (Р6 — не трогать).
- 🚫 Never: новые секрет-токены в URL; английские слова в UI; `process.env.*`; ослабление проверки доступа (войти может только тот, кому встреча доступна — это решает бэкенд `join`/`access`); удаление/переписывание create-time invite.

## Хелпер (единый источник «можно ли войти»)
Ввести/переиспользовать предикат joinable-статусов (по FSM): `isJoinableStatus(status) = status === 'scheduled' || status === 'active'`. Использовать во всех фазах (карточка/деталь/лобби) — единый критерий показа «Войти»/«Скопировать ссылку» vs «Открыть результат».

## Фаза 1 — «Войти» + «Скопировать ссылку» у идущей/запланированной встречи

**Цель:** дать с платформы войти в встречу и переслать ссылку, пока она `scheduled/active`.

**Мини-картография:**
- `frontend/src/ui/components/meetings-journal/MeetingsJournalReal.tsx:886-1050` — `MeetingDetailPane` (сейчас только «Открыть полную страницу результата» :969-973); :435-520 — `MeetingRowCard` (нет действий для active).
- `frontend/src/api/meetings.api.ts:66` — `{id,url}`; ссылка строится как `/m/${id}`.
- Образец copy+toast — `ControlsBar.tsx` `copyLink()` (:145-149) + паттерн `toast.success` в проекте.

**Требование видимости (Р4):** кнопки «Войти в встречу» и «Скопировать ссылку» у joinable-встречи должны быть **видны сразу** (первичные, на виду), а НЕ спрятаны в hover-меню/«Ещё»/дроп-даун. Владелец прямо сказал «сейчас я не вижу её».

**Что входит:**
1. В `MeetingDetailPane`: если `isJoinableStatus(meeting.status)` — показать **на виду** первичные действия **«Войти в встречу»** (link/`router.push('/m/'+id)`, `target` тот же) и **«Скопировать ссылку»** (копирует `${location.origin}/m/${id}`, тост «Ссылка скопирована»). «Открыть результат» оставить вторичной/как есть. Для НЕ-joinable (completed/ai_*/failed) — поведение как сейчас (только результат).
2. В `MeetingRowCard` (строка списка): для `isJoinableStatus` добавить **постоянно видимые** (не hover-only) кнопки/иконки «Войти» и «Скопировать ссылку» — не ломая выбор строки в master-detail.
3. Бейдж/индикатор «идёт» у active встречи (если ещё нет) — по образцу статусов, чтобы joinable-встреча визуально отличалась.
4. Кнопка **«Пригласить»** в детали (открывает `InviteDialog` из Ф5 — авто-приглашение по почте/Телеграм). Размещение — рядом с «Войти»/«Скопировать ссылку» (Р7). Реализация диалога/эндпоинта — Ф5; здесь только размещение в `MeetingDetailPane`.

**Что НЕ входит:** изменение бэкенда (эндпоинт — в Ф5); создание share-токенов; правка экрана результата; правка create-time invite.

**Acceptance:**
- Для встречи `status='active'`/`'scheduled'` в детали присутствуют «Войти в встречу» (href/навигация `/m/<id>`) и «Скопировать ссылку» (grep-маркер: `/m/${` + `toast.success`).
- Клик «Скопировать ссылку» кладёт в буфер `…/m/<id>` и показывает тост (ручная проверка/юнит на формирование строки).
- Для `status='ai_ready'` — действий «Войти/Скопировать» нет (только результат). Негатив-проверка по `isJoinableStatus`.
- `bun run typecheck && lint && build` зелёные.

**Закрывает:** пробел №1 (платформенный доступ).

## Фаза 2 — Возврат хоста (rejoin) + хостовое «Выйти»

**Цель:** хост, выйдя/закрыв вкладку у идущей встречи, может вернуться; «Выйти» (не завершая) отделено от «Завершить».

**Мини-картография:**
- `frontend/app/(public)/m/[id]/MeetingPageShell.tsx:54-70` (авто-join, role host + active/scheduled), `:56` `autoJoinAttempted`, `:170-177` пустой скелет после выхода.
- `frontend/src/ui/components/meeting-room/MeetingRoom.tsx:135-138` (`onLeave` → `setJoined(null)` + `access.mutate()`).
- `frontend/src/ui/components/meeting-room/ControlsBar.tsx:169-176` (хост «Завершить»), `:180-191` (гость «Выйти» = `room.disconnect()`+`onLeave()`).

**Что входит:**
1. **Хостовое «Выйти» (не завершая):** в `ControlsBar` для хоста добавить кнопку «Выйти» рядом с «Завершить» — `room.disconnect()` + `onLeave()` (как у гостя), БЕЗ завершения встречи. «Завершить» оставить как есть (красная, с подтверждением).
2. **Экран «Вы вышли» после `onLeave`:** в `MeetingPageShell`, если встреча всё ещё `isJoinableStatus`, показывать вместо пустого скелета блок: «Вы вышли из встречи» + кнопка **«Вернуться в встречу»** (повторно дёргает join) + «Скопировать ссылку». Снять блокировку повторного входа: при явном «Вернуться» сбрасывать `autoJoinAttempted`/вызывать `joinAsHostOrGuest()` напрямую.
3. Если встреча уже `completed/ai_*` — показывать существующий finished-плейсхолдер (не «Вернуться»).

**Что НЕ входит:** изменение бэкенд-join; авто-переподключение без действия пользователя (явная кнопка — чтобы не дёргать токен в фоне); правка «Завершить».

**Acceptance:**
- В комнате у хоста видны ДВЕ кнопки: «Выйти» (disconnect без завершения) и «Завершить» (конец, с подтверждением). После «Выйти» встреча в БД остаётся `active` (ручная проверка/diag).
- После выхода на `/m/<id>` для joinable-встречи виден блок с «Вернуться в встречу»; клик возвращает в комнату (новый `POST /api/v1/meetings/<id>/join → 200`, рендер комнаты). Grep-маркер: текст «Вернуться в встречу».
- Повторный вход работает многократно (нет блокировки `autoJoinAttempted` при явном «Вернуться»).
- `bun run typecheck && lint && build` зелёные.

**Закрывает:** пробел №2 (возврат организатора).

## Фаза 3 — Надёжная «Ссылка» в комнате (фидбэк + fallback)

**Цель:** клик «Ссылка» даёт явный результат, даже если `navigator.clipboard` заблокирован.

**Мини-картография:** `frontend/src/ui/components/meeting-room/ControlsBar.tsx:145-149` — `copyLink()` → `navigator.clipboard.writeText('/m/'+meetingId)` (живой прогон: `NotAllowedError`, тоста нет).

**Что входит:**
1. `copyLink()`: при успехе — `toast.success('Ссылка скопирована')`; при ошибке clipboard (`NotAllowedError`/нет API) — fallback: показать поповер/диалог с полем, где ссылка выделена для ручного копирования (или `document.execCommand('copy')` как запасной путь), + тост-инструкция. Никогда не падать молча.
2. Тултип/подпись кнопки уточнить: «Скопировать ссылку» (вместо просто «Ссылка»), чтобы было понятно, что это приглашение.
3. Кнопка **«Пригласить»** в тулбаре комнаты у хоста (открывает `InviteDialog` из Ф5 — авто-приглашение по почте/Телеграм). Размещение — рядом с «Скопировать ссылку» (Р7). Реализация диалога/эндпоинта — Ф5; здесь только размещение в `ControlsBar` (хост).

**Что НЕ входит:** изменение того, ЧТО копируется (остаётся `/m/{id}`); новые токены; реализация эндпоинта (Ф5).

**Acceptance:**
- Успех → тост «Ссылка скопирована» (grep `Ссылка скопирована`).
- Симуляция отказа clipboard → виден fallback с ссылкой для ручного копирования (не молча). Юнит/ручная проверка.
- Кнопка имеет понятную подпись/тултип про копирование ссылки.
- `bun run typecheck && lint && build` зелёные.

**Закрывает:** пробел №3 (немой copy в комнате).

- `bun run typecheck && lint && build` зелёные.

## Фаза 5 — Авто-приглашение ПОСЛЕ создания / во время встречи (reuse, не ломать существующее)

**Цель:** дать второй способ допригласить — авто-приглашение (выбрать сотрудника → почта/Телеграм) не только при создании, но и у уже созданной/идущей встречи. **Существующую авторассылку при создании НЕ трогаем** (Р6), переиспользуем её логику (Р5).

**Мини-картография (что переиспользуем, НЕ дублируем):**
- Фронт-пикер: `frontend/src/ui/components/create-meeting-form/CreateMeetingFormV2.tsx:160-174` (маппинг `invitees`) и `:322` (`<ParticipantPicker value onChange showChannels/>`). Пикер — переиспользуемый компонент.
- Контракт invitees: `{ userId, personId, email, sendVia: ['email'|'telegram'][] }` — `backend/src/modules/meetings/dto/create-meeting.dto.ts:35-46`.
- Бэк-логика приглашения: создание pre-seed `Participant{invitationStatus:'invited', inviteToken:nanoid()}` + `deliverMeetingInvites` (`backend/src/modules/meetings/meetings.service.ts` — invitees-блок и метод доставки, ссылка `…/m/<id>?inv=<token>`).

**Что входит:**
1. **Бэкенд — общий метод + эндпоинт.** Вынести из `createForUser` приём-invitees в переиспользуемый метод `addInvitees(tenantId, meetingId, invitees, actorUserId)` (pre-seed Participant + `deliverMeetingInvites`), **без изменения поведения при создании** (создание вызывает тот же метод). Новый эндпоинт `POST /api/v1/meetings/:id/invitees` (Zod-DTO = тот же массив invitees, что в create; Swagger; коды ошибок), `@RequireSubscription` (как создание), `TenantGuard`, доступ — только хост встречи (как host-controls). Идемпотентность: повтор того же `userId`/`email` для встречи = no-op (не плодить дублей Participant; по `@@unique`/upsert по (meetingId, livekitIdentity/inviteToken)). Разрешён при `isJoinableStatus` (scheduled/active).
2. **Фронт — `InviteDialog` (переиспользуемый).** Диалог с `ParticipantPicker (showChannels)` + кнопка «Отправить приглашение» → `meetingsApi.addInvitees(id, invitees)`; тост успеха/ошибки. Открывается кнопкой «Пригласить» из Ф1 (детали) и Ф3 (комната). Новый метод в `frontend/src/api/meetings.api.ts`: `addInvitees(id, invitees)` → `POST /api/v1/meetings/:id/invitees`.

**Что НЕ входит:** правка/удаление create-time invite (Р6 — только рефактор-вынос общего метода без смены поведения создания); отзываемые/ротация токенов; приглашение гостем (только хост).

**Контракт (переиспользуем существующий invitees):**
```ts
// frontend/src/api/meetings.api.ts (новое):
addInvitees: (id: string, invitees: InviteeInput[]) =>
  apiClient.post(`/api/v1/meetings/${encodeURIComponent(id)}/invitees`, { invitees })
// InviteeInput — тот же, что при создании: { userId?: string|null; personId?: string|null; email?: string|null; sendVia: ('email'|'telegram')[] }
```

**Acceptance:**
- `POST /api/v1/meetings/<id>/invitees` с `{invitees:[{userId, sendVia:['telegram']}]}` для active-встречи → 200/201; у приглашённого появляется `Participant{invitationStatus:'invited'}` + уходит сообщение со ссылкой `…/m/<id>?inv=<token>` (проверка diag/логи `deliverMeetingInvites`).
- Повтор того же приглашённого = no-op (дубль Participant не создаётся) — идемпотентность как acceptance.
- Создание встречи с invitees по-прежнему работает (регресс-проверка: существующий `meetings.service.createForUser.spec.ts` зелёный — поведение при создании не изменилось).
- Кнопка «Пригласить» открывает `InviteDialog` в детали (Ф1) и в комнате (Ф3); отправка показывает тост.
- Swagger: эндпоинт виден под тегом meetings; `@RequireSubscription` присутствует.
- `bun run typecheck && lint && build` (frontend + backend) + `bunx vitest run …meetings.service*.spec.ts` зелёные.
