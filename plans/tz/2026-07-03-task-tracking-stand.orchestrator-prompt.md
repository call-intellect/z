## 🧭 Фазы (детали — в ТЗ)

- **Ф0 prepare:** создать мир из **`task-stand-fixtures.json`** — синтетический тенант (свежая «Стрела» через
  `seed-synthetic-company` ИЛИ существующая org `cmr1qbvpx0001pwbwxbgmh1jl`) + второй тенант ORG_B; проекты со
  статусами (обязательно `category='completed'`; проект `nocomplete` намеренно без него — под J-12); исполнители-
  Person с userId (имена из фикстур); пины крутилок на дефолты из `fixtures.json.configPins`.
- **Ф1 seed:** создать 19 baseline setup-задач из **`fixtures.json.setupTasks`** через `IssuesService.create
  (skipDedup:true)`; **дождаться эмбеддингов** (`issue-embed.worker`, `embedding IS NOT NULL` — иначе KNN не
  сматчит, будут ложные no_match); ORG_B-двойник; сгенерить `task-stand-manifest.json` (сшивка setupTasks-ID +
  ожидаемых исходов из банка).
- **Ф2 inject:** загрузить **`task-stand-scenarios.json`** (100 входов), подать каждый по его `channel` через
  **реальный конвейер** (RawEvent/адаптеры, как `clone-build-harness`), дождаться `RawEvent.received=0`.
  **Обязательно (замер Т1):** для 3–4 creation-входов отдельно и раздельно вызвать три извлекателя
  (`SpecialistsCombinedService.persistTasks` — предположительно живой; `Specialist315TasksService.processBlock` и
  `TaskExtractionService.extractTasks` — предположительно легаси) и зафиксировать, какой реально рождает задачу.
  Для journal/closure при нестабильном классификаторе — дублировать прямой инъекцией IdeaBlock с нужным
  signalType (done_item/task_completed/task_status_changed).
- **Ф3 assert (без LLM):** сверить сырой результат с `expect` каждого сценария: тип исхода (issue/intake/candidate/
  progress/relation/probe/subtask/nothing/error — точный матч кодов) + счётчик (ловит проафферацию) + поля (enum/
  category/error — точно; title/assignee — нечётко) + **детерминированные инварианты** INV-1 (нет закрытий/merge
  без confirm), INV-2 (нет кросс-тенант), INV-4 (повтор не растит счётчики).
- **Ф4 judge + report:** панель majority-of-3, судья видит `expect`/`input.text` из банка. Отчёт: scorecard по
  категориям A–J и по механизмам; оси C/D/G/J/X/P; **статус INV-1..4**; **таблица Т1–Т10** (подтверждён/снят/
  ruler-defect с доказательством); конфиг прогона (какой извлекатель жив).
- **Ф5 baseline:** чистка кэшей (`bull:*`/answer-кэш/`probe:dedup`/SETNX) → run → judge → report на 100 + свежие
  15. Каждый провал — ручной разбор против сырой трассы (линейка сама может врать → диагноз `ruler-defect`
  чинить первым).

## 🚫 Жёсткие правила

- **Прод не трогать.** `assertNotProd` первым вызовом каждого скрипта. Только локальная синтетика. Единственная
  допустимая правка прод-кода — **аддитивная трасса** (добавить поля в возврат/лог, поведение-нейтрально); лучше
  снимай трассу read-only из БД. Снапшот-тесты промптов не ломать.
- **Живой backend обязателен** (`cd backend && bun run dev`) — конвейер крутится in-process; без него стенд не
  измеряет. dev-инфра: `docker compose -f docker-compose.dev.yml up -d`. `STRELA_ORG` + `TASK_STAND_ORG_B` в `.env`.
- **Синтетику не переделывать и не подгонять под ответы.** Банк/фикстуры/эталоны фиксированы. Инвариант **R13**
  осевой: если стенд «ожидает» авто-закрытие/авто-merge — это ошибка эталона, а не бага. Правки эталонов — только
  ручным разбором с фиксацией причины.
- `createPrismaClient()` из `_lib/prisma.ts` (не голый `new PrismaClient()`); ORG из ENV; per-run архив, не
  перезапись; чистить кэши/дедупы перед каждым прогоном.
- Ты реализуешь ТЗ, не переспрашивая по мелочам; необратимые «решения владельца» (менять планку/поведение) —
  эскалируй.

## ✅ Что вернуть владельцу (Definition of Done)

1. Рабочий раннер: `bun run scripts/task-stand/stand.ts all` (и по-фазно) гоняет 100 сценариев.
2. **Baseline-отчёт** `docs/testing/task-stand-report.md`: распределение вердиктов по 4 механизмам; **статус
   инвариантов INV-1..4**; **вердикт по Т1–Т10** — что подтвердилось как баг (с доказательством из трассы), что
   снято; какой извлекатель жив (Т1); честный разбор потолка.
3. Список **приоритетных слабых мест** (подтверждённые Т* + новые находки) → вход для **отдельного ТЗ-фикса** (не
   делать фиксы в этом задании).
4. `typecheck/lint/build` зелёные; заполнить секцию результатов в `task-stand.md`; строка в реестре стендов; прод
   не тронут.

**Ожидаемо по прогнозу** (сверь с фактом; резкое расхождение → сначала `ruler-defect`): Т1 покажет, что часть
входов чата/встречи не рождает задачу (осиротевший извлекатель) или рождает через SpecialistsCombined; Т2 —
обещание себе (A-04/A-05, FR-02) уходит в Goal; Т3 — многоблочное дело (B-02/B-06/B-07) даёт неверное число
задач; INV-1 (R13) соблюдён — если нарушится, это находка №1.

Начни с чтения готовых документов и `index_status`/окружения, затем Ф0 (из `task-stand-fixtures.json`).
