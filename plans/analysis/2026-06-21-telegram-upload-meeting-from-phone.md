# Анализ: загрузка встречи (аудио/видео) с телефона через Telegram

> **Тип:** research-complete. Это анализ, не ТЗ. Цель — оценить, что нужно, чтобы
> присланный в Telegram-бот файл (видео/аудио) превращался в полноценную
> «видеовстречу» Коры со штатным AI-отчётом. Тип встречи и разметку спикеров
> владелец дозаполняет позже с компьютера (как и сформулировано в запросе).

## 1. Запрос владельца

Клиент спрашивает, можно ли загружать запись встречи **с телефона** — например,
прислать аудио/видео в Telegram-бота, чтобы оно дальше «определялось как
видеовстреча» в системе. Привязку (тип встречи, пароль, спикеры) можно дозаполнить
потом с компьютера. Нужен анализ осуществимости и предложение.

## 2. Главный вывод

**Бóльшая часть уже построена.** Задача — не новая фича с нуля, а **тонкий мостик**
между двумя уже работающими подсистемами:

1. **Конвейер «файл → видеовстреча»** ([meeting-uploads](../../backend/src/modules/meeting-uploads/)) — реализован полностью.
2. **Telegram-бот** ([telegram-bot](../../backend/src/modules/conversational/adapters/telegram-bot/)) — уже принимает медиа, знает, кто пишет, и умеет скачивать файлы.

Не хватает: маршрутизации присланного медиа в первый конвейер + серверной загрузки
в S3 + приёма видео. **И один реальный блокер — лимит Telegram 20 МБ на скачивание
ботом** (§5), который наш прокси НЕ снимает.

## 3. Что уже есть в коде (две готовые половины)

### 3.1. Конвейер загрузки файла → встреча — РЕАЛИЗОВАН

Модуль [meeting-uploads](../../backend/src/modules/meeting-uploads/) даёт сквозной поток:

| Шаг | Что происходит | Где |
|---|---|---|
| `POST /api/v1/meetings/upload` | Создаёт `Meeting(source='upload', status='scheduled')` + presigned-PUT в S3 | [meeting-uploads.service.ts:70](../../backend/src/modules/meeting-uploads/meeting-uploads.service.ts#L70) |
| Загрузка в S3 | Клиент кладёт файл по ключу `meetings/{id}/upload/source.{ext}` | presigned PUT |
| `POST /:id/upload/complete` | Ставит job `meeting.upload-ingest` | [:134](../../backend/src/modules/meeting-uploads/meeting-uploads.service.ts#L134) |
| воркер `meeting.upload-ingest` | ffprobe → извлечение аудио (Opus/OGG 16k mono, fallback WAV); если видео — ремукс mp4 faststart → `Recording.mainVideoUrl`; статус → `recording_ready` | [meeting-upload-ingest.worker.ts](../../backend/src/modules/meeting-uploads/workers/meeting-upload-ingest.worker.ts) |
| воркер `meeting.upload-transcribe` | Vox с диаризацией → `MeetingUploadSpeaker[]` + `Transcript`; статус → `awaiting_speakers` | [meeting-upload-transcribe.worker.ts](../../backend/src/modules/meeting-uploads/workers/meeting-upload-transcribe.worker.ts) |
| `GET/PUT /:id/speakers` | Разметка спикеров (сотрудник/внешний/исключить/слить) — экран в вебе | [:201](../../backend/src/modules/meeting-uploads/meeting-uploads.service.ts#L201) |
| `POST /:id/speakers/confirm` | Создаёт `Participant[]`, переразмечает транскрипт → `ai_processing` → штатный AI-отчёт по типу встречи | [:288](../../backend/src/modules/meeting-uploads/meeting-uploads.service.ts#L288) |

**Важно:** загруженная встреча проходит ровно тот же финальный AI-анализ
(`ai.analyze`, `ai.behavior-metrics`, `meeting-report-fast`), что и живая встреча
с LiveKit. То есть «определяется как видеовстреча» — это уже факт для веб-загрузок.

**Ограничения конвейера:** до 2 ГБ, 12 видео- + 10 аудио-форматов, квота ~20
загрузок/мес (`billing.meetingUploadsPerMonth`). Тип встречи и `customPrompt`
задаются при создании; их можно оставить дефолтными и поправить позже.

### 3.2. Telegram-бот — УЖЕ принимает медиа и знает автора

[telegram-bot.adapter.ts](../../backend/src/modules/conversational/adapters/telegram-bot/telegram-bot.adapter.ts) + [telegram-api-client.ts](../../backend/src/modules/conversational/adapters/telegram-bot/telegram-api-client.ts):

- **Webhook** без сторонних SDK (нативный NestJS), дедуп `update_id` в Redis.
- **Привязка к нашему `User`+`Org`** — через подтверждённый `ChannelBinding`
  (одноразовый код из кабинета, раздел «Каналы»). То есть «кому принадлежит
  присланный файл» **уже решено** — `requireVerifiedBinding()` даёт `userId`+`tenantId`.
- **Скачивание файлов уже реализовано** — `getFile()` → `downloadFile()` (в `Buffer`),
  [:93-143](../../backend/src/modules/conversational/adapters/telegram-bot/telegram-api-client.ts#L93).
- **Уже обрабатывает** `voice`/`audio` (→ ASR → классификатор интента) и `document`
  (→ `DocumentsService.upload` в базу знаний).
- Лимит документа в коде сейчас — `MAX_DOCUMENT_BYTES = 20 МБ`.

## 4. Чего не хватает (это и есть объём работы)

1. **Маршрутизация в нужный конвейер.** Сейчас присланное аудио/`voice` уходит в
   ассистента/чек-ин/заметку, а `document` (включая mp3/m4a) — в базу знаний. **Ни
   то ни другое не создаёт встречу.** Нужен новый ветвитель: «это запись встречи»
   → в `meeting-uploads`.
2. **Серверная загрузка в S3.** `createUpload()` отдаёт presigned-PUT для браузера.
   Бот же держит файл как `Buffer` → нужен серверный метод (условно
   `ingestUploadFromBuffer({tenantId, ownerId, buffer, fileName, type})`): кладёт
   Buffer в `meetings/{id}/upload/source.*` через `S3Service` напрямую и ставит
   `meeting.upload-ingest`. **Это малая надстройка над готовым сервисом** — весь
   остальной конвейер переиспользуется без изменений.
3. **Приём видео.** Бот сейчас игнорирует `video`/`video_note` — их надо добавить
   в разбор update + конфиг-флаг (по аналогии с `BOT_VOICE_ENABLED`).
4. **Дозаполнение с компьютера.** Бот создаёт встречу с дефолтным типом и отвечает
   ссылкой в кабинет, где владелец правит тип и размечает спикеров (готовый экран
   `awaiting_speakers`). Здесь править почти ничего не нужно — экран уже есть.

## 5. 🔴 Блокер: лимит Telegram 20 МБ на скачивание ботом

**Факт из официального Bot API:** бот может скачать через `getFile` файл размером
**только до 20 МБ**, даже если пользователь отправил больше (клиент Telegram даёт
отправлять до 2 ГБ, но бот его не получит — `getFile` вернёт «file is too big»).

**Наш прокси НЕ помогает.** `telegram.crossmark.ru` — это транспортный
**ретранслятор** к `api.telegram.org` (open-relay для зарегистрированных ботов),
а не self-hosted Local Bot API Server. Подтверждено: ТЗ
[2026-05-26-telegram-via-crossmark-proxy.md](../tz/2026-05-26-telegram-via-crossmark-proxy.md) §1
(«прокси ретранслирует в `api.telegram.org`») и рефлексия
[2026-06-04-telegram-proxy-static-token.md](../../second-brain/05_история/2026-06-04-telegram-proxy-static-token.md)
(«проксирует Bot API только для зарегистрированных ботов»). Файл `/file/bot<token>/...`
проходит через тот же `api.telegram.org` → **лимит 20 МБ сохраняется**.

**Что значит 20 МБ на практике:** ≈15–20 минут аудио (mp3 128k ≈ 1 МБ/мин) или
1–2 минуты видео. Для реальной встречи на 30–60 минут — недостаточно. То есть
**без отдельного решения «видео встречи с телефона» работать не будет**, только
короткие фрагменты.

### Варианты обхода лимита

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Local Bot API Server** (рекомендую) | Поднять self-hosted `telegram-bot-api` как сервис в `infra/`; лимит скачивания → 2 ГБ | Снимает блокер полностью; видео/аудио на час+; по стеку допустимо (инфра, не продакшен-Python) | +1 инфра-сервис; нужны `api_id`/`api_hash`; webhook и `getFile` идут через него — надо совместить/заменить crossmark-прокси (региональная доступность из ДЦ Новосибирска — проверить) |
| **B. MVP «только ≤20 МБ»** | Ничего не поднимать; принимать только то, что отдаёт штатный API; при превышении — честное сообщение «запись большая, загрузите с компьютера» | Быстро, ноль инфры | Для реальных встреч почти бесполезно — только голосовые заметки/очень короткие |
| **C. Догрузка по ссылке** | Бот на большой файл отвечает кнопкой «Догрузить с телефона» → одноразовая presigned-ссылка/мини веб-форма (мобильный браузер грузит прямо в S3 по существующему presigned-PUT, который уже есть) | Обходит лимит бота вообще; переиспользует presigned-PUT 1:1; работает с телефона | Не «чистый Telegram» (пользователь выходит в браузер); нужна мини-страница загрузки |

**Рекомендация:** для настоящего продукта — **A (Local Bot API Server)**. Но как
быстрый первый шаг сильнее всего **C** — она даёт «загрузку с телефона» без нового
инфра-сервиса и без лимита, переиспользуя уже готовый presigned-PUT; Telegram
остаётся точкой входа («пришли запись» → ссылка). A и C не взаимоисключающи:
C закрывает потребность за дни, A добавляет полностью нативный путь позже.

## 6. Предлагаемый UX-поток (по решению владельца — различение по типу+размеру)

```
Пользователь в боте присылает видео/аудио-файл
   │
   ├─ короткое voice (< N сек, как сейчас) ──────► ассистент / чек-ин / заметка (без изменений)
   │
   └─ video / video_note / audio / audio-как-document / крупный файл
         │
         ├─ файл ≤ 20 МБ ──► бот скачивает Buffer ──► ingestUploadFromBuffer()
         │                       └─► создаётся Meeting(source=upload, дефолтный тип)
         │                       └─► «Принял запись, обрабатываю» + ссылка в кабинет
         │
         └─ файл > 20 МБ ──► [Вариант A] скачать через Local Bot API Server (до 2 ГБ)
                              [Вариант C] ответить кнопкой «Догрузить с телефона»
                                          → presigned-PUT ссылка → загрузка из браузера
   │
   ▼
Кабинет (с компьютера): владелец правит тип встречи + размечает спикеров
   (готовый экран awaiting_speakers) ──► штатный AI-отчёт
```

**Различение «встреча vs голосовое ассистенту»** (решение владельца — по типу+размеру):
`video`/`video_note`/`audio`/audio-как-`document`/файл крупнее порога → встреча;
короткое `voice` до N секунд → ассистент как сейчас. Порог N — крутилка в AdminSetting.

## 7. Архитектурное предложение (минимальный, переиспользующий код)

1. **`MeetingUploadsService.ingestUploadFromBuffer(...)`** — новый серверный вход:
   валидация формата/размера/квоты (вынести из `createUpload`), `S3Service.putObject`
   Buffer'а в `uploadSourceKey`, `meeting.create(source='upload')`,
   `enqueueUploadIngest`. Весь конвейер ниже — без изменений.
2. **Ветка `handleMeetingMedia()` в telegram-bot.adapter** — рядом с `handleVoice`/
   `handleDocument`: `getFile`→`downloadFile`→`ingestUploadFromBuffer`; ответ
   пользователю текстом + ссылка в кабинет. Различать аудио/видео-файлы (→встреча)
   от PDF/DOCX (→`DocumentsService`, как сейчас) по mime/расширению.
3. **Конфиг-флаги** (kill-switch, по Ship-On): `BOT_MEETING_UPLOAD_ENABLED`,
   порог `BOT_MEETING_VOICE_MAX_SECONDS` — в AdminSetting.
4. **(Вариант A)** отдельное ТЗ на Local Bot API Server в `infra/` — поднимает
   потолок до 2 ГБ.
5. **(Вариант C)** мини-страница загрузки `(public)` + повторное использование
   presigned-PUT + `complete`.

Дублирования бизнес-логики нет: ~80% берётся из готового `meeting-uploads`, бот
лишь поставляет файл и автора.

## 8. Развилки и решения владельца

- **Р-1 (лимит 20 МБ) — главное.** A (Local Bot API Server, полноценно) /
  B (только ≤20 МБ) / C (догрузка по ссылке из браузера). Рекомендация: **C как
  первый шаг + A как цель.** *(Развилка №1 «проверить прокси» закрыта фактом:
  прокси лимит не снимает.)*
- **Р-2 (различение медиа).** Принято владельцем: **по типу+размеру файла**.
- **Р-3 (документ-анализ).** Принято: оформить в `plans/analysis/` (этот файл).
- **Р-4 (тип встречи по умолчанию).** Какой `MeetingType` ставить при загрузке из
  бота, пока владелец не уточнил с компьютера? Рекомендация: `team` (нейтральный)
  либо последний использованный пользователем; правится в кабинете.
- **Р-5 (квота).** Считать ли Telegram-загрузки в ту же месячную квоту
  `billing.meetingUploadsPerMonth`? Рекомендация: **да** — единый учёт.

## 9. Оценка объёма (грубо)

- Мостик «Telegram → meeting-uploads» (п.7.1–7.3) + приём видео: **~2–3 дня** на ТЗ+реализацию.
- Вариант C (мини-страница + presigned reuse): **~1–2 дня**.
- Вариант A (Local Bot API Server в infra/, совмещение с crossmark-прокси, прод-выкат):
  **отдельное ТЗ, ~3–5 дней** + эксплуатация.

## 10. Открытые вопросы

1. **Достижимость Local Bot API Server из ДЦ Новосибирска** — та же причина, по
   которой подняли crossmark-прокси. Если прямой канал к Telegram из ДЦ
   недоступен, Local Bot API Server тоже нужно разворачивать там, где Telegram
   достижим (как и прокси). Влияет на жизнеспособность варианта A.
2. **`getFile` через crossmark-прокси для файла >20 МБ** — вернёт ошибку Telegram
   («file is too big») или прокси-ошибку? Проверить экспериментом (влияет на текст
   сообщения пользователю в варианте B/C).
3. **Видео без речи/битые контейнеры с телефона** — конвейер уже даёт
   `UPLOAD_NO_AUDIO_STREAM`/`UPLOAD_DECODE_FAILED`; нужен дружелюбный текст бота.
4. **MAX-канал** — у Коры есть и MAX-адаптер; стоит ли сразу закладывать тот же
   мостик и для MAX (отдельный вопрос).

## 11. Итог

Технически «загрузка встречи с телефона через Telegram» **реализуема малыми силами**
поверх готового `meeting-uploads` — нужен мостик-адаптер (~2–3 дня). Единственный
настоящий блокёр — **лимит 20 МБ на скачивание ботом**, который наш прокси не
снимает; он решается либо Local Bot API Server (полноценно, отдельное ТЗ), либо
догрузкой по presigned-ссылке из мобильного браузера (быстро, без новой инфры).
Привязка автора и AI-отчёт уже работают — дозаполнение типа и спикеров с компьютера
ложится на существующий экран `awaiting_speakers`.
