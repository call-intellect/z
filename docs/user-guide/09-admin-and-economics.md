# Администратору: модели и экономика

Этот раздел — для владельца и администратора компании. Если вы рядовой сотрудник или менеджер, можно пропустить.

Здесь — как Кора управляется «за кадром»: какие LLM-модели используются, сколько они стоят, как поменять модель без программистов, как видеть себестоимость каждого клиента и как поставить лимит расхода.

> Часть страниц из этого раздела доступна только владельцу. Администратор видит чтение и часть управления, но не может менять тариф или удалять данные.

## Что Кора делает за вас

- Сама агрегирует расход по моделям и сотрудникам каждый день.
- Сама считает себестоимость на компанию-клиента в месяц.
- Сама шлёт алерт владельцу, если расход подскочил.
- Сама рекомендует более дешёвую модель, если на ваших задачах качество примерно одинаковое.

## Что вы делаете сами

- Заходите в админку раз в неделю и проверяете расход.
- Меняете цены, когда провайдер их обновил.
- Включаете/выключаете модели по своим политикам.
- Настраиваете лимиты и алерты.

## Как устроены LLM в Коре

Кора не привязана к одной модели. Внутри есть **роутер**, который под каждый тип задачи выбирает подходящую модель из цепочки:

- **Primary** — первая попытка (обычно быстрая и дешёвая).
- **Secondary** — резервная (если primary не справилась).
- **Tertiary** — последняя надёжда (обычно локальная модель Ollama, которая всегда доступна).

Например, для разбора встречи на блоки сейчас используется:

1. DeepSeek-V4-flash (primary, дёшево и быстро).
2. OpenAI gpt-4o-mini (secondary).
3. Локальная Ollama qwen3.5:9b (tertiary, на нашем сервере).

Если primary недоступна или вернула ошибку — Кора автоматически переходит к secondary. Это решает проблему «провайдер лёг — система встала».

## Раздел «Модели и провайдеры»

Доступ: `/admin/llm/providers`, `/admin/llm/models`.

### Провайдеры (`/admin/llm/providers`)

Список доступных провайдеров. Каждая запись:

- Имя: DeepSeek, OpenAI, GigaChat, Ollama, Anthropic (если есть ключ), Custom.
- Endpoint — куда стучимся.
- Тип авторизации (api-key, oauth, прочее).
- Имя переменной окружения с ключом (сам ключ хранится в защищённом виде).
- Активен / выключен.
- Какие классы данных поддерживает (public / internal / sensitive / private).
- Заметки.

Кнопка «Тест подключения» — отправляет тестовый запрос и показывает, работает ли провайдер.

### Модели (`/admin/llm/models`)

Список всех моделей. Каждая запись:

- Провайдер.
- Имя модели (например `deepseek-chat-v4-flash`).
- Размер контекста (сколько токенов помещается в один запрос).
- Максимум выходных токенов.
- Что поддерживает: tools, JSON mode, кэширование, vision.
- Активна / выключена / устарела.
- Заметки в markdown — описание модели и для каких задач лучше.

Кнопки:

- **Тест connectivity** — отправить запрос с тестовым промптом.
- **Запустить smoke-test** — прогнать модель по нашему стандартному набору задач (как в playbook) и получить результат с качеством и стоимостью.

## Раздел «Цены»

Доступ: `/admin/llm-prices`.

Тут вручную проставляются цены за токены. Когда провайдер изменил цены — вы добавляете новую запись (не перезаписываете старую — это сохраняет историю).

Поля:

- Модель.
- Валюта (RUB или USD).
- Цена за **input** (вход) за 1M токенов.
- Цена за **output** (выход) за 1M токенов.
- Цена за **cached input** за 1M (если модель поддерживает кэширование — у DeepSeek и Anthropic это дешевле).
- Цена за embedding за 1M.
- Действует с какой даты по какую.
- Источник (URL прайса провайдера).

Как добавить новую цену:

1. Откройте `/admin/llm-prices`.
2. Нажмите «Добавить цену».
3. Выберите модель.
4. Введите числа.
5. Укажите дату «действует с».
6. Сохраните.

Старая цена не стирается — у неё проставится «действует до» = «новая дата минус 1 секунда». Все исторические записи доступны для audit и для понимания «сколько стоила эта обработка тогда».

## Раздел «Маршруты задач»

Доступ: `/admin/llm-routes`.

Тут вы говорите Коре: «для задачи X используй primary такую-то модель, secondary такую-то, tertiary такую-то».

Типы задач (taskType):

- `block-ingest-v2` — извлечение блоков из текста.
- `axis-classify` — классификация по 4 осям знания.
- `chat-v2-answer` — ответ помощника компании.
- `concierge-orchestrate` — оркестрация сложных запросов.
- `report-generate` — генерация отчёта.
- `embedding` — векторное представление текста.
- и т.д.

Для каждой задачи — таблица «primary / secondary / tertiary» с моделью, dataClass-ограничением и приоритетом.

Можно перетаскивать модели в цепочке (drag-and-drop).

Кнопка «A/B-тест» — запускает эксперимент: половина запросов на этом taskType идёт на вариант A (например, DeepSeek), половина на вариант B (например, OpenAI). По итогам — отчёт «cost vs latency vs success rate vs квазиметрика качества».

## Раздел «Использование» (usage dashboard)

Доступ: `/admin/llm/usage`.

Тут вы видите расход в реальном времени.

Фильтры:

- Период (день / неделя / месяц / период).
- Компания-клиент (для super_admin — все, для админа компании — своя).
- Тип задачи.
- Модель.
- Tier (primary / secondary / tertiary).

Метрики:

- Количество вызовов.
- Токены (input / output / cached).
- Стоимость в RUB и USD.

Графики:

- Стоимость по времени.
- Топ-10 самых дорогих запросов (с указанием задачи и клиента).
- Доля fallback (сколько запросов ушли в secondary/tertiary).

Если доля fallback > 5% — есть проблема (primary часто падает), стоит проверить.

## Раздел «Эксперименты»

Доступ: `/admin/llm/experiments`.

Тут вы запускаете и смотрите A/B-тесты. Например:

- На разборе встреч: DeepSeek-V4-flash vs OpenAI gpt-4o-mini.
- На ответах помощника: DeepSeek-V4 vs Claude (если есть доступ).

Для каждого эксперимента — live-результаты:

- Стоимость на запрос.
- Latency (время ответа).
- Success rate.
- Quality proxy (через эвристику или ручное ревью).

По итогам решаете, переключать ли primary.

## Раздел «Экономика»

Доступ: `/admin/economics` (для команды Коры) или `/admin/org/economics` (для админа компании).

Самая интересная страница для владельца. Тут видно, **сколько вы зарабатываете на каждом клиенте**.

### Что показано

Для каждой компании-клиента в системе:

| Метрика | Что значит |
|---|---|
| **Total cost** (за месяц) | Сколько мы потратили на этого клиента: LLM + storage + инфра. |
| **By taskType** | Разбивка по типам задач (на что ушли деньги). |
| **By specialist** | Сколько съели агенты регламентов, решений, инсайтов и т.д. |
| **Tariff revenue** | Сколько он платит нам по тарифу. |
| **Margin** | Маржа в рублях. |
| **Margin %** | Маржа в процентах. |

Снизу таблица «Топ-10 клиентов по марже» — видно, кто прибыльный, а кто убыточный.

Снизу — **прогноз** до конца месяца на основе linear extrapolation (продолжения текущего тренда).

### Алерты

В разделе «Правила алертов» можно задать:

- «Если клиент X тратит > $50 в этом месяце — пришли мне нотификацию».
- «Если общий расход вырос на 30% за неделю — алерт».
- «Если cache_hit_ratio упал ниже 40% — алерт».

Алерты приходят владельцу через канал, который он задал (in-app / email / Telegram).

## Лимиты расхода

Доступ: `/admin/org/limits` (для каждой компании).

Тут можно поставить **дневной/месячный лимит**:

- На общий расход компании ($/RUB в месяц).
- На отдельных пользователей (например, рядовому сотруднику — 5 сложных research-запросов в день).
- На отдельные taskType (например, не больше N оркестраций в день).

Если лимит достигнут:

- Кора **продолжает базовые функции** (запись встреч, разбор блоков — это критично).
- Лишние запросы (консьерж в режиме «исследуй», большие отчёты) **блокируются** с понятным сообщением: «лимит исчерпан до конца месяца, увеличить или дождаться».

Это защищает от случайного «разгона» бюджета, например, если кто-то запустил много исследовательских запросов в консьерже.

## Промпты — управление без программистов

Доступ: `/admin/prompts`.

Промпты — это инструкции, которые Кора даёт LLM-модели для каждой задачи. По умолчанию они закодированы в системе как «code fallback». Но из админки вы можете:

- Открыть конкретный промпт (например, `block-ingest-v2`).
- Отредактировать его.
- Сохранить — изменения применятся **немедленно**, без выкатки кода.
- Откатить к предыдущей версии или к code fallback.

Каждое изменение версионируется, видно, кто и когда менял.

Это важная функция: когда выходит новая модель или меняется задача, вы или ваш ассистент может подстроить промпт без обращения к разработчикам.

## Шаблоны отчётов встреч

Доступ: `/settings/templates`.

Те самые **9 типов встреч** имеют каждый свой шаблон AI-отчёта. Это тоже редактируется из админки. Можно:

- Открыть шаблон (например, Discovery).
- Поменять, какие блоки должны быть в отчёте.
- Сохранить, отменить.
- Создать **свой новый тип** встречи под вашу специфику (например, «Совет директоров» или «Performance Review»).

## Helpfulness Overview

Доступ: `/admin/helpfulness-overview`.

Командная карта полезности сотрудников. Показывает два блока:

- **Team-map** — агрегированная карта по всем сотрудникам: у кого какие traits выражены сильнее (help_provided, proactive_hint, mentoring, emotional_support, constructive_feedback).
- **Unanswered questions widget** — список вопросов, на которые никто не ответил. Позволяет админу увидеть пробелы в коммуникации.

Приватные traits (question_unanswered, question_acknowledged_no_action) **видны только админу**. Обычные сотрудники и менеджеры их не видят.

## Обратная связь с AI-кластеризацией

Доступ: `/admin/feedback` (только super_admin).

Дашборд пользовательских предложений и отзывов. Кора автоматически кластеризует похожие обращения по темам — ночью запускается AI-прогон, который группирует сообщения в `FeedbackTopic`-блоки с процентами по items.

### Что видно

- Список тематических блоков (`FeedbackTopic`) с процентным соотношением.
- Внутри каждого блока — конкретные предложения пользователей.

### Действия

- **Rename** — переименовать тему, если AI назвал её неточно.
- **Merge** — объединить две похожие темы.
- **Archive** — архивировать устаревшую тему.
- **Ручной запуск** — кнопка принудительного ночного прогона кластеризации (не ждать до утра).

### Детальная страница

`/admin/feedback/[topicId]` — карточка конкретного блока: все items внутри, история действий (rename/merge/archive), диалоги по каждому item.

## Что нельзя

- Нельзя удалить провайдера, по которому есть исторические записи использования (но можно деактивировать).
- Нельзя удалить старую цену — только архивировать.
- Нельзя выгрузить ключи API из системы (для безопасности).
- Нельзя поменять стоимость задним числом — историческая стоимость рассчитана по ценам на момент вызова.

## Что попробовать

- Раз в неделю — заходите в `/admin/economics` и смотрите топ убыточных клиентов. Иногда это сигнал «надо менять тариф» или «слишком сложная конфигурация».
- Раз в месяц — пересматривайте `/admin/llm-prices` (провайдеры часто меняют цены).
- Один раз — запустите A/B-тест primary vs secondary на основной задаче. Часто оказывается, что secondary даёт почти то же качество за меньшие деньги.

## Полезные команды консьержу

Из любой страницы:

- «покажи топ-5 самых дорогих запросов за вчера»
- «сравни наш расход в этом месяце с прошлым»
- «какой клиент самый убыточный»
- «поставь алерт если расход на ИксЛТД превысит 30000 в месяц»
- «откати промпт block-ingest-v2 к предыдущей версии»
