# Умный поэтапный поиск для «Мастера»: синтез + перепроверка

## Граница (важно — не дублировать граф-ТЗ)
- **Нижний слой (качество одного поиска)** — зона `plans/tz/2026-06-23-knowledge-graph-ingestion-rebuild.md`: retrievable «суть встречи», обход рёбер, склейка людей, актуальность. НЕ переделываем здесь.
- **Этот анализ — верхний слой (оркестрация помощника):** план → поэтапный поиск с переформулировкой → осмысленная остановка → честный ответ. Поверх улучшенного графом поиска.

## 1. Рамка проблемы (простым языком)
Помощник крутит «слепую петлю»: подумал → дёрнул инструмент → посмотрел → снова, до жёсткого потолка 5. Два изъяна:
1. **Нет плана** — простой вопрос и тяжёлый агрегат («по всем встречам с X — какие возражения») гоняются одинаково дорого; потолок «5» рубит, но не отвечает «достаточно ли собрано».
2. **Ложное «Готово ни с чем»** — ответ отдаётся без проверки «а найденное вообще про то, что спросили, и подтверждает ли мой ответ» (нет гейта заземления).
Метрика «решено»: меньше токенов на простых, точные ответы на агрегатах, честный отказ вместо выдумки, остановка по смыслу.

## 2. Дерево этапов умного поиска (MECE) — каждый со статусом у нас
- **Э0. Роутинг сложности** — `none`/`single`/`iterative` на входе (Adaptive-RAG). _У нас: нет верхней развилки._
- **Э1. План** (для сложных) — массив под-шагов (Plan-and-Execute/ReWOO/декомпозиция). _У нас: `dialog-extract-plan` — зачаток._
- **Э2. Объёмный поиск (recall)** — найти всех кандидатов по теме. _У нас: `chat-v2` гибрид + `dialog-multi-query`._
- **Э3. Отбор (слияние RRF + реранк)** — отсеять мусор. _У нас: слияние, вероятно, наивное; реранкера нет — gap._
- **Э4. Детальный поиск + переформулировка из находок** — вытащить факт по каждому, дозапросить недостающее. _У нас: ReAct-петля concierge — основа есть._
- **Э5. Достаточность/остановка** — «хватит ли», а не «5 шагов» (FAIR-RAG sufficiency + loop-guard). _У нас: только слепой `MAX=5`._
- **Э6. Синтез + гейт заземления + честный отказ** — проверить подтверждённость до выдачи (Self-RAG `[IsSup]`/CRAG abstain). _У нас: главная дыра — нет гейта._

## 4. Рекомендация: вариант C (гибрид), слоями по ROI
**Почему C:** роутер экономит на массе простых запросов; план+breadth→per-item — каноническая декомпозиция нашего кейса; гейт заземления убивает «ложное Готово»; sufficiency заменяет слепой «5»; всё переиспользует имеющееся и всё на TS; single-agent (не плодим агентов — прямая рекомендация Яндекса). Вся литература 2025 сходится к **роутингу**, а не к одной архитектуре навсегда — red-team подтвердил это независимо (консенсус, не спорная ставка).

**Порядок слоёв (СКОРРЕКТИРОВАН red-team'ом, каждый Ship-On):**
1. **Loop-guard по отпечаткам** (детерминированный, 0 токенов: кольцевой буфер, SHA256(tool+args), threshold=3) + `MAX=5` → AdminSetting, лимит **на шаг плана**, при достижении — честный частичный ответ, не пустота.
2. **Гейт заземления + честный отказ** в chat-v2 — НО сразу **с контролем over-abstention** (крутилка + метрика в diag; иначе вылечим «ложное Готово» ценой «отказ на отвечаемом»). Судья — **иная модель/иной промпт**, чем генератор (против self-enhancement bias).
3. **Реранк (Э3) вместе с RRF** — red-team поднял реранкер: именно он даёт наибольший прирост, RRF без реранка слаб и хрупок к доменному сдвигу. LLM-as-reranker (gpt-5-mini) для v1.
4. **Роутер сложности (Э0)** — few-shot, но fallback-инвариант «при сомнении → `single`, не `none`» + сбор misroute в diag (классификатор day-1 мисроутит, точность растёт только на фидбеке).
5. **Planner+replan + breadth→per-item** для подтверждённо-агрегатных запросов — **декомпозиция ЗА гейтом и с fallback на одношаговый** (наивное дробление деградирует: lost-in-retrieval, error propagation).
6. **Sufficiency-судья** (FAIR-RAG: чек-лист фактов → confirmed/gaps/sufficient) — ранний осмысленный выход.
7. **Опционально за гейтом по типу**: step-back/HyDE/query-rewrite только для why/how/сравни/диалоговых.

**Все пороги — в AdminSetting (§9):** `rag.crag.upper/lower`, `rag.rrf.k`, число версий multi-query, `concierge.max_steps`, веса dense/sparse, top-k. Чужие числа из papers (k=60, пороги CRAG) НЕ копировать — калибрует super_admin на нашем графе.

## 5. Маппинг на наши модули

## 6. Риски (синтез + 5 добавленных red-team'ом)
- **R-cold-start (КРИТИЧНЫЙ для Коры):** на малом графе (2–3 встречи у нового тенанта) тяжёлые ветки ломаются — breadth не на чем работать, sufficiency вечно «gaps», over-abstention взлетает. → **Нижняя граница объёма данных, ниже которой — простой режим (одношаговый chat-v2).**
- **R-latency-compounding:** агрегат = 8+ последовательных вызовов (часть ×N элементов) → секунды-десятки. → Жёсткий wall-clock SLA, не fail-safe.
- **R-iterative-cost-no-gain:** на медианном «сложном» одношаговый chat-v2+гейт может бить полный гибрid. → «iterative»-ветка сама **за гейтом объёма + доказана A/B**, не по факту классификации.
- **R-RRF-domain-shift:** RRF хрупок к домену (русский, смесь встреч/чатов); k=60 неприменим. → Калибровать k и веса, не только пороги CRAG.
- **R-judge-self-enhancement:** судья и генератор = одна flash-модель → оценивает свой ответ как заземлённый. → Судья — другая модель/промпт.
- (синтез) +N лёгких вызовов — держать на flash, батчить; пороги калибровать; цифры — чужие бенчмарки.
