ЭТАП 0 — PRE-FLIGHT (ОБЯЗАТЕЛЬНО ДО ПЕРВОЙ ФАЗЫ)
═══════════════════════════════════════════════════════════════════════════

Перед тем как делегировать что-либо агентам, ты:

0.1. ЧТЕНИЕ ИСТОЧНИКОВ ПРАВДЫ
- Прочитай целиком:

0.2. ИЗУЧЕНИЕ СУЩЕСТВУЮЩЕГО КОДА (vexp first, не Grep напрямую)
- Запусти vexp `run_pipeline` с задачей описания: «реализовать зонтик
  main-screen-umbrella — нужны: AccountsService.register, RbacService,
  TenantGuard, DirectorDashboardClient, AssistantSidebar,
  /onboarding/welcome/complete, /admin/demo, org-switcher».
- Используй `get_skeleton` для каждого ключевого файла из frontmatter

- ВНИМАНИЕ: дочерние ТЗ перечисляют существующие файлы — проверь, что
  они до сих пор существуют по тем же путям (могли переименоваться).
- Если какой-то файл не существует — пометь как блокер и спроси
  пользователя ДО продолжения.

0.3. PARALLEL SESSIONS CHECK
- `git fetch --all --prune`
- `git log --all --since="2 hours ago" --pretty=format:"%h %ad %s %an"`
- Если найдены коммиты от других авторов (не текущего git-user'а) за
  последние 2 часа в backend/src/modules/{onboarding,rbac,accounts} или
  frontend/app/(authenticated)/dashboard — спроси пользователя, не идёт
  ли параллельная работа.

0.4. ОТВЕТ ПОЛЬЗОВАТЕЛЮ ДО СТАРТА (под этим разделом — «возврат с решением»)
Пришли пользователю короткий (до 400 слов) отчёт со следующими разделами:

а) КАКИЕ ТЗ ПРОЧЁЛ — список с количеством строк/КБ каждого.

б) КАКИЕ КЛЮЧЕВЫЕ ФАЙЛЫ КОДА ИЗУЧИЛ — список с краткой пометкой
   «соответствует ТЗ» / «нужно уточнить N» / «отсутствует».

в) РЕКОМЕНДАЦИИ ПО ИСКЛЮЧЕНИЯМ (scope-cuts) — что из ТЗ ты предлагаешь
   НЕ делать в этой итерации и почему:
   * фазы дочерних ТЗ, которые блокируются отсутствующим API
   * виджеты, для которых нет данных и backend-эндпоинт не создаётся
   * edge-cases низкого приоритета (например, super_admin bypass —
     можно отложить, если super_admin сейчас не используется)

г) РИСКИ И РАЗВИЛКИ, КОТОРЫЕ НЕ ЗАКРЫТЫ В ТЗ:
   * перечисли open questions из обоих дочерних, которые требуют решения
     именно сейчас (а не отложены)
   * для каждого — предложи свой default с обоснованием

д) ПОРЯДОК ВОЛН — финальный план: «Поток А (фазы 0-7) → Поток Б (фазы 0-9)
   → Поток В (шаги 1-7)» или адаптированный (например, какие-то фазы
   объединяются для скорости).

е) ОЦЕНКА ОБЪЁМА — сколько коммитов будет, сколько часов работы агентов
   суммарно. Не для точности, для ощущения масштаба.

После этого СТОП. Жди от пользователя одного из:
  * «погнали» / «погнали Поток А» — стартуй
  * правки по конкретным пунктам отчёта
  * «отменяем» — закройся

2.4. ФАКТ-ЧЕК ПОСЛЕ АГЕНТА (КРИТИЧЕСКИ ВАЖНО — НЕ ДОВЕРЯЙ):
Из feedback memory: «Агенты могут лгать про [x] — всегда грепать факт-чек».

После получения отчёта от агента ОБЯЗАТЕЛЬНО:
а) `git status --short` — сравни со списком файлов из отчёта агента.
   Несовпадение = красный флаг, перепроверь все маркеры.
б) Grep по 3-5 ключевым маркерам из re-Read цитат отчёта:
   `Grep(pattern="<уникальный маркер из цитаты>", path="<файл из отчёта>")`
   Если маркер не найден — агент соврал, нужно либо доделать самому
   через Edit, либо перезапустить агента с уточнением.
в) Самостоятельно прогони `bun run typecheck` и `bun run lint` (агент
   мог сказать «зелёный» в качестве пустого вывода, но содержимое могло
   не дойти). 4 строки tail.
г) Если ничего не сломалось — фаза завершена. Иначе — fix-it loop:
   либо мини-задача агенту на исправление, либо ручной Edit.

2.5. КОММИТ:
- `git add` с ЯВНЫМ ПЕРЕЧИСЛЕНИЕМ файлов (никогда не `-A` или `.`)
  Из feedback memory: «Перед каждым git add явно перечисляй пути».
- `git status` после add — проверь, что нет лишнего staged.
- `git commit -m` с HEREDOC, conventional commits format:
  `feat(<scope>): Фаза N — <название> (зонтик main-screen-umbrella)`
  Тело: что сделано · что не сделано · Verification: typecheck+lint зелёные.
  Co-Authored-By в конце.
- НЕ push после каждой фазы — только в самом финале.

2.6. ОБНОВЛЕНИЕ TODOWRITE:
- Текущая фаза → completed с указанием коммит-хэша.
- Следующая фаза → in_progress.

2.7. ПЕРЕХОД К СЛЕДУЮЩЕЙ ФАЗЕ.
Делай без пауз. Из feedback memory: «Многоволновая оркестрация — без
остановок между волнами; зелёная верификация → commit → следующая волна
в том же ответе; push с подтверждением».

- `git push -u origin feature/main-screen-umbrella`
- Покажи ссылку на PR creation (gh pr URL).
- Не создавай PR автоматически — это решает пользователь.

# Метаинформация (НЕ часть промпта)

## Как использовать этот файл

1. **Открой новую сессию Claude Code** в проекте `c:\work\z` (рекомендуется
   на чистом dev'е, без активной feature-ветки).
2. **Скопируй содержимое раздела «# ПРОМПТ ОРКЕСТРАТОРА»** (всё внутри
   тройных бэктиков) — это первое сообщение пользователя в новой сессии.
3. **Жди отчёт Pre-flight** — он покажет план и предложит scope-cuts.
4. **Скажи «погнали»** (или внеси правки) — оркестратор стартует.
5. После всех фаз и финальной верификации скажи **«push»** — ветка уйдёт
   на origin.

## Что оркестратор делает САМ (без твоего участия)

- Чтение всех 3 ТЗ + analysis.
- Изучение существующего кода (vexp + get_skeleton).
- Параллельная-сессия чек.
- Создание feature-ветки.
- Цикл 24+ фаз (А.0..А.7 = 8, Б.0..Б.9 = 10, В.1..В.7 = 7 → ~25 фаз).
- Делегирование каждой фазы агенту с шаблонным промптом.
- Факт-чек после каждого агента (grep + typecheck + lint).
- Коммит с явными путями файлов.
- TodoWrite обновление.
- Финальная верификация (build + tests).
- Обновление second-brain + dashboards-registry + prod-deploy-log.
- Написание рефлексии.

## Что оркестратор делает с твоим участием

- **Pre-flight отчёт** → ждёт «погнали».
- **Остановка при развилках** (см. Этап 3 промпта).
- **Финальный push** → ждёт явного «push».

## Что НЕ делает оркестратор

- Не пушит без явного разрешения.
- Не создаёт PR (это решает пользователь).
- Не пишет новые backend-эндпоинты, которых нет в ТЗ.
- Не выдумывает данные для виджетов (если поля нет в API).
- Не вносит изменения в файлы, которых нет в перечне ТЗ.
- Не amend'ит/не force-push'ит без явного указания.

## Failure-modes и их обработка

| Failure | Действие оркестратора |
|---|---|
| Агент вернул отчёт с маркерами, которых нет в файлах | Перезапуск агента с уточнением «маркер X в файле Y не найден, проверь и доделай» |
| typecheck красный после фазы | Fix-it loop: либо мини-задача агенту, либо ручной Edit |
| Build падает с regression не из нашей фазы | Стоп → спросить пользователя |
| ТЗ требует endpoint которого нет | Фиксируем как открытый хвост, UI рендерим с заглушкой / `null`, продолжаем |
| Параллельная сессия записала в наши файлы | Стоп → git pull, разобраться, спросить пользователя |
| Агент дважды отдал «не получилось» | Стоп → попросить пользователя пересмотреть фазу или сделать вручную |

## Эстимация

Зонтик содержит ~25 фаз (А: 8, Б: 10, В: 7). Каждая фаза = 1 коммит.
По опыту предыдущей оркестрации (dashboards-wow-polish, 11 фаз =
~3 часа работы агентов + ~30 мин на факт-чек) — ожидаем **~8-10 часов
работы оркестратора суммарно**, ~25-28 коммитов в feature-ветке.
