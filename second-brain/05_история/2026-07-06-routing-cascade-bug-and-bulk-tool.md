# Каскадная потеря тиров роутинга — реальный инцидент, находка бага, восстановление и защитный инструмент

## Что было поставлено

Владелец прислал два скриншота: (1) `/admin/analytics/llm-cost?view=company` — в таблице «по моделям» не видно провайдера, нет фильтров по дате/модели; (2) `/admin/ai/routing` — почти у всех задач (`summary`/`chapters`/`tasks`/`chat`/...) пустой `primary` И пустой `tertiary`, остался только `secondary` (minimax). Дословно: «Роутинг моделей у меня сейчас получается вообще модели никакие не используются... потому что я удалил другие модели, но почему-то не поставился провайдер и модели из умолчания — АНАЛИЗ И ФУНКЦИИ СЛОМАЛИСЬ!» Плюс запрос на фичу: авто-подстановка дефолта для ВСЕХ незанятых сразу + меню «выставить всем провайдером X нужную модель».

## Как решал

**Диагностика (не гадание — прямые запросы к БД).** Сначала проверил реальное состояние `LlmTaskRoute` в БД для нескольких `taskType` — подтвердил: строк `primary`/`tertiary` физически НЕТ (не null-провайдер, а отсутствие строки целиком). Прошёлся по `LlmTaskRouteChange` audit-логу по времени и восстановил ПОЛНУЮ цепочку событий: 09:36 удалён `deepseek` (default=openai-via-proxy, primary мигрировал корректно) → 09:44 удалён `kie` → 09:45 удалён САМ `openai-via-proxy` (был дефолтом, дефолт сменился на `minimax`) — и вот тут, при миграции primary+tertiary на новый дефолт `minimax`, код увидел, что `secondary` УЖЕ был `minimax` (стоял так с самого начала, никто не трогал), посчитал это «дубликатом» по правилу Р2 из прошлой фичи (llm-provider-default-fallback) и вместо переключения — УДАЛИЛ мигрирующую строку. Так по цепочке съелись оба соседних тира почти у 176 задач.

**Корень — код, не данные.** `AdminLlmProvidersService.migrateRoutesToDefault()`: проверка «уже есть дубликат в группе на другом тире → удалить» не учитывала, что при НЕСКОЛЬКИХ последовательных удалениях подряд дефолт-провайдер каждый раз меняется, и старый нетронутый тир может СЛУЧАЙНО совпасть с новым дефолтом. `@@unique([taskType, tenantId, tier, providerName])` включает `tier` — то есть два тира с одним и тем же провайдером технически легальны, дедуп был чисто косметическим решением (Р2), которое на практике оказалось опасным. Убрал удаление полностью — теперь всегда `UPDATE`.

**Восстановление данных.** Провайдеры были только soft-deleted (данные целы) — реактивировал через прямой `UPDATE`. Для потерянных ROUTES (реально удалённых строк) прогнал напрямую (в обход once-only ledger `apply-prod-deploy.ts`) уже существующие идемпотентные скрипты `seed-llm-default-primary-deepseek-pro.ts` (169 primary) и `patch-normalize-llm-chains-deepseek-openai-kie.ts` (190 tier-строк) — оба уже были в проекте именно для этой цели, просто раньше не пришлось их перезапускать вручную.

**Защитный инструмент вместо неявной магии.** По запросу владельца добавил `POST /admin/ai-models/bulk-reassign` (+ preview) — явное, ПОДТВЕРЖДАЕМОЕ (preview + обязательный reason) действие: либо заполнить все ПУСТЫЕ (taskType,tier), либо переключить ВСЕ маршруты с провайдера X на Y одним прозрачным шагом, вместо того чтобы полагаться на автоматическую цепную реакцию при удалении провайдера (которая и породила инцидент).

**Попутно** — `byModel` в дашборде расхода (overview + company-detail) не показывал `provider`, из-за чего одинаковые имена моделей у разных провайдеров (`gemini-3.1-pro` через `kie` и `grsai`) были неотличимы. Добавил `provider` в группировку (`groupBy(['provider','model'])` вместо `['model']`) везде, плюс `dateFrom`/`dateTo`/`provider`/`model` фильтры на странице компании (с UI-селектами, populated из реальных данных периода).

## Что вышло

Все 3-тирные цепочки восстановлены и проверены живьём (скриншот роутинга — primary/secondary/tertiary на месте у всех проверенных задач). Полный backend-прогон 7888/7958 (16 сбоев — те же самые предсуществующие, что были и до этой сессии, не новые). Живая QA: bulk-reassign preview для `scope=unassigned` → «0 маршрутов» (подтверждает восстановление полное), для `scope=provider,kie` → «176 маршрутов» с полным списком (совпадает с ожиданием). Company-detail: столбец «Провайдер» на месте, фильтр по провайдеру реально сузил `$0.118→$0.097` и график.

## Чему научился

- **«Похоже на баг фичи, которую я сам недавно писал» — сначала проверь БД, потом код, потом делай выводы.** Не спекулировать о том, что случилось — прямой SQL-запрос к `LlmTaskRoute` за 30 секунд показал, что строк физически нет (не null-поле), а `LlmTaskRouteChange` с сортировкой по времени дал ПОЛНУЮ, однозначную картину происшествия без единой догадки.
- **Дедуп-логика, одобренная для ОДНОГО события миграции, может быть опасна при ЦЕПОЧКЕ независимых событий.** Р2 («не плодить видимость резерва там, где провайдер уже дважды в цепочке») была верна для одного разового удаления — но при последовательных удалениях с меняющимся дефолтом та же логика начинает есть данные, которых никто не трогал. Constraint-анализ (`tier` входит в `@@unique`) сразу показал, что дедуп технически не был НУЖЕН для целостности — только «красивости», ради которой рискнули данными.
- **Явный инструмент с preview лучше неявной магии при удалении.** Вместо того чтобы полагаться на автоматическую миграцию routes при удалении провайдера (которая и привела к каскаду), явная кнопка «Балковое назначение» с обязательным предпросмотром — более безопасный путь для ИМЕННО ТАКИХ операций massed-изменения.
- **Восстановление данных — используй УЖЕ СУЩЕСТВУЮЩИЕ идемпотентные seed/patch-скрипты, а не ручные UPDATE построчно**, если они есть в репозитории именно для этой цели (`seed-llm-default-primary-deepseek-pro.ts`/`patch-normalize-llm-chains-deepseek-openai-kie.ts` существовали заранее, просто требовали запуска в обход once-only ledger локально).
