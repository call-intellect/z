# «Поправить карточку знаний»: исправить или оспорить провизорную карточку

## 0. Откуда взялось и зачем (человеческим языком)

Лестница доверия (Часть A) разрешила ИИ **самому** канонизировать критические карточки (решения/правила/процессы) как **провизорные** (`trustTier='provisional'` = «ИИ одобрил, человек не проверял»). Фаза **C1** сделала это **видимым** — плашка «Не проверено человеком».

Но петля не замкнута: пользователь видит «не проверено» и **ничего не может с этим сделать там, где смотрит**. Нужна не «жалоба», а **исправление**.

**Ключевое решение (фидбек владельца):** просто «это неверно» — самый бедный сигнал («тут что-то не так»), а самое ценное — *как правильно* — теряется. Если человек сразу правит текст, получаем **три выгоды разом**:
1. **Данные исправлены** — карточка сразу становится правильной, а не «помеченной сомнительной».
2. **Доверие повышается** — провизорная карточка после правки человеком становится **`trustTier='human'`** (плашка C1 снимается). Живой апгрейд доверия прямо в потоке.
3. **Обучение богаче** — модель учится не «вот это плохо», а **«вот как правильно»** (несравнимо более полезный сигнал для самокоррекции лестницы).

## Развилки (закрыты)

1. **Только флаг vs исправление с текстом** → **ОБА пути.** Иногда человек знает, что неверно, но не знает правильного ответа («сроки устарели, актуальных не помню»). Если оставить только «исправь» — он промолчит, ошибка останется. Поэтому:
   - **«Исправить»** — редактирование текста карточки (предзаполнено текущим) + поле «в чём была ошибка».
   - **«Это неверно»** — флаг без правки → карточка уходит к людям на разбор (очередь курации), не остаётся молча провизорной.
2. **Куда попадает авторская правка** → зависит от прав (анти-вандализм):
   - **owner / admin / назначенный куратор** — правка применяется **сразу**: новая версия карточки с `trustTier='human'` (карточка становится человеко-проверенной).
   - **обычный сотрудник** — правка не применяется напрямую, а **предлагается** → `CurationItem` в очередь курации (чтобы кто попало не переписывал регламенты). После одобрения куратором → каноническая человеко-проверенная версия.
3. **Строить новое или связать существующее** → **связать.** Все кирпичи есть: `recordDecision` (флаг + обучающий сэмпл), механизм версий `CardVersion` (новая версия с правленым payload; человеческое решение проставляет `trustTier='human'`), очередь курации (`CurationItem` + `decide`). Не изобретаем — соединяем.
4. **Какие типы карточек** → критические, где есть провизорность: `regulation` / `decision` / `process` (+ `policy`). Не входит: сущности графа (для них уже есть `/entities/:id/mark-wrong`), метрики/инструменты (не версионируются `CardVersion`).

## Что уже готово (не переделывать)

- `CurationService.recordDecision()` (`curation.service.ts:710`) — generic «карточка/ребро неверны» по `(tenantId, resourceType, resourceId, decisionType, recordedBy, reason, context)` → `CurationItem(decided, light)` + `CurationDecision` + эмит `curation.decision_recorded` → обучающий `LlmPreferenceSample`.
- Образец флаг-эндпоинта: `POST /api/v1/entities/:id/mark-wrong` (`entities.controller.ts:553`).
- Механизм версий `CardVersion` (append новой версии с `trustTier`) — используется в курации; человеческое решение даёт `trustTier='human'`.
- Очередь курации + `decide` (`approve_with_edits` принимает правленый payload) — путь «предложение → одобрение».

## Фаза E1 — Backend: исправление и оспаривание карточек

**Что входит:**

1. **Оспаривание (флаг)** — тонкие эндпоинты по образцу `entities/:id/mark-wrong`:
   - `POST /api/v1/regulations/:id/dispute` (kind regulation/process/policy) → `recordDecision({ resourceType, resourceId, decisionType:'mark_as_misleading', recordedBy, reason })`.
   - `POST /api/v1/decisions/:id/dispute` → то же для `resourceType:'decision'`.
   - Тело: опц. `reason` (свободный текст «в чём ошибка»). Доступно любому, кто видит карточку (read-доступ); эффект — сигнал + (для провизорных) уход на человеческий разбор.

2. **Исправление (правка с текстом)** — эндпоинты, создающие **исправленную версию**:
   - `POST /api/v1/regulations/:id/correct`, `POST /api/v1/decisions/:id/correct`.
   - Тело: `correctedPayload` (правленые поля карточки) + опц. `reason`.
   - **Логика по правам (внутри сервиса, RBAC):**
     - есть write-право на ресурс (owner/admin/назначенный куратор) → **применить сразу**: append `CardVersion` с `correctedPayload` и `trustTier='human'`, обновить `currentVersion` карточки; записать обучающий сэмпл («было → стало»).
     - нет write-права → **предложить**: создать `CurationItem(level=light, reason=user_correction)` с `proposedPayload=correctedPayload` в очередь курации (куратор одобрит через существующий `decide`/`approve_with_edits`).
   - Переиспользовать существующий путь версии/курации, не дублировать.

3. **Обучающий сигнал** в обоих случаях — через существующий эмит `curation.decision_recorded` (флаг) / запись правки (исправление), чтобы лестница доверия училась.

**Что НЕ входит:** менять саму логику триажа/канонизации (A1/A2); трогать сущности графа (у них свой mark-wrong).

**Acceptance:**
- [ ] `dispute` на провизорную регуляцию/решение создаёт `CurationItem` + обучающий сэмпл; для провизорной карточки эффект — уход на человеческий разбор.
- [ ] `correct` от owner/admin/куратора → новая версия `trustTier='human'`, `currentVersion` обновлён, плашка «Не проверено человеком» снимается; «было → стало» записано как обучающий сэмпл.
- [ ] `correct` от обычного сотрудника → `CurationItem` с `proposedPayload` в очереди (карточка пока не меняется), без 403-тупика.
- [ ] RBAC: чужой tenant / нет read-права → отказ. Unit/e2e на оба пути + проверка прав.
- [ ] typecheck/lint/тесты зелёные.

**Файлы-ориентиры:** `curation.service.ts` (`recordDecision`, append `CardVersion`, `decide`/`approve_with_edits`), `entities.controller.ts:553` (образец), `regulations`/`decisions` контроллеры+сервисы (где живут карточки и их версии), RBAC-гарды этих модулей.

## Фаза E2 — Frontend: действия «Исправить» и «Это неверно» на карточке

**Что входит:**
- На детальной карточке регуляции/решения (особенно при `trustTier='provisional'`, рядом с плашкой C1 `TrustBadge`) — **два действия**:
  - **«Исправить»** → форма: текст карточки на редактирование (предзаполнен текущим `payload`) + поле «в чём была ошибка» (опц.). Сабмит → `correct`. Для owner/admin/куратора — подпись «Сохранить как проверенную версию»; для остальных — «Предложить правку» (уйдёт на проверку). После успеха: тост + обновление; провизорная → человеко-проверенная (плашка исчезает) либо «Отправлено на проверку».
  - **«Это неверно»** → лёгкий диалог с опц. полем «почему» → `dispute`. Тост-подтверждение.
- Тексты на русском, парные цветовые токены; форма правки переиспользует существующий UI-паттерн редактирования карточки, если он есть (иначе — простое контролируемое поле/поля).

**Что НЕ входит:** массовое редактирование; правка не-критических типов.

**Acceptance:**
- [ ] На детали провизорной карточки видны «Исправить» и «Это неверно»; подпись действия зависит от прав (правка vs предложение).
- [ ] Исправление owner/admin/куратором → карточка обновилась, плашка «Не проверено человеком» снята. Исправление обычным сотрудником → «Отправлено на проверку», карточка не изменилась мгновенно.
- [ ] «Это неверно» фиксирует оспаривание (тост). Парные токены, русский. typecheck/lint/test:unit зелёные.
