# Орг-сущности: твои 2 промта vs наши агенты — что улучшить

> **Вывод в одну строку.** Твой **экстрактор** (#1) уже близок к нашим — он даёт точечные усиления
> (негативный список, доменная калибровка, `roles`, evidence/description, пример). Твой **компилятор**
> (#2) — это **целый агент, которого у нас НЕТ** (`contentMd` сейчас собирается без структуры).
> Его и надо завести: твой #2 — почти готовая спецификация. Ниже — конкретика.

| trustTier | `auto · provisional · human` (лестница доверия) | — |
| **Агент-компилятор `contentMd`** | **ОТСУТСТВУЕТ** (`find` по `*document-compiler*` пусто; ТЗ Ф7 — new) | — |

**Два вывода сразу:**
1. **«Статус» — это две РАЗНЫЕ оси, которые сейчас слиплись.** Твой `существует/нужен/обсуждается` —
   про «это норма или ещё только разговор» (наш C2: извлечённое ≠ подтверждённое). Код-овский
   `active/deprecated/archived` — про жизненный цикл уже принятой карточки. Их нельзя маппить 1:1:
   `нужен/обсуждается` — это вообще НЕ `active`. Нужен **отдельный extraction-status** (или гейт
   «в lifecycle `active` попадает только `confirmed`+триаж»).
2. **`contentMd` некому собирать по-человечески.** `regulation-extract` выдаёт короткий `statement`,
   `regulation-dedupe` — только verdict (new/merge/extension), а «extension» делает `update` поля.
   Никто не компилирует структурный документ из накопленных блоков. Это и есть пробел Ф7 = твой #2.

## 1. Маппинг: твои 2 промта → наши агенты

| Твой промт | Что делает | Наш(и) агент(ы) | Зрелость |
|---|---|---|---|
| **#1 Экстрактор** (текст → массив сущностей процесс/регламент/инструкция) | распознать и типизировать сущности | **block-ingest (группа Б)** — видит окно сегментов, выдаёт `processes/regulations/policies[]`; **regulation-extract** — 1 блок → 1 черновик; **specialists-combined** — все блоки → 8 сущностей | ✅ есть, усилены в рерайтах; нужны точечные добавки (§2) |
| **#2 Компилятор** (тип+название+материал+существующий док → готовый структурный документ) | собрать `contentMd` по шаблону типа, режимы СОЗДАНИЕ/ДОПОЛНЕНИЕ, маркеры, changelog | **— НЕТ —** (частично перекликается `role-profile-build`, `card-rollup-v2`, но это другие сущности) | ❌ агента нет — **главный пробел** (§3) |

> **Важная архитектурная поправка.** Твой экстрактор — ОДИН проход по всему тексту, поэтому он
> легко считает «сколько ролей» (ключ дискриминатора процесс/регламент/инструкция). Наш
> `regulation-extract` работает **по-блочно** (1 IdeaBlock) и контекста «сколько ролей во всей теме»
> НЕ видит → дискриминатор слабее. Поэтому 3-way дискриминатор и негативный гвард надо ставить в
> первую очередь там, где агент видит **весь текст**: `block-ingest` (окно) и `specialists-combined`
> (все блоки встречи), а per-block `regulation-extract` оставить как «дочерний», доверяя ему меньше.

## 2. Экстрактор: что забрать из твоего #1 в наши (точечно)

Мой рерайт `regulation-extract` (пилот §3) уже взял из твоего черновика: 4-way различение с
`instruction`, негативный фильтр «разовое ≠ норма», статус `confirmed/proposed/needed/discussed`,
опору на цитату. **Чего у меня НЕТ, а у тебя есть — стоит добавить:**

| # | Из твоего #1 | Где у нас слабо | Рекомендация |
|---|---|---|---|
| 2.1 | **Полный негативный список**: разовые задачи · отрицания без содержания · **чужие практики** («у конкурентов катят через CTO») · **гипотетика** («вот если бы как в Google») · **упоминание документа без содержания** («глянь в регламенте») → `status=существует`, низкий confidence | У меня только «разовое ≠ норма». Нет «чужие практики», «гипотетика», «упоминание без содержания» | Добавить эти 3 пункта в `## Чего НЕ делать` у `block-ingest` (группа Б), `regulation-extract`, `specialists-combined`. Это снимет фантомные сущности про конкурентов и мечты |
| 2.2 | **`roles[]`** как явное поле вывода | Наша схема: `scope` (строка) + `ownerHint`; ролей-списка нет. Процесс держит роли только в `steps[].ownerRoleHint` | **Изменение схемы (опц., полезно):** `roles: string[]` в `regulation_extract_v1` + в группе Б. Даёт (а) сам дискриминатор (≥2 ролей → регламент/процесс, 1 → инструкция), (б) фронту — список участников карточки |
| 2.3 | **`evidence` (дословно) ОТДЕЛЬНО от `description` (своими словами)** | `regulation_extract_v1` отдаёт только `statement`; evidence-цитата приходит в USER, в выводе её нет → нельзя аудировать заземление (A3) | Добавить `evidenceQuote: string` в вывод (как в `block-ingest`). `statement`/`contentMd` — пересказ; `evidenceQuote` — дословная опора |
| 2.4 | **Доменная калибровка confidence** (0.9–1.0 = есть шаги/роли/сроки; 0.5–0.6 = упоминание без содержания) | У нас generic `withConfidenceCalibration` (про «обсуждено двумя участниками») — не про «есть ли в сущности шаги/роли» | Дать локальные якоря под орг-сущности (как у тебя), не полагаться только на generic |
| 2.5 | **Рабочий мини-пример с ДВУМЯ сущностями из одного текста** (регламент возвратов + инструкция по заведению заявки, с разными status) | У `regulation-extract` примера нет; у `process-template-extract` пример на 1 сущность | Добавить few-shot, где из одной реплики извлекаются и регламент (`обсуждается`), и инструкция (`нужен`) — учит и разделению, и статусу |
| 2.6 | **Дедуп внутри текста** (одна сущность, упомянутая много раз → один элемент; evidence — самый информативный фрагмент) | Per-block `regulation-extract` этого не может (видит 1 блок); межблочный дедуп у нас — отдельный `regulation-dedupe` | Для `block-ingest`/`specialists-combined` (видят много блоков) — добавить правило «одна сущность = один элемент, не плодить из каждого упоминания» |
| 2.7 | **Status: 3 значения** существует/нужен/обсуждается | У меня 4: confirmed/proposed/needed/discussed (I5). Твои `обсуждается` ⊇ мой `proposed`+`discussed` | **Свести к твоим 3** (проще для UI и людей): `существует(confirmed) · нужен(needed) · обсуждается(proposed+discussed)`. Меньше — лучше; «proposed vs discussed» человек не различит |

**Статус-маппинг (фикс «всё Действует») — единое решение для всех экстракторов и фронта:**
```
extraction status (новое поле)     →  lifecycle status (active/deprecated/archived)
  существует (норма действует)     →  active  (если триаж/доверие подтвердили)
  нужен / обсуждается              →  НЕ active — карточка-черновик (draft) или скрыта из «Действует»
```
То есть `extractionStatus` — отдельное поле сущности; в `active` карточка переходит только при
`existует`+курации. На фронте «Действует» показывать только для них; `нужен/обсуждается` — отдельная
секция «Черновики/обсуждается».

## 3. ГЛАВНЫЙ пробел — агент-компилятор документа (ТЗ Ф7). Черновик СТАЛО

Твой промт **#2** — это, по сути, готовая спецификация недостающего агента
`structured-document-compiler`. У нас сейчас `contentMd` собирается без структуры, а «дополнение»
= plain update. Ниже — **полный СТАЛО под наши контракты** (имена полей, таблицы, версии — реальные).

### Контракт (новый агент)
- **Вход (USER):** `kind ∈ {regulation|process|policy|instruction}` · `name` · `newSourceBlocks[]`
  (накопленные блоки темы: вопрос/ответ/цитаты) · `existingContentMd` (текущее тело, может быть пусто) ·
  `existingSteps[]` (для process) · `nowIso`.
- **Выход:** tool/json `compile_org_document` →
  `contentMd: string` (готовый markdown по шаблону типа) ·
  `steps[]` (для kind=process — синхронно с `ProcessStep`-таблицей) ·
  `changeReason: string` (ложится в `RegulationVersion.changeReason`) ·
  `signals: string[]` (type-mismatch / no-info — для триажа).
- **Режим:** `existingContentMd` пуст → СОЗДАНИЕ; иначе ДОПОЛНЕНИЕ. Версия — инкремент через
  существующую инфру `RegulationVersion` (компилятор НЕ нумерует сам — отдаёт `changeReason`).
- **E1/E2:** `newSourceBlocks`/`existingContentMd` — пользовательский контент → `wrapUserData` +
  `withInjectionGuard` на call-site (в текст SYSTEM не вшивать).

### СТАЛО (SYSTEM)
```
## Роль
Ты — специалист по корпоративной документации компании Кора. Получаешь тип документа, его
название и материал (накопленные блоки из встреч, переписок, заметок) и собираешь из сырого
материала готовый структурный документ одного из типов: Инструкция, Регламент, Описание процесса,
Политика. Ты не пересказываешь материал и не украшаешь его — ты собираешь рабочий документ,
который сразу ложится в базу знаний.

## Режим
- `existingContentMd` пуст или отсутствует → СОЗДАНИЕ.
- `existingContentMd` непустой → ДОПОЛНЕНИЕ (слияние по правилам ниже).

## Алгоритм (строго по порядку)
1. Определи режим.
2. Извлеки из материала факты по теме `name`: действия, роли, сроки, условия, инструменты,
   последовательности. Всё, что не относится к теме документа, — отбрось (в разговоре много лишнего).
3. Проверь тип. Если факты явно противоречат типу (просили инструкцию, а материал — взаимодействие
   пяти ролей со сроками), всё равно пиши в заданном типе, но добавь в `signals` строку
   «материал больше похож на <тип> — рекомендуется пересмотреть тип».
4. Разложи факты по разделам структуры нужного типа (ниже).
5. В режиме ДОПОЛНЕНИЯ — слей с существующим по правилам слияния.
6. Закрой пробелы маркерами, проверь по чек-листу, верни результат.

## Правила слияния (ДОПОЛНЕНИЕ)
- Сохраняй существующее: не удаляй и не переформулируй валидные пункты без основания; правка
  ради правки запрещена.
- Заполняй пробелы: если в документе `[требует уточнения: …]`, а материал даёт ответ — подставь,
  маркер убери.
- Добавляй новое в логичное место (шаг в середину последовательности, если он там по смыслу).
- Обновляй изменившееся (материал актуальнее старого), помечай прямо в тексте:
  `[изменено: было «…», стало «…»]`.
- Фиксируй конфликты, не угадывай: `[конфликт — требует подтверждения: A «…» / B «…»]`.
- Ничего не теряй молча: каждый факт старого документа либо сохранён, либо обновлён с пометкой.
- Маркеры `[изменено: …]` из прошлых версий считай принятыми: маркер убери, формулировку оставь.

## Общие принципы
- Не выдумывай: только то, что есть в материале или однозначно следует. Запрещено придумывать
  сроки/ответственных/названия систем «для полноты».
- Помечай пробелы: нет данных для раздела — `[требует уточнения: <что именно>]`. Честная дырка
  ценнее красивой выдумки.
- Роли, а не имена: пиши через роль, имя в скобках если есть («Менеджер (Ирина) передаёт…»).
  Роль неясна — `Иван [требует уточнения: роль]`.
- Деловой язык, настоящее время, ролевые формулировки («Менеджер проверяет…»).
- Один шаг — одно действие (глагол + объект + условие). Не склеивай три действия в пункт.
- Единая терминология: один объект — один термин во всём документе.
- Без воды: короткий точный документ лучше длинного.

## Структура по типам (раздел contentMd)

### kind = instruction (для одного исполнителя)
1. Назначение · 2. Область применения (кто исполняет) · 3. Что нужно перед началом ·
4. Последовательность действий (нумерованные шаги, каждый = одно действие одного человека) ·
5. Как понять, что сделано верно · 6. Если что-то пошло не так · 7. Связанные документы.

### kind = regulation (взаимодействие ролей) — ядро: таблица
1. Назначение · 2. Область применения · 3. Участники и роли ·
4. Порядок выполнения — таблица: | Шаг | Действие | Ответственный | Срок | Результат |
   (неизвестный срок/ответственный → `[требует уточнения]` в ячейке, не пропуск) ·
5. Контроль и эскалация · 6. Связанные документы.

### kind = process (сквозной поток) — synced со steps[]
1. Цель · 2. Границы (триггер/результат) · 3. Владелец процесса · 4. Участники ·
5. Шаги (для каждого: вход → действие → выход; ветвления «если…, то…») ·
6. Схема потока (Шаг 1 → Шаг 2 → …, текстом) · 7. Метрики (или `[требует уточнения]`) ·
8. Связанные процессы и документы.
   ВАЖНО: шаги верни ТАКЖЕ в поле `steps[]` (order/name/description/ownerRoleHint/slaMinutes) —
   они синхронизируются с таблицей ProcessStep.

### kind = policy
1. Назначение · 2. Область действия · 3. Положения (правила/ограничения) ·
4. Уровень строгости (рекомендация/обязательная/критическая) · 5. Последствия нарушения ·
6. Связанные документы.

## Краевые случаи
- В материале нет ничего по теме → не выдумывай: ДОПОЛНЕНИЕ — верни существующий contentMd без
  изменений; СОЗДАНИЕ — каркас из маркеров `[требует уточнения]`; в `signals` — «в материале нет
  информации по теме».
- Материала мало (1–2 фразы) — нормально: заполни что можно, остальное маркеры, не растягивай.
- В материале несколько тем — бери только относящееся к `name`.

## Чек-лист (молча, не в ответ)
Каждый факт прослеживается до материала? Пустоты закрыты маркерами, не выдумкой? В ДОПОЛНЕНИИ
ничего не пропало молча? Термины единые, шаги атомарные, роли (не только имена)?

## Формат вывода
Верни через инструмент compile_org_document: contentMd (по структуре типа), steps[] (для process),
changeReason (1–3 строки «что изменилось в этой версии» — только для ДОПОЛНЕНИЯ; для СОЗДАНИЯ —
«первичная сборка из материала»), signals[]. Никакого текста вне инструмента.
```

> Чем это лучше «голого `contentMd`»: документ собирается по **структуре типа** (D6), копится не
> теряя фактов (D4), честно помечает дырки и конфликты (D2/D3), отдаёт `changeReason` в готовую инфру
> `RegulationVersion` (D5). Это закрывает Ф7 ТЗ и ложится на уже существующие версии/курацию.

## 4. Фронт (страница «Правила, процессы и политики»)

Что менять на фронте, чтобы агенты «доезжали» до пользователя:

1. **`instruction` как вид.** `REGULATION_KIND_LABEL += { instruction: 'Инструкция' }`
   (`frontend/src/domain/regulation.ts`) + `RegulationKindSchema += 'instruction'` (DTO) +
   отдельная вкладка-фильтр «Инструкции» в `RegulationsListClient.tsx` (сейчас всё валится в «Процессы»).
2. **Развести два статуса.** Не показывать `нужен/обсуждается` как «Действует». Варианты:
   (а) добавить `extractionStatus` в карточку и секцию «Черновики / обсуждается»; (б) минимум —
   не переводить в lifecycle `active` ничего, кроме `существует`+курации. Это прямой фикс бага «всё Действует».
3. **Структурный `contentMd`.** Когда заведём компилятор — рендерить markdown по шаблону типа
   (таблица «кто-что-когда» для регламента; шаги вход→выход для процесса) и **подсвечивать маркеры**
   `[требует уточнения]`/`[конфликт]` как видимые чипы-«дырки» (призыв уточнить), а не серый текст.
4. **История версий уже есть** (`RegulationVersion` + UI) — подключить `changeReason` компилятора как

5. **`roles[]`** (если добавим, §2.2) — показывать списком участников на карточке.
