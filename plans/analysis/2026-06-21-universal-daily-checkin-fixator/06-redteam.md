# Red-team: единый детектор дневных сигналов

Атакована модель «единый детектор любого сообщения любого канала → DailyCheckIn(personId)». Независимый поиск, не повтор основной выдачи.

## Риск 1 — Privacy mode в группе → ПОДТВЕРЖДЁН (критично)
Telegram включает privacy mode по умолчанию (`can_read_all_group_messages=false`): бот в группе получает только команды к нему, reply на его сообщения, inline. Спонтанный текст «сделал X, план Y» не видит. Отключение через @BotFather **не применяется к уже добавленным группам** — нужно remove/re-add бота. Свежие issue 2026 фиксируют «бот молча не реагирует в группе». Это убивает реактивную модель «слушаем всех».
**Митигатор:** канон — личка/встреча; групповой чек-ин — явный prompt+reply (reply privacy mode пропускает); для «слушать всех» — onboarding-шаг (privacy off + re-add + проверка), без флага — детектор по группе выключен (degrade gracefully).

## Риск 2 — Ложные срабатывания → ПОДТВЕРЖДЁН
«Завтра к врачу», «надо доделать», «план Б» лексически = morning_plan. Ложный «сдал» красит дашборд зелёным — хуже пропуска (пропуск самокорректируется как «не сдал», ложное «сдал» создаёт ложную картину исполнения).
**Митигатор:** (1) solicited-only по умолчанию (чек-ин = ответ на prompt в окне N часов); спонтанное → кандидат `unsolicited`, не влияет на «сдал». (2) Если unsolicited — двухпороговый: предфильтр + LLM возвращает `{kind, confidence}`, запись только при `confidence≥порог` (AdminSetting). (3) Класс `personal/non-work` → drop, негативные few-shot примеры.

## Риск 3 — Дубли (встреча+личка в один день) → ПОДТВЕРЖДЁН частично
upsert по `(personId,date,kind)` даёт одну строку, но второй источник = last-write-wins, молча перезатрёт. Порядок джоб (BullMQ) недетерминирован → победитель случайный. upsert решает дедуп строки, не выбор контента.
**Митигатор:** ключ `(personId, businessDate по TZ Org, kind)`. Не LWW — детерминированный `sourceRank`: solicited личка > встреча > unsolicited; обновлять контент только если `incoming.rank≥existing.rank` (равный → merge/append). Хранить все вклады как source-рядки, DailyCheckIn — агрегат-проекция (аудит).

## Риск 4 — 152-ФЗ → ПОДТВЕРЖДЁН (юридический, высокий)
Классификация всех сообщений группы = массовая обработка ПДн (имена/ник/телефон/тело/аватар). 2025 — РКН усилил контроль мессенджеров; штрафы по поправкам 30.11.2024 до 5 млн₽+. В группе — не-сотрудники, личное, третьи лица. Согласие 152-ФЗ — конкретное/информированное/отдельное; «бот в чате» не покрывает. LLM-классификация всего потока (DeepSeek/китайский endpoint) = трансграничная передача тел сообщений.
**Митигатор:** scope только сотрудники (Person/binding в Org), отбрасывать внешних ДО LLM; solicited-only сужает объём; согласие/уведомление при onboarding + RBAC + retention (AdminSetting); dataClass-gate на LLM. NB: privacy как эпик deprioritized — но scope-мин + solicited нужны по продуктовым причинам, заложить сразу.

## Риск 5 — Стоимость LLM на каждом сообщении → ПОДТВЕРЖДЁН
Классификация каждого сообщения capable-моделью — проигрыш: разница моделей 60–300x, сигнал/шум в чате низкий («ок», «👍»). Бюджет LLM в Z без enforce — известный риск.
**Митигатор (каскад FrugalGPT):** (1) solicited-only срезает 90%+ бесплатно. (2) предфильтр до LLM (длина, временные маркеры «сегодня/завтра/план/сделал/итог», не-команда, сотрудник) → <5% кандидатов. (3) flash-модель `{kind,confidence}`, не capable. (4) cache-friendly промпт (экономия 95–99%).

## Риск 6 — Batch-добор «раз в сутки» → ПОДТВЕРЖДЁН (это переразбор, не дозагрузка)
Bot API не отдаёт историю до момента добавления бота; getUpdates/webhook — только real-time. Метода «дай сообщения за вчера» у бота нет (только MTProto-userbot). Cron не может дозагрузить из Telegram то, что бот не получил онлайн.
**Митигатор:** проектировать как **re-process сохранённого** (cron переразбирает свой RawEvent/лог — новая версия детектора, добор по TZ, агрегация вечернего отчёта), НЕ восполнение пропусков. Надёжность real-time приёма критична (webhook+ack, идемпотентное сохранение, dead-letter). Инвариант: «полнота сигналов = полнота онлайн-приёма + privacy off». Не обещать ретро-сбор группы.

**Сквозной вывод:** 4 из 6 рисков (1,2,4,5) закрываются ОДНИМ решением — **solicited-only поверх личного канала** вместо «слушаем всю группу». Модель «единый детектор любого сообщения любого канала» в групповом Telegram ломается о Bot API (privacy mode + нет истории) и о 152-ФЗ одновременно. Сузить инвариант: канон = ответ на prompt в личке/встреча; группа — опциональный degraded-режим (явный reply + privacy-off); cron — переразбор своего лога.
