# ТЗ: развести идею и решение (полный набор изменений)

## 1. Проблема (доказана по факту)

Развилка «идея/решение» делается один раз в `block-ingest` (выбор `signalType`); роутер дальше — статический mapping без перепроверки ([router.service.ts:236](backend/src/modules/knowledge-core/services/router.service.ts#L236)); специалисты гейтят по `signalType` и не реклассифицируют. Итог — три дефекта:

- **Дубль** — на «предложил→приняли» ingest создаёт И `idea`-, И `decision`-блок → одна вещь в двух реестрах. **[ТЕСТ]** дубли: PRO **11/37**, flash **10/37** (§10.1).
- **Тихая потеря** — `idea-extract` присваивает себе любое решение. **[ТЕСТ]** на решениях `isIdea=true` **3/3** (§10.2). **[БОЙ]** на встрече «Роман» 3 decision-блока → 0 Decision (`gap decision:3→0`, §9).
- **Перекос/деградация** — система по умолчанию штампует «идея». **[БОЙ]** соотношение idea:decision сигналов ≈ **13:1** на реальных встречах (§9). **[ТЕСТ]** дешёвый flash усиливает дубль и рвёт большой транскрипт.

## 2. Различитель (инвариант, на нём строится всё решение)

**Идею от решения отличает ровно одно — состоялся ли АКТ ПРИНЯТИЯ предложения** («решили / договорились / окей, делаем / берём / принято / утвердили», в т.ч. отказ «решили НЕ делать»). Без акта принятия («давайте / предлагаю / может быть / хорошо бы / если бы / подумаем») — это идея/предложение. Личное «я сделаю …» — это commitment (отдельный класс).

Подтверждение инварианта:
- **[ТЕСТ]** держится во всех прогонах PRO/flash.
- **[ИНДУСТРИЯ]** dialogue-act теория явно разделяет *proposal*, *acceptance* (backward-looking accept) и *commissive/commit*; в meeting-NLP (AMI corpus) решение детектируется по сигналам согласия — то есть именно «proposal + acceptance».
- **[ИНДУСТРИЯ]** ADR: «proposed» = ещё обсуждается, не в силе; «accepted» = в силе. То есть идея и решение — две стадии одного объекта, граница = принятие.

## 3. Целевая модель (куда двигаемся) — ADR-выровненный жизненный цикл

«Идея» = решение в статусе **«предложено»**; принятие лишь переводит статус в **«принято»**; отказ → «отклонено», отсрочка → остаётся «предложено»/«отложено», замена → «вытеснено» со ссылкой. Это 1:1 со стандартом ADR (proposed → accepted → rejected → superseded) **[ИНДУСТРИЯ]** и снимает дубль по построению (нет второй сущности для дублирования) **[ИНФЕРЕНС из ТЕСТ: дубли 11→0, как только перестаём плодить два объекта]**. Связь «идея→стало решением» — это смена статуса + ссылка-цепочка (decision-log «эволюция мышления») **[ИНДУСТРИЯ]**.

### Ф5. Структурная унификация: статус-жизненный-цикл (ADR) `[ИНДУСТРИЯ + ИНФЕРЕНС → бой]` `[x]`
**Цель:** «идея» без принятия = `Decision(status=proposed)`; принятие → `status=approved`; отказ → `rejected`; отсрочка → `proposed`/`deferred`; замена → `superseded` со ссылкой. Сущности уже почти готовы: `DecisionStatus` имеет `proposed/approved/rejected/implemented/cancelled/superseded` ([signal-type-label.ts:129](backend/src/modules/knowledge-core/prompts/signal-type-label.ts#L129)); `IdeaStatus` имеет `captured/in_discussion/accepted/...`.
**РЕШЕНО (Р-2): форма 5a** (доказательство из ограничений — см. §8). Ниже 5a (целевая) и 5b (отвергнута, для контекста):
- **5a (рекомендую, менее разрушительно):** оставляем сущность `Idea` для «сырых хотелок/запросов клиента», но при акте принятия идея **повышается** в `Decision(status=approved)` со ссылкой `Idea --realized_as--> Decision` (не дубль, а переход). Принятое-в-окне сразу пишется как `Decision(proposed→approved)`, минуя Idea.
- **5b (полный ADR):** единая сущность Decision со статусами; Idea — это её представление в статусе proposed. Больше миграции и правок downstream.
**Что трогает:** маппинг ingest→специалист (proposal→decision(proposed)), `specialist-3-3`/`3-6`, проекции/карточки, UI (показ статуса), клоны/дашборд-потребители.
**Доказательная база:** **[ИНДУСТРИЯ]** ADR — точный аналог; **[ИНФЕРЕНС]** A/B показал, что отказ от второго объекта убирает дубли без компромисса. **Проверка — в бою** (§5): дубли=0, реестр решений наполняется, idea:decision-перекос выправляется.
**Выкат:** ship-and-observe; при риске — за kill-switch (аварийный рубильник, не «дефолт OFF»).

### Ф6. Сверка idea↔decision в рамках встречи `[ИНДУСТРИЯ + reuse]` `[x]`
**Цель:** если в одной встрече есть idea-блок и decision-блок про один предмет — связать (`realized_as`/`supersedes`) и показывать ОДНУ карточку с историей, а не две (decision-log «эволюция мышления» **[ИНДУСТРИЯ]**).
**Reuse:** механизмы уже есть — `idea-cluster-merge`, `decision-supersede-detect` (KNN по эмбеддингу/цитате) — расширить на кросс-тип idea↔decision.
**Приёмка/бой:** падение числа «карточка и в идеях, и в решениях» в реальном графе (§5).

### Ф7. (Опция) комбинированный специалист с правом переноса `[ИНФЕРЕНС → бой]` `[x]`
**Факт:** `specialists-combined` ([specialists-combined.prompt.ts](backend/src/modules/knowledge-core/prompts/specialists-combined.prompt.ts)) видит idea и decision вместе, флаг `SPECIALISTS_COMBINED_ENABLED` OFF.
**Изменение:** включить + переписать инструкцию «не доверяй ярлыку слепо: если граница спорная — реши сам и положи в нужный массив» (право переноса idea↔decision в одном проходе). Плюс — дешевле (в эксперименте Б+ был в 3.7× дешевле раздельных).
**Доказательная база:** **[ИНФЕРЕНС]** combined видит оба класса разом → может убрать дубль/misroute в одном вызове. **Проверка — в бою**; держать как kill-switch.
**Зависимость:** не отменяет Ф5 (без статуса дубль/потеря просто переедут внутрь combined).

## 5. Наблюдение в бою (как смотрим, что сыграло)

После каждого выката — read-only `diag graph --meeting <id>` по новым встречам тенанта (и по svmazur как эталон-до). Метрики и цели:
- **Дубли** (блок, давший И idea-, И decision-карточку на один предмет): цель **→ 0** (база: PRO 11/37 синтетика; в бою — ручной обзор карточек).
- **`gap decision:N→0`** (решение увидено, не материализовано): цель **отсутствует** (база: «Роман» 3→0).
- **Соотношение idea:decision** материализованных: цель — выправляется к реалистичному (база ≈13:1; ждём роста доли решений после Ф1+Ф3+Ф5).
- Регрессия экстракторов: настоящие идеи по-прежнему ловятся (idv-ab.ts B2 = 3/3).

## 8. Принятые решения (развилок для владельца НЕТ — решено автором + доказано)

**Р-1 — модель на развилке → `deepseek-v4-pro`.** Доказательство: прогнал три модели на одном наборе. flash — дубли + обрыв на большом тексте (хуже). `deepseek-v4-pro` — дубли 0, без обрыва, верно ~95%. `gpt-5.4` (proxy, crux+big ×2) — верно 21/22, дубли 0, потери 1 → **ничья** с pro по качеству. Тай-брейкер при равном качестве: цена (deepseek-v4-pro дешевле в ~5–12×) + уже prod-primary + без нового провайдера/data-class → **deepseek-v4-pro**.

**Р-2 — форма структурной унификации → 5a (промоут idea→decision со ссылкой, сущность Idea сохраняем).** Доказательство из ограничений (структуру не A/B-тестируют, выбор доказывается инвариантами):
1. **Семантика:** не каждая идея — «предложенное решение». Клиентские запросы и сырой брейншторм часто НЕ доходят до выбора — это деманд-сигнал, не решение. `[ИНДУСТРИЯ]` idea-management = ранняя стадия воронки (многое не выбирается); ADR моделирует именно РЕШЕНИЯ, а не «все идеи». 5b (всё в Decision) — семантический перебор.
2. **Радиус поражения/обратимость:** 5b = единая сущность, демонтаж/слияние таблицы Idea → большая миграция, переписывание ВСЕХ потребителей Idea (карточки, деманд-сигнал, дашборд), тяжёлый откат. 5a аддитивна (ребро + путь промоута), Idea остаётся, **обратима** → совместима с ship-and-observe.
3. **Переиспользование:** 5a опирается на уже существующие `decision-supersede-detect` / `idea-cluster-merge` (ребро `realized_as`), 5b их частично выбрасывает.
→ При равном целевом эффекте (дубли по построению = 0) 5a дешевле, безопаснее и семантически точнее.

Полный набор: Ф1–Ф4 — доказаны тестом, дешёвые, без флагов; Ф5–Ф6 — структура и сверка, выровнены по индустриальному стандарту ADR и decision-log-практике, выкатываются и наблюдаются в бою; Ф7 — опция combined под kill-switch.
