# 2026-07-03 — `costRub` пишется, hard-cap бюджета технически способен сработать

## Что было поставлено

Первая из трёх независимых vNext-фич, вынесенных при закрытии родительского ТЗ `llm-providers-models-routing-admin` (реестр не-сделанного, строка 284): `AiUsageLogService.record()` никогда не писал `AiUsageLog.costRub` → `BudgetGuardService.getMtdRub()` суммировал пустую колонку → `mtdRub` всегда 0 → жёсткий лимит бюджета (`llm.budget.enforce_enabled`) физически не мог сработать, даже если бы владелец его включил.

Полный цикл: `solution-blueprint` (архитектура человеческим языком, одобрена) → `tz-author` (ТЗ с двумя проходами + challenge-loop) → `tz-orchestrator` (реализация фаза за фазой). Владелец выбрал: делать оба фикса разом (запись при вставке + fallback при чтении), `enforce_enabled` не включать — это отдельное решение (сумма + поведение).

## Как решал

**Архитектура (`plans/architecture/2026-07-03-llm-budget-cost-rub-hard-cap-fix.md`):** нашёл при разборе, что у владельца сегодня вообще нет UI-экрана для установки суммы лимита организации (эндпоинт `PATCH /admin/orgs/:id/budget` есть, фронт не подключён) — зафиксировал как отдельный, не-в-scope пробел, не стал его чинить заодно.

**ТЗ (`plans/tz/2026-07-03-llm-budget-cost-rub-hard-cap-fix.md`):** ключевое техническое решение — не копировать грубый fallback `OrgEconomicsCron` (`if (sum(costRub)===0) rub = sum(costUsd)*fxRate`), потому что в переходный месяц после этого фикса будет смесь старых NULL-строк и новых заполненных — суммарная проверка «весь ноль» перестанет срабатывать и молча занизит результат. Вместо неё — построчный `COALESCE("costRub", "costUsd"*fxRate)` через `$queryRaw`. Второе решение — вынести `CurrencyRateService` из `AdminModule` в отдельный `CurrencyRateModule`, чтобы `AiModule` не тянул весь `AdminModule` целиком (по образцу уже существующего `EmbeddingsModule`).

**Реализация (tz-orchestrator, 3 фазы, суб-агенты `general-purpose` + независимая приёмка на каждой):**
1. `d066ed43` — `CurrencyRateModule` (новый файл), `AdminModule`/`AiModule` перепроводены.
2. `621ab6c8` — `AiUsageLogService.record()` пишет `costRub`, best-effort, fail-open.
3. `31e1cc55` — `BudgetGuardService.getMtdRub()` на `$queryRaw` с построчным `COALESCE`.

На каждой фазе: `git diff` сверен построчно с контрактом ТЗ до коммита, `bun run typecheck` + целевой `vitest` прогнаны САМИМ оркестратором (не со слов суб-агента). После Фазы 3 — полный прогон `bunx vitest run src/modules/ai/services` (весь модуль) — 49 файлов / 506 тестов, регрессий не найдено.

## Что вышло

Все 3 фазы реализованы, закоммичены на ветке `fix/invite-password-existing-user-multi-org` (правило проекта — не плодить ветки, работать в текущей не-dev ветке). Typecheck/lint/vitest зелёные на каждом шаге и после интеграции. Push не делался — ждёт отдельного подтверждения владельца.

`second-brain/04_не-сделано/README.md` — строка 284 перенесена из «Открыто» в «Закрытые (архив)». `docs/operations/feature-flags.md` пункт 1 — добавлена пометка, что данные для hard-cap готовы (само решение владельца о сумме/поведении осталось открытым).

## Чему научился

- Слепое копирование существующего "похожего" паттерна (`OrgEconomicsCron`'s суммарный fx-fallback) без анализа граничных условий (переходный период со смешанными данными) — тихая ловушка: код выглядит правильным и проходит поверхностную проверку, но занижает результат именно в момент, когда он важнее всего (первый месяц после фикса).
- Модульная топология NestJS — не мелочь: перед тем как «просто заимпортировать сервис из другого модуля», стоит проверить направление зависимости (`AdminModule`↔`AiModule`) — выделение в общий листовой модуль (без зависимостей от обоих) дешевле, чем импорт целого гигантского модуля или, тем более, будущий цикл.
- `tz-orchestrator`: независимая верификация оркестратором (не доверяя отчёту суб-агента) один раз реально поймала бы регрессию, если бы она была — здесь всё совпало, но сам процесс (re-Read diff + свой прогон typecheck/vitest) стоит того по времени.
