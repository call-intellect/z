# Разбор подсистемы «Уведомления / Уточняющие вопросы (probe) / Модерация»

> Дата: 2026-06-10. Аналитика по живым находкам владельца (раздел «Уведомления» = `/me/notifications`, источник — proactive/probe/moderation) + код.
> Это **аналитика для ТЗ** (код не правился). ТЗ на исправление — отдельным файлом.

## Симптомы (что видит пользователь)

1. Заголовки уведомлений — сырые коды: `proactive.notification`, `checkin.prompt`, `operations.daily_digest`, `issue.mention` (вместо русских названий).
2. Текст вопроса/уведомления технический: «Отдел … не связан ни с одним **FunctionalDomain**», «**CompanyProfile** без **Mission / Vision / Strategy**: «cmpnflrfy…»», «На проверке карточка **knowledge_profile** cmpzl0mf… (уверенность 77%) — уровень: **light**», «У **chydo_002** обнаружена экспертиза …».
3. Ответ пользователя показан как сырой JSON: `{ "response": "техический специалист настя" }`.
4. **Вопросы приходят не тому пользователю**: вопрос про сотрудника X падает владельцу/другому админу; round-robin раскидывает вопросы про разных людей по разным админам.

## Корни (по коду)

### A. Адресация (самое серьёзное)
- `probe-dispatcher.worker.ts:124-137` — получатель = **первый** из `ProbeEvent.recipientCandidates` (round-robin). Диспетчер сам не знает, «про кого» вопрос.
- `recipientCandidates` задаёт **эмиттер** probe-события. Подтверждено: `consistency-checker.cron.ts:96` `findOwnerCandidates(org.id)` → gap-правила (R1–R6) шлются **владельцам**. Эмиттер скилл/экспертизы (probe «обнаружена экспертиза») — по тому же паттерну кладёт привилегированных кандидатов, не самого сотрудника-субъекта (нужно проверить конкретный эмиттер skill-trait).
- **Итог:** вопрос «про экспертизу chydo_002» приходит владельцу; вопросы про разных людей размазываются по админам. Это и есть «приходит не тому».
- **Как надо (варианты для ТЗ):**
  - V1 (рекоменд.): probe «про сотрудника X» (skill/expertise/profile) → адресовать **самому X** (само-подтверждение), fallback — руководителю отдела X. Структурные gap-правила про компанию (R6 CompanyProfile, структура) → владельцу/админу (это их зона) — но с человеческим текстом.
  - V2: маршрут по типу probe (таблица reason→audience).
  - Проверить: что эмиттеры реально кладут в `recipientCandidates` (skill-trait projection, consistency-checker, proactive-insights) — это место правки.

### B. Технический текст (англ. + ID)
- `consistency-checker.cron.ts:57-64 RULE_DESCRIPTIONS` — формулировки с жаргоном: «CompanyProfile без Mission / Vision / Strategy», «Артефакт (Document) без процесса-источника», «Шаг процесса без owner Role». Эти строки уходят в `payload.message` probe-события.
- `probe-dispatcher.worker.ts:213-214` — fallback `formulate()` берёт `payload.message` **дословно** (когда LLM probe-formulate не отработал/недоступен) → технический текст виден как есть.
- Сырые `KNOWLEDGE_PROFILE`/`knowledge_profile`/`light`/cuid в уведомлении модерации и `chydo_002` (хэндл вместо имени) — эмиттеры вставляют тип ресурса/уровень/ID/логин вместо человеческих имён.
- **Как надо:** (1) `RULE_DESCRIPTIONS` + шаблоны модерации/скиллов — человеческий русский без названий сущностей-классов; (2) ID/хэндл → резолвить в имя (название отдела, ФИО сотрудника, название карточки); (3) `probe-formulate` промпт обязан выдавать простой русский и НЕ эхоить сырые типы/ID/логины; fallback тоже человеческий.

### C. Заголовки-коды
- `frontend/src/domain/conversational.ts:84 EVENT_TYPE_LABELS` содержит только `probe.question`. Все прочие (`proactive.notification`, `checkin.prompt`, `operations.daily_digest`, `issue.mention`, модерация…) → fallback на сырой код (`conversational.ts:95-96`).
- **Как надо:** заполнить словарь типов уведомлений → RU (или отдавать готовый заголовок с бэка).

### D. Ответ как сырой JSON
- `frontend/app/(authenticated)/me/notifications/NotificationsClient.tsx:433` — `JSON.stringify(n.responsePayload, null, 2)` в `<pre>`.
- **Как надо:** показывать `responsePayload.response`/`.text` обычным текстом («Ваш ответ: …»).

### E. Сырой контекст
- `NotificationsClient.tsx:338-355` рендерит `payload.context` / `payload.title` дословно — туда и попадает технический текст из (B). Чинится в корне (B), но стоит и на фронте не показывать пустые/служебные поля.

## Рекомендация по объёму ТЗ

Это **одна подсистема** — чинить её отдельным ТЗ (адресация + человеческие тексты + словарь заголовков + рендер ответа), а не точечно. Самый приоритетный пункт — **A (адресация)**: это не косметика, а «вопросы про людей приходят не тем людям». Связано с [[knowledge-access-groups]] (кто что видит) — но это отдельный механизм (адресация probe ≠ доступ к графу).
