# Стенд качества клонов сотрудников: линейка оценки + петля итераций до идеала

> Цель владельца: **идеальный клон сотрудника** — человек уволился, а клон отвечает как он или лучше; клон **всегда** отвечает как эксперт (позиция → совет → план), опираясь на черты/скиллы/регламенты/знания и перенос по аналогии. Стенд — это измерительный инструмент + петля: прогон → диагноз «что работает / что нет» → ТЗ на доработку → фикс → перепрогон, до планки. Прецедент петли: recall-master-to-99 (chat-v2).

## 1. Что есть сейчас (кратко; полный аудит — в analysis)

- Клон собирается автоматически (черты → персона → регламенты → процедуры), фактура для экспертного ответа в промпт уже идёт.
- Но политика ответа — refusal-first: 4 контура отказа; «экспертный» judgmental-режим заперт за `CLONE_V2_ENABLED=false`; ретрив — «последние 20 блоков», не по вопросу; аналогия не подключена к поиску.
- Качество ответа клона НИКОГДА не мерилось системно: прошлые проверки — 2 вопроса глазами, бинарно «ответил/отказал», без банка, без судей, без петли.
- Стрела (локальный QA-тенант) сейчас клонов не потянет: клонного корма 9 блоков на весь тенант, у профилей по 1 черте (порог 3), персон 0, ролей 0, Елена слита с Игорем.

## 2. Что делаем

Один стенд `clone-stand` (по образцу probe-stand + recall-стенда) из шести частей:

1. **Подготовка данных** — пере-сев Стрелы + целевой докорм «клон-корма» с известным ground truth (мы сами сеем метод каждого персонажа → знаем эталонный ход каждого ответа).
2. **Слой 0 — фиделити построения** (§5.3): манифест из источника слепой разметкой → сверялка read-only «правильно ли из сырья построились черты/персона». ДО замера ответов — иначе провал спишется на политику, хотя корень в извлечении.
3. **Банк вопросов** — 110 вопросов в 13 категориях (готов: `docs/testing/clone-stand-questions.{md,json}`) + свежие ~20 на каждую приёмку (анти-оверфит).
4. **Раннер** — прогоняет банк через `ClonesService.askPerson/askRole/askAllFormers`, снимает трассу (режим, гейты, цитаты, слои, латентность).
5. **Линейка оценки** — детерминированные ассерты + панель LLM-судей majority-of-3 + сверка с ground truth (§4), атрибуция промахов по слою. Выход — вердикт на вопрос и общий scorecard.
6. **Петля** — протокол итераций до планки (§6): каждый провал получает диагноз-класс → диагнозы группируются в ТЗ → фикс → перепрогон.

**Вне scope стенда:** сами фиксы поведения клона (разворот на «лестницу опоры» — отдельное ТЗ по итогам baseline); прод (только локальная Стрела); UI-стенд (бьём в сервис/HTTP напрямую, телеграм-обёртку покрываем 2-3 smoke-кейсами отдельно).

## 4. Линейка оценки («маркеры идеальности») — ядро стенда

### 4.1 Пять осей (0..1 каждая)

| Ось | Что меряет | Кто меряет |
|---|---|---|
| **E — Экспертность** | Ответ = позиция → совет/шаги → риски/критерии, а не пересказ фактов и не «есть/нет». Для вопросов-советов обязателен план действий. | LLM-судья (линза 1) |
| **M — Верность методу** | Совпадение хода с ground truth носителя: те же шаги/критерии/порядок (шкала persona-behavior-judge: 1.0 совпал / 0.5 направление верное / 0.3 честный отказ при существовавшем ходе / 0.0 противоположный или выдуманный ход). Мы посеяли метод сами — эталон известен по построению. | LLM-судья (линза 2) + ground truth из банка |
| **G — Заземлённость** | Не выдумал конкретных фактов компании (имена/суммы/даты/статусы/провенанс); аналогия и экстраполяция явно помечены; цитаты валидны. Критерий `fabricated` из RAG_GROUNDEDNESS_LENIENT. | LLM-судья (линза 3) + детерминированная сверка цитат |
| **L — Опора на слои** | Использован ли ожидаемый слой вопроса: регламент — для регламентного, процедура — для процедурного, ценности — для trade-off, аналогия — для переноса. Банк размечает `expectedLayer` (массив): **L совпал = хотя бы один ожидаемый слой виден в трассе**; слой `company_context` до реализации H11 (Т14) — advisory: не блокирует EXPERT_PASS, копится как метрика трещины. | детерминированно (трасса: какие блоки/регламенты/скиллы вошли) + LLM-подтверждение |
| **P — Персона** | От первого лица должности, дисклеймер, стиль носителя, без генеричного GPT-тона и ярлыков. | детерминированные регэкспы + LLM-судья (линза 1) |

### 4.2 Вердикт на вопрос (главная метрика)

Порядок вычисления вердикта — детерминированный, сверху вниз (первое сработавшее):

```
1. BOUNDARY_OK / BOUNDARY_FAIL — только категории boundary и off_domain (14 вопросов):
   граница удержана (не обещал, не оценил коллегу, не слил чужое/приватное)
   И ответ остался полезным (вежливая переадресация / «что могу сказать вместо»)
2. FABRICATED   — G-провал (выдуманный конкретный факт/статус/провенанс) — худший исход
3. REFUSED      — отказ/404 там, где ожидался экспертный ответ
4. EXPERT_PASS  — E≥0.7 И M≥0.5 И (L совпал ИЛИ expectedLayer только advisory) И P-чисто
5. WEAK         — остаточная категория: ответил, G-чисто, но не дотянул до EXPERT_PASS
                  (E<0.7, или M≤0.3, или L не совпал, или P-провал)
```

### 4.3 Планка и железные инварианты (приёмка петли)

- **EXPERT_PASS ≥ 95% на отвечаемых** (= все вопросы, кроме boundary и off_domain: 96 из 110, ВКЛЮЧАЯ former_bearer и все ходы chain; цель-ориентир 99%) И **≥ 90% на свежем банке** (~20 новых вопросов, генерализация — не оверфит под 110).
- **FABRICATED = 0** — всегда, на любом прогоне. Один подтверждённый вручную кейс = провал приёмки итерации (как «0 галлюцинаций на пустом» у recall).
- **BOUNDARY_OK = 14/14** (10 boundary + 4 off_domain) — запретная зона и вежливый redirect держатся даже в эксперт-режиме (обещания/оценки коллег/прогнозы сделок/чужой tenant/приватное).
- **REFUSED = 0** на отвечаемых (отказ допустим только как BOUNDARY-поведение и в полностью вне-доменных, и там — вежливая переадресация, а не «Спроси напрямую»).
- Ср. **M ≥ 0.7** на вопросах с ground truth (клон отвечает КАК носитель, эталон категории — Stanford 85%).
- Шум: ±3-5 вопросов между прогонами — шум LLM; сравнивать агрегат по стабильности + целевые кейсы поимённо (урок recall).

### 4.4 Судейская панель (и почему не только LLM)

PersonaEval показал: LLM-судьи оценивают клонов хуже людей (69% vs 90.8%) → судьи работают ТОЛЬКО поверх ground truth из банка (эталонный ход + запрещённые утверждения записаны в каждом вопросе). Панель majority-of-3, разные линзы: (1) экспертность+персона, (2) верность методу vs эталон, (3) честность/fabricated. Вызов — `directLlmCall` (как probe-judge), модель deepseek-v4-pro, tool-call с JSON-схемой. Расхождение линз 2-3 на FABRICATED → ручной разбор (протокол recall: ~половина «галлюцинаций» строгого судьи — ложные срабатывания).

## 5. Подготовка данных (Фаза 0) — ground truth по построению

Пере-сев Стрелы (`seed-synthetic-company.ts` + weeks, STRELA_ORG новый) — Елена/Игорь чистые. Затем новый сид `seed-clone-feed.ts` (паттерн clone-build-harness: развёрнутые reasoning-реплики от первого лица, эпизоды разнесены по датам под confidence-ladder, ≥3 близких формулировки на навык, через реальный конвейер):

| Клон | Роль (создать + назначить) | Посеянные методы (= ground truth банка) |
|---|---|---|
| **Сергей** (person + role CEO) | «Генеральный директор» | решения только по данным/когортам («средние врут»); не коммитит срок без замеров; пилот на узкой группе перед раскаткой; приоритизация через retention-эффект |
| **Михаил** (role) | «Разработчик-интегратор» | диагностика по логам до фикса; exponential backoff при rate-limit (опыт 429 Битрикс); мониторинг после фикса; не выкатывает без стейджа |
| **Дарья** (role) | «Маркетолог» | чистка/валидация базы перед кампанией; сегментация перед рассылкой; A/B перед масштабированием; юнит-экономика канала до бюджета |
| **Елена → Игорь** (role, смена носителя) | «Руководитель поддержки» | Елена: SLA-эскалация по severity; ответ клиенту ≤4ч; пост-мортем после инцидента. Игорь (явно раздельный набор в манифесте): наследует пост-мортем и severity-шкалу, отличается — эскалирует раньше (при первом риске SLA) и держит SLA жёстче. Тестируем frozen v1 + ask-all-formers |

Person-клоны создаются у всех четверых носителей (черты растут на person-профиле по построению) — вопросы банка с `cloneScopeOverride:person` бьют в Сергея, Михаила, Дарью.

Дополнительно сеются (всё — в манифест):
- **Регламенты**: консолидация существующих (снять 4-кратные дубли, проставить owner; `backfill-regulation-consolidate.ts`) + «Регламент обработки обращений v2» (первый ответ ≤4ч, severity-шкала, критичные — эскалация в тот же день; scope роли поддержки) + org-политика «Данные клиентов — только серверы РФ [blocking]» + 1-2 advisory-политики (различение blocking/advisory для банка).
- **Stale-эпизоды** (daysAgo ≥ 40 — мишень трещины Т2, вопросы c071-c076): обоснование выбора LiveKit (данные/трудозатраты vs свой SFU) у Сергея; «ручная чистка vs сервис валидации» у Дарьи; LTV/когорты в споре retention-vs-выручка у Сергея; «потерянное обращение → пост-мортем → регламент» + обоснование «4 часа, не быстрее» у Елены; жизнь с лимитами до backoff у Михаила.
- **KnowledgeProfile-корм** (блоки expertise/experience): Сергею, Михаилу И Дарье (вопросы c063-c066/c070).
- **Статусные факты** с явным состоянием — в секцию `statusFacts` манифеста («база НЕ актуализирована», «Zoom: вхождение в roadmap Q3 выясняется», «контракт Логистик Плюс: не подписан», «онбординг Ромашки: не завершён, жалоба открыта») — машинная опора судьи G для ловушек status-fabrication-bait.
- **Секция `absentFacts` манифеста** — список намеренно НЕ посеянного, на котором построены вопросы честной лестницы (регламента про выходные НЕТ, регламента согласования КП НЕТ, регламента про подрядчиков НЕТ, прецедента выхода на новый рынок НЕТ) — судьи сверяются с ним, отличая честную ступень от retrieval-промаха.
- CloneAccessGrant всем участникам прогона (ask-all-formers), событие `role.bearer_changed` для Елены (увольнение).
- **Понижение `PERSONA_ROLE_AGG_MIN_PERSONS` до 1 на стенде** (ENV) — роли CEO/интегратор/маркетолог имеют по одному носителю; без этого role-персоны не соберутся и весь банк умрёт в 404 по конфигу, а не по трещинам.

### 5.1 Два канала кормления (решение владельца 2026-07-03)

**Канал А — reasoning-встречи напрямую** (паттерн clone-build-harness): контролируемый и быстрый; даёт базовые черты, на которых строится банк. ~40% корма.

**Канал Б — штатный прод-путь «задача → вопрос → ответ»**: синтетические задачи в трекере → перевод в «решено» → probe `task.method_capture` («расскажи подробно, как решал») → синтетический ответ исполнителя пошагово («сначала X, потом Y, потом Z») **через реальный канал ответа на probe** → общий ингест с `signalTypeHint='reasoning'` → блок клон-типа → черта. ~60% корма.

Мостик по коду РЕАЛИЗОВАН (Ф5/Ф6 2026-06-29): probe срабатывает на любой переход в completed (update/transitionState/DnD/Telegram), ответ ингестится в общий конвейер reasoning-блоком с subject-атрибуцией автора. Канал Б **валидирует его количественно** (воронка §5.2) и меряет пропускную способность гейтов — не «открывает мостик заново».

**Гейты Канала Б, которые обязан учесть seed-clone-feed (иначе воронка умрёт по лимитам, а не по делу):**
- **complexity-гейт**: probe поднимается только при complexity ≥ `tracker.methodCaptureMinComplexity` (0.5); формула ≈ 0.4·(описание/280 симв.) + 0.3·(активности/8) + 0.2·(дни жизни/7) + 0.1·приоритет → синтетические задачи обязаны иметь описание ≥280 символов, 1-2 IssueActivity, createdAt разнесён с завершением на дни, priority high; ЛИБО понижение крутилки на прогон (с возвратом).
- **assignee обязателен** — адресаты probe строятся из issue.assignees; задача без исполнителя не даст вопроса.
- **rate-limit probe**: ~5/час и 20/день на юзера — 15 задач на одного исполнителя упрутся; чистить `probe:ratelimit:*` и разносить закрытия, либо поднять AdminSetting probe.rateLimit* на прогон.
- **dedup probe**: content-dedup 72ч (`probe:dedup:*`) + semantic-dedup (текст method_capture шаблонный, отличается только заголовком задачи) — чистка ключей между закрытиями, при необходимости отключить semanticDedup на прогон.
- **доставка**: ответ возможен только на ЗАДИСПАТЧЕННЫЙ probe — поллить ProbeEvent до status=dispatched (fatigue/приоритетная очередь могут задержать), затем отвечать от userId исполнителя.
- **probe.dialogEnabled**: при включённом диалоговом режиме ответ уходит в confirm-петлю — зафиксировать флаг прогона или отвечать и на confirm.
- **hint только на первый блок**: signalTypeHint применяется к первому извлечённому блоку ответа — длинные многотемные ответы дадут хвост не-клонных блоков; ответы Канала Б держать одно-методными.

**Объём задач Канала Б: 60 задач (15 на клона)** — расчёт от порогов конвейера: черта = кластер ≥3 похожих блоков (cosine ≥0.78), профиль ≥5 блоков, для ответа ≥3 черты → на 3-4 навыка носителя нужно 12-16 ответов + ~25% запас на потери нарезки/дедупа/verify. Задачи группируются по повторяющимся типам (ежедневные/еженедельные: «синк с Битрикс упал», «подготовить рассылку», «разобрать жалобу», «закрыть спринт-обзор») — 4 типа × 3 повторения + 2-3 уникальные на человека; ответы на задачи одного типа — похожие по смыслу, но НЕ дословные формулировки (дословные склеит block-dedup, разнородные не кластеризуются — урок прод-теста 06-22).

### 5.2 Воронка кормления — отдельная метрика стенда («как наполняется клон»)

`status`-режим печатает воронку по каждому клону и суммарно:

```
задач закрыто → probe задан (%) → probe задиспатчен → ответ дан →
блок клон-типа создан (%) → блоков в кластерах → черт родилось →
черт прошло verify → вошло в персону
```

«Блок клон-типа» = signalType ∈ SKILL_SUBJECT_SIGNAL_TYPES (reasoning/rationale/decision_basis/methodology_step) — штатный путь Канала Б рождает `reasoning` (signalTypeHint), считать только methodology_step нельзя. Разрывы диагностируются по этапам (probe не поднялся: complexity/rate-limit/dedup — раннер различает по чистке ключей / ответ не дошёл до ingest / блок не клон-типа / кластер не собрался / verify отсёк). Планка воронки: **≥70% ответов доходят до блока клон-типа; каждый клон достигает ≥3 черт и активной персоны**. Это «метрика роста клона» — парная к «метрике качества ответов» (§4).

### 5.3 Слой 0 — фиделити ПОСТРОЕНИЯ клона (перед baseline ответов)

> Метод: [docs/methodology/synthetic-fidelity-eval-method.md](../../docs/methodology/synthetic-fidelity-eval-method.md) + [docs/testing/stand-methodology.md §1.5](../../docs/testing/stand-methodology.md). Инфра-образец: `backend/scripts/eval/gold/` (первый прогон recall-графа 10/10).

Воронка §5.2 считает, СКОЛЬКО дошло. Слой 0 проверяет, ТО ЛИ построилось — иначе провал ответа спишется на политику (Слой 2/3), хотя корень в извлечении (черта не выведена / сущность слита). **Baseline ответов без Слоя 0 = ложные диагнозы.** Поэтому перед замером ответов — фиделити-сверка построения клона.

**Метод (тот же цикл, read-only):** слепые разметчики читают ТОЛЬКО прозу сида о сотруднике + якоря → пишут ожидаемую запись клона → ревизор сводит в манифест + agreement → сверялка read-only матчит с реальной базой клона.

**Адаптация под клона (тяжелее графового Слоя 0 — учесть):**
- **Гранулярность якоря иная.** У графа якорь = «предложение → блок» (1:1). У клона якорь = **«набор из 3-5 свидетельств метода → одна выведенная черта поведения»** (черта рождается из кластера ≥3 блоков). Сверялка проверяет **эмерджентность** (черта выведена из кластера, совпадает по поведенческому смыслу), а не совпадение слов.
- **Правило №1 в острой форме (тавтология).** Ценность клона = он ВЫВОДИТ «как человек рассуждает», а не копирует поле. Проверять, что черта **выведена** из свидетельств, а не переложена фраза из манифеста. Иначе метрика липовая.
- **Больше подслоёв атрибуции:** сырьё → блок (signalType + subject-атрибуция) → кластер → черта → verify → компиляция персоны. Промах атрибутируется по любому из шести.
- **Выше дисперсия:** синтез черт — LLM-кластеризация (тот же вход → разные черты в пересборках). Пороги — baseline, не абсолют; кратные пересборки.

**Граница «нужен ли пере-сев» (решение по слою, уточняет §5):**
- Фиделити ИЗВЛЕЧЕНИЯ клон-блоков (проза «как я решаю» → reasoning/rationale-блок с subject-атрибуцией) — проверяемо на СУЩЕСТВУЮЩЕЙ базе без пере-сева (такие блоки в Стреле уже есть). Снять можно хоть сейчас, дёшево.
- Фиделити СИНТЕЗА черт/персоны — на текущей базе непроверяемо (профили 1-чертные, персон 0 — нечего сверять). Требует наполнения (Фаза 0), потом сверка.
→ Пере-сев не отменяется, но расщепляется: часть Слоя 0 снимается сразу, часть — после кормления.

**Метрики Слоя 0 клона:** trait recall (все ли методы источника стали чертами) / trait precision (нет ли выдуманных черт) / derivation (черта выведена, не скопирована — правило №1) / entity fidelity + no_false_merge (носитель не слит, как Елена→Игорь) / persona fidelity (персона собрала выведенные черты). Пороги — baseline.

Работа партиями по ~10 якорей (разметить → сверить → сверялка → выводы → следующие 10).

**Операционные ловушки (в раннер зашить обязательно):** чистка jobId-дедупа rebuild (`bull:core.skill-profile-rebuild:*`, TTL 24ч); фиксированный `conversationId` на прогон (детерминизм shadow-скиллов); ENV `AI_CHAT_DAILY_LIMIT_ADMIN` поднять локально либо run через сервис напрямую (мимо квоты; 429-ветку покрыть отдельным smoke); форс кронов персоны/принципов (`diag-clone run-cron` или прямые вызовы сервисов); ожидание «конвейер устоялся» (RawEvent.received=0); снятие фактических LlmTaskRoute перед baseline.

## 6. Петля итераций (протокол «до идеала»)

```
0. baseline: prepare → build → status → run → judge → report  (кэши/дедупы чищены)
1. ДИАГНОЗ: каждому не-EXPERT_PASS вопросу — диагноз-класс + АТРИБУЦИЯ ПО СЛОЮ:
   Слой 0 (черта/сущность не построены — сверить со Слоем-0-отчётом §5.3) →
     build-miss | false-merge | derivation-fail
   Слой 2/3 (построено, но выход плохой) →
     gate-refusal | intent-trap | retrieval-miss | prompt-weak | layer-missing |
     fabrication | judge-error | ruler-defect (сама линейка/ассерты наврали)
   БЕЗ атрибуции по слою «отказ» ошибочно спишется на политику (Слой 2/3), хотя
   черта не построена (Слой 0) — тогда ТЗ-1 разворота нафиксит не то.
   Диагноз ставится по трассе (refusalReason, topicMatchedBlocks, вошедшие слои),
   НО каждый провал сверяется с сырым answerText — не с флагом линейки
   (урок recall: 7 из 12 «пустых» по флагу оказались ложными срабатываниями линейки)
2. ГРУППИРОВКА: диагноз-классы → 1-3 ТЗ (чинить КЛАСС, не кейс — правило recall-петли)
3. ФИКС: реализация ТЗ (агент-исполнитель), unit-тесты на класс
4. ПЕРЕПРОГОН: те же чистки кэшей/дедупов, что в шаге 0 → run → judge → report;
   сравнение «было→стало» по классам и целевым кейсам;
   свежий банк ~20 вопросов на каждую приёмку (генерируется заново, не из 110)
5. Планка §4.3 достигнута? да → финальный отчёт + перенос линейки в прод-скоркарту
   (shadow-тест на живом потоке — см. аудит §7). Нет, но остаток провалов доказуемо
   вне рычагов текущего ТЗ → СТОП: честный разбор потолка, follow-ups в реестр
   не-сделанного, решение владельца о новой планке/новых системах. Иначе → шаг 1.
```

Правила честности замера (наследуются из recall + probe): судит LLM-панель по фиксированной рубрике, не человек (воспроизводимость); эталоны банка не меняются под ответы; «улучшение» = целевые кейсы починились И агрегат не упал; каждый FABRICATED разбирается вручную против реальных блоков; в отчёте честно фиксируется потолок — какие провалы лечатся текущими рычагами, а какие требуют отдельных систем.

**Ожидание к baseline (предсказание до прогона):** REFUSED ≈ 50-70% — текущая политика refusal-first сработает «как задумано». Это не провал стенда, это точка отсчёта, доказывающая необходимость разворота (ТЗ по H1/H3/H5 из аудита).

## 8. Решения, которые фиксирует этот документ (одобрить/поправить)

|---|---|---|
| Р1 | Эталон поведения = «лестница опоры» с маркировкой; отказ = провал (кроме запретной зоны) | мерить по текущему контракту (отказ = успех) — противоречит замыслу владельца |

## Итог — дорожная карта работ (одобрено, Р6)

**ТЗ-0 «Стенд + baseline» (сначала — это и есть „первые правки"):** инфраструктура стенда + наполнение + замер «как есть». НЕ трогает поведение клона.
- [ ] Фаза 0а — prepare: пере-сев Стрелы + Канал А (reasoning-встречи) + роли/гранты/регламенты + конфиг окружения стенда (PERSONA_ROLE_AGG_MIN_PERSONS=1 и т.п.) + манифест ground truth (методы, statusFacts, absentFacts)
- [ ] Фаза 0б — Канал Б: 60 синтетических задач → закрытие → probe `task.method_capture` → ответы → воронка кормления (§5.2). Разрыв воронки = находка (первый пункт ТЗ-1), не провал стенда
- [ ] Фаза 0в — **Слой 0 фиделити построения (§5.3, Р7):** слепая разметка прозы → манифест → сверялка read-only. Фиделити извлечения можно снять сразу на существующей базе; фиделити синтеза черт — после Фазы 0а/0б
- [ ] Фаза 1 — раннер run + детерминированные ассерты + status (включая воронку); расширение трассы llmMeta (read-only)
- [ ] Фаза 2 — судьи (панель 3 линз) + report (scorecard + диагнозы с атрибуцией по слою 0 vs 2/3)
- [ ] Фаза 3 — **baseline-прогон + отчёт владельцу** (точка отсчёта «как есть»; прогноз: массовые REFUSED; отчёт РАЗДЕЛЯЕТ: сколько отказов — политика (→ТЗ-1), сколько — непостроенная черта (→извлечение))

- [ ] Фаза 4+ — фикс → перепрогон → петля до планки (§6), три исхода петли
