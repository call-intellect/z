# Память о субъекте + самообучение — синтез

## 0. TL;DR для владельца

Твоя мысль распадается на **три слоя одной системы — «память о субъекте»**, и все три уже частично построены в Коре и **спят**:

| Слой | Субъект | Что уже есть в коде | Главный пробел |
|---|---|---|---|
| **1. Профиль компании** | вся организация | модель `CompanyProfile` (mission/vision/strategy + поля `sourceBlockIds`+`confidence` под авто-сбор) | авто-наполнения нет (cron создаёт пустышку); описание не подставляется в промпты |
| **2. Профиль сотрудника + маршрутизация** | человек / роль | `RoleProfile` (ролевой), `SkillTrait`/`SkillTraitConcept` (персональный, с embedding `vector(1536)`) | маршрутизации «задача без исполнителя → нужный человек» нет; роль людей не идёт в промпт (`role: null`) |
| **3. Выученная память уточнений** | сам ассистент | probe (вопросы), curation (accept/reject фактов), `*-supersede-detect` (конфликт фактов) | нет памяти «не переспрашивать дважды» (глоссарий/разрешённые неоднозначности) |

**Ключевой вывод состязательного рынка:** по всем трём направлениям и зарубеж, и РФ либо строят граф **без** связного текст-описания, либо генерят текст **разово без жизненного цикла**; авто-вывод компетенций из активности и обучение на правках без human-approval — **почти свободная ниша**. Кора уже стоит на нужном фундаменте (граф из событий) — надо достроить и **включить** три спящих слоя, а не строить с нуля.

## 1. Рамка проблемы (две конкурирующие формулировки)

**Формулировка A (узкая, «контекст для агента»):** агенты Коры (chat-v2, ассистент, извлечение задач/отчётов) не знают, *чем компания занимается* и *кто за что отвечает*, поэтому отвечают обобщённо и переспрашивают то, что уже знают. Метрика «решено»: доля ответов/задач без уточняющего вопроса; доля задач, поставленных на верного исполнителя без явного указания.

**Формулировка B (широкая, «петля самообучения»):** Кора не превращает реакцию людей (ответил на вопрос / принял / отклонил / поправил) в накапливаемое знание, поэтому не становится умнее со временем — повторяет одни и те же вопросы и ошибки. Метрика «решено»: снижение кумулятивного числа уточняющих вопросов и правок при росте объёма работы (кривая обучения уходит вниз).

**Кто страдает (роли Z):** рядовой сотрудник (лишние переспросы → бросает рефлекс пользоваться); руководитель/CEO (ставит задачу «в воздух», система не доводит до исполнителя); админ Org (вынужден вручную чистить логи и править промпты). Формулировка B — корневая (Iceberg): A — симптом отсутствия петли B.

## 4. Teardown-инсайты (что копировать, что НЕ копировать)

- **НЕ копировать слепо** статический org-параграф в SYSTEM ради «контекста компании» — лидеры держат контекст в RAG-grounding, потому что текст устаревает и раздувает токены. **НО** у нас есть нюанс (см. §6, вариант): короткий стабильный *org-capsule* (1 абзац: чем компания занимается + как себя называет) полезен именно для **тональности и самоидентификации** ассистента («я сотрудник компании X»), а фактура — через RAG. Это разные роли: capsule = «кто я», RAG = «что я знаю».
- **Копировать** у Mem0/Graphiti: ретрив-перед-записью + операции ADD/UPDATE/NOOP; bitemporal-инвалидация вместо delete (у нас уже есть `*-supersede-detect` — достроить).
- **Критическая поправка из `01`** (arxiv 2606.01435, verified): **свежесть факта решает код по `max(occurredAt)`, а не LLM** (LLM на длинном контексте деградирует 75%→61%; код +21 п.п.). LLM — только «тот же это факт?», победителя выбирает детерминированный код.
- **Копировать** у Workday/MS: skill-профиль = авто-инференс из активности + флаг provenance (AI-inferred серым vs Confirmed) — у нас `SkillTrait` уже «гипотезы» с confidence, это ровно тот паттерн.
- **Копировать** у CIPHER/TRACE: правило хранить как **сжатый текст** (вчетверо дешевле сырых примеров по токенам), ретрив k-ближайших, свёртка в промпт; reject — самостоятельный сигнал.
- **НЕ копировать** human-SME-реверификацию Guru — у нас правило «без human-approval»; нужен авто-судья + A/B.

## 6. Матрица вариантов + рекомендация (по каждому слою)

### Слой 1 — где живёт «описание компании»
| Критерий | A: текст-параграф в SYSTEM | B: дериват-граф + RAG-grounding | C (рекоменд.): гибрид — короткий org-capsule в SYSTEM + фактура через RAG |
|---|---|---|---|
| Свежесть | плохо (устаревает) `02` | хорошо | хорошо (capsule редко меняется, факты live) |
| prompt-cache (правило Коры) | ломает при правке | стабильно | стабильно (capsule = стабильный префикс) |
| Самоидентификация ассистента | да | слабо (нет «кто я») | да |
| Стоимость токенов | растёт | низкая | низкая |
| Реюз кода Коры | — | граф есть | `CompanyProfile`+граф есть |
**Рекомендация C:** агент-компилятор раз в N часов собирает `CompanyProfile.summary` (3-5 абзацев) из графа с провенансом; в SYSTEM ассистента/chat-v2 идёт **сжатый capsule (1 абзац «компания X занимается …»)** для тональности, фактура — через текущий RAG. Закрепление владельцем перекрывает авто. Источник: `02` (RAG vs static), правило cache-friendly.
> **Поправка red-team (`98`, важно):** capsule НЕЛЬЗЯ вставлять внутрь начала стабильного SYSTEM — иерархия инвалидации кэша (tools→system→messages) означает, что каждая авто-регенерация параграфа обнулит prompt-cache у ВСЕХ запросов ассистента (ломает наше же cache-friendly правило). Решение: capsule — **отдельный cached-блок ПОСЛЕ стабильного SYSTEM** (десятки токенов, меняется редко), всё динамичное — только RAG; гейт качества — **cache hit-rate ≥60%**. Перегенерировать capsule не чаще, чем реально меняется суть компании (не по расписанию ради расписания).

### Слой 2 — уровень профиля и матчинг
| Критерий | A: только ролевой | B: только персональный (SkillTrait) | C (рекоменд.): двухуровневый (роль-приор + человек при ≥2 носителях) |
|---|---|---|---|
| Точность выбора при 2 носителях | нет | да | да |
| ПДн 152-ФЗ | безопасно | риск (профилирование) | безопасно (роль-приор) + гибрид-гейт |
| Cold-start | хорошо | плохо | хорошо |
| Совпадение с принципами Коры | да (клоны ролевые) | конфликт | да |
**Рекомендация C** + матчинг **гибрид**: pgvector top-K → LLM-арбитр (DeepSeek) → исполнитель+confidence+объяснение; результат — **всегда предложение человеку в один тап**, не авто-назначение. Источник: `03`.
> **Поправка red-team (`98`, жёсткая):** авто-назначение СНЯТЬ полностью. (1) Юр-блокер verified — ст.16 152-ФЗ прямо запрещает решения исключительно на авто-обработке, затрагивающие интересы субъекта, без письменного согласия + права на возражение. (2) SkillRouter (arxiv, verified): близкие конкуренты-навыки («канцелярия≠закупки≠АХО» — ровно hard-distractors) роняют точность −18…−30%; при >30 навыков деградация уже идёт, 200 навыков → ~20%. Поэтому матчинг строить **двухступенчато: явные теги навыка/отдела = hard-gate (если есть) → pgvector+LLM = подсказка человеку**, финальное назначение — действие человека. На v1 чистый semantic без тегов годится только как «предложить кандидата», не как решение.

### Слой 3 — как учить
| Критерий | A: human-approval каждого правила | B (рекоменд.): авто composite-judge + A/B, human kill-switch | C: чистый онлайн без судьи |
|---|---|---|---|
| Масштаб (30 чел «соглашаются не глядя») | проваливается | ок | ок |
| Защита от самоотравления | да (но не работает на 30) | да (judge+вес+регресс) | нет |
| Совпадение с принципом Коры | конфликт | да | частично |
| Риск дрейфа | низкий | средний (управляем) | высокий |
**Рекомендация B:** правило выводится агентом из сигнала, активируется только если composite-judge (не self-eval) не даёт регресса; вес подтверждений±, TTL/decay, регресс-набор старых правил, per-Org изоляция; human — аварийный выключатель. Источник: `04`.
> **Поправка red-team (`98`):** «composite-judge → сразу прод» ОПРОВЕРГНУТА. (1) На 30 пользователях offline-A/B статзначимости не даст — заменить на **canary/shadow-режим + авто-rollback по ВНЕШНЕЙ метрике** (объём правок/переспросов до и после правила), а не по самооценке. (2) LLM-судья systematically self-preference/verbosity/position-biased (verified) — судья должен быть **ансамблем и НЕ совпадать с генератором правила**. (3) Closed-loop деградирует (entropy decay/variance amplification, verified) — обязательны регресс-набор + decay + tenant-изоляция уже в v1. (4) Конфликт правил решать **перезаписью/supersede по `max(occurredAt)`** (как mem0), не голосованием LLM. Это совместимо с правилом «без human-approval»: человек остаётся только kill-switch, активацию гейтит метрика, а не одобрение.

## 6-bis. Итог состязательной перепроверки (red-team, `98`)
| Рекомендация | Вердикт | Главная поправка |
|---|---|---|
| Слой 1 — org-capsule в SYSTEM | **ослаблена** | capsule = отдельный cached-блок ПОСЛЕ стабильного SYSTEM, не в его начале; гейт cache hit-rate ≥60% |
| Слой 2 — skill-маршрутизация | **ослаблена, авто-назначение снято** | теги = hard-gate → semantic = подсказка человеку; финал — действие человека (152-ФЗ ст.16 verified) |

## 10. Открытые вопросы владельцу (каждый с рекомендацией)
1. **Очерёдность ТЗ.** Рекомендую **3 → 1 → 2** (сначала петля самообучения как корень, затем профиль компании как самый дешёвый и со свободной нишей, затем маршрутизация как самый рискованный по ПДн). Почему: слой 3 — корневая боль (B), слой 1 — быстрый видимый эффект на готовом фундаменте, слой 2 — требует решений по ПДн и порогам.
2. **Слой 1 — capsule в SYSTEM или чистый RAG?** Рекомендую гибрид C, но capsule — **отдельным cached-блоком после стабильного SYSTEM** (поправка red-team), фактура через RAG. Почему: самоидентификация «ассистент = сотрудник компании» нужна, но регенерация внутри SYSTEM обнулила бы кэш всем запросам.
3. **Слой 2 — авто-назначение или предложение?** Рекомендую **никогда не авто, всегда предложение в один тап**, и матчинг через теги-hard-gate → semantic-подсказка. Почему: ст.16 152-ФЗ (прямой запрет, verified) + деградация semantic-матча на близких компетенциях.
4. **Слой 3 — что считаем сигналом на v1?** Рекомендую начать с probe-ответов + reject задач (самые чистые сигналы), correct/edit-distance — во вторую волну. Почему: edit-distance требует аккуратной инфраструктуры черновик→финал, probe-ответы уже структурированы.
