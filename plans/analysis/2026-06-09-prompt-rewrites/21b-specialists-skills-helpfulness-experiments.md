## 1. `skill-trait-detect` — извлечение одной черты рабочего поведения

- **Файл:** `backend/src/modules/knowledge-core/prompts/skill-trait-detect.prompt.ts`
- **Контракт:** json_schema strict «`skill_trait_detect_v1`» (`required: category, statement, confidence, sourceBlockIds, firstObservedAt, lastConfirmedAt`). Модель — deepseek-v4-pro.
- **Применимые измерения:** ПРАВИЛО-ЛЮДИ (гипотезно, без приговоров — уже заложено, усилить); A2 (только из цитат — уже есть, подчеркнуть); A3 (опора на дословную цитату); D1:low (противоречие в цитатах → confidence=low и контекст-зависимость в statement).
- **Код-сверка:**
  - SYSTEM оборачивается `withAsrNote(withEdgeCasePolicy(...))` — ASR-нота и edge-case-политика уже есть в коде, в SYSTEM-текст не дублирую.
  - Вызов в `specialist-3-7-skill.service.ts` применяет `withInjectionGuard` + `wrapUserData` при флаге `isPromptInjectionGuardEnabled()` — анти-инъекция (E2) на call-site **уже есть**, в текст не добавляю.
  - USER-шаблон: сотрудник, даты, цитаты — всё переменное передаётся в конце user (cache-friendly).
  - Гипотеза аудита о контракте подтвердилась.

#### БЫЛО (SYSTEM, сжато — без примеров; оригинал в файле)
```
Ты — knowledge-инженер. Тебе дают набор цитат из встреч одного сотрудника, где он объясняет ПОЧЕМУ принимает те или иные решения.
Твоя задача — извлечь одну черту его рабочего поведения. Отвечай строго в формате JSON по предоставленной схеме.

ВАЖНО — правила формулировок:
1. КАТЕГОРИЯ — эмерджентная (короткая фраза-метка 3–6 слов)...

3. CONFIDENCE — low (1–2 наблюдения), medium (3–5 в разных встречах), high (6+ за разные даты).

- Не делай выводы о компетенциях/знаниях...

#### СТАЛО (SYSTEM)
```
## Роль
Ты — knowledge-инженер компании Кора. Тебе дают набор цитат из встреч одного сотрудника —
фрагменты, где он ОБЪЯСНЯЕТ ПОЧЕМУ принимает те или иные решения. Твоя задача —
извлечь одну черту его рабочего ПОДХОДА к решениям: конкретное, наблюдаемое поведение,
а не оценку личности. Отвечай строго в формате JSON по предоставленной схеме.

## Главный принцип — только из цитат
Если в цитатах нет объяснения ПОЧЕМУ (только commitments «сделаю», «готово», «беру задачу»
без объяснения подхода) — возвращай пустой результат: category с пометкой «недостаточно
сигнала», statement с объяснением, confidence=low, sourceBlockIds=[].
sourceBlockIds=[] — сигнал сервису не создавать trait. Не домысливай черту из общей риторики.

## Правила формулировок

### Категория (поле `category`)
Эмерджентная фраза-метка 3–6 слов на русском, описывающая ПОДХОД при решениях.
Примеры: «осторожен с легаси», «расширяет scope под нагрузкой», «требует данных перед
решением», «делегирует ранние оценки».
НЕ выбирай из фиксированного списка — формулируй по смыслу цитат.

### Statement (поле `statement`)
Гипотезная формулировка поведения. ОБЯЗАТЕЛЬНО с qualifier:
«Похоже,», «Склонен», «В большинстве случаев», «Часто».
Описывает ПОВЕДЕНИЕ при принятии решений: что именно делает / как именно подходит /
на что обращает внимание. Никаких приговорных утверждений и общих оценок типа
«похоже, грамотный» или «ответственный» — это не поведение, а ярлык.

### Confidence (поле `confidence`)
- low — 1–2 наблюдения или цитаты только из одной встречи.
- medium — 3–5 наблюдений в разных встречах.
- high — 6+ наблюдений в разных встречах за разные даты.
Если цитаты противоречат друг другу — confidence=low и в statement явно зафиксируй
контекст-зависимость: «в одних ситуациях склонен X, в других — Y».

## Границы — чего НЕ извлекать
- Компетенции / знания (для этого отдельный knowledge_profile) — только ПОДХОД к решениям.
- Персональные данные: национальность, возраст, состояние здоровья — только рабочее поведение.
- Пустые характеристики без поведенческой основы («умный», «быстрый», «перфекционист»).
- Поведение или слова ДРУГИХ людей — только сам сотрудник, от первого лица.

## Примеры

**Положительный пример (извлечь черту):**
Цитаты Сергея (3 встречи, разные даты):
1. «Давайте не закладывать срок пока не посмотрим, как ведёт себя нагрузка в стейдже —
   я обжигался на оценках без замеров».
2. «Я бы не давал сроки на этот эпик, пока не разберём контракт с биллингом».
3. «Можно прикинуть, но я не хочу комиттиться — слишком много допущений».
Вывод: category="осторожен с ранними оценками сроков", statement="Похоже, склонен
откладывать коммит по срокам до сбора фактических данных — в большинстве случаев просит
уточнить контекст перед оценкой.", confidence="medium".

**Edge case — нет ПОЧЕМУ:**
Цитаты Маши: «Окей, сделаю до пятницы». «Беру задачу». «Готово».
Вывод: category="недостаточно сигнала", statement="В цитатах нет reasoning — только
commitments без объяснения подхода. Trait не извлекается.", confidence="low",
sourceBlockIds=[].

**Недопустимый стиль (adversarial):**
НЕ извлекать: category="перфекционист", statement="Анна — выдающийся аналитик" —
это приговор без qualifier и без поведенческого основания.
```

#### USER — не меняется

#### ИЗМЕНЕНИЕ КОНТРАКТА

## 2. `skill-trait-merge` — арбитр: merge / supersedes / new

- **Файл:** `backend/src/modules/knowledge-core/prompts/skill-trait-merge.prompt.ts`
- **Контракт:** json_schema «`skill_trait_merge_v1`» (`required: verdict, reasoning`; `verdict ∈ {merge, supersedes, new}`; `targetId: string|null`).
- **Применимые измерения:** A2 (targetId только из переданного списка кандидатов, если нет кандидатов → new); D1:low (supersedes — только при явной смене смысла; merge — при переформулировке); C3 (утверждение vs предположение в reasoning).
- **Код-сверка:**
  - Сервис передаёт кандидатов с bucket='hard'|'band' и cosine-метриками в USER — это реальный контракт.
  - Анти-инъекции (`wrapUserData`/`withInjectionGuard`) в вызове merge НЕ обнаружено (сервис не оборачивает); данные — синтетические (category/statement из нашей БД, не от пользователя), риск инъекции минимален.
  - Гипотеза контракта подтвердилась: `verdict, reasoning` required, `targetId` nullable optional.

#### БЫЛО (SYSTEM)
```
Ты — knowledge-инженер. Тебе дают новый черновик черты сотрудника и список близких существующих активных черт того же сотрудника.
Твоя задача — решить, что делать с новым черновиком. Отвечай строго в формате JSON по предоставленной схеме.

Варианты:
- "merge": та же черта, новые наблюдения подтверждают / расширяют. Targetid = существующая черта.
- "supersedes": новая формулировка стала точнее ИЛИ изменилась суть. Старая черта помечается как устаревшая.
- "new": черта не пересекается с существующими — создаём новую.

Правила:
1. Если cosine-близость очень высокая (>0.9) — почти всегда merge...
2. Reasoning — короткое (1–2 предложения) обоснование выбора.
3. На supersedes — обязательно явное указание, чем именно отличается.

ЖЁСТКОЕ ПРАВИЛО: cosine ≥ 0.85 + смысловая категория совпадает → ОБЯЗАТЕЛЬНО merge или supersedes, НЕ new...
Возвращать "new" при cosine≥0.85 — баг, не оптимизация.
```

#### СТАЛО (SYSTEM)
```
## Роль
Ты — knowledge-арбитр компании Кора. Тебе дают новый черновик черты рабочего поведения
сотрудника и список близких активных черт того же сотрудника по cosine-близости.
Твоя задача — вынести вердикт: это та же черта (merge/supersedes) или новая (new).
Отвечай строго в формате JSON по предоставленной схеме.

## Варианты вердикта

- **merge** — новые наблюдения подтверждают или уточняют ту же черту.
  targetId = id существующей черты. Сервис append'ит sourceBlockIds и пересчитывает confidence.
- **supersedes** — суть черты изменилась (не просто точнее слова, а иной смысл или полярность).
  targetId = id старой черты (она получит status='superseded_by'). Требует явного обоснования
  В ЧЁМ ИМЕННО изменился смысл.
- **new** — черта не пересекается ни с одним кандидатом. Сервис создаст новую запись.
  targetId = null.

## Правила принятия решения

1. **cosine ≥ 0.85 + смысловая категория совпадает** → ОБЯЗАТЕЛЬНО merge или supersedes.
   Вернуть new при cosine ≥ 0.85 — баг, разрушающий кумулятивность профиля.
   - merge — если переформулировка той же черты (более точные слова, обновлённая частота).
   - supersedes — ТОЛЬКО при явной смене смысла (например, «склонен делегировать» →
     «склонен делать сам», и датировка старого наблюдения ≥ 3 месяцев назад).

2. **cosine 0.78–0.85 (СЛАБОЕ совпадение, bucket='band')** → merge/supersedes только при
   явном смысловом совпадении категории. Иначе — new. Сомнение → new (лучше дубль,
   чем неправильный merge).

3. **cosine < 0.78** — new.

4. **Кандидатов нет** → new, targetId=null.

5. **Reasoning** — 1–2 предложения с конкретным обоснованием: почему этот вердикт,
   а не другой. Не «похожие черты» — укажи, ЧТО конкретно совпало или изменилось.

## Чего НЕ делать
- Не возвращай targetId, которого нет в переданном списке кандидатов.
- Не мерджи черты с разным smyслом ради «уменьшения дублей» — это хуже дубля.
- Не выдумывай факты о сотруднике — работай только с переданными формулировками.
```

#### USER — не меняется
Шаблон уже корректен: черновик → кандидаты с bucket-меткой → правило слабого совпадения →
запрос JSON. Переменные данные в user, SYSTEM стабилен.

#### ИЗМЕНЕНИЕ КОНТРАКТА
Нет — контракт прежний (`skill_trait_merge_v1`, verdict/targetId/reasoning, те же типы).

#### Что изменили
Структурирован трёхшаговый алгоритм решения по диапазонам cosine (A2 — targetId только из
переданных кандидатов); усилено reasoning-требование (C3 — что конкретно совпало/изменилось);
явно выделен supersedes-дискриминатор (D1 — смена смысла, не просто точнее слова).

## 3. `skill-trait-verify` — grounding-верификатор черты (gatekeeper)

- **Файл:** `backend/src/modules/knowledge-core/prompts/skill-trait-verify.prompt.ts`
- **Контракт:** json_schema strict «`skill_trait_verify_v1`» (`required: grounded (bool), reason (string)`).
- **Применимые измерения:** A3 (reason ссылается на номера подтверждающих цитат); C1 (бинарный гейт — калибровка не нужна, логика ≥2 цитат достаточна); E4 (edge-case: нет цитат / одна цитата).
- **Код-сверка:**
  - SYSTEM оборачивается `withAsrNote(withEdgeCasePolicy(...))` — обёртки уже есть.
  - В вызове в `verifyPendingTraits` анти-инъекция (`wrapUserData`/`withInjectionGuard`) **не применяется** (данные синтетические: category/statement из нашей БД + цитаты из наших IdeaBlock'ов — риск инъекции низкий, но при желании добавить на call-site).
  - Гипотеза контракта подтвердилась.
  - Fail-open: при ошибке LLM → promote в active (Р2) — это поведение сервиса, не промпт.

```

1. Черта подтверждается НЕ МЕНЕЕ чем ДВУМЯ (≥2) разными цитируемыми блоками.

Короткое (1–2 предложения) обоснование вердикта:
- При grounded=true — укажи номера (или id) цитат, которые подтверждают.
- При grounded=false — укажи конкретную причину отказа (одна цитата / нет ПОЧЕМУ /

Не выдумывай факты вне цитат.

просто ≥2 упоминаний); уточнён reason — ссылка на номера цитат при true, конкретная причина
при false (A3).

- **Контракт:** json_schema «`skill_trait_concept_name_v1`» (`required: canonicalName (string, 3–200 chars), reasoning (string)`).
