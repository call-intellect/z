# Пакет B — Мастер отвечает на факт/экспертизу (H3)

## Что сейчас
Ассистент компании («Мастер») на вопросы про факты/экспертизу («что решили по пилоту?», «что знает Михаил?») отвечает **«ничего не нашлось»**, хотя данные есть.
Корень: `chat-v2.service.ts:1285-1303 runStructuralRoute` пропускает всё, кроме `queryClass='list'`, — фактические/тематические запросы классифицируются как `fact`/`topic` и мгновенно получают `[]`. При этом `chat-v2-retrieval.service.ts:353-427 runStructuralAggregate` (агрегация блоков по участнику/сущности) **существует, но для fact/topic не вызывается**. Пустой пул → generic-сообщение «Недостаточно данных» (`:909-942`), без честного «точного нет — вот близкое».

## Что делаем (to-be)
1. **Data-driven маршрут:** структурную агрегацию запускать при **любом** `queryClass`, если резолвер вернул `personIds`/`entityIds`. Расширить `runStructuralRoute` на приём `fact`/`topic` при наличии разрешённых id.
2. **Честный фолбэк:** при пустом пуле, когда структурный маршрут пробовался с разрешёнными людьми/сущностями, отдавать `«По [Михаил / компании X] в памяти ничего не нашлось»` (перечислить, по кому искали), а не generic.

## Развилки — решены
**Р-1. Куда встраивать: в классификатор запроса (A) или в диспетч ретрива (B)?** → **B (диспетч ретрива).**
*Доказательство:* в `runRetrieval` уже есть both-ways логика (`:1158-1159`: низкая уверенность/структурный класс → параллельно semantic+structural). Расширить `runStructuralRoute` — минимальная локальная правка. Классификатор остаётся про `queryClass` (кэш-ключ не ломается), а решение «звать ли агрегацию» — на слое ретрива по данным (наличие id), а не по классу модели. Вариант A связал бы классификатор dialog-слоя с данными ретрива — плохое разделение.

**Р-2. Триггерить по классу или по наличию id (при высокой уверенности)?** → **По наличию id, независимо от confidence.**
*Доказательство:* при `fact`+высокая уверенность both-ways сейчас не срабатывает (порог), и агрегация не зовётся, хотя люди/сущности разрешены. Data-driven (есть id → зови) надёжнее model-driven (доверять confidence классификатора).

## Как будет выглядеть
«что знает Михаил?» → резолвер даёт `personId(Михаил)` → `runStructuralAggregate` собирает блоки по участнику → ответ с цитатами. Если реально пусто — «по Михаилу в памяти ничего не нашлось», а не «недостаточно данных».

## Объём изменений (для ТЗ)
- `chat-v2.service.ts:~1292 runStructuralRoute`: принимать `fact`/`topic` при непустых `personIds`/`entityIds`; метрика `structural_fallback_used{queryClass}`.
- `chat-v2.service.ts:909-942`: honest-fallback сообщение + хелпер `describePersonAndEntityFilters(personIds, entityIds)`.
- `chat-v2-retrieval.service.ts:353-427`: опц. `entityNames` для логов (тело не меняется).

## Зависимость
Пакет A: `structuralFilters.personIds/entityIds` наполняет dialog-слой через резолв сущностей/персон. После A резолв людей рабочий → B получает корректные id. Порядок: A → B.

## Тест-план
- Unit: `runStructuralRoute(queryClass='fact', personIds=[x])` при непустом пуле → зовёт агрегацию.
- Integration: «что решили по пилоту» + сущность «пилот» в БД → цитаты, не «ничего».
- Regression: пустой результат при разрешённом Михаиле → honest-сообщение с именем, не generic.
