# Починка триггера авто-черновика прогресса задач

## Что было поставлено

Владелец увидел в кабинете уведомления «Кора собрала черновик прогресса» и попросил разобраться: что это, кто и зачем создаёт. Дальше — разгрести черновики, оценить правильность и решить, надо ли крутить порог.

## Как решал

**Диагностика (Playwright + API прод, кабинет владельца svmazur@mail.ru, Org «Ооо луа»):**
- Вошёл, открыл `/issues/...` из уведомления → блок «Прогресс» с карточкой «Кора собрала черновик прогресса» (Подтвердить/Поправить/Отклонить).
- Через залогиненную сессию дёрнул `GET /api/v1/pending-actions?limit=200` (X-Org-Id из localStorage `z.activeOrgId`). Итог: **черновиков прогресса всего 2**, а гора в колокольчике (134) — это curation (98), probe (19), conflict (9), intake (6). Ощущение «навалило черновиков» было ложным.
- Оба черновика — ложные срабатывания: единственные сигналы (`evidenceQuote`) — две взаимно-обратные смены статуса (A→B, B→A, net-zero). LLM честно вернула `at_risk`, confidence 0.2/0.3, текст «движения не видно». Отклонил оба через `POST /pending-actions/confirm {resolution:'reject'}` (безопасно — reject не публикует).

**Корень (по коду `progress-auto-draft.cron.ts`):** `collectSignals` считал каждую смену статуса отдельным сигналом; порог `minSignals=2` пройден двумя флипами; confidence LLM записывалась в БД, но гейтом не проверялась.

**Цепочка планирования соблюдена:** solution-blueprint (архитектура человеческим языком, владелец одобрил вариант A + планка 0.35) → tz-author (ТЗ-контракт) → tz-orchestrator (реализация 3 фазы через суб-агентов).

**Реализация:**
- Нетто-схлопывание статуса (`netStatusSignal`: first.oldValue===last.newValue → 0 сигналов; иначе один сводный A→C).
- Гейт содержательности (нужен ≥1 чек-пункт/граф-сигнал) до вызова LLM; гейт уверенности (≥0.35) после LLM, до записи.
- 2 крутилки в AdminSetting (`progressAutoDraftMinConfidence`, `progressAutoDraftRequireSubstantiveSignal`), счётчики `RunSummary.{noSubstantive,lowConfidence}`.

## Что вышло

- Коммиты: `feat(tracker)` крутилки · `fix(tracker)` логика · `test(tracker)` кейсы+docs.
- Верификация (сам, не по отчёту агента): typecheck зелёный, lint моих файлов чистый, build exit 0, **spec 18 passed, модуль tracker/workers 88 passed**.
- Прод: только прогон сид-скрипта (уже в `apply-prod-deploy.ts` STEPS), миграций/ENV нет.

## Чему научился

- **Проверять «объём проблемы» цифрами до выводов.** Владелец (и я поначалу) думал «навалило черновиков», а их было 2 из 134 — гору делает curation. Один API-запрос с группировкой по source сразу расставил приоритеты.
- **Порог ≠ смысл сигнала.** Инстинкт «поднять minSignals 2→3» не лечил бы: net-zero флипы засчитывались как сигналы. Чинить надо, что считается сигналом, а не сколько.
- **Тонкость взаимодействия гейтов, которую обязан ловить оркестратор:** при `minSignals=2` гейт `no_substantive` изолированно недостижим (0 содержательных → максимум 1 нетто-статус-сигнал → срабатывает `below_threshold` раньше). Тест на него требует `makeCfg({minSignals:1})`. Передал это кодеру заранее — иначе тесты падали бы.
- **Залогиненная Playwright-сессия = быстрый read/write доступ к прод-API** без diag.ts, когда нужно и посмотреть, и точечно подействовать (reject).
