# Анализ: Дизайн личного кабинета (ЛК) Фазы 0

## 0. Зачем этот документ

Аналитика ЛК — единственный блокер для sub-TZ 0c. Без неё непонятно, как выглядит навигация после Фазы 0, куда возвращается пользователь после wizard'а, что видит admin vs member, и как новые разделы Фазы 0 уживаются с уже работающим стеком MVP-встреч.

Документ закрывает три большие развилки и десяток мелких. По итогам — карта навигации, контракт по страницам и план изменений в [Sidebar.tsx](../../frontend/src/ui/components/app-shell/Sidebar.tsx). Эти артефакты — вход в sub-TZ 0c.

**Что я НЕ решаю в этом документе:** визуальный дизайн (цвета, шрифты, motion — это [delivery/06-ux-ui.md](../../delivery/06-ux-ui.md) + design-system), конкретные API-контракты страниц (это sub-TZ 0a/0c), формулы и тексты копирайта (это `delivery/ui/copy-strings.ru.md`).

---

## 1. Контекст: три ментальные модели одного ЛК

Сегодня в проекте сосуществуют три **разные** ментальные модели «что такое ЛК Z», и они не сходятся друг с другом.

| # | Модель | Где зафиксирована | Метафора | Дефолтный экран | CTA |
|---|---|---|---|---|---|
| 1 | Текущий код | [Sidebar.tsx](../../frontend/src/ui/components/app-shell/Sidebar.tsx) | «Оперативный кабинет встреч» | `/dashboard` | «Создать встречу» |
| 2 | Целевой UX из delivery/ | [delivery/06-ux-ui.md](../../delivery/06-ux-ui.md), [delivery/ui/screens.md](../../delivery/ui/screens.md) | «Память компании — срезы времени и сущности» | `/today` | «⊕ Дамп» |
| 3 | Фаза 0 (зонтичный ТЗ) | [plans/tz/2026-05-21-phase-0-roles-and-onboarding.md](../tz/2026-05-21-phase-0-roles-and-onboarding.md) | «Каркас компании: Структура / Документы / Карты должностей» | дашборд компании после wizard'а | — |

Аналитика ЛК — это **примирение трёх моделей** в одну непротиворечивую навигацию, которую можно постепенно эволюционировать от состояния «как сейчас» к состоянию «целевой UX delivery/», проходя через состояние Фазы 0 без переписывания фронта на каждом шаге.

**Ключевой принцип примирения:** меняем смысловую группировку и лейблы Sidebar'а, **не трогаем существующие URL** (`/meetings`, `/cards`, `/tasks`, `/themes`, `/goals`, `/chat`, `/admin/*`). Это даёт сразу видимое сдвинутое позиционирование без риска для MVP-вертикали.

---

## 2. Что хотим сделать (одним абзацем)

В Фазе 0 ЛК становится «кабинетом памяти компании». Верхняя навигация делится на три смысловые группы: **Компания** (граф памяти и каркас), **Оперативка** (источники графа и личное), **Настройки**. Owner/admin после wizard'а попадает на дашборд компании; member — на свою личную страницу с картой должности и своими встречами. Разделы будущих фаз (Процессы / Регламенты / Политики / Метрики) видны всем как disabled-пункты с пояснением, для admin — со счётчиком «N автоматически собрано, ждёт UI». Wizard — отдельный 5-шаговый flow без AppShell, с возможностью прервать и продолжить.

---

## 3. Зачем (цель и ценность)

- **Для пользователя:** один кабинет вместо «приложения для встреч + что-то про память сбоку». Понятно, куда положить структуру компании, документы и где увидеть автоматически собирающийся профиль роли. Видимая польза сразу после wizard'а.
- **Для проекта:** аналитика ЛК — последний блокер sub-TZ 0c. После закрытия можно стартовать 0c параллельно с 0a/0b (см. порядок реализации в зонтичном §5).
- **Для будущих фаз:** новая навигация задумана с заделом под Фазы γ, δ, ζ — переход к ним становится «добавление страниц», без перестройки каркаса (DoD §7 зонтичного ТЗ, строка 68).

Цели (/goals)                 ← gated feature.goals_strategy

## 5. Решения

### Решение 1 — пересборка навигации в три смысловые группы

**Решение:** разбиваем Sidebar на три группы; маршруты сохраняем, лейблы и группировка меняются; добавляем 5 новых маршрутов под Фазу 0 + 4 disabled-маршрута под γ.

```
КОМПАНИЯ                              (граф памяти — Фаза 0 + γ-заделы)
  Главная                  /dashboard         ← переименовано из «Главная», семантика расширена
  Структура                /structure         ← НОВОЕ (0c): табы Отделы / Должности / Сотрудники
  Документы                /documents         ← НОВОЕ (0c)
  Карты должностей         /roles             ← НОВОЕ (0c)
  Темы                     /themes            ← как есть, gated feature.theme
  Цели и стратегия         /goals             ← как есть, gated feature.goals_strategy
  ─── Будет в следующей фазе ───  (свёрнутая подгруппа, см. решение 3)
  Процессы                 /processes         ← disabled-γ
  Регламенты               /regulations       ← disabled-γ
  Политики                 /policies          ← disabled-γ
  Метрики                  /metrics           ← disabled-γ

ОПЕРАТИВКА                            (источники графа + личное)
  Встречи                  /meetings          ← как есть, label «Мои встречи» → «Встречи»
  Дамп                     /dump              ← НОВОЕ (0c, минимальный): пункт в коде уже есть
  Карточки                 /cards             ← как есть
  Задачи                   /tasks             ← как есть
  Помощник компании        /chat              ← как есть, gated feature.chat_org (label обновлён)
  Я                        /me                ← НОВОЕ (0c, минимальный): моя должность + мои док-ты + мои встречи

НАСТРОЙКИ
  Шаблоны                  /settings/templates    ← как есть
  Интеграции               /settings/integrations ← как есть
  Настройки                /settings              ← как есть
  ─── Админка ───  (только для owner / admin / super_admin)
  Админка Org              /settings/admin        ← как есть
  Z-Admin                  /admin                 ← как есть (только super_admin)
```

**Обоснование:**
- Целевой UX delivery/ исходно требует CTA «⊕ Дамп», а не «Создать встречу». Сейчас CTA = встреча. Постепенный переход требует, чтобы Sidebar уже сейчас читался как «кабинет памяти», иначе при последующей смене CTA продукт «прыгает» — это плохой UX.
- Маршруты сохраняются — это спасает MVP-вертикаль. Меняются только лейблы и группировка.
- Группа «Будет в следующей фазе» свёрнута по умолчанию (см. решение 3) — не загромождает Sidebar, но показывает «куда идёт продукт».
- CTA в шапке: **оставляем «Создать встречу»** на Фазу 0. Меняем на «⊕ Дамп» только в γ, когда `/dump` будет реальным первичным capture'ом с голосом и AI-feedback. В Фазе 0 `/dump` — минимальный (см. решение 6).

**Что отверг:**
- «Просто добавить новые пункты в конец Sidebar» — отвергнуто. Тогда продукт продолжает читаться как «приложение для встреч с добавкой про память», что противоречит позиционированию.
- «Переписать Sidebar полностью на delivery/06-структуру (Сегодня / Неделя / Месяц / Карта / Темы / ...)» — отвергнуто. Половина этих экранов не реализована; полная замена убивает MVP-флоу без замены.

**Tradeoff:** пользователи, привыкшие к нынешнему Sidebar, увидят перегруппировку. Смягчение — URL не меняются, страницы те же, никто из активных пилотов физически не ломается.

### Решение 2 — единый ЛК, разный default landing по роли

**Решение:** один кабинет для всех ролей, дефолтный экран после логина зависит от `currentOrgRole`:

| Роль | Default landing | Почему |
|---|---|---|
| `owner` / `admin` | `/dashboard` | Пульс компании — то, ради чего admin вообще зашёл |
| `member` | `/me` | Сначала видимая польза для себя; пустые состояния (`/me` без назначенной должности) — баннер «Вашу должность ещё не назначили», см. §7.2 |
| `super_admin` (только Z-Admin без org-членства) | `/admin` | Технический оператор Z, у него нет «своей компании» |

Multi-org switcher — в шапке Header, dropdown рядом с UserCard. Активная Org — источник `tenantId` для всех API. Во время wizard'а switcher временно скрыт (мы внутри только что созданной Org, переключение бессмысленно).

**Обоснование:**
- В [delivery/06-ux-ui.md](../../delivery/06-ux-ui.md) единый набор экранов для всех ролей. Разделение admin/member происходит **не на уровне URL, а на уровне содержимого экранов** (RBAC).
- Раздваивать роуты (`/dashboard` vs `/dashboard-personal`) — путь к двум разъезжающимся UI. Один URL + разное содержимое = одна реализация, проще поддерживать.
- Member, попавший сразу на `/dashboard` без данных компании (структура только что заведена, у member ещё не было встреч), увидит пустой экран. Это плохое первое впечатление. `/me` даёт хотя бы свою должность.

**Что отверг:**
- «Все на `/dashboard` всегда» — плохо для member на первой неделе.
- «Member вообще не имеет доступа к `/dashboard`» — плохо, лишает member ощущения «я часть компании, вижу её пульс».

**Tradeoff:** для member нужно сначала собрать минимальный `/me`. Это +1 страница в scope sub-TZ 0c. См. решение 4.

### Решение 3 — γ-разделы видны всем, состояний три

**Решение:** в группе «Компания» появляется свёрнутая подгруппа «Будет в следующей фазе» с четырьмя disabled-пунктами (Процессы / Регламенты / Политики / Метрики). По клику открывается **preview-страница** с описанием раздела и для admin — счётчиком «N сущностей уже автоматически собрано, UI появится в Фазе γ».

Три различных визуальных состояния пункта Sidebar:

| Состояние | Когда | Визуал | Поведение клика |
|---|---|---|---|
| **Работает** | Реализован в текущей фазе | Обычная иконка + лейбл | Переход на страницу |
| **disabled-γ** | Запланирован в будущей фазе | Приглушённый цвет + иконка часов справа | Переход на preview-страницу `/processes`, `/regulations` и т.д. (one-page «здесь будет X, план в `plans/tz/...`») |
| **tariff-locked** | Доступен на старшем тарифе | Приглушённый + иконка замка справа | Редирект на `/settings/billing` (как сейчас) |

Иконка часов выбрана осознанно, чтобы **не путать с замком тарифного гейтинга** — это два разных смысловых ограничения.

**Обоснование:**
- Открытый вопрос №10 зонтичного ТЗ предлагает гипотезу «скрывать для не-admin». **Отвергаю.** Скрытие создаёт ощущение обедненного продукта, противоречит позиционированию «память компании» (а не «приложение для встреч»). Visible-but-disabled — это «купите будущее», что является сознательным маркетинговым выбором.
- Свёрнутость подгруппы по умолчанию решает проблему перегруза Sidebar (4 пункта — это много).
- Для admin счётчик «N собрано автоматически» — мощный психологический сигнал «продукт уже работает на меня, даже без UI».

**Что отверг:**
- «Скрывать для member» — отвергнуто (см. обоснование выше).
- «Использовать иконку замка для всех ограничений» — отвергнуто, путает тарифный и фазовый гейтинг.
- «Полностью убрать γ-пункты из Sidebar» — отвергнуто, теряем pre-marketing будущих фаз.

**Tradeoff:** preview-страницы (`/processes`, `/regulations`, `/policies`, `/metrics`) — это 4 простых статических страницы, которые надо собрать в sub-TZ 0c. Объём небольшой (≈1-2 часа на все), оправдан.

### Решение 4 — минимальная `/me` уже в Фазе 0

**Решение:** `/me` — это **скромная страница**, которая показывает:

1. **Моя должность** (если назначена) — ссылка на свою `RoleProfile`; если не назначена — баннер «Вашу должность ещё не назначили. Попросите администратора».
2. **Мой отдел** — название, ссылка на `/structure?tab=departments&id=...`.
3. **Мои документы** — список документов, которые я загрузил (фильтр `Document.uploaderId = currentUser`).
4. **Мои встречи** — компактная версия `/meetings` с фильтром «я участник».

Что **НЕ входит** в `/me` в Фазе 0:
- Мои обещания (`signalType='promise'` из knowledge-core) — Фаза γ.
- Моё настроение, чек-ин — Фаза δ.
- Employee Clone — Фаза ζ.
- Compliance «удалить мой след» — Фаза β (security).

**Обоснование:**
- Без `/me` решение 2 (member-landing) не сводится — member некуда направить.
- `RoleProfile` создаётся в Фазе 0d, не показывать её пользователю — упущенная видимая польза.
- Все данные для `/me` уже есть в БД после Фазы 0a (Person, Role, Document, Meeting). Страница — простая агрегация, не дорогая.

**Что отверг:**
- «Полная `/me` сразу как в delivery/06» — отвергнуто, скоп растёт в разы (обещания требуют новой логики извлечения, настроение — отдельной системы, Employee Clone — Фаза ζ).
- «`/me` только в γ, member пока сидит на `/dashboard`» — отвергнуто (см. решение 2).

**Tradeoff:** +1 страница в скоп 0c. Объём — небольшой агрегационный экран, ≈ 1-2 дня frontend-разработки на основе уже существующих API.

### Решение 5 — multi-org switcher в шапке

**Решение:** в [Header.tsx](../../frontend/src/ui/components/app-shell/Header.tsx) добавляется dropdown «Активная компания» рядом с UserCard. Показывает имя текущей Org + список других Org, в которых пользователь имеет membership. Переключение → перезагрузка контекста, активная Org становится источником `tenantId` для всех API.

**Состояния:**
- Одна Org → switcher не отрисовывается, в Header показывается только название текущей Org (truncated до 20 символов, полное имя — в tooltip).
- Несколько Org → dropdown: активная Org (truncated до 20 символов) + chevron; в открытом dropdown — полные имена остальных Org с количеством непрочитанных уведомлений (если есть).
- Внутри wizard'а — switcher временно скрыт.
- super_admin без org-членства — текст «Режим Z-Admin».

**Обоснование:**
- `currentOrgRole` уже подразумевается в `useAuth()` и пробрасывается в [Sidebar.tsx:110](../../frontend/src/ui/components/app-shell/Sidebar.tsx#L110), но визуального переключателя нет. Это известный долг, который надо закрыть до того, как у пилотов появятся пользователи с двумя Org (типичный сценарий: консультант с несколькими клиентами).
- Реализуется компактно — backend уже поддерживает multi-org (orgs модуль), нужен только UI.

**Tradeoff:** небольшое усложнение Header'а, оправдано перспективой пилотов-консультантов.

### Решение 6 — `/dump` минимальный в Фазе 0, расширение в Фазе 0b

**Решение:** в Фазе 0 (sub-TZ 0c) собираем минимальный `/dump`:
- Большой textarea «Расскажи всё, что хочешь зафиксировать».
- Кнопка «Сохранить».
- После сохранения — короткий feedback «Записал».

Backend для `/dump`: добавляется `text.adapter` в [ingest/](../../backend/src/modules/ingest/) как побочный продукт sub-TZ 0b (там и так делается `document.adapter`). Сохранённый текст идёт в обычный pipeline `block-ingest` → `block-distill` → `entity-resolver`, то есть автоматически появляется в knowledge-core, темах, AI-чате.

Что **НЕ** входит в `/dump` Фазы 0:
- Голос (push-to-talk) — Фаза γ.
- Прикреплённые файлы (картинки, документы) — Фаза γ (документы есть в `/documents`, дублировать в дамп пока не нужно).
- AI-feedback «Вижу 3 сигнала: ...» — Фаза γ.
- Telegram-бот — Фаза γ.

**Обоснование:**
- Пункт `/dump` уже есть в [Sidebar.tsx:87](../../frontend/src/ui/components/app-shell/Sidebar.tsx#L87), но ведёт на 404 — это давний долг от delivery/, надо закрыть.
- Минимальный `/dump` — это **очень маленькое расширение скопа 0b** (новый адаптер) + **очень простая страница в 0c**. Зато даёт member ЛК ради чего открыть, помимо встреч.
- `text.adapter` концептуально дешевле `document.adapter` (нет парсинга PDF/DOCX), идеологически — это второй адаптер ingest, который надо в любом случае иметь как образец для будущих (Telegram, email).

**Что отверг:**
- «Не делать `/dump` в Фазе 0, оставить заглушку» — отвергнуто, разочарование member и невыполненный долг.
- «Сразу делать полный `/dump` с голосом и AI-feedback» — отвергнуто, скоп Фазы 0 раздувается на месяц минимум.

**Tradeoff: это РАСШИРЕНИЕ scope зонтичного ТЗ Фазы 0.** Зонтичный ТЗ не предусматривал `/dump` и `text.adapter`. Предлагаю включить — оправдано (см. обоснование), и backend-объём небольшой. **Это решение надо явно отразить при ревью зонтичного ТЗ**, см. §11.

## 7. Структура страниц (контракты)

Не wireframes пиксель-в-пиксель — это уровень sub-TZ 0c. Здесь — **что должна показывать страница** и **с какими состояниями работает**.

### 7.1. `/dashboard` для admin (Фаза 0)

Эволюция [DirectorDashboardClient.tsx](../../frontend/app/(authenticated)/dashboard/DirectorDashboardClient.tsx). К существующим виджетам добавляются:

- **Виджет «Структура компании»** — счётчики: N отделов, N должностей, N сотрудников, N документов, N карт должностей в статусе «формируется». Каждый счётчик кликабелен → переход в соответствующий раздел.
- **Виджет «Знакомство»** — если структура пустая, большой CTA «Пройти знакомство с компанией» → `/onboarding/company`. После прохождения wizard'а — баннер исчезает.

Состояния:
- **Empty (структура пустая, wizard не пройден):** доминирует виджет «Знакомство».
- **Default (структура заведена, данных мало):** все виджеты в обычном режиме, виджеты knowledge-core (Согласованность стратегии, AI-сводки) могут показывать «накапливаем данные».
- **Полное наполнение:** все виджеты с реальными числами.

### 7.2. `/me` для member (Фаза 0)

Минимальный личный кабинет (см. решение 4).

**Доступ:** `/me` доступна **всем** пользователям с членством в Org, включая owner/admin (они тоже `Person` со своей должностью). Для admin — это не default landing, но страница работает по той же логике. RBAC: пользователь видит только свои данные (`Person.userId = currentUser.id`).

Структура:

```
┌─ Шапка: Имя, аватар, должность, отдел ──┐
│ Иван Петров                              │
│ Должность: «Менеджер по продажам»   →    │
│ Отдел: «Продажи»                    →    │
└──────────────────────────────────────────┘

┌─ Моя карта должности ───────────────────┐
│ (превью RoleProfile.summaryCache         │
│ или статус «формируется»)                │
│                                           │
│ [Открыть полностью →]                    │
└──────────────────────────────────────────┘

┌─ Мои документы ──────────────────────────┐
│ • job-description-sales-manager.pdf      │
│ • presentation-q1.pdf                    │
│ [Загрузить документ]                     │
└──────────────────────────────────────────┘

┌─ Мои встречи ────────────────────────────┐
│ (компактный список, последние 5)         │
│ [Все мои встречи →]                      │
└──────────────────────────────────────────┘
```

Состояния:
- **Empty (только что приглашён, должность не назначена):** баннер «Вашу должность ещё не назначили. Попросите администратора». Видны только секции «Мои документы» (пустая) и «Мои встречи» (пустая).
- **Default:** все секции с данными.
- **RoleProfile пустой:** карточка «Карта должности формируется. Заполнится автоматически после нескольких встреч и документов с этой ролью.» (без прогресс-бара, см. решение по badge ниже).

### 7.3. `/structure` (Фаза 0)

Одна страница с **тремя табами** (выбор сохраняется в URL `?tab=departments|roles|persons`):

- **Отделы** — плоский список с возможностью добавить, переименовать, удалить. Поле `parentDepartmentId` есть в схеме (зонтичный ТЗ §2 «Не входит»), но UI плоский — это решение зонтичного ТЗ.
- **Должности** — список с фильтром по отделу. На каждой строке: название, отдел, количество назначенных людей, статус карты должности.
- **Сотрудники** — список с фильтром по отделу и по должности. Каждая строка: имя, email, должность, отдел, **статус приглашения** (`не приглашён` / `приглашение отправлено` / `активен`). Действия на строке:
  - «Пригласить» — создаёт `Membership` + отправляет email через существующий механизм `orgs/invitations`. Доступно если `Person.userId IS NULL`.
  - «Переназначить должность» — изменяет связь `executes_role` (создаёт новую с `validFrom=now`, закрывает старую `validTo=now`).
  - «Удалить из компании» — soft-delete `Person`, закрывает все связи `executes_role`/`member_of` `validTo=now`; `User` остаётся, но теряет `Membership`.
- На табе **«Должности»** на каждой строке есть действие «Загрузить должностную инструкцию» — создаёт `Document` со связью `JobDescription → derived_from → Document` (эквивалент шага 4 wizard'а, но для отдельной должности после прохождения wizard'а).

**Обоснование табов (а не 3 отдельных страниц):** структура — это единая сущность, пользователь часто переключается между отделами/должностями/сотрудниками. Табы быстрее. SEO для админки не нужен. Альтернатива — sidebar внутри `/structure` — избыточна для трёх сущностей.

Empty-states каждого таба:
- Отделы пустые → большая CTA «Заведите первый отдел» + ссылка на wizard.
- Должности пустые → «Сначала заведите отделы» (если отделов нет) или «Заведите первую должность».
- Сотрудники пустые → «Сначала заведите должности» или «Заведите первого сотрудника».

### 7.4. `/documents` (Фаза 0)

Список загруженных документов. Колонки: имя, тип (PDF/DOCX/MD), кем загружен, к какой должности привязан, статус парсинга (`uploaded → parsing → parsed → blocks-extracted → failed`), дата.

Действия:
- Загрузить документ (drag-drop + кнопка).
- При загрузке — выбор: «привязать к должности» (опционально), «общий документ» (по умолчанию).
- Открыть → детальная страница с парсенным текстом + список извлечённых блоков идей + **readonly-список извлечённых сущностей группы Б** (имя + тип + `confidence`).

**Граница UI группы Б в Фазе 0.** На странице документа сущности группы Б (`Process`, `Decision`, `Regulation`, `Policy`, `Metric`, `Tool`, опц. `Mission`/`Vision`/`Strategy`) показываются **только как провенанс документа** — список «что мы из этого документа извлекли». Это не CRUD: нельзя редактировать, нельзя кликнуть на сущность и перейти на её отдельную страницу (страниц нет — они появятся в Фазе γ). Идентификатор сущности можно скопировать (для отладки/админки). Логика «одна сущность упоминается в N документах» — тоже γ. В Фазе 0 на странице документа — плоский список без дедупликации между документами.

Прогресс парсинга — polling раз в 2 секунды (см. открытый вопрос №6 зонтичного ТЗ, гипотеза автора).

### 7.5. `/roles` (Карты должностей, Фаза 0)

Список всех должностей компании с превью карты должности:

```
┌──────────────────────────────────────────┐
│ Менеджер по продажам                     │
│ Отдел: «Продажи»  •  3 сотрудника        │
│ Карта формируется (12 блоков идей,        │
│ ждём ≥N для генерации)                   │
└──────────────────────────────────────────┘

┌──────────────────────────────────────────┐
│ Старший разработчик                       │
│ Отдел: «Разработка»  •  5 сотрудников    │
│ ✓ Карта собрана (обновлена 2 ч. назад)   │
│ Сводка: ответственности / навыки / ...   │
└──────────────────────────────────────────┘
```

Детальная страница `/roles/:id`:
- Шапка: название, отдел, сотрудники.
- Должностная инструкция (`JobDescription`) — если есть, превью + ссылка на источник.
- Карта должности (`RoleProfile.summaryCache`):
  - Ответственности (`responsibilities[]`).
  - Навыки (`skills[]`).
  - Типичные решения (`decision_patterns[]`).
  - Типичные грабли (`common_pitfalls[]`).
  - Стиль работы (`style_profile`).
- Источники (провенанс): какие встречи, документы, блоки идей участвовали в построении.
- Кнопка «Пересобрать карту» (admin only) → POST `/api/v1/role-profiles/:roleId/rebuild`.
  - После клика — кнопка `disabled` на 60 секунд + статус «Карта собирается, обычно 1–2 минуты». Защита от случайного двойного клика.
  - Если на момент клика job уже в очереди или выполняется — POST возвращает `409 Conflict` с текущим статусом (`queued` / `running` / `since: timestamp`). UI показывает «Карта уже собирается с {время}». Это убирает риск дорогих повторных LLM-вызовов на одну Role.
  - Idempotency на стороне worker'а — по `roleId+buildVersion` (зонтичный ТЗ строка 37 матрицы).

Empty-state карты должности: «Карта формируется. Заполнится автоматически после {N} встреч/документов с этой ролью. Сейчас собрано: {M}.» Конкретный порог N — открытый вопрос №5 зонтичного ТЗ (гипотеза автора: пустой `summaryCache` + явный статус).

## 8. Wizard «Знакомство с компанией» (5 шагов)

Отдельный flow `/onboarding/company/*` без AppShell (как `/onboarding/change-password` сегодня). Доступен только owner/admin при первом входе в новую Org. Кнопка «Прервать и вернуться позже» на каждом шаге — состояние сохраняется в БД (черновик `OnboardingState` или в самих созданных сущностях).

### Шаг 1 — Отделы

«Заведите отделы вашей компании.»

Простой повторяющийся ввод: поле «Название отдела» + [Добавить ещё]. Иерархия отделов в UI плоская (зонтичный ТЗ §2 «Не входит»). Минимум 1 отдел для перехода. Возможен импорт из CSV (открытый вопрос №4, гипотеза автора: nice-to-have).

### Шаг 2 — Должности

«Заведите должности.»

Для каждой должности: название, отдел (dropdown из шага 1). Минимум 1 должность. Возможен импорт из CSV.

### Шаг 3 — Сотрудники

«Заведите сотрудников.»

Для каждого: имя, email, должность (dropdown из шага 2). Email обязателен. Цель шага — создать `Person` в БД и связи `executes_role` + `member_of`. **`Person.userId` остаётся `NULL` до отправки приглашения** — это нормальное состояние модели (Person ≠ User).

**Приглашение не отправляется в wizard'е.** Owner делает это позже отдельным действием в `/structure?tab=persons` (см. §7.3 «действия на сотруднике»). Связка `Person ↔ User ↔ Membership` создаётся в момент принятия приглашения существующим механизмом [`backend/src/modules/orgs/invitations`](../../backend/src/modules/orgs/) — там пользователь регистрируется/логинится и подтверждает email. После принятия `Person.userId` обновляется атомарно в одной транзакции с созданием `Membership`.

Возможен импорт из CSV (открытый вопрос №4 зонтичного ТЗ — nice-to-have в MVP).

### Шаг 4 — Должностные инструкции

«Загрузите должностные инструкции для должностей.»

Список должностей из шага 2 + drag-drop зона на каждую. Опционально (можно пропустить полностью, но рекомендуется). Каждый загруженный файл — `Document` со связью `JobDescription → derived_from → Document` (зонтичный ТЗ строка 31).

Парсинг идёт асинхронно — wizard не ждёт завершения, переходит к шагу 5 сразу после успешной загрузки в S3.

### Шаг 5 — Готово

«Готово, открываем дашборд компании.»

Краткое summary: «Заведено: N отделов, M должностей, K сотрудников, L документов на парсинге.» Кнопка → `/dashboard`.

**После wizard'а:**
- Owner на `/dashboard` видит виджет «Структура компании» с реальными числами и виджет «Знакомство» уже скрыт.
- Запускается фоновый процесс — `RoleProfileAgent` начинает строить карты должностей (но они ещё долго будут пустыми, пока не накопятся данные из встреч).
- Документы парсятся, извлекаются `IdeaBlock`-и и типизированные сущности группы Б.

**Если wizard прерван:**
- Owner видит на `/dashboard` баннер «Незавершённое знакомство» с кнопкой «Продолжить» → возврат к последнему незавершённому шагу.

**Доступ к wizard'у — однократно при пустой Org.**
- Wizard `/onboarding/company/*` доступен только если у Org нет ни одного `Department` (то есть знакомство ещё не пройдено или прервано).
- После полного прохождения wizard'а попытка зайти на `/onboarding/company/*` редиректит на `/dashboard`.
- Добавление новых отделов / должностей / сотрудников **после** wizard'а — через обычный CRUD на `/structure`, не через перезапуск wizard'а. Это сознательное упрощение: wizard — единоразовая церемония знакомства, не повторяемый flow.
- Загрузка новых должностных инструкций после wizard'а — через действие «Загрузить должностную инструкцию» в `/structure?tab=roles` (см. §7.3).

**DoD wizard'а:** прохождение от начала до конца ≤ 15 минут (зонтичный ТЗ DoD «Бизнес-критерии»).

## 13. Принятые решения по мелким развилкам

Перечень небольших развилок, которые я закрыл на этапе ревью аналитики — чтобы не тащить их в sub-TZ 0c как открытые вопросы.

| № | Развилка | Решение |
|---|---|---|
| 13.1 | Хранение незавершённого wizard'а | **По реально созданным сущностям**, без отдельной модели `OnboardingState`. Шаг = первый шаг, на котором нет сущностей нужного типа (`Department.count = 0` → шаг 1, `Role.count = 0` → шаг 2, и т.д.). Загрузка должностных инструкций (шаг 4) необязательна → если шаг 4 пропущен, шаг 5 считается достигнутым. Меньше моделей, меньше синхронизации |
| 13.2 | `/dashboard` для admin до wizard'а | Доминирующий виджет «Знакомство» вверху во всю ширину; остальные виджеты (по фактически уже наработанным данным MVP — встречи, задачи, темы) **остаются видимы ниже**, но без расчётов «по структуре компании», так как структуры ещё нет. Это даёт admin'у понять, что Z уже работает на встречах, но карта компании ещё ждёт настройки |
| 13.3 | Multi-org switcher: full reload vs soft-reload | **Soft-reload** через `mutate(undefined, { revalidate: true })` всех `auth-context` + ключевых SWR-кешей (`meetings`, `cards`, `themes`, `documents`, `structure`, `roles`). Маршрут — `router.replace(currentPath)` чтобы остаться на той же странице. Full reload — fallback если switcher ломается, но не дефолт |
| 13.4 | Роутинг wizard'а | `/onboarding/company/step-1` … `/onboarding/company/step-5` внутри [`frontend/app/(authenticated)/onboarding/`](../../frontend/app/(authenticated)/onboarding/) (рядом с существующим `change-password/`). Без AppShell (`hideShell` в layout, как делает [`AuthenticatedShell.tsx:61`](../../frontend/app/(authenticated)/AuthenticatedShell.tsx#L61) для `change-password`) |
| 13.5 | Визуальный язык disabled-γ-пунктов | `opacity-60` + `text-muted-foreground` (классы Tailwind, уже используются в проекте); иконка часов `lucide-react` `Clock4` 16px справа от лейбла; курсор `cursor-pointer` (клик ведёт на preview-страницу, не disabled полностью). Деталь визуала — в sub-TZ 0c |

**Передаём в sub-TZ 0c как открытые (требуют эксперимента или замеров, не дизайн-развилок):**

- CSV-импорт в wizard (шаг 1/2/3) — открытый вопрос №4 зонтичного ТЗ. Гипотеза: nice-to-have, включаем если есть запас по времени и/или если на 1-м пилоте обнаруживается, что ручной ввод >10 минут.
- Порог `N` блоков идей для запуска генерации `RoleProfile` — открытый вопрос №5 зонтичного ТЗ. Гипотеза: эмпирически на пилотах, дефолт `N=5`.
