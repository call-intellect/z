# 2026-07-03 — Probe-стенд: прогон на Стреле, поле правильности, судья по смыслам

## Что было поставлено

1. Прогнать стенд уточняющих вопросов (`backend/scripts/probe-stand/`) на локальной Стреле, дать отчёт польза/шум, подготовить ТЗ на починку `curation.consistency_checker`.
2. По ходу владелец развернул задачу: не резать вопросы до белого списка — сформулировать **смысловые критерии** («поле правильности»), и подготовить стенд к передаче агенту-циклисту, который будет итеративно вычислять, какие вопросы жить/автоматизироваться, и где вопросов не хватает.

## Как решал

- **Прогон 1 (`stand.ts all`)**: судья упал на 100% типов (maxTokens=700 обрезал JSON tool-call; при `tool_choice: auto` DeepSeek v4-pro отвечал текстом/пустотой). Фикс в `judge.ts`: 2500 токенов, извлечение JSON из текста/fences, 3 попытки. Сценарий method-capture честно отсёк обычную задачу (complexity 0.42 < 0.5).
- **Фикстуры**: в Стреле не было ни документов, ни шагов процессов, ни ролей/зон (R1–R5 пустые), все интейки без исполнителя И срока (ветка `due_date_missing` мертва), открытых задач с исполнителем — ноль. Написал идемпотентный `seed-fixtures.ts` (префикс «QA-стенд:»). Redis-гигиена перед повтором: чистка `probe:dedup:*`, `probe:ratelimit:*`, `consistency:dedup:*`.
- **Прогон 2**: 18 типов осуждено; consistency дал 10 событий с 5 дыр; `task.method_capture` создался, но получил `dropped_rate_limit` — лимит 5/час съели sweep-вопросы (rate-limiter слеп к приоритету). Гипотезы (dedup TTL=интервалу крона → 6×/сутки; дайджест 5/сутки < приток; дубль R6↔companyprofile; provenance-заглушка) записал в отчёт.
- **Разворот владельца**: сначала предложил агрегацию (блюпринт `plans/architecture/2026-07-03-consistency-checker-probe-noise.md`, draft), затем белый список из 6 типов — владелец отверг обоих: «смыслы, а не конкретные вопросы; типы вычислит стенд циклами».
- **Поле правильности**: `docs/testing/probe-field-rules.md` — P1–P8 из слов владельца (только человек знает ответ; автоматика сначала; противоречия важны; не спрашивать про неподтверждённое; адресат; один смысл — один вопрос; понятное действие; метрики — не вопросы) + бюджет ≤5 вопросов/чел/сутки. Судья читает файл при каждом запуске.
- **Судья 2.0** (`judge.ts`): вердикты `keep/rework/automate/drop` + `humanOnly`/`machinePath`/`violatedPrinciples` + обратная проверка `judgeGaps` («каких вопросов не хватает»). `stand.ts`: новая таблица, секция «Пробелы», снапшот каждого прогона в `docs/testing/probe-stand-runs/`. Runbook цикла — в `docs/testing/probe-stand.md`.

Коммит: `7c2ec342` (feat(probe-stand)), ветка `work/2026-07-02`.

## Что вышло

- Верификационный прогон: **18/18 вердиктов без сбоев** → 7 drop / 8 automate / 1 rework / 2 keep (безоговорочные keep: `task.method_capture`, `process_template.missing_output_artifact`); **5 кандидатов-пробелов** (уход сотрудника, затухающий клиент, противоречие стратегий, конфликт загрузки, затянувшийся найм) — все по P1/P3.
- Калибровочная оговорка владельцу: судья пометил task-вопросы `automate`, но рекомендация сохраняет вопрос-фолбэк (P2) — при желании мягче judge-метки правится одной строкой в поле правильности.
- Блюпринт инспектора порядка остался draft — решения выработает цикл; ТЗ не писал (жёсткий gate: нет approved-архитектуры).

## Чему научился

- **DeepSeek v4-pro + tool_choice=auto + малый maxTokens = рваный JSON**: у reasoning-модели бюджет уходит в размышления; для схемных ответов давать ≥2000 токенов и парсить и tool-call, и текст (fences, первый `{`…последний `}`), с retry.
- **Стенд, который сам форсит инспекторов, гасит собственные сценарии**: `all` сначала гонит sweep в trigger, потом сценарий — dedup 72ч и rate-limit 5/час уже потрачены, сценарий всегда «пустой». Порядок шагов в комбинированных прогонах — часть контракта стенда.
- **Синтетика без негативных веток бесполезна для поведенческих проверок**: у всех интейков Стрелы не было ОБОИХ полей → ветка `due_date_missing` в принципе недостижима; все участники — owner'ы → проверка «исполнителю, не владельцу» вакуумна. Фикстуры должны целенаправленно покрывать каждую ветку условий.
- **Рубрика судьи в файле, а не в промпте** — владелец правит критерии без правки кода, судейство воспроизводимо между циклами, снапшоты дают сравнение «до/после».
- **Слушать разворот владельца до конца**: «упростить вопросы» ≠ «агрегировать» и ≠ «белый список» — ему нужны были принципы + механизм вычисления. Два моих захода (агрегация, 6 типов) были преждевременной фиксацией решения.
