# Анализ входных данных дневного отчёта «День компании»

Перепроверка по коду: какие каналы дают данные за день, где хранятся, **сохранена ли подпись
«кто из сотрудников это сказал»**, и что из этого сейчас доходит до отчёта.

> **СТАТУС (2026-06-29): собираем требования к разработке дневного дашборда (комплексно — текстовый отчёт + виджеты).**
> - **Планы / чек-ины / отчётность — ЗАКРЫТО** (Ф1–Ф8 закоммичены в `dev`). Где хранятся — см. раздел внизу.
> - **Тайминг:** планы/чек-ины собираются **~05:00 МСК** → генерацию отчёта сдвигаем **позже** (с запасом на обработку), см. решение 1.
> - Зависшие задачи и «кто просрочил» — **чисто механические** (детерминированный слой 1).

## Вывод по атрибуции (главный вопрос владельца)

**Подпись «кто сказал» на уровне хранения есть почти везде** — но в трёх разных «системах координат»:

- **person** — только чек-ины (`personId`, железно, без подписи запись невозможна).
- **user** — помощник, чат, free-note (`userId`). Это аккаунт, не сотрудник; нужен маппинг `userId → Person`.
- **external** — Bitrix (`authorExternalId`/`authorName` — юзер Bitrix), чатбокс (`senderName` + `senderType`). Это внешние ID; нужен маппинг на `Person` сотрудника + различение сотрудник/клиент.

**Где атрибуция реально теряется / ненадёжна:**
1. **Probe** — `recipientUserId` это получатель опроса, не обязательно автор ответа. Ненадёжно.
2. **Мысли/жалобы в чек-ине** — `rawResponseText` хранит всё, но LLM-парсер раскладывает только план/факт/блокеры; «мысль/жалоба», не распознанная как блокер, остаётся лишь в `rawResponseText`, который **наружу (в DTO) не отдаётся** → до отчёта не доходит.
3. **Единый слой `→ Person`** для user- и external-каналов существует частично (ChannelBinding для Telegram, BitrixUser resolve), но не сведён в одну точку «дай всё, что сотрудник X наговорил за день по всем каналам».

## Что доходит до отчёта сейчас

Только **встречи (summaryFast)** и **чек-ины частично** (доли настроения + сырой текст красных). Помощник,
чат, free-note, Bitrix, чатбокс, probe — **в отчёт не подаются**, хотя данные с подписью автора лежат готовые.

## Тайминг (расхождение с «в 12:00»)

Сбора ровно в 12:00 МСК **нет**:
- Bitrix sync/analyze — `EVERY_DAY_AT_MIDNIGHT` без timezone = **03:00 МСК**.
- Чатбокс sync — `00:00 МСК`, analyze — каждые 10 минут.
- Дневной отчёт — `@Cron('0 3 * * *')` без timezone = **06:00 МСК** (за прошедшие сутки).

Модель сейчас: отчёт **утром за вчера**. К 06:00 данные за вчера собраны. «12:00» из обсуждения — отдельная
развилка (промежуточный дневной срез? перенос времени? — решить в ТЗ).

## Гэпы под промпт v2 (что доготовить на входе)

1. **Bitrix + чатбокс → в отчёт.** Решить: сырьё (`*Message.text` с авторами) или готовые дневные саммари
   (`*DialogSession.summary` / `ChatboxChatSession.summary`). Сырьё точнее, но дороже по токенам.
2. **Мысли/жалобы сотрудника → в отчёт с подписью.** Подать помощника (Concierge), чат (Chat-V2),
   free-note и `rawResponseText` чек-инов — сгруппированные по сотруднику. Сейчас «голос сотрудника» теряется.
3. **План↔факт по людям.** Достать `plansJson`/`donesJson` из чек-инов (есть, но не подаётся) — для секции «Отчётность».
4. **Единый резолв `userId`/`externalId` → `Person`** + различение сотрудник/клиент — чтобы всё было «подписано сотрудником».
5. **Probe** — починить атрибуцию (автор ответа, не получатель) либо не подавать.

## Принятые решения владельца (2026-06-29)

1. **Время отчёта — «утром за вчера», но генерацию СДВИГАЕМ позже.** Источники за вчера собираются:
   чатбокс 00:00, Bitrix 03:00, **планы/чек-ины ~05:00 МСК**. Текущая генерация 06:00 МСК — слишком рано
   (час на весь ночной разбор графа после чек-инов мало). Сдвигаем отчёт на **позже 05:00 с запасом на
   обработку** (ориентир 07:00–08:00 МСК; точное время — в ТЗ, после готовности всех источников).
   «12:00»/промежуточный дневной срез не вводим — отчёт по-прежнему утренний за прошедшие сутки.
2. **Bitrix + чатбокс → СЫРЬЁ переписки целиком** (`*Message.text` с авторами `authorName` /
   `senderName`+`senderType`), не дневные саммари. Следствие: нужен бюджет токенов и защита от
   переполнения при большом трафике (приоритизация/обрезка по объёму), но базово — полная переписка
   за день с подписью «кто говорил» и различением сотрудник/клиент.
3. **Голос сотрудника → забираем из ГРАФА по авторству, БЕЗ нового агента.** Ночной разметчик
   (`block-ingest`) уже извлекает из всех разговоров идеи/риски/боли/мысли и проставляет автора.
   Не заводим новый агент — добавляем выборку «что сотрудник X высказал за день» по авторству:
   идеи → `Idea`, риски/боли → `Insight`, прочее → `IdeaBlock`. Требует проверки (см. ниже):
   надёжность проставления авторства на блоке и резолв спикеров Битрикс/чатбокс в `Person`.
4. **Модель и лимиты.** Оставляем DeepSeek (Pro, большой контекст — должен справиться с объёмом).
   Жёсткий `maxTokens` (сейчас 8000) снимаем. В план — нагрузочные тесты на реальном объёме
   (сырьё Битрикс/чатбокс + сигналы + голос сотрудника) ДО выката, чтобы подтвердить, что влезает.

## Что это меняет в архитектуре первого этапа (вход)

- **Новый сборщик в дневном пакете**: Bitrix + чатбокс — читать `*Message` за день, группировать по
  автору, резолвить `authorExternalId`/`senderExternalId` → `Person` (сотрудник) vs клиент.
- **Забор «голоса сотрудника» из графа** (НЕ новый агент): выборка `Idea`/`Insight`/`IdeaBlock` по
  авторству (`authorPersonId`) за день — переиспользуем разметку `block-ingest`. Требует проверки
  надёжности авторства на блоке и резолва внешних спикеров (Битрикс/чатбокс) в `Person`.
- **Единый резолв в `Person`**: `userId` (помощник/чат/free-note) и `externalId` (Bitrix/чатбокс) →
  `Person`. Без него «подписано сотрудником» не гарантировано.
- **Достать `plansJson`/`donesJson`** чек-инов в дневной пакет — для секции «Отчётность и план↔факт».
- **Probe** — починить атрибуцию (автор ответа) или оставить вне scope.

## Слой 2 — сигналы (блокеры / риски-боли / идеи): как забирать (решено 2026-06-29)

**Состав — три потока:**
- **Блокеры** — `IdeaBlock` (`signalType=blocker`), с `confidence`.
- **Риски/боли** — `Insight` (из signalType `pain`/`risk`/`churn_risk`/`objection`) + «замолчавшие темы»
  (`theme-silence-detector` `@Cron('0 4 * * *')` ежедневно создаёт Insight-`silence`).
- **Идеи** — `Idea` (из `idea`/`feature_request`), с `weight` / `supporterCount` / `supporters` / `status`.

**Повторяемость/тренд УЖЕ готовы и ЖИВЫЕ — новый детектор НЕ нужен.** Пересчитываются синхронно при каждом
повторном наблюдении (`Specialist35Service.recalcMetrics`, окно 7д vs 30д), не cron:
- `Insight.dynamicLabel` ∈ `growing`/`spike`/`stable`/`declining` — готовый признак «растёт/всплеск».
- `Insight.sourceBlockIds.length` — число наблюдений (повторяемость).
- `Insight.frequencyScore` — доля в общем шуме компании; `dynamicScore` — сила тренда (ratio 7д/30д).
- `Idea` — рост `supporterCount`/`weight`/`lastDiscussedAt`.
- (`topic-recurrence-detector` `@Cron('0 5 * * 1')` недельный → `RecurringTopic` за 90д, ≥5 упоминаний —
  это «хронические темы за квартал», НЕ дневная подсветка. Для дня используем `dynamicLabel`.)

**Три среза для дневного отчёта:**
| Срез | Условие | Метка |
|---|---|---|
| Новое сегодня | `firstObservedAt` в окне дня, 1 наблюдение | 🟢 новое |
| Растёт / всплеск | `dynamicLabel ∈ {growing, spike}` | 🔴 набирает обороты |
| Повторяется | `sourceBlockIds.length ≥ 3`, `stable` | 🟡 системное |
| Горит сейчас | `status active/mitigating`, `severity high/critical` | продолжает тлеть |

**Что доделать (дёшево — всё посчитано, дневной отчёт сейчас эти поля выбрасывает):**
- В выборку `Insight` добавить: `dynamicLabel`, `sourceBlockIds` (count), `frequencyScore`, `lastObservedAt`.
- В выборку `Idea` добавить: `supporterCount`, `weight`, `status`, `lastDiscussedAt`.
- Подать агенту с пометкой среза → в отчёт «риск молчания, всплыл ×3, растёт ⚠️→🔴».

**Развилка А/Б (как считать повторяемость) — СНЯТА:** читаем готовый `dynamicLabel`, ничего не считаем и
не заводим дневной детектор.

Источники: `schema.prisma` (Insight 6540–6622, Idea 6702–6757); `specialist-3-5-insights.service.ts:333–416`
(recalcMetrics); `daily-digest.service.ts:561–575, 689–698` (текущая выборка сигналов).

## Проверка авторства сигналов — результат (2026-06-29)

**Вердикт:** тезис «всё подписано, надо просто забирать» — ВЕРЕН в основе. На пути сырьё → граф авторство
сохраняется для разговорных источников (встречи, чаты, Битрикс, чатбокс). Но подпись лежит в ТРЁХ разных
местах, и есть инженерные оговорки.

**Где хранится подпись автора-сотрудника:**
| Сущность | Поле подписи | Надёжность |
|---|---|---|
| `IdeaBlock` (мысли/блокеры/прочее) | НЕ на блоке; на `IdeaBlockEvidence.authorPersonId` (+ `commitmentAuthorPersonId` только для commitment) | заполнено для встреч/чатов/Битрикс-чатбокс с привязкой; `null` для bot/email/web_form/части meeting_report/внешних |
| `Idea` (идеи) | `Idea.createdByUserId` — это **User**, не Person (есть индекс) | `null` для `client_request` (клиентские) |
| `Insight` (риски/боли) | прямого автора НЕТ; косвенно через `sourceBlockIds` → evidence; есть `personSubjectIds` | через блоки |

**Битрикс/чатбокс (подтверждено):** per-message авторство; резолв `BitrixUser.linkedPersonId` /
`ChatboxMember.linkedPersonId` → `Person`; менеджер → `Person.id`, клиент → `null` (верно). Доходит до
`IdeaBlockEvidence.authorPersonId`.

**Что доделать, чтобы «просто забирать» заработало:**
1. **Выборка «голос сотрудника за день»** — не одна колонка, а 3 пути: блоки/мысли → через
   `IdeaBlockEvidence(authorPersonId, sourceTimestamp)` + JOIN `IdeaBlock` (группировка по `signalType`);
   идеи → `Idea.createdByUserId`; риски/боли → косвенно через `Insight.sourceBlockIds`.
2. **Новый индекс** `IdeaBlockEvidence(tenantId, authorPersonId, sourceTimestamp)` — иначе полный скан
   (миграция).
3. **Обработка `null`-авторства** — внешние источники без подписи; для отчёта берём подписанные или метим
   «без автора».
4. **`userId` vs `personId`** — `Idea` подписана User, остальное Person; нужен единый резолв `Person.userId`.

Источники: `schema.prisma` (IdeaBlock 3416–3604, Insight 6540–6622, Idea 6702–6757);
`block-ingest.worker.ts` (resolveEvidenceAuthor 1847–1901, persist 1373); `bitrix-ingest.service.ts:258–298`;
`chatbox-ingest.service.ts:310–363`.

## Виджеты дашборда после текста — текущее устройство и что добить (2026-06-29)

| Виджет | Группировка сейчас | Бэк |

**Готово на бэке, но НЕ подключено в дашборд:**
- **Причины рисков** — `causeCategory` (process_gap / tooling / communication / role_skill / priority /

**Что добить для комплексного дашборда (ПРИНЯТО владельцем 2026-06-29 — все три группировки):**

2. ✅ **Риски — группировать по причине** (`causeCategory`): процессы / инструменты / коммуникация / люди. Бэк готов.
3. ✅ **Идеи — кластеризовать** (`IdeaCluster`): похожие в один кластер («3 человека про онбординг»). Бэк готов.
4. Зависшие задачи — оставить как есть (группировка по человеку уже есть).
5. Подсветка повторяемости (`dynamicLabel`) на рисках — уже есть, сохранить.

## Ось «Команда» и конфликты между сотрудниками (исследуется 2026-06-29)

**Договорённость:** ось «Команда» (и секция «что помешало») в дневном отчёте должна показывать
**конфликты и трения между сотрудниками** — это мешает работе. В реальном дашборде они УЖЕ ловятся
(Лента «Конфликт (idea_block): противоречие», риски «трения и коммуникационные проблемы», «конфликты
между сотрудниками»); в разметке `block-ingest` есть `signalType` = `team_friction` / `process_friction`.

**Результат проверки (по коду, 2026-06-29):**
- **Детект конфликтов ЕСТЬ — это два отдельных агента** (не просто signalType общей разметки):
  - `PersonalRelationBuilderWorker` — срабатывает на `signalType=team_friction/process_friction` (из
    разговоров и встреч) → создаёт `EntityLink` типа `conflicted_with` между парами Person.
