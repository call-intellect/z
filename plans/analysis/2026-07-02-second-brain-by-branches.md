> Цель разбора: доказать, стоит ли собрать всё знание компании (темы, регламенты, процессы, документы, решения) в ОДНО структурированное место по 12 веткам компании — и в каком виде. Внутренняя IA-фича (структура/навигация), рынок покрыт [[2026-07-02-notion-agent-teardown-and-borrow]].
> Следующий шаг → архитектура (solution-blueprint): plans/architecture/2026-07-02-second-brain-by-branches.md
> Связь: [[2026-07-02-living-topic-space]] — живая страница темы это ЛИСТ; этот разбор про ХРЕБЕТ (структура по веткам).

## 1. Рамка проблемы
**Мысль владельца:** «мы закладывали 12 веток компании — если это есть, надо визуализировать/структурировать; и регламенты/инструкции/документы — это тоже знание текстом, как живая страница темы; хочу, чтобы всё хранилось в одном месте».

**Iceberg:** симптом — «12 веток только фильтр» + «регламенты в отдельном разделе». Корень — **знание компании собрано, но разложено по 7 разрозненным разделам и плоско; нет верхнеуровневой структуры компании, по которой человек ориентируется**.

**Формулировка:** «менеджер/руководитель не может окинуть знание компании одним взглядом по областям и провалиться от области → к теме → к регламенту, потому что темы, регламенты, процессы, документы, решения живут в разных разделах и не сгруппированы по 12 веткам». Метрика «решено»: путь «область компании → тема/регламент» проходится из одного места; ноль «в каком разделе это лежит?».

**Роли Z:** руководитель (карта компании за 30 сек), менеджер (всё по своей области в одном месте), новый сотрудник (онбординг по областям), админ Org.

## 2. Что уже есть в коде (baseline, факты)
- **12 веток жёстко заложены** — `enum ThemeBranch` [schema.prisma:834]: strategy, clients, sales, marketing, product, operations, team, finance, technology, production, partnerships, legal. Каждой теме LLM проставляет `branch` ([theme-classification.service.ts]).
- **Ветка сейчас = только фильтр/бейдж** — [ThemesClient.tsx:35] `BRANCH_OPTIONS` (фильтр), бейдж на карточке темы. Верхнеуровневой «карты по веткам» нет; темы — плоский список.
- **Хаб «Память» уже есть, но плоский по типам** — [memory/page.tsx]: плитки «Решения», «Оцифровано» (регламенты/процессы/инструкции/политики), «Темы», «Сущности», «Таблицы», «Идеи», «Сигналы» + ссылка на `/chat`. Это сетка реестров, НЕ структура по веткам.
- **Знание разложено по отдельным модулям/страницам:** `regulations` (Regulation [schema:6145] + Instruction [schema:6208]), `processes` (Process [schema:5850]), `documents` (Document [schema:5309]), decisions, themes — свои разделы `/regulations`, `/processes`, `/documents`, `/memory`, `/themes`.
- **Связки с графом УЖЕ существуют (ключевой факт):** Regulation/Instruction/Process несут `entityId` (уникальная связь с сущностью графа); Document несёт `attachedThemeId` (прямая привязка к теме); сущность связана с темами через `ThemeEntity`; тема несёт `branch`. То есть цепочка **регламент → сущность → тема → ветка** и **документ → тема → ветка** уже прослеживается.

**Пробел:** (1) нет верхнего уровня «карта компании по 12 веткам» с наполнением; (2) регламенты/процессы/документы/решения не собраны под веткой/темой в одном месте; (3) у регламента/процесса нет прямой ветки (только через сущность→тему, и то не всегда — сущность может не быть ни в одной теме).

## 3. Gap-таблица «что нужно × что есть × дельта»
| Возможность | Что есть сейчас | Дельта / что строить |
|---|---|---|
| Карта компании по 12 веткам | ветка — только фильтр тем | верхний экран: 12 веток + наполнение (N тем/регламентов/решений, сигнал) |
| Всё знание ветки в одном месте | разложено по 5 разделам | экран ветки: темы + регламенты + процессы + документы + решения вместе |
| Регламент рядом со своей темой | связь через `entityId`→сущность→тема есть, не показана | показать регламенты/документы на живой странице темы (дёшево — связки есть) |
| Ветка у регламента/процесса | нет (только `entityId`) | либо деривить через сущность→тему, либо классифицировать (branch на сущность/регламент) |
| Единый вход «второй мозг» | хаб «Память» плоский по типам | эволюция хаба в структуру по веткам (не плодить ещё раздел) |

## 4. Матрица вариантов
**Критерии (ограничения Z):** ценность (карта компании) · дешевизна (что уже связано) · надёжность (полнота карты — всё ли попадёт в ветку) · не-плодим-разделы (консолидация, не добавка) · соответствие AI-COO.

| Критерий | A: как есть (плоско) | B: карта по веткам, ветку ДЕРИВИТЬ через сущность→тему (read-time) | C: карта по веткам + хранить `branch` на регламенте/процессе/документе (классификатор) |
|---|---|---|---|
| Ценность (карта) | низкая | высокая | высокая |
| Дешевизна | — | **высокая** (связки есть, ничего не мигрируем) | средняя (миграция + классификатор веток) |
| Полнота карты | — | **средняя** (регламент без темы → «Не отнесено») | высокая (всё получает ветку) |
| Не плодим разделы | — | ✓ (эволюция хаба «Память») | ✓ |
| Риск | — | часть знания в «Не отнесено» | миграция + LLM-классификация регламентов |

**Рекомендация: B на старте, C как дозревание.** Первая версия — деривить ветку через существующие связи (`attachedThemeId`, `entityId→ThemeEntity→theme.branch`), нераспознанное — в корзину «Не отнесено»; параллельно переиспользовать существующий branch-классификатор (`theme-classify` уже даёт `branch`), чтобы дозаполнять ветку регламентам/процессам, у которых нет темы. Почему: связки уже есть → дёшево показать карту немедленно; хранить branch везде — дозревание для полноты, не блокер первого показа.

**JTBD:** «окинуть компанию по областям» (карта веток), «всё по области в одном месте» (экран ветки), «регламент рядом с темой» (лист — living topic page + его регламенты/документы).

## 5. Рекомендация (ADR)
- **Эволюционировать хаб «Память» в структуру по 12 веткам** (не плодить новый раздел — консолидация, принцип «упрощаем=консолидируем»).
- **Ветку деривить через существующие связи**, «Не отнесено» — явная корзина; дозаполнять классификатором как дозревание.
- **Living topic page (одобрено)** — лист; добавить в неё показ регламентов/документов темы (дёшево, связки есть) — первый шаг «в одном месте».
- **Не переносить и не ломать** существующие разделы `/regulations` `/processes` `/documents` — они остаются как «список типа», карта веток — надстройка-навигация над теми же данными (как linked-view, не копия).

## 6. Открытые вопросы к владельцу (с рекомендацией)
1. **Ветку регламентам/процессам — деривить или классифицировать сразу?** — *Рекомендую: деривить на старте + «Не отнесено», классификатор дозреванием.* Дёшево показать карту немедленно; полнота — потом.
2. **Карта веток — заменяет хаб «Память» или добавляется вкладкой?** — *Рекомендую: становится главным видом «Памяти», плоские реестры — вторичной вкладкой «Все реестры».* Консолидация, а не ещё один раздел.
3. **Регламенты/документы на живой странице темы — в это ТЗ (living-topic-space) или в новое?** — *Рекомендую: лёгкую связку в текущее ТЗ, полную карту веток — в новое.* Первый шаг «в одном месте» дёшев и сразу ценен.
4. **12 веток — фиксированы или владелец может переименовать/скрыть неактуальные?** — *Рекомендую: на старте фиксированы (как в коде), переименование ярлыков — крутилкой позже.* SMB редко нужны все 12; скрытие пустых — UX-деталь.

## 7. Ограничения и непроверенное
- **Полнота деривации ветки не замерена** — доля регламентов/процессов, чья сущность попадает в тему с веткой, на реальных данных неизвестна; «Не отнесено» может быть большим на старте → аргумент за классификатор.
- **Решения (Decision) под веткой** — связь решения с веткой через сущность/тему предполагается по аналогии; перед blueprint уточнить модель Decision (не читал детально).
- Ветка присваивается LLM (theme-classify) — возможна ошибка отнесения; не критично для навигации, поправимо вручную (дозревание).
