# Фича «Заметки»: полная цепочка планирования за одну сессию

## Что было поставлено

Владелец: «изучи, что у нас есть, и с точки зрения рынка. Понятие заметок — ты на выставке накидал
мыслей, чтобы сохранялись в памяти и вспомнились; красивая страница-лента, полистать по дням;
различать типы (заметка/задача/идея/рассуждение), часть — в задачи; накидал → потом
проанализировать. Глубокое исследование, вывод, предложение, найди лучшее и докажи.» Далее по ходу:
поправка про «личное», согласие с рекомендациями, «оформляй в анализ, блюпринт, ТЗ», «коммит и пуш».

## Как решал

Прошёл всю цепочку скиллов `feature-analyst → solution-blueprint → tz-author`:
- **Baseline по коду ПЕРВЫМ** (vexp не подключён в сессии → Bash+Read по памяти `project_vexp-not-indexed`).
  Нашёл, что ~90% фичи уже есть: захват `/dump` (`DumpClient.tsx` → `WebFormDumpController` →
  `DumpService.createDump`) + `free_note` (`ingestFreeNote` → RawEvent), авто-типизация ~50 `SignalType`
  (`schema.prisma:412`), материализация `Idea`/`Decision`/`Issue`, разбор дня `PersonalDayNarrativeService`.
  **Критично:** `/dump` уже существует как write-only «Текстовая заметка» — чуть не предложил дубль;
  baseline спас. И `IntakeIssue` — готовый прецедент staging-модели «capture→triage→materialize».
- **Рынок — Workflow fan-out на 8 контуров** (7 рыночных + red-team, ~150 источников, 553k токенов).
  Главный вывод: полной петли «накидал → само разложилось по типам → вернулось разобранным» не даёт
  никто (зарубеж/РФ/OSS) — пустая ниша под наш движок. Teardown Notion (2026-07-02) уже закрывал
  командный угол; этот разбор — личный.
- **Red-team переопределил наивную гипотезу:** лента-архив = кладбище (Roam 80/20), подтверждение типа
  на входе убивает захват, второй дайджест не читают. И поднял 152-ФЗ.
- **Поправка владельца сняла юр-блок:** «это НЕ личные заметки как у физлица, а собственные рабочие
  заметки про компанию». 152-ФЗ-гейт → мягкая грань «сырьё↔результат». Переписал анализ.
- **Blueprint** (`plans/architecture/2026-07-08-personal-notes.md`, approved): 5 макетов + «было→стало» +
  живой образец. **TZ** (`plans/tz/2026-07-08-personal-notes.md`, ready-to-implement): 7 фаз, модель
  `Note` зеркалом `IntakeIssue`, grounding-цепочка `Note.rawEventId→IdeaBlockEvidence→IdeaBlock→sourceBlockIds`.

## Что вышло

Три документа (analysis research-complete, architecture approved, TZ ready-to-implement), владелец
одобрил каждое звено, закоммичено+запушено `6ef0db6d` (881 строка). Код не трогал — реализация ждёт
явного «погнали». Прод-операций нет (только планы). Все 8 продуктовых решений + развилка `only_me`
зафиксированы владельцем.

## Чему научился

1. **Baseline ПЕРЕД рынком — иначе предложишь дубль.** `/dump` уже был готовой витриной захвата;
   без чтения кода анализ ушёл бы в «постройте страницу заметок», которая наполовину есть. Gap оказался
   не «нет захвата», а «нет видимости исхода захвата».
2. **Red-team вскрывает failure-mode, но его юр-паника требует сверки рамки с владельцем.** Я поднял
   152-ФЗ как гейт №1 — владелец одной фразой («заметки рабочие, не личные») его снял. Урок: перед тем
   как делать правовой риск блокером, уточнить у владельца саму рамку («что это за данные вообще»).
3. **Архитектура Коры сама подсказывает форму новой сущности.** `IntakeIssue` (staging «capture→triage→
   materialize» с HITL для задач) — точный шаблон для `Note`; `RawEvent` без `userId`-индекса отсёк
   «тонкую проекцию». Свой прецедент > абстрактный «best practice».
4. **Grounding-цепочка для «что Кора сделала»:** `Note.rawEventId → IdeaBlockEvidence(rawEventId,blockId)
   → IdeaBlock.signalType`, а исход — `Idea`/`Issue`/`Decision` с пересечением `sourceBlockIds`. Данные
   для «Кора разобрала: 2 задачи · 1 идея» уже есть, нужен только read-слой.
5. **Устаревший текст скилла — сверять с CLAUDE.md.** `tz-author` инвариант говорил «`prisma:push`, никогда
   `migrate*`» и «отдельный worker-процесс» — оба отменены (версионируемые миграции с 2026-06-05, воркеры
   in-process). CLAUDE.md приоритетнее текста скилла.
