## Контекст (что наблюдал владелец)

- **Telegram-бот «Консьерж»**: голосом попросил найти встречи с «Александром робототехника» и составить список его запросов/болей. Бот задал уместный уточняющий вопрос → владелец ответил «Ищи по всем словам по дате да» → бот ответил **«Готово»** и **не выдал список**. Остановился.
- **Вкладка «Память»**: поиск «сколько встреч с александром робототехника» вернул **сырые чанки** (10 карточек с «уверенность %»), а не умный ответ.
- Две разные сущности (виджет-помощник и «Память») должны быть **одной**.
- Пропала фича **«создать новый чат»** (была точно, неясно когда исчезла).
- Поле ввода маленькое, текст не виден при росте.
- Слово «Консьерж» → «Мастер» везде, где его видит человек.

## Состояние рабочего дерева на момент старта (важно)

Незакоммичено (вероятно параллельная сессия) в `frontend/src/ui/concierge/`:

## Фазы

### Ф0 — Баг ложного «Готово» (ответ прилипает к чужому probe) · `[x]` разбор кода, `[ ]` развилка
Симптом: ответ на уточняющий вопрос засчитался как `probe_reply` к постороннему открытому вопросу Коры («Откуда взялся документ „Дамп от 05.06.2026“»), задача пользователя не выполнена («Готово» без результата).

**Механика (подтверждено кодом):**
- `telegram-bot.adapter.ts:403` → `findOpenProbe` → `:408` `classifyIntent(openProbeQuestion)` → `:415` если `probe_reply && openProbe` → ответ уходит как answer на этот probe; иначе `:431` → `assistant_turn` (консьерж с историей диалога).
- `findOpenProbe` (`:1040`): `notification.findFirst({ where:{ tenantId, recipientUserId, eventType:{in:['probe.question','probe.digest']}, responseStatus:'pending' }, orderBy:{createdAt:'desc'} })` — **берёт последний pending probe ЛЮБОГО возраста, без привязки к текущему диалогу/каналу.**

**Два дефекта класса:**
- **A.** Встроенное уточнение консьержа (`concierge-respond`) не сохраняется как «ожидается ответ в этом диалоге» → ответу не к чему легитимно привязаться.
- **B.** `findOpenProbe` без окна свежести и без проверки «этот probe — последнее, что бот отправил» → старый висящий probe (18 дней) перехватывает несвязанные ответы.

**Минимальный корректный фикс:** не дать старому/нерелевантному probe перехватывать implicit-ответ; тогда ответ доходит до `assistant_turn`, где консьерж продолжает диалог по истории.

**Развилка Ф0 — РЕШЕНО (владелец, 2026-06-23): Вариант А.**
Implicit-ответ привязывается к probe только если этот probe — последнее сообщение бота пользователю в этом канале и он свежий; иначе ответ уходит в `assistant_turn`. Плюс **TTL: pending-probe старше 3 дней авто-закрывается** (не участвует в implicit-матчинге). «Дамп от 05.06» висел 18 дней — именно этот класс и убираем.

### Ф4 (+Ф6) — Умный поэтапный поиск с планом вместо «слепого круга» · `[x]` разбор кода, `[ ]` исследование

**Объединено с Ф6 (владелец, 2026-06-23): про одно и то же — качество поиска/ответа.**

**Разбор кода:**
- Концьерж крутит ReAct-петлю до **`MAX_TOOL_LOOP_ITERATIONS = 5`** (`concierge.service.ts:30`, цикл `:253`): на каждом проходе LLM решает «дёрнуть инструмент» или «ответить», аккумулируя результаты инструментов. **Плана нет** — реактивно, вслепую, до потолка → трата токенов и «Готово» ни с чем.
- При «не нашёл» нет переформулировки запроса и нет уточнения объёма (сколько встреч с X, какие из них релевантны).

**Что хочет владелец:**

3. **Поэтапный поиск с переформулировкой**: достал инфо → понял → сгенерировал новые запросы из неё (как research-агент).
4. База знаний у владельца тоже чинится отдельно — но помощника усиливаем независимо.
