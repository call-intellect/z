# Перестройка графа знаний + умный поэтапный поиск Мастера

## Что было поставлено
Два связанных ТЗ как один заход через `tz-orchestrator`:
- `plans/tz/2026-06-23-knowledge-graph-ingestion-rebuild.md` (Ф1–Ф10) — достройка
  проводки графа знаний (эпизод-узел, провенанс, контекст чанка, суть встречи,
  alias-cache идентичности, гибрид рёбер, поиск с обходом рёбер, Theme.summary,
  включение bi-temporal).
- `plans/tz/2026-06-23-master-smart-search-phase4.md` (Ф4.1–Ф4.7) — слой-агент
  умного поэтапного поиска поверх улучшенного графом retrieval (сторож, гейт
  честности, строгий гейт переспроса, роутер сложности, ReWOO-план, реранк+RRF,
  судья достаточности).

Порядок: сначала весь граф (фундамент = строим базу), затем поиск (агент ищет в
базе). Пересечение — RRF-утилита из Ф7, переиспользованная Ф4.6.

## Как решал
Оркестрация: 8 параллельных Explore-картографов (line-номера в ТЗ устарели,
сверялся по символам), затем фаза за фазой. Схему/миграции/enum/флаги и
R-1-критичный композитный судья делал сам; крупные мех. фазы (контекст чанка,
alias-cache, гибрид рёбер структурные, поиск, theme-summarize, rag-ветки)
делегировал кодерам с самодостаточными промптами и фактчекал маркеры + свой
typecheck/build/тесты.

Коммиты (ветка `feature/2026-06-23-kg-ingestion-and-smart-search`):
- TZ1: Ф1 sourceTitle · Ф2 провенанс-инвариант · Ф3 контекст чанка+R13 · Ф4 суть
  встречи · Ф5 alias-cache · Ф6 гибрид рёбер+судья · Ф8 Theme.summary · Ф7
  поиск RRF+обход · Ф9 bi-temporal ON.
- TZ2: каркас+Ф4.1+Ф4.3 · Ф4.2 гейт честности · Ф4.6 RRF+реранк ·
  Ф4.4+4.5+4.7 итеративная ветка.

4 миграции (sourceTitle, EntityAlias, LinkCreatedBy+system, Theme.summary),
9 новых taskType, 20 крутилок (граф + smart-search), 3 метрики
(kc_block_without_evidence_total, kc_risk_edge_total, rag_abstain_total),
новый cron theme-summarize, сервис ChunkContextService, утилита rank-fusion.

## Что вышло (верификация)
- typecheck (вкл. spec) + build (DI-граф) + lint(0 ошибок) — зелёные на каждой волне.
- Целевые spec'ы зелёные по каждой фазе; финальный полный unit-прогон зелёный.
- R-1 (ложное supersedes/contradicts): композитный судья-скептик fail-closed —
  без подтверждения риск-ребро НЕ создаётся, факт НЕ замещается (тесты).
- R-2 (alias-cache): неоднозначность → null, разных людей не склеиваем (тесты).
- Ф10 (живой re-test на проде) обоих ТЗ — НЕ выполнено: требует подтверждения
  прод-доступа владельцем (см. реестр не-сделанного).

## Чему научился
- Сериализационные хабы (`block-ingest.worker.ts`, `admin-setting-schema-registry`,
  `typed-config`, `llm-router`) трогают почти все фазы → нельзя гонять параллельно;
  TZ1 шёл в основном последовательно, а вот непересекающиеся файлы (concierge /
  chat-v2-orchestration / knowledge-core-retrieval) распараллелил безопасно.
- Конструктор с позиционными spec'ами: новый деп добавлять ТОЛЬКО `@Optional()`
  последним параметром, иначе ломаются юнит-тесты (chunkContext, BlockLinkService,
  metrics, LlmRouterService — все так).
- Контекст-обогащение/новые поля в промпт класть в USER, не в SYSTEM (prompt-cache);
  правка SYSTEM (R13, строгий гейт) — разовый контракт, допустима.
- Кодеры стабильно добавляли нарративные JSDoc вопреки запрету — фактчекать и
  вычищать после каждого.
- Прод-клиент Prisma периодически отставал от schema.prisma (enum/поле) — кодеры
  ловили `bun run prisma:generate`; стоит держать в чек-листе.
