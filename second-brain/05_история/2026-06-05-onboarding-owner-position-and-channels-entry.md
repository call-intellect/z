# Рефлексия — онбординг собственника: должность на «Я» + единый вход в Telegram-каналы

## Что было поставлено

Владелец при первом запуске компании наткнулся на два пробела:
1. На странице «Я» висит «Должность не назначена», и неясно, где её себе задать. Сам собственник в системе есть (Person создаётся при регистрации), но без должности.
2. Привязку Telegram негде найти: страница `/me/channels` не выведена ни в меню, ни на «Я»; вторая страница привязки `/settings/integrations` дублирует логику.

Сначала исследовали код и ответили на вопросы в чате, затем написали ТЗ (`tz-author`), затем реализовали (`tz-orchestrator`).

## Как решал (файлы, коммиты)

Фича оказалась **чисто фронтовой** — весь бэкенд уже готов:
- Должность назначается `PATCH /api/v1/persons/:id { roleId }` (создаёт `PersonRole` + `Appointment`), `GET /me/profile` читает роль из `person.personRoles[0]` ([me.service.ts:86](../../backend/src/modules/me/me.service.ts#L86)). Каталог должностей — `GET/POST /api/v1/roles`.
- Person владельца создаётся в `orgs.service.ts:105` (`ensurePersonForUser`).

Ветка `feature/onboarding-owner-position-and-channels-entry`, 5 фаз = 5 коммитов + ТЗ:
- Ф1 (`25cb46d2`) — пункт меню «Каналы»→`/me/channels`; дедуп на `/settings/integrations`.
- Ф2 (`b97db12c`) — `MyTelegramCard` на «Я».
- Ф3 (`33f16eae`) — `MyPositionCard` (Popover+Command, выбор/создание роли).
- Ф4 (`c2d9bb8d`) — баннер-подсказка.
- Ф5 (`7a9704e8`) — удалён `TelegramLinkSection.tsx`.

Картография и кодинг — суб-агентами; приёмку (греп-маркеры, re-Read, typecheck/lint/build) прогонял сам.

## Что вышло

- `typecheck` / `lint` / `build` фронта — зелёные после каждой фазы и финально.
- Ручная боевая проверка (реальное назначение + привязка в проде) НЕ делалась — оставлена владельцу.
- Prod-операций нет (фронт-only).

## Чему научился (грабли)

1. **Узкий grep при написании ТЗ соврал про состав страницы.** В REALITY-CHECK я написал «`/settings/integrations` рендерит только `TelegramLinkSection`», потому что грепнул `rg "TelegramLinkSection|export default|title"` — и не увидел второй блок `<DestinationsClient />` (направления доставки, отдельная фича). Решение Р1 «redirect страницы целиком» осиротило бы `DestinationsClient`. Поймал это только потому, что **кодер Ф1 честно поднял флаг** в отчёте. Урок: при планировании удаления/редиректа страницы — читать её `page.tsx` ЦЕЛИКОМ (Read), а не точечный grep по ожидаемому символу. Скорректировал на лету: оставил `DestinationsClient`, убрал только дубль-блок Telegram, пункт «Интеграции» сохранил.
2. **Фронт-тип `ListRolesQuery` беднее бэкенда.** Бэк `GET /roles` поддерживает `q` (фильтр по имени), но фронтовый `ListRolesQuery` — только `departmentId`. Не стал расширять тип — грузим весь список (ролей в Org немного) и фильтруем на клиенте. Меньше связанности, надёжнее.
3. **Полезный паттерн дедупа SWR между компонентами:** баннер Ф4 и карточка Ф2 используют один ключ `['me-channels', orgId]` с одинаковым фетчером — SWR дедуплицирует, второго запроса нет. Это дешевле, чем прокидывать статус пропсами или поднимать в контекст.
4. **«Сделай ТЗ» ≠ «сделай код».** Сначала владелец явно попросил ТЗ (только документ), потом отдельно — «пиши код». Разделение соблюдено.
