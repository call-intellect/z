## ПРОБЛЕМЫ (доказаны свежей загрузкой)

### ❌ P1 — Задачи НЕ попадают в трекер: `specialist-3-15-tasks` крашится в проде (Prisma 7 `void`)
За ~6 мин после загрузки: идеи, решения, блокеры, обязательства материализовались, а **задачи в трекере — нет** (issues 32→32, intake 10→10, дельта 0). Все action items осели только блоками-обязательствами (signalType=commitment) в графе.

**Корень подтверждён прод-логами супер-админа** (diag `logs --search "3-15-tasks" --from 2026-06-27`, события 07:11–07:12 UTC, повторяются по политике BullMQ):
```
[ERROR] KNOWLEDGE_GRAPH/specialist:3-15-tasks  specialist:3-15-tasks.failed
PrismaClientKnownRequestError: Invalid `prisma.$queryRaw()` invocation:
Raw query failed. Message: `Failed to deserialize column of type 'void'.
If you're using $queryRaw … try casting this column to any supported Prisma type such as String.`
[ERROR] Specialist315TasksService  specialist-3-15.processBlock: ошибка записи — пробрасываю для повтора (BullMQ retry)
```
Это **не** ограничение source-type «дамп» (первая гипотеза неверна) и **не** дизайн. Это **runtime-баг**: первая же строка транзакции создания задачи —
[`specialist-3-15-tasks.service.ts:184`](../../backend/src/modules/knowledge-core/services/specialist-3-15-tasks.service.ts#L184):
```ts
await tx.$queryRaw`SELECT pg_advisory_xact_lock(hashtext(${block.tenantId + ':' + normTitle}))`;
```
`pg_advisory_xact_lock(...)` возвращает `void`; в Prisma 7 (driver-adapter) `$queryRaw` пытается десериализовать колонку `void` → бросает `PrismaClientKnownRequestError`. Транзакция падает целиком, блок-задача не создаётся, BullMQ ретраит бесконечно.

**Масштаб:** извлечение задач в трекер сломано **на 100% для ЛЮБОГО источника** (встреча/чат/дамп) — не только для синтетики. Это объясняет, почему идеи/решения (`specialist:3-6-ideas: успех`) работают, а задач нет вовсе.

**Тот же дефектный паттерн (`$queryRaw` + `pg_advisory_xact_lock`) есть ещё в:** `issues.service.ts:1946` (advisory-lock на parentId при update), `cycles.service.ts:146`, `checklists.service.ts:358` (последние два — через `$queryRawUnsafe`, поведение надо проверить отдельно). Все они — кандидаты на тот же краш под Prisma 7.

**Направление фикса:** для void-возвращающих операторов использовать `$executeRaw`/`$executeRawUnsafe` (не десериализует колонки), либо кастовать: `SELECT pg_advisory_xact_lock(...)::text`. Совпадает с pitfall'ом Prisma 7 из CLAUDE.md.

**Следствие:** трекер не наполняется из текста; кросс-канальный дедуп задач и жизненный цикл карточки заблокированы этим багом.

### ❌ P2 — Фрагментация сущностей (одна сущность → несколько)
Свежие сущности расщепляют один смысл:
- retention → **3 отдельные сущности**: `metric:retention пользователей` + `metric:удержание за месяц` + `metric:недельный возврат` — при том что само решение прямо приравнивает retention = удержание.
- `vendor:Битрикс` (новая) НЕ слита с уже существующей `technology:Битрикс24` (baseline) — две карточки одного вендора.
**Корень (тот же, что в «Ооо луа», где Битрикс расщеплён на 7 карточек):** ключ резолва `(type, lower(name))` — разные `type` никогда не сливаются; кросс-типовый/синонимный merge не срабатывает.

### ⚠️ P3 — «exponential backoff» классифицирован как РЕШЕНИЕ, потерян как идея и как задача
В Тексте 3: Анна «предлагаю реализовать backoff» (предложение → должно быть идеей), Михаил «беру реализацию backoff» (поручение → должно быть задачей). По факту создано **решение** «Реализовать exponential backoff для запросов к Битрикс API». Предложение Анны не стало идеей, задача Михаила не создана. Класс «идея vs решение vs задача» из одного контекста разведён неверно.

### ⚠️ P4 — «Не создавать задачу по жалобе плеера» извлечено как РЕШЕНИЕ
Реплика Елены «отдельную задачу пока не завожу» (бытовое не-действие) материализовалась решением «Не создавать задачу по жалобе пользователя на плеер». Шум в реестре решений: бытовой отказ-от-действия ≠ зафиксированное решение команды.

### ⚠️ P5 — На уровне блоков нет кросс-source склейки задачи «база контактов»
Задача «актуализировать базу контактов» присутствует как **два отдельных блока-обязательства** (из Текста 1 и Текста 3: «Дарья актуализирует базу до среды» и «Дарья обязуется почистить мёртвые адреса… до среды»). Блоки по источникам не сливаются (ожидаемо — дедуп задумывался на уровне трекера, который не наполнился, см. P1).

### ⚠️ P6 — Другие падающие воркеры в проде (из супер-админ логов, 2026-06-27)
`diag logs --at-least ERROR --from 2026-06-27` → 160 ошибок за день. Кроме задач (40 событий, P1):
- **BlockIngestWorker / kc.block-ingest** (21): «все окна LLM-извлечения провалились (taskType block-ingest) — RawEvent НЕ ingested, job уходит в failed». Часть RawEvent не извлекается вовсе из-за сбоев LLM-провайдера → извлечение флапает (часть наших дампов могла частично не пройти).
- **StrategicAlignmentWorker / kc.strategic-alignment** (12): «LLM вернул невалидный JSON: Unrecognized token 'Г'/'П'», «LLM вернул пустой ответ», «expected number, received undefined». LLM отдаёт прозу/битый JSON, схема не проходит — нет защиты парсинга/ретрая на этом воркере.

### ❌ P7 — Закрытие задачи из разговора (TaskClosureCandidate) не срабатывает
Обходной тест жизненного цикла: создал Issue вручную (MTG-25 «Актуализировать базу контактов», открыта), затем дозалил дамп с явным сигналом исполнения («База контактов готова и актуализирована… задача выполнена и закрыта»). За ~2.5 мин:
- В `GET /api/v1/pending-actions` **не появился** кандидат на закрытие (source `task_closure`); присутствуют только `conflict`/`curation`/`probe`.
- Задача осталась открытой (`completedAt=null`).
- Прод-логи (diag): за сегодня **нет** событий `task.completion_signalled`, `done_item`-роутинга, активности `RouterService`. Ранее (03:00) единственная запись `TaskCompletionHandler`: «task-closure: embed блока не посчитался — пропуск матча».

**Вывод:** путь «сказали „выполнено“ в тексте → кандидат на закрытие» на практике не доходит до создания кандидата. Причина-кандидат: (а) блок не классифицируется сигналом `done_item`/`task_completed` → `RouterService` не эмитит событие; и/или (б) флап эмбеддингов (см. P6) обнуляет матч. Требует разбора в ТЗ. Жизненный цикл карточки «исполнение → закрытие» **не подтверждён**.
