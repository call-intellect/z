## TD-1. α-9 LLM-извлечение миссии/видения/стратегии

**Что:** автоматическое наполнение `CompanyProfile.missionJson`, `visionJson`, `strategyJson` из записанных встреч (стратсессии, плановки CEO) и загруженных документов.

**Что есть сейчас:** ручной ввод через UI `/company`. Воркер [company-profile-builder.cron.ts](backend/src/modules/company-foundation/workers/company-profile-builder.cron.ts) — пассивный страв-мэн, только lazy-create.

**Почему отложено:**
- Миссия — критичный документ. Ошибка LLM здесь дороже, чем в дайджесте: компания будет строить решения на неверной формулировке.
- Требует комплексных извлечений из множества источников (8-10 встреч за квартал + загруженный pitch deck + старые регламенты). Это работа δ-1 Orchestrator, который пока не реализован.
- Нет user-pull сигнала: текущие клиенты заполняют миссию руками за 15 минут.

**Триггер активации:** появление δ-1 + жалоба клиента «не хочу руками».

## TD-2. β-6 Experiment Tracker

**Что:** реестр A/B-гипотез исправлений процессов. «Попробовали ввести daily standup → через 2 недели проверили: блокеры упали на 40%». Модели `Experiment`, `Hypothesis`, `Variant`, `Outcome` + страница `/experiments` + интеграция в Decisions Registry.

**Что есть сейчас:** ничего. В Decision есть поле `actualOutcomes` (β-3), но это пост-фактум, не запланированный эксперимент.

**Почему отложено:**
- Отдельный продукт-домен, не «доделка COO».
- Минимум 3-4 недели разработки + дизайн (эксперимент — сложная UX-сущность, не таблица).
- Прямо сейчас COO без неё работает: фиксирует решения, через 30 дней руками проверяет результат.

**Триггер активации:** клиент попросит явное «проверь, помог ли наш эксперимент» — пока ни один не просил.

## TD-3. γ-3 CrossFunctionalProcess + Handoff

**Что:** межотдельные процессы с handoff'ами (sales → onboarding → delivery, маркетинг → продажи, разработка → саппорт). Модели `CrossFunctionalProcess`, `Handoff` с participants / SLA / триггерами. Страница `/processes/handoffs` с виджетом «где сейчас потери на стыке».

**Что есть сейчас:** одиночные `Process` + `ProcessStep` (α-7), но без понимания, что process пересекает несколько отделов.

**Почему отложено:**
- Зависит от α-7 доделки (ProcessTemplate с DecisionPoint и Handoff-фундаментом). Без этого CrossFunctionalProcess строить не на чем.
- 3 недели минимум.
- COO-дашборд показывает team-frictions (`EntityLink.relationType='conflicted_with'`) — это уже частично закрывает потребность.

**Триггер активации:** клиент пожалуется «у нас падает онбординг — продажи передают плохо, никто не понимает кто виноват».

## TD-4. δ-2 ProactiveWatcher

**Что:** превентивный детектор паттернов, который сигнализирует ДО того, как проблема стала повторяющейся. «Похоже, через 2 недели у вас будет проблема с X — потому что Y и Z».

**Что есть сейчас:** Probe Agent (β-5) — реактивно дёргает куратора по конкретному поводу. Insights Radar (β-4) — обнаруживает паттерны, но постфактум.

**Почему отложено:**
- Зависит от δ-1 Orchestrator + от 3+ месяцев продакшен-данных (чтобы было на чём учить детектор).
- Без статистики проактивные сигналы будут шумом.
- Probe Agent закрывает ~70% потребности в проактивности.

**Триггер активации:** β-8.3 в проде ≥ 3 месяцев + накоплены данные для тренировки.

## TD-5. Раздельные RBAC-секции COO Dashboard

**Что:** разделить право `dashboard_operations.read` на отдельные ресурсы: `dashboard_operations.temperature` (настроения), `dashboard_operations.commitments` (обещания), `dashboard_operations.maturity` (зрелость), и т.д. Чтобы admin Org мог видеть одно, но не видеть другое.

**Что есть сейчас:** единое право `dashboard_operations.read` для `coo+owner+admin+super_admin`.

**Почему отложено:**
- Решение «кому что показывать» — не техническое, продуктовое. Сейчас нет user-pull.
- Реализация — час работы (расширить policy.csv + добавить проверки).

**Триггер активации:** клиент скажет «у нашего admin'а не должно быть доступа к настроениям» или «у руководителей команд должен быть доступ к зрелости их домена».

## TD-6. Per-Org часовой пояс ежедневного отчёта

**Что:** сейчас отчёт генерируется в 01:00 МСК глобально. Если клиент в Казахстане (UTC+5, +2 к МСК) — у него отчёт готов в 03:00 по местному, но всё ещё успевает к рабочему дню. Если клиент в Калининграде (UTC+2, -1 к МСК) — готов в 00:00, тоже норм. Реальная проблема — за пределами часовых поясов СНГ.

**Что есть сейчас:** глобальный cron `0 22 * * *` UTC.

**Почему отложено:**
- ICP Z — РФ + СНГ (один часовой пояс ±3 часа от МСК).
- Преждевременная оптимизация для несуществующих клиентов.
- Реализация — 1-2 дня (cron уже умеет фильтровать по `Org.timezone`, см. `daily-checkin-prompt.cron`).

**Триггер активации:** первый клиент вне СНГ.

## TD-7. Email-рассылка ежедневного / недельного отчёта

**Что:** доставка дайджестов на почту COO/owner вдобавок к Telegram + дашборду.

**Что есть сейчас:** только Telegram (через α-1 `ConversationalService`). Email-инфраструктура для outbound уведомлений — частично есть (transactional через SMTP `mail.hosting.reg.ru`), но без шаблонизации операционных дайджестов.

**Почему отложено:**
- Зависит от Phase 4 трекера (email-инфраструктура + email-to-task IMAP-парсер).
- Не критично: Telegram охватывает ICP Z (российский средний бизнес).

**Триггер активации:** клиент попросит «у нас не Telegram, на почту шлите».

---

## TD-8. Backfill старых дат для ежедневного отчёта

**Что:** генерация отчётов задним числом за период до раскатки β-8.3.

**Что есть сейчас:** только начиная с даты включения cron.

**Почему отложено:**
- Сейчас никто не попросит — отчёты исторические никому не нужны до первой генерации.
- Реализация — полдня (admin-эндпоинт + range-цикл).

**Триггер активации:** клиент после месяца использования попросит «покажи, что было 3 недели назад».

---

## TD-9. Per-Org override Telegram-рассылки

**Что:** сейчас тумблер `operations.daily_digest.deliver_to_telegram` — глобальный (на платформу). Логичный следующий шаг — per-Org override (одна Org хочет, другая нет).

**Что есть сейчас:** глобальный `AdminSetting`.

**Почему отложено:**
- Сначала надо понять, **сколько Org реально включит**. Если все 100% — глобальный тумблер достаточен. Если 50/50 — нужен per-Org.
- Реализация — 1 день (`OrgSetting` + наследование от `AdminSetting`).

**Триггер активации:** первая Org попросит выключить, при глобальном `true`.

---

## TD-10. History snapshots `maturityScore`

**Что:** хранить ежедневные snapshot'ы `CompanyProfile.maturityScore` + `FunctionalDomain.completeness`, чтобы строить график «как менялась зрелость за квартал».

**Что есть сейчас:** только текущее значение (перетирается ежедневным cron в 05:00 UTC).

**Почему отложено:**
- Виджет зрелости в β-8.3 только релизится. Пока никто не попросит «покажи динамику».
- Реализация — неделя (модель `MaturitySnapshot` + расширение cron + chart-виджет).

**Триггер активации:** β-8.3 в проде ≥ 1 месяц + COO попросит «как меняется зрелость».
