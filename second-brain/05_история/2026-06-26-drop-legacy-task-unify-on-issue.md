# Полный дроп legacy-модели `Task` — унификация задач на `Issue`

## Что было поставлено

ТЗ [`2026-06-25-drop-legacy-task-model-unify-on-issue.md`](../../plans/tz/2026-06-25-drop-legacy-task-model-unify-on-issue.md) (Ф0–Ф10): задачи жили в двух параллельных моделях БД (`Task` + `Issue`), миграция плодила третью копию `meeting_legacy` в обход дедуп-гейта → размножение дублей. Цель — убрать `Task` полностью, оставить единый слой `Issue`. Владелец: «опираясь на последний код, новая ветка веером, веди ТЗ-оркестратором, вопросы решай сам, иди до конца».

## Как решал

Оркестрация фаза-за-фазой суб-агентами (картография → промпт кодеру → независимая приёмка мной → ревью → покоммитная фиксация). Ветка `feature/drop-legacy-task-unify-issue` от текущей (не main/dev).

- **Картография** — параллельный Workflow из 8 read-only агентов верифицировал дрейфующие якоря ТЗ и вернул дословные сниппеты. Окупился: line-номера ТЗ почти везде сместились на 3–60 строк.
- **Ф0–Ф2** (`e7c8519b`, `b1da4066`): diag-разведчик, GIN-индекс, переписан `migrate-task-to-issue.ts`, новый collapse-backfill, юнит-тесты.
- **Ф3–Ф6 + Ф7a** — один батч из 5 параллельных кодеров (непересекающиеся файлы), затем единый typecheck + покоммитная фиксация (`270c66b1`, `f41f79b4`, `b79abc35`, `515407f2`, `e0dc1257`).
- **Ф7b** (`95f3b963`): бэк-эндпоинт `?linkedMeetingId` + фронт-перевод вкладки встречи на tracker.
- **Ф9** (`6aa4c0b7`): чистка 5 флагов. **Ф8** (`ec41a025`): дроп схемы + миграция + pre-migrate хук.
- **Ф10**: сквозная верификация; починка кросс-фазных регрессий (`309d1638`) + 2 чужих красных (`629d9bf6`, `19d09ca5`).

## Что вышло

typecheck/lint/build **back+front зелёные**; полный сьют **6468 passed**. Осталось 2 предсуществующих env-фейла (ssrf `::1`/IPv6, webhooks Redis :6379) — не из этого ТЗ, зелёные в CI. Прод-выкат — одной командой `apply-prod-deploy --with-schema` (авто-бэкап → перенос → дроп).

## Чему научился

1. **Порядок схема-фаза vs STEPS в `apply-prod-deploy` — load-bearing.** `runSchemaPhase` (`--with-schema`) делает `prisma migrate deploy` ДО цикла `STEPS`. Значит деструктивную дроп-миграцию НЕЛЬЗЯ совмещать в одном деплое с миграцией данных, если та живёт в STEPS — таблица дропнется раньше переноса. Решение: перенос данных встроен в `runSchemaPhase` ПЕРЕД `migrate deploy` (рядом с существующим `preDedupe`-хуком, тот же паттерн «data-fix перед schema-migration»). Это сделало дроп безопасным в один деплой, а не в два релиза.

2. **Скрипт, который должен пережить дроп своей же модели, читает её через raw SQL.** `migrate-task-to-issue.ts` после удаления `model Task` из `schema.prisma` не скомпилировался бы с `prisma.task.*`. Перевод чтения `Task`/`TaskSource(taskId)` на `$queryRaw` + guard `to_regclass('public."Task"')` (no-op после дропа) — канон для «migrate-then-drop». Проект требует prisma-миграцию для дропа (не db push), поэтому модель уходит из клиента — raw SQL обязателен.

3. **`grep prisma.task` НЕ ловит всех читателей Task.** Пропустил: relation-include `meeting.tasks` в публичной шаре (`shares.service`), `import type { Task }` (dead-code метод), и Task-обращения в `backend/scripts/` (мой греп был только по `src`). Их поймал лишь `prisma generate` + сквозной typecheck на Ф8 (удаление relation-поля делает `meeting.tasks` ошибкой типа). Урок: на рефакторинге-сносе финальный gate — это удалить модель и дать typecheck показать всех потребителей; одним грепом по `prisma.<model>` не закрыть (релейшены, типы-импорты, скрипты вне `src`).

4. **Кросс-фазные спек-регрессии ловит только прогон модуля ЦЕЛИКОМ, не «новых файлов».** Кодер Ф5 поменял 5 сервисов, но обновил спеки лишь 2 из них; остальные 3 (`director-dashboard` ×3, `value-recap`, `meeting-roi-scorer`) мокали `prisma.task.count` и падали в рантайме (typecheck их пропускал — мок generic). Покрыл сводный прогон по затронутым модулям. Урок приёмки: после правки сервиса прогоняй ВСЕ спеки его модуля, а не только обновлённые кодером.

5. **Env-фейлы честно отделять от багов.** 2 чужих красных (`getaddrinfo ENOTFOUND [::1]`, `ECONNREFUSED 6379`, BullMQ-таймаут на отсутствии Redis) — ограничения песочницы, код корректен, в CI зелёные. «Починить» их = ослабить security/queue-тесты. Правильно — не трогать и явно сообщить владельцу. А вот чужой `accounts`-тест (`demo_observer` vs `owner`) был реальным устаревшим тестом после онбординг-фикса «своя орга первична» — его привёл к коду.
