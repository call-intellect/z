# Провайдер по подписке + фикс цен в каталоге + реальный баг gpt-4o-mini

## Что было поставлено

Продолжение марафонской сессии. Владелец в разговорном тоне (матом) указал на два прод-бага и один новый запрос:
1. Скриншот smoke-теста провайдера `minimaxio2`: `openai-chat minimaxio2: 400 invalid params, unknown model 'gpt-4o-mini'` — «причём тут 4o модель то, почему тестирование запроса идёт через gpt модель, а не через модель провайдера???»
2. «Где редактирование цен?? Провайдер уже удалён, но цена до сих пор осталась в каталоге!»
3. Новая фича: провайдер может тарифицироваться не по токену, а по фиксированной ежемесячной подписке (упомянул 5-часовые+недельные квоты запросов, как у Anthropic Claude Pro/Max) — учёт стоимости подписки, токены при этом всё равно считаются, просто бесплатны.

## Как решал

**Баг №1 (реальный, не выдумка).** Разобрал `openai-chat.adapter.ts`/`custom-http.adapter.ts` — оба резолвили модель по умолчанию через `provider.defaultModel`, поле которое заполняется ТОЛЬКО у 6 захардкоженных ENV-провайдеров в `ProviderInfoResolver.buildFromEnv` (`anthropic`/`minimax`/`openai-via-proxy`/`deepseek`/`ollama`/`kie`/`grsai`). Для ЛЮБОГО провайдера, добавленного через админку (как `minimaxio2`), это поле всегда `undefined` — реальная DB-модель по умолчанию живёт в ОТДЕЛЬНОМ поле `defaultModelKey` (добавленном в прошлой фиче llm-provider-default-fallback), которое адаптеры просто забыли учитывать. Fallback-цепочка `input.model ?? provider.defaultModel ?? 'gpt-4o-mini'` тихо приземлялась на хардкод. Фикс — `input.model ?? provider.defaultModelKey ?? provider.defaultModel ?? 'gpt-4o-mini'`. Живьём подтверждено на самом `minimaxio2`: smoke-тест из красного (400 unknown model) стал зелёным сразу после рестарта бэка.

**Баг №2 (реальный UX-пробел).** `LlmPricesClient.tsx` вообще не имел кнопки редактирования — только «Добавить цену» (которая на самом деле уже умела «редактировать» через версионирование `effectiveFrom/To`, просто без явного входа в этот сценарий с существующей строки). Добавил «Изменить» на каждую активную строку прайса (открывает тот же диалог, предзаполненный, provider/model залочены). Для «цена удалённого провайдера всё ещё в каталоге» — разобрался, что это НЕ баг: `LlmModelPrice` намеренно хранит историю цен по строке `provider`/`model`, не FK на `LlmProvider` — если удалять цену вместе с провайдером, ломается историческая стоимость уже понесённых расходов (`AiCostDaily` ссылается на старые provider/model). Вместо удаления — бейдж «провайдер удалён» на строке (сверка со списком актуальных `LlmProvider.name`), чтобы не путать.

**Фича подписки.** Полная цепочка `solution-blueprint → tz-author → tz-orchestrator`, с двумя развилками через `AskUserQuestion` (владелец выбрал оба раза рекомендованный простой вариант): (1) только учёт стоимости в эту итерацию, без rate-limit enforcement квоты — это отдельная, куда более тяжёлая инфраструктура (Redis sliding-window, pre-dispatch гейт); (2) сумма подписки в дашборде — разовая строка ровно в день списания (как банковская выписка), не размазывается по дням месяца.

Ключевое архитектурное решение: подписочный платёж — НЕ строка `AiCostDaily` (та per-tenant, используется бюджетами компаний), а отдельная platform-level таблица `LlmProviderSubscriptionCharge` — платформа платит провайдеру, это не расход конкретного клиента. `LlmCostDashboardService.overview()` мёржит её В ТОТ ЖЕ `trend`/`totals.costUsd` только на уровне read-модели дашборда (платформенный вид, без tenant-фильтра), не трогая исходные per-org агрегаты.

Реализация: 3 фазы (схема+bypass в `computeCostUsd` → cron списания+admin CRUD валидация → дашборд+фронт), сделал сам напрямую (не через суб-агентов — паттерн уже был полностью понятен из предыдущей аналогичной фичи в этой же сессии).

## Что вышло

13 новых тестов (bypass ×2, cron ×6, providers-валидация ×4, dashboard-merge ×1), полный backend-прогон 7878/7948 (16 сбоев — все предсуществующие, не мои). Живая browser-QA на реальной локальной БД: назначил `minimaxio2` подпиской $50/мес → бейдж появился → прогнал cron вручную (создал charge) → дашборд показал `subscriptionCostUsd:50` и спайк в графике на дату списания → тестовые данные убраны, провайдер возвращён в `per_token`.

**Найдена и исправлена ещё одна реальная грабля при самой работе (не фичи):** применил сгенерированную миграцию напрямую через `psql < migration.sql` на локальной AGE-базе — таблица ушла в `ag_catalog` вместо `public` (тот же класс проблемы, что уже был в памяти проекта `project-age-search-path-ddl-trap`, просто конкретно СЕЙЧАС забыл `SET search_path TO "public"` первой строкой). Поймал сразу на первом обращении к таблице (`P2021 TableDoesNotExist`), исправил `ALTER TABLE ... SET SCHEMA public` — PK/индексы/FK не пострадали (проверил `\d public.X`).

## Чему научился

- **Один и тот же баг-класс может рецидивировать, даже когда он уже в памяти** — записал усиление памяти `project-age-search-path-ddl-trap`: правило «первая строка миграции — SET search_path» касается ЛЮБОГО способа применения сырого SQL к AGE-базе, не только `prisma migrate deploy`, а и ручного `psql < file.sql`. Нужно реально СВЕРЯТЬСЯ с памятью перед похожим действием, а не полагаться, что раз читал — значит не повторю.
- **«Похожий» баг может оказаться из другого поля.** Пользователь пожаловался на `gpt-4o-mini` — интуитивно можно было подумать про роутинг/маршруты, но реальная причина — два конкретных адаптера читали не то поле провайдера (`defaultModel` вместо `defaultModelKey`). Стоило сразу грепнуть по буквальной строке `'gpt-4o-mini'` в коде — нашлось за один запрос.
- **«Цена осталась после удаления провайдера» — не всегда баг.** Разница между «баг» и «намеренное поведение, которое выглядит как баг» — история цен нужна для расчёта уже понесённых прошлых расходов; UI-подсказка (бейдж) достаточна, удаление данных было бы неверным решением.
