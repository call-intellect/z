## Как делал

### 1. Параллельный аудит — 2 Explore-агента

Один проверил backend (SubscriptionGuard + декораторы), второй — frontend (PaywallBanner/Modal/SubscriptionContext + SubscriptionClient).

**Backend нашёл 3 бага:**
- ❌ Guard не пропускал GET-запросы (нарушение §3.2 ТЗ — DEMO должен иметь read-only доступ).
- ❌ Guard не пропускал `/api/v1/billing/*`, `/api/v1/subscription/*`, `/api/v1/auth/*` пути (зависел только от отсутствия `@RequireSubscription` — уязвимость к ошибке разработчика).
- ⚠ `SubscriptionService.ensureDemo()` существует, но **не вызывается при регистрации Org** — у новых тенантов нет записи `Subscription`. Guard полагался на `?? 'DEMO'`-fallback, но это маскировало проблему.

**Frontend нашёл 3 мелочи:**
- BlockedHero не обрабатывал `PAST_DUE` (пятый статус в enum).
- Тесты `SubscriptionClient.spec.tsx` использовали `seatsBase: 30`, а в реальности константа `BASE_SEATS = 31` — этого не заметили при review.
- `SubscriptionCard` рендерил `subscription.seatsBase + 1` (off-by-one).

### 2. Рефакторинг SubscriptionGuard

`backend/src/modules/billing/guards/subscription.guard.ts`:
- Добавил константу `BYPASS_PATH_PREFIXES = ['/api/v1/billing', '/api/v1/subscription', '/api/v1/auth']`.
- Добавил bypass для `req.method === 'GET' | 'HEAD' | 'OPTIONS'` (read-only всегда пропускается).
- Добавил bypass по path. Логика теперь явная: guard срабатывает ТОЛЬКО на мутирующий метод + не-bypass путь + наличие `@RequireSubscription`.

Тесты `subscription.guard.spec.ts`: было 14, стало 21 (+7: GET/HEAD/OPTIONS + 3 bypass paths + позитивный POST /projects). `makeContext` теперь принимает `method`/`path` и дефолтит к `POST /api/v1/projects` (соответствует основному use-case paywall).

### 3. ensureDemo при создании Org

`backend/src/modules/orgs/orgs.service.ts`: добавил `SubscriptionService` в DI, вызываю `subscriptions.ensureDemo(org.id, tx)` после создания Org внутри `createForOwner`.

`backend/src/modules/orgs/orgs.module.ts`: добавил `BillingModule` в imports. Циклов нет (проверил: AuthModule/RbacModule/MeetingsBalanceModule не зависят от Orgs).

`backend/src/modules/billing/services/subscription.service.ts`: `ensureDemo` теперь принимает опциональный `tx?: Prisma.TransactionClient` — для атомарности с `createForOwner` внутри транзакции регистрации.

### 4. Frontend-фиксы

- `SubscriptionClient.tsx`: `isBlocked` теперь включает `PAST_DUE`; `BlockedHero` имеет title/description для `PAST_DUE`. `SubscriptionCard` теперь рендерит `seatsBase` без off-by-one.
- `SubscriptionClient.spec.tsx`: `seatsBase: 30 → 31` (2 места).

### 5. Фаза 4.2 — read-only индикаторы

Создал:
- `frontend/src/hooks/useCanCreate.ts` — единая точка для UI-блокировок: возвращает `{canCreate, isReadOnly, loading, reason, showPaywall}`.
- `frontend/src/ui/components/PaywallGuardButton.tsx` — обёртка над shadcn `Button`: в ACTIVE-режиме это обычная кнопка, в read-only — приглушённый стиль (`opacity-60`) + tooltip с причиной + клик открывает PaywallModal вместо `onClick`. Это дополнение к глобальному UX (PaywallBanner + 403-interceptor → Modal).
- 6 тестов в `PaywallGuardButton.spec.tsx` (ACTIVE/DEMO/SUSPENDED/data-attribute/loading).

Ключевое решение: НЕ применил `<PaywallGuardButton>` массово к 50+ кнопкам — глобальный UX уже покрыт `PaywallBanner` (на каждой странице через AppShell) + interceptor 403 → `PaywallModal`. `<PaywallGuardButton>` оставлен как opt-in helper для разработчиков, когда нужна явная visual блокировка.

### 6. Фаза 5.1 — миграционный скрипт

`backend/scripts/backfill-demo-subscriptions.ts`: для каждой Org без `Subscription` создаёт `Subscription{status=DEMO}` + `SubscriptionEvent{CREATED}`. Идемпотентен. Зарегистрирован в `backend/scripts/apply-prod-deploy.ts` (phase: `backfill`, `skipBootstrap: true`).

## Чему научился

1. **Aудит-агенты (Explore) на двух подсистемах параллельно сильно экономят время.** Каждый дал структурированный «✅ сделано / ⚠ нужно поправить / ❌ отсутствует»-отчёт со ссылками file:line. На основе этого видно конкретные дельты без перечитывания всего кода.
2. **Defensive coding в guard'е дороже понимания.** SubscriptionGuard был «прозрачным» (срабатывал только при наличии `@RequireSubscription`), что технически выполняло требования ТЗ, но не защищало от ошибки разработчика, поставившего декоратор на GET. Явный bypass по `method`/`path` делает контракт guard'а само-документирующимся.
3. **Бизнес-инвариант важнее «оно работает».** `SubscriptionService.ensureDemo()` существовал, но не вызывался — guard маскировал баг через `?? 'DEMO'`. Это значило, что любой запрос к `SubscriptionService.getByTenant(orgId)` возвращал `null`, не `Subscription{DEMO}`. Грабля скрытая: тесты guard'а зелёные, фронт-расчёты ломались (null vs object).
4. **Off-by-one от прошлой сессии прятался в одном `+ 1`.** Тест `SubscriptionClient.spec` поймал это как «мок=31, рендер=32» — повезло, что тест вообще проверял отображение.
5. **«Закончить полностью ТЗ» ≠ implement everything.** 5.2 (email) и 5.3 (Grafana) — это часы работы и новая инфра. Явно вынес их за scope MVP в ТЗ, чтобы не растягивать commit и не плодить наполовину-сделанные фичи.
