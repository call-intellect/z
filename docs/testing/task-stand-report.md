# task-stand — baseline + доказательство текст-фикса (Т11)

> Прогон: 2026-07-06/07. Тенант — свежая синтетическая «Стрела» (создаётся заново на каждый прогон,
> `TASK_STAND_ORG_A`). HEAD-коммиты штампуются в raw.json (`headCommit`). Судьи majority-of-3 —
> `deepseek-v4-pro`. Стенд гоняет банк 110 через РЕАЛЬНЫЙ конвейер (ingest → block-distill → specialists →
> materialize → auto-triage). Батчи: `b1` (11 сценариев, baseline), `after-fix` (13 сценариев, после Ф5).
> Автогенерируемый scorecard перезаписывается на каждый `report`; это — курированный разбор прогонов.

## 0. TL;DR

- **Т11 (качество текста задачи) — подтверждён и ИСПРАВЛЕН.** Baseline: описание задачи = дословная речь
  постановщика со словами-паразитами. После фикса Ф5 (`plans/tz/2026-07-04-task-text-reformulation.md`):
  описание = короткий структурный текст по сути, факты сохранены. Доказано на meeting-сценариях K.
- **Т1 (осиротевший извлекатель) — худший сценарий ОПРОВЕРГНУТ.** Задачи из встречи/чата создаются живым
  `SpecialistsCombined`. Легаси `TaskExtractionService` работает в изоляции, но дормантен (не вызывается).
- **Новая находка (приоритет): `IssueEmbedWorker` не зарегистрирован** → `Issue.embedding` не считается →
  дедуп/закрытие не находят AI-созданные задачи. ТЗ цикла 2: `plans/tz/2026-07-07-issue-embedding-worker-registration.md`.
- **Находка: block-extraction нестабилен** (`deepseek-v4-flash` не принимает `tool_choice` через прокси →
  ретраи) → конвейер медленный (встреча дозревает >5 мин).

## 1. Доказательство текст-фикса (Т11) — было → стало

Категория **K** (text-quality), meeting-канал, свежий тенант до (b1) и после (after-fix) Ф5:

| Сценарий | BEFORE (b1, сырьё) | AFTER (Ф5, структурно) |
|---|---|---|
| **K-03** | «Пете надо договор с **этими**, с Логистик Плюс, на **три с половиной**, до **15-го числа** оформить» | «Пете поручено оформить договор с контрагентом Логистик Плюс на сумму **3,5 миллиона рублей**. Срок — **до 15 июля 2026 года**.» |
| **K-04** | «по лендингу, **значит: ну, во-первых**, текст этот надо… **э-э**… **короче**, прикрутить. Всё на Оле.» | «Сергей поручил Оле четыре задачи по подготовке лендинга: написать текст, согласовать макет, купить домен и подключить аналитику. Все шаги выполняет Оля.» |
| **K-01** (MTG-14 филлер) | nothing (чистая болтовня отвергнута) | задача с чистым описанием «…зафиксировать результаты проверки того, как передаются данные в платформе, для демонстрации.» |
| **K-10** | — | «Сергей поручил Кате полный онбординг клиента Ромашка… установочный звонок, доступы, обучение менеджера, сбор обратной связи через неделю.» — **вердикт PASS** |

**Детерминированный сигнал стенда:** `descriptionClean` для K-03 перешёл **false → true** (b1 → after-fix).
Заголовок не менялся (был чистым и остался). Провенанс (дословная цитата) сохранён в `IntakeIssue.rawContent`
(«Цитата: …»). Факты (имя, сумма, срок, число шагов) сохранены; выдумок нет.

**Вывод:** фикс Ф5 (структурное `description` в combined-извлекатель + `resolvedDescription` в materializer/
дедуп) решает кейс MTG-14. Реализован, 32 юнита зелёные.

## 3. Честные ограничения стенда (не продукт)

Выявлены на прогонах, **лимитируют полноту baseline, но не подрывают доказательство Т11**:

1. **freeNote (chat/telegram/email) атрибуция несовершенна.** Задачи из свободных заметок дозревают после окна
   сценария; meeting-атрибуция по `meetingId` точная, а freeNote — по content-match (порог 0.4). В прогоне
   `after-fix` freeNote-сценарии (D-01/D-07/K-02/K-05..09) не дали новых intake вовсе (даже ясный K-07 «Аня,
   подготовь отчёт» → 0) — путь `ingestFreeNote`→конвейер в стенде нестабилен. Требует доработки.
2. **content-reconcile матчит setup-задачи.** D-01/D-07 ложно приписались к предсуществующим setup-задачам
   («смета X»), т.к. content-match не исключает `manifest.setupTasks` id из кандидатов. Фикс: исключать setup-id.
3. **Латентность конвейера** (block-extraction ретраи) — встреча дозревает >5 мин; полный прогон 110 сценариев
   последовательно = часы. Для CI/петли нужна оптимизация (пайплайнинг + глобальный дренаж).
4. **Регрессия дедупа (ось D) не замерена чисто** — freeNote-дедуп-сценарии не дали кандидатов. Теоретический
   риск низкий: дедуп теперь сравнивает структурный текст с обеих сторон (лучше выровнено), а не сырьё↔структуру.
   Рекомендация: точечный дедуп-перепрогон после фикса freeNote-атрибуции.
