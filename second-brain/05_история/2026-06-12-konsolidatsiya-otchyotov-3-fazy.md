# Консолидация отчётного слоя встречи — 3 фазы за сессию (оркестрация + ультра-код)

## Что было поставлено

Реализовать ТЗ `2026-06-11-meeting-report-consolidation-graph-and-prompts` целиком,
в ветке `svdev` параллельно с другой активной сессией (probe). Три фазы, порядок
выката Ф3→Ф1→Ф2:
- **Ф3** — апгрейд 3 LLM-промптов отчётов (meeting-report-fast / type-sales /
  client-meeting-split) по дословным текстам Приложения A.
- **Ф1** — снос 3 дублирующих воркеров (chapters/tasks-extract/quality-score),
  единое ядро = meeting-report-fast, + 4 доводки чтоб не сломать UI.
- **Ф2** — отчёт→граф (вторичный источник, защита от галлюцинаций). Развилка Р1
  оставлена ТЗ владельцу.

## Как решал (файлы, агенты, коммиты)

- **Ф3 (`e4fded3c`).** Дословная вставка текстов A1/A2/A3 делал САМ (Edit), не
  делегировал — это ровно тот случай, где суб-агенты перефразируют. Новое: общий
  словарь ярлыков `MEETING_TYPE_LABEL_RU` в `common.ts`. Снапшоты промптов
  обновил через `vitest -u`. Поймал, что `withToolInstructions` задвоил бы
  финальную tool-строку A2 → убрал из `type-sales.buildPrompt`.
- **Ф1 (`2501d72b`).** Картография 2 параллельными Explore-агентами вскрыла два
  отклонения от ТЗ: (1) `task-extraction.service` НЕЛЬЗЯ удалять — его юзает
  прод-`chatbox-analyze.worker` (удалил только сам воркер); (2) `code-fallback`
  ветка `tasks` остаётся (на `prompts/tasks`). Снос + 4 доводки делал кодер-агент,
  я верифицировал лестницей (греп 0 остаточных, re-Read swapless-логики,
  typecheck/build/592 теста). Качество fast теперь пишет каноничную
  `MeetingQualityScore` (одна транзакция + `qualityScoreStatus='ready'`); regenerate
  перенаправлен на `enqueueMeetingReportFast` (+`reason` варьирует jobId, обходя
  дедуп removeOnComplete 24ч). Спека `prompt-resolver` сломалась от Ф3-текста —
  починил (урок: прогонять ВЕСЬ ai-модуль при правке промптов, не только prompts/).
- **Ф2 (`13a6ac69`).** Ультра-код: Workflow #1 (11 агентов — верификация фактов +
  3 дизайна + 3 судьи + запись суб-ТЗ). Развилку Р1 спросил у владельца → выбрал
  **Б** (summaryFast + структурные extract_*). Суб-ТЗ написал отдельным файлом
  `report-to-graph-phase2.md`. **Я упростил ГАРД C** из синтеза workflow (он
  предлагал cron+TTL+draft-лимбо, исключающий report-only из графа — это обнуляло
  вариант Б): report-only идёт штатным `markCanonical`, вторичность по весу через
  ГАРД A (cap confidence + dynamicScore + primarySource). Реализация — 2 кодера
  (ingest-путь Ф2/Ф3; гарды Ф4). Миграцию (enum `meeting_report` + поле
  `IdeaBlock.primarySource`, 2 файла) делал сам — локальная dev-БД не поднята,
  файлы написал вручную по паттерну `daily_checkin`. Ф4-кодер упал на транзиентном
  529, но правки УЖЕ были на диске — доделал верификацию сам. Workflow #2
  (состязательное ревью диффа, 4 линзы + adversarial-проверка) дал 1 подтверждённую
  находку из 4 (гард «пустого отчёта» игнорировал `chapters.length` → терял
  узлы-главы) — пофиксил + тест.

## Что вышло (верификация)

- typecheck/lint(0)/build зелёные после КАЖДОЙ фазы; суммарно ~594 теста
  knowledge-core+ingest+ai (вкл. регресс transcript↔transcript, swapDirection, D6,
  ГАРД A, новые writeQualityScore-тесты).
- 0 остаточных ссылок на удалённое (греп-факт-чек).
- Все 3 фазы закоммичены, документация по 9 файлам + 2 ТЗ обновлена.

## Чему научился

1. **При правке текста LLM-промпта прогоняй ВЕСЬ модуль-потребитель, не только
   prompts/.** Спека `prompt-resolver.service` ассертила старую фразу type-sales —
   поймалось только широким прогоном ai-модуля, не точечным. (→ code-pitfalls?)
2. **Вставку дословного текста из ТЗ делай сам, не делегируй** — агенты
   перефразируют; verbatim-edit + снапшот надёжнее.
3. **Суб-агент может упасть на 529 ПОСЛЕ записи правок** — всегда проверяй
   фактическое состояние диска (git status + греп маркеров), а не верь «агент
   умер = работы нет». Здесь Ф4 был фактически готов.
4. **Не доверяй синтезу workflow слепо** — судьи оптимизировали «безопасность
   графа» в изоляции и предложили исключить report-only, что противоречило
   выбору владельца (Б = обогатить граф). Орхестратор обязан сверять с продуктовым
   интентом и упрощать over-engineering.
5. **Картография до сноса обязательна** — `task-extraction.service` казался
   удаляемым по ТЗ, но прод-chatbox его юзает. Line-номера в ТЗ устаревают.
6. **Детерминированный machine-guard > soft-флаг** для провенанса: явное поле
   `primarySource` + строгое условие swapDirection надёжнее, чем «промпт попросит
   LLM выбрать транскрипт» (LLM источник вообще не видел).
