# Анализ: интеграция «Второго мозга компании» с Z (СУПЕРСЕТНУТ)

> Этот документ суперсетнут [plans/tz/2026-05-10-knowledge-core-tz.md](../tz/2026-05-10-knowledge-core-tz.md). Подход «tier_brain как опциональный слой» заменён на «единое ядро знаний как фундамент Z».

## Что хотим сделать

В папке [delivery/](../../delivery/) лежит самодостаточное ТЗ другого продукта — **«Второй мозг компании»** (универсальная корпоративная AI-память, 40 модулей, self-host).
Z — продукт **AI-видеовстреч на LiveKit**.
Задача — найти модель, при которой эти два продукта живут как одно целое: разные тарифы открывают разные срезы функциональности, не разрушая ни ядро видеовстреч, ни концепцию «второго мозга».

Дополнительно — сравнить «старый» и «новый» подход к сбору, хранению и поиску информации (что используется в Z и что предложено в delivery/) и описать, как переписать ТЗ, чтобы получившийся скоуп можно было реально отдать в код.

## Зачем (цель и ценность)

1. **Расширение продукта Z от «инструмента встречи» к «памяти компании».** Видеовстречи — это первая точка входа для клиента, но единственная: вокруг них естественно нарастают чаты, переписки, CRM, документы. Если мы не закроем эти источники — их закроет конкурент, и пользователь Z будет смотреть туда за инсайтами, а к нам приходить только провести звонок.
2. **Дифференциатор уже есть в Z частично.** Cards + cross-meeting RAG-чат + transcript-индексация — это де-факто 30% слоя «понимание + структура» из delivery. Достроить дешевле, чем построить с нуля.
3. **Тарифная модульность.** На одном кодовом ядре — два разных продуктовых предложения: «AI-встречи» (короткий цикл продажи, малый чек) и «Второй мозг компании» (длинный цикл, большой чек, enterprise). У этих сегментов разная экономика, но один маркетинговый воронкообразный ход: «попробуй встречи, пойми, что в них есть инсайты, подключи остальные источники».
4. **Снятие противоречия в репозитории.** Сейчас `delivery/` лежит рядом с Z и содержит **другую** архитектуру (Python, FalkorDB, Kafka, Temporal, AGPL, single-tenant). Без явного решения это превращается в «два продукта, один репозиторий» и через месяц в «никто не знает, что из этого правда».

## Как работает сейчас

### Z (фактическое состояние, 2026-05-10)

**Стек:** NestJS + Prisma + PostgreSQL (с pgvector) + Redis + BullMQ; Next.js 15 + Tailwind + shadcn; LiveKit Server + Egress + S3.
**Идентичность:** standalone-аккаунты (`auth-and-accounts.md`), один пользователь = одна персональная учётка. **Понятие «организация» отсутствует.** Cards привязаны к userId.
**Данные о смыслах встреч:**

| Сущность | Где живёт | Как наполняется |
|---|---|---|
| `Meeting` (метаданные, статусы FSM) | Postgres | Backend |
| `MeetingTranscriptChunk` (vector 1536) | Postgres + pgvector HNSW | `transcript-index.worker` |
| `Task`, `MeetingChapter`, `MeetingHighlight` | Postgres | structured-extraction worker'ы через `LlmRouter` |
| `MeetingChatMessage` (per-meeting и per-card) | Postgres | RAG над chunks (cosine similarity) |
| `Card` (CRM-карточка) | Postgres | Ручное создание + явная привязка `meeting.cardId` |
| `Card.summaryCache` | Postgres | `card-rollup.worker` (BullMQ, debounce 5с) |
| `Tag`, `MeetingTag` | Postgres | Пользовательские теги |
| `LlmTaskRoute` | Postgres | Админка маршрутизации моделей по `taskType` |

**Что Z уже умеет, и это пересекается с «Вторым мозгом»:**
- Stream-чат с памятью (single-meeting context-stuffing + cross-meeting RAG) — аналог M-23 «Агент-исполнитель запросов».
- Embedding-индексация транскриптов — аналог технического фундамента под M-11.
- Public REST API + API keys + outgoing webhooks с HMAC и SSRF-guard — аналог M-39 «Шина инструментов» в её out-going части.
- Cards + rollup — аналог упрощённого M-08 «Темы» (но привязка строго ручная, без auto-suggest).
- Soft-delete + retention extras — аналог raw retention policy.
- Audit log + quotas — каркас под compliance.

**Что Z НЕ делает (и в этом разница с delivery):**
- Нет источников, кроме встреч (нет коннекторов к чатам/email/CRM/метрикам).
- Нет графа связей. Таблица «упоминаний клиентов/людей/проектов поперёк встреч» отсутствует — есть только cosine-поиск.
- Нет типизированных сигналов (`client_pain`, `feature_request`, `risk`, `commitment`, ...). Всё, что AI извлекает — это `Task`, `Chapter`, `Highlight` и свободный summary; смысловой классификации нет.
- Нет понятия «темы» как отдельного объекта со временем жизни, весом, связью с целями. `Tag` — это пользовательский лейбл, не AI-сущность.
- Нет «целей компании», «дрейфа стратегии», «настроения команды».
- Нет уровней доверия выводов (`proposed → analyzed → confirmed → locked`).
- Нет multi-tenancy. Multi-user тоже нет — один аккаунт = один пользователь, не «компания из 100 человек с ролями».

### «Старый метод» сбора знаний в Z

Здесь важная терминологическая ловушка. В Z **уже есть** папка `second-brain/` — но это **внутренняя память Claude Code про сам проект Z**, а не продуктовая фича. Конкретно:

- `second-brain/` = markdown-файлы под Obsidian-стиль, описывают «что сейчас работает по факту».
- Источник наполнения — Claude (агент), который после каждой кодовой сессии вручную обновляет затронутые файлы по чек-листу из [CLAUDE.md](../../CLAUDE.md).
- Поиск — открытие файлов в IDE и читалка.
- Хранение — git-репозиторий.

То есть «старый метод» — это **ручная агентская дисциплина по поддержанию документации проекта**. Это инструмент разработчика Z, не продукт для пользователя.

«Новый метод» из delivery/ — это **автоматический промышленный pipeline для пользователей продукта**: коннекторы → нормализация → эмбеддинги → сигналы → темы → граф → дашборд. Это инструмент для сотрудника компании-клиента, не для разработчика.

**Это две принципиально разные вещи, не нужно их сливать.** Папка `second-brain/` остаётся как есть и обслуживает разработку Z. Из delivery/ берётся **продуктовая модель** для пользователей. Когда ниже в документе говорится про «второй мозг» в контексте интеграции — речь всегда про продуктовую модель из delivery/, не про разработческую папку.

### delivery/ (целевое состояние «Второго мозга компании»)

**Стек:** Python 3.12 / FastAPI / LangGraph / LiteLLM / Temporal / Kafka / pgvector / FalkorDB+Graphiti / Meilisearch / MinIO / Keycloak / OpenFGA / OpenBao / Langfuse + Grafana stack. Лицензия — AGPL-3.0.
**Деплой:** один экземпляр = одна компания, self-host (DR-009).
**Объём:** все 40 модулей в первом релизе (DR-001).
**UI:** русский, без англицизмов (DR-014); без форм/чекбоксов/тегов — только свободный текст и голос (DR-012).
**Этический каркас:** «память, не контроль» (DR-013) — запрещены напоминания, эскалации, gamification.

## Главный конфликт двух миров

| Аспект | Z | delivery/ | Природа конфликта |
|---|---|---|---|
| Стек бэкенда | NestJS / TypeScript | FastAPI / Python | Стилистический + найм + экосистема AI-библиотек |
| Граф знаний | нет (только pgvector) | FalkorDB + Graphiti обязателен | Архитектурный |
| Очереди | BullMQ (Redis) | Temporal + Kafka | Архитектурный |
| Multi-tenancy | single-user (multi-account, но не multi-org) | single-tenant self-host | Идеологический: разные модели продажи |
| Источники данных | только встречи + вручную привязанные карточки | 13 классов источников включая чаты/email/CRM/метрики | Скоуп |
| UI-философия | формы, фильтры, теги, multi-select, англицизмы (Tasks, Highlights) | свободный текст/голос, чистый русский | Идеологический |
| Лицензия | проприетарная (Z — SaaS-проект владельца) | AGPL-3.0 | Юридический |
| Объём первого релиза | поэтапно, фазами 0-9 + расширения | сразу 40 модулей, без MVP | Процессный |

**Полное слияние стеков нерационально** — придётся либо переписать Z на Python (выкинуть весь NestJS-код за 3 месяца разработки), либо выкинуть архитектурные требования delivery (FalkorDB/Kafka/Temporal). Оба варианта — потеря инвестиций.

## Варианты интеграции

### Вариант A — «Z поглощает second-brain»

Z остаётся ведущим продуктом и тарифом обрастает функциями второго мозга. Стек Z (NestJS, BullMQ, pgvector) сохраняется. Из delivery/ берётся **продуктовая модель** (сигналы, темы, граф, дашборд директора, цели), но реализуется на нашем стеке без FalkorDB/Kafka/Temporal.

**Что добавляется в Z как новые модули:**
- `Tenant` (организация) + `Membership` + RBAC по 3 измерениям (роль / уровень / атрибуты), Casbin как первичный engine (OpenFGA отложить).
- `Source` + `SourceConnection` — коннекторы к чатам/email/CRM/документам, реализуем поэтапно (начать с чата Telegram + email IMAP — два дешёвых).
- `Signal` — типизированный извлечённый смысл (15 типов из M-05). Хранится поверх `MeetingTranscriptChunk` и поверх новых типов источников.
- `Theme` — кластер сигналов с весом и динамикой (постепенно вытесняет `Card` либо встаёт рядом: Card = «явная папка пользователя», Theme = «AI-обнаруженный кластер»).
- `EntityMention` + `EntityLink` — простой граф упоминаний на pgvector + jsonb-связях. FalkorDB не вводим. Если KNN+rerank+LLM-арбитр окажется слишком слабым — вернёмся к FalkorDB как отдельному микросервису.
- `Goal`, `StrategicAlignment` (M-15, M-16) — отдельная страница «Куда идёт компания».
- `ConfirmationLevel` (proposed/analyzed/confirmed/locked) — добавить как поле в Theme/Signal/EntityLink.
- Дашборд директора + чат «к памяти всей компании», переиспользует существующий cross-meeting RAG, расширяя scope с meetings до signals/themes.

**Что отбрасываем из delivery:**
- AGPL — у нас проприетарный SaaS, не self-host.
- FalkorDB + Graphiti + Kafka + Temporal — заменяем на pgvector + jsonb + BullMQ + Redis Streams. Откат к стеку delivery — только если конкретный модуль не работает.
- Жёсткое «русский UI без англицизмов» — оставляем смесь, как сейчас в Z (или принимаем отдельным решением, см. открытый вопрос ниже).
- «Только текст/голос, никаких кнопок» — неприменимо в Z, у нас уже формы и фильтры. Принцип берём как **рекомендацию** для новых ввода данных в «памяти», не как догму.
- 40 модулей сразу — переписываем под фазовый подход Z (фазы 0-N).

**Тарифная модель:**
- `tier_meet` (текущий Z) — встречи, AI-отчёт по типу, cards, RAG-чат внутри карточки.
- `tier_brain` — добавляет источники (чат/email/CRM), сигналы, темы, граф упоминаний, дашборд директора, цели.
- `tier_brain_plus` (опционально позже) — настроение команды, стратегический согласователь, двигатель уроков, departure capture.
- Реализация переключений — модуль `entitlements` (одна сущность `OrgEntitlement` с `tier` enum + per-feature overrides). Все модули второго мозга проверяют entitlement перед выполнением.

**Плюсы:** сохраняем всю инвестицию в Z; один стек, одна команда, одна доставка; естественный апсейл по тарифам.
**Минусы:** теряем чистоту delivery-архитектуры (нет FalkorDB → граф будет беднее); приходится решать конфликт UI-философии; multi-tenancy в Z — это переписать модель данных.

### Вариант B — «Второй мозг как отдельный сервис, Z — источник данных»

Z остаётся как есть, ничего не достраивается. Параллельно строится отдельный продукт по delivery/ ровно в его стеке (Python/FastAPI/...). Z для этого продукта — **один из источников** (M-01 класс `meetings`). Интеграция через Z Public API: второй мозг подписывается на webhook `meeting.ai_ready` от Z, забирает транскрипт + summary + tasks, складывает в Raw Memory.

**Плюсы:** delivery/ реализуется ровно как написано — без компромиссов; разные команды; разные ритмы релиза; ценовое разделение естественно (две подписки).
**Минусы:** два продукта — два UI, два логина (или OIDC SSO с лагами), две инфраструктуры; для пользователя «второй мозг» Z — просто один из 13 источников, без видимой синергии в UI; для команды — два кодовых базы и удвоение каждого cross-cutting (auth, billing, observability, deploy).

### Вариант C — гибрид: «ядро graph-services отдельным сервисом, остальное — внутри Z»

Внутри Z остаётся всё, что естественно ложится на NestJS (entitlements, источники, сигналы, темы, дашборд, чат, цели). А самое тяжёлое — **граф связей и temporal KG (M-11/M-12)** — выносится отдельным микросервисом на Python+FalkorDB+Graphiti, реализованным по delivery/. Связь — через REST/gRPC.

**Плюсы:** Z остаётся монолитом NestJS для 90% кода; компромисс по графу — в выделенный сервис, где он действительно нужен; команда AI/ML работает в своей экосистеме (Python).
**Минусы:** межсервисная сложность (sync embeddings между Z-pgvector и graph-сервисом); два деплоя; обоснованность только если граф реально критичен. Если можно прожить на pgvector + LLM-арбитре без FalkorDB — этот вариант перерождается в A.

### Рекомендация (для обсуждения, не для немедленного утверждения)

**Вариант A** для первой фазы. Конкретно потому, что:
1. У Z уже есть pgvector + RAG-чат + Cards + rollup + Public API + entitlement-каркас (через `LlmTaskRoute`-подобные таблицы) — наращивание дешевле новой стройки.
2. FalkorDB/Graphiti дают преимущество на размере данных «вся компания за 3 года». На «компания за первые 6 месяцев» pgvector + LLM-арбитр выдаёт сравнимое качество. Откладываем введение FalkorDB до доказанной необходимости.
3. Тарифная модель естественно мапится на «один кодовый ядро + entitlements», что в варианте B пришлось бы реплицировать в обоих продуктах.
4. **Если вариант A на каком-то модуле упирается в потолок (граф, оркестрация долгих воркфлоу) — этот конкретный модуль выводится в микросервис на стеке delivery (становится локальным C для этого модуля), не переписывая весь Z.**

Вариант B имеет смысл, только если есть бизнес-решение **строить два разных продукта под две разные клиентские группы** — здесь интеграция уже не нужна, нужна просто общая платформа авторизации.

## Сравнение «старый метод» vs «новый» в продуктовом смысле

| Что | Z сейчас | delivery/ предлагает | Что забираем |
|---|---|---|---|
| Сбор данных | Только встречи + ручные карточки | 13 классов источников, idempotency, нормализация | Постепенно: M-01/M-02 + 2 коннектора (TG + email) на старте |
| Хранение оригиналов | `Meeting`, `Recording`, `MeetingTranscriptChunk` | Raw Memory (M-03) с чексуммами + соответствие 7 лет 152-ФЗ | Концепция «иммутабельного источника» уже есть фактически — добавить чексумму и явную пометку `data_class` |
| Понимание | `summary` + `Task` + `Chapter` + `Highlight` (свободные тексты + extracted entities) | Типизированные сигналы M-05 (15 типов), confidence, evidence_links | Ввести таблицу `Signal` поверх существующих транскриптов; AI-extraction worker по аналогии с tasks/chapters |
| Структура | `Card` (ручная) + `Tag` (пользовательский) | `Theme` (AI-кластер с весом, динамикой, связью с целями) | Ввести `Theme` параллельно с `Card`; Card остаётся для явной привязки пользователем, Theme — для AI-обнаружения |
| Связи | Только cosine similarity между chunks; `Meeting.cardId` (one-to-many) | Граф (M-11/M-12) с типизированными связями + объяснением + confidence | Ввести `EntityMention` + `EntityLink` на pgvector + jsonb. Без FalkorDB на старте. |
| Поиск | Cross-meeting RAG (cosine) + Postgres ILIKE через `/search` | Гибрид: BM25 (Meilisearch) + pgvector + graph traversal + LLM-арбитр | Добавить полнотекстовый русский tokenizer (Meilisearch или Postgres `tsvector` с pg_trgm) — `searchModule` в Z уже размечен «vNext: tsvector» |
| Чат к памяти | Per-meeting + per-card | Глобальный по всей памяти компании (M-23) с фильтрами по доступу | Расширить scope существующего cross-meeting чата: добавить scope=org, фильтры по signal/theme |
| Принятие решений | нет | M-21 «Отслеживание решений» (сигнал → тема → решение → действие → результат) | Опционально на втором этапе |
| Цели и стратегия | нет | M-15 + M-16 «Стратегический согласователь» | На втором этапе как отдельная страница |
| Подтверждение AI-выводов | нет | proposed/analyzed/confirmed/locked + история переходов | Ввести как поле во всех новых сущностях с первого дня |

## Конфликты, требующие явного решения владельца

1. **Multi-tenancy.** Сейчас Z — multi-account (много персональных пользователей), но НЕ multi-org. «Второй мозг компании» по определению про организацию с сотрудниками и ролями. Решение: ввести `Tenant`/`Org` + `Membership` уже на первой фазе, иначе все следующие модули встанут.
2. **Лицензия.** delivery — AGPL. Если мы тащим из delivery именно код (а не только концепции) — наследуем AGPL. Решение по умолчанию: **берём только концепции и схемы, не копируем код**. Свой код остаётся проприетарным.
3. **«Никаких кнопок» (DR-012).** Жёсткое требование delivery. Не применимо к существующим экранам Z (там формы, теги, multi-select). Решение: **принцип применяется к новым экранам «памяти компании»** (дашборд директора, чат к памяти, ввод дампа мысли); существующие экраны Z (создание встречи, журнал, settings) остаются как есть.
4. **«Русский UI без англицизмов» (DR-014).** Z уже использует «Tasks», «Highlights», «Cards». Решение: **либо переименовываем повсеместно** (большая работа, но правильно для русского рынка), **либо принимаем смесь и фиксируем DR в Z**. Откладываем до отдельного решения; не блокирует архитектурную работу.
5. **«Память, не контроль» (DR-013).** Не противоречит Z, но влияет на UX будущей работы с обещаниями (`commitment`-сигнал) и настроением команды. Принимаем как принцип.
6. **40 модулей сразу vs фазовый Z.** Z работает фазами (это закреплено в [CLAUDE.md](../../CLAUDE.md) и `plans/`). Решение: **DR-001 delivery не наследуем**, scope «второго мозга» внутри Z разбиваем на 4-6 фаз.
7. **Двойной opt-in для mood/настроения.** Если делаем модуль M-19 — обязательно. Запоминаем для будущей фазы.
8. **152-ФЗ.** Z уже про РФ, но «второй мозг» расширяет PII-периметр (личные данные сотрудников клиента). Нужен явный анализ DPA (data processing agreement) для тарифа `tier_brain`.

## Структура переписанного ТЗ

Вместо одного гигантского ТЗ «второго мозга» — **серия фазовых ТЗ** в `plans/tz/`, каждое — самодостаточная функциональность, проходимая за разумный срок (1-3 недели чистой работы).

Предлагаемая последовательность (имена — рабочие):

1. **`2026-05-NN-tenant-and-rbac-tz.md`** — фаза 0. Ввод `Tenant`/`Org`, `Membership`, миграция существующих сущностей под `tenantId`, базовый RBAC (Casbin или подобный). Без этой фазы остальные не работают.
2. **`2026-05-NN-entitlements-and-tiers-tz.md`** — фаза 0.5. Модуль `entitlements`, тарифы `tier_meet` / `tier_brain` / `tier_brain_plus`, gating всех будущих модулей. Сейчас в Z разрозненные quota/route/limit — собрать в единую модель.
3. **`2026-05-NN-signals-and-themes-tz.md`** — фаза 1. Таблицы `Signal` + `Theme`, AI-extractor поверх существующих транскриптов, `theme-matcher` worker (мэппинг сигнал → существующая/новая тема), scoring (M-09), интеграция в карточку встречи и в Card.
4. **`2026-05-NN-entity-graph-tz.md`** — фаза 2. `EntityMention` + `EntityLink`, KNN+rerank+LLM-арбитр, страница «связи» в карточке темы. **Без FalkorDB.** Решение о FalkorDB — отдельным DR после оценки качества.
5. **`2026-05-NN-director-dashboard-tz.md`** — фаза 3. Дашборд для роли «владелец / директор», топ-метрики, чат «к памяти всей компании», отчёт «что узнали за неделю/месяц».
6. **`2026-05-NN-external-sources-tz.md`** — фаза 4. Источники: Telegram-bot ingest + IMAP email ingest. Идемпотентность, нормализация, привязка к `Source`. Расширение AI-pipeline на новые типы источников (не только meetings).
7. **`2026-05-NN-goals-and-alignment-tz.md`** — фаза 5. M-15 (цели) + M-16 (согласователь). Опционально: M-21 (отслеживание решений), M-32 (открытые вопросы).
8. **`tier_brain_plus`** — отдельные ТЗ по запросу: настроение, отделы, метрики, departure capture, CRM-коннекторы.

Каждое ТЗ:
- следует [`plans/tz/_template.md`](../tz/_template.md);
- начинается со **скоупа фазы**, **что не делаем**, **критериев готовности**;
- содержит **DTO/Prisma-схему** изменений;
- содержит **обновления `second-brain/`** в чек-листе фазы (по правилам из [CLAUDE.md](../../CLAUDE.md));
- содержит **матрицу entitlement** — какой тариф открывает функцию;
- ссылается на **исходный M-NN из delivery** для трассировки.

Параллельно — **ADR в Z** (новый формат — например, `second-brain/02_architecture/adr/`):
- ADR-001 «Интеграционная стратегия: вариант A с возможным выводом graph-сервиса в микросервис».
- ADR-002 «Multi-tenancy через `tenantId` во всех моделях, без schema-per-tenant».
- ADR-003 «Stack delta: pgvector + jsonb вместо FalkorDB на старте, критерий пересмотра — N связей или K мс на запрос».
- ADR-004 «UI-философия: принцип "только текст" применяется к новым `tier_brain` экранам, существующие Z остаются как есть».
- ADR-005 «Лицензия: концепции delivery — да, код delivery — нет (несовместимая лицензия)».
- ADR-006 «Тарифы и entitlements: `tier_meet` / `tier_brain` / `tier_brain_plus`».

Папка `delivery/` остаётся в репо как **референс-источник** (read-only), но из активной работы исключается. Возможный жест — добавить `delivery/STATUS.md`: «Этот пакет — источник концепций для tier_brain в Z. Реализация — через ТЗ в plans/tz/. Изменения здесь не влияют на код Z; вносим — через новый ADR в second-brain/».

## Открытые вопросы

- [ ] **Какой вариант (A / B / C) принимаем?** Рекомендация — A с условием возможного вывода graph-сервиса. Нужно решение владельца.
- [ ] **Делаем ли multi-tenancy сразу или multi-account-per-org с одним owner-аккаунтом?** Простейший путь — `Org`-сущность поверх существующего `User`, owner = текущий аккаунт, остальные приглашаются по email.
- [ ] **Принимаем ли «русский UI без англицизмов» как DR Z или оставляем смесь?** Влияет на объём работы по rename'у Tasks/Highlights/Cards.
- [ ] **Принимаем ли «никаких кнопок» как принцип для tier_brain экранов?** Если да — дашборд директора получает только чат-подобный ввод, без фильтров.
- [ ] **Что с лицензией delivery?** Подтвердить, что мы НЕ копируем код, только концепции/схемы — иначе AGPL заразит весь Z.
- [ ] **Сохранять ли папку `delivery/` в репо или вынести в отдельный репозиторий-документация?** Сейчас она создаёт двусмысленность.
- [ ] **Маркетинговое позиционирование двух продуктов.** «Z — встречи и память компании» vs «два тарифа одного продукта» vs «два бренда»? Влияет на UI/название/onboarding, не на код.
- [ ] **Где границы 152-ФЗ для tier_brain.** Нужна юридическая консультация по DPA с клиентом, согласие на сбор PII через коннекторы (не только встречи).
