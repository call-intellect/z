# Аудит конвейера усвоения знаний Коры

## Вердикт одной фразой
**Конвейер в нормальном режиме доводит знания до базы, но по всей цепочке рассыпан ОДИН класс «тихих потерь» — данные молча исчезают при сбое LLM, сбое очереди (Redis) или гонке двух воркеров, без ошибки и без повтора.** Отдельно: вкладка «Задачи» на встрече при дефолтных настройках читает не ту таблицу, куда новый агент пишет задачи, — поэтому владелец их не видит (это **не баг кода**, а рассинхрон путей).

## 🔴 Что сломано (подтверждено чтением кода)

### block-distill — самый системный (🔴)
Блок помечается «эталонным» в базе, и только ПОТОМ запускаются специалисты. Запуск — «как получится»: если Redis моргнул, ошибка проглатывается в `.catch(warn)`, повтора нет. Блок навсегда «обработан», а специалисты по нему не отработали → знания не извлекутся.
- 3 места: `block-distill.worker.ts:169-195` (markCanonical), `:318-351` (mergeInto, high), `:474-511` (swapDirection, high). Точное воспроизведение класс-бага «commit статуса до enqueue».

### specialist-3-3 (решения) — проглот без повтора (🔴) — **фикс готов**
Внешний `catch` (`specialist-3-3-decisions.service.ts:445-457`) пишет ошибку в лог и не пробрасывает → очередь считает «успех», повтора нет. Плюс гонка guard↔create (`:187/:973`). **Идемпотентный фикс реализован** (worktree, см. [ТЗ](../tz/2026-06-20-decision-materialization-idempotency-fix.md)). Доп. мелочи: лог «обогащено» вне try/catch (ложный успех), triage-сбой оставляет решение без карточки.

### specialist-3-1 (регламенты) — инструкции мимо куратора + потеря версий (🔴)
- `upsertInstruction` (`:1059-1169`) **не вызывает** `triageProposed`/`checkAndEmitProbes` (а соседи regulation/process/policy — вызывают). Инструкции навсегда «авто-одобрены», куратор их не видит.
- `nextCardVersion` (`:1657-1672`) считает номер версии вне транзакции → гонка → второй воркер падает на `@@unique`, снимок версии теряется (сама регуляция сохраняется).
- Мелочь: в аудит инструкции уходит `kind:'process'` вместо `'instruction'` (`:1064-1068`).

### graph.service — дубли решений (🔴)
Защита от повторов только внутри `if (sourceIdeaBlockId)` (`:692-700`); решение без «адреса блока» (`null` на `:686-689`) идёт сразу в `create` (`:701-719`) → повторное извлечение плодит дубли. Плюс гонки «найти→создать» без транзакции (`:568-662`, `:693-718`).

### specialist-3-5 (инсайты) и 3-6 (идеи) — проглот ошибки записи (🔴)
- Инсайты: ошибка `insight.create` (`:943`) проглочена внешним catch (`:300-312`) → инсайт теряется.
- Идеи: гонка плодит дубли (на массив-поле `@unique` невозможно → даже ошибки нет, `:132-254`); ошибка `create` проглочена (`:326-338`); сбой вектора (`:780-798`) делает идею невидимой для будущих слияний.

## 🟡 Частично (не «сломаны», но риск)

- **specialist-3-14 (цели):** ошибка `goal.create` проглочена (`:406-418`); гонки безвредны.
- **specialists-combined:** дубли «категорий знаний» при повторе (`:598`); потеря навыка при гонке (`:663`).
- **entity-resolution:** двойники сущностей по имени при параллели — в схеме нет `@@unique([tenantId,type,canonicalName])` (`schema.prisma:3605` только индекс) и нет транзакции вокруг «найти→создать» (`:191-303`). Слияние — корректно (в транзакции).
- **meeting-extract-actions:** дубли поручений при ручном повторе (нет `@unique` на `IntakeIssue`, `:292-303`); потеря хвоста задач при сбое базы (`:360-388`).

## Задачи: почему владелец не видит (вывод расследования) — НЕ баг кода

> **Поправка по прод-реальности (сверка с `intake-issue-linked-meeting-ids-fix`):** мой статический аудит читал КОД-дефолт флага (`OFF`), но в ПРОДЕ `knowledge.meetingTasksToTrackerOnly` = **ON** (через AdminSetting, diag 2026-06-17). При ON вкладка ищет `Issue` по `linkedMeetingIds: { has: meetingId }` (`meeting-action-items.service.ts:207`), а конвейер `IntakeIssue→Issue` **не прокидывает `linkedMeetingIds`** → 0 результатов. **Итог тот же (пусто), но точный обрыв — `linkedMeetingIds`, и на него УЖЕ есть ready-ТЗ** [`intake-issue-linked-meeting-ids-fix`](../tz/2026-06-17-intake-issue-linked-meeting-ids-fix.md) (добавить `meetingId` в IntakeIssue → прокинуть в `Issue.linkedMeetingIds`). Ниже — код-дефолтная (OFF) ветвь моего разбора, она тоже верна для дефолтной конфигурации.
- **Развилка:** флаг `knowledge.meetingTasksToTrackerOnly` по умолчанию **OFF** (`typed-config.service.ts:1575`).
- **Новый агент пишет в `IntakeIssue`** (статус `pending`, ждут на `/intake`) — `meeting-extract-actions.service.ts:360`.
- **Вкладка «Задачи» встречи** (`GET /meetings/:id/tasks`) при OFF читает **только старую таблицу `Task`** (`tasks.service.ts:63`), а туда новый агент **не пишет** (писал бы только старый `meeting-report-fast`).
- **Авто-приём не спасает:** Issue создаётся только при `confidence≥0.75 И assigneeId≠null И projectId≠null` одновременно; для источника `meeting` подстановка владельца-исполнителя не работает (`intake.source!=='meeting'`) → без явного исполнителя авто-приём заблокирован, задача висит в `pending`.
- **Итог:** видимая задача оседает в **`IntakeIssue` на `/intake`**, а вкладка встречи смотрит в пустую `Task`.
- **Доказательство тестом:** готовый юнит-тест уже есть — `meeting-action-items.service.spec.ts:45` (при OFF IntakeIssue с `source='meeting'` НЕ появляется в `listForMeeting`).

## Вывод для приоритизации
Это не 16 разных багов — это **один класс в ~6 местах** (block-distill ×3, специалисты 3-1/3-3/3-5/3-6, graph.service) + рассинхрон задач. Лечится двумя машинными гардами: (1) **enqueue до commit статуса / reconcile-cron** на «обработанные без проекций»; (2) **идемпотентная запись (upsert/create+catch→merge) + транзакция вокруг «найти→создать»** во всех писателях. Фикс decisions (Ф1) — образец. Задачи — не фикс, а решение владельца: включить флаг ON / донастроить авто-приём / объяснить путь `/intake`.
