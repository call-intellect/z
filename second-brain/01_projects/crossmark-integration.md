# Crossmark Integration — связь Z и Crossmark

## Решение от 2026-05-06

Z — **полностью независимый сервис**. Crossmark не диктует архитектуру, не даёт код, не блокирует деплой.

Внутрь Crossmark Z встраивается **через программный интерфейс (API)** — Crossmark вызывает Z по API, чтобы создать встречу / получить ссылку / получить результат, и показывает это своим пользователям.

Развёртываются **отдельно**: Z живёт на своих двух серверах в дата-центре Новосибирска со своей базой и своим кодом.

## Что это означает на практике

| Аспект | Как сделано |
|---|---|
| Codebase | Свой репозиторий Z, не привязан к Crossmark |
| База данных | Своя PostgreSQL (отдельная), не разделяет таблицы с Crossmark |
| Пользователи | Своя таблица пользователей (агентов, продавцов и т.п.), кого «приглашает» Crossmark по API |
| Авторизация | Своя система токенов; Crossmark передаёт токен через API при создании встречи |
| Биллинг и тарифы | Свой biling-слой в Z (тарифы фиксируются на самой записи в `retention_days`) — Crossmark может опрашивать через API использование, но решение о тарифе принимается Z |
| AI-инфра | Общая (через `proxy.agent-lia.ru` и `vox.agent-lia.ru` — это не часть Crossmark, а отдельная инфра компании) |
| Деплой | Отдельный, в собственном DC, не зависит от Crossmark-релизов |
| Падение Crossmark | Не валит Z. Падение Z — не валит Crossmark |

## Что НЕ закладываем

- Никакого «единого входа» (SSO) с Crossmark — Z должен работать standalone.
- Никаких прямых обращений Z в БД Crossmark.
- Никаких импортов кода из Crossmark.

## Пользовательский путь: как попадает на встречу

Решение от 2026-05-06: **одна ссылка на встречу для всех, как в Zoom / Google Meet / Яндекс Телемост.** Никаких отдельных гостевых ссылок, никаких автоматических рассылок от Z.

### Хост (Crossmark-пользователь, создатель встречи)

1. Сидит в интерфейсе Crossmark.
2. Нажимает «Создать встречу».
3. Crossmark backend → вызывает Z API → получает разовый deep-link `https://meet.crossmark.ru/m/<id>?t=<jwt>`.
4. Crossmark отдаёт хосту ссылку → она открывается в **отдельной вкладке** браузера.
5. На странице Z проверяет токен → ставит cookie на 24 часа → 302 redirect на чистый URL `meet.crossmark.ru/m/<id>` (без `?t=`, чтобы токен не остался в истории).
6. Дальше хост в комнате опознаётся по cookie.

### Хост приглашает участников

В комнате есть кнопка **«📋 Скопировать ссылку»**. Копируется чистый URL `meet.crossmark.ru/m/<id>`. Хост сам отправляет её куда хочет — Telegram, WhatsApp, почта, мессенджер компании, что угодно. **Z сам ничего никому не рассылает.**

### Гость (любой, кто получил ссылку)

1. Открывает `meet.crossmark.ru/m/<id>` в браузере.
2. У него нет токена в URL и нет cookie.
3. Z показывает страницу «Введите имя» → гость вводит → попадает в комнату как гость.

### Особые случаи

- **Crossmark-пользователь открывает чужую ссылку.** Если у него нет cookie от Z для этой встречи — он гость, как все. Чтобы быть хостом, нужно создать встречу из Crossmark. Это сознательное упрощение.
- **Кто-то открывает ссылку до начала встречи** (`scheduled`, не `active`) — попадает в «зал ожидания» (загрузочный экран до момента, как хост подключится). MVP-вариант — просто страница «Встреча ещё не началась, обновите позже».
- **После окончания встречи** (`completed`) — страница «Встреча завершена», без входа.

**Не используем встроенный фрейм (iframe).** Причина: браузеры по соображениям безопасности нестабильно дают камеру/микрофон/демонстрацию экрана и полноэкранный режим внутри фрейма. Для продукта про видео это критично.

**Crossmark может рисовать у себя** список встреч, превью карточки результата (саммари, задачи) — забирая данные через Z API. Это поверх deep-link потока, не вместо него.

### Что Z НЕ делает

Не рассылает приглашения от своего имени. Не отправляет писем. Не ходит в адресную книгу хоста. Не интегрируется с календарями. Хост сам копирует ссылку и сам шлёт. Просто и понятно — как у всех.

## Авторизация (решение от 2026-05-06)

Два уровня:

### Уровень 1 — между серверами Crossmark и Z

Crossmark получает «ключ интеграции» (API-ключ, ~64 случайных символа). На каждый запрос — подписывает тело методом HMAC-SHA256 (подпись на основе общего секрета). Z сверяет подписи.

```
POST https://api.crossmark.ru/v1/meetings
Headers:
  Authorization: Bearer <api-key>
  X-Crossmark-Signature: <hmac-sha256 от тела запроса>
  X-Crossmark-Timestamp: <unix-время>
Body:
{
  "host": {
    "external_id": "crossmark_user_42",
    "email": "ivan@firma.ru",
    "name": "Иван Петров"
  },
  "type": "sales",
  "title": "Созвон с Ромашкой",
  "custom_prompt": null   // или текст — переопределяет шаблон отчёта по типу
}
```

Заголовок `X-Crossmark-Timestamp` защищает от повтора перехваченного запроса (replay-attack — атака повторного использования). Z отвергает запросы со штампом старше 5 минут.

**Хранение ключей в Z:** таблица `integration_keys(id, partner_name, key_hash, created_at, revoked_at)`. Сам ключ хранится только в виде хеша (sha-256). При создании ключа выдаётся один раз — потом не показывается.

### Уровень 2 — между Z и браузером пользователя

Z в ответе API возвращает короткоживущий токен формата JWT (подписанный токен с зашитыми данными). Внутри: `meeting_id`, `user_id`, `expires_at = now + 15 min`. Подпись — секретом Z (`Z_JWT_SECRET`).

Crossmark подкладывает токен в ссылку: `https://meet.crossmark.ru/m/<id>?t=<jwt>`.

Когда пользователь открывает ссылку:
1. Z проверяет подпись и срок действия.
2. Если ОК — выставляет обычный браузерный cookie (сессия на 24 часа на домене `.crossmark.ru`).
3. Делает 302 redirect без `?t=` в URL — чтобы токен не остался в истории браузера, в логах прокси, в Referer-заголовках.
4. Дальше пользователь ходит по интерфейсу Z через cookie.

**Почему так:**
- Подпись HMAC-SHA256 для серверов — стандарт (LiveKit webhooks, GitHub, Stripe). Просто, надёжно, поверх обычного HTTPS.
- Короткоживущий JWT для пользовательской ссылки — потому что ссылка может попасть в логи и историю. 15 минут жизни + одноразовый обмен на cookie = украденная ссылка через час бесполезна.
- Cookie после обмена — стандартная веб-сессия, фронтенд не таскает токен в каждый запрос.

OAuth 2.0 (полноценный протокол с access/refresh-токенами) **не делаем** — переусложнение для случая «один партнёр-вызыватель». Перейдём, когда у Z появятся ≥5 партнёров с разными правами.

Crossmark передаёт `external_id`, `email`, `name` в каждом вызове API; Z создаёт запись пользователя при первом упоминании, при следующих вызовах находит по `external_id` и обновляет email/имя. Crossmark не зовёт Z при регистрации пользователей у себя — только когда нужна встреча.
