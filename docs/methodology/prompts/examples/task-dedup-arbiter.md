# Эталон промпта: `task-dedup-arbiter`

> Арбитр дедупа задач ПЕРЕД записью в трекер. Одно поручение приходит из встречи, чата и отчёта → без дедупа становится N задачами. До записи кандидата ищем семантически близкие открытые задачи (KNN) и спрашиваем арбитра: дубль, разное или подходящей нет.
> **Где живёт:** `backend/src/modules/tracker/prompts/task-dedup-arbiter.prompt.ts`, `taskType='task-dedup-arbiter'`, вызывается из `backend/src/modules/tracker/services/task-dedup.service.ts` (оба уровня входа: intake + прямой create).
> **Контракт реализации:** `plans/tz/2026-06-16-task-dedup-and-tracker-reconcile.md` Ф1. **Доказательная база:** `plans/analysis/2026-06-15-task-dedup-and-conversation-to-tracker-reconcile.md`.

---

## Ключевое решение: NIL первым (защита от «лепим к top-1»)

KNN отдаёт список похожих ПО СЛОВАМ задач — но похожие слова ещё не дубль. Если бы вердикт был только `same|different`, дешёвая модель тяготела бы привязать кандидата к ближайшему top-1. Поэтому первый и дефолтный вердикт — `nil` («ни одна из показанных не подходит»). Дубль (`same`) объявляется только когда совпали и действие, и объект, и (если виден) исполнитель.

Второй инвариант (R13): арбитр НИКОГДА не сливает задачи сам — вердикт `same` лишь **подсказывает** человеку (на уровне intake блокирует авто-приём; на прямом create заводит связь «дубликат»). Авто-merge запрещён владельцем.

## Эталонный промпт (канон — копировать байт-в-байт)

Полный текст — в `task-dedup-arbiter.prompt.ts` (`TASK_DEDUP_ARBITER_SYSTEM_PROMPT`, обёрнут `withAsrNote`, на call-site — `withInjectionGuard`). Структура:

### SYSTEM (стабильный, few-shot внутри → кэшируется)
- **# Кто ты** — арбитр-привратник задач: до записи решает дубль / разное / нет подходящей; бережёт каждое отдельное поручение.
- **# Что держать в голове (смысл задачи)** — ЗАЧЕМ (одно поручение из трёх каналов → три задачи), КОМУ (человек видит подсказку, авто-слияния нет), ЧТО станет (nil/different → новая задача; same → пометка «похоже на №…»), ГЛАВНОЕ ПРАВИЛО (сомневаешься → nil).
- **# Критерии (по порядку)** — 8 правил: (1) сначала проверь, есть ли вообще подходящая → иначе nil; (2) дубль только при совпадении действия+объекта+исполнителя, укажи номер; (3) один объект, разный этап → different; (4) разные исполнители → different/nil; (5) общая тема ≠ дубль; (6) ASR-искажения; (7) confidence про вердикт; (8) rationale по-русски без латиницы/кодов.
- **# Примеры (плохо → хорошо)** — 4 пары: NIL (похожие слова, дубля нет), SAME (одно поручение разными словами), DIFFERENT (один объект, разные этапы), NIL (разные исполнители).
- **# Перед тем как вернуть ответ — самопроверка** — 5 пунктов; при сомнении к «same» → перепиши на «nil».
- Финал: «Верни строго JSON по схеме TaskDedupArbiterVerdict… никакого текста вне JSON».

### USER (переменные — в конце; человеческие заголовки, не id)
```
Новая задача (кандидат на создание):
«<заголовок кандидата [+ описание]>»

Уже открытые похожие задачи (по порядку, ссылайся номером):
  1. «<заголовок>»
  2. «<заголовок>»

Определи: новая задача дублирует одну из открытых, это разное дело, или подходящей среди них нет.
Верни JSON по схеме TaskDedupArbiterVerdict.
```

### Выходной контракт
```json
{ "verdict": "nil|same|different", "sameWithRef": 0, "confidence": 0.0, "rationale": "одно русское предложение" }
```
`schema_name = "TaskDedupArbiterVerdict"`, strict. `sameWithRef` — 1-based номер из списка (при `same`), иначе 0 (модели не подаём id/коды).

## Разбор по анатомии (почему классный)

| Блок методологии | Как реализован здесь |
|---|---|
| **1. Роль/персона** | «Ты — арбитр-привратник задач… бережёшь каждое отдельное поручение». Узкая роль. |
| **2. Якоря смысла** | «Что держать в голове»: зачем (3 канала → дубли), кому (человек, авто-слияния нет), что станет с вердиктом. |
| **3. Критерии хорошего** | 8 нумерованных правил вместо «найди дубль»: действие+объект+исполнитель, этапы, общая тема, ASR. |
| **4. Few-shot** | 4 пары «плохо → хорошо»: NIL / SAME / DIFFERENT / NIL — покрывают все три вердикта, два из них NIL (дефолт). |
| **5. Self-check** | «Перед ответом проверь 1–5; склоняюсь к same при сомнении — перепиши на nil». |
| **6. Контракт** | строгий JSON `{verdict, sameWithRef, confidence, rationale}`, schema strict, NIL первым в enum. |
| **7. Запреты Z** | rationale «без латиницы, без кодов, без id»; на вход — заголовки, не машинные id. |
| **Cache-friendly** | весь текст и примеры в SYSTEM (стабилен); кандидат + список похожих — в конце USER. |
| **Человеческий вход** | подаём заголовки задач, ссылка номером (`sameWithRef`), не cuid. |
| **Гейт ≠ формулировка** | «делать дедуп вообще» решает код (порог `taskDedup.suggestThreshold`); LLM — только верификация «дубль ли». NIL-первый смягчает CLAMBER-переуверенность. |
| **Анти-инъекция** | заголовки могут прийти из разговора → `withInjectionGuard` + `wrapUserData` на call-site (как meeting-task-dedupe). |

## Как мерили (ship-on, без блокирующего golden)

Выкат включённым (kill-switch `taskDedup.enabled` ON). Прод-метрики: доля вердиктов `same` (ложно-высокая = арбитр клеит лишнее), доля принятых человеком подсказок-дублей, reopen после слияния. A/B порога `suggestThreshold` через AdminSetting. Жёстко — только `typecheck`/`build`/snapshot-spec; golden не блокирует ([[feedback_no_golden_ship_and_observe_prod]]).
