# ТЗ: консолидация извлечения (дедуп сущностей + блоков + граница pain/blocker)

## Зачем

Фиделити-прогон «Стрелы» (44 якоря): полнота **44/44**, но **консолидация сломана** — сущности задвоены
(23 имени как несколько Entity разных типов: Битрикс=technology+vendor+product, Логистик Плюс=client+
customer+vendor, retention=goal+topic+metric), блоки дублируются (блокер 429 ×4, webhook-риск ×3, «Моя
история» ×2). Это фрагментирует граф → **корень ведра ④ recall** (резолв не дотягивается). Фикс чинит и
качество графа, и recall одновременно. Данные — `plans/analysis/2026-07-03-strela-extraction-fidelity-results.md`.

## Границы

- **В scope:** консолидация сущностей (Д1), кросс-канальный дедуп блоков (Д2), граница pain/blocker (Д3).
- **НЕ в scope:** захват/полнота (работает 44/44); агрегирующий summary-узел (Д4, минор — отдельно).
- **Owner-gate:** Ф1/Ф2 меняют прод-поведение мёржа → одобрение владельца ДО кода.
- **Верификация:** прямой read-only запрос (before/after) + fidelity-eval Слоя 0 (когда построен).

## Ф0 — Диагностика корня (read-only, без стенда) `[ ]`

Установить ТОЧНУЮ причину по коду (path:line + дословно), не угадывая фикс:
- **Задвоение сущностей:** где принимается решение merge/create в `entity-resolution.service.ts` /
  `entity-merge.service.ts` / `entity-resolver.worker.ts`. Гипотеза: ключ мёржа = (нормализованное имя +
  **type**), поэтому одно имя с разным выведенным типом → разные Entity. Подтвердить/опровергнуть.
- **Дубли блоков:** почему `block-distill.worker.ts` (арбитр ~:103) не схлопывает один факт из разных
  каналов/дней — ключ дедупа per-source/per-window? Порог похожести? Подтвердить.
- Выход Ф0: точная причина каждого дефекта + место фикса.

Приёмка: короткая записка (path:line + вывод) в analysis-док; согласование фикса с владельцем (owner-gate).

## Ф1 — Консолидация сущностей (Д1) `[ ]`

- **Тип — атрибут канонической сущности, не ключ раскола.** Одно реальное имя → одна Entity; тип
  резолвится в «лучший» (приоритет доменных типов над generic topic/custom), остальные типы — в
  evidence/aliases, не в отдельные строки.
- **Консолидирующий проход** для существующего графа (стиль `graph-reconcile.cron`): найти same-name Entity
  (нормализация имени), слить в одну каноническую (`mergedIntoId`), выбрать тип по приоритету, объединить
  aliases/связи. Идемпотентно, kill-switch, батч-крутилка.
- Сохранить анти-generic (`entity-name-quality.ts`) и анти-over-merge (не слить реально разные —
  negative-cache `markEntityPairDistinct`).
- **Приёмка:** прямой запрос — «имён с несколькими типами» **23 → ≤3**; общее число активных Entity
  «Стрелы» падает (171 → ближе к ~143 уникальным); «Битрикс»/«Логистик Плюс»/«retention» — по одной
  канонической; юнит на консолидатор (same-name→merge, разные→не слиты, идемпотентность).

## Ф2 — Кросс-канальный дедуп блоков (Д2) `[ ]`

- Усилить `block-distill` арбитр: один факт из **разных каналов/дней** → один canonical IdeaBlock с
  несколькими `IdeaBlockEvidence`, а не N параллельных блоков. Матч — семантический (embedding-порог) поверх
  текущего ключа, кросс-source/кросс-window.
- Сохранить `primarySource='transcript'` побеждает report (block-distill.worker.ts:433).
- **Приёмка:** прямой запрос — блокер «Битрикс 429» **4 → 1** canonical (с ≥4 evidence); webhook-риск 3→1;
  «Моя история» idea 2→1. Юнит: два блока одного факта из разных source → merge; разные факты → не слиты;
  идемпотентность второго прогона.

## Ф3 — Граница pain/blocker (Д3) `[ ]`

- Правило в `block-ingest.prompt.ts` (+ классификатор типа): **критичный клиентский инцидент,
  останавливающий работу клиента** (напр. «отчёт не формируется второй день, завтра совет директоров») →
  `blocker`, не `pain`. `pain` — про внутреннюю боль/трение, не про клиент-стоп.
- Cache-friendly: правка в теле правил, стабильный префикс.
- **Приёмка:** golden-фикстура D3-кейса → `blocker`; A/B на затронутых кейсах не роняет остальную типологию;
  прямой запрос — инцидент Ромашки помечен blocker.
