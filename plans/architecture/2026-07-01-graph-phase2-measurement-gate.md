# Гейт-замер формы запросов — чтобы триггер фазы 2 графа перестал быть слепым

## Что это и зачем (человеческим языком)

Мы сознательно **отложили тяжёлый граф-обход** (Cypher-обход + community-summaries) до момента, когда пользователи реально начнут задавать «широкие» вопросы (multi-hop / агрегаты), а не только точечные факты. Решение и его цена разобраны в [`2026-07-01-graph-phase2-when-and-cost-decision-review.md`](../analysis/2026-07-01-graph-phase2-when-and-cost-decision-review.md).

Проблема: правило «включаем граф, когда пойдут широкие вопросы» **слепое** — мы нигде не видим, какая доля вопросов широкая. Значит момент «пора» придётся угадывать.

Эта фича делает момент видимым: каждый вопрос к памяти уже классифицируется системой (точечный факт vs список/тема/обзор/агрегат), надо лишь **вывести это в метрику с нужным разрезом** и записать **правило «на какой доле — считать, что пора думать про граф»** и **куда смотреть**. Дёшево, безопасно, ничего в проде для пользователя не меняет.

## Как сегодня (по факту кода, REALITY-CHECK)

- Каждый вопрос к памяти проходит шаг «понимания» `DialogService.process` → определяется `queryClass ∈ {list, topic, temporal, overview, fact}` и булев `aggregation` (ось «сколько/сумма/самый»).
- Уже есть метрика `z_router_query_class_total{class}` — считает распределение по 5 классам. **Но булев `aggregation` в метрику не попадает** → нельзя отделить «точечный факт» от «агрегата».
- **Concierge (Telegram-помощник) уже покрыт:** его вопросы к памяти идут через `chatV2.askEphemeral` → `resolveAnswer` → тот же `dialog.process`. Отдельный замер не нужен.
- **Крючки схемы из ADR Q5 уже на месте:** `RawEvent.sourceTitle` есть; рёбра `EntityLink` уже **bi-temporal** (`validFrom`/`validUntil` + бэкофилл). Схему трогать не нужно — ноль миграций.

## Что делаем

1. Добавляем в метрику `z_router_query_class_total` разрез `aggregation` (`yes` / `no` / `unknown`), прокидывая уже вычисленный `queryPlan.aggregation` из места, где метрика и так инкрементится.
2. Подтверждаем acceptance-проверкой, что путь concierge (`askEphemeral`) идёт через тот же `dialog.process` — т.е. покрыт автоматически.
3. Записываем в операционные доки **правило-гейт** (порог + окно + что делать при срабатывании) и **куда смотреть** (метрика в `/metrics`, пример PromQL).
4. Схему НЕ трогаем (крючки уже есть) — только сверка, зафиксированная в REALITY-CHECK.

## Как это будет выглядеть

**Было:** `z_router_query_class_total{class="fact"} 812` — не видно, сколько из них агрегатных, слепо.

**Стало:** доступен разрез, и по нему считается доля:
```
z_router_query_class_total{class="fact",  aggregation="no"}   980   ← точечные факты (single-hop)
z_router_query_class_total{class="topic", aggregation="no"}   140   ← широкие
z_router_query_class_total{class="overview",aggregation="no"}  60
z_router_query_class_total{class="fact",  aggregation="yes"}    75   ← агрегаты
...
```
PromQL «доля широких/агрегатных за 30 дней»:
```
sum(increase(z_router_query_class_total{aggregation="yes"}[30d]))
  + sum(increase(z_router_query_class_total{class=~"topic|overview|list"}[30d]))
/ sum(increase(z_router_query_class_total[30d]))
```
И правило в доке: «≥ порога на окне при ≥ N вопросов → повод поднять фазу-2 графа в приоритет (запустить feature-analyst по multi-hop-ретриву)». Автоматически ничего не включается — это сигнал человеку.

## Решения, принятые за владельца (дефолты, поправишь при желании)

| # | Решение | Обоснование |
|---|---|---|
| 1 | Порог-ориентир: **доля широких/агрегатных ≥ 20%** на окне **30 дней** при **≥ 200** вопросах к памяти | Порядок величины: пока single-hop доминирует (>80%), граф не окупается (ADR); 20% широких — заметный устойчивый спрос. Это **ориентир для человека, не автотриггер** — ничего в проде не меняет, поправить в доке дёшево. |
| 2 | Разрез — только `aggregation`, без `personScope` | Гейт про форму hop (single vs широкий); `class` + `aggregation` этого достаточно. `personScope` — про адресата, не про hop → не добавляем (не код ради кода). |
| 3 | Наблюдение — правило-док + метрика в `/metrics`, **без нового алерта/дашборд-инфры** | Alert/Grafana-инфры в доках нет; заводить её ради одного гейта — преждевременно. Ручная свер­ка раз в период по PromQL достаточна на текущем масштабе. |

## Границы (что НЕ входит — вне scope)

- **Горячий граф-слой** (community-summaries, Cypher-обход на чтении) — не трогаем; он включается по срабатыванию этого гейта, отдельным ТЗ.
- **Bi-temporal / крючки схемы** — уже реализованы, не трогаем.
- **Новый алертинг / Grafana-дашборд** — не заводим (Решение 3).
- **Изменение самой классификации** (`queryClass`/`aggregation`) — используем как есть, не переобучаем.

## Как поймём, что получилось

- В `/metrics` у `z_router_query_class_total` появился лейбл `aggregation` с ненулевыми сериями после реальных вопросов.
- Concierge-вопрос к памяти инкрементит ту же метрику (подтверждено путём кода).
- В операционном доке есть правило-порог + PromQL + инструкция «что делать при срабатывании».
