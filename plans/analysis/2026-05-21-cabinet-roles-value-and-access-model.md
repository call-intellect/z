# Анализ: Польза ЛК для руководителя и сотрудника + модель доступа к информации

## 0. Зачем этот документ

Аналитика [user-cabinet-design.md](2026-05-21-user-cabinet-design.md) (от 2026-05-21) закрыла **навигацию и каркас** ЛК (личного кабинета). Этот документ закрывает следующий уровень — **продуктовую ценность** и **уровни доступа к информации**:

1. **Зачем руководителю** открывать ЛК Z каждый день — функция × польза.
2. **Зачем сотруднику** открывать ЛК Z каждый день — функция × польза.
3. **Как ограничивается доступ** к информации внутри одной компании — кто видит финансовые/HR/стратегические факты, кто нет.

Без этого документа:
- Sub-TZ 0c (мастер знакомства и страницы Фазы 0) можно дописать, но он не будет отвечать на вопрос «а member ради чего сюда заходит, если он не запускает встречу прямо сейчас» — есть риск построить мёртвый раздел `/me`.
- В Фазе 0 уже копятся IdeaBlock-и из финансовых/HR-встреч, и **по умолчанию они доступны всем manager'ам Org через `policy.csv`** (см. §5.2 ниже). Это блокер для пилотов в компаниях 50+ человек ещё до полноценной Фазы β с ABAC.

**Что я НЕ решаю в этом документе:** конкретные API-контракты эндпоинтов (sub-TZ), UI-визуал (delivery/), полная спецификация ABAC на уровне фактов (это отдельный ТЗ Фазы β).

## 1. Контекст: что уже зафиксировано

### 1.1. Категория продукта и ICP (идеальный профиль клиента)

Из [positioning.md](../../second-brain/06_marketing/positioning.md): **«память компании»** для CEO и руководителей компаний 50–300 человек. Это значит:

- **Главный пользователь ЛК** — руководитель (CEO / директор / руководитель отдела). Он принимает решение о покупке и для него ЛК должен показывать пульс компании.
- **Массовый пользователь ЛК** — сотрудник, у которого нет интереса «следить за всей компанией», но есть интерес «не потерять свою память» и «быстро спросить помощника».
- **Косвенный пользователь** — гость встречи (внешний партнёр / кандидат / клиент), который вообще не должен ничего знать про устройство Z.

### 1.2. Текущая модель ролей

Из [orgs-and-rbac.md](../../second-brain/01_projects/orgs-and-rbac.md) + [policy.csv](../../backend/src/modules/rbac/policies/policy.csv):

**Внутри Org (бизнес-роль в Membership):**

| Роль | Назначение | Кого ассоциировать |
|---|---|---|
| `owner` | Владелец Org (один на компанию) — стратегические решения, биллинг, право удалять личные данные (152-ФЗ) | CEO / founder |
| `admin` | Заместитель owner'а — всё, кроме owner-only действий | IT-директор / операционный директор |
| `manager` | Рядовой сотрудник Org | Любой сотрудник компании клиента |

**Вне Org (платформенная роль):**

| Роль | Назначение |
|---|---|
| `super_admin` (`User.isSuperAdmin`) | Оператор Z (наша сторона) — Z-Admin, bypass RBAC, доступ через `SuperAdminAccessLog` |
| Гость встречи (Guest) | Без аккаунта в Z; LiveKit-токен ограниченного типа; только Live-комната |

**В этом документе под «руководитель» понимается `owner` + `admin` Org, под «сотрудник» — `manager` Org.** Гость рассматривается отдельно в §4.

### 1.3. Текущие слои защиты информации (4 уровня)

Что уже есть в коде:

1. **`tenantId` на каждом ресурсе** — multi-tenancy (мультиарендность); пользователи разных Org не видят друг друга в принципе. Реализовано через `TenantGuard` (`backend/src/modules/rbac/guards/tenant.guard.ts`).
2. **RBAC по типу ресурса** — `policy.csv` с правилами вида `p, manager, *, *, block, read` (manager читает все блоки идей). Гранулярность — тип ресурса × действие.
3. **`Org.visibilityMode = open | strict`** — переключатель «manager видит всё в Org» (open) vs «manager видит только своё» (strict). Применяется только к ресурсам с `ownerUserId` (Meeting, Card, Task) — не применяется к shared knowledge (IdeaBlock, Theme, Entity).
4. **`dataClass` на источнике** — `public | internal | sensitive | private`. **Но это НЕ ACL** — это только маршрутизация в LLM-роутере (sensitive/private нельзя слать во внешний Claude, см. `LlmTaskRoute.requiredDataClass`).

**Ключевой вывод:** в Z **нет ни одного механизма ACL уровнем глубже, чем «тип ресурса × роль × open/strict»**. Внутри Org все встречи равны, все документы равны, все блоки идей равны.

## 2. Польза ЛК для руководителя (owner / admin)

### 2.1. Главная история (one-liner)

> **«Я вижу пульс компании за 30 секунд и нахожу любой факт за один вопрос помощнику, даже если автор уволился.»**

Соответствует hero-блоку лендинга — benefit-2 («CEO видит компанию за 30 секунд») + benefit-3 («Знание остаётся в компании, а не уходит с людьми») из [positioning.md](../../second-brain/06_marketing/positioning.md).

### 2.2. Карта функций × польза (Фаза 0 + γ)

| Функция ЛК | URL | Польза для руководителя | Когда заходит | Доступно в |
|---|---|---|---|---|
| **Дашборд директора** | `/dashboard` | Один экран: горячие сигналы, активные темы, согласованность с целями, структура компании, недавние решения | Утром, после совещаний, перед отчётом совету директоров | Фаза 0 (расширяется) |
| **Структура компании** | `/structure` | Видит карту: отделы → должности → сотрудники со статусом приглашения; может пригласить нового, переназначить должность, уволить | Онбординг нового сотрудника, реорганизация отдела | Фаза 0 |
| **Документы компании** | `/documents` | Все должностные инструкции, регламенты, политики, договоры — в одном месте, с автоматическим извлечением фактов | Готовится к ревью отдела, проверяет «что у нас вообще зафиксировано» | Фаза 0 |
| **Карты должностей** | `/roles` | По каждой должности автоматически собранная сводка: ответственности, навыки, типичные решения, типичные грабли, стиль работы | Подбор замены при увольнении, оценка пробелов в команде | Фаза 0 (наполнение от 0d) |
| **Цели и стратегия** | `/goals` | Декомпозиция: миссия → стратегия → цели → процессы; для каждой цели — индикатор согласованности с темами и встречами | Стратегическая сессия, квартальный обзор | Существует (Фаза 9), расширяется в γ |
| **Темы** | `/themes` | AI-кластеры сигналов: «что обсуждают», «что нарастает», «что затухает»; источник — все встречи Org | Поиск трендов, подготовка к совету директоров | Существует (Фаза 4) |
| **Карточки клиентов/проектов** | `/cards` | На каждого ключевого клиента — AI-сводка по всем встречам, контактам, решениям | Перед встречей с клиентом за 1 минуту понять контекст | Существует |
| **Помощник компании** | `/chat` | Спрашивает на естественном языке: «Что мы решили по проекту X в прошлом квартале?», «Какие риски обсуждали с клиентом Y?», «Какие болевые точки чаще всего у отдела продаж?» — ответы по всему графу памяти | Постоянно, заменяет «спросить Иру из HR кто что когда говорил» | Существует (Фаза 7), расширяется в γ |
| **Встречи** | `/meetings` | Все встречи компании (в режиме open) или только свои (в режиме strict) с поиском по содержимому | Поиск конкретной встречи, аудит | Существует |
| **Z-Admin функции для Org** | `/settings/admin` | Управление членством, политикой видимости, retention, тарифом, источниками ingest | Конфигурация Org, выдача доступов | Существует (Фаза 7, частично) |
| **Дамп мысли** | `/dump` | Быстро записать неструктурированную мысль, которая автоматически попадёт в граф памяти | Между встречами, на ходу | Фаза 0 минимальный, γ — расширение (голос, AI-feedback) |
| **Личная страница «Я»** | `/me` | Своя должность, свои документы, свои встречи — как у любого сотрудника | Если хочет посмотреть на компанию глазами обычного сотрудника | Фаза 0 минимальный |

### 2.3. Что руководитель **должен мочь делать**, но это не всегда очевидно

Список «не очевидных, но необходимых» функций, которые часто упускают из ЛК CEO:

1. **Делегировать без передачи owner'ства.** Руководитель уехал на 2 недели — заместитель должен мочь приглашать сотрудников, видеть всё, кроме owner-only действий (билллинг, удаление личных данных). → Это уже закрыто ролью `admin`, нужно явно показывать в UI.
2. **Понизить себя в строгий режим временно.** На время аудита — переключить Org в `strict` mode, чтобы видеть, что увидит manager. → Сейчас `Org.visibilityMode` есть, переключатель в UI — не реализован.
3. **Видеть, что про него самого говорят.** В встречах сотрудников могут упоминаться решения руководителя. Должна быть страница «упоминания меня» — отфильтрованный список блоков идей с упоминанием `Person` руководителя. → Не реализовано, кандидат на γ.
4. **Помечать встречу/документ конфиденциальной.** До любого ABAC — простой чекбокс «эта встреча видна только мне и приглашённым». → Не реализовано, **критический gap** (см. §5).
5. **Запросить отчёт у Z за период.** «Что произошло в компании за неделю?» — отдельный режим помощника с шаблоном. → Расширение `/chat` в γ или отдельная страница `/today`/`/week`.
6. **Видеть AI-расход компании.** Сколько токенов / денег ушло на анализ, какие модели использовались. → Существует частично в `/admin/ai-usage` и `/settings/admin`.
7. **Видеть журнал доступа к чувствительным данным.** Кто и когда смотрел финансовую встречу, кто скачивал документ с зарплатами. → Не реализовано, **обязательно для compliance** (см. §5.4 «Фаза β»).

### 2.4. Что **не** входит в ЛК руководителя

- Управление кодом Z, тарифной сеткой, провайдерами LLM — это Z-Admin (`/admin`), доступно только super_admin (наша сторона).
- Управление LiveKit-серверами, диагностика медиа — Z-Admin.
- Создание новых типов встреч в системе — Z-Admin (Фаза γ может добавить custom-типы per Org).

## 3. Польза ЛК для сотрудника (manager)

### 3.1. Главная история (one-liner)

> **«Я не теряю свою память (встречи, документы, договорённости) и быстро спрашиваю помощника по компании, что мне разрешено знать.»**

Это **другая** ценность, чем для руководителя. Руководитель хочет видеть компанию сверху. Сотрудник хочет, чтобы Z был его рабочим инструментом, как почта или мессенджер, и **не требовал лишних усилий**.

### 3.2. Карта функций × польза

| Функция ЛК | URL | Польза для сотрудника | Когда заходит | Доступно в |
|---|---|---|---|---|
| **Моя страница** | `/me` | Один экран: моя должность, мой отдел, моя карта должности (что про меня знает Z), мои встречи, мои документы | Default landing после логина (см. [user-cabinet-design.md решение 2](2026-05-21-user-cabinet-design.md)); проверка «что Z про меня знает» | Фаза 0 минимальный |
| **Моя карта должности** | `/roles/:myRoleId` | Что Z собрал про мою должность из моих встреч и документов; помогает онбордингу новых коллег на ту же должность | Раз в неделю, после крупных встреч | Фаза 0 |
| **Мои встречи** | `/meetings?my=true` | Все встречи, в которых я участвовал, с AI-отчётом, расшифровкой, поиском по содержанию | Восстановить «что мы там договорили на прошлой неделе» | Существует |
| **Создание встречи** | `/meetings/create` | Создать комнату, пригласить участников (зарегистрированных или гостей), выбрать тип встречи под AI-отчёт | Перед звонком с клиентом, командой, кандидатом | Существует |
| **Мои документы** | `/documents?uploader=me` | Документы, которые я загрузил (договоры, мои заметки, должностная инструкция) | Найти «куда я положил тот пдф» | Фаза 0 |
| **Загрузка нового документа** | `/documents` (кнопка) | Положить документ → Z автоматически распарсит, извлечёт факты, привяжет к должности или общим документам | Каждый раз когда получил новый pdf/docx | Фаза 0 |
| **Дамп мысли** | `/dump` | Быстро записать мысль/идею/наблюдение → попадёт в граф памяти, через помощника потом найдётся | Между делами, мысль на ходу | Фаза 0 минимальный |
| **Помощник компании** | `/chat` | Спрашиваю по компании — «как у нас принято делать X», «что мы решили про Y» — получаю ответ по доступной мне части памяти | Минимум раз в день, заменяет «спросить коллегу» | Существует |
| **Карточки и темы** | `/cards`, `/themes` | Доступ к карточкам клиентов/проектов и темам компании (если режим open) | Подготовка к встрече с клиентом | Существует |
| **Задачи** | `/tasks` | Задачи, извлечённые из встреч, в которых я участвовал | Утренняя проверка «что мне сегодня делать» | Существует |
| **Уведомления** | (header) | Меня пригласили в Org / приходит новая запись встречи / на меня назначена задача | Постоянно, фоном | Существует частично |

### 3.3. Тонкие моменты пользы для сотрудника

1. **Помощник компании НЕ должен утечь чужие данные.** Если сотрудник пишет «какая выручка в Q1?» — система **не должна** ответить из финансовой встречи CEO. Должна вежливо отказать («у меня нет доступа к этим данным») или ответить из публичных коммуникаций. → Требует фильтрации RAG (поиск с дополнением, retrieval-augmented generation) по уровню доступа задающего вопрос. Сейчас этого нет (см. §5.2).
2. **Карта должности — главный «вау-эффект» для сотрудника.** Это первое, что он видит на `/me`. Если карта пустая или содержит ерунду — сотрудник теряет доверие к Z. Поэтому в Фазе 0d (`RoleProfileAgent`) есть порог `N` блоков идей перед генерацией.
3. **Сотрудник может не знать, что есть Z**, пока его не пригласят. Первый экран после принятия приглашения должен сразу показывать пользу — иначе он не вернётся.
4. **Сотрудник в `strict` режиме** видит только свои встречи и документы. Это нормально для крупных компаний (50–300 чел). Но в маленьких командах (10–30 чел) `strict` создаст ощущение «изолированного приложения для встреч», что противоречит позиционированию «память **компании**». Дефолт — `open`, переключение — осознанное решение руководителя.

### 3.4. Что **не** входит в ЛК сотрудника

- Управление структурой (отделы, должности, приглашения) — только owner/admin.
- Чужие документы и встречи (зависит от режима visibility + ABAC в будущем).
- Цели компании — read-only в режиме open, скрыто в strict; редактирование — только owner.
- Биллинг, тариф, удаление личных данных — только owner.
- Z-Admin — никогда.

## 4. Польза для гостя встречи (Guest)

Гость встречи — **не пользователь ЛК**, у него нет аккаунта в Z. Он попадает только в одну точку — `https://meet.<domain>/m/<id>` — и:

- Видит Live-комнату (видео/аудио/чат/screen share).
- Может включать-выключать свой микрофон/камеру.
- Поднимает руку.
- **Не видит** AI-отчёт после встречи (это право только host'а).
- **Не получает** никаких корпоративных данных, кроме того, что говорится в самой комнате.
- LiveKit-токен — ограниченного типа, без admin-permissions комнаты. См. [rbac-access-control.md](../../second-brain/01_projects/rbac-access-control.md).

**Польза для гостя:** нет трения — не надо регистрироваться, чтобы попасть на встречу с компанией клиента. Это маркетинговое отличие vs Zoom/Teams (там тоже есть guest access, но в РФ-аналогах часто требуется регистрация).

**Важно для модели доступа:** гость в Z по факту = «недоверенная сторона». Всё, что он скажет в встрече, попадёт в граф памяти компании-host. Гость **не получит** ничего обратно. Это правильно по умолчанию, но создаёт обязательство: если гость говорит конфиденциальное (например, на CustDev-интервью), хост должен иметь возможность пометить встречу `confidential` сразу при создании.

## 5. Модель доступа к информации

### 5.1. Что есть сейчас (4 слоя защиты)

Возвращаюсь к §1.3 с детализацией.

#### Слой 1 — `tenantId` (Org boundary)

**Что защищает:** разные Org не видят друг друга вообще.
**Как работает:** `TenantGuard` извлекает `tenantId` из `X-Org-Id` / `:orgId` / тела / дефолта; кладёт в `req.tenantId`; все Prisma-запросы скоупятся через `where: { tenantId }`.
**Слабые места:** super_admin bypass'ит (но это намеренно — он оператор Z).

#### Слой 2 — RBAC по типу ресурса

**Что защищает:** какая роль (owner/admin/manager) может что делать с каким типом ресурса.
**Как работает:** [policy.csv](../../backend/src/modules/rbac/policies/policy.csv) (формат Casbin), `RbacService.canAccess(role, visibilityMode, resourceType, action, ownerMatch)`.
**Гранулярность:** тип ресурса × действие × `self`/`*`. **Внутри одного типа все ресурсы равны** — нет понятия «эта конкретная встреча чувствительнее той».

#### Слой 3 — `Org.visibilityMode` (open/strict)

**Что защищает:** в режиме `strict` manager видит только ресурсы, где `ownerUserId == self`.
**Где применяется:** Meeting, Card, Task, MeetingChapter, MeetingHighlight, MeetingChatMessage, Tag.
**Где НЕ применяется:** IdeaBlock, Entity, Theme, Document, Person, Role, Department, RoleProfile — это **shared knowledge** компании, manager читает всё (в обоих режимах).

#### Слой 4 — `dataClass` на источниках/блоках

**Что защищает:** маршрутизацию в LLM-роутере — `sensitive` и `private` запрещены к отправке во внешний Claude.
**Что НЕ защищает:** просмотр пользователем. Manager с правом `read` на `block` увидит блок любого `dataClass`.

### 5.2. Где это ломается — 4 сценария

#### Сценарий А — Финансовая встреча CEO

Owner и CFO провели Zoom-звонок про выручку Q1 и план M&A. Тип встречи `team` (общая командная) или новый `finance` (если завести). Org в режиме `open` (дефолт).

**Что произошло после AI-pipeline:**
1. `Meeting` создан с `dataClass = internal` (дефолт).
2. `AiResult.structured_data` = `{ revenue: ..., ebitda: ..., m_and_a_targets: [...] }`.
3. Из транскрипта извлечены `IdeaBlock`-и с `signalType ∈ {fact, decision, risk}`, наследует `dataClass=internal`.
4. `Decision` (Фаза 0 группа Б) — «решено купить компанию X за Y млн».

**Что видит **любой** manager Org:**
- `Meeting` метаданные ✓ (видит — `p, manager, open, *, meeting, read`).
- `AiResult` со структурированными финансовыми данными ✓ (видит через Meeting).
- `IdeaBlock`-и с фактами ✓ (видит — `p, manager, *, *, block, read`).
- `Theme` про финансы (если кластер собрался) ✓.
- **Помощник компании** в RAG-чате найдёт финансовые блоки и выдаст любому manager'у по запросу «расскажи про финансовые планы».
- **`Decision` — единственное исключение**: `p, manager, *, self, decision, read` — менеджер видит **только свои** решения. Это уже частичная защита, но недостаточная.

**Вывод:** в нынешней модели **финансовые встречи нельзя проводить в Org**, если в Org больше 2-3 человек и есть хотя бы один manager. Это блокер для пилотов в SMB (малом и среднем бизнесе) 50–300 чел.

#### Сценарий Б — HR-встреча про увольнение

Owner с HR-директором обсуждают увольнение конкретного сотрудника. Тип встречи `team` или новый `hr`. То же, что в сценарии А: все факты и решения становятся видны всем manager'ам — **включая того сотрудника, которого собираются уволить**. Это юридический и репутационный риск.

#### Сценарий В — Стратегическая встреча про привлечение раунда

Owner + 1-2 партнёра обсуждают подготовку к раунду A. Не должно стать публичным внутри компании ни в каком виде. Та же проблема.

#### Сценарий Г — CustDev-интервью с клиентом

Sales провёл интервью с клиентом, обсудили боли, бюджет, кто принимает решения. По договорённости с клиентом, **некоторые цитаты конфиденциальны** (например, упоминания конкурентов или внутренних проблем клиента). В нынешней модели весь транскрипт и все факты доступны всей команде на чтение — это нарушает обещание sales'а клиенту.

### 5.3. Целевая модель — 5 слоёв (расширение текущих 4)

Добавляем **слой 5: чувствительность факта + явный круг доступа (ABAC, attribute-based access control)**.

| Слой | Что защищает | Где есть сейчас | Целевое состояние |
|---|---|---|---|
| 1. `tenantId` | Org boundary (между Org) | ✓ | Без изменений |
| 2. RBAC по типу ресурса | Роль × тип × действие | ✓ | Без изменений |
| 3. `Org.visibilityMode` | open/strict для ресурсов с владельцем | ✓ | Добавить UI-переключатель для owner |
| 4. `dataClass` (LLM routing) | Выбор провайдера LLM | ✓ | Без изменений (это про data residency, не про ACL) |
| 5. **`sensitivity` + ACL на факте** | Кто видит **этот конкретный** ресурс | ✗ | **Новое — Фаза γ / β** |

#### Слой 5 — устройство (минимальная версия в γ)

Три уровня чувствительности на ключевых ресурсах:

```
enum Sensitivity {
  public      // открыто всем member Org
  internal    // дефолт; видно всем manager (как сейчас)
  confidential // видно только owner/admin + явному списку Person из ACL
}
```

Добавить поле `sensitivity` на:
- `Meeting` — задаётся host'ом при создании встречи (по умолчанию `internal`).
- `Document` — задаётся загружающим (по умолчанию `internal`).
- `IdeaBlock` — **наследуется** от источника (`RawEvent.dataClass` + `Meeting.sensitivity` + `Document.sensitivity`).
- `Decision` — **наследуется** от источника или задаётся явно при ручном создании в γ.

Для `confidential`:
- Поле `confidentialityAcl: PersonId[]` — список людей, имеющих доступ помимо owner/admin.
- При создании встречи в UI — multiselect «кто ещё видит» с автоподсказкой по `Person`/`Department`/`Role`.
- При загрузке документа — то же.
- Наследование на `IdeaBlock`/`Decision`/`AiResult` — автоматически.

#### Слой 5 — устройство (полная версия в β)

`FactAcl` (отдельная таблица) — N:M между `IdeaBlock`/`Decision`/`Entity` и `Person`/`Role`/`Department`. Позволяет:
- Раздать доступ к конкретному факту, не ко всей встрече (например, после агрегации тем).
- Унаследовать через граф (если факт упомянут в встрече X, виден тем, кто видит X).
- Делать **temporal walk**: «факт виден от valid_from до valid_to» (привязка к bi-temporal слою Фазы α).

Это полноценный ABAC, требует:
- `FactAcl` модели.
- Расширения `GraphService` на проверку доступа при обходе графа.
- Перекодировки `KnowledgeSearchService` и `chat-rag.service` на фильтрацию по доступу задающего.

### 5.4. Поэтапное внедрение

#### Этап 1 — Фаза 0 (СЕЙЧАС, никаких новых моделей)

Что сделать без расширения скопа Фазы 0:

1. **Документировать gap явно.** Добавить в [phase-0-roles-and-onboarding.md](../tz/2026-05-21-phase-0-roles-and-onboarding.md) §8 «Риски и ограничения» строку: «Внутри Org нет fact-level ACL. Финансовые/HR/стратегические встречи в режиме `open` видны всем manager'ам. Для пилотов в SMB 50+ чел — переходить на `strict` mode или ограничивать пилоты руководящей командой до Фазы γ».
2. **На лендинге и в продаже** не обещать «факт-уровневой защиты до Фазы γ». Реальное обещание Фазы 0 — multi-tenancy + RBAC + open/strict, не больше.
3. **Дефолт `visibilityMode = open`** оставить (как сейчас) — для маленьких команд это правильное. Но в `/settings/admin` сделать видимый переключатель + объяснение в одно предложение «что меняется».
4. **Помощник компании** (`/chat`, `knowledge-core` chat-rag) — на Фазе 0 фильтрует контекст по `visibilityMode` (для `strict` manager-а — только его источники). Это уже частично есть в [chat-rag.service](../../backend/src/modules/ai/services), нужно проверить и зафиксировать тестом.
5. **`Decision` уже защищён** правилом `p, manager, *, self, decision, read` — фиксируем как образец, документируем why.

#### Этап 2 — Фаза γ (после Фазы 0, отдельное ТЗ)

Минимальный ABAC через `sensitivity` + `confidentialityAcl`:

1. Добавить enum `Sensitivity` + поля `sensitivity` на `Meeting`, `Document`, `IdeaBlock`, `Decision`, `AiResult`.
2. Добавить `confidentialityAcl: Json` (список `personId` + опционально `roleId`/`departmentId` как краткая запись «вся должность X»).
3. UI:
   - При создании встречи — selector «Кто видит результаты»: `Всем (internal)` / `Только мне` / `Список людей`.
   - При загрузке документа — то же.
   - На странице встречи/документа — иконка замка для `confidential`, hover показывает «доступ: …».
4. Backend:
   - Расширить `RbacService.canAccess` на проверку `sensitivity` + `confidentialityAcl`.
   - `KnowledgeSearchService` фильтрует выдачу по доступу запрашивающего.
   - `chat-rag.service` исключает закрытые блоки из контекста LLM.
   - `BlockExtractionService` при разборе — копирует `sensitivity` от источника на каждый `IdeaBlock`.
5. Журнал доступа к чувствительным ресурсам (`SensitiveAccessLog`) — кто и когда смотрел `confidential` ресурс. Видно owner'у.

**Что НЕ входит в γ:** полноценный fact-level ABAC на отдельные `IdeaBlock`-и (это β); temporal walk; делегирование acl.

#### Этап 3 — Фаза β (после α)

Полный ABAC согласно roadmap'у. Содержание:
- `FactAcl` модель.
- Расширение `GraphService` и поисковых сервисов.
- Делегирование доступа через `Role`/`Department` (например, «все, кто на роли CFO, видят все факты с тегом `finance`»).
- Temporal acl (доступ от valid_from до valid_to).
- Compliance-журналы (152-ФЗ, GDPR).

Это отдельный зонтичный ТЗ, оценка — 1.5–2 месяца после Фазы α.

### 5.5. Матрица доступа: кто что видит в Фазе 0 (как есть)

Сводная таблица по ключевым типам данных. Для каждой роли — что видит **в обоих режимах** (`open` и `strict`).

| Ресурс | owner | admin | manager (open) | manager (strict) | guest |
|---|---|---|---|---|---|

| Meeting | RW все | RW все | R все, W свои | R/W только свои | в комнате на время встречи |
| AiResult (отчёт встречи) | R все | R все | R все | R только своих встреч | — |
| Recording (аудио/видео) | R все | R все | R все, **скачать только свои** | R/скачать только свои | — |
| Document | RW все | RW все | R все, W свои | R/W только свои | — |
| Card (CRM) | RW все | RW все | R все, W свои | R/W только свои | — |
| Task | RW все | RW все | R все, W свои | R/W только свои | — |

## 6. Что отверг

| Идея | Почему отверг |
|---|---|
| Сделать ABAC сразу в Фазе 0 | Фаза 0 уже на пределе (16 моделей, AGE-инфраструктура, мастер, агент). ABAC — отдельный большой блок, который растянет фазу ещё на 6–8 недель. Гэп закрываем процедурно (см. §5.4 этап 1) |
| Сделать `member` отдельной ролью между `manager` и без-прав | Достаточно `manager` + `visibilityMode` для покрытия большинства сценариев. 4-я роль усложняет policy.csv без явной пользы |
| Отдельный кабинет для руководителя и для сотрудника (разные URL) | См. [user-cabinet-design.md решение 2](2026-05-21-user-cabinet-design.md): один URL, разное содержимое через RBAC. Раздваивать роуты — путь к двум разъезжающимся UI |
| Скрыть `/dashboard` от manager-а | Member тоже должен чувствовать себя «частью компании», видеть пульс. Закрытие = силосный продукт. Содержимое дашборда фильтруется по доступу, но сам URL — общий |
| Запретить guest-доступ полностью, требовать регистрацию | Противоречит UVP («гость без регистрации» — отличие от конкурентов в РФ, см. positioning.md строка 44). Guest должен остаться |
| Сделать `dataClass` ACL'ем | `dataClass` — это про data residency и LLM routing (`sensitive`/`private` нельзя слать наружу). Совмещение с ACL смешает две разные оси — где данные физически лежат vs кто их может смотреть |
| Шифровать конфиденциальные блоки на уровне БД | Преждевременная сложность. Z работает on-prem или в РФ-юрисдикции (см. positioning.md), угроза «облачный провайдер читает БД» не релевантна. ABAC на уровне приложения — достаточно для всех заявленных threat models |

## 9. Резюме (TL;DR)

**Польза руководителю:** пульс компании за 30 сек + помощник, который помнит за всю команду. Главные точки входа — `/dashboard`, `/structure`, `/roles`, `/chat`. Главное опасение — «утечка финансовых/HR/стратегических фактов всем подряд» — закрывается процедурно в Фазе 0 + ABAC в γ.

**Польза сотруднику:** не теряю свою память + быстро спрашиваю помощника по доступной мне части. Главные точки входа — `/me`, `/chat`, `/meetings`, `/dump`. Главное опасение — «карта должности пустая или ерундовая» — закрывается порогом `N` блоков в `RoleProfileAgent` (Фаза 0d).

**Польза гостю:** нет трения, не надо регистрироваться. Гость никогда не получает данные Org обратно.

**Текущая модель доступа — 4 слоя** (`tenantId` + RBAC + `visibilityMode` + `dataClass`-routing). **Не хватает 5-го слоя** — чувствительность факта + явный круг. До его внедрения:

1. **Фаза 0** — документировать gap, помощник компании фильтрует контекст по `visibilityMode`, дефолт `open` для маленьких команд, `strict` для 30+;
2. **Фаза γ** — `sensitivity` enum + `confidentialityAcl` на Meeting/Document/IdeaBlock/Decision/AiResult; UI-замок и selector «кто видит»;
3. **Фаза β** — `FactAcl` с делегированием через Role/Department, temporal acl, compliance-журналы.
