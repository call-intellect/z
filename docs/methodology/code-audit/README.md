# Методология: состязательный аудит логики модуля («найди → опровергни»)

> **Что это.** Универсальный способ за один прогон проверить ЛЮБОЙ модуль (или любого
> агента, воркер, cron, сервис) на скрытые **баги логики и несоответствия** — не
> «прочитать глазами», а развернуть рой агентов, который сначала ищет проблемы, а потом
> КАЖДУЮ находку отдаёт независимому скептику на опровержение. На выходе — список
> подтверждённых проблем (симптом + корень + фикс + `file:line`) и отдельный список
> опровергнутых (чтобы их больше никто не перепроверял).
>
> **Что ищем — не только «падает».** (1) Баги логики: гонки, утечки/застой статусов,
> дрейф счётчиков, раннавей-расход, потеря данных, обход гейтов. (2) **Несоответствия
> (рассогласования):** код противоречит своему контракту/комментарию/схеме; две ветки
> или два источника правды расходятся; денормализованные данные дрейфуют; реализация не
> совпадает с тем, что заявлено. Несоответствие — такой же дефект, как явный баг.
>
> **Это самостоятельная методология — про КОД, не про промпты.** Лежит в общем хабе
> методологий рядом с [методологией промптов](../prompts/README.md), но независима: ту
> вызывают, чтобы писать/чинить промпты, эту — чтобы искать дефекты в коде любого модуля.
> Обе «вызываются» владельцем одной фразой.
>
> **Происхождение.** Выведена из аудита модуля M5 «Клоны» (2026-06-16): 8 под-областей,
> ~35 агентов, 2 прохода → 27 находок → **21 подтверждён, 6 опровергнуто**. Пример —
> в конце документа.

---

## 0. Когда применять / когда нет

**Применять:**
- перед или после крупной правки модуля — «убедиться, что не осталось багов»;
- когда модуль накопил несколько волн доработок и в нём легко спрятался регресс;
- когда «что-то ломается, но непонятно где» — рой покрывает модуль шире, чем один проход.

**Не применять (дорого и не нужно):**
- одна-две функции / точечная правка — хватит обычного чтения;
- чисто косметика/переименования без логики;
- когда уже точно известны и баг, и место.

> ⚠️ Это **многоагентный прогон** (десятки агентов, заметный расход токенов). Он
> запускается только при явном согласии — см. §3. Без согласия Claude делает
> урезанную последовательную версию (один ревьюер на область, без отдельных скептиков).

---

## 1. Главный принцип: «найди → опровергни» (find-then-refute)

Одиночный ревьюер выдаёт «правдоподобные, но неверные» находки: звучит как баг, а по
трассе кода — не баг. Поэтому **ни одна находка не считается багом, пока её не
попытался опровергнуть отдельный скептик**, читая реальный код и строя трассу.

Три правила, которые делают метод честным:
1. **Состязательность.** Скептик получает задачу ОПРОВЕРГНУТЬ находку, а не
   «оценить». По умолчанию — «не баг», пока не доказано обратное трассой.
2. **Severity — ПОСЛЕ опровержения.** Критичность ставится только тем находкам, что
   пережили скептика. До проверки severity не присваиваем (чтобы не раздувать панику).
3. **Опровергнутые сохраняем.** Список «проверено — НЕ баг» с причиной идёт в отчёт,
   чтобы следующая сессия их не перепроверяла (экономия и защита от повторов).

## 2. Архитектура прогона (2 прохода + синтез)

```
Проход 0 (Карта)     один агент читает модуль → делит на N независимых под-областей
                     (по сервисам / стадиям пайплайна / кронам), отдаёт список с файлами
        │
        ▼
Проход 1 (Поиск)     по одному finder-агенту на под-область, ПАРАЛЛЕЛЬНО.
                     Каждый читает реальный код и выдаёт находки (симптом + трасса + фикс).
        │            finder'ы слепы друг к другу — это и нужно (разные углы).
        ▼
Проход 2 (Проверка)  по каждой находке — отдельный скептик. Пытается ОПРОВЕРГНУТЬ
                     по коду. Вердикт: confirmed | refuted + почему + severity.
                     ⚡ запускается per-finding, как только finder области закончил
                        (пайплайн, без барьера) — область B ещё ищет, а находки A уже проверяются.
        │
        ▼
Синтез               дедуп (одна и та же причина из разных областей → один баг),
                     сортировка по severity × радиусу поражения, контракт выхода (§4).
```

**Почему пайплайн, а не «сначала все finder'ы, потом все скептики»:** проверка
находки не зависит от других областей. Пайплайн начинает проверять находки области A,
пока область B ещё ищет — wall-clock (общее время) короче, ничего не простаивает.
Барьер (ждать ВСЕ finder'ы) нужен только если перед проверкой надо дедупнуть находки
между областями — обычно не нужно, дедуп делаем в синтезе.

## 3. Как это вызвать (для владельца)

**Триггер-фраза** (скажи Claude примерно так):

> «Проведи состязательный аудит логики модуля `<путь или имя модуля>` по методологии
> `docs/methodology/code-audit`. Разбей на под-области, найди баги, каждую находку
> проверь независимым скептиком, подтверждённые сведи в ТЗ с контрактом
> симптом+корень+фикс+`file:line`.»

**Что полезно (но не обязательно) дать:**
- путь модуля (`backend/src/modules/<x>`), если знаешь;
- сколько под-областей грубо (по умолчанию 6–8);
- «глубоко» / «бегло» — задаёт размер роя (§8).

**Что Claude сделает:** при включённом многоагентном режиме (ultracode / «use a
workflow») — запустит workflow-скрипт из §9; иначе предложит запустить рой или
сделает урезанную последовательную версию и честно об этом скажет.

## 4. Контракт выхода (что ОБЯЗАН содержать каждый баг)

Каждый подтверждённый баг = строка с полями (это же — входной контракт для «другой
сети», которая будет писать фиксы):

| Поле | Что | Зачем |
|---|---|---|
| `id` | короткий код (Б1, Б2…) | ссылаться |
| `severity` | 🔴 high / 🟠 med / 🟡 low (см. §5) | порядок работы |
| `симптом` | что наблюдаемо ломается | понять последствие |
| `корень + трасса` | ПОЧЕМУ, по шагам кода | не лечить симптом |
| `file:line` | точное место (сверено по коду) | сразу открыть |
| `фикс` | конкретное изменение | готовое задание |

Плюс два общих блока:
- **Сводка** — сколько high/med/low, какие баги чинить вместе (связки), рекомендованный порядок.
- **Опровергнуто** — находки, которые скептик закрыл, + почему (НЕ перепроверять).

> Складывается это в `plans/tz/YYYY-MM-DD-<module>-audit.md`, раздел вида «§8 —
> аудит логики». Шаблон уже отработан на M5 — см. пример.

## 5. Калибровка severity (после опровержения)

- 🔴 **High** — ломает основную фичу модуля, теряет/портит данные, утечка доступа,
  бесконечный/раннавей-расход (LLM-вызовы по кругу), гонка с двумя «истинами».
- 🟠 **Med** — деградация в краевых случаях, тихий дрейф счётчиков/дат, лишний расход
  без потери данных, латентно при росте.
- 🟡 **Low** — недетерминизм выборки, отсутствие `orderBy`/курсора при малых объёмах,
  косметика, «на вырост».

Правило: **severity ставит скептик, а не finder** — finder склонен преувеличивать.

## 6. Правила-ловушки (специфика Z — обязательно в промпт скептика)

Эти грабли уже стоили времени; зашивай их в задачу скептику, иначе будут ложные баги
ИЛИ пропущенные:

1. **Один симптом ≠ один корень.** Серию похожих находок проверяй ПО ОТДЕЛЬНОСТИ —
   за одинаковым симптомом бывают разные причины (и наоборот). (memory
   `feedback_fix_the_whole_class_not_the_case`).
2. **Баг-паттерн чини классом.** Если корень — повторяемый конструкт (формат `jobId`,
   отсутствующий guard, `take` без `orderBy`), скептик отмечает «искать ВСЕ вхождения»,
   а фикс закрывает класс + машинный гард, не один кейс.
3. **Поведение фреймворка — доказывай, не угадывай.** Семантику NestJS/Prisma/BullMQ
   (scope пайпов, NULL в `@@unique`, порядок guard'ов) скептик подтверждает трассой/
   мини-проверкой, а не «по памяти». (memory `feedback_verify_framework_behavior_empirically`).
4. **Один контейнер в проде.** Backend Z в проде — ОДИН процесс/контейнер (`worker:dev`
   как отдельного процесса в проде нет). «Нет Redis-лока между процессами» — НЕ баг,
   если конкурентных процессов нет (но cron+HTTP+handler внутри одного процесса
   конкурировать могут — это уже баг). Скептик обязан различать.
5. **Типы/каст уже защищают.** Часть «находок» закрывается типами БД (pgvector
   отвергает NaN/неверную длину), partial-unique, идемпотентностью — скептик проверяет
   это ПРЕЖДЕ чем подтвердить.
6. **Агенты могут соврать про факт.** finder/скептик иногда ссылается на строку, которой
   нет. Перед фиксацией в ТЗ — **сверять `file:line` по реальному коду** (memory
   `feedback_agents_can_lie_about_edits`). В синтезе это обязательный шаг.

## 7. Куда складывать результат

1. **ТЗ** `plans/tz/YYYY-MM-DD-<module>-audit.md` — раздел «Аудит логики» с контрактом
   §4 (подтверждённые) + блок «опровергнуто». Это и есть задание на фиксы.
2. **Реестр не-сделано** `second-brain/04_не-сделано/README.md` — одна строка-указатель
   на ТЗ (что не сделано · почему · ссылка · кто разблокирует). Это часть триггера
   завершения работы.
3. **НЕ** в `second-brain/` как «факт» — пока баги не починены, это план (идея), его дом
   `plans/`. Карту модуля в `second-brain/` правим только когда фиксы выкачены.

## 8. Масштабирование роя

| Запрос | Под-областей | Скептиков на находку | Примерно агентов |
|---|---|---|---|
| «бегло проверь» | 4–5 | 1 | ~15 |
| «нормально» (дефолт) | 6–8 | 1 | ~30–40 |
| «тщательно / критичный модуль» | 8–10 | 2–3 (перспективы: корректность / гонки / данные) | ~60–100 |

Параллелизм агентов всё равно ограничен (≈10–16 одновременно), но рой любого размера
доходит до конца — лишние просто ждут слота. Для критичных модулей включай 2–3 скептиков
на находку с РАЗНЫМИ ракурсами (не три одинаковых), это ловит больше классов отказа.

## 9. Готовый workflow-скрипт (шаблон)

Запускается через Workflow-инструмент (нужен многоагентный режим). Параметризуется
через `args = { module, areas, skeptics }`. Сохрани как файл и запусти, либо отдай
Claude фразой из §3.

```js
export const meta = {
  name: 'module-bug-audit',
  description: 'Состязательный аудит логики модуля: карта → finders → per-finding скептик → синтез',
  phases: [
    { title: 'Карта',    detail: 'разбить модуль на под-области' },
    { title: 'Поиск',    detail: 'finder на каждую под-область' },
    { title: 'Проверка', detail: 'независимый скептик на каждую находку' },
    { title: 'Синтез',   detail: 'дедуп + severity + контракт' },
  ],
}

const MODULE   = args?.module   ?? 'backend/src/modules/<укажи модуль>'
const N_AREAS  = args?.areas    ?? 8
const SKEPTICS = args?.skeptics ?? 1   // 2–3 для критичных модулей (разные ракурсы)

const AREAS_SCHEMA = {
  type: 'object', required: ['areas'],
  properties: { areas: { type: 'array', items: {
    type: 'object', required: ['key', 'what', 'files'],
    properties: { key: { type: 'string' }, what: { type: 'string' },
      files: { type: 'array', items: { type: 'string' } } } } } },
}
const FINDINGS_SCHEMA = {
  type: 'object', required: ['findings'],
  properties: { findings: { type: 'array', items: {
    type: 'object', required: ['title', 'symptom', 'rootTrace', 'fix', 'fileLine'],
    properties: { title: { type: 'string' }, symptom: { type: 'string' },
      rootTrace: { type: 'string' }, fix: { type: 'string' }, fileLine: { type: 'string' } } } } },
}
const VERDICT_SCHEMA = {
  type: 'object', required: ['status', 'severity', 'reason'],
  properties: {
    status:   { type: 'string', enum: ['confirmed', 'refuted'] },
    severity: { type: 'string', enum: ['high', 'med', 'low', 'none'] },
    reason:   { type: 'string' },
    fileLineVerified: { type: 'boolean' } },
}

// Проход 0 — карта под-областей
phase('Карта')
const map = await agent(
  `Прочитай РЕАЛЬНЫЙ код модуля ${MODULE} (сервисы, воркеры, cron, читатели).
   Разбей его на ${N_AREAS} независимых под-областей для аудита (по сервисам/стадиям
   пайплайна/кронам). Для каждой: key (короткий слаг), what (что делает), files (ключевые).
   Только то, что есть в коде — не выдумывай.`,
  { schema: AREAS_SCHEMA },
)
const areas = (map?.areas ?? []).slice(0, N_AREAS)
log(`Под-областей: ${areas.length}`)

// Проход 1+2 — пайплайн: finder → скептик(и) по каждой находке
const reviewed = await pipeline(
  areas,
  (area) => agent(
    `Состязательный аудит под-области «${area.key}» модуля ${MODULE} (${area.what}).
     Файлы: ${area.files.join(', ')}. Читай реальный код. Найди (а) баги ЛОГИКИ
     (гонки, утечки/застой статусов, дрейф счётчиков, раннавей-расход, потеря данных,
     обход гейтов, NULL в @@unique, take без orderBy) И (б) НЕСООТВЕТСТВИЯ (код
     противоречит своему комментарию/контракту/схеме; две ветки или два источника
     правды расходятся; реализация не совпадает с заявленным поведением).
     Для каждого: title, symptom, rootTrace (по шагам кода), fix, fileLine (точно).
     Severity НЕ ставь — это сделает проверяющий.`,
    { label: `find:${area.key}`, phase: 'Поиск', schema: FINDINGS_SCHEMA },
  ),
  (found, area) => parallel(
    (found?.findings ?? []).flatMap((f, i) =>
      Array.from({ length: SKEPTICS }, (_, k) => () =>
        agent(
          `Ты СКЕПТИК. Попытайся ОПРОВЕРГНУТЬ находку по реальному коду ${MODULE}.
           По умолчанию это НЕ баг, пока не доказано трассой. Ракурс №${k + 1}
           (${['корректность', 'гонки/конкуренция', 'целостность данных'][k] ?? 'корректность'}).
           Находка: ${f.title} — ${f.symptom}. Трасса автора: ${f.rootTrace}. Место: ${f.fileLine}.
           Учитывай ловушки Z: один контейнер в проде (но cron+HTTP+handler в одном процессе
           конкурируют), типы/каст БД уже защищают (pgvector/partial-unique/идемпотентность),
           один симптом ≠ один корень. Сверь, что ${f.fileLine} реально существует.
           Верни status (confirmed|refuted), severity (high|med|low|none) и reason.`,
          { label: `verify:${area.key}#${i}.${k}`, phase: 'Проверка', schema: VERDICT_SCHEMA },
        ).then((v) => ({ ...f, area: area.key, verdict: v })),
      ),
    ),
  ),
)

// Синтез — дедуп + разделение + калибровка
phase('Синтез')
const all = reviewed.flat().filter(Boolean)
// при нескольких скептиках: баг подтверждён, если большинство confirmed
const byFinding = {}
for (const r of all) {
  const key = r.fileLine + '|' + r.title
  ;(byFinding[key] ??= { finding: r, votes: [] }).votes.push(r.verdict)
}
const confirmed = [], refuted = []
for (const { finding, votes } of Object.values(byFinding)) {
  const yes = votes.filter((v) => v?.status === 'confirmed').length
  const sev = votes.map((v) => v?.severity).find((s) => s && s !== 'none') ?? 'low'
  if (yes * 2 >= votes.length) confirmed.push({ ...finding, severity: sev })
  else refuted.push({ ...finding, reason: votes.map((v) => v?.reason).join(' | ') })
}
log(`Подтверждено: ${confirmed.length} · опровергнуто: ${refuted.length}`)

return { module: MODULE, confirmed, refuted }
```

> После прогона: **сверь `file:line` по коду** (агенты иногда врут про строки, §6.6),
> разложи confirmed по severity × радиусу, опиши связки «чинить вместе», сложи в ТЗ (§7).

## 10. Чек-лист качества прогона (перед сдачей)

- [ ] каждая под-область покрыта своим finder'ом, finder'ы были слепы друг к другу;
- [ ] КАЖДУЮ находку проверял ОТДЕЛЬНЫЙ скептик с задачей опровергнуть;
- [ ] severity проставлен скептиком, не finder'ом;
- [ ] опровергнутые сохранены с причиной (чтобы не перепроверять);
- [ ] `file:line` всех подтверждённых сверены по реальному коду;
- [ ] дедуп: одинаковый корень из разных областей сведён в один баг + помечены связки;
- [ ] результат в `plans/tz/…-audit.md` (контракт §4) + строка в реестре не-сделано;
- [ ] карту модуля в `second-brain/` НЕ трогали (фиксы ещё не выкачены).

## Приложение — эталонный прогон: модуль M5 «Клоны» (2026-06-16)

- **Цель:** «проверь логику кода модуля, чтобы не было багов; что нашлось — в ТЗ».
- **Рой:** 8 под-областей (конвейер черт / нормализация концептов / принципы роли /
  сборка персоны / версионирование / валидация / чтение клона / CDM-probe), по
  finder'у на область + скептик на каждую находку, ~35 агентов, 2 прохода.
- **Итог:** 27 находок → **21 подтверждён** (10 high / 6 med / 5 low), **6 опровергнуто**.
- **Опровергнутые (примеры — почему НЕ баги):** «нет Redis-лока в weekly-cron» (один
  контейнер в проде); «parsevector-nan» (pgvector отвергает каст); «скрытый no-op
