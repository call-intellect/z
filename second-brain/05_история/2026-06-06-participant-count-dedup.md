# Дублирование счётчика участников: «позвал двоих → показало 5»

## Что было поставлено
Владелец по ходу сессии: «дублируется количество участников — позвал двоих, показало 5; найди самое лучшее решение, докажи, что лучшее, реализуй». Развилки делегированы мне.

## Корень (доказан чтением, не догадка)
Уникальность `Participant` только по `(meetingId, livekitIdentity)`. Приглашение создаёт строку `invitee:<token>` (`invitationStatus='invited'`), вход без личной ссылки `?inv=` создаёт **вторую** строку `guest:<nanoid>` того же человека — разные identity, дедуп не схлопывает. Счётчик = сырой `participants.length`. Арифметика: хост(1)+2 invite+2 join = **5**. Дедуп по `userId` (был) не ловил приглашение по сотруднику (`userId=null, personId=<id>`).

## Как решал (доказательство «лучшего» + 3 фазы)
Challenge-loop по развилкам, потом оркестрация фазами с независимой приёмкой:
- **Р1 (что считать):** present-only `invitationStatus != 'invited'`. **Владелец подтвердил это явно** в процессе («приглашённые, но не пришедшие — не участники»). Доказательство «лучшего»: робастно даже к остаточным дублям — не-пришедшую `invited`-строку исключает, реальную join-строку считает один раз; ноль изменений FSM.
- **Р2 (DB-инвариант):** отложил. App-дедуп + фильтр уже решают видимое; partial-unique миграция рискованна на фоне незавершённого прод-baseline миграций.
- **Фаза A** (`6b645c71`): общий предикат `participant-presence.ts`; `getResult`-DTO + `_count` в ROI/pulse → present-only (инфляция не течёт и в метрики/AI).
- **Фаза B** (`1f370d98`): дедуп на входе — `join` матчит pre-seed по `userId` ИЛИ `personId` (резолв `Person.userId`); webhook принимает `invitee:` (точность `joinedAt`).
- **Фаза C** (`f991e18c`): проброс `inviteToken` `MeetingPageShell → Lobby → GuestNameForm → join` — ручная гостевая форма теряла токен (auto-join слал).

## Что вышло
3 коммита, каждый: typecheck/lint/build + тесты зелёные (предикат 5→3; дедуп по personId+негатив; webhook invitee:; RTL-тест формы). Видимый баг закрыт + корень закрыт (новые дубли не плодятся). ТЗ `plans/tz/2026-06-06-participant-count-dedup.md` → `implemented` (Ф1/2/3/5), Ф4 отложена в реестр не-сделано.

## Чему научился
- **Симптом и корень — разные слои, чини оба, но фильтр-счётчик важнее «делать всё».** Present-предикат робастен к дублям → фиксит видимое НЕЗАВИСИМО от того, остались ли дубли в БД. Это дало право отложить рискованную миграцию (Ф4) без потери ценности для владельца.
- **Дедуп по личности ≠ дедуп по `userId`.** Приглашение по сотруднику кладёт `personId`, а `userId=null` — матч только по userId структурно промахивался. Связь `Person.userId` — мост. См. [[../02_architecture/code-pitfalls]].
- **Токен из URL легко теряется на «втором» пути.** `?inv=` доходил до auto-join, но ручная гостевая форма (отдельная ветка `role='none'`) его не получала — классический «один путь прокинул, другой забыл».
- Инфляция сырого `_count.participants` тихо течёт в ROI-скоринг и AI-промпты — «fix the whole class» включает производные счётчики, не только видимый UI.
