# Методология написания лучших промптов (Кора)

> Источник правды о том, **как мы пишем системные/пользовательские промпты для LLM-агентов Коры**, и растущая коллекция эталонов. Из этого документа в будущем вырастет скилл `prompt-author` (см. раздел «Будущий скилл»).
>
> **Когда применять:** при создании любого нового LLM-агента/`taskType`, при переписывании промпта, который «выдаёт глупости», при ревью промпта перед выкатом. Не для тривиальной правки одной строки уже хорошего промпта.
>
> **Связанные правила проекта:** [[feedback_llm_prompts_cache_friendly]] (кэш), [[feedback_language_plain_russian]] / [[feedback_admin_ui_russian_only]] (чистый русский), skill `z-ai-agent-rules` (prompt registry, code-fallback), [[feedback_no_golden_ship_and_observe_prod]] (выкат без блокирующего golden).

---

## Главный принцип: агент должен ПОНИМАТЬ, что он получил и зачем

Большинство «глупых» промптов в Z проваливались по одной причине: **модели давали данные, но не давали смысла.** Она не знала, кто она, зачем спрашивает/отвечает, кому пишет и что станет с её выводом — поэтому генерила générique-текст или, хуже, переносила в ответ служебный мусор (коды, идентификаторы, английские названия сущностей).

Эталон ниже (probe-formulate) родился из живого провала: промпт из 4 строк получал на вход машинные коды (`decision.overdue`, `3-3-decisions`), которые сам же запрещал использовать. Лечение — не «подкрутить тон», а дать модели полную ментальную модель задачи.

## Анатомия эталонного промпта (7 блоков)

Хороший SYSTEM-промпт Коры собирается из этих блоков. Не все обязательны для каждого агента, но блоки 1–4 и 6 — почти всегда.

| # | Блок | Что в нём | Зачем |
|---|---|---|---|
| 1 | **Роль / персона** | «Ты — голос Коры, …», чей голос, в одном абзаце | Модель выбирает регистр и тон; без этого — generic-ассистент |
| 2 | **Якоря смысла** | Зачем эта задача · кому адресован вывод · что станет с результатом | Модель понимает СМЫСЛ, а не только формат. Самый недооценённый блок |
| 3 | **Критерии «что делает результат хорошим»** | Нумерованный чек-лист (5–8 пунктов): конкретность, длина, тон, запреты | Превращает «хороший» из прилагательного в проверяемые правила |
| 4 | **Few-shot «плохо → хорошо»** | 3–5 примеров: антипример + эталон на реальных входах | Дешёвые модели без примеров «плавают» между провайдерами (подтверждено: инструкции Microsoft для declarative-агентов; research §4.2 probe-анализа) |
| 5 | **Self-check** | «Перед ответом проверь по пунктам N; если осталось X — перепиши» | Дешёвый внутренний фильтр мусора без второго LLM-вызова |
| 6 | **Выходной контракт** | «Верни строго JSON по схеме на русском» + JSON Schema (`strict`) | Машинно-парсится, ретраи на уровне tool-call |
| 7 | **Запреты Z** | «Ни одного кода/идентификатора/английского названия — даже если они во входе» | Главная утечка в UI конечного пользователя |

## Жёсткие требования Z (нарушение = промпт не готов к выкату)

1. **Cache-friendly.** SYSTEM **стабилен** (включая few-shot — они тоже кэшируются), все переменные данные — **в конце USER**. DeepSeek/OpenAI-proxy/MiniMax кэшируют 95–99% префикса; правка SYSTEM ломает кэш разово — это приемлемо, но любая переменная в SYSTEM ломает кэш на КАЖДОМ вызове. [[feedback_llm_prompts_cache_friendly]]
2. **Чистый русский на выходе.** Ни одного английского слова/кода/идентификатора/названия сущности (`CompanyProfile`, `Document`, `Role`…). Если они есть во входе — промпт обязан явно запретить их перенос. [[feedback_language_plain_russian]]
3. **Вход — человеческий, не машинный.** Не подавай модели `reason='decision.overdue'` / `emittedByService='3-3-decisions'`. Заведи словарь `код → человеческий ярлык` и подавай ярлык. Иначе промпт противоречит сам себе.
4. **Модель НЕ решает «уместность» дешёвой моделью.** Тонкое различие (research CLAMBER): few-shot/CoT помогают **формулировке**, но на **гейте «стоит ли вообще делать/спрашивать»** дешёвая модель с few-shot переуверена и ошибается. Гейтинг держи на правилах в коде; LLM оставляй формулировку. Если нужен LLM-гейт — отдельный judge на собранных данных, не в формулирующем промпте.
5. **Крутилки — не в промпт.** Пороги/лимиты/тексты, которые владелец может менять, — в `AdminSetting` (prompt registry с code-fallback), не хардкод. `z-ai-agent-rules`.

## Чек-лист перед выкатом промпта

- [ ] Есть роль/персона (блок 1) и якоря смысла «зачем/кому/что-дальше» (блок 2)?
- [ ] Критерии «хорошего результата» — нумерованный список, без прилагательных «качественно/удобно» (блок 3)?
- [ ] Есть ≥3 few-shot «плохо → хорошо» на РЕАЛЬНЫХ входах (блок 4)? Хотя бы один — из живого провала.
- [ ] Self-check перед ответом (блок 5)?
- [ ] Строгий выходной контракт + JSON Schema (блок 6)?
- [ ] На вход подаётся человеческий ярлык, а не машинный код?
- [ ] SYSTEM стабилен, переменные — в конце USER (кэш)?
- [ ] В выходе физически невозможны англицизмы/коды (явный запрет + self-check)?
- [ ] Версия схемы поднята, если изменился контракт USER (`*_v2 → *_v3`)?
- [ ] Выкат по «ship-on», наблюдаем прод-метрики (отвечаемость / доля «непонятно»), без блокирующего golden?

## Антипаттерны (как НЕ надо)

- **Тонкая персона.** «Ты — Кора. Сделай X.» Модель не понимает контекст → generic-выход.
- **Машинные коды на входе при запрете в SYSTEM.** Промпт сам себе противоречит (наш реальный баг).
- **Ноль примеров.** «Пиши хорошо» без few-shot → разнобой между провайдерами.
- **Few-shot/CoT на дешёвом ГЕЙТЕ.** Не путать с формулировкой — на гейте «делать/не делать» это вредит (CLAMBER).
- **Переменные в SYSTEM.** Ломают кэш на каждом вызове — деньги на ветер.
- **Англицизмы/идентификаторы в выходе.** Утечка в UI конечного пользователя; самый частый «глупо выглядит».
- **«Качественно/удобно/корректно» как критерий.** Непроверяемо — заменяй предикатом (≤200 символов, один вопрос, ноль кодов).

## Будущий скилл `prompt-author`

Эта методичка — заготовка скилла, который по запросу «напиши/улучши промпт для агента X»:
1. Изучает агента в коде (где живёт, `taskType`, какой вход реально приходит, текущий промпт).
2. Собирает SYSTEM по анатомии (блоки 1–7), извлекая few-shot из реальных входов/провалов.
3. Прогоняет чек-лист + жёсткие требования Z (кэш, русский, человеческий вход, гейт-vs-формулировка).
4. Выдаёт промпт + словарь `код→ярлык` + версию схемы, готовые к вставке в код/registry.
5. Не пишет код реализации — отдаёт промпт-контракт (как `tz-author` отдаёт ТЗ).

Когда эталонов накопится ≥3–4 и методология стабилизируется — оформляем через skill `skill-creator`.
