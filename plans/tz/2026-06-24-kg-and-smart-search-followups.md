# Хвосты: граф знаний v2 + умный поиск — что осталось и почему

## Зачем этот документ
Оба ТЗ функционально закрыты по коду (Ф1–Ф9 графа, Ф4.1–4.7 поиска). Но «фаза закрыта» ≠ «проверено на проде» и ≠ «откалибровано на реальном трафике». Ниже — честный список остатка, чтобы ни один долг не потерялся между сессиями.

## Принятые границы (почему не в первом заходе)
- **Ф10 обоих ТЗ — живой re-test на проде** требует прод-доступа (diag.ts / qa-tester к meet.crossmark.ru / korateam.ru), который владелец подтверждает в каждой сессии явно [[feedback_prod_diagnostic_access_requires_confirmation]]. Без «да» владельца — нельзя. Поэтому вынесено.
- **Калибровка LLM-стадий на реальном трафике** (over-abstention гейта честности, польза iterative-ветки, пороги реранка/RRF) — по методологии проекта правки промптов/агентов не блокируются golden-харнессом, а наблюдаются на проде (diag + метрики) [[feedback_no_golden_ship_and_observe_prod]]. Поэтому — после выката, на данных.

## Фазы

### Ф1 — Живая прод-приёмка графа знаний (Ф10 граф-ТЗ) `[ ]`
**Цель:** доказать на проде, что граф отвечает.
**Что входит (5 пунктов, qa-tester/diag.ts read-only, после `docker compose up -d --build` + `apply-prod-deploy.ts`):**
1. «суть встречи X» → связная суть + кликабельный источник (не «не нашёл»).
2. Человек, упомянутый в встрече и чате, — один профиль (alias-cache: «Настя»↔аккаунт).
3. Поиск возвращает блок, достижимый ТОЛЬКО через ребро (обход рёбер реально работает).
4. У новых блоков нет «висящих» без источника (evidence.rawEventId непустой; diag).
5. bi-temporal: устаревший (superseded) факт не в активной выдаче.
**Acceptance:** 5 пунктов зелёные глазами + сетевые статусы; скриншоты в `plans/analysis/2026-06-23-knowledge-graph-ingestion-audit/verification/`.
**Разблокирует:** владелец (прод-доступ + наблюдение, т.к. bi-temporal ON меняет выдачу).

### Ф2 — Живая прод-приёмка умного поиска (Ф10 поиск-ТЗ) `[ ]`
**Цель:** доказать на проде, что Мастер перестал лишне переспрашивать и ложно «Готово».
**Что входит:** кейс «Александр» (агрегат → список без переспроса); кейс «нет данных» (честный отказ, а не выдумка); проверить, что гейт честности (`rag.groundedness_mode`) не уходит в over-abstention (метрика `rag_abstain_total`), при необходимости — `shadow` для наблюдения.
**Acceptance:** 2 кейса зелёные; over-abstention под порогом (наблюдение по метрике).
**Разблокирует:** владелец.

### Ф3 — Калибровка iterative-ветки на проде (A/B + cold-start) `[ ]`
**Цель:** убедиться, что многошаговая ветка (роутер→ReWOO→достаточность) реально окупается, а не тратит токены впустую.
**Что входит:** под `rag.iterative_enabled` держать ветку за наблюдением; собрать долю `iterative`-вопросов и сравнить качество/латентность одношагового vs многошагового на медиане (риск R-iterative-cost-no-gain из поиск-ТЗ); откалибровать `rag.cold_start_min_blocks` по реальным малым тенантам; пороги `rag.rerank_min_pool`, `rag.rrf_k` — по шуму нашего графа (не из papers).
**Что НЕ входит:** golden-харнесс (по методологии — наблюдаем прод).
**Acceptance:** решение по ветке принято на данных (оставить ON / сузить гейт / выключить), пороги зафиксированы в AdminSetting.

### Ф4 — Интеграционное покрытие staged-loop end-to-end `[ ]`
**Цель:** закрыть пробел: стадии умного поиска покрыты юнитами ИЗОЛИРОВАННО (route/plan/sufficiency/groundedness/rerank — каждый отдельно), но полный путь `ask()` (router→plan→retrieval→sufficiency→synth→groundedness) и проток ответа гейта честности в `appendMessage/answerCache/return` проверены только статически (typecheck), без e2e-теста.
**Что входит:** интеграционный spec на `chat-v2.service.ask()` с замоканными LLM (детерминир. вердикты стадий), проверяющий: iterative-вопрос → план ≥2 шага → накопление → sufficiency-стоп → синтез → гейт честности применён к финальному тексту; single-вопрос → одношаговый путь; fail-open ветки.
**Acceptance:** интеграционный spec зелёный; покрыт проток answerText гейта честности.

### Ф5 — Cross-encoder реранкер (vNext из Ф4.6) `[ ]`
**Цель:** заменить LLM-as-reranker (v1, ~2с/вызов) на cross-encoder-микросервис (<100мс) при росте объёма.
**Что входит:** отдельный HTTP-микросервис в `infra/*` (исключение §7 — не в backend-пути) ИЛИ локальная модель; `rag-rerank` переключается на него при доказанном объёме.
**Что НЕ входит сейчас:** v1 LLM-реранк достаточен на текущем трафике (доказано прототипом). Это — при росте.
**Acceptance:** реранк <100мс на пуле >порога; качество не хуже LLM-реранка.
**Разблокирует:** владелец (новый сервис в infra — ⚠️ ask-first из поиск-ТЗ).

### Ф6 — Backfill исторических блоков без источника / без bi-temporal `[ ]`
**Цель:** закрыть пробел провенанс-инварианта для СТАРЫХ данных.
**Что входит:** граф-ТЗ Ф2 ввёл гард «блок без evidence не пишется» только для НОВЫХ блоков (`[ASSUMPTION: исторические не бэкфиллим]`). Аналогично bi-temporal `validFrom` пишется только при ingest с флагом ON. Backfill-скрипт: проставить `validFrom` старым блокам (= `createdAt`/самый ранний evidence.sourceTimestamp); пометить/отчитаться по историческим блокам без evidence.
**Что НЕ входит:** удаление старых блоков (только отчёт + best-effort `validFrom`).
**Acceptance:** backfill идемпотентен (повторный прогон = no-op); отчёт по числу затронутых; зарегистрирован в `apply-prod-deploy.ts STEPS` `phase:'backfill'`.

### Ф7 — Битрикс-адаптер `RawEvent` (vNext из граф-ТЗ scope) `[ ]`
**Цель:** реальный коннектор Битрикс → `RawEvent(sourceType=...)` поверх готовой схемы.
**Что входит:** граф-ТЗ заложил готовность схемы `RawEvent`+`sourceTitle` принять Битрикс-источник, но сам адаптер (как `meeting.adapter`/`report.adapter`) — отдельное ТЗ. Реализовать адаптер: маппинг сущностей Битрикс (сделки/контакты/задачи) → эпизоды с `sourceTitle`.
**Что НЕ входит:** менять контракт `RawEvent` (он готов).
**Acceptance:** событие Битрикс → `RawEvent` → block-ingest → граф; человек из Битрикс склеивается alias-cache с человеком из встреч.
**Разблокирует:** владелец (приоритет источника).
