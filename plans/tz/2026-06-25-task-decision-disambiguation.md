# ТЗ: разведение «задача vs решение» в извлечении — симметричные few-shot в обоих агентах

> Анализ-основание: [plans/analysis/2026-06-25-tasks-vs-decisions-noise-audit.md](../analysis/2026-06-25-tasks-vs-decisions-noise-audit.md).
> Доказательство: `backend/scripts/diag-decision-classifier-test.ts` — старый промпт пропускает 4/5 поручений как решения, усиленный отсекает 5/5 без регресса (deepseek-v4-flash, 2026-06-25).

## Зачем

В реестр решений (`/decisions`) утекают **поручения и постановки задач** (33% реестра: 21 из 64 на живом кабинете). Корень — промпты извлечения **не разводят «задача» и «решение»**: ни в `decision-extract`, ни в `task-extract`, ни в классификаторе `block-ingest` нет правила «поручение/постановка задачи ≠ решение; выбор между вариантами ≠ задача» и нет контрастных примеров обоих классов.

**Требование владельца:** контрастные примеры «вот задача / вот решение» должны быть в **обоих** агентах — и в том, что вытаскивает задачи, и в том, что вытаскивает решения — чтобы каждый видел границу с двух сторон и не путал классы. Один и тот же набор пар, две проекции.

## Принцип решения

**Единый источник пар → две проекции → три точки интеграции.**

1. Один файл-реестр контрастных пар (задача ↔ решение). Правка примеров — в одном месте, агенты не разъезжаются.
2. Две проекции одного реестра:
   - для извлекателя **решений**: «РЕШЕНИЕ → берём (isDecision=true) · ПОРУЧЕНИЕ/ЗАДАЧА → НЕ берём (isDecision=false)»;
   - для извлекателя **задач**: «ЗАДАЧА → берём (isTask=true) · РЕШЕНИЕ → НЕ берём (isTask=false)».
3. Тот же реестр (сокращённо) — в классификатор `block-ingest`, чтобы реплика «задача X» получала `signalType=action_item`, а не `decision` (рубеж 1, до экстракторов).

Формула-инвариант во всех трёх: **Решение = ЧТО выбрали; задача = КТО что делает. Одно решение может породить задачи.**

## Фаза 1 — Единый реестр контрастных примеров `[ ]`

### 1.1 Новый файл `backend/src/modules/knowledge-core/prompts/task-decision-examples.ts`

Экспортирует:
- `TASK_VS_DECISION_PAIRS` — массив пар (см. Приложение А), структура:
  ```ts
  type TaskDecisionPair = {
    topic: string;
    decision: { text: string; why: string };
    task: { text: string; why: string };
  };
  ```
- `TASK_VS_DECISION_RULE: string` — общее правило-дискриминатор (текст ниже).
- `renderExamplesForDecisionExtractor(): string` — рендер пар с вердиктами для агента решений.
- `renderExamplesForTaskExtractor(): string` — рендер пар с вердиктами для агента задач.
- `renderRuleForBlockIngest(): string` — компактная версия (правило + 2 пары) для классификатора.

Текст `TASK_VS_DECISION_RULE`:
> Не путай задачу с решением. Решение фиксирует ВЫБОР между вариантами («берём Б», «уходим к Y», «решили НЕ делать X») и несёт обоснование. Задача — конкретное действие к исполнению, назначенное кому-то («подготовь смету», «настрой мониторинг»), в том числе со словом «задача», «поручаю», «ставлю задачу», «назначаю ответственным», «возьми на себя». Согласие исполнителя взять задачу («подходит», «беру», «да») не делает её решением. Формула: решение = ЧТО выбрали; задача = КТО что делает (одно решение может породить задачи).

Файл — чистый TS (строки + функции), без NestJS-зависимостей (как `signal-type-label.ts`), чтобы импортировался и в проде, и в diag-тестах.

### Acceptance Ф-1
- `bun run typecheck` зелёный; файл не тянет DI/Prisma.
- `renderExamplesForDecisionExtractor()` и `renderExamplesForTaskExtractor()` возвращают непустые строки, покрывающие все пары; вердикты противоположны по классам.

## Приложение А — 12 РАЗНООБРАЗНЫХ контрастных пар (в реестр `task-decision-examples.ts`)

> **Принцип:** примеры few-shot — намеренно из РАЗНЫХ индустрий и функций (закупки, HR, финансы, IT, продажи, юристы, производство, маркетинг, продукт, логистика, поддержка, ценообразование). Продукт используют компании любого профиля → агент должен обобщать границу «задача/решение», а НЕ привязываться к одной тематике. Реплики конкретного кабинета (Telegram-боты, Кора) в few-shot НЕ используются — они только в тест-фикстурах (Фаза 7). Каждая пара: один домен, две формулировки.

| # | Домен | РЕШЕНИЕ (isDecision=true / isTask=false) | ЗАДАЧА (isTask=true / isDecision=false) |
|---|---|---|---|
| 1 | Закупки | «Переходим на поставщика упаковки «ТараПро» — на 15% дешевле при том же качестве» | «Запросить у «ТараПро» договор и прайс на квартал» |
| 2 | HR / найм | «Нанимаем одного senior-разработчика вместо двух джунов — критична скорость» | «Опубликовать вакансию senior-разработчика на hh.ru» |
| 3 | Финансы | «Урезаем бюджет маркетинга в Q3 на 20% в пользу R&D» | «Подготовить пересмотренный бюджет маркетинга к понедельнику» |
| 4 | IT / архитектура | «Переносим БД с MySQL на PostgreSQL ради JSONB и партиционирования» | «Написать скрипт миграции схемы на PostgreSQL» |
| 5 | Продажи | «Фокусируемся на среднем бизнесе, малый сегмент замораживаем» | «Обновить скрипт холодного звонка под средний бизнес» |
| 6 | Юристы | «В типовой договор добавляем пункт о NDA по умолчанию» | «Подготовить шаблон NDA к пятнице» |
| 7 | Производство | «Вторую смену не запускаем, пока первая не выйдет на 80% загрузки» | «Составить график первой смены на следующую неделю» |
| 8 | Маркетинг | «Основной канал привлечения — контент-маркетинг, контекстную рекламу сворачиваем» | «Подготовить контент-план блога на месяц» |
| 9 | Продукт | «Мобильное приложение делаем после веба, не параллельно» | «Собрать требования к мобильному приложению» |
| 10 | Логистика | «Доставку отдаём на аутсорс СДЭК вместо своего курьера» | «Заключить договор со СДЭК и настроить интеграцию» |
| 11 | Поддержка | «Вводим SLA 4 часа на ответ для приоритетных клиентов» | «Настроить в хелпдеске правило приоритизации тикетов» |
| 12 | Ценообразование | «Поднимаем цены на 10% с нового года — рынок позволяет» | «Обновить прайс на сайте и уведомить клиентов» |

Граничные кейсы (включить как контр-примеры, чтобы агент не перегибал):
- «Решили добавить отчёт по продажам **и поручили** аналитику его сделать» → decision = «вводим отчёт по продажам»; task = «сделать отчёт по продажам». Не плодить три записи на одну мысль.
- «А давайте попробуем новую CRM?» (вопрос/идея, не выбор) → ни decision, ни task (это идея/обсуждение).

Проекция в промптах (один реестр — три вида):
- **decision-extract** видит: «РЕШЕНИЕ (левая колонка) → isDecision=true; ЗАДАЧА (правая) → isDecision=false».
- **task-extract** видит: «ЗАДАЧА (правая) → isTask=true; РЕШЕНИЕ (левая) → isTask=false».
- **block-ingest** видит выборку из 2–3 пар разных доменов: решение → `decision`, задача → `action_item`.

> В промпт подаётся репрезентативная выборка (6–8 пар разных доменов), полный реестр (12+) расширяется свободно и целиком прогоняется регресс-тестом. Few-shot ≠ фикстуры: разнообразные синтетические примеры учат границе, реальные реплики кабинета (Фаза 7) доказывают эффект на боевых данных.
