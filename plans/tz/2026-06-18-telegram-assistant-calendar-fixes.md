# ТЗ: фикс помощника Коры в каналах — дубли ответов + даты/таймзоны календаря

> ⚠️ СВЁРНУТ В МАСТЕР-ТЗ — работать по [2026-06-18-assistant-calendar-master.md](2026-06-18-assistant-calendar-master.md)
> (он включает эти фиксы + продуктовую модель: контрагент-vs-место, рабочий профиль, онлайн-пометка).
> Этот файл оставлен как первичная декомпозиция багов; источник правды — мастер.

> Статус: НЕ начато (реализация по явному «начни реализацию»).
> Основано на доказательной диагностике: [plans/analysis/2026-06-18-telegram-assistant-calendar-bugs-diagnosis.md](../analysis/2026-06-18-telegram-assistant-calendar-bugs-diagnosis.md).
> Скоуп: backend. Канал: Telegram (и MAX — тот же мост). Затрагивает `conversational`, `concierge`, `events`.
> Принципы: Ship-On (выкатываем включённым), prompt-cache (дата только в USER), TZ через существующий `local-date.ts`.

## Цель
Устранить 4 дефекта диалога с помощником в мессенджерах:
1. бот шлёт по 4–5 дублей ответа на одно сообщение;
2. бот не понимает «завтра/сегодня/в среду» (нет текущей даты в контексте LLM);
3. «какие сегодня встречи» отдаёт встречи за вчера/завтра (окно дня считается в UTC, не в TZ пользователя);
4. очная встреча с местом создаётся как онлайн-видеокомната и «проваливается» (`failed/never_activated`).

## Критерии приёмки (общие)
- На одно входящее сообщение в Telegram приходит **ровно один** ответ помощника (повторная доставка апдейта не плодит ответов).
- «Запиши встречу завтра в 10:00» создаёт событие на корректную дату **без переспроса** (при заданной TZ пользователя).
- «Какие у меня сегодня встречи» возвращает события **сегодняшних суток в таймзоне пользователя** (не вчера/завтра).
- Очная встреча с указанным местом создаётся как `offline_meeting` (без LiveKit-комнаты), не плодит проваленных видеовстреч.
- `bun run typecheck && bun run lint && bun run build` зелёные; затронутые unit-тесты зелёные.

## Фаза 1 — Дедупликация входящих апдейтов + ранний ACK (баг 1) `[ ]`

**Проблема.** `processUpdate` ждёт `dispatchInbound` → `handleAssistantTurn` → `concierge.process`
(14–15 с) до возврата 200; отправитель апдейта ретраит доставку; нет дедупа `update_id`.

**Решение (2 слоя, оба включены сразу).**

1. **Идемпотентность по `update_id` (основной фикс).** В начале `processUpdate` (после verify secret,
   до тяжёлой обработки) — атомарный Redis `SET key NX EX`:
   - ключ: `tg:update:<channelId>:<update_id>` (для MAX — аналог по его id апдейта);
   - `SET … NX EX <ttl>` (TTL 1 час). Если ключ уже стоит (`NX` не сработал) → это повторная
     доставка → немедленно вернуть `{ ok: true }` (200), ничего не обрабатывая.
   - Если `update_id` в апдейте отсутствует/невалиден — обрабатываем как раньше (без дедупа), с WARN.
   - **Защита от «залипшего» ключа при падении:** если дальнейшая обработка апдейта бросила
     фатально (catch в `processUpdate`), ключ удалить (`DEL`), чтобы ретрай Telegram смог
     доставить сообщение повторно. Успешная обработка ключ оставляет до TTL.
   - Redis недоступен → fail-open (обрабатываем без дедупа, WARN), как остальная память моста.

2. **Ранний ACK (UX, чтобы не копить ретраи).** Развязать ответ webh/200 от тяжёлой обработки:
   `dispatchInbound` для `assistant_turn` запускать так, чтобы HTTP-ответ Telegram возвращался
   сразу (≤ сотен мс), а LLM-конвейер шёл в фоне.
   - **Рекомендуемый способ:** обработку `assistant_turn` вынести в существующий BullMQ
     (надёжный фон + контролируемые ретраи), webhook возвращает 200 сразу после enqueue.
     В очереди — тот же `handleAssistantTurn`.
   - **Минимальный способ (если очередь дорого):** в контроллере не `await`-ить `dispatchInbound`
     для фоновых типов, а запускать его «fire-and-forget» c защитой (ловить ошибку, метрика).
     Тогда корректность дублей держится только на дедупе `update_id` из п.1.
   - Любой способ — **за kill-switch** `ASSISTANT_INBOUND_ASYNC_ENABLED` (kill-switch, ON по
     умолчанию; см. feature-flags.md). Аварийно выключить → синхронное поведение как сейчас.
   - Запись в реестр флагов: `docs/operations/feature-flags.md`.

**Файлы:** `telegram-webhooks.controller.ts` (processUpdate), `telegram-bot.adapter.ts` (id апдейта),
аналог в MAX-адаптере; опц. новый BullMQ-процессор в `conversational`.

**Приёмка фазы:** локальный e2e/ручной — повторная отправка одного `update_id` (двойной POST вебхука)
даёт один ответ; webhook отвечает 200 быстро (лог времени ответа < 1 c).

## Фаза 2 — Текущая дата/время/TZ в контекст помощника (баг 2 + часть бага 3) `[ ]`

**Проблема.** LLM не знает «сейчас» и таймзону пользователя.

**Решение.** Подмешивать в **USER-блок** (НЕ в SYSTEM — иначе ломается prompt-cache) строку «сейчас»:
- источник TZ: `User.timezone` (дефолт `Europe/Moscow`), резолв через `local-date.ts`;
- формат (русский, человекочитаемо + машинно): например
  `Сейчас: 2026-06-18 (среда), 16:30 по таймзоне пользователя (Asia/Novosibirsk, UTC+7).`
  + явная подсказка: `«сегодня» = эта дата; «завтра» = +1 день; время понимай в этой таймзоне.`
- Точка вставки: в начало контекст-блока — `ConciergeContextBuilderService.build` добавляет первую
  строку «Сейчас…», ИЛИ `composeConciergeUserBlock` дописывает её перед `Контекст:`. Контекст-блок
  и так per-request и едет в USER → кэш SYSTEM не страдает.
- `now` брать один раз на запрос (`new Date()`), TZ — из профиля пользователя (прокинуть `timezone`
  в `build({ tenantId, userId, timezone })` или дочитать User в билдере — он уже читает User).

**Файлы:** `concierge-context-builder.service.ts` (или `concierge.service.ts` composeConciergeUserBlock),
`concierge-respond.prompt.ts` (если нужна строка-инструкция про относительные даты — добавить в USER-шаблон, не в SYSTEM).

**Приёмка фазы:** «запиши встречу завтра в 10:00 с N» → `POST /events` проходит с корректной датой
без переспроса и без 400; в `requestPreview` LLM-вызова видна строка «Сейчас…».

## Фаза 3 — Окно «сегодня/диапазон» в таймзоне пользователя (баг 3, серверная часть) `[ ]`

**Проблема.** `resolveCalendarWindow` дефолтит окно через `setUTCHours(0,0,0,0)` (UTC), а должно — в TZ пользователя.

**Решение.**
1. Добавить в `local-date.ts` helper `startOfLocalDayUtc(now, timezone): Date` (и/или
   `localDayWindowUtc(now, tz) → {from, to}`): вычислить «00:00 локального дня в TZ» и вернуть как UTC `Date`
   (через `Intl.DateTimeFormat` с `timeZone`; без сторонних либ, как остальной файл).
2. `resolveCalendarWindow` принимает `timezone` пользователя и строит дефолт окна по локальному дню:
   `from = startOfLocalDayUtc(now, tz)`, `to = from + 24ч`. Прокинуть `timezone` из `getMyCalendar`/
   `getUserCalendar` (дочитать `User.timezone` или передать из контроллера `/me/calendar`).
   Поведение при явных `from`/`to` из запроса — без изменений.
3. Дефолт `timezone` в `create_event` (`CreateEventSchema`, дефолт `Europe/Moscow`) — при создании
   через помощника подставлять `User.timezone` вместо хардкода Moscow (если LLM не передал явный offset).

**Файлы:** `operations/utils/local-date.ts` (+ helper и unit-тест), `events/services/events.service.ts`
(`resolveCalendarWindow`, `getMyCalendar`, `getUserCalendar`), `events.controller.ts` (/me/calendar),
опц. `events.dto.ts` / `EventsService.create` (дефолт TZ).

**Приёмка фазы:** unit на `startOfLocalDayUtc` (UTC+7, UTC+3, переход суток); для пользователя UTC+7
«сегодня» возвращает события локальных суток, не смещённые на 7 ч.

## Фаза 4 — Корректный выбор инструмента/типа встречи (баги 3-в и 4) `[ ]`

**Проблема.** (а) `list_meetings` описан как годный для «что было сегодня», хотя фильтра даты не имеет;
(б) `create_event` ставит `kind=meeting` (онлайн-видео) для очной встречи с местом.

**Решение (правка описаний инструментов — это USER-сторона, влияет на выбор LLM).**
1. `list_meetings` — убрать из описания фразу «что у меня было сегодня»; явно указать: «возвращает
   последние видеовстречи Коры без фильтра по дате; для вопросов про календарь/«сегодня/на неделе»
   используй `list_my_events`».
2. `create_event` — в описании добавить правило выбора `kind`:
   «если у встречи есть физическое место (адрес, завод, офис, “у клиента”) и не сказано
   “онлайн/созвон/видео” → `kind=offline_meeting` (видеокомната НЕ создаётся). `kind=meeting` —
   только для явных онлайн-созвонов.»
3. (опц., если останутся мусорные проваленные комнаты) — рассмотреть, чтобы `offline_meeting`/`call`
   не порождали LiveKit-комнату и idle-cron их не валил. Подтвердить по `EventsService.create`.

**Файлы:** `service-map-generator.service.ts` (описания `list_meetings`, `create_event`),
проверка `events.service.ts` (создание Meeting только для `kind=meeting`).

**Приёмка фазы:** «запиши встречу с N на заводе завтра в 10» → создаётся `offline_meeting` с `location`,
без LiveKit-комнаты и без последующего `failed/never_activated`.

## Фаза 5 — Способ задать реальную таймзону пользователя (данные, не код-баг) `[ ]`

**Проблема.** Даже с фиксами всё считается верно только если `User.timezone` соответствует реальности.
Сейчас дефолт `Europe/Moscow`, а пользователь в UTC+7 — и нет очевидного способа это поправить.

**Решение (рекомендация владельцу — выбрать объём):**
- минимум: бот-команда/намерение «моя таймзона — Новосибирск/UTC+7» → запись в `User.timezone`
  (валидация через `isValidTimezone`);
- лучше: поле таймзоны в настройках профиля кабинета + предложить выбрать при первом обращении,
  если TZ не задана явно;
- (необязательно) эвристика по сообщениям времени — НЕ рекомендуется (ненадёжно).

**Файлы:** `users`/`me` settings, опц. интент в помощнике. Вынести отдельно — не блокирует Фазы 1–4.

## Развилки для владельца (рекомендации даны)
- **Р1 (баг 1):** дедуп `update_id` + ранний ACK через **BullMQ** (рекоменд., надёжный фон) vs
  «fire-and-forget без очереди» (дешевле, но без ретраев). → **Рекомендую BullMQ**, т.к. при падении
  обработки сообщение не теряется.
- **Р2 (Фаза 5):** объём установки TZ — бот-команда (быстро) vs настройка профиля + онбординг
  (полнее). → **Рекомендую профиль + автоспрос при незаданной TZ**.
- **Р3:** делать ли `offline_meeting`/`call` без LiveKit-комнаты (Фаза 4 п.3) сейчас или отдельным ТЗ.
  → **Рекомендую** подтвердить поведение `EventsService.create` в рамках Фазы 4 и поправить, если комната создаётся для очных.
