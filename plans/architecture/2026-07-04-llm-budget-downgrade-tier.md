# Архитектура «Экономный режим лимита расходов на ИИ» (человеческим языком)

## 1. Что это и зачем

Сегодня у лимита расходов на ИИ есть только два состояния: «просто предупреждать» и «отключить ИИ совсем». Второй вариант рискован — сотрудники компании в разгар месяца вдруг перестают получать AI-отчёты о встречах и другие AI-функции, потому что кто-то один раз решил ограничить бюджет. Нужен третий, средний вариант: при перерасходе не отключать ИИ и не просто пугать уведомлением, а автоматически перейти на более простую (дешёвую) модель — чтобы функции продолжали работать, а расходы под конец месяца не улетали в небо.

Страдает сегодня: владелец компании — либо теряет ИИ-функциональность целиком (жёсткий вариант), либо не может сделать вообще ничего с перерасходом, кроме как получать уведомления (мягкий вариант). Косвенно страдают и сотрудники компании — они вдруг не получают AI-отчёт о встрече из-за решения по бюджету, которое к ним не имеет отношения.

## 2. Как сегодня (от чего отталкиваемся)

- Лимит на компанию задаётся только точечным техническим запросом к серверу — у владельца платформы уже есть форма для этого (поле «сумма в рублях» + пороги для уведомлений), у обычного владельца компании такой формы нет вообще.
- Есть два режима: **мягкий** (по умолчанию) — компания получает уведомление при достижении настроенных порогов (например 80%, 100% от лимита), ничего не блокируется; **жёсткий** — при превышении лимита ВСЕ обращения к ИИ для этой компании начинают отказывать с ошибкой до начала следующего месяца.
- Общего лимита «по умолчанию для всех компаний, у кого нет своего» сейчас нет вообще — если компании явно не задали лимит, для неё нет ни ограничения, ни даже напоминания.
- Общий рубильник платформы «жёсткий лимит на самом деле применяется» сейчас выключен — режим существует, но нигде не активирован (осознанная отсрочка, см. предыдущую архитектуру о починке расчёта рублей).
- Уведомление о превышении порога уже приходит владельцу компании тем же каналом, что и другие системные уведомления — не по email, а во внутреннюю ленту компании (тот же канал, которым уже пользуются другие AI-уведомления).
- Для каждой AI-задачи (например, «сделать отчёт о встрече») уже настроен список моделей: «основная → запасная → ещё более запасная». Этот список сегодня используется только при технических сбоях — если основная модель не ответила или ответила с ошибкой, автоматически пробуется следующая по списку. К бюджету он сегодня отношения не имеет.

## 3. Что делаем (решение простыми словами)

Добавляем третий вариант режима лимита — назовём его **«экономный режим»**: при достижении лимита компания не теряет функциональность (как при жёстком) и не остаётся просто предупреждённой без всякого действия (как при мягком) — вместо этого все обращения к ИИ до конца месяца автоматически идут через более дешёвую модель из уже настроенного для этой задачи списка. Тот же самый список, которым сегодня уже пользуется переключение при сбое провайдера — просто теперь выбор из него может происходить и по причине «дорого», а не только по причине «не отвечает».

Плюс — заводим лимит «по умолчанию для всех компаний» (общий, на уровне платформы), который автоматически действует на компанию, если у неё нет своего собственного значения. По умолчанию, как и сегодня для лимита на компанию, «без ограничений».

## 4. Как это будет выглядеть

### Сценарии «было → стало»

**Сценарий: компания в экономном режиме превышает месячный лимит**
- Было (жёсткий режим): 25 июня — встреча закончилась → сотрудник ждёт AI-отчёт → получает ошибку «ИИ временно недоступен»; все AI-функции компании отключены до 1 июля.
- Стало (экономный режим): 25 июня — встреча закончилась → сотрудник как обычно получает AI-отчёт, просто его подготовила более простая модель → владелец компании получает одно уведомление: «с 25 июня расходы компании на ИИ достигли месячного лимита — до 1 июля работаем в экономном режиме на более простой модели».

**Сценарий: владелец платформы задаёт лимит по умолчанию**
- Было: у компании без персонального лимита расходы ничем не ограничены и никак не отслеживаются.
- Стало: владелец платформы один раз задаёт «лимит по умолчанию» (например 5 000 ₽/мес) → он автоматически действует на все компании без собственного лимита. Как только у компании появляется персональный лимит — общий её больше не касается.

### Макет: уведомление владельцу компании (живой образец, в стиле уже существующих уведомлений о лимите)

```
🔔 Экономный режим ИИ включён

Расходы компании на ИИ в июне достигли лимита 5 000 ₽.
Чтобы не останавливать работу совсем, до конца месяца
AI-отчёты и другие функции используют более простую модель.

С 1 июля режим автоматически вернётся к обычному.
```

### Макет: форма лимита компании (расширение уже существующей формы у владельца платформы)

```
┌─ Бюджет ──────────────────────────────────────┐
│ Лимит:  [ 5000        ] ₽/мес  (0 = без лимита)│
│ Режим:  ( ) Мягкий — только уведомлять         │
│         ( ) Жёсткий — останавливать ИИ         │
│         (•) Экономный — переходить на          │
│             более дешёвую модель               │
│ Пороги алертов: [ 80, 100 ]                    │
└──────────────────────────────────────────────────┘
```

### Макет: лимит по умолчанию (новый, отдельная настройка платформы)

```
┌─ Лимит по умолчанию (для компаний без своего) ─┐
│ [ 0            ] ₽/мес  (0 = без ограничений)  │
└──────────────────────────────────────────────────┘
```

## 5. Делаем поверх существующего (масштаб)

Чистое расширение уже работающего механизма лимитов, не новая подсистема:
- Переиспользуем существующую форму и хранение лимита на компанию — добавляем третий вариант режима к уже имеющимся двум.
- Переиспользуем существующий канал уведомления владельца (тот же, что уже шлёт «превышен лимит на N%») — новый повод для того же уведомления, с той же защитой от спама (одно уведомление за месяц на компанию, не на каждое обращение к ИИ).
- Переиспользуем уже существующий для каждой AI-задачи список «основная модель → запасная → ещё более запасная» — при экономном режиме выбираем из него самую дешёвую по факту модель, не заводим отдельный список «дешёвых моделей».
- Новое: лимит «по умолчанию для всех компаний сразу» — раньше такого не было ни в каком виде.

## 6. Границы — что НЕ делаем

- НЕ делаем общий потолок расходов по всей платформе разом (сумму по всем компаниям вместе) — только лимит «по умолчанию», который действует на компанию отдельно. Владелец явно отверг общий платформенный потолок.
- НЕ меняем страницу расходов, которую видит сам владелец компании (self-service) — она остаётся как есть; в этой итерации там не появляется отдельный визуальный индикатор «сейчас работаем в экономном режиме» — единственный сигнал владельцу это уведомление. Индикатор на самой странице можно добавить позже, если понадобится.
- НЕ включаем экономный или жёсткий режим ни одной компании автоматически без решения владельца платформы — включение по-прежнему ручное на компанию, либо через явно заданный лимит по умолчанию.
- НЕ трогаем и не переписываем существующий механизм переключения модели при сбое провайдера — экономный режим ПОЛЬЗУЕТСЯ тем же списком моделей, ничего в нём не меняя.
- НЕ включаем сам общий рубильник «лимиты реально применяются» этой доработкой — это отдельное, самостоятельное решение владельца платформы (см. границы предыдущей архитектуры по починке расчёта рублей).

## 7. Решения, которые я принял за тебя

| # | Решение | Почему так |
|---|---|---|
| Р1 | «Более дешёвая модель» = самая дешёвая по факту цена среди моделей, уже настроенных для этой конкретной AI-задачи (тот же список «основная → запасная → ещё запасная»), а не отдельный список «дешёвых моделей». | Не плодим вторую систему выбора моделей поверх уже существующей; список для задачи и так поддерживается в админке моделей — переиспользуем его как есть. |
| Р2 | Если для задачи в списке всего одна модель или все стоят одинаково — экономный режим просто продолжает работать как раньше, без ошибок и без искусственной деградации. | Нечего понижать — лучше «как обычно», чем выдуманная деградация там, где деградировать некуда. |
| Р3 | Уведомление владельцу — одно за календарный месяц (в момент первого перехода в экономный режим), а не на каждое обращение к ИИ. | Иначе будет спам уведомлениями при активном использовании; тот же принцип уже применён к уведомлениям о превышении процентных порогов. |
| Р4 | Экономный режим действует до конца текущего календарного месяца и сбрасывается 1-го числа — как и жёсткий режим сегодня. | Совпадает с уже принятой логикой месячного лимита, не вводим отдельного окна времени. |
| Р5 | 0, введённый в поле лимита (и общего, и на компанию), означает «без ограничений»; технически хранится как «лимит не задан». | Для лимита на компанию пустое поле уже сегодня значит «без лимита» — явно разрешаем и 0 с тем же смыслом, для единообразия с общим лимитом по умолчанию. |

## 9. Как поймём, что получилось

- В форме лимита компании (у владельца платформы) наравне с «мягкий»/«жёсткий» можно выбрать «экономный».
- Владелец платформы может задать один общий лимит по умолчанию, и он реально действует на компании без собственного лимита.
- При достижении лимита в экономном режиме: встречи компании продолжают получать AI-отчёты (без ошибок), но через более простую модель; владелец получает ровно одно уведомление об этом за месяц, не поток уведомлений.
- 0, введённый в любое из полей лимита, трактуется как «без ограничений» — не как «лимит в 0 ₽», который заблокировал бы всё.
