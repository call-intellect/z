# Pulse Волны 1+2 — оркестрация 13 фаз за одну сессию

## Что было поставлено

Пользователь поручил быть главным оркестратором по ТЗ [plans/tz/2026-05-30-pulse-full.md](../../plans/tz/2026-05-30-pulse-full.md) (~1450 строк, 6 волн, 15 недель работы по плану). Полная автономия: исследовать каждую фазу, готовить промпт, запускать агента, верифицировать, двигаться дальше. Между волнами — коммитить и пушить самостоятельно.

## Как решал

**Шаблон цикла** для каждой фазы:
1. Read ТЗ (компактно — только нужная фаза), grep по существующей инфраструктуре, чтение профильных DTO/services/моделей.
2. Принимать решения за оркестратора (например: «metadata.isEmpty vs top-level isEmpty» — выбрал второй как проще; «single-org fallback в middleware или guard» — guard, не дублируем БД-запросы в middleware).
3. Писать детальный промпт для агента — со спецификацией файлов, кода, DTO, тестов, DoD. Включал блок «✅ Уже существует» и «❌ Создаём».
4. Запускать `general-purpose` агента.
5. **Факт-чек** результата: `git status`, grep ключевых маркеров (TenantMiddleware, isEmpty, raisedCount, KpiHero и т.д.), запуск тестов локально, не доверяя пометкам `[x]` от агента (`feedback_agents_can_lie_about_edits`).
6. Если зелено — следующая фаза.

**13 фаз пройдены за одну сессию** (Волна 1: 8 фаз, Волна 2: 5 фаз). Все DoD выполнены, 186/186 backend тестов зелёные, typecheck/lint/build чисто.

**Архитектурные решения, которые я принимал по ходу:**
- TenantMiddleware **без БД-запросов** (single-org fallback оставлен в TenantGuard где `req.user.id` уже есть).
- KpiHero — расширение паттерна StatCard через threshold-coloring + paired chip-tokens; не модифицировал существующий StatCard.
- Runtime-секции в Daily/Weekly digest **без миграции БД** (вычисляются при выдаче DTO, не персистятся). Это быстрее реализуется и не блокирует deploy.
- Меmig sentinels: Decision получил `raisedCount/lastRaisedAt` — это минимально необходимое изменение БД. Подсчёт исторических merge-событий не делали (default=1 покрывает старые записи).
- Citations parser — отдельный сервис, регекс whitelist (`[ib|theme|ent|mtg|goal|dec:UUID]`), валидирует ID против переданных SOURCES, удаляет галлюцинации.
- Phase 2.3: НЕ добавлял `Issue.lastActivity` field — использовал существующий `Issue.updatedAt` (минимальное безопасное изменение). Если в будущем понадобится разделение «meaningful activity vs auto-update» — добавим field тогда.
- Phase 2.5: `Goal.ownerPersonId` не существует в схеме → секция целей команды осталась stub'ом с TODO Wave 6.5 (Promise Network).

**Коллизии со схемой**, которые агенты обнаруживали и я разруливал:
- Phase 2.1: Meeting использует `endedAt` (не `completedAt`), `durationMs` (не `durationMinutes`) — агент адаптировал.
- Phase 2.5: `Goal.ownerPersonId` не существует — пустой массив + TODO.
- TenantGuard `singleOrgFallback` возвращает `string | null`, а `req.tenantId: string | undefined` — конверсия через `?? undefined`.

## Чему научился

1. **Параллельная сессия Z** (commit `3772736 feat(agents-v2): umbrella implementation` от 16:16 того же дня) попала в репо до старта моих работ — пришлось убедиться что её зона (probe, multi-agent debate, autorule, GEPA, practice-skill) **не пересекается** с моей зоной (dashboard, operations, rbac middleware, teams). Не пересеклась. Правило `git fetch + log --since=1h перед стартом каждой фазы` (`feedback_parallel_sessions_git_check`) работает — нужно ему следовать в начале.

2. **«Уже существует» секции в ТЗ работают только если в них есть пути файлов**. v2-rewrite ТЗ после 6 Explore-агентов добавил эти секции — это сэкономило мне массу времени. Без этого я бы дублировал `AssistantSignal` поверх `ActivityFeedItem` (как раз эту ошибку v1-ТЗ и допускал).

3. **Runtime-секции без миграции БД — отличный паттерн** для расширения отчётов (daily/weekly digest получили 7 новых секций без единой строки schema.prisma). Запрос Prisma в момент выдачи DTO + try/catch + default empty arrays = устойчиво и обратно совместимо.

4. **Threshold inverted** для negative-KPIs (hanging decisions — меньше = лучше) **нужно явно класть в DTO компонента**, не в стилях. Иначе UI логика расползается. `KpiThreshold` с флагом `inverted?: boolean` — правильное место.

5. **Citation marker `[type:id]` → `[N]` парсер** на бэке + footnote-list на фронте — рабочий паттерн для transparent sourcing. Регекс whitelist типов + валидация ID против переданных sources = защита от LLM-галлюцинаций без сложных доказательств.

6. **Скоупно для одной сессии разумно ~10-13 фаз** при глубине 1 фаза ≈ 2-4 файла + тесты. 6-волновое ТЗ за раз нереально, нужно дискретизировать на коммиты между естественными чекпоинтами (волнами).

7. **Большие промпты агенту работают лучше**, чем дробление на десяток мелких. Один промпт = одна фаза = одна цельная задача с DTO, моделями, сервисом, фронтом, тестами. Агент успешно делал по 30-50 tool_uses в одном вызове.

8. **Cohort threshold** (min 3 чел.) как явный гражданин в TeamHealthService — правильно. Защищает от доксинга маленьких команд + честная статистика. `belowCohort: true` строка с серым фоном вместо пропуска — UX-победа (отдел не «исчезает», просто показывает почему пуст).

9. **Параллельная сессия трогала те же файлы операций** (`operations-dashboard.service.ts`, `dto/operations-dashboard.dto.ts`, фронт), но я добавлял только новые методы/поля — merge-конфликтов на push не было.
