## ТЗ-1 — Стабильность фронта: ChunkLoadError + видео (🔴 приоритет 1)
**Объединить в одно ТЗ — общий корень: Turbopack в prod-сборке.**

**Проблема.** (а) Детальные страницы периодически падают в английский экран «This page couldn't load» (стабильно `/tables/[id]`, иногда `/result`) — это и есть жалоба владельца на «задержки/тормоза при переходах». (б) Видео записи не проигрывается — вечная крутилка.

**Корень (доказан).**
- ChunkLoadError: `Failed to load chunk /_next/static/chunks/0ly-k3c_rg6_b.js from module 964893` при том, что прямой fetch чанка → **200**. Это рассогласование манифеста рантайма и содержимого чанка: `next build` в Next 16 идёт **Turbopack'ом по умолчанию** ([package.json:8](../../frontend/package.json#L8) `"build":"next build"` без флага), `deploymentId` не задан → version skew (старый HTML вкладки vs новый билд). `/tables/[id]` стабильно — там единственная гарантированная клиентская lazy-граница ([TableClient.tsx:41-51](../../frontend/app/(authenticated)/tables/[id]/TableClient.tsx#L41-L51) `dynamic(()=>import('./components/GridView'),{ssr:false})`). Одна фронт-реплика (не multi-replica skew).
- Видео: `<media-player>` Vidstack не «оживает» (React-контроллер не присоединяется → `<video> src=""`, networkState=0). Фикс `load="eager"` (`8fab2fc2`) **на проде есть, но бессилен**. Та же Turbopack-сборка не подгружает чанк инициализации Vidstack.
- **ЭМПИРИЧЕСКИЙ ТЕСТ (доказательство):** нативный `<video src={presignedUrl}>` вставлен в живую страницу прода → **играет**: `readyState:4, duration:90.6с, 1280×720, played:true`. Файл/кодек/CSP/presigned — исправны. Сломан ТОЛЬКО Vidstack.

**РЕШЕНИЕ (decisive).**
1. **`next build --webpack`** — увести prod-сборку с Turbopack на webpack (`frontend/package.json`). Закрывает И ChunkLoadError, И инициализацию Vidstack одним ходом.
2. **`deploymentId`** в `next.config.mjs` (`process.env.DEPLOYMENT_VERSION`/git sha, прокинуть build-arg) — включает штатную Next-защиту от version skew (hard MPA-navigation).
3. **Глобальный ChunkLoadError-обработчик** → один тихий `location.reload` (с защитой от цикла через sessionStorage) + **`app/global-error.tsx` и локальные `error.tsx` на РУССКОМ** (вместо «This page couldn't load»).
4. **Заменить Vidstack-плеер записи на нативный `<video src={videoUrl} controls preload="auto" playsInline>`** в `MeetingPlayer.tsx` + обеих share-страницах (`ShareMeetingClient`/`ShareClipClient`); маркеры глав — CSS-оверлеем. (Прецедент: нативный `<audio>` в [MeetingResultPageReal.tsx:1275-1283](../../frontend/src/ui/components/meeting-result-v2/MeetingResultPageReal.tsx#L1275-L1283) уже работает.)

**Почему так.** Webpack — проверенное годами поведение чанков; ChunkLoadError «from module N» при 200 — характерный класс Turbopack-prod рассогласования. `deploymentId` штатно гасит skew. Нативный `<video>` гарантированно играет (тест доказал) и снимает целый класс рисков (tree-shaking регистрации, апгрейды Next/React). Делаем и (1), и (4) — чтобы не зависеть от того, оживит ли webpack именно Vidstack.

**Что ТЗ должно специфицировать.** Точные правки `package.json`/`next.config.mjs`/Dockerfile build-args; формат `deploymentId`; код ChunkLoadError-обёртки + анти-цикл; русские тексты error-boundary (парные токены, без английских слов); замену `<MediaPlayer>`→`<video>` в 3 местах с сохранением UX (controls, главы-оверлей).

**Acceptance-сигнал.** На проде после выката: `/tables/<id>`, `/structure/persons/<id>`, `/result` открываются без «This page couldn't load» (повторные reload); в Network нет 404 на чанки; видео на `/result` и share — `<video>.readyState>0`, играет; экран ошибки (если случится) — на русском.

**Прод-проба до ТЗ (опц.):** сверить `buildId` в HTML словившей ошибку вкладки vs сервера — подтвердить skew vs чистый Turbopack-баг (от этого зависит, достаточно ли `deploymentId` без webpack; рекомендую делать webpack в любом случае).

## ТЗ-2 — Надёжность записи/пайплайна: 18-минутная пауза (🔴 приоритет 1)
**Проблема.** Иногда отчёт встречи готовится ~20 минут, иногда ~50 секунд. Владельца это путало.

**Корень (доказан 2 встречами).** Весь старт пост-обработки (`transcribe→…→граф`) висит на ОДНОМ вебхуке LiveKit `egress_ended` (готовность composite-видео). Крон-фоллбэка, который сам дотянул бы статус, НЕТ ([livekit-events.handler.ts:503-507](../../backend/src/modules/webhooks/livekit-events.handler.ts#L503-L507) — единственный enqueue transcribe; reconcile-крон [recording-track-reconcile.cron.ts:35](../../backend/src/modules/recordings/cron/recording-track-reconcile.cron.ts#L35) смотрит только TRACK, не composite). Когда вебхук теряется (LiveKit держит «хвост» событий при недоставке предыдущего — напр. рестарт backend), пайплайн пассивно ждёт ~18 мин. **Факт: встреча 1 — пауза 18м22с; встреча 2 — пауза 1.7с** (тот же код, разный результат ⇒ интермиттентная доставка вебхука).

**РЕШЕНИЕ (decisive).**
1. **Composite-egress reconcile-крон (главное):** добавить `listEgress` в `LivekitEgressClient`, `@Cron('*/1–2')` по встречам `completed/recording_processing` старше ~60с; если composite `EGRESS_COMPLETE` — вызвать существующий `onCompositeEnded` + `maybePromoteMeetingToReady` (вынести из webhook-handler в общий сервис). Ограничивает паузу сверху ≤2 мин. Kill-switch ENV.
2. **Ack-first вебхуки:** обработку вебхука увести в фон, всегда быстро отвечать 200 (чтобы LiveKit не держал секвенс); + метрика gap `room_finished→egress_ended`.
3. **Честный UI обработки:** пока отчёта нет, `/result` показывать «Отчёт готовится, обычно несколько минут» + поллинг, а НЕ бесконечный скелетон.
4. (опц., хвост) block-linker распараллелить (`p-limit` вместо последовательного for-loop) — 44–73с/проход.

**Почему так.** Reconcile-крон — дёшево, переиспользует весь готовый промоут-код, жёстко ограничивает паузу; ack-first бьёт в корень секвенс-холда, но без гарантий (вебхуки не гарантированы) → крон обязателен как резерв. Честный UI убирает ощущение «зависло».

**Что ТЗ специфицировать.** `listEgress` обёртка (SDK 2.15.3 умеет); точный `@Cron` + предикат выборки + идемпотентность; вынос промоут-логики в сервис; ENV-флаг крона; контракт честного статуса на фронте.

**Acceptance-сигнал.** На искусственно «потерянном» вебхуке (или по факту) пауза `completed→recording_ready` ≤ интервала крона; `diag chain` показывает промоут от крона, не только от вебхука; на `/result` во время обработки — текст статуса, не скелетон.

**Прод-проба:** `webhook_seen_event`/`meeting_event` встречи `01KTEAH38…` (что приходило 11:21–11:39); логи контейнера LiveKit Egress (EGRESS_COMPLETE timestamp); был ли рестарт backend в окне.

## ТЗ-3 — Граф знаний теряет связи (🟠 приоритет 2)
**Проблема.** block-linker / entity-graph-builder часто получают невалидный JSON от LLM-арбитра → ретрай → иногда «fallback на none» (связь не создаётся). WARN-спам несколько раз/час.

**Корень (доказан).** `json_schema strict` для DeepSeek превращается в синтетический tool с `tool_choice:'auto'` (без `required`, без `function.strict`) → `deepseek-v4-flash` вправе вернуть прозу ([deepseek.service.ts:139-160](../../backend/src/modules/ai/services/deepseek.service.ts#L139-L160)). Битый ответ router считает успехом (200, непустой text) → fallback на secondary НЕ срабатывает ([llm-router.service.ts:1489](../../backend/src/modules/ai/services/llm-router.service.ts#L1489)). entity-graph ещё хуже: голый `JSON.parse` без ретрая ([entity-graph.service.ts:330-338](../../backend/src/modules/knowledge-core/services/entity-graph.service.ts#L330-L338)).

**РЕШЕНИЕ (decisive).**
1. Для НЕ-thinking моделей (flash, gpt-5.4-*) ставить `tool_choice:{type:'function',function:{name}}` + `function.strict:true` вместо `'auto'` (с per-model guard и откатом на 'auto' по существующей `LlmFormatNotSupportedError`).
2. Устойчивый парс: `tryParseJson` в entity-graph (как в block-linker); и **parse-fail пробрасывать как throw в router** → срабатывает реальный fallback на secondary (gpt-5.4-nano с настоящим strict).
3. Метрика невалидного JSON для entity-graph (у block-linker уже есть).

**Почему так.** Корень — режим вызова (модель вправе не вернуть структуру) + «битый = успех». (1) заставляет модель вернуть структуру, (2) гарантирует доезд до провайдера с настоящим strict, если flash не справился. Не меняем модель на дорогую pro (правило primary=flash сохраняем).

**Предусловие/связь:** ТЗ-7 (DeepSeek-отчёт) §2 отмечает, что этот фикс снижает риск миграции на router в будущем.

**Acceptance-сигнал.** Мини-e2e: при «грязном» ответе арбитра связь всё равно строится (или честный fallback); `kc_block_linker_fallback_none_total` падает; метрика entity-graph существует.

**Прод-проба (обязательна до ТЗ):** мини-e2e на прокси agent-lia — принимает ли `deepseek-v4-flash` форс `tool_choice` конкретной функции + `function.strict:true`. Если 400 — опираться на пункт (2) (router-fallback).

## ТЗ-4 — Задачи: один источник + дедуп + устойчивость к ASR (🟠 приоритет 2; продуктово важно)
**Проблема (владелец видел).** Задачи извлекаются с дублями и пропусками: «Сделать рассылку на 2000» и «на 2 000» — дубль; «Набрать команду» и «Набрать команду (…)» — дубль; теряются «200 встреч», «50 сделок».

**Корень (доказан кодом + 2 встречами).**
1. **ТРИ источника задач:** `aiResult.structuredData.tasks` (отчётный агент, для чтения) · таблица `Task` (пишут ДВА экстрактора — fast из `meeting-report-fast.worker` + main из `analyze.runTasks`) · `IntakeIssue` (трекер, [meeting-extract-actions.service.ts:304](../../backend/src/modules/tracker/services/meeting-extract-actions.service.ts#L304)).
2. **Слабый дедуп:** [task.ts:58-68](../../frontend/src/domain/task.ts#L58-L68) `pickPrimaryTasks` нормализует только `trim+lowercase` → «2000»/«2 000» и скобки не схлопывает.
3. **ASR врёт на входе:** «100 платящих»→«стопящих», «10 месяцев»→«10 минусов»; шаг очистки [transcript-clean-refine.ts:27-38](../../backend/src/modules/ai/services/prompts/transcript-clean-refine.ts#L27-L38) НАМЕРЕННО не правит числа/имена; в промптах нет ноты про ASR; контекст компании (люди/проекты/цели) в summary/report не инъектится.

**РЕШЕНИЕ (decisive, МИНИМАЛЬНО — без тяжёлого глоссария).**
1. **Один канонический источник задач для UI → таблица `Task`.** Не давать fast И main оба писать `Task`: fast — только мгновенный предпросмотр (не персистить как `Task`), канон — один. `structuredData.tasks` и `IntakeIssue` ЧИТАЮТ из `Task`, а не извлекают своё.
2. **Сильный дедуп** перед сравнением: нормализовать числа (убрать пробелы-разделители: «2 000»→«2000»), срезать скобочные уточнения; опц. семантический дедуп близких заголовков.
3. **ASR-нота** — лёгкий хелпер `withAsrNote(system)` в `common.ts`: «Текст — результат распознавания речи (ASR), возможны ошибки в числах/именах/единицах (‘100 платящих’↔‘стопящих’, ‘10 месяцев’↔‘10 минусов’). Восстанавливай вероятный смысл по контексту встречи; нормализуй числа.» Применить к summary/report-by-type/tasks/extract-actions. **Без глоссария** — только нота (минимально).
4. **Инъекция org-контекста** (люди/проекты/цели — уже грузится в `meeting-extract-actions.loadOrgContext`) добавить в summary/report-by-type, чтобы модель цепляла имена/термины. Минимально — переиспользовать существующую загрузку, не строить новую систему.

**Почему так.** Дубли и рассинхрон — от 3 пересекающихся извлечений + слабого дедупа; чиним КОРЕНЬ (один источник правды), а не симптом на каждой поверхности. ASR-нота + контекст — самый дешёвый способ поднять понимание речи без замены ASR (демонстрация: на том же гарбленом тексте с нотой+контекстом восстанавливаются все задачи). Никаких тяжёлых глоссарных систем — владелец прямо просил минимально.

**Что ТЗ специфицировать.** Где обрезать fast-персист; контракт «structuredData.tasks/IntakeIssue читают Task»; алгоритм нормализации дедупа (точные правила); текст `withAsrNote`; точку инъекции org-контекста в summary/report.

**Acceptance-сигнал.** На тест-встрече: счётчик задач одинаков во всех поверхностях и = числу реальных Task; нет дублей «2000»/«2 000»; на гарбленом ASR-входе извлекаются конкретные задачи (числа/наймы раздельно), не схлопнутые.
