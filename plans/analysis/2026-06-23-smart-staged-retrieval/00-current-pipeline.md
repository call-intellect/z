# Текущий конвейер ответа ChatV2 — 5 звеньев друг за другом

## Карта потока (по коду)

```
Вход (вопрос из кабинета /chat или из концьержа-инструмента / Telegram)
  └─ DialogService.process (dialog-layer, ПЕРЕД chat-v2.ask):
       1) QueryClassifierService.classify      → taskType dialog-classify
       2) MultiQueryExpansionService.expand     → taskType dialog-multi-query(/-clone)
       3) QueryPlanExtractorService.extract      → taskType dialog-extract-plan (+resolveStructuralFilters)
  └─ ChatV2Service.ask(queries, structuralFilters):
       4) ChatV2RetrievalService.fetchCandidates → НЕ-LLM: эмбеддинг + cosine(HNSW)+BM25 + 1-hop граф
       5) LLM-синтез                             → taskType chat-v2
```
Файлы: `dialog.service.ts`, `query-classifier.service.ts`, `multi-query-expansion.service.ts`, `query-plan-extractor.service.ts`, `chat-v2-retrieval.service.ts`, `chat-v2.service.ts`.

**Фронт (что видит пользователь):** `ChatV2Stage = 'understanding' | 'searching' | 'writing'` (`chat-v2.service.ts:54`). `'searching'` эмитится перед retrieval (`:633`), `'writing'` перед синтезом (`:835`). Звенья 1–3 идут под «understanding».

**Обёртка концьержа (отдельно от этих 5):** при входе через «Мастер»/Telegram сверху крутится ReAct-петля `concierge.service.ts` до `MAX_TOOL_LOOP_ITERATIONS=5`, которая вызывает ChatV2 как инструмент «ответ из памяти». См. `plans/tz/2026-06-23-edinyy-pomoshnik-master.md` Ф0/Ф4.

### Кто задаёт уточняющие вопросы (подтверждено кодом + прод-вызовом)
**Только концьерж/«Мастер» (`concierge-respond`).** Не классификатор (он лишь ставит ярлык типа в JSON), не ChatV2 (он отвечает из памяти или честно «не нашёл», переспрашивать не умеет).
- Источник правила — системный промпт `concierge-respond`, правило №4: «сомневаешься, к чему отнести сообщение, или без уточнения можешь сделать НЕ ТО → ОБЯЗАТЕЛЬНО задай ОДИН короткий уточняющий вопрос, особенно перед действием, меняющим данные».
- Прод-доказательство (Org «ООО ЛУА», 2026-06-23): вызов `concierge-respond` `cmqqa5c9500tm` выдал уточнение «искать по участнику или по слову; вернуть первые две по дате?» в ответ на понятную просьбу про Александра.
- **Проблема (владелец, 2026-06-23):** правило №4 слишком «пугливое» — переспрашивает там, где можно взять разумное умолчание и выполнить. Это политика переспрашивания концьержа, НЕ классификатор и НЕ поиск. Лечится в Ф4/Ф6 (порог/гейт ценности уточнения).

## Звено 1 — Классификатор намерения (`dialog-classify`)
**Функционально (простым языком):** понимает, что это за вопрос — факт / обзор / анализ / «ответь как клон» (а также личный план/отчёт, заметка, ответ-на-probe). От типа зависит дальнейшая глубина.
**Технически:** `QueryClassifierService.classify`. Сначала дешёвая эвристика по регуляркам (`сколько/когда/почему/расскажи/в стиле…`); если не сработала или есть открытый probe — LLM `dialog-classify` со строгим JSON-schema (`intent`+`confidence`). Модель — по роутеру (на проде наблюдался `deepseek-v4-pro`). Fail → `factual` (или checkin-эвристика).
**Слабые места для Ф4:** только классификация типа, не строит план; на ошибке тихо валится в `factual` (теряет намерение).

## Звено 2 — Мульти-запрос (`dialog-multi-query`)
**Функционально:** из одного вопроса делает несколько переформулировок для поиска (синонимы/ракурсы), чтобы поднять полноту.
**Технически:** `MultiQueryExpansionService.expand`. LLM `dialog-multi-query` (для клонов — `dialog-multi-query-clone`), JSON `{queries:[]}`, берёт до **3** переформулировок + оригинал, дедуп. Промпт `query-understand.prompt` (с summary+историей → standalone-вопрос + расширения). Fail-open → только оригинал.
**Слабые места:** расширение «вслепую» ДО какого-либо поиска — не на основе того, что реально нашлось (не итеративное); фикс 3 шт.

## Звено 3 — Извлечение плана / структурные фильтры (`dialog-extract-plan`)
**Функционально:** вытаскивает из вопроса «рамки»: период (эта неделя / вчера…), типы фактов, темы, упомянутые люди/сущности, «мои», «актуальные сейчас» — чтобы сузить поиск.
**Технически:** `QueryPlanExtractorService.extract`. LLM `dialog-extract-plan`, строгий JSON; порог применения `confidence ≥ 0.6` (`QUERY_PLAN_MIN_CONFIDENCE`); `resolveStructuralFilters` резолвит подсказки-имена в `entityId` через `Entity.canonicalName/aliases`. Fail-open → без фильтра. За флагом `dialogLayer.queryPlanExtractionEnabled`.
**Слабые места:** это «план фильтров», а НЕ план многошагового поиска (нет «сначала узнать сколько встреч, потом достать детали»); резолв сущностей упирается в идентичность (см. граф-ТЗ Ф5).

## Звено 4 — Поиск кандидатов (НЕ LLM)
**Функционально:** собственно «ищет в памяти» — по смыслу (эмбеддинги) + по словам, с учётом фильтров, и добирает соседей по связям графа на 1 шаг.
**Технически:** `ChatV2RetrievalService.fetchCandidates`. `embedQuery` → гибрид cosine(HNSW `embedding <=> qvec`) + небольшой BM25 + recency; при структурном фильтре — recall-safe скан (не HNSW-LIMIT); **1-hop graph expansion** по `IdeaBlockLink status='active'` (`expandViaGraph`); граф-соседи получают сниженный score. Fail (нет эмбеддинга) → BM25/recency. Замечание граф-ТЗ RC-9: базовый `search.service.ts` плоский, обход рёбер живёт только здесь.
**Слабые места:** обход всего на 1 шаг; нет переформулировки запроса при «пусто»; нет узла «суть встречи» (граф-ТЗ Ф4/Ф7).

## Звено 5 — Синтез ответа (`chat-v2`)
**Функционально:** пишет финальный человеческий ответ строго по найденному, со ссылками на источники `[BLOCK:id]`, честно про пустоту/конфликт.
**Технически:** `ChatV2Service.ask`, LLM `chat-v2` (на проде `gemini-3.1-pro` и `deepseek-v4-pro`), системный промпт-«Кора» (роль/границы/цитирование/самопроверка), свой timeout `knowledge.chatV2SynthesisTimeoutMs`; парс `[BLOCK:id]` → citations, strip маркеров. Параллельно идёт ветка таблиц (`runTableBranch`) через `Promise.allSettled`.
**Слабые места:** один проход синтеза по тому, что дал поиск; если поиск пуст/мимо — честно «не нашёл» (наблюдалось на проде по кейсу Насти/Айназ), но НЕ инициирует доп-поиск.

## Сквозные наблюдения (вход для Ф4)
1. **Нет единого ПЛАНА поиска.** Звенья 1–3 — это разбор вопроса (тип/переформулировки/фильтры), а не план «какими шагами добыть ответ». Поиск (4) одноразовый, синтез (5) одноразовый.
2. **Переформулировка «вслепую».** Мульти-запрос строит варианты ДО поиска, не на основе промежуточных находок — это не итеративный/агентный retrieval.
3. **Нет цикла по результату на уровне ChatV2.** Цикл есть только в обёртке концьержа (потолок 5, реактивно), и он же даёт «слепой круг» и трату токенов (граф-ТЗ Ф0/наш Ф4).
4. **Fail-open везде** — звенья тихо деградируют (classify→factual, multi-query→оригинал, plan→без фильтра): надёжно, но прячет «помощник не понял».
5. **Граница с граф-ТЗ:** качество одного поиска (узел «суть встречи», обход рёбер >1-hop, склейка людей, актуальность) — зона `plans/tz/2026-06-23-knowledge-graph-ingestion-rebuild.md`. Наш Ф4 — верхний слой (план + поэтапность + умная остановка), НЕ переделываем звено 4 заново.
