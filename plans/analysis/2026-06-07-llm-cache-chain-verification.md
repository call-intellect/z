# Кэш LLM в цепочке встречи — проверка и лучшее решение

> **Вопрос владельца:** после видеовстречи один и тот же транскрипт прогоняется по всем агентам — срабатывает ли кэш, экономим ли (были тесты до 90%)?

## 1. Где «те тесты с 90%»

Контрольный эксперимент **2026-05-25**. Источник правды — [second-brain/02_architecture/llm-cache-status.md](../../second-brain/02_architecture/llm-cache-status.md). Скрипты:
- `backend/scripts/eval/probe-deepseek-cache.ts`
- `backend/scripts/eval/probe-llm-cache-matrix.ts` (все каналы)
- отчёты — `backend/test/eval/cache-experiment/reports/`

Переверка: `cd backend && bun scripts/eval/probe-llm-cache-matrix.ts`.

Матрица (из эксперимента): DeepSeek pro/flash — **99.9%** hit; OpenAI-via-proxy — 99.7–99.8%; **MiniMax — 100%, но только с явным `cache_control:'ephemeral'`** (в коде он стоит только на system, не на user — `llm-router.service.ts:1149`); KIE/GRSAI — 0% (не пробрасывают).

## 2. Эмпирика прямо сейчас — реальные вызовы встречи «111» (diag call)

| Агент | Модель | input / cached токены | % кэша |
|---|---|--:|--:|
| meeting-report-fast | `deepseek-v4-pro` | 2530 / **2304** | **91%** ✅ |
| tasks | `deepseek-v4-flash` | 1578 / **1280** | **81%** ✅ |
| summary | `MiniMax-M2.5` | 735 / **0** | **0%** ❌ |

**Вывод фактический:** DeepSeek кэширует на 81–91% — механизм жив, «90%» подтверждены на живом проде. Но часть цепочки ушла на MiniMax с нулевым кэшем.

## 3. Как кэш работает на самом деле (важный нюанс к постановке вопроса)

Кэш срабатывает по **стабильному префиксу запроса** (в Z это SYSTEM-промпт + инструкции), а **не по транскрипту, переиспользуемому между агентами**:
- SYSTEM каждого агента стабилен между встречами → он уже в кэше от прошлых прогонов → отсюда 81–91% hit даже на ПЕРВОМ вызове по новой встрече.
- Транскрипт лежит в КОНЦЕ user, у каждого агента — **свой** SYSTEM. Префиксы расходятся уже на SYSTEM → транскрипт после разных SYSTEM **не шарится между агентами**. Для каждого агента транскрипт — это cache-miss (уникальный хвост).

На встрече «111» транскрипт крошечный (437 символов ≈ ~110 токенов), поэтому потеря мизерна. **Но вопрос именно про ДЛИННЫЕ встречи** — там транскрипт это тысячи токенов, и он уходит uncached в КАЖДОГО из ~6–8 агентов. Экономия идёт на SYSTEM (инструкции), а на самом транскрипте — нет.

## 4. Находки (что не так против плана «везде DeepSeek для кэша»)

| # | Находка | Доказательство | Severity |
|---|---|---|---|
| К1 | **summary / report-by-type / tasks-legacy идут на MiniMax**, а не DeepSeek | trace встречи: 3 вызова `minimax:MiniMax-M2.5`; `analyze.worker.ts:566,737,806` (agentType summary/report-by-type, taskType `summary`) | high — расхождение с планом «везде DeepSeek», и именно у MiniMax кэш не сработал (0%) |
| К2 | **MiniMax `cache_control:'ephemeral'` только на system, не на user** | `llm-cache-status.md:36`, мини-ТЗ `2026-05-25-minimax-cache-control-on-user.md` (проверить, докатан ли) | medium — на больших транскриптах MiniMax кэш упускается полностью |
| К3 | **Транскрипт не шарится между агентами** — общего кэш-префикса с транскриптом нет | §3 выше; каждый агент шлёт транскрипт в своём user после своего SYSTEM | high именно для длинных встреч |
| К4 | summary (735 ток) ниже порога кэша MiniMax (chunk ~1024) | `llm-cache-status.md:68` + cached=0 | low — мелкие промпты в принципе не кэшируются |

## 5. Лучшее решение (с доказательством, почему именно оно)

### Решение А (быстрое, обязательное): вернуть всю цепочку отчёта на DeepSeek
Перевести `summary` / `report-by-type` / legacy `tasks` с MiniMax на `deepseek-v4-flash` (или pro). 
**Почему лучшее:** DeepSeek кэширует 99.9% **без** ручного `cache_control` (MiniMax требует ephemeral и имеет более высокий порог); план изначально был «везде DeepSeek»; устраняет К1+К2+К4 одной правкой роутов (`seed-llm-task-routes`, без кода). Альтернатива «докатать MiniMax ephemeral на user» хуже: оставляет два разных кэш-механизма, более высокий порог, и не возвращает к единому плану.
**Доказательство выгоды:** на этой встрече 3 MiniMax-вызова дали 0% кэша; на DeepSeek те же дали бы 80–99% (по матрице и по соседним вызовам той же встречи).

### Решение Б (архитектурное, максимальный эффект на длинных встречах): общий кэш-префикс с транскриптом
Перестроить пакет агентов одной встречи на shared-prefix:
```
[ SYSTEM: общая преамбула «ты анализируешь встречу типа X» ]
[ USER: транскрипт встречи  ]  ← cache_control: ephemeral, ОДИН на всю встречу
[ USER/инструкция: конкретная задача агента (summary | tasks | chapters | ...) ]  ← переменный суффикс
```
Тогда префикс `[преамбула + транскрипт]` кэшируется на ПЕРВОМ агенте и переиспользуется всеми остальными агентами этой встречи.
**Почему лучшее:** на длинной встрече транскрипт = основная масса токенов; сейчас он оплачивается uncached × N агентов. Shared-prefix превращает это в 1× full + (N−1)× ~1% (cache hit). Это ровно сценарий «один транскрипт по всем агентам экономит», которого ждёт владелец.
**Доказательство выгоды (оценка):** встреча 27 мин ≈ ~10k токенов транскрипта, 7 агентов. Сейчас ≈ 70k uncached input-токенов транскрипта. С shared-prefix ≈ 10k + 6×~100 ≈ 10.6k → **экономия ~85% input по транскрипту** (на DeepSeek hit ~99% дешевле miss). На коротких встречах эффект мал — поэтому решение профильное именно под длинные.
**Риск/ограничение:** ломает индивидуальную тонкую настройку SYSTEM под каждый агент (общая преамбула должна быть достаточной); часть агентов (meeting-report-fast — один вызов) в shared-prefix не нуждается. Применять там, где ≥2 агента на одних данных (это и есть отложенное ТЗ «cache-prefix-everywhere» из `llm-cache-status.md:99`).

### Что проверить машинно (чтобы кэш не деградировал тихо)
Алерт/метрика `z_llm_cache_hit_ratio{provider,model}` уже есть (ai-jobs.md T7 F3). Добавить в smoke: после типовой встречи hit-ratio по DeepSeek-агентам ≥ 0.6, иначе WARN. Это ловит регрессии вроде «taskType увели на некэширующий провайдер» (К1).

## 6. Прямой ответ владельцу
- Кэш **срабатывает и экономит** на DeepSeek (81–91% на реальной встрече, 99.9% в эксперименте) — «90%» подтверждены.
- **Но:** (1) часть цепочки уехала на MiniMax с 0% кэша — вернуть на DeepSeek (Решение А); (2) сам транскрипт между агентами не кэшируется — для длинных встреч внедрить общий кэш-префикс (Решение Б). После этого экономия на длинных встречах вырастет кратно.
