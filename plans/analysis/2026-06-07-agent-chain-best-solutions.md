# Цепочка агентов встречи — лучшие решения и доказательства

> Документ собран из трёх источников: (1) живой разбор реального звонка через diag+Playwright; (2) многоагентный аудит 45 субагентов (по каждому из 22 промптов: разбор → улучшение ≥20% → состязательная проверка на кэш-безопасность); (3) сверка по коду. Каждое решение — с доказательством, почему оно лучшее.

## 0. Что проверено и главный вывод

| Поток | Результат |
|---|---|
| Цепочка на реальном звонке «111» | 21 агент, 0 ERROR — **каркас здоров** (B1–B7 из аудита 06-04 закрыты) |
| Наполнение памяти (реальный тестовый кабинет) | Сущности 25 ✅, Цели 2–3 ✅, Задачи 10 (в триаже) ⚠, **Решения 0 ❌, Идеи 0 ❌, Темы 0 ❌**, Поведение — недоступно ❌ |
| Кэш DeepSeek | 81–91% на DeepSeek ✅, но часть цепочки на MiniMax (0%) — см. [Часть 2](2026-06-07-llm-cache-chain-verification.md) |
| Промпты (22 агента) | каркас правил соблюдён у block-ingest/арбитров; **сквозные дыры**: нет ASR-ноты у специалистов, мёртвая ветка `meetingDateIso`, нет few-shot/калибровки confidence |

**Главный вывод (доказанный с двух сторон — эмпирикой и аудитом):** цепочка хорошо **извлекает атомы** (блоки, сущности, цели, задачи), но плохо **связывает их в память** и плохо **доводит до действия**. Это «острова знания»: цель есть, но «0 тем» и не связана с задачами; задачи есть, но застряли в триаже; решения/идеи вообще не материализуются. Совокупный резерв роста полноты памяти — **~+24%** (оценка аудита), сосредоточен в «последней миле» (связывание + доведение), а не в извлечении.

## 1. Архитектура цепочки — что продумано верно, что нет

### Сделано правильно (доказательство — реальный прогон + код)
- **Два пути после merge не блокируют друг друга:** быстрый отчёт пользователю (meeting-report-fast, 1 вызов, ~2 мин) и память компании (block-ingest→distill→linker→специалисты, ~7 мин).
- **Лестница draft→canonical** с дедупом блоков (KNN cosine 0.92 + LLM-арбитр) и сущностей (0.88 + entity-merge-arbiter); специалисты вызываются только на canonical.
- **Один SpecialistRoutingDispatcherWorker** вместо 14 конкурирующих — устранил потерю job'ов (фикс B2).
- **Детерминированная subject-атрибуция** (role:'subject') — оживляет клонов и WHO-ось.
- **JSON-резилиенс арбитра** (validate-fallback + tryParseJson) — на звонке 8× flash→fallback, граф достроился.
- **Идемпотентность** по всему конвейеру (детерминированные jobId, дебаунсы, reingest-cron).

### Где цепочка НЕ доведена (корень — «острова знания»)
1. **Цель ↔ задачи ↔ решения не связаны.** 3-14-goals строит только иерархию Goal↔Goal, но НЕ связывает Goal с Issue/Task из того же разговора. Декомпозиция «воронка 5000→100→10» (видна в задачах) висит отдельно от цели с «0 тем».
2. **Два пути задач расходятся на витрине** (meeting-report-fast vs structured) — дубли под одним счётчиком «5».
3. **Порог авто-Issue 0.92 недостижим** на живой речи (реальные 35–75%) → все задачи мертво в триаже.
4. **Темы требуют ~100 блоков** → на малом тенанте 0 тем → цели без согласованности.
5. **Специалисты слоя 3 невидимы в trace** → нельзя измерить, рождаются ли Decision/Idea/Goal.
6. **Поведенческие метрики мертвы** без word-timings Vox.

## 2. ПЯТЬ лучших архитектурных решений (с доказательством и вкладом)

> Порядок = приоритет по соотношению «вклад в полноту памяти / стоимость». Суммарный потолок ≈ +24%.

### Р1. Связать цель ↔ задачи ↔ решения (goal↔task↔decision linking) — **+8–10%**
**Что:** после того как 3-14-goals создал Goal, а meeting-extract-actions — Issue/Task из ОДНОГО RawEvent, добавить шаг линковки на уровне встречи: новый лёгкий арбитр `goal-task-link` (stable SYSTEM + few-shot, переменные — список целей+задач встречи в конце USER, JSON Schema, `{links:[]}` если связи нет). Писать `parentGoalId` на Issue или `IdeaBlockLink(develops)`.
**Почему лучшее (доказательство):** альтернатива «связывать пер-блок внутри block-ingest» хуже — на момент block-ingest задачи/цели ещё не созданы (они downstream). Связывание на уровне встречи, когда оба набора готовы, — единственная точка, где доступны и цели, и задачи. Cache-safe (отдельный SYSTEM, не трогаем существующие). Прямо закрывает «острова знания» — главную ценность продукта «связанная память».
**Эффект:** цель наполняется темами/задачами вместо «0 тем»; дерево цель→задачи→решения навигируемо в дашборде CEO.

### Р2. Свернуть два пути задач в один + СЕМАНТИЧЕСКИЙ дедуп — **+4–6%**
**Что:** выбрать canonical-источник задач (рекомендую **structured/MiniMax — он даёт исполнителей**), fast оставить только для мгновенного черновика. Дедуп заменить со строкового `normTaskTitle` на семантический: embedding (text-embedding-3-small) + KNN cosine ~0.85, серая зона → лёгкий LLM-арбитр `task-dedupe`. Применять к ОБЪЕДИНЁННОМУ набору, не пер-источник. Свести две summary-сводки в одну витрину.
**Почему лучшее:** доказано эмпирикой — строковый дедуп не схлопнул «Провести встречу с командой»/«Встретиться с командой» (разные глаголы → разные ключи). Семантика ловит смысл, а не строку. Canonical=structured доказан тем, что у него есть исполнители (у fast — нет).
**Эффект:** убирает дубли и двойные сводки, видимые пользователю прямо сейчас.

### Р3. Порог авто-Issue → AdminSetting + понизить барьер для живой речи — **+5–7%**
**Что:** вынести `AUTO_ACCEPT_CONFIDENCE_THRESHOLD=0.92` из static const в `AdminSetting autoIssueThreshold` (по правилу «крутилки в AdminSetting», с history+audit). Снизить дефолт до ~0.65 ИЛИ двухступенчато: ≥0.65 + source=meeting + найден suggestedAssigneeId → авто-Issue с пометкой «черновик, подтвердите исполнителя»; ниже → IntakeIssue. Убрать из промпта триажа жёсткое «≥0.92 только если ВСЕ поля найдены», добавить ASR-ноту.
**Почему лучшее:** доказано — реальные уверенности 35–75% против порога 0.92 = 100% задач застряли. Альтернатива «просто снизить const» хуже: нарушает правило «крутилки в AdminSetting» и не даёт настроить per-Org. Лестница доверия curation (provisional) — уже есть инфраструктура.
**Эффект:** разблокирует мёртвый триаж — память доходит до действия (Issue в трекере).

### Р4. Специалистам слоя 3 — trace-логи по `mtg_<id>` + петля верификации графа — **+3–4% (фундамент)**
**Что:** во все 14 специалистов добавить `LogService` с `traceId='mtg_<meetingId>'` на ветках extracted/skipped(reason)/created(entityId)/merged. Поверх — петля: после встречи проверять, что для встреч с decision/idea/commitment-блоками реально появились записи (а не только dispatched), иначе алерт. Прогнать golden-харнесс на реальных транскриптах.
**Почему лучшее:** доказано — Решения=0 и Идеи=0 при «контракте, принуждающем к карточке» означают, что специалисты **вообще не вызываются** (проблема классификации signalType/роутинга), а не «вызываются и молчат». Но без trace-логов это нельзя подтвердить — мы измеряем вслепую. Это **предусловие** для проверки Р1–Р3.
**Эффект:** впервые можно ИЗМЕРИТЬ полноту памяти и ловить тихие skip/fail.

### Р5. Word-timings Vox + стабильность арбитра графа — **+1–2%**
**Что:** мини-e2e к Vox: включить `diarizationEnabled` / выбрать ASR-модель с word-level timestamps (через switchable ENV). Если endpoint их не отдаёт — считать поведение на уровне turn/segment, либо честно пометить недоступным (UI уже честен). Параллельно: flash 8× отдал битый JSON арбитру — включить forced `tool_choice` (флаг есть) или перевести арбитр на capable-модель (fallback удваивает стоимость/латентность графа).
**Почему лучшее:** доказано WARN `vox.no_words` + 8× fallback в trace. Меньший вклад в полноту текстовой памяти, но оживляет «поведение участников» и удешевляет граф.

### Р6. Консолидировать summary в meeting-report-fast, убрать отдельный summary-агент — экономия + конец дубля
**Идея владельца (подтверждена картированием 4 субагентов):** summary не нужен отдельным LLM-вызовом — умная модель `meeting-report-fast` уже делает его последней секцией (`summary_markdown` → `AiResult.summaryFast`). Отдельный summary-агент (`analyze.worker.ts:213-225`, через MiniMax → `AiResult.summary`) — legacy-дубль: 0% кэша + видимый «дубль двух сводок».
**Что (2 шага, доказательно безопасно):**
- **Шаг 1 (переключить чтение, summary-агент ещё жив — ничего не ломается):** все прямые потребители `AiResult.summary` → на `summaryFast ?? summaryV2 ?? summary` (единый helper; на фронте он уже есть — `pickPrimarySummary`, `frontend/src/domain/ai-result.ts:112`). Это сразу убирает видимый дубль.
- **Шаг 2 (отключить за флагом):** убрать `runSummary` из `analyze.worker` (сам worker остаётся — он пишет `structuredData`/`report-by-type`/`followUpEmail`). `−1` LLM-вызов на встречу, уходит некэшируемый MiniMax.

**Полный список «кого переключить» (читают ТОЛЬКО `summary`, в обход селектора):**

| Потребитель | Файл | Эффект при пустом summary |

| **card-rollup (обзор карточки/память)** | `card-rollup.service.ts:62-72` | **критично:** все встречи отфильтруются → `summaryCache=null`, обзор карточки пустеет |
| Превью журнала встреч (**причина видимого дубля**) | `MeetingsJournalReal.tsx:967` | журнал показывает legacy summary, а страница — summaryFast → две разные сводки |
| Экспорт MD/DOCX | `md.generator.ts:39`, `docx.generator.ts:49` | пропадает секция «## Summary» |

| Публичный API v1 | `meetings.public.controller.ts:84` | внешние клиенты получают '' |

**Граф знаний НЕ пострадает (доказано):** `meeting.adapter.ts:64-152` кладёт в RawEvent только `transcript.turns` + метаданные, summary в граф не попадает; block-ingest/SegmentBuilder читают только turns. Дашборды/уведомления/дайджесты/follow-up — тоже не читают summary.
**Почему это лучшее (vs альтернатива «писать текст и в summary тоже»):** дублировать в два поля — оставить неясность «какое каноническое» и держать card-rollup на legacy. Один источник истины (`summaryFast`) + единый селектор чище и обратимо (флаг). Заодно решается судьба `summaryV2` (помечен «удалить после A/B»).
**Эффект:** −1 вызов/встречу, конец расхождения сводок, единый источник. Совместимо с Р2 (один путь задач) — это та же консолидация.

## 3. Сквозные (классовые) проблемы промптов — чинить КЛАСС, не кейс

Аудит 22 промптов показал, что слабости **повторяются** почти у всех — значит правильно чинить общими хелперами (по правилу «фикси весь класс»), а не пер-промпт. Это самый дешёвый рычаг качества по всей памяти сразу.

| # | Класс-проблема | Где | Лучшее решение (доказательство) |
|---|---|---|---|
| C1 | **Нет ASR-ноты у специалистов** — едят сырой транскрипт, числа/имена искажены | decision/idea/insight/regulation/process/skill/goal/block-ingest/table-extract — НЕ применён `withAsrNote` | Применить существующий хелпер `withAsrNote` ко ВСЕМ извлекающим промптам. Cache-safe (стабильная константа). Доказано: только summary/report через analyze.worker его имеют, специалисты — нет |
| C2 | **`EDGE_CASE_POLICY` ссылается на `meetingDateIso`, которого USER не передаёт** — мёртвая ветка | decision/idea/regulation/process/skill/goal-extract | Либо передавать `meetingDateIso` в USER-шаблон (cache-safe — переменная в конце), либо убрать мёртвое правило. Это реальный баг: правило ISO-нормализации сроков не работает |
| C3 | **Контракт принуждает к карточке** (нет булева гейта) — `statement minLength 5`, нельзя вернуть «пусто» | decision/idea/regulation/insight | Добавить булев гейт `isDecision/isIdea/hasSignal` + разрешить пустой результат. Анти-плодёж |
| C4 | **Нет few-shot** у 16 из 22 | большинство | Добавить 1–3 статичных few-shot в SYSTEM (cache-safe). Самый дешёвый рычаг для extraction/классификации enum |
| C5 | **Confidence без калибровки** — нет якорей шкалы 0.3/0.6/0.9 | meeting-report-fast, summary, tasks, chapters, theme, entity-merge, block-distill, ... | Единая шкала-якорь в SYSTEM (как в block-ingest/decision) |
| C6 | **Анти-галлюцинация участников** — имена «как звучат», без сверки со списком | meeting-report-fast, tasks, block-ingest, specialists-combined | Правило «имя ТОЛЬКО из переданного списка участников, иначе null» + передавать список в USER |
| C7 | **Injection-guard рассинхронизирован/не подключён** — маркеры `<<<USER_DATA>>>` в SYSTEM, но USER не оборачивается | table-extract-rows, decision/idea/regulation/process/goal | Синхронизировать обёртку USER с маркерами SYSTEM (или убрать рассинхрон) |
| C8 | **Расхождение SYSTEM↔контракт** | entity-merge-arbiter («до 5 кандидатов», а шлётся 1 пара); specialists-combined (`tool_choice='required'` не поддержан thinking-моделью) | Привести текст SYSTEM в соответствие реальному коду |

## 7а. Синтетический прогон (golden-харнесс) — Часть 3

Создана синтетическая фикстура «Стратегия роста — воронка продаж и найм» в двух вариантах (для теста устойчивости к ASR — находка C1):
- `backend/scripts/fixtures/agent-golden/growth-funnel.clean.json` — чистый транскрипт;
- `backend/scripts/fixtures/agent-golden/growth-funnel.asr_garbled.json` — тот же разговор с искажениями распознавания (числа словами, «срм»=CRM, «варонка»=воронка, «Игор»=Игорь), эталон тот же.

Эталон (golden): 5 задач (5000 рассылок, скрипт продаж, найм продажника, найм техспеца, настройка CRM) + 2 решения (воронка 5000→100→10, еженедельная планёрка). Встреча намеренно содержит и **цель** (10 клиентов / 5 млн ₽), и её **декомпозицию в задачи** — то есть проверяет и извлечение, и будущую связку Р1.

**Как прогнать** (нужен живой backend+воркеры+LLM, НЕ прод):
```bash
cd backend
FIXTURES_GLOB='growth-funnel' bun run scripts/agent-quality-harness.ts
```
Харнесс прогонит обе фикстуры через реальный AI-пайплайн на синтетическом тенанте и напечатает completeness/precision/dupeRate по задачам и решениям, плюс дельту clean↔asr_garbled (просадка на garbled = цена отсутствия ASR-ноты, C1). 

**Ограничение харнесса (доказательство, почему он не заменяет прод-прогон):** `readExtraction` читает только `Task.title` и `structuredData.decisions` — он НЕ покрывает граф, цели, темы, клонов. Поэтому наполнение этих сущностей проверено напрямую на проде (§0), а харнесс оставлен для регрессий извлечения задач/решений.
