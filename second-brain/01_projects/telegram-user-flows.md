# Telegram-бот Z (Кора) — пользовательские сценарии

> **Назначение этого файла.** Описать на простом русском, что сотрудник может делать через нашего общего бота и что пока нельзя. Технические детали (адаптер, прокси, моделей Prisma, метрики) — в [[conversational-channels|conversational-channels.md]]. Этот файл — **карта продукта** со стороны пользователя, чтобы не приходилось каждый раз заново анализировать код.

## 1. Один общий бот на всю платформу — `@kora_bot`

С 25 мая 2026 года все клиенты пользуются **одним нашим общим ботом**. Раньше у каждой компании был свой бот — отказались, потому что плодить ботов под каждого клиента трудоёмко и для пользователя путано.

Технически:
- В базе один объект «канал связи» **без привязки к конкретной компании** (`Channel.tenantId IS NULL`).
- Главный администратор Z настраивает токен бота через админку `/admin/system/telegram-bot`.
- Трафик идёт через посредника `telegram.crossmark.ru`. Телеграм видит только посредника, посредник пересылает сообщения нам. Сделано потому, что серверы Z в Новосибирске — прямой выход в Telegram нестабильный.
- Аварийный откат на прямой Telegram — переменной окружения `TELEGRAM_PROXY_ENABLED=false`.

## 2. Привязка сотрудника к Telegram-боту

«Привязка» — это запись в таблице связок (`ChannelBinding`), которая соединяет идентификатор сотрудника в нашей системе с идентификатором его чата в Telegram. Запись считается активной, когда у неё стоит отметка «подтверждено» (`verifiedAt IS NOT NULL`).

**Основной путь — приглашение от руководителя (в стиле GitHub):**
1. Руководитель в кабинете отправляет приглашение сотруднику.
2. На почту приходит письмо с двумя ссылками: вход в веб-кабинет и вход в бот (`https://t.me/kora_bot?start=<секретный-код>`).
3. Сотрудник кликает по второй ссылке — Telegram открывает бота с командой `/start <код>`.
4. Бот находит код, узнаёт, к какому сотруднику он привязан, и записывает связку «этот чат в Telegram теперь принадлежит этому сотруднику этой компании».
5. Срок жизни приглашения — **14 дней**. Автонапоминания: на 7-й день — сотруднику, на 14-й — руководителю.
6. Если у сотрудника нет почты (линейный персонал) — руководитель копирует ссылку приглашения и пересылает руками в любой мессенджер.

**Второй путь — код из личного кабинета:**
1. Сотрудник в кабинете → раздел «Каналы» (`/me/channels`) → «Получить код» (живёт 10 минут).
2. Шлёт код боту обычным сообщением — бот распознаёт по шаблону `[a-f0-9]{6,32}` и привязывает.

**Что бот проверяет при каждом входящем сообщении:**
1. Достаёт идентификатор отправителя в Telegram (`from.id`).
2. Ищет в базе связку с этим идентификатором + отметкой «подтверждено».
3. Если связки нет → отвечает «Аккаунт не привязан. Получите код в личном кабинете».
4. Если связка есть → по ней находит сотрудника и его членство в компании (`Membership`) → отсюда `tenantId`.
5. Если у сотрудника нет членства ни в одной компании → отвечает «Попросите руководителя выслать ссылку-приглашение».

**Принцип:** один пользователь = одна компания. Защита на уровне сервиса при создании членства.

## 3. Что РАБОТАЕТ через Telegram

### 3.1 Свободные заметки → в память компании

- Любой обычный текст (без вопросительного знака, без слов «как / что / почему / зачем / кто / где / когда / сколько»…) считается заметкой.
- Сообщение сохраняется как «сырое событие» (`RawEvent`) и идёт в общий конвейер знаний: смысловые блоки → сущности → специалисты-агенты разбирают по своим направлениям (решения, регламенты, инсайты, идеи).
- **Голосовое** — бот скачивает аудио, прогоняет через распознаватель речи (Vox), получает текст, дальше как заметка. Лимит — 10 голосовых в час на сотрудника.
- **Документ** (PDF/DOCX/MD/TXT до 20 МБ) — скачивается и подаётся в отдельный конвейер разбора документов. Бот отвечает: «Документ принят. Я разберу его и подключу к знаниям компании».

### 3.2 Утренний дайджест задач — в 9:00 локального времени сотрудника

Cron [`TelegramDigestCron`](../../backend/src/modules/conversational/adapters/telegram-bot/telegram-digest.cron.ts) срабатывает каждый час, для каждого сотрудника проверяет «у тебя сейчас 9 утра по часовому поясу?», и если да — собирает три секции задач из трекера:
- задачи на сегодня (срок — сегодня);
- задачи в работе сейчас;
- просроченные задачи.

Прогоняет через LLM-промпт `telegram-digest-formulate` и шлёт сотруднику «☀️ Доброе утро» с разбивкой. Защита от дублей — на сутки.

### 3.3 Вопрос к AI-чату компании (ChatV2)

Это первый AI-агент Z — отвечает по всей памяти компании.

Конвейер:
1. Сотрудник пишет в бот текст с `?` или с вопросительным словом.
2. Классификатор (`QueryClassifierService`) решает «это вопрос, а не заметка» (LLM + эвристика).
3. Создаётся входящее сообщение типа `chat_query`.
4. `ChatV2OmnichannelBridge` ловит его и зовёт AI-чат компании: поиск по памяти + синтез ответа с цитатами.
5. Ответ возвращается **тем же каналом, откуда пришёл вопрос** — обратно в Telegram, как обычное текстовое сообщение с припиской «Источников: N».

### 3.4 Уточняющие вопросы агентов и подсказки

Когда какой-нибудь агент-специалист хочет уточнить у сотрудника («Это решение в силе?», «Кто отвечает за этот процесс?») — отправляется «проба» (`probe.question`), которая по умолчанию идёт первым делом **в Telegram** (max_bot и in-app — запасные).

Сотрудник отвечает через **Reply** на сообщение бота. Бот сопоставляет ответ с открытой пробой по идентификатору сообщения и помечает её как отвеченную.

Также через Telegram приходят:
- `chat.answer` — ответы AI-чата (см. 3.3);
- `proactive.notification` — инициативные сообщения «я заметил X» от ProactiveWatcher;
- `issue.mention` — вас упомянули в комментарии к задаче;
- `event.reminder` — напоминания о событиях календаря.

### 3.5 Управление задачами

**Гейт намерения (ТЗ §2, 2026-06-10):** входящее сообщение СНАЧАЛА классифицируется (`QueryClassifierService`, `dialog-classify`), и только потом маршрутизируется. Раньше «бот для задач» (`TelegramBotMessageHandler.tryHandle`) перехватывал ЛЮБОЙ непустой ввод и делал из него задачу — план дня и вопросы ошибочно становились задачами. Теперь:
- классификатор различает 9 намерений, включая `task` (поставить задачу) и `show_tasks` (показать мои задачи);
- `tryHandleStructural` обрабатывает ДО классификации только **структурные спецслучаи** — reply на уведомление о задаче и forward;
- остальное решает классификатор: `task`→создание задачи (`handleCreateTask`), `show_tasks`→читалка списка (`handleShowTasks`), `daily_plan_morning`/`daily_report_evening`→чек-ин, вопросы→AI-чат, прочее→заметка;
- confidence-gate: `task`<0.7 → заметка, `show_tasks`<0.7 → вопрос (чтобы не плодить ложные задачи).

Помимо утреннего дайджеста (3.2):
- Свободный текст вида «создай задачу: переслать клиенту коммерческое до пятницы» (intent=`task`) — парсится как создание задачи (`TelegramBotMessageHandler.handleCreateTask` + `TelegramTaskParserService`), создаётся черновик в трекере (Intake).
- Голосом то же самое — ASR (`handleVoice` адаптера) → классификация → тот же маршрут.
- «Какие у меня задачи?» (intent=`show_tasks`) — текстовый список открытых задач из трекера (`handleShowTasks` → `IssuesService.listOpenForAssignee`), zero-button, без создания задачи.
- Forward (пересылка) сообщения боту — создаёт задачу.
- Reply на уведомление бота о задаче — становится комментарием, сменой статуса или подзадачей (в зависимости от классификации).

### 3.6 Команда `/login` — вход в веб-кабинет

`/login` — единственная (помимо `/start <код>`) разрешённая команда. Бот выпускает временную magic-link для входа в веб-кабинет (живёт 15 минут). Удобно сотрудникам без почты: достаточно бота, чтобы попасть в кабинет.

## 4. Что НЕ РАБОТАЕТ через Telegram

### 4.1 Утренние и вечерние чек-ины — ✅ доставляются в Telegram (Задача 1 закрыта)

В системе есть [`DailyCheckInPromptCron`](../../backend/src/modules/operations/workers/daily-checkin-prompt.cron.ts), который каждый час проверяет, у кого сейчас 9:00 (утренний чек-ин) или 18:00 (вечерний), и спрашивает «как день / какие планы». Раньше событие `checkin.prompt` не было указано в карте маршрутизации `EVENT_TYPE_CHANNEL_POLICY` и уходило только в веб-кабинет (in-app). Теперь строка добавлена: `'checkin.prompt': ['telegram_bot', 'max_bot', 'in_app']` ([`conversational.service.ts:157`](../../backend/src/modules/conversational/conversational.service.ts#L157)) — бот-каналы приоритетны, in-app fallback. Чек-ин-prompt доходит до Telegram.

### 4.2 Спросить клона роли через Telegram — пока нельзя (Concierge подключён, но clone-инструмент не в канальном whitelist)

Concierge как обработчик уже подключён (2026-06-12, **Задача 2 закрыта**): входящие свободные сообщения из бота (вопросы и задачи) уходят типом `assistant_turn` → [`AssistantChannelBridge`](../../backend/src/modules/concierge/services/assistant-channel.bridge.ts) → `ConciergeService.process`, который сам решает, какой инструмент позвать (AI-чат компании, создание события/встречи, постановка/чтение задач, поиск свободного слота). Маршрутизация за kill-switch `ASSISTANT_CHANNEL_ROUTING_ENABLED` (default true).

Но **именно клон роли через бот пока недоступен**: инструмент `ask_role_clone` (`POST /api/v1/clones/roles/:roleId/ask`) зарегистрирован в реестре Concierge, однако НЕ входит в канальные whitelist'ы (`CHANNEL_TOOL_WHITELIST_SELF` / `CHANNEL_TOOL_WHITELIST_MANAGER` в [`assistant-channel.bridge.ts`](../../backend/src/modules/concierge/services/assistant-channel.bridge.ts)) — значит провайдер его в канале не видит и не вызовет. Чтобы «спросить клон должности» работало из Telegram, нужно добавить `ask_role_clone` (и при желании `list_clones`) в канальный whitelist. Это **открытый пункт Задачи 2**.

### 4.3 Личная «память моего клона» концептуально не существует

С 25 мая 2026 года решено: клоны делаются **по должности, а не по сотруднику** («Клон Маркетолога версия 2», «Клон CFO версия 3»). Сотрудник не видит «своего» клона.

Заметки сотрудника через Telegram **не идут в «его клон»** (его нет), а попадают в общую память компании и оттуда — в карту знаний должности, если сотрудник на этой должности работает. Это работает, просто называется иначе. См. [[skill-and-clone]].

### 4.4 Бот отвечает только текстом (по дизайну)

Голосовой ввод есть (распознавалка речи), голосового вывода нет. Никаких «🔊 Послушать ответ». Это сознательное продуктовое решение (см. memory `feedback_concierge_text_only_output`).

## 7. Открытые задачи

См. [`plans/`](../../plans/) — будут оформлены отдельными ТЗ:

1. **Чек-ины в Telegram** — ✅ **Реализовано 2026-06-12.** `checkin.prompt` добавлен в карту маршрутизации (`'checkin.prompt': ['telegram_bot', 'max_bot', 'in_app']`, [`conversational.service.ts:157`](../../backend/src/modules/conversational/conversational.service.ts#L157)): утром в 9:00 бот спрашивает «планы на день», вечером в 18:00 — «как прошёл день»; ответ обрабатывает `CheckinResponseHandler` и сохраняет в `DailyCheckIn`.
2. **Concierge как обработчик свободных сообщений из Telegram** — ✅ **Реализовано 2026-06-12** (Ф5 assistant-channels + channels-sync). Входящие вопросы и задачи из бота идут типом `assistant_turn` → `AssistantChannelBridge` → `ConciergeService.process`; помощник сам вызывает AI-чат компании, создаёт события/встречи, ставит/читает задачи, ищет свободный слот. **Открытый пункт:** клон роли пока недоступен из бота — `ask_role_clone` зарегистрирован в реестре Concierge, но не добавлен в канальные whitelist'ы (`CHANNEL_TOOL_WHITELIST_SELF` / `_MANAGER` в [`assistant-channel.bridge.ts`](../../backend/src/modules/concierge/services/assistant-channel.bridge.ts)), поэтому в канале не вызывается. Нужно добавить `ask_role_clone` (и опц. `list_clones`) в whitelist.
3. **Утренний план и вечерний отчёт как структурированный тип запроса** — ✅ **Реализовано 2026-05-30**. ТЗ: [`plans/tz/2026-05-29-telegram-self-initiated-checkins.md`](../../plans/tz/2026-05-29-telegram-self-initiated-checkins.md) (ревизия 3 — LLM primary). Расширили `QueryClassifierService.classify` на 3 новые intent (`daily_plan_morning`, `daily_report_evening`, `note`) + параметр `skipHeuristicFirstPass=true` для bot-flow. SYSTEM-промпт `DIALOG_CLASSIFY_SYSTEM_PROMPT` зафиксирован (см. Приложение А ТЗ) — НЕ править без явного согласования владельцем, ломает prompt cache deepseek-v4-flash. Маппинг в `TelegramBotChannelAdapter.classifyIntent`: confidence-gate ≥0.7 для plan/report → `InboundMessage{type='daily_checkin_self', kind}`; иначе fall through в `free_note`. Подписчик в `CheckinResponseHandler.onModuleInit` (`conversational.subscribeInbound('daily_checkin_self', ...)`) → `processSelfInitiated()` парсит, upsert'ит `DailyCheckIn{source='self_initiated'}` (всегда, даже при низкой parser confidence — curatorReview=true), закрывает pending `checkin.prompt` notification через `markAsAnsweredByCheckin` (без эмиссии event'а, чтобы не зациклить), отправляет `checkin.ack` подтверждение по originChannelBindingId (4 шаблона `formatCheckinAck`). Fallback-эвристика (5+5 триггеров в `dialog-layer/services/checkin-fallback-triggers.ts`) — только при недоступности LLM. Новое поле `DailyCheckIn.source ∈ {cron_prompted, self_initiated, manual}` (default `cron_prompted`) + patch-скрипт `patch-daily-checkin-backfill-source.ts` (manual для записей без notificationId). Frontend `/me/check-ins` — значок 🌅/✋/🖊 рядом с датой. Метрики: `z_bot_checkin_intent_classifier_total{kind, source}`, `z_bot_daily_checkin_self_total{kind, outcome}`. SMOKE — 8 сценариев в `backend/src/modules/conversational/adapters/telegram-bot/SMOKE.md`.
