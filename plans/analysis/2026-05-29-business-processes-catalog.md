# Каталог бизнес-процессов платформы Z

## 0. Зачем этот документ

Платформа Z за полгода обросла десятками сквозных потоков: видеовстреча → транскрибация → клон сотрудника → отчёт COO; сообщение в Telegram → агенты → граф знаний; кнопка в трекере → задача → активити → знания. Сейчас всё это **описано фрагментарно**: модули в `02_architecture/module-map.md`, очереди в `01_projects/workers-queues.md`, агенты в `01_projects/ai-jobs.md`, страницы в `frontend-pages.md`. Это **атомарный справочник по кирпичикам**.

Чего нет — **горизонтального среза**: «как из факта `встреча закончилась` получается факт `у компании в графе знаний появилось новое решение и обновился клон маркетолога`». Без такого среза:
- Непонятно, реализовано ли всё, что задумано, или часть до сих пор живёт только в ТЗ.
- При баге сложно найти «где сломалось» — приходится поднимать всю карту по памяти.
- Новому человеку (или себе через 3 месяца) непонятно, что платформа реально делает.

**Решение:** новый раздел `second-brain/03_processes/`, каталог сквозных процессов, каждый описан в двух регистрах одновременно — бытовом (для не-программиста) и техническом (с путями к коду).

---

## 1. Принципы каталога

1. **Один файл = один сквозной процесс.** Не один модуль, не один эндпоинт, не один воркер. Процесс — это **цепочка** от триггера до конечного результата.
2. **Два регистра в одном файле.** Сначала простой русский (что и зачем), потом техническая таблица (где, как, какие данные). Регистры **связаны якорями** — шаг N в обоих описаниях говорит об одном и том же.
3. **Каждый шаг помечен статусом** — реализован / частично / только в ТЗ / отменён. Это превращает каталог в инструмент аудита.
4. **Каталог пишется по коду, не по ТЗ.** Если ТЗ и код расходятся — фиксируем расхождение в разделе 8 карточки.
5. **Каталог не дублирует существующие реестры.** На `workers-queues`, `ai-jobs`, `api-layer`, `frontend-pages`, `01_projects/<feature>.md` — только ссылки.
6. **Бытовой раздел — без англицизмов.** Правило `feedback_language_plain_russian` распространяется. Где термин нужен — пояснение в скобках русским.

## 2. Структура раздела

```
second-brain/03_processes/
  index.md                          # реестр всех процессов, одна строка на процесс
  _template.md                      # эталонный шаблон карточки
  meeting-post-processing.md
  telegram-inbox-ingestion.md
  coo-daily-digest.md
  ...
```

Подключение в `second-brain/index.md` — отдельный заголовок `## Процессы` после `## Архитектура`.

## 5. Предварительный список процессов

7 групп, ~27 процессов. Список не финальный — уточняется при первом проходе по коду.

### А. Встречи и медиа
1. **meeting-create-and-invite** — создание встречи и приглашение гостя.
2. **meeting-in-progress** — что происходит во время встречи (медиа, in-room чат, сигналы).
3. **meeting-end-and-recording** — окончание встречи и сохранение записи.
4. **meeting-post-processing** ⭐ — сквозная пост-обработка: транскрибация → отчёт → память.
5. **recording-retention** — очистка записей по TTL тарифа.

### Б. Conversational-каналы (входящие)
6. **telegram-inbox-ingestion** ⭐ — свободная заметка из Telegram-бота.
7. **inapp-free-note-ingestion** — заметка через Concierge внутри платформы.
8. **email-to-task** — IMAP → задача в трекере.

### В. Conversational-каналы (исходящие)
9. **notification-dispatch** — событие → канал по предпочтению → доставка → tracking.
10. **probe-question-flow** — специалист 3-X спросил → доставлено → ответ → обработка.
11. **coo-daily-digest** ⭐ — ежедневный отчёт COO (cron 22:00 UTC).

### Г. Знания (knowledge-core)
12. **raw-event-to-graph** — ingest сырого события в граф (RawEvent → IdeaBlock → Entity → связи).
13. **theme-clustering** — кластеризация тем (cron каждый час).
14. **card-rollup-v2** — карточки клиента/проекта (debounce 60s после изменений в графе).
15. **reframing-cycle** — переоценка слабых связей (cron 3:00).

### Д. Специалисты Слоя 3 (агенты второго мозга)
16. **specialist-3-1-regulations** — регламенты / процессы / политики из встреч.
17. **specialist-3-2-knowledge-clone** — что человек знает.
18. **specialist-3-3-decisions** — реестр решений с supersede.
19. **specialist-3-4-project-customer** — карточки проектов и клиентов.
20. **specialist-3-5-insights** — радар повторяющихся проблем.
21. **specialist-3-6-ideas** — сбор идей сотрудников и клиентов.
22. **specialist-gamma-1-skill-clone** — клон должности (Skill Profile + ExecutablePersona).

### Е. Трекер
23. **issue-lifecycle** — жизнь задачи: создание → переходы → закрытие.
24. **tracker-to-knowledge** — активити трекера → RawEvent → граф знаний.

### Ж. Биллинг и онбординг
25. **signup-and-onboarding-wizard** — регистрация → онбординг → wizard «Знакомство с компанией».
26. **billing-cycle-tochka** — подписка → invoice → webhook → активация.
27. **referral-program** — реферальная программа (slug → beacon → cron 10-го → выплата).

**Звёздочкой ⭐** помечены 3 эталонных процесса для Волны 1.

## 7. Что НЕ в скоупе

- Не пишем нового кода и не правим существующий.
- Не переписываем `workers-queues.md`, `ai-jobs.md`, `api-layer.md`, `frontend-pages.md` — они остаются как атомарный справочник, на них только ссылаемся.
- Не дублируем содержимое `01_projects/<feature>.md` — там описаны **компоненты**, у нас — **сквозные процессы**.
- Не создаём отдельные процесс-документы для процессов, у которых **нет автоматики** (например, «принятие решения на встрече» — это часть бытового рассказа в `meeting-post-processing`, не отдельный процесс).

## 8. Критерии готовности Волны 1

- 3 карточки прочитываются без программиста за 5 минут каждая (раздел 1) и дают полный технический разрез за 10 минут (раздел 5).
- Каждый шаг в разделе 5 проверен по реальному коду (агент читал файлы), а не по ТЗ.
- Владелец говорит «формат подходит, добивай остальные» или «вот эти правки, потом добивай».
