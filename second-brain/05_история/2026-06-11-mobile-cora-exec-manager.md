# Мобильная версия Коры (руководитель/менеджер): исследование → макет → ТЗ

## Что было поставлено
Владелец: спроектировать мобильную версию Коры — минимальный полезный набор для руководителя и для менеджера. Существующие внутренние исследования брать как контекст, но подвергать сомнению, искать свежие доказательства и разбор конкурентов. По ходу владелец уточнил ключевое: суть не в iOS/нативке, а в том, чтобы **доказать по ролям, что критично, а что НЕ критично** на мобиле.

## Как решал (файлы/инструменты)
1. **feature-analyst** → Workflow с 10 суб-агентами (8 исследователей РФ+зарубеж+OSS/техника, 2 независимых red-team), реальный web-поиск (~1.1М токенов). Baseline по коду Z — прямым чтением (vexp-демон офлайн → Grep/Read).
2. Аналитика `plans/analysis/2026-06-11-mobile-cora-exec-manager-value.md` (research-complete): §5 — критично/не критично по ролям с доказательством; §7 платформа; §8 навигация; §9 red-team.
3. HTML-макет `plans/analysis/2026-06-11-mobile-cora-mockup.html` — 3 итерации по фидбеку владельца: (а) экраны руководителя/менеджера → (б) владелец захотел overview-first вместо action-triage → переразложил в «приборную панель» (Вариант A) → (в) нарисовал все 9 экранов (5 руководитель + 4 менеджер).
4. **tz-author** → ТЗ `plans/tz/2026-06-11-mobile-cora-exec-manager.md` (ready-to-implement, 8 фаз). REALITY-CHECK по реальному коду перед написанием.
5. Коммит `661b89cf` (docs, 3 файла) + push в текущую ветку.

## Что вышло
- Доказанный минимум: руководителю критичны «День компании/Обзор» (картина за взгляд) + спросить память + одно действие; менеджеру — «Моё» (позитивная рамка) + чек-ин голосом + спросить. Остальное (полные дашборды, настройка, аналитика, админка, трекер) — desktop-only, не удаляем.
- Платформа: PWA-first + тонкая RuStore-обёртка (vNext); нативка RN отвергнута. Навигация: bottom-tabs, не свайп-карусель. Архитектура: мобайл = тот же web-app, viewport-gate по роли, десктоп не меняем.

## Чему научился (грабли и факты)
1. **Движок утреннего возврата у Z уже построен** — `personal-daily-brief.cron` (per-timezone бриф «Твой день» → web-push через дневной бюджет+тихие часы), контроллер `my-daily-brief.controller.ts` (`GET /api/v1/me/daily-brief`, `POST .../opened`, `/me/knows-who`), модель `PersonalDailyBrief` с `openedAt`/`deliveredAt`, полный `backend/src/modules/push/*`. «Мобильная версия» ≈ фронт-слой + включить VAPID, а не стройка с нуля.
2. **Verified-пробел:** фронт-страницы `/me/daily-brief` НЕТ → push-крон `actionUrl:'/me/daily-brief'` ведёт в никуда (404/редирект). Первая задача реализации.
3. **VAPID-ключи в prod не заданы** → `WebPushSender` no-op (подписки копятся, отправки нет). Фронтовый комментарий в `push.ts` «backend 404 TODO» — устарел (backend есть). Конфликт источников в нашем коде — разрешать в пользу кода.
4. **Урок про fan-out:** я дал research-агентам стартовый тезис «backend push = 404 TODO» (по устаревшему фронт-комментарию), и они дружно повторяли это как «главный gap». Вывод: суб-агентам давать verified-факты, а сам baseline по своему коду снимать ДО фан-аута, не после.
5. **Инстинкты владельца, скорректированные доказательствами:** свайп-карусель между дашбордами (NN/g/Baymard/Runyon: 84% не листают → bottom-tabs); «показать менеджеру где провалился» (surveillance-демотивация → позитивная рамка, провалы приватны); утренний push как единственный крючок (iOS-PWA хрупок → pull-first + контекстный push). Оба red-team дали «weakened» — ядро выжило, правки встроены.
6. `DirectorDashboardDto` уже несёт зоны «Обзора»: `valueStrip`=«Кора за неделю», `goalsPulse`/`goalTree`=«Цель», `requiresAction`/`signals`=«Что мешает/Требует тебя». Роль на фронте — `currentOrgRole` в auth-context.

## Состояние
Аналитика + макет + ТЗ готовы и запушены. Реализация НЕ начата (ждёт «начинай реализацию» → tz-orchestrator). Открытая развилка: порядок волн (рекомендую менеджера первым — бэк брифа готов).
