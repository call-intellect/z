# Помощник: постановка задачи на другого сотрудника + уведомление в бот, и человекочитаемый текст подтверждения

## 0. Контекст (что попросили)

Из тестового диалога с помощником («Настя Окк»), 19.06.2026:

> — Если я ставлю задачу на другого сотрудника, можно сделать так, чтобы ему в боте приходило уведомление, что я поставила задачу?
> — *(помощник)* Подтвердите действие: **create_task (title: Тестирование бота в Telegram (Айназ), description: Поручено Айназ…, dueDate: 2026-06-19)**. Ответьте «да»…

Два запроса владельца:
1. **Уведомление исполнителю.** Когда задача ставится на кого-то — этому человеку должно приходить уведомление в бот.
2. **Текст подтверждения.** В подтверждении торчат английские технические поля (`create_task`, `title:`, `description:`, `dueDate:`). Так быть не должно — текст должен быть красивым, понятным, человеческим.

Задача этого документа: только анализ + решение. Код не меняем; дальше — ТЗ.

## 1. Где это «делается» (карта кода)

Помощник = модуль `concierge`. Поток постановки задачи:

| Звено | Файл | Что делает |
|---|---|---|
| Инструмент `create_task` (схема) | `concierge/services/service-map-generator.service.ts:145` | Описан как «поставить задачу **СЕБЕ** в проект Входящие»; `POST /api/v1/me/tasks` |
| Исполнение инструмента | `concierge/services/tool-router.service.ts:49` | loopback-HTTP к REST-эндпоинту с service-auth |
| Эндпоинт постановки | `tracker/controllers/me-tasks.controller.ts:35` | `createSelfTask`; в описании: «не принимает ни проект, ни **чужого исполнителя** — доступ не расширяется» |
| Запись задачи | `tracker/services/me-tasks.service.ts:50` | **жёстко** `assigneeUserIds: [userId]` (исполнитель = автор) |
| Текст «Подтвердите…/Готово…» | `concierge/services/assistant-channel.bridge.ts:202,372` | оборачивает `preview` в фразу для канала |

## 2. Проблема 1 — уведомление исполнителю. Корень глубже, чем кажется

### 2.1. Сейчас помощник НЕ умеет ставить задачу на другого

`createSelfTask` ставит `assigneeUserIds: [userId]` — исполнителем всегда становится **тот, кто пишет помощнику**. Эндпоинт намеренно не принимает чужого исполнителя (комментарий контроллера: «доступ не расширяется»).

**Следствие из диалога:** «Айназ» в том звонке попала только в **текст** задачи («…(Айназ)», «Поручено Айназ»). Реальный исполнитель в системе — автор (Настя). Система не знает, что задача «для Айназ», → **уведомлять физически некого**.

### 2.2. Уведомления-при-назначении нет нигде, не только в помощнике

Даже в обычном трекере (через интерфейс) при смене исполнителя эмитится событие `issue.assignee_changed` (`tracker-emitter.service.ts:125`), но его слушает **только граф знаний** (knowledge-core ingest). Ни один подписчик не шлёт пуш исполнителю. Значит «уведомление при назначении» — это **новая** функциональность, а не «починить помощник».

### 2.3. Инфраструктура доставки уже есть (3 кирпича готовы)

1. **Назначение на другого.** Сам трекер это умеет: `issues.service.create` принимает `assigneeUserIds`. Ограничение живёт только в self-обёртке `me/tasks`. → Нужен новый эндпоинт/инструмент, принимающий исполнителя.
2. **Доставка в бот.** Примитив `ConversationalService.sendNotification({ recipientUserId, eventType, payload, dataClass })` уже доставляет проактивные сообщения конкретному пользователю в его канал (см. как им пользуется `proactive-watcher.service.ts:613`). Дойдёт до Telegram и MAX.
3. **Красивый рендер в боте.** Уже есть прецедент — `issue.mention` рендерится как «Вас упомянули в задаче …» (`telegram-bot.adapter.ts:1143`). Новый тип `issue.assigned` добавляется по тому же образцу. Для непокрытых типов есть generic-fallback `title`+`body` (`telegram-bot.adapter.ts:1201`) — но для качества лучше отдельный `case`.

### 2.4. Условие доставки

Пуш дойдёт, только если у исполнителя **привязан бот** (`ChannelBinding`). Если бота нет — нужен fallback: уведомление в кабинет («колокольчик»/лента). Это надо заложить в ТЗ.

## 3. Проблема 2 — английские «аббревиатуры» в подтверждении

**Источник.** `buildConfirmPreview` (`concierge.service.ts:568`) берёт первые 3 параметра инструмента и склеивает сырые ключи: `` `${k}: ${v}` `` → `title: …, description: …, dueDate: …`. Плюс имя инструмента ищется в карте русских названий `CONFIRM_TOOL_RU_NAMES` (`concierge.service.ts:86`), где есть только встречи/события/чат — **`create_task` там нет**, поэтому имя осталось техническим.

То есть оба артефакта («Подтвердите действие…» и «Готово…») наследуют один уродливый `preview`.

**Решение — человекочитаемый предпросмотр**, правится централизованно (один источник → симметрично «Подтвердите» и «Готово»):
- добавить пишущие инструменты (`create_task`, будущий `assign_task`, …) в карту русских названий;
- маппить ключи параметров в русские подписи и форматировать значения (дата → «сегодня, 19 июня»; исполнитель → имя, а не id);
- в идеале — для каждого пишущего инструмента отдельный короткий человеческий шаблон фразы.

**Было:**
> Подтвердите действие: create_task (title: …, description: Поручено Айназ…, dueDate: 2026-06-19). Ответьте «да»…

**Станет:**
> Поставлю задачу «Тестирование бота в Telegram», исполнитель — Айназ, срок — сегодня, 19 июня. Выполнить? Ответьте «да» или «нет».

## 4. Решения владельца (зафиксированы 2026-06-20)

| # | Развилка | Решение |
|---|---|---|
| Р1 | Объём | **Полноценно**: реальное назначение на другого + уведомление в бот + чистка текста подтверждения. |
| Р2 | Кому можно ставить на других (RBAC) | **Всем сотрудникам** (любой → любому). В уведомлении видно, КТО поставил. |
| Р3 | Охват уведомления | **Везде**: единый механизм и для интерфейса трекера, и для помощника (через `issue.assignee_changed`). |

## 5. Рекомендованная архитектура для ТЗ

### 5.1. Бэкенд — назначение
- Новый инструмент помощника `assign_task` (или расширить `create_task` параметром «исполнитель»). Рекомендация: **отдельный `assign_task`**, чтобы `create_task` остался простым «себе», а назначение на другого было явным действием с разрешением имени.
- Эндпоинт, принимающий исполнителя (не `me/tasks`): использует `issues.service.create` с `assigneeUserIds`. RBAC по Р2 — `issue:write` (есть у member), исполнитель — любой сотрудник той же Org.
- **Разрешение имени → user.** «Айназ» (свободный текст) → конкретный сотрудник Org. Нужен поиск person/user по имени с обработкой неоднозначности (несколько Айназ / не найдено) — помощник переспрашивает, не угадывает.

### 5.2. Бэкенд — единое уведомление (Р3)
- Новый подписчик на `tracker.event_occurred` типа `issue.assignee_changed`, action `added`: шлёт `sendNotification({ recipientUserId: assigneeUserId, eventType: 'issue.assigned', payload })`.
- Триггерится из ЛЮБОГО источника назначения (UI трекера и помощник эмитят одно и то же событие) → охват «везде» бесплатно.
- Не слать пуш, если `assigneeUserId === actorUserId` (поставил сам себе — спам не нужен).
- Дедуп/идемпотентность: одно назначение = одно уведомление (по issueId+assignee+action).

### 5.3. Канал — рендер `issue.assigned`
- Отдельный `case 'issue.assigned'` в `telegram-bot.adapter.ts` (и в MAX-адаптере) по образцу `issue.mention`:
  «Вам поставили задачу: «{title}». Поставил(а): {actorName}. Срок: {due}.» + ссылка на задачу.
- Зарегистрировать payload-схему в `conversational/types/event-payload.registry.ts`.
- Fallback в кабинет, если у исполнителя нет привязанного бота (§2.4).

### 5.4. Текст подтверждения (Проблема 2)
- Переписать `buildConfirmPreview` на человекочитаемый предпросмотр + расширить `CONFIRM_TOOL_RU_NAMES`.
- Симметрично поправить «Готово: …» (`assistant-channel.bridge.ts:372`).
- Покрыть тестом (`assistant-channel.bridge.spec.ts` / `concierge.service.spec.ts`): в preview нет латиницы-ключей.

## 6. Открытые подвопросы (решить при написании ТЗ)
- **Разрешение имени исполнителя**: точный источник (Person vs Membership), поведение при 0 и при ≥2 совпадениях (переспрос помощника).
- **Привязка канала**: где брать `ChannelBinding` исполнителя; политика при отсутствии бота (только кабинет / e-mail-fallback?).
- **dataClass уведомления** и совместимость с gating-каналом (в памяти: `chat.answer sensitive>internal` уходит в кабинет, не в Telegram). Для `issue.assigned` — `internal`.
- **i18n/копирайт**: финальные строки шаблонов — только русский (правило проекта), даты в человеческом формате с учётом «сегодня/завтра».
- **Анти-спам**: лимит уведомлений при массовом назначении (по образцу `MAX_NOTIFICATIONS_PER_RULE_PER_ORG`).
