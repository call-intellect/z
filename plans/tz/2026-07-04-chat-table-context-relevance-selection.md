# ТЗ — релевантный выбор таблицы в табличной ветке чата «Мастер»

> **Почему draft-needs-owner-approval, а не сразу в работу:** изменение трогает `ChatV2TableContextService.fetchByKeywordTables` — общий путь табличного контекста для ВСЕХ вопросов (блэк-радиус на весь банк 111, не только структурные). Чистая валидация требует полного перепрогона банка + панель судей (шум на 21 вопросе не покажет мелкий сдвиг). По правилу «крупное изменение → ТЗ + подтверждение владельца» — реализуется после «да».

## Проблема (доказано замером + пробой на «Стреле» 2026-07-04)

Умные таблицы Ф4/Ф4.5/Ф4.6 **наполнены** (99 строк на «Стреле»: Идеи 17 / Обещания 43 / Цели 1 / Гипотезы 11 / Риски 27). Но A/B-замер на структурном подмножестве банка (21 вопрос: risks 8 + blockers 7 + goals 6) показал: **с таблицами recall НЕ вырос, а слегка упал** (CORRECT 3/21 = 14.3% против 5/21 = 23.8% graph-only; в пределах шума LLM, но лифта нет).

**Корень (проба `fetchTableContext` по 21 вопросу):**
1. **Перехват не той таблицей.** Для риск/blocker-вопросов («Что горит?», «Что блокирует продажи?») выбирается таблица **«Обещания и обязательства»**, потому что её колонка названа «**Что**» и токен «что» из вопроса матчит имя колонки. В контекст льётся **20 нерелевантных промисов** → синтез деградирует.
2. **«Реестр рисков» не выбирается никогда** для риск/blocker-вопросов: лексический матчер точечный (без морфологии): «риски»≠«рисков», «блокирует»≠«блокер»; в колонках риск-таблицы нет топиковых слов вопроса.
3. **Залив строк:** при совпадении отдаётся до `chat_v2.table_context_max_rows` (20) строк таблицы без ранжирования по релевантности к вопросу.

Итог: `fetchByKeywordTables` (`chat-v2-table-context.service.ts:121-197`) скорит таблицы по пересечению токенов вопроса с `name + description + имена_колонок`, `score>0`, exact-match. Три дефекта: generic-имена колонок перехватывают; нет морфологии; нет row-level релевантности.

## Цель
Табличный контекст выбирает **правильную** таблицу для вопроса и отдаёт **релевантные** строки → recall на структурных вопросах растёт (не падает). Замер: A/B на 21 структурном + перепрогон банка 111 (без деградации broad/fact/expertise).

## Scope / фазы (dependency-ordered)

### Ф1 — Убрать перехват generic-именами колонок
- В `fetchByKeywordTables` haystack скоринга строить из **`name` + `description`** (топиковые), исключив `имена_колонок` из первичного скоринга ИЛИ отфильтровав стоп-набор структурных токенов (`что`, `срок`, `статус`, `описание`, `дата`, `владелец`, `тип`, `имя`, …).
- Порог отбора: `score ≥ 2` ИЛИ относительный (лучший ≥ 2× второго), чтобы 1 случайный токен не выбирал таблицу.
- **Acceptance:** проба — «Обещания» больше НЕ выбирается для q088/q082/q083/q086/q093b; для goals-вопросов выбирается «Цели и метрики».

### Ф2 — Топиковые описания системных таблиц (лексический матч находит нужную)
- Добавить `description` в `SystemTableTemplate` + провижининг + backfill существующих system-таблиц. Описания — с синонимами намерения:
  - Реестр рисков: «риски, угрозы, блокеры, что мешает/блокирует/стопорит, узкие места, барьеры, проблемы, что горит».
  - Обещания: «обещания, обязательства, договорённости, кто что обещал, дедлайны».
  - Цели: «цели, OKR, метрики, целевые показатели, план на квартал, retention».
  - Гипотезы: «гипотезы, эксперименты, что проверяем». Идеи: «идеи, предложения, бэклог».
- **Acceptance:** проба — для risks/blockers-вопросов выбирается «Реестр рисков» (rows>0), не «Обещания».

### Ф3 — Морфология в матчере (или эмбеддинг выбора таблицы)
- Вариант A (дёшево): prefix-stem матч токенов (общий префикс ≥4 символов) → «риски»~«рисков», «блокир*». Вариант B (сильнее, дороже): эмбеддинг вопроса × эмбеддинг(`name+description`) по образцу Ф2 recall-master (`resolveEntityHintsByEmbedding`), top-K по косинусу, порог через `getDynamic`. Начать с A; B — если A не закрывает.
- **Acceptance:** «какие риски» без слова «рисков» матчит «Реестр рисков».

### Ф4 — Row-level релевантность + кап
- В `applyFilterToRows`/после него — ранжировать строки по совпадению с вопросом (лексика/эмбеддинг), отдавать top-N (`getDynamic('chat_v2.table_context_max_rows_per_table', 8)`), не 20 подряд. Не заливать всю таблицу.
- **Acceptance:** для «главные риски» в контекст идут риск-строки про 429/Zoom/базу, а не первые попавшиеся.

### Ф5 — Замер (приёмка)
- Проба выбора (детерминированно, без LLM): нужные таблицы выбираются на 21 вопросе.
- A/B recall (LLM-судья, `scripts/_measure-tables-recall.ts`): с таблицами CORRECT+PARTIAL на структурном подмножестве > graph-only (лифт, не шум).
- Перепрогон банка 111 (`batch-recall-trace.ts`): нет деградации на broad/fact/expertise/meetings.
- **Acceptance:** структурный recall с таблицами > graph-only; банк 111 не просел.

## Границы
- ✅ **Always:** пороги/кап через `getDynamic` + реестр + сид; изменения за kill-switch (уже есть `table.graphsync.enabled` для данных; для чат-ветки — рассмотреть флаг `chat_v2.table_context_enabled`); все запросы с `tenantId`.
- 🚫 **Never:** заливать всю таблицу; выбирать таблицу по generic-имени колонки; хардкод порогов.

## Прод-гейт (важно)
До реализации этого ТЗ **НЕ гонять `backfill-table-graphsync.ts` на проде** (наполнение таблиц активирует табличную ветку чата, которая сейчас деградирует структурные ответы). Данные-фичу (таблицы в UI) можно, но chat-coupling — после фикса. Владельцу: держать прод-выкат Ф4-данных до этого фикса ИЛИ выкатывать вместе.
