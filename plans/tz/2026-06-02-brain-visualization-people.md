# Brain Visualization — мозг компании из людей

## Зачем

После wizard'а у владельца должен быть один «вау»-экран, который:
1. Эмоционально показывает всю компанию целиком (вкладка «Карта» из тезиса 2026-05-22).
2. Собран **из людей**: каждый сотрудник — своя светящаяся доля мозга; яркая = роль наполнена, тусклая = провал.
3. Растёт на глазах: после каждой встречи доли подрастают (анимация), сверху — метрика роста.
4. Позволяет ткнуть в человека → увидеть его карточку-прогресс (клон роли) → попросить подлить недостающее.

Это третье представление того же графа знаний (наряду со смарт-таблицами и деревом «Структура»): **данные одни, меняется только форма показа** — рассинхрона нет.

## Доказательная база (выжимка deep-research 2026-06-02, task w43zz13ov)

**Что подтверждено (high confidence):**
- **Ядро «граф как представление/привязка над данными, не отдельное хранилище» — валидный enterprise-подход.** Microsoft Fabric Ontology авто-генерирует онтологию-граф поверх семантической модели через data bindings, *«integrate data into a semantic layer without copying source data»* — [learn.microsoft.com/fabric/iq/ontology/how-to-bind-data](https://learn.microsoft.com/en-us/fabric/iq/ontology/how-to-bind-data). Прямая валидация выбора Z.
- **Наивный force-directed layout имеет известные failure modes** (нестабильность сходимости, «hairball», *«poor for >few hundred vertices»*) — [mdpi.com/2073-431X/13/8/189](https://www.mdpi.com/2073-431X/13/8/189). ⟶ обязательна серверная кластеризация / агрегация в супер-узлы / прогрессивное раскрытие (Фаза 1).

**Три поправки, заложенные в это ТЗ:**
1. **Метрика-герой = рост, а не процент.** «Мозг заполнен на N%» опасен: потолок недостижим, метрика девальвируется (vanity-metrics, nngroup; backfiring progress bars, irrationallabs). ⟶ герой = **«+K фактов за неделю»**; процент `maturityScore` показываем только per-domain/per-role в drill-down, где он осмыслен. *(Каноничный источник по выбору именно этой метрики не найден — это продуктовое решение, подкреплённое только косвенно. Принято осознанно.)*
2. **«Синхронные представления» ≠ real-time.** У Fabric привязка работает в bind-and-refresh, не мгновенно. ⟶ обновление графа **инкрементальное** (после `meeting.finalized` + по cron), не позиционируем как live-streaming.
3. **3D — не для старта.** Прямого доказательства преимущества 3D для B2B-дашборда нет; риск hairball выше. ⟶ старт на `react-force-graph-2d` (уже в репо), 3D — опциональный тумблер в Фазе 5.

## Фаза 0 — Метрика-герой и снапшоты роста (backend)

### Цель
Считать «+K фактов за неделю» и per-person «налитость», чтобы фронту было из чего рисовать героя и яркость долей-людей.

### Что входит
1. **Расширить `MaturityScorerService`: scope `person`.** Добавить в `MaturityScopeSchema` значение `'person'`. `scopeDetail({scope:'person', id})` возвращает score человека = агрегат `maturityScore` ролей, которые он занимает (через существующую связь Person↔Role; реализатор сверит модель — вероятно `Role.holderPersonId` или join). Если связи нет — fallback на плотность фактов (`IdeaBlockEntity` count для `Entity` человека), нормированную 0..1.
2. **Новая модель `BrainGrowthSnapshot`** (Prisma, `bun run prisma:push` + `prisma:generate`, без `migrate*`):
   ```prisma
   model BrainGrowthSnapshot {
     id          String   @id @default(cuid())
     tenantId    String
     capturedAt  DateTime @default(now())
     factCount   Int      // canonical IdeaBlock + Entity в тенанте
     nodeCount   Int      // узлы графа (люди+отделы+сущности)
     edgeCount   Int      // EntityLink + IdeaBlockLink active
     perScope    Json     // { roleAvg, depAvg, companyScore } снимок maturity
     @@index([tenantId, capturedAt])
   }
   ```
3. **`BrainGrowthService`** (`backend/src/modules/brain/services/` — новый модуль `brain`, либо внутри `company-foundation`, реализатор решит):
   - `captureSnapshot(tenantId)` — считает counts, пишет `BrainGrowthSnapshot`.
   - `getGrowth(tenantId)` → `{ factCount, deltaWeek, deltaDay, companyScore, capturedAt }`, где `deltaWeek` = текущий `factCount` − ближайший снапшот ≥7 дней назад (если нет — `null`, фронт показывает «копим данные»).
4. **Cron `brain-growth-snapshot.cron.ts`** — раз в сутки `captureSnapshot` по всем Org. Регистрация в `apply-prod-deploy.ts` не нужна (cron, не one-off скрипт), но **новый cron → Шаг 12 prod-deploy-log (smoke grep)**.
5. **Endpoint `GET /api/v1/brain/growth`** под `CookieAuthGuard + TenantGuard + @RequireEntitlement('feature.graph')`. Zod-DTO + Swagger.
6. **AdminSetting**: `BRAIN_GROWTH_SNAPSHOT_RETENTION_DAYS` (default 180), `BRAIN_WEAK_NODE_THRESHOLD` (default 0.3).

### Acceptance criteria
- [ ] `MaturityScorerService.scopeDetail({scope:'person'})` возвращает score 0..1 для существующего сотрудника.
- [ ] Cron создаёт `BrainGrowthSnapshot` для каждой Org раз в сутки; повторный прогон в тот же день — не плодит дубли (или допускается, но `getGrowth` берёт по `capturedAt`).
- [ ] `GET /api/v1/brain/growth` возвращает `factCount` и `deltaWeek` (или `null`, если истории <7 дней).
- [ ] Пороги читаются из `AdminSetting` через `TypedConfigService.getDynamic`, не из `process.env`.
- [ ] Unit-тесты: `getGrowth` (есть история / нет истории), `scopeDetail person` (с ролью / без роли → fallback).

### Что НЕ входит
- Сам граф-API (Фаза 1). Снапшот хранит counts, но кластеризацию не делает.

## Фаза 1 — Глобальный граф-API с серверной кластеризацией (backend)

### Цель
Отдать фронту свёрнутый «мозг»: верхний уровень = отделы + крупные роли/люди, яркость по maturity, призрачные узлы для дыр, без hairball.

### Что входит
1. **`BrainGraphService.buildClusteredGraph(tenantId, { expand?: string[] })`**:
   - **Уровень 0 (по умолчанию):** узлы = `Department` (супер-узлы) + `Person`/`Role` верхнего уровня. Рёбра = агрегированные связи между отделами (свёрнутые `EntityLink`/со-участие во встречах).
   - **Раскрытие (`expand: [departmentId]`):** возвращает людей/роли внутри отдела + их прямые связи.
   - Каждый узел: `{ id, kind: 'department'|'person'|'role'|'entity', label, maturity: 0..1, factCount, isGhost: boolean, expandable: boolean }`.
   - **`isGhost = true`** для declared-but-unobserved (V9): unit существует, но `maturity < BRAIN_WEAK_NODE_THRESHOLD` и `factCount == 0`.
   - Лимит узлов на ответ (default 200, как `neighbors` имеет 100) + `truncated`.
2. **Endpoint `GET /api/v1/brain/graph?expand=...`** под тем же гейтом. Zod-DTO + Swagger. Для глубокого drill-down в конкретную сущность фронт переиспользует существующий `/api/v1/knowledge/graph/neighbors`.
3. **Реюз агрегатов**: maturity берём из уже посчитанных `Role.maturityScore` / `Department.completeness` (Фаза 0 их уже поддерживает), не пересчитываем на лету.

### Acceptance criteria
- [ ] `GET /api/v1/brain/graph` без `expand` возвращает ≤ 200 узлов: отделы + крупные люди/роли, с `maturity` и `factCount` на каждом.
- [ ] `expand=[departmentId]` возвращает сотрудников/роли этого отдела.
- [ ] Узлы declared-but-unobserved помечены `isGhost=true`.
- [ ] На тенанте с 50 людьми и 2000 блоков ответ верхнего уровня — ≤ 1.5 сек (95p).
- [ ] `truncated=true` при превышении лимита.
- [ ] Unit/integration: кластеризация (отделы как супер-узлы), ghost-флаг, лимит+truncated.

### Что НЕ входит
- WebSocket realtime (анимация роста — пакетно по refetch после `meeting.finalized`, Фаза 2).
- Таймлайн «как рос по неделям» (Фаза 5).

## Фаза 2 — Секция «Мозг компании»: оболочка + вкладка «Карта» (frontend)

### Цель
Экран `/brain` с переключателем вкладок («Карта» / «Структура») и героем-метрикой сверху. В этой фазе делаем оболочку-табы + наполняем вкладку **«Карта»**: живое облако-граф из людей/отделов, яркость по maturity, анимация подрастания после встреч. Вкладка «Структура» в этой фазе — заглушка «скоро» (наполняется в Фазе 2b).

### Что входит
1. **Маршрут `/brain`** в route-группе `(authenticated)`, гейт `feature.graph`. Server component + client.
2. **Оболочка-табы**: переключатель «Карта» / «Структура» (URL-state `?tab=map|structure`, дефолт `map`). Герой-плашка роста — над табами, общая для обеих вкладок.
3. **Слои** ApiDto → DomainModel → UiModel (skill `frontend-rules`): `src/api/brain.api.ts` → `src/domain/brain.ts` → UI.
4. **Компонент `BrainGraphCanvas`** (вкладка «Карта») — обобщение существующего `ForceGraphCanvas`:
   - Узлы: размер и яркость по `maturity` (V2). Призрачные (`isGhost`) — полупрозрачный контур.
   - Цвет — по `kind` (отдел/человек/сущность), парные токены (V13), не hex поверх status-токенов.
   - Клик по узлу-человеку → drawer карточки (Фаза 3). Клик по отделу → `expand`.
   - Свёрнут по умолчанию (V5); раскрытие по клику.
5. **Герой-плашка** (над табами): «Мозг компании: **+{deltaWeek} фактов за неделю**» из `/api/v1/brain/growth`. Если истории <7 дней — «копим данные о вашей компании».
6. **Анимация роста**: после `meeting.finalized` — фронт делает refetch графа (SWR revalidate по событию/поллингу), новые/подросшие узлы анимируются. **Без отдельного WS** на старте (поправка 2; realtime — Фаза 5).
7. **Легенда**: «ярко = роль наполнена», «тускло = есть провал», «контур = система пока не знает».
8. **Вкладка «Структура» — заглушка** «скоро» (полноценно — Фаза 2b).

### Acceptance criteria
- [ ] `/brain` рендерит оболочку с двумя вкладками; `?tab=` переключает и сохраняется в URL.
- [ ] Вкладка «Карта» рендерит граф отделов/людей; яркость визуально различает налитые и пустые доли.
- [ ] Герой показывает `+K фактов за неделю` (или fallback-текст), виден на обеих вкладках.
- [ ] Призрачные узлы видимы как полупрозрачные контуры.
- [ ] Клик по человеку открывает drawer; клик по отделу раскрывает его людей.
- [ ] Нет `text-white`/сырых hex на status; все строки на русском.
- [ ] После завершения встречи граф обновляется (refetch), подросшие узлы анимируются.
- [ ] `frontend: bun run typecheck && bun run lint && bun run build` зелёные.

## Фаза 2b — Вкладка «Структура» (практика, frontend + backend)

### Цель
Вторая вкладка секции «Мозг компании» — рабочий вид из тезиса 2026-05-22 §5. Сознательно **не второй граф** (в графе не почитаешь и не заполнишь): дерево + панель узла + просмотр процесса + прогресс по доменам. Здесь владелец видит детали и понимает, что заполнять.

### Что входит
1. **Дерево-навигатор** (слева): Компания → Отделы → Люди/Роли → Процессы. Сворачивается/разворачивается. Иерархия — из `Department`/`Role`/`Person` (+ `roles-domain`). **Backend**: `GET /api/v1/brain/structure/tree` (новый, либо расширить `structure.controller.ts`) — отдаёт дерево с `maturity` на каждом узле (реюз посчитанных `Role.maturityScore`/`Department.completeness`).
2. **Панель узла** (справа): при выборе узла — слоты («что заполнено»), дыры («открытые вопросы»), провенанс («из какой встречи факт»), прогресс по узлу. Реюз: `GET /api/v1/maturity` `scopeDetail` (`contributingFactors` уже отдаёт факторы налитости) + `role-profiles` (`RoleProfile.summaryCache` — слоты роли). Кнопка «Попросить подлить» (Фаза 4) — здесь тоже.
3. **Просмотр процесса**: при открытии процесса — блок-схема со стрелками (шаги→шаги) через **React Flow (`@xyflow/react`)**. Данные — из модуля `processes` (`process-template.service.ts`). Перед интеграцией библиотеки — Context7-проверка актуального API `@xyflow/react`.
4. **Панель прогресса по доменам** (постоянно внизу/сбоку): «Маркетинг 70%, Продажи 40%, Производство 15%» — из `FunctionalDomain.completeness` (уже считается `MaturityScorerService`) + счётчики `StructureService.summary`. Здесь процент **осмыслен** (per-domain), в отличие от компании целиком (V3).
5. **Связность с «Картой»**: клик по узлу-человеку на «Карте» → переключение на вкладку «Структура» с выбранным этим узлом (как в тезисе §4 «клик → переход к нему во вкладке Структура»).

### Что НЕ входит
- Редактор процессов (только просмотр блок-схемой; создание/правка — вне scope).
- Inline-ответы на уточняющие вопросы прямо в панели (это Probe-flow, отдельная задача; здесь — только показ дыр + кнопка nudge).

### Acceptance criteria
- [ ] Вкладка «Структура» рендерит дерево Компания→Отделы→Люди/Роли→Процессы, сворачивается/разворачивается.
- [ ] Выбор узла показывает панель: слоты заполнены/пусто + факторы из `maturity scopeDetail`.
- [ ] Открытие процесса рисует блок-схему (React Flow) со стрелками шагов.
- [ ] Панель прогресса по доменам показывает проценты из `FunctionalDomain.completeness`.
- [ ] Клик по человеку на «Карте» открывает «Структуру» на этом узле.
- [ ] `GET /api/v1/brain/structure/tree` под `feature.graph`, tenant-scoped, Zod-DTO + Swagger.
- [ ] Нет `text-white`/сырых hex; всё на русском.
- [ ] `backend: bun run typecheck && lint` + `frontend: bun run typecheck && lint && build` зелёные.
- [ ] Unit: `tree` (иерархия + maturity на узлах); reuse-тесты не дублировать.

### Новая зависимость
- **`@xyflow/react` (React Flow)** для просмотра процессов. Обоснование: тезис явно называет React Flow для блок-схем процессов; своя реализация стрелок/раскладки дороже. Перед добавлением — Context7-проверка версии и согласование (правило «не вводить либы без обоснования»).

## Фаза 3 — Карточка сотрудника (drill-down, frontend)

### Цель
Клик по доле → drawer с аватаром-уровнем, что налито/пусто, и кнопкой действия.

### Что входит
1. **Drawer `PersonBrainCard`** (Sheet справа, как `RowDetail` в смарт-таблицах):
   - **Аватар-уровень** (V7): 5 ступеней по `maturityScore` — «Новичок/Растущий/Опытный/Эксперт/Мастер». Прогресс-кольцо или бар. Позитивная рамка.
   - **«Налито / пусто»**: список из `MaturityScopeDetailDto.contributingFactors` (Полнота описания / Опорные карточки / Probe-отклик — они уже возвращаются `scopeDetail`).
   - **`+K за неделю` по человеку** (если посчитаем per-person delta; иначе — общий рост).
   - Ссылки: «Открыть клон роли» (`clones`), «Пульс» (`persons/[id]/pulse`) — реюз.
2. **Кнопка «Попросить подлить»** — видна owner/admin/manager (RBAC). Дёргает Фазу 4. Текст: «Олег, про твою роль почти ничего нет — расскажи 5 минут?» (финальную формулировку крафтит proactive).

### Acceptance criteria
- [ ] Drawer показывает ступень-уровень и факторы налитости из `/api/v1/maturity` scopeDetail.
- [ ] Метафора — прокачка/уровни, нигде нет «толстый/худой», тон не порицающий (V7).
- [ ] Ссылки на клон роли и пульс работают.
- [ ] Кнопка «Попросить подлить» видна только по RBAC.

### Что НЕ входит
- Сам отправляющий механизм (Фаза 4).

## Фаза 4 — «Попросить подлить» (backend + frontend)

### Цель
По кнопке сотруднику уходит мягкое приглашение рассказать про пробел — через существующий proactive-канал.

### Что входит
1. **`POST /api/v1/brain/nudge`** body `{ personId, scope: 'role'|'department', targetId, gapHint? }`. RBAC: owner/admin/manager.
2. **Внутри** — вызов `ProactiveService` (реюз `proactive-message-craft.service.ts`): крафт сообщения по шаблону «о пробеле в роли X», доставка в Telegram/консьерж сотруднику. **Текст-only** (V10, [[feedback_concierge_text_only_output]]).
3. **Throttle** через `AdminSetting` `BRAIN_NUDGE_MAX_PER_PERSON_PER_WEEK` (default 2) — не спамить одного человека.
4. **Идемпотентность**: повторный nudge по той же (person, target) в окне throttle — no-op + понятный ответ «уже просили на этой неделе».
5. **Промпт-кей** (если крафт через LLM) — cache-friendly (стабильный SYSTEM с правилами тона, переменные данные в конце user; [[feedback_llm_prompts_cache_friendly]]). Или реюз существующего proactive-крафта без нового кея — приоритет реюзу.

### Acceptance criteria
- [ ] `POST /api/v1/brain/nudge` доставляет сообщение через proactive в канал сотрудника.
- [ ] Throttle: >N в неделю на одного человека → 429/понятный отказ.
- [ ] Сообщение — только текст, на русском, тон приглашающий, не порицающий.
- [ ] Unit: throttle, идемпотентность, RBAC-отказ для рядового сотрудника.

### Что НЕ входит
- Автоматический nudge без действия человека (на старте — только по кнопке; авто-режим — отдельная задача, не в этом ТЗ).

## Острые места / Caveats

1. **Hairball на больших тенантах.** Митигация — V5 (серверная кластеризация, свёртка по умолчанию). Не рендерить тысячи raw-узлов. Источник: mdpi 13(8):189.
2. **«Стена позора».** Риск, что слабые доли унизят людей. Митигация — V7 (прокачка, не толщина), V8 (роль, не личность), тон nudge. Реализатор не должен «оптимизировать» формулировки в негатив.
3. **Per-person связь Person↔Role.** Точная модель связи — за реализатором (Фаза 0 шаг 1); если нет прямой — fallback на плотность фактов.
4. **Метрика-герой не доказана источником.** «+K фактов/нед» — продуктовое решение (поправка 1), подкреплено только косвенно (vanity-metrics). Приемлемо; при пилоте проверить, что растёт и мотивирует.
5. **«Факт» = IdeaBlock+Entity** — грубая прокси. Если счётчик скачет неинтуитивно (дедуп блоков уменьшает count) — пересмотреть определение факта в Фазе 0 без изменения API.
