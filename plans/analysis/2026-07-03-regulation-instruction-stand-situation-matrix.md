# Карта ситуаций (360°) — стенд регламентов и инструкций

> Это **линейка покрытия**: перечень всех ситуаций, которые могут возникнуть «на сотнях компаний»,
> сгруппированных по трём агентам конвейера. Каждая ячейка = ситуация/режим отказа + пример + что
> ДОЛЖНО получиться (эталон). Синтетический корпус (`regulation-stand-corpus.json`) наполняется
> покрытием этой карты — каждая ячейка ≥1 сценарий, критические ячейки ≥3.

## Конвейер под тестом (кто за что отвечает)

```
IdeaBlock(signalType ∈ regulation|process_step|policy)
  → [A1 Экстрактор regulation-extract] понять вид + суть + фильтры
  → материализация в таблицу (Regulation/Instruction/Policy/Process+ProcessStep)
  → [A2 Арбитр regulation-dedupe] судьба черновика: new|merge|extension|contradicts
  → [A3 Компилятор structured-document-compiler] собрать/дополнить contentMd (+steps)
  → CardVersion (история) · ConflictItem (противоречие) · deprecated (проигравший при merge)
```

Плюс два пути запуска консолидации, оба тестируем:
- **онлайн** — на каждый новый блок (`consolidateCard` внутри upsert).
- **свод/бэкфилл** — `RegulationConsolidatorService.consolidateTenant` (крон/разовый проход по всему тенанту).

## A1 — ЭКСТРАКТОР (`regulation-extract`): «что это + суть»

### A1.1 Классификация вида (kind) — 5 видов
| Вид | Признак | Пример-эталон |
|---|---|---|
| `regulation` | норматив с порядком действий, ответственными, сроками | «договоры с подрядчиком → юристу, ответ за 3 дня» |
| `instruction` | пошаговое «как сделать X» для **одной** роли, без передачи | «как менеджеру оформить возврат в 1С» |
| `process` | последовательность **сквозь несколько ролей** (передача работы) | «онбординг клиента»: продажи → юрист → внедрение |
| `policy` | правило-принцип + severity (advisory/mandatory/blocking) | «данные клиентов — только серверы РФ [blocking]» |
| `standard` | внешний норматив (ISO и т.п.), на который ссылаемся | «работаем по ISO 9001» |

### A1.2 Границы классификации (где путается — критические ячейки)
- **regulation ↔ policy** — есть пошаговый порядок с ответственными → regulation; принцип без процедуры → policy.
- **instruction ↔ process** — одна роль без передачи → instruction; работа идёт между ролями → process.
- **regulation ↔ instruction** — правило-норматив (что обязательно) vs пошаговое «как сделать».
- **regulation ↔ standard** — наш внутренний норматив vs внешний стандарт-ссылка.
- **process ↔ instruction** — многошаговость ≠ процесс, если исполнитель один.
- **Один kind на норму** — норма, изложенная через таблицу/разделы, не должна расщепляться на несколько видов.

### A1.3 Фильтр «наша норма» (`isOrgNorm=false` → не материализуем)
- чужая практика («как в Google», «у конкурентов», «в больших компаниях»);
- гипотетика («хорошо бы когда-нибудь», «можно было бы», «если бы сделать как…»);
- разовое поручение на эту встречу (не повторяемая практика);
- голое упоминание документа без содержания (existence-сигнал, confidence≈0.5, тело не извлекать).

### A1.4 Чья норма (`ownerCompany`, материализуется только «наша»)
- `наша` → материализуется;
- `клиент` — на продаже/работе с клиентом/партнёрстве/интервью вторая сторона описывает СВОЙ бизнес → не наша;
- `гость` — внешний участник;
- `неизвестно` — по тексту не определить.
- **Ловушка приора:** `ownerCompanyPrior='клиент'` + внешняя встреча → по умолчанию не наша, пока в тексте ЯВНО не сказано «это делаем мы».

### A1.5 Существенность (`isKeepableOrgNorm=false` → не храним)
- `product_demo` — кнопки самого продукта «Кора» («как добавить ярлык», «куда нажать»);
- `trivial_ui` — тривиальное общеизвестное действие;
- `one_off` — разовое, не повторяемое.
- **Ловушка:** «используем инструмент X (Bitrix/1С) в нашей работе» — это НОРМА поверх стороннего сервиса (`isKeepable=true`), не product_demo.

### A1.6 Статус существования (`extractionStatus` → ProcessStatus)
- `существует` → `active`; `нужен`/`обсуждается` → `deprecated` (материализуется, но не активна).

### A1.7 Извлечение структурных полей (fidelity)
- `statement` — суть без домысленных шагов (следить за галлюцинацией деталей в task/commitment-подобных);
- `scope` — `org` | `department:<id>` | `role:<id>` | `project:<id>`;
- `roles` — для instruction исполнитель (одна роль), для process вся цепочка;
- `severity` — только policy (advisory/mandatory/blocking);
- `category` — только regulation/standard;
- `ownerHint` → резолв в `ownerPersonId` (ответственный);
- `processStepHint` — processName/stepName/stepOrder (для шага процесса);
- `evidenceQuote` — дословная опора (≤15-20 слов), точной цитаты нет → null;
- **калибровка confidence** — шаги/роли/сроки → 0.9; голое упоминание → 0.5.

### A1.8 Чистота вывода
- человеческие строки (name/statement/evidenceQuote/ownerHint) — чистый русский, без кодов и латиницы.

### A1.9 Устойчивость к форме входа (одна норма разными словами)
- одна норма, произнесённая по-разному в разных каналах/днях → один и тот же kind + сводимый statement (готовит почву для арбитра).

## A2 — АРБИТР (`regulation-dedupe`): судьба черновика

Исходы схемы: `new` | `merge` | `extension` | `contradicts`. Скрытый пятый рабочий исход — **distinct**
(арбитр вернул `new`/пометил пару distinct, когда кандидат похож, но это другая норма).

### A2.1 `new` — новая запись
- граф пуст, ИЛИ среди кандидатов нет той же нормы (смежная тема, но норма про другое).

### A2.2 `merge` — та же норма другими словами
- «отпуск согласуется за две недели» = «заявление на отпуск не позднее 14 дней» → merge, статьи об одном.
- эталон: карточек по норме остаётся **одна**, проигравшая → `deprecated`.

### A2.3 `extension` — дополнение (аддитивно, старое сохраняется)
- «при сделке > 1 млн договор дополнительно визирует юрист» ПОВЕРХ «договоры подписывает директор» → extension (не отменяет, добавляет условие);
- «релиз после ревью **двух** инженеров и **зелёных** тестов» уточняет «после ревью и тестов» → extension;
- эталон: одна карточка, новая `CardVersion` (`changeReason='extension'`), **старое содержимое сохранено** в истории.

### A2.4 `contradicts` — противоречие (людям)
- «договоры подписывает руководитель проекта» ПРОТИВ «договоры подписывает **только** директор» → contradicts;
- эталон: создан `ConflictItem` (`relationType='contradicts'`, `detectedBy='specialist'`), карточки **не** слиты молча.

### A2.5 distinct — анти-over-merge (самая дорогая ошибка)
- «расходы до 5 тыс — руководитель отдела» vs «командировочные — финотдел по авансовому» → **разные нормы**, не merge;
- «Портал» (проект) vs «Портал» (продукт) — одноимённые, разный охват → distinct;
- эталон: **две** карточки остаются раздельными; пара кэшируется как distinct (не пересуживается).

### A2.6 Асимметрия и ловушки
- **при сомнении → new/extension**, не молчаливый merge/contradicts (цена ошибочного слияния/конфликта выше);
- похожие названия при разном охвате (отдел/документ/роли) → distinct, не merge;
- обновление без противоречия → extension, не contradicts и не merge;
- `targetId` кандидата скопирован **дословно** (иначе исход не применится);
- **кросс-эффект A1→A2:** арбитр ищет кандидатов только того же `kind` → если экстрактор ошибся видом, дубль в другой таблице не найдётся (провал атрибутируем A1, не A2);
- **кандидатная выборка по cosine (0.82 консолидатор / KNN арбитра):** дубль «совсем другими словами» может не попасть в кандидаты → арбитр не вызовется → ложный `new`. Отличать «арбитр ошибся» от «пара не дошла до арбитра».

## A3 — КОМПИЛЯТОР (`structured-document-compiler`): текст документа

Режимы: **СОЗДАНИЕ** (`existingContentMd` пуст) и **ДОПОЛНЕНИЕ** (непустой).

### A3.1 СОЗДАНИЕ — каркас с нуля по шаблону типа
- разные структуры для regulation/process/policy/instruction;
- `changeReason` = «первичная сборка из материала»;
- для `process` — заполняет `steps[]` (синхронизируются с `ProcessStep`).

### A3.2 ДОПОЛНЕНИЕ — слияние без потери старого (ядро «дополнять, дополнять»)
- новый пункт **добавлен**, весь старый текст **сохранён** (главный инвариант — не затирать);
- **не дублировать** пункт, который уже есть в теле;
- **не смешивать** старую и новую редакцию в одну строку;
- рост карточки во времени: A → A' → A'' даёт связную растущую инструкцию, а не свалку.

### A3.3 Сигналы триажа (`signals[]`)
- `type-mismatch` (пришёл черновик не того типа), `no-info`, отметки конфликтов — для кураторов.

### A3.4 Ловушки компилятора
- потеря старого содержимого при дополнении (регресс контента) — **критично**;
- задвоение пункта; смешение редакций; рассинхрон `steps[]` ↔ `ProcessStep`;
- потеря структуры шаблона типа; разрастание/шум без консолидации;
- компилятор **опционален** (`docCompiler?`): выключен → `contentMd = statement` (нет сборки) — стенд обязан включить и зафиксировать флаг.

## СК — сквозные ситуации (весь конвейер, эффекты порядка и масштаба)

- **СК1 Последовательность жизни карточки:** A(create) → A'(merge, тот же смысл) → A''(extension, добавка) → A'''(contradicts) — проверяем рост + историю версий + один ConflictItem.
- **СК2 Версионирование:** каждая операция → `CardVersion`; история полна; откат/диф виден; `changeReason` верный.
- **СК3 Депрекация:** при `merge` проигравшая карточка → `status='deprecated'` (+ ссылка), активной остаётся одна.
- **СК4 Идемпотентность:** повторный прогон того же корпуса ⇒ Δ=0 (нет новых карточек/версий/конфликтов).
- **СК5 Два пути консолидации:** онлайн (per-block) и `consolidateTenant` (свод) дают согласованный результат.
- **СК6 Масштаб/шум (precision под нагрузкой):** десятки близких, но РАЗНЫХ норм не схлопываются в кашу; over-merge не растёт с объёмом.
- **СК7 Резолв ответственного:** `ownerHint` → `ownerPersonId` (нужны посеянные Person/роли).
- **СК8 dataClass:** наследование класса данных на карточку (internal по умолчанию, чувствительные — выше).
- **СК9 human-guard:** карточка с `trustTier='human'` (правил куратор) — консолидатор её НЕ трогает (`skipped_human`).

## 360° — вариативность формы входа (как «пишут» на сотнях компаний)

Каждый сценарий варьируется по осям, чтобы покрыть реальный разброс:

| Ось | Значения |
|---|---|
| **Канал** | планёрка (устно, ASR-шум/оговорки) · чат (кратко, обрывки) · документ (формально) · интервью/онбординг |
| **Регистр** | формальный норматив · разговорное «мы обычно делаем так» |
| **Полнота** | полная норма · обрывок · голое упоминание |
| **Отрасль/тема** | юр-проверка договоров · онбординг клиента · возврат/1С · деплой-релиз · обработка обращений/SLA · отпуска/расходы · безопасность данных (РФ-серверы) · склад-логистика · найм · эскалации · закупки |
| **Язык** | чистый русский · со сленгом/латиницей/названиями систем (Bitrix, 1С, Zoom) |
| **Владелец** | наша · клиент-на-продаже (ловушка ownerCompany) · гость |
