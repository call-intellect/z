# Экспертные клоны — рождение эксперта (кабинет + приём материалов + постройка мозга + продажа доступа)

## Цель

Супер-админ (владелец платформы) может в z-admin создать «эксперта» (например, «Эксперт по маркетингу»), залить в него произвольный контент (ссылки на видео YouTube/Rutube, аудио/видео-файлы, документы, тексты), система автоматически переваривает контент в граф знаний и навыковый профиль эксперта, после чего супер-админ выдаёт конкретной компании платный доступ к этому эксперту.

## Контекст: на что мы опираемся (уже построено)

| Что | Где | Как переиспользуем |
|---|---|---|
| Generic ingest с адаптерами | `backend/src/modules/ingest/` (`ingest.service.ts`, `adapters/*`) | Добавляем новый адаптер `media-url`; для документов/текстов переиспользуем `document`/`text` адаптеры как есть |
| Постройка графа из любого `RawEvent` | `backend/src/modules/knowledge-core/workers/block-ingest.worker.ts` | Без изменений — кабинет эксперта это тот же tenant, граф строится автоматически |
| ASR (распознавание речи) | `backend/src/modules/ai/services/vox.service.ts`, `ai/workers/transcribe.worker.ts` | Переиспользуем для аудиодорожки видео; диаризация — см. развилка Р3 |
| Навыковый профиль + persona | `SkillProfile`, `ExecutablePersona`, воркеры `skill-profile-rebuild`, `executable-persona-build`, сервис `specialist-3-2-knowledge-clone` | Прогоняем по Person-эксперту внутри его кабинета; добавляем `PersonaScope='expert'` |
| Изоляция по компаниям | `tenantId` на всех сущностях (`Source`, `RawEvent`, `IdeaBlock`, `ExecutablePersona`, …) | Кабинет эксперта = отдельный `tenantId` → знания эксперта изолированы «бесплатно» |
| Доступ к клону | `CloneAccessGrant` (per-user, внутри одной Org) | НЕ подходит напрямую (эксперт глобальный, доступ продаётся компании, а не юзеру) → новая модель `ExpertAccessGrant` (per-Org) |
| Python-сайдкар в docker-compose | паттерн узаконен в [document-ingest ТЗ](2026-05-31-document-ingest-universal.md) Д2 | По тому же образцу заводим `media-fetch` микросервис (yt-dlp + ffmpeg) |
| Платформенная админка | `backend/src/modules/admin/platform/*`, фронт — z-admin route group ([ТЗ](2026-05-31-z-admin-standalone-route-group.md)) | Сюда вешаем все super-admin эндпоинты и UI эксперта |

## Принятые решения владельца (2026-06-02)

| # | Решение | Контекст |
|---|---|---|
| Р1 | **Эксперт = системный Org-«кабинет».** На каждого эксперта заводится отдельный служебный Org (`Org.kind='expert_cabinet'`), исключённый из биллинга, обычных списков компаний и пользовательских flow. Весь pipeline переиспользуется один-в-один, изоляция знаний — даром. | Подтверждено в чате |
| Р2 | **Создаёт только супер-админ.** Никакая компания не может создать эксперта. Все эндпоинты — под платформенным super-admin guard. | Подтверждено в чате |
| Р3 | **Доступ продаётся компании (per-Org), не пользователю.** Новая модель `ExpertAccessGrant` (`expertId` + `grantedToOrgId` + `paid` + `expiresAt` + soft-revoke). Внутри компании эксперт доступен всем (политику «кому именно внутри компании» уточним в ТЗ #2). | Подтверждено в чате |
| Р4 | **Знания эксперта изолированы и в граф фактов компании НЕ попадают.** Гарантируется тем, что они физически в другом `tenantId`. Кросс-tenant чтение появляется только в ТЗ #2 и только для ответа. | Подтверждено в чате (без этого ломается ядро продукта) |
| Р5 | **Скачивание видео — отдельный Python-микросервис `media-fetch`** (yt-dlp + ffmpeg), REST-контракт, результат (аудио) кладётся в S3. В `backend/` Python не вводим (правило CLAUDE.md §7). | Паттерн Д2 из document-ingest |
| Р6 | **Постройка «мозга» = существующий механизм навыкового профиля + persona.** Внутри кабинета заводится один `Person` (сам эксперт), на него атрибутируется весь контент, по нему строятся `SkillProfile` (решения + навыки) и `ExecutablePersona` (`scope='expert'`). | Подтверждено («это как сейчас делается») |

## Открытые развилки (закрыть на старте фазы)

- **Р-Диаризация (разделение по говорящим).** Внешнее видео — одна дорожка (на встречах у нас дорожка на участника, здесь так нельзя). Нужно проверить, умеет ли текущий Vox-провайдер диаризацию. Рекомендация: для MVP считать видео эксперта **монологом** (одна целевая дорожка = сам эксперт) и не делать алгоритмическую диаризацию; если в материале явно интервью на двоих — добавить диаризацию в `media-fetch`-сайдкаре (pyannote, Python — допустимо в infra) во второй итерации. **Решить Plan-агентом на Фазе 1.**
- **Р-Хранение мозга для persona.** `ExecutablePersona` сейчас завязана на `SkillProfile` (`profileId`) для scope='person' и на `Role` для scope='role'. Для `scope='expert'` — `scopeRefId = expertId` (или personId эксперта внутри кабинета). **Решить Plan-агентом на Фазе 2** (минимально инвазивно к unique-constraint `@@unique([profileId, scope, scopeRefId, version])`).

## Технические изменения

### База данных (Prisma — только `bun run prisma:push`)

- **Новая модель `Expert`** (глобальная, без привязки к компании-клиенту):
  - `id`, `displayName` (имя эксперта), `specialization` (в чём силён), `avatarUrl?`, `bio?`,
  - `cabinetOrgId` (FK на служебный Org-кабинет, `@unique`),
  - `personId` (FK на Person-эксперта внутри кабинета),
  - `status` (`draft` | `ingesting` | `brain_building` | `ready` | `archived`),
  - `brainBuiltAt?`, `materialsCount`, `createdByUserId` (super-admin), таймстемпы.
- **Новая модель `ExpertAccessGrant`** (продажа доступа компании):
  - `id`, `expertId` (FK), `grantedToOrgId` (FK на компанию-клиента),
  - `paid` (Boolean), `grantedById` (super-admin), `grantedAt`, `expiresAt?`, `revokedAt?`, `revokedBy?`,
  - `@@unique([expertId, grantedToOrgId])`, индексы по `grantedToOrgId` и `revokedAt`.
- **`Org`:** новое поле `kind String @default("company")` (значения `company` | `expert_cabinet`). Все обычные списки/биллинг/онбординг фильтруют `kind='company'`.
- **`PersonaScope` enum:** добавить значение `expert`.
- **`SourceType` enum:** добавить `media_url` (если ещё нет подходящего; иначе переиспользовать `document`/новый из document-ingest ТЗ).
- Бэкфилл: проставить `Org.kind='company'` всем существующим (default это сделает; для надёжности — backfill-скрипт-no-op с логом).

### Backend (NestJS)

- **Новый модуль `experts/`** (`backend/src/modules/experts/`):
  - `ExpertsAdminService` + контроллер под super-admin guard: CRUD эксперта, добавление материалов (ссылки/файлы), статус обработки, ручной запуск постройки мозга.
  - `ExpertProvisioningService`: создание кабинета (`Org.kind='expert_cabinet'`) + `Person`-эксперта + дефолтных `Source`.
- **Новый ingest-адаптер `media-url`** (`ingest/adapters/media-url/`):
  - принимает ссылку или загруженный медиафайл → дёргает `media-fetch` микросервис → получает аудио в S3 → ставит job в `ai.transcribe` → по готовности транскрипта формирует канонический payload (как `meeting.adapter` формирует turns) → `IngestService.ingest({ tenantId: cabinetOrgId, ... })`.
  - идемпотентность по ссылке (как у `meeting.adapter` по meetingId).
- **Постройка мозга** (Фаза 2): после ingest всех материалов — прогон существующих воркеров навыкового профиля/persona по `Person`-эксперту; persona создаётся со `scope='expert'`.
- **`ExpertAccessService`**: выдать/продлить/отозвать `ExpertAccessGrant`; helper `listExpertsForOrg(orgId)` (для ТЗ #2 и для UI компании «доступные эксперты»).
- Все super-admin эндпоинты — через платформенный admin-guard (`modules/admin/platform`).

### Frontend (z-admin route group)

- Страница **«Эксперты»** в z-admin: список, создать, карточка эксперта.
- Карточка: имя/специализация/аватар, блок **«Материалы»** (вставить ссылки списком + загрузить файлы), индикатор обработки (сколько переварено / в очереди / ошибки), статус мозга, кнопка «Пересобрать мозг».
- Страница **«Доступы»**: кому из компаний выдан доступ к эксперту (выдать/продлить/отозвать, платно, срок).
- **Никакого UI потребления эксперта компанией здесь нет** — это ТЗ #2.

### Интеграции / очереди

- **Новый микросервис `infra/media-fetch/`** (Python, docker-compose): REST `POST /fetch {url|fileRef}` → скачивает видео (yt-dlp) → извлекает аудио (ffmpeg) → грузит в S3 → возвращает ключ. Switchable базовый URL через `TypedConfigService`/ENV.
- Параллелизм бесплатный: BullMQ-воркеры (`ai.transcribe`, `core.raw-events`) уже гоняют джобы конкурентно — массовая заливка материалов раскидывается сама.

## Критерии готовности (DoD)

- [ ] Супер-админ создаёт эксперта → автоматически заводится кабинет (`Org.kind='expert_cabinet'`) + Person-эксперт.
- [ ] Кабинет эксперта не появляется в обычных списках компаний, не биллится, не виден в пользовательских flow.
- [ ] Вставка ссылки на видео → видео скачано, аудио извлечено, транскрипт получен, граф знаний кабинета пополнен (`IdeaBlock` появились).
- [ ] Загрузка файла (документ/аудио/видео) → переварен в граф кабинета.
- [ ] Массовая заливка (≥10 материалов) обрабатывается параллельно, не по очереди.
- [ ] После постройки мозга у Person-эксперта есть `SkillProfile` с traits и активная `ExecutablePersona` (`scope='expert'`).
- [ ] Знания эксперта НЕ видны ни в одной реальной компании (проверка изоляции по `tenantId`).
- [ ] Супер-админ выдаёт компании доступ (`ExpertAccessGrant`, платно, срок) → `listExpertsForOrg` возвращает эксперта; отзыв/истечение срока убирает его.
- [ ] Тесты: unit на `ExpertProvisioningService`, `media-url` адаптер (мок микросервиса), `ExpertAccessService` (идемпотентность/revoke/expiry); e2e на «создать эксперта → залить 1 ссылку → дождаться графа».
- [ ] `bun run typecheck` + `bun run lint` зелёные (backend и frontend).
- [ ] Second Brain обновлён: `01_projects/` (новая заметка про экспертов), `02_architecture/module-map.md` (модуль `experts/`), `02_architecture/data-model.md` (новые модели). `docs/operations/prod-deploy-log.md` — Шаг 4 (новые модели + enum), Шаг 1 (новые ENV для `media-fetch`), Шаг 12 (smoke новых очередей/эндпоинтов), и регистрация backfill-скрипта в `apply-prod-deploy.ts`.

## Риски и ограничения

- **Права на контент.** Клонирование чужого YouTube без разрешения — серая правовая зона. Для модели «эксперт = реальный консультант, который согласился» — ок. Зафиксировать согласие эксперта на этапе процесса (юр. вне scope кода, но отметить в UI создания: чекбокс «есть согласие правообладателя»).
- **Диаризация** (см. Р-Диаризация) — для интервью на 2+ голоса MVP-монолог даст шум; помечаем как известное ограничение первой версии.
- **Стоимость ASR** на больших объёмах видео — массовая заливка часов видео = заметный расход на распознавание; добавить квоту/лимит на эксперта (super-admin видит счётчик минут).
- **`media-fetch` и блокировки/капчи** YouTube/Rutube — yt-dlp периодически ломается на изменениях площадок; сайдкар должен версионироваться отдельно и легко обновляться.
- **Unique-constraint `ExecutablePersona`** при `scope='expert'` — закрыть развилкой Р-Хранение мозга до кода, чтобы не ломать существующие person/role персоны.

### Связь с ТЗ #2 (для контекста, не реализуется здесь)

ТЗ #2 «Работа эксперта» построит думающего помощника поверх готового мозга: при вопросе сотрудника компании — мультиагентный pipeline, который читает память **компании-клиента** (её `tenantId`), собирает контекст, прикладывает знания/persona эксперта (кросс-tenant чтение под `ExpertAccessGrant`) и отвечает разбором + рекомендацией.
