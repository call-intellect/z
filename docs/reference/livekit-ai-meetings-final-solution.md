# Финальное решение для разработки AI-встреч на LiveKit

## Решение

Делаем собственный модуль видеовстреч на базе **LiveKit**.

LiveKit используем не как готовый “чужой видеочат”, а как **медиа-движок**.  
Вся бизнес-логика остаётся в нашем SaaS:

- пользователи;
- гости;
- встречи;
- ссылки;
- роли;
- записи;
- типы встреч;
- AI-анализ;
- задачи;
- follow-up;
- календарь;
- тарифные ограничения.

---

## 1. Что делаем в первой версии

### Основной сценарий

Авторизованный пользователь в личном кабинете создаёт встречу.

Система генерирует:

```text
meeting_id
room_name
host_token
guest_link
meeting_type
recording_status
```

Гость получает ссылку и может войти **без регистрации**, указав имя.

Пример:

```text
https://your-service.ru/meet/abc123
```

---

## 2. Ограничение первой версии

Для MVP фиксируем:

```text
1 встреча = до 10 участников
```

Пока не делаем:

- вебинары на 100+ человек;
- большие конференции;
- breakout rooms;
- сложные роли для зрителей;
- отдельный “зал ожидания” в первой версии.

---

## 3. Обязательные функции встречи

В комнате должны быть:

- камера;
- микрофон;
- демонстрация экрана;
- чат;
- список участников;
- вход гостя по ссылке;
- кнопка “начать запись”;
- кнопка “остановить запись”;
- выход из встречи;
- завершение встречи ведущим.

---

## 4. Роли участников

### Host

Авторизованный пользователь, который создал встречу.

Права:

```text
- начать запись
- остановить запись
- выключить микрофон участнику
- удалить участника
- завершить встречу
- видеть итоговый AI-отчёт
- видеть запись встречи
```

### Guest

Гость по ссылке.

Права:

```text
- войти без регистрации
- включить/выключить камеру
- включить/выключить микрофон
- показать экран
- писать в чат
- выйти из встречи
```

---

## 5. Запись встречи

Запись делаем обязательно в двух форматах.

### 5.1. Общая запись встречи

Это обычная запись, которую можно посмотреть после встречи:

```text
видео + общий звук + демонстрация экрана
```

Нужна для человека.

### 5.2. Отдельные аудиодорожки участников

Это критически важно для AI.

Для каждого участника сохраняем отдельный аудиофайл:

```text
participant_id
participant_name
track_id
audio_file_url
started_at
ended_at
```

Зачем:

- точная расшифровка;
- разделение по спикерам;
- понимание, кто что сказал;
- анализ продаж;
- анализ собеседования;
- задачи и договорённости;
- AI-чат по встрече.

Важно: **не полагаться только на общий аудиомикс**. Общий микс хуже для анализа.

---

## 6. Где хранить записи

Записи сохраняем в S3-compatible storage.

Варианты:

- Yandex Object Storage;
- Selectel;
- SberCloud;
- MinIO;
- другое S3-совместимое хранилище.

В базе храним не сам файл, а ссылки и метаданные:

```json
{
  "meeting_id": "123",
  "recording_main_url": "...",
  "audio_tracks": [
    {
      "participant_id": "u1",
      "name": "Сергей",
      "audio_url": "..."
    }
  ]
}
```

## 8. AI-анализ зависит от типа встречи

Главное отличие продукта:  
не просто “саммари встречи”, а **правильный результат под тип встречи**.

### Командная встреча

AI вытаскивает:

```text
- что обсудили
- решения
- задачи
- ответственные
- дедлайны
- блокеры
```

### Планёрка

AI вытаскивает:

```text
- текущие приоритеты
- кто что делает
- новые задачи
- блокеры
- что нужно решить руководителю
- следующая контрольная точка
```

### План / факт по задачам

AI вытаскивает:

```text
- что было запланировано
- что реально сделано
- что не сделано
- причины отклонений
- ответственные
- риски
- следующий план
```

### Проектная встреча

AI вытаскивает:

```text
- договорённости сторон
- зоны ответственности
- сроки
- риски
- открытые вопросы
- следующий шаг
```

### Продажная встреча

AI вытаскивает:

```text
- боль клиента
- интерес
- возражения
- бюджет
- ЛПР
- срочность
- следующий шаг
- follow-up письмо
```

### CustDev / интервью

AI вытаскивает:

```text
- боли
- сценарии использования
- цитаты клиента
- текущие альтернативы
- частотность проблемы
- готовность платить
- инсайты
```

### Партнёрская встреча

AI вытаскивает:

```text
- выгода для нашей стороны
- выгода для партнёра
- модель партнёрства
- совместная механика
- пилот
- риски
- следующий шаг
```

### Собеседование

AI вытаскивает:

```text
- опыт кандидата
- сильные стороны
- слабые стороны
- риски
- мотивация
- соответствие роли
- итоговая оценка
- следующий этап
```

### Customer Success

AI вытаскивает:

```text
- результат клиента
- проблемы
- риск оттока
- возможности апсейла
- что нужно сделать
- следующий контакт
```

## 13. LiveKit Server

Отвечает только за:

```text
- аудио
- видео
- screen share
- подключение участников
- media routing
```

Бизнес-логику туда не кладём.

---

## 14. LiveKit Egress

Отвечает за:

```text
- общую запись встречи
- отдельные аудиотреки участников
- сохранение файлов в S3
```

Egress лучше держать отдельно от LiveKit SFU.

---

## 15. AI Processing

После завершения встречи:

```text
1. Забираем аудиодорожки
2. Делаем транскрибацию
3. Склеиваем диалог по времени
4. Разделяем по спикерам
5. Применяем шаблон анализа по типу встречи
6. Формируем итоговый отчёт
7. Генерируем follow-up
8. Генерируем задачи
9. Сохраняем результат в базу
```

## 18. Мощность серверов

Для старта под модель:

```text
до 10 участников в одной встрече
запись общей встречи
отдельные аудиодорожки
AI-обработка после встречи
```

### Минимальный тестовый вариант

```text
LiveKit SFU: 4 vCPU / 8 GB RAM
Egress: 4 vCPU / 8 GB RAM
Backend + DB + Redis: 4 vCPU / 8 GB RAM
```

### Нормальный public beta

```text
LiveKit SFU: 8 vCPU / 16 GB RAM
Egress: 8–16 vCPU / 16–32 GB RAM
Backend: 4 vCPU / 8 GB RAM
PostgreSQL: 4 vCPU / 8–16 GB RAM
Redis: 2 vCPU / 4 GB RAM
TURN: 4 vCPU / 8 GB RAM
```

### Ориентир по 64 ядрам

Если есть сервер:

```text
64 ядра / 2.4 GHz
```

То для модели с записью и отдельными аудиодорожками можно планировать:

```text
безопасно: 50 одновременных встреч
рабочий ориентир: 80–100 одновременных встреч
после тестов: 120–150 одновременных встреч
рискованно: 200+
```

Для бизнес-плана лучше считать:

```text
64 ядра = около 100 одновременных записываемых встреч до 10 участников
```

---

## 19. Что важно не делать

Не ставить всё на один сервер в production:

```text
LiveKit + Egress + Backend + PostgreSQL + Redis + Storage
```

Почему:

- запись может съесть CPU;
- качество звонков может просесть;
- БД может тормозить;
- сложно масштабировать;
- сложно искать причину проблем.

Правильнее разделять:

```text
LiveKit SFU отдельно
Egress отдельно
TURN отдельно
Backend отдельно
PostgreSQL отдельно
Storage отдельно
```

## 22. Финальное продуктовое позиционирование

Это не просто видеосвязь.

Правильная формулировка:

> **Свой модуль AI-встреч внутри SaaS: видеозвонок, запись, отдельные аудиодорожки, расшифровка и умный отчёт под тип встречи.**

Главная ценность:

> Пользователь не просто провёл встречу, а сразу получил результат: задачи, решения, follow-up, CRM-заметку, риски и следующий шаг.

## 23. Финальное решение

Выбираем:

```text
LiveKit
```

```text
self-hosted
open-source
свой frontend
свой backend
свои роли
свои гостевые ссылки
свои AI-отчёты
свои типы встреч
```

