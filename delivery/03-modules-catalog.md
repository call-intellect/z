# 03 — Каталог 40 модулей

Этот документ — авторитетный справочник по модулям. Каждый модуль идентифицируется кодом `M-NN` (от M-01 до M-40). Запоминать русские названия не обязательно, но в UI они должны использоваться повсеместно (см. [13-glossary.md](13-glossary.md)).

## Формат описания

Каждый модуль описан в одном формате:

- **Назначение** — для чего модуль существует, в одном предложении.
- **Слой** — на каком из 7 слоёв он живёт (или «сквозной»).
- **Вход** — что модуль получает (события из event bus, API-вызовы, расписание).
- **Выход** — что модуль производит (события, записи в БД, API-ответы).
- **Зависимости** — от каких модулей зависит.
- **Внутренняя логика** — ключевые правила и алгоритмы.
- **Контракт API** — публичные endpoint'ы (если есть).
- **Хранилища** — какие таблицы/коллекции/индексы использует.
- **Безопасность** — кто может видеть данные модуля, что чувствительно.
- **Бюджет** — ограничения по латентности, токенам, объёму.
- **Edge cases** — нестандартные ситуации.

Полные SQL-схемы — в [05-data-schema.md](05-data-schema.md). Полная API-спецификация — в [04-api-spec.md](04-api-spec.md).

## M-01 — Источники данных

**Назначение:** реестр всех типов источников, из которых может приходить информация.

**Слой:** 1.

**Это не сервис, а конфигурационная сущность.** Описывает классы источников и привязывается к экземплярам подключений.

**Поддерживаемые классы источников:**

| Класс | Примеры | Активный/Пассивный |
|---|---|---|
| `chat` | Telegram, Slack, MS Teams, Discord | Пассивный (webhook + history) |
| `email` | IMAP / Exchange / Gmail Workspace | Пассивный |
| `crm` | Bitrix24, amoCRM, HubSpot, Salesforce | Активный (poll + webhook) |
| `task_tracker` | Yougile, Kaiten, Bitrix24 Tasks, Jira | Активный (только чтение) |
| `documents` | Google Workspace, MS Office 365, Confluence | Активный (poll) |
| `meetings` | Zoom, Google Meet, Telemost, Контур.Толк | Через запись + транскрипция (M-04) |
| `voice` | Прямая запись голосовой, входящие звонки | M-04 |
| `web_form` | Внутренняя веб-форма «дамп мысли» | Пассивный |
| `tg_bot` | Внутренний бот «второй мозг» | Пассивный |
| `metrics` | Yandex.Metrica, Google Analytics, ClickHouse-витрины | Активный (poll) |
| `erp` | 1С, МойСклад | Активный (poll) |
| `external_signals` | RSS, конкуренты, новости, Telegram-каналы | M-33 |
| `database` | Generic SQL, CSV, Excel | Активный (poll) |

**Хранилища:** `sources`, `source_connections`.

**Безопасность:** конфигурация источников видна только администраторам. Каждый источник несёт `data_class` по умолчанию.

## M-02 — Точка приёма (Ingest)

**Назначение:** единая дверь для всех входящих событий. Идемпотентность, нормализация, запись в Raw Memory.

**Слой:** 1.

**Принцип:** **«одна дверь + AI-разборщик»**. Не делаем 30 разных приёмников по каждому типу. Все входящие нормализуются в один формат `RawEvent` с полями:

```python
class RawEvent:
    id: UUID                            # generated
    idempotency_key: str                # sha256(source_id + external_id + ts)
    source_id: UUID                     # связь с M-01
    source_class: SourceClass           # chat/email/crm/...
    external_id: str                    # ID в источнике
    occurred_at: datetime               # когда произошло в источнике
    received_at: datetime               # когда приняли мы
    author: AuthorRef                   # человек/система-источник
    channel: ChannelRef                 # конкретный канал/папка/проект
    content_type: ContentType           # text/audio/video/file/structured
    content_ref: str                    # ссылка на MinIO или inline для коротких
    metadata: dict                      # source-specific JSONB
    data_class: DataClass               # public/internal/sensitive/private
    visibility_hints: list              # rough hint, finalize в M-20
```

**Вход:**
- Webhooks от внешних систем (Telegram, CRM).
- API endpoint `POST /api/v1/ingest/event`.
- Pull-loop для систем без webhook (через M-40).
- Загрузка файлов через `POST /api/v1/ingest/file` (multipart).
- Голосовая запись через WSS-стрим в WhisperX → fallback на M-04.

**Выход:**
- Запись в `raw_events` (PostgreSQL) и `MinIO/raw/{event_id}` (бинарь).
- Публикация события `ingest.raw.events` в Kafka.
- Idempotent return: если событие уже было, возвращаем тот же `event_id`.

**Зависимости:**
- M-01 для конфигурации источников.
- M-03 для записи.
- M-20 для проставления prelim `data_class`.
- M-40 для активного pull.

**Внутренняя логика:**

1. Принять входящее.
2. Вычислить `idempotency_key`. Если уже есть в `raw_events.idempotency_key` — вернуть существующий `event_id`.
3. Извлечь author/channel из источника, нормализовать (см. таблицу normalizers ниже).
4. Если содержимое > 10 МБ — стримить напрямую в MinIO, не в память.
5. Применить prelim `data_class` по правилам M-20.
6. Записать `raw_events` транзакционно с публикацией Kafka-события (outbox pattern).
7. Вернуть `event_id` клиенту.

**Нормализаторы:**

Каждый `source_class` имеет свой адаптер:
- `chat_normalizers/telegram.py` — конвертирует Telegram update в RawEvent.
- `chat_normalizers/slack.py` — Slack event API.
- `email_normalizers/imap.py` — MIME → RawEvent + attachments.
- ... и так далее.

Адаптеры должны быть pure functions: на вход — raw payload, на выход — RawEvent. Ничего не сохраняют сами.

**Хранилища:** `raw_events`, `MinIO bucket: raw`.

**Безопасность:**
- Любая ingest-операция — аутентифицирована (либо API-ключ источника, либо JWT пользователя).
- Webhook'и проверяют HMAC-подпись, иначе reject 401.
- Голос/видео загружаются по pre-signed MinIO URL, без проксирования через FastAPI.

**Бюджет:**
- p50 обработки: 100 ms (без транскрипции и LLM).
- p99: 500 ms.
- Throughput: 1000 событий/сек на одну ноду.

**Edge cases:**
- Event с occurred_at < now() - 30 дней → допускается, но помечается флагом `historical_backfill`. Влияет на retention и не триггерит уведомления в дашборде.
- Source с retry-storm → rate-limit на уровне source_id (1000 событий/сек).
- File > 1 ГБ → отвергаем синхронно, требуем загрузку через `POST /api/v1/ingest/file/chunked`.

## M-03 — Сырая память (Raw Memory)

**Назначение:** неизменное хранилище первоисточников. Защищает от подмены оригинала интерпретацией.

**Слой:** 2.

**Принцип:** «интерпретация не вытесняет первоисточник». Любой вывод системы должен быть восстановим до набора записей из M-03.

**Вход:** записи из M-02.

**Выход:**
- Чтение по запросу из M-23 (Query Agent) для подтверждения вывода.
- Чтение из M-05 (LLM-анализ).
- API `GET /api/v1/raw-events/{id}` (с проверкой M-20).

**Хранилища:**
- `raw_events` — метаданные.
- `raw_event_bodies` — текстовое содержимое (если короткое).
- `MinIO bucket: raw` — бинарные первоисточники, файлы, аудио, видео.
- Hash-таблица `raw_event_checksums` для проверки целостности.

**Внутренняя логика:**

1. Запись событий иммутабельна: `INSERT ONLY`. Нет `UPDATE`.
2. Каждые 24 часа cron-job пересчитывает SHA-256 от тела и сравнивает с `raw_event_checksums`. Несовпадение → алерт.
3. Удаление поддерживается только через compliance-flow (см. [08-security-privacy.md](08-security-privacy.md)). При удалении создаётся tombstone-запись с причиной и автором.

**Безопасность:**
- Видимость определяется M-20 на уровне строки.
- В audit-log пишется каждое чтение чувствительных записей.

**Бюджет:**
- Хранение: до 1 ТБ на компанию 200 чел / 2 года (90% — аудио/видео).
- Чтение: cache в Valkey для горячих 10% записей.

**Edge cases:**
- Запрос на удаление субъекта данных → каскад: удаляем все RawEvent с этим author/mentioned_person, не позже 30 дней. Экспорт перед удалением — обязателен.
- Раз в год — backup-проверка восстановления полного снапшота на тестовый стенд.

## M-04 — Транскрипция

**Назначение:** превращать аудио и видео в текст с разделением спикеров и опциональным саммари.

**Слой:** 1.

**Вход:** события `ingest.raw.events` с `content_type ∈ {audio, video}`.

**Выход:**
- Текстовая транскрипция, записанная как новый `RawEvent` с `parent_event_id` ссылающимся на исходный.
- События `transcription.completed` для дальнейшего анализа.

**Зависимости:** M-02, M-03, M-27 (для durable workflow), M-38 (для саммари через AI-команду).

**Внутренняя логика:**

1. WhisperX (faster-whisper backbone) с выбором модели по длительности:
   - до 10 мин → `large-v3-turbo`.
   - до 1 часа → `large-v3`.
   - больше → split на сегменты по 30 мин.
2. Pyannote.audio для диаризации (разделение голосов).
3. Сопоставление спикеров с известными людьми (через M-25 «база знаний») — heuristic by speaker_id reuse + LLM-сверка с участниками встречи из календаря.
4. Опционально — саммари встречи через специализированного агента «Аналитик встреч» из M-38.
5. Транскрипция помечается `data_class = audio_inherit` (наследует от исходного аудио).

**Безопасность:**
- Запись транскрибируется только при наличии `consent: true` для всех участников встречи. Источник консента — внешний или явное подтверждение в момент записи.
- Если `consent` не подтверждён — аудио хранится с пометкой `transcription_blocked`, ждёт ручного решения админом.

**Бюджет:**
- Локальная WhisperX large-v3 на A100/RTX 4090 — до 10× real-time. На CPU — до 1× (медленно).
- Минимальный hardware на ноду транскрипции: 1 GPU 24 ГБ или мощный CPU 16+ ядер.
- Latency для встречи 1 час: ≤ 6 минут (на GPU), ≤ 60 минут (CPU).

**Edge cases:**
- Многоязычная встреча → WhisperX переключается между языками автоматически. Метка `multi_language: true` в метаданных.
- Шум/плохое качество → confidence < 0.6 → отметить флагом `quality: low`, не использовать для commitment-extraction (M-37).
- Длинная (5+ часов) запись → split + параллельная транскрипция кусков → объединение.

## M-05 — Первичный AI-анализ

**Назначение:** превращать сырое событие в типизированные сигналы и метаданные первичного понимания.

**Слой:** 3.

**Вход:** события `ingest.raw.events` из Kafka после Raw Memory commit.

**Выход:**
- Записи в `signals` (M-06).
- Поля анализа в `raw_event_analysis`: краткое содержание, упомянутые люди/клиенты/проекты, эмоциональная окраска (positive/negative/neutral/mixed), важность (low/medium/high), уверенность анализа.
- Событие `signals.extracted`.

**Зависимости:** M-03, M-06, M-08 (предложить тему-кандидата), M-38 (через специализированного агента «Аналитик входящего»), M-39, M-20 (выбор LLM по data_class).

**Внутренняя логика:**

1. Берёт RawEvent, читает текст (после транскрипции если был аудио).
2. Если текст > 8000 токенов — chunking по семантическим границам.
3. Вызывает LLM (через M-39 → LiteLLM по политике data_class) с промптом «Аналитик входящего» (см. `prompts/m05-analyzer.md`).
4. LLM возвращает структурированный JSON:

```json
{
  "summary_short": "...",
  "summary_long": "...",
  "signals": [
    {
      "signal_type": "client_pain",
      "text": "...",
      "confidence": 0.85,
      "evidence_offsets": [123, 234],
      "mentioned_persons": ["Алексей Иванов"],
      "mentioned_clients": ["ООО Ромашка"]
    }
  ],
  "emotion": "negative",
  "importance": "high",
  "language": "ru",
  "topics_hint": ["интеграция с Bitrix24", "медленная поддержка"]
}
```

5. Каждый сигнал сохраняется в M-06 с `confirmation = analyzed`.
6. `topics_hint` передаётся M-08 для тематического матчинга.
7. Если confidence < 0.6 — событие помечается для повторной обработки более сильной моделью.

**Безопасность:**
- LLM выбирается по data_class:
  - `public/internal` → политика 1 (внешний LLM по умолчанию).
  - `sensitive/private` → политика 3 (только локальный LLM).
- Если разрешённого LLM нет — событие в очереди `pending_llm_unavailable`.

**Бюджет:**
- Стоимость на событие: до 0.05 ₽ (Claude Haiku) / 0.5 ₽ (Sonnet) / 0 ₽ (локальная Qwen 72B на собственном железе).
- Latency: p50 < 2 сек, p95 < 8 сек.
- Если включена политика 3 (только локальное) — может расти до 30 сек на встречу 1 час.

**Edge cases:**
- Не текст → если содержимое — изображение, использовать vision-модель (gpt-4o, claude-sonnet, gemini-2-pro). Если их нет в политике — попытка OCR через PaddleOCR + анализ извлечённого текста.
- Очень короткое сообщение («ок», «спасибо») → не вытаскиваем сигналы, помечаем `low_information: true`.

## M-06 — Хранилище сигналов

**Назначение:** типизированное хранилище извлечённых сигналов, их связей с первоисточниками и атрибутов.

**Слой:** 3.

**Вход:** записи от M-05.

**Выход:** чтение из M-08 (theme matcher), M-09 (scoring), M-11 (linker).

**Хранилища:**
- `signals` — основная таблица.
- `signal_evidence` — связь с первоисточниками (raw_event_id + offset_start + offset_end).
- `signal_mentions` — упоминания людей/клиентов/проектов.
- `signal_embeddings` — эмбеддинги через pgvector (для быстрого matching в M-08).

**Структура signal:**

```sql
CREATE TABLE signals (
    id UUID PRIMARY KEY,
    signal_type signal_type_enum NOT NULL,
    text TEXT NOT NULL,
    confidence FLOAT NOT NULL,
    importance importance_enum NOT NULL,
    emotion emotion_enum,
    confirmation confirmation_enum NOT NULL DEFAULT 'analyzed',
    confirmation_history JSONB NOT NULL DEFAULT '[]',
    raw_event_id UUID NOT NULL REFERENCES raw_events(id),
    theme_id UUID REFERENCES themes(id),
    data_class data_class_enum NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    -- ...
);
```

**Внутренняя логика:**

1. Insert от M-05 с одновременным расчётом эмбеддинга (через локальный bge-m3).
2. Эмбеддинг кладётся в `signal_embeddings` (pgvector HNSW).
3. Match с темой:
   - K-NN среди существующих тем (top-5 по cosine).
   - Если best similarity > 0.78 → assign theme_id.
   - Иначе → создать candidate theme и пометить для review через M-14.

**Безопасность:**
- Сигнал наследует data_class от raw_event.
- Видимость через M-20 на уровне строки (RLS).

**Edge cases:**
- Один RawEvent может породить несколько сигналов разных типов.
- Если signal_type не из закрытого списка → ошибка валидации, отвергаем insert.

## M-07 — Карта компании

**Назначение:** верхнеуровневая карта из 12 веток (с возможностью кастомизации).

**Слой:** 4.

**Стандартные 12 веток** (применяются по умолчанию для нового тенанта):

1. Стратегия и видение
2. Клиенты и аудитория
3. Продажи и pipeline
4. Маркетинг и позиционирование
5. Продукт
6. Операции и процессы
7. Команда и культура
8. Финансы
9. Технологии и инфраструктура
10. Производство и доставка
11. Партнёрства
12. Юридика и комплаенс

При онбординге компании владелец проходит короткий диалог с AI: «у вас есть собственное производство?», «есть ли международные партнёры?» — и AI настраивает ветки (включает/выключает/добавляет специфические).

**Хранилища:** `branches` — конфигурация веток на тенант.

**Внутренняя логика:**
- Ветки — конфигурируемые сущности с уровнем `confirmation`.
- Темы (M-08) привязываются к одной ветке (главная) и опционально 1-2 побочным.
- Изменение веток — через M-26 (корректировка пользователем) или через AI-предложение от M-14.

**Edge cases:**
- Кастомные ветки могут быть введены владельцем при онбординге через диалог.
- Удаление ветки → нужно либо удалить все привязанные темы, либо переназначить. Диалоговое подтверждение.

## M-08 — Темы

**Назначение:** смысловые единицы среднего уровня. Объединяют сигналы общим смыслом.

**Слой:** 4.

**Вход:** сигналы от M-06, корректировки от M-26.

**Выход:** темы для M-09 (scoring), M-11 (связи), M-23 (выдача в чате), M-24 (дашборд).

**Хранилища:** `themes`, `theme_signals` (M2M), `theme_versions` (snapshot для time-travel).

**Структура:**

```sql
CREATE TABLE themes (
    id UUID PRIMARY KEY,
    title TEXT NOT NULL,
    description TEXT,
    branch_id UUID NOT NULL REFERENCES branches(id),
    secondary_branches UUID[] DEFAULT '{}',
    weight FLOAT NOT NULL DEFAULT 0,
    status theme_status_enum NOT NULL,  -- emerging, active, declining, archived
    confirmation confirmation_enum NOT NULL DEFAULT 'analyzed',
    confirmation_history JSONB NOT NULL DEFAULT '[]',
    embedding vector(1024),  -- средний эмбеддинг сигналов в теме
    created_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL,
    last_signal_at TIMESTAMPTZ,
    -- ...
);
```

**Внутренняя логика:**

1. **Появление темы:**
   - При добавлении сигнала в M-06 ищем подходящую тему (cosine similarity > 0.78 + branch match).
   - Если нет — создаём «emerging» тему с одним сигналом.
   - Через 3 сигнала из ≥2 разных источников → переход в `active`.
2. **Назван темы:** генерируется LLM из топ-5 сигналов темы. Имя в стиле «короткая фраза, понятная без контекста».
3. **Декей и архив:** если тема не получает сигналы > 90 дней → `declining`. Через 180 дней → `archived`.
4. **Слияние/разделение:** делает Reframing Agent (M-14). Любое слияние/разделение создаёт snapshot в `theme_versions`.

**Безопасность:**
- Тема наследует max(`data_class`) среди своих сигналов.
- Скрытие чувствительных тем от ролей с недостаточным доступом — через M-20.

**Edge cases:**
- Дублирование тем («медленная поддержка» и «отвечают долго на тикеты») → ловится M-14 при ночном переосмыслении.
- Тема с 1 сигналом не показывается на дашборде, чтобы не создавать шум. Видна только через прямой запрос.

## M-09 — Оценка важности темы

**Назначение:** считает приоритет темы по 8 факторам, обновляет `themes.weight`.

**Слой:** 4.

**Формула (интерпретируемая):**

```
weight = (
    w_freq * normalize(signal_count_30d) +
    w_div  * source_diversity +
    w_fresh * freshness_score +
    w_goal * goal_alignment +
    w_money * money_impact +
    w_risk * inaction_risk +
    w_conf * avg_signal_confidence +
    w_human * human_confirmed_boost
)
```

Стартовые коэффициенты (`w_*`):
- `w_freq = 0.10` (частота сигналов)
- `w_div  = 0.20` (разнообразие источников — важнее, [DR-002](14-decisions-log.md#dr-002))
- `w_fresh = 0.10` (свежесть)
- `w_goal = 0.20` (связь с активной целью)
- `w_money = 0.15` (финансовый эффект)
- `w_risk = 0.10` (риск бездействия)
- `w_conf = 0.05` (уверенность AI)
- `w_human = 0.10` (boost при подтверждении человеком)

Сумма коэффициентов = 1.0. Коэффициенты конфигурируемые на тенант.

**Каждый компонент** — нормализованное число [0, 1]. Detailed расчёты в `prompts/m09-scoring.md`.

**Запуск:** на каждый append signal в тему + cron каждый час пересчитывает все active темы (incremental).

**Хранилища:** `themes.weight`, `theme_score_components` (для UI «откуда такой вес»).

**Безопасность:** оценка не зависит от роли наблюдателя. Срез по ролям делает M-23 при чтении.

## M-10 — Оценка веса источника

**Назначение:** определяет, насколько сильно один сигнал из этого источника влияет на вес темы.

**Слой:** 4.

**Принцип:** «разнообразие источников важнее частоты». Если 10 сигналов пришли от одного человека, это слабее, чем 10 сигналов от 10 разных.

**Базовые веса источников:**

| Тип источника | Вес |
|---|---|
| Платящий клиент с метрикой (выручка > X) | 1.0 |
| Платящий клиент | 0.8 |
| Лид/потенциальный клиент | 0.5 |
| Сотрудник C-level | 0.7 |
| Сотрудник middle | 0.5 |
| Сотрудник junior | 0.3 |
| Внешний эксперт | 0.4 |
| Метрика (автоматический сигнал) | 0.6 |
| Внешний источник (RSS, конкурент) | 0.3 |
| Анонимный фидбек | 0.2 |

Базовые веса конфигурируются на тенант.

**Diversity bonus:** при подсчёте важности темы (M-09) функция `source_diversity` считается как:

```
source_diversity = log2(unique_sources_count + 1) / log2(total_unique_sources_in_company + 1)
```

То есть 5 разных источников из 50 общих → 0.39, а 50 источников из 50 → 1.0.

**Хранилища:** `source_weights` (тенант-специфичные), `signal_source_weight` (snapshot для повторяемости).

## M-11 — Динамические связи знаний

**Назначение:** **сердце концепции.** Поиск явных и неявных связей между сущностями (сигналы, темы, цели, идеи, риски, решения, люди), создание новых узлов графа, переосмысление.

**Слой:** 5.

**Это критический модуль.** Если он не работает — продукт превращается в «дорогую CRM».

**Технический фундамент:** Graphiti (temporal KG) + FalkorDB (storage) + pgvector (KNN-кандидаты) + cross-encoder (rerank) + LLM-арбитр (тип связи и объяснение). См. [01-architecture.md](01-architecture.md), C4-Level 3.

**Стандартные типы связей:**

- `подтверждает` — A усиливает B
- `противоречит` — A опровергает B
- `мешает` — A препятствует достижению B
- `помогает` — A помогает достижению B
- `вызывает` — A → B (causation)
- `относится_к_цели` — A связано с целью B
- `упоминает_человека` — в A упомянут человек B
- `упоминает_клиента` — в A упомянут клиент B
- `повторяет` — A — другая формулировка того же что в B (для merge candidates)

**Кастомные типы связей** (создаются специализированными детекторами):

- `стратегическое_расхождение` — детектится M-16 (Strategic Alignment).
- `ранний_симптом_риска` — детектится при паттерне «N слабых сигналов одного направления». Алгоритм: clustering сигналов с low confidence + LLM-арбитр «являются ли это симптомами одного риска».
- `новая_сторона_старой_проблемы` — детектится M-14 при reframing (новый сигнал не подходит ни в одну из существующих интерпретаций темы).
- `общий_корень_нескольких_проблем` — детектится M-13 (consolidation): если несколько разных тем имеют пересекающиеся клиенты/процессы — кандидат на «общий корень».

**Алгоритм поиска связей (online):**

1. Триггер: появление нового сигнала / темы / решения.
2. Извлечь эмбеддинг (bge-m3, 1024-dim).
3. KNN-поиск top-50 кандидатов в pgvector среди узлов того же тенанта.
4. Cross-encoder rerank до top-10.
5. Graph traversal по существующему графу: смотрим соседей второго хопа от уже связанных узлов.
6. Для каждого кандидата — LLM-арбитр (Claude Sonnet или эквивалент) решает:
   - есть ли связь?
   - какой тип?
   - объяснение (1-3 фразы)?
   - уверенность?
7. Если confidence > 0.7 — связь записывается с `status = "предложена_AI"`, `confirmation = analyzed`.
8. Если confidence > 0.85 — публикуется событие `links.proposed` для отображения в дашборде.
9. Если confidence ≤ 0.7 — связь отбрасывается, в audit-log.

**Алгоритм переосмысления (offline, ночь):**

Запускается через M-14 (Reframing Agent). Пробегает по существующим связям и:
- Удаляет связи, у которых исходные узлы изменили семантику (через эмбеддинг-drift).
- Помечает `archived` связи, не подтверждённые человеком за 90 дней с confidence < 0.8.
- Ищет новые связи между узлами, обновлёнными за последние 24 часа.

**Хранилища:**
- FalkorDB — основной граф, все рёбра.
- Graphiti — поверх FalkorDB, добавляет временные срезы и provenance.
- PostgreSQL — таблица `link_proposals_log` для audit и review через M-26.

**Безопасность:**
- Связь между двумя узлами наследует `max(data_class)`.
- Видимость через M-20: пользователь видит связь только если видит оба её конца.

**Бюджет:**
- LLM-вызовов на сигнал: 5-10 (один на каждого кандидата после rerank).
- При 1000 сигналов/день: 5-10к LLM-вызовов/день. Стоимость: до 5000 ₽/день при использовании внешних провайдеров, ≈0 при локальных.
- Ночной reframing: дополнительно 100к-500к LLM-вызовов в зависимости от размера графа. Локальные модели обязательны для больших инсталляций.

**Edge cases:**
- Циклы в графе → разрешены, но при traversal ограничиваем глубину 3 хопа.
- Конфликтующие связи (A `подтверждает` B и одновременно `противоречит` B) → допустимо, потому что «отчасти подтверждает по X, а противоречит по Y». Объяснение должно отражать.
- Связь, отклонённая человеком → не предлагается снова в том же виде. Если AI находит её снова через 60+ дней — может предложить с пометкой «возможно, обстоятельства изменились».

## M-12 — Граф сущностей

**Назначение:** хранение всех связей между сущностями.

**Слой:** 5.

**Технология:** FalkorDB + Graphiti.

**Типы узлов:**
- `Signal`
- `Theme`
- `Branch`
- `Goal`
- `Idea`
- `Risk`
- `Decision`
- `Person` (сотрудник)
- `Client`
- `Department`
- `Project`
- `Document`
- `Metric`

**Типы рёбер:** см. M-11.

**Особенности Graphiti:**
- Каждое ребро имеет `valid_from`, `valid_to`. По умолчанию `valid_to = NULL` (актуально).
- Изменение ребра (например, переоценка confidence) создаёт новую версию с `valid_from = now()`, старая получает `valid_to = now()`.
- Time-travel запросы: «как граф выглядел 3 месяца назад» — `MATCH ... WHERE valid_from <= $t AND (valid_to IS NULL OR valid_to > $t)`.

**API внутри M-12:**
- `add_node(entity_type, entity_id, properties)`.
- `add_edge(from, to, relation_type, properties)`.
- `find_neighbors(node, depth, filter)`.
- `find_paths(from, to, max_depth, relation_filter)`.
- `as_of(timestamp)` — снапшот на момент.
- `subgraph(seed_nodes, depth, role_filter)` — для рендера в M-24.

**Хранилища:** FalkorDB, отдельный keyspace на тенант.

**Безопасность:** на чтение применяется RBAC через M-20 (фильтрация рёбер по data_class каждого конца).

## M-13 — Агент консолидации

**Назначение:** фоновый агент, периодически просматривающий новые данные за период и обновляющий веса, находящий повторы, добавляющий связи.

**Слой:** 6.

**Запуск:** каждые 4 часа (cron в Temporal).

**Что делает:**
1. Берёт все RawEvents и Signals за последние 4 часа.
2. Смотрит, не появились ли темы-дубли (cosine similarity > 0.85 → flag for merge).
3. Пересчитывает веса тем (M-09).
4. Ищет паттерны «несколько слабых сигналов одного направления» → создаёт candidate `ранний_симптом_риска`.
5. Публикует summary в `agent.actions` лог.

**Что не делает:**
- Не переписывает тему сам — только ставит флаги. Реальный merge — у M-14.

**Хранилища:** `consolidation_runs` — лог запусков с метриками.

**Бюджет:** один цикл — 5-10 минут на размер 200 чел. LLM-вызовы — 100-500 на цикл.

## M-14 — Агент переосмысления

**Назначение:** ночной агент, переоценивающий структуру тем, формулировок, связей.

**Слой:** 6.

**Запуск:** раз в сутки в 03:00 локального времени тенанта (cron в Temporal).

**Что делает:**

1. **Merge тем-дублей:** берёт candidates из M-13, окончательно сливает.
2. **Split тем:** если в одной теме сигналы образуют 2+ кластера с разной семантикой → split на 2 темы.
3. **Reframing формулировок:** перегенерирует имя темы, если новые сигналы существенно изменили её смысл.
4. **Переоценка старых связей (M-11):** удаляет архивные, проверяет актуальность.
5. **Декей весов:** применяет decay-функцию к темам без новых сигналов.
6. **Публикует daily-digest** для дашборда: «вот что переосмыслили этой ночью».

**Особенность:** пользователь утром видит **видимый эффект ночной работы** — это часть UX «видимая польза» (см. [00-executive-summary.md](00-executive-summary.md), принцип 1).

**Бюджет:** 1-3 часа на размер компании 200 чел. LLM-вызовов: 1-10 тыс. Локальные модели обязательны.

**Edge cases:**
- Если ночной запуск падает → retry через час, дальше — алерт админу.
- При сильном дрейфе (20%+ тем нуждаются в reframing за ночь) → останавливается на пороге, эскалируется человеку через M-26.

## M-16 — Стратегический согласователь

**Назначение:** главный дифференциатор продукта. Постоянно проверяет, движется ли компания к своим целям.

**Слой:** 7.

**Топ-индикатор:** **«Согласованность стратегии»** — число от 0 до 100. Показывается на дашборде самым крупным виджетом.

**Трёхуровневая аналитика:**

1. **Уровень 1 — индикатор «Согласованность стратегии» (0-100).** Композит из 3 субметрик.
2. **Уровень 2 — три субметрики:**
   - **Слаженность голосов** (0-100): насколько единообразно говорят разные роли о стратегии (CMO/CSO/CTO/COO).
   - **Связь действий с целями** (0-100): сколько решений (M-21) и активных тем (M-08) явно связаны с активными целями (M-15).
   - **Скорость дрейфа** (-100..+100): тренд за 30 дней. Положительное = улучшаемся.
3. **Уровень 3 — детализация субметрик:**
   - Разрезы по ролям, отделам, темам, периодам.
   - Каждая аномалия раскрывается до конкретных событий и решений-причин.

**Алгоритм расчёта:**

1. Раз в сутки берём все активные цели (M-15).
2. Для каждой цели находим связанные темы и решения через M-12 (граф) — рёбра `относится_к_цели`.
3. Считаем «слаженность голосов»: для каждой цели берём сигналы за 30 дней с упоминанием её темы, классифицируем по роли автора, считаем дисперсию формулировок (через эмбеддинги).
4. Считаем «связь действий с целями»: % решений за 30 дней, имеющих ребро `относится_к_цели` хотя бы с одной целью.
5. Скорость дрейфа: разность согласованности этой недели и 4 недели назад.
6. Композит: weighted avg субметрик.

**Каждое падение метрики на 10+ пунктов за неделю** триггерит уведомление на дашборде («снижается слаженность по цели X — посмотрите детализацию»).

**Хранилища:** `alignment_snapshots` — ежесуточные снимки.

**Безопасность:** топ-индикатор виден всем, детализация — по ролям.

## M-19 — Настроение команды

**Назначение:** отслеживание эмоционального состояния и нагрузки команды.

**Слой:** 6.

**Этически критичный модуль.** См. [08-security-privacy.md](08-security-privacy.md), раздел «Mood module».

**Двухканальная модель** (см. [DR-007](14-decisions-log.md#dr-007)):

### Канал 1 — пассивные сигналы (cross-source)

Анализирует:
- Тон сообщений в открытых каналах (Slack public, командные чаты).
- Загрузку календаря (% времени в встречах, овертаймы по календарю).
- Velocity в task-tracker / GitHub (если интегрированы).
- Частоту упоминаний выгорания, усталости в открытых обсуждениях.

**Whitelist сигналов** (закрытый список того, что разрешено):
- ✅ Тон публичных сообщений.
- ✅ Время встреч в календаре.
- ✅ Объём commits/PR.
- ✅ Открытые упоминания «устал», «нет сил», «много работы», «выгораю».
- ❌ Личные DM сотрудников.
- ❌ Скрининг писем.
- ❌ Личные документы.
- ❌ Анализ настроения по голосу в личных созвонах.

### Канал 2 — активный чек-ин

Раз в день в чате-боте: 6 коротких вопросов:

1. «Как самочувствие сегодня?» (1-5)
2. «Загрузка адекватна?» (1-5)
3. «Понимаешь, что и зачем делаешь?» (1-5)
4. «Чувствуешь поддержку коллег?» (1-5)
5. «Если что-то блокирует — что именно?» (свободный текст или «всё хорошо»)
6. «Хочешь что-то добавить?» (свободный текст или пропустить)

Только 1 и 2 — обязательные. Остальные — опциональные.

### Двойной opt-in

- **Уровень компании:** владелец/HR должен включить функцию M-19 целиком.
- **Уровень сотрудника:** каждый сотрудник лично подтверждает участие в M-19. Без подтверждения — данные о нём в M-19 не собираются.
- Без обоих opt-in модуль для конкретного сотрудника не работает.

### Анонимизация по умолчанию

- Агрегаты по командам/отделам видны менеджеру и HR.
- Персональные данные (mood, ответы на вопросы) видны только самому сотруднику и анонимно — HR-агрегату.
- В «срезе HR» персональные имена никогда не показываются. Только «5 человек в команде разработки сообщают пониженную поддержку».
- k-anonymity: если в группе < 5 человек — детализация скрывается.

### Детектор тревожных паттернов

- Если у одного сотрудника `mood_self < 3` 5 дней подряд → скрытое уведомление лично ему: «Возможно, стоит поговорить с {выбранный_сотрудником_доверенный_контакт}». Это уведомление **не идёт менеджеру или HR без явного согласия сотрудника**.
- Если у команды агрегат `mood_avg < 3` за неделю → агрегатное уведомление менеджеру (без имён).

**Хранилища:**
- `mood_passive_signals` (агрегатные, без личных привязок).
- `mood_active_responses` (личные, видны только субъекту + анонимный агрегат).
- `mood_aggregates` (по командам/отделам).

**Бюджет:**
- Активный чек-ин — 1 LLM-вызов на ответ, для классификации + сохранения.
- Пассивный анализ — обновление раз в сутки.

## M-20 — Приватность и доступ

**Назначение:** RBAC + Visibility Matrix. Определяет, кто что видит. Сквозной модуль.

**Слой:** сквозной.

**Три измерения ролей** (см. [DR-003](14-decisions-log.md#dr-003)):

1. Функциональная роль (CMO, CSO, COO, CTO, CFO, HR-директор, владелец, member, product-owner).
2. Иерархический уровень (L0 — владелец, L1 — C-level, L2 — руководитель отдела, L3 — тимлид, L4 — рядовой).
3. Кастомизация (свои роли + явные правила).

**Технология:** OpenFGA (primary), Casbin fallback. См. [DR-006](14-decisions-log.md#dr-006).

**Visibility Matrix** — 4 измерения видимости (см. [08-security-privacy.md](08-security-privacy.md)):

1. `source_class` (откуда): public/team/private/sensitive.
2. Роль читающего.
3. `knowledge_type` (что за знание): strategy / customer_voice / internal_ops / mood / financial / legal / hr.
4. `P-attribute` (флаги защиты): pii, salary, legal_privileged, medical, client_nda.

**Применение:**
- На каждый запрос к API → middleware подгружает контекст пользователя (роль + иерархия + custom rules).
- Каждый объект в БД имеет `data_class` и `visibility_tags`.
- Row-level security (PostgreSQL RLS) фильтрует выдачу.
- В графе (M-12) фильтрация рёбер на этапе traversal.

**API:**
- `POST /api/v1/access/check` — boolean проверка для конкретного объекта.
- `POST /api/v1/access/filter` — фильтрация списка объектов.
- `GET /api/v1/access/my-roles` — какие роли у текущего пользователя.

**Хранилища:**
- OpenFGA store на тенанта.
- `users`, `roles`, `role_assignments`, `custom_role_rules`.

## M-21 — Отслеживание решений

**Назначение:** замыкание петли «сигнал → тема → инсайт → рекомендация → решение → действие → результат → память».

**Слой:** 7.

**Структура решения:**

```sql
CREATE TABLE decisions (
    id UUID PRIMARY KEY,
    title TEXT,
    description TEXT,
    rationale TEXT,
    alternatives_considered TEXT,
    consequences_predicted TEXT,
    consequences_actual TEXT,  -- заполняется через 90 дней
    related_signals UUID[],
    related_themes UUID[],
    related_goals UUID[],
    related_ideas UUID[],
    related_risks UUID[],
    decided_by UUID REFERENCES users(id),
    decided_at TIMESTAMPTZ,
    confirmation confirmation_enum,
    confirmation_history JSONB DEFAULT '[]',
    -- ...
);
```

**Формат:** ADR-style. Когда пользователь говорит «мы решили X», AI извлекает Decision и предлагает заполнить разделы (rationale, alternatives, consequences). Не блокирует, если пользователь не хочет.

**Через 90 дней** — AI напоминает (по запросу!), что пора оценить consequences_actual. Не лезет сам без явного запроса пользователя «покажи мне старые решения для оценки».

**Безопасность:** решения видны всем сотрудникам, если не помечены как `sensitive`.

## M-22 — Метрики и влияние

**Назначение:** связь тем и решений с количественными метриками (конверсия, retention, churn, лиды, скорость, поддержка).

**Слой:** 6.

**Источники метрик:**
- Из M-40 (бизнес-данные): CRM, метрики продукта, ERP.
- Из веб-аналитики (Yandex.Metrica, Google Analytics).
- Из БД клиента (через generic SQL коннектор).

**Что делает:**
- Хранит timeseries метрик в `metrics_timeseries`.
- Выявляет аномалии и существенные изменения → создаёт сигнал `metric_change`.
- Связывает изменение метрики с решениями (M-21) для оценки `consequences_actual`.
- Показывает разрезы метрик по командам/темам/источникам.

**Хранилища:** `metrics`, `metrics_timeseries` (партиционирование по дням), `metric_anomalies`.

**Алгоритм аномалий:** STL decomposition + 3-sigma порог. Можно подключить Prophet для сложных сезонностей.

## M-23 — Агент-исполнитель запросов (чат)

**Назначение:** главный интерактивный интерфейс к памяти. Пользователь спрашивает на русском — AI находит ответ со ссылками на оригиналы.

**Слой:** 7.

**Это самый важный пользовательский модуль.**

**Поведение:**
- Принимает свободный русский текст / голос.
- Использует **гибридный поиск** (см. ниже) для retrieval первоисточников.
- Использует **AI-команду M-38** для маршрутизации запроса к специализированному агенту.
- Возвращает ответ + список первоисточников (с возможностью развернуть до дословного).
- Работает с историей диалога (memory of conversation), но не больше 50 сообщений в окне.

### Гибридный поиск

Один запрос → одновременно:

1. **Векторный поиск** (pgvector, KNN top-50): семантическая близость.
2. **Полнотекстовый** (Meilisearch): русская морфология, BM25-аналог.
3. **Граф traversal** (M-12): соседи через связи M-11.
4. **Объединение результатов:** Reciprocal Rank Fusion + cross-encoder rerank top-20.
5. **Применение M-20:** фильтрация по доступу читающего.
6. Top-10 идут в LLM-агента как контекст.

### Маршрутизация запроса

См. [07-ai-team.md](07-ai-team.md). Supervisor смотрит на запрос и решает:
- Это вопрос о продажах → CSO-агент.
- Это вопрос о клиентах → CMO-агент.
- Это вопрос о команде → HR-агент.
- Это сложный комбинированный вопрос → composition: несколько агентов готовят свои части, supervisor собирает.

**Без подписей агентов в дефолтном UI.** Пользователь видит чистый ответ без «Ответил CSO-агент» — это часть UX «внутренняя кухня скрыта». Можно включить через настройку «показывать источник ответа».

**Контракт API:** см. [04-api-spec.md](04-api-spec.md), endpoint `POST /api/v1/chat/messages` (streaming через WSS).

**Бюджет:**
- p50 latency до первого токена: 1.5 сек.
- p95: 4 сек.
- p99: 10 сек.
- Стоимость на запрос: ≤ 5 ₽ (внешний LLM) / 0 ₽ (локальный).

## M-26 — Корректировка пользователем

**Назначение:** канал, через который человек поправляет AI.

**Слой:** 7.

**Что можно скорректировать:**
- Подтвердить/отклонить связь от M-11.
- Подтвердить/отклонить тему (создание / merge / split).
- Изменить вес темы вручную (override).
- Скорректировать классификацию сигнала.
- Изменить владельца/тип идеи/риска.
- Подтвердить решение для повышения confirmation.

**Принципы:**
- **Любое действие через диалог с AI**, а не через формы.
- AI спрашивает «уверен, что нужно слить эти две темы?» и принимает свободное «да/нет/уточни».
- Каждое действие записывается в `confirmation_history` соответствующей сущности.
- AI **не возвращается** к отклонённому предложению в течение 60 дней.

**Триггеры показа предложений:**
- В дашборде блок «AI ждёт подтверждения» — список candidates.
- В чате после ответа: «кстати, я нашёл связь между X и Y, подтвердить?» — но только если пользователь сам недавно работал с X или Y.
- Никаких agressive notifications.

## M-37 — Обещания и договорённости

**Назначение:** **память о том, что обещано.** Не задачник, не контролёр.

**Слой:** 7.

**Принцип:** см. [00-executive-summary.md](00-executive-summary.md), «Память, не контроль».

**Что делает:**
- Извлекает из разговоров фразы вида «я сделаю X», «мы договорились Y», «к пятнице будет Z».
- Сохраняет как `commitments` с владельцем, дедлайном, контекстом.
- **НЕ напоминает.** Никаких «вы обещали».
- **Отвечает на запрос:** «что я обещал на прошлой неделе?» — выдаёт список.
- Опционально пишет в task-tracker одной строкой («появилось обещание X от Y») — настройкой, по умолчанию выключено.

**Структура commitment:**

```sql
CREATE TABLE commitments (
    id UUID PRIMARY KEY,
    text TEXT,
    person_id UUID,
    deadline DATE,
    source_event_id UUID,
    status commitment_status_enum,  -- mentioned / acknowledged / mentioned_done / forgotten
    -- ...
);
```

**Status `forgotten`** — просто отметка «дедлайн прошёл, упоминаний выполнения нет», без давления. Может быть использовано пользователем для собственного аудита.

**Безопасность:** свои обещания видит только сам человек + его руководитель (если иерархия).

**Не путать с M-17 (идеи) и M-21 (решения).** Это слой ниже — обещание не равно решению.

## M-38 — Слой AI-команды

## M-39 — Шина инструментов

**Назначение:** единый реестр инструментов, доступных AI-агентам. Двойной транспорт MCP + REST.

**Слой:** сквозной.

**Инструменты:**

| Категория | Примеры |
|---|---|
| Поиск в памяти | `search_signals(query, filters)`, `search_themes(query)`, `find_related(node_id)` |
| Чтение | `get_theme(id)`, `get_signal(id)`, `get_decision(id)` |
| Запись (под контролем confirmation) | `propose_link(from, to, type)`, `propose_theme(...)`, `propose_decision(...)` |
| Анализ | `extract_signals(text)`, `summarize(text, length)`, `classify(text, taxonomy)` |
| Внешние данные (через M-40) | `crm_query(...)`, `metrics_get(...)`, `task_tracker_query(...)` |
| Системные | `get_user_role(user_id)`, `check_access(user_id, object_id)` |

**Транспорт:**
- **MCP (Model Context Protocol)** — для агентов, поддерживающих MCP (Claude). Сервер MCP публикует все инструменты.
- **REST API** — для агентов через LangGraph (внутренние агенты). Тот же реестр инструментов.
- **Один реестр** инструментов в обоих транспортах (single source of truth).

**Безопасность:**
- Каждый инструмент проходит check через M-20 (доступы агента).
- Audit-log всех вызовов через `agent_actions`.

**Хранилища:** `tools_registry`, `agent_tool_access` (какому агенту какие инструменты доступны).

## M-40 — Коннекторы к бизнес-данным

**Назначение:** интеграция с CRM/ERP/task-trackers/метриками.

**Слой:** 1.

**Поддерживаемые на старте (приоритет РФ):**

| Интеграция | Тип | Режим |
|---|---|---|
| 1С (Бухгалтерия 8.3, УТ 11) | ERP | Snapshot ingest (раз в сутки) + online query |
| Bitrix24 | CRM + tasks | Webhook + REST API |
| amoCRM | CRM | Webhook + REST API |
| МойСклад | ERP | Snapshot ingest |
| Yougile | Tasks | Webhook |
| Kaiten | Tasks | Webhook |
| HubSpot | CRM | REST API + webhooks |
| Generic SQL | DB | Read-only SQL queries по расписанию |
| CSV / Excel | files | Загрузка через UI |
| Yandex.Metrica | analytics | Reporting API |
| Google Analytics 4 | analytics | Reporting API |

**Принцип:**
- **Snapshot ingest** для крупных таблиц (раз в сутки, инкрементально).
- **Online query** для агента M-23 — когда пользователь спрашивает «сколько у нас сейчас сделок в работе» — делается живой запрос.
- **Никогда не пишем** в внешние системы (исключение — настраиваемая односторонняя sync M-37 → task-tracker, выключено по умолчанию).

**Безопасность:**
- Учётные данные коннекторов — в OpenBao.
- Минимальные права (read-only).
- Audit log каждого online-запроса.

**Хранилища:** `connectors`, `connector_runs`, `business_data_cache` (для часто запрашиваемых).
