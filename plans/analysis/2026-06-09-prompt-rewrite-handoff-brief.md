# Хэндофф: переписать все промпты Z «БЫЛО → СТАЛО»

## 0. TL;DR (для агента)
Тебе передают начатую работу. Уже сделаны **диагноз** (аудит 145 промптов) и **план** (ТЗ по фазам). **Чего ещё НЕТ и что нужно сделать: сами переписанные промпты — полноценный текст «БЫЛО → СТАЛО» по каждому промпту.** Твоя задача — пройтись по ВСЕМ промптам агентов и выдать их расширенные, полноценные версии — НО строго совместимые с нашим кодом: где промпт отдаёт JSON/tool по схеме — переписанный текст обязан давать валидный вывод под ТУ ЖЕ схему; где свободный текст — оставаться свободным текстом; имя tool/контракт не ломать; новое поле = явно помеченное изменение схемы (с указанием файла). **Сначала перепроверь предыдущий анализ по реальному коду — предыдущие агенты могли ошибаться.**

---

## 1. Что делали и зачем (контекст)
Владелец принёс свои **черновики промптов** (командная встреча; клиентская встреча — протокол+карточка+граф; орг-сущности — экстрактор и компилятор документа) и сформулировал **новый подход к усилению промптов**. Цель — **усилить промпты ВНУТРИ системы Z** (память компании Кора, AI-видеовстречи на LiveKit), а не внедрять черновики дословно. Черновики владельца — **донор смыслов**, не объект правки.

«Усилить промт» в понимании владельца = **показать его полноценный переписанный текст**: что было → что стало, в нормальной глубине (роль, принципы, структура, правила, чего НЕ делать, при необходимости примеры) — НЕ куцый набросок на 4 строки.

## 3. Решения владельца — ЗАФИКСИРОВАНЫ (учитывай при переписывании)
- **Р1** — старый v2-путь (`tasks-v2`/`summary-v2`/`chapters-v2`) **удаляем** (не переписывать — они на ретайр).
- **Р2** — **«Инструкция» — полноценная отдельная сущность** (отдельная таблица), в один ряд с Регламент/Процесс/Политика; старые инструкции-как-процессы пересчитать backfill-скриптом. → В экстракторе орг-сущностей добавляется `kind='instruction'` с дискриминатором «инструкция = пошагово для ОДНОЙ роли; не процесс (сквозная цепочка ролей); не разовая задача».
- **Р3** — доступ к HR-оценкам не трогаем (уже строгий); это про код/роли, не про текст промптов.
- **Р4** — `process-steps-extract` **удаляем** (сирота, не переписывать).
- **Р5** — старый список `AiResult.tasks` (`runTasks`) **убираем** (мёртвый) — переписывать не нужно.

## 4. Методология усиления (рубрика — применяй к каждому промпту, ТОЛЬКО применимые измерения)
- **A1** негативный дискриминатор: отличать целевое от похожего и от «разовой активности» (разовая задача ≠ процесс; пожелание «надо бы» ≠ задача/решение; жалоба ≠ системный insight; единичный эпизод ≠ устойчивая черта).
- **A2** только из входа; честное «не зафиксировано». **A3** опора на дословную цитату. **A4** имена только из списка участников (не угадывать по созвучию ASR).
- **B1** провенанс: кто/какая сторона сказал. **B2** «слова участника» vs «наша интерпретация». **B3** клиентские встречи → ДВА документа (нейтральный протокол наружу + внутренняя карточка), граница конструкцией.
- **C1** калиброванная шкала confidence (якоря 0.3/0.6/0.85/0.95). **C2** дисциплина статуса (существует/нужен/обсуждается — извлечённый ≠ подтверждённый). **C3** утверждение vs предположение.
- **D1** темпоральность: новое отменяет старое; устаревание; validFrom/validUntil.
- **E1** ASR-нота (поверх транскрипта). **E2** защита от инъекций (обёртка пользовательского ввода). **E3** относительные сроки → ISO от даты встречи. **E4** edge-case (пустой/противоречивый вход).
- **F1** cache-friendly (стабильный SYSTEM, переменные данные в КОНЕЦ user). **F4** дисциплина вывода. **G1** «что стоит уточнить».
- **Про людей:** оценки людей — гипотезно («похоже, склонен…», с опорой на реплику), без приговоров.

> Полные определения — в методологии и в аудите. **E1/E2 (ASR-нота и анти-инъекция) реализуются преимущественно ОБЁРТКОЙ на стороне кода (call-site)**, а не текстом промпта — в переписанном SYSTEM их не дублируй, помечай как «обёртка на call-site».

## 5. ТВОЯ ЗАДАЧА
Пройтись по **ВСЕМ промптам агентов** (список и текущие тексты — в каталоге + Приложение Б аудита) и для каждого выдать **полноценную переписанную версию**: «БЫЛО → СТАЛО». Глубина — как эталон в §8 (роль, принципы, структура, правила, чего НЕ делать), а не куцый набросок. Применяй методологию (§4) и решения (§3) — только то, что применимо к конкретному промпту.

Объём большой (~120+ промптов на усиление, без тех, что на ретайр по Р1/Р4) — разумно делать батчами/субагентами, но **каждый переписанный промпт сверяй с реальным кодом**.

## 6. КРИТИЧЕСКОЕ требование — переписанный промпт ОБЯЗАН вписаться в наш код
Это главное, на чём предыдущая версия буксовала. Для каждого промпта **сначала определи его контракт вывода**, прочитав и сам промпт-файл, и вызывающий сервис/воркер (`this.llm.call(...)` / `router.call` / `LlmFallbackService.complete`):

1. **Тип вывода.** Определи, что это:
   - **tool-use** (Anthropic tool / `tool_choice`) — есть `TOOL`/`TOOL_NAME` + `input_schema`;
   - **`responseFormat: json_schema` strict** — есть `*_JSON_SCHEMA` + `*_SCHEMA_NAME`;
   - **`responseFormat: json_object`** — «верни валидный JSON»;
   - **bare JSON array** — голый массив;
   - **свободный текст / Markdown** — без схемы.
2. **Сохрани контракт.** Переписанный СТАЛО обязан давать вывод, **валидный под ту же схему** (то же имя tool, те же обязательные поля, тот же тип ответа). Свободный текст оставляй свободным текстом; JSON — JSON; tool — tot же tool.
3. **Новое поле = изменение схемы, помеченное явно.** Если усиление требует НОВОГО поля (`said_by`, `to_clarify`, `status`, провенанс, два-протокольный split) — это НЕ «просто допиши в текст»: укажи отдельным блоком **«ИЗМЕНЕНИЕ КОНТРАКТА»** — какой файл-схему (Zod + JSON-schema + TS-тип) и как поменять, и приведи обновлённый фрагмент схемы. Иначе модель вернёт поле, которое валидатор отбракует.
4. **Имена схем/tool не выдумывай** — бери реальные из кода (например `extract_team`, `regulation_extract_v1`, `submit_meeting_analysis`).
5. **Cache-friendly:** стабильный текст — в SYSTEM; переменные данные (транскрипт, участники, дата) — в user, в конце. Не вставляй переменное в SYSTEM.
6. **Где у промпта несколько каллеров/обёрток** (напр. `tasks-unified` под 3 пути) — учитывай все, не сломай ни один.

## 8. ЭТАЛОН ГЛУБИНЫ (на него равняйся — продажи, протокол клиента)
```
СИСТЕМНЫЙ ПРОМПТ — «Протокол встречи с клиентом» (для отправки клиенту)

## Роль
Ты — деловой ассистент компании. На вход — транскрипт встречи с клиентом или
потенциальным клиентом (автоматическое распознавание речи, возможны искажения чисел,
имён и терминов). Ты готовишь ПРОТОКОЛ встречи — вежливый нейтральный документ, который
менеджер скопирует и отправит клиенту. Это лицо компании перед клиентом.

## Главный принцип — граница конфиденциальности
Это документ ДЛЯ КЛИЕНТА. В нём НЕ должно быть ни одной внутренней оценки: ни
«температуры»/интереса, ни ярлыков «боль»/«возражение», ни анализа ЛПР, ни предположений
о бюджете, ни сравнения с конкурентами, ни наших планов по сделке. Только нейтральная
фиксация. Вся внутренняя аналитика — в отдельный документ (внутренняя карточка), не сюда.

## Принципы
- Не выдумывай. Чего не было — не пиши. И не пиши «бюджет не обсуждался» — это внутренняя пометка.
- Провенанс по сторонам: различай, что сказала наша сторона, а что клиент.
- Слова клиента — его словами, нейтрально: «вы отметили, что…», «вы спросили про…». Без ярлыков.
- Имена и компании — только из списка участников (в конце сообщения). Не угадывай по созвучию,
  не транскрибируй на слух; не уверен — пиши роль («представитель клиента»).
- Числа/сроки/суммы переноси по смыслу (транскрипт мог исказить цифру), не выдумывай точные.
- Относительные сроки («к пятнице») переводи в дату от даты встречи.
- Тон: вежливый, деловой, краткий. Без воды, канцелярита и эмодзи.

## Структура (Markdown)
### Протокол встречи
- Дата: <из данных встречи> | Участники: обе стороны с ролями | Тема: одной фразой
### Кратко
2–3 предложения: зачем встречались и к чему пришли.
### Что обсудили
Ключевые темы, по пунктам, нейтрально.
### Что вы отметили
Потребности/вопросы клиента — его словами, без ярлыков.
### Договорённости и следующие шаги
Таблица: | Шаг | Ответственный (мы/вы) | Срок |. Только реальные договорённости;
нет ответственного/срока → «уточняется».
### Открытые вопросы
Нейтрально; если нет — раздел опусти.

## Чего НЕ делать
- Не добавляй разделов про интерес/бюджет/ЛПР/конкурентов/наши планы.
- Не оценивай клиента. Не пиши «не обсуждалось»/«уклонился». Не выдумывай договорённостей.
- Не начинай с «Вот протокол…» — сразу по структуре.

(Список участников и дата встречи — отдельным блоком в конце user; ответ — только Markdown.)
```

## 9. Клиентские типы — обязательно ДВА документа
Для `sales`/`customer_success`/`partner`/`custdev`/`follow-up`:
- **Документ 1 — нейтральный протокол** (как §8): что обсудили / что клиент отметил / договорённости / открытые вопросы. Можно отправить клиенту.
- **Документ 2 — внутренняя карточка** (только наша сторона): pain, интерес (+якоря), возражения+наш ответ+принято, **критерии выбора**, ЛПР+бюджет, **конкуренты вкл. «ничего не делать»**, **что зацепило**, срочность, **главное-что-мешает-продвинуть**, следующий шаг; провенанс «клиент vs мы».
- Граница — **конструкцией**: два отдельных вызова/контракта, поля карточки помечены internal-only. Не один промпт с правилом «не показывай».

## 10. Чего НЕ делать
- Не ломай контракты молча (новое поле без пометки изменения схемы — запрещено).
- Не вставляй черновики владельца дословно — это донор смыслов.
- Не переписывай промпты на ретайр (Р1: tasks-v2/summary-v2/chapters-v2; Р4: process-steps-extract).
- Не дублируй в тексте SYSTEM то, что делается обёрткой на call-site (ASR-нота, анти-инъекция) — помечай ссылкой на call-site.
- Не трогай код в этой задаче — выход = переписанные ТЕКСТЫ промптов + пометки изменений схем (реализация — отдельно по ТЗ).

## 11. Перепроверка (обязательно)
Предыдущий аудит делали субагенты — **проверяй их выводы по реальному коду** (grep/чтение), не доверяй на слово. В частности: реальный контракт каждого промпта (tool/json/free-text) и реальную схему сверяй ЧТЕНИЕМ вызывающего сервиса, а не по памяти. Если находка аудита не подтверждается — отметь и не применяй.
