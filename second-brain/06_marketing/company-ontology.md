# Онтология компании — ядро архитектуры «второго мозга»

> Зафиксировано 2026-05-20. Базовая концепция, на которой строится продуктовая часть «второй мозг компании» (Z + delivery/knowledge-core). Источник — формулировка от основателя.

## Концепция

Компания моделируется как **граф типизированных сущностей с типизированными отношениями** между ними. Каждый объект в компании (человек, процесс, решение, документ) — это узел определённого типа с атрибутами. Каждая связь между ними — это типизированное ребро (кто что сделал с кем когда зачем). LLM извлекает эти сущности и связи из неструктурированных данных автоматически.

**Клон сотрудника** в этой модели — это не отдельная сущность. Это **проекция графа**: subgraph всех узлов и рёбер, к которым человек прикасался, плюс его стилистический профиль для генерации. «Поговорить с клоном Маши» = запросить её subgraph + сгенерировать ответ в её стиле.

## Базовые классы сущностей

Минимально достаточный набор для типовой компании — **13 классов**. Расширяется под клиента.

### Person (Человек)

- **Что это.** Сотрудник, контрагент, клиент-индивид, кандидат. Любой персонифицированный участник деятельности компании.
- **Ключевые атрибуты.** ФИО (canonical + aliases), роль/должность, отдел, корпоративный email, телефон, telegram-юзернейм, время в компании, руководитель, прямые подчинённые, ключевые компетенции, рабочий язык/часовой пояс, статус (active / left / on_leave).
- **Источники извлечения.** Кадровая система (1С:ЗУП), корпоративная почта (адресная книга), Bitrix24 / amoCRM (контакты), Telegram (упоминания), записи встреч (распознанные голоса), документы (подписанты).
- **Главные связи.** `reports_to → Person`, `member_of → Project/Team`, `decided → Decision`, `participated_in → Event`, `owns → Document/Process`, `responsible_for → Risk/Metric`.

### Process (Процесс)

- **Что это.** Повторяющаяся последовательность шагов с целью и стадиями. Имеет длительность, участников, входы и выходы. Бизнес-процесс, операционный процесс, R&D-процесс.
- **Ключевые атрибуты.** Название, тип (sales / operations / development / support / …), стадии (entry → … → exit), участники по ролям, среднее время прохождения, метрики качества, владелец процесса, status (active / deprecated / in_design).
- **Источники извлечения.** Регламенты в Confluence / Notion / Yandex Wiki, описания в Jira (workflow), CRM-воронки (стадии сделок), повторяющиеся паттерны в коммуникациях.
- **Главные связи.** `owned_by → Person`, `produces → Document/Product`, `consumes → Document/Resource`, `instance_of → Process` (для конкретных запусков процесса), `depends_on → Process`, `uses → Technology`.

### Decision (Решение)

- **Что это.** Конкретный выбор между альтернативами с автором, контекстом и обоснованием. **Самая ценная сущность для бизнес-кейсов** — большинство knowledge loss в компании это потеря логики прошлых решений.
- **Ключевые атрибуты.** Формулировка решения, дата, автор(ы), статус (proposed / approved / rejected / superseded), обоснование (rationale), рассмотренные альтернативы, ожидаемые последствия, фактические последствия (заполняется позже).
- **Источники извлечения.** Протоколы встреч, переписка в почте / Slack / Telegram, записи Zoom / Telemost, RFC-документы, решения в Jira-комментариях. Это то, что особенно сложно извлечь — LLM нужно отличать «мы обсуждали X» от «мы решили X».
- **Главные связи.** `decided_by → Person(s)`, `concerns → Project/Process/Technology`, `based_on → Document/Event`, `supersedes → Decision`, `caused → Event/Decision`, `affects → Customer/Product`.

### Project (Проект)

- **Что это.** Конечная инициатива с целью, сроками, командой и результатом. В отличие от процесса — имеет финал. Может быть R&D, клиентский, внутренний.
- **Ключевые атрибуты.** Название, цель, статус (planning / active / paused / completed / cancelled), сроки (start / end), бюджет, заказчик, тимлид, команда, milestones, definition_of_done.
- **Источники извлечения.** Jira / YouTrack / Yandex Tracker (epics), CRM (клиентские проекты), Notion-страницы, презентации, кадровые приказы.
- **Главные связи.** `owned_by → Person`, `team_includes → Person(s)`, `for_customer → Customer`, `produces → Product/Document`, `uses → Technology`, `subject_of → Decision`, `composed_of → Event(s)`.

### Document (Артефакт / Документ)

- **Что это.** Любой материальный артефакт работы: договор, презентация, спецификация, отчёт, регламент, дизайн-макет, код. Это отдельная сущность, не путать с «исходным сырым файлом» в raw storage.
- **Ключевые атрибуты.** Название, тип, версия, авторы, дата создания, дата последнего изменения, статус (draft / review / approved / archived), confidentiality_level, ссылка на raw-объект.
- **Источники извлечения.** Google Drive / Yandex 360 / SharePoint (файлы), Notion / Confluence (страницы), Git (коммиты + файлы), почта (вложения).
- **Главные связи.** `authored_by → Person`, `belongs_to → Project/Process`, `references → Document/Decision`, `superseded_by → Document`, `mentions → Person/Customer/Product`.

### Event (Событие)

- **Что это.** Произошедшее в конкретный момент времени с участниками. Встреча, звонок, инцидент, релиз, изменение статуса сделки, увольнение, найм.
- **Ключевые атрибуты.** Тип (meeting / incident / release / transition / …), дата и длительность, участники, место (физическое / виртуальное), повестка, итоги, артефакты (например, запись встречи).
- **Источники извлечения.** Календари (Google Calendar, Outlook, Yandex Calendar), записи Zoom / Telemost (как факт встречи), Jira (status transitions), CRM (этапы сделки), Telegram-каналы инцидентов.
- **Главные связи.** `attended_by → Person(s)`, `concerned → Project/Process/Decision`, `produced → Decision/Document`, `triggered → Event/Decision`, `discussed → Topic`.

### Technology (Технология)

- **Что это.** Инструмент, библиотека, методика, фреймворк, оборудование, программа. То, что компания использует или производит как технологический выбор.
- **Ключевые атрибуты.** Название, тип (library / framework / tool / method / equipment), вендор, версия, статус в компании (evaluating / in_use / deprecated / banned), стоимость (если есть), владелец-эксперт.
- **Источники извлечения.** Git (зависимости в package.json / requirements.txt), документация, RFC, заявки в IT-департамент, упоминания в почте / Slack.
- **Главные связи.** `used_by → Project/Process/Person`, `replaces → Technology`, `requires → Technology`, `expert_is → Person`, `subject_of → Decision`.

### Customer (Клиент)

- **Что это.** Внешняя организация или индивид, покупающий у компании. Отдельно от Person, потому что это юридическое / коммерческое лицо со своей структурой.
- **Ключевые атрибуты.** Название, ИНН, тип (физлицо / юрлицо / госорган), сегмент (enterprise / SMB / SOHO), статус (lead / active / churned / dormant), AM-менеджер, lifetime value, контакты внутри клиента (как Person сущности).
- **Источники извлечения.** CRM как основной источник, договоры, бухгалтерская система (1С), переписка с клиентскими адресами.
- **Главные связи.** `account_manager → Person`, `contacts → Person(s)` (контакты внутри клиента), `subject_of → Project`, `signed → Document` (договоры), `participated_in → Event` (встречи, демо).

### Vendor (Поставщик)

- **Что это.** Внешняя организация, у которой компания что-то покупает. Программы, услуги, оборудование, консалтинг.
- **Ключевые атрибуты.** Аналогично Customer, но в обратном направлении денежного потока. Контракт, условия, ответственный с нашей стороны.
- **Источники извлечения.** Бухгалтерия (1С), договоры, заявки на закупку.
- **Главные связи.** `provides → Technology/Service`, `contracted_by → Person`, `subject_of → Decision` (выбор поставщика).

### Product (Продукт)

- **Что это.** То, что компания производит и продаёт. Для услуговых — пакеты услуг. Для tech-компаний — модули / фичи продукта. Для производства — артикулы.
- **Ключевые атрибуты.** Название, тип, версия, статус (alpha / beta / GA / EOL), ответственный (product owner), целевой сегмент, цена / тариф.
- **Источники извлечения.** Продуктовая документация, Notion, CRM (что продаётся), сайт компании, прайс-листы.
- **Главные связи.** `owned_by → Person` (product owner), `built_by → Project/Process`, `uses → Technology`, `sold_to → Customer`, `subject_of → Decision`.

### Goal (Цель)

- **Что это.** OKR, KPI, стратегическая цель компании или подразделения. Имеет владельца, измеряемость, дедлайн.
- **Ключевые атрибуты.** Формулировка, уровень (company / department / team / individual), period (Q1 2026, год, …), owner, target value, current value, status.
- **Источники извлечения.** OKR-системы, Notion-странички планирования, презентации стратегий, протоколы стратегических встреч.
- **Главные связи.** `owned_by → Person`, `measured_by → Metric`, `contributes_to → Goal` (иерархия целей), `worked_on_by → Project/Process`.

### Risk (Риск)

- **Что это.** Потенциальная угроза с вероятностью и влиянием. Регуляторный, технологический, кадровый, финансовый, репутационный.
- **Ключевые атрибуты.** Описание, категория, вероятность, потенциальный impact, статус (identified / mitigating / realized / closed), owner, mitigation plan.
- **Источники извлечения.** Risk-логи (если есть), incident-постмортемы, аудиторские отчёты, обсуждения в стратегических встречах.
- **Главные связи.** `affects → Project/Product/Process`, `owned_by → Person`, `mitigated_by → Decision/Process`, `realized_as → Event` (инцидент).

### Metric (Метрика)

- **Что это.** Измеримый показатель. Финансовый (revenue, MRR, CAC), операционный (NPS, churn, time-to-resolve), технический (uptime, latency).
- **Ключевые атрибуты.** Название, формула, периодичность измерения, target value, current value, time series исторических значений, owner.
- **Источники извлечения.** BI-системы, отчёты, дашборды, аналитические письма.
- **Главные связи.** `measures → Goal/Process/Product`, `tracked_by → Person`, `affected_by → Decision/Event`.

## Основные типы отношений (рёбра графа)

Минимальный набор около **40** — этого хватает на типовую компанию. Рёбра типизированные, направленные, с атрибутами.

**Авторство и владение:** `authored_by`, `owned_by`, `responsible_for`, `created`, `modified`, `approved`

**Участие:** `participated_in`, `attended`, `assigned_to`, `member_of`, `team_includes`

**Принятие решений:** `decided`, `proposed`, `approved`, `rejected`, `vetoed`

**Структурные:** `reports_to`, `belongs_to`, `composed_of`, `subset_of`, `instance_of`

**Зависимости:** `depends_on`, `blocked_by`, `requires`, `enables`, `caused`, `triggered`

**Замена и эволюция:** `supersedes`, `replaces`, `succeeds`, `derived_from`

**Коммуникация:** `mentions`, `references`, `discussed`, `addressed_to`

**Использование:** `uses`, `consumes`, `produces`, `provides`

**Целеполагание:** `contributes_to`, `measured_by`, `affects`

### Обязательные атрибуты каждого ребра

- `valid_from` / `valid_to` — временной диапазон действия отношения.
- `source_event_id` — provenance (из какого события извлечено).
- `confidence` — уверенность экстрактора (0.0 – 1.0).
- `weight` — сила связи (может быть бинарной или непрерывной).

## Как клон сотрудника собирается из этой модели

**Personal subgraph** для конкретного человека (например, Маша):

1. **Центральный узел** — `Person(Маша)`.
2. **Первый круг** — все узлы, к которым она привязана прямыми рёбрами: проекты, в которых член команды; решения, которые приняла или участвовала; документы, которые авторила; события, в которых участвовала; технологии, которые использует.
3. **Второй круг** — узлы, на которые ссылаются узлы первого круга: связанные проекты, цитированные документы, упомянутые клиенты.
4. **Стилистический профиль** — отдельный объект, извлекаемый из всех текстов, которые она писала (письма, сообщения, документы): tone, lexicon, типичные фразеологизмы, manner of decision-making, complexity-уровень.
5. **Voice profile** (опционально) — если есть достаточно аудио из записей встреч — fine-tuned TTS.

Когда коллега Петя «спрашивает клона Маши» — query идёт по её subgraph с фильтром по правам Пети (что Пете разрешено видеть из её данных), а ответ генерируется в её стилистическом профиле. Все ответы несут **provenance** — из каких источников клон сделал тот или иной вывод.

После ухода Маши её subgraph остаётся неизменным, нет новых данных — клон отвечает как **срез знаний на момент ухода**. Можно явно показывать это: «На момент 2026-05-01 Маша знала X. Текущая ситуация может отличаться».

## Особенности под российскую компанию

Дополнительные классы сущностей, специфичные для РФ-контекста:

- **LegalEntity** — отдельно от Customer / Vendor для случаев, когда у одного контрагента несколько юрлиц (что норма в РФ для налоговой оптимизации). ИНН / КПП / ОГРН как ключевые атрибуты.
- **GovernmentBody** — отдельный класс для госорганов: ФНС, Роспотребнадзор, ФСБ, ЦБ. Они одновременно регуляторы, иногда клиенты, иногда поставщики данных. Связь с ними особо важна для compliance.
- **Tender** — отдельный класс для госзакупок и тендеров. С атрибутами площадки (ЭТП, Госзакупки), номера, статуса. Это особый процесс с жёсткой временной структурой.
- **License** — лицензии, сертификаты, разрешения. Особенно важны в регулируемых отраслях (банки, медицина, телеком, фармацевтика).

**Адаптация онтологии под конкретного клиента — обязательная часть первого месяца внедрения.** Каждый клиент добавит 2-5 своих специфических классов сущностей под свою отрасль.
