# «Мастер» recall — потолок 79%: диагностика и гипотезы до 95–99

## TL;DR (честно и с поправками к самому себе)

Диагностика сместила картину: **значимая часть «провала 21%» — это дефекты ЛИНЕЙКИ, а не продукта.**
Три вывода, два из которых исправляют мой же after-report:

1. **Анафора диалога РАБОТАЕТ** (я был неправ, что это «отсутствующая подсистема»). q109 «И на что она
   влияет?» → понималщик развернул `«она» → «Zoom-интеграция»` и ответил. Гипотезу H3 **снимаю**.
2. **Линейка ломает счёт двумя способами** (оцифровано: 7 из 12 «пустых» — ложные). Реальный рычаг №1 —
   не фича синтеза, а **надёжная линейка** (H0).
3. **Умные таблицы уже подключены к чату** (`ChatV2TableContextService`), но пустые → вклад в recall ≈0.
   Оживление таблиц (ТЗ 2026-06-21) закрывает ведро «структурных фактов» (кто-по-роли / даты / суммы)
   **детерминированно** и **поглощает** мою H2 (не строим отдельный факт-индекс).

Потолок 95–99 остаётся портфелем на несколько итераций, но диагностика его **удешевила**: анафора
уже есть; факт-индекс = оживление готового движка; часть «провала» испарится с честной линейкой.

## 2. Дефекты линейки (рычаг №1) — оцифровано

Из 111 вопросов харнесс пометил «пусто» (`honest=True`) **12**, но **7 из них ложные** (ответ >200 симв,
без honest-маркера). Причины — ДВА независимых дефекта:

### Дефект A — эвристика «`usedBlockIds==0` → пусто»
`batch-recall-trace.ts:57-61`: `honest = …|| (usedBlockIds.length===0 && citations.length===0)`.
Заземлённые синтез-ответы со списками/без валидных block-id клеймятся пустыми.
Задело: **q054, q055** (перечни встреч), **q088** (риски), **q109** (анафора).

### Дефект B — отказ ловится по ТОЧНОЙ строке
`HONEST = 'В памяти компании я этого не нашёл'`. Модель отказывает **своими словами** → не матчится:
- **q074** [empty]: «В памяти компании **я не нашёл договорённостей** с „Мега-Транс“… Возможно, вы про
  „Логистик Плюс“?» — **идеальный честный отказ**, но перефразирован → посчитан ложно-пустым.

### Разбор 7 ложно-пустых (что на самом деле)

| id | angle | Что реально | Классификация |
|---|---|---|---|
| q074 | empty | Честный отказ (Мега-Транс нет), перефразирован | ✅ ВЕРНО (дефект B) |
| q109 | multistep | Анафора развёрнута, ответ дан | ✅ верно (дефект A) |
| q054 | meetings | Перечень встреч | ✅ верно (дефект A) |
| q055 | meetings | Встречи с Логистик Плюс | ✅ верно (дефект A) |
| q088 | risks | 429 Битрикс верно + `[BLOCK:…]` в тексте, но `usedBlockIds=[]` | ⚠ partial + провенанс-аномалия |
| q110 | expertise | Ответ дан | ✅/⚠ (проверить содержание) |
| **q008** | expertise | **«не нашёл», хотя Анна есть в памяти** | ❌ **реальный провал резолва (④)** |

**Итог линейки:** «сырое» число харнесса завышает провал. Реальный судья (панель majority-of-3)
это частично уже снимал (88/111), но **сама линейка как сигнал сломана** — нельзя строить итерации на
`honest`-флаге. Из семи «пустых» реальный провал — **один (q008)**.

### Провенанс-аномалия (кандидат в реальный баг, не только замер)
q088: ответ содержит инлайн `[BLOCK:cmr1qp24z008jhcbw58bow7nn]` и др., но `usedBlockIds=[]`, `citations=0`.
Статически: `parseUsedBlockIds`/`parseCitationsFromAnswer` (chat-v2.service.ts:2681/2632) фильтруют по
`contextBlocks` (`valid.has(id)`); регэксп `\[BLOCK:([a-z0-9]+)\]` cuid ловит. 24-символьный cuid модель
**не выдумывает** — копирует из контекста. Значит **набор блоков, показанный LLM, ШИРЕ набора валидации
citations**. Ведущий кандидат-источник: contradiction-блоки (`chat-v2.service.ts:2345` эмитит
`[BLOCK:${c.id}]`), граф-соседи или строки таблиц — их показывают модели, но не кладут в `contextBlocks`.
**Последствие для прода:** пользователь может видеть заземлённый ответ **без кликабельных источников**.
Требует repro под стендом (сопоставить показанный контекст ↔ `contextBlocks`). → отдельный фикс-трек.

## 3. Обновлённые гипотезы (с поправками)

Поправка по инфраструктуре: **rerank уже есть** (`chat-v2-rerank`), multi-query уже есть
(`MultiQueryExpansionService`, ровно 3 под-вопроса, берёт history+summary). Значит «ввести» → «усилить».

| # | Гипотеза | Статус после диагностики | Вариант |
|---|---|---|---|
| **H0** | Надёжная линейка + постадийные метрики | **Рычаг №1, подтверждён.** Чинит дефекты A/B, парс `[BLOCK:]`, прогон follow-up с историей, recall@k / faithfulness раздельно | Ввести (eval-слой, изолирован от горячего пути) |
| **H1** | Retrieval recall | Реранкер есть → **усилить** (multi-query качество, RRF-слияние, HyDE) | Доработать/изменить |
| **H2** | Детерминированный факт-индекс | **Поглощается таблицами** — не строим отдельно | → Волна «Таблицы» |
| ~~H3~~ | ~~Анафора диалога~~ | **СНЯТА** — механизм работает (q109) | — |
| **H4** | Полнота синтеза broad | Последним, под линейкой (риск вернуть выдумки ①) | Изменить (map-reduce) |
| **H5** | Резолв по роли (q008) | Реальный провал; **таблицы закрывают детерминированно** («Команда» {роль→человек}) | → Волна «Таблицы» + точечно |

### Качество под-вопросов — новое (пункт владельца)
Промпт `query-understand` уже делает шаг «разверни местоимения» + 3 ракурса, с примерами — **он хороший**.
Но **качество под-вопросов не измеряется** (метрика только `step:'multi-query'` длительность + битый JSON).
Это часть H0: линейка должна мерить recall@k «с экспансией / без» и долю разрешённых референтов.
Ужесточать промпт вслепую рано — сперва измерить, где течёт. (Примечание: флаг
`multiQueryExpansionEnabled` живёт в ENV `MULTI_QUERY_EXPANSION_ENABLED` — по правилу №9 это крутилка,
кандидат на перенос в AdminSetting; мелочь, не блокер.)

## 4. Умные таблицы как второй индекс (пункт владельца — подтверждён)

`ChatV2TableContextService.fetchTableContext` **уже подаёт строки таблиц в контекст чата**:
- `fetchByEntityBridge` — строки, привязанные к резолвнутым `entityIds`;
- `fetchByKeywordTables` — топ-`table_context_max_tables`(=2) таблиц по токен-оверлапу → семантический фильтр;
- крутилки `chat_v2.table_context_max_rows`(=20) / `max_tables`(=2), fail-open.

То есть «идём по базе И по таблицам» — **уже реализовано**. Не хватает одного: **данных**. По
ТЗ `2026-06-21-smart-tables-revive-and-autofill` (status ready-to-implement, «Реализовано — ничего,
осталось всё») таблицы операционно мертвы (нет меню, деталка крашилась, авто-наполнение 4/10). Пустая
таблица → нечего доставать → вклад ≈0 сегодня.

**Оживление таблиц даёт двойную ценность:** сам продукт таблиц + recall-бонус на структурных фактах, где
вектор слаб — прямое закрытие ведра ④ (q008 «кто по фронтенду» → строка «Команда» {роль=фронтенд→Анна}
детерминированно, в обход провала резолва графа) и класса «когда/сколько».

**⚠ ТЗ 2026-06-21 требует РЕВИЗИИ перед реализацией:** с 21 июня кодовая база, память и схема БД уехали
(появились новые сервисы chat-v2, изменилось извлечение/хранение). Reality-check ТЗ (что «уже есть, не
переписывать») **устарел** — пересмотреть перед стартом. Плюс мелкие доработки под recall-роль таблиц:
усилить `fetchByKeywordTables` (наивный токен-оверлап, топ-2 → семантический выбор, больше таблиц).
Оговорка честности: помогает только если наполнено И качество авто-наполнения хорошее (LLM → риск выдумок;
гейт уверенности 0.85 в ТЗ есть — критичен).

3. **Таблицы:** тонкий срез (Ф0-Ф1 оживить → Ф4 наполнить) или весь ТЗ 2026-06-21 целиком? В любом
   случае — **сначала ревизия ТЗ** (устарел reality-check).
