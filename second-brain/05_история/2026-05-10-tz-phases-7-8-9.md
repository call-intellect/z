## Что вышло

- Все три дочерних ТЗ — self-contained: каждое начинается с цели, заканчивается чек-листом «Итог».
- Формат идентичен между ТЗ: цель → что входит → архитектурные решения (нумерованные, не пересматриваются) → что НЕ входит → DoD → риски и митигации → текущее состояние → пошаговый план → затронутые файлы → сквозные правила → открытые вопросы → связанные документы → итог.
- В каждом ТЗ зафиксированы решения, чтобы агент не задавал лишних вопросов и не возвращался к родителю. Если возникает развилка не из списка — следовать skill'ам Z (`core-engineering-standards`, `nestjs-rules`, `frontend-rules`, `prisma-db-push-rules`, `z-ai-agent-rules`).
- Документ родителя `knowledge-core-tz.md` сохранён как высокоуровневый контракт, не размывается.
- Никакой код не написан в этой сессии — только ТЗ. Это и было задачей.
- Никаких изменений в schema/коде — только текстовые файлы. Прод-операции не нужны.

## Чему научился

1. **Дочерние ТЗ важнее, когда фаза >50 строк.** Родитель `knowledge-core-tz.md` (1497 строк) уже на грани читаемости. Передавать агенту фрагмент «строки 1161-1320» — плохо: агент тратит контекст на родителя. Дочернее self-contained ТЗ позволяет агенту работать без родителя. → В будущем: для каждой нетривиальной фазы создавать отдельный файл `plans/tz/<phase-name>.md`.

2. **Архитектурные решения нумеровать, не пересматривать.** В каждом ТЗ есть таблица «Архитектурные решения» с явной строкой «не пересматриваем». Это закрывает класс вопросов «а если по-другому?» — агент знает, что решение уже принято.

3. **Открытые вопросы с default-решением — норма.** Если вопрос неважный (cursor-формат пагинации, цвет timeline) — фиксирую default + допускаю отклонение, документируя его в `decisions-log`. Это снимает blocking без превращения ТЗ в окончательный закон.

4. **Состояние кода — обязательная секция.** «Что уже есть» / «Что нужно добавить» — экономит агенту полчаса на разведку. Особенно полезно для Фазы 7: половина схемы уже подготовлена в Фазе 0 (Org/Membership/AiUsageLog/LlmTaskRoute/LlmModelPrice), агент не должен дублировать.

5. **Зависимости между фазами — явно в ТЗ.** Фаза 9 расширяет Фазу 8, и это указано в каждом релевантном месте (ТЗ-9 + Решение #14 + плашка в ТЗ-8 «Фаза 9 добавит индикатор»). Без этого агент Фазы 9 удалил бы поле `strategicAlignment` как «лишнее» в DTO Фазы 8.

6. **Читать только то, что нужно.** Не читал родителя целиком (>25k токенов = ошибка лимита Read'а). Только фрагменты Фаз 7-9 (1155-1500). Сэкономил контекст на изучение состояния кода.

7. **Skill'ы Z (`core-engineering-standards`, `nestjs-rules`, `frontend-rules`, `prisma-db-push-rules`, `z-ai-agent-rules`, `safe-seed-rules`) — единственное место правил.** Не дублирую их в каждом ТЗ; ссылаюсь. Это уменьшает рефакторинг при изменении правил.
