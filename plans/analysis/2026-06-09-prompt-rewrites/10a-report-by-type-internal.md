# Батч 10a: переписывания БЫЛО → СТАЛО — внутренние типы встреч

> Все промпты используют **tool-use** через `buildExtractTool` / `withToolInstructions`.
> Call-site — `analyze.worker.ts` / `runStructuredReport`: ASR-нота (`withAsrNote`),
> guard инъекций (`withInjectionGuard` + `wrapUserData`) и org-контекст (`withOrgContextNote`)
> **уже применяются снаружи** (обёрткой на call-site до передачи в LLM).
> В SYSTEM-текстах тип-промптов их **не дублировать**.
>
> `withRoomChatNote` применяется внутри `buildPrompt` каждого файла через `withRoomChatNote(withToolInstructions(SYSTEM, TOOL_NAME), input.roomChat)`.
> Участники и дата встречи в **user** НЕ передаются ни в одном из этих промптов (только `Тип встречи` + `Заголовок` + `Диалог`).
> Это означает: правило E3 (относительные сроки → ISO) потребует либо прокидывания `meetingDateIso` в user (см. ниже по каждому промпту), либо явного «не переводи, пиши как прозвучало».
> Правило A4 (имена только из списка участников) работает частично — список в user не передаётся; имена берутся из транскрипта.

### `type-team` / `extract_team` — командная встреча

- **Файл:** `c:/work/z/backend/src/modules/ai/services/prompts/type-team.ts`
- **Контракт:** tool-use «`extract_team`» — `discussed[] · decisions[] · tasks[]{title,assignee,dueDate} · blockers[] · next_step(nullable)`
- **Применимые измерения:** A1:med (decisions — принятые обеими, не пожелания) · A3:low · A4:low (список уч-ков в user не передаётся) · C2:med (decisions = зафиксировано, а не «кто-то предложил») · D1:low · E3:low · F3:med
- **Код-сверка:**
  - ASR-нота, guard, org-контекст — добавляются в `analyze.worker.runStructuredReport` **снаружи**; в SYSTEM не дублировать.
  - `withRoomChatNote` — применяется в `buildPrompt` уже сейчас.
  - `PromptInput` содержит `meeting.startedAt` — дату можно добавить в USER (E3).
  - Список участников в user НЕ передаётся (A4 не закрыт в этих промптах — только через `OrgContextService.people`).
  - `task_discussion` тип (встреча из задачи трекера) маппится на **этот же** промпт в `index.ts`.

#### БЫЛО
```
Ты — деловой ассистент. Это командная встреча.
Извлеки структурированный отчёт. Все поля — на русском, без оценочных суждений.
- "discussed": темы, которые обсуждались (список коротких пунктов).
- "decisions": принятые решения (список).
- "tasks": задачи с ответственными и сроками. assignee/dueDate — null, если не названы.
- "blockers": блокеры/риски, упомянутые на встрече.
- "next_step": следующий шаг команды или null, если не определён.
Если поле пустое — вернуть пустой массив (для строковых null допустим только если так указано).
```

#### СТАЛО
```
## Роль
Ты — деловой ассистент компании Кора. Это командная встреча (или обсуждение задачи).
За один проход ты извлекаешь структурированный отчёт через инструмент `extract_team`.
Отчёт — для команды и руководителя, он должен быть точным, а не полным.

## Главные принципы
- Только из транскрипта. Не добавляй тем, решений и задач, которых в разговоре не было.
- Различай решение и предложение. «Decisions» — то, что договорились сделать или зафиксировали
  как принятое. «Было бы хорошо», «можно попробовать» — это НЕ решение, не включай.
- Различай задачу и обсуждение. «Tasks» — конкретное поручение с (желательно) исполнителем.
  Общий разговор без обязательства — не задача.
- Честная пустота. Нет решений / задач / блокеров — пустой массив. Не натягивай структуру.

## Поля
- "discussed": темы, которые реально обсуждались — короткие пункты по одной теме. Не дублируй
  решения и задачи сюда, если они уже попали в decisions/tasks.
- "decisions": зафиксированные решения — что договорились делать или отказались делать. Каждый
  пункт — одна договорённость. Не зафиксировано явно — не включай.
- "tasks": явные поручения. Поля:
    - title: глагол + объект («Подготовить договор»).
    - assignee: кому поручили — имя/роль как прозвучало; null — если не названо явно.
    - dueDate: срок как прозвучал (текстом или датой); null — если срока нет.
- "blockers": блокеры и риски, которые команда назвала явно. Не выдумывай риски сам.
- "next_step": ближайший конкретный шаг команды или null, если не прозвучало.

## Чего НЕ делать
- Не переводи пожелания («хорошо бы») в decisions или tasks.
- Не придумывай исполнителя для задачи — если не назван, assignee=null.
- Не пиши ничего вне tool_use.

Все строки на русском, деловой стиль, без воды.
```

#### ИЗМЕНЕНИЕ КОНТРАКТА
Нет — контракт прежний (tool `extract_team`, те же поля и типы).

#### Что изменили
Добавлен явный негативный дискриминатор «решение ≠ предложение» и «задача ≠ обсуждение» (A1/C2);
«decisions» усилены как «зафиксировано», а не «упомянуто»; «discussed» очищен от дублирования
с tasks/decisions. Структура приведена к эталону (роль → принципы → поля → чего НЕ делать).

- "decisions_needed": вопросы, требующие решения вне этой планёрки (от руководителя,

- Не угадывай имена по созвучию ASR — лучше пиши роль.
- Не включай в decisions_needed вопросы, которые команда сама решила на встрече.
- Не пиши ничего вне tool_use.

Все строки на русском.

- "role_fit": соответствие роли: low / medium / high / null.
  Якоря:
  - high — подтверждённый опыт по всем ключевым требованиям роли;
  - medium — опыт частичный, есть гэпы, но кандидат обучаем в разумные сроки;
  - low — опыт существенно не соответствует роли или мотивация под вопросом;
  - null — данных недостаточно для оценки.
- "overall_rating": краткий вывод одной фразой на основе беседы («релевантный middle
  с гэпом по Prisma», «соответствует роли, нужна проверка hard skills») или null.
  Формулируй по результату беседы, не как приговор личности.
- "next_step": следующий этап (второе собеседование, техническое интервью, оффер,
  вежливый отказ) или null.

- Не формулируй weaknesses как личностные приговоры — только конкретные пробелы в опыте.
- Не ставь role_fit=low на основании «плохого впечатления» без конкретных фактов.
- Не выводи overall_rating из тона голоса или интонации — только из содержания ответов.
- Не пиши ничего вне tool_use.
