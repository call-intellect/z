# Гигиена графа знаний + качество идей

## Что было поставлено

Два парных ТЗ от 2026-06-25, ветка `feature/knowledge-graph-idea-quality` (10 коммитов):

- **ТЗ-1 «гигиена графа знаний»** (`plans/tz/2026-06-25-knowledge-graph-hygiene.md`, Ф1–Ф5). Граф сущностей забит мусором (ID задач трекера `MANA-7`, телефоны, email, обрывки слов). Поставить гейт качества на входе, не извлекать сущности из эхо-событий трекера, дать «провалиться к источнику» с карточки сущности, вычистить накопленное.
- **ТЗ-2 «качество идей»** (`plans/tz/2026-06-25-idea-quality.md`, Ф1–Ф6). 85% идей без обоснования (direct-path пишет `rationale=null` в обход хорошего сборщика), дубли плодятся, в идеи затекают задачи, нельзя провалиться к источнику. Каждая идея — полная формулировка + обоснование; пороги дедупа в крутилку; «задача ≠ идея»; provenance идеи.

## Как решал

Оркестрация фаза-за-фазой суб-агентами-кодерами с личной приёмкой каждой фазы (греп / re-Read / свой typecheck-lint-build-тесты + ревью перед коммитом).

Ключевые архитектурные решения:

- **Переиспользование `knowledge.*`-ключей вместо `ideas.*`-дублей.** Буквальный текст ТЗ-2 §8 просил завести namespace `ideas.clusterThreshold` / `ideas.extractMinConfidence`. По факту реестр `admin-setting-schema-registry.ts` уже давно содержал `knowledge.ideaClusterThreshold` и `knowledge.ideasExtractMinConfidence` (засиданы соседним ТЗ task-decision-disambiguation). Новые ключи не заводил — переключил код на чтение существующих через `getDynamic`. Дубль крутилок того же смысла — нарушение правила 9.
- **Проводка `clusterThreshold` в 3-й потребитель — cron.** ТЗ называл 2 точки (`findMatchingIdea`, `reconcileIdeaForDecision`); реальный код имеет третью — `idea-clusterer.cron`, который тоже читал хардкод-порог. Провёл `getDynamic` и туда — иначе крутилка была бы дырявой (правило 9 требует полноты).
- **Фикс бага §8 соседнего смерженного ТЗ.** `IdeasListClient` рендерил `<ProvenanceChip entityType="block" entityId={idea.id}>` — передавал id ИДЕИ в тип «блок». ТЗ-2 Ф4 явно помечен как `supersedes` этой строки: переписал на `entityType="idea"` + завёл бэк-резолв `idea.sourceBlockIds`.
- **EntityLink без FK.** В backfill-чистке сущностей `EntityLink` (полиморфная, `NULL`=legacy `'entity'`) надо удалять вручную `deleteMany` по обеим сторонам — каскада нет. Вынес граблю в `code-pitfalls.md`.

## Что вышло

- 10 коммитов на ветке `feature/knowledge-graph-idea-quality`.
- backend typecheck / lint / build — зелёные; frontend typecheck / lint / build — зелёные (234 страницы).
- Затронутые спеки — 81/81 зелёные.
- LLM/БД-зависимое (прогон backfill-скриптов, diag ≥80% отсева) проверено только типами — снимается на проде.
- Документация: обе ТЗ отмечены выполненными (фазы + DoD), `knowledge-core.md` (раздел про гейт сущностей / provenance entity+idea / idea-extract direct-path / крутилку дедупа), `code-pitfalls.md` (EntityLink без FK), `prod-deploy-log.md` (новый блок «Накоплено»), эта рефлексия.

## Чему научился

- **Приёмка ловит то, что кодеры пропускают.** В `backfill`-скрипте при приёмке всплыли ошибки типов, которые кодер пропустил: `TS7022` (циклическая инференция типа из самоссылающегося `const`) и `noUncheckedIndexedAccess` (индексный доступ к массиву без guard'а). typecheck кодера был «зелёный» локально, потому что `scripts/` лежит вне базового `tsconfig` — типизировать скрипты надо через временный extends-конфиг, включающий `src/**`, иначе дрейф типов в `scripts/` не виден.
- **Буквальный текст ТЗ про namespace ключей разошёлся с реальностью.** ТЗ писалось до мержа соседнего, который уже завёл нужные ключи под `knowledge.*`. Перед заведением «нового» ключа из ТЗ — грепни реестр: возможно, ключ того же смысла уже есть, и правильно переиспользовать, а не плодить дубль-крутилку.
- **`scripts/` вне базового tsconfig** — отдельный класс слепоты: typecheck корня их не покрывает. Канон приёмки скрипта — прогнать `tsc` с временным конфигом `extends` базового + `include: ['scripts/**', 'src/**']`.
