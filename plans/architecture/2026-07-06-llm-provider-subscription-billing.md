# Провайдер по подписке — учёт стоимости (без rate-limit)

## 1. Что есть сегодня

Каждый вызов LLM стоит денег по цене за токен: `LlmRouterService.computeCostUsd()` ищет цену в `LlmModelPrice` (БД) либо в захардкоженной карте `MODEL_PRICES`; если не находит — пишет `costUsd=0` и WARN «цена не найдена, заполни в админке» + метрику `llm_cost_unpriced_total`. Это работает для провайдеров, которые реально берут деньги за токен (DeepSeek, OpenAI и т.д.).

Не все провайдеры так работают. У владельца есть провайдер (например, MiniMax) с фиксированной ЕЖЕМЕСЯЧНОЙ подпиской и лимитами запросов (5-часовое окно + недельное — как у Anthropic Claude Pro/Max), а не платой за токен. Сегодня для таких провайдеров либо приходится вручную зануливать цену на КАЖДУЮ модель в `LlmModelPrice` (чтобы не было unpriced-warning), либо просто получать спам предупреждений — и нигде не видно РЕАЛЬНУЮ стоимость (ежемесячный платёж за подписку) в дашборде расходов.

## 2. Что делаем (эта итерация — только учёт стоимости, без rate-limit)

Провайдер помечается как «по подписке» (`billingMode='subscription'`) с суммой в месяц и датой начала. С этого момента:

- Любой вызов через этот провайдер стоит **$0** автоматически — цену в `LlmModelPrice` заполнять не нужно, unpriced-warning не срабатывает. Токены (input/output/cached) по-прежнему считаются и попадают в `AiUsageLog`/аналитику как обычно — просто у них стоимость 0, а не «неизвестно».
- Раз в месяц, в день годовщины начала подписки (с учётом коротких месяцев — если старт 31-го, в феврале это 28/29-е), платформа записывает РЕАЛЬНЫЙ расход — сумму подписки — в отдельный реестр. Это НЕ расход конкретной компании (Org), это расход платформы перед провайдером — поэтому не идёт в per-org таблицу `AiCostDaily` (она про то, кто из клиентов сколько потратил) и не влияет на бюджеты компаний.
- В общем дашборде расходов (`/admin/analytics/llm-cost`, платформенный — не per-org) сумма подписки добавляется как разовый скачок в график расхода по дням — в день фактического списания.

## 3. Границы — что НЕ делаем

- НЕ делаем rate-limit enforcement (блокировку запросов при исчерпании 5-часовой/недельной квоты) — отдельная, куда более тяжёлая инфраструктура (Redis sliding-window counter, pre-dispatch гейт в роутере). Решение владельца: в этой итерации закрываем только учёт стоимости.
- НЕ учитываем подписочный платёж в per-org `AiCostDaily`/бюджетах компаний — это расход платформы, не конкретного клиента.
- НЕ трогаем существующую механику `LlmModelPrice` — она остаётся как есть для провайдеров с оплатой за токен; для подписочных провайдеров просто НЕ требуется её заполнять.
- НЕ делаем UI для истории/отмены/редактирования уже списанных подписочных платежей в этой итерации — только показ в графике расхода.

## 4. Решения

| # | Решение | Почему |
|---|---|---|
| П1 | Только учёт стоимости, без rate-limit enforcement. | Владелец подтвердил (2026-07-06): rate-limit — куда более тяжёлая инфраструктура (Redis, pre-dispatch гейт, поведение при исчерпании квоты), тянет на отдельное ТЗ. |
| П2 | Ежемесячный платёж подписки — разовая строка ИМЕННО в день списания (не размазывается по дням месяца). | Владелец подтвердил: соответствует факту реального списания (как банковская выписка), не искажает данные задним числом. |
| П3 | Подписочный платёж — отдельный реестр (`LlmProviderSubscriptionCharge`), НЕ строка в `AiCostDaily`. | `AiCostDaily` — per-org атрибуция расхода (кто из клиентов сколько потратил, используется бюджетами компаний). Платёж за подписку не вызван никаким конкретным клиентом — приписывать его случайному/всем Org было бы неверно. |
| П4 | Один провайдер — одна активная подписка (`billingMode`+`subscriptionMonthlyCostUsd`+`subscriptionStartedAt` — три поля на `LlmProvider`, не отдельная таблица конфигурации). | Проще: подписка — атрибут провайдера, а не отдельная сущность с историей планов. Если тариф подписки поменяется — правится то же поле (старое значение просто переставало действовать с этой даты, история платежей всё равно в `LlmProviderSubscriptionCharge`). |
