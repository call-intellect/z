# База знаний Коры: читабельность, раскладка, таксономия, ручная загрузка

## 0. TL;DR для владельца

Четыре отдельные проблемы, три из них дешёвые, одна — продуктовый разрыв:

1. **«Стена текста» — это БЭК, не фронт.** Markdown на странице рендерится правильно (react-markdown). Но новая карточка сохраняет в тело документа сырой одноабзацный вывод LLM (`contentMd = statement`). Форматтер (агент-компилятор) у нас **уже есть**, но включается только при слиянии версий, а не при создании. Почин — переписать промпт так, чтобы структура (заголовки + нумерованные пункты) собиралась **сразу**, + разовый прогон по старым карточкам.
2. **«Узкий интерфейс» — ложное противоречие.** Расширять надо оболочку (на весь экран: дерево-папки слева + область чтения + оглавление справа), а сам текст держать в колонке ~700px. Так делают GitBook, Notion, Confluence, Wikipedia. Сейчас у нас вся страница зажата в `max-w-6xl` и поделена на список+карточку без левой навигации.
3. **Таксономия в целом верная (4 типа), но запутана подача:** дубль «Шаблоны процессов» (вкладка) и «Процессы» (фильтр), редкие «Политики», расхождение счётчиков. Политики **реально извлекаются** (не заглушка), но в речи их обсуждают редко — отсюда «их почти нет».
4. **Ручная загрузка НЕ доходит до базы знаний гарантированно** (ответ на ваш прямой вопрос). Пометка «это регламент» при загрузке сегодня — просто метаданные; станет ли документ регламентом, решает LLM заново. Это разрыв, но механизм детерминированного типа у нас уже есть — нужно его подключить к каналу документов.

## 1. Рамка проблемы

**Симптом (слова владельца):** «интерфейс ужасный, узкий; контент — нечитаемая стена текста; непонятно, база это знаний или нет; политик вроде нет».

**Конкурирующие формулировки корня (Iceberg — отделяем симптом от причины):**

- **Формулировка A (поверхностная, неверная):** «плохой рендер карточки». — Опровергнуто: рендер корректен (см. §2.4). Не нести в ТЗ.
- **Формулировка B (структурная, главная):** «оцифрованное знание сохраняется и подаётся как сырой текст в тесной утилитарной раскладке — это читается как лог экстракции, а не как база знаний компании». Корень распадается на 4 независимых вектора: форматирование контента (бэк), информационная архитектура + ширина (фронт), таксономия/нейминг, целостность каналов наполнения (ручная загрузка ↛ карточка).
- **Формулировка C (продуктовая, для позиционирования):** «у Коры есть уникальный актив — знание уже лежит графом, — но раздел показывает его беднее, чем обычная ручная вики (istok/Teamly/Notion), хотя должен показывать богаче (граф-навигация, провенанс из встреч, темпоральная актуальность)». Это не баг-фикс, а возможность обогнать.

**Кто страдает (роли Z):** владелец/директор (не доверяет разделу, «не похоже на базу знаний»); рядовой сотрудник (не может прочитать регламент — стена текста); тот, кто вносит знание вручную (загрузил регламент — он «пропал», не виден в базе).

**Метрика «решено»:** (а) тело любого документа читается с заголовками/списками без сырых абзацев; (б) раздел использует всю ширину экрана, слева — дерево папок по типам, текст в читаемой колонке; (в) ручная загрузка с пометкой типа гарантированно создаёт карточку нужного типа и проходит ту же верификацию; (г) внятная таксономия без дублей и расхождений счётчиков.

## 2. Карта текущей реализации (baseline по коду)

### 2.1. Данные — четыре first-class сущности (не «одна таблица»)
Единый UI «База знаний» агрегирует 4 модели Prisma ([schema.prisma:5683–6039](backend/prisma/schema.prisma#L5683)):

| Модель | Что | Ключевые поля | UI-фильтр |
|---|---|---|---|
| `Regulation` | Регламент / стандарт | `category: regulation\|standard`, `contentMd`, `statement`, `confidence`, `currentVersionId→CardVersion` | «Правила и стандарты» |
| `Instruction` | Инструкция (одна роль) | `forRole` (single-role признак), зеркалит Regulation | «Инструкция» |
| `Policy` | Политика | `severity: advisory\|mandatory\|blocking` | «Политики и положения» |
| `ProcessTemplate` | Шаблон процесса | версионируемый (`ProcessTemplateVersion`), `decisionPoints`, `handoffs` | «Шаблоны процессов» (отдельная вкладка) + «Процессы» (фильтр через legacy `Process`) |

Enum'ы ([schema.prisma:975–991](backend/prisma/schema.prisma#L975)): `RegulationCategory {regulation, standard}`, `PolicySeverity {advisory, mandatory, blocking}`, `ProcessStatus {active, deprecated, archived}`.

### 2.2. Агент-экстрактор (кто заполняет) — Specialist 3.1
Pipeline: `RawEvent → block-ingest.worker → IdeaBlock → block-distill (draft→canonical) → RouterService.dispatch(по signalType) → core.specialist-routing jobName='3-1-regulations' → Specialist31Service`.

- LLM-вызов `taskType: 'regulation-extract'` ([regulation-extract.prompt.ts:22](backend/src/modules/knowledge-core/prompts/regulation-extract.prompt.ts#L22)) — STRICT JSON, возвращает `{kind, name, statement, confidence, scope, severity, category, isOrgNorm, ...}`. **`statement` — один сплошной абзац на естественном языке** (пример прямо в промпте: «Каждый договор с подрядчиком проходит юридическую проверку до подписания…»).
- Тип (`kind`) и `category`/`severity` выбирает **LLM**, не эвристика. `confidence` — тоже LLM (калибровка в промпте: есть шаги/роли/сроки → 0.9, голое упоминание → 0.5). Порог отсечения `< 0.4` → skip.
- KNN-дедуп → LLM-арбитр `regulation-dedupe` (`new | merge | extension | contradicts`).
- Промпты **НЕ admin-editable** (нет в registry; живут в коде, без DB-fallback). SYSTEM стабилен → cache-friendly.

### 2.3. ⚠️ Корень «стены текста» (подтверждено лично)
[specialist-3-1-regulations.service.ts:406–419](backend/src/modules/knowledge-core/services/specialist-3-1-regulations.service.ts#L406) — ветка `new`:
```
create: { contentMd: draft.statement, statement: draft.statement, ... }
```
**Тело документа = сырой одноабзацный `statement`.** Структурный markdown собирает агент-компилятор `StructuredDocumentCompilerService` (`taskType: 'compile-org-document'`, [structured-document-compiler.prompt.ts:142](backend/src/modules/knowledge-core/prompts/structured-document-compiler.prompt.ts#L142)) — он умеет разложить по типам (регламент → таблица «Шаг·Действие·Ответственный·Срок·Результат»; процесс → цель/границы/шаги; инструкция → нумерованные шаги; политика → положения/строгость). Но вызывается **только** на `merge`/`extension` ([service:455–465](backend/src/modules/knowledge-core/services/specialist-3-1-regulations.service.ts#L455)). Итог: первая (и часто единственная) версия карточки — всегда сырой абзац. Форматтер есть — просто не на том шаге.

### 2.4. API (`regulations` + `processes`)
- `GET /regulations?kind=&status=&scope=&q=` — список (фильтр по одному `kind`). `GET /regulations/:id?kind=` — деталь. `GET /:id/sources` (провенанс-цитаты из IdeaBlock→Meeting), `GET /:id/history` (CardVersion timeline).
- `GET /regulations/summary` → `{regulations, processes, instructions, policies, weekDelta}` — чипы-счётчики.
- Действия: `POST /:id/confirm` (→`lastConfirmedAt`), `/supersede` (→deprecated + supersedesId), `/correct` (owner/admin → сразу CardVersion human-verified; иначе в очередь курации), `/dispute` (обучающий сигнал `mark_as_misleading`).
- `processes/templates/*` — полный CRUD + версии + decision-points + handoffs.

**Расхождение счётчиков (не баг, архитектура):** чипы берут глобальные `count()` по 4 таблицам (`/summary`), а список фильтруется по одному `kind`. Отсюда «9 политик» в чипе при «Всего: 1» в списке (активен фильтр «Инструкция»). UX-проблема (вводит в заблуждение), не дефект данных.

### 2.5. Фронт (раскладка, которую владелец не любит)
[regulations/RegulationsListClient.tsx](frontend/app/(authenticated)/regulations/RegulationsListClient.tsx):
- Страница в `max-w-6xl` (≈1152px), master-detail `md:grid-cols-[1fr_1.4fr]` ([:494](frontend/app/(authenticated)/regulations/RegulationsListClient.tsx#L494)) — список слева, карточка справа. **Левой навигации-папок нет.** Фильтр видов — горизонтальные табы.
- Тело рендерит `ContentMarkdown` ([:1021](frontend/app/(authenticated)/regulations/RegulationsListClient.tsx#L1021)): `react-markdown@10` + `rehype-sanitize`, обёртка `prose prose-sm`. **Markdown парсится корректно** — стена текста не отсюда, а из §2.3 (нечего форматировать). Маркеры `[требует уточнения]`/`[конфликт]` вырезаются в чипы.
- Дизайн — **старый язык** (bg/border-токены), не новый редизайн `/redesign` (стекло/градиент).
- Мобильно: master-detail схлопывается в стопку, спец-обработки узких экранов нет (UX-долг).

### 2.6. ⚠️ Разрыв ручной загрузки (ответ на прямой вопрос владельца)
Цепочка `POST /documents (docType='regulation') → DocumentIngestAdapter → RawEvent.payload.docType → block-ingest → LLM сам решает signalType → (если ='regulation') Specialist 3.1 → Regulation`.

**`docType` НЕ передаётся как `signalTypeHint`** ([block-ingest.worker.ts:976](backend/src/modules/knowledge-core/workers/block-ingest.worker.ts#L976) читает только `payload.signalTypeHint`, который проставляет лишь `TrackerAdapter`). Значит тип карточки переопределяет LLM, а не выбор пользователя. Если LLM классифицирует текст как `idea`/`decision` — документ **не станет** регламентом и **не появится** на `/regulations`, осядет в отдельном контуре `/documents`.

**Вердикт:** «загрузил и пометил регламентом → появится в базе и будет перепроверен» — сегодня **НЕ гарантировано** (зависит от повторного решения LLM). НО механизм детерминизма (`signalTypeHint` override) уже существует — почин = пробросить `docType → signalTypeHint` в `DocumentIngestAdapter`. Верификация: ручной контент так же идёт в триаж/курацию (trustTier `auto`→`human`), т.е. «перепроверка» технически есть.

## 3. Ландшафт аналогов (двухконтурный, сжато)

Полные карточки teardown'ов — в возвращённых отчётах суб-агентов; здесь — выжимка под решения. Срез 2026-06-16.

**Зарубеж (раскладка «настоящей базы знаний»):** GitBook, Notion, Confluence, Document360, ReadMe, Mintlify, Nuclino, Slite, Slab, Obsidian Publish, Outline, Guru. Общий каркас: **широкая оболочка + левое дерево (≤3 уровня) + читаемая колонка + правый авто-TOC + тумблер ширины**. `[verified]` по официальным докам со скриншотами.

**РФ (водораздел подтверждён):** istok.ai, Teamly AI, Minerva Knowledge, Yonote, Битрикс24 База знаний. Все — модель «человек вносит/загружает → RAG отвечает». Видимые сигналы доверия (уверенность, «полезно/нет», честный отказ) публично показывает **только istok**. `[claimed]` (RU-вендоры прячут UX за демо; пиксельно проверен только istok — наш прошлый teardown).

**Ключевой вывод ландшафта:** список «читается базой знаний» не из-за карточек, а из-за **трёхслойной структуры**: организатор верхнего уровня (по типу/отделу) → неглубокое дерево слева → landing-страница раздела с аннотированными строками (источник·дата·статус·теги) вместо плоского перечня. У Коры есть честный козырь, которого нет у конкурентов кроме Nuclino — **граф-вид** (знание уже в графе).

## 5. Матрица вариантов

### 5.1. Проблема форматирования (главный инженерный выбор)

| Критерий (ограничения Z) | A. Встроить структуру в промпт создания | B. Отдельный LLM-проход «форматтер» после каждой карточки | C. Только рендер-эвристика на фронте |
|---|---|---|---|
| Стоимость токенов | ≈0 (та же генерация) `[verified]` | 2× prefill каждой карточки `[verified]` | 0 |
| Prompt-cache (feedback: cache-friendly) | сохраняется (структура в стабильном SYSTEM) | **ломает** (новый SYSTEM, двойная оплата) `[verified]` | n/a |
| Риск искажения фактов | низкий (один контекст) | выше (второй проход «додумывает») `[claimed]` | нулевой, но и пользы мало |
| Решает корень (сырой абзац) | да | да | **нет** (нечего парсить, если в тексте нет `1.`/`-`) `[inferred]` |
| Старые накопленные карточки | нет (нужен backfill) | да | нет |
| Сложность | средняя (правка промпта + включить компилятор на create) | низкая, но дорого в проде | низкая |

**Источник оценок:** OpenAI cookbook (one-task-per-call), Fireflies/Fellow (секции в промпте), BrassTranscripts («formatting is part of the prompt, not post-processing»), AWS/Redis (cache+token), наш `feedback_llm_prompts_cache_friendly`.

**Рекомендация (форматтер): A + точечный B для миграции + рендер-фиксы C.**
- **A (основное):** включить агента-компилятор `compile-org-document` **на создании** карточки (не только merge), либо зашить markdown-каркас типа прямо в `regulation-extract`/компилятор так, чтобы `contentMd` сразу был структурным. Каркас секций → в стабильный SYSTEM (кэш цел). Constrained-инструкция «структурируй, не добавляй/не убирай факты; чего нет — помечай, не выдумывай» (faithfulness).
- **B (только backfill):** разовый идемпотентный прогон по уже накопленным плоским карточкам на дешёвой `deepseek-v4-flash` («не меняя фактов — переразметь в markdown»). Не штатный второй хоп.
- **C (бесплатно, сразу):** рендер-фиксы (ширина, типографика) — см. 5.2; даже сырой абзац станет легче при колонке ≤75 символов.

### 5.2. Проблема раскладки/навигации

| Критерий | A. Косметика (расширить, причесать карточку) | B. Полный редизайн «база знаний» (дерево слева + wide shell + TOC) |
|---|---|---|
| Закрывает «не похоже на базу знаний» | частично | да |
| Соответствует прямой просьбе владельца («слева папки, расширить») | нет | да |
| Граф-вид, landing-страница, провенанс | нет | да (поэтапно) |
| Использует новый редизайн `/redesign` | можно | да (естественно) |
| Объём | малый | средний-крупный (фазируется) |

**Рекомендация (раскладка): B — полный редизайн.** Каркас (доказан индустрией, §3, визуальные эталоны): **оболочка 100% ширины → дерево-папки слева ~280px (Тип → Категория → карточки, drag-drop, крошки) → центральная читаемая колонка ~700–760px → правый авто-TOC ~260px → тумблер «Чтение/Широкий»**. Снимает «узость» (расширяется хром, не строка) и «нет папок» разом. Граф-вид и landing-страница раздела — отдельные фазы.

### 5.3. Таксономия

**Рекомендация:** 4 типа оставить (они концептуально различны и заполняются), но:
- Свести дубль: «Шаблоны процессов» (вкладка) и «Процессы» (фильтр) — в один раздел «Процессы» дерева.
- Чипы-счётчики синхронизировать с активным фильтром (или явно подписать «всего в базе» vs «найдено») — убрать «9 политик / Всего: 1».
- «Политики» оставить типом (реально извлекаются), но в дереве показывать пустые типы свёрнуто/с подсказкой «Кора добавит, когда обсудите».
- Нейминг папок (предложение): **Регламенты · Процессы · Инструкции · Политики · Стандарты** (стандарт — это `category` внутри Regulation, можно отдельной веткой).

### 5.4. Ручная загрузка
**Рекомендация:** пробросить `docType → signalTypeHint` в `DocumentIngestAdapter` (механизм уже есть), чтобы пометка типа при загрузке **детерминированно** создавала карточку нужного типа, и она шла в общий триаж (та же «перепроверка»). Малый почин, закрывает разрыв §2.6.

## 7. Рекомендация (синтез)

Делать **в порядке ROI**, фазами:

1. **Рендер-фиксы ширины/типографики** (C из 5.2) — самый дешёвый видимый эффект, не зависит от бэка: колонка ~720px, тело 16–18px, line-height 1.5–1.6. Можно отдельной мелкой правкой ещё до редизайна.
2. **Промпт-фикс форматтера** (A из 5.1) — структура на создании карточки + constrained-инструкция. Корень «стены текста».
3. **Backfill старых карточек** (B из 5.1) — разовый прогон на дешёвой модели.
4. **Редизайн раскладки** (B из 5.2) — дерево слева + wide shell + TOC + тумблер, на новом дизайн-языке `/redesign`.
5. **Проброс docType→signalTypeHint** (5.4) — починить ручную загрузку.
6. **Таксономия/счётчики** (5.3) — свести дубли, синхронизировать чипы.
7. **(Обгон, позже):** граф-вид, landing-страница раздела с аннотированными строками, усиление сигналов доверия.

## 8. Открытые вопросы владельцу (каждый с рекомендацией)

1. **Форматтер — переписываем промпт или включаем компилятор на create?**
   *Рекомендация:* зашить markdown-каркас в промпт + включить `compile-org-document` на создании. *Почему:* корень в том, что структура не собирается на первой версии; компилятор уже умеет нужные шаблоны типов — его надо просто вызвать раньше. Cache-friendly, без второго хопа.
2. **Ручная загрузка: достаточно ли «docType→signalTypeHint», или нужен ещё прямой путь «создать карточку из текста» в UI?**
   *Рекомендация:* сделать оба — проброс (закрывает загрузку файлов) + кнопка «Добавить регламент вручную» в дереве (для тех, кто просто хочет вписать текст). *Почему:* ваш ментальный сценарий «напишу, что это регламент» должен работать буквально, а не зависеть от LLM.
3. **Граф-вид — в этот редизайн или отдельной фазой потом?**
   *Рекомендация:* потом, отдельной фазой. *Почему:* это обгон-преимущество, но он не нужен, чтобы снять боль «узко/нечитаемо»; не раздувать первый релиз.
4. **«Политики» и «Стандарты» — отдельные ветки дерева или свернуть редкие?**
   *Рекомендация:* показывать все 5 типов в дереве, пустые — свёрнуто с подсказкой. *Почему:* честнее («Кора умеет, появится когда обсудите»), чем прятать.
5. **Светлая тема** (вы планировали дизайнить отдельно) — закладывать токены сразу в редизайн базы знаний?
   *Рекомендация:* заложить парные токены (`bg-*` + `text-*-fg`), но визуал светлой темы — вашим дизайном позже. *Почему:* не переделывать потом.

## 9. Допущения и риски

- `[ASSUMPTION]` Включение компилятора на create не сломает throughput воркера (доп. LLM-вызов на каждую новую карточку). Проверить: нагрузка очереди `core.specialist-routing` + бюджет LLM. *desirability high / feasibility medium.*
- `[ASSUMPTION]` Backfill старых карточек на `deepseek-v4-flash` не исказит факты при constrained-промпте. Проверить на выборке вручную перед массовым прогоном. *feasibility medium.*
- **Риск faithfulness:** любой переформат — шанс «додумать». Снижается жёсткой инструкцией «только структурируй» + провенанс-цитаты остаются (sources не трогаем).
- **Риск scope-creep редизайна:** граф-вид/landing/сигналы доверия легко раздувают релиз. Держать в фазе 7.
- **Промпты НЕ admin-editable** — правка форматтера = code-commit + выкат (не из админки). Это ок, но учесть в ТЗ.
