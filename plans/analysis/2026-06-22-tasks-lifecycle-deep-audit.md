## 0. Короткий ответ на главный вопрос

**Почему случилась 404 «не нашёл сотрудника».** Ассистент перевёл фразу «поставь задачу Сергею» в вызов `assign_task` и передал имя **в дательном падеже** — «Сергею». Резолвер исполнителя на проде матчит имя **буквально** (равно / начинается с / содержит), падежи не разворачивает → «Сергею» ≠ «Сергей» → `not_found`. И тут ключевое: в коде `assignTask` резолв исполнителя стоит **до** создания задачи, и при `not_found` бросается `404`, при двух тёзках — `409`. **Задача не создаётся вообще** ([me-tasks.service.ts:100-119](../../backend/src/modules/tracker/services/me-tasks.service.ts#L100-L119)).

**Почему «уже чинили, но воспроизвелось».** Фикс склонений (`beb39c85`) и вся «петля задача→решение» лежат на ветке `feature/2026-06-22-task-loop-and-qa-fixes`. Эта ветка **не влита в `dev`**, а прод собирается с `dev` → на проде до сих пор старый буквальный резолвер. Фикс реально написан, но не выкачен.

**Почему это не закрывает вашу мысль до конца.** Даже фикс склонений лечит только «чаще находит правильного человека». Когда имя реально неизвестно или неоднозначно — `assignTask` **по-прежнему отвечает ошибкой**, задача не создаётся, уточняющий вопрос «на кого повесить?» через probe **не поднимается**. Желаемое вами поведение — «создать задачу всегда, потом спросить кому» — **не реализовано ни в коде, ни в ТЗ ветки**. Это главный архитектурный пробел (§3, §5).

## 1. Карта подсистемы: тут НЕ одна система задач, а две, и два резолвера

Это корень большинства путаниц.

| | Конвейер A — **Issue** (трекер) | Конвейер B — **Task** (чаты) |
|---|---|---|
| Сущность | `Issue` (+ `IntakeIssue` как пред-слой) | `Task` (+ `TaskSource`) — отдельная таблица |
| Источник | Встречи (транскрипт) + помощник/ручной ввод | Переписки chatbox / Bitrix24 |
| Запуск | Событийно: после AI-анализа встречи ([analyze.worker.ts:399](../../backend/src/modules/ai/workers/analyze.worker.ts#L399)) | Суточный крон в полночь ([chatbox-analyze.cron.ts:27](../../backend/src/modules/chatbox/chatbox-analyze.cron.ts#L27)) — **это и есть «раз в сутки из чатов»** |
| Фильтр качества | Да, жёсткий quality-gate (см. §2) | Нет quality-gate |
| Где видно | `/intake` → доска проекта | отдельный слой `Task` |

**Эти два конвейера не сходятся.** Cross-source-дедуп в чатах дедуплицирует только среди `Task`, не видит трекерных `Issue` ([cross-source-task-dedupe.service.ts:228](../../backend/src/modules/chatbox/cross-source-task-dedupe.service.ts#L228)). Одна и та же задача, прозвучавшая на встрече и в чате, родит и `Issue`, и `Task` в двух разных местах UI. Продуктовый вопрос: либо чаты тоже гнать через `IntakeIssue→Issue`, либо явно объявить `Task` пред-трекерным слоем и сделать промоут `Task→Issue`.

**Два резолвера исполнителя:**
- `tracker/services/assignee-resolver.service.ts` — для интерактивного назначения (помощник, `assign_task`). **Строгий**: не нашёл → 404.
- `knowledge-core/services/task-assignee-resolver.service.ts` — для задач из встреч. **Мягкий**: не нашёл → `assigneeUserId=null`, задача создаётся без исполнителя ([task-assignee-resolver.service.ts:90-91](../../backend/src/modules/knowledge-core/services/task-assignee-resolver.service.ts#L90-L91)).

Поведение рассогласовано: один путь теряет задачу с ошибкой, другой создаёт без исполнителя.

## 2. Извлечение задач (откуда забираются)

### Конвейер A (встречи) — пошагово
1. AI-анализ встречи завершён → `MeetingExtractActionsService.extract` (один раз на встречу, best-effort).
2. LLM (`taskType:'meeting-extract-actions'`) тянет action items из транскрипта + чата комнаты.
3. Резолв исполнителя — только по участникам встречи; проект — по токенам в названии встречи.
4. **Quality-gate** ([task-quality-gate.util.ts:141-149](../../backend/src/modules/tracker/services/task-quality-gate.util.ts#L141-L149)): для встречи пропускает, только если форма «не вопрос/намерение» **И** (есть исполнитель **ИЛИ** есть срок).
5. Прошло → `IntakeIssue(pending)` (идемпотентно по sha1) → очередь авто-триажа.
6. Авто-триаж ([intake-auto-triage.worker.ts](../../backend/src/modules/tracker/workers/intake-auto-triage.worker.ts)): второй LLM-проход, авто-приём в `Issue` при `confidence ≥ 0.75` И есть исполнитель И есть проект И не дубль. Иначе висит на `/intake` для человека.

### 🔴 Прямое нарушение вашего «задача должна создаться в любом случае»
**Quality-gate тихо ВЫБРАСЫВАЕТ поручение встречи без ответственного И без срока** ([meeting-extract-actions.service.ts:340-354](../../backend/src/modules/tracker/services/meeting-extract-actions.service.ts#L340-L354)). Типичный кейс «надо сделать лендинг» (нет owner, нет срока) → `IntakeIssue` **не создаётся вообще**, только `skipped++` и лог. Задача исчезает без следа в UI. Это сознательный антиспам трекера, но он прямо противоречит вашему требованию.
→ **Фикс:** для AI-источника не отбрасывать, а всегда создавать `IntakeIssue(pending)` с пустым исполнителем — пусть висит на `/intake` как «требует разбора»; gate использовать как пометку `lowQuality`, а не как drop.

### Конвейер B (чаты) — «раз в сутки»
- Парные суточные кроны в полночь (UTC процесса ≈ **03:00 МСК**): `chatbox-sync` (синхронизация сообщений) + `chatbox-analyze` (анализ закрытых сессий). Аналогичная пара для Bitrix24.
- Воркер: summary сессии → кормит граф знаний → `extractTasks` создаёт строки в таблицу `Task`.
- **Извлечение задач из чатов ВКЛЮЧЕНО по умолчанию** (`CHATBOX_TASK_EXTRACTION_ENABLED = true`, [env.schema.ts:256](../../backend/src/common/config/env.schema.ts#L256); cron-агент ошибочно прочитал `?? false` в воркере как дефолт — это лишь null-guard).
- Quality-gate тут не применяется. Если у Org нет владельца — весь набор задач из переписки **молча теряется** ([chatbox-analyze.worker.ts:262](../../backend/src/modules/chatbox/chatbox-analyze.worker.ts#L262)).

### Прочее
`autoAcceptSources` (селективный авто-приём) по умолчанию **пуст = разрешено всем источникам** — то есть авто-приём фактически глобальный, не «только встречи».

## 3. Назначение задачи на человека + баг 404 (ядро запроса)

### Полный путь «поставь задачу Сергею»
Помощник (LLM выбирает `assign_task`) → confirm-гейт → loopback `POST /api/v1/me/tasks/assign` → `MeTasksController.assignTask` → `MeTasksService.assignTask` → `AssigneeResolverService.resolve(имя)`.

### Точка 404
[me-tasks.service.ts:100-119](../../backend/src/modules/tracker/services/me-tasks.service.ts#L100-L119): резолв **до** создания (строка 100). `not_found` → `404 assignee_not_found` (строка 102), `ambiguous` → `409 assignee_ambiguous` (строка 112). `issues.create` — только при `resolved` (строка 133). До создания не доходит — **задача не сохраняется**. Ошибка скармливается обратно LLM, который её пересказывает («не нашёл сотрудника, уточните имя» — это и есть ваше «ты, может, остался поискать»).

### Почему ломалось склонение
На `dev` `normalizeName` = trim+lowercase+схлоп пробелов, **без морфологии** ([assignee-resolver.service.ts:10-12](../../backend/src/modules/tracker/services/assignee-resolver.service.ts#L10-L12)). Матчинг: `===` → `startsWith` → `includes`. «сергею» vs «сергей»: ни одна проверка не срабатывает (запрос длиннее и расходится окончанием) → `not_found`. `translit.ts` тут **ни при чём** — это транслитерация для slug проектов, к именам не относится.

### Состояние фикса (важно для понимания «почему воспроизвелось»)

| | `dev` (= прод) | ветка `feature/2026-06-22-task-loop-and-qa-fixes` |
|---|---|---|
| Склонения имени | НЕТ (буквальный матч) | **ЕСТЬ** — `declensionEquivalent` через новый `common/text/levenshtein.ts` + ступенчатый матч (точно → токен+склонение → startsWith → includes), ё→е, чтение `User.name` |
| Порог нечёткости | — | крутилка `tracker.assigneeMatchMaxEdits` (AdminSetting, дефолт 2) |
| 404/409 при неизвестном/неоднозначном | да | **тоже да** (фикс лишь чаще находит, поведение «создать+спросить» НЕ добавлено) |
| Петля «выполнил/прогресс» | нет | есть (`completeTask`/`reportTaskProgress`, /actions в навигации, видимость исполнителю) |

Ветка реализована (ТЗ `plans/tz/2026-06-22-task-resolution-loop-and-cross-channel-completion.md`, коммиты `beb39c85`/`a3baba64`/`bd7e126c`/`f1dcaada`), но **не в `dev` и не в проде**. Первый и самый дешёвый шаг — довести ветку до прода.

### 🔴 Глубинный пробел: нет «создать задачу + спросить на кого»
Даже на ветке `assignTask` при `not_found`/`ambiguous` бросает ошибку, а **не**:
1. создаёт `Issue` в «Входящих» без исполнителя, и
2. поднимает уточняющий вопрос (probe) «на кого повесить эту задачу?» с кандидатами.

Это ровно ваша мысль, и её в коде нет. Точка внедрения — те же строки [me-tasks.service.ts:101-119](../../backend/src/modules/tracker/services/me-tasks.service.ts#L101-L119): вместо `throw` — создать неназначенную задачу и вернуть 201 с флагом `needs_assignee` (+ кандидаты для ambiguous), чтобы помощник задал вопрос. Готовый кирпич для подсказки «по навыкам подошёл бы…» уже есть — `SkillRoutingService.suggestAssignee` (отдельный путь `suggest_assignee`, по компетенциям), но он сейчас нигде не соединён с провалом резолва по имени.

## 4. Уточняющие вопросы (probe): работают, но не про задачи

**Механизм жив и реально задаётся** (не зависает): единая точка `ProbeService.suggest` → серия гейтов (policy-silent, точный и семантический дедуп, rate-limit, cold-start, value-gate по приоритету, nudge) → BullMQ-воркер → `conversational.sendNotification('probe.question')` в каналы **Telegram / MAX / кабинет**. Ответ ловится, классифицируется LLM, кормит граф, выводит правило subject-memory, шлёт «Спасибо, записано». Master-switch нет; shadow→canary→active — это только про выученные правила subject-memory, не про сами вопросы.

### 🔴 Probe НЕ интегрирован с назначением задач
Среди ~50 reason-кодов ([probe-reason-labels.ts](../../backend/src/modules/probe/probe-reason-labels.ts)) **нет ни одного про «не определён исполнитель задачи»**. Источники probe — только фоновые анализаторы графа (решения без автора, регламент без владельца, факт устарел…). Сценарий «поставь задачу <неизвестное имя>» в probe **не заходит** — он обрабатывается в трекере синхронной ошибкой 404/409. Поэтому Кора **не спрашивает «на кого повесить?»**, а отказывает.
→ **Фикс:** добавить reason `task.assignee_unresolved`/`task.assignee_ambiguous`, в `assignTask` на ветках not_found/ambiguous звать `probeService.suggest` (получатель — автор, payload — название задачи + кандидаты), **и** научить `probe-response.handler` исполнять ответ — реально проставлять выбранного исполнителя (сейчас handler только кормит граф, действий по карточке не делает; это отдельный пробел [probe-response.handler.ts:88-148](../../backend/src/modules/probe/probe-response.handler.ts#L88-L148)).

### ⚠️ «Громкость» probe сильно прижата
Многие источники ставят `priorityHint≈0.4` → `priority≈40`, а порог push `immediatePushMinPriority=70`. То есть масса поводов по умолчанию **не пушится, уходит в дайджест** — может читаться как «вопросы не приходят». Стоит свериться с реальным распределением через `/probe/control` и при необходимости поднять приоритет важным поводам.

## 5. Решения, «сделано», движение по задаче

- **Решения** извлекает специалист графа `specialist-3-3-decisions` (LLM → `Decision`), либо вручную. Линковка к задаче — по общим блокам-источникам (`DecisionTaskLink{derived}`), но **только в момент создания задачи из intake**. Обратной стороны нет: решение, появившееся ПОСЛЕ задачи по тем же блокам, к ней не привяжется ([decision-task-link.util.ts](../../backend/src/modules/tracker/services/decision-task-link.util.ts)).
- **Карточка прогресса** (`IssueProgressUpdate`): суточный крон **07:00** ([progress-auto-draft.cron.ts:55](../../backend/src/modules/tracker/workers/progress-auto-draft.cron.ts#L55)) по задачам «в работе» собирает сигналы (чек-лист / смена статуса / упоминания «сделал» из графа), при ≥2 сигналах LLM пишет черновик «что сделано / что дальше», статус `pending` — **требует подтверждения человеком**. На ветке это уже переведено на **событийный** триггер (не только крон) и снят фильтр «только начатые».
- **Карточка «сделано»** (`TaskClosureCandidate`): событийно — когда из разговора приходит «сделал/готово», система семантически (embedding + KNN ≥ 0.85 + LLM-верификатор) находит открытую задачу и заводит **обратимый** кандидат «Похоже, выполнено». Issue **не закрывается автоматически** (R13). Закрывает человек, подтверждая кандидата ([pending-actions.service.ts:466](../../backend/src/modules/pending-actions/services/pending-actions.service.ts#L466)).
- **Замыкания «решение внедрено → задача закрыта» нет**: `Decision.status='implemented'` в авто-пути нигде не выставляется; закрытие задачи использует семантический матч, а не связь с решением. Контур «доля доведённых решений» для владельца разомкнут.

⚠️ На `dev` кандидаты закрытия видит **только owner/admin** — отсюда «Ждёт подтверждения N» копится у владельца, хотя «сделал» обычно знает исполнитель. **На ветке это исправлено** (видимость исполнителю своих задач, Ф4).

## 6. Напоминания утром/вечером (ваш сценарий с сотрудником)

Тут несколько независимых механизмов, и важно понимать, что именно сотрудник реально получает.

### Что есть утром
1. **Telegram-дайджест задач** ([telegram-digest.cron.ts](../../backend/src/modules/conversational/adapters/telegram-bot/telegram-digest.cron.ts)) — реальный список задач (секции: задачи / спринт / **зависшие**), локальные 9:00, `priorityTier:1` (пробивает тихие часы), пропуск выходных/праздников/отпусков. **Но только Telegram** — без привязки TG сотрудник его не получит.
2. **«Твой день»** ([personal-daily-brief.cron.ts](../../backend/src/modules/operations/workers/personal-daily-brief.cron.ts)) — кабинет (`/me/daily-brief`) всегда + push. Содержит мои задачи / обещания / блокеры. **Две дыры:** (а) задачи берутся только с `dueDate ≤ конец дня` ([personal-daily-brief.service.ts:155](../../backend/src/modules/operations/services/personal-daily-brief.service.ts#L155)) — **задачи без срока в сводку не попадают**, а помощник часто создаёт задачи без срока; (б) push идёт `priorityTier:2` → **режется тихими часами**, если окно их покрывает 9:00 (бывает на кастомных настройках), в отличие от чек-ина, которому подняли tier 1.
3. **Чек-ин-планёрка** ([daily-checkin-prompt.cron.ts](../../backend/src/modules/operations/workers/daily-checkin-prompt.cron.ts)) — открытый **вопрос** «Какие 1-3 задачи на сегодня? блокеры?», не список. `tier:1`.

### Что есть вечером
- Чек-ин 18:00 — открытый вопрос «Что удалось закрыть? блокеры на завтра?». **Не** сверяет план с фактом и **не** называет незакрытую задачу.
- Ближайшее к вашему сценарию «отчитался, но по задаче Y ничего не сделал» — `rulePlanItemOverdue` ([proactive-watcher.service.ts:481](../../backend/src/modules/proactive/services/proactive-watcher.service.ts#L481)): сравнивает утренний план и вечернее «сделано». **Но порог — 30 дней** и крон раз в 6 ч → это ретро-напоминание о старом плане, **не** вечерняя сверка «сегодня».
- **«Ты обещал — выполнил?»** ([commitment-followup.cron.ts](../../backend/src/modules/operations/workers/commitment-followup.cron.ts)) — шлёт автору вопрос и эскалацию руководителю «сотрудник молчит про обещание». **Но работает по обещаниям (IdeaBlock commitment), а не по задачам трекера.**

### Зависшие/просроченные
- `issue-overdue-detector` (09:00) находит просроченные Issue — **но только по `dueDate`** и **никому из людей не шлёт**: эмитит доменное событие в граф, исполнитель push/in-app о просрочке **не получает** ([tracker-emitter.service.ts:144](../../backend/src/modules/tracker/services/tracker-emitter.service.ts#L144)).

### 🔴 Сквозная дыра
Задача, назначенная **без срока**, невидима почти всем напоминаниям: нет в «Твой день» (фильтр по dueDate), никогда не «просрочена», не покрыта commitment-followup (это про обещания). Сотрудник может её просто не увидеть.

### Тихие часы и каналы
- Тихие часы режут **только push** (Telegram/MAX/почта); кабинет (in_app) идёт всегда. Дефолт окна 22:00→08:00, bypass при `priorityTier===1`/critical ([notification-budget.service.ts:50,67](../../backend/src/modules/conversational/notification-budget.service.ts#L50)).
- Надёжно для рядового работает **только кабинет**. Telegram — опционально (после привязки). Почта в политику чек-инов/проактивных уведомлений **не входит**.
- `pending-actions-reminder` («Ждёт подтверждения N») шлёт **только в Telegram** — без TG не приходит вовсе.

**Что есть:**
- Перегруз по людям — `load/by-person` (порог 8 из AdminSetting), уровни overload/normal/idle ([execution-dashboard.service.ts:315](../../backend/src/modules/dashboard/services/execution-dashboard.service.ts#L315)). Единственное явное «перегружен».
- План-факт по людям — `workload` (open/inProgress/overdue/completed7d) + `goal-vector/by-person` (вклад в цель).
- Зависшие/риск — `tasksWithoutMovement` (>3 дней без активности), `tasksAtRisk`, `activityColor`, `issue-chains` (задача держит задачу) — **но всё это живёт только внутри спринта/цикла**. Без спринтов руководитель зависших задач не видит.
- Объяснимость «что/зачем/почему» — есть в AI-нарративах спринта/директора и в `people-at-risk.topReason` («N просроченных обещаний — помогите расставить приоритеты»).

**🔴 Пробелы для «вижу кто что и где затык»:**
- Объяснимость вклада в цель **посчитана, но выброшена**: `goal-vector-tracker` пишет текстовые причины в `signalsJson`, а дашборд их не читает ([execution-dashboard.service.ts:160-180](../../backend/src/modules/dashboard/services/execution-dashboard.service.ts#L160-L180)) — руководитель видит «netScore −0.7 вниз», но не «почему».
- Нет **кросс-проектного** экрана зависших задач (только в спринте).
- Два разных счётчика «нагрузки» (`workload` vs `load/by-person`) дают расхождение цифр на одного человека.

## 8. Сценарий «отдел дизайна сделать дизайн / в концерне заказать канцелярию»

**Не работает как «задача на отдел».** «Обучение компании» в коде — это профиль компании (`company-foundation`) и онбординг, **не** канал приёма задач. Реплика идёт через помощника (concierge), и:
- Если LLM выберет `assign_task` (а «сделать/поручить» к этому склоняет, и промпт прямо велит передать имя «как назвал пользователь» — [concierge-respond.prompt.ts:47-48](../../backend/src/modules/concierge/prompts/concierge-respond.prompt.ts#L47-L48)) → резолвер ищет **человека** по имени «отдел дизайна», не находит → **404 «уточните имя»**. Система принимает название отдела за опечатку в имени.
- Если выберет `suggest_assignee` → подберёт **одного** человека по компетенциям; жёстко ограничиться отделом по названию не может (`departmentId` требует CUID, которого у LLM нет; инструмента «название отдела → id» в карте нет).

**Пробелы:** (а) резолвер не отличает «имя человека» от «отдел/роль»; (б) нет резолва «отдел дизайна» → departmentId; (в) нет понятия «задача на отдел/роль» в данных (Issue хранит только userId); (г) промпт гонит название отдела в тупик 404. **Это продуктовая развилка:** поручать отделу целиком (новое поле адресата + уведомление всем) или всегда сводить к одному человеку через подбор+подтверждение.

## Приложение. Полная таблица кронов (временной каркас)

ScheduleModule без timeZone → фикс-час по **UTC** процесса (для РФ +3ч). Уведомления-в-окне (чек-ин/telegram-digest/«Твой день»/pending-reminder) тикают ежечасно и сравнивают **локальный** час сотрудника — у них пояс корректный.

|---|---|---|
| chatbox-sync / chatbox-analyze | 00:00 UTC | «раз в сутки из чатов»: синхронизация + анализ → граф + Task |
| specialist-3-3-probe | 05:00 UTC | probe по решениям без автора/просроченным |
| recurrence-materialize | 06:00 UTC | материализация повторяющихся задач |
| goal-alignment-low | пн 06:00 UTC | nudge «много задач без цели» |
