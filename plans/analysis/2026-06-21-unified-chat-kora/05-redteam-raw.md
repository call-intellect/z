## Состязательная проверка (red-team) варианта B

### 1. Контекст проверки

Вариант B — «единый экран, разные движки»: тикетная поддержка на таблицах `Issue`/`IssueMessage`, командный чат на новых `Conversation`/`Message`, оба под одним UI «Сообщения». Адаптеры на бэкенде приводят оба хранилища к единому list-DTO. Ниже — честная попытка опровергнуть это решение данными из реальных продуктов.

---

### 2. Как лидеры рынка решали «командный чат + поддержка»

#### Intercom — единое ядро `Conversation` с типизированными частями

Intercom хранит клиентское сообщение и внутреннюю заметку агента **в одном объекте** `conversation_parts[]`. Различие — поле `part_type`: `"comment"` / `"note"` / `"note_and_reopen"`. Никакого отдельного хранилища для внутреннего чата нет. Правило «один объект, разные типы частей» действует на уровне схемы, а не через адаптерный слой над двумя таблицами.
> Источник: [Intercom Conversation Model, developers.intercom.com, 2025](https://developers.intercom.com/docs/references/2.1/rest-api/conversations/conversation-model) — дата проверки 2026-06-21 — тег: `#unified-core`

#### Missive — один объект Conversation для email и внутреннего обсуждения

Missive использует **одну модель Conversation** для входящей почты клиента и внутренних комментариев команды. Разграничение — через `access scope` (shared/private) и визуальные маркеры, не через отдельную таблицу. API открывает единый список разговоров без разделения хранилищ.
> Источник: [Missive Conversations Docs, missiveapp.com](https://missiveapp.com/docs/core-features/conversations) — дата проверки 2026-06-21 — тег: `#unified-core`

#### Slack — болезненный урок разделения каналов/групп/DM

Slack изначально держал публичные каналы в таблице `channels` (C-идентификатор), приватные группы в таблице `groups` (G-идентификатор), DM — отдельно. Итог через несколько лет: «distinct (but often duplicative) logic for channels, groups and direct messages, which added greater complexity to each feature or performance improvement». Потребовалась масштабная операция: новый `conversations.*` API, отказ от ID-схемы privacy, миграция клиентов и партнёров. Платформа Slack Grid дополнительно показала, что дублирование org-level данных (DM) в разных workspace datastores порождало **стойкие баги синхронизации** при неуспешной репликации.
> Источник: [Slack Engineering — How Slack Built Shared Channels, slack.engineering](https://slack.engineering/how-slack-built-shared-channels/) — дата проверки 2026-06-21 — тег: `#unified-migration-cost`
> Источник: [InfoQ — Changing the Model: Why and How We Re-Architected Slack](https://www.infoq.com/presentations/slack-rearchitecture/) — дата проверки 2026-06-21 — тег: `#dual-storage-bugs`

#### Zendesk — «side conversations» как эталонный провал раздельного хранилища под единым UI

Zendesk сделал именно то, что предлагает вариант B: главный тикет в одном хранилище, боковой разговор (внутренний) — в другом, оба показываются агенту на одном экране. Задокументированные последствия:

- **Поиск не работает**: `The Side Conversations tab might show 0, even if there are side conversations with the words you searched for` — контент боковых разговоров недоступен в глобальном Zendesk Search.
- **Аналитика нет из коробки**: `There isn't a dataset in Explore that allows you to report on side conversations out of the box` — пользователи вынуждены делать workaround через теги.
- **Рассинхрон полей**: child-тикет копирует поля от родителя только в момент создания; при обновлении родителя данные не синхронизируются. Изменение внешнего ID ребёнка необратимо рвёт связь.
- **Дублирование триггеров**: при включении child-tickets нотификации срабатывают дважды.
- **Репликация не полная**: triggers не работают на closed/archived тикетах, поэтому ответы в боковых разговорах старых тикетов уходят незамеченными.

> Источник: [Zendesk — About side conversations](https://support.zendesk.com/hc/en-us/articles/4408844206746-About-side-conversations) — дата проверки 2026-06-21 — тег: `#dual-storage-real-failures`
> Источник: [Zendesk — Can I report on side conversations?](https://support.zendesk.com/hc/en-us/articles/4412384153754-Can-I-report-on-side-conversations) — дата проверки 2026-06-21 — тег: `#search-analytics-gap`
> Источник: [Zendesk — Using side conversation child tickets](https://support.zendesk.com/hc/en-us/articles/4408836521498-Using-side-conversation-child-tickets) — дата проверки 2026-06-21 — тег: `#sync-inconsistency`

#### Front — единая Conversation для почты и internal discussion

Front строит весь продукт на одном типе Conversation, который вмещает внешние email-треды и внутренние комментарии (`@mentions`, private notes). Разница реализована через поле visibility/access внутри объекта, а не через отдельный движок.
> Источник: [Front — Email Management, front.com](https://front.com/email-management) — дата проверки 2026-06-21 — тег: `#unified-core`
> Источник: [Front Review 2026, thectoclub.com](https://thectoclub.com/tools/front-review/) — дата проверки 2026-06-21 — тег: `#unified-core`

### 3. На чём именно ломается вариант B

#### 3.1 Единый read-cursor невозможно поддержать корректно

Два хранилища — два независимых счётчика непрочитанного. Чтение Issue-сообщения не обнуляет счётчик в Conversation и наоборот. Единый `unread_count` в list-DTO потребует агрегации двух асинхронных источников при каждом запросе списка. При сетевой ошибке одного из них пользователь видит ghost-badge или пропускает сообщение. Это точный паттерн, который Slack называл «sync problems when updates failed to propagate» в своей Grid-архитектуре.

#### 3.2 Поиск и аналитика — дублирование индексов

Полнотекстовый поиск по «Сообщениям» потребует union-запроса к двум индексам (или двум таблицам) с последующей merge-сортировкой по `created_at`. Это либо медленно, либо требует третьего, синтетического индекса, который нужно держать в синхронизации. Именно этот gap зафиксирован у Zendesk side conversations: глобальный поиск видит только один тип, второй слепой.

#### 3.3 Пагинация через адаптер — cursor-hell

Cursor-based pagination (`cursor: last_item_id`) не работает поверх двух независимых источников: у `Issue` и `Conversation` разные первичные ключи и временные метки из разных последовательностей. Offset-pagination через UNION деградирует по производительности при > 10 k записей. Придётся либо денормализовать всё в единую timeline-таблицу (что де-факто переходит к варианту A), либо смириться с ограниченным окном списка.

#### 3.4 Расхождение схем прочтения и уведомлений

`Issue` уже имеет статусы (`open`/`pending`/`resolved`) и SLA-поля. `Conversation` в новом ядре их не имеет. Адаптер может скрыть разницу в list-DTO, но при попытке unified-фильтра по статусу («показать только открытые») придётся либо эмулировать отсутствующий статус в чате (семантическая ложь), либо показывать чат всегда без статуса (потеря информации). Это точный механизм «schema divergence» — каждая новая фича в одном движке требует решения: «нужно ли добавить эквивалент в другой».

#### 3.5 Дублирование кода нотификаций

Push-уведомления, email-дайджесты, badge-счётчики в header — всё это придётся писать дважды (по одному на движок) или городить ещё один абстракционный слой поверх двух. Slack прошёл через это и в итоге объединил модели именно потому, что «each feature or performance improvement» дублировалась.

#### 3.6 AI-граф получает неоднородные данные

В контексте Коры критично: `ingest-pipeline` будет получать сообщения двух разных схем. Это либо два отдельных `document.adapter.ts` с разной логикой извлечения сущностей, либо один, насилующий общий контракт через `if type === 'issue'`. Второй путь — прямая дорога к silent-quality-degradation в графе.

### 4. Steelman альтернатив

#### Вариант A — единое ядро `Conversation/Message` на всё, поддержку мигрировать

**Честное усиление:** Intercom, Missive, Front, Pylon — все они сделали именно это и не сожалеют. Единый объект с полем `conversation_type: 'support' | 'internal'` и `visibility` решает поиск, аналитику, read-cursor, пагинацию и AI-граф одним движением. Slack потратил годы на переход от раздельных моделей к единой `conversations.*`-модели — именно потому, что раздельные накапливали долг при каждой новой фиче. **Главный контраргумент в пользу A:** у Issue уже есть продуктовые инварианты (SLA, статусы, привязка к клиенту), и «мигрировать» означает либо перетащить их в Conversation (усложнить схему), либо потерять.

#### Вариант C — полностью раздельно (две отдельные фичи)

**Честное усиление:** честнее с точки зрения пользователя — разные UI-паттерны для разных задач (тикет vs чат). Нет иллюзии единства, нет hidden drift, нет cursor-hell. Zendesk выбрал C для основного тикета, и пока не пытается притворяться, что side conversations это то же самое — хотя цена: пользователи страдают от разрыва. **Главный контраргумент:** для Коры это означает два отдельных раздела навигации, два read-state, два поиска — ровно то, от чего вариант B пытается уйти.

### 5. Когда вариант B был бы НЕправильным выбором

B — неправильный выбор, если:

1. **Поиск по всей переписке** является ключевым продуктовым обещанием (Zendesk доказал: два хранилища = слепые пятна в поиске).
2. **AI-граф** должен обрабатывать оба типа сообщений по единой логике без разветвления по типу источника.
3. **Аналитика** (дашборд CEO/пульс компании) агрегирует данные из обоих типов в одном запросе.
4. **Команда маленькая** (в Коре, по контексту, ~30 человек в продукте) — стоимость поддержки двух движков с адаптером непропорционально высока.
5. **Схемы планируют активно развиваться** — каждая новая фича потребует двойного решения (добавить в обе или только в одну).

Именно пункты 2 и 3 специфичны для Коры и делают B более рискованным, чем для универсального SaaS.

### 6. Финальный вердикт

**Вариант B устоял, но условно — с тремя красными флагами:**

Как паттерн «единый список поверх двух движков через адаптер» — это не архитектурный нонсенс. Его используют в переходный период, когда миграция к единому ядру стоит дорого. Но Zendesk side conversations — прямой доказательный пример того, что **адаптерный слой не закрывает поиск, аналитику и read-cursor без дополнительных обходных решений**, которые с каждым месяцем накапливают долг.

Для Коры конкретно вариант B несёт дополнительный риск: AI-граф — ядро продукта, и схема «два разных адаптера на ingest» создаёт расхождение в качестве извлечения знаний.

Если переходить к B, то только с жёсткими инвариантами (см. ниже). Если от B хочется уйти — Вариант A сильнее стратегически, но требует согласия на миграцию Issue в новую схему.

### 7. Обязательные инварианты для варианта B (если принят)

Чтобы B не развалился, в ТЗ должны быть закреплены следующие контракты:

| Инвариант | Почему обязателен | Аналог-провала без него |
|---|---|---|
| **Единый list-DTO через адаптеры** — `MessageThreadDto { id, type, title, lastMessage, unreadCount, updatedAt }` — оба движка обязаны реализовать интерфейс полностью, без nullable-полей, специфичных для одного | Пагинация и сортировка по `updatedAt` работают единообразно | Zendesk side conv: разные поля = разный рендер |
| **Единый read-cursor контракт** — `markRead(threadId, cursorMessageId)` должен быть атомарен внутри каждого движка, а badge в header суммирует оба через один RPC/cache-ключ с TTL | ghost-badge и пропущенные сообщения при partial failure | Slack Grid: sync failure → stale unread |
| **Единый поисковый индекс** — оба движка при записи пишут в общую поисковую таблицу `MessageSearchIndex(source_type, source_id, text, created_at)` | Поиск по «Сообщениям» возвращает результаты из обоих источников | Zendesk: side conv не в поиске |
| **Общий компонент сообщения** — в UI один `<MessageBubble>` с prop `sourceType`, без if-else в рендер-логике выше него | Визуальный дрейф при развитии | Классический «а вот у тикетов пузырь другой» |
| **Единый AI-ingest адаптер** — `IMessageSource` interface реализуют оба движка; `ingest-pipeline` работает только через интерфейс | Качество графа не зависит от типа источника | Молчаливое расхождение качества знаний |
| **Запрет прямого доступа из UI к движку** — фронтенд вызывает только `/api/v1/message-threads?type=all` через единый контроллер; никаких `/api/v1/issues` и `/api/v1/conversations` напрямую в одном экране | Адаптер не превращается в мёртвый слой при следующем рефакторе | Технический долг «адаптер обходят» через 3 месяца |
| **Схема расхождений зафиксирована** — список полей, которые есть только в Issue (`sla_due_at`, `status`, `client_org_id`) и только в Conversation (`thread_type`, `participants[]`), не скрывается адаптером, а явно маркируется `null` в DTO с документацией | Разработчик знает чего ожидать; фильтры по типо-специфичным полям не рендерятся для чужого движка | Schema drift без документации |

---

**Итог red-team:** вариант B не опровергнут принципиально, но опровергнут в форме «адаптер решает всё сам». Реальные продукты (Zendesk side conversations как отрицательный пример; Intercom/Missive/Slack как положительный пример единого ядра) показывают: адаптер — это scaffold, а не архитектура. Без семи инвариантов выше вариант B воспроизведёт Zendesk side conversations с теми же жалобами через 6–12 месяцев.
