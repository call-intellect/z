# Дедуп задач между каналами + петля «разговор → статус в трекере»

## 0. TL;DR — вердикт после состязательной проверки

**Надо — но не то и не так, как звучит в первой формулировке.**

- **Э1 (дедуп задач перед трекером): ДА, строить.** Дёшево (переиспользует уже существующий `SimilarIssuesService`), безопасно, закрывает реальный баг «5 источников → 5 задач». НО в форме **pre-create suggest-гейт** (показать похожие → слить в каноническую), не молчаливый авто-merge. Сам по себе это `table-stakes` (базовая планка рынка), рва не даёт.
- **Э2 (петля выполнение→статус): ДА, но как СИГНАЛ, а НЕ как авто-закрытие.** Авто-закрытие задачи по фразе из разговора **атаку не пережило** — это задокументированная мина доверия, от которой все лидеры рынка отказались **сознательно**. Строить: обратимый «**кандидат на закрытие**» + объяснимый сигнал доведения (в стиле Gong: «почему считаем сделанным: реплика X, +/− сигналы») + независимый детерминированный верификатор + петля reopen для измерения ошибок.
- **Каскад отмены задач при supersede решения: НЕ авто.** Только пометка «под вопросом» (review). Авто-каскад = аналог `CASCADE DELETE`, катастрофа.
- **Архитектура реконсиляции: событийно (на новый блок) + идемпотентный ключ; суточный батч — только как ЧИСТКА** перекрывающегося окна, не как основной механизм.
- **Где ров (а не догон):** не в автоматизации закрытия (её все избегают), а в **дедупе через граф ролей/людей** (кросс-канальный — этого не делает никто) и **сигнале «кто держит слово / доведение решений»**, привязанном к памяти компании. Это совпадает с фичами из аудита кабинета [[2026-06-12-product-audit-cabinet-ui-dashboards]].
- **Перепроверено по коду (проход 2, см. §11-bis): ложится чисто, рекомендации держатся.** Э2 — это **зеркало уже работающей петли обещаний** (`CommitmentResponseHandler`), не новая подсистема. 5 из 6 развилок подтверждены (3 с нюансами), Р6 (scope) переформулирована. Найдены 3 технические правки, которые ОБЯЗАНЫ войти в ТЗ: (а) **нет единого chokepoint** — задачи рождаются двумя классами путей, гейт нужен на двух уровнях; (б) **`Issue.embedding` на свежей задаче всегда `null`** (async-воркер) → дедуп не может опираться на `findSimilar(issueId)`, нужен синхронный embed кандидата + `findSimilarByVector`; (в) **Outbox/CDC в репозитории нет** → «синхронизация обратно» делается детерминированным суточным reconcile (БД — источник правды), а не push-событием.

## 1. Рамка проблемы

Две конкурирующие формулировки (намеренно не одна):

**A. «Узкая» — гигиена трекера.** Проблема в том, что одно поручение из разных каналов (встреча + Telegram + отчёт) плодит дубли задач, а выполненные задачи висят открытыми, потому что никто не закрывает их по факту разговора. → Решение: дедуп + авто-апдейт статуса.

**B. «Широкая» — рассинхрон двух миров.** Проблема структурная: у Коры **память (граф)** и **трекер (Issue)** — два параллельных мира, которые не сверяются. Память знает правду (она деду­плицировала, она «слышала», что сделано), но никогда не пишет авторитетный статус обратно; а трекер пишется из памяти только в одну сторону (создание). → Решение: не «починить трекер», а **замкнуть контур память↔исполнение с гейтом доверия**.

**Принимаем B как корневую** (A — её симптом). Это меняет проект с «фичи трекера» (которую делают все) на «контур доверия память→исполнение» (где у Коры уникальный угол).

**Кто страдает (роли Z):**
- Рядовой сотрудник — заводит дубли, не доверяет трекеру, ведёт задачи «мимо» (drive-of-usage падает).
- Руководитель/COO — не видит реального состояния: «доведено или нет» неизвестно, авто-метрика решений `approved→implemented` не срабатывает (цепочка разорвана в первом звене).
- Админ Org — тонет в «Подтверждения 47» (очередь курации без гейта).

**Метрика «решено»:**
- доля дублей задач между источниками → near-0 (при сохранении провенанса — видно, из скольких каналов поднималось);
- доля решений, доходящих до `implemented` без ручного закрытия задач, растёт;
- **reopen-rate авто-закрытых** (ложные срабатывания) ниже заданного порога — главный предохранитель;
- снижение размера очереди «Подтверждения N» (за счёт гейта, а не за счёт слепого авто-применения).

## 2. Iceberg: симптом vs корень

| Уровень | Что видно |
|---|---|
| Событие (симптом) | «5 одинаковых задач», «выполненная задача висит открытой» |
| Паттерн | каждый источник пишет в трекер независимо; экстракция льётся без гейта уверенности (Б-1..Б-7 аудита кабинета: «вопросы=задачи=отделы») |
| Структура (корень) | граф и трекер не сверяются; память — односторонний поставщик создания, не авторитет статуса; нет обратимого промежуточного состояния и петли измерения ошибок |
| Ментальная модель | «AI сам решит, что сделано, и закроет» — карго-культ автоматизации, который лидеры рынка отвергли по цене ложного закрытия |

Главный риск проекта — **зацементировать симптом**: построить авто-закрытие поверх неисправленной экстракции и масштабировать мусор. Сначала объективный гейт на **создании**, потом статус.

## 3. Дерево вопросов (MECE) — каркас будущих фаз

```
Контур «событие → задача → доведение → статус»
├── 3.1 Вход: одно ли это поручение? (дедуп ДО трекера)
│     ├── семантический матч кандидата с открытыми задачами тенанта (pgvector kNN)
│     ├── порог + LLM-арбитр на спорных + NIL («ни одна — создать новую»)
│     └── провенанс при слиянии (canonical-задача + перенос источников)
├── 3.2 Создание: это вообще задача? (гейт уверенности на СОЗДАНИИ)
│     ├── объективные детерминированные критерии (тип, явный owner/срок, источник=решение)
│     └── intent/вопрос ≠ обещание (см. ТЗ 2026-06-15)
├── 3.3 Доведение: что говорит о выполнении? (сигнал, не действие)
│     ├── детект сигналов done/blocked из разговора (уже есть в block-ingest)
│     ├── матч сигнала с конкретной существующей Issue (mention→record)
│     └── объяснимый «почему считаем сделанным» (+/− сигналы, как Gong)
├── 3.4 Применение: кто и как меняет статус? (обратимость + независимый верификатор)
│     ├── обратимый «кандидат на закрытие», не смена SoT
│     ├── независимый верификатор (не тот агент, что породил задачу)
│     └── петля reopen = измерение false-positive
├── 3.5 Каскад: отменили решение — что с задачами? (review, не авто-снос)
└── 3.6 Реконсиляция: событийно + идемпотентность + суточная чистка окна
```

Каждая ветвь → отдельная фаза ТЗ.

## 4. Baseline по коду Z (что есть / чего нет)

Сведено из выверенных по коду прогонов этой сессии (состязательно подтверждено).

**Что есть (кирпичи под решение):**
- **Дедуп в графе — `source-agnostic`** (не смотрит канал/дату, только смысл): блоки (`block-merge.service.ts:114` kNN cosine + LLM `block-distill`), сущности (`entity-merge` + `entity-resolver`), решения (`specialist-3-3` kNN pgvector + supersede, считает `raisedCount`). [verified — наш код]
- **`SimilarIssuesService.findSimilar`** — KNN pgvector HNSW по `Issue.embedding` (sim~0.82), УЖЕ существует, но вызывается только из read-эндпоинта `issues.controller.ts:399`; как гард при создании **не подключён**. [verified]
- **`decision-implementation.service.ts:117`** — суточный крон `approved→implemented`, если все связанные Issue `completedAt!=null` или есть `actualOutcomes`; связь `DecisionTaskLink` по пересечению `sourceBlockIds`. Комментарий :115 явно: «mention-based по транскриптам НЕ делаем». [verified]
- **`commitment-response.handler.ts:82`** — `@OnEvent('notification.responded')` → LLM `commitment-extract-status` → `fulfilled|missed` (только по ответу человека на probe, не по тексту встречи). [verified]
- LLM в `block-ingest.prompt.ts:475` **уже распознаёт** `task_completed/task_status_changed/done_item/commitment_status` — но создаёт только `IdeaBlock`, Issue не трогает. [verified]
- `tracker-emitter → tracker.adapter` — смена статуса Issue (вручную/API) публикуется в граф как `task_completed` (направление **трекер→граф**). [verified]

**Чего нет (дельта):**
- единой точки дедупа задач перед записью Issue (`IssuesService.create:167` пишет напрямую, без pre-create lookup); каждый из 4 источников дедупит только по своему `externalId`; [verified]
- петли «выполнено в разговоре → закрыть/двинуть существующую Issue»; [verified — греп всех потребителей сигналов пуст на писателей `issue.update`]
- связи `commitment(IdeaBlock) ↔ Issue`; [verified]
- каскада/реакции в трекере на `supersede` решения; [verified]
- гейта уверенности на создании (отсюда Б-болезни кабинета); [verified]
- у `Goal` нет вектор-колонки → дедуп целей слабый (ILIKE по 2 словам, `specialist-3-14:528`). [verified]

> Вывод baseline: **80% инфраструктуры уже на месте** (pgvector, `llm-router`, BullMQ, граф, `SimilarIssuesService`, `DecisionTaskLink`, `commitment-response`). Не хватает именно **гейта**, **обратимого состояния**, **матча сигнал→Issue** и **идемпотентного применения**.

## 5. Ландшафт аналогов

**Зарубеж — три уровня зрелости:**
1. **База (односторонний push):** Otter, Fireflies, Fathom, Read AI, Supernormal, Granola, Spinach, Circleback, tl;dv — создают задачу из action item и останавливаются. Ни дедупа, ни возврата статуса. [verified, см. источники]
2. **Двусторонний статус — только Fellow и Avoma.** Fellow: чек complete в Fellow/Asana обновляет оба; Jira auto-transition. Avoma: 2-way с CRM-полями. НО синк управляется **ручным чекбоксом/правкой**, не извлечением «сделано» из разговора. [verified / claimed]
3. **Revenue-intelligence (Gong, Clari):** извлекают next steps/обещания из звонков и — ключевое — превращают невыполнение в **явный риск-сигнал** (Gong Deal Monitor: likelihood + список +/− сигналов). Но **«no agentic execution»** — останавливаются на сигнале, не на авто-действии. [verified / triangulated]

**РФ — два лагеря, петлю не замыкает никто:**
- ИИ-секретари (НаВстрече, Таймлист, MyMeet, MTS Link, Контур.Толк, SberJazz, Kaiten AI) делают левую половину: транскрипт → задачи-**черновики** → ручная выгрузка во внешний трекер. Часто через no-code прослойку (Albato). [verified / triangulated]
- Трекеры с ИИ (Битрикс24, Пачка, Kaiten, Weeek, Yougile, Aspro) создают задачи из чата/NL. Ближе всех Битрикс24 (MCP может найти/обновить/закрыть задачу — но **строго по запросу пользователя и с подтверждением**) и Пачка (заявлен инструмент «обновления задач», детали не раскрыты). [verified / claimed]

**Ключевая находка обоих контуров:** **никто** документированно не делает (а) семантический дедуп задач между встречами/каналами и (б) авто-обновление статуса из текста **следующего** разговора. Пункт (б) лидеры избегают **намеренно** — это не отставание рынка, а защита от цены ложного закрытия.

## 6. Teardown ключевых (функционально + технически)

### Fellow — лучший референс по механике (превзойти, не скопировать)
- **Функционально (простым языком):** «дисциплинированный секретарь регулярных встреч». Невыполненные пункты переносит в следующую встречу серии; опция «linked copies» — отметил в новой → закрылось в прошлой, в списке показывается один раз. 2-way статус с Asana/Jira.
- **Технически:** перенос статуса по `email-матчу`, настройка по проекту; carry-forward по умолчанию = **новая копия (дубль)**, «linked copies» = связывание чекбоксов **внутри одной серии**, не семантический матч между источниками. Jira — `transition` по `Push status`. [verified]
- **Чего не делает (дельта Z):** completion всегда **ручной** (чекбокс); кросс-источникового дедупа нет; авто-завершения по транскрипту нет — **осознанный выбор**.

### Gong / Clari — референс «сигнала доведения»
- **Функционально:** «аналитик сделок, который замечает, что обещание провисает». Извлекает next steps, при задержке → риск-флаг с объяснением.
- **Технически:** ML на 300+ сигналах, likelihood-перцентиль, видимый список +/− сигналов. **`no agentic execution`** — не закрывает ничего сам. [verified / triangulated]
- **Дельта Z:** взять модель **объяснимого сигнала** («кто держит слово / доведение»), привязав к графу ролей и памяти — у Коры это сильнее, т.к. она владеет и графом, и задачей в одном контуре.

### Linear — референс дедупа
- **Технически:** эмбеддинги в **PostgreSQL+pgvector**, cosine, срабатывает при создании/в triage; merge **ручной** в каноническую задачу с переносом источников. Сознательно выбрали pgvector вместо выделенной вектор-БД ради maintainability. [verified] → **прямой рецепт под стек Z** (у нас pgvector уже есть).

### Битрикс24 — ближайший РФ
- **Технически:** MCP-примитивы (найти/обновить/закрыть задачу, двигать сделку) — но «**только по запросу пользователя, с подтверждением**». [verified] Подтверждает: даже самый продвинутый РФ-игрок не делает авто-замыкание.

## 8. Технические паттерны (доказательная база под развилки)

**Confidence-gate (когда AI меняет source-of-truth):**
- НЕ доверять сырому скору LLM: «0.9» ≈ 70% реальной точности, ECE до 0.43, скоры систематически переоценены. [verified] Порог двигать по **асимметрии денежной цены ошибки**, не в середину. [verified]
- Эталон **Ona**: авто-применение только при выполнении **ВСЕХ** объективных детерминированных критериев; **запрет самоклассификации** (решает не автор); разделение «одобрить» и «применить». [verified]
- Цена ложного авто-закрытия задокументирована: Zendesk (re-contact 24–48ч, падение CSAT, «налог на доверие») [verified]; stale-bot (похороненные баги, взрыв дублей, утрата доверия) [verified].
- **HITL не спасает:** человек-в-петле повышает слепое принятие (+7пп), ловит лишь 60% крупных ошибок, «не служит аварийным тормозом». [verified] → очередь подтверждений ≠ гейт; нужен **независимый верификатор**. Смыкается с feedback Z «30 человек соглашаются не вникая».

**Reconcile (событийно vs батч — ложная дихотомия):**
- Канон: at-least-once доставка + **идемпотентный консьюмер** (Inbox/dedup-таблица, ключ ULID/log-LSN, conditional write в одной транзакции с эффектом) = «эффективно-ровно-один-раз». [verified]
- **Плюс** суточный сверщик с watermark и allowed lateness, пересчитывающий **перекрывающееся окно N дней** через UPSERT — ловит опоздавшие/переоткрытые без двойного применения; совсем поздние → DLQ. [verified / triangulated]
- Outbox+CDC — чтобы статус и его трансляция в Telegram/кабинет не разъезжались (у Z уже была боль рассинхрона канала). [verified]

**Матч «упоминание → конкретная Issue»:**
- Coarse-to-fine (LELA): retrieval кандидатов (hybrid) → reranker top-k → **LLM-арбитр с обязательным пунктом NIL** «ни один не подходит» (= создать новую, не лепить top-1). [verified]
- Неоднозначность близких кандидатов: self-consistency (N проходов + majority, плато ~3) + cosine-гейт (t≈0.85); если majority не сходится или все ниже порога → **очередь курации**, не авто-привязка. [verified]

## 9. Матрица вариантов + доказательство (ADR)

### Э1 — дедуп задач перед трекером

| Критерий (ограничения Z) | A. Ничего (статус-кво) | B. Авто-merge по порогу | **C. Pre-create suggest-гейт (kNN+арбитр+canonical)** |
|---|---|---|---|
| Убирает дубли между источниками | нет | да | да |
| Риск ложного слияния | — | **высокий** (склеит разные задачи) | низкий (человек/арбитр + NIL) |
| Переиспользует наш код | — | частично | **да (`SimilarIssuesService` + `llm-router` + pgvector)** |
| Сохраняет провенанс (из скольких каналов) | нет | теряет | **да (canonical + перенос источников, как Linear)** |
| Соответствие «без слепого авто» (feedback Z) | — | нарушает | **соответствует** |
| Ров | нет | нет | слабый сам по себе; **силён через граф ролей** |

**Рекомендация Э1 = C.** Двухфазно (pgvector kNN → LLM-арбитр на спорных с NIL), результат — **предложение слияния в каноническую задачу** с переносом источников. Уникальный угол — матч не только по тексту, но и по **графу ролей/людей** (один владелец, одна сущность-проект), чего не делает никто.

### Э2 — петля «выполнение → статус»

| Критерий | A. Авто-закрытие по разговору | B. Только ручной (статус-кво Fellow) | **C. Обратимый «кандидат» + сигнал + верификатор** |
|---|---|---|---|
| Закрывает реальную боль (висящие задачи) | да | нет | да (через предложение + объяснение) |
| Риск разрушения доверия | **катастрофа** (stale-bot, ECE 0.43, вход зашумлён >35%) | нет | низкий (обратимо + reopen-петля) |
| Соответствие «intent≠обещание» / Б-болезни | нарушает (масштабирует мусор) | — | **соответствует** (гейт на создании первым) |
| Калибруемость | нет (порог вслепую) | — | **да (reopen-rate = измеренная цена FP)** |
| Совпадает с выбором лидеров | **противоречит** (все избегают) | да | **превосходит** (объяснимость + обратимость) |
| Ров | нет (все избегают авто) | нет | **да (сигнал доведения на графе памяти)** |

**Рекомендация Э2 = C.** Не менять source-of-truth автоматически. Строить:
1. **детект** done/blocked (уже есть в `block-ingest`);
2. **матч** сигнала с конкретной Issue (LELA-паттерн с NIL);
3. **независимый детерминированный верификатор** (тип=решение/поручение, явный owner/срок, источник≠реплика-вопрос);
4. **обратимый «кандидат на закрытие»** + объяснимый «почему» (+/− сигналы, как Gong);
5. **петля reopen** — измеряет false-positive, калибрует порог.

**supersede-каскад = review-пометка**, не авто-снос (аргумент `CASCADE DELETE` [verified]).

**Архитектура = событийно (на новый блок) + идемпотентный ключ; суточный батч — только чистка** перекрывающегося окна.

## 11-bis. Перепроверка по коду — ложится ли в наш код (проход 2, 2026-06-15)

Отдельный проход «только по коду»: точки интеграции, переиспользуемые кирпичи, технологическая верность. Вердикт: **ложится в основном чисто; рекомендации держатся; есть 3 обязательные технические правки и несколько новых рисков.**

### Главная находка: Э2 — это зеркало уже работающей петли, не новая подсистема
В коде **уже есть полный прецедент Э2** для обещаний:
`canonical-блок commitment_status → RouterService.emit('commitment.status_received') → @OnEvent CommitmentResponseHandler → LLM-верификатор (taskType commitment-extract-status + анти-инъекция) → resolves-ребро + обновление статуса, идемпотентно и обратимо.`
[verified — `router.service.ts:379-399`, `operations/services/commitment-response.handler.ts:82-272`]
Э2 для задач достраивается **тем же контуром**, заменив «обновить commitmentStatus» на «создать обратимый кандидат на закрытие Issue». Это сильнейший сигнал, что фича вплетается в существующую архитектуру, а не пристраивается сбоку.

### Точки интеграции (куда именно встраивать)
| Узел | Где в коде | Как ложится |
|---|---|---|
| Подписка на сигнал из разговора | `router.service.ts:230-424` (switch по signalType) | Добавить `case 'task_completed'/'task_status_changed'/'done_item'` → `eventEmitter.emit('task.completion_signalled')`. **Сейчас `done_item` = no-op, `task_completed/task_status_changed` вообще не в switch** — сигнал из разговора никуда не идёт. Идти через `emit`, НЕ `targets.add` (иначе anti-fan-out trim, `router.service.ts:174-194`) |
| Матч сигнал→Issue | `Issue.embedding` + HNSW (`postgres-init.sql:478`) | Семантический KNN. **`sourceBlockIds`-матч (как `decision-task-link.util`) НЕ годится** — блок разговора имеет свои `sourceBlockIds`, не пересекающиеся с `Issue.sourceBlockIds` |
| Обратимый «кандидат на закрытие» | `pending-actions/services/pending-actions.service.ts:99` | Новый `PendingActionsProvider 'task_closure_candidate'` (контракт count/list/confirm/snooze готов; `IntakePendingProvider` — калька). **CurationItem НЕ переиспользовать** — это очередь карточек графа, натяжка |
| Применение закрытия | `issues.service.transitionState` (category='completed') | Корректно ставит/снимает `completedAt` |
| Reopen-петля (FP-метрика) | `issues.service.ts:770-779` + `IssueActivity` | **Бесплатно** — при reopen код уже обнуляет `completedAt` и пишет `IssueActivity(status_changed)`. Метрика FP = доля авто-закрытых, вернувшихся в non-completed |
| Независимый верификатор | новый `llm-router` taskType + анти-инъекция | Прямое зеркало `commitment-extract-status` (`withInjectionGuard/wrapUserData`) |
| Суточный reconcile | `decision-implementation.cron.ts:36-118` | Готовый каркас per-Org @Cron + try/catch + kill-switch; **источник правды — БД** (надёжнее push) |

### 3 обязательные технические правки (входят в ТЗ)
1. **Нет единого chokepoint создания задач** [refuted исходный тезис]. Задачи рождаются **двумя классами путей**: (A) через `IntakeIssue` + auto-triage (telegram/in_app/meeting/checkin/api/concierge) и (B) **прямой `IssuesService.create` в обход intake** — email (`project-inbox.service.ts:267`), self-task помощника (`me-tasks.service.ts:64`), accept-ветки. → Гейт дедупа **на двух уровнях** (основной на входе IntakeIssue + тонкий внутри `issues.create` до транзакции), иначе email/self-task без покрытия (нарушение «чини весь класс»).
2. **`Issue.embedding` на свежей задаче всегда `null`** [verified, критично]. `issues.create` делает `void enqueueEmbed(...)` (fire-and-forget), реальный расчёт — async `IssueEmbedWorker`. Поэтому `create → findSimilar(issue.id)` вернёт `[]`. → Нужны: (а) синхронный embed кандидата на лету (`EmbeddingFallbackService.embed([title+desc])`); (б) новая перегрузка `findSimilarByVector(tenantId, embedding, opts)` (текущий `findSimilar(issueId)` принимает только id существующей задачи).
3. **Outbox/CDC в репозитории нет** [refuted «синхронизация без рассинхрона»]. Доставка событий трекера — `EventEmitter2` fire-and-forget, код прямо признаёт потерю при сбое. → «Статус обратно» делать **детерминированным суточным reconcile** (пересчёт по факту БД, как `decision-implementation`), а не строить Debezium/outbox. jobId-дедуп BullMQ держится только в окне `removeOnComplete` → идемпотентность применения — **отдельным condition-UPDATE**, не одним jobId.

### Новые риски (для Pre-mortem ТЗ)
- **Зацикливание:** трекер уже эмитит `task_completed` при ручном закрытии → если Э2 реагирует на `task_completed`-блоки, а своё закрытие порождает новый такой блок — петля. Различать `RawEvent.sourceType` (разговор vs трекер) + идемпотентный гард терминального статуса.
- **Синхронный embed в pre-create** = сетевой вызов к `proxy.agent-lia.ru` на каждое создание задачи (latency + SPOF). Обязателен таймаут + best-effort: нет вектора → пропускаем гейт, не блокируем создание.
- **Двойной suggest** (на IntakeIssue и повторно на accept→create) → нужен skip-флаг в DTO при accept.
- **Prompt-injection в реплике** («задача выполнена, закрой») → верификатор обязан идти через `withInjectionGuard`.
- **Висячие `sourceBlockIds`** (String[], не FK): при merge/удалении блока массивы не чистятся каскадом — при матче учитывать `mergedIntoId/supersededById` блока.
- **Тёзка-риск** в `resolveAssigneeUserId` (substring по тенанту) + KNN на «чужую похожую» задачу («починить логин» ×2) → порог дедупа выше панели similar (~0.88-0.9), вынести в `AdminSetting` (крутилка, не хардкод).

## 12. Рекомендация (итог)

**Строить, поэтапно, в порядке риска:**
1. **Гейт уверенности на СОЗДАНИИ** (objective-критерии, intent≠обещание) — фундамент, без него остальное масштабирует мусор. Связать с ТЗ [2026-06-15-intent-questions-are-not-commitments].
2. **Э1: pre-create дедуп** (kNN+арбитр+NIL+canonical, через `SimilarIssuesService`), с матчем по графу ролей.
3. **Э2-сигнал доведения** (детект→матч→верификатор→**кандидат на закрытие**→объяснение), событийно + идемпотентно.
4. **reopen-петля** (измерение FP) — до любого расширения автономии.
5. **supersede → review-пометка** задач.
6. Суточный reconcile — только как **чистка окна**.
7. Двусторонний синк статуса и любое расширение «авто» — **только после** того, как reopen-rate на своих данных доказал безопасность порога.

## 13. Открытые вопросы владельцу (каждый с рекомендацией)

1. **Авто vs очередь для Э2.** → **Рекомендую: обратимый «кандидат на закрытие» + объяснение, человек подтверждает крупное; авто только за объективным гейтом и только после бэктеста reopen-rate.** Почему: цена ложного закрытия задокументирована (stale-bot/Zendesk), HITL слепо принимает — нужен независимый верификатор, а не просто очередь. — **Код-вердикт: ✅ подтверждено.** Готовый каркас `PendingActionsService` (новый провайдер), reopen-детект бесплатно (`completedAt`+`IssueActivity`), прецедент авто-за-гейтом (`decision-implementation`).
2. **Порог дедупа Э1 и режим (авто-merge vs suggest).** → **Рекомендую: suggest (предложить слияние), не авто-merge.** Почему: авто-склейка разных задач необратима и бьёт по доверию; Linear/Jira тоже оставляют merge за человеком. — **Код-вердикт: ✅ с нюансом.** Гейт на **двух уровнях** (нет единого chokepoint); `Issue.embedding` async → нужен синхронный embed + `findSimilarByVector`; denorm-дубль через `IssueRelation`, не новой колонкой.
3. **Матч сигнал→Issue при неоднозначности.** → **Рекомендую: pgvector kNN + LLM-арбитр с обязательным NIL; majority-несходимость → курация.** Почему: LELA-паттерн, защита от «лепим top-1». — **Код-вердикт: ✅ с нюансом.** Матч **семантический по `Issue.embedding` KNN** (НЕ по `sourceBlockIds` — разные блоки); HNSW готов; верификатор = зеркало `CommitmentResponseHandler`.
4. **supersede-каскад.** → **Рекомендую: review-пометка «под вопросом», не авто-отмена.** Почему: CASCADE DELETE-катастрофа при ошибочной/временной отмене решения. — **Код-вердикт: ✅ с нюансом.** Паттерн «не авто-снос» уже доминирует для Decision, НО **у `Issue` нет флага review** (статус = FK на `IssueState`, не enum) → нужна новая колонка ИЛИ внешний слой (`IssueRelation`/pending-actions). Не выдавать за готовый кирпич.
5. **Цели без вектора.** → **Рекомендую: добавить `embedding` цели и kNN-дедуп (закрыть слабый ILIKE-дедуп).** Почему: разные формулировки одной цели сейчас плодят дубли-цели; инфра pgvector уже есть. — **Код-вердикт: ✅ с нюансом — это самая дорогая развилка.** Полный набор: колонка+hash (миграция, НЕ db push) + HNSW в `postgres-init.sql` + `goal-embed.worker` + backfill + STEPS. Промежуточный дешёвый вариант — через уже существующий `Entity{type=goal}.embedding`.
6. **Scope каналов Э1 в v1.** → ~~встреча + Telegram + отчёт~~ → **ПЕРЕСМОТРЕНО (код-вердикт: 🔄 revised).** Формула смешивала две оси (откуда задача *создаётся* vs откуда приходит *сигнал выполнения*) и оставляла email/self-task без покрытия. **Правильно: Э1 = «оба класса входа» (IntakeIssue + тонкий гейт в `issues.create`), Э2 = подписка на canonical-блок из разговора (отдельная ось).** По правилу «чини весь класс».
