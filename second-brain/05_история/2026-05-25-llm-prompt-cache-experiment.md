# 2026-05-25 — LLM prompt cache experiment по 9 каналам Z

## Постановка

Пользователь принёс гипотезу из §5 копилки ТЗ: «DeepSeek V4 Pro кэширует только первые ~2700 токенов префикса». Гипотеза была интерпретацией Variant Г эксперимента 3 specialists, где средний cache_hit_ratio у 8 параллельных специалистов вышел 21%.

Задача: проверить контрольным экспериментом, действительно ли есть «потолок» кэша. Затем — расширить проверку на все production-каналы Z и зафиксировать, где кэш реально работает.

Дополнительно — найти все способы вызова LLM в коде (LlmRouter, провайдеры) и проверить кэш по каждому. Согласовать с пользователем матрицу до запуска.

## Что сделал

**Раунд 1 — гипотеза «потолок 2700»:**
- Написал `backend/scripts/eval/probe-deepseek-cache.ts` — 3 сценария (sequential identical, 8 parallel identical, общий префикс + переменный хвост) на размерах 256/1024/2048/2700/3500/5000/10000/20000/50000 токенов.
- Запустил на `deepseek-v4-pro`: hit 99.9% до 43k токенов. **Гипотеза опровергнута.**
- Объяснение Variant Г: каждый из 8 параллельных специалистов имел свой `system`, свой `tools[]`, свой `submit_<name>` в user → префикс совпадал только в самом начале (≈2700 общих преамбул).

**Раунд 2 — GPT через прокси:**
- Аналогичный `probe-openai-proxy-cache.ts` для `gpt-5-mini` через `proxy.agent-lia.ru/v1/responses` (продовый путь). Hit 99.8% до 49k токенов. Прокси кэш не ломает.

- Прогон выявил 3 бага в моём скрипте: MiniMax URL без `/v1/`, KIE GPT usage в неправильных полях, опечатка `avgHitS2`. Исправил, перезапустил только сломанные цели.
- Финальная матрица: deepseek/openai-proxy/minimax работают (95-100%), KIE/GRSAI кэш не пробрасывают (0%), KIE GPT нестабилен (балансировка backend).

## Что вышло

- Реальные запросы на все 9 каналов прошли. Бюджет: ~$0.06 за 3 эксперимента (DeepSeek + OpenAI + матрица).
- Артефакты: 6 JSON+CSV отчётов в `backend/test/eval/cache-experiment/reports/`.
- Финальная сводка hit ratio:
  - DeepSeek (любая модель, прямой): **99.9%** до 50k токенов.
  - OpenAI gpt-5-mini через прокси: **99.8%** (порог 1024).
  - OpenAI gpt-5.4-mini через прокси: **99.7%** (порог ~2048 — отличие!).
  - MiniMax-M2.5: **100%** (с явным `cache_control: 'ephemeral'`).
  - KIE Claude/Gemini/GPT: **0%** или нестабильно.
  - GRSAI Gemini: **0%** (usage без `cached_tokens`).
- Документация согласована и закоммичена.

## Чему научился

1. **Гипотезы из «один артефакт = одно объяснение» часто ошибочны.** «Потолок 2700 токенов» был неверной интерпретацией одного измерения Variant Г. Реальное объяснение — **сломанный префикс**, не лимит провайдера. → Когда вижу подозрительную цифру в чьём-то выводе, надо в первую очередь подумать, **не артефакт ли это методологии**, а не свойство системы.

2. **Когда тестируешь чужую сериализацию payload — копируй её 1-в-1.** Variant Г имел разный `system`/`tools[]`/`submit_<name>` в каждом из 8 специалистов; этого было достаточно, чтобы убить кэш. Любой провайдер хэширует **весь payload-префикс**, не только messages. Изменение порядка элементов в `tools[]` или другое `tool_choice` тоже ломает кэш.

3. **gpt-5.4 family имеет повышенный порог попадания в кэш — ~2048 токенов** (vs ~1024 у gpt-5-mini). Это легко пропустить, если тестируешь только одну модель. → В матричных тестах брать **минимум одну модель из каждой подсемьи**.

4. **MiniMax (Anthropic-формат) поддерживает `cache_control: 'ephemeral'` отлично — hit 100%.** У нас в `LlmRouter.dispatch` cache_control ставится **только на system**. На длинных user-промптах (транскрипты) кэш упускается. → Создан мини-ТЗ на расширение.

5. **KIE и GRSAI кэш не пробрасывают.** Это важно для расчётов экономики: при подключении этих каналов в LlmRouter (ТЗ `kie-grsai-llm-router-integration.md`) **скидку cached учитывать нельзя**. Параллельная сессия (`b8547c1`) уже подключила их в admin-UI — наша cache-разметка попала туда вовремя.

6. **`bun run -e` использует bun-специфичные флаги.** Когда пишу одноразовый JS-скрипт через `-e` — лучше создать временный файл и запустить через `bun <file>`, чем боротья с цитированием. Потерял минуту на пустой пробег.

7. **При запуске длинного matrix-скрипта — обязательно делать «try/catch» вокруг каждого target, а не один глобальный.** Я это и так сделал, но столкнулся с edge-case: внутри `runTarget` была ошибка `avgHitS2 is not defined` ПОСЛЕ того как все данные собраны и принтнуты. Из-за неё summary каждой цели падал в FATAL, хотя rows[] сохранились. Урок: **в самом конце функции — defensive try/catch вокруг final summary**, чтобы не терять собранные данные из-за typo.

8. **Параллельные сессии Claude Code = git может уже измениться между моим коммитом и моим push.** post-push-reflection.py hook делает auto-pull. Если параллельная сессия в это время делает push, мои изменения могут уже быть на сервере к моменту моего ручного push (и сверху ещё что-то). → Всегда `git rev-parse HEAD vs origin/dev` перед push, не доверять «cached» представлению.

## Что осталось

- **Реализация ТЗ `minimax-cache-control-on-user.md`** — не приоритет, MiniMax сейчас A/B-кандидат, не основной канал.
- **Periodic re-verify cache-карты** — раз в N месяцев прогонять `probe-llm-cache-matrix.ts` и обновлять `verified_at` в `llm-cache-status.md`. Можно навесить @Cron в Z-Admin.
- **Кэш при подключении новых моделей** — добавить в чек-лист «новая модель в verified-карте»: прогнать probe на новой модели и записать в колонку «Кэш».
