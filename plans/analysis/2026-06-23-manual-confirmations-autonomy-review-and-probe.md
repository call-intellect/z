## 3. Риск, найденный при ревизии: молчаливая потеря критического знания

`CurationItemLifecycleCron` истекает pending-карточки старше 30 дней в статус `expired` — знание, которое ждало проверки, **тихо выпадает**: не канонизировано и не отклонено, просто пропало.

- Для рутины (некритичные) — приемлемо.
- **Для критических** (регламент / решение, которое ИИ-судья не пропустил, а человек не разобрал за 30 дней) — это **потеря знания по таймауту**, противоречит инварианту «ничего не теряем». Старые ~44 карточки владельца, вероятно, частью именно так и истекли.

**Под Р1 («человек = аварийный стоп») это надо изменить:** критические на истечении не гасить молча, а авто-канонизировать (provisional + аудит) либо эскалировать владельцу одним дайджест-пунктом.

**Доказательство ценности дедупликации:** 15 → 9 (−40%) только за счёт схлопывания дублей A и B. Это чистый код-рычаг (хеш по теме), без LLM.

**«Лестница владельца» (C, H, I)** — единый алгоритм для всех «не назначен ответственный»: владелец родителя → единственный держатель роли → автор/инициатор → (несколько равных кандидатов) человек. Закрывает owner-вопросы детерминированно, без обращения к человеку.

**Гейт ценности** (G и подобные «проверить?»): напоминания о чужих задачах — это NUDGE, им место в дневном дайджесте, а не в счётчике «ждёт вашего решения».

### 5.1. Живая приёмка владельцем (2026-06-23) — доказательная база

Прошли все 9 тем с владельцем в формате «улучшенного probe»: простой вопрос + предложенное решение + почему лучше. **Результат: по всем 9 темам владелец выбрал вариант «Кора делает сама»** — ни одна не потребовала формата «спроси меня».

| Тема | Выбор владельца |
|---|---|
| A. Миссия/видение/стратегия | Кора собирает черновик из памяти, владелец правит |
| B. Документ «Дамп» | Кора привязывает к процессу по содержимому |
| C. Владелец процесса чат-бокса | назначить автора автоматически |
| D. Урок эксперимента | Кора пишет черновик урока, владелец правит |
| E. Артефакт шага | Кора предлагает из контекста, владелец подтверждает |
| F. Экспертиза chydo_002 | (снят заранее — тихо записать) |
| G. 92% задач без целей | (снят заранее — в дайджест) |
| H. Владелец эксперимента | назначить автора автоматически |
| I. Владелец шага процесса | назначить автора автоматически |

**Вывод (эмпирический):** текущий probe спрашивает ровно там, где должен действовать. Правильное поведение по всем 9 = AUTO/HYBRID (сделать самой, максимум показать черновик/результат), а не HUMAN. Это снимает 15 вопросов из счётчика практически полностью.

**Что чинит каждый рычаг (под Р1):**
1. **Дедупликация по теме** (хеш) — чистый код: 15 → 9.
2. **«Лестница владельца»** (C, H, I) — назначение автора/владельца автоматически: −3.
3. **Черновик вместо пустого вопроса** (A, B, D, E) — Кора приносит черновик из памяти, человек правит при желании: 4 «вопроса» → 0 в счётчике (HYBRID, не блокирует).
4. **Тихо записать фон** (F) и **NUDGE в дайджест** (G): −2 из счётчика.

Итог: из 15 «вопросов Коры» в счётчике «требует решения» осталось бы около нуля.

## 6.1. ИИ-судья карточек — корень и доказанная починка (2026-06-23)

Почему критические карточки летят к людям, а не канонизируются молча: судья (`curation-verify`) почти всегда отказывает. Два корня:
1. **Не видит первоисточник** — `runAiVerifier` зовёт `judge()` с `contextBlocks: []` ([curation.service.ts:1043](../../backend/src/modules/curation/services/curation.service.ts)), а критик инструктирован «reject, если не обоснована фактами».
2. **Промпт не по методологии + дешёвая отказная модель** (2 из 3 голосов — `deepseek-v4-flash`, «склонна к reject»).

**Локальный A/B/C-прогон** ([backend/scripts/judge-ab-test.ts](../../backend/scripts/judge-ab-test.ts), 12 карточек, реальные вызовы flash):

| Вариант | Верных/12 | Мусора принято | Хорошего отклонено |
|---|---|---|---|
| A (как сейчас) | 7 | 1 | 4 |
| B (+первоисточник) | 9 | 0 | 3 |
| C (+методология+цитата) | **11** | **0** | **1** |

→ Оформлено в ТЗ [plans/tz/2026-06-23-curation-judge-context-and-methodology.md](../tz/2026-06-23-curation-judge-context-and-methodology.md): дать судье первоисточник, переписать промпт по методологии, требовать цитату из текста.

## 6.2. Самообучение на ответах (Subject Memory) — реализовано, но слепое (2026-06-23)

Фича «Кора учится на ответах руководителя» (`SubjectMemory`, ТЗ `2026-06-21-learned-clarifications-memory.md`) реализована и **включена** в проде (флаги `subjectMemory.enabled`/`retrieveBeforeAskEnabled`=true, `shadowToCanaryMinConfirm`=0). Механика: ответ на probe → выводится правило → перед похожим вопросом `retrieve-before-ask` подавляет переспрос; активация shadow→canary→active через судей + откат по метрике.

**Но по факту ни разу не сработала** (логи: `deriveRule`=0, `answered_by_memory`=0) — потому что после выката на probe не отвечали (15 висят без ответа, старые — до выката).

**Живой тест (Org «ооо ромашка», 2026-06-23):** ответил на 1 из 3 дублей про «Дамп от 05.06.2026 13:05» → вопрос принят и ушёл (10→9). Но:
1. **Вывод правила подтвердить нельзя** — нет наблюдаемости (правила негде смотреть; метрики per-replica; лог-стор не покрывает воркер).
2. **2 дубля про тот же дамп остались** — подавление работает на новых probe, висящие не чистит.

→ Дельта оформлена в ТЗ [plans/tz/2026-06-23-subject-memory-observability-and-dedup.md](../tz/2026-06-23-subject-memory-observability-and-dedup.md): наблюдаемость (read-эндпоинт + диаг + страница «Что Кора выучила») + дочистка висящих дублей при выводе правила. Зафиксировано в реестре не-сделанного.

## 6.3. Конфликты — решение владельца: не трогать (2026-06-23)

Арбитр конфликтов (`conflict-arbiter.cron`) **уже получает первоисточник** (`contextBlocks` с `evidence` обеих версий, conflict-arbiter.cron.ts:238) — в отличие от судьи карточек. Разобрал 36/40 в Org «Ооо луа». 4 висящих — свежие (ждут ночного крона 02:00) или законный `escalate` (реально спорное → человеку). **Решение: не трогать сейчас** (автономен на 90%, главная правка «дать контекст» здесь не нужна — уже есть). Вернуться, если после крона 4 не разойдутся. Опционально vNext — причесать промпт арбитра по методологии (выигрыш мал).

## 6.4. Доставка-«добивалки» — решение владельца: не трогать (2026-06-23)

Напоминание «ждёт подтверждения» (до 5×/день, слоты 9/12/15/18/21) + проактивный сторож (каждые 6ч, 8 правил) + отдельные сообщения по вопросам — **оставляем как есть**. Причина: в параллельной сессии идёт работа над уведомлениями постановки задач в трекер; правки доставки рискуют сломать тот код. Отложено до завершения той работы (владелец, 2026-06-23). Рычаг сам по себе дешёвый (только частота) — вернуться после.
