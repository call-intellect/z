# 12 — Roadmap реализации

Этот документ — план параллельной сборки. Не «MVP-этапы» (см. [DR-001](14-decisions-log.md#dr-001) — без MVP), а **порядок начала работы команд**, чтобы зависимые модули не блокировали друг друга.

## Ключевая идея

40 модулей — много. Но разделение на слои даёт чёткий граф зависимостей. Команды могут работать параллельно, если правильно расставить порядок старта.

**Critical path** (то, что блокирует остальное):

1. **Инфраструктура** (Caddy, Keycloak, PostgreSQL, Kafka, MinIO) — нужна всем.
2. **M-20 (RBAC)** — нужен всем сервисам перед началом работы с данными.
3. **M-02 + M-03 (ingest + raw memory)** — без этого нет данных для обработки.
4. **M-05 (LLM-анализ)** + **M-06 (signal store)** — без этого нет сигналов.
5. **M-08 (themes)** — нужен для остальных.
6. **M-11 + M-12 (граф)** — нужен для дашборда и чата.
7. **M-23 (чат)** — главная функция для пользователя.

После critical path остальное собирается параллельно.

## Структура команд

Рекомендуемый состав (на старт):

| Команда | Состав | Ответственность |
|---|---|---|
| **Платформа** | 2 backend, 1 DevOps | Инфра, k8s, CI/CD, hardening, observability |
| **Ingest** | 2 backend (1 Python, 1 Go) | M-01, M-02, M-04, M-33, M-40 + коннекторы |
| **Понимание** | 3 backend (Python) + 1 ML | M-05, M-06, M-08, M-09, M-10 + промпты |
| **Граф** | 2 backend + 1 ML | M-11, M-12, Graphiti интеграция |
| **Фоновые агенты** | 2 backend | M-13, M-14, M-19, M-22, M-34 |
| **Решения и UX** | 2 backend + 2 frontend | M-15-M-26, M-32, M-36, M-37, дашборд |
| **AI-команда** | 2 backend + 1 prompt-инженер | M-38, M-39, маршрутизация |
| **Безопасность** | 1 backend + 1 security | M-20, audit, secrets, compliance |
| **Frontend** | 3 frontend + 1 UX/дизайнер | веб, Telegram-бот, мобильный |
| **QA** | 2 QA-инженера | тесты, evals, golden set |

Итого: 24-26 человек. Можно сократить до 12-15 с увеличением сроков (2× времени).

## Общий тайминг (оценка)

| Phase | Длительность | Накопленный срок |
|---|---|---|
| Phase 0 | 1 неделя | 1 нед |
| Phase 1 | 4-6 недель | 7 нед |
| Phase 2 | 4-6 недель | 13 нед |
| Phase 3 | 4-6 недель | 19 нед |
| Phase 4 | 3-4 недели | 23 нед |
| Phase 5 | 3-4 недели | 27 нед |

**Total: ~6-7 месяцев** до GA с командой 24+ человек, full-scope.

При меньшей команде (12-15 чел) — ~12-14 месяцев.

Это **не** waterfall. Phase'ы пересекаются, в каждой могут идти доработки предыдущих фаз. Это **порядок старта**, не deadline-grid.

## Критерии готовности (Definition of Done)

### По модулю

Модуль считается готовым, когда:

1. **Контракт реализован** согласно [03-modules-catalog.md](03-modules-catalog.md).
2. **API соответствует** [04-api-spec.md](04-api-spec.md).
3. **Схема БД** в [05-data-schema.md](05-data-schema.md).
4. **Unit тесты** покрывают ≥ 80%.
5. **Integration тесты** покрывают основные flow.
6. **Security review** пройден.
7. **Promtfoo eval** для AI-частей > target.
8. **Observability** — метрики, логи, трейсы.
9. **Документация** в README модуля.
10. **Code review** двух человек.

### По всему продукту

Готов к GA когда:

1. ✅ Все 40 модулей в DoD.
2. ✅ Все E2E-сценарии проходят.
3. ✅ Load test на reference hardware прошёл.
4. ✅ Penetration test без HIGH issues.
5. ✅ Forget-drill работает на тестовом тенанте.
6. ✅ Backup/restore drill пройден.
7. ✅ Все runbook'и написаны.
8. ✅ Один клиент в production 30+ дней без SEV-1.
9. ✅ Стоимость на типового клиента в норме.
10. ✅ Документация соответствия 152-ФЗ выпущена.

## Риски и митигации

| Риск | Вероятность | Митигация |
|---|---|---|
| Graphiti непредсказуемое поведение на больших объёмах | Средняя | PoC на 1М узлов в Phase 1, fallback на pure FalkorDB |
| Локальные LLM не дают качества в анализе | Средняя | Promptfoo evals, при провале — увеличиваем модели до 70B+ |
| OpenFGA latency не выдерживает | Низкая | Готов Casbin fallback (см. [DR-006](14-decisions-log.md#dr-006)) |
| Стоимость LLM выше ожидаемого | Средняя | Hybrid mode + кэш + локальные модели |
| Промпты не работают на длинных контекстах | Средняя | Chunking + summary хирархия |
| 152-ФЗ требования меняются | Низкая | Гибкий retention + готовый forget-flow |
| Внешние LLM-провайдеры исчезают | Низкая | Полный fallback на локальные |
| WhisperX не справляется с русским | Низкая | Альтернативный fallback на AssemblyAI как managed |

## Что **НЕ** делаем (anti-roadmap)

- **Не делаем preview / alpha / beta-релизы** на сторонних клиентов до Phase 5.
- **Не делаем feature freeze** в смысле «не принимаем багфиксы». Багфиксы — всегда.
- **Не урезаем scope** в случае давления по срокам — лучше сдвинуть GA, чем выпустить без ключевого модуля.
- **Не делаем maintenance mode** на старых версиях. Все клиенты на одной версии (благо single-tenant deployment).
- **Не делаем feature flagging** для пользовательских функций — только для технических переключений (например, выбор LLM-провайдера).

## После GA (post-launch)

- Postmortem каждого SEV-1 / SEV-2.
- Continuous improvement промптов на основе negative feedback.
- Periodic upgrade моделей LLM по мере выхода новых.
- Расширение списка коннекторов M-40 (по запросам клиентов).
- A/B тесты UX-изменений через Langfuse experiments.
- Quarterly security review.
