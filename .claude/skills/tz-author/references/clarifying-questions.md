# Уточняющие вопросы

Правило: **добирай сам всё, что выводимо из кода/доков; спрашивай только то, что (а) критично для результата И (б) не определимо из кода.** Перед любым вопросом — context-поиск Шага 1. Не спрашивай задокументированное.

## Классификатор impact

**HIGH-impact — спрашивай ВСЕГДА, если ответа нет в коде:**
- Архитектурная развилка, где проходы A и B разошлись и оба сильны.
- Новая Prisma-модель/колонка, новый enum, изменение существующего контракта API.
- FSM встречи (переходы статусов), retention записей.
- Billing / entitlements / тарифы / лимиты.
- Выбор LLM-провайдера/модели, если влияет на стоимость или качество заметно.
- RBAC / границы tenant / кто что видит.
- Необратимое (удаление данных, миграция), бюджет, прод-доступ.

**LOW-impact — реши сам, пометь `[ASSUMPTION: …]` в ТЗ:**
- Naming внутри слоя (имя переменной, приватного метода).
- Формат текстового сообщения, порядок полей в ответе.
- Детали поведения, однозначно выводимые из соседнего кода.

Принцип: «правдоподобно неверное» предположение опаснее очевидно неверного — делай предположения видимыми через `[ASSUMPTION]`, чтобы владелец/оркестратор их заметил.

## Три типа неоднозначности (ClarEval) — self-check перед фиксацией
1. **Missing goals** — зачем фича и какая метрика успеха? Нет метрики → нет проверяемого Acceptance.
2. **Premises** — на каком состоянии данных / какой ENV / какой feature-flag вкл/выкл это работает? Что если данных 0 / очень много / конкурентный доступ?
3. **Terminology** — термины Z однозначны? Org/tenant, IdeaBlock, Entity, Theme, тип встречи, Host/Guest, клон ролевой (не персональный). Расхождение терминов → расхождение реализации.
Не закрыто кодом → вопрос владельцу.

## Формат батча
Собери ВСЕ HIGH-вопросы и задай **разом**, не капельно. К каждому — рекомендация + 1–2 строки почему (`feedback_propose_best_solution_with_reasoning`).

**Основной механизм — `AskUserQuestion`** (если доступен): по вопросу на развилку, первой опцией — рекомендованная с «(рекомендую)» и пояснением в description.

**Fallback (надёжен в headless/SDK):** если инструмента нет — один текстовый блок:
```
Перед финализацией ТЗ — 3 развилки (для каждой мой рекомендованный вариант):

1. Хранение черновиков: [A] новая таблица DraftTable / [B] JSONB-поле в Org.
   Рекомендую A — независимый индекс по tenantId, чище RBAC. Почему: …
2. …
```

## Чего НЕ делать
- Не выносить LOW-мелочь владельцу — это шум, решай сам.
- Не задавать вопрос без рекомендованного дефолта.
- Не оформлять уточняющий диалог фичи через inline-кнопки (`feedback_probe_no_buttons_text_voice_only`) — probe только свободный текст/голос. `AskUserQuestion` к владельцу — это служебный UI выбора, не probe; путать не надо.
- Не спрашивать то, что уже есть в CLAUDE.md / second-brain / коде.
