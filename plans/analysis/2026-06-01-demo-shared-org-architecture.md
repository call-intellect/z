# Анализ: shared demo Org как единственный источник демо-данных

> Это **анализ**, не ТЗ. Цель — закрыть все архитектурные развилки до начала ТЗ, чтобы реализация не упёрлась в спор «а как мы решили вот это». ТЗ будет отдельным документом после одобрения этого анализа.

---

## 1. Контекст и наблюдаемая проблема

### 1.1. Что увидел владелец продукта (2026-06-01)

Зайдя в новую Org «ооо ромашка» на проде, владелец увидел:
- Тост в правом верхнем углу: «Готовим демо-данные «ТехноСтрим»…».
- Бейдж сверху: «Демо-режим: просмотр данных без возможности создания».
- Часть страниц частично заполнена, часть (например `/entities`) — EmptyState «Сущностей пока нет».
- Это происходит **каждый раз** для нового пользователя.

Возражение владельца: *«Почему сид уходит сейчас? Сид сделали один раз программистом, данные хранятся в БД. Новый человек заходит — у него должно сразу быть готовое демо. Зачем что-то готовить?»*

Возражение концептуально корректно. Текущая архитектура противоречит ментальной модели владельца и продукта в целом.

### 1.2. Что происходит на самом деле — текущая модель

Демо-кабинет «ТехноСтрим» — это **не данные**, это **23 seed-функции** в [backend/src/modules/onboarding/demo-data/](backend/src/modules/onboarding/demo-data/) с ~2000 захардкоженных `prisma.X.create(...)`. При первом нажатии «Создать демо» (либо через `/admin/demo` super-admin'ом, либо через старый `/onboarding/demo-choice` владельцем Org) backend:

1. Синхронно прогоняет 23 модуля INSERT'ов **в Org пользователя** ([onboarding.service.ts:257-278](backend/src/modules/onboarding/onboarding.service.ts#L257-L278)).
2. В каждую запись пишет `externalSource='demo'` через `markAllDemoEntitiesForTenant`.
3. Проставляет `Org.demoWorkspaceSeededAt=now()`.
4. Возвращает HTTP-ответ через 8-30 секунд (на проде, по нагрузке).

При оплате (`SubscriptionStatus DEMO → ACTIVE`) задумано (но **ещё не реализовано** — ТЗ `2026-05-31-demo-auto-seed-and-cleanup.md` в draft'е) удалять всё с `externalSource='demo'` по 35 таблицам через `resetDemoWorkspace`.

### 1.3. Почему текущая модель плоха

| # | Проблема | Цена |
|---|---|---|
| 1 | На каждого нового пользователя в БД **копируются ~2000 строк** «ТехноСтрим» | Линейный рост места: 1000 пользователей × 2000 строк = 2M мусорных строк |
| 2 | Seed синхронный 8-30 секунд → ожидание + тост «Готовим…» | UX-разрыв, ощущение тормозов |
| 3 | Seed может упасть посередине (нет транзакции на 23 модуля), разные пользователи получают **разный частичный демо** | Поддержка превращается в «у одних работает, у других нет» |
| 4 | Pulse-snapshot'ы для главной частично пишутся seed'ом, частично — cron-агентами с интервалом раз в час. У свежей Org cron'ы не успели → виджеты пустые | «Главная частично есть» — точное описание текущего состояния |
| 5 | Имена сотрудников «Алексей Морозов», «Марина Волкова» лежат в Org `ооо ромашка` как **её собственные сотрудники** | Это бред с точки зрения чистоты данных и любого экспорта/аналитики |
| 6 | Для «обновления демо» (добавили виджет, новый раздел) — надо запускать `seedExtra` для каждой Org отдельно или менять seed-функции и cleanup перед re-seed | Поддержка контента демо требует patch-скриптов |
| 7 | `resetDemoWorkspace` ходит по 35 таблицам в транзакции 30 секунд, может таймаутиться на горячем проде | Cleanup при оплате — точка отказа |
| 8 | Нет единого «эталона», на котором можно демонстрировать клиентам, делать скриншоты, прогонять регрессии UX | Маркетинг и продакт-демонстрации страдают |

### 1.4. Желаемая модель (из слов владельца)

> Данные загружены в БД ОДИН РАЗ программистом, новый пользователь заходит — у него **сразу** уже готовый демо-кабинет.

Это паттерн **shared demo tenant**: одна эталонная Org «ТехноСтрим» живёт в БД постоянно, любой новый пользователь видит её как наблюдатель (read-only), пока не оплатит — тогда переключается на свою.

## 2. Целевая модель — обзор

```
БД (постоянно):
  ┌─ Org "ТехноСтрим" (tenantId=DEMO_ORG_ID, isReferenceDemo=true)
  │    ├─ 12 Person, 3 проекта, 7+ встреч, граф знаний, регламенты, идеи,
  │    │  документы, календарь, рефералка, фидбек, 8 Pulse-снапшотов
  │    └─ Subscription(status=ACTIVE, bonus, paymentMode='reference')  ─── НЕ DEMO!
  │                                                                       (иначе наблюдатели увидят paywall на ОЩУЩЕНИЕ демо)
  │
  └─ Org "ООО Ромашка" (своя Org пользователя)
       ├─ ПУСТАЯ — никаких копий «ТехноСтрим»
       └─ Subscription(status=DEMO)

Пользователь Иван:
  ├─ User.id=u1
  ├─ OrgMember(u1, "ТехноСтрим", role='demo_observer')   ← НОВАЯ роль, read-only
  └─ OrgMember(u1, "ООО Ромашка", role='owner')

Заход Ивана в кабинет:
  → По умолчанию открывается "ТехноСтрим" (потому что своя пустая)
  → Видит "Демо: ТехноСтрим — это пример. Создайте встречи в своей компании."
  → Может переключиться в "ООО Ромашка" через org-switcher
  → В "ТехноСтрим" любая мутация → блок (даже без paywall — guard срабатывает раньше)

Иван оплачивает:
  → Subscription("ООО Ромашка").status: DEMO → ACTIVE
  → По событию SUBSCRIPTION_ACTIVATED_PAID — listener удаляет OrgMember(u1, "ТехноСтрим", demo_observer)
  → currentOrg переключается на "ООО Ромашка"
  → Демо больше не виден

Эталонная "ТехноСтрим" в БД остаётся НЕТРОНУТОЙ.
```

Никакого копирования. Никакого ожидания seed'а. Один раз залили программистом — навсегда.

## 3. Развилки и рекомендуемые решения

15 архитектурных решений, сгруппированных по уровню инвазивности.

### Развилка 1. Где живут демо-данные

**Варианты:**

| Вариант | Описание | Pro | Contra |
|---|---|---|---|
| **A. Одна shared Org в БД (`isReferenceDemo=true`)** | Реальная Org с реальными записями, как у живого клиента | Нулевой код-маршрут «спецслучая»: вся текущая система видит её как обычную Org. Cron-агенты сами поддерживают актуальные snapshot'ы. RBAC, TenantGuard, аналитика, экспорт — всё работает «из коробки» | Нужен механизм пометить её как «эталонную», чтобы не показывать в админских аналитиках/выгрузках |
| B. Файл-снапшот (JSON / SQL dump) | Демо живёт в `backend/demo-snapshot.sql`, импортируется на старте | Простой rollback к эталону | Не работает с FK/sequence'ами Postgres, нет cron-snapshot'ов, snapshot устаревает с каждым изменением схемы |
| C. Отдельная схема в Postgres (`demo.*` namespace) | Демо в схеме рядом с `public` | Логическая изоляция | TenantGuard и весь Prisma-код заточены на `tenantId`, не на схему. Огромный рефактор всего слоя данных. Не оправдано |

**Рекомендация: A.**

**Доказательство:**
- Z уже multi-tenant по дизайну. Shared demo Org — это просто ещё один тенант с особым флагом. Не требует ни одной строки специальной логики на уровне Prisma/TenantGuard.
- Cron-AI-агенты Pulse (engagement-scorer, recurring-topics-detector, bus-factor-analyzer) уже работают по `tenantId`. Они будут автоматически обновлять snapshot'ы эталонной Org — демо станет «живым» (engagement дрейфует, появляются новые темы, ROI-встреч пересчитывается). Это плюс для маркетинга («смотрите, продукт живёт») и для регрессионного тестирования (если cron сломался — заметим на эталоне).
- Если когда-то понадобится «откатить эталон к зафиксированному состоянию» — это отдельная задача (snapshot + restore через скрипт), но не блокер старта.

### Развилка 2. Как новый пользователь видит shared demo Org

**Варианты:**

| Вариант | Описание | Pro | Contra |
|---|---|---|---|
| **A. `OrgMember`-запись с новой ролью `demo_observer`** | На signup создаётся `OrgMember(userId, DEMO_ORG_ID, role='demo_observer')` | Каноничный путь через RBAC. TenantGuard и `RbacService.loadContext` уже умеют возвращать `MembershipRole` — добавится одна ветка | Растёт таблица `OrgMember` на N×1 запись (N пользователей). На 100k пользователей — 100k записей, копейки |
| B. Без OrgMember: middleware/`TenantGuard` спецслучаем | TenantGuard видит `tenantId=DEMO_ORG_ID` и пускает любого аутентифицированного user в read-only | Нет записей в БД | Спецслучай размазан по guard'ам. Аналитика «кто сейчас в демо» — `JOIN`-ы по user без membership. Нарушает invariant «доступ к Org = OrgMember-запись» |
| C. Proxy-режим: `User.currentOrgId=DEMO_ORG_ID` без членства | Просто currentOrg-указатель | Очень дёшево | TenantGuard НЕ пустит без OrgMember (см. [rbac.service.ts](backend/src/modules/rbac/rbac.service.ts)). Нужен спецслучай в каждом контроллере. Хуже B |

**Рекомендация: A.**

**Доказательство:**
- Главный аргумент — invariant «доступ к Org = OrgMember». Z многотенантен, эта инвариант пронизывает всё: guard'ы, репозитории, аналитика. Ломать её ради экономии одной записи на пользователя — плохой обмен.
- `MembershipRole` enum в [schema.prisma:179-193](backend/prisma/schema.prisma#L179-L193) уже содержит `owner / admin / manager / coo / hr_partner`. Добавление `demo_observer` — пять символов в enum + `db push` + одна ветка в `RbacService.canMutate` («`demo_observer` → false»).
- Получаем «бесплатно»: список «кто сейчас в демо», возможность отозвать доступ конкретному пользователю, обычный аудит-лог OrgMember.

**Конкретный enum-патч:**
```prisma
enum MembershipRole {
  owner
  admin
  manager
  coo
  hr_partner
  /// 2026-06-01: для пользователей до оплаты — членство в эталонной демо-Org с read-only доступом.
  /// Все мутации блокируются на уровне RbacService.canMutate. Снимается при первой оплате.
  demo_observer
}
```

### Развилка 3. Когда создаётся «своя» Org пользователя

**Варианты:**

| Вариант | Описание | Pro | Contra |
|---|---|---|---|
| **A. Сразу на signup (как сейчас), но пустая** | `AccountsService.register` создаёт `Org(name=email-домен или "Моя компания")` и сразу `OrgMember(owner)`. Welcome обновляет name/industry/etc. | Минимум изменений в существующем flow (`AccountsService`, `OnboardingService`, welcome-страницы) — все они уже работают с existing Org | На каждого незаплатившего user в БД есть пустая Org. На 100k user — 100k пустых Org. Не критично, но мусор |
| B. Только на оплате | Welcome-ответы хранятся в `User.pendingOrgData JSON`. При оплате создаётся реальная Org | Чистая БД: нет пустых Org-ов «незаплативших» | Welcome flow и весь код ниже становится «возможно, Org ещё нет». Огромный рефактор: dashboard, settings, billing, integrations — все они исходят из «у user есть current Org» |

**Рекомендация: A.**

**Доказательство:**
- Стоимость B — десятки изменений в коде, который уже стабильно работает. Стоимость A — нулевая.
- Пустые Org — не «мусор», а реальные сущности, в которых уже хранятся ответы welcome (`Org.industry / teamSize / painPoints / currentStack / plannedFeatures`). Это полезный контекст для CRM и аналитики «кто регистрируется, но не платит».
- Cleanup-стратегия для умерших Org (никогда не активировались, нет владельца с активной сессией > 90 дней) — отдельный скрипт, не блокер.

### Развилка 4. Где хранятся welcome-ответы

**Варианты:**

A. На `Org` (как сейчас): `industry, teamSize, painPoints, currentStack, plannedFeatures`. Org создаётся сразу.
B. На `User`: `User.pendingWelcomeData JSON` (нужно если развилка 3 = B).

**Рекомендация: A** (следствие выбора 3.A). Welcome пишет в Org как сейчас. Менять не надо.

### Развилка 5. Как enforcing read-only для demo_observer

**Варианты:**

| Вариант | Описание | Pro | Contra |
|---|---|---|---|
| **A. `RbacService.canMutate(role)` + новый Guard `DemoObserverGuard`** | Расширяем существующий RBAC: для `demo_observer` все write-actions → false. Глобальный `DemoObserverGuard` подключаем в `AppModule` — он смотрит метод (POST/PUT/PATCH/DELETE) и роль | Единая точка контроля. Существующие RBAC-policies (`policies/policy.csv`) расширяются без изменения логики | Нужно покрыть guard'ом все mutating endpoints. Унижение через decorator `@PublicDemo()` для исключений (если будут) |
| B. Опираемся на `SubscriptionGuard` | Сейчас он блокирует мутации при `Subscription.status='DEMO'`. Если у демо-Org статус ACTIVE — наблюдатели свободно мутируют | НЕ работает. Если на shared demo-Org поставить DEMO-статус — обычные сценарии «новый пользователь смотрит демо» сломаются (paywall везде). А если ACTIVE — наблюдатели смогут писать | НЕ применим |
| C. Per-controller проверка | В каждом write-эндпоинте: `if (user.role === 'demo_observer') throw 403` | Локально предсказуемо | 100+ точек правок, легко забыть |

**Рекомендация: A.**

**Доказательство:**
- B концептуально неверен: `SubscriptionGuard` про **подписку Org**, а не про **роль пользователя в Org**. Эталонная Org должна быть ACTIVE (см. развилку 6 ниже), иначе наблюдатели получают paywall — это не «демо», это «показываю как выглядит paywall».
- C — операционно непригоден (100+ контроллеров).
- A — каноничный путь, расширение существующего RBAC. Реализация: одна функция `canMutate(role: MembershipRole): boolean` в `RbacService`, один глобальный guard, добавление в `AppModule.providers`. ~50 строк кода.
- Дополнительный плюс A: если позже понадобятся другие read-only-роли (аудитор, инвестор, регулятор) — переиспользуем механизм без изменений.

**Поведение при попытке мутации:** возвращаем `403 demo_observer_readonly` с понятным сообщением «Это демо-кабинет. Создайте свою компанию или оплатите подписку — после этого сможете создавать данные». UI-перехват — открывает paywall-модалку (как сейчас при DEMO-подписке).

### Развилка 6. Какой Subscription.status у эталонной демо-Org

**Варианты:**

| Вариант | Описание | Pro | Contra |
|---|---|---|---|
| **A. ACTIVE (bonus, paymentMode='reference')** | Эталонная Org — как «вечно оплаченная» | Нет paywall'а: наблюдатели видят настоящий продукт, не paywall-обёртку. Cron-агенты Pulse работают (часть из них проверяет `Subscription.status='ACTIVE'`). Корректные данные везде | Нужен новый `paymentMode='reference'` в enum, чтобы в billing-overview эта Org не считалась как платящий клиент |
| B. DEMO | Унификация: эталон в том же статусе, что и пользовательские пустые Org | Наблюдатели видят paywall везде (`SubscriptionGuard` режет любую мутацию ДО `DemoObserverGuard`, выдаёт paywall-модалку с CTA). Cron-агенты могут не работать на DEMO-Org. **Главное противоречие:** мы строим демо, чтобы показать продукт, а пользователь видит paywall. Это анти-демо |

**Рекомендация: A.**

**Доказательство:**
- Цель демо — показать ПРОДУКТ, а не блокер. Pay wall — это «после демо», не «во время».
- `SubscriptionGuard` ([guards/subscription.guard.ts](backend/src/modules/billing/guards/subscription.guard.ts)) на чтении не срабатывает — он на мутации. Чтение возможно при любом статусе. Но: ряд UI-компонентов (`PaywallBanner`, `PaywallGuardButton`) явно реагируют на `status='DEMO'` и показывают баннеры/блоки. Чтобы наблюдатели НЕ видели paywall-обёртку — статус должен быть ACTIVE.
- `paymentMode='reference'` (новое значение в enum) — маркер, по которому `billing-overview.service.ts` исключает эту Org из метрик «paid Orgs / bonus Orgs / total MRR». Влияет только на одну строку в одной агрегации.

### Развилка 7. Какой Org показывать по умолчанию при заходе нового пользователя

**Варианты:**

A. **«ТехноСтрим» по умолчанию**, своя Org в org-switcher как вторая опция (с пометкой «пусто, оплатите»).
B. **Своя Org по умолчанию**, ссылка «Посмотреть демо» в шапке.
C. Развилка на welcome: «Сначала покажу демо?» / «Сразу к своей».

**Рекомендация: A.**

**Доказательство:**
- C — это худшая модель, которая у нас была (`/onboarding/demo-choice`). Пользователь не знает, что выбрать, скипает.
- B — пользователь сразу видит пустоту, не понимает что делать. Низкая конверсия в «полноценный просмотр демо».
- A — пользователь сразу видит работающую компанию, тур, цифры на главной. Конверсия в «вау, понятно как это выглядит» максимальная.
- Org-switcher в шапке UI уже существует. Своя Org в нём — с серой иконкой «пусто» и подписью «Создайте встречи после оплаты».
- На странице своей Org (когда пользователь туда переключится) — большой EmptyState с CTA «Оплатить и начать работу» + ссылка «Вернуться в демо».

### Развилка 8. Что происходит при оплате

**Варианты:**

A. **Удаляем `OrgMember(user, DEMO_ORG, demo_observer)`** + переключаем `User.currentOrgId` на свою Org.
B. Оставляем `OrgMember` к демо, но меняем роль на `viewer` (если такая будет).
C. Оставляем как есть, наблюдатель просто переключился вручную.

**Рекомендация: A.**

**Доказательство:**
- B вводит «viewer»-роль, которая нигде больше не используется — over-engineering. После оплаты у пользователя нет повода продолжать видеть демо в своём org-switcher'е, это шум.
- C — приём «само рассосётся» — пользователь забудет, в каком Org он, увидит чужие данные после оплаты. Confusing.
- A — listener на событие `SUBSCRIPTION_ACTIVATED_PAID` (из ТЗ Tochka billing — уже работает) делает в транзакции:
  1. `OrgMember.deleteMany({ userId, orgId: DEMO_ORG_ID, role: 'demo_observer' })`
  2. `User.update({ id: userId, data: { currentOrgId: <own-org-id> } })`
- Фронт по тику SWR-refetch подписки → видит ACTIVE → org-switcher обновился, демо ушла.

### Развилка 9. На каком Org висит подписка пользователя

**Варианты:**

A. На своей Org пользователя (как сейчас). Подписка про **компанию**.
B. На User (subscription per-user). Подписка про **человека**.

**Рекомендация: A.**

**Доказательство:**
- Текущая модель Z — подписка на Org (одна Subscription на tenantId, оплачиваются места внутри). Менять — огромный рефактор billing'а и квот.
- shared demo Org имеет свою отдельную «техническую» Subscription со статусом ACTIVE (см. развилку 6). Subscription пользователя на его Org начинается с DEMO, при оплате → ACTIVE.
- Никакого пересечения подписок нет — они на разных tenantId.

### Развилка 10. Cron-агенты на эталонной Org

**Варианты:**

A. **Работают как обычно** — эталонная Org живёт, snapshot'ы дрейфуют, темы обновляются.
B. Замораживаем — для эталона cron-агенты не запускаются.

**Рекомендация: A** (с оговоркой).

**Доказательство:**
- A даёт ощущение «живого продукта»: пользователь видит, как тренды engagement пересчитываются, появляются новые риски, и т.д. Это часть продуктовой ценности.
- Но: исходные данные (встречи, регламенты, идеи, ввод) — статичны (загружены seed-скриптом). Cron-агенты пересчитывают **производные** snapshot'ы. Это нормально.
- **Оговорка:** PR-критичные виджеты главной (BusFactor, RecurringTopic, Forecast) должны иметь baseline-снапшоты в seed (как описано в `2026-05-31-demo-content-expansion-pulse.md` §6.3) — на случай, если cron ещё не успел отработать после первого деплоя или эталон только что пере-засеян. Cron'ы потом «дорисуют» поверх.

### Развилка 11. Privacy: что наблюдатель НЕ должен видеть в эталонной Org

**Что в обычной Org видно всем участникам, но в эталоне не нужно:**

| Что | Решение |
|---|---|
| `/settings/billing`, `/settings/subscription` | RbacService для `demo_observer` режет доступ → 403 / редирект на свою Org |
| `/admin/...` (super-admin) | TenantGuard и так не пускает |
| Список членов Org (`/settings/members`) — наблюдатель увидит всех других наблюдателей | `OrgMember.role='demo_observer'` отфильтровываем из publicListMembers — наблюдатели видят только Person-карточки демо-сотрудников, не «реальных людей в демо» |
| `/settings/integrations`, `/api`, `/webhooks`, `/sources`, `/exports` | RbacService режет |
| Audit log Org | RbacService режет |
| Концерж-сессии других наблюдателей | Per-user state (см. развилка 13) |

**Рекомендация:** новый список «эндпоинтов, запрещённых для demo_observer» вшит в `RbacService.allowedActions(role)`. Все остальные read-эндпоинты разрешены.

### Развилка 12. Per-user state в shared Org

**Кейсы, где разные наблюдатели могли бы перепутаться:**

| Что | Сейчас (per-Org) | Решение для shared Org |
|---|---|---|
| **Концерж-история** (чат с AI «помощником компании») | Хранится по `tenantId` + `userId` | Уже per-user. Работает без изменений — каждый наблюдатель видит свою историю |
| **Tour progress / onboarding-туры** | Хранится по `userId` (см. [tour-progress.api.ts](frontend/src/api/users/tour-progress.api.ts)) | Per-user, работает |
| **Прочитанные уведомления** | Сейчас связаны с `personId` или `userId`-логикой | На эталоне notifications для системы создаются «от имени демо-Person'ов» — наблюдатели видят их, отметка «прочитано» идёт по User |
| **Drafts / черновики** | По userId | Per-user — но это write-операция, у `demo_observer` блокируется через DemoObserverGuard. Если для UX важны черновики «текста запроса» — храним в localStorage |
| **Probe-вопросы** (опросы AI-агента к user'у) | Заточены на конкретного Person'а в Org | На эталоне probe-event'ы НЕ инициируются для `demo_observer` (один из узлов фильтрации в воркере) — иначе ИИ будет «допрашивать» наблюдателей-гостей |

**Рекомендация:** провести аудит таблиц по столбцу «scoped по userId или по personId» и убедиться, что для `demo_observer` всё корректно. В частности:
- Probe-events / check-ins / задачи назначенные на demo-сотрудников — НЕ должны автоматически назначаться на наблюдателя.
- Концерж-чат, tour-progress, чтение уведомлений — per-user, работают.

Это рутинный аудит ~2-3 часа работы в ТЗ.

### Развилка 13. Доставка демо-данных в эталонную Org (как заливаем)

**Варианты:**

| Вариант | Описание | Pro | Contra |
|---|---|---|---|
| **A. CLI-скрипт `seed-demo-workspace.ts`, запускается один раз при выкатке нового контента** | Прогон через `docker compose exec backend bun run scripts/seed-demo-workspace.ts --org-id=DEMO_ORG_ID` | Прозрачно, контролируемо. Owner вручную решает «обновить эталон». Скрипт уже существует и работает. Идемпотентен через `Org.demoWorkspaceSeededAt` | Нужно помнить запустить при добавлении новых seed-модулей |
| B. На старте backend'а автоматически | `OnStart`: если `DEMO_ORG_ID` пустая — засеять | Не забудешь | Опасно: случайная пересейка стирает обновлённые cron-агентами snapshot'ы. Дублирующиеся запуски при scale-out |
| C. CronCreate: раз в месяц | Регулярное обновление | Свежий контент | Зачем? Контент в seed-функциях меняется только при добавлении новых модулей |

**Рекомендация: A.**

**Доказательство:** B — опасно, гонки на старте подов. C — overkill. A — контролируемо, как любая prod-операция. Skрипт регистрируется в `apply-prod-deploy.ts` (см. CLAUDE.md), при добавлении нового seed-модуля — отдельный шаг в `prod-deploy-log.md`.

**Идемпотентность:** скрипт смотрит на `Org.demoWorkspaceSeededAt`. Если стоит — упало бы с `demo_already_seeded`. Чтобы поддерживать «обновление эталона», добавляем флаг `--force-update` который: (a) проверяет, что Org помечена `isReferenceDemo=true`, (b) делает `resetDemoWorkspace` внутри транзакции, (c) сидит заново. Это безопасный путь для обновления контента.

### Развилка 14. Что делать с existing «копиями ТехноСтрим» у пользователей на проде

**Контекст:** на проде есть N Org-ов, у которых `demoWorkspaceSeededAt != null` — это копии «ТехноСтрим», засеянные старой моделью.

**Варианты:**

| Вариант | Описание | Pro | Contra |
|---|---|---|---|
| **A. Patch-скрипт: для каждой такой Org вызвать `resetDemoWorkspace`, затем создать `OrgMember(owner, DEMO_ORG, demo_observer)`** | Чистим копии, добавляем доступ к эталону | Чистая БД, единая модель | Удаляем то, что пользователь видел; если он успел «привязаться» к псевдо-данным — потеряет |
| B. Оставить копии как есть, новых пользователей подключать к эталону | Гибрид | Меньше изменений | Два режима демо в проде, поддержка хуже |
| C. Конвертировать копии в собственные данные (снять `externalSource='demo'`) | Каждая копия становится «реальной» Org пользователя | Никто ничего не теряет | Каждый пользователь становится владельцем компании «ТехноСтрим» с сотрудниками Морозов/Волкова — это бред |

**Рекомендация: A.**

**Доказательство:**
- Текущие «копии демо» — это **техническая фикция**, не данные клиента. Никто не привязался к Алексею Морозову как к своему сотруднику.
- B оставляет двойной режим — поддержка превращается в ад.
- C — бред (см. contra).
- A — patch-скрипт `patch-migrate-old-demo-orgs.ts`:
  1. Найти все Org где `demoWorkspaceSeededAt != null`.
  2. Для каждой: получить ownerUserId, проверить, что нет реальных данных (e.g., `Meeting.count where externalSource IS NULL`). Если есть реальные — **не трогать**, оставить.
  3. Запустить `resetDemoWorkspace` (удалит всё с `externalSource='demo'`).
  4. Создать `OrgMember(ownerUserId, DEMO_ORG_ID, role='demo_observer')`.
  5. Залогировать в audit.
- Скрипт идемпотентен (повторный запуск ничего не сломает: если демо уже сброшено, шаг 3 — no-op).

### Развилка 15. Что если super-admin хочет создать «свой» демо-кабинет для презентации клиенту

**Кейс:** super-admin хочет показать гипотетическому клиенту демо «как будет в его отрасли» — с переименованными сотрудниками, другой нишей.

**Варианты:**

A. **Не поддерживаем — все смотрят shared эталон.**
B. Возвращаем кнопку «Создать копию эталона» в `/admin/demo` для отдельных случаев.
C. Делаем «вторичные эталоны» (например, отдельный «эталон для FinTech», «эталон для производства»).

**Рекомендация: A** на первый шаг. C — отдельным ТЗ позже, если будет реальная потребность.

**Доказательство:** B — тот же самый «копирование на каждую Org», только триггер вручную. Возвращает все боли текущей модели. A — простая, монолитная. Если когда-то понадобится — закроем через C, не B.

- Не трогаем `SubscriptionGuard`, `PaywallBanner`, `PaywallModal`, `SubscriptionContext` — они работают со статусом подписки, всё остаётся валидным для своей Org пользователя.

- Не реализуем `2026-05-31-demo-auto-seed-and-cleanup.md` — он становится не нужным (нечего сидить и нечего чистить per-user).

## 6. Итоговая рекомендуемая модель — сводка

1. **Эталонная Org `cmp_demo_technostream`** в БД. Помечена `isReferenceDemo=true`. `Subscription.status=ACTIVE`, `paymentMode='reference'`.

## 10. Аргумент в одну строку

Текущая модель решает «как сделать, чтобы у нового пользователя были демо-данные» через копирование. Правильное решение — не копировать, а показывать. Shared demo Org — это просто ещё один тенант в multi-tenant системе, что естественно вписывается в архитектуру Z и не требует ни одной строки специальной логики на уровне данных.
