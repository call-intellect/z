# ТЗ — «Второй мозг по 12 веткам» (second-brain-by-branches)

**Принцип.** Надстройка-навигация над уже существующим знанием: 12 областей компании становятся картой, под каждой — её темы + регламенты + процессы + документы + решения, собранные из существующих связей. **v1 — read-only, без миграции БД и без переноса данных** (витрина поверх существующих разделов, не копия). Живая страница темы ([[living-topic-space]]) — лист, куда проваливаешься.

## Вне scope / отложено владельцем (vNext)
- **Хранение `branch` на регламенте/процессе/решении + классификатор-дозаполнение** — vNext (v1 деривит ветку из связей; неотнесённое → «Не отнесено»). Триггер материализации: если доля «Не отнесено» на реальных данных высока ИЛИ read-time агрегация тормозит при >~5000 сущностей.
- **Переименование/скрытие 12 областей владельцем** — vNext (v1 фиксированы как в `enum ThemeBranch`).
- **Глубокая аналитика/пульс области для руководителя** — vNext (v1 — только сигнал-светофор на плитке).
- **Перенос/удаление разделов** `/regulations` `/processes` `/documents` — не трогаем; карта — надстройка над ними.

## Цель + Зачем
Знание компании собрано, но разложено по 7 разделам и плоско (см. [[../analysis/2026-07-02-second-brain-by-branches]]); нет верхнеуровневой структуры «карта компании». Даём единый вход «второй мозг» по 12 областям: руководитель окидывает компанию за 30 сек, менеджер видит всё по своей области вместе, новичок понимает структуру с одного экрана. Отстройка: у нас 12 областей уже зашиты и всё связано графом — конкуренты этого не собирают.

## REALITY-CHECK (факт по коду 2026-07-02)
- **12 областей заложены:** `enum ThemeBranch` [schema.prisma:834] = strategy, clients, sales, marketing, product, operations, team, finance, technology, production, partnerships, legal. `Theme.branch` проставляет LLM.
- **Ветка сейчас = только фильтр:** [ThemesClient.tsx:35] `BRANCH_OPTIONS`; список тем фильтруется по ветке (`ListThemesQuerySchema.branch` [theme.dto.ts:8]).
- **Хаб «Память» плоский:** [memory/page.tsx] — плитки Решения/Оцифровано/Темы/Сущности/Таблицы/Идеи/Сигналы + `/chat`.
- **Связи для деривации ветки УЖЕ есть:**
  - `Theme.branch` — прямая.
  - `Document.attachedThemeId` [schema:5309] → тема → ветка (прямая).
  - `Regulation.entityId` [schema:6145] (unique), `Instruction.entityId` [schema:6208], `Process.entityId` [schema:5850] → сущность → `ThemeEntity(themeId)` [schema:4456] → `Theme.branch`.
  - `Decision.entityId`/`Decision.affectsEntityIds[]` [schema:6402/6421] → сущность → `ThemeEntity` → `Theme.branch`.
- **Контроллеры-соседи (переиспользуем для ссылок, НЕ переписываем):** `KnowledgeThemesController` (`/api/v1/knowledge/themes`), `RegulationsController` (`regulations.controller.ts`), `ProcessesController` (`/api/v1/processes`), `DocumentsController` (`/api/v1/documents`).
- **Схема БД в v1 НЕ меняется** — фича read-only агрегация. (Отличие от [[living-topic-space]], где была миграция.)
- **Личные темы** (`Theme.origin=user, visibility=personal` — вводится в living-topic-space) видны только автору → карта обязана это учитывать при подсчёте/показе.

## Доказательство выбора (2 прохода + challenge-loop)
**Развилка: деривить ветку read-time vs хранить колонкой.**
| Критерий | A: read-time деривация из связей (выбрано, v1) | B: колонка `branch` на Regulation/Process/Decision + классификатор |
|---|---|---|
| Дешевизна старта | ✓ ноль миграции, ноль LLM | ✗ миграция + LLM-классификация всех регламентов/процессов |
| Полнота карты | средняя (без темы → «Не отнесено») | высокая |
| Рассинхрон | ✓ нет второго источника правды | ✗ колонка может протухнуть при переклассификации темы |
| Масштаб | ok на SMB (десятки-сотни сущностей); риск на десятках тысяч | ✓ индекс |
**Вывод:** A на v1 (SMB-масштаб, скорость, без миграции), B — vNext с числовым триггером (доля «Не отнесено» высока ИЛИ >~5000 сущностей на Org). **Challenge-loop:** (1) корень — «нет структуры компании», решаем картой, а не ещё одним реестром; (2) эффективность — не плодим миграцию/LLM ради навигации; (3) не код ради кода — переиспользуем существующие списки регламентов/тем ссылками, не дублируем.

**Развилка: новый раздел vs эволюция «Памяти».** Эволюция «Памяти» (Р3) — не плодим разброс, который и чиним; карта = главный вид, реестры → вкладка.

## Scope
**Входит:** сервис деривации ветки; агрегация «карта 12 областей» (счётчики тем/регламентов/процессов/документов/решений + сигнал + «Не отнесено»); эндпоинт детали области (сборка секций); эволюция хаба «Память» (карта — главная, реестры — вкладка «Все реестры»); экран области со ссылками в существующие разделы; учёт личных тем в подсчёте/показе.
**Не входит:** см. «Вне scope».

## Граничные контракты
- **Списки внутри области** (регламенты/процессы/документы/решения) — либо переиспользуют существующие list-сервисы этих модулей с фильтром по производному множеству id, либо агрегируются read-only в новом сервисе; **логику этих модулей не переписывать** (перечитать актуальные `regulations.controller.ts`/`processes.controller.ts`/`documents.controller.ts` перед реализацией).
- **`Theme.branch`/личные темы** — из [[living-topic-space]] (origin/visibility). Если living-topic-space ещё не смержен — карта работает и без личных тем (все темы = auto/team); учёт `visibility` включить, когда поле есть (условно). Пометить `[ASSUMPTION: visibility учитывается при наличии поля Theme.visibility]`.

### Эндпоинты (Ф2) — новый `KnowledgeBranchesController` (`api/v1/knowledge/branches`), guards как у тем (`CookieAuthGuard, TenantGuard`, `@RequireEntitlement('feature.theme')`, `rbac.canRead(user.id, tenantId, 'theme')`)

export interface BranchTileDto {
  branch: string;                       // 'clients' | ... | 'unassigned'
  label: string;                        // русский ярлык
  counts: { themes: number; regulations: number; processes: number; documents: number; decisions: number };

}
export interface BranchesMapDto { tiles: BranchTileDto[]; }   // 12 веток + 'unassigned' при counts>0

// GET /api/v1/knowledge/branches/:branch — деталь области
export const BranchParamSchema = z.object({
  branch: z.enum([...THEME_BRANCH_VALUES, 'unassigned']),

export interface BranchDetailDto {
  branch: string; label: string; summary: string;   // 1-2 строки «где мы по области» (из summary тем)
  themes: ThemeItemDto[];
  regulations: { id: string; title: string; category: string; href: string }[];
  processes:   { id: string; name: string; href: string }[];
  documents:   { id: string; title: string; href: string }[];
  decisions:   { id: string; statement: string; reversibility: string | null; href: string }[];

Коды ошибок: `tenant_required`, `forbidden`, `unknown_branch`. `href` ведёт в существующий раздел (ссылка, не копия — Р2).

### Сервис деривации (Ф1) — `branch-derivation.service` (knowledge-core)
- `deriveBranchForEntityIds(tenantId, entityIds[]) → Map<entityId, ThemeBranch|null>`: join `ThemeEntity`→`Theme` по `entityId`, вернуть `theme.branch` (при нескольких темах — с максимальным `weight`); нет темы/ветки → null.
- `branchForRegulation/Process/Decision` = дерайв по `entityId` (+ для Decision по `affectsEntityIds`); `branchForDocument` = `attachedThemeId`→`theme.branch`.
- Агрегация карты — групповыми SQL-запросами (не N+1): счётчики per branch + бакет `unassigned` для сущностей без ветки. `tenantId` во всех запросах.
- **Сигнал области (В3):** `red` если есть тема области со `status`/`dynamic` риска (напр. `dynamic=declining` или наличие red-сигнала), иначе `yellow` при `dynamic=stable` с открытыми обязательствами, иначе `green`. Точную формулу задать как чистую функцию + unit-тест; порог — крутилка `branches.signal.*` при необходимости (не хардкод магии).

### AdminSetting (при необходимости) — реестр `admin-setting-schema-registry.ts`
Если появятся пороги сигнала — регистрировать `['branches.signal.<...>', ...]` (через `getDynamic`, code-fallback). Магические числа сигнала в коде — запрещены (принцип №9).

### Ф1 — Сервис деривации ветки + агрегация [x]
**Ценность:** как система знаний, получаю единый способ отнести регламент/процесс/документ/решение к области и посчитать наполнение, чтобы карта и деталь стояли на одной логике.
**Что входит:** `branch-derivation.service` (дерайв через `ThemeEntity`→`Theme.branch` и `attachedThemeId`; бакет `unassigned`); групповая агрегация счётчиков per branch; чистая функция сигнала области + порог-крутилки при наличии.
**Что НЕ входит:** HTTP (Ф2), UI (Ф3/Ф4), любое изменение схемы.
**Файлы:** новый сервис в `backend/src/modules/knowledge-core/services/`; читать `ThemeEntity`/`Theme`/`Regulation`/`Process`/`Document`/`Decision` (перечитать модели перед запросами).
**Acceptance:** unit-тесты на синтетике «Стрела»: регламент со связью через сущность темы «Клиенты» → ветка `clients`; регламент без темы → `unassigned`; счётчики per branch суммируются верно; сигнал области = чистая функция (тест на green/yellow/red); все запросы tenant-scoped (нет утечки между Org). `bunx vitest run` зелёный.
**Закрывает:** R3, R7.

### Ф2 — API карты и детали области [x]
**Ценность:** как фронт, получаю карту 12 областей и деталь области, чтобы построить экраны «второго мозга».
**Что входит:** `KnowledgeBranchesController` с `GET /branches` (карта) и `GET /branches/:branch` (деталь); DTO из «Контрактов»; Swagger; коды ошибок; учёт личных тем (`visibility`) при подсчёте/показе (условно — см. граничный контракт).
**Что НЕ входит:** frontend.

**Acceptance:** Swagger `/api/docs` показывает `/knowledge/branches` и `/knowledge/branches/:branch`; `GET /branches` возвращает 12 плиток + `unassigned` при наличии, с корректными счётчиками; `GET /branches/clients` возвращает темы(branch=clients) + деривированные регламенты/процессы/документы/решения + `summary`; неизвестная ветка → 400 `unknown_branch`; личная тема user A не попадает в счётчики/деталь для user B (негативный тест). Интеграционные spec зелёные; `typecheck && lint && build` зелёные.
**Закрывает:** R1, R2, R6.

### Ф3 — Эволюция хаба «Память» в карту [x]
**Ценность:** как руководитель, открываю «Второй мозг» и вижу компанию по 12 областям за 30 сек, а прежние реестры остаются под вкладкой.
**Что входит:** слой `ApiDto→DomainModel→UiModel` (`frontend/src/api/branches.api.ts`, `frontend/src/domain/branch.ts`); карта 12 плиток (счётчики + сигнал + «Не отнесено») как главный вид `/memory`; прежние плитки — вкладка «Все реестры»; состояния пусто/загрузка/ошибка; UI по-русски, парные токены.
**Что НЕ входит:** экран области (Ф4).
**Файлы:** `frontend/app/(authenticated)/memory/page.tsx` (перечитать; вынести прежние плитки в таб), новый `BranchMapClient`.
**Acceptance:** `/memory` по умолчанию показывает карту 12 областей с числами и сигналом; вкладка «Все реестры» показывает прежние плитки без регрессии; клик по области ведёт на её экран; `typecheck && lint && build` зелёные; `test:unit` по карте зелёный; playwright-скриншот карты.
**Закрывает:** R4.

### Ф4 — Экран области (всё знание вместе) [x]
**Ценность:** как менеджер, проваливаюсь в свою область и вижу всё по ней (темы + регламенты + процессы + документы + решения) в одном месте со ссылками в разделы.
**Что входит:** `BranchDetailClient` (секции Темы/Регламенты/Процессы/Документы/Решения + краткая суть области); каждая карточка — ссылка в свой раздел (тема → живая страница темы; регламент → `/regulations/...`; и т.д.); состояния.
**Что НЕ входит:** редактирование сущностей здесь (только показ+ссылка); пульс/аналитика области (vNext).
**Файлы:** `frontend/app/(authenticated)/memory/[branch]/…` (новый роут) + `BranchDetailClient`.
**Acceptance:** экран `Клиенты` показывает темы(clients) + деривированные регламенты/процессы/документы/решения; клик по теме → живая страница темы; клик по регламенту → раздел регламентов; «Не отнесено» доступно с карты; `typecheck && lint && build` зелёные; playwright-скриншот экрана области.
**Закрывает:** R2, R5.

## Требования (трассировка)
- **R1** Когда пользователь открывает «Второй мозг», система shall вернуть 12 областей со счётчиками (темы/регламенты/процессы/документы/решения) и сигналом, tenant-scoped.
- **R2** Когда пользователь открывает область, система shall собрать её темы + деривированные регламенты/процессы/документы/решения + краткую суть, показывая ссылки (не копии).
- **R3** Система shall деривить область регламента/процесса/решения через сущность→тема→ветка, документа — через `attachedThemeId`; неотнесённое → «Не отнесено».
- **R4** Система shall сделать карту главным видом «Памяти», сохранив прежние реестры вкладкой «Все реестры» без переноса данных.
- **R5** Карточки в области shall ссылаться в существующие разделы, не дублируя данные.
- **R6** Если тема личная (`visibility=personal`), then она учитывается/показывается только автору (в рамках Org).
- **R7** Система shall показывать сигнал области (🟢/🟡/🔴) как детерминированную функцию от тем области.
